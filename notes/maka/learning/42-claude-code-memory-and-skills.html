第 42 章｜Claude Code：记忆、规则与 Skills

本章概览

核心问题：默认偏好、当前例外与可复用方法，怎样在 Claude Code 中保存并用于恰当任务？

关键概念：CLAUDE.md：人工持续指令；auto memory（自动记忆）：后续任务可用的记录；索引：常驻的主题线索；作用域：规则适用对象；Skill（技能说明包）：按需方法；Skill 独立上下文：以正文和参数驱动子任务。

关系主线：持续规则与记忆提供背景，索引引导读取细节，当前要求决定本次例外；方法装载、独立执行与工具预批准各有不同寿命和边界。

所属主题：第 1–5 节对应 第36章 Memory，第 6 节起对应 Skills 与 第39章 协作。

前置：第20章 Memory、第23章 Skills 与 Subagents、第33章的权限边界。

1. 从“记住了”拆出四个问题

延续扫描器任务。用户先说：“这个仓库的报告用中文。”后来又说：“这次给外部协作者的报告用英文，代码注释规则不变。”一次会话里两句话都在，模型仍可能套错；换会话后，还多了是否保存和是否读入的问题。

跨会话使用涉及信息范围、持久化决定、读取入口与冲突处理。一个 MEMORY.md 文件的存在，只能证明存储载体存在。

Claude Code 官方把人工维护的 CLAUDE.md 与 auto memory 分开。前者表达持续指令，后者保存有助后续任务的记录；两者作为模型背景使用，不构成硬权限。auto memory 用自己的 MEMORY.md 索引和主题文件组织；与 Maka 的文件同名，但各自管理文件与读取规则。Claude Code 的 auto memory 当前默认仓库范围内共享，机器之间不自动共享；启动读索引前 200 行或 25KB，以先到者为限，主题文件按需读。

这些文件规则没有公开向量库、语义去重或原子写入协议，不能据此补出对应实现。

2. 四种经常被叫作“记忆”的东西

表 1 / Table 1 · 2. 四种经常被叫作“记忆”的东西
对象服务哪个时间尺度主要内容变化后影响什么
人工项目指令（Project Instructions）多次任务持续规则、默认约定后续任务的背景与行为倾向
自动记忆（Auto Memory）后续会话有价值的偏好、修正与项目背景后续任务可能取回的材料
压缩材料（Compaction）当前长任务已做、待做、约束、关键观察下一次请求怎样继续
文件检查点（Checkpoint）某次编辑前后可追踪文件状态哪些代码变化可以恢复

表里最后一项不是用来教模型用户偏好的，前三项也不是文件回滚器。后续恢复案例沿不同对象解释这个差别。

对于扫描器题目，可以这样分配材料：

  • “项目测试入口是文档规定的检查流程”可作为简短项目规则，但命令是否仍有效要查当前项目。
  • “本仓库报告默认中文”是有作用域的表达习惯；本次英文要求是当前例外，不能悄悄升级成所有未来报告都英文。
  • “链接检查报告的固定步骤”适合按需装载的 Skill。
  • “已修实现，空格路径用例尚未复测”属于当前任务连续性。
  • “编辑前的 scan.py 内容”属于文件恢复数据。

把材料归位的收益不只是省 token。它让修改责任变清晰：改默认规则、纠正一条记忆、替换一个方法和恢复一段代码，是不同操作。

3. 第一张图：写入和使用有两条闭环

其中“判断范围与未来用途”以及“当前请求与相关记忆一起解释”是课程概括的职责，图不意味着宿主对每次语义冲突都有确定性求解器。当前明确要求直接参与当前任务，不必先完成持久化。公开文件机制提供可审查的载体，是否选中正确条目和是否正确应用仍需要检查。

表 2 / Table 2 · 3. 第一张图：写入和使用有两条闭环
步骤本题输入（Input）状态变化（State）可观察输出（Output）

每一行都可能独立失败。保存成功不等于下次索引可见；索引可见不等于读了详细文件；读过也不等于推理时选择正确。

4. 正常案例：三次会话怎样避免扩大偏好

会话 A：建立默认。 用户说本仓库报告使用中文。教学上先明确它的对象是“报告”，范围是“当前仓库”，有效期是持续默认。它不涉及测试数据、代码注释，也不自动适用于所有仓库。

会话 B：出现局部例外。 用户要向外部协作者交付本次英文报告。模型应按当前请求输出英文，但后续记忆整理应避免把这次例外写成全局偏好。如果有必要保存项目背景，可以保留“本次交付对象和语言”的有限事实，并明确后续应重新确认。

会话 C：没有重述语言。 用户只说“生成最新检查报告”。此时才需要检验默认是否真正发挥作用。若当前会话没有其他语言线索，读取相关偏好后采用中文，才构成一条完整的使用轨迹。

但“输出中文”仍不能单独证明来自 Memory。系统指令、界面语言、用户本次中文输入都可能解释这个结果。因此验证应控制其他来源，检查读入材料，并加入移除该条目的对照。Memory 的评价对象不是某次输出看起来合理，而是在需要旧背景时是否正确使用、在不适用时是否克制。

5. 容量与冲突：写进文件仍可能丢在入口之外

索引的作用是把少量线索常驻，让详细材料按需出现。同一文件机制下，两种失误会产生不同后果。

失误一：索引写成了一本手册。 前面全是详细步骤，关键例外放在很后面。即使文件完整保存，启动装载边界也可能使后半部分不进入模型。参考处理是每条索引只表达主题、适用条件和条目位置；长过程移到 Skill 或详细文件。

失误二：两个条目同时自称默认。 旧条目说报告中文，新条目说报告英文，却都没有范围和条件。即使全部读进来，模型也缺少正确选择的依据。改法不是增加更多形容词，而是纠正对象、作用域和例外条件，移除已经无效的冲突内容。

下面是课程自拟的完整记忆内容，不是 Claude Code 强制 schema：

subject: 扫描器报告的语言
scope: 当前仓库的日常检查报告
default: 中文
exception: 当前用户明确指定其他语言时按本次要求
does_not_apply_to:
  - 代码注释
  - 测试 fixture 中的原始字符串
review_when: 团队报告规范发生变化

does_not_apply_to 用反例限制过度泛化，review_when 表达失效条件。简单偏好可以使用更少字段，只要仍能区分适用范围与失效条件。

6. Skill 解决的是方法复用

项目规则“提交前运行检查”还没有告诉模型如何检查链接、怎样理解失败、如何组织报告。Skill 可以装载一套相关方法。官方扩展概览把常驻指令、按需方法、外部能力和独立任务分成不同功能；组合时仍应围绕实际任务需求。

一个好 Skill 的首要产物是可完成的任务，而非工具名清单。对于扫描器，步骤可以是确定输入目录，找到验证入口，执行相关检查，分类无效链接和不可访问对象，给出带范围的报告。若用户只问一个函数含义，整套检查流程可能无需调用。

当模型可见许多 Skill 时，名称和描述承担发现作用；正文承担执行方法。描述太泛会误触发，描述漏掉常用说法会漏触发。可以用几条正反例评估：修坏链接应命中，解释 Python 列表不应命中，用户明确调用时应有清晰任务输入。

7. 第二张图：装载方法与分出上下文是两个选择

Skill 的 context: fork 在独立子上下文执行，不能按“复制完整父对话”的 conversation fork 理解。当前 Skills 文档还明确：allowed-tools 是调用 turn 的预批准，下一条用户消息后结束，不是工具白名单；Skill 内容与这份临时许可的寿命不同。

这带来一个具体的陷阱：一份 Skill 写“只读审查”，同时配置了广泛的 allowed-tools。自然语言方法不能自动限制实际工具，预批准也不能证明仅允许只读。方法内容、可调用工具集合和权限规则必须分别审查。

8. 只读调查 Skill 的完整参考定义

下面是采用公开字段的教学示例。它用于只读调查；agent: Explore 的工具能力由产品定义，正文仍显式重述本题必须到达子任务的限制。

---
name: inspect-link-checker
description: 调查指定目录的 Markdown 链接检查流程，返回检查入口和潜在失败原因
disable-model-invocation: true
context: fork
agent: Explore
---

调查 $ARGUMENTS。

任务限制：只读取文件，不修改，不上传项目内容。
1. 找到扫描器入口和测试配置。
2. 确认含空格目录如何穿过参数边界。
3. 区分已读代码事实与需要实际运行才能确认的假设。
4. 返回：入口、参数流、可疑位置、建议检查、未完成项。
若找不到目标目录，明确返回缺失信息。

任务参数提供调查对象；正文说明产物；失败分支允许返回缺失；必要限制写在子任务实际收到的正文里。仅写“遵守上面讨论的要求”会依赖它未必拥有的父对话。

disable-model-invocation: true 使本例偏向用户明确调用的方法。若改为自动发现，描述就要足够区分相邻任务，并增加误触发评估。是否后台执行、怎样控制完成顺序，则属于下一课的委派设计。

9. 三个工程反例

反例一：压缩后记得偏好，却忘了测试失败细节。 不矛盾。持久背景和当前任务摘要走不同链，能读到前者不证明后者完整。应重取关键错误，不能用正确语言风格掩盖功能状态未知。

反例二：主任务用了一个 Skill，子任务却不知道那套规则。 独立子任务的初始化不等于主任务当前输入。必须检查它依据的是单独提供的任务说明（brief）、父对话分叉（conversation fork），还是 Skill 自己驱动的上下文，并传入必要方法。已装载过不等于所有后代都继承；这几种初始化方式在下一章展开。

反例三：两个 worktree 同时修改相同记忆主题。 文件工作区隔离不保证长期背景也隔离。公开的文件式记忆接口本身不说明并发冲突如何解决。参考方案让同一主题由一个写入 owner 提交，以旧版本作为更新前提；发生冲突时保留两方意图并重新核对适用范围。这是额外设计，不能声称某个 worktree 的代码隔离或公开文件接口已经实现了它。

这些条件的参考结果可以逐项区分：换到不适用仓库后，旧偏好不应作为有效默认；删除条目后，后续索引即使仍有线索，也不能把读取失败当成正文；当前明确改用英文时，本次输出采用英文而不自动改长期默认；压缩丢失失败细节时，需要回读任务记录；委派时遗漏规则，则应补到子任务实际收到的输入中。这些是设计判定，尚未形成该产品的新增运行轨迹。

10. 取舍：何时放常驻，何时按需

表 3 / Table 3 · 10. 取舍：何时放常驻，何时按需
内容选择收益代价判断问题
常驻项目规则（Project Rules）每次任务容易获得关键约定长文件争夺注意力和预算它是否几乎每次都需要？
索引与详细记忆（Index · Memory）可审查，低成本暴露线索选条目和读条目可能失败描述是否足以发现正确例外？
技能按需装载（Skill Loading）方法可复用，可独立迭代发现与触发需要评价它是否定义了清楚任务与产物？
独立上下文执行技能（Skill Context）调查噪声留在子任务缺失父背景、结果需整合能否写出自足 brief？

Maka 与 Claude Code 都需要在常驻成本和按需漏读之间取舍，但使用 Markdown 并不意味着两者具有相同的 scope、读取顺序或权限语义。

11. 常见场景与完整参考结论

题一：CLAUDE.md、auto memory、compaction、checkpoint 分别回答什么？

参考答案：CLAUDE.md 提供人工持续指导；auto memory 提供后续任务可能用到的记录；compaction 组织当前长任务的输入；checkpoint 追踪特定文件恢复状态。它们有不同对象与生命周期，不能通过一条“保存”箭头互相替代。

题二：索引写入成功，为什么新会话仍没用到条目？

参考答案：依次检查内容是否在启动读取范围、索引描述是否相关、详细条目是否被读取、当前任务是否覆盖旧偏好、最终推理是否正确。不要只重复写入；先定位哪一环断了。

题三：把手册拆成许多被 CLAUDE.md 导入的文件，就能省上下文吗？

参考答案：文件组织和装载策略是两件事。若仍在启动时展开所有内容，拆文件主要改善维护。要减少常驻成本，应选择按任务或路径装载，并验证需要时能被找到。不能只按磁盘文件数判断请求大小。

题四：Skill 的 allowed-tools 为何不是安全白名单？

参考答案：该字段表达临时预批准，未列出的工具仍受其正常权限规则控制，而非因此不存在。需要限制能力时，应使用真正的工具限制与权限机制；方法正文只是另外一层指导。

题五：独立 Skill 只写“按前文分析”，会怎样？

参考答案：它可能没有前文，只收到含糊任务。应提供明确对象、必要背景、限制和交付标准；若确实依赖完整历史，评估其他上下文模式，不要误读 context: fork 的含义。

用户要把报告默认从中文改为英文，怎样区别于本次例外？

参考答案：当前措辞明确要求改变默认，因此先定位旧默认范围，再更新或撤销旧条目，避免两条并存。后续新会话没有重述语言时，参考输入应包含英文默认，参考输出为英文报告；只有实际读取与输出记录才能证明这一链发生过。已有历史报告无需无关改写。

按产品连续复盘时可读：子任务、回收与恢复。记忆与方法的更多场景见 第55章与 第57章。
