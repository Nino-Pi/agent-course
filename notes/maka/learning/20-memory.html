第 20 章｜记忆的写入、读取与更新

本章概览

核心问题：“以后用中文解释”怎样从当前要求变成未来任务可用、可更正的信息？

关键概念：Memory（记忆）保存可复用信息；scope（范围）限定适用对象；Local Memory（本地记忆）通过读取门进入输入；CAS（原子比较并更新）仅在版本匹配时接受写入；Atomic LTM（结构化长期记忆）已有写入与查询基础。

关系主线：写入、持久化、选择、输入组装与实际采用是不同步骤。更正要处理旧规则和并发版本；同 Turn 已捕获正文不会自动撤回，Atomic 查询也不等于已接通自动召回。

贯穿案例中，用户在修复 formatDuration(seconds)、运行测试并更新 README 时补充：“以后请用中文解释结果。”当前模型输入与历史压缩分别见 第15章和 第19章。

核心阅读：一条偏好，四个不同的动作

1. 当前能用中文，还不需要长期记忆

用户刚刚说过中文要求，它就在本次模型输入中。本轮输出中文可以说明回答符合这项当前要求，却不能证明已经保存长期记忆。模型回复“我记住了”也只是生成了一句话。

困难出现在新会话：新输入只有“解释这次测试结果”，没有旧偏好。要再次使用那条信息，系统必须在当前对话之外保留它，并建立后续读取和使用的路径。这里讨论的是 Agent 的外部记忆机制，不讨论改变模型权重的训练。

若旧对话不再进入输入，又没有保存偏好，这条路径就无法为新请求提供中文要求；偶然输出中文也不构成记忆生效的证据。

2. 最小闭环不要求先建复杂数据库

先采用一个限定设计：用户显式保存一条偏好，程序串行执行，只有一个使用者。一个可读取的文件就能承担存储。

旧会话中的明确要求是“以后用中文”，新会话只说“解释这次测试结果”。下图的两个外框分开这两次会话，存储连接它们；最后的核对还需实际模型回答，不能从写入成功直接跳到记忆生效。

文件、JSON、数据库是表示和存储选择。版本号、幂等 receipt、向量索引分别解决进一步的更新、重试和检索问题，不属于上述最小闭环必需的固定字段。

下面是教学伪代码，不是 Maka API，也未单独执行：

# 旧会话：用户显式要求保存
save_preference("解释结果时使用中文")

# 新会话：当前请求没有重复语言偏好
background = read_relevant_preference(current_task)
model_input = compose(current_task, background)

此处尚未证明模型实际遵守了偏好。伪代码最后只组好了请求；只有调用模型并检查回答，才能继续判断使用效果。可以沿同一条证据线逐项核对：

存储里有这条信息 → 本任务实际取回了它 → 它确实进入本次输入 → 回答按适用条件使用了它

任何一个箭头都需要自己的接线或观察。数据库提供查询函数，不代表 Agent 调用了它；内容进入输入，也不代表模型一定遵循。四步闭环中的“用”既要检查输入组装，也要检查最终行为。

3. 每出现一个新问题，再增加一种机制

现在用户说：“工作区 A 用英文，其他项目仍用中文。”这不一定推翻全局偏好，而可能增加一个局部例外。只按字符串相似度选旧信息无法判断适用范围。

记忆还可能过期或含有不可信指令。它可以提供任务背景，不能因为保存得久就获得授予文件、网络权限的权力。若当前用户说“这次发布说明用英文”，不能拿旧中文偏好压过这次明确要求；但这次例外也不自动授权永久覆盖旧偏好。本次怎么用、长期怎么改、实际能执行什么是三个需要分别作出的判断。

真实补例：条目没删，为什么新会话不再用那个格式

第22章 的 Local Memory 小对照保存“已修改／已验证／待处理”三段报告格式，然后让两个新 Session 完成相同的只读测试任务。开启读取时，实际请求含有这条偏好，回答使用这三个标题；关闭读取后，条目仍在，实际请求不再包含它，回答变为普通的结果摘要和失败说明。

这个对照把同一条存储内容、两份输入和两次回答关联起来。保存由原生管理接口完成，展示的是 Local Memory；不是模型凭一句“记住了”写入，也不是 Atomic recall 实验。两边都用中文提问，所以不拿中文回答本身作为记忆证据。

保存、读取与使用问答

问题 1。 旧会话回答中文、并说“记住了”，为什么不足以证明 Memory？

解释。 当前输入本来就包含要求；模型承诺也未提供独立的写入和读取证据。必须在旧输入消失后继续检查保存、查询和组装。

问题 2。 用一个文件实现上述最小闭环，是否必须先添加 version、receipt 与向量索引？何时才需要讨论它们？

解释。 不必。先用显式保存与顺序读取建立闭环；多写者引出冲突控制，请求重发引出幂等，字面检索不足才引出其他检索方式。

问题 3。 Maka 透明文件已保存但读开关关闭，与 Atomic Store 可查询但缺少 Agent caller，有什么共同点、什么区别？

解释。 两者都不能从“存在已保存内容”推出“进入本次输入”。透明路径已有受开关控制的读取接线；Atomic 目前缺少 Agent-facing recall/injection 消费者，开启透明读取不能补上它。

问题 4。 新会话仍然用中文，怎样排除“当前请求已经再次要求中文”这个替代解释？

解释。 让新请求不携带旧偏好，核对实际背景来源，再做关闭读取或移除记忆的对照。固定格式程序只能验证输入选择，真实模型的行为仍需另测。

问题 5。 旧记忆说“结果解释用中文”，用户这次明确要英文发布说明，应怎样使用和更新记忆？

解释。 本次按明确要求写英文；先把它视为当前任务条件，不自动改掉长期中文偏好。只有依据后续明确的更新意图和适用范围，才决定是否修改存储。记忆也不能改变文件或网络授权。

实现深化：由失败约束理解 Maka 的具体选择

持久更新还会遇到 第18章 的结果未知窗口：写入可能已决定，返回却丢失。以下 S1/T7/R7 是教学身份，用于区分更新提交、重新读取和实际使用。

Maka：透明 MEMORY.md 与 Atomic LTM 是两套系统

路径 A：用户可见的 MEMORY.md

MEMORY.md 是透明 Local Memory 产品面。用户可以查看、编辑和审批内容，它与 PENDING.md 组成一个 revisioned bundle。

显式 remember 可以直接追加已获用户批准的内容；propose / approve / reject 则处理 PENDING 中的提案及审阅状态。因此，保存到 MEMORY 并不要求每次先经过 PENDING。

它有两个独立开关：

enabled            Memory 产品是否启用
agentReadEnabled   Agent 是否可以把 active entries 放进 prompt

当前默认值是：

enabled = true
agentReadEnabled = false

所以“文件里已经保存”并不自动意味着“下次 Agent 会读”。

读取链

开启 Agent 读取后，Host 会：

读取 MEMORY.md / PENDING.md bundle
  → 解析 active entries
  → session 条目精确匹配当前 sessionId；workspace 条目不做项目过滤
  → secret redaction
  → Unicode-safe truncate
  → 作为 <local-memory> untrusted system block 注入

正文超过 12,000 个 JavaScript 字符串长度单位（UTF-16 code units）时，先在不拆开代理对的位置截断，再追加截断提示；Host 随后还会添加标题和 <local-memory> 包装。因此 12,000 是正文截断阈值，不是 token 预算或包装后 prompt 的严格总长上限。Memory 文档另有 128 KiB 上限。两种限制约束不同的对象。

untrusted 是设计重点：Local Memory 可以影响语言和偏好，但不能授予文件、网络或 Host 权限。

写入与崩溃边界

remember / propose / approve / reject / archive / restore 使用 revision CAS：只有预期版本仍匹配时才接受提交。bundle 发布采用：

stage → durable decision → finish publication

如果 durable decision 后结果未知，Host 会标记当前 authority 不再安全并进入排空（poison/drain），而不是猜测重写。这避免两个 Client 或一次重启把已经决定的 Memory bundle 用旧 revision 覆盖。

路径 B：Atomic long-term memory

Atomic LTM 把结构化 MemoryItem 存进独立的 memory.sqlite。它当前不会自动同步到 MEMORY.md。

一条 Item 可包含：

  • itemId 与 optimistic version；
  • kind：preference、identity、context、knowledge、failure、note；
  • statement 与 temporal 类型；
  • global 或显式 workspace scope；
  • active / archived lifecycle；
  • content hash 与时间；
  • exact/entity/concept/alias/code keys；
  • 精确 sessionId / runId / turnId / eventId provenance。

这些字段服务于当前 Maka 的可审计写入设计；向量检索可以是另一条读取轴，两者并不互相替代。

提取 cursor 记录已经覆盖到哪段历史，receipt 保存一次操作的结算回执。原子提交可以用一行具体状态表示：Items=[]，cursor=0，receipt=无。一次提取成功后应成为 Items=[偏好]，cursor=已覆盖位置，receipt=本次结果。commitExtraction 在 BEGIN IMMEDIATE 后检查幂等 receipt 与期望 cursor，把三者放在同一事务里，再 COMMIT。如果 cursor 已写、receipt 未写时抛错，不能留下“已处理但没保存”的半状态；第21章 的 SQLite 故障实验重开后看到三者都回到未提交状态。

COMMIT 后失去返回则相反：实验把子进程杀在 COMMIT 后，新进程读到三者均存在。此时应按 operation identity 查回/重放原结果；直接当失败再造一个新 operation，可能制造重复。相同请求重放得到 replayed=true，key 查询只有一个 Item。这里验证的是存储提交，不是模型是否正确提炼用户偏好。

三种触发

当前设计有三类写侧触发：

  1. memory_remember：用户明确要求记住，foreground 同步返回保存结果；
  2. memory_extract：模型标记 incidental durable info，Turn terminal 后异步提取；
  3. compaction boundary：从 checkpoint 固定的 durable prefix 补做提取。

显式“记住”和后台“发现可能值得记住”是不同意图，不能混成一次无边界扫描。

提取只信稳定用户证据

Atomic LTM 的提取链可以简化为：

stable RuntimeEvent range
  → 检查 cursor / receipt / pending failure
  → 只选 non-partial user-authored text 作为 evidence
  → 模型提出有界候选
  → 必要时在同一 Session 做有界字面定位
  → isolated canonicalization
  → exact quote / secret / scope / schema admission
  → 原子提交 Items + cursor + receipt

assistant 内容只可作为 interpretation context；tool 内容不能成为 evidence/provenance。quote 必须是 provider-visible 用户原文的 exact substring，防止模型虚构“用户曾说过”。

失败和隐私有 durable 语义
  • 同一 coverage range 的 proposal、可选 localization 和 canonicalization 共享有界模型调用预算；
  • background extraction 失败会冻结范围并只重试一次，再失败则原子 discard 并推进 cursor；
  • incognito 或 disabled 可以在 compaction boundary 形成 durable policy denial，避免以后重新开启后追溯提取当时被拒绝的内容；
  • sensitive requested batch 原子结算为空 no-op，不做一半成功、一半失败；
  • subagent 和 archived Session 不参与自动 extraction。

两个 “remember” 名字相近，但不会自动同步

这两个名字很像，但实际写入的是不同存储：

memory.mutate { kind: "remember" }
  → 修改用户可见的 MEMORY.md bundle

Agent tool memory_remember
  → 写入 atomic LTM 的 memory.sqlite

两个路径当前不会自动互相同步。看到日志里有 remember，必须先问“是哪一个 owner、哪一个 store、哪一种读取路径”。

Atomic LTM 已可查询，但 Agent recall 尚未接线

当前 Storage facade 已提供 readItem() 和 searchByKeys()；SQLite 支持 exact/prefix、workspace、archived 和 limit 等有界查询。

但 production Runtime/Host 目前：

  • 没有把查询结果注入 prompt；
  • 没有 memory_recall Agent tool；
  • Composer 没有 Agent-facing atomic LTM recall caller；
  • 没有 embeddings、vector index 或 semantic ANN retrieval；
  • 自动 extraction 主要 create Item，没有成熟的自动 merge/update/semantic dedup；
  • native OpenAI Responses lane 不支持这条 extraction 路径。

因此准确状态是：

Atomic LTM extraction / store     已接写侧
Atomic LTM read / key-query API   Store 层已存在
Agent-facing recall / injection   尚未接线

“数据库查得到”不能简写成“Agent 未来会想起”。

History search、Workspace instructions 和 ArchiveRead 都不是 Memory recall

几个相邻能力容易被误命名为 Memory：

  • SearchHistory 在 Session title 和 StoredMessage 中做有界 substring scan；
  • ReadHistory 根据 hit/message/Turn anchor 读取有界邻域；
  • AGENTS.md 等 workspace instructions 是项目规则，不是对话中学出的事实；
  • ArchiveRead 按引用回读大 tool result，不跨 Session 检索偏好；
  • Compaction checkpoint 缩短旧 History，不负责长期偏好 lifecycle；
  • Read image Context Offload 保存 payload，不做知识提取。

这些入口分别按历史文本、固定引用或长期信息作用域寻找内容，因而有不同的读取条件与失败处理。

Child Session 默认不继承父 Memory

关联子会话（linked child Session）是被委派独立工作的一份会话，第23章会展开它的创建与结果交接。它会自己进行 composition，默认不隐式继承父历史、Local Memory 或 personalization。父 Agent 如果需要 child 用中文，应把这个要求显式写进 child task，而不是假设“同一个用户，所以所有长期信息都自动扩散”。

源码微步：读取开关怎样改变实际输入

HostMemoryCoordinator.readPromptProjection 在读取文件前检查策略。下面两个源码片段之间的分支由文字展开；片段依赖方法上下文，不能独立执行。

      if (
        policy.policy.privacy.incognitoActive ||
        !policy.policy.memory.enabled ||
        !policy.policy.memory.agentReadEnabled
      ) {
        return {
          bundleRevision: null,
          memoryRevision: null,
        };
      }

文件已经存在且 active，但 agentReadEnabled=false 时，这段检查会在 this.#store.read() 前返回，返回值也没有 body。文件没有因此被删除；改变的是本次投影的可用内容。

允许读取后，同一方法先调用 this.#store.read()，再检查 snapshot.memory.kind。只有 document 分支继续解码并构造正文；缺席或 safe_mode 状态不会走到下面的代码。

存储层的 snapshotForBytes 在文档超过 128 KiB 或字节不是有效 UTF-8 时返回 safe_mode。Host 此时可以保留 revision，但不生成正文。可读文档分支则调用 decodeDocument 与 buildLocalMemoryPromptBody：

      const content = decodeDocument(snapshot.memory);
      const body = buildLocalMemoryPromptBody(content, { sessionId });
      return {
        bundleRevision: snapshot.revision,
        memoryRevision: snapshot.memory.revision,
        ...(body ? { body } : {}),
      };

组装器消费投影（Composer）可选 body 与独立的请求组成正文才能被加入本次输入；revision 本身不是 Memory 正文

调用方继续消费这份投影：interactive-run-composer.ts::readPromptState 只在 body 非空时调用 renderMemoryPrompt；resolveSystemPrompt 将这段带 <local-memory> 的 untrusted 文本加入主 Session system prompt，并带上 memory/bundle revisions。execution-model-composition.ts 的 systemPrompt 回调把它交给 AiSdkTurn，后者最终通过 modelAdapter.startStream 的 system 参数传给所选 adapter。revision 不会自动变成正文；数据库中的 Atomic Item 也没有在这条链中被查询。

图中的 Local Memory 路径由新 Turn 首次采集触发，旁边的 bundle 是数据来源。“允许读取”要求产品启用、Agent 读取开启且非 incognito；默认 enabled=true / agentReadEnabled=false 会走“否”。无正文支路仍汇入普通模型请求，关闭的是 Memory 读取。两条虚线分别表示受门控的数据读取和仍需另外核对的使用效果。

“没有正文”可能来自读取被关闭、文档缺席或进入 safe mode，也可能是筛选后为空；不能一概解释成存储被删除。筛选只对 session 条目匹配 Session，workspace 条目没有项目目录过滤。有正文时仍以不可信背景包装，不能授予执行权限。已捕获的同一 Turn 不会随文件更新重采集；后续新 Turn 才重新判断。写入、请求可见与正确使用仍需分别取证。

Atomic 使用另一条存储链： memory.sqlite 已有写入与 Store 查询 API，但所查主执行链尚未接通 Agent 读取与注入。它不自动流入 Local bundle，打开 Local 读取开关也不能补上这段消费链。

在实验中观察同一条链：第21章 Maka 后半节保存真实 bundle 后结束写进程，启动新进程调用同一个 composer。开启读取的 prompt 含偏好；关闭读取没有 <local-memory>，MEMORY.md 字节不变。同一 Turn 已 capture 后再写一条偏好，同 Turn 仍用旧 prompt，下一 Turn 才包含新增内容，因为缓存按 Session/Turn 区分。该实验测到输入组成，未调用模型；不能把 prompt 中有中文偏好就记成模型已遵循中文。

buildLocalMemoryPromptBody 继续检查解析状态与 active entries，只对 session 条目精确匹配 sessionId；workspace 条目没有 cwd/project 过滤，这里也没有按 decayTtlMs 自动排除过期条目。随后才做 secret redaction 与有界截取。解析器 parseLocalMemoryMarkdownRaw 另有大小检查：字符串按 UTF-8 计超过 128 KiB 时，返回 safeMode: true，body builder 不再生成可注入正文。这是输入大小边界，不表示它已经判断内容可信。

若省掉读取门，用户关闭读取的选择将不再由这里执行；若省掉适用范围筛选，其他 Session 的局部内容可能进入当前背景。这两个反例用于推演被省掉的检查会失去什么保证，并非故障实测结果。

连续推演：从 pytest 改成 make check，哪一步才算改好了

把语言偏好换成项目规则：A 原来用 pytest，用户明确更正“以后 A 用 make check，B 仍用 pytest”。难点是让未来任务读到新规则，同时保留 B 的规则，并说清当前正在运行的请求是否已经改变。下面是遵循实际接线的教学推演，不是产品运行记录；条目 ID 和内容均为示例，r0/r1/r2 是三个 revision 的教学标签，不表示接口返回递增数字。

这是测试入口更正迁移到另一项目约束的纸面场景；第04章 四文件 fixture 仍用 npm test，不要求在那里执行 pytest 或 make check。

部署假设是：A、B 使用不同 State Root，各自拥有 Local bundle；State Root 在此是 Host 管理长期控制状态和 bundle 的存储边界，与命令的项目目录、Session 身份分别判断。这不是 Local 自动识别项目的能力。本例 Turn-0 表示已捕获旧正文的一次请求。A 使用 scope=workspace，条目正文写明项目和用户来源；未来读取限定为该 Root 的普通主 Session。Memory 产品已启用、非 incognito，且 Agent 读取已显式开启。用户这次已授权保存更正，所以使用原生管理接口的 remember，不必先制造 PENDING 提案；它不是写 Atomic 的 memory_remember 工具。

这两次操作分别经过 HostMemoryCoordinator.#commitSemantic，每次都按 expectedRevision 提交 bundle。CAS 保护提交顺序，不判断两句话的语义关系。 remember 只追加条目；如果省掉归档，它不会自行发现 E0 已被替代。反过来，归档成功、追加失败会留下暂时没有该规则的状态，必须报告“旧规则已归档，新规则尚未保存”，不能说原子替换已完成。并发冲突时，应重新读取状态再决定后续修改，不能拿旧 revision 盲目继续。

r2 的新内容怎样到达模型？readPromptProjection 先检查读取门，再从 bundle 筛选正文；readPromptState 将其包装，composer 把结果装入主 Session 的 system prompt，最后通过 modelAdapter.startStream 交给模型。composer 按 Session/Turn 缓存已经捕获的材料，因此这里说的是后续新 Turn 的捕获，不是文件一改就推送替换当前请求。归档也不删除历史消息、旧工具结果或已经发生的动作。

最后仍要走到“用”：新任务没有重述命令时，先检查实际输入是否包含 E1，再看 Agent 是否结合当前项目说明选择 make check、读取执行结果并判断验证是否通过。Memory 进入输入不保证采纳正确；命令执行成功也不证明它覆盖了应验证的行为。这些判断都满足后，才有条件讨论记忆是否改善了任务表现。

改变边界会暴露哪些缺口？若 A/B 改用同一个 Root，workspace 条目不按项目键过滤，A 的文字也会进入 B 的候选正文；写上“A”只是给模型的范围线索。改用 session scope 可以限制到 S1，却不会自动带到新的 S2。child instruction 路径又省略父级 Local Memory，不能把上述主 Session 结论推广到所有执行分支。若改写 Atomic，当前 extraction 创建新 Item，不自动替换旧 Item；Store 独立 mutation 的 update/archive 等能力没有因此被这条提取链调用。已有查询 API 也没有在所查主执行链接成自动 recall。Local 读取开关不能补齐它。

同一更正交给 Codex：从显式修改变为后台整理

Codex 给出另一条真实路线。这里选择生成 MEMORY.md 与 memory_summary.md 的文件整理路径，实现中称为 V1，且先假定已开启 memories。总 feature 默认关闭，不能把内部 generate/use 的默认 true 理解为所有用户默认启用。下文的 Thread 是 Codex 的可延续对话容器，app-server 是接收客户端工作的应用服务层。这里复用 A/B 的逻辑情境，但不继承 Maka 的 Root 隔离假设：Codex 所查选源与摘要读取没有按当前项目做硬过滤，项目差异需要来源材料表达并被正确理解。

  1. 选择来源。 app-server 在有输入、Turn 为 Started（已启动新一轮工作）且有主环境等条件下触发后台任务。它选择其他合格旧 Thread，默认至少空闲 6 小时、每次最多认领 2 个，排除当前 Thread。“用户刚更正了”不等于该更正已进入本次输入集合。
  2. 提取并整理。 第一阶段将选定 rollout（旧任务的交互轨迹记录）交给模型提取，保存带来源的结果；第二阶段再用有界候选、旧材料和差异整理 MEMORY.md、memory_summary.md 等文件。要正确保留“A 改为 make check，B 仍为 pytest”，模型必须理解范围和时序。job 所有权、事务及文件格式校验不替它作语义判断。
  3. 提供入口，再由模型读用。 后续会话初始上下文装配时，Memory extension 读取有界摘要形成 developer 片段；摘要可引导模型搜索手册或阅读来源。进一步读取取决于实际工具与策略，专用 Memory 工具默认关闭，不是摘要注入的前置条件。

失败反例：更正刚发生，尚未达到空闲门槛。 旧摘要可能继续包含 A/pytest；后台管线没有出错，也不能凭空处理尚未被选入的更正。触发后台任务的当前 Turn 不等待整理完成，更不能承诺每一步自动热更新摘要。若当前用户已明确要求 make check，应按当前要求处理，不能用旧摘要否决它。

对于少量、需立即审阅的项目规则，显式条目便于定位修改对象；跨许多任务积累经验时，后台提取与整理能承担更多材料组织，但增加模型成本、延迟和更新错误。需要同 Root 跨项目隔离时，应先补清作用域选择；需要即时撤回时，应先定义请求可见性，不能靠增加索引或换整理模型解决。第36章 的知识记录模型与迁移题用独立的设计字段表示这些差异，而不把它们当成两家产品共享的 schema。

替代方法：先改变约束，再选择实例

把中文偏好改成“工作区 A 英文，其他项目中文”，再添加一次从测试失败中提炼的环境经验。分别判断存得对、找得到、用得对；用户原话可以证明偏好，工具反馈与复测才能支持环境经验。

Memory 方法空间分别比较表示与按需读取、写前检索与更新、链接组织、带反馈的经验、主动检索和评估。每个实例只承担其方法轴的解释，文件记忆、向量检索、反思和图结构不构成互斥的产品名单。

Maka Atomic 当前用户证据治理可以帮助判断写入来源，却不能直接补齐 recall、consolidation 或经验学习。一个替代方法是否值得引入，应看它是否解决眼前失败、增加多少成本，以及有什么未证实的假设。

机制与条件变化解析

问题 1。 memory.mutate { kind: "remember" } 与 Agent tool memory_remember 写到哪里？开启透明读取能让后者自动召回吗？

解释。 前者写透明 bundle，后者写 Atomic SQLite；两者不自动同步。透明读取开关不能创建缺失的 Atomic caller。

问题 2。 为什么一次 readPromptProjection 返回 revision，仍可能没有可注入正文？

解释。 文档缺席、存储层 safe_mode（过大或无效 UTF-8）、解析器大小检查未通过、没有 active 条目、scope 过滤或正文为空，都可能使 body 缺席。revision 用于识别状态，不能当正文。

问题 3。 已经写入 Item，却没有可靠记录提取范围，会遇到哪两类恢复错误？

解释。 写后未记范围可能重复提取；先推进范围但未可靠写入则可能漏存。当前Atomic通过同一提交边界处理Items、cursor与receipt，其他设计需提供自己的对应保证。

问题 4。 新场景：用户说“发布说明用英文，但排错解释继续中文”。应直接覆盖旧语言偏好吗？需要保留哪些可判定条件？

解释。 不应直接全局替代。这是按工作类型区分的要求，需要明确“发布说明/排错解释”的适用条件和来源；现有global/workspace字段是否足以表达，还需审查具体表示与选择策略，不能凭字段名假设已支持。

问题 5。 ArchiveRead、History search 与 Memory recall 分别按什么信息寻找内容？

解释。 ArchiveRead按受限引用回读大工具结果；History search按历史标题/文本寻找会话内容；Memory recall为当前任务选择已保存的可复用信息。它们可以协作，但输入契约和负责组件不同。
