第 20 章｜记忆（Memory）的写入、读取与更新

本章概览

核心问题：“以后用中文解释”怎样成为未来工作可读取、可更正的信息，而不止是模型（Model）当场的一句承诺？

关键概念：记忆（Memory）保存可复用信息；作用域（Scope）限定适用对象；本地记忆笔记（Local Memory）通过读取策略进入输入；比较后写入（Compare-And-Swap，CAS）处理版本冲突；条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）以条目和来源组织写入。

关系主线：保存、取回、组装输入与实际使用分别建立依据。更正要处理旧内容和并发，已发出的请求不会被文件变化追溯修改，数据库可查询也不代表自动召回（Recall）已接通。

前情回顾：当前看见与以后想起是两条路径

第15章说明，模型输入（Model Input）来自实际选择与组装，文件存在不等于已被读取。第19章说明，上下文压缩（Context Compaction）整理当前历史（History）的表示，检查点（Checkpoint）不自动承担长期偏好的写入、更新与召回（Recall）。

仍从README修复工作中的要求出发：“以后请用中文解释结果。”它刚被说出时就在当前上下文（Context）中，所以本轮中文回答无需借助长期记忆（Long-Term Memory）。本章接着改变一个条件：开启新会话（Session），新请求只说“解释这次测试结果”，没有重述旧偏好，也不直接带入旧对话。系统怎样取得那条信息，才成为需要单独解释的问题。

本章讨论智能代理（Agent）的外部记忆（Memory），不是改变模型（Model）权重的训练。沿用第19章的编号，S1是会话（Session），T7是其中修复README的工作轮次（Turn），R7是承担它的执行（Run）；A/B项目的新条件稍后再交代。教学推演与第21、22章已有运行案例分开。

一条偏好怎样跨过新会话（Session）？

当前遵守要求，不等于长期保存

模型（Model）本轮使用中文，可以说明回答符合当前要求；它说“我记住了”仍只是一段生成文字。若旧对话不再进入输入，也没有其他保存与读取路径，这次承诺就不能为新请求提供背景。偶然继续输出中文，也无法单独证明记忆（Memory）生效。

需要检查四件事：信息确实保存；本任务实际取回；内容进入这次输入；回答或动作按适用条件使用。任何一步都不能由前一步的名称代替。

最小闭环：一个文件也能把链路讲清楚

先限定为单个使用者、串行操作、用户显式要求保存。此时可读取文件已经能承担存储，不必先引入复杂数据库。下图把旧、新两次会话（Session）分开；存储连接两者，最后的使用效果仍需要单独观察。

下面是教学伪代码，不是Maka接口（Interface），也没有单独执行。前一段负责写入，后一段只负责为新请求组装背景，两段跨越的是不同会话（Session）。

# 旧会话（Session）：用户显式要求保存
save_preference("解释结果时使用中文")

# 新会话（Session）：当前请求没有重复语言偏好
background = read_relevant_preference(current_task)
model_input = compose(current_task, background)

save_preference提供保存入口；read_relevant_preference依据当前任务选择适用内容；compose将它与新请求放到一起。最后一行尚未调用模型（Model），所以只能判断输入准备，不能宣称回答已经遵循偏好。

文本文件、JavaScript对象表示法（JavaScript Object Notation，JSON）或数据库，是表示与存储选择。版本（Version）、幂等回执（Idempotency Receipt）与向量索引（Vector Index）分别处理更新、重试和检索问题，不是所有最小设计都必须预先拥有的字段。

为什么“正确保存”仍可能“错误使用”？

现在用户增加条件：“工作区A用英文，其他项目仍用中文。”这可能是局部例外，不是推翻全局偏好。若读取方只选语义相似的旧句子，却不判断作用域（Scope），存得再准确也可能用错地方。

这些机制不是相互替代的升级清单。范围不清不能靠增加记录数量解决，并发冲突也不能靠更准确的相似度解决。先明确失败原因，再选择对应设计。

记忆（Memory）还可能过期或携带不可信指令。它提供背景，不因保存时间长就获得文件、网络或宿主（Host）权限。当前用户要求“这次发布说明用英文”时，应按本次要求处理；这次例外也不自动授权永久覆盖长期中文偏好。本次怎样用、长期怎样改、实际获准做什么，需要分别判断。

Maka两条实现路径分别接到了哪里？

Maka当前有两套不自动同步的长期记忆（Long-Term Memory）路径。文件组（Bundle）指共同读取与提交的一组文件；本地记忆笔记（Local Memory）用它关联正式正文和待审提案。

既有真实对照：条目仍在，回答格式却变了

第22章的本地记忆笔记（Local Memory）对照保存“已修改／已验证／待处理”三段报告格式，让两个新会话（Session）完成相同只读测试（Test）任务。开启读取时，实际请求包含偏好，回答使用三个标题；关闭读取后，条目仍在，请求中没有该内容，回答改成普通摘要（Summary）与失败说明。

这段旧实验关联了同一存储、两份输入和两次回答。保存由原生管理接口（Interface）完成，不是模型（Model）凭一句承诺写入；它也不是条目化长期记忆（Atomic LTM）召回（Recall）实验。两边都用中文提问，所以中文本身不能作为这个对照的记忆（Memory）证据。

保存、读取与使用问答

问题1。 为什么本轮中文回答和“记住了”不足以证明长期记忆（Long-Term Memory）？

参考答案。 当前输入已经包含要求，生成承诺不提供写入或读取证据；应在旧输入不再直接出现的条件下，分别检查存储、取回和组装。

问题2。 最小文件设计必须先有版本（Version）、回执（Receipt）与向量索引（Vector Index）吗？

参考答案。 不必。多写者引出冲突控制，请求重发引出幂等（Idempotency），字面检索（Lexical Retrieval）不足才需要其他读取方法；这些问题要按实际约束引入。

问题3。 本地记忆笔记（Local Memory）读取关闭，与条目化长期记忆（Atomic LTM）缺少主链召回（Recall）消费者（Consumer），有什么不同？

参考答案。 前者已有受开关控制的接线，后者所核主链缺少查询与注入（Injection）调用方（Caller）。两者都不能从保存推出本次可见，打开前者的开关也不会自动补上后者。

问题4。 新会话（Session）仍用中文，怎样排除当前请求再次要求中文？

参考答案。 核对新请求没有重述偏好，追踪实际背景来源，并结合关闭读取等对照。固定格式程序只能验证选择与组装，模型（Model）行为需要单独观察。

问题5。 当前要英文发布说明，是否立即覆盖长期中文偏好？

参考答案。 本次按英文要求处理；是否永久修改，还需明确的更新意图与适用范围。记忆（Memory）也不能改变执行授权（Authorization）。

本地记忆笔记（Local Memory）：先追踪一条可见的读取链

两个开关控制两件事

enabled表示记忆（Memory）产品是否启用，agentReadEnabled表示是否允许智能代理（Agent）读取适用条目并加入提示词（Prompt）。当前默认值分别为 true和 false。因此，文件中已经保存，不能推出下次自动读取。

这两个开关也不能代替内容筛选。允许读取后，仍要判断正式文档是否可解码、条目是否有效、作用域（Scope）是否适用，以及筛选后是否还有正文。

源码微步：为什么有版本（Revision），却没有正文？

宿主（Host）的 HostMemoryCoordinator.readPromptProjection负责提供一份可选的输入投影（Projection）：正文若可用就返回，同时携带所读状态的版本（Revision）。下面两个TypeScript片段来自同一方法，保留原代码；它们依赖方法上下文，不能独立执行。阅读时抓住三个阶段：先判断是否允许读取，再判断文档状态，最后生成正文。

第一段位于存储读取之前。隐私模式（Incognito）开启、产品禁用或自动读取关闭，任一条件成立就提前返回。

      if (
        policy.policy.privacy.incognitoActive ||
        !policy.policy.memory.enabled ||
        !policy.policy.memory.agentReadEnabled
      ) {
        return {
          bundleRevision: null,
          memoryRevision: null,
        };
      }

返回值没有 body，后面的 this.#store.read()也不会执行。文件并没有被删除；改变的是本次输入投影（Projection）能使用什么。

通过这道策略检查（Policy Check）后，方法读取文件组（Bundle）并检查 snapshot.memory.kind。只有 document分支继续解码；文档缺席或处于安全模式（Safe Mode）时，都不会走到第二段。存储层（Store）的 snapshotForBytes会在文档超过128二进制千字节（Kibibyte，KiB，即131,072字节），或字节不是有效的8位Unicode转换格式（Unicode Transformation Format—8-bit，UTF-8）时返回安全模式（Safe Mode）。这时仍可保留版本（Revision），但不生成正文。

下面才是可读文档分支。decodeDocument得到文本；buildLocalMemoryPromptBody结合当前 sessionId筛选内容；最后的条件展开只在非空时返回 body。

      const content = decodeDocument(snapshot.memory);
      const body = buildLocalMemoryPromptBody(content, { sessionId });
      return {
        bundleRevision: snapshot.revision,
        memoryRevision: snapshot.memory.revision,
        ...(body ? { body } : {}),
      };

版本（Revision）回答“这份状态是哪一份”，正文回答“本次可提供什么背景”。两者的用途不同，因此返回前者而没有后者完全可能。

读取结果还有实际消费者（Consumer）。readPromptState仅在 body非空时调用 renderMemoryPrompt；resolveSystemPrompt将其加入普通主会话（Session）的系统提示词（System Prompt），并保留文件与文件组（Bundle）的版本（Revision）信息。随后系统提示词（System Prompt）回调交给 AiSdkTurn，最终经 modelAdapter.startStream的 system参数进入所选模型协议适配器（Model Adapter）。

这段接线没有查询条目化长期记忆（Atomic LTM）的数据库。打开本地记忆笔记（Local Memory）读取，只会启用这一条已存在的消费路径。

下图从新工作轮次（Turn）的首次采集开始。数据来源放在旁边，避免把“文件已保存”误读成自动触发模型（Model）请求。两条虚线分别表示受策略限制的读取，以及还需另外核对的使用效果。

没有正文的支路仍汇入普通请求，所以关闭的是该项背景读取，不是禁止模型（Model）工作。组装器（Composer）按会话（Session）与工作轮次（Turn）缓存已捕获的材料。同一工作轮次（Turn）不会随文件变化重新采集；后续新工作轮次（Turn）才重新判断。

第21章的既有实验用真实文件和新进程调用同一个组装器（Composer）：读取开启时包含偏好，关闭时没有 <local-memory>，MEMORY.md字节不变。已捕获背景后再写入一条偏好，同一工作轮次（Turn）沿用旧输入，下一次才包含新增内容。该实验测到的是输入组装（Input Composition），没有调用模型（Model）；不能改写为回答已经遵循偏好。

范围、大小与可信度是三种边界

正文构造（Prompt Body Construction）会检查解析状态，只选有效条目（Active Entry）。会话作用域（Session Scope）要求 sessionId精确匹配；工作区作用域（Workspace Scope）在这里没有按项目目录过滤，也没有按 decayTtlMs自动排除过期条目。名称中有“工作区（Workspace）”，不代表实现已经识别每个项目。

随后才进行秘密信息脱敏（Secret Redaction）与有界截断（Bounded Truncation）。正文超过12,000个16位Unicode转换格式（Unicode Transformation Format—16-bit，UTF-16）编码单元时，会在不拆开代理对的位置截断，再追加提示。宿主（Host）还会添加标题和 <local-memory>包装，因此12,000是正文截断阈值，不是词元（Token）预算，也不是包装后输入的严格总长度上限。前面的128二进制千字节（KiB）文件限制约束字节数；解析器还按8位Unicode转换格式（UTF-8）的字节长度检查文档，超限就不再生成可注入正文。

最后的包装把这部分标为不可信背景（Untrusted Context）。能解码、在大小限制内，只说明可以处理，不说明内容可信，更不授予执行权限（Execution Permission）。如果省掉读取开关，用户关闭读取的选择会失效；如果省掉会话作用域（Session Scope）筛选，其他会话（Session）的局部条目可能进入当前输入。这是由检查职责推出的反例，不是故障实测结果。

更正本地记忆笔记（Local Memory）：提交成功以后，谁会看到变化？

版本（Revision）检查保护并发，不能判断语义

显式保存、提案、批准、拒绝、归档与恢复都经过比较后写入（CAS）：调用方（Caller）提供 expectedRevision，只有它仍与当前版本（Revision）一致，提交才被接受。两个客户端（Client）同时基于旧内容修改时，后提交者不能静默覆盖已经接受的新状态。

文件组（Bundle）的发布顺序是“暂存文件→持久化决策（Durable Decision）→完成发布”。决策一旦可靠写下，后续恢复就需要尊重它。若此后出现提交结果未知（Commit Outcome Unknown），宿主（Host）会启动标记不安全与排空（Poison / Drain），不再沿当前裁决权（Authority）猜测性续写。它不是把未知一律解释成失败后再覆盖一次。

这些机制保护版本（Revision）与发布顺序，却不判断“A用旧命令”和“A改用新命令”是否冲突。语义更新仍需要明确选出旧条目、决定归档或替代，并保存新内容。

连续推演：A从 pytest改为 make check

现在把语言偏好换成项目规则：A原来使用 pytest，用户明确更正“以后A用 make check，B仍用 pytest”。这是按现有接线展开的教学推演，不是新产品运行；第04章四文件示例仍使用 npm test，这里不改变它。

先把条件说清楚。A、B使用不同的状态根（State Root），各自拥有本地文件组（Bundle）。状态根（State Root）是宿主（Host）管理长期控制状态的存储边界，与命令工作目录和会话（Session）身份分别判断；这种隔离来自部署条件，不是本地记忆笔记（Local Memory）自动识别项目。A条目使用 scope=workspace，正文写明项目和用户来源；读取对象限定为该状态根（State Root）的普通主会话（Session）。产品已启用、非隐私模式（Incognito），自动读取也已显式开启。

用户已授权保存更正，所以这里使用原生管理接口（Interface）的 remember，不必先构造待审提案；它不是写条目化长期记忆（Atomic LTM）的 memory_remember工具。下表E0/E1为示例条目，r0/r1/r2为三个版本（Revision）的教学标签，不表示接口返回递增数字。Turn-0表示已捕获旧正文的一次工作轮次（Turn）。

r1以r0提交 set_status，把E0设为 archived新采集不再包含E0；没有其他规则时，该部分暂时为空
r2以r1提交 remember，追加有效的E1：“A改用 make check”，附更正来源后续新工作轮次（Turn）在读取条件满足时包含E1、排除E0
r2之后B的独立文件组（Bundle）没有修改；A仍保留归档的E0B可读自己的 pytest规则；Turn-0已缓存的背景不被追溯改写

两次操作分别调用 HostMemoryCoordinator.#commitSemantic，各自遵守预期版本（Expected Revision）。remember只追加，不会自动发现E0被替代。省去归档就可能让两个规则同时存在；归档成功、追加失败，则会留下暂时缺少该规则的状态。应准确报告“旧规则已归档，新规则尚未保存”，不能称为一次原子替换（Atomic Replacement）。发生版本（Revision）冲突后，应重新读取并判断下一步，不能拿旧依据盲目继续。

r2到达模型（Model），仍需经过前面的读取门、正文筛选、组装器（Composer）和模型协议适配器（Model Adapter）。这里保证的是后续新工作轮次（Turn）的采集条件，没有把文件更新推送到已发出的请求。归档也不删除历史（History）、旧工具结果（Tool Result）或已经发生的动作。

最后还要核对使用效果：新任务没有重述命令时，实际输入是否包含E1？智能代理（Agent）是否结合当前项目说明选择 make check？是否读取结果并判断检查覆盖了哪些行为？背景已进入输入，不保证采纳正确；命令成功，也不等于验证覆盖完整。

改变一个条件，结论会怎样变化？

若A、B改用同一个状态根（State Root），工作区作用域（Workspace Scope）没有项目键过滤，A的文字也会进入B的候选正文。“A”这个字只是供模型（Model）理解范围的线索。改用会话作用域（Session Scope）可以限制到S1，却不会自动带到新的S2。

关联子会话（Linked Child Session）是被委派独立工作的一份会话（Session），第23章会展开。它会自行进行输入组装（Input Composition），默认不隐式继承父历史（History）、本地记忆笔记（Local Memory）或个性化（Personalization）背景。需要它使用中文，就把要求明确写进子任务，不能把主会话（Session）的读取结论推广到所有执行分支。

若把更正改写到条目化长期记忆（Atomic LTM），也不能沿用上述文件更新结论。当前提取（Extraction）主要创建新条目；独立存储接口（Interface）拥有更新、归档等能力，不表示这条提取链已自动调用它们。接下来就看它真正解决了什么。

为什么条目（Memory Item）、游标（Cursor）、回执（Receipt）必须一起结算？

提取游标（Extraction Cursor）标记已覆盖到哪段历史（History），操作回执（Operation Receipt）保存一次操作的结果。先看两个反例：内容写入而游标（Cursor）未推进，恢复后可能重复提取；进度先推进而内容未可靠保存，恢复后又可能跳过尚未写入的信息。只知道其中一项，无法还原整个处理结果。

可以把一次教学状态变化写为：初态 Items=[]，cursor=0，receipt=无；成功后成为 Items=[偏好]，cursor=已覆盖位置，receipt=本次结果。commitExtraction在 BEGIN IMMEDIATE后核对幂等回执（Idempotency Receipt）和预期游标（Expected Cursor），将三部分放入同一事务（Transaction），最后 COMMIT。

第21章的既有SQLite故障实验分别检查了提交前后。游标（Cursor）已写、回执（Receipt）未写时抛错，重开后看到三者回到未提交状态；若子进程在 COMMIT后被杀，新进程则读到三者均存在。前者应按未提交处理，后者只是调用方（Caller）丢失返回。

后者需要用原操作身份（Operation Identity）查回或重放。相同请求重放得到 replayed=true，按键查询只有一个条目（Memory Item）；若一律当失败并新造操作，反而可能重复。这段实验验证存储提交与恢复，不证明模型（Model）提炼出的偏好本身正确。

三种触发分别代表什么意图？

当前写入入口分为三类：

  1. memory_remember接收用户明确要求记住的信息，前台（Foreground）同步返回保存结果。
  2. memory_extract由模型（Model）标记顺带出现、可能长期有用的信息，在工作轮次（Turn）进入终态（Terminal）后异步提取。
  3. 上下文压缩（Context Compaction）边界从检查点（Checkpoint）固定的持久前缀（Durable Prefix）补做提取。

显式保存意图和后台（Background）候选发现不同；后者也受固定覆盖范围约束，不是无限回扫所有用户历史（History）。检查点（Checkpoint）提供可定位的材料边界，不因出现就自动等于长期记忆（Long-Term Memory）已经成功写入。

提取（Extraction）怎样阻止“模型（Model）替用户编一句话”？

先从稳定的运行时事件（Runtime Event）范围中检查游标（Cursor）、回执（Receipt）与待处理失败（Pending Failure）。证据（Evidence）只选非部分结果、由用户创作的文本。助手消息（Assistant Message）可作为解释背景（Interpretation Context），工具（Tool）内容不能成为这里的用户证据（Evidence）或来源（Provenance）。

模型（Model）先提出有界候选，必要时在同一会话（Session）进行有界字面定位（Lexical Localization），再做隔离的规范化（Canonicalization）。写入前还需通过引用、秘密信息、作用域（Scope）与结构约束（Schema）的准入检查（Admission Check）。引用必须是模型服务提供方（Provider）实际可见用户原文的精确子串（Exact Substring），不能用“意思差不多”替代。

例如，用户只说“这次发布说明用英文”，助手后来概括成“用户偏好所有内容英文”。后一段可以帮助解释上下文（Context），却不能反过来充当用户提出全局偏好的证据（Evidence）。即使引用是真的，适用范围仍需要正确判断；精确引用检查不能独自完成语义更新。

失败和隐私怎样限制后续重试（Retry）？

提案（Proposal）、可选的字面定位（Lexical Localization）与规范化（Canonicalization）共享同一覆盖范围内的有界模型调用（Model Query）预算。后台提取（Background Extraction）失败后冻结范围，只再重试一次；再次失败就原子丢弃（Atomic Discard）并推进游标（Cursor），避免永久卡在同一段。

隐私模式（Incognito）或产品禁用可在上下文压缩（Context Compaction）边界形成持久策略拒绝（Durable Policy Denial）。以后重新开启，不会因此自动追溯提取当时被拒绝的范围。显式请求批次涉及敏感信息时，会整体结算为空操作（No-op），不做半批成功；关联子会话（Linked Child Session）和归档会话（Archived Session）不参与自动提取（Extraction）。

这些规则分别处理预算、恢复和隐私意图。它们不等于删除旧记忆（Memory），也不能保证候选总是有用；已经保存什么、现在允许读什么、哪些材料允许再提取，需要分别判断。

两个 remember与一个尚未接通的召回（Recall）入口

名字相近时，先找负责者（Owner）、存储层（Store）与消费者（Consumer）：原生管理操作 memory.mutate { kind: "remember" }修改可见的本地文件组（Bundle）；智能代理（Agent）工具 memory_remember写条目化长期记忆（Atomic LTM）的数据库。两者当前不自动同步。

该数据库的存储接口（Interface）已有 readItem()和 searchByKeys()，支持精确或前缀匹配、工作区（Workspace）、归档状态与数量上限等有界查询。在所核普通运行时（Runtime）与宿主（Host）主链中，尚未找到调用这些查询并注入模型输入（Model Input）的自动召回（Recall）消费者（Consumer），也没有 memory_recall工具。

同一核对范围内，没有接入嵌入向量（Embedding）、向量索引（Vector Index）或语义近似最近邻检索（Semantic Approximate Nearest Neighbor Retrieval，Semantic ANN Retrieval）；自动提取（Extraction）主要创建条目，未形成成熟的自动合并（Merge）、更新（Update）与语义去重（Semantic Deduplication）。原生OpenAI Responses路径还明确不支持这条提取（Extraction）入口。因此，应报告“写入已接通、存储查询已存在、主链自动召回（Recall）尚未接通”，不能简写成“智能代理（Agent）未来一定会想起”。

同一更正交给Codex：后台整理（Consolidation）改变了生效时机

这里选择Codex生成 MEMORY.md和 memory_summary.md的文件整理路径，实现中称为V1，并假定 memories功能已开启。总开关默认关闭，不能把内部生成与使用配置的默认 true理解为所有用户默认启用。线程（Thread）是Codex的可延续对话容器，应用服务层（App Server）接收客户端（Client）工作。

继续使用“A改用 make check，B仍用 pytest”这个逻辑情境，但不继承Maka不同状态根（State Root）的隔离条件：所核Codex选源与摘要（Summary）读取没有按当前项目做硬过滤，需要来源材料表达项目差异并被正确理解。

从选源到读取，需要经过三个阶段

首先，应用服务层（App Server）在有输入、工作轮次（Turn）为 Started且有主环境等条件下触发后台任务（Background Job）。它选择其他合格旧线程（Thread），默认至少空闲6小时，每次最多认领2个，排除当前线程（Thread）。用户刚作出的更正未必已经进入这次选源范围。

其次，第一阶段将交互轨迹（Rollout）交给模型（Model）提取，保存带来源的结果；第二阶段使用有界候选、旧材料和差异（Diff），整理 MEMORY.md、memory_summary.md等文件。任务所有权（Job Ownership）、事务（Transaction）与文件格式验证保护执行和产物边界，不能替模型（Model）判断“A变了、B没变”的语义。

最后，后续会话（Session）的初始上下文（Context）装配时，记忆扩展（Memory Extension）读取有界摘要（Summary），形成开发者消息片段（Developer Message Fragment）。这份入口可引导进一步搜索手册或阅读来源，但是否实际读取仍取决于工具（Tool）与策略（Policy）。专用记忆（Memory）工具默认关闭，并不是摘要（Summary）注入的必要条件。

没有程序故障，也可能暂时继续读到旧规则

如果来源尚未达到默认空闲条件，后台整理（Consolidation）可能继续包含A使用 pytest的旧信息；管线没有出错，也无法处理尚未被选入的更正。触发后台任务（Background Job）的当前工作轮次（Turn）不等待整理结束，更不能承诺每个模型步骤（Model Step）都热更新摘要（Summary）。若当前用户明确要求 make check，就应按当前要求处理，不能让旧背景否决它。

少量需要立即审阅的项目规则，显式条目便于定位修改对象；跨许多任务累积经验，后台提取（Extraction）与整理（Consolidation）能承担更多组织工作，但增加模型（Model）成本、延迟与更新错误。需要跨项目隔离，应先建立作用域（Scope）选择；需要即时撤回，应先定义哪些请求能够看见变化。增加索引（Index）或更换整理模型（Model）不能代替这些条件。

第36章的知识记录（Knowledge Record）案例用独立设计字段进一步区分这些问题，不把两家产品视为共享同一套结构约束（Schema）。

机制与条件变化问答

问题1。 memory.mutate { kind: "remember" }与智能代理（Agent）工具 memory_remember分别写到哪里？开启本地读取能让后者自动召回（Recall）吗？

参考答案。 前者写本地文件组（Bundle），后者写条目化长期记忆（Atomic LTM）的SQLite数据库，两者不自动同步。本地读取开关不能创建缺失的数据库查询消费者（Consumer）。

问题2。 readPromptProjection返回版本（Revision），为什么仍可能没有正文？

参考答案。 文档缺席、安全模式（Safe Mode）、解析器大小检查不通过、没有有效条目（Active Entry）、作用域（Scope）不匹配或正文为空，都可能使 body缺席。版本（Revision）用于识别状态，不能当作记忆（Memory）内容。

问题3。 已写入条目（Memory Item），却没可靠记录处理范围，会引出哪两类恢复错误？

参考答案。 内容先写、进度未记录，可能重复提取（Extraction）；进度先推进、内容未可靠保存，可能永久漏存。当前条目化长期记忆（Atomic LTM）把条目（Memory Item）、游标（Cursor）、回执（Receipt）放入同一提交边界，其他设计也需要自己的对应保证。

问题4。 用户说“发布说明用英文，排错解释继续中文”，是否应直接覆盖旧语言偏好？

参考答案。 这是按工作类型区分的要求，应保留两种适用条件及来源（Provenance）。现有全局或工作区作用域（Workspace Scope）是否足够，需要检查具体表示与选择方法，不能凭字段名称假设已经支持。

问题5。 归档回读（Archive Read）、历史搜索（History Search）与记忆召回（Memory Recall）分别按什么寻找内容？

参考答案。 前者按受限引用（Reference）回读归档时移出的有效模型投影（Effective Model Projection），并不保证返回完整原始业务结果；中者按历史标题或文本定位旧交互；后者为当前任务选择保存的可复用信息。三者可以协作，输入契约（Input Contract）与负责者（Owner）不同。
