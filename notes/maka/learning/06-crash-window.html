第 06 章｜效果（Effect）与执行轨迹（Trajectory）的崩溃窗口（Crash Window）

本章概览

文件已经改好，执行轨迹（Trajectory）却可能仍停在上一轮。本章用一个完整案例解释崩溃窗口（Crash Window）：执行环境（Environment）先产生效果（Effect），进程随后整理观察消息（Observation Message），最后才保存（Save）记录。本例用 SIGKILL 实现硬终止（Hard Termination），让内存中的行动请求（Action）来不及落盘。沿着文件、内存消息（Message）和磁盘快照（Snapshot）三条线，可以判断已发生什么、尚不知道什么，以及恢复（Recovery）前为什么需要重新读取现实。

前情回顾：退出（Exit）与保存（Save）不是同一承诺

第05章说明了最小代理循环（Agent Loop）的顺序：模型调用（Model Query）返回后，行动请求（Action）先追加进内存；执行环境（Environment）运行命令，返回内容整理成观察消息（Observation Message）；本轮到达 finally 时，才尝试保存（Save）执行轨迹（Trajectory）。正常退出（Exit）是程序走完结束协议，硬终止（Hard Termination）则不给 Python 执行 finally 的机会。

沿用第04章的项目模板时，README 初态写的是错误命令 npm run check，正确入口是 npm test。但本章另建了一个独立的固定样例（Fixture），只检查 README 写入与记录落盘的先后，不执行第04章的完整函数修复与测试验收。这里的 PASS 只证明指定崩溃窗口（Crash Window）被观察到，不代表任务成功（Task Success）。

本章给出已有实验的输入、实现结构、完整关键结果和解释。真实模型（Model）没有参与；固定响应驱动真实 DefaultAgent 与 LocalEnvironment。下面直接解释已有结果；自动恢复（Recovery）不在这次实验范围内。

1. 崩溃窗口（Crash Window）：先区分三个状态

同一次硬终止（Hard Termination），三份状态有不同进度

第一轮先读取旧 README，观察消息（Observation Message）和这轮执行轨迹（Trajectory）已保存（Save）。第二轮才提出改写命令。执行环境（Environment）写好文件后，子进程被硬终止（Hard Termination）：第二轮行动请求（Action）在内存里，第二轮观察消息（Observation Message）尚未追加，本轮执行轨迹（Trajectory）也尚未保存（Save）。

图中每一行都跨过同一次硬终止（Hard Termination），不是分别做了三次实验。它们分别回答三个问题：文件中现在有什么；进程终止前内存已走到哪里；终止后磁盘记录能证明什么。不能把其中一条线当成其余两条的完整代表。

为什么会连第二轮行动请求（Action）都看不到

保存（Save）在整轮模型调用（Model Query）与执行结束之后，而不是模型调用（Model Query）一返回就立刻落盘。因此，第二轮行动请求（Action）虽然已经存在于内存，磁盘上的 messages 仍只有第一轮的四条消息（Message）。读取旧快照（Snapshot）的消费者（Consumer）看不到这一步，不等于执行环境（Environment）没有收到它。

这也限定了本例的结论：实验观察的是“效果（Effect）发生后、本轮观察消息（Observation Message）追加与保存（Save）之前”的窗口，没有测试“正在按 JavaScript 对象表示法（JavaScript Object Notation，JSON）格式写文件时中断”或“已有请求记录但缺少最终结果”的其他窗口。

2. 故障注入（Fault Injection）：谁执行，谁留下来检查

先看程序框架，再看关键命令

完整实现位于案例脚本，由两层进程协作：控制进程准备独立的固定样例（Fixture），启动子 Python 智能代理（Agent），并在子进程结束后读取产物；子进程运行两步固定计划，第二步命令在写入后终止这个特定子进程。

顺序执行者处理过程此时能得到什么
1控制进程新建独立输出目录与固定样例（Fixture）初始 README 仍是 npm run check
2子进程中的智能代理（Agent）第一轮执行 cat README.md，随后保存（Save）旧内容的观察消息（Observation Message）与第一轮执行轨迹（Trajectory）
3真实本地执行环境（Environment）命令解释器（Shell）运行第二条命令，同步改写 README，并写实验标记文件出现 npm test，效果（Effect）已发生
4同一命令解释器（Shell）在同一条命令中，向该子进程的具体进程标识符（Process Identifier，PID）发送硬终止（Hard Termination），随后结束子进程返回码（Return Code）为 -9，本轮无法到达 finally
5仍然存活的控制进程比较文件、差异与执行轨迹（Trajectory）判断指定崩溃窗口（Crash Window）是否出现

可移植操作系统接口（Portable Operating System Interface，POSIX）是一组操作系统接口标准。本例使用其中的进程与信号相关能力，已有实验在 macOS 上执行。它终止的是为本案例启动的特定子进程，不是任意匹配名称的进程。命令只修改生成目录里的文件；命令解释器（Shell）随后结束，没有遗留延时或后台工具进程。

案例的调用形式如下。my-crash-run 是展示入口用的新目录名，下面的历史结果来自已经保留的实验目录；这条命令不是本次重构时新执行的记录，也不是阅读完成的条件。

.workspace/learning-labs/.venv/bin/python notes/maka/learning/labs/assets/mini-code-lab.py crash --output .workspace/learning-labs/mini/my-crash-run

结果检查为什么要同时读文件与执行轨迹（Trajectory）

run_crash() 先核实子进程返回码（Return Code）是 -signal.SIGKILL，随后读取 trajectory.json、README 和实验标记。下面摘出已有实现中的关键检查并添加注释；这里的局部变量 output 是本次独立输出目录的 Path 对象，trajectory 是控制进程读取 trajectory.json 并按 JavaScript 对象表示法（JSON）解析后得到的 Python 字典。它是控制进程中的连续片段，不是另一个完整故障注入（Fault Injection）入口。

# 先检查磁盘消息（Message）究竟停在哪一轮，不能用配置中的预定命令替代。
roles = [message["role"] for message in trajectory["messages"]]
old_observation = trajectory["messages"][-1]["extra"]["raw_output"]
readme = (output / "repo" / "README.md").read_text()
if roles != ["system", "user", "assistant", "tool"] or "npm run check" not in old_observation:
    raise AssertionError("The saved trajectory was not the first completed read step")
# 再检查现实文件和独立标记，确定写入确实先于子进程终止。
if "npm test" not in readme or not (output / "effect-written.txt").exists():
    raise AssertionError("The intended filesystem effect did not precede the crash")

第一组检查要求已存消息（Message）恰好是第一轮读取，且最后的原始内容仍含旧命令；第二组要求现实 README 已有新命令，并存在写入标记。只有两组同时成立，才能支持“记录停在读取、文件已经改好”。只看任何一组，都不能证明这个特定崩溃窗口（Crash Window）。

读取的证据看到的结果可以支持的判断

控制进程的历史命令正常完成，退出码（Exit Code）为 0；表里的 -9 属于被终止的子进程。两者负责不同工作，不应混为一个返回码（Return Code）。

还有一个细节：固定响应实现会把预先安排的内容写进 info.config.model，其中可能包含第二步改写命令。那是配置里的计划，不是实际发生过的消息（Message）。因此 saved_write_action_in_messages: false 的精确含义是“已存 messages 中没有第二轮助手行动请求（Action）”；不能因为配置里搜索到了命令，就改口说本轮执行记录已保存（Save）。

4. 恢复（Recovery）：先读回现实，再决定剩余工作

程序重新启动以后，磁盘快照（Snapshot）的消费者（Consumer）只看到旧读取结果。如果仅据此再发一遍原命令，就把“没有记录”误解释成“没有执行”。本例应先读取当前 README 与差异，核实 npm test 已写入，再决定是否还需改动或验证其他任务条件。

这给出的是有证据的恢复（Recovery）思路。实验没有接通自动恢复（Recovery）入口，没有重新启动智能代理（Agent）续跑，也没有证明任务的剩余部分已经完成。

幂等性（Idempotency）要针对具体操作判断：把指定旧文本替换成新文本，重复执行可能不再改变内容；追加一行可能变成两行；远程创建请求可能产生第二个资源。遇到状态未知的远程效果（Effect），需要按资源身份查询和核对，不能用本地文件案例保证它能安全重试。

本例尤其不能把整条故障注入（Fault Injection）命令当成恢复（Recovery）动作重放。它除了替换 README，还会写标记，并向某个具体进程标识符（PID）发送硬终止（Hard Termination）。即使文本替换具有幂等性（Idempotency），也推不出整个命令可重试。重新研究同一窗口时，应由受控案例入口建立新的独立固定样例（Fixture）；恢复（Recovery）实际工作时，则从读回的现实状态出发构造剩余动作。

5. 直接问答：哪些结论已经成立

问：代码有 finally，为什么没有保存（Save）第二轮执行轨迹（Trajectory）？

答：finally 依赖 Python 有机会展开调用栈（Call Stack）。硬终止（Hard Termination）由系统直接结束进程，不是可被普通 except Exception 捕获的异常（Exception）。本例在文件已改、观察消息（Observation Message）尚未追加时终止，因而未执行本轮保存（Save）。

问：执行轨迹（Trajectory）里连第二轮行动请求（Action）都没有，文件怎么会变？

答：第二轮行动请求（Action）先进入内存，执行环境（Environment）随后改文件；磁盘记录要等整轮末尾才更新。硬终止（Hard Termination）使内存中这条消息（Message）没有落盘，已经产生的效果（Effect）仍留在文件里。

问：saved_model_calls: 1 是否证明第二次模型调用（Model Query）根本没发生？

答：它来自旧快照（Snapshot）的 api_calls 字段，只说明最后成功保存（Save）时的统计值。第二轮已提出并执行改写命令；不能把磁盘里滞后的计数当成终止前全部过程。

问：实验的 PASS 是否说明修复完成并且恢复（Recovery）可用？

答：都不能。PASS 验收的是文件已改、记录仍旧这一指定崩溃窗口（Crash Window）。完整修复与自动恢复（Recovery）不在这次运行范围内，也没有用此结果替代任务成功（Task Success）的验收。

问：这个文本替换可以重复，为什么不直接重放第二条命令？

答：文本替换的幂等性（Idempotency）不能覆盖命令中的标记写入和针对具体进程标识符（PID） 的硬终止（Hard Termination）。需要先读回效果（Effect），再为剩余工作生成合适的行动请求（Action），而不是重放整条故障注入（Fault Injection）命令。
