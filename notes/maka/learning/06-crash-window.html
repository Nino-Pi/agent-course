第 06 章｜写入与轨迹保存的崩溃窗口

本章概览

核心问题：文件已经改了，为什么重开后看到的执行轨迹仍可能停在修改之前？

关键概念：effect（效果）是实际文件变化；observation（观察）是返回给 Agent 的结果；trajectory（轨迹）是已保存的过程；SIGKILL（硬终止）会跳过 finally 收尾。

关系主线：本例在写入后、结果返回和保存前终止子进程，对照文件效果、进程内消息与已保存轨迹。记录缺口不能证明未执行；继续前需要核对现实，故障注入通过也不代表修复任务成功。

案例从 第04章 的同一项目模板建立独立 fixture，只改 README 并打断进程，不把函数是否修好作为验收项。PASS 表示观察到了指定记录缺口，不表示 Agent 成功完成修复。

场景：文件写入早于轨迹保存

这次先完成第一轮读取，让 observation 进入 messages 并保存 trajectory；再让第二轮命令修改 README，随即终止子 Agent。下图的三行对应同一过程中的三种状态，箭头只表示时间向右推进。每一行从中间到右侧经过的是同一次 SIGKILL，不是三次不同的故障：

第一轮留下的是读取旧 README 的结果。第二轮的 action 已进入进程内消息并启动命令，但观察尚未返回，这一轮的新消息也还没保存。SIGKILL 不会替程序把内存补写到轨迹文件；控制进程仍能读到已经改过的 README 与较旧的 trajectory。

在这个指定窗口，README 已含新测试命令；trajectory 仍是第一轮快照，没有第二轮修改 action、成功 tool observation 或 exit。下面的控制进程结果把这些判断逐项对应到实际产物。

故障注入的关键动作

案例通过以下入口启动故障注入，输出参数是示例目录；关键行为是脚本控制写入与终止的先后时点：

.workspace/learning-labs/.venv/bin/python notes/maka/learning/labs/assets/mini-code-lab.py crash --output .workspace/learning-labs/mini/my-crash-run

实验仅支持 POSIX 环境，即本例采用的类 Unix 进程接口。控制进程创建独立 fixture 并启动一个子 Python Agent。上游真实 LocalEnvironment 启动的第二条 Shell 命令先同步写入生成目录中的 README 与实验标记，再向该子 Agent 的具体进程标识（PID） 发送 SIGKILL。Shell 随后结束；控制进程保留并检查产物。这不是模拟一次普通 Python Exception：SIGKILL 不会执行 finally。

命令可在 脚本的 crash_worker() 中完整阅读。这里不启动远程工具、不连接模型服务，也不终止其他 Agent 或用户进程。

有一个确定性模型特有的细节：它的 serialize() 会把预设 outputs 一起写进 info.config.model。所以配置里可能已经看见“准备修改”的脚本；那是预先安排的计划，不是执行记录。上表的“未保存 action”严格指 messages 中没有实际追加的第二轮 assistant 消息，不能把配置中的计划当成已发生事实。

读回现实后决定下一步

对这份可直接读回的 README，下一步可以检查实际内容与 diff，确定目标文本已出现，决定接着测试还是补完修改。这个实验没有实现通用自动恢复，也没有自动重放第二条命令。

如果 action 是“在日志追加一行”，盲目重试会追加两次。如果 action 是外部系统操作，而系统无法查询是否已完成，单凭缺少 observation 就更不能猜它没发生。应把结果记为“尚未确认”，再讨论查询、去重或人工处理办法。

effect 是现实已经改变，observation 是 Agent 得到的结果信息。它们之间存在时间窗口。

问题解析

问题 1。 为什么这个实验没有触发 DefaultAgent.run() 的 except Exception 并保存 exit？

解释。 SIGKILL 在进程层面直接终止子 Agent，不是可由 Python 捕获的 Exception，也不会执行 finally。

问题 2。 磁盘上的 trajectory 没有记录写入 action，为什么 README 文件还是改变了？

解释。 第二轮 assistant/action 已在进程内存中产生，Environment 已启动命令并产生 effect；正常路径要等 output 格式化并追加 messages 后，再在该轮 finally 中保存。这个窗口中的修改还没有落入旧 trajectory。

问题 3。 只考虑 README 文本替换，重复执行后内容不再变化，是否就证明整条故障注入命令可以作为恢复方案重放？

解释。 不能。此处文本替换第二次不再改变 README，但整条实验命令还写标记并向特定子 Agent PID 发送 SIGKILL；不要从轨迹复制它作为恢复命令。案例由 crash 入口在独立目录中创建并管理子进程，命令里的 PID 只属于那次注入。真实恢复先读回目标，再执行仍需完成的工作；追加、计费或提交又有各自的重复效果。
