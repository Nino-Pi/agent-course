第 59 章｜评价设计与任务进展

本章概览

核心问题：怎样判断一次机制改动真正改善任务，又避免把合法等待（Valid Waiting）误判为无进展？

关键概念：任务合同（Task Contract）：固定成功条件；有效评分（Valid Score）：有可采用判定的结果；未知状态（Unknown State）：暂缺任务真值；截止交付（Confirmed Delivery）：期限内确认成功；分层指标（Layered Metrics）：分别衡量工具（Tool）、输入（Input）、记忆（Memory）与总任务（Task）；无进展信号（Stagnation Signal）：重复活动没有增加相关信息或改变目标状态。

关系主线：在相同任务条件下收集结果、失败和总成本，再按明确分母比较；控制策略结合新观察结果（Observation）与等待状态决定继续、提示或停止，不能只数相同调用。

前情回顾：内部指标怎样连接到用户要求

第49章把代码修复的成功条件落实到任务合同（Task Contract）：函数行为正确、文档入口正确、修改范围合规，需要同时成立。第54章说明，压缩（Compaction）只改变后续输入的表示；更短的输入仍可能漏掉用户限制。第55章又把记忆（Memory）的保存、读取和实际使用分开，存储成功不能独自证明任务改善。

第26章与第40章区分完整试次（Trial）、有效评分（Valid Score）和确认交付（Confirmed Delivery）。暂时看不到任务结果时，保留未知状态（Unknown State），然后在固定分母中计算覆盖与费用。第39章还提醒我们，合法等待（Valid Waiting）可能重复同一查询，必须结合外部状态判断进展。

本章先用同一份代码任务比较两种日志组织方式，再把“需要什么证据”用于运行途中的继续与停止。无进展检测（Stagnation Detection）部分是教学提案，不能当成 Maka 已实现全部语义判断的事实。

1. 原题与约束

你换了工具接口（Tool Interface）、压缩（Compaction）策略和记忆（Memory）检索，怎样证明改进有效？智能代理（Agent）一直调用工具（Tool）但没有推进时怎样处理？

评价对象与成功条件必须对应。工具（Tool）合法调用率、任务完成率、费用和恢复（Recovery）正确性各回答不同问题。只看一个综合分可能掩盖严重退化。

先重述第04章的四文件任务：package.json定义测试入口，README给运行说明，测试要求非负整数秒格式为m:ss，src/duration.js完成计算。用户允许修实现与README，并要求检查行为和修改范围。

本章先只改变测试日志的组织方式：基线（Baseline）保留长日志，候选（Candidate）提供关键错误片段及回读（Readback）入口；模型（Model）、初态、权限（Permission）、预算（Budget）与验收（Acceptance）要求相同。后面再单独讨论只改README的权限（Permission）变体及无进展控制。若同时换工具（Tool）、压缩（Compaction）和记忆（Memory），只能先评价整套改动，不能从总分把收益直接分给其中一项。

2. 参考方案

先确定评价对象。如果关心整项任务，工具调用（Tool Call）合法只是中间条件，后续还要取得行为、文档和范围的证据。如果关心一种输入组织方法，还要知道原始约束与错误是否保留、缺失材料是否能回读（Readback），以及全部请求花了多少成本。

其次固定可比条件。基线（Baseline）与候选（Candidate）使用同一任务、模型（Model）、初态、权限（Permission）和总预算（Budget）；存在模型（Model）的随机性时，重复运行并报告样本数量与波动。失败与缺失结果仍在原分配中，不能只把双方成功的例子拿来比较。

运行中的控制另看新观察结果（Observation）。分页可能取得新数据，轮询可能等待远端完成；精确重复失败、提供方错误与用户取消（Cancellation）也有不同责任。控制策略先辨认这些条件，再决定继续、提示、重规划或停止；已发生效果（Effect）仍需单独结算。

3. 从任务到评价判断

基线（Baseline）与候选（Candidate）方案接受同一任务和验收（Acceptance）合同，汇入同一套证据与判断。只比较各自作者挑选的成功 demo，不构成可比实验。

4. 评价合同与一个可识别失败的用例

下面的字典是评价合同（Evaluation Contract）的数据表示。先读 task 与 behavior_checks 确认目标，再读 allowed_files 与 must_not 固定边界；stress 只改变日志条件，不增加成功标准。这些字段在观察候选（Candidate）结果之前确定，由后续检查程序消费，不能临时修改来迎合结果。

case = {
    # 合同在比较前固定；这里保存数据，不执行检查。
    "task": "修复 formatDuration 并更新 README",
    "allowed_files": ["src/duration.js", "README.md"],
    "behavior_checks": ["125 秒为 2:05", "分钟/余秒边界正确"],
    "must_not": ["修改测试掩盖错误", "假报未执行的测试"],
    "stress": "测试日志包含大量重复进度和少量关键断言"
}

真正判定需要三种观察结果（Observation）：对当前候选程序运行可信、未被篡改的行为检查；把README命令与项目配置比较；读取文件差异（Diff）确认修改范围与用户内容。每项观察结果（Observation）先记为True（确认满足）、False（确认不满足）或None（本次未能判定）。例如执行测试的工具（Tool）故障产生的是最后一种状态，不能补写成“程序行为失败”。

本例将“没有假报测试”也纳入行为检查：最终说明中的测试声称须与执行记录一致，确认虚报则记为False，缺少必要记录则保留None。因此行为检查为True需要行为要求满足且相关说明可核对，不能只读取候选（Candidate）自己报告的“测试通过”。

下面的函数只汇总已经给定的观察结果（Observation）。它先拒绝不合法的值，再找可信反例，最后判断是否全部通过；调用者仍要保存原始检查与来源。函数不会执行测试，也不会自行证明观察结果（Observation）可信。

为什么 False 能与 None 同时出现，却仍得出整体失败？任务合同（Task Contract）要求三项同时成立，只要范围检查确认越界，合同就已被否定；行为检查的未知仍然保留。这个结论没有把未知行为猜成失败，也没有完成失败原因归因。

def task_outcome(checks):
    required = ("behavior", "readme", "scope")
    values = [checks.get(name) for name in required]
    if any(value is not None and type(value) is not bool
           for value in values):
        raise TypeError("检查结果只能是 True、False 或 None")
    # 已有可信反例足以否定合同；调用者仍要保存其余未知检查。
    if any(value is False for value in values):
        return "fail"
    if all(value is True for value in values):
        return "success"
    return "unknown"

汇总状态与三项原始检查一起保存，费用、端到端时间及失败位置也各自从实际记录取得。一个fail标签不能独自说明是模型（Model）选错、工具执行（Tool Execution）错还是环境不可用。人工审核、确定性测试和模型（Model）判断可以组合，但要记录各自看到了什么。

五个分配任务：依次计算覆盖、质量与交付

给定同一截止时点的五个教学结果：成功、成功、失败、基础设施不可用、缺失结果；前两项都已在截止前确认成功。它们不是实际模型（Model）运行。分配数量为 N=5N=5N=5，有效评分（Valid Score）数量为 Nvalid=3N_{\mathrm{valid}}=3Nvalid​=3，确认成功数量为 S=2S=2S=2。

有分数覆盖率（Score Coverage）回答“多少分配得到了可采用的任务判定”，有效评分条件下成功率（Conditional Success Rate）回答“可判定的部分表现如何”：

C=NvalidN=35,Q=SNvalid=23.C=\frac{N_{\mathrm{valid}}}{N}=\frac{3}{5},\qquad Q=\frac{S}{N_{\mathrm{valid}}}=\frac{2}{3}.C=NNvalid​​=53​,Q=Nvalid​S​=32​.

截止确认交付率（Confirmed Delivery Rate）以全部分配为分母：

D=SN=25=C Q.D=\frac{S}{N}=\frac{2}{5}=C\,Q.D=NS​=52​=CQ.

最后一个等式在本例 Nvalid>0N_{\mathrm{valid}}>0Nvalid​>0 时成立。若没有有效评分（Valid Score），QQQ 应记为未定义，不能人为填零；DDD 仍可按确认成功数量计算。这三个量描述的是可观察的评分与交付，不能据此猜测缺失任务的真实能力结果。

再给定五项已产生的成本为 10、12、9、2、4 个单位。完整已知成本 KKK 为：

K=10+12+9+2+4=37.K=10+12+9+2+4=37.K=10+12+9+2+4=37.

只给前三项记账会得到 313131，遗漏后两项的 666。没有评分不等于没有花费，尚未确定的追加费用还要另列。成功两项的费用也不能代替整批成本。

第40章的评价证据链给出三个实现对象：Maka 目标（Goal）的文本窗口、Maka 评价模块（Eval）的被评对象（Subject）与判定器（Verifier）分工与 Harbor 的奖励（Reward）文件。完成判断与评估专题进一步推导尝试（Attempt）选择、至少一项通过率（pass@k）和观察盲区。

把分层指标放回本章对照。以下是给定的教学过程，没有运行两套智能代理（Agent）：基线（Baseline）从长日志中找到125 → 2:25与期望2:05，候选（Candidate）先返回同一断言和原日志位置ref，再按需回读（Readback）。两边都据此定位余秒计算、完成修复，并取得行为、文档和范围三项True；因此质量在这一个案例上相同。接下来比较的才是压缩（Compaction）、读取、回读（Readback）和验证全部计入后的费用与时间。没有这份完整账本，不能仅凭首次返回更短宣布节省。

失败走读另采用一个 仅改文档（README-only）变体：allowed_files 只有 README.md，用户要求只修文档并报告源码测试失败。候选（Candidate）方案词元（Token）更少，却裁掉“只改 README”并修改了源码。长度指标改善，授权范围指标失败，不能写为无条件优化。这个变体与上面允许修函数的完整任务分别建 case，不能混用验收（Acceptance）合同。

6. 无进展检测的最小设计

下面是无进展检测（Stagnation Detection）的教学控制方案，尚未实现为完整控制器，不声称 Maka 已实现全部语义判定。已有专题见 语义停滞研究，其提案与历史实现范围独立保留。

为什么只数调用不够？查询同一个外部作业（Job）三次，可能分别看到“排队、运行、完成”；同一编辑工具（Edit）三次零匹配且文件没变，却没有增加定位依据。检测器需要保存前后观察结果（Observation），才能区分这两种情况。

教学记录中的scope标明当前目标，action_identity关联正在比较的动作，observation_summary与target_state保留新观察结果（Observation）和目标变化；分页再记cursor，外部作业等待再记wait_reason。这些字段按活动需要出现，不要求每次文件读取都构造分页游标。计数也应限于当前目标，不能把上一个文件的失败直接累计到一个新的修复目标。

停止决定要放在能结算工具结果（Tool Result）的位置，保留已发生的效果（Effect）；不能在收到一半输出时就把整个操作标成“从未发生”。策略初期可以先只记录或提示，观察误报后再决定哪些情况适合自动停止。

7. 递进追问

同一个命令执行三次就是死循环吗？

不是。外部作业（Job）状态可能在变化，文件可能被用户修改，分页可能有新游标（Cursor）。要问有没有新信息、是否仍在合法等待（Valid Waiting）预算（Budget）内；重复文本与无进展不是同一判据。

模型自评（Model Self-Evaluation）可以作为唯一完成判断吗？

可作为一个信号，但代码任务还应有实际测试、文件差异（Diff）和用户需求映射。自评输入是否包含失败日志也要核对，否则再聪明的评估器也可能基于缺失材料误判。

只跑一遍成功可以报告提升吗？

只能报告那次运行的结果。存在模型（Model）的随机性时使用重复运行、配对任务并报告样本数和波动；样本小就保留不确定性。不应生成没有真实运行支撑的百分比。

同一任务第一次明确失败，之后重试到成功，只保留成功能否算单次能力？

不能。先区分基础设施不可用的替换、完整策略中的自主重试与独立统计重复试次（Repetition）。Maka 的结果选择会保留首个不可替换结果，并非取最高分；若评估允许 k 次候选（Candidate）或带反馈重试，必须明确预算（Budget）、状态重置及选择器，不能直接冒充单次成功率。

检测器误停了一个合法任务怎么办？

记录触发证据、范围与当时动作，用离线回放检查规则。将误停率与节省调用一并考虑；恢复（Recovery）时先核对已完成效果（Effect），不盲目重启全部工作。
