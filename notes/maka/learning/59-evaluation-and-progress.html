第 59 章｜评价设计与任务进展

本章概览

核心问题：怎样判断一次机制改动真正改善任务，又避免把合法等待误判为无进展？

关键概念：任务合同：固定成功条件；有效评分：有可采用判定的结果；未知状态：暂缺任务真值；截止交付：期限内确认成功；分层指标：分别衡量工具、输入、记忆与总任务；无进展信号：重复活动没有增加相关信息或改变目标状态。

关系主线：在相同任务条件下收集结果、失败和总成本，再按明确分母比较；控制策略结合新观察与等待状态决定继续、提示或停止，不能只数相同调用。

前置：第49章、第54章、第55章，以及 第26章 评价最小模型中的完整试次、选择与成本。无进展检测部分是教学提案；Maka 已有具体 loop gate 的范围需按当前文档核对。

前面几章分别改变了工具入口、工作输入与长期背景。共同问题是：内部机制变了，用户的任务是否真的更好地完成？本章把“少读了多少文字”和“是否完成全部要求”放到同一次对照中，再讨论运行途中如何判断继续等待还有没有价值。

1. 原题与约束

你换了工具接口、压缩策略和 Memory 检索，怎样证明改进有效？Agent 一直调用工具但没有推进时怎样处理？

评价对象与成功条件必须对应。工具合法调用率、任务完成率、费用和恢复正确性各回答不同问题。只看一个综合分可能掩盖严重退化。

先恢复第04章的四文件任务：package.json定义测试入口，README给运行说明，测试要求非负整数秒格式为m:ss，src/duration.js完成计算。用户允许修实现与README，并要求检查行为和修改范围。

本章先只改变测试日志的组织方式：基线保留长日志，候选提供关键错误片段及回读入口；模型、初态、权限、预算与验收要求相同。后面再单独讨论只改README的权限变体及无进展控制。若同时换工具、压缩和Memory，只能先评价整套改动，不能从总分把收益直接分给其中一项。

2. 参考方案

我会先固定任务与可检验目标，再做可比对照。工具层看选对工具、参数合法、执行结果和错误是否可用；Context 层看约束保留、证据能否找回与总成本；Memory 分开看写入、检索、注入和实际行为；整体任务看需求是否满足、修改范围和验证证据。比较时尽量固定模型、权限、环境和任务，随机性需要多次运行并报告波动。无进展控制也不能只数重复调用：分页、轮询和重新读取都可能合法。应记录任务范围和新观察，区分重复失败、等待中的外部工作、目标状态变化。先采用提示或有界等待，停止要保留已知效果，并单独处理提供方错误和用户取消，避免把所有失败归成模型循环。

3. 从任务到评价判断

基线与候选方案接受同一任务和验收合同，汇入同一套证据与判断。只比较各自作者挑选的成功 demo，不构成可比实验。

4. 评价合同与一个可识别失败的用例

下面先把用户要求写成评价合同。它是判定之前固定的输入，不能等看见候选结果后再改。stress只描述日志条件，不是一个额外成功标准。

case = {
    "task": "修复 formatDuration 并更新 README",
    "allowed_files": ["src/duration.js", "README.md"],
    "behavior_checks": ["125 秒为 2:05", "分钟/余秒边界正确"],
    "must_not": ["修改测试掩盖错误", "假报未执行的测试"],
    "stress": "测试日志包含大量重复进度和少量关键断言"
}

真正判定需要三种观察：对未被篡改的程序运行行为检查；把README命令与项目配置比较；读取diff确认修改范围与用户内容。每项观察先记为True（确认满足）、False（确认不满足）或None（本次未能判定）。例如测试工具故障产生的是最后一种状态，不能补写成“程序行为失败”。

本例将“没有假报测试”也纳入行为检查：最终说明中的测试声称须与执行记录一致，确认虚报则记为False，缺少必要记录则保留None。因此行为检查为True需要行为要求满足且相关说明可核对，不能只读取候选自己报告的“测试通过”。

下面只实现这些观察的汇总：有可信反例就能确认任务失败；三项都确认满足才成功；其余保留未知。它接收给定检查结果，不执行测试，也不自行核验检查结果是否可信。

def task_outcome(checks):
    required = ("behavior", "readme", "scope")
    values = [checks.get(name) for name in required]
    if any(value is not None and type(value) is not bool
           for value in values):
        raise TypeError("检查结果只能是 True、False 或 None")
    # 已有可信反例足以否定合同；调用者仍要保存其余未知检查。
    if any(value is False for value in values):
        return "fail"
    if all(value is True for value in values):
        return "success"
    return "unknown"

汇总状态与三项原始检查一起保存，费用、端到端时间及失败位置也各自从实际记录取得。一个fail标签不能独自说明是模型选错、工具执行错还是环境不可用。人工审核、确定性测试和模型判断可以组合，但要记录各自看到了什么。

手算一个教学小样本：预先分配 5 个任务，得到成功、成功、失败、基础设施不可用、缺失结果。按约定，前三个有有效评分，所以评分覆盖为 3/5，有效评分内成功为 2/3；确认成功交付占全部任务的 2/5。这三个分母回答不同问题。若五项分别已花费 10、12、9、2、4 个成本单位，已知总成本仍是 37，不能因为后两项没分数就只记 31；尚未确定的追加费用另列。样本与金额单位仅供计算，不是产品结果。

第40章 的评价证据链给出三个实现对象：Maka Goal 的文本窗口、Maka Eval 的 subject/verifier 分工与 Harbor 的 reward 文件。完成判断与评估专题进一步推导 attempt 选择、pass@k 和观察盲区。

层次应记录什么单独不能证明什么
工具（Tools）选择、参数错误、结果可用性、未知效果任务最终成功

把分层指标放回本章对照。以下是给定的教学过程，没有运行两套Agent：基线从长日志中找到125 → 2:25与期望2:05，候选先返回同一断言和原日志位置ref，再按需回读。两边都据此定位余秒计算、完成修复，并取得行为、文档和范围三项True；因此质量在这一个案例上相同。接下来比较的才是压缩、读取、回读和验证全部计入后的费用与时间。没有这份完整账本，不能仅凭首次返回更短宣布节省。

失败走读另采用一个 README-only 变体：allowed_files 只有 README.md，用户要求只修文档并报告源码测试失败。候选方案 token 更少，却裁掉“只改 README”并修改了源码。长度指标改善，授权范围指标失败，不能写为无条件优化。这个变体与上面允许修函数的完整任务分别建 case，不能混用验收合同。

6. 无进展检测的最小设计

下面是教学控制器，不声称 Maka 已实现完整语义 detector。已有专题见 语义停滞研究，其提案与历史实现范围独立保留。

为什么只数调用不够？查询同一个job三次，可能分别看到“排队、运行、完成”；同一Edit三次零匹配且文件没变，却没有增加定位依据。检测器需要保存前后观察，才能区分这两种情况。

教学记录中的scope标明当前目标，action_identity关联正在比较的动作，observation_summary与target_state保留新观察和目标变化；分页再记cursor，外部作业等待再记wait_reason。这些字段按活动需要出现，不要求每次文件读取都构造分页游标。计数也应限于当前目标，不能把上一个文件的失败直接累计到一个新的修复目标。

停止决定要放在能结算工具结果的位置，保留已发生的效果；不能在收到一半输出时就把整个操作标成“从未发生”。策略初期可以先只记录或提示，观察误报后再决定哪些情况适合自动停止。

7. 递进追问

同一个命令执行三次就是死循环吗？

不是。外部 job 状态可能在变化，文件可能被用户修改，分页可能有新 cursor。要问有没有新信息、是否仍在合法等待预算内；重复文本与无进展不是同一判据。

模型自评可以作为唯一完成判断吗？

可作为一个信号，但代码任务还应有实际测试、diff 和用户需求映射。自评输入是否包含失败日志也要核对，否则再聪明的评估器也可能基于缺失材料误判。

只跑一遍成功可以报告提升吗？

只能报告那次运行的结果。存在模型随机性时使用重复运行、配对任务并报告样本数和波动；样本小就保留不确定性。不应生成没有真实运行支撑的百分比。

同一任务第一次明确失败，之后重试到成功，只保留成功能否算单次能力？

不能。先区分基础设施不可用的替换、完整策略中的自主重试与独立统计 repetition。Maka 的结果选择会保留首个不可替换结果，并非取最高分；若评估允许 k 次候选或带反馈重试，必须明确预算、状态重置及选择器，不能直接冒充单次成功率。

检测器误停了一个合法任务怎么办？

记录触发证据、范围与当时动作，用离线回放检查规则。将误停率与节省调用一并考虑；恢复时先核对已完成效果，不盲目重启全部工作。
