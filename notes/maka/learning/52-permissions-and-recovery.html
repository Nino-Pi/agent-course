第 52 章｜权限（Permission）与效果（Effect）恢复（Recovery）

本章概览

核心问题：怎样分别判断“这次操作是否获准”与“崩溃前是否已改变现实”？

关键概念：权限策略（Permission Policy）决定允许范围；隔离（Isolation）约束实际访问；准备边界T1记录从此可能执行，结果结算T2保存已接受的结果（Outcome）；未知效果（Unknown Effect）承认现实尚无法确认；幂等键（Idempotency Key）依接收方合同识别同一业务动作。

关系主线：可信授权（Authorization）约束执行，持久记录帮助解释故障位置；缺少回执（Receipt）时先回查记录，再按原身份（Identity）查询或对账（Reconciliation）。

前情回顾：权限（Permission）、执行与已知结果各有负责者（Owner）

第17章把权限策略（Permission Policy）、批准（Approval）与强制执行（Enforcement）分开：策略（Policy）判断能不能，批准（Approval）在需要时补充授权（Authorization），执行环境限制实际访问。工具可见并不代表能执行，模型（Model）的“安全命令”声明也不等于可信决定。

第51章解释了资源层合同：读取（Read）提供观察版本（Observed Version），条件提交（Conditional Commit）负责检查并写入，进程（Process）收束则汇集退出与输出。这些都不同于第18章的持久结果结算：文件可能已改，回执（Receipt）却还没保存。

本章沿用允许修正 README 测试入口与时长实现的四文件任务，先在本地工作区（Workspace）讨论，再另设远端作业（Job）变体。接口（Interface）、状态（State）与编号是教学设计；Maka 对照限定为配置了持久接收端（Durable Sink）的普通运行时执行（Runtime-Executed）路径。客户端能力（Client Capability）与模型服务代执行（Provider-Executed）另有条件，不能直接套用。

最小方案：三种责任，不能交给同一句提示词

只在提示词写“不要越权”，不能阻止进程（Process）访问文件；只用沙箱（Sandbox），也不能判断允许范围内的一次删除是否符合用户意图。先把责任分给三个对象：

表 1 / Table 1 · 最小方案：三种责任，不能交给同一句提示词
负责者（Owner）接受什么决定或记录什么无法独自证明什么
可信策略裁决者（Policy Authority）用户要求、规则、当前允许与拒绝范围权限（Permission）决定及允许的申请入口进程（Process）已经遵守限制
执行环境当前执行边界（Execution Boundary）和具体操作落实隔离（Isolation），执行并收集观察业务目标已经达成
持久运行时（Durable Runtime）调用身份（Identity）、参数和执行结果准备边界T1、结果结算T2与恢复（Recovery）记录任意远端效果（Effect）恰好发生一次

已有授权（Authorization）覆盖的操作可直接继续；确实缺少能力时，先判断策略（Policy）与入口是否允许申请，再提出具体目的和范围。显式禁止不能被一次普通扩边请求覆盖。用户决定经可信链路进入边界，而不是由模型（Model）改一个参数即生效。

因此设计的核心并非“遇到危险就总问用户”。它是让已有权限（Permission）可用、拒绝可解释、需要的新批准（Approval）能准确约束下一次执行。

一次普通调用：T1 之后仍有实时边界检查

先读时序图中的三个位置：准备边界T1成功，之后实现才可能运行；效果（Effect）发生在资源侧；结果结算T2成功后，后续模型（Model）才能使用已接受结果。图展示普通调用且最后保存成功的路径，持久失败稍后单列。

在 Maka 的这条普通路径中，顺序是执行前检查（Preflight）→T1→实时执行边界（Live Execution Boundary）→实现→T2。不是所有权限（Permission）检查都发生在T1之前。参数或当前步骤可用性可先拒绝；命令所需声明范围不足，也可能在已分派（Dispatch）、尚未启动进程（Process）时明确拒绝。

所以“命令没启动”不等于“运行时（Runtime）没有分派（Dispatch）”。T1只标记从这里以后实现可能开始，不证明真实效果（Effect）已经产生，更不证明成功。普通工具准备与结算。

当前源码没有持久接收端（Durable Sink）时，prepareDurableToolAttempt 可不创建持久调用；本章的数据库恢复（Recovery）保证因此明确要求该接线存在。更一般的系统可以设计不同准备阶段，但必须逐一解释持久标记（Durable Marker）的意义，不能只借用T1/T2名称。

批准（Approval）怎样改变下一次调用

范围不足先形成明确结果；任务确实需要该能力且策略（Policy）允许时，再申请具体范围。宿主（Host）将决定与当前边界修订（Revision）核对并保存，后续调用读取新边界。这里的修订（Revision）表示权限配置的变化，不是文件内容版本。

批准（Approval）不会把上一条失败结果变成成功，也不会自动改变已经运行的进程（Process）。权限（Permission）收紧后，后续准入（Admission）应使用新边界；排队或运行中的工作可能要停止、重建执行环境或按能力重新检查。一次实时读取不能追回已发生访问，更不能令远端对象立即消失。

三种结果（Outcome）与一种必须停止的边界失败

先把“知道失败”与“不知道效果（Effect）”分开。执行失败可能已经产生已知的部分效果（Effect），因此不能把所有异常都写成“未执行”。下面的联合类型是教学结果合同：

type Outcome =
  | { status: "succeeded"; result: unknown; receipt?: string }
  | { status: "failed"; code: string; effect: "none" | "partial_known" }
  | { status: "unknown"; reason: string; operationId: string }

result: unknown 的 unknown 是 TypeScript 类型，表示此处未限定值的结构；status: "unknown" 是业务标签，表示效果（Effect）无法确认。partial_known 则表示部分变化已知，恢复（Recovery）时必须保留它。

还有第四种问题不在这个普通结果集合里：持久结算本身失败。 若结果结算T2未可靠完成，运行时（Runtime）必须停止当前循环，不能先把“成功”或“未知效果（Unknown Effect）”交给模型（Model），再后台补存。下一次恢复（Recovery）先回查数据库；没有收到提交回执（Receipt），不等于数据库一定没有提交。

表 2 / Table 2 · 三种结果（Outcome）与一种必须停止的边界失败
所在层一个例子可继续的前提
进程（Process）或资源收束进程（Process）状态待查，或文件回复丢失形成有依据的结果（Outcome），包括未知效果（Unknown Effect）

Maka 文件系统执行者（Filesystem Worker）的回复失联、不可解析等情形，可以被分类为未知效果（Unknown Effect）；这份不确定性还能保存为错误结果T2。在本节普通T1/T2记录分支中，恢复分类的 completed 表示已找到匹配响应（Matching Response），不等于业务成功。文件结果分类、记录形状与恢复判定。

分派（Dispatch）函数：把异步边界放在正确位置

下面保留一份完整控制骨架。输入是工具调用（Tool Call）call 和注入的运行时（Runtime）；prepare 必须持久认领，拒绝重复身份（Identity）或参数冲突。executeAndClassify 依据执行者（Worker）证据形成前述结果（Outcome）；它不能把任何异常都吞成无效果（Effect）。

阅读顺序是：先拒绝不应分派（Dispatch）的请求；再准备；准备成功才读当前边界并执行；最后保存T2并交付。函数中的各个服务是抽象合同，不是可直接运行的 Maka 接口。

async function dispatch(call, runtime) {
  const refusal = runtime.validateBeforeDispatch(call)
  if (refusal) {
    await runtime.storeSyntheticPair(call, refusal) // 没有 T1 dispatch
    return refusal
  }

  // claim 负责拒绝重复身份和参数冲突；失败不能继续执行。
  const claim = await runtime.ledger.prepare(call)
  if (claim.kind !== "newly_prepared") return runtime.resolveExisting(claim)

  const outcome = await runtime.executeAndClassify(call, async () => {
    const boundary = await runtime.authority.readCurrent()
    return runtime.executor.execute(call, boundary)
  })

  // T2 失败时抛出边界错误并停止；不能输出一个成功结果再后台补存。
  await runtime.ledger.acceptOutcome(claim.operationId, outcome)
  return runtime.toModelObservation(outcome)
}

两个等待决定了合法次序：prepare 成功返回之前不能调用实现；acceptOutcome 成功之前不能交付结果。storeSyntheticPair 保存的是执行前拒绝的合成调用/响应（Synthetic Call/Response），没有T1。resolveExisting 则按已有记录接回、等待或停放（Park），不能暗中把同一身份（Identity）再执行一次。

operationId 关联本次调用和结果，businessIntentKey 若存在，表达跨调用仍相同的业务意图（Business Intent）。模型（Model）换一个调用编号重发“为这次变更创建测试作业（Job）”，可能仍是原意图；参数相同也不能强行去重，因为用户可能明确要求再运行一次测试。身份（Identity）的语义必须由业务合同定义。

崩溃以后，先判断可靠记录覆盖到哪里

图中的崩溃点A–E表示不同位置；重启后先查实际留下的记录，不能用进程（Process）退出位置的猜测代替回查。

“收到执行回执（Receipt），但尚未保存”仍可能只留下T1：进程内曾经知道的内容随崩溃丢失。反过来，T2可能已经保存，只是确认消息没回来。先查是否有匹配T2，再根据结果内容判断；缺少客户端回执（Receipt）不是缺少持久记录的证明。

正常走读：已有授权（Authorization）内修改与测试

设执行边界（Execution Boundary）修订（Revision）为b4，允许当前工作区（Workspace）读写及所需本地执行，网络受限。模型（Model）读取 package.json 和 README，提出合法编辑（Edit）。运行时（Runtime）保存T1，再读b4；文件系统执行者（Filesystem Worker）核对目标并修改，保存T2后，下一步模型（Model）才读到编辑结果。

模型（Model）随后选择 npm test。若测试只需要当前本地环境，就不必扩权；假设观察到四项通过，保存结果后仍检查差异（Diff），交付时区分修改内容、实际检查与覆盖范围。这些是教学条件，没有重新运行产品或测试。

另设需要下载依赖的变体：若当前入口能够在启动前识别未获准的网络需求，可以明确拒绝；不能把它解释成函数断言失败，也不能声称任意命令都能静态预知全部网络行为。假设策略（Policy）允许申请，用户批准（Approval）后b4更新为b5，下一次调用使用b5；先前未运行的测试仍是未运行。

失败走读：README 已改，o9 还没有结果结算T2

这一段明确给定故障发生在T2提交之前，重启回查也确认只有T1；不是仅凭没收到确认作推断。

  1. 数据库持久记录操作（Operation）o9的T1，绑定本次参数。
  2. 执行者（Worker）把 README 测试入口改成 npm test。
  3. T2提交前进程（Process）崩溃，重启只能读到T1。
  4. 恢复器（Recovery Resolver）保留o9的未知效果（Unknown Effect），不原样重发写入。
  5. 通过已授权的只读操作检查当前文件与差异（Diff）。若已有正确入口，记录当前状态（State），继续必要验证。
  6. 没有可归因回执（Receipt）时，仍区分“当前内容正确”与“已证明o9成功”；用户可能在间隙中完成或改变同一文件。

这个例子说明：避免重复写入可以是基于现态的正确决策，却不必伪造一份旧操作成功证明。反之，如果回查发现T2已保存，应读取那份结果，而不继续坚持“只有T1”。

把写文件换成经授权创建远端持续集成（Continuous Integration，CI）作业（Job），现态要向真正负责者（Owner）查询。主机文件和本地进程（Process）不能证明远端未创建；需要原作业（Job）编号或业务键。没有可靠查询和幂等性（Idempotency）合同，就保留未知效果（Unknown Effect），避免制造第二次可能收费或写入的操作。

幂等键（Idempotency Key）：同一意图仍须接收方认领

在请求里加入通用唯一标识符（Universally Unique Identifier，UUID），只产生一个标识；它不会自动让接收方去重。真正的幂等性（Idempotency）合同要回答：哪个账户/业务范围内相同、保留多久、同键不同参数怎样拒绝、同键并发怎样原子接受、重复请求返回什么。

幂等键（Idempotency Key）还应在首次发送前持久保存，恢复（Recovery）时沿用它。每次重试换键，会被当成不同意图；过期后继续复用，也未必仍受原去重保证保护。查询后再创建若没有原子约束，两位执行者（Worker）还可能同时查不到，然后各创建一次。

T1/T2记录“可能执行”与“接受结果”，并未把远端效果（Effect）纳入同一个事务（Transaction）。因此它们不能独自推出恰好一次（Exactly Once）；更强保证要落到具体资源负责者（Resource Owner）的原子去重或条件提交（Conditional Commit），并说明故障覆盖。任意命令执行（Bash）可能触及多个系统，不能统一承诺。

客户端（Client）断线，远端 j9 仍在运行

现在明确改为另一组条件：远端已经接受作业（Job）j9，本地也已保存创建回执（Receipt），随后客户端（Client）断线。它不同于前面只有T1的o9。三类操作分别处理：

表 4 / Table 4 · 客户端（Client）断线，远端 j9 仍在运行
操作负责者（Owner）与输入能确认什么
取消本地等待（Cancel Wait）本地控制器停止对j9的等待只证明当前等待结束
取消远端作业（Cancel Job）有权执行者（Worker）向服务提交j9取消（Cancellation）请求服务确认 cancelled 才能报告远端停止；超时仍需回查

用户只关闭窗口而没有取消（Cancellation）要求时，仍存活的宿主（Host）可以继续观察j9；用户明确停止时，停止后续创建与无关调用，已开始工作的收尾依原授权（Authorization）和服务合同处理。j9若恰在取消（Cancellation）前完成，保留真实完成结果，不能改写成从未执行。

若改变条件，本地只有创建调用T1而无服务回执（Receipt），则按持久业务键查询；没有查询能力，保留未知效果（Unknown Effect）。本地等待结束、远端工作停止和撤销既成效果（Effect）各是一个动作。撤回权限（Permission）后把账本（Ledger）改成 failed，不能替代这些动作，也不能改变历史。

换执行路径时，哪些保证需要重新核对

模型上下文协议（Model Context Protocol，MCP）描述工具接入方式，不自动决定资源与恢复（Recovery）合同。Maka普通协议适配器仍经过工具运行时（Tool Runtime）；以下几条路径必须分别解释：

执行路径已有边界不能直接继承什么

客户端能力（Client Capability）的准备也有模式条件：当前执行边界（Execution Boundary）为 bypass，或会话（Session）的权限模式（Permission Mode）为 ask，才可进入准备路径；对需要会话级授权（Session Authorization）的目标，ask 分支还检查或请求相应的会话级授权记录（Session Grant）。重启处理可以为已分派（Dispatch）但未结算的此类调用保存未知效果（Unknown Effect）的错误结果T2；它结算“不确定”这一事实，不能替远端证明成功。客户端准备、重启结算。

普通Maka Edit 默认按 never_auto_retry 处理，不能由缺回执（Receipt）推出可重做。managed_mutation_v1 托管修改（Managed Mutation）存在更强基础设施，但宿主（Host）默认绑定尚未为普通 Write/Edit 接入相应合同，不能据此升级默认保证。

T1/T2与保守未知效果（Unknown Effect）持久区分准备与接受结果查询、对账（Reconciliation）或有权人工处理
业务键与负责者（Owner）查询在具体合同内重提或接回服务端去重、键生命周期与参数冲突
资源条件提交（Conditional Commit）拒绝陈旧前提并接受变化原子性（Atomicity）、事务（Transaction）和协作写入范围

完整方案先落实可信权限（Permission）和隔离（Isolation），再记录可能执行之前的T1与接受结果之后的T2。崩溃恢复（Recovery）先核记录，后按原身份（Identity）调查效果（Effect）；记录无误仍需判断业务条件。能接回已有工作就接回，能根据新观察安全继续就继续，证据不足则保留未知效果（Unknown Effect），不靠盲重试制造确定性。

验证应分别覆盖允许/拒绝的路径与网络、符号链接（Symbolic Link）替换、缺失沙箱（Sandbox）后端、批准（Approval）修订（Revision）冲突，以及客户端（Client）的实际执行边界（Execution Boundary）。故障场景应落在T1前后、效果（Effect）之后、回执（Receipt）之后和T2之后，同时检查资源、重复次数、账本（Ledger）和最终报告。这里是验证方案，没有运行这些实验。

还要分别记录正常完成率、重复效果（Effect）、错误的无效果（Effect）判定、未知效果（Unknown Effect）数量与对账（Reconciliation）成功率。把未知都改写成成功会让指标好看，却破坏了恢复（Recovery）合同。

有T1/T2，为什么仍不能保证恰好一次（Exactly Once）？

本地记录与远端效果（Effect）通常不在同一事务（Transaction）。需要具体接收方的去重或条件提交（Conditional Commit），并说明范围与期限，不能只凭两条标记。

加一个通用唯一标识符（UUID）能无限重试吗？

不能。服务必须原子认领同一键，并定义参数、期限和返回合同；调用方还要持久保留原键。标识本身不执行去重。

已有沙箱（Sandbox），为何还要策略（Policy）与批准（Approval）？

隔离（Isolation）限制可达范围，策略（Policy）判断某次行为是否符合要求，批准（Approval）按具体需求补授权（Authorization）。批准（Approval）也不能修好有缺陷的执行器（Executor）。

权限（Permission）撤回后，把账本（Ledger）写成失败就结束了吗？

没有。需要分别处理未开始、运行中和远端已接受的工作，确认停止或撤销；账本（Ledger）记录事实，不能倒转效果（Effect）。

模型上下文协议（MCP）、客户端能力（Client Capability）与模型服务代执行（Provider-Executed）能共用同一恢复（Recovery）结论吗？

不能仅凭都叫工具就继承保证。要追实际准备、准入（Admission）、执行和持久记录；普通模型上下文协议（MCP）适配器可共用外层T1/T2，客户端（Client）另有接受证据（Acceptance Evidence）与会话级授权记录（Session Grant），模型服务代执行（Provider-Executed）另走模型（Model）内部路径。

更完整的工具发现与协作条件见第56章、第58章。
