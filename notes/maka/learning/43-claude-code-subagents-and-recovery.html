第 43 章｜Claude Code：子任务、隔离与恢复

本章概览

核心问题：Claude Code 委派调查或实施后，怎样核对背景、工作副本和返回结果，并处理取消与恢复？

关键概念：brief（任务说明）：自足的目标与限制；对话分叉：继承选定父背景；worktree（工作副本）：分离文件修改；部分结果：已完成范围与剩余缺口；checkpoint（检查点）：恢复可追踪状态；对账：确认外部效果。

关系主线：输入模式与文件隔离分别选择，子任务返回后由父任务采纳并验收；取消不回滚效果，代码恢复、对话恢复和远端补救各走自己的合同。

所属主题：第39章 协作与恢复；同题对照：Codex 子任务机制；综合设计：第47章。

前置：第42章、第18章 恢复、第23章 委派。

1. 从 Maka 带过来的问题：委派不是任务完成

本章另设一轮扫描器扩展任务：检查三个目录的不同文档规范，同时修正参数处理。用户允许父任务修改实现、必要测试与 README，要求保留已有配置改动并禁止上传；子任务只做调查。这里使用这份新任务范围，不继承第38章“不改 README”的情境。适合独立调查的工作变多，但实现文件仍是一份。主任务可以同时安排“找测试入口”“读文档规范”“分析参数流”，自己保留修改和集成测试的责任。

如果只把目标拆成三个动词，就容易出现三种问题。子任务不知道用户禁止上传；两个子任务都改 scan.py；三个结果都说“完成”，却没人验证组合后的行为。它们分别对应输入缺失、文件冲突、验收缺位。

因此一次委派应该至少说清对象、必要背景、读写范围、产物和停止条件。使用哪个模型是后续选择；模型能力再强，也不能保证猜中未交代的写入边界；必要范围要在委派和执行能力中明确。

2. 先认清三种输入方式

当前官方文档区分从定义与 brief 开始的 non-fork subagent，以及继承父对话的 conversation fork；Skill 的 context: fork 则由 Skill 内容驱动独立任务。Explore/Plan 有更精简的初始化，省略 CLAUDE.md 与父会话 git 状态；关键规则需要写入委派。对话分叉的可用性受运行方式、版本和配置影响。

表 1 / Table 1 · 2. 先认清三种输入方式
选择子任务输入（Input）适用任务最容易遗漏什么
非分叉子任务（Non-fork Subagent）任务 brief 加自身定义及相应初始化材料找一个测试入口、独立阅读模块父任务早先的约束和已读内容
对话分叉（Conversation Fork）从创建时的父对话背景分出工作检查多轮讨论后的设计一致性背景里仍有噪声和过时假设
技能独立上下文（Skill Context）方法正文与调用参数成为任务一套重复使用的调查流程把它误当完整父历史副本

这张表只解释输入的区别，不规定模型必须按一棵固定决策树选择。任务是否足够自足，是我们可以设计并验证的质量标准。

3. 第一张图：上下文和工作区是两条独立轴

图的上半部选择输入，下半部选择文件工作区。“独立上下文”只确定前一项，不能证明文件不会相互覆盖。官方提供 isolation: worktree 的文件隔离选项，但是否使用它是另一项决定；工作副本的创建、保留和清理仍要按所选模式处理。

即使两份 worktree 文件分开，它们也可能访问同一个数据库、同一个远端报告系统、同一个机器本地长期背景目录。工作区隔离减少代码写冲突，不等于所有状态都复制出一份。

4. 正常案例：父任务保留哪项责任

本课将任务拆成三个只读调查，加一个主任务实施。这是教学方案，不是 Claude Code 默认编排。

表 2 / Table 2 · 4. 正常案例：父任务保留哪项责任
工作输入与范围（Input · Scope）输出合同（Output Contract）父任务怎样使用
调查 A：测试入口测试配置与扫描器测试文件入口、实际覆盖、未覆盖用例决定执行哪些检查
调查 B：文档规范三个目录的规则与 README目录差异、冲突项、适用范围选择正确报告和文档内容
调查 C：参数流scan.py 及调用者参数从入口到下游的变化、可疑步骤形成可检验的修复假设
主任务实施三份结果与最新文件实现、测试、README 的统一修改最终测试、diff 与交付

委派之前，主任务已经确认这些调查互不依赖。调查 A 不需要等待实现改完；但最终功能检查必须等实施结束。并行优化的是独立阅读时间，不能打破实际的数据依赖。

调查结果到达时，主任务先核对是否对应当前文件和题设。例如调查 C 说“按空格切分造成错误”，主任务应能追到具体数据流；如果结论只是一句可能性，就仍然是假设。调查 A 的测试命令还要在当前环境执行，子任务找到命令不等于检查通过。

最后进行整体集成验收：普通路径、含空格路径、文档示例与报告输出一致；用户已有配置改动没有被覆盖；禁止上传约束没有失效。父任务应对这项整体验收负责，而不是把三份报告拼起来即交付。

5. 委派与返回结果的参考合同

下面是自拟教学类型，不是 Claude Code Agent 工具 schema。

type DelegationBrief = {
  taskId: string;
  objective: string;
  requiredContext: string[];
  readScope: string[];
  writeScope: string[];
  deliverables: string[];
  stopWhen: string[];
};

type ReturnedWork = {
  taskId: string;
  status: "complete" | "partial" | "blocked" | "stopped";
  findings: { claim: string; support: string }[];
  changedFiles: string[];
  checks: { name: string; outcome: "pass" | "fail" | "not-run" }[];
  unresolved: string[];
};

status 表示这项子工作到了哪一步，不代表父目标状态；checks 区分“发现检查入口”和“执行检查”；changedFiles 让只读任务发生意外修改时不能藏在摘要里。即使所有字段存在，仍需要执行器落实权限，并由父任务核实产物。

对于真实的自定义子任务定义，可以用下面的公开格式教学例子理解范围配置：

---
name: scan-inspector
description: 只读分析扫描器的参数流与相关测试
tools: Read, Glob, Grep
maxTurns: 12
---

围绕委派中的问题读取必要文件。
说明参数在哪一步变化，并给出当前代码支持的理由。
不要把尚未运行的测试写成通过。
无法定位目标时，返回已查范围与缺少的信息。

选择 Read、Glob、Grep 是为了使本例不承担修改或执行测试的任务。若需要运行检查，必须调整任务与实际能力，而不能要求子任务靠缺失的工具完成。maxTurns 给了有限调查边界，触及上限时应接受部分结果并决定后续，而不是自动认为失败等于无价值。

6. 第二张图：从“返回消息”到“接受工作”

图里的检查与接受属于本课设计。公开产品可以提供子任务结果回传，但“得到一条完成消息”和“验收通过”是两件事。

输入不完整时，追加 brief 的目的应是补上具体缺口。例如“排除 vendor 目录，只检查课程样例”，优于“再仔细一点”。发生冲突时，应指出哪条新事实推翻旧假设，避免两个 Agent 反复重复同一结论。

一个可恢复的子任务还可以继续先前上下文；公开文档同时存在一次性类型与可恢复类型，不能把任意子任务都当成能无限继续的工作进程。使用恢复入口前，需要先确认它保留什么身份和材料，而不是重新启动同名任务就当成同一个实例。

7. 并发、冲突与取消的三个推演

推演一：两个子任务都改了同一行。 如果共享目录，后一个操作可能建立在过时观察上。应停止继续叠加修改，读取现态与各方意图，由一个明确责任方整合；如果分开 worktree，则冲突转移到集成阶段，仍需要解决语义一致性。worktree 降低相互覆盖，却不保证两种方案相容。

推演二：父任务收到用户新约束，子任务还在执行旧 brief。 新要求不会因存在父上下文就自动证明已送达每个执行中的任务。教学方案是明确传达新范围；必要时停止相关子任务，再检查它已经做了什么。只在父会话里改一行计划，不是传播完成的证明。

推演三：子任务因预算结束，只完成两个目录。 返回应是 partial，列清覆盖与未覆盖。父任务可以接受已核实的两部分，再安排第三部分，或报告限制。把所有结果丢弃浪费已得信息；把 partial 直接改成 complete 则误报覆盖。

三个推演都要求一个稳定概念：停止控制下一步能否继续，效果检查回答此前发生了什么。 无论产品界面是否能停止任务，都不能据此推断远端效果撤销或本地文件恢复。

8. Checkpoint 的恢复对象必须讲具体

Claude Code 的 checkpoint 提供会话层面的文件撤回选择，/rewind 可选择恢复代码、恢复对话或整理部分对话。覆盖有明确边界：直接文件编辑、Bash 修改、其他子任务和外部修改不具有相同追踪保证；前台运行的 forked Skill 有特定例外，其他子任务编辑通常不被主会话 rewind 恢复。链接文件及快照保留也有限制。

恢复涉及两个独立坐标：

表 3 / Table 3 · 8. Checkpoint 的恢复对象必须讲具体
选择对话状态（Conversation State）文件状态（File State）恢复检查（Recovery）
只恢复对话（Conversation Recovery）回到较早讨论点保留当前文件旧叙述与现有代码是否冲突
只恢复代码（Code Recovery）保留后续讨论在支持范围内恢复历史里的“已修”是否已失效
同时恢复（Combined Recovery）两者都尝试回到选定点仅覆盖可追踪的文件外部效果和未追踪修改仍需查
整理对话（Compaction）用较短材料继续文件不因摘要而恢复关键任务状态是否仍可理解

当只恢复代码时，会话里可能还保留“空格路径测试通过”的旧结果，而当前代码已经回退。那条测试证据仍属于当时被测试的内容，不能直接证明当前文件。反过来，只恢复对话时，模型可能再次提出已经实施过的修改，因此必须先重读文件。

9. 第三张图：恢复后重新建立可信起点

这是一份参考恢复流程，不是声称 Claude Code 内部采用这套持久状态机。尤其不能从“会话可以恢复”推导日志、工具效果和远端请求之间有原子事务。

对于扫描器，若误改文件来自主会话直接编辑，可按产品支持范围考虑 rewind，然后看 diff；若子任务通过 Bash 删除了文件，则需要其他恢复来源；若远端报告已发布，需要远端查询和撤回能力。三者不能共享一条“点击撤销 → 世界回到原状”的箭头。

10. 远端效果未知的完整参考处理

假设任务变成“检查后创建远端工单”。发送请求后超时，父任务不知道是否创建成功。文件 checkpoint 对这个问题没有帮助。

课程方案是给业务动作稳定身份，记录已发出与结果已知的区别；恢复时先查询远端是否存在对应对象，再决定重试。远端若支持幂等键，应把同一逻辑动作绑定同一键；若不支持，就承认查询与重试之间仍可能有竞争窗口，必要时交由人工核对。

这是一份针对远端效果未知的设计方案，不是 Claude Code 内部恢复实现的描述。

11. 什么时候值得委派

表 4 / Table 4 · 11. 什么时候值得委派
情况更合适的起点原因要评价的成本
很短的单文件修改主任务直接完成交接可能比工作本身更重调用与解释开销
独立、大量只读调查自足 brief 子任务可隔离观察噪声并行阅读漏背景与摘要损失
依赖长讨论的一致性检查在可用条件下考虑对话分叉减少手工重述重要背景复制噪声、继承旧假设
并行尝试互斥实现分开文件工作区减少直接覆盖集成与合并成本
多步骤外部写入先建立动作和恢复合同分工不能替代效果管理对账、重试、取消和补救

评价时看整项任务的正确性、总时间、总成本和整合错误。主上下文变小只是一个局部指标；如果父任务要花更多轮纠正遗漏，委派可能得不偿失。

12. 常见场景与完整参考方案

题一：有独立上下文，为什么仍可能互相覆盖代码？

参考答案：上下文决定模型看到什么，工作区决定操作哪份文件。两个独立上下文仍可共享目录。必须明确只读范围、分工或选择独立 worktree，并在集成时处理语义冲突。

题二：Explore 子任务漏掉项目规则，最先检查什么？

参考答案：检查它实际的初始化和委派内容，而不是假设父任务所有材料都继承。对于必须约束调查的规则，把它写进 brief；最终父任务仍在完整任务背景下验收结果。

题三：三个子任务都返回 complete，父任务能直接宣布完成吗？

参考答案：先检查各子任务合同、实际覆盖和未运行检查，再进行组合后的整体验收。子任务 complete 只代表其自身声明的结束状态，不能代替总目标判断。

题四：用户取消后如何交付状态？

参考答案：说明已停止或仍待确认的执行，列出已发生修改、已获得结果和未知效果。不继续旧目标下的相关动作；是否恢复文件或补救远端操作要看用户意图与可用能力。取消不能自动证明没有副作用。

题五：只恢复代码后，之前的测试通过还能用吗？

参考答案：它仅证明当时被测状态。恢复改变了文件，要检查是否仍是相同代码和运行条件；若不是，重新运行相关检查。会话里出现通过记录，不足以证明当前文件正确。

题六：哪些内部问题本课不能替 Claude Code 回答？

参考答案：工具效果与日志的原子顺序、远端动作的 exactly-once 保证、完整取消传播协议、压缩选择器以及所有子任务组合的恢复语义。可以提出自己的设计，但不能将设计名词写成已公开产品事实。

可恢复的并行扫描器：完整参考结果。

输入为三个目录的规范、测试配置和当前 scan.py；约束是禁止上传、子任务只读、父任务负责修改。A/B/C 分别调查测试、目录规则和参数流，工具为 Read/Glob/Grep，返回位置、判断依据、覆盖缺口与检查状态。父任务确认三份结果对应当前文件后，统一实施，再检查普通路径、含空格路径、文档和输出的一致性。

给定 B 到达预算时只查完两个目录，它返回 partial，保留两个目录的结论并列出第三目录未查；没有执行测试的 A/C 把相应检查列为 not-run。若父任务实际运行测试得到失败，则记录该检查 fail，不能因三份调查已结束就宣告修复通过。这里是给定条件下的参考交付，不是一次产品运行报告。

若用户此时取消，父任务停止接纳新的相关动作并传播停止要求，保留已写文件及仍待确认的执行状态；本地追踪文件按支持范围考虑恢复，远端工单则按原业务身份查询。无法确认的远端结果仍为未知。若改用并行实施，独立 worktree 只能把文件冲突推迟到整合，父任务仍需检查语义冲突并复测。

更多完整场景见 第61章 Claude Code 机制设计与第62章 综合案例。其中分别标明产品公开支持的操作和为更强恢复要求增加的参考设计。
