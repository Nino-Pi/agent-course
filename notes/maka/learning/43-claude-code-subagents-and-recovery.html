第 43 章｜Claude Code：子代理（Subagent）的分工、隔离（Isolation）与恢复（Recovery）

本章概览

核心问题：把工作交出去以后，怎样判断返回结果可用，并在中断后继续？

关键概念：子代理（Subagent）是独立执行工作的代理；子任务（Subtask）是交给它的一份工作。任务说明（Brief）交代目标与限制，工作树（Worktree）分开文件修改，结果采纳（Result Adoption）把已核实的产物接回总任务。检查点（Checkpoint）只恢复其支持的状态。

关系主线：先分别选择背景输入与文件范围，再核对返回结果并整体验收（Acceptance）；取消（Cancellation）后检查已发生的效果（Effect），恢复对话、恢复文件和远端补救分别处理。

前情回顾：独立执行为什么仍需要父任务（Parent Task）负责

第 23 章区分了技能说明包（Skill）与子代理（Subagent）：前者提供可重复使用的方法，后者实际承担一份子任务（Subtask）。把工作交出去称为委派（Delegation），但总目标仍需要有人判断。这里把承担分工与交付责任的一方称为父任务（Parent Task）。

第 42 章讲过，规则文件与技能说明包（Skill）只有进入实际输入，才能成为本次判断依据。子代理（Subagent）有自己的上下文（Context），因此“父任务（Parent Task）知道用户禁止上传”不能代替检查接收方是否也拿到了这条约束。

第 18 章则提醒我们：文件已被修改、远端对象已被创建，属于真实效果（Effect）；完成消息属于对它的报告。两者可能不同步。因此本章先解释怎样接回结果，再解释取消（Cancellation）与恢复（Recovery）。所属主题见第 39 章，Codex 的同题机制见第 41 章。

一份明确的子任务（Subtask），比三个宽泛动词更有用

本章另设一轮扫描器扩展任务：检查三个目录的文档规范，同时修正 scan.py 的参数处理。用户允许父任务（Parent Task）修改实现、必要测试与 README，要求保留已有配置改动并禁止上传；交出的调查全部只读。这里不继承第 38 章“不改 README”的情境。

可以把工作拆成“找测试入口”“读文档规范”“分析参数流”，但三个动词还不足以开始可靠的委派（Delegation）。接收方至少需要知道：检查哪些文件、结论给谁使用、什么算有依据、哪些操作不允许、何时该交回未完成范围。

例如，“找测试入口”返回一个命令即可吗？如果父任务（Parent Task）要判断含空格路径的回归风险，还需要知道这个入口实际覆盖什么。找到命令和执行成功是两种不同结果。类似地，“读文档规范”若只读了三个目录中的两个，结论可能有用，却不能宣称已经覆盖全部。

委派（Delegation）首先设计信息与责任的交接。 模型能力不能补回未交代的文件范围，也不能让一条“已完成”消息自动证明总目标达成。

背景输入：三种方式会带来什么

Claude Code 公开说明中，有从定义与任务说明（Brief）开始的非分叉子代理（Non-fork Subagent），也有继承当前父对话的对话分叉（Conversation Fork）。技能说明包（Skill）的 context: fork 又有特定含义：以方法正文与调用参数形成独立任务，不等于复制父对话历史。

这里的 Explore/Plan 类型会省略 CLAUDE.md 与父会话（Session）启动时的 Git 状态材料，因此关键规则要写进任务说明（Brief）。不能让“它可以读取项目”替代“它已经收到该规则”。对话分叉（Conversation Fork）的可用方式还受产品版本、运行模式与配置影响，不能把某个交互模式的默认行为推广到所有调用入口。初始化与分叉说明、技能说明包（Skill）的独立执行。

输入越完整并非总是越好。一个只需定位测试命令的子任务（Subtask），通常不需要整段历史；复杂一致性检查若缺少已经讨论过的约束，又容易返工。选择的依据是“哪些背景决定本次结论”，而不是固定偏好某一种方式。

上下文（Context）与工作树（Worktree）是两条独立轴

上下文（Context）决定模型看到什么；工作区（Workspace）决定工具操作哪里。前者独立，不能推出后者也独立。

图的上半部选背景，下半部选文件位置。Git 工作树（Worktree）是同一仓库的另一份检出，可以让文件修改分开；泛指一份可改文件副本时，本课使用工作副本（Working Copy）。Claude Code 提供 isolation: "worktree" 选项，但创建、保留和清理仍按所选产品模式处理，不能由“独立上下文（Context）”自动推断已启用它。

即使文件位于两份工作树（Worktree），它们仍可能访问同一个数据库、远端报告系统或机器上的长期背景目录。文件隔离（Isolation）减少直接覆盖，无法保证所有可访问状态都复制了一份。相应地，共享工作区（Workspace）也不必然有问题：本例三个调查只读，父任务（Parent Task）统一修改，就是一种清楚的分工。

正常过程：从调查结果到整体验收（Acceptance）

本课采用三个只读调查，加一项统一实施。这是教学方案，不是 Claude Code 默认生成的固定流程。

表 2 / Table 2 · 正常过程：从调查结果到整体验收（Acceptance）
工作输入与范围返回内容父任务（Parent Task）怎样使用
调查 A：测试入口测试配置与扫描器测试文件入口、实际覆盖、未覆盖用例决定执行哪些检查
调查 B：文档规范三个目录的规则与 README目录差异、冲突项、适用范围选择报告与文档的正确内容
调查 C：参数流scan.py 及调用者参数从入口到下游的变化、可疑步骤形成可检验的修复假设
统一实施三份调查结果与最新文件实现、测试、README 的一致修改检查组合后的行为与最终交付

A/B/C 的独立性在分工前已经确认：找测试入口不需要等待修改完成，阅读目录规则也不依赖参数流结论。但最终功能检查依赖新实现。并行（Parallelism）能重叠独立调查的时间，不能消除数据依赖。

结果到达以后，先做结果采纳（Result Adoption）：它是否对应当前文件？是否回答了原问题？判断依据能否定位？例如 C 说“按空格切分导致错误”，父任务（Parent Task）应能沿具体数据流确认；若只有猜测，就继续把它当作假设。

之后才是整体验收（Acceptance）：普通路径与含空格路径是否都正确，文档示例与报告输出是否一致，已有配置修改是否保留，禁止上传约束是否仍满足。三份合格调查并不能单独证明组合后的修改正确。结果采纳（Result Adoption）认可一份局部产物，整体验收（Acceptance）判断总目标。

把任务说明（Brief）与返回结果写成可检查的结构

下面两组类型是自拟教学合同，不是 Claude Code 工具的真实接口。第一组回答“交出什么”；第二组回答“实际做了什么”。阅读时按身份（Identity）、范围、依据、检查、缺口五组信息理解，不必逐字段背诵。

type DelegationBrief = {
  // 身份（Identity）用于把返回结果对应到这次子任务（Subtask）。
  taskId: string;
  objective: string;
  requiredContext: string[];
  // 范围须由实际执行能力落实，字段自身不会阻止越界写入。
  readScope: string[];
  writeScope: string[];
  deliverables: string[];
  stopWhen: string[];
};

type ReturnedWork = {
  taskId: string;
  status: "complete" | "partial" | "blocked" | "stopped";
  // 判断和支撑材料一起返回，便于父任务（Parent Task）核实。
  findings: { claim: string; support: string }[];
  changedFiles: string[];
  // 发现检查入口不等于执行检查，未运行保留 not-run。
  checks: { name: string; outcome: "pass" | "fail" | "not-run" }[];
  unresolved: string[];
};

这份结构的消费者（Consumer）是父任务（Parent Task）。status 描述局部工作的状态，checks 描述实际检查，changedFiles 则让只读调查中的意外修改不能藏在一句摘要（Summary）里。字段齐全仍需要核实内容；真实权限（Permission）也必须由执行器落实。

假设 B 在预算内只读完两个目录，它应返回 partial，给出已核实的两部分，并把第三目录列入 unresolved。父任务（Parent Task）可以采纳仍适用的事实，再补齐第三部分。这个处理既保留已完成工作，也避免把部分结果（Partial Result）误报成完整覆盖。

实际的自定义子代理（Subagent）可以采用下面的公开定义格式。这里选择 Read、Glob、Grep，把职责限制为阅读与定位；它不是一个负责运行测试的定义。

---
name: scan-inspector
description: 只读分析扫描器的参数流与相关测试
tools: Read, Glob, Grep
maxTurns: 12
---

围绕委派中的问题读取必要文件。
说明参数在哪一步变化，并给出当前代码支持的理由。
不要把尚未运行的测试写成通过。
无法定位目标时，返回已查范围与缺少的信息。

若需要执行检查，就要调整子任务（Subtask）范围与实际可用工具，不能要求它凭缺失能力完成。maxTurns: 12 限制代理循环（Agent Loop）的轮次数，并非词元（Token）、费用或墙钟时间上限。Claude Code v2.1.246 起会把达到该上限的输出标记为部分结果（Partial Result）；较旧版本不能默认按同一呈现判断。

结果采纳（Result Adoption）：返回之后还有一轮判断

这张图表达课程的判断流程。产品负责回传结果，并不意味着它替你证明每一项业务条件都满足。

缺少背景时，补充任务说明（Brief）应指出具体缺口，例如“排除 vendor，只检查课程样例”，而不是重复“再仔细一点”。发现冲突时，要指出哪条新事实推翻旧假设；反复发送原问题不会自动带来新的依据。

继续调查也有两种动作：新建一个子代理（Subagent），或者沿已有身份（Identity）继续先前工作。公开文档中的 Explore/Plan 是一次性类型，不返回可继续使用的代理身份（Identity）；支持继续的类型则可保留原对话历史。达到 maxTurns 后，能否接着做还要看返回的身份（Identity）与类型条件。重新启动同名工作不能直接当成同一个实例。继续已有子代理（Subagent）的条件。

三种变化条件：冲突、取消（Cancellation）与部分结果（Partial Result）

变化一：违反只读合同，两个子代理（Subagent）都改了同一行。 这已经偏离本例授权范围。共享目录中的后一个操作可能建立在过时观察上，应停止继续叠加，读取现态与各方意图，由明确负责者（Owner）整合。若另设经授权的并行实施，分别使用工作树（Worktree）可以把直接覆盖转为集成时处理，但仍不能保证两份实现语义相容。

变化二：父任务（Parent Task）收到用户新限制，接收方仍在执行旧任务说明（Brief）。 新要求存在于父对话中，不是它已送达每个接收方的证明。应传达具体变化；需要停止的工作要发出取消（Cancellation），并核对已经发生的修改。仅更新父任务（Parent Task）的计划，不等于传播完成。

变化三：B 只完成两个目录。 返回部分结果（Partial Result）并保留覆盖缺口，父任务（Parent Task）核实后决定补查或报告限制。把全部产物丢弃会浪费已有信息，把 partial 改成 complete 则掩盖缺口。

三种情况都要区分：停止是在控制下一步，效果（Effect）检查是在确认此前发生了什么。取消（Cancellation）本身不会撤销远端对象，也不能证明文件已回到原状。

检查点（Checkpoint）究竟恢复什么

Claude Code 的检查点（Checkpoint）提供会话（Session）层面的撤回入口。/rewind 可以恢复代码、恢复对话、同时恢复，或整理对话，但不同修改并不具有同样的追踪范围。

快照（Snapshot）也不是永久存档：可用范围受数量和保留期限制。工作轮次（Turn）中途加入的消息通常不单独创建检查点（Checkpoint）；回到启动该轮的提示，会连同该消息到达前的本轮工作一起处理。因此先选清楚恢复对象与时间点，再看实际结果。检查点（Checkpoint）的支持范围。

对话恢复（Conversation Recovery）回到较早讨论点保留当前文件旧叙述是否已落后于代码

例如，只恢复代码以后，对话里仍可能保留“含空格路径测试通过”。那条记录证明的是当时被测内容，不能直接证明当前文件。反过来，只恢复对话以后，模型可能再次提出已经实施的修改，因此应先重读文件。恢复（Recovery）的第一项产物，是一个重新核对过的起点。

恢复（Recovery）后怎样重新建立起点

这是一份参考处理流程，不是 Claude Code 内部持久状态机（State Machine）的实现图。文件、对话与远端对象未必共用原子事务（Atomic Transaction），因此每条分支都要回到事实检查。

在基本扫描器任务中，主任务直接编辑造成的误改，可按支持范围使用 /rewind 后检查差异（Diff）；如果违规子任务（Subtask）通过 Bash 删除文件，就需要其他恢复来源。两者都不能只凭“撤回已结束”判断修复后的行为正确。

下一节单独增加经用户批准的远端写入情境。它不属于前面“禁止上传”的基本任务；引入它是为了说明文件恢复（Recovery）无法覆盖另一系统里的效果（Effect）。

未知效果（Unknown Effect）：先对账（Reconciliation），再决定重试

现在改用新的授权条件：用户允许检查后创建一个远端工单。请求发出后超时，父任务（Parent Task）不知道远端是否已经创建成功。即使把本地代码恢复到此前状态，也回答不了这个问题。

教学方案是给该逻辑动作一个稳定身份（Identity），把“请求已发出”和“结果已确认”分开记录。恢复（Recovery）时按原身份（Identity）查询，这个过程称为对账（Reconciliation）。若接收方支持幂等键（Idempotency Key），重复同一逻辑请求可以按其合同返回已有对象，而不重复增加业务效果（Effect）；这种性质称为幂等性（Idempotency）。

查询结果必须足以确认同一对象；一次暂时“查不到”不必然证明从未创建。接收方若没有原子去重（Atomic Deduplication），两个执行者（Worker）还可能同时查不到，然后各创建一次。条件不足时保持未知效果（Unknown Effect），报告缺少哪项依据，必要时由人核对，不能直接改成失败后无条件重试。

这里设计的是应用层恢复（Recovery）合同，没有声称 Claude Code 已在内部实现这套协议。第 44 章将进一步解释，为什么可靠的控制重放（Replay）也不能单独提供外部效果恰好一次（Exactly Once）。

问答与完整参考结果

独立上下文（Context）为什么仍可能互相覆盖代码？

它决定模型的输入，不决定文件位置。两个子代理（Subagent）仍可共享目录。只读分工、明确写入范围或独立工作树（Worktree）处理不同问题，最终还要检查组合后的语义。

Explore 漏掉项目规则，最先检查什么？

检查实际初始化和任务说明（Brief），不能假定父任务（Parent Task）的全部材料都被继承。必须约束调查的规则要明确传达，返回后仍在总任务条件下验收（Acceptance）。

三个子任务（Subtask）都返回 complete，能宣布总目标完成吗？

先核对各自范围、依据与未运行检查，再验收（Acceptance）组合后的状态。局部完成声明无法替代总目标判断。

用户取消（Cancellation）后应交代什么？

哪些执行已停止、哪些仍待确认，文件已有何种修改，哪些结果已取得，哪些效果（Effect）仍未知。停止后是否恢复文件或补救远端操作，取决于用户意图与实际能力；取消（Cancellation）不能证明没有副作用（Side Effect）。

代码恢复（Code Recovery）后，之前的测试通过还能用吗？

先确认是否仍对应同一代码和运行条件。状态改变后应重新验证相关行为；会话（Session）中的通过记录不足以证明当前文件正确。

哪些内部保证不能从本章公开行为推出？

工具效果（Effect）与日志的原子顺序、外部效果恰好一次（Exactly Once）、完整取消（Cancellation）传播、上下文压缩（Context Compaction）选择器，以及任意子代理（Subagent）组合的恢复（Recovery）语义。可以提出更强设计，但必须与产品事实分开。

完整参考结果仍回到最初的只读调查任务：输入是三个目录规范、测试配置与当前 scan.py，禁止上传，父任务（Parent Task）保留实施责任。A/B/C 使用 Read/Glob/Grep，分别给出位置、依据、覆盖缺口和检查状态。父任务（Parent Task）确认结果仍对应当前文件后，统一修改并检查普通路径、含空格路径、文档和报告的一致性。

给定 B 只读完两个目录，它返回 partial；没有执行测试的 A/C 保留 not-run。若父任务（Parent Task）实际检查得到失败，则该项为 fail，不能因三份调查结束而宣告修复成功。这是给定条件下的教学交付，不是一次产品运行报告。

若此时收到取消（Cancellation），停止接纳相关新动作，传播停止要求，保留已发生修改及仍待确认的执行状态；本地文件按支持范围处理。只有在前述另行授权的远端变体中，才继续按原业务身份（Identity）对账（Reconciliation），无法确认时保留未知效果（Unknown Effect）。若另行改为并行实施，工作树（Worktree）仍需集成与复测。
