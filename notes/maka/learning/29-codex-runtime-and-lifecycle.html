第 29 章｜Codex：运行时（Runtime）与任务生命周期（Task Lifecycle）

本章概览

核心问题：用户中途改要求、停止工作或关闭连接时，输入与执行怎样分别变化？

关键概念：任务线程（Thread）组织持续对话；接纳（Admission）决定输入属于哪轮工作；步骤快照（Step Snapshot）固定本次请求的配置与能力视图；引导消息（Steering）在允许边界进入后续决策；取消（Cancellation）要求停止推进。

关系主线：应用服务（App Server）把输入交给执行内核（Core），负责者（Owner）决定接纳（Admission）与消费；终态（Terminal State）、效果（Effect）和连接资源各有边界，关闭界面不能替它们作出同一个判断。

前情回顾：工作身份（Identity）、观察与资源寿命怎样分开？

第13章用会话（Session）、工作轮次（Turn）与执行（Run）区分长期工作、一次接纳（Admission）和实际推进。第14章说明，持久保存的事件（Event）与界面投影（Projection）是不同对象。第25章进一步问：观察连接消失时，谁仍持有工作，具体进程又由谁负责？

这三个问题可以带到 Codex，但名称不能直接替换。下面的任务线程（Thread）是产品中的对话容器，不是操作系统线程（Operating System Thread）；执行内核（Core）中的会话（Session）是管理活跃任务的对象。同名或相似名词不自动给出相同的持久化与恢复（Recovery）合同。

本章开始一个独立的 Python 文档检查器案例：用户要求“修复带空格的路径处理，更新 README，并运行相关测试”；读取期间补充“仅修改检查器，暂时不要改 README”；测试尚未结束时又要求停止。三句话按顺序改变任务条件。后文另将最后条件换成“只断开连接，不请求停止”，以比较资源寿命。

案例时点和下面的接口均为教学推演，不是实际 Codex 运行记录。源码主线限定为应用服务（App Server，代码目录 app-server）进入执行内核（Core，代码目录 core）的路径；其他宿主（Host）的接线需另行核对。

1. 工作身份（Identity）、执行状态（State）与显示内容

如果客户端（Client）收到输入就启动模型（Model）、收到增量就更新聊天框，还在界面里执行工具调用（Tool Call），它可以演示代理循环（Agent Loop）。但另一个窗口加入、用户修改要求或界面退出后，就必须回答：哪个对象拥有工作，哪个对象只是观察者？

Codex 的产品协议以任务线程（Thread）、工作轮次（Turn）和过程项（Item）表示工作；执行内核（Core）的会话（Session）则持有活跃任务、输入队列（Input Queue）和历史（History）。先按责任读下面的表。

表 1 / Table 1 · 1. 工作身份（Identity）、执行状态（State）与显示内容
对象它回答的问题本例内容不能由此推出
任务线程（Thread）后续输入属于哪段对话？检查器修复对话此刻一定仍在执行
工作轮次（Turn）哪一轮工作接纳（Admission）了输入？修复路径处理这一轮只调用过一次模型（Model）
过程项（Item）本轮产生哪些可观察单元？消息、命令、文件变化每项都是独立用户任务

一次工作轮次（Turn）可以包含多次模型调用（Model Query）、工具调用（Tool Call）和上下文压缩（Context Compaction）。Maka 的执行（Run）与 Codex 的过程项（Item）因此不能机械一一对应；应比较谁接纳（Admission）、谁执行、谁保存、谁展示。

2. 接纳（Admission）响应与执行结果分两条路径

先看责任图。它概括所讲调用链，不把每个方框当成独立进程。

客户端（Client）先完成初始化握手，再创建或恢复任务线程（Thread），然后提交工作。即时响应回答“这次提交怎样处理”；后续通知回答“工作怎样发展”。如果收到前者就显示成功，测试（Test）可能还未开始。

沿最初任务，实际责任依次是：应用服务（App Server）转换输入及设置，执行内核（Core）判断去向；新工作启动时处理输入及钩子（Hook）；步骤快照（Step Snapshot）确定本次配置、工具和权限（Permission）；模型（Model）提出读取动作，运行时（Runtime）执行后返回观察结果（Observation）；满足继续条件才生成下一次请求，最后报告终态（Terminal State）。

3. 步骤快照（Step Snapshot）为什么要在请求前固定？

假设用户界面（User Interface，UI）刚收窄写权限（Permission），同时模型上下文协议（Model Context Protocol，MCP）的某个工具发生变化。若声明取自时刻A、注册表（Registry）取自B、执行设置取自C，模型（Model）看到的工具合同就可能无法解释随后的执行。

需要保留的不变量（Invariant）是：同一次请求所展示的工具能力，必须能关联到处理返回调用的那份路由与配置。 这不要求整个进程停止变化，而是要求这次请求有一致的解释依据。

StepContext 保存已解析设置、当次模型上下文协议（MCP）绑定和工具路由器（Tool Router）。主循环在一步中捕获它，记录本步环境状态（World State）的变化，再从历史（History）生成适合模型（Model）输入模态的表示并采样。工具声明与返回调用共享本步视图，后续刷新不追溯改变已发请求的解释。步骤快照（Step Snapshot）源码

表 3 / Table 3 · 3. 步骤快照（Step Snapshot）为什么要在请求前固定？
时点消费哪些材料本步结果
采样前已接纳（Admission）输入、钩子（Hook）、环境捕获配置与能力视图

这样既能在步骤之间吸收更新，又避免一步内任意错配。它不保证刚收窄权限（Permission），已经发到外部系统的请求就被撤回；在途动作的取消（Cancellation）和效果（Effect）仍需单独判断。

4. 引导消息（Steering）：改变后续输入，不改写过去

用户在读取时补充“不改 README”，可以向活跃工作轮次（Turn）提交引导消息（Steering）。它先进入输入队列（Input Queue），到允许的步骤边界才经处理写入历史（History），参与后续模型输入（Model Input）。

主循环保留两个排序条件：新工作轮次（Turn）的原始输入先被采样；自动上下文压缩（Context Compaction）之后，如果模型（Model）或工具（Tool）需要先延续，取出引导消息（Steering）可能暂缓。所以“接纳（Admission）了”与“当前请求已看见”有时间差。

图示假定补充约束赶在后续修改前生效。若 README 此前已改，后续应检查并说明已有变化，按最新意图处理；不能把历史（History）写成从未修改。

预期身份（Expected Identity）怎样防止误投？

显式引导入口 steer_turn 带有 expected_turn_id。用户看见的是旧工作轮次（Turn），服务端却可能已开始另一轮；负责者（Owner）必须在接纳（Admission）时核对目标，不能只相信客户端（Client）先前的忙闲判断。

下面用两段教学代码表达接口及其消费者（Consumer）。先读两种意图和三种结果：普通提交允许开始或加入；显式引导必须匹配目标。

// 教学类型；不是 Codex 的公开应用程序编程接口（API）。
type SubmitResult =
  | { kind: "started"; turnId: string }
  | { kind: "steered"; turnId: string }
  | { kind: "not_submitted"; reason: string };

type InputIntent =
  | { mode: "start_or_steer"; text: string }
  | { mode: "steer"; expectedTurnId: string; text: string };

消费者（Consumer）只模拟空闲、普通活跃工作和收束三种情形。检查与变更都在一次同步调用内完成，中间没有让出执行的等待点。

const owner = {
  closed: false,
  activeTurnId: null as string | null,
  nextId: 1,
  queue: [] as string[],
  acceptInput(intent: InputIntent): SubmitResult {
    // 先判收束；拒绝分支不能把输入留进队列。
    if (this.closed) return { kind: "not_submitted", reason: "draining" };
    if (intent.mode === "steer" && intent.expectedTurnId !== this.activeTurnId)
      return { kind: "not_submitted", reason: "turn_mismatch" };
    if (this.activeTurnId !== null) {
      this.queue.push(intent.text);
      return { kind: "steered", turnId: this.activeTurnId };
    }
    const turnId = `T${this.nextId++}`;
    this.activeTurnId = turnId;
    this.queue.push(intent.text);
    return { kind: "started", turnId };
  },
};

// 教学接口：状态判断与接纳（Admission）位于同一负责者（Owner）。
async function submit(intent: InputIntent): Promise<SubmitResult> {
  return owner.acceptInput(intent);
}

5. 取消（Cancellation）停止什么，又留下什么？

用户要求停止时，turn/interrupt 指定任务线程（Thread）和工作轮次（Turn）。内核传播取消令牌（Cancellation Token），然后中止与清理。abort_all_tasks 先让任务观察取消（Cancellation），再清除待处理批准（Approval）；否则等待被丢弃可能先被误表示成权限拒绝（Permission Denial）。

表 4 / Table 4 · 5. 取消（Cancellation）停止什么，又留下什么？
停止时点控制的目标仍需核对
等待模型（Model）响应停止等待或继续采样服务是否已计算或计费
等待批准（Approval）结束等待并正确表达中断没有误写为模型（Model）收到拒绝
文件已经修改停止后续推进当前文件及用户需要怎样处理
后台终端（Background Terminal）运行中中断该工作轮次（Turn）具体终端进程是否仍存活

取消（Cancellation）不等于事务回滚（Transaction Rollback），也不能代替后台终端（Background Terminal）的独立清理。即时成功响应后仍应观察终态（Terminal State）。这条协议的工作状态使用 inProgress/completed/interrupted/failed，不能直接借用别的系统的 cancelled 枚举。

教学状态模型可分别记录“已经请求停止”“执行已结束”“效果（Effect）已知或未知”。这些是要区分的事实，不是本章声称产品存在一个 cancel_requested 字段。若第一轮尚未结束就开始冲突操作，单个界面布尔值无法保护文件。

6. 历史重建（History Reconstruction）、继续工作与转交执行权（Execution Authority）

恢复（Resume）已有任务线程（Thread）通常先重建历史（History），再继续工作。历史重建（History Reconstruction）会选择仍有效的上下文压缩检查点（Compaction Checkpoint），按顺序处理幸存尾部记录及上下文基线；它不搬运程序栈、套接字（Socket）或每个等待对象。

只断开连接：同一测试命令可以有三种寿命

现在明确改变案例：测试（Test）仍在运行，只关闭连接，不发送取消（Cancellation）。相同文字的命令可能来自普通工作轮次（Turn）的工具调用（Tool Call），也可能经连接拥有的 command/exec 或 process/* 创建。先确认入口，再讨论是否继续。

连接清理先关闭远程过程调用（Remote Procedure Call，RPC）接纳（Admission）门，等待有界收束，再清理各类连接资源。它按负责者（Owner）处理，没有将所有活动统一改成已取消的动作。

tunload=max⁡(ts,ti)+Δ.t_{\mathrm{unload}}=\max(t_s,t_i)+\Delta.tunload​=max(ts​,ti​)+Δ.

任一条件不成立，就没有这个卸载（Unload）目标；新观察到的活动还可能刷新计时。这里的活跃（Active）按 ThreadStatus::Active 跟踪，不能靠聊天框是否吐字推断。到时再次核对条件，处理已无人回答的回调（Callback），等待关闭后，以运行实例身份（Runtime Identity）匹配才移除对象；失败或超时另有分支，迟到的卸载（Unload）不能删除同名新实例。

这也能重新解释第25章的四组坐标：HHH 是控制责任，WWW 是工作状态，VVV 是观察连接，EEE 是执行资源及结果。VVV 消失时 WWW 可以仍在；若 EEE 本来属于该连接，清理会主动改变 EEE。历史（History）可读不证明进程仍活着，发送终止控制也不证明效果（Effect）未发生。

部署条件：本地子进程、托管执行与工作树（Worktree）

官方发布时的应用服务（App Server）设计区分本地与托管场景：本地应用或集成开发环境（Integrated Development Environment，IDE）可以启动长期子进程，保持标准输入输出（Standard Input/Output，stdio）通道；网页场景由服务端工作者（Worker）在容器（Container）中维持执行，浏览器只接收事件。后一种设计允许标签关闭而工作继续，不能推导所有本地应用退出都有相同行为。发布时部署设计

另一篇发布说明用任务线程（Thread）组织并行工作，并以工作树（Worktree）隔离代码副本。这解决文件落在哪份副本的问题，不保存进程内存、套接字（Socket）或远端效果（Effect）；也不表示所有桌面入口自动创建副本。工作树设计说明

需要另一客户端（Client）接手时，审阅补丁可从文件和持久结果开始；继续活跃执行还须确认应用服务（App Server）、进程及负责者（Owner）可用。关闭标签、本地管理进程退出和换工作树（Worktree）改变的是不同条件。

等待批准（Approval）时停止先传播取消（Cancellation），再清等待后续终态（Terminal State）确认中断，已改文件仍需检查
command/exec 启动测试后断开清理所属句柄（Handle），不加入重连队列（Queue）发送 Terminate，实际退出与文件变化另查

问题。 普通任务线程（Thread）仍活跃，另一条相同命令由断开的连接通过 command/exec 启动，两者都能称为“重连继续”吗？换成网页标签或新工作树（Worktree）又怎样？

参考答案。 不能。第一条观察连接的清理不普遍中断工作，仍需查询具体工具状态；第二条会收到终止控制。托管网页设计改变应用服务（App Server）所在位置，新工作树（Worktree）改变文件副本，两者都不自动证明进程或效果（Effect）已迁移。

问题。 用户刚追加“不改 README”，为什么还要检查当前差异（Diff）？

参考答案。 引导消息（Steering）只在后续允许边界被消费。README 可能已经改变，必须保留当时事实，再按最新意图处理。显式目标标识解决误投问题，不能把时间倒转。

问题。 关闭用户界面（UI）、中断工作轮次（Turn）与停止后台终端（Background Terminal）能共用一个“停止”按钮状态吗？

参考答案。 展示可以简洁，内部事实仍需分开：观察是否断开、工作是否结束、进程是否退出、效果（Effect）知道多少。它们如何互相触发由具体入口的合同决定。

问题。 与 Maka 比较时应该保留哪些条件？

参考答案。 固定任务范围、在途时点、执行入口和部署，比较身份（Identity）、接纳（Admission）、新输入生效点、结果通知及恢复（Recovery）边界。单进程脚本可以先有清晰循环与日志；有多入口和频繁纠正时再增加相应机制，不能按类名数量排名。

工具执行机制见第32章，同类设计场景见第60章。下一章用相同反馈问题阅读 Claude Code 的公开行为。
