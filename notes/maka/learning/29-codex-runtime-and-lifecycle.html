第 29 章｜Codex：运行时与任务生命周期

本章概览

核心问题：用户中途改要求、停止工作或关闭连接时，Codex 的输入与执行怎样分别变化？

关键概念：Thread（会话）：持续工作的上下文容器；请求接纳：确认输入去向；步骤快照：本步固定的配置与工具视图；steering（中途输入）：在允许边界进入后续决策；取消：传递停止请求并收束执行；连接资源：按连接管理的命令进程。

关系主线：应用服务层将请求交给执行内核，接纳后的输入按步骤消费；终态、效果结算与连接资源清理各有边界，不能由关闭窗口互相推断。

所属主题：第28章 架构与生命周期；同题对照：Claude Code 循环。

贯穿案例是修复一个 Python 文档检查器。用户最初要求“修复带空格的路径处理，更新 README，并运行相关测试”；模型读取代码期间，用户补充“仅修改检查器，暂时不要改 README”；测试还没结束，用户又要求停止。我们逐步推导这三句话怎样影响运行。

本章讲的是本地源码中经 app-server 进入 core 的一条路径。其他宿主可以复用 core，也可能采用不同的接线。这里的接口片段是教学模型，不是可复制调用的产品 API。

与 第25章 Host的连接问题对照时，需要区分三项机制：请求接纳、连接资源的 owner与部署条件。

1. 先拆开工作身份、执行状态和显示内容

一个客户端很容易写出这样的代码：收到用户输入就启动模型，收到 token 就追加到聊天框，遇到工具调用就在前端执行。如果用户永远只开一个窗口、一次只发一个要求，而且程序永不退出，这个方案能够演示基本循环。复杂性从“同一个任务还有别的观察者和控制者”开始。

Codex 的 app-server 协议用 Thread、Turn、Item 描述工作。Thread 标识一段可继续的对话；Turn 是一次工作过程；Item 是过程中的消息、命令、文件变化或其他可观察单元。执行内核中的 Session 则持有活跃任务、输入队列和历史等运行状态。它们分别回答不同问题。

表 1 / Table 1 · 1. 先拆开工作身份、执行状态和显示内容
对象它回答的问题贯穿案例中的内容不能从它推出什么
会话（Thread）后续输入属于哪段对话？检查器修复对话这个对话此刻一定正在运行
工作轮（Turn）哪一轮工作接纳了输入？修复路径处理这一轮只调用过一次模型

步骤上下文快照（Step snapshot）这次模型请求使用什么环境和能力？当前工具、权限、世界状态后续请求永远沿用同一配置

Maka 的 Session/Turn/Run 强调执行生命周期；Codex 的 Thread/Turn/Item 同时承担产品观察协议。迁移时应该对照责任，而不是把名称直接替换。例如 Codex 的一次 Turn 可以包含多次模型请求、多次工具执行和一次中途压缩，不能机械地把它当成 Maka 的某一次模型调用。

2. 从协议到内核：请求被接纳与工作完成有两次确认

下图区分请求接纳与后续执行。

客户端先初始化协议，再创建或恢复 Thread，然后提交工作。请求的即时响应解决“服务器是否接纳这次提交”；之后的进度与终态通知解决“这轮工作实际怎样发展”。如果把二者合并，客户端就容易在请求返回时显示“完成”，但测试可能尚未开始。

以最初的修复任务为例：

  1. 客户端提交输入和目标 Thread。服务端检查输入与线程状态，并把工作交给 core。
  2. core 判断可以开始新 Turn，还是应该把输入加入已运行的 Turn，或当前状态不允许提交。
  3. 新工作启动后，core 准备当轮状态，接纳输入并经过输入相关 hooks。
  4. 本步确定执行环境、工具表面和权限，组装模型请求。
  5. 模型输出读取文件的动作，runtime 执行并写回观察。
  6. 执行状态、预算等继续条件允许时，根据模型延续需求或已接纳输入进入后续步骤。
  7. 工作结束或被打断后，客户端收到该 Turn 的最终状态。

接纳结果分为 Started、Steered、NotSubmitted：Started 表示开始新 Turn，Steered 表示输入交给已运行的 Turn；NotSubmitted 表示没有记录或排队接纳该输入，调用者不能将它视为等待模型回复；明确这一区别，才能判断是否重新提交。

3. 为什么每一步要抓取同一份上下文快照

假设 UI 刚把写权限收窄，同时一个 MCP 工具发生变化。若工具声明来自时刻 A、执行 registry 来自时刻 B、权限读取又来自时刻 C，模型看到的合同与实际执行环境可能不一致。

本地 Codex 主循环在一个 step 中抓取上下文，让上下文、模型可见工具和工具调用共享本次请求视图。随后把 world state（本步环境与配置背景）的变化记录到历史，投影适合模型输入模态的 history，再执行采样。StepContext 明确持有当次解析后的设置、MCP binding 和 ToolRouter；后续设置刷新不会追溯改写已发请求的解释。这种快照不是把整个进程冻结，而是给本次请求一个清楚的解释边界。

表 2 / Table 2 · 3. 为什么每一步要抓取同一份上下文快照
时点输入（Input）本步动作（Action）产生的结果
采样前已接纳的用户输入、当前环境处理输入与 hooks，抓取 step 上下文本步配置与能力视图

采样中模型输出流展示增量、识别工具调用文本进度或待执行调用
执行后工具结果与 pending input判断是否需要后续采样下一步或收尾
窗口不足预算状态、继续需求进入适用的上下文处理分支新窗口中的继续工作

这里的权衡是：逐步抓取能够在步骤之间吸收更新；本步一致性又避免声明与执行随意错配。它不表示用户刚点权限按钮，已经发到外部系统的请求就会自动撤回。对在途动作仍需要独立的取消和效果判断。

4. 用户补充要求：steering 是排队输入，不是改写已经执行的过去

现在用户在读文件时补充：“仅修改检查器，暂时不要改 README。”这不是一个新项目，也不一定需要关闭当前工作重新开始。steering 表示把新输入交给正在进行的正常 Turn。

本地循环会在允许的步骤边界读取 pending input，经过输入处理后写入历史，再生成后续模型请求。它有两个明确的排序考虑：新 Turn 的原始输入先被采样；中途压缩后，如果模型或工具的延续需要先恢复，steering 可能暂缓到之后读取。因此“接纳了补充要求”与“当前在途采样已看到补充要求”有时间差。

补充约束在图示边界进入后续请求。如果 README 已经在补充输入到达前修改，正确后续可能是识别已有改动、说明情况并按最新意图处理；不能把历史伪装成从未修改。

显式 steer 还携带预期的活跃 Turn 身份。如果用户界面显示的是旧 Turn，但服务端已经完成旧工作、开始另一轮，带身份的检查可以拒绝误投。这样的接口避免“检查当前忙不忙，再另发输入”的时间竞争。

教学上可以写成：

type SubmitResult =
  | { kind: "started"; turnId: string }
  | { kind: "steered"; turnId: string }
  | { kind: "not_submitted"; reason: string };

type InputIntent =
  | { mode: "start_or_steer"; text: string }
  | { mode: "steer"; expectedTurnId: string; text: string };

// 教学接口：状态判断与接纳应位于同一个负责执行权的组件。
async function submit(intent: InputIntent): Promise<SubmitResult> {
  return owner.acceptInput(intent);
}

这段代码刻意不让客户端先 isRunning() 再决定调用哪个底层函数。两个请求之间状态可以改变，把选择交给 owner 才能给出有意义的接纳结果。

5. 取消：停止继续推进，需要按执行阶段判断已经发生的效果

用户点击停止时，协议请求的是取消指定 Turn。内核向任务传播 cancellation token，并进入任务中止与清理流程。相关代码还注意一个顺序：让任务先观察取消，再清除等待中的批准，避免原本是用户打断，却被误投影为模型收到了一次权限拒绝。

但取消不等于事务回滚。它至少涉及四种不同情况。

表 3 / Table 3 · 5. 取消：停止继续推进，需要按执行阶段判断已经发生的效果
取消发生的位置可合理期待的行为仍要单独检查的事实
等模型响应停止等待或继续采样外部服务是否已计算、是否已计费
等用户批准结束在途等待，输出正确的中止语义等待结果是否被误当作拒绝
文件修改后停止后续工作，保留已发生事实文件内容、是否需要按用户意图恢复
后台终端运行中结束该 Turn 的推进终端进程是否仍存活

app-server 协议明确将 Turn 中断与后台终端清理区分开。由此可见，UI 上“已停止”必须说明停止的是哪一种活动。对应的状态模型把 cancel_requested、执行已结束、外部效果状态分开保存；单个 UI 布尔值无法表达这些组合。

同样，客户端收到取消请求的即时成功响应后，应继续观察终态通知，以确认该 Turn 的中断流程已经结束。否则用户可能立即发起第二个具有冲突副作用的任务，而第一轮尚未完全停止。

6. 继续对话、恢复历史、迁移执行权，是三个动作

继续对话通常需要恢复已存的 Thread 和历史，再开始后续工作。它不意味着把程序栈、socket 和每一个等待对象原样搬回来。Codex 的历史重建代码会寻找仍然有效的压缩 checkpoint，再按顺序重放幸存的尾部记录，同时恢复上下文基线与窗口等元数据。

本地还存在只在空闲时恢复原 Turn 身份的入口，以及为执行权转交准备的 suspend/shutdown 路径。后者强调执行停止、历史 flush 和 writer 关闭后，才算满足转交前提；对于排队输入、批准等等待对象，不能据此宣称强保证。这是一个比“断线后重新连接”更严格的问题。

表 4 / Table 4 · 6. 继续对话、恢复历史、迁移执行权，是三个动作
动作目标要恢复或确认什么
客户端重新订阅重新看到工作当前运行状态与可读取记录
恢复 Thread继续已有对话history、上下文基线与配置等

恢复历史与恢复执行权需要不同机制。历史文件存在，不证明后台作业都可冷恢复；各执行入口的寿命和清理条件仍需分别判断。

同一断线问题：Thread 与连接拥有的进程各自怎样收尾

把贯穿案例的最后一个条件改为“测试尚在运行，客户端连接关闭”，先不额外发送取消。下面按 app-server 的资源管理路径推演。仅说“命令在后台”信息不足：它可能是 core Turn 中的一次工具调用，也可能是客户端通过 command/exec 或 process/* 单独建立的资源。相同命令文字不赋予相同寿命。

这里 active 按源码跟踪的 ThreadStatus::Active 判断，是执行状态，不是“有人订阅”的别名。连接清理由 connection_closed 进入：先关闭这条连接的 RPC 接纳门，等待有界收束，再分别清理输出、文件系统、命令/进程与 Thread 观察关系。这里按资源 owner 清理，没有一个把所有活动同时改成 cancelled 的通用动作。

资源与所读 owner连接关闭时实际走的分支对当前测试能说到哪里
普通 Thread 的连接/订阅关系remove_connection 删除反向索引、更新是否仍有连接；Thread 的 connection_closed 处理不普遍取消活跃 Turn少了观察者不等于 Turn 已结束；工具进程仍需按对应 core 工具合同判断

连接拥有的 command/exec按 connectionId 移除 handle，向 active session 发送 Terminate该连接断开会触发终止控制；不是“所有后台命令自动继续”，发出终止请求也不等于已确认进程退出
连接拥有的 process/*ProcessExecManager::connection_closed 对所属 process 发送 Kill应进一步确认进程结果与已发生文件变化；发 Kill 不回滚已有副作用

因此这个问题要拆成两次查询：执行对象是否仍 active，以及具体进程由谁拥有、是否已接受终止控制或报告结果。 保存了 Thread history 能帮助恢复观察，不证明一个连接拥有的命令也被接回。反过来，某个 command/exec 被终止，也不能推导所有 Thread 都被取消。

与 第25章 的 H/W/V/E 对照：一个观察连接可以消失，W 仍由执行 owner 管理；但当 E 本来属于该连接，连接释放会主动改变 E。这样设计能避免失去调用者的进程无限占用资源，代价是客户端不能把连接断开当作无影响事件。需要跨连接持续任务时，应选择具有明确持久身份、查询和接手合同的执行入口，而不是只把命令放到“后台”。

Desktop 的工作副本与 Web 的托管进程：部署条件也属于题目

官方介绍的 App Server 架构包含两种部署：本地 App/IDE 通常启动一个长期子 App Server，用 stdio 交互；Web 则由 worker 在容器内启动 App Server，浏览器通过后端接收事件，状态保存在服务端。后者解释了为什么关闭标签页可以只丢观察。它是发布时披露的设计，不能推出退出任何本地桌面应用也有相同行为。

官方 App 设计说明按 Thread 组织任务，并支持 worktree，让并行工作使用不同代码副本。这解决文件改动的隔离；worktree 不保存进程内存、socket 或远端操作结果。这是工作副本的设计作用，不代表所有 Desktop 入口都会自动创建独立副本。

回到“测试中断后另一个客户端接手”：若只需审阅补丁，可检查工作副本与持久结果；若要继续活跃执行，还须确认 App Server、进程与执行 owner 仍可用。把本地子进程的管理者退出、网络断开、Web 标签关闭和切换 worktree 混成一个“关窗口”，就丢掉了判断所需的部署前提。

7. 中途修订、取消与断线的参考状态

如果只是课程中的单进程脚本，保留清晰循环和可检查日志就足够起步。产品化时，优先加三类边界：明确的工作身份，统一的输入接纳，带状态的进度与终态。用户开始在运行中频繁纠正任务后，再加入 steering；需要多宿主接手时，再研究执行权转交。

按前述调用链，三个相互独立的条件变化得到以下参考结果；这是源码语义推演，没有新增产品运行。

读取文件时补充“不改 README”若接纳为 Steered，消息等待允许的后续步骤，再进入请求不能改写在途输入，也不能撤销此前已经发生的编辑

8. 常见场景与参考结论

题一：turn/start 返回了对象，是否可以显示任务成功？

参考答案：只能据相应合同显示接纳或初始状态，后续仍要观察工作进度和 Turn 终态。任务成功还需要领域验证，例如相关测试通过和实际 diff 符合约束。

题二：用户追加“不改 README”，为什么不能保证所有已发出的动作都遵守它？

参考答案：steering 在接纳后经队列进入允许的后续步骤，在途模型请求或已发生效果无法被一句新输入倒转。系统应在后续请求中体现约束，并检查已发生的变化。

题三：为什么使用 expectedTurnId？

参考答案：它让执行 owner 判断补充输入是否仍属于用户看到的那轮工作，避免 UI 状态滞后导致误投。只做一次客户端 isRunning 检查无法消除竞争。

题四：关闭 UI、取消 Turn、停止后台终端分别意味着什么？

参考答案：关闭 UI 影响观察连接；取消 Turn 影响活跃工作的继续推进；停止终端影响一个具体进程。三者是否互相触发由实现决定，不能凭名称混为一谈。

题五：比较 Codex 与 Maka 的架构，需要固定哪些条件？

参考答案：选择同一场景，例如中途输入和取消，逐项比较工作身份、接纳结果、输入生效点、进度协议和恢复边界。先陈述具体调用路径，再讨论不同需求下的取舍，避免按术语数量或模块数量排名。

同一命令换 owner 的参考分析。 客户端失联时，普通 Thread 仍 active；另一条相同的测试命令经该连接的 command/exec 启动。两条命令能否都写成“重连继续”？再把窗口改成官方文章中的 Web 标签，或把代码复制到新 worktree，哪一项事实发生了变化？

参考结论

不能统一归类。这里的 Thread 连接清理不普遍取消活跃 Turn，应查询它和具体工具的状态；command/exec 的连接清理向所属活动会话发 Terminate，不能直接承诺重连即继续。两者已经产生的文件效果都不因此撤销。Web 发布设计把 App Server 与状态放在服务端，所以标签消失不等于其进程退出；本地应用子进程关系需另核。新 worktree 改变代码副本位置，不证明 W 的执行状态、E 的进程或外部效果已迁移。需要的是资源身份、实际状态及接手合同，而不是相同的命令文本。

工具执行机制见第32章，同类设计场景见第60章。
