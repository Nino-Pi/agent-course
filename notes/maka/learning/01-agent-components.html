第 01 章｜智能代理（Agent）与运行支撑（Agent Harness）

本章概览

核心问题：智能代理（Agent）怎样把一项要求变成实际行动，为什么生成正确命令还不等于完成工作？

关键概念：任务（Task）给出目标与约束；模型（Model）根据材料提出下一步；运行支撑（Agent Harness）组织输入、执行工具（Tool）并控制流程；执行环境（Environment）提供文件、测试与反馈。

关系主线：先用文档修复区分提出请求、实际执行与结果验收，再用职责图连接各部分，最后把这条关系映射到一个可阅读的实现。

阅读起点：会回答，怎样进一步做到？

本章是课程起点，不要求先读其他章节。只需带入一个熟悉的经验：聊天程序可以告诉我们“应该运行什么命令”，但电脑上的文件不会因此自动改变。要完成真实工作，还需要把建议交给执行程序，取得结果，并据此决定下一步。

案例背景。 一个 Node.js 项目的 README.md（使用说明）把测试命令写成了 npm run check，而 package.json（脚本配置）实际提供的入口是 npm test。用户要求只修正文档里的命令，运行测试，再用中文报告。本例假设项目代码与原有测试正常；后面的完整案例会解释这些文件和命令怎样相连，并给出全部处理结果。

假如聊天程序回答“把命令改成 npm test”，它已经提出了一个可检查的建议；但我们还不知道文件是否被改、测试是否运行、修改是否越界。提出正确建议、把建议执行出来、证明要求得到满足，是三个需要分别取得依据的判断。 接下来要认识的各个角色，就是为了连接这三个判断。

智能代理（Agent）、模型（Model）与运行支撑（Agent Harness）

智能代理（Agent）是围绕目标，通过观察、决策、行动与反馈推进工作的系统。 修复代码时，它先了解文件和失败现象，再选择修改与检查；如果检查暴露新问题，后续行动也随之调整。代码代理（Code Agent）是这类系统在软件工作中的应用，可以涉及理解仓库、读改代码、运行检查和交付说明。

本课程讨论由语言模型（Language Model）参与决策的智能代理（Agent）。其中，模型（Model）根据当前材料生成文字和行动请求（Action）；运行支撑（Agent Harness）把它接入实际工作过程。 这里的行动请求（Action）是“希望执行什么”的表示，还不是已经发生的修改。

下表中的“文档修复”都指开头的同一个例子：

表 1 / Table 1 · 智能代理（Agent）、模型（Model）与运行支撑（Agent Harness）
概念回答什么问题文档修复中的例子
智能代理（Agent）整个系统怎样围绕目标推进？发现命令不一致，修改文档，检查结果并交付
任务（Task）要完成什么，受什么约束？只修 README，运行测试，用中文报告
模型（Model）根据当前材料，下一步可能做什么？提出读取、修改或测试请求，解释已有结果
运行支撑（Agent Harness）怎样准备输入、执行请求、记录和控制过程？将读取结果交回决策过程，调用工具（Tool），处理失败、预算（Budget）与结束
执行环境（Environment）工作操作哪些对象，从哪里取得反馈？仓库文件、配置、测试、命令行与相关服务

任务（Task）是工作输入，提供目标与约束；它不是会主动执行的部件。模型（Model）、工具（Tool）和控制程序共同参与执行。项目规则说明工作约定，测试和服务提供可调用接口（Interface）；实际能做什么还要由能力与权限（Permission）落实。

例如，提示里写“本次只读”，是在指导模型（Model）选择行动请求（Action）。若它仍提出写入，要保证文件没有被修改，还需执行层依据权限（Permission）拒绝操作。这样才能区分“输入中要求了什么”和“执行时真正限制了什么”。

后文采用结构简洁的 mini-SWE-agent 作为代码代理（Code Agent）实例。在它的接线中，运行支撑（Agent Harness）把消息列表（Message List）交给 model.query(messages)。读取结果加入其中后，下一次调用才会带上当前文件内容；文件仅仅位于仓库中，还没有完成这条输入链。其他系统可以采用不同的输入与状态（State）接续方式。

一个目标怎样变成行动请求（Action）与观察结果（Observation）

下图把智能代理（Agent）的处理过程展开。模型（Model）负责提出下一步，运行支撑（Agent Harness）负责组织输入与执行控制，执行环境（Environment）中的文件和服务则是被操作、被观察的对象。

沿正常路径，执行程序接收行动请求（Action），操作执行环境（Environment），再把观察结果（Observation）纳入后续输入。读取也属于行动：它未必修改文件，却能改变下一步判断的依据。反馈（Feedback）可能是失败、重复信息或不完整结果，因此系统还要决定是补充调查、调整方案，还是停止。

图中的控制出口有意写成“交付或停止”。预算（Budget）耗尽可以导致停止，任务（Task）仍可能没有完成；模型（Model）给出完成文字，也要经过系统的结束规则。是否完成，应结合原要求、实际产物和检查结果判断。这张图解释责任关系，不声称每次工具调用（Tool Call）都经过同一套内部实现。

运行支撑（Agent Harness）的六组责任

为了阅读后面的工程实现，本课程把运行支撑（Agent Harness）分成六组责任。它们可以由同一小程序承担，也可以分散在多个组件中；这是一种教学分组，并非唯一标准。

图中各框并列，表示责任分工，不表示从第一组依次执行到第六组。下表继续用同一项软件工作解释每组要解决的问题。

表 2 / Table 2 · 运行支撑（Agent Harness）的六组责任
责任组解决的问题在软件工作中的表现
输入组织（Input Composition）本次决策需要哪些指令和材料？选入当前要求、相关文件、工具（Tool）说明和必要历史
模型与工具循环（Model / Tool Loop）请求怎样执行，结果怎样回到下一步？调用模型（Model），解释动作，执行并处理返回，然后继续或退出
状态与恢复（State / Recovery）工作到了哪里，中断后能依据什么继续？保存消息（Message）或运行事实，区分已知结果与未确认效果
权限与隔离（Permissions / Isolation）当前允许做什么，实际怎样限制访问？检查修改范围、处理批准、限制文件和网络访问
任务推进与协作（Task Progress / Collaboration）多步或多次工作怎样组织？管理待办、触发后续工作、委派工作单元并采纳结果
观察与评价（Observation / Evaluation）看到了什么，怎样判断进展与完成？取得测试及文件情况，核对要求、成本与未完成项

最小代理循环（Agent Loop）可以只有内存里的消息（Message）、命令（Command）执行和简单预算（Budget）；持久恢复、协作、定时运行与长期记忆（Long-Term Memory）按需求增加。看到某个接口（Interface）名称，还要继续核对它实际承担了哪些责任。

这些责任也会相互连接。记忆（Memory）的保存与更新涉及状态（State），检索和选入又影响输入组织（Input Composition）；技能说明包（Skill）提供可复用工作方法，附带脚本是否运行仍经过工具（Tool）的执行路径。观察结果（Observation）把发生的事带回来，评价（Evaluation）再回答这些结果是否满足目标。因此，分组帮助我们定位责任和缺口，不能把整个系统理解成互不相干的盒子。

一个完整的 README 修复例子

本例的任务（Task）原文是：

检查 package.json 和 README.md，把 README 中的测试命令改正确，运行测试，然后用中文总结结果。

范围限定为只改 README。下面的文件片段、行动顺序和结果是完整的教学示意：假设项目已经可以运行，函数及原有测试正常。第04章将增加“函数本身也有错误”的条件，并展示已有真实执行结果；它与本章是两种场景。

先读懂文件（File）、程序（Program）和命令（Command）

文件（File）是在电脑上按名称保存的内容；项目分别存放说明、配置、程序和测试。程序（Program）是一组可执行指令，只有被运行，才会读取输入并产生结果。README 里写着一条命令（Command），只是告诉读者怎样操作，不会自动执行它。

本例用 JavaScript 编写程序（Program），由 Node.js 运行。命令（Command）是告诉程序做什么的一行文本；命令行（Command Line）让人或执行工具（Tool）提交这样的文本并取得输出（Output）。npm test 会启动 npm，让它查找项目配置里名为 test 的脚本（Script），也就是预先写好、可以按名字启动的命令。

表 3 / Table 3 · 先读懂文件（File）、程序（Program）和命令（Command）
对象本例中是什么消费者（Consumer）：谁实际使用它
README.md给人阅读的项目说明人和智能代理（Agent）读取测试步骤
package.json保存项目设置的配置文件（Configuration File）npm 读取其中的脚本（Script）配置
npm按项目配置启动脚本（Script）等工作的命令行工具（Command-Line Tool）执行程序用 npm test 请求它启动测试
Node.js运行 JavaScript 程序（Program）的运行时（Runtime）本例用它启动测试
测试程序（Test Program）比较实际结果与预期结果的程序运行后返回检查结果，供智能代理（Agent）判断

这里的消费者（Consumer）不是“谁拥有文件”，而是“谁读取内容并据此行动”。下面用实际配置走通这条关系。

该配置采用 JavaScript 对象表示法（JavaScript Object Notation，JSON），记录字段（Field）与值（Value）：冒号左边是名称，右边是内容；花括号包住一组数据。值（Value）既可以是引号中的文本，也可以是另一组字段（Field），所以能一层套一层：

{
  "scripts": {
    "test": "node --test"
  }
}

这份配置已经完整填写。最外层的字段（Field）是 scripts，它的值（Value）是内层对象（Object）；内层的 test 对应文本 node --test。后文写 scripts.test，就是“先找 scripts，再找其中的 test”的路径简写。JavaScript 对象表示法（JSON）表达的是数据结构，格式本身不负责启动测试。

当执行程序提交 npm test，npm 读取配置，找到 scripts.test，再运行其中的 node --test；node 启动 Node.js，--test 要求进入测试模式。关系链可以按消费者（Consumer）读成：执行程序启动 npm → npm 读取配置 → Node.js 执行测试 → 返回输出（Output）→ 智能代理（Agent）据此判断。 配置存在、入口被调用与测试得到结果，是这条链上不同的步骤。

程序（Program）结束时还可以返回一个数字，称为退出码（Exit Code）。0 通常表示命令（Command）正常退出，其他值要结合输出（Output）判断原因。它描述的是这次执行，不能单独证明测试确实发现了用例，或整项任务（Task）已经完成。

本章给定的观察结果（Observation）是：项目原有测试正常，实际发现的用例均通过。若返回错误，则应按具体内容继续判断；配置里有入口，不能代替检查结果。读者无需安装或运行工具（Tool），下节已给出完整处理过程；第04章再展示固定响应驱动真实执行时的已有输出（Output）。

## 测试

测试命令：npm run check

配置没有名为 check 的脚本（Script），所以 npm run check 指向不存在的入口；应改为能够找到 test 的 npm test。智能代理（Agent）最初只收到任务（Task），读取之后才取得两份文件（File）的当前内容。以下过程把行动请求（Action）、观察结果（Observation）与下一步依据放在一起：

表 4 / Table 4 · 对照两份文件（File），再修改与核查（Verification）
阶段模型（Model）提出的请求或判断运行支撑（Agent Harness）与执行环境（Environment）提供的结果下一步依据
读取（Read）读取配置和 README返回 scripts 与文档正文配置提供 test，文档却指向不存在的 check

修复后的 README 是：

## 测试

测试命令：npm test

参考交付说明是：“README 的测试命令已改为 npm test。测试运行完成，已发现的用例均通过，差异仅包含这处文档修改；未修改源码或测试文件，其他环境和未覆盖行为尚未验证。”这段话是在给定观察下的示例答案，不是本章新增的真实运行报告。

如果测试失败，会怎样？ 先区分入口无法运行，还是断言（Assertion）暴露了源码错误。在本题只改 README 的范围内，可以修正文档并报告测试失败；发现函数缺陷不会增加修改函数的权限（Permission）。第04章会另给明确授权，演示完整函数修复。

如果修改命令（Command）正常退出，README 却没变，会怎样？ 替换目标没有匹配时，进程（Process）仍可能正常退出。回读内容或核对差异（Diff）能发现缺口，这时应重新定位，不能报告修复完成。退出码（Exit Code）、实际改动和任务（Task）满足要求，分别回答了不同的问题。

为什么需要代理循环（Agent Loop）？ 下一步取决于新取得的观察结果（Observation）：没有脚本（Script）要找入口，断言（Assertion）失败要定位行为，修改未生效要核对目标。若所有步骤与分支已经确定，普通脚本（Script）通常更直接；模型（Model）参与的价值在于结合新材料选择后续调查与行动，并不保证每轮都取得进展。

把概念映射到 mini-SWE-agent

前面已经走通请求、执行与反馈（Feedback），现在再进入接口（Interface），就可以逐项回答“这部分由谁实现”。mini-SWE-agent 把代理循环（Agent Loop）做成容易观察的结构：通用概念中的智能代理（Agent）是整个工作系统，源码里的 DefaultAgent 类主要承担控制职责，它与模型（Model）、执行环境（Environment）共同形成这个最小实例。

这里的上下文（Context）是一次模型调用（Model Query）实际收到的材料；控制（Control）则决定什么时候调用、怎样处理结果、何时结束。下面把两项责任放在同一行，是因为这个最小实现由同一个类承担，并不表示它们是同一概念。

表 5 / Table 5 · 把概念映射到 mini-SWE-agent
概念责任mini 中的对应位置作用
任务输入（Task Input）run(task) 与初始消息模板（Message Template）把目标和约束放入消息（Message）；没有单独的任务（Task）运行对象
上下文与控制（Context / Control）DefaultAgent 的 messages、配置和循环保存当前材料，协调调用、结果与退出
模型调用（Model Query）model.query(messages)交入准备好的材料，取得文字或行动请求（Action）
工具执行（Tool Execution）env.execute(action)；本机实现为 LocalEnvironment执行命令（Command），返回输出（Output）、退出码（Exit Code）或异常信息
结果反馈（Result Feedback）模型协议适配器（Model Adapter）整理结果，DefaultAgent 追加消息（Message）后续调用才能依据这份结果继续判断

LocalEnvironment 直接在本机启动命令（Command），其执行接口（Interface）本身不提供完整安全隔离（Isolation）；默认交互入口还会在 DefaultAgent 的基础上增加人工确认（Confirmation）等控制。消息（Message）可以保存为执行轨迹（Trajectory），但真实文件（File）的变化与轨迹快照（Trajectory Snapshot）之间仍可能存在记录缺口，后续章节会展开。

第02章追踪代理循环（Agent Loop）与预算（Budget），第03章解释行动请求（Action）、命令解释器（Shell）执行与观察消息（Observation Message）的转换；这种消息（Message）承载观察结果（Observation），供后续调用使用。第05章说明交互、退出与执行轨迹（Trajectory）。这些实现说明各项责任怎样接通；接口（Interface）声明本身还不会校验所有运行数据。

意图、执行与接口（Interface）问答

问题 1。 模型（Model）给出了正确命令（Command），是否已经证明智能代理（Agent）完成工作？

解释。 还需要接纳并执行行动请求（Action），取得观察结果（Observation），继续判断和验收。运行支撑（Agent Harness）把各部分连成闭环，完成与否仍取决于实际结果。

问题 2。 运行支撑（Agent Harness）与 README、测试有什么关系？

解释。 前者提供读取、输入组织（Input Composition）、执行与控制；README 说明项目约定，测试提供可调用的检查。材料经实际读取和执行才能影响本次工作，规则文字与执行权限（Permission）需要分别落实。

问题 3。 没有协作或长期记忆（Long-Term Memory），还算智能代理（Agent）吗？

解释。 可以。围绕目标，根据观察结果（Observation）选择行动请求（Action），并利用反馈（Feedback）继续工作，就具备这里讨论的基本闭环。协作、长期记忆（Long-Term Memory）与跨会话恢复解决进一步的需求。

问题 4。 DefaultAgent 类是否就是智能代理（Agent）的通用定义？

解释。 这个类是一个实现中的控制部件。理解整个实例，还要看模型（Model）、执行环境（Environment）、配置和任务（Task）；其他系统可能把这些责任分给不同组件。
