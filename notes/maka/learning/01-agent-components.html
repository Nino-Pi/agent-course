第 01 章｜什么是 Agent 与 Agent Harness

本章概览

核心问题：Agent 怎样围绕目标行动，Model 与 Harness 负责什么？

关键概念：Agent（智能代理）：目标驱动系统；Task（任务）：目标与约束；Model（模型）：生成文字与动作请求；Harness（运行支撑）：组织输入、调用工具并控制流程；项目环境：文件、测试与服务。

关系主线：模型参与决策，Harness 连接环境并收集反馈，Agent 据此继续或结束。完整案例先解释文件、命令与配置字段怎样相连，再根据修改与测试结果验收任务。

Agent、模型与运行支撑

Agent 是围绕目标，通过观察、决策、行动和反馈推进工作的系统。 例如，修复代码时先了解当前文件与失败现象，选择修改，再检查结果；测试暴露新问题，后续行动也随之调整。Code Agent 是这类系统在软件任务中的应用，工作可能包含理解仓库、读改代码、运行检查和交付说明。

本课程讨论以语言模型参与决策的 Agent。Model 是其中的决策部件；Harness 是让模型参与实际工作的运行支撑。 先用一个小任务说明它们的关系。

案例背景。 一个 Node.js 项目的 README.md（使用说明）把测试命令写成了 npm run check，而 package.json（脚本配置）实际提供的入口是 npm test。这里 Node.js 负责运行项目程序，npm 负责按配置启动测试；它们是本例的项目工具。用户要求 Agent 核对这两份文件，只修正文档中的命令，运行测试，再用中文报告。本例假设项目代码和原有测试正常；本章后面的“一个完整的 README 修复例子”会解释配置的读法，并给出文件片段与处理结果。

下表中的“README 修复”都指这项任务：

表 1 / Table 1 · Agent、模型与运行支撑
概念回答什么问题README 修复中的例子
智能代理（Agent）整个系统怎样围绕目标推进？发现测试命令不一致，修改文档，核对结果并交付
任务输入（Task）要完成什么，受什么约束？只修 README，运行测试，用中文报告
模型（Model）根据当前材料，下一步可能做什么？提出读取、修改或测试请求，解释已有结果
运行支撑（Harness）怎样准备输入、执行请求、记录和控制过程？将文件结果交给模型，调用工具，处理失败、预算与结束
项目环境（Environment）工作操作哪些对象，从哪里取得反馈？仓库文件、配置、测试、命令行与相关服务

任务提供目标与约束，模型、工具和控制程序共同参与执行。项目规则说明工作约定，测试和服务提供可调用接口与反馈；文件能否读取、动作能否执行，仍由实际能力和权限边界落实。例如，提示里写“本次只读”是在指导模型选择动作；若模型仍提出写入请求，要保证文件不被修改，还需执行层拒绝这次写入。

后文采用 mini-SWE-agent 这个结构简洁的代码 Agent 实例；其中，Harness 把当前消息列表传给 model.query(messages)。读文件的结果加入列表后，下一次请求才会带上这份当前内容；文件仅仅位于仓库中，还没有完成这条输入链。这里说的是 mini 的接线，其他系统可以采用不同的输入与状态接续方式。

一个目标怎样变成行动与反馈

下图展示 Agent 收到任务后的处理过程，把 Harness 的输入和执行职责展开，让模型处于它支持的循环中。项目环境中的文件和服务是被操作、被观察的对象。

沿正常路径，模型提出请求，执行程序操作环境，取得的观察进入后续输入。读取也属于行动，它未必修改文件，却能改变下一步判断的依据。环境可能返回失败、重复信息或不完整结果，系统据此选择补充观察、调整方案或停止。

图中的“交付或停止”是控制出口：预算耗尽可以导致停止，任务仍可能未完成；模型给出完成文字，也要经过系统的结束规则。任务正确与否由需求、实际产物和检查结果共同判断。这个图表达责任关系，不声称每个工具调用都经过同一套内部实现。

Harness 的六组责任

为了阅读后面的工程实现，本课程把运行支撑分成六组责任。它们可以由同一小程序承担，也可以分散在多个组件中；这是一种教学分组，并非唯一标准。

下图把六组责任并列放在同一个 Harness 范围内。框的并列表示责任分工，没有从第一组依次走到第六组的执行顺序；下表再用代码任务逐项解释。

表 2 / Table 2 · Harness 的六组责任
责任组解决的问题在代码任务中的表现
输入组织（Input Composition）本次模型需要哪些指令和材料？选入当前要求、相关文件、工具说明和必要历史
模型与工具循环（Model / Tool Loop）请求怎样执行，结果怎样回到下一步？调模型、解释动作、调用工具、处理返回并继续或退出
状态与恢复（State / Recovery）工作到了哪里，中断后能依据什么继续？保存消息或运行事实，区分已知结果与未确认效果
权限与隔离（Permissions / Isolation）当前允许做什么，实际怎样限制访问？检查修改范围、处理批准、限制文件和网络访问
任务推进与协作（Task Progress / Collaboration）多步或多次工作怎样组织？管理待办、触发后续工作、委派子任务并采纳结果
观察与评价（Observation / Evaluation）看到了什么，怎样判断进展与完成？取得测试/文件状态，核对任务条件、成本与未完成项

最小循环可以只有内存消息、命令执行和简单预算；持久恢复、子任务、定时运行与自动长期记忆按需求增加。具有某个接口名称，也还要看它实际完成了哪些责任。

这些责任会连接起来。**Memory（长期记忆）**的保存与更新属于状态管理，检索和注入又影响输入组织；**Skill（可复用方法包）**为模型提供工作方法，附带脚本是否执行仍经过工具链。观察把结果带回来，评价再回答它是否满足目标。分组是为了找到责任和缺口，不是把系统切成互不相干的盒子。

一个完整的 README 修复例子

任务输入是：

检查 package.json 和 README.md，把 README 中的测试命令改正确，运行测试，然后用中文总结结果。

这里限定只改 README。下面的文件片段、动作顺序和结果是完整的教学示意：假设项目已经可以运行，函数及原有测试正常。后面的第04章将增加“函数本身也有错误”的条件，并展示真实执行结果；它与本章的简化示意是两种场景。

先读懂文件、程序和命令

文件是在电脑上按名称保存的内容；项目用不同文件放说明、配置、程序和测试。程序是一组可执行的指令，只有被运行，才会读取输入并产生结果。README 里写着一条命令，只是在告诉人怎样操作，不会自动执行它。

本例的程序用 JavaScript 语言编写，由 Node.js 运行。命令是告诉程序做什么的一行文本；命令行让人或执行工具提交这样的文本并取得输出。npm test 就是一条命令：启动 npm，让它查找项目配置里名为 test 的脚本。这里的脚本指预先写好、可以按名字启动的一段命令。本例所用文件与程序的关系如下：

表 3 / Table 3 · 先读懂文件、程序和命令
对象本例中是什么谁使用它
README.md给人阅读的项目说明人和 Agent 读取测试步骤
package.json保存项目设置的配置文件npm 读取其中的脚本配置
npm按项目配置启动脚本等工作的命令行工具执行工具用 npm test 请求它启动测试
Node.js运行 JavaScript 程序的工具本例用它启动测试程序
测试程序比较实际结果与预期结果的程序运行后返回检查结果，供 Agent 判断

下面是本例已知的配置。它用 JSON 这种数据格式记录“字段名与值”：冒号左边是字段名，右边是值；花括号包住一组字段。值既可以是引号中的文本，也可以是另一组字段，所以能一层套一层：

{
  "scripts": {
    "test": "node --test"
  }
}

这份配置已经完整填写。最外层有一个 scripts 字段，它的值是内层对象；内层的 test 字段，值为文本 node --test。后文写 scripts.test，就是“先找 scripts，再找其中的 test”的路径简写。引号和花括号用于表示数据，JSON 文件本身不负责启动测试。

当执行工具提交 npm test，npm 读取这份配置，找到 scripts.test，再运行其中的 node --test；node 启动 Node.js，--test 要求它进入测试运行模式。测试程序随后给出结果，执行工具把输出交回 Agent：

工具执行 npm test
  → npm 读取 package.json 中的 scripts.test
  → 启动配置值 node --test
  → Node.js 运行测试并给出输出
  → Agent 根据实际输出判断测试状态

程序结束时还可以返回一个数字，称为退出码；0 通常表示命令正常退出，其他值要结合输出判断原因。它描述的是这次命令，不能单独证明测试确实发现了用例或整项任务已经完成。

本章给定的教学观察是：项目原有测试正常，实际发现的用例均通过。若输出是错误，则应按错误内容继续判断；配置里写了测试入口，不能代替测试结果。这里不需要安装工具或运行命令，后面的表格已给出本例完整过程。第04章再展示固定响应驱动真实命令时的已有输出。

对照两份文件，再修改和核查

待修的 README 是：

## 测试

测试命令：npm run check

这份配置没有名为 check 的脚本，所以 README 中的 npm run check 指向了不存在的入口；应改为能找到 test 脚本的 npm test。Agent 最初只收到任务，读取以后才取得这两份当前内容。以下过程给出请求、观察与决策之间的关系：

表 4 / Table 4 · 对照两份文件，再修改和核查
阶段模型提出的行动或判断Harness 与环境提供的结果下一步依据
读取（Read）读取配置和 README返回 scripts 与文档正文配置提供 test，文档却指向不存在的 check
修改（Edit）只把 README 的命令改成 npm test执行修改，并取得修改结果已有修改结果；测试状态仍待检查
核查（Verification）运行 npm test，查看 README 差异本例给定观察为测试已发现并通过；diff 只有命令替换文档入口和当前受测行为得到检查，修改范围符合任务
交付（Delivery）用中文说明改动与检查范围系统依据结束规则收束本次工作报告本次完成项，保留未覆盖范围

修复后的 README 是：

## 测试

测试命令：npm test

参考交付说明是：“README 的测试命令已改为 npm test。测试运行完成，已发现的用例均通过，差异仅包含这处文档修改；未修改源码或测试文件，其他环境和未覆盖行为尚未验证。”这段话是在上述给定观察下的示例答案，不是本章新增的真实运行报告。

如果测试返回失败，会怎样？ 读取具体输出后，先区分入口无法运行与断言暴露源码问题。在本题 README-only 范围内，可以修正文档并报告源码测试失败；发现函数 bug 并不增加修改函数的许可。第04章将另给明确授权，完整演示函数修复。

如果修改命令返回正常，README 却没变，会怎样？ 例如替换目标没有匹配，进程仍可能正常退出。回读文件或核对 diff 能发现缺口；这时应重新定位，不报告修复完成。命令退出、目标文件已改变、整项任务满足要求，是三个不同判断。

为什么需要循环？ 下一动作取决于观察：没有脚本要找入口，断言失败要定位行为，修改没生效要核对目标。如果步骤和所有分支都已确定，普通脚本通常更直接；模型参与的价值在于结合新材料选择后续调查与行动，而非保证每轮都取得进展。

把概念映射到 mini-SWE-agent

mini-SWE-agent 把这条循环做成容易观察的实现。通用概念中的 Agent 是整个工作系统；源码中名为 DefaultAgent 的类主要承担控制职责，它与模型、执行环境共同形成这个最小实例。

表 5 / Table 5 · 把概念映射到 mini-SWE-agent
概念责任mini 中的对应位置作用
任务输入（Task Input）run(task) 与初始消息模板把目标和约束放入消息；没有单独的 Task 运行对象
当前输入与控制（Context / Control）DefaultAgent 的 messages、配置和循环保存本轮材料，协调调用、结果与退出
模型调用（Model Query）model.query(messages)将明确准备的消息交给模型，取得文字或动作请求
工具执行（Tool Execution）env.execute(action)；本机实现为 LocalEnvironment运行命令并返回输出、返回码或异常信息
结果反馈（Result Feedback）模型适配器整理观察，Agent 加入消息后续请求才能依据这份结果继续判断

LocalEnvironment 直接在本机启动命令，执行接口本身不提供完整安全隔离；默认交互入口还会在 DefaultAgent 的基础上增加人工确认等控制。消息可以保存为 trajectory（执行轨迹），但文件效果与轨迹快照之间仍可能存在记录缺口，后续章节会展开这些边界。

第02章追踪循环与预算，第03章解释动作参数、shell 执行和观察消息的转换，第05章说明交互、退出与轨迹。它们解释上述责任怎样在代码中接通，接口声明本身还不负责校验所有运行数据。

意图、执行与接口问答

问题 1。 一个模型给出了正确命令，是否已经构成完成任务的 Agent？

解释。 还需要系统接纳并执行行动、取得结果、继续判断和验收。Model 是决策部件，Harness 把它接入工作循环；任务完成则取决于实际结果。

问题 2。 Harness 与项目里的 README、测试有什么关系？

解释。 Harness 提供读取、输入组织、执行和控制；README 说明项目约定，测试提供可调用的检查。材料经实际读取和执行才能影响本次工作，规则文字与执行权限分别落实。

问题 3。 一个小 Agent 没有子任务和长期 Memory，还算 Agent 吗？

解释。 可以。只要它围绕目标，根据观察选择行动并利用反馈继续工作，就具备这里讨论的基本闭环。子任务、长期记忆和跨会话恢复解决进一步的需求。

问题 4。 mini 的 DefaultAgent 类是否就是 Agent 的通用定义？

解释。 该类是一个实现中的控制部件。理解整个实例还要看 Model、Environment、配置和任务；其他系统可能把这些责任分给不同组件。
