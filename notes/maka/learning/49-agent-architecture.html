第 49 章｜设计代码修复 Agent

本章概览

核心问题：从收到一个 bug 到交付修复，Agent 的主循环、状态和界面应怎样分工？

关键概念：Context（上下文）：本次提供给模型的材料；模型适配器：转换模型请求与返回；工具执行器：校验并执行动作；请求认领 Claim：为同一任务确定运行身份与处理权；持久事实：保存已接受的结果；终态：记录结束原因；界面投影：展示运行状态。

关系主线：入口先认领或查询任务，只有取得派发许可的新执行进入模型与工具循环；结果成为后续观察，控制器按预算与完成证据继续或停止，关闭窗口后的处理仍取决于 Host 和执行器是否存活。

前置：第11–14章、第48章 设计参考方案。本题的组件名和伪代码是教学方案，用来讨论各部分为何需要分开。

1. 原题与约束

用户给你一个代码仓库和 bug 描述，设计一个能定位、修改、验证并解释结果的 Agent。

方案由用户规模、修改范围、测试位置和中断后的恢复要求共同决定。

本题采用单用户、本地仓库、每个会话一个顶层任务；允许修复指定源码及 README，不允许通过修改测试来掩盖失败。成功条件包括用户问题得到验证、相关测试结果和符合范围的 diff；本题没有远端调度需求。

2. 参考方案

我会先做一个顺序的模型—工具循环。入口把用户任务和允许范围固定下来，Context 组装器收集项目规则、当前需求和已获得的观察，模型提出读取、编辑或执行测试的动作。工具执行器校验参数、检查权限，在受控环境中执行，并把结构化结果交回循环。模型根据已获得的观察决定下一步；重复查询也可能没有增加新信息。系统保存任务身份、工具请求和结果、最终状态，让界面能够展示可核对的过程。完成不能只看模型说“修好了”，需要核对用户问题、测试结果和 diff。第一版用明确的步数、时间和输出预算控制循环。出现长历史时加入压缩，需要跨会话信息时增加独立 Memory；要求崩溃恢复时，再为可能产生效果的操作增加执行记录和对账策略。

3. 执行链与状态归属

图画出首次允许派发的执行主线；重复请求在接纳层查询既有身份，已认领但未派发的工作进入第 4 节的恢复分支，不沿此箭头再开一轮。模型与工具构成反馈环，输入组装连接此前观察，持久事实同时供后续执行与用户视图消费。工具结果保存和最终状态保存是两个时点。V 是本题设计的检查职责，可以由确定性检查与模型说明共同实现；不表示 Maka 存在一个同名通用业务验证器。

三条不变量：未执行的动作不能显示为完成；结果未知不能转换为成功；界面显示不能反过来覆盖持久的执行事实。

4. 最小状态与主循环

以下为教学 Python 伪代码，辅助函数不是 Maka 的现有 API。接纳（Admission）回答“这份任务是否已有运行身份”，派发（Dispatch）回答“该身份现在能否启动执行”；两者之间可能发生崩溃。仅让去重函数返回同一个 run_id，并不能阻止调用方再次进入循环。

本题给辅助函数约定如下合同。这里的原子操作是“要么共同提交，要么均不提交”，需要事务或同一串行 owner 实现，不能用先查再写替代。

表 1 / Table 1 · 4. 最小状态与主循环
教学接口必须满足的合同
authorize_and_freeze先核对本次调用者的授权，再确定稳定的请求命名空间 scope，例如调用者与仓库的组合；冻结任务内容、允许范围和验收条件。查询已有结果也要授权，不能凭猜中 request_id 读取别人的任务。
claim_or_observe_atomically在同一 scope + request_id 下原子核对已冻结内容并持久保存唯一的任务到 Run 绑定。内容或允许范围不同则返回冲突；相同则返回既有身份与状态，只有首次认领返回 new_dispatchable 及派发凭证。
begin_dispatch_atomically执行 owner 核对该 Run 的派发凭证、取消状态及当前派发状态；只有本次调用取得唯一启动权时返回 may_run=True。竞争失败或已启动时不能进入下面的循环。
dispatch_or_reconcile按原 Run 恢复派发或核对已有执行；运行中只观察，任何终态只读取既有结果，派发或效果未知先对账。具体分支见第58章的控制契约。

这里的派发凭证只限制谁能启动这一份 Run；record 只表示保存机制。二者都不保证外部效果 exactly-once（恰好一次）。

先读入口。它的输入是用户任务、策略和预算，输出可能是既有结果、订阅或恢复处理；只有取得唯一派发权的分支才调用下一段执行循环。因此，第一段最需要检查的是每个重复请求有没有在进入模型前离开：

def run(task, policy, budget):
    request = authorize_and_freeze(task, policy)
    claim = claim_or_observe_atomically(
        request.scope, task.request_id, request.frozen_payload
    )
    if claim.kind == "running":
        return query_or_subscribe(claim.run_id)
    if claim.kind == "terminal":  # 成功、失败、取消等终态都不重跑
        return read_recorded_result(claim.run_id)
    if claim.kind in {"admitted_not_dispatched", "recovery_required"}:
        return dispatch_or_reconcile(claim.run_id)
    if claim.kind != "new_dispatchable":  # 冲突、拒绝或未识别状态
        return report_admission_problem(claim)

    execution = begin_dispatch_atomically(claim.run_id, claim.dispatch_token)
    if not execution.may_run:
        return dispatch_or_reconcile(claim.run_id)
    return run_claimed_execution(execution, budget)

再读已取得派发权的执行。execution 带着已接受的 Run 身份和冻结输入，observations 保存本次执行已经知道的结果。循环每请求一次模型就消耗一步额度；有工具时先取得、保存结果，再把它加入下一次输入；没有工具时进入完成证据检查。这段的阅读重点是观察如何从工具回到下一次模型请求：

def run_claimed_execution(execution, budget):
    run_id = execution.run_id
    task, policy = execution.accepted_input  # 已冻结任务及本次有效的受限策略
    observations = load_known_observations(run_id)
    while budget.allows_next_step():
        if cancellation_requested(run_id):
            return finish(run_id, "cancelled", observations)
        budget.consume_model_step()  # 准入一次请求就计一步，不能只检查而不扣减
        request = compose(task, policy, observations)
        response = model_call(request)
        record(run_id, response)
        if cancellation_requested(run_id):
            return finish(run_id, "cancelled", observations)
        if response.tool_calls:
            for call in response.tool_calls:   # 第一版顺序执行
                if cancellation_requested(run_id):
                    return finish(run_id, "cancelled", observations)
                result = execute_with_policy(call, policy, cancel_signal(run_id))
                record(run_id, call.id, result)  # 保存完成后，才进入后续观察
                observations.append(result)
        else:
            report = assess_evidence(task.acceptance, observations)  # 完成候选需验收
            return finish(run_id, report.status, response.text, report)
    return finish(run_id, "budget_exhausted", observations)

这段代码只展开模型步数的扣减；实际费用应按返回的 usage 或账单记录，工具时间与整体期限另行检查。请求失败也不能把已发生的尝试和费用抹掉。

这里存在三个层次：一次用户任务、一次实际执行、一次模型请求。scope 防止不同调用者或仓库的同名请求碰撞，冻结的 payload 防止同一个请求身份偷偷变成另一项任务；派发时采用的策略不得超出原授权范围，并继续受当前有效限制约束。内容冲突必须显式拒绝，不能覆盖原任务。身份与恢复的其他边界见第13章和第52章。

以上循环以单一顺序执行 owner 为前提。如果将来允许租约（Lease，即有期限的处理权）失效后由另一进程接管，派发、工具接纳与事实写入还需要校验 owner 代次，拒绝旧 owner 的迟到动作；这类校验常称为 fencing。租约到期只说明处理权失效，不证明旧进程或远端动作已停止，因此不能据此把 running 改成“可以从头跑”。恢复时还要沿用已记账的预算，不能因重试刷新执行额度。

下面是六种情境的直接参考判定。它们用于核对教学合同，不是产品故障实验的实测结果。

终态后重试同一 Run 已成功、失败、取消或因预算耗尽结束读取该终态和已有结果。确需再次尝试时，须显式提交并授权一份新请求，不能复用旧身份偷偷重跑。
认领后、派发前崩溃Run 绑定已持久保存，执行 owner 能确认该 Run 尚未启动恢复者按原 Run 竞争派发权，再经同一执行入口启动；若不能确认未启动，改走下一行的对账路径。
派发已发出，或效果可能已发生，但回执丢失不能可靠判断是否开跑，或不能确认某个外部动作的结果先按原 Run/工具调用身份查询执行器、文件或外部系统；只补记能确认的事实。无法确认时保留未知并按恢复策略处理，不盲目重放有副作用的动作。

请求去重解决“是否同一份任务”，派发仲裁解决“谁能启动该 Run”，外部效果的核对解决“那个动作到底发生了什么”。三个问题需要分别回答。

本题在模型返回后和每次工具接纳前再次检查停止意图，避免等待期间收到取消后仍启动后续调用；执行器也接收取消信号。检查与实际启动间的竞争仍需由执行入口处理。已开始的工具先结算实际结果或未知状态，取消不抹去既有效果。生产实现还须处理 provider/存储异常与终态竞争，这段循环只展开本题的决策骨架。

无工具返回是本题协议的结束候选。mini 的完成 marker 和其他产品的停止语义不同，不能把该分支当跨产品规则。

5. 用一个任务走完

下面把两段伪代码放回同一任务，按设计合同作教学推演，不是这份伪代码的实跑日志。仓库中的 formatDuration 应把非负整数秒显示为“分钟:两位余秒”；错误实现用 % 100 算余秒，使 125 秒显示为 2:25，正确余秒应按 % 60 计算。README 另有错误测试入口，需要从配置确认实际命令；本题沿用“只修改指定源码与 README、保留测试作为验证依据”的授权。

若只给定四个测试，硬编码四个输入也可能通过。因此验收还要看行为要求和补充边界输入，不能把已有测试数当完整业务定义。

失败走读：第一次运行不存在的测试脚本，错误发生在测试入口，尚未运行断言。模型应回读配置定位正确入口；把这一步计作“代码测试失败，因此修改函数”会引入无依据修改。

6. 递进追问

任务运行几十分钟怎么处理？

分开管理 Context 预算、累计费用/步数、工具时间和整体任务期限。压缩解决模型输入问题，不能自动减少已经消耗的调用费用，也不能替代任务停止策略。

两个 Read 可以并行吗？

若输入独立且没有共享副作用，可以并行读取；编辑依赖读取结果，复测依赖编辑完成。每个结果保留对应调用身份。加入并行以后还要定义取消、部分失败和结果回收；见 第56章。

为什么需要 Runtime，模型自己不能决定吗？

模型可提出动作，但操作系统访问、参数校验、执行隔离、记录和生命周期需要实际程序落实。把检查步骤写进 prompt 可以指导决策，无法替代这些执行职责。

模型说完成但测试没跑怎么办？

报告“修改已生成、验证未完成”，或在预算与权限允许时继续验证。不要伪造测试结果，也不要把 Runtime 的执行终态和业务问题已解决混为一谈。

最小验证集：错误脚本、真实失败断言、成功修复、超出写入范围、工具超时、预算耗尽、重发请求。错误脚本应保留入口失败，越界调用应在效果前拒绝，预算耗尽应停止新调用，重发请求应查询同一身份；这些预期状态共同限定方案的验收结果。

8. 窗口关闭后的完整处理

假设修复尚未完成，用户关闭的只是观察窗口，Host 与普通执行器仍存活。窗口关闭不创建新任务，也不直接取消已有 Run：模型与工具按原身份继续，执行结果由 Runtime 保存，Host 发布持久状态。新窗口先读取同一 Run 的快照，再消费当前订阅的增量。

如果实际工具由已断开的 Client 提供，结论就不同：执行能力可能消失，已开始动作要结算为已知结果或 unknown；不能把普通 Host 执行器的存活条件套用过去。如果 Host 也退出，则从已提交事实恢复观察并按该实现的恢复政策处理未结束执行，不承诺恢复任意进程栈。

例如 README 编辑结果已持久保存，而测试尚未启动。重连后的报告可以明确“文档已改，测试未运行”；它既不能宣布完整修复，也不需要重新编辑 README。若只知道编辑已发出而没有可靠结果，先核对当前文件和执行记录，避免重复效果。
