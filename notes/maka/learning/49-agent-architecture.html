第 49 章｜设计代码代理（Code Agent）的完整修复流程

本章概览

核心问题：从收到故障描述到交付修复，怎样把模型决策、实际执行与完成证据接成一条可靠的过程？

关键概念：上下文（Context）提供本次判断材料；认领（Claim）确定工作归属；派发（Dispatch）控制谁能开始；观察结果（Observation）支持下一步；终态（Terminal State）记录结束，验收（Acceptance）判断任务是否满足要求。

关系主线：入口识别同一请求并取得启动权，模型（Model）与工具（Tool）根据结果循环；持久事实（Persistent Fact）供后续工作和界面消费，恢复（Recovery）继续核对原身份（Identity），不能把重连当成重做。

前情回顾：把已学职责组合成一个方案

第11章把智能代理（Agent）的目标与决策，和运行支撑（Agent Harness）的输入组织、执行及记录分开。模型（Model）提出行动请求（Action），实际程序才能读取文件、修改代码或启动测试（Test）。本章先选择最小的职责组合，再解释中断和重复请求怎样改变处理。

第13章区分会话（Session）、工作轮次（Turn）与执行（Run）；第14章区分持久事实（Persistent Fact）与用户界面（User Interface，UI）的投影（Projection）。这两组概念在这里直接有用：两次网络提交可能对应同一项工作，恢复（Recovery）界面也不意味着重新运行。

第48章先固定任务合同（Task Contract）：什么算成功、允许改哪里、什么情况保留未知。本章将它写成组件责任、入口分流、完整循环和参考结果。下面的组件名、接口（Interface）和代码均为教学设计，不是可直接启动的产品实现。

1. 原题与约束：先固定这次修复的初态

用户给你一个代码仓库和故障描述，设计一个能定位、修改、验证并解释结果的智能代理（Agent）。

本题采用单用户、本地仓库、每个会话（Session）一次一个顶层任务（Task）。用户允许修改指定源码与README，要求保留已有改动，不允许通过修改测试（Test）掩盖失败；本题没有远端调度需求。请求仍可能因连接问题重发，所以单用户不等于没有重复提交。

沿用第04章的四文件背景：package.json说明项目命令，src/duration.js实现formatDuration，test/duration.test.js提供四个既有测试（Test），README.md说明怎样运行。这里重新采用函数仍有缺陷、说明入口也有错的初态，不沿用第13章函数已经正确的简化条件。

对案例范围内的非负JavaScript安全整数秒数 sss，函数应输出分钟和两位余秒。令分钟数为 mmm、余秒为 rrr：

给定 s=125s=125s=125，得到 m=2m=2m=2、r=5r=5r=5，所以应显示2:05。错误实现用% 100取余，显示2:25。README还写了错误的测试（Test）入口；需要读取配置确认实际命令。成功要同时满足一般行为要求、相关测试（Test）和允许范围内的差异（Diff），不能只检查某一句完成声明。

2. 完整参考方案：每份材料由谁消费

先做顺序的模型（Model）与工具（Tool）循环。入口固定任务（Task）内容、允许范围和验收（Acceptance）条件，控制器管理身份（Identity）与预算（Budget）。上下文（Context）组装器选择项目规则、当前要求和已有观察结果（Observation），模型（Model）据此提出下一项行动请求（Action）。

执行器（Executor）校验参数与当前权限（Permission），在受控环境中完成实际操作，将结构化结果交回。保存后的工具结果（Tool Result）供下一次模型输入（Model Input）选择，也可供界面读取。重复查询未必增加信息，下一步应由新证据改变，而不是只让循环次数增加。

完成时核对用户问题、测试（Test）与差异（Diff）。第一版用明确的模型步骤（Model Step）、时间和输出预算（Output Budget）控制工作；长历史（History）需要压缩（Compaction），跨会话（Session）经验需要独立长期记忆（Long-Term Memory）。要求崩溃恢复（Recovery）时，还要为可能产生效果（Effect）的操作保存身份（Identity）并制定对账（Reconciliation）策略。

3. 执行链：结果怎样回到下一次决策

图只画首次获准派发（Dispatch）的主线。重复请求在准入（Admission）层查询原身份（Identity）；已认领（Claim）但未派发（Dispatch）的工作进入下一节的恢复（Recovery）分支，不沿图上箭头另开一次执行（Run）。

从工具结果（Tool Result）回到上下文（Context）的箭头包含两个步骤：先保存本次接受的结果，再选入下一次模型输入（Model Input）。工具结果（Tool Result）与最终终态（Terminal State）在不同时间保存，界面也分别消费它们。这里的用户界面（User Interface，UI）投影不能反过来改写持久事实（Persistent Fact）。

V是本题的完成检查（Completion Check）职责，可以结合确定性检查与模型（Model）说明；不表示Maka存在一个同名通用业务验证器。它至少要守住三条不变量（Invariant）：未执行的行动请求（Action）不能显示为完成，未知结果不能转换为成功，界面状态不能覆盖已保存的执行事实。

4. 身份（Identity）、派发（Dispatch）与主循环

先推导三个不同的决定

设客户端（Client）重发一次请求。只让去重函数返回同一个run_id，调用者仍可能再次进入循环；仅保存编号没有限制谁能启动。因此要依次回答三个问题：这是不是同一份任务（Task），谁获准启动这次执行（Run），此前的外部效果（Effect）是否已经发生。

准入（Admission）建立请求与执行（Run）的绑定；派发（Dispatch）决定当前能否启动；对账（Reconciliation）核对可能已经发生的效果（Effect）。它们之间可能发生崩溃。下面的教学Python辅助函数不是Maka现有应用编程接口（Application Programming Interface，API），每个名称都需要对应的实际合同。

表 2 / Table 2 · 先推导三个不同的决定
教学接口（Interface）必须满足的合同
authorize_and_freeze先核对当前调用者的授权（Authorization），再确定稳定请求作用域（Scope），例如调用者与仓库组合；冻结任务（Task）内容、允许范围与验收（Acceptance）条件。查询既有结果也要授权（Authorization），猜中request_id不能读取别人的工作。
claim_or_observe_atomically在同一scope + request_id下原子核对冻结内容，持久保存唯一的任务（Task）到执行（Run）的绑定。内容或范围变化返回冲突；相同返回原身份（Identity）与状态（State）；仅首次认领（Claim）返回new_dispatchable和派发凭证（Dispatch Token）。

dispatch_or_reconcile按原执行（Run）恢复派发（Dispatch）或核对既有工作；运行中只查询，任何终态（Terminal State）只读取原结果，派发（Dispatch）或效果（Effect）未知先对账（Reconciliation）。完整分支在第58章继续展开。

表中的原子操作（Atomic Operation）要求相关检查与写入要么共同提交，要么均不提交，需要事务（Transaction）或同一串行负责者（Owner）实现。先查询“没有”，稍后再写入，可能让两个调用都判断自己是首次。

派发凭证（Dispatch Token）只限制谁能开始这一份执行（Run）；record只表示选定的保存机制。二者都不保证外部效果（Effect）恰好一次（Exactly Once）。已写文件与本地结果记录之间，仍可能有单独的失败窗口。

入口：重复请求在模型调用（Model Query）前分流

第一段输入用户任务（Task）、策略（Policy）与预算（Budget），输出可能是原结果、订阅或恢复（Recovery）处理。只有取得唯一派发（Dispatch）权的分支才调用第二段。按这些出口阅读，就能看出为什么相同请求不会无条件再问模型（Model）：

def run(task, policy, budget):
    request = authorize_and_freeze(task, policy)
    claim = claim_or_observe_atomically(
        request.scope, task.request_id, request.frozen_payload
    )
    if claim.kind == "running":
        return query_or_subscribe(claim.run_id)
    # 所有终态（Terminal State）读取原结果。
    if claim.kind == "terminal":
        return read_recorded_result(claim.run_id)
    if claim.kind in {"admitted_not_dispatched", "recovery_required"}:
        return dispatch_or_reconcile(claim.run_id)
    # 冲突、拒绝或未识别状态（State）。
    if claim.kind != "new_dispatchable":
        return report_admission_problem(claim)

    execution = begin_dispatch_atomically(claim.run_id, claim.dispatch_token)
    if not execution.may_run:
        return dispatch_or_reconcile(claim.run_id)
    return run_claimed_execution(execution, budget)

执行循环：先保存观察结果（Observation），再支持下一步

execution携带已接受的执行（Run）身份与冻结输入，observations保存本次已知结果。每次模型请求（Model Request）消耗一个模型步骤（Model Step）；有工具调用（Tool Call）时，按顺序执行并保存；没有工具调用（Tool Call）时，检查完成候选。compose选择材料，execute_with_policy产生实际结果，record保存后才把它加入后续观察结果（Observation）。

def run_claimed_execution(execution, budget):
    run_id = execution.run_id
    # 冻结输入与有效策略（Policy）。
    task, policy = execution.accepted_input
    observations = load_known_observations(run_id)
    while budget.allows_next_step():
        if cancellation_requested(run_id):
            return finish(run_id, "cancelled", observations)
        # 请求准入即消耗模型步骤（Model Step）。
        budget.consume_model_step()
        request = compose(task, policy, observations)
        response = model_call(request)
        record(run_id, response)
        if cancellation_requested(run_id):
            return finish(run_id, "cancelled", observations)
        if response.tool_calls:
            for call in response.tool_calls:  # 第一版顺序执行
                if cancellation_requested(run_id):
                    return finish(run_id, "cancelled", observations)
                result = execute_with_policy(call, policy, cancel_signal(run_id))
                # 保存后才进入后续观察结果（Observation）。
                record(run_id, call.id, result)
                observations.append(result)
        else:
            report = assess_evidence(task.acceptance, observations)
            return finish(run_id, report.status, response.text, report)
    return finish(run_id, "budget_exhausted", observations)

assess_evidence接收冻结的验收（Acceptance）条件和已有观察结果（Observation）。它要分别核对用户问题是否被验证、相关测试（Test）是否实际完成、差异（Diff）是否符合范围；缺少任何必要证据，就不能给出完整成功。它不需要通过编辑测试（Test）让结果变好，也不能把模型（Model）的总结当成缺失证据。

预算（Budget）与取消（Cancellation）约束的是后续安排

若模型步骤（Model Step）上限为 BqB_qBq​、已计数为 qqq，本题的下一步条件与记账更新分别是：

q<Bq,q′=q+1.q<B_q,\qquad q'=q+1.q<Bq​,q′=q+1.

例如另设 Bq=4B_q=4Bq​=4、开始时 q=3q=3q=3，可以再准入一次请求，随后 q′=4q'=4q′=4；下一次循环停止新请求。检查而不扣减会使条件一直成立，失败后把计数退回也会抹去已经发生的尝试。这里仅解释模型步骤（Model Step）预算（Budget），费用还应按实际使用量（Usage）或账单记录，工具（Tool）的执行时间与整体期限另行检查。压缩（Compaction）不会返还已经花掉的费用。

本题在模型（Model）返回后及每次工具（Tool）准入前重新检查停止意图，执行器（Executor）也接收取消信号（Cancellation Signal）。这可防止等待期间收到取消（Cancellation）后仍主动安排后续调用；检查与真正启动之间的竞争，还需要执行入口处理。已开始的工具（Tool）先结算实际结果或未知状态，取消（Cancellation）不能抹去已有的效果（Effect）。

生产实现还需要处理模型服务提供方（Provider）异常、保存失败和终态（Terminal State）竞争，代码仅展开本题决策骨架。本题将无工具调用（Tool Call）的返回视作结束候选；mini的本地环境则检查完成标记和退出码，不能把一个方案的完成协议套给所有产品。

恢复（Recovery）继续使用原身份（Identity）与累计预算（Budget）

这里有用户任务（Task）、实际执行（Run）、模型请求（Model Request）三个层次。请求作用域（Scope）防止不同调用者或仓库的同名请求碰撞，冻结内容防止旧身份（Identity）偷偷变成新任务（Task）。派发（Dispatch）策略不得超出原授权（Authorization），还要受当前有效限制约束；内容冲突显式拒绝，不能覆盖原任务（Task）。

当前循环以单一顺序执行负责者（Execution Owner）为前提。若以后允许租约（Lease，即有期限的处理资格）过期后由另一进程接管，派发（Dispatch）、工具（Tool）准入和事实写入还需要校验负责者代际（Owner Generation），拒绝旧负责者（Owner）的迟到请求，这称为隔离令牌检查（Fencing）。租约（Lease）失效不能证明旧进程或远端行动已经停止，恢复（Recovery）也不能重置累计预算（Budget）。

6. 递进追问与完整参考答案

任务（Task）运行几十分钟怎么办？

分开管理上下文（Context）预算（Budget）、累计费用和模型步骤（Model Step）、工具（Tool）的执行时间与整体期限。压缩（Compaction）解决模型输入（Model Input）容量，不能减少既有费用或替代停止策略；等待外部结果也应有独立的等待预算（Waiting Budget）。

两个Read可以并行吗？

输入独立且没有共享效果（Effect）时，可以并行读取；编辑依赖读取结果，复测依赖编辑完成。各结果保留调用身份（Call Identity）。加入并行后仍要定义取消（Cancellation）、部分失败和结果回收，见第56章。

为什么需要运行时（Runtime），模型（Model）自己不能决定吗？

模型（Model）可提出行动请求（Action），操作系统（Operating System，OS）访问、参数校验、执行隔离（Isolation）、记录与生命周期（Lifecycle）则需要实际程序落实。提示词（Prompt）中的检查步骤能指导决策，不能替代这些执行职责。

模型（Model）说完成，但测试（Test）没跑怎么办？

报告“修改已生成、验证未完成”，或在预算（Budget）和权限（Permission）允许时继续验证。不能伪造测试（Test）结果，也不能把运行时（Runtime）的终态（Terminal State）和业务问题已解决混为一谈。

7. 方案取舍：按依赖与恢复（Recovery）需求增加能力

表 5 / Table 5 · 7. 方案取舍：按依赖与恢复（Recovery）需求增加能力
选择适用条件代价与需要核对的问题
顺序单智能代理（Sequential Agent）工作较小、依赖紧密易追踪；比较总延迟与循环次数
并行工具（Parallel Tools）独立查询较多核对延迟收益、部分失败与取消（Cancellation）
子代理（Subagent）子任务（Subtask）可独立交付，或需要上下文（Context）隔离核对委派（Delegation）成本、交付质量与整合失败
持久恢复（Durable Recovery）需要跨进程续看或核对效果（Effect）核对具体崩溃窗口；日志文件存在不代表恢复（Recovery）成功

本方案的最小验证集包括错误脚本、真实失败断言、成功修复、越界写入、工具（Tool）超时（Timeout）、预算（Budget）耗尽与重发请求。对应参考结果是：入口失败保留真实原因，越界调用在效果（Effect）前拒绝，预算（Budget）耗尽停止新调用，重发请求查询原身份（Identity）；已开始的操作仍需结算。这些是待验证的设计合同，不是新增运行成绩。

8. 窗口关闭：先判断哪个执行器（Executor）还活着

假设修复未完成，用户关闭的只是观察窗口，宿主（Host）与普通执行器（Executor）仍存活。关窗口不创建新任务（Task），也不直接取消原执行（Run）：模型（Model）与工具（Tool）继续使用原身份（Identity），运行时（Runtime）保存结果，宿主（Host）发布持久状态（Durable State）。新窗口先读取同一执行（Run）的快照（Snapshot），再消费当前订阅的增量。

若实际工具（Tool）由已断开的客户端（Client）提供，执行能力可能消失，已开始的行动请求（Action）要结算为已知结果或unknown。普通宿主（Host）执行器（Executor）的存活条件不能套用到它。若宿主（Host）也退出，则根据已提交事实恢复观察，并按该实现的恢复（Recovery）策略处理未结束执行（Run），不承诺找回任意进程调用栈。

例如README编辑结果已持久保存，测试（Test）尚未启动，重连后的报告可以是“文档已改，测试未运行”。这既不能宣布完整修复，也不要求重新编辑README。若只知道编辑已发出而没有可靠结果，则先核对文件与执行记录（Execution Record），避免重复效果（Effect）。

相关机制：第12章请求生命周期、第14章事实与投影、第25章宿主（Host）与客户端（Client）。
