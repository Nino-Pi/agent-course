第 34 章｜沙箱（Sandbox）隔离后端（Backend）：谁约束实际资源访问？

本章概览

核心问题：测试脚本已经获准运行，却尝试读取凭据或任意联网时，限制在哪一层生效？

关键概念：原生沙箱（Native Sandbox）借宿主内核（Host Kernel）限制资源；系统调用（System Call）是程序请求内核服务的接口；应用内核（Application Kernel）代为实现应用所需接口；微型虚拟机（Micro Virtual Machine，microVM）有独立来宾内核（Guest Kernel）；网络代理（Network Proxy）检查经由它的连接。

关系主线：先从任务推导允许访问的对象，再沿一次操作比较三种内核边界；配置、实际执行、兼容成本与外部效果（Effect）恢复（Recovery）分别判断。

前情回顾：获准启动，并不回答启动以后能做什么

第17章说明，权限（Permission）限定允许的意图，隔离（Isolation）约束进程实际能够访问的资源。把工作目录设为仓库，只改变相对路径的起点；程序仍可能使用绝对路径。第33章进一步区分了本机 Bash、内置文件工具和外部工具路径，不能用一个沙箱（Sandbox）名称替全部通道作保证。

第31章还保留了效果未知（Outcome Unknown）：程序可能已改变远端系统，随后才丢失回执。操作系统（Operating System，OS）限制与恢复（Recovery）协议解决不同问题。本章先研究实际访问，最后再接回这个缺口。

Codex、Pi 是智能代理（Agent）的执行入口；Anthropic sandbox-runtime 是可接入宿主（Host）的隔离（Isolation）库；gVisor 与 Firecracker 提供底层机制。以下比较它们的位置，不表示这些产品互相采用了全部能力。案例是教学设计，不是一次新运行或跨后端（Backend）测评。

1. 固定任务：让测试有足够能力，也有明确边界

沿用第30、33章的 Python 文档扫描器，当前需要验证空格路径修复。这里把未知测试脚本作为单独的执行对象：项目文件可读，临时目录和指定产物目录可写，用户已有配置不能改。修复实现的编辑入口仍按原任务范围控制，并不意味着测试脚本也需要任意修改源码。

再设一个有条件的网络变体：只有确需下载依赖且该动作已明确允许时，才开放已确认的包源。这个新增条件不授权上传仓库或发布结果。

这里的不可信代码既包括模型（Model）生成的命令，也包括仓库中原有的测试。允许运行一个入口，不能证明已审阅它调用的每一段代码；只做静态读取时，也没有必要同时授予执行脚本和联网的能力。

这给出两个设计原则。最小权限（Least Privilege） 从完成任务所需能力出发，缩小误操作的影响范围；完整仲裁（Complete Mediation） 要求每次资源访问仍受有效授权约束，旧的批准（Approval）不能掩盖后来变化的范围。它们帮助我们选择检查位置，不是某套实现无漏洞的证明。

还要区分威胁：脚本误写文件，需要限制可写对象；脚本刻意利用内核漏洞，则要看它能够直接接触多少宿主内核（Host Kernel）接口。后一问题才使三种内核边界的比较有意义。

2. 原生沙箱（Native Sandbox）：把配置变成内核检查

程序调用 open、connect，分别请求打开文件和建立连接。这类系统调用（System Call，syscall）把用户程序的请求交给内核。原生沙箱（Native Sandbox）仍由宿主内核（Host Kernel）处理请求，但在它提供的检查点限制资源。

用读取仓库文件这一步理解几种构件：

Codex 的一条本地启动链

在本章核对的本地路径中，SandboxManager::transform 将有效权限（Permission）转成要启动的参数数组（Argument Vector）：macOS 生成 Seatbelt 参数并加上 sandbox-exec；Linux 交给专用辅助程序（Helper）。未启用 use_legacy_landlock 的 Linux 路径先建立 bubblewrap 环境，再重新进入内部阶段施加安全计算机制（seccomp）。这一路失败不会自动切回旧的 Landlock 路径；后者由显式选项控制。

因此，类型名 LinuxSeccomp 并没有列出整个执行边界。需要沿真正的启动链检查文件视图、网络与调用过滤如何组合。Maka 的负责者（Owner）、沙箱配置语言（Sandbox Profile Language，SBPL）和文件执行器（File Executor）链见第17章；不同产品必须分别闭合，不能复制默认值。

为什么系统调用（syscall）过滤不能独自表达“只读这个仓库”？

安全计算机制（seccomp）使用伯克利包过滤器（Berkeley Packet Filter，BPF）形式的程序检查系统调用（syscall）；这里被检查的是调用数据，而非网络包。普通过滤程序可以看到编号和寄存器参数，却不能沿参数指针读取任意路径字符串。

假设应用请求 open(path)。过滤器看到某个参数位置保存了地址，不等于知道那个地址中的字符串是仓库文件还是凭据路径。只允许 open 也不会自动表达“只打开仓库”。文件视图、挂载和资源访问控制需要负责对象范围，调用过滤则进一步缩小操作面。

子进程继承过滤器，回答的是限制能否延续；过滤器能否表达文件路径，回答的是规则能检查什么。两者不能混为一谈。所有这些检查仍依赖宿主内核（Host Kernel）正确执行，原生接口带来工具兼容性，也保留了获准内核接口的攻击面。

路径检查以后，对象可能换成另一个

设某个只读保护路径穿过仍可写的符号链接（Symbolic Link）。初始化时解析并保护旧目标，脚本随后替换链接，同一逻辑路径就会指向别处。检查与使用时间差（Time-of-check to Time-of-use，TOCTOU） 在这里形成竞态；一次 realpath 不能覆盖整个执行期。

Codex 的 append_read_only_subpath_args 与 append_unreadable_root_args 对跨越可写符号链接（Symbolic Link）的相应保护返回错误。它不把当时目标的快照（Snapshot）冒充持续有效的策略。这个例子说明：当后端（Backend）不能可靠表达所需限制时，停止启动可以比静默近似更符合合同。

3. gVisor：应用内核（Application Kernel）接住请求

换成 gVisor，应用面对的 Linux 接口由用户态应用内核（Application Kernel）Sentry 实现。Sentry 必要时才使用受限的宿主（Host）能力；应用请求与它发给宿主内核（Host Kernel）的系统调用（syscall）不是一一转发关系。

用一个简单操作建立直觉：应用请求 getpid 时，Sentry 可以查自己的进程表返回标识，无需问宿主内核（Host Kernel）“当前宿主进程是谁”。读取文件时，则先进入 Sentry 的文件系统语义，再使用授予它的访问路径。应用不能把整套 Linux 应用二进制接口（Application Binary Interface，ABI）原样交给宿主内核（Host Kernel）；未实现的接口会成为兼容性边界。

Systrap 怎样转交系统调用（syscall）？

信号（Signal）是操作系统（OS）向进程或操作系统线程（OS Thread）递送事件（Event）的一种机制。Systrap 使用安全计算机制（seccomp）的 SECCOMP_RET_TRAP，让触发的线程收到 SIGSYS。应用侧已安装的转交代码（Stub）通过共享状态通知 Sentry，后者处理后恢复应用执行。

这与第06章的 SIGKILL 不同：后者直接终止进程，不能由应用安装处理程序来继续。这里的调用过滤构件用于转交处理，不能看到安全计算机制（seccomp）就断言“该调用一定被拒绝”。

gVisor 也有基于内核的虚拟机（Kernel-based Virtual Machine，KVM）执行平台，使用处理器虚拟化机制隔离和切换地址空间（Address Space），应用需要的内核接口仍由 Sentry 实现。它保留进程模型，没有像 Firecracker 那样启动完整 Linux 来宾系统（Guest）。硬件辅助虚拟化（Hardware-assisted Virtualization）也不是逐条模拟整台机器的每条指令。

Systrap 不要求虚拟化扩展，在已有虚拟机（Virtual Machine，VM）内可以避开嵌套虚拟化（Nested Virtualization）的依赖。平台选择改变所用宿主（Host）机制与开销，不能单凭“基于内核的虚拟机（KVM）”这个名称判断内部是哪一种系统。

Gofer 与 Directfs：授予文件树，仍需具体配置

第17章的文件描述符（File Descriptor，fd）是对已打开对象的句柄；路径后来改变，不会自动让旧句柄指向新文件，但句柄本身不锁住内容。

Gofer 是 gVisor 的文件代理（File Proxy）。当前官方文档中，Directfs 默认启用：Gofer 把挂载点的文件描述符（fd）交给 Sentry，使其经基于句柄的调用访问已授予的树，减少文件代理（File Proxy）往返。关闭 Directfs 时，Sentry 的文件访问限制更严格，更多操作需要经远程过程调用（Remote Procedure Call，RPC）交给 Gofer。

所以不能把所有配置都画成“每个文件字节必经 Gofer”。对本例，关键是只授予仓库和运行库所需的树；如果把凭据目录也暴露进去，应用内核（Application Kernel）不会重新推断用户想让它保密。

网络栈（Network Stack）也不等于目的地许可

默认的 netstack 是用户态网络栈（User-space Network Stack），经已准备的底层链路交换数据。--network=host 则使用 hostinet，改用宿主网络（Host Networking），交换了一部分隔离（Isolation）以使用原生网络能力。包源的目的地限制仍需要另行配置。

这条路线的成本取决于负载。大量本地计算与频繁的小系统调用（syscall）可能承受不同开销；兼容性、文件往返与网络路径也会改变结果。比较时应固定真实任务和配置，不能用一个启动时间或综合性能测试（Benchmark）给所有智能代理（Agent）工作负载排名。

4. Firecracker：来宾内核（Guest Kernel）与虚拟设备（Virtual Device）

Firecracker 启动微型虚拟机（microVM）。应用先向独立的来宾 Linux 内核（Guest Linux Kernel）请求服务，再经虚拟设备（Virtual Device）访问存储和网络。虚拟机监控器（Virtual Machine Monitor，VMM）与基于内核的虚拟机（KVM）设施构成相应边界。

继续问 getpid：本次由来宾内核（Guest Kernel）提供语义。并非每次系统调用（syscall）都触发虚拟机监控器（VMM）的业务审批；例如读取命中来宾内存中的缓存，可在内部完成，涉及设备的输入/输出（Input/Output，I/O）才进入相应设备处理路径。

三条分支比较请求经过的边界。图中 microVM 是微型虚拟机（Micro Virtual Machine），KVM 是基于内核的虚拟机（Kernel-based Virtual Machine）设施；gVisor 的基于内核的虚拟机（KVM）执行平台已在前节单独解释，不能根据同名设施把两种结构合并。

磁盘、网络和虚拟机监控器（VMM）自己分别由谁限制？

Firecracker 的块设备（Block Device）由宿主（Host）文件支撑；网络设备由宿主（Host）的 TAP 虚拟网络接口（TAP Virtual Network Interface）支撑。这种接口交换以太网帧，即链路层数据包，与第26章的通用测试协议（Test Anything Protocol，TAP）同名但含义不同。

在本例可把仓库准备到来宾系统（Guest）可见的磁盘，另给产物盘。虚拟机监控器（VMM）处理块设备（Block Device），不会理解哪个文件是 README、哪个业务请求属于发布。Firecracker 的设计文档要求宿主（Host）承担网络过滤，微型虚拟机（microVM）不自带“仅访问本题包源”的业务策略。

还要约束虚拟机监控器（VMM）进程本身。Firecracker 的隔离启动器（Jailer）准备资源、关闭多余文件描述符（fd）、清理继承环境、改变文件视图和用户身份（Identity），再执行目标程序；目标的安全计算机制（seccomp）继续限制向宿主内核（Host Kernel）发出的系统调用（syscall）。隔离启动器（Jailer）的路径和资源输入由可信操作者负责，它不是任意二进制通用的沙箱（Sandbox）启动器。

独立来宾内核（Guest Kernel）增加一层边界，但仍需信任基于内核的虚拟机（KVM）设施、虚拟机监控器（VMM）、宿主（Host）配置和授予的设备。镜像准备、数据导入导出、内核与设备维护也会增加工程成本。因此，“有独立内核”不能单独证明完整服务安全。

5. 网络代理（Network Proxy）：怎样让脚本必须经过出口？

前面三种环境还没有自动回答“只访问包源”。HTTP_PROXY 环境变量帮助愿意遵守的程序选择出口；脚本可以忽略它，直接建立连接。要形成强制边界，还需关闭绕过代理（Proxy）的路径。

Anthropic sandbox-runtime 的所核 Linux 分支在需要网络限制时使用 --unshare-net 建立隔离的网络命名空间（Network Namespace），将通往宿主代理（Host Proxy）的 Unix 套接字（Unix Socket）桥接进来。macOS 通过 Seatbelt 限制出站连接，并为指定代理（Proxy）端口添加许可。环境变量负责引导，操作系统（OS）边界负责限制直连；获准的本地通信等例外仍需按实际配置核对。

接下来，库中的 filterNetworkRequest 验证并规范化目标主机（Host Name），先查拒绝名单（Denylist），再查允许名单（Allowlist）。未匹配时，按配置拒绝或调用询问回调（Ask Callback）；strictAllowlist 禁止用该回调扩大名单。检查时与连接时必须使用一致的目标解释，否则可能检查一个名称、实际连接另一对象。

目的地可达，不等于允许上传这份内容

超文本传输协议（Hypertext Transfer Protocol，HTTP）的 CONNECT 方法可以建立隧道（Tunnel）。普通代理（Proxy）据主机和端口允许隧道，端到端传输层安全协议（Transport Layer Security，TLS）加密则让它看不到内部请求内容。

假设包源与攻击者仓库位于同一个获准域名：连接策略可能允许到达两者，却没有表达“只下载这个依赖，不上传源码”。目的地许可（Destination Permission）与数据用途（Data Use）需要分开。

库的可选传输层安全终止（TLS Termination）让代理（Proxy）终止加密连接，再配合 filterRequest 检查明文超文本传输协议（HTTP）请求或已终止的安全超文本传输协议（Hypertext Transfer Protocol Secure，HTTPS）请求。指定豁免目标、SOCKS 套接字代理（SOCKS Proxy）及非传输层安全协议（TLS）的不透明隧道（Opaque Tunnel）不会自动经过这项内容检查。进一步约束接口方法和业务资源仍需要显式策略。

双向传输层安全认证（Mutual Transport Layer Security，mTLS） 还要求客户端（Client）用证书证明身份（Identity）。代理（Proxy）将连接拆为两段后，需要另行安排双方认证，不能自动继承客户端（Client）身份（Identity）。证书固定（Certificate Pinning） 要求对端证书或公钥匹配预先认可的值，替代证书可能被拒绝。这些是兼容条件，不代表所有双向传输层安全认证（mTLS）连接都不能经代理（Proxy）转发。

由此应同时保留两条限制：默认隧道（Tunnel）不是内容防泄漏证明；这个独立库也不只是永远检查域名。该结论针对所核源码分支，不能推广到每个采用它的产品。

文件默认策略也不能从工作目录猜出来

该库 README 的读取策略默认允许，再按拒绝路径及局部重新允许收窄；写入则需要明确允许，并可在其中继续禁止。若要实现“仅可读仓库”，必须从这个默认值推导额外规则，不能只设置当前工作目录（Current Working Directory）。

本节核对独立库的 macOS/Linux 路径。仓库另有 Windows 实现，其机制与默认不从这里继承；Claude Code 的产品设置与实际覆盖范围也不能由库主干的新字段推断，仍需按第33章的产品合同判断。

6. 接回 Pi：可替换执行器（Executor）不等于强制隔离（Mandatory Isolation）

Pi 把工具输入输出与具体执行分开：BashOperations.exec(command, cwd, options) 提供实际执行操作，createBashTool 可以接收另一份实现。默认 createLocalBashOperations 进入本地命令解释器（Shell）启动路径；官方沙箱扩展（Sandbox Extension）则通过 wrapWithSandbox 包装命令后启动。

先看外围框架：扩展创建 localBash，注册同名工具，并在会话（Session）启动时初始化沙箱（Sandbox）。下面摘取注册工具内的真实分支，只新增两条教学注释。输入仍是原工具参数，输出仍回到原工具协议；改变的是采用哪份执行实现。

async execute(id, params, signal, onUpdate, _ctx) {
    // 未启用或初始化未成功时，这个可选扩展继续使用本地执行。
    if (!sandboxEnabled || !sandboxInitialized) {
        return localBash.execute(id, params, signal, onUpdate);
    }

    // 成功启用后，替换实际操作；工具表面保持不变。
    const sandboxedBash = createBashTool(localCwd, {
        operations: createSandboxedBashOps(),
    });
    return sandboxedBash.execute(id, params, signal, onUpdate);
},

片段需要注册对象和外围变量，不是独立程序。createSandboxedBashOps 内部调用 SandboxManager.wrapWithSandbox，再启动包装后的命令；不是只改工具名称便获得限制。扩展也为 user_bash 提供相同执行操作，但没有因此替换所有文件工具或外部工具通道。

关闭配置、平台不支持或初始化失败，都会让上述本地分支继续生效。示例依赖的是 sandbox-runtime 0.0.26，不能把前节独立库主干的新字段自动赋给它。存在扩展点（Extension Point），只证明开发者可以选择执行器（Executor）；“本任务要求强制隔离（Mandatory Isolation），失败不启动”则需要另一条不能降级的合同。

执行合同（Execution Contract）初始化失败时所承诺的能力

再接回第31章：工具注册表（Registry）解析身份（Identity），批准（Approval）限定动作，执行后端（Backend）限制实际访问。Goose 对工具负责者（Owner）的重新检查不能替代后端（Backend）；后端（Backend）也不能替可信远端接口判断业务动作是否正确。

恢复快照（Snapshot），为什么不能直接重发远端任务？

再改变任务条件：用户明确允许创建一次远端持续集成任务（Continuous Integration Job，CI Job）。脚本已提交请求，回执到来前被终止，随后从较早的虚拟机（VM）快照（Snapshot）继续。

Firecracker 的快照（Snapshot）保存来宾内存和虚拟机（VM）状态，磁盘文件仍有外部管理责任，连接状态也不保证保留。它没有和任意外部服务组成一笔原子事务（Atomic Transaction）。恢复到本地“尚未提交”的画面，不会使远端已创建的持续集成任务（CI Job）消失。

表 5 / Table 5 · 恢复快照（Snapshot），为什么不能直接重发远端任务？
操作改变什么没有自动完成什么
停止进程阻止它继续执行撤销先前效果（Effect）
销毁沙箱（Sandbox）释放该环境的资源删除远端业务对象
恢复快照（Snapshot）恢复所覆盖的环境状态与外部服务一起回滚（Rollback）
补偿（Compensation）远端效果（Effect）在另一次获准操作中改变业务状态保证补偿（Compensation）自身一定成功

后续应按原业务标识查询效果（Effect）的负责者（Owner），结合仍有效的幂等（Idempotency）合同决定重试（Retry）。无法查询且缺乏相应合同时，保留效果未知（Outcome Unknown）。沙箱（Sandbox）越强，也不会填平这项业务回执缺口。

8. 参考问答：沿真实对象作判断

问题 1。 cwd=repo 与 HTTP_PROXY 都已设置，能否限制未知脚本？

参考答案。 两者分别提供路径起点和代理（Proxy）路由建议。脚本仍可能用绝对路径或直接连接；必须再有实际文件访问控制和不能绕过的出口。

问题 2。 三种环境中的 getpid 分别由谁提供语义？

参考答案。 原生进程由宿主内核（Host Kernel）提供；gVisor 由 Sentry 提供；微型虚拟机（microVM）由来宾内核（Guest Kernel）提供。存在基于内核的虚拟机（KVM）设施，不足以判断完整结构。

问题 3。 允许某类系统调用（syscall），为何不等于允许某棵文件树？

参考答案。 普通安全计算机制（seccomp）的过滤程序不能沿路径指针读取字符串；对象范围需要文件视图、挂载或资源访问控制共同表达。规则继承与表达能力是两个维度。

问题 4。 已采用应用内核（Application Kernel）或微型虚拟机（microVM），为何还要配置挂载和出口？

参考答案。 隔离（Isolation）限制对未授予资源的访问，授予哪些资源仍由可信配置决定。获准连接也可能承载错误业务请求，目的地许可（Destination Permission）不能代替数据用途（Data Use）判断。

问题 5。 沙箱扩展（Sandbox Extension）初始化失败后继续本地执行，何时违反合同？

参考答案。 若任务要求强制隔离（Mandatory Isolation），它违反“无法建立限制就不启动”的条件；若系统只承诺可选扩展，这是已定义的降级，但不能再称本次受该后端（Backend）保护。

问题 6。 从创建持续集成任务（CI Job）前的快照（Snapshot）恢复，下一步该做什么？

参考答案。 先核对远端效果（Effect），不能看到较早本地状态就重复提交。查询与幂等（Idempotency）合同不足时保留未知，并报告恢复（Recovery）范围。

把本章设计用于原扫描器验证时，可信宿主（Host）先准备所需资源范围，后端（Backend）建立限制后才启动脚本；强制隔离（Mandatory Isolation）失败则停止。网络变体还需受控出口；另行获准的远端动作若丢回执，进入效果未知（Outcome Unknown）处理。这条设计路径并不表示某个智能代理（Agent）已经完整采用全部机制。
