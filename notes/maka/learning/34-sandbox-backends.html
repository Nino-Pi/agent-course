第 34 章｜沙箱隔离后端

本章概览

核心问题：不可信脚本无视提示词并直接访问文件或网络时，实际限制在哪一层生效？

关键概念：原生沙箱：借宿主内核限制资源；seccomp：过滤系统调用；Sentry：gVisor 的用户态内核实现；microVM（微型虚拟机）：具有独立来宾内核的执行环境；网络代理：按策略转发连接；执行后端：承接 Agent 操作的实现。

关系主线：从工具参数追到系统调用和资源访问，比较宿主、用户态内核与虚拟机边界；初始化失败、兼容成本及外部效果恢复分别判断。

前置：第31章工具契约、执行与恢复。

Codex 与 Pi 提供 Agent 执行入口；Anthropic sandbox-runtime 是可接入宿主的隔离库；gVisor 与 Firecracker 提供不同的底层隔离机制。以下比较它们的作用位置，不表示这些 Agent 都使用了这些后端。

1. 固定任务，再决定必须防住什么

仍然修复文档检查器。先读取仓库，运行仓库提供的测试脚本；若确需下载依赖，只允许访问已确认的包源。把三个动作拆开，是因为它们需要不同能力：

表 1 / Table 1 · 1. 固定任务，再决定必须防住什么
动作（Action）正常需要一个具体反例设计必须说明什么
读仓库（Read）读源码、测试和必要运行库工具顺便读取宿主凭据目录实际可读对象集合，不能只说 cwd 在仓库

这里的不可信输入既包括模型生成的命令，也包括仓库里已有的脚本。允许执行项目的测试入口，不等于审阅了它递归调用的每段代码。另一方面，若任务只需静态读取，给它启动任意脚本和联网的能力没有帮助。

这正是最小权限原则的用途：从正常任务推导必要权限，降低错误发生时能波及的范围；完整仲裁原则则要求每次资源访问仍有约束，不能靠一次缓存的批准覆盖以后所有变化。它们帮助选择检查位置，并不承诺某套规则没有漏洞。

先区分两个威胁：脚本误写了用户文件，可以用文件访问边界限制；脚本刻意利用宿主内核漏洞，则要考虑它直接接触多大内核接口。后一问题引出用户态应用内核（application kernel）与虚拟机（VM）对内核攻击面的不同处理。

2. 从 Agent 参数走到 OS 约束：原生后端做了哪几步

普通程序运行 open、connect 等系统调用（syscall），请内核访问文件、建立连接。原生隔离继续使用宿主内核，同时在它提供的检查点施加限制。各机制的约束对象不同：namespace 改变进程看到的资源视图，只读挂载限制写入，seccomp 筛选系统调用编号和参数，Seatbelt 则对资源操作应用 profile。

在当前 Codex 的选定本地路径中，SandboxManager::transform 将有效权限转换为真正要启动的 argv。macOS 分支生成 Seatbelt 参数后加上 sandbox-exec；Linux 分支交给专用 helper。Linux helper 的非 legacy 路径先建立 bubblewrap 环境，再进入内部阶段施加 seccomp；源码明确区分显式 legacy Landlock 路径，不能概括成“Linux 永远只有 Landlock”。这解释了为什么一个 SandboxType 名称不足以描述真实边界。

从权限（Permissions）到隔离（Isolation），需要把可信配置落实为进程无法自行跳过的资源检查。

“可信宿主”是一个实质条件：如果模型能替换实际使用的权限配置或绕过这条启动路径，profile 再精细也无效。Maka 的具体 owner、SBPL 与 worker 链放在 第17章；Codex 的接线提供另一种执行编排实例。

为什么 seccomp 不能独自表达“只读这个仓库”

普通 seccomp 的 BPF 过滤程序由内核执行，可检查 syscall 编号及寄存器参数，不能解引用参数指向的路径字符串。因此可以限制某类 socket 或危险 syscall，却不能靠一个 open(path) 的指针值判断路径是否在仓库。Linux 官方文档也明确将它定位为缩小内核攻击面的构件，需要结合其他权限机制。子进程继承过滤器与“能表达何种文件策略”是两件事。

对本例，文件视图和可写挂载负责“哪些树可访问”，syscall 过滤负责进一步缩小操作面。二者仍依赖同一个宿主内核正确执行。优点是应用通常继续使用原生系统接口，便于接入本地开发工具；代价是后端必须适配平台，且允许的内核接口仍是攻击面。

路径字符串批准以后，对象还可能改变

设只读保护路径经过一个仍可改写的符号链接（symlink）。初始化时解析它并保护当时的目标，之后脚本换掉链接，逻辑路径就可能指向另一对象。这是检查时与使用时不一致的 TOCTOU 问题，单纯做一次 realpath 不能给整个执行期提供保证。

Codex 的 append_read_only_subpath_args 与 append_unreadable_root_args 对跨越可写 symlink 的相应保护直接报错：它拒绝把不能可靠表达的策略近似成启动时快照。这个例子也说明“限制不支持，停止启动”为什么有时比接受一个看似相同的配置更符合合同。

3. gVisor：把应用的 Linux 接口放到 Sentry 中实现

gVisor 的关键变化不是增加一张 syscall denylist，而是让应用面对一个用户态 application kernel：Sentry 在自己的实现中处理 Linux 接口，必要时才用受限的宿主能力。应用的 syscall 与 Sentry 发给宿主的 syscall 不再是一一转发关系。未实现的接口会形成兼容性边界。

以 getpid 为例，Sentry 可以从自己的任务表返回结果，无需询问宿主“当前进程 PID”。以读取文件为例，请求先进入 Sentry 文件系统语义，随后才使用授予该沙箱的文件访问路径。这让不可信应用无法直接把它想调用的整套 Linux ABI——程序与内核约定的二进制调用接口——交给宿主内核。

系统调用究竟如何转交给 Sentry

信号是操作系统向进程或线程递送事件的一种机制。Systrap 中，当前系统调用触发 seccomp 的 SECCOMP_RET_TRAP，使线程收到 SIGSYS；已安装的处理程序接住它，应用侧的小段转交代码（stub）通过共享状态把事件交给 Sentry，处理后恢复应用执行。这与第06章直接终止进程的 SIGKILL 不同。这里 seccomp 用于转交处理，与上一节“允许或拒绝 syscall”的典型用途不同。

gVisor 也有基于 Linux 虚拟化设施 KVM 的执行平台。KVM 让程序使用 CPU 提供的虚拟化执行机制，建立和切换受隔离的执行上下文；gVisor 借它运行应用并控制地址空间，应用所需的内核接口仍由 Sentry 实现。硬件辅助虚拟化不等于逐条指令模拟整台机器，这条路径也没有像 Firecracker 那样启动完整 Linux 来宾系统（guest）。Systrap 不要求虚拟化扩展，在已有 VM 内部署时避免依赖嵌套虚拟化；平台选择同时影响性能和使用的宿主机制。

文件代理不是一个永远固定的拓扑

Gofer 为文件挂载提供代理服务。当前文档中的 Directfs 默认开启：Gofer 将挂载目录的已打开句柄（文件描述符，FD）交给 Sentry，Sentry 可用基于 FD 的调用访问授予的树，从而省去部分 RPC；关闭 Directfs 才使用更严格的 Sentry 文件访问限制和更多 Gofer 往返。两者不能画成同一张“所有文件字节都经 Gofer”的图。

对应本例，关键仍是只暴露仓库和运行时需要的挂载。给 Sentry 暴露整份凭据目录，它就可以在授权范围内读取；application kernel 不会重新推断用户想让哪些文件保密。FD 授权减少路径解析所能触达的对象，选择哪些 FD 仍由外部配置承担。

网络也有同样的边界：默认 netstack 在用户态实现网络栈，接到受控的底层链路；--network=host 则使用 hostinet，交换了部分隔离以利用原生网络。用户态 TCP/IP 栈不是域名允许名单，对包源的目的地限制仍需另行配置。

这种路线适合讨论多租户不可信代码与内核攻击面，但必须承认 syscall 兼容和中间处理成本。CPU 密集计算与高频小 syscall 的代价不会相同；不能拿一个启动时间或综合 benchmark 为所有 Agent 任务排名。

4. Firecracker：应用 syscall 留在 guest，跨 VM 边界的是设备交互

Firecracker 启动 microVM。脚本先调用来宾 Linux 内核（guest Linux kernel）；guest 通过虚拟设备使用存储和网络，Firecracker 的虚拟机监控器（VMM）与 KVM 提供虚拟机边界。并非每次应用 syscall 都触发一次 VMM 审查。 例如 guest 内存里的文件缓存命中可能在 guest 内完成，跨设备 I/O 才进入相应虚拟化处理路径。

图中三个分支是机制概览；gVisor 的 KVM platform 另见上一节。可见“存在 KVM”不足以判断应用看到哪种 kernel interface。

Firecracker 的块设备（block device）由宿主文件支撑，网络设备由宿主 TAP 虚拟网络接口支撑。TAP 让 VMM 等用户态程序与宿主网络栈交换以太网帧，即链路层的数据包；它与第26章的同名测试输出格式含义不同。对本例，可以把仓库准备进 guest 可见磁盘，另给产物盘；VMM 处理的是块设备，不会理解哪个文件是 README、哪个 HTTP 操作是发布。设计文档明确要求宿主承担网络过滤，不能把 microVM 误认为自带包源域名策略。

还要限制 VMM 自己。Firecracker 的 jailer 准备隔离资源、关闭多余 FD、清理继承环境、切换文件视图和用户身份后执行 VMM；VMM 的 seccomp 再约束其宿主 syscall。jailer 的路径和资源输入由可信操作者负责，它不是任意二进制通用的 sandbox launcher。

因此 VM 把应用与宿主之间加入独立 guest kernel 和虚拟设备边界，但仍需信任 KVM、VMM、宿主设置及授予的设备。为了隔离强敌手，这种边界可能值得；为了频繁读改本地小文件，镜像准备、数据导入导出、内核和设备维护则成为新的工程成本。不能仅凭“有独立内核”判断某个完整服务的安全性。

5. Anthropic sandbox-runtime：代理怎么成为强制经过的网络关口

前面三种执行环境都还没回答“只访问指定包源”。把 HTTP_PROXY 写入环境，只帮助愿意遵守的程序路由；恶意脚本可以删掉变量，直接 connect。有效方案还要关闭这条绕行路径。

当前 Anthropic sandbox-runtime 的 Linux 分支在需要网络限制时使用 --unshare-net，并将通往宿主代理的 Unix socket 桥接进沙箱；macOS 通过 Seatbelt 限制连接到指定代理端口。代理在允许的出口上裁决目的地。环境变量帮助应用使用出口，namespace/profile 负责让忽略变量的应用不能按原方式直连。

其 filterNetworkRequest 先验证并规范化 host，再检查 deny、allow，未匹配时根据配置拒绝或进入询问 callback。strictAllowlist 禁止 callback 扩张此边界。host 和 port 的一致解释很重要：批准时与连接时若将同一个名称解析成不同形式，就可能检查了一个对象却连接另一个。

“目的地可达”与“允许上传这份内容”之间还差什么

普通 HTTPS CONNECT 代理可以按主机名和端口（host/port）决定是否建隧道，但端到端 TLS 加密下看不到应用请求内容。获准访问代码托管域名，也可能访问攻击者控制的仓库。域名策略限制可达服务，不自动表达“只能下载该依赖，不能上传源码”。

这个开源库还提供可选 TLS termination：代理终止加密连接，使这一段 HTTPS 请求可被检查；配合 filterRequest，可在明文 HTTP 或被终止的 HTTPS 路径作请求过滤。HTTPS 豁免、SOCKS 代理和非 TLS 的不透明转发隧道不能继承这项检查。进一步约束 API 方法/资源需要显式过滤策略，TLS 检查也会改变原连接的认证条件。

双向 TLS 认证（mTLS）除验证服务端外，还要求客户端以证书证明身份；代理把一条连接拆成两段时，需要另行安排两侧认证，不能自动继承原来的客户端身份。证书固定（pinning）要求对端证书或公钥与预先认可的值相符；代理出示的替代证书可能因此被客户端拒绝。这些是代理的兼容条件，不表示所有 mTLS 连接都无法代理。不能把默认隧道能力说成内容防泄漏，也不能说该库永远只能检查域名。

文件策略亦需读实际默认值：该库 README 将读取设计成默认可读、deny 后可局部 re-allow，写入则需显式 allow 并可设置 deny。要实现“仅可读仓库”，还需收窄默认读取范围；设置工作目录本身不限制可读对象。本文聚焦 macOS/Linux；当前仓库另有 Windows 实现，其机制和默认不从这里继承。

这里读取的是独立库当前主干。Claude Code 如何配置、哪些工具路径覆盖及如何降级，仍以 第33章｜Claude Code：工具、Hooks 与安全 的产品资料范围为准；开源库有新字段不证明已在某个 Claude Code 发布版本接线。

6. 回到 Agent：可替换执行器与默认强边界是两项能力

Pi 的 BashOperations.exec(command, cwd, options) 把工具输入/输出与实际执行分开。默认 createLocalBashOperations 进入本地 shell spawn；createBashTool 可接入另一份 operations。官方 sandbox 示例就在这个接缝调用 Anthropic wrapWithSandbox，再启动包装后的命令。这是扩展点的具体价值：保留 Bash 工具表面，替换执行位置与限制。

但示例的 disabled、unsupported 或初始化失败路径会保留本地执行，且该示例只替换相应 Bash 路径。不能由存在这个例子推出“Pi 默认所有工具已强制隔离”。示例依赖声明为 sandbox-runtime 0.0.26，也不能把本章读取的独立库主干新字段自动算给它。

由此得到两种不同的执行合同：开发者自行选择 execution operations，优先组合灵活性；或者只要某任务被声明为必须隔离，初始化失败就禁止启动，优先边界不能降级。前者便于组合，后者适合强制隔离需求；初始化失败时的行为是两者的关键差别。

再接回 第31章：registry 保证工具身份，approval 确定动作授权，backend 限制其实际访问。Goose 的 owner 重查不能替代 backend，backend 也不能阻止可信远端 API 在已授权范围内做错业务动作。

最后考虑：脚本已经创建远端持续集成任务（CI job），回执到来前被杀，随后从 VM 快照恢复。隔离环境恢复不使远端 job 消失。Firecracker 的快照涉及 guest 内存和虚拟机状态，磁盘文件仍有外部管理责任，连接状态也不保证保留；它没有与任意外部服务建立一笔原子事务。

因此重试仍须由业务 key、效果查询和受信回执决定。停止进程、销毁沙箱、恢复快照和补偿远端效果是四项不同操作。

8. 资源访问与恢复的参考结论

为什么 cwd=repo 加 HTTP_PROXY 不能限制未知脚本？

cwd 只影响相对路径；代理变量只是路由建议。脚本仍可能使用绝对路径和原始连接，实际限制还需文件访问控制与无法绕过的网络出口。

三个环境中的 getpid 由谁提供语义？

原生进程由宿主内核提供；gVisor 由 Sentry 提供；microVM 中由 guest kernel 提供。不能假设每次 syscall 都由 VMM 按业务规则审批。

为什么 seccomp allowlist 不能单独表达允许的文件树？

普通 BPF filter 不能解引用路径指针；文件系统视图、挂载或资源访问控制必须共同表达允许访问的对象。

Sentry 或 VM 已隔离，为什么还需要挂载、磁盘和出口策略？

隔离限制对未授予资源的访问，授予哪些资源仍由可信配置决定。允许访问的网络也可能被用于错误目的，目的地限制不等于数据用途许可。

sandbox extension 初始化失败后继续本地 Bash，改变了什么？

它不满足“该任务必须隔离，不能绕过后端”的强制合同。若系统只承诺可选扩展，这可以是既定降级策略，但不能再将本次执行描述为受该后端保护。

恢复到创建 CI job 前的 VM 快照，为什么不能直接重跑提交？

快照不包含外部服务的原子回滚，原请求可能已经创建 job。恢复流程应查询效果 owner，并按仍有效的幂等合同处理原操作；无法查询时保留未知。

把这些结论放回同一任务，可以得到一条完整参考路径：Host 生成“仓库可读、产物目录可写、仅经受控出口访问包源”的可信配置，后端安装相应资源限制后启动测试脚本；若所需隔离无法建立，强制隔离合同下不启动。执行后若创建 CI job 的回执丢失，运行状态进入未知效果处理，按原业务标识查询远端，而不是恢复快照后再次提交。这是设计推演，不表示某个 Agent 已完整采用所有机制。

工具与执行、Codex和Claude Code分别说明这些边界怎样接到具体工具通道。
