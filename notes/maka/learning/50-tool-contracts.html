第 50 章｜设计工具（Tool）的声明、执行与结果合同

本章概览

核心问题：怎样让模型（Model）准确提出一次编辑，又让真实执行遵守权限（Permission）和文件条件，并在失败后选择正确下一步？

关键概念：参数结构（Schema）限定输入形状；执行上下文（Execution Context）绑定可信身份与边界；观察版本（Observed Version）标识读取依据；条件提交（Conditional Commit）检查前提；结果合同（Outcome Contract）区分成功、失败与未知。

关系主线：声明帮助选择，运行时（Runtime）校验与准入（Admission），资源负责者（Resource Owner）提交效果（Effect）；结果再进入模型输入（Model Input）。编辑成功、远端任务被接纳与整项任务完成，各需要自己的证据。

前情回顾：工具（Tool）成功只是修复链的一步

第16章把工具声明（Tool Declaration）与真实实现分开：名字、描述和参数结构（Schema）供模型（Model）选择，执行器（Executor）才能接触文件。第18章又区分效果（Effect）与回执（Receipt）：没有收到成功，不等于没有发生修改。

第49章用这些结果决定继续调查还是交付。本章把范围收窄到其中的一次README编辑，明确模型（Model）填写哪些参数、可信运行时（Runtime）绑定哪些条件、资源负责者（Resource Owner）接受什么写入。整体设计顺序沿用第48章，不要求先选择某种工具（Tool）名称。

本文接口（Interface）、状态（State）和值均为教学设计，不是Maka应用编程接口（Application Programming Interface，API）。尤其是观察版本（Observed Version）与条件提交（Conditional Commit），需要实际资源协议支持，不能通过给普通Edit多加字段获得。

1. 原题与约束：这一次只修改README

让智能代理（Agent）修正README的测试（Test）命令。工具（Tool）的描述、参数、结果和失败处理应怎样配合？

这里使用与第49章同类的本地项目，但另设只修README的任务（Task），源码与测试（Test）保持不动。题设中package.json的scripts.test为node --test，README却有一处Run npm run check.；应把说明改为Run npm test.。之后实际执行入口和检查差异（Diff），才能判断这项任务（Task）是否完成。用户可能在模型（Model）读取后继续编辑同一个文件。

最小能力集合是Read、Edit、Bash。读取配置与文档提供定位依据，编辑选择具体变更，测试（Test）结果支持后续判断。合成一个FixEverything会隐藏中间决策；细拆成取一个字符又会增加调用成本。工具粒度（Tool Granularity）应保留必要观察结果（Observation），并让每次操作有明确成功条件。

本题选择的单次编辑合同是：在指定工作区（Workspace），将基于指定观察版本（Observed Version）的唯一旧片段替换为新文本；只有资源负责者（Resource Owner）接受提交，才报告修改成功。 这是更强的教学选型，不表示Maka的old_string已经代表文件版本（File Version）。

2. 完整参考方案：四组职责分别闭合

模型（Model）读到实际配置和文档后才提出编辑。Edit的工具声明（Tool Declaration）包含名字、用途、前提和严格参数结构（Schema）；参数表达工作区（Workspace）内路径、Read返回的观察版本（Observed Version）、唯一旧片段与新片段。描述还应说明何时先读、失配后怎样重新定位，而不是让模型（Model）只猜另一段旧文本。

运行时（Runtime）从可信执行上下文（Execution Context）注入工作区（Workspace）、调用身份（Call Identity）、取消信号（Cancellation Signal）和权限边界（Permission Boundary），校验参数与本步可用性，再交给文件执行器（File Executor）。模型（Model）不能通过自填“我是管理员”取得授权（Authorization）。

文件执行器（File Executor）把操作交给资源负责者（Resource Owner），核对当前对象、版本（Version）和匹配条件，以原子条件提交（Conditional Commit）或受可靠锁保护的检查与写入完成修改。只有旧片段仍存在，不足以证明用户没有改过文件其他部分。

返回结果区分成功、明确失败与未知效果（Unknown Effect），提供原因、可回读（Readback）证据和下一步需要的新观察结果（Observation）。大差异（Diff）可作为产物（Artifact）保存，再给模型（Model）有界摘要，需要细节时按需读取。最终验收（Acceptance）仍检查测试（Test）与允许范围，不能把单次编辑成功直接当作代码修复成功。

这四组责任可以位于同一进程，但不能互相替代。崩溃恢复（Recovery）还要保存操作身份（Operation Identity）并处理未知状态（Unknown State），不是把某个返回值改成ok就能完成。

3. 两条链：工具声明（Tool Declaration）与效果（Effect）提交

第一条链让模型（Model）知道怎样提出行动请求（Action）：声明提供选择依据，参数表达意图。第二条链通过可信执行上下文（Execution Context）、准入（Admission）和资源提交产生实际效果（Effect）。箭头从声明到模型（Model），没有把执行权限（Permission）一并交给它。

可信执行上下文（Execution Context）绑定本次工作身份（Work Identity），不能被模型（Model）提供的参数覆盖。执行器（Executor）到资源负责者（Resource Owner）的箭头才可能改变文件；参数校验和生成补丁（Patch）本身都不是编辑效果（Effect）。结果回到模型（Model）时，提供的是下一步证据，而非再次陈述原意图。

图中不变量（Invariant）是：未通过执行准入（Admission）的参数不能进入效果（Effect）操作，只有实际接受的结果才能成为后续观察结果（Observation）。其中“接受”也包括如实保存失败或未知，不等于宣布外部资源正确。持久化（Persistence）失败怎样阻止循环继续，见第52章。

4. 接口（Interface）：参数、可信上下文与结果

输入分组：意图可以填写，资格不能自报

下面的TypeScript仅定义教学接口（Interface）。EditArgs是模型（Model）依据Read结果提出的参数；ToolContext由运行时（Runtime）提供。observedVersion虽然是字符串，其含义、作用域（Scope）与有效性都由资源负责者（Resource Owner）定义，不能由模型（Model）编一个值就要求它生效。

type EditArgs = {
  // 模型（Model）表达目标与读取依据。
  path: string
  observedVersion: string
  oldText: string
  newText: string
}

type ToolContext = {
  // 可信执行身份与边界不来自模型（Model）参数。
  workspaceId: string
  callId: string
  boundary: Boundary
  signal: AbortSignal
}

例如Read已返回README的v17和唯一旧段落，模型（Model）填写oldText与newText = "Run npm test."；工作区（Workspace）、调用编号和权限边界（Permission Boundary）仍由运行时（Runtime）填入ctx。知道路径和观察版本（Observed Version）只够表达请求，不能授予写入权限（Permission）。

结果分组：失败与未知需要不同的下一步

Outcome<T>描述调用返回，Tool<A, T>连接声明与真实实现。先看成功分支有没有值，再看失败分支对效果（Effect）的陈述，最后看未知分支要求沿哪个身份（Identity）核对：


type Outcome<T> =
  | { status: "succeeded"; value: T; evidenceRef?: string }
  | { status: "failed"; code: string; message: string;
      effect: "none" | "partial_known"; retry: "reobserve" | "do_not_retry" }
  | { status: "unknown"; code: string; message: string;
      operationRef: string; retry: "reconcile_first" }

type Tool<A, T> = {
  // 声明供模型（Model）选择，实现由运行时（Runtime）调用。
  name: string
  description: string
  inputSchema: Schema<A>
  execute(args: A, ctx: ToolContext): Promise<Outcome<T>>
}

A代表参数类型，对Edit就是EditArgs；T代表成功后的值，例如新观察版本（Observed Version）与变更摘要。Promise<Outcome<T>>表示等待异步结果后再判断status。只有succeeded分支含value；可选evidenceRef定位完整证据，不表示证据内容已经进入模型输入（Model Input）。

failed是已知失败，但不保证所有工具（Tool）都没有部分效果（Effect），所以另设effect。如果到底改没改无法确认，应返回unknown，不能塞进failed且声称effect=none。取消（Cancellation）是控制请求，不能单独决定结果落在哪个分支。

Schema、Boundary仍是省略底层实现的抽象类型（Abstract Type）。类型定义不会校验真实权限（Permission）、写文件或保存证据；返回一个结构正确的对象，也不证明执行器（Executor）如实实现了合同。

严格声明：形状合法不代表获准执行

下面用JavaScript对象表示法（JavaScript Object Notation，JSON）给出完整声明。限制值是本题起点，不是所有工具（Tool）的最优配置：

{
  "name": "Edit",
  "description": "将当前工作区文件中的唯一旧片段替换为新片段。先用 Read 获取当前内容与观察版本。版本过期或目标不唯一时不写入，应重新读取并定位。编辑成功后仍需审查 diff 并验证任务。",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["path", "observedVersion", "oldText", "newText"],
    "properties": {
      "path": { "type": "string", "minLength": 1 },
      "observedVersion": { "type": "string", "minLength": 1 },
      "oldText": { "type": "string", "minLength": 1 },
      "newText": { "type": "string" }
    }
  }
}

参数结构（Schema）检查类型、必填项和基本形状，路径是否越界、目标是否唯一、观察版本（Observed Version）是否仍有效，则需要执行层检查。本题允许空newText表达删除，禁止空oldText，避免把“在哪里插入”的含义藏在空字符串匹配里；需要插入时应另定明确的位置合同。

可信配置还要规定输入字节上限、超时（Timeout）和输出预算（Output Budget），模型（Model）不能把这些限制改成无限大。工具（Tool）的只读或可并行等执行事实（Execution Facts）由可信绑定提供，不能仅相信第三方描述（Description）或注解（Annotation）。

条件提交（Conditional Commit）：检查必须覆盖真实写入时点

为理解本题的提交条件，令 PPP 表示当前请求获准，vov_ovo​ 为观察版本（Observed Version），vcv_cvc​ 为提交时当前版本（Current Version），nnn 为当前内容中旧片段的匹配数。通过基本参数校验后，至少还要满足：

P ∧ (vc=vo) ∧ (n=1).P\ \land\ (v_c=v_o)\ \land\ (n=1).P ∧ (vc​=vo​) ∧ (n=1).

三个条件回答不同问题：是否能写、是否仍基于同一内容、是否只指向一个目标。oldText在文件中仍出现一次，只能支持 n=1n=1n=1，不能推出 vc=vov_c=v_ovc​=vo​；用户可能已在别处新增一段说明。

这些条件须与写入在资源协议规定的同一次条件提交（Conditional Commit）中结合，或由覆盖相关写入者的可靠锁保护。若只在开始时检查，写入前别人仍可修改；仅本进程持有互斥锁，也不能自动约束不遵守该协议的外部写入者。资源协议还要保证应被拒绝的内容变化会改变版本（Version）；如果内容可变而标识不变，相等检查就没有提供所需保护。观察版本（Observed Version）不是普通文件路径，也不是已打开文件对象的身份（Identity）。

正常情境重新固定在v17：Read package.json给出scripts.test = "node --test"，Read README.md给出观察版本（Observed Version）v17与唯一旧段落Run npm run check.。本节结果按教学合同给定，未实际运行文件工具（Tool）。

6. 失败走读：相似文案不代表相同恢复（Recovery）路径

陈旧版本（Stale Version）：重读后保留用户的变化

另设一个并发情境，起点仍为模型（Model）刚读完v17，不是上一节编辑成功后的继续。用户先加入一段测试（Test）环境说明，当前版本（Current Version）变为v18。资源负责者（Resource Owner）在条件提交（Conditional Commit）时发现失配，返回failed/version_conflict/effect=none/retry=reobserve。

运行时（Runtime）不能删去版本（Version）条件自动重试。模型（Model）重新Read，保留用户的新段落，再基于新观察结果（Observation）提出另一调用。这里重读是为了获得改变决策所需的材料，机械提交旧参数并没有修复冲突原因。

回执（Receipt）丢失：先对账（Reconciliation），不猜没有效果（Effect）

再换一个故障点：资源负责者（Resource Owner）可能已接受编辑，回执（Receipt）通道却断开。调用者应返回unknown并保存操作引用（Operation Reference），先查询资源负责者（Resource Owner）或核对文件，不能因没有成功回包就原样写第二遍。

即使回读（Readback）发现当前内容符合目标，也只能先证明现态。没有可靠回执（Receipt）时，仍不能断言是原调用完成该写入；这并不阻止根据现态继续有权限（Permission）的验证，却阻止无依据的重复效果（Effect）。

7. 递进追问与完整参考答案

追问一：为什么不用一个Bash完成所有读、改、测？

可以，尤其现成命令行接口（Command-Line Interface，CLI）已经满足需求时。代价是目标匹配、引用、当前工作目录（Current Working Directory，cwd）、多个退出码与部分成功由脚本承担。若只输出done，模型（Model）会失去重新判断的机会。保留每步状态（State），需要诊断时返回控制权；结构化工具（Structured Tool）的价值来自清楚的语义与检查，不来自名字。

追问二：描述（Description）越详细越好吗？

不一定。先保留用途、输入含义、前提、主要效果（Effect）与关键失败行为。重复背景增加参数结构（Schema）周边说明的输入成本，相似工具（Tool）更需要具体选择差异。应以易混淆任务（Task）的选错率和实际结果判断，而非只比较文案长度。

追问三：让模型（Model）传authorized=true能简化执行吗？

不能。模型（Model）填写任务（Task）参数，授权（Authorization）来自用户与可信策略（Policy）。执行身份（Execution Identity）、权限上限（Permission Ceiling）、批准范围（Approval Scope）和取消信号（Cancellation Signal）由运行时（Runtime）注入；参数结构（Schema）合法不构成授权（Authorization）。

追问四：工具（Tool）返回成功，智能代理（Agent）就能结束吗？

不能。它只支持该操作合同完成的判断。Edit不证明函数正确，测试（Test）通过不证明没有无关修改；主任务（Task）要对照目标与验证证据完成验收（Acceptance）。还需相信并核对执行器（Executor）是否真实履行了返回值所声明的合同。

追问五：工具接口（Tool Interface）需要版本化（Versioning）吗？

名称不变但参数或结果含义变化时，需要兼容策略（Compatibility Policy）。可信注册表（Registry）可绑定版本（Version）或代际（Generation），使一次调用固定使用对应实现；不能发现时看旧说明、执行时静默换成不兼容实现。新增可选字段且旧语义保持时，才可能兼容扩展。

多步组合工具（Composite Tool）控制流（Control Flow）固定、机械处理多中间反馈（Feedback）易丢失，部分成功复杂每个失败点、取消（Cancellation）与子调用证据

完整验证输入应覆盖缺字段、越界路径、空旧片段、零/一/多处匹配、并发版本冲突（Version Conflict）、成功后的结果投影（Result Projection）、写后回执（Receipt）丢失和大输出。模型（Model）层还要看reobserve之后是否增加新观察结果（Observation）。本章给出的是验证方案与参考结论，没有把这些故障场景说成已运行。

例如，版本冲突（Version Conflict）的参考结果是本次无写入并要求重读；回执（Receipt）丢失则是unknown并先对账（Reconciliation）。两者不能共用无条件重试策略。

9. 远端测试（Test）任务（Task）：接纳、执行与通过分别记录

现在把单次Edit替换成“为当前变更创建远端测试（Test）任务（Task）”。资源负责者（Resource Owner）变为持续集成（Continuous Integration，CI）服务，教学请求固定repository、revision、testPlan与businessIntentKey。这里revision=rev18标识整个待测代码快照（Code Snapshot），与前文单文件的观察版本（Observed Version）v17/v18不同。

用户授权（Authorization）与凭据（Credential）仍由可信执行上下文（Execution Context）提供。相同业务意图键（Business Intent Key）必须绑定相同业务参数，模型（Model）不能随意换键来绕过去重（Deduplication）。

最后回到产品边界：Maka普通Edit没有本文的observedVersion参数。其旧文本匹配和文件对象身份（File Object Identity）检查，不能自动获得从先前Read到当前写入之间的内容版本（Content Version）保护。本章选择的更强条件提交（Conditional Commit），必须由资源层真正实现。
