第 50 章｜设计工具契约

本章概览

核心问题：一个工具怎样让模型表达意图，又让可信运行时控制实际效果和失败后的下一步？

关键概念：Schema（参数结构）：限定调用输入；可信上下文：注入身份、工作区与权限；观察版本：绑定编辑所依据的内容；条件提交：前提通过才写入；结构化结果：区分成功、失败与未知；操作身份：关联远端任务和重试。

关系主线：声明帮助选择，参数与当前执行边界接受检查，资源负责者提交效果并返回可用观察；单次编辑成功不等于任务完成，远端任务接纳也不等于测试通过。

前置：第16章 工具与 Agent Loop、第49章 整体架构。设计结构见 第48章。本文接口、状态和值均为教学设计，不是 Maka API。

1. 原题、约束与最小起点

让 Agent 修正 README 的测试命令。你会怎么设计它使用的 Tool？工具描述、参数、结果和失败处理如何配合？

工具粒度、并行写入者和任务验收者决定接口边界。本题假定模型负责判断修改位置，Runtime 管理执行，工具只完成一次明确的文件编辑；用户可能同时编辑文件。

最小能力集合是 Read、Edit、Bash：测试入口、修改选择与测试反馈各需要独立观察。合成一个 FixEverything 会隐藏中间判断；细拆到“取一行”“数一个字符”又会增加调用开销。工具粒度应保留必要观察，并有明确的成功条件。

一次编辑的合同是：在指定工作区，将基于指定观察版本的唯一片段替换为新文本；只有资源 owner 接受提交才报告修改成功。 版本条件是本题选用的方案，不能据此声称 Maka 的 old_string 已代表文件版本。

2. 完整参考方案

我先定义工具要完成的单次操作，以及它允许产生的效果。对 README 修复，我保留 Read、Edit 和执行测试三个操作，让模型在读到真实 scripts 之后再提出编辑，编辑以后再用测试和 diff 验证任务。

Edit 的模型声明包含名字、适用场景和严格输入 schema。参数包含工作区内路径、Read 返回的观察版本、唯一旧片段和新片段；不让模型传入“我是管理员”这样的授权字段。description 要说明何时使用、何时先 Read，以及失配后应重新定位。

Runtime 从可信上下文注入工作区、调用身份、取消信号和权限边界，校验参数和本步可用性，再把操作交给实际的文件执行者。执行者检查当前对象和版本，以原子条件提交或受可靠锁保护的检查写入完成修改。只在字符串里找到旧片段，不能证明文件没有被别人改过。

结果不能只有 ok。我会区分成功、明确失败与效果未知，并返回匹配或版本冲突的原因、可回读证据和下一步需要的新观察。成功只表示编辑合同满足，不表示代码已经修好。大 diff 可以保存为产物，再给模型有界摘要；模型需要细节时按需读取。

验证时我会覆盖唯一匹配、零匹配、多匹配、陈旧版本、并发写入、写后断线和大输出，检查是否覆盖他人改动、是否错误重试，以及模型能否根据失败改下一步。

声明、执行和任务验收分别负责调用含义、真实效果与整体结果；崩溃恢复进一步要求保存操作身份和未知状态。

3. 模型声明与真实执行的两条链

图中四条关键箭头承担不同责任：

  1. 声明 → 模型只提供“怎么提出动作”，没有把执行权限交给模型。
  2. 可信上下文 → Runtime 绑定本次执行身份，不能由模型参数覆盖。
  3. 执行者 → 资源 owner 是可能改变现实的位置，校验和描述本身不产生编辑效果。
  4. 结果 → 模型提供下一步证据，不能把调用意图或生成的 patch 当作成功结果。

图上的不变量：未通过执行准入的参数不进入效果操作；只有实际接受的结果才能成为后续模型观察。 持久化失败时如何停止循环，交给 第52章。

4. 接口：模型参数与可信执行上下文

以下 TypeScript 是教学接口，先把输入分成两组。EditArgs 是模型根据 Read 结果提出的编辑意图；ToolContext 是运行时注入的执行身份与边界。其中 observedVersion 用字符串保存资源 owner 发放的观察标识，其作用域和有效性由该 owner 定义；它不是模型可以自行编造并要求生效的版本。

type EditArgs = {
  path: string
  observedVersion: string
  oldText: string
  newText: string
}

type ToolContext = {
  workspaceId: string
  callId: string
  boundary: Boundary
  signal: AbortSignal
}

例如，Read 已返回 README.md 的 v17，正文中有一处 Run npm run check.，而 package.json 的 scripts.test 是 node --test。模型据此提出 oldText 与 newText = "Run npm test."；当前工作区、调用编号和权限边界仍由运行时填入 ctx。知道文件路径和版本，只足以表达一次修改请求，不能授予该请求写入权限。

接下来才定义执行返回什么，以及工具怎样把输入和输出接起来：


type Outcome<T> =
  | { status: "succeeded"; value: T; evidenceRef?: string }
  | { status: "failed"; code: string; message: string;
      effect: "none" | "partial_known"; retry: "reobserve" | "do_not_retry" }
  | { status: "unknown"; code: string; message: string;
      operationRef: string; retry: "reconcile_first" }

type Tool<A, T> = {
  name: string
  description: string
  inputSchema: Schema<A>
  execute(args: A, ctx: ToolContext): Promise<Outcome<T>>
}

这里的 A 代表该工具的参数类型，对 Edit 就是上面的 EditArgs；T 代表成功后的结果值，例如新观察版本与变更摘要。Promise<Outcome<T>> 表示调用要等待异步执行，完成后再判断 status。只有 succeeded 分支有 value，可选的 evidenceRef 则用于定位完整证据。Schema、Boundary 等仍是省略底层实现的抽象类型，类型声明本身不会完成权限校验、文件写入或证据保存。

failed 表示已知的失败结果，不保证所有工具都没有部分效果，因此单独写 effect。若到底改没改无法确认，就用 unknown，不能塞进 failed/no-effect。取消是一个控制请求，也不能直接决定结果属于哪一类。

模型看到的声明可以这样写；限制值是本题起点，不是通用最优值：

{
  "name": "Edit",
  "description": "将当前工作区文件中的唯一旧片段替换为新片段。先用 Read 获取当前内容与观察版本。版本过期或目标不唯一时不写入，应重新读取并定位。编辑成功后仍需审查 diff 并验证任务。",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["path", "observedVersion", "oldText", "newText"],
    "properties": {
      "path": { "type": "string", "minLength": 1 },
      "observedVersion": { "type": "string", "minLength": 1 },
      "oldText": { "type": "string", "minLength": 1 },
      "newText": { "type": "string" }
    }
  }
}

schema 检查类型、必填项和基本形状；实际路径是否越界、目标是否唯一、观察版本是否仍有效，都要在执行层检查。这里允许空 newText 表达删除，但禁止空 oldText，避免把“插入哪里”的语义藏在空字符串匹配里；需要插入时另定义明确的位置合同。

运行前还需设置输入字节上限、超时和输出预算。这些是可信配置，不能允许模型把上限改成无限大。工具的“只读”“可并行”等执行事实也由可信绑定提供，不能仅相信第三方 description 或 annotation。

5. 正常走读：一次成功编辑怎样变成下一步证据

教学输入是：Read package.json 得到 scripts.test = "node --test"；Read README.md 得到观察版本 v17，旧段落为 Run npm run check.。

表 1 / Table 1 · 5. 正常走读：一次成功编辑怎样变成下一步证据
步骤输入或状态（Input · State）检查与输出（Output）
提出编辑path=README.md，version=v17，旧片段与新片段模型只表达将入口改为 Run npm test.
运行时准入（Runtime Admission）当前工具面包含 Edit，参数结构有效注入工作区和调用身份，进入文件执行者
条件提交（Conditional Commit）owner 当前版本仍为 v17，旧片段一处owner 原子接受新内容，产生 v18
接受结果（Accepted Outcome）succeeded，v18，diff 引用给模型“README 已修改”的有界观察
后续验证（Verification）读取必要 diff；执行实际测试入口测试结果与修改范围共同支持最终说明

即使测试退出 0，也要确认 README 是否写对；即使 diff 只改一行，也不能证明测试命令可用。每个结果都有自己的证明范围。

6. 失败走读：同样一句“没改成”，下一步并不相同

假设模型拿着 v17 准备编辑，用户先加入一段测试环境说明，当前版本变成 v18。owner 在条件提交时发现版本不一致，返回 failed/version_conflict/effect=none/retry=reobserve。Runtime 不自行删除版本条件重试；模型重新 Read，保留用户的新段落，再基于新观察提出另一调用。

再换一个故障点：owner 可能已接受编辑，但回执通道断开。调用者返回 unknown，保存 operation 引用。它先查询 owner 或核对当前文件；不能因为没有收到成功结果就原样写第二遍。只读核对发现内容符合目标，只能先证明当前状态，若没有可靠回执仍不能断言是谁完成了该写入。

表 2 / Table 2 · 6. 失败走读：同样一句“没改成”，下一步并不相同
错误（Error）已知什么合理的下一步
参数结构 schema 缺少 path未形成合法执行输入修正字段，不重读文件也能解决
旧片段 oldText 匹配两处本次目标不唯一，未写入Read 更多上下文，缩小目标
版本冲突（version_conflict）观察已陈旧，本次条件提交未接受重新 Read，保留并发变化
访问拒绝（access_denied）当前边界不足判断任务是否仍可在边界内完成；确需扩权才走授权链
响应丢失（response_lost）效果无法确认查询或对账，阻止盲目重试

7. 递进追问与参考答案

追问一：为什么不用一个 Bash 完成所有读、改、测？

可以，尤其现成 CLI 已满足需求时。代价是目标匹配、引用、cwd、多个退出码和部分成功由脚本承担。若脚本把几步串起来最后只输出 done，模型会失去重新判断的机会。应保留每步状态，在需要诊断时返回控制权。结构化工具的价值来自清楚的语义和检查，不来自名字本身。

追问二：description 越详细越好吗？

不一定。先保留用途、输入语义、前提、主要副作用和最关键失败行为。重复背景会增加 schema 成本；相似工具需要具体的选择差异。用容易混淆的任务测选错率，不能仅凭文案长度判断质量。

追问三：让模型传 authorized=true 可以简化执行吗？

不可以。模型可填写任务参数，授权来自用户和可信策略。执行身份、权限上限、已批准范围与取消信号由 Runtime 注入；schema 合法也不构成授权。

追问四：工具返回 success，Agent 就能结束吗？

不能。工具成功只证明该操作合同完成。Edit 不证明函数正确，测试通过不证明没有无关修改。主任务完成由目标和对应验证证据共同判定。

追问五：工具接口需要版本化吗？

当名称不变但参数或结果语义改变时需要兼容策略。可在可信 registry 中绑定版本或 generation，让一次调用固定使用某代实现；不能搜索时看旧说明、执行时静默换成不兼容实现。只有新增可选字段且旧语义保持时，才可能兼容扩展。

8. 取舍与验证：先证明解决了什么

表 3 / Table 3 · 8. 取舍与验证：先证明解决了什么
方案适用条件代价优先验证
少量通用 Read/Edit/Bash任务类型变化较多，模型能分步判断模型需要多轮组织工作目标定位、错误反馈、任务成功率
领域工具（Domain Tool）UpdateTestCommand稳定领域有明确结构和高重复操作领域规则维护，超出领域能力不足非标准文档、正确拒绝、额外修改

测试输入应覆盖缺字段、越界路径、空旧片段、唯一/零/多匹配、并发版本冲突、成功后的结果投影、写后回执丢失。模型层另测是否会在 reobserve 后增加新观察，而非机械重试。例如版本冲突预期为本次无写入并要求重读，回执丢失预期为 unknown 并先对账；两者不能共用无条件重试。

9. 远端测试任务的完整契约

将单次 Edit 换成“为当前变更创建远端测试任务”时，资源 owner 变为 CI 服务。教学请求固定 repository、revision、testPlan 和 businessIntentKey；其中 revision=rev18 标识整个待测代码快照，与前文单个文件的观察版本 v17/v18 不同。用户授权与凭据仍由可信上下文提供。相同 key 必须绑定相同业务参数，不能由模型随意换 key 来绕过去重。

表 4 / Table 4 · 9. 远端测试任务的完整契约
阶段请求或观察（Request · Observation）参考处理
首次提交前业务 key=k7，revision=rev18，testPlan=regression先持久保存 key 与参数，再调用服务端
服务已接受返回 jobId=j9、queued保存回执；queued 只表示任务存在，不表示测试通过
提交响应丢失不知道是否已创建 j9按 k7 查询，或仅在服务端明确的幂等合同内重提相同参数
查询返回 running测试仍进行中在等待预算内查询同一 job，不创建第二份任务
查询返回 finished/failed有退出状态与失败用例作为任务观察交回 Agent，再决定修改或报告

服务端若不提供查询或幂等保证，响应丢失只能保留 unknown；调用者自造 UUID 不会补出服务端去重能力。这个结果模型也解释了为什么一个 ok: true 不足以表达“提交成功、执行完成、测试通过”三个阶段。

普通 Maka Edit 没有本文的 observedVersion 参数。该字段表达更强的条件提交设计，必须由资源层实现，不能靠给默认工具多传一个字段获得。
