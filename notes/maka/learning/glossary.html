本表解释课程中的概念、职责与适用范围。同名术语在不同项目中可能对应不同对象；Maka 专用词按本课程所分析的实现定义。

最基础的 Agent 概念

Agent（智能代理）

围绕目标，通过观察、决策、行动与反馈推进工作的系统。本课程讨论由语言模型参与决策的 Agent：模型生成文字和动作请求，运行支撑将请求接到工具与环境，并把观察用于后续判断。任务还需按目标与约束验收。

Agent 指整个工作系统；某个项目中名为 Agent 的类可能只承担控制职责。持久恢复、长期记忆、子任务和定时工作是按需求增加的能力，不是每个最小 Agent 的必备清单。

Code Agent（代码代理）

以软件任务为对象的 Agent，例如理解仓库、读取和修改代码、运行检查、解释结果。它需要面对真实文件与执行环境；生成一段代码建议和将修改执行、验证、交付是不同阶段。

Harness（运行支撑）

让模型参与实际工作的支撑机制，包括输入组织、模型与工具循环、状态与恢复、权限与隔离、任务推进与协作、观察与评价。这六组是本课程的教学划分，不是统一的组件数量；简单实现可以只提供其中的基础能力，复杂实现可能将一项责任分给多个组件。

项目规则、测试入口和服务提供工作环境的配置、材料与接口；Harness 通过相应读取、执行和控制路径使用它们。规则写在文件里不等于本次已加载，也不等于硬权限。Memory 的存取与输入选择、Skill 的方法装载与执行工具会跨越上述分组，见第01章责任图与例子。

Agent Loop（代理循环）

Agent 反复执行“组成 Context → 请求模型 → 解释输出 → 必要时调用工具 → 把结果加入下一次 Context”的控制循环。循环何时开始、何时停止以及崩溃后怎样恢复，由 Runtime 和更外层控制面决定，不由模型单独拥有。

Model / LLM（模型 / 大语言模型）

接收一组输入并生成下一段输出的推理组件。输出可能是回答文字、推理内容，或“调用某个工具并传入这些参数”的结构化请求。模型服务会把这些内容包装为自己的响应或流式事件，再交给 Agent 处理；本地文件修改由执行工具的程序完成。

一次 Model 调用 ≠ 一次完整 Agent 工作。一个 Run 中可以有多次模型请求。

Task（任务）

交给 Agent 的目标与约束，例如“只修 README 的测试命令，运行相关检查，并报告失败”。它是工作输入，不是会主动运行的部件。在 mini-SWE-agent 中，agent.run(task) 将字符串渲染进初始用户消息；其他系统可以为任务另外保存结构化状态。

任务文字本身不提供跨项目统一的持久身份。进入 Maka 后，Session、Turn 和 Run 分别标识会话、用户工作与执行。

Message（消息）

带有角色或用途的一条记录，例如 system、user、assistant、tool。mini-SWE-agent 的 messages 是线性列表，还可记录用于退出处理的 exit；不能把这个项目内部角色当成所有模型服务都接受的消息角色。普通响应和 observation 会追加进列表，退出与异常的具体路径见 第05章。

Messages ≠ 系统全部事实。生产系统还可能保存权限、准入、恢复和控制状态；模型也不一定看到全部已保存事实。

Action（行动请求）

模型输出中被 Agent 解释为“希望执行什么”的结构化内容。mini-SWE-agent v2.4.6 的默认 CLI 组合把它解析为带 command 的 Bash action；text-based 变体则从特定代码块提取命令。

Action ≠ Effect。Action 是意图；只有执行器真正运行以后，外部世界才可能改变。

Environment（执行环境）

Agent 进行观察与行动所面对的对象和运行条件，例如仓库文件、进程、测试与相关服务。项目规则说明工作约定，配置和工具接口决定怎样接触这些对象；实际访问还受权限和隔离机制约束。

在 mini-SWE-agent 源码中，同名 Environment 是执行接口：接收 action，在工作目录与环境变量下运行命令并返回结果。LocalEnvironment 直接启动本机 shell 子进程；接口可替换不代表每种实现都有相同的确认、权限或 sandbox 能力。通用环境与这个具体接口须按上下文区分。

Observation（观察结果）

执行 action 后反馈给 Agent、并用于下一次模型判断的信息，例如 stdout、return code 或 timeout 错误。它把“模型想做什么”连接到“执行后看见了什么”。

缺少 Observation ≠ 副作用没有发生。进程可能在真实 effect 已发生、结果尚未来得及记录时崩溃。

Trajectory（执行轨迹）

一条 Agent 运行中保存下来的消息、模型统计、配置和退出信息，用于复盘、调试或训练数据处理。mini-SWE-agent 的 save() 可以把完整序列化结果写成 JSON 文件。

保存轨迹不等于保存了每一步的可靠结果。例如文件已经修改，进程却在保存本轮轨迹前退出，磁盘上的轨迹就可能落后于实际文件。保存时机和恢复方式见 第06章。

Provider（模型服务提供方）

真正接收模型请求并返回结果的服务或适配目标，例如某个云模型 API。Provider 有自己的消息格式、工具协议、重试行为和原生状态；Runtime 需要通过 adapter 将内部表达转换成 provider 能理解的格式。

JSON（字段与值）

一种记录结构化数据的文本格式。对象用花括号包住字段，冒号连接字段名与值；值可以是文本、数字、另一对象或列表等。例如 {"scripts":{"test":"node --test"}} 中，scripts 的值是内层对象，test 的值是命令文本。数据能解析不等于字段已满足业务要求，也不表示文本中的命令已经执行。第01章完整读法、第03章请求转换。

npm 与 Node.js（项目工具）

Node.js 运行 JavaScript 程序；npm 可以按项目配置启动脚本等工作。本课配置将 test 脚本写为 node --test，所以工具提交 npm test 后，npm 读取 package.json 中的 scripts.test，再启动 Node.js 的测试运行模式。这些是案例项目使用的工具，不是所有 Agent 必须具备的部件；测试是否通过仍要看实际输出。配置与结果的完整关系。

Shell / Bash（命令解释器与工具名）

shell 是解释并运行文本命令的程序，Bash 是常见的一种 shell。课程中名为 bash 的模型工具接收命令参数，但工具协议名不保证执行器实际启动 /bin/bash；不同执行环境可以采用不同 shell。Maka 的 Read、Edit 等原生工具也不能全部归为 Bash 命令。第02章首例、第03章实际执行方式。

Agent Backend（执行后端）

Runtime 用来承载一次 Run 的具体执行实现。当前 Maka Host 默认注册 ai-sdk，由 AiSdkBackend/AiSdkTurn 组织模型与工具循环，见普通 Turn 主链。Backend 是执行实现，Provider 是模型服务目标；更换模型服务不一定要更换 backend。

Model Adapter（模型协议适配器）

负责把内部消息、工具声明和调用选项转换成某个模型服务接受的格式，并解释其返回值。它解决“怎样表达和传输这次请求”，不能仅凭它支持某种格式就推断整个 Agent 的权限、恢复或工具效果已经闭合。provider-native 消息也不自动代表换了一个 Agent Backend，具体边界见模型输入组成。

Provider-Executed Tool（由模型服务代执行的工具）

工具效果发生在 provider 正在处理的模型请求内部，而不是由 Maka 的普通 ToolRuntime 调用本地实现。Maka 可以保存它观察到的 call/result 时间线，但普通工具的 T1/T2 不能直接证明这条子通道的外部效果。“provider 支持原生工具”也不等于本次调用已由 provider 执行；需要运行事件明确标记 providerExecuted=true。

Prompt（提示词）

广义上指交给模型的一整组指令与输入，不只是 system prompt 的一段文字。在 Maka 中，一次请求通常还会包含当前用户输入、历史投影、Memory、workspace instructions、Skill 内容和工具 schema。

Prompt ≠ History，也不等于数据库中所有可用信息。

Context（上下文）

系统为某一次模型请求提供的输入集合。“模型看见”表示内容已进入该次输入；这不保证模型注意到或正确使用了每一项。输入受上下文窗口限制，因此完整历史、长期 Memory 和当前 Context 不能视为同一个东西。

Working Context（工作上下文）

为了当前模型请求，从事实历史、指令、Memory、Skill 和工具定义中选择、整理出来的可用输入。它是一个视图，可以在下一次 step 重新构造。

Composition Snapshot / promptComposition（组成快照 / 请求组成诊断）

这组记录帮助解释：一次 Run 的配置来自哪里，以及其中某次模型请求的输入由哪些部分组成。两者的记录范围不同。

RunCompositionSnapshot 记录一次执行选择了哪些规则、工具和组成来源；promptComposition 记录某次模型请求的组成统计，例如工具定义与消息各占多少序列化字节；ModelCallAttempt 关联这次调用的状态、使用量和成本。前者帮助查配置，后两者帮助查单次请求。组成统计不保存完整请求正文，不能凭它逐字还原模型输入，详见 第15章。

Snapshot（快照）

某次选定状态的表示。读到“快照”时，先问它记录了什么、何时采集、由谁读取，再看保存和刷新合同；这个名字本身不保证已经持久化、资源永远不变，或能够恢复整个执行。

History（历史）

过去发生过的用户输入、模型输出、工具调用、工具结果和终态等事实。History 可能很长；模型这一次看到的 Context 通常只是它的安全投影或压缩形式。

Memory（记忆）

用于跨轮次或跨会话复用信息的机制。它不是一个固定技术名称。聊天历史、Context、摘要、MEMORY.md、结构化 LTM 和 workspace instructions 各自解决不同问题，不能因为都与“过去的信息”有关就叫成同一个 Memory。

产品、运行时与身份

Client（客户端）

用户操作和观察 Agent 的产品界面，例如 Desktop、TUI 或 CLI。Client 提交意图、显示投影，也可能反向提供 Computer Use 或 MCP 能力；它不因此成为 canonical Run owner。

Runtime Host（运行时宿主）

承担长期控制责任的组件：接收请求、决定是否开始、管理连接与恢复，再把工作交给 Runtime 执行。这里的“长期”描述责任与状态的连续性，不保证同一个进程一直常驻；具体驻留和释放条件由 Runtime Host 系统维护。

State Root / Single Writer（状态根 / 单写者）

State Root 是 Host 用来组织长期控制状态的根；single writer 表示同一时刻只有获得有效 authority 或 lease 的写者可以修改它。目的不是让整个 Agent 串行，而是避免两个 Host 对同一份关键控制状态同时拍板。

Broker（能力中介）

夹在能力提供方与调用方之间，负责发现、转发、接受和结算请求的组件。例如 Client Capability broker 把 Desktop 提供的能力接给 Runtime。Broker 能协调协议，不因此自动拥有外部副作用的真实结果或 Session 的最终 authority。

State（状态）

某个对象在一个时点的情况，例如会话选择了什么配置、工具效果是否已确认、任务还剩哪些步骤。读图时要先找状态所属对象与负责更新的组件。运行状态、文件状态、记忆内容和界面显示可能不同步，不能用同一个“已完成”标签代替。见第13章与第14章。

Lifecycle（生命周期）

一个对象从创建、接纳、运行到结束和清理的过程。不同对象有不同生命周期：连接断开、任务执行结束、资源释放并不是同一事件。图中的时序或状态节点需要指明在描述哪种对象。见第25章。

Runtime（运行时）

真正运行模型—工具循环的执行系统。Maka 的 Runtime 包含 SessionManager、RuntimeKernel、AgentRun、backend、context 和 tool loop；它和负责长期接入及控制的 Runtime Host 不是同一个层次。

Session（会话）

长期存在的工作房间，保存会话身份、workspace context、配置和历史投影。一个 Session 可以经历很多 Turn 和 Run。

Session ≠ 一次执行。

Turn（轮次 / 用户可观察工作边界）

Session 中一项用户可观察的顶层工作，例如一条用户消息触发的工作。它用 turnId 标识。一个 Turn 内可以经历多个模型 step 和工具调用。

Run / AgentRun（运行 / 执行封套）

一次真正的 durable Agent 执行尝试，用 runId 标识。它拥有执行状态、组成证据和终态。普通情况下，一个 Run 里会多次调用模型并穿插工具执行。

Run ≠ 一次 Provider 请求。

Root Execution（顶层执行）

直接占用一个 Session 顶层工作位置的执行，例如用户 Turn、Goal continuation 或 Schedule 唤醒后进入的 Run。它与 child Session 内的执行相对；Host 会对同一 Session 的 root admission 做冲突控制。

Model Step（模型步骤）

Agent loop 中的一轮模型判断。模型可能在一个 step 返回工具调用，在得到工具结果后进入下一个 step，最终某个 step 返回面向用户的答案。

Tool Call（工具调用）

模型提出的结构化行动请求，例如 Read(package.json)。它只是意图；在通过 availability、schema、权限与执行边界检查之前，不代表工具已经执行。

invocationId（执行事实关联坐标）

将一次执行的 opening、事件、工具 operation 与 terminal 关联起来。RuntimeInvocationRecord 从这些事件重建，不再依赖 mutable live Run header。普通 Run 的 invocationId 可默认等于 runId；它有明确的事实数据结构，但不引入另一套独立调度器。

决策权、准入与并发控制

负责者（Owner）

对某类状态（State）和业务决定负最终责任的组件。例如负责目标（Goal）的协调组件决定是否继续推进；存储（Store）可以保存记录，却不会自行决定下一轮应不应该开始。课程统一用“负责者（Owner）”强调职责归属；其他材料也会译为“所有者”，此处不表示文件所有权或用户账号。

Authority（裁决权 / 权威边界）

“谁有资格拍板”的规则或主体。它强调决策权，而不只是“谁执行了一段代码”。Owner 常拥有某类 authority，但两个词关注点不同：owner 偏责任归属，authority 偏有效裁决权。

Admission（准入）

工作真正开始前的受控入口。系统检查身份、冲突、权限和当前状态，并先留下足够的 durable 事实，再允许执行继续。Client 提交请求不等于准入已经完成。

Claim（认领）

某个 worker 或 coordinator 用持久状态声明“这项工作由我处理”的动作。它用于避免两个执行者同时处理同一工作，但具体保证取决于 claim 的存储、过期和恢复协议。

Lease（租约）

带有有效期或持有条件的临时所有权。租约可以避免永久锁死，但系统必须定义过期、续租、接管和旧持有者迟到写入的处理方式。

CAS（Compare-And-Swap / 比较后写入）

写入时原子地检查“当前值或版本，是否仍等于我读取时的预期”。例如 A、B 都读到版本 7：A 以“仍为 7”为条件提交并推进到 8；B 再以版本 7 提交就应被拒绝。B 需要重读并处理冲突，而不是照原内容盲写。检查与写入必须处在同一个不可被其他写者插入的操作中，先查一次再普通写入不具备这项保证。

事实、事件和展示

Fact（事实）

系统已经接受并能够据此做出后续判断的记录，例如某个 Run 已被准入、某个工具结果已经结算、某个 terminal 已经写入。日志文本不一定都是业务事实。

Canonical Fact（规范事实 / 权威事实）

当不同界面、缓存或重试产生冲突时，系统指定用来裁决的事实。例如 UI 显示“完成”不能覆盖 canonical terminal fact。

Event（事件）

描述“发生了什么”的结构化记录。事件可以是临时流式事件，也可以被接受并持久化为 durable 事实；必须看具体类型和写入边界，不能只凭名字判断。

RuntimeEvent（Maka 运行时语义事件）

Maka 用于记录用户、模型、工具和 terminal 等执行语义的 canonical ledger 条目。它是 execution/model replay 的重要事实源，但不是整个产品唯一账本；admission、approval、Goal 等有各自的 durable owner。

Partial / Streaming Event（未完成的流式片段）

模型响应尚在生成时到达的一段增量，例如“已”随后扩展成“已更新 README”。它适合实时展示，但不能把每个增量都当成一条完整回答重复放进下一次模型 Context。

Visibility / Origin（可见性 / 来源）

事件元数据：visibility 约束它是否进入某类消费者的投影，origin 记录它来自用户、模型、工具、Host 或其他通道。它们帮助构造 UI 与模型 history，但具体安全保证仍取决于保存和投影规则。

Ledger（账本）

按规则记录事实的持久结构。账本强调“哪些记录可以用来证明什么”。Maka 使用多个专用 ledger，而不是把所有业务状态都塞进一张万能事件表。

Durable（持久、崩溃后仍可读）

数据在进程崩溃或重启后仍能从持久存储中恢复。写入内存、发出 UI stream 或打印日志通常不能单独称为 durable。

Projection / Read Model（投影 / 读取视图）

从一组事实计算出的面向特定消费者的视图，例如 UI transcript 或下一次模型的 history。Projection 可以重建、过滤或压缩，因此它不必等于 canonical facts 的原始形态。

Projection Transition / Effective Fold（投影变换 / 有效折叠）

Projection transition 是一条持久规则，说明某段 canonical 内容在后续模型视图中应怎样被摘要、裁剪或替换成归档引用，而不删除原始事实。Effective fold 是按顺序应用这些变换，得到模型此刻真正使用的 effective history。Compaction、预算和 replay 必须读取同一折叠结果，才能避免已裁剪的大结果被重新“复活”。

Head Anchor（当前工作起点）

在本课程的 compaction 场景中，用来定位当前用户工作起点的锚。它帮助划定哪些旧历史可以覆盖，哪些当前任务内容必须保留；不是把最新一句话随意指定为切点。见 第19章 的 H1–H5 推演。

Request Shaping（请求整形）

在发送模型请求前，根据当前有效历史、保护边界和预算等规则选择或调整本次输入表示，例如用合规 checkpoint 替换旧前缀。它不等于改写原始事件，也不保证整个请求一定装得下。首步整形指本 Turn 第一次调用前的这项准备；真实 overflow 是 provider 拒绝后的另一条处理路径。见 第19章。

Terminal State / Terminal Fact（终态 / 终态事实）

说明一次 Run 已经 completed、failed 或 cancelled 的最终执行状态。Maka 要求终态由 durable ledger 证明，而不是由 Client loading 状态或连接关闭来猜测。执行结束后，仍需按任务目标核对交付结果。

Settled（资源结算完毕）

表示 iterator、临时资源或后台清理也已经结束。它可能晚于用户已经能够看到的 terminal completion，所以 terminal ≠ settled。

Tool、权限与副作用

Tool（工具）

Agent 与外部世界交互的受控能力，例如读文件、改文件、运行命令、访问网络或操作 GUI。模型生成 tool call，Runtime/adapter/executor 才可能实施行动。

Tool Surface（工具表面）

某一轮向模型提供的“工具目录”：包含工具名称、用途和参数格式。它决定本次请求声明了哪些能力，不直接决定某次调用是否获得权限。

Schema（结构与字段约束）

用来描述数据应有哪些字段、字段类型和限制的规则。例如工具要求 path 是字符串，传入数字就不符合 schema。通过结构检查只说明参数形状合法；文件是否存在、是否允许访问、修改是否符合任务，还要继续判断。

Binding（工具绑定）

把工具名称和 schema 连接到真实实现的关系。系统知道一个工具名字，不代表当前 Session 已绑定实现；绑定了实现，也不代表本 step 一定向模型展示。

Availability（当前可见 / 可调用性）

在冻结的模型 step 中，某个已绑定工具是否出现在 active schema 中。Deferred tool 可以先被搜索、再在下一 step 激活。Availability 解决 Context 和能力暴露问题，不等于授权。

Permission（权限）

某个主体在给定条件下获准执行的操作及其范围。Permissions 是复数形式，例如一组文件读取、写入和网络访问权限。权限表达“允许做什么”；Prompt 中写“请只读”不能单独证明实际访问已经受限，执行时还需可信的边界检查与隔离机制。

Permission Policy（权限策略）

用于判断操作是否允许、拒绝或需要批准，以及允许扩张到何种范围的规则。Policy（策略）强调判断依据，Permission（权限）强调在给定条件下被允许的操作范围。策略文本与当前生效权限不是同一份事实，还要核对规则由谁解释、当前授权状态和具体执行边界。

Confirmation（确认）

向人展示明确事项、询问是否继续并接收决定的交互。第05章的 mini 确认模式让用户决定一组候选动作是否继续；它不会自动建立沙箱。确认被什么授权流程接纳，决定它对执行的影响；填写任务参数也不能自动视为批准新增权限。

Approval（批准）

由有权主体针对明确请求作出的同意决定。它可以确认已有授权，也可通过可信流程改变允许范围；不必每次工具调用都重新发生。Approval 不等于动作已执行，不等于 OS 已阻止越界，也不代替 Authority（裁决权）对决定资格的要求。

Authorization（授权）

依据身份、策略和当前状态，判断某次操作是否被允许的过程及其结果。它可以依据已有授权完成，不一定每次都询问用户；需要明确同意时，Approval 是其中的一次批准决定，Authority 则说明谁有权作出有效决定。工具可见性（Tool Visibility）只描述模型能看到哪些工具与请求格式，不能证明本次授权已经通过。

Isolation（隔离）

通过运行边界限制状态共享和资源访问，使一个执行单元不能任意读写另一个单元或宿主的资源。隔离要说明具体对象：上下文隔离、文件工作区隔离、进程隔离和网络隔离各有范围；分出子会话并不自动隔离文件。Sandbox（沙箱）是落实某些执行资源限制的机制。图中的“权限与隔离 Permissions & Isolation”同时关心是否允许行动，以及执行层怎样约束它。见第17章与第23章。

ExecutionBoundary（执行边界）

Maka 为当前 Session 保存的文件、网络和宿主能力访问边界，并用修订号区分边界的不同状态。工具接近实际执行时读取当前边界，避免继续使用模型提出调用时的旧权限。超界请求只有符合申请条件时才进入显式批准流程；被提出并不意味着一定可以扩权。

Sandbox（沙箱）

在操作系统或执行器层实际限制进程能访问什么的机制。Permission（权限）表示允许范围，Permission Policy（权限策略）提供判定规则，Sandbox 通过具体后端落实资源访问限制。能否强制阻止越界，要看该后端与配置的真实能力，不能从一条策略声明或批准记录直接推导。

Side Effect（外部副作用）

会改变模型自身之外世界的操作，例如写文件、发送消息、启动进程或提交网络请求。副作用可能已经发生，但对应结果尚未来得及持久化，这是恢复系统最困难的窗口之一。

T1 / T2（工具副作用前后标记）

在已接入持久化边界的普通 Runtime 工具路径中，T1 是调用工具实现前的持久记录，T2 是结果的持久结算。T2 可以记下成功，也可以记下失败；它不是“任务成功”的同义词。两者帮助划分恢复窗口，不自动提供 exactly-once，也不能套用到所有 provider、远端或 Client 执行路径。具体前提见 第18章。

Settlement（结算）

把执行结果变成 durable 事实的过程。真实操作返回成功和 T2 成功写入之间仍可能存在 crash window，因此“工具实现返回了”与“结果已结算”不是同一时刻。

失败与恢复

Recovery（恢复）

系统重启后，根据 durable facts 判断哪些工作已完成、哪些肯定没开始、哪些结果不确定，以及哪些控制状态需要继续协调。Recovery 不是简单地把所有 running 项重跑一次。

Reconcile（对账 / 收敛）

把多个事实源或外部系统的当前状态重新比对，收敛出可证明结论。例如向外部服务查询一个请求是否已成功，从而解决本地记录缺失的问题。

Indeterminate / Outcome Unknown（结果不确定）

系统有证据表明操作可能开始，但没有足够证据证明成功或失败。正确处理通常是保留现场、人工确认或外部 reconcile，而不是默认重做。

Parked（暂停等待裁决）

系统主动不再自动推进某项结果不确定的工作，把它停在可检查状态，等待 reconcile、人工处理或更强证据。

Fail Closed（无法证明安全时停止）

当权限、身份或副作用状态不能被可靠证明时，系统选择拒绝或暂停。它优先保护正确性和安全性，代价是有时需要用户介入。

Fail Open（依赖判断失败时仍继续）

某个检查、评估或优化步骤失败时，系统选择一条默认的“继续”路径，而不是停止。这个词只描述行为，本身不代表该选择安全。例如新摘要生成失败后保留原始 Context，通常是保守降级。

当前 Goal evaluator 在 timeout、调用错误或不可解析时返回 evaluatorFailed: true 的中性结果：尚未形成关于目标是否达成的可靠判断，也不把本次评估当作取得进展或停滞的证据。是否继续仍由当前目标、状态、预算和准入条件决定，见第24章 的继续条件。这仍可能浪费预算或掩盖判断失败。权限、安全边界或未知副作用不能仅因为产品希望继续就随意 fail open。

Liveness Guard / Circuit（活性保护 / 熔断）

防止系统对同一失败输入无限重复工作的有界机制。它可以用稳定 fingerprint 识别“相同来源、相同配置、相同失败”，达到阈值后暂时停止该自动路径或保留原始表示。它保护系统最终能退出循环，不代表原问题已经解决。

Poison / Drain（标记权威不再安全 / 排空）

当一次关键写入的结果变得不确定时，poison 表示当前 writer authority 不能再安全接受新决定；drain 表示停止接纳新工作，并让已有工作结算或转入恢复。它们是在证据不足时保护单写者状态，不是“清空数据”或“忽略错误”。

Idempotency（幂等性）

在约定范围内，同一操作重复执行与执行一次产生相同的目标效果。例如把字段设为 5，重复设置后仍为 5；把字段加 1，重复执行则继续增加。外部服务也可以用固定请求 key 识别重复，但保证取决于 key 的作用域、保存期限以及去重记录与实际操作怎样一起提交。只给请求加一个 key，不会自动获得幂等性。

Exactly Once（恰好执行一次）

强到要求操作既不丢失也不重复。跨本地账本和外部世界通常很难实现。Maka 的 T1/T2 提供可审计的失败分类，但不能因此笼统宣称所有工具 exactly-once。

长 Context 与 Memory

Context Window（上下文窗口）

模型一次调用可处理的上下文容量，通常以 token 计量。若接口让输入与输出共享总窗口，就要先为输出留出空间；有独立输入或输出限制时，也须同时满足。不能把标称总窗口全部分给历史消息。参见 第36章 的预算算例。

Token（模型处理的序列单位）

模型使用的分词器把文本编码成 token 序列。一个 token 不固定等于一个汉字、单词或字符；相同文字在不同分词器下的数量也可能不同。课程中人为给定的 token 数用于手算预算，真实请求应按对应模型与接口的计量方式估算。

Compaction（上下文压缩）

尝试把一段旧的模型可见历史整理成更紧凑的表示，为后续请求腾出空间。摘要是否真的更短、整次请求是否装得下，还要分别检查。Maka 的 compaction 改变模型输入投影，不应改写原始 RuntimeEvents。

Checkpoint（检查点）

在本课程的压缩场景中，Checkpoint 把摘要与它所覆盖的历史范围、来源等信息一起保存，供后续请求恢复较短的上下文。应用前还要验证它是否对应当前历史；“检查点已经写入”不保证摘要保留了每一条重要约束，也不是所有文件、工具或进程的完整快照。见 第19章。

Archive / Offload（归档 / 外置）

把过大的内容保留在 Context 之外，并用有界引用让 Agent 在需要时读取。它减少当前 Prompt 体积，但不等于自动召回，也不一定和 Memory 共用同一存储。

MEMORY.md（透明文件记忆）

用户可以看到、编辑和控制的长期信息文件。Maka 的 Agent 读取开关启用后，还要检查内容能否解析、条目是否有效且适用当前范围，再把选中的内容加入模型输入。文件存在或开关开启，都不能单独说明本次已读到某条偏好。

Atomic LTM（原子长期记忆）

Maka 把符合来源要求的结构化记忆写入独立 memory.sqlite 的机制。“原子”关注一次存储提交内的记录是否一起成立，不代表后续检索和使用都会成功。当前已有提取、持久化和存储查询接口，但尚未把这套查询接到 Agent 的自动召回和输入组装，见 第20章。

Workspace Instructions（工作区指令）

项目为 Agent 提供的规则与背景，例如 AGENTS.md。它们通过相应 Host 的发现、读取和组成路径进入输入，实际范围与加载时点取决于实现和配置。它们属于显式指令，不是通过对话自动学习出的 Memory；规则文字也不代替执行层权限。

Recall（召回）

按当前问题，从已保存的信息中找出候选。在搜索推荐中，召回通常强调先找出候选集合，再交给过滤、排序等后续步骤；Agent Memory 也需要区分这些阶段。

例如查询返回“项目 A 使用英文”，但当前任务属于项目 B，这条候选就可能被过滤；即使保留下来，还要加入本次输入，才可能影响模型。存得下、召回到、装入输入、正确使用是四个不同的判断。

Skill、子代理与继续工作

Trigger（触发条件）

允许某个控制域创建或推进下一项工作的事实，例如用户批准 Plan，或时钟到点并取得 Schedule claim。Graph 依赖满足时首先得到的是可重算的 Readiness，还要经过 claim / admission 才能触发执行。Trigger 只证明“现在可以尝试下一步”，通常不证明后续 AgentRun 已经成功。

Evaluator（完成评估器）

根据目标、当前结果和证据判断“是否已经满足 Goal”的组件。它提供判断材料，但 timeout、解析失败和含糊输出怎样处理取决于控制策略；不能把 evaluator 的一句自然语言直接当成无条件终态。

Orchestration（编排）

根据步骤、依赖、资源和当前状态安排工作由谁推进、何时开始以及结果怎样交回。它协调执行单元，本身不能代替工具的实际执行或任务验收。“任务推进与协作”这组教学职责包含此类安排，也涉及触发、委派和采纳。见第24章与第39章。

Coordination State（协同状态）

记录多个执行单元如何协作的状态，例如谁依赖谁、什么已经就绪、下一步由谁推进。官方设计文章用“协同状态在 Graph 中，还是分散在 Mailbox 对话中”来比较两种多 Agent 路径；这是一种架构观察角度，不是新的 Run 状态，也不能替代 AgentRun / RuntimeEvent 的执行事实。

DAG / Edge（有向无环图 / 边）

DAG 用节点和有方向、无环的边表示先后依赖：后继节点等待必要输入就绪，没有依赖关系的节点从这个角度具备并发条件。实际并发还要检查共享资源、权限和预算；两节点即使没有依赖边，同时写同一文件仍可能冲突。在 Agent Graph 中，节点可承载 Operator，Edge 表达依赖或记录路由；Edge 本身不复制完整上游内容、不授予跨 Session 权限，也不执行模型。

Topology（图结构）

Agent Graph 中有哪些节点、节点之间有哪些依赖边，以及结果应流向哪里。Topology 描述工作结构，不执行模型—工具循环。

Readiness（就绪性）

Agent Graph 根据当前 topology、输入记录与策略反复推导出的“前置条件是否满足”视图。它应当可以无副作用地重算；同一意图再次显示为 ready，不代表可以再启动一次。真正把它绑定到具体 Session / Turn / Run，要继续经过 Claim 与 Admission。

Quiescence（静止点）

图中当前没有可运行节点、没有在途 child，并且没有待处理唤醒的状态。它有助于判断 Graph 是否需要结束或等待，但“没有活动”不自动等于“所有业务目标都成功”。

Skill（技能说明包）

为 Agent 提供特定工作方法、知识、脚本或资源的可复用内容。Skill 主要增强输入和工作流程；它不会因为被加载就自动扩大 ExecutionBoundary 或创建一项新 Run。

Subagent / Linked Child Session（子代理 / 关联子会话）

由父任务委托、具有独立 Session 和 Run 的执行单元。它有 lineage 和受限能力，不是把同一个 Prompt 函数递归调用一下，也不应默认继承父会话全部历史和权限。

Operator（算子）

把 Subagent 当作一项边界封闭、可按依赖调度的工作单元时使用的角色名称。Maka Agent Graph 以 linked child Session 作为稳定的 Operator 容器，以普通 child AgentRun 作为一次 activation；它接收显式 instruction 与已提交输入的有界交接，不因此获得修改全局 Schedule Revision 的 authority。

Participant（协作参与者）

把 Agent 当作可寻址、可持续收发消息并动态磋商的协作者时使用的设计角色。它常与 Mailbox 配套，工作流随对话交织演进。Participant 是官方文章用于对照 Operator 的概念，不是 Maka 当前源码中的另一种 Session 类型，也不能把所有 Subagent 都自动归入这一类。

Mailbox（私有信箱）

面向某个可寻址 Agent 的异步入站消息队列；在某些 Mailbox 设计中，消息可以只排队，也可以附带“唤醒一个新轮次”的调度意图。队列内容、唤醒信号、会话历史是否持久必须分别核对。Inter-agent Mailbox 是 Agent 之间的协同原语，不是 Client 与 Runtime Host 之间用于重连、snapshot 和 subscription 的网络连接。

Plan（计划）

由用户查看、批准和推进的 durable workflow。Plan 管理步骤和用户控制状态，不等于自主循环，也不拥有另一套通用 Agent Runtime。

Goal（目标）

能够根据 evaluator 判断“尚未完成”而触发下一轮工作的 continuation domain。Goal 拥有自己的 durable control state，真正执行时仍进入普通 Hosted AgentRun。

ScheduledTask / Schedule（定时任务）

由 durable clock 和 fire claim 在指定时间触发的工作。到点只是取得触发资格，不等于 Agent 工作已经完成。

Schedule Revision（调度修订）

Root supervisor 对 Agent Graph 追加的一次 durable control decision，例如增加 work、停止或替换旧分支、选择结果并 finish。Revision 按顺序持久化且不就地改写过去；提交它只改变调度意图，仍要由 Reconcile 重建视图，并经过 Readiness、Claim 与 Admission 才能启动普通 Run。

Agent Graph（代理图）

持久化 Schedule Revision、Topology、依赖、claim 和 supervisor wake 的控制平面。它组织谁何时执行，不重新实现模型—工具循环，也不是 Agent 之间的共享 Mailbox。

Continuation（继续执行）

让未来的新工作在某个业务条件满足时开始。Plan resume、Goal continuation、Schedule fire、Graph wake 和 Client reconnect 都可能被口头称为“继续”，但 owner、状态和语义完全不同。

实现状态与机制

Production Path（当前生产主路径）

产品默认或真实接线正在使用的执行路径。存在类型、Store 或测试基础，不足以证明一项机制已进入 production path。

Foundation（实现基础）

已经有 contract、数据结构、Store、adapter 或测试入口，但缺少产品主路径 consumer 或完整闭环的能力。它比“只有想法”更强，但不能宣传成用户已经得到的完整能力。

Experimental（实验性）

实现存在，但接口、行为、部署或安全保证尚不稳定，通常需要显式开启或不能承担 production 承诺。

Compatibility / Legacy（兼容路径 / 历史路径）

为了读取旧数据、旧协议或旧调用方式而保留的路径。它不一定代表当前新建数据或默认执行方式。

Source Fact（源码事实）

通过阅读实际调用链、状态变化，以及相关测试的设置与断言得到的实现判断。只找到类名或测试文件还不足以支持行为结论；读懂代码也不等于它已在自己的环境运行成功。

Design Intent（设计意图）

官方架构文档、注释或 proposal 描述的目标。它可以帮助寻找实现，但不能单独证明当前 production 接线已经兑现目标。

Mechanism（机制）

一项能力实际怎样由 owner、状态、调用链、持久化边界和失败处理共同实现。比较 Agent 时应比较 mechanism，而不是只比较名称或 UI 功能入口。

Contract / Invariant（行为约定 / 不变量）

Contract 说明输入满足什么条件时，组件应产生什么输出或失败；例如 Edit 要求旧文本匹配，否则返回冲突。Invariant 是整个过程中始终需要成立的约束，例如未获允许的文件不能因重试而变得可写。接口类型只表达其中一部分，执行过程也必须遵守这些规则。

产生者（Producer）与消费者（Consumer）

产生者（Producer）创建某份数据，消费者（Consumer）读取它并据此行动。例如记忆（Memory）提取器产生候选，输入组装器选择材料作为背景。只有实际用于后续输入或行动，材料才进入影响工作结果的链条。课程统一用“消费者（Consumer）”；旧材料中的“使用者”在这里表示同一角色，不能把保存位置或持有者自动当成实际消费者（Consumer）。

Fixture（测试用的受控设置）

为一个测试准备的输入、对象和环境，例如临时数据库、指定事件序列或预写模型响应。Fixture 可以替代部分组件，同时调用真实存储或运行时；阅读测试时要分清哪些是真的执行，哪些由测试预先设定。第04章 的预写模型响应与真实命令执行就是这样的组合。

方法比较常用词

主动读取与检索

检索按当前问题从候选库选择内容；主动读取强调 Agent 依据已有线索决定下一步去哪里读、读哪部分。二者可以组合；“内容在存储中”不表示本次已进入模型 Context。

Consolidation（记忆整理）

把新经验和已有记忆合并、修订、建立联系或淘汰。整理可能降低重复与冲突，也可能把误判传播到长期状态，因此需要来源、作用域与更新/删除规则。它不等于无损保存全部历史。

Opaque State（不可直接解释的状态）

provider 返回供后续调用使用、通常不能直接读懂的结构或加密内容。能被相应 provider 消费不等于可跨 provider 迁移、可人工审计或保证不丢语义。

SOTA 与代表方法

SOTA 是给定任务、指标、预算、日期和可比基线下的最好已知结果。代表方法说明一种机制怎样实现；前沿论文说明一个新假设或报告结果。两者都不能自动成为“SOTA”，更不能由知名 Host 名称推出。
