第二部分：Maka 核心机制与任务接续 · 26 / 62

第 26 章｜任务评价（Task Evaluation）与综合设计（Integrated Design）

本章概览

核心问题：一次修复通过，究竟能支持多强的可靠性、成本与架构结论？

关键概念：试次（Trial）是规定初态和预算下的一整项任务；判定器（Grader）按正确性标准（Oracle）检查结果；至少一项通过率（pass@k）关注多个候选（Candidate）中是否存在正确项；设计分析卡（Design Analysis Card）连接主张、实现条件与反例。

关系主线：先固定成功条件和统计单位，再保留失败、未知与全部成本；最后沿实际读写及效果边界（Effect Boundary），解释设计为何能支持这些结果。

前情回顾：停止、通过与被使用是三件事

第05章说明，代理循环（Agent Loop）停止只表明执行（Run）结束；任务是否完成还须检查产物。第16章说明，工具结果（Tool Result）只支持实际观察到的范围：退出码（Exit Code）为 0，不独自证明目标测试运行，更不证明任务全部完成。

第20章又把保存与消费分开：本地记忆笔记（Local Memory）写入后，还要经过读取与请求组成；条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）有持久化及查询基础，也不能据此宣称默认模型请求已自动召回。状态存在、输入包含、输出遵循，需要不同的观察。

本章把这些区别接在一起：先判断一次修复，再比较多次尝试，最后解释是哪条机制支持了结果，以及哪一个条件变化会让结论失效。

1. 先说明怎样才算修好，再计算成功率

正确性标准（Oracle）与判定器（Grader）各做什么

本章切回第04章的原始缺陷分支：formatDuration 余秒计算用了 % 100，README 测试入口也不正确。任务要求修复一般计算、修正文档入口，并保留测试与无关文件。这与第12、25章“函数已正确，只修文档”的条件不同。

正确性标准（Oracle）给出什么算对，例如分钟与余秒的计算规则、允许修改的文件范围；判定器（Grader）负责执行检查并给出判断，可以是程序，也可以是按规则复核的人。两者不应混成“运行一个脚本就算完成”。

例如，某个补丁只对四个已知输入做特判，四项断言（Assertion）全部通过，但 61 秒仍算错。判定器（Grader）的覆盖不足，不会使该补丁满足一般计算要求。反过来，判定器（Grader）本身也可能出错；处理冲突应回到任务要求并保留修正理由，不能为提高分数降低正确性标准（Oracle）。

2. 试次（Trial）、重试（Retry）与后续推进（Continuation）怎样计数

一次试次（Trial）是从规定初始状态出发，在同一预算和权限下完成的一整项修复。它可以包含许多模型调用（Model Query）和工具调用（Tool Call），不是一次网络请求，也不是一条断言（Assertion）。

把同样的补集计数推广到固定池：共有 nnn 个候选（Candidate），其中 ccc 个正确，均匀不放回地取 kkk 个，且 1≤k≤n1\le k\le n1≤k≤n。全部组合数为 (nk)\binom nk(kn​)，全失败组合数为 (n−ck)\binom{n-c}k(kn−c​)，因此：

pass@k^=1−(n−ck)(nk).\widehat{\mathrm{pass@k}}=1-\frac{\binom{n-c}{k}}{\binom nk}.pass@k​=1−(kn​)(kn−c​)​.

固定池的组合概率与未来模型的成功概率仍要分开。 在给定池上，5/65/65/6 是上述选取事件的精确概率；把它作为至少一项通过率（pass@k）的样本估计，则还需要候选（Candidate）的生成符合相应抽样条件。原论文在独立同分布（Independent and Identically Distributed，IID）的二项计数设定下证明该估计无偏（Unbiased），并说明直接将经验通过比例代入 1−(1−p^)k1-(1-\widehat p)^k1−(1−p​)k 会产生偏差。原论文 §2.1 与附录 A

这也不能代替选择器（Selector）：候选池里有正确答案，而交付规则选中 2，任务仍失败。读取前次失败反馈的后续推进（Continuation）改变了条件，不能直接套成互不影响的新候选（Candidate）。评价专题进一步讨论不同估计对象。

基础设施重试（Infrastructure Retry）与未知结果都要留下

假设试次（Trial）3 开始前还有一次环境启动失败，耗时 10 秒，没有模型调用（Model Query）。按预定规则，它记为基础设施重试（Infrastructure Retry）；恢复后才发生表中的第 3 次，所以业务通过比例仍为 2/42/42/4，不是 2/52/52/5。

但那次故障不能从部署可靠性和成本记录中消失。如果最后仍无法执行，应保留无有效判定的数量与原因，分别报告任务判定统计和端到端可用性（End-to-end Availability）。不能悄悄删题，也不能把未知评分（Unknown Score）直接填成 0，伪装成已取得的任务判定。

如果把失败反馈再交给第 3 次的智能代理（Agent），让它继续修到通过，评价对象就增加了后续推进（Continuation）策略。不能擦掉原失败、直接宣布原预算下变成 3/43/43/4。应事先规定触发条件、次数与额外预算，对所有符合条件的试次（Trial）一致执行，保留原结果、继续过程、最终结果和总成本。

完整成本（Total Cost）不能只统计生成

四次生成合计 22,000 词元（Token），模型与工具累计 110 秒。再假设验证与选择另耗 2,000 词元（Token）和 8 秒，人工复核另需 60 秒，加上前述 10 秒环境故障：

Ctokens=6000+4000+5000+7000+2000=24000,Tsystem=30+20+25+35+10+8=128 s,Tdelivery=128+60=188 s.\begin{aligned} C_{\mathrm{tokens}} &= 6000+4000+5000+7000+2000=24000,\\ T_{\mathrm{system}} &= 30+20+25+35+10+8=128\ \mathrm{s},\\ T_{\mathrm{delivery}} &= 128+60=188\ \mathrm{s}. \end{aligned}Ctokens​Tsystem​Tdelivery​​=6000+4000+5000+7000+2000=24000,=30+20+25+35+10+8=128 s,=128+60=188 s.​

CtokensC_{\mathrm{tokens}}Ctokens​ 是已列全部模型开销的词元（Token）数；TsystemT_{\mathrm{system}}Tsystem​ 是假设系统步骤全部串行、没有其他开销的用时；TdeliveryT_{\mathrm{delivery}}Tdelivery​ 再计入顺序人工复核。真实并行系统的墙钟时间（Wall-clock Time）应根据实际起止时间记录，不能用各项时长之和替代；词元（Token）也不等于货币账单。

在这一假设方案中已经生成四个候选（Candidate），计算至少一项通过率（pass@2）不会把实际开销变成只生成两个。一个指标描述哪种成功事件，和获得该数据到底花了多少资源，是两个问题。

评价泄漏（Evaluation Leakage）：检查材料何时参与了设计

保留未参与调优的检查，才能反驳只迎合已知样例的修复。例如根据分钟/余秒契约选择新输入，而不是先把“61 秒的答案”告诉被测策略，随后仍称未见评价。

如果先读保留答案，据此调整提示词（Prompt）或规则，再用同一批题报告收益，就发生评价泄漏（Evaluation Leakage）：评价材料参与了方案选择。开发时读取公开测试是正常工作；已经用于开发的材料不能继续冒充独立检验。新的评价还需核对任务分布与判定质量，并非换一批题就自动消除所有偏差。

问题 1。 四次中两次通过，有一次启动故障，又把一个失败继续修好了，业务统计可以写成 3/53/53/5 吗？

参考答案。 不能混算。原试次（Trial）结果仍是 2/42/42/4；启动故障另报基础设施重试（Infrastructure Retry）；后续成功属于新加入的后续推进（Continuation）策略，要连同反馈和新增预算评价。

问题 2。 只报告 22,000 词元（Token）与 5/65/65/6，漏掉了什么？

参考答案。 开销漏了验证与选择的 2,000 词元（Token）、10 秒环境故障及人工时间；已知合计是 24,000 词元（Token）、128 秒系统串行时间、额外 60 秒人工。5/65/65/6 只说明候选集合中至少一项通过，不说明选择器（Selector）交付正确，也不代表所有任务的稳定成功率。

第40章继续处理交付时限、未知评分（Unknown Score）与成本；评价专题中的运行对象解释实验（Experiment）、单元（Cell）与尝试（Attempt）的产品含义，名称不必与通用统计单位一一相同。

问题 1。 新项目的 README 写 npm test，配置却声明 check: node --test，应保留原课程命令吗？

参考答案。 按新配置，候选入口是 npm run check。只有它返回测试名称与断言（Assertion）结果，才能从入口错误推进到行为判断。换了构建系统还需重新定位。此处是新条件推演，没有新增运行。

问题 2。 新任务约定空列表返回 0，旧函数对 [] 抛错，但非空样例全过，什么检查能区分两者？

参考答案。 输入 []、期望 0，依据来自任务契约（Contract）。不能为让测试变绿发明期望；未执行该检查时，只能给出推导，不能说已经验证。

问题 3。 看到 Done 后断线，持久结果却缺失，是否可以自动重做？

参考答案。 Done 是已观察到的文本。文件写入需读取当前目标并关联原操作身份（Operation Identity）；只有 T1、没有结果时仍可能产生了效果（Effect）。不能由记录缺口推断未执行。有幂等键（Idempotency Key）或明确对账（Reconciliation）协议，才可能支持更强的重试（Retry）。

这三类判断分别使用既有观察、源码推导和新条件假设。读取一份执行轨迹（Trajectory）可以解释其行为，不会变成读者自己运行过的记录；旧测试通过也只描述旧文件状态。

6. “崩溃以后不会重复修改”需要哪条效果（Effect）合同？

表中的位置是假设能够观察完整时序时给出的故障点；重启后的本地记录通常不能精确区分 T1 后、效果（Effect）前，与效果（Effect）后、T2 前。

表 9 / Table 9 · 先固定工具路径，再讨论恰好一次（Exactly-once）
崩溃位置本地记录能支持什么怎样约束下一步
工具调用（Tool Call）形成后、T1 前在此受控路径尚未越过持久派发标记（Durable Dispatch Marker）按解析器契约（Resolver Contract）重新决策，不能推广到绕过该路径的执行器（Executor）

T2 后结果已持久结算（Durable Settlement）读取原结果，不应重复原效果（Effect）

若能凭稳定操作身份（Operation Identity）向资源方对账（Reconciliation），或操作自身满足幂等性（Idempotency），恢复策略可能更强。但必须找到具体工具配置（Tool Profile）和实际消费者（Consumer）。存在托管修改契约（Managed Mutation Contract）的类型，不等于当前生产主路径（Production Path）的 Write/Edit 已采用它。

普通运行时（Runtime）适配的客户端能力（Client Capability）和远端模型上下文协议（Model Context Protocol，MCP）工具，可以共享工具运行时（ToolRuntime）外层 T1/T2；它们不能继承本机文件执行器（Executor）的对象检查、恢复能力或沙箱（Sandbox）保证。由模型服务代执行的工具（Provider-executed Tool）则不经过这条普通路径。相同工具调用（Tool Call）外观不说明相同效果边界（Effect Boundary）。

问题。 把本地 Edit 换成远端模型上下文协议（MCP）工具，T1/T2 还成立吗？

机制解释可以逐步加深：先找到负责者（Owner），再闭合输入到结果的正常路径（Normal Path），然后加入并发、取消、超时、部分成功、恢复（Recovery）和权限约束，最后用能区分两种解释的实验检验。比如目标协调器（Goal Coordinator）决定是否继续，运行时（Runtime）推进已准入工作；计划（Plan）批准后经负责者（Owner）形成意图再准入，仅解释了正常开始，还没有解释并发批准会不会重复启动。

8. 采用一个新设计时，怎样同时比较收益与代价？

假设把完整测试日志改成摘要（Summary）加原文引用。原日志关键事实是 exit=1，125 秒期望 2:05、实际 2:25。如果摘要（Summary）保留这三项和可回读位置，模型仍能定位余秒问题；若只剩“测试失败”，诊断依据就变弱。

比较应在相同任务与预算下计入定位正确率、约束保留、回读成本和最终测试结果。摘要（Summary）变短本身不是成功条件。本例给出采用标准与反例，没有运行新的压缩方案。

同样，采用更完整的恢复（Recovery）记录，可以改善对未知结果的表达，但也增加身份（Identity）、存储和结算成本；能否值得采用，要看它是否解决目标场景中的实际故障。第47章把这些合同连接起来：运行时事件（Runtime Event）记录事实，顶层准入（Root Admission）控制新执行（Run），交互（Interaction）与业务领域（Domain）各有等待和继续状态；一次执行（Run）的终态（Terminal State）不自动结束目标（Goal）。

任务评价（Task Evaluation）也需要被下一份工作消费。例如函数已修好而 README 未改，结束记录应保留“函数检查通过、文档尚未完成”；下一次先核对当前要求与文件，再选择剩余工作。若用户已改函数，旧测试通过只描述旧状态。第27章接着展示跨会话（Session）的任务推进与工作交接（Handoff）。
