第 26 章｜任务评价与综合设计

本章概览

核心问题：一次修复通过，究竟能支持哪些可靠性、成本与架构结论？

关键概念：试次：规定初态和预算下的一整项任务；判定器：按规则检查产物；pass@k：多个候选中至少一个通过的指标；未知评分：未取得有效判定；设计分析卡：连接主张、实现条件与反例的说明。

关系主线：先固定任务和统计单位，再对照实际输入、状态及结果；将失败和全部成本保留，并用具体接线与失效条件限定设计结论。

前置：第11–20章中的循环、工具、上下文与记忆机制。

核心路线

先用第 04 章的代码、测试与轨迹说明一次修复的判定，再把机制、替代设计和失败条件组织成完整的设计分析卡。第 47 章进一步连接跨模块状态与授权。

评价最小模型

程序退出和任务验收并不相同；一次修好又与反复委托时的可靠性不同。后者需要在相同条件下观察多次完整任务。

先把任务成功写成可检查的条件。仍用 第04章：正确修复 formatDuration 的一般计算、修正 README 测试入口、保留测试和无关文件。判定器（grader）是执行检查并给出判断的程序或人；oracle 是判定所依据的正确结果或规则。它们只能支持自己覆盖的结论。四个断言全过而 61 秒仍错误，说明判定覆盖不足；不能把这种补丁算作已经满足一般契约。

试次、重试与候选的统计单位

本节约定一次试次是从规定初始状态出发，在同一预算和权限下完成的一整项修复，可以包含多次模型调用和工具执行。它不是一次 API 请求，也不是一条测试断言。

表 1 / Table 1 · 试次、重试与候选的统计单位
发生了什么统计时怎样处理
从干净副本重新开始，不读取上次补丁、轨迹或经验一个新的重复试次（repetition）；用来观察同条件下的结果变化
环境启动失败，Agent 尚未得到机会执行；按事先约定重新启动基础设施重试（retry），单独记录原因和成本；不是多获得一次成功样本的机会
在原工作状态中继续，读到失败反馈后再改补丁continuation，属于带历史的继续策略；不能当作一个全新、独立的候选
为同一任务生成多个候选，再选择一个交付多候选策略；既要评价候选中是否有正确项，也要评价选择器能否选中它

重开进程本身不能决定属于哪一类：要看是否继承状态、为何重开，以及实验事先如何定义试次。本课 第04章 的固定响应脚本会重复预写动作，反复播放它不能估计真实模型的随机成功率。

同一任务的四个假设试次

下表的补丁结果、token 和时间都是教学假设，不是本课或某产品的运行记录。假设四次都从同一干净副本开始，使用相同模型条件、权限和每次预算，不向后续试次传递前一次经验。判定在候选生成后按事先固定的任务条件进行。这里用四次帮助理解分母，不把小样本当成稳定结论。

同一任务的单试次通过比例为 2 / 4 = 50%，分母是四个完整业务试次。它不等于四项断言的通过比例，也不能推出其他 bug、仓库或任务分布上的 50%。要评价更广泛的工作，应另选代表性任务，分别报告每题的重复结果、失败与预算，再说明怎样汇总。

再问“有两个候选时，至少一个正确”这个问题。从这四个已生成候选中等概率、不放回地取两个，共六对：(1,2)、(1,3)、(1,4)、(2,3)、(2,4)、(3,4)。只有 (2,3) 两个都失败，因此至少一个通过的比例是 5 / 6 ≈ 83.3%。若要求两个都正确，则只有 (1,4)，比例是 1 / 6 ≈ 16.7%。候选更多时也可以反着数：先数全部对子，再减去两个都失败的对子，剩下的就是至少一个通过的对子；组合数公式留到评价专题再展开。

这就是本例有限样本 pass@2 估计的手算：pass@k 关注 k 个候选里至少一个通过。它不表示 k 次都能成功，也不表示生产中一定能选到正确候选。如果交付规则选中候选 2，任务仍失败；检查器把特判误当正确时，报告的高分也会失真。将有限样本估计推广为模型的成功概率，还需匹配采样假设；带前次反馈的自修复不能直接套作独立候选。详细估计与假设见评价专题 §8。

失败、继续与成本不能从表里消失

假设试次 3 在开始前还发生过一次环境启动失败，耗时 10 秒，没有模型调用。按本例预先约定，该事件记为基础设施重试；恢复后才执行表中的试次 3，所以仍是四个业务试次、两个通过。启动故障应另报，不能从部署可靠性和成本记录中消失。若最后仍未能执行，应保留“无有效结果”的数量与原因，分别说明任务判定统计和端到端可用性，不能悄悄删掉这一题或把未知分数填成 0。

如果又把失败反馈交给试次 3 的 Agent，让它继续修到通过，评价对象就加入了继续策略。不能把原表的失败擦掉后宣布原预算下的比例提高；应事先规定哪些失败允许继续、增加多少预算，并将完整继续过程计入比较。只挑一个失败样本补救，与对所有任务实施相同继续政策，回答的是不同问题。

本表四次生成共 22,000 token、累计执行 110 秒。再假设验证与选择另耗 2,000 token 和 8 秒，人工复核另需 60 秒，环境重试是前述 10 秒。则已列模型成本合计 24,000 token；若所有步骤串行且无其他开销，系统用时 110 + 10 + 8 = 128 秒，加人工后顺序交付用时为 188 秒。真实并行系统应另记起止时间，不能把各任务时长之和叫墙钟时间；token 也不等于货币账单。算 pass@2 时，不能把这次研究实际生成四个候选的成本改记成只生成两个。

最后保留一条没有看过的检查来反驳投机修复。例如从分钟/余秒契约设计新输入，而不是把“61 秒的答案”直接告诉待比较策略后仍称独立检验。若先查看保留的测试答案、据此调提示或修改规则，再用同一批题报告收益，就产生了评价泄漏：评价材料参与了方案选择。开发过程中读取可见测试是正常工作，但已用来调方案的材料不能继续冒充未见评估。判定器和题目也可能有错；发现冲突须回到任务要求，记录修正理由，不能为了高分降低标准。

改变约束后，分母还一样吗

问题 1。 四次中两次成功，第 3 次开始前环境重试过一次。业务通过比例是 2/4 还是 2/5？还必须报告什么？

解释。 按本例约定是 2/4；启动重试不是新业务试次。仍要报告那次环境故障和 10 秒成本；若重试未成功，还应保留无法判定的结果并报告可用性，不能选择性隐藏失败。

问题 2。 从四个候选取两个，为什么“至少一个通过”与“两个都通过”分别是 5/6 和 1/6？为何 5/6 不能保证选出的补丁正确？

解释。 六对里只有 (2,3) 没有正确项；只有 (1,4) 两项都正确。至少一个正确描述候选集合，真实交付还依赖选择器和判定标准；选到 2 仍失败。

问题 3。 第 3 次看到失败反馈后继续成功，能直接把原表改成 3/4 吗？怎样设计一个可比较的继续策略？

解释。 不能。继续过程改变了可见反馈、预算和策略。先固定允许继续的触发条件、次数与预算，对所有符合条件的试次一致执行，保存原结果、继续轨迹、最终结果和总成本，再与同条件基线比较。

问题 4。 把保留测试的答案用于调提示后，再用同一题报告进步，缺了什么独立性？只报告 22,000 token 又漏了哪些已知成本？

解释。 这批测试已经参与开发，不能证明未见任务上的收益；需要未用于选择方案的评估材料，并核其任务分布与判定质量。22,000 漏了验证/选择的 2,000 token，还未表达环境重试、系统时长和人工复核；本例已知合计为 24,000 token、128 秒系统串行时间及额外 60 秒人工。

第40章 的整项工作评价继续处理未知分数、交付时限和成本；评价专题说明 Maka 的 Experiment/Cell/Attempt 怎样对应具体运行。产品对象名与这里的通用统计单位不必一一同名。

一次完整修复的五项判断

第 04 章的固定案例可以从五个角度解释。同一份结果只能支持与其观察范围相符的结论。

问题 1。 入口错误、函数错误和修复完成分别由什么结果支持？

解释。 最初 npm run check 报缺少脚本，测试尚未启动；实际入口 npm test 得到 2 pass/2 fail。将 % 100 改为 % 60、README 改为 npm test 后得到 4 pass/0 fail，diff 仅涉及两份目标文件，测试未变。三个判断依赖三个阶段的结果。

问题 2。 为什么固定轨迹有 8 次 query、7 条普通 tool observation？

解释。 前七次动作分别产生普通执行结果，凭 tool call ID 与 observation 配对。最后一次完成动作触发 Submitted，由 run 写入 exit；它没有生成普通 tool observation。8/7 是这份固定轨迹的计数，不是 Agent 的通用规则。

问题 3。 同一修复在 Maka 中怎样对应 S1/T7/R7 与多步工具调用？

解释。 S1 是长期会话，T7 是本次用户工作，R7 是承载它的一次 backend execution。R7 可多次调用模型：Read 返回配置与代码，后续模型据此提出 Edit；本例的成功编辑报告支持修改已经发生，Bash 的测试输出才支持行为判断，diff 则支持范围判断。下一次调用是否获得新事实取决于实际观察，重复读取不一定增加信息。工具可见也不表示已经获准或执行。

问题 4。 “下一任务也用中文”比本轮中文回答多出哪些步骤？

解释。 当前请求可直接约束本轮回答。未来复用还需明确写入、保存、按适用范围读取、进入新请求并实际被模型采用。Local Memory 需要相应读写开关；Atomic 写入和查询基础不能补出当前尚未接线的自动 recall。保存成功、输入包含、输出遵循分别需要不同观察。

问题 5。 这份案例支持什么成功结论，仍不能证明什么？

解释。 它支持给定 fixture 的四个断言实际通过且测试未改。固定响应没有独立诊断未知 bug，四例也不证明全部输入、所有 provider、操作系统或恢复行为都正确。一般计算的源码推理可以补充测试覆盖，却不能冒充额外执行。

换一个项目，哪些判断仍成立

取余基数与命令名属于原项目；定位入口、形成可区分的观察、核对结果的方法可以用于新场景。以下都是改变条件后的参考推演，没有新增运行结果。

问题 1。 新仓库没有 npm test，README 的命令也失败，下一步怎样定位入口？

解释。 假设配置实际声明 check: node --test，README 却写 npm test，读取配置就会得到候选入口 npm run check。只有该入口返回测试名称和断言结果，才能把故障从命令选择推进到被测行为。若配置与测试目录指向另一套构建工具，结论还会改变，不能硬套原案例的 npm 命令。

问题 2。 新函数只在空输入时失败，现有测试全过，怎样区分样例通过与问题修复？

解释。 假设任务约定空列表返回 0，旧实现却抛错，则输入 []、期望 0 是能区分两者的检查；现有非空样例全过没有覆盖它。这个期望来自任务合同，不能仅为测试变绿而发明。未执行该检查时，只能给出复现与修复推导，不能报告已验证。

问题 3。 命令显示 Done，随后连接断开且没有持久结果，下一步能直接重做吗？

解释。 不能。Done 是已观察到的文本；持久结果与外部效果仍需分别核对。若是文件写入，可读取当前目标并关联原操作身份；若只发现 T1 而无结果，不能由记录缺口推断未执行。无法确认时保留 unknown，具有幂等键或明确对账协议的资源才可能支持更强的安全重试。

三个真实片段的结果解释

第22章中的三个实际片段进一步说明结果的含义。

问题 1。 为什么 mini 检查错误脚本时外层返回 0？

解释。 管道末端是 head，之后又执行 echo。外层 0 不能证明前面的 npm 命令成功；输出正文实际写着脚本不存在。

问题 2。 为什么 Maka 两个 Edit 成功后仍要测试？

解释。 Edit 报告修改，测试检查程序行为。即使替换了目标文本，也可能改错公式或影响正常输入；这两类结果不能互相代替。

问题 3。 为什么只修 README 的案例保留红色测试？

解释。 该次任务只授权修文档。模型准确报告源码仍失败，并保持源码、配置和测试不变；擅自修源码会越过这次任务范围。

“会记住”与“不会重复”的实际条件

贯穿案例结束后，产品介绍可能出现两句话：

A. Maka 会记住用户以后希望使用中文解释。

B. Maka 崩溃恢复后不会重复执行 README 修改。

这两句话都不能只凭 Demo 判断。

对 A，我们要区分：

这张教学链把每一步需要确认的事实分开。箭头表示要继续核验的消费关系，不代表前一项一成立，后一项就自动成立。

任何一个箭头缺失，“会记住”都可能只是部分成立。

对 B，我们要区分：

先看正常链，再看写入后、结果保存前的崩溃分支。恢复必须解释原记录与外部效果，不是无条件再做一次。

如果在 effect 后、T2 前崩溃，本地只知道结果不确定。除非操作自身幂等或能向外部状态 reconcile，否则不能笼统承诺 exactly-once。

四种实现状态

Production path

Production path 指产品默认或真实入口确实会经过的接线路径。判断它不能只看文件名，要从 Client/Host admission 或实际 composer 一路跟到 consumer。

示例：普通 Runtime-executed tool 在 production Host 注入 durable sink 的前提下，会经过 T1/T2。结论必须同时保留“普通 lane”和“已注入 sink”两个限定。

Foundation

Foundation 表示 contract、类型、Store、adapter 或测试基础已经存在，但产品主路径尚未消费，或闭环还缺一段。

示例：Atomic LTM 有写入和 Store 查询 API，不等于当前 Agent 已有 production recall/prompt injection。

Experimental

Experimental 表示代码可以存在甚至能够试用，但协议、部署、安全或兼容承诺尚不稳定。

示例：官方将 direct-peer transport 标为 experimental；源码中有网络接口，仍不等于它已经在各种 WAN、NAT 或 relay 环境下可靠运行。

Compatibility

Compatibility 路径用于读取旧数据或维持历史调用方式。看到它不能反推新建数据仍采用旧模型。

示例：StoredMessage 的 UI/import 兼容读取或 legacy slug-only schedule row 说明系统需要处理历史数据；前者不是当前 provider-history fallback，后者不代表新建 Schedule 的执行方式。

架构文档有设计意图当前源码和 production wiring
Demo 成功一条正常路径可运行并发、失败、崩溃、恢复和安全边界

从代码位置到可检验的机制解释

目录定位、调用链解释、失败推演和运行检验支持不同强度的结论。每一步都要补足前一步尚未回答的问题。

能找到职责与决定者

找到 packages/runtime/src 只完成定位。接着应能说清：系统解决什么问题，谁有权作决定，谁只负责转换、保存或展示。

例如，Goal coordinator 决定是否继续；Runtime 执行已获准的 Run。仅找到这两个组件，还不能宣布它们在崩溃后一定恢复正确。

能顺着输入走到结果

沿真实调用追踪输入、关键类型、状态变化和输出，解释每一跳为什么需要下一跳。

例如，用户批准 Plan 后，Plan owner 形成执行意图，经 Host 准入进入普通 AgentRun。这能解释正常工作如何开始；仍未回答并发批准或重启会不会重复启动。

能解释异常与边界

在正常链上逐项加入约束：

  • 哪份状态具有最终决定权，哪些只是缓存或投影；
  • 哪次写入先于外部效果，哪次写入确认结果；
  • 并发请求怎样认领、冲突或失效；
  • 取消、超时、部分成功与重启后怎样处理；
  • 权限、隐私和信任边界是否仍成立。

代表测试的设置与断言决定它能反驳哪一种解释。测试名称或文件存在不能代替这一关系；阅读测试也不等于运行了它。

能用实验检验解释

最小实验通过改变一个条件来区分两种解释。例如第 06 章在写入后终止进程，直接分开“文件未改”与“文件已改、记录未跟上”；若只观察退出码，两种解释都可能成立。命令、环境、文件字节与失败时点共同限定实验结论。

正常测试通过只支持它覆盖的场景。一次重连实验不能替所有平台证明恢复；一个内存数据库测试也不能独自证明跨进程持久性。理解机制与运行验证相互补充，任何一项都不能省略另一项的前提。

一条主张怎样拆成可核验问题

架构主张可以拆成八个相互关联的问题。下表继续用“普通 Edit 丢失结果后能否自动重做”给出对应解释：

表 6 / Table 6 · 一条主张怎样拆成可核验问题
分析维度（Analysis dimension）Edit 丢失结果的对应解释
问题避免把已发生的修改误当未执行，再做一次

八个问题把主张拆成可定位、可推演、可反驳的部分。

示例一：检验“Agent 会记住中文偏好”

第一步：澄清用户语义

用户真正需要的不是数据库里多一行，而是未来相关任务中模型能够看见并遵循偏好。

第二步：列出可能机制

  • 当前 Session history；
  • compaction summary；
  • MEMORY.md；
  • Atomic LTM；
  • workspace instructions。

它们都可能包含“中文”两个字，但语义和生命周期不同。

第三步：找 owner 和读写闭环

两种实现分别把保存与消费接在哪里：

问题MEMORY.mdAtomic LTM
谁写入用户经原生管理接口修改 bundle受用户证据与准入规则约束的提取链，提交到 Store
存在哪里文件 bundlememory.sqlite
是否可读取是Store/facade 有 read/key query
是否进入 Agent Prompt读取开关启用时可以当前没有 production recall/injection
用户能否直观看见可以需要产品查询面

第四步：形成限定结论

由这些条件得到的结论是：

当前可进入 Prompt 的长期记忆路径是用户启用读取的 MEMORY.md。Atomic LTM 已有结构化写入和 Store 查询基础，但不能仅凭这些宣称下一轮 Agent 会自动召回中文偏好。

示例二：检验“Edit 崩溃后不会重复”

第一步：先限定执行 lane

先区分谁真正产生效果。普通 Runtime 适配的 Client Capability 和远端 MCP 可以共享 ToolRuntime 外层的 T1/T2，但不能继承文件执行器的对象检查、恢复能力或本机 sandbox 保证；provider-executed tool 则在模型服务内部执行，不经过普通 ToolRuntime。比较必须落到所选执行路径，不能把“都有 tool call”当成同一种效果边界。

第二步：比较崩溃位置

表 8 / Table 8 · 第二步：比较崩溃位置
崩溃位置本地通常能证明什么自动重做是否安全
Tool call 后、T1 前实现尚未越过 durable dispatch marker通常可重新决策，但仍按 resolver contract
T1 后、effect 前实现可能开始不能只凭本地事实确认
effect 后、T2 前外部修改可能成功，结果未结算默认不安全
T2 后结果已 durable settlement不应重复 effect

第三步：检查外部 reconcile 或幂等性

如果 Edit 能根据预期内容读取文件并判断是否已应用，恢复策略可能更强；但这需要明确 profile/consumer 和实际接线。类型里存在 managed mutation contract，不等于 production Write/Edit 已使用它。

第四步：形成限定结论

由这些条件得到的结论是：

普通 production ToolRuntime 用 T1/T2 标出可能执行与结果结算边界；T1 后缺少 T2 时结果可能不确定，因此不能笼统承诺 exactly-once。更强恢复取决于工具 profile、幂等性或外部 reconcile 是否真实接线。

按问题和 owner 读源码，不按目录横扫

按目录顺序阅读可能形成这样的路线：

从 packages/core 第一行开始
→ 顺序读完整个 runtime
→ 再读 storage
→ 最后打开 Desktop

这种方法很容易记住类名，却看不见跨 package 的业务主链。更有效的方法是先提出一个问题：

为什么 UI 不能自行宣布 R7 完成？

然后按 owner 向内追：

Client turn.start
→ Host root admission
→ SessionManager.sendMessage
→ RuntimeKernel.startTurn
→ AgentRun accepts RuntimeEvents
→ terminal durable barrier
→ Host canonical publication
→ Client projection

同一请求中，每一跳的职责可以这样区分：

转发参数与拥有决定权不同。能拒绝、claim、commit 或形成合法 terminal 的组件，才可能拥有相应边界的控制权；一个组件有写入能力也不表示它拥有整项任务的全部 authority。

用设计分析卡组织一个可检查的解释

下面是一张已经填好的分析卡，问题是“关闭 Local Memory 读取后，新请求还会得到原偏好吗”。它把真实实现条件与尚未观察的部分放在同一解释里。

问题与主张：读取关闭不会删除偏好，但新 Turn 不应取得 Local Memory 正文。
适用条件：普通主 Session 的 Local 路径；新 Turn 尚未捕获输入。
谁决定，谁执行：Memory policy 决定能否读；coordinator 取正文；composer 组装。
持久状态与视图：bundle 保存条目；prompt 是一次输入表示，不是另一份权威存储。
输入变化：条目仍在 → read 门关闭 → 不生成 Local 正文 → 普通请求仍可组成。
正常场景：第 21 章关闭读取后 prompt 无 Local 块，文件 digest 不变。
反例边界：同一 Turn 已捕获的正文不会因开关变化自动撤回；已发请求也不能撤回。
权限与隐私：scope 和读取许可共同约束消费；workspace scope 不自动按 cwd 隔离项目。
替代设计：真正按项目隔离需独立 root，或另设计明确的项目 key 与读取选择器。
采用代价：更多隔离与选择规则也增加配置、冲突和迁移成本。
已有观察：存储和 composer 对照；另有第 22 章的新 Session 真实模型案例。
尚未证明：所有未来任务都遵循偏好，或 Atomic 已自动 recall。
可推翻点：在以上限定条件成立时，新 Turn 仍收到被关闭的 Local 正文。

这张卡同时说明“为何相信”和“何时失效”。字段中的新项目选择器是设计方案，不是当前实现；不同案例的观察不能拼成一次未曾运行的完整 trace。

负向结论尤其要小心。没有搜索到 caller，只能先写“在当前检索范围内未发现”；若要写“明确不支持”或“尚未实现”，还需要核对 contract、feature flag、compatibility path 和实际 composition。

常见误区

误区一：README 写了，所以 production 已实现

README 或架构文档证明设计意图，不能替代真实 producer/consumer 接线。

误区二：测试文件存在，所以行为已经验证

先读设置与断言，才能知道测试覆盖什么；实际执行并取得结果，才能讨论该场景是否通过。即使运行通过，也不能把一个局部测试扩成全系统保证。

误区三：公共流程正确，所以每个 provider 都正确

不同 adapter 的消息转换、重试、凭据、原生工具、checkpoint 与 usage 处理可能不同。公共流程的结论需要结合这些差异逐一判断。

误区四：同名机制可以跨项目直接比较

两个项目都叫 Session、Memory 或 Tool，不代表 owner、状态和恢复语义相同。比较应对齐问题和失败窗口。

误区五：版本标签能代替实际运行条件

配置文件中的版本号不一定代表正式发布，也不能说明本次启用了哪条 adapter 或实验功能。判断行为时，应确认实际入口、配置和环境，不能只看产品名字或版本标签。

问题。 把本地 Edit 改成远端 MCP，哪些结论仍成立，哪些需要重新限定？

解释。 只要仍是普通 ToolRuntime 且 durable sink 已接入，T1/T2 仍能标识本地准入与结果结算；远端资源的实际效果却不能继承本机文件对象检查或 Seatbelt 保证。缺结果后能否重试，取决于远端是否提供稳定 operation identity、幂等执行或可确认效果的查询。没有这些合同，结果仍可为 unknown；外层记录更完整不等于远端操作可安全重做。

问题。 把完整测试日志改为摘要加原文引用，怎样判断是否值得采用？

解释。 假设原日志的关键事实是 exit=1、125 秒期望 2:05 而实际 2:25。摘要保留这三项并给可回读位置，模型仍能定位余秒问题；若只剩“测试失败”，定位依据就变弱。比较应在相同任务与预算下计入定位正确率、约束保留、回读成本和最终测试结果。摘要短却遗漏决定性失败行，不能仅凭长度判优。这里是采用标准与反例的推导，没有运行新的摘要方案。

第47章进一步连接这些合同：RuntimeEvent 记录执行事实，root admission 控制执行准入，Interaction 与业务 domain 分别拥有等待和继续状态；Run terminal 不自动结束 Goal。

比较对象由问题决定。源码支持选定链的行为，官方说明支持其公开设计合同，论文支持其设定下的算法与报告；只有公开设计时，内部 owner、存储和时序仍应保留未知。设计建议也不能代替当前实际接线。

从本次判定进入下一次工作

任务判定也要被后续工作读取。例如函数已修好但 README 未改，结束记录应保留“函数检查通过、文档尚未完成”，下一次先核对当前要求与文件，再选择文档工作。若用户已修改函数，旧测试通过只描述旧状态，不能直接沿用为当前通过。第 27 章｜跨会话任务推进与工作交接给出完整交接记录、读取逻辑与两次工作的参考结果。
