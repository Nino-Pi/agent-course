第二部分：Maka 核心机制与任务接续 · 18 / 62

第 18 章｜持久效果（Durable Effect）与故障恢复（Recovery）

本章概览

核心问题：工具（Tool）效果可能已经发生却没有成功回执时，恢复（Recovery）系统怎样避免盲目重做？

关键概念：副作用（Side Effect）改变外部世界；持久（Durable）表示提交后仍可读取；T1 标记准备执行；T2 保存结果结算；对账（Reconciliation）核对记录与资源状态（State）。

关系主线：已接入持久存储（Durable Storage）的普通工具（Tool）路径在效果前后分别提交记录。缺少 T2 时需回查，T2 也可能明确记录效果未知；安全重试（Retry）还取决于工具（Tool）的幂等（Idempotent）与对账（Reconciliation）合同。

前情回顾：允许执行之后，还要知道结果保存在哪里

第17章区分权限（Permission）、批准（Approval）与沙箱（Sandbox）的强制执行（Enforcement）。一个合法操作真的开始后，还会遇到另一个问题：文件已经改变，负责记录结果的程序却可能崩溃。第12章已经提醒，文件效果、持久记录和客户端（Client）展示是三个状态（State）；本章进一步解释它们暂时不一致时怎样判断。

继续沿用会话（Session）S1、工作轮次（Turn）T7、执行（Run）R7，只把README的错误测试（Test）入口改成 npm test。函数是否正确与这次文件写入是否发生，是两件事；本章的崩溃位置和操作编号属于教学设定，引用第06、35章时才使用其明确范围内的历史结果。

本章把操作对运行时（Runtime）之外资源的改变称为副作用（Side Effect），把提交后重启仍可按合同读取称为持久（Durable）。负责者（Owner）接受相应记录，恢复分类器（Resolver）读取账本（Ledger），模型（Model）则消费后续实际输入。关键不是多保存几句说明，而是明确每份记录能排除哪些情况。

核心阅读

问题：README 已经改了，但系统还没来得及说“成功”

仍以 README 的测试（Test）命令从 npm run check 改为 npm test 为例。下面的 patch 表示这项修改，editFile 与 saveToolResult 是教学接口，分别表示改文件和保存结果，不是 Maka 的实际应用程序接口（Application Programming Interface，API）。两行异步代码之间就可能出现这个窗口：

const result = await editFile("README.md", patch)
await saveToolResult({ ok: true, result })

给定故障位置是 editFile已经返回、README已经改变，而进程在调用 saveToolResult之前崩溃。恢复（Recovery）程序重启后只读得到持久记录，看不到已丢失的内存返回值。

这段两行代码只说明先改文件、再保存结果，省略了函数定义与失败处理，不能独立运行。两次 await分别等待各自操作；它们不会把两个操作变成同一个事务（Transaction）。

故事已经告诉我们效果发生在崩溃前；恢复（Recovery）程序却读不到这份旁白，只看到数据库中没有成功结果。单凭这份记录，它不能区分两种执行过程：A，编辑根本没开始；B，编辑已经完成，只是结果没保存。 A 中第一次执行可能仍有必要，B 中同样的调用却可能造成重复效果；账本（Ledger）相同，安全的下一动作未必相同。

若恢复（Recovery）看到“没有结果”就自动重做：

  • 对精确替换，第二次可能报“旧文本不存在”；
  • 对追加写入，内容可能重复两次；
  • 对发邮件，用户可能收到两封；
  • 对扣费应用程序接口（API），费用可能发生两次；
  • 对创建问题记录（Issue），远端可能出现两个副本。

这就是 副作用（Side Effect） 的核心：操作改变了运行时（Runtime）之外的世界，而且改变未必能自动撤销。

“函数返回”不是持久（Durable）事实

程序内存里的 result 只在当前进程活着时存在。要称为 持久（Durable），它必须先写入重启后可读取的存储，并满足相应的提交规则。

因此以下时刻不同：

需要跨进程恢复（Recovery）的智能代理（Agent），必须说明这些时刻中自己实际保证了哪几个，不能只用一个模糊的“done”代替。

“没有成功记录”不等于“没有执行”

记录缺失只说明当前记录没有证明结果已提交，不能推出真实效果没有发生。恢复（Recovery）时要把两个问题分开：账本（Ledger）保存了什么，以及文件或外部服务实际变成了什么。

恢复（Recovery）要先确定安全的继续条件，避免为了补一条结果记录而制造第二次不可逆效果。

同一份记录，为什么对应不同现实

把两种可能历史记为 hAh_AhA​ 与 hBh_BhB​，把重启后可读取的记录记为 L(h)L(h)L(h)。用 E(h)E(h)E(h)表示这次操作是否已产生所讨论的外部效果，0表示没有，1表示有。上面的给定窗口可能满足：

L(hA)=L(hB),E(hA)=0,E(hB)=1.L(h_A)=L(h_B), \qquad E(h_A)=0, \qquad E(h_B)=1.L(hA​)=L(hB​),E(hA​)=0,E(hB​)=1.

这些符号是教学模型，不是产品字段，也没有给两种历史分配概率。等式说明，仅以 LLL 为输入的恢复（Recovery）程序无法区分两种现实。要缩小未知范围，必须增加可回读的边界证据，或查询真实资源；把“没有结果”改写成“失败”，并没有添加信息。

下面的T1/T2协议增加的是记录所能区分的情况。它仍不保证每个可能窗口都能自动恢复（Recovery），也不会把未知变成成功。

一种具体做法：在副作用（Side Effect）前后各留下一个持久边界

为缩小重启后的不确定范围，Maka 在已接入持久存储（Durable Storage）的普通工具（Tool）路径中采用“先记准备，再做操作，再记结果”的协议。图中实线表示正常提交顺序，虚线表示故障窗口。一条待查分支尚未确认 T2，另一条已有 T2 却记录了效果未知；两者都不能直接要求工具（Tool）再执行一次。

没有 T2 不等于没有效果；有错误结果T2 也可能只是保存了“效果未知”。 崩溃或没收到提交回执时，还不能先断定“只有 T1”：T2 可能已保存，应先回查，再按结果内容判断；不能确认时继续保留未知。图中的“核对记录与现实”是恢复（Recovery）处理方向，不表示当前每个工具（Tool）都有自动查询或自动对账（Reconciliation）实现。只有取得可用证据、当前授权（Authorization）和继续条件后，才能决定后续动作；停止或重启不会撤销已经写入的字节。更详细的普通 Edit 分叉见同一次 Edit 的推演。

这里的 T1/T2 是一次工具调用（Tool Call）的两次提交边界，不是会话（Session）中“第 1/2 个工作轮次（Turn）”的编号。沿用案例的 T7 仍指用户的那一轮工作；其中每次普通工具调用（Tool Call）各自跨过自己的 T1/T2：

  • T1：从这里起，工具（Tool）实现可能已经开始；
  • T2：运行时（Runtime）已经持久接受了这次调用的结果；这个结果可以是成功、业务错误，或明确记录“效果未知”。

T1 不是“效果一定成功”；T2 不是“业务一定成功”，也不保证外部世界的 恰好一次（Exactly Once）（效果恰好发生一次）。它们让重启后的系统区分“结果尚未可靠结算”与“已有可读取的结算结果（Outcome）”，再根据结果内容作决定。

为什么 T1 必须在效果之前

如果先调用工具（Tool），再写 T1，崩溃可能留下一个已经发生却完全没有分派（Dispatch）痕迹的效果。恢复（Recovery）会把它误判成“肯定没有执行”。

如果把准备记录放在效果之后，顺序就成了“效果发生 → 崩溃 → T1缺失”，记录会漏掉真实操作。正确的协议顺序要求T1先于效果，T2再保存所见结果；它仍不能把文件写入与数据库提交合成一个跨资源原子操作。

为什么 T2 必须在结果回到模型（Model）之前

假设模型（Model）先看到了“README 已修改”，于是继续运行测试（Test）；随后运行时（Runtime）在持久化（Persistence）编辑结果之前崩溃。重启后，账本（Ledger）只留下测试（Test）的后续事实，却没有模型（Model）赖以作决定的编辑结果，会破坏可重放性。

因此正确的依赖顺序是工具结果（Tool Result） → T2持久提交（Durable Commit） → 下一模型步骤（Model Step）。若先让模型（Model）继续、再找时间落盘，后续动作就可能依赖重启后找不回来的依据。

幂等性（Idempotency）不等于“随便重试（Retry）”

幂等性（Idempotency） 通常指同一个操作重复执行，最终状态（State）与执行一次相同。例如“把状态（State）设置为 closed”可能幂等（Idempotent）；“余额减 10”通常不幂等（Idempotent）。

但仅凭工具（Tool）名字叫 set_status 还不够。真实系统还要确认：

  • 两次调用使用同一个幂等键（Idempotency Key），即关联同一逻辑操作的去重键吗？
  • 远端服务真的承诺按幂等键（Idempotency Key）去重吗？
  • 参数完全相同吗？
  • 第一次调用是否可能只完成了一半？
  • 本地结果是否能从远端查询回来？

因此“工具（Tool）自称幂等（Idempotent）”只是一项恢复（Recovery）契约，不是恢复（Recovery）可以无条件重放的许可证。读取也可能计费、消耗一次性令牌（Token）、改变游标或触发远端审计；能否安全重复取决于工具（Tool）合同，而非工具（Tool）名字。

对账（Reconciliation）是“查清现实”，不是“再做一遍”

对账（Reconciliation） 会使用稳定身份（Identity）检查外部世界：

表 2 / Table 2 · 对账（Reconciliation）是“查清现实”，不是“再做一遍”
对账（Reconciliation）对象核对的材料结论的边界
文件当前文本与目标修改可证明当前后置状态（State），未必能证明原调用的因果贡献
远端问题记录operationId对应的资源取决于服务是否保存并允许查询这项关联
支付操作同一幂等键（Idempotency Key）的服务记录取决于去重范围、期限与参数合同
后台任务已保存的任务身份（Identity）与存活状态（State）有条件地重新接入（Reattach），不等于重新创建

专用对账（Reconciliation）可以得到四类判断；它们不是所有工具（Tool）共用的一组应用程序接口（API）返回值：

  • 有证据确认效果：按该恢复（Recovery）合同补记或复用结果；仅看到目标文本还不一定能证明是哪次调用造成；
  • 有证据确认未开始：再核当前授权（Authorization）、参数与重试（Retry）条件；
  • 证据不足：保留现场，停放（Park）任务，交给有权处理者或专用恢复（Recovery）逻辑；
  • 记录冲突：停止自动恢复（Recovery），先处理数据不一致。

Maka 的恢复分类器（Resolver）读取操作记录并判断恢复（Recovery）状态（State）。它的 completed 分类表示记录已经结算，也可能结算的是“效果未知”。这项记录状态（State）与上面的“有证据确认效果”不同。已结算的未知结果（Outcome Unknown）就是一种重要反例：程序已经可靠记下“不知道效果”，仍然没有得到“效果成功”的证据。

在这个受控实验里，固定脚本、停止点和文件共同支持“写入发生在保存之前”。在真实多人工作区（Workspace），只看到目标文本存在，还不能单独证明它由某次调用造成；文件也可能由另一个人修改。

先判断当前状态（State），再决定下一次动作

发现缺少成功记录后，先读取当前文件、确认工作区（Workspace）身份（Identity）并检查差异（Diff）。已经达到目标时保留现状；仍需修改且证据充分时，按当前内容构造新调用；身份（Identity）或效果仍无法确认时保留未知，暂停自动推进。

新调用仍要遵守用户授权（Authorization）。不要为得到干净差异（Diff）覆盖他人的段落；也不要因为工具（Tool）名叫 Bash，就假设测试（Test）重复运行必然无副作用（Side Effect）。

例如，T2 中保存“测试（Test）退出码（Exit Code） 1”支持分析测试（Test）失败；保存“远端效果未知，不能安全重试（Retry）”仍不支持重做远端操作。结算解决的是记录状态（State），结算内容决定业务上知道了多少。

这是记录协议给出的证据界限；“T1 后文件其实还没打开”和“文件已写但 T2 没提交”在账本（Ledger）里可能一样。因此恢复（Recovery）不能拿自己猜测的崩溃时刻冒充事实。

最终总结只能写当前证据支持的内容

确认文件和测试（Test）结果后，才写“修改完成，测试（Test）通过”。若效果未知，应说明“运行中断，当前记录不足以确定结果，尚未重复执行”。这不是文字风格，而是让下一位操作者知道哪些判断仍然开放。

从不确定性回到一个新的、可验证的任务

延续第16章的重新定位（Retarget）：如果中断后 README 同时出现新测试（Test）命令与别人新增的段落，先读取当前文件并查看差异（Diff）。若仍需修订，用当前内容构造新的调用，保留他人段落；不能改变旧调用的参数后继续冒用同一次操作的身份（Identity）。稳定操作身份（Operation Identity）与参数摘要用于检测这种冲突。

第06章展示的是缺口，不证明 Maka 当前通用恢复（Generic Recovery）自动完成文件对账（Reconciliation）。

若继续代码修复实验中的 formatDuration 任务，重新读取函数和测试（Test）后，应分别记录：余秒现在是否为 % 60、README 是否使用 npm test、测试（Test）是否真的重跑、差异（Diff）是否只含授权（Authorization）改动。只有这些当前证据支持的部分才能写进最终总结。是否允许重跑测试（Test）还取决于测试（Test）脚本实际副作用（Side Effect）；实验的离线小固定示例项目（Fixture）不能替未知项目作保证。

现实效果与保存结果问答

问题 1。 README 已写入但成功记录还没保存，为什么不能盲目重跑 Edit？

参考答案。 效果可能已经发生，重复调用可能叠加效果、发生冲突或覆盖并行修改。

问题 2。 T1 与 T2 的直觉分别是什么？T2 保存了“效果未知”时，业务结果已经确定了吗？

参考答案。 T1 标记从这里起执行可能开始；T2 表示运行时（Runtime）已持久接受一份结果。结果若是“效果未知”，未知仍然成立；记录已结算不等于业务成功，也不保证任意外部恰好一次（Exactly Once）。

问题 3。 对账（Reconciliation）与重试（Retry）有什么区别？

参考答案。 对账（Reconciliation）先查现实及身份（Identity）来缩小不确定性；重试（Retry）是再执行一次，可能产生新效果。

问题 4。 文件现在符合目标，能否据此认定“一定是刚才那次调用改的”？

参考答案。 不能；这只能支持当前状态（State）判断，内容可能由别的调用或人形成。

问题 5。 中断后看到别人新增的段落，重新定位（Retarget）应怎样处理？

参考答案。 读取当前文件和差异（Diff），保留他人内容；如仍需修改，用新观察构造新调用，不盲套旧补丁（Patch）。

A：执行前拒绝

这里限定实际到达工具运行时（ToolRuntime）的调用：它因参数结构（Schema）、工具（Tool）未激活或循环闸门而在 T1 前被拒绝，实现没有运行。为了让模型（Model）理解，系统可以保存一对“调用（Call） + 合成错误响应（Synthetic Error Response）”，但不能写一个假的分派（Dispatch）标记（Marker）。

B：T1 已提交，但实现可能尚未真正开始

在 Maka 的普通路径中，T1 后还要读取实时执行边界（Live Execution Boundary），即 ExecutionBoundary，然后才进入实现。如果进程在 T1 与执行边界（Execution Boundary）读取 之间崩溃，现实上也许没有任何效果。

但账本（Ledger）没有更细的持久（Durable）标记（Marker）来证明崩溃发生在实现前。因此恢复（Recovery）必须保守地把“T1 无 T2”视为无法确定（Indeterminate）。知道内部代码大概率还没执行，和拥有可证明的持久（Durable）事实，不是同一件事。

C：实现执行到一半

写文件、解压目录或调用远端工作流可能部分完成。此时既不能宣称成功，也不能假设回滚。恢复（Recovery）需要工具（Tool）专用的状态（State）检查或人工处理。

不要假设测试（Test）永远只读。测试（Test）脚本可能创建数据库、启动服务器、上传覆盖率（Coverage）或访问网络。若 T1 存在、T2 缺失，通用恢复（Generic Recovery）同样不能仅凭工具（Tool）名 Bash 自动重跑。

若有后台任务（Background Task）身份（Identity），可以尝试重新接入（Reattach）；若没有可证明的状态（State），就停放（Park），即暂停自动推进或要求用户确认。

D：效果完成，但 T2 未提交

这是最典型的重复副作用（Side Effect）风险。README 已经修改，数据库却没有最终响应（Response）。盲目重试（Retry）可能重复追加或遇到前置条件已变化。

  1. 核对工作区（Workspace）和目标文件身份（Identity）；
  2. 检查目标新文本是否存在；
  3. 检查旧文本是否仍存在；

E：T2 已提交，下一模型步骤（Model Step）尚未开始

这是相对清晰的情况。运行时（Runtime）可以复用已提交T2中的结算事实，再按当前有效投影（Projection）准备后续模型输入（Model Input），不需要为补结果而再次执行工具（Tool）。归档或输入整理可能使模型（Model）看到有界摘要；复用事实不承诺逐字重发原始数据。

这些恢复（Recovery）操作分别作用于不同状态（State）。Edit 的 T2 表示运行时（Runtime）接受了工具结果（Tool Result），不包含整个编辑进程的内存、后台测试（Test）服务或打开的连接；新的执行仍需取得正确的项目文件、按当前规则重建输入并通过接手条件。第19章的上下文（Context）检查点（Checkpoint）保存旧历史的摘要或兼容状态（State），数据库预写日志（Write-Ahead Log，WAL） 服务于数据库的提交与恢复（Recovery）。它们都不是虚拟机的进程与内存快照，不能据此承诺交互式解释器变量或任意外部连接会回来。

T2 写入失败不能降级成普通工具（Tool）错误

工具（Tool）本身失败，例如测试（Test）退出码（Exit Code）为 1，可以形成错误结果T2，让模型（Model）分析失败原因。但若工具（Tool）完成后 T2 的持久提交（Durable Commit）自己失败，系统不能把它包装成“普通测试（Test）失败”继续循环。

原因是：模型（Model）一旦继续，就会基于一个未可靠保存的结果作出新决定。持久提交边界（Durable Commit Boundary）失败必须击穿普通代理循环（Agent Loop），交给更高层恢复（Recovery）。

客户端（Client）断线不等于执行（Run）失败

客户端（Client）只是提交和展示界面。若宿主（Host）已经准入（Admission） R7，关闭用户界面（User Interface，UI）或网络断开不应让客户端（Client）自行决定重跑。重连恢复（Recovery）的是传输（Transport）与投影（Projection）；业务执行是否完成，要看宿主（Host）和持久（Durable）账本（Ledger）。

模型服务提供方（Provider）内部执行的工具（Tool）更难判断

若 providerExecuted=true，工具（Tool）效果发生在模型服务提供方（Provider）的物理请求内部，没有普通 Maka 工具运行时（ToolRuntime）的本地 T1/T2。Maka 可以保存观察到的调用（Call）/结果（Result），并在看到活动后禁止不安全地整次重发请求，但跨进程崩溃 的通用恢复分类器（Generic Resolver）尚没有等价的完整判定边界。

因此不能因为“本地没有分派（Dispatch）标记（Marker）”就认定模型服务侧副作用（Provider-Side Effect）没发生。

Maka：普通生产工具（Tool）的持久（Durable）效果协议

以下说明只针对生产运行时宿主（Runtime Host）已注入 由SQLite存储支持的持久接收端 runtimeCommitSink 的普通由运行时（Runtime）执行的工具（Tool）。可嵌入的 ToolRuntime 允许不注入持久接收端（Durable Sink）；那种接法不能继承同样的持久（Durable）保证。

操作身份（Operation Identity）

Maka 为普通工具（Tool）操作构造稳定身份（Identity）。下面 invocationId 标识所属执行，providerToolCallId 标识模型（Model）服务返回的这次工具调用（Tool Call）；toolName 是工具（Tool）名，normalizedPersistedArgs 是规范化后保存的参数，hash 表示计算摘要。核心关系可以简化为：

o=Hid(i,c),h=Hargs(n,a). o = H_{\mathrm{id}}(i,c), \qquad h = H_{\mathrm{args}}(n,a).o=Hid​(i,c),h=Hargs​(n,a).

这里 ooo 对应操作标识 operationId，iii 对应执行关联标识 invocationId，ccc 对应 providerToolCallId；hhh 是参数摘要，nnn 是工具名 toolName，aaa 是规范化后保存的参数。两个函数下标特意不同：操作身份（Operation Identity）与参数摘要（Args Hash）分别回答“哪次调用”和“这次调用的内容是否一致”，不是同一哈希输入合同。

这里的身份函数是教学简写；真实 buildToolOperationId还给摘要加上前缀并截取固定长度，参数摘要则使用另一套规范化合同。下面比较两个请求时，只依赖上述输入关系，不把数学记号当作真实返回格式。

新 AgentRun 通常令 invocationId = runId。invocationId 关联这次执行的事实；operationId 由 invocationId 与模型服务提供方（Provider）返回的工具调用标识（Tool Call ID）组合得到，用于标识其中一次工具（Tool）操作。这不需要另建一层独立生命周期。

同一个 invocationId与同一个 providerToolCallId应得到同一操作身份（Operation Identity）。重用同一身份（Identity）时，系统重新计算并比较规范化的参数摘要（Args Hash）；摘要不一致时判为冲突。这依赖既定的规范化合同（Contract），不能从摘要相同反推原始对象表示法（JSON）逐字相同。反过来，模型（Model）用新的工具调用标识（Tool Call ID）原样再提一次，即使参数相同，也会得到另一操作身份（Operation Identity）。所以“参数相同”不证明系统已经替两次请求去重。

每次调用需要稳定身份（Identity）

恢复（Recovery）还要知道 T1 和 T2 是否属于同一次调用。可以为操作建立稳定的 operationId，并记录：

  • 所属会话（Session）、工作轮次（Turn）、执行（Run）；
  • 模型服务提供方（Provider）返回的工具调用标识（Tool Call ID）；
  • 工具（Tool）名；
  • 规范化参数的摘要（Hash）；
  • 恢复（Recovery）策略；
  • 最终结果或错误。

参数摘要（Hash）能阻止危险的“身份（Identity）相同、参数却漂移”：如果重启后的代码用同一个 operationId 改了另一个文件，系统应视为冲突，而不是覆盖旧记录。

T1 原子保存什么

通过所有 T1之前检查后，Maka 在一个 SQLite 事务（Transaction）中保存：

  • 模型可见（Model Visible）的函数调用（Function Call）；
  • 模型不可见（Model Hidden）的分派（Dispatch）事实；
  • TOOL_BOUNDARY_PROTOCOL_V1 / t1_after_preflight_v1 协议标记；
  • operationId、工具（Tool）名、模型服务提供方（Provider）调用（Call）标识；
  • 规范参数摘要（Canonical Args Hash）；
  • 恢复（Recovery）模式（Mode）；
  • 准备阶段操作日志（Prepared Operation Journal）。

只有 T1 成功后才继续。若发现已有占用声明（Claim）、身份（Identity）冲突或摘要（Hash）漂移，当前调用不能偷偷改参数后执行。

T1 后才读取实时执行边界（Live Execution Boundary）并调用实现

普通路径依次完成T1之前的执行前检查（Preflight），等待 commitToolPrepared保存T1，再读取实时执行边界（Live Execution Boundary），最后交给 tool.impl及其执行器（Executor）或适配器（Adapter）。

这保证每次实现调用读取当前修订号（Revision），而不是执行（Run）开始时的过时权限（Permission）。代价是：执行边界（Execution Boundary）读取 失败也已经越过 T1，需要形成错误结果T2；如果在两者之间崩溃，账本（Ledger）仍只能保守判为无法确定（Indeterminate）。

T2 原子保存什么

工具（Tool）返回或抛出业务错误后，Maka 规范化结果，并在 T2 保存：

  • 匹配函数响应（Matching Function Response）；
  • 运行时（Runtime）接受的 规范结果（Canonical Result）；
  • 与模型服务提供方（Provider）无关的模型投影（Model Projection）；
  • 结算结果（Outcome）日志（Journal）；
  • 操作（Operation）从已准备（Prepared）到结果已提交（Outcome Committed）的状态（State）转换。

只有 T2 提交成功，结果才允许进入下一次模型步骤（Model Step）。业务错误也可以是已结算结果（Outcome）；“结果为错误”和“结果没能持久（Durable）保存”必须分开。

恢复（Recovery）看账本（Ledger）形状，不按工具（Tool）名字猜

客户端（Client）的“已结算错误”仍可能表示效果未知

客户端能力（Client Capability）使用 outcome_unknown 恢复（Recovery）模式（Mode）。宿主（Host）重启恢复（Recovery）时可以给遗留调用写入明确的 错误结算结果（Error Outcome），表示客户端（Client）效果可能已发生，且 retrySafe=false。这让账本（Ledger）不再悬着，但它没有把业务事实变成“没有发生”或“已经成功”。模型服务代执行（Provider-Executed）则连这套普通本地 T1/T2 都没有，通用恢复分类器（Generic Resolver）目前未建立等价分支，不能套用上表。

上述工具（Tool）等待只覆盖普通工具运行时（ToolRuntime）能管理的活动结算（Active Settlements）。模型服务代执行（Provider-Executed）工具（Tool）发生在模型服务提供方（Provider）请求内部，不拥有这套本地 T1/T2；取消（Cancellation）该请求也不能证明模型服务提供方（Provider）副作用（Side Effect）已撤销。内部执行后端（Backend）还支持 after_step，它请求在当前模型步骤（Model Step）后停止继续；面向用户的 Stop默认走 immediate，并不公开模式（Mode）。这个区别是控制语义，不是任意外部程序能在某个固定毫秒数内停止的承诺。

实际负责者（Owner）也要核对：没有宿主交互裁决权（Host Interaction Authority）的嵌入式运行时（Runtime）可以直接结算 Stop 终态（Terminal State）；宿主管理路径（Hosted Path）需保留宿主（Host）对终态（Terminal State）和模型服务状态无法确定（Provider Indeterminate）的裁决权（Authority）。不能拿底层测试（Test）中 settleStopTerminal 的一次调用代表所有生产入口。

托管修改（Managed Mutation） 是更强基础，但尚非默认 Edit 保证

Maka 的 managed_mutation_v1 协议可以把工作区（Workspace）的基础版本、路径、版本身份与修改预留（Mutation Reservation） 更紧密地绑定。

但生产宿主（Host）尚未为普通内建 Write/Edit 注入相应准入（Admission），工具（Tool）也未默认声明该 执行配置（Execution Profile）。因此 R7 中的普通 Edit README.md 仍应按一般 T1 → 文件系统实现 → T2 理解，不能写成“每次编辑都获得工作区（Workspace）后继版本（Successor）的恰好一次（Exactly Once）保证”。

把同一次 Edit 从准入追到后置证据

普通 Edit 的动作、权限（Permission）检查和结果记录可以放在同一条时间线上。任务仍是把 README 的错误测试（Test）入口 npm run check 改为 npm test。限定为宿主（Host）注入持久接收端（Durable Sink）、托管限制（Managed）文件工作进程（Worker）可用、目标已获准的普通 Edit；不套用模型服务代执行（Provider-Executed）或更强托管修改（Managed Mutation） 协议。下面按这条实现链作教学推演，不是实测轨迹。C17/O17 只是本次调用及其操作（Operation）的示例标签，不是另一个待调用的应用程序接口（API）。

改变两个条件，再判断下一步

问题一：同样假设 README 已写入，但宿主（Host）在保存未知（Unknown）的错误结果T2 之前退出。重启后还能判已结算（Completed）吗？新的 Read 已看到 npm test，能否直接宣布 O17 成功？

参考答案

不能沿用上表的已结算（Completed）。此时持久记录只有分派（Dispatch）、没有匹配响应（Matching Response），恢复分类器（Resolver）判 indeterminate / dispatch_without_response。文件现态与上表可能完全相同，系统已保存的知识却不同。

新的 Read 可以证明当前可见文本包含目标入口；若其他要求也满足，可避免重复编辑。它不能唯一证明由 O17 完成，也不会自动补成 O17 的成功 T2。当前通用恢复（Generic Recovery）没有自动完成这一整套文件对账（Reconciliation）；应保留未知，并按有权处理恢复（Recovery）的入口继续任务。

问题二：前一次 Read 后，另一位编辑者原地修改了 README 的介绍，索引节点号（Inode）没变，旧测试（Test）命令仍唯一存在。能否认为文件层 T0 身份（Identity）比较检查必然拒绝本次 Edit，保护了上一轮 Read 的完整版本？

参考答案

不能。普通 Edit 没有 observedVersion 参数；文件层比较 dev/ino，不比较上一轮 Read 的全部内容。若外部修改在工作进程（Worker）读取前已完成且旧命令仍可唯一匹配，Edit 可以基于当前内容继续替换。不能把“同一对象”当成“同一版本”。

这也不保证执行期间任意外部写者都被排除：工具（Tool）的路径锁只协调参与该锁的调用。更强的设计需要在负责提交的资源层检查观察版本，并定义检查与写入的原子边界。对当前工具（Tool），涉及并发变化时应重新读取、保留他人改动并核对后置状态（State）；该增强方案不是默认 Edit 已有的保证。

await 的含义是等待异步提交完成或抛错，不是冻结整个进程。如果删掉它，代码可能在提交失败前就沿成功路径继续；如果吞掉提交错误，模型（Model）可能基于重启后无法还原的结果作下一步决策。若把 T2 移到真实效果之前，则又会记录一项尚未观察到的结果。三种改法各破坏一条不同的因果关系。

同一 commitOutcome 内紧邻的 catch 允许尽力补偿，但补偿不能覆盖 T2 原始失败；成功后才设置内存中的 committedOutcome。调用侧 executeTool 通过 durableAttempt?.commitOutcome(...) 先等待提交，再构造 resultMsg 并发布结果。?. 表示只在该对象存在时调用，因此这条持久保证以“生产已注入持久接收端（Durable Sink）”为前提。

这个源码片段依赖调用侧和持久接收端（Durable Sink），不能独立运行；它固定了“效果已发生 → 等待结果提交 → 发布结果”中的后两步顺序。

更深一层的常见误区

用户点击 Stop 后立刻写终态（Terminal State）最安全

如果仍有活动工具（Active Tool）正在结算，这会让终态（Terminal State）排在工具结果（Tool Result）之前。应先中止（Abort），再等待可以结算的结果（Outcome）。

客户端（Client）重连就是恢复（Recovery）业务执行

重连只恢复（Recovery）连接和视图。执行（Run）、工具（Tool）、目标（Goal）等业务由各自宿主（Host）负责者（Owner）根据持久存储（Durable Storage）恢复（Recovery）。

恢复（Recovery）协议的适用范围问答

问题 1。 带当前协议标记的普通调用（Call） + 合成（Synthetic）响应（Response）、没有分派（Dispatch），说明什么？old_string 未找到也一定属于这种形状吗？

参考答案。 前者是 T1之前拒绝（Refusal），实现未运行；旧片段是否最终可匹配，要在 Edit 实现内检查；若在写入前拒绝且错误保存成功，是分派（Dispatch）后的错误结果T2，不能混同。

问题 2。 T2 写入失败为何不能变成普通“请重试（Retry）”的工具（Tool）错误？

参考答案。 否则模型（Model）可能基于不存在的持久历史（Durable History）继续或重复副作用（Side Effect）；提交边界错误需要传播并进入恢复（Recovery）处理。

问题 3。 idempotent 标签为什么不等于无条件安全重试（Retry）？

参考答案。 还要核对同一意图身份（Identity）、参数、服务端去重作用域/期限和部分执行合同，标签不是实现。

问题 4。 客户端（Client）恢复（Recovery）写入 retrySafe=false 的 错误结算结果（Error Outcome），业务效果已确定了吗？

参考答案。 没有。运行时（Runtime）结算的是“效果未知、不能安全重试（Retry）”，不是远端业务成功或无效果。

问题 5。 模型服务代执行（Provider-Executed）缺本地分派（Dispatch）标记（Marker），能否证明没执行？

参考答案。 不能；该执行子通道（Execution Lane）在模型服务提供方（Provider）内执行，不适用普通本地账本（Ledger）推断，通用崩溃恢复（Crash Recovery）仍有缺口。

问题 6。 当前每次内建 Edit 都会提交托管工作区（Managed Workspace）后继版本（Successor）吗？

参考答案。 不是。托管修改（Managed Mutation） 基础协议存在，但普通内建工具配置（Builtin Tool Profile）与宿主（Host）准入（Admission）默认接线仍未启用。

问题 7。 Edit 已经写入后按 Stop，为什么取消（Cancellation）终态（Terminal State）之前仍可能出现这次 Edit 的成功 T2？

参考答案。 Stop 不回滚已发生效果；普通工具（Tool）仍需把可结算结果（Outcome）持久保存，保持 T2 早于终态（Terminal State）。成功 T2 只报告这次编辑的结算结果（Outcome），取消（Cancellation）终态（Terminal State）表示后续执行（Run）被停止，两者不矛盾。

恢复（Recovery）方法比较了本地账本（Ledger）、远端幂等键（Idempotency Key） 与资源版本提交各自由谁承担保证。
