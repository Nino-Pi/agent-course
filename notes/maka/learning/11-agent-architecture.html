第 11 章｜Maka 的 Agent Harness 结构

本章概览

核心问题：Maka 怎样把模型、工具、工作状态和客户端组织成一套 Agent Harness？

关键概念：Host 接纳并协调工作；Runtime 推进执行循环；Client 展示结果；工具执行器落实动作；持久存储保留工作与执行记录。

关系主线：任务经 Host 接纳，由 Runtime 组织模型与工具协作，运行记录被保存，Host 向客户端提供状态与展示增量。六组 Harness 职责落到这些部件；文件变化、测试结果与执行终态分别支持不同结论。

与最小循环的职责对应见 从 mini 到 Maka。

Maka 如何实现 Agent Harness

第01章把 Agent 解释为围绕目标观察、决策、行动并接收反馈的系统，把 Harness 解释为组织模型与外部世界交互的运行软件。本章沿用这一区分，观察 Maka 怎样分配责任。

Maka 的 Host（宿主）接纳并协调工作，Runtime（运行时）推进一次执行，Client（客户端）展示结果并接收用户输入。工具执行器负责实际读写和命令运行；持久存储保留已接受的工作及执行记录。它们是协作的软件部件，模型在其中负责提出下一步和解释观察。

Host 从持久事实构造快照，并转发运行中的增量；Client 通过协议读取和订阅。因此即时展示不必等同于已经持久结算的结果。图中箭头表示主要信息流，不是全部接口：Client 的请求也经 Host 提交，工具可能由本地或其他执行端承载。可用性与当前授权由工具运行链检查，具体执行端落实资源限制；持久记录的写入时机则决定崩溃后能知道什么。

这六组是学习地图；具体机制不必各有一个同名类。Context 是本次输入，Memory 是供后续复用的信息：后者必须被读出并选入输入，才能影响当前模型调用。模型看到 Edit 的说明，只能提出调用意图，实际执行仍受工具绑定、参数和当前许可约束。

一项 README 修复怎样推进

贯穿全套教程的案例

代码修复任务来自 第04章 的四文件案例：

修正 README 的测试步骤，找出并修复 formatDuration 的时间格式化错误，运行测试并检查 diff；用中文解释结果。

formatDuration(seconds) 要把非负整数秒表示为 minutes:ss，例如 125 → 2:05。README 告诉人怎样启动测试，函数实现和测试则用来判断行为是否正确。

这里抽出“只更新 README”的简化情形：假设功能测试原本已通过，只需要读、改说明、测、总结；这不证明完整任务中的函数缺陷已修复。第16章使用完整修复任务。简化任务还包含一项长期偏好：

检查 package.json 与 README.md，更新 README 的测试步骤，运行测试，最后用中文总结；以后也请记住我希望使用中文解释。

这段工作使用三个教学标签：Session（会话） S1 标识长期归属，Turn（轮次） T7 标识用户这项工作，Run（运行） R7 标识一次具体执行。一次 Run 可以包含多次模型与工具调用；它们的生命周期见 第13章。

从提交到总结的调用链

在只更新 README 的情形中，循环按下面的因果顺序推进：

用户在 S1 中提交 T7
  ↓
系统接受任务，为它建立 R7
  ↓
构造第一次模型上下文
  ↓
模型请求 Read(package.json) 与 Read(README.md)
  ↓
工具返回两份真实文件内容，结果被保存
  ↓
构造下一次模型上下文（现在包含两个 Read 结果）
  ↓
模型请求 Edit(README.md, ...)
  ↓
工具执行修改并返回结果
  ↓
模型请求 Bash(测试命令)
  ↓
工具返回测试输出与退出状态
  ↓
模型用中文总结真实结果
  ↓
系统保存执行的结束状态，并通知客户端展示

下一步之所以依赖前一步，是因为结果可能推翻原来的判断。例如 README 写着 npm run check，package.json 的 scripts 却只声明 test 脚本，其调用入口为 npm test，模型应根据配置修正入口。完整修复任务还可能出现函数断言失败，那又需要诊断实现。重复读取未变化的文件也可能没有新发现；循环提供根据结果调整的机会，不保证每一步都增加信息。

正常例子与失败例子

正常例子：所有观察都能闭环

  1. 两个 Read 分别返回 package.json 中的真实测试脚本和 README 当前说明；
  2. 模型比较两份内容后生成精确 README 修改；
  3. Edit 明确返回修改成功；
  4. Bash 返回退出码 0，输出说明哪些测试已通过；
  5. 检查文件差异（diff）确认改了预期位置，最终回答说明改了什么、运行了什么、测试覆盖到哪里。

失败例子：测试命令不存在

  1. 两个 Read 都成功，模型拿到配置和 README 当前内容；
  2. 模型错误地请求一个不存在的测试脚本；
  3. Bash 返回非零退出状态和错误输出；
  4. 模型应当根据错误决定是否尝试经过允许的替代命令，或者如实报告失败；
  5. 即使系统正常结束了本次执行，也不能把“已结束”写成“已经满足所有用户要求”。

失败结果会改变后续判断；它不会因 Run 已结束而变成测试通过。

第22章 的小代码修复记录了实际工具调用、文件变化和测试结果。上面的 R7 是教学示意，不要求真实模型固定使用同一步数或动作顺序。

核心问题解析

问题 1。 模型说“已修复”能证明文件已经改变吗？还要检查什么？

解释。 只证明模型生成了这句话。文件变化看实际内容与 diff，行为看对应测试；还需确认测试覆盖了用户要求。

问题 2。 为什么先读文件、再编辑、再测试，通常需要多次模型调用？

解释。 当下一动作依赖尚未取得的文件内容或测试反馈时，要先执行、再把结果交给后续调用。一次工具调用也可能没有新发现；不能预先假定每一步都增加信息。

问题 3。 模型、工具执行器与循环控制各负责哪一件事？

解释。 模型提出下一步并解释结果；执行器产生真实操作与输出；循环控制组织输入、保存状态并决定继续或停止。

进程退出后，工作依据怎样保留

准入固定工作身份

用户可以在同一个会话里发起多项工作。系统需要把模型事件、工具结果和结束状态关联到正确的 Session、Turn 和 Run，才有可能区分重试与新任务。

准入（Admission）是 Host 正式接受工作并固定执行身份的过程。Client 点击发送只提交意图；Host 还要检查当前是否已有冲突工作、是否可以开始，再把接纳结果保存下来。第12章展开了这些步骤。

执行许可与效果记录

模型看到 Edit 的说明，不代表可以修改任意文件。工具是否绑定、当前是否可用、目标是否获准、执行环境能否落实限制，是不同条件。权限必须在实际执行位置受到检查，不能仅靠提示词中的要求。

如果 Edit 已把内容写入文件，程序却在保存结果前崩溃，重启后就可能不知道修改是否发生。重做可能重复效果，直接报告“没有修改”也可能错误。Maka 把关键执行记录写入持久存储（Durable），使恢复程序能读取已提交的结果；记录仍不足时保留未知，而不猜测成功或失败。第18章用具体提交窗口解释这些判断。

持久事实生成展示视图

事实（Fact）是负责相应状态的系统组件接受并保存的记录。客户端（Client）如 Desktop、CLI、TUI 接收 Host 提供的快照、增量与聊天记录页面，生成聊天气泡和运行状态；界面可能延迟、断线或丢失缓存，重新打开时应通过服务接口回读状态并重建视图。

回答文字和 Run 终态也不同：文字说明了模型输出什么，终态说明执行怎样结束。界面的 loading 动画结束，不能替代持久终态，更不能证明所有测试都通过。

同一句请求中的长期偏好

“本轮用中文”可以直接进入当前上下文。“以后也用中文”还需要长期记忆（Memory）的写入、后续读取和输入组装；最终回答“我记住了”不完成这些步骤。即使偏好已进入后续输入，是否被正确使用仍要观察实际回答。

会话历史、当前上下文、用户可编辑的长期笔记和结构化记忆解决不同问题。把整段聊天存进数据库也不能自动决定哪些内容适用、该更新什么，以及怎样影响下一次任务。第20章追踪保存、读取和使用的完整区别。

机制问题解析

问题 1。 Context 与完整历史有什么差别？

解释。 Context 是本次模型实际收到的组合；历史可能更大，且部分内容不进入模型。

问题 2。 为什么 Client 不能独自宣布 Run 完成？

解释。 Client 是展示端，完成判断应来自执行 owner 的持久终态事实。

问题 3。 为什么本轮中文回答不等于未来自动使用中文偏好？

解释。 未来使用还要完成保存、读取和注入；本轮要求可以直接放进当前输入。两种情况下都要观察实际回答，才能判断这次是否遵循。
