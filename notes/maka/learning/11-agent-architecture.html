第 11 章｜Maka 的运行支撑（Agent Harness）结构

本章概览

核心问题：Maka 怎样把模型（Model）、工具（Tool）、工作状态（State）和客户端（Client）组织成可追踪的协作过程？

关键概念：宿主（Host）接纳并协调工作；运行时（Runtime）推进一次执行（Run）；工具执行器（Tool Executor）产生实际结果；持久存储（Durable Storage）保留记录；客户端（Client）提交请求并显示状态（State）。

关系主线：先分清谁负责决定、谁读取输入、谁改变现实，再沿 README 修复连接这些部件。工具结果（Tool Result）、执行终态（Terminal State）与任务验收分别支持不同结论，记忆（Memory）还需要后续消费者（Consumer）。

前情回顾：从共同问题走到具体负责者（Owner）

第08章把运行支撑（Agent Harness）分成六组教学职责，并用真实修复片段说明：mini 与 Maka 都能读取、修改、检查，但请求表达和执行顺序可以不同。文件已经改变、记录已经保存、界面已经更新，是三个需要分别核对的状态（State）。因此，比较架构不能只数类或工具（Tool），还要找谁对这些状态（State）负责。

本章把负责更新某项状态（State）、接受相应结果的部件称为负责者（Owner）；把实际读取并使用一份材料的人或程序称为消费者（Consumer）。同一个部件可以同时承担两种角色，但“保存过”与“已经被下一步使用”仍是两件事。

第09章讨论接手项目时怎样确认任务范围（Task Scope）、文件初态和检查入口；第10章提供类型、等待和事件交接的语言读法。本章将使用这些读法解释责任关系，不要求先记住全部源码入口，也不把一个类型所在的包直接当成执行负责者（Owner）。

Maka 如何实现运行支撑（Agent Harness）

智能代理（Agent）围绕目标读取情况、作出决定、请求行动并接收反馈。模型（Model）承担其中的决策与文本生成；运行支撑（Agent Harness）负责把这些决定接到真实程序、状态（State）与用户交互。本章讨论的是 Maka 当前普通宿主（Host）路径，具体运行由默认 ai-sdk 执行后端（Agent Backend）承载。执行后端（Agent Backend）是供上层选择的执行实现；换一条实现后，重试或恢复（Recovery）保证仍须重新核对。

先按“收到什么、改变什么、交给谁”阅读各部件：

表 1 / Table 1 · Maka 如何实现运行支撑（Agent Harness）

持久存储（Durable Storage）对应负责者（Owner）提交的记录按存储合同保存、读取与校验记录恢复（Recovery）程序、输入组装与展示服务
客户端（Client）宿主（Host）提供的快照（Snapshot）与更新接收用户意图，显示当前可见状态（State）用户读取界面；新的请求再交给宿主（Host）

表中的执行边界（Execution Boundary）表示当前这次操作受哪些资源与授权（Authorization）条件约束。工具执行器（Tool Executor）最终读写文件或运行命令；前面的校验、绑定和许可检查不因此都归给底层执行器。

沿中间的循环读，模型（Model）提出请求，工具执行链（Tool Execution）落实操作，结果再进入运行时（Runtime）。沿右侧记录与显示的路径读，宿主（Host）既能转发运行增量，也会回读持久事实（Durable Fact）构造快照（Snapshot）。正在显示的文字，不必已经完成持久结算（Durable Settlement）。 图中是主要信息流，不是全部接口或每个包的导入关系。

这种分工让两个问题能够分别回答：一个工具（Tool）当前能否运行，由实际工具执行链（Tool Execution）判断；客户端（Client）断线后怎样重新显示工作，则由宿主（Host）的观察服务与持久记录共同支持。存储文件存在，不会自行开始模型调用（Model Query）；界面重新打开，也不会自行获得重新执行业务操作的许可。

这里的模型步骤（Model Step）是一轮输入交给模型（Model）并取得决策的阶段，可以包含多个工具调用（Tool Call）。六组职责是学习地图，不要求分别存在六个同名类，也不是运行时（Runtime）要依次经过的六步流程。

上下文（Context）是本次模型（Model）实际收到的组合；记忆（Memory）是供后续复用的信息。后者只有被读出并选入模型输入（Model Input），才可能影响这次回答。这条消费者（Consumer）关系也适用于工具（Tool）：看见 Edit 的说明只使模型（Model）能够提出调用意图，实际执行仍受绑定、参数和许可约束。

一项 README 修复怎样推进

贯穿教程的案例与本章初态

第04章的完整任务包含两处修改：修正 README 的测试（Test）入口，并把 formatDuration(seconds) 的余秒计算从 % 100 改为 % 60。函数接受非负安全整数秒，返回 minutes:ss；例如125秒应显示为 2:05。四份文件分别提供说明、项目配置、实现和断言（Assertion）。

本章改变初态：函数已经正确，既有四个测试（Test）原本通过，只需要修正 README。 本章允许修改 README，保留函数、测试（Test）与配置；没有沿用原始 % 100 缺陷。这个变化使我们能专注看责任交接，不能据此声称完整函数修复已经在此运行。

教学请求是：

检查 package.json 与 README.md，更新 README 的测试步骤，运行测试，检查改动范围，最后用中文总结；以后也请记住我希望使用中文解释。

README 当前写着 npm run check，项目配置只提供 "test": "node --test"，实际入口为 npm test。Read、Edit、Bash 是 Maka 的实际工具标识，分别用于读取文件、修改文件和运行命令；标识保持原文，不能从名字直接推断参数或授权（Authorization）已合法。

用三种工作身份（Work Identity）追踪它：会话（Session）S1 表示长期归属，工作轮次（Turn）T7 表示用户可识别的这一项工作，执行（Run）R7 表示本次具体执行。一次执行（Run）可以包含多次模型调用（Model Query）和工具调用（Tool Call）；三者的生命周期（Lifecycle）在第13章进一步展开。S1、T7、R7 都是教学标签，不是某次捕获的真实运行编号。

正常例子与失败例子

正常例子：每个结论都有对应材料

两个 Read 分别取得配置与README当前内容，模型（Model）据此形成精确局部替换。Edit 返回修改结果后，Bash 运行配置中确认的 npm test。在本章函数原本正确的条件下，教学预期为四项测试（Test）通过、退出码（Exit Code）0；随后检查差异（Diff），确认本次只改了README中的目标位置。

最终说明应同时包含改动、运行过的检查与覆盖范围。说“已修复”是一个待支撑的结论，不能拿这句话替代文件、工具结果（Tool Result）或断言（Assertion）。

失败例子：测试（Test）命令不存在

假设两个 Read 已成功，但模型（Model）仍错误地请求 npm run check。Bash 返回非零退出码（Exit Code）和 Missing script。这说明测试（Test）入口没有找到，尚不能评价函数行为；下一步应依据已经取得的配置选择获准的正确命令，或者如实说明无法继续的原因。

若改用 npm test 后实际出现断言（Assertion）失败，就有新证据推翻“函数原本正确”的教学假设。真实任务应报告所见失败，并按用户范围决定后续动作；不能为了维持示例而改写结果。即使R7正常结束，失败的测试（Test）也不会因此变成通过。

第22章保存了真实工具调用（Tool Call）、文件变化和测试（Test）结果。本节的R7与四项通过是给定条件下的教学推演，不能拼接成那次真实运行的新增步骤。

核心问题解析

问题1。 模型（Model）说“已修复”能证明文件已经改变吗？

参考答案。 只能证明生成了这句话。文件变化要看当前内容与差异（Diff）；行为要看针对目标的测试（Test）。即使四项通过，也要核对这些断言（Assertion）是否覆盖本次要求。

问题2。 为什么先读文件、再编辑、再检查，通常需要多次模型调用（Model Query）？

参考答案。 下一项行动请求（Action）若依赖尚未取得的文件或执行结果，就要先实际执行，再把材料送入下一模型步骤（Model Step）。多个互不依赖的读取可以由一个模型步骤（Model Step）提出；调用次数与工具（Tool）数量不能直接相等。

问题3。 模型（Model）、工具执行器（Tool Executor）与循环控制各负责什么？

参考答案。 模型（Model）提出下一步并解释结果；工具执行器（Tool Executor）产生真实操作与输出；运行时（Runtime）组织输入、接纳执行记录并判断是否继续。负责展示的客户端（Client）不替这些部件完成验收。

进程退出后，工作依据怎样保留

准入（Admission）固定工作身份（Work Identity）

用户可以在同一个会话（Session）发起多项工作。系统需要把模型（Model）事件、工具结果（Tool Result）和执行终态（Terminal State）关联到正确的会话（Session）、工作轮次（Turn）和执行（Run），才能区别“同一请求的重试”与“新工作”。

准入（Admission）是宿主（Host）正式接受工作、固定输入与工作身份（Work Identity）的过程。客户端（Client）点击发送只提交意图；宿主（Host）还要检查会话（Session）状态（State）、冲突工作及相同身份（Identity）的既有内容。接纳结果先保存，才交给执行路径。第12章会解释为什么网络超时不能直接触发一个新R7。

执行许可与效果（Effect）记录

工具（Tool）说明可见、当前已经绑定、参数有效、目标已获准、执行环境（Environment）能强制限制资源，是不同条件。权限（Permission）需要在实际执行位置检查，不能仅靠提示词（Prompt）中的“不要越界”。

若 Edit 已写入文件，程序却在保存结果前崩溃，重启后的记录可能不足以说明修改是否发生。重做可能重复效果（Effect），直接报告“没有修改”也可能错误。普通已接入持久结果接收端的工具（Tool）路径，用执行前后的持久边界保留可核对材料；恢复（Recovery）程序据此读取已提交结果，不足时保留结果未知（Outcome Unknown）。具体条件见第18章，不能将同一保证直接推广给所有执行后端（Agent Backend）。

持久事实（Durable Fact）生成展示视图

持久事实（Durable Fact）是相应负责者（Owner）接纳并保存的记录。它不表示对真实世界的全部描述都已正确；例如一条已保存的测试（Test）失败结果，准确记录的就是失败。记录由谁提交、包含什么、保存成功怎样确认，仍有具体合同。

客户端（Client）通过宿主（Host）提供的快照（Snapshot）、增量和历史页面显示内容。把事实（Fact）整理成某种可读视图的过程称为投影（Projection）。界面可能延迟或丢失缓存，重新连接时应回读状态（State）并重建投影（Projection），而不是凭旧画面重新执行任务。

最终文本说明模型（Model）输出了什么，执行终态（Terminal State）说明R7怎样结束，两者也可能先后到达。加载动画结束不能代替持久终态（Terminal State），更不能证明测试（Test）通过。反过来，客户端（Client）未收到最终通知，也不能推导负责者（Owner）尚未保存结果。

同一句请求中的长期偏好

“本轮用中文”可以直接进入当前上下文（Context）。“以后也用中文”则需要记忆（Memory）写入、后续读取与输入组织（Input Composition）；最终回答“我记住了”不完成这条链。即使偏好已进入下一次模型输入（Model Input），是否被正确使用仍要观察实际回答。

会话（Session）历史、工作上下文（Working Context）、用户可编辑的长期笔记与结构化记忆（Memory）各有用途。工作上下文（Working Context）是为本次判断选取并整理的材料；保存整段聊天，并不会自动决定哪些偏好继续适用或怎样更新。第20章展开两种记忆（Memory）的读写与消费者（Consumer），下一章先说明本例为什么不能把“已写入”当作“未来一定会使用”。

机制问题解析

问题1。 上下文（Context）与完整历史有什么差别？

参考答案。 上下文（Context）是本次模型（Model）实际收到的组合；保存的历史可能更大，部分内容没有入选。需要检查输入组织（Input Composition）及实际消费者（Consumer），不能只看数据库里有没有材料。

问题2。 为什么客户端（Client）不能独自宣布执行（Run）完成？

参考答案。 客户端（Client）管理显示，执行负责者（Owner）管理相应终态（Terminal State）。网络和缓存能改变眼前画面，却不能把未保存的终态（Terminal State）变成事实（Fact）。任务验收还需要单独的结果材料。

问题3。 本轮中文回答为什么不等于未来会使用中文偏好？

参考答案。 本轮指令可以直接进入模型输入（Model Input）；未来复用还需保存、选取、读取与装载。两种情况下都要检查实际回答，才能说明该次是否遵循。
