第 21 章｜记忆的保存、读取与使用

本章概览

核心问题：保存偏好、关闭读取和提交后崩溃，会怎样改变下一进程看到的状态与输入？

关键概念：跨进程读取检验信息是否保留；scope（范围）决定选择；composer（组装器）生成请求背景；COMMIT（事务提交）成功后使本次事务修改生效；receipt（回执记录）识别同一操作的重放。

关系主线：Python 案例展示范围选择，Maka 案例对照文件、数据库与组装结果。关闭读取不等于删除，提交后丢回执不等于回滚；两组都未调用模型，不能由此保证偏好被采用。

第一项使用 Python 标准库、JSON 文件和顺序启动的新进程，不调用 Maka；第二项使用真实 Maka Memory 存储、composer 和 SQLite 事务。两项都不调用模型，相关定义见 第20章。

旧会话保存“解释用中文”，随后增加“工作区 A 用英文，其他工作区继续中文”。新请求始终只有“解释 formatDuration 的测试结果”，没有重述偏好。

跨进程保存与读取的完整过程

这个固定输入案例的结果为 PASS，七项检查均通过。它只调用 Python 标准库，没有调用 Maka 或模型。

脚本每次保存或读取都用 subprocess.run 启动新进程，并等待它退出后才启动下一步。trace 记录动作与 PID，因此读取不会依赖上一个进程里的 Python 字典。文件是本实验跨进程保留信息的载体。

关键代码改变了什么

实验脚本中，三个分支决定状态变化：

  1. worker 的两个保存分支：先保存全局偏好，再添加 A 的例外，原全局值仍保留。
  2. worker 的读取分支：关闭读取时直接返回空背景；开启时按工作区选择。这一步决定“已经保存的信息”是否进入背景。
  3. run 的正反对照：比较 A、B、关闭读取和故意只读全局偏好的结果，同时核对关闭读取前后的文件 hash 相同。

实际状态依次为：

文件：global=zh
  → 新读进程A：background=zh
文件：global=zh，workspace A=en
  → 新读进程A：background=en
  → 新读进程B：background=zh
  → 关闭读取的A：background=[]；文件不变
  → 错误读取器A：background=zh；暴露scope选择错误

输出的 background 是供请求装配使用的数据，不是模型回答。即使程序选择了 en，也没有验证模型最终用英文、更没有证明模型正确解释了测试。

真实模型的输出对照

第22章 的真实 Local Memory 案例继续观察模型输出：相同保存条目，开启读取的新会话按指定三段格式解释测试，关闭读取的新会话使用普通结构。程序选择了什么与模型怎样回答，是两项独立观察。

增加工作区例外与任务规则

问题。 新用户要求“B 用日文，其他工作区照旧”。存储中增加什么，A、B、C 分别读取什么？

参考答案

在既有工作区映射中增加 B 的日文例外，保留 global=zh 和 A=en。A 读英文，B 读日文，C 回落到全局中文。实现时还需让写入分支接收对应值；本实验源为便于观察而固定写入 en，因此仅更换 workspace 参数不能完成该迁移。

问题。 若要求变成“发布说明用英文，排错解释用中文”，仅按 workspace 选择还够吗？

解释。 不够，新规则区分的是任务类型。一个明确的教学方案是先由本次任务确定 task_type，再按 release_notes → en、debug_explanation → zh 选择；未知类型继续使用原工作区规则。这样，A 的发布说明用英文、A 的排错解释用中文，B 的发布说明也用英文。这里假定任务规则优先于工作区规则，并由用户要求支持这一优先级；若任务同时属于两类且没有优先规则，应保留冲突。该选择器是新条件的设计推演，原 Python 脚本没有实现它。

这个 Python 实验用 write_text 保存文件，没有建立崩溃事务，也没有处理多写者或幂等重试。真实存储的重开、事务和故障行为由下面的 Maka 实验检查。

Maka 的写入、重开与输入组装

第二个案例直接使用构建后的 Maka 模块，在独立测试状态根中保存明确给定的内容。写入进程退出后，新进程重新打开同一状态并组成输入；它不读取用户实际 Memory，也不调用模型。

运行环境需与编译产物和原生依赖匹配。若进程未能启动，或尚未取得状态根的使用资格，失败发生在 Memory 操作之前，不能据此判断保存或事务行为。

Local 与 Atomic 的实验调用链

两组实验各自有完整消费者：Local 路线读取后组成输入，Atomic 路线重开后查询事务与回执。两条路径没有画出模型调用，也没有把 Atomic 接到 Local composer。

Local 部分使用真实 root lease（对该状态根的独占写入资格）、policy Store、Memory coordinator 与 composer；为了隔离本题，可用 Skill 方法目录（inventory）与工具集合均设为空，workspace instructions 关闭。Skill 的加载机制将在第23章展开。Atomic 部分直接调用低层 Store 的 failpoint，测试事务本身；它不运行模型提取器，也不绕此接口宣称生产权限已验证。

写入、事务与重读怎样解释结果

该案例的 10 项检查均通过，真实调用了 Maka 存储与组装组件，没有调用模型或 provider。下面的调用顺序解释了表中结果为何不同。

三个调用窗口分别负责写入、事务与重读：

  1. memory-coordinator.ts::#commitSemantic/readPromptProjection：写入用 revision CAS；读关闭在 bundle read 前返回。interactive-run-composer.ts::readPromptState/resolveSystemPrompt 则把 body 放进输入，并按 Session/Turn 缓存。
  2. sqlite-long-term-memory-store.ts::commitExtraction：BEGIN IMMEDIATE 开启事务，after_cursor_write 位于 cursor 写入后，随后写 operation/receipt 并 COMMIT；after_commit 已在提交之后。因此两侧抛错会留下不同持久结果，统一 catch 中的 rollback 不能撤销已经提交的事务。
  3. 同文件 readItem/searchByKeys/#readSnapshot：重开的读侧查询真实数据库，不依赖写进程中的对象。composer 没有调用 Atomic 查询来组成输入，因此 Store 查询成功仍不等于自动召回。

这里的关键反例是：commit 后抛错或进程死掉，调用者没收到成功，却不能推出数据库没有提交。 重试应携带原 operation identity，先识别 receipt；另造新 identity 会丢失这层幂等关系。实验中的固定 key/用户文本是明确输入，不是模型实际抽取的成果。

实现问题解析

  • 文件已更新而同 Turn prompt 不变，是持久化失败吗？不是；先检查是否命中了同一 Session/Turn 的 composer 缓存。新 Turn 能读到新增内容才是这个实验的下一步观察。
  • COMMIT 前后两个故障都使调用失败，为什么数据库结果相反？前者仍可整体回滚，后者已提交，只是结果未交到调用者；重开与 receipt 才能区分。
  • memory.sqlite 有 Item 且 key query 命中，为什么没有进入 prompt？这证明了 Store 查询；当前 composer 只接 Local Memory，不能自动补出缺失的 Atomic recall caller。
  • 这 10 项能证明模型会遵守偏好吗？不能；它们覆盖存储与输入组成，没有模型输出。还需固定当前请求、读取条件与验收标准，观察实际回答。
