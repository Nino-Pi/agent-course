第 21 章｜记忆（Memory）的保存、回读（Readback）与提交（Commit）边界

本章概览

核心问题：保存偏好、关闭读取和事务提交（Commit）后崩溃，会怎样改变新进程能够取得的状态与输入？

关键概念：作用域（Scope）决定背景选择；组装器（Composer）准备模型输入（Model Input）；版本（Revision）识别更新依据；事务提交（Commit）决定修改是否生效；回执（Receipt）帮助查回同一操作的结果。

关系主线：先用固定程序追踪文件保存与范围选择，再用Maka组件对照缓存（Cache）、提交（Commit）前回滚（Rollback）和提交（Commit）后重放（Replay）。关闭读取不删除文件，丢失回复不撤销提交（Commit）；这些实验没有调用模型（Model），使用效果仍需另行观察。

前情回顾：第20章的四个环节，分别怎样取得证据？

第20章把长期信息的使用拆成保存、取回、组装输入与实际采用。文件中有一条偏好，只回答第一件事；本次请求是否读取它、模型（Model）是否按它回答，仍有各自的消费者（Consumer）和观察依据。本章继续用“解释结果时采用什么语言”检验前面的关系。

这里有两项已经执行过的实验。第一项是Python标准库程序，每个动作启动一个新进程；第二项调用真实Maka存储与组装组件。两项都没有调用模型（Model）。 输出中的背景和提示词（Prompt）只能说明准备了什么，不能直接当作回答。

固定程序：新进程怎样选出正确背景？

输入与选择规则先于实现

旧会话（Session）先保存“解释用中文”，随后增加“工作区（Workspace）A用英文，其他工作区（Workspace）继续中文”。新请求始终是“解释 formatDuration 的测试结果。”，没有再次写入语言偏好。

用 ggg 表示全局语言，OOO 表示工作区（Workspace）例外映射，WWW 表示本次工作区（Workspace）。只在允许读取并成功取得文件后，正常选择器按下面的规则返回语言 ℓ(W)\ell(W)ℓ(W)：

ℓ(W)={O[W],W∈dom⁡(O),g,W∉dom⁡(O).\ell(W)= \begin{cases} O[W], & W\in\operatorname{dom}(O),\\ g, & W\notin\operatorname{dom}(O). \end{cases}ℓ(W)={O[W],g,​W∈dom(O),W∈/dom(O).​

dom⁡(O)\operatorname{dom}(O)dom(O) 是映射中已有例外的名称集合。本例先有 g=zhg=\text{zh}g=zh、空映射，后来增加 O[A]=enO[\text{A}]=\text{en}O[A]=en。因此A选英文，B回落到中文。关闭读取时不计算这项选择，而是直接返回空背景；“空背景”也不表示偏好被删除。

这是一项明确的教学规则，并非Maka本地记忆笔记（Local Memory）的作用域（Scope）复刻。第20章已经说明，Maka工作区作用域（Workspace Scope）不会仅凭当前项目目录自动过滤。

保存分支：补充例外，保留全局值

完整程序的核心处理函数名为 worker。它接收动作、文件路径、工作区（Workspace）和读取开关。先看同一函数的两个保存分支：save-global建立初态，save-override读回文件后只添加指定工作区（Workspace）的英文例外。

def worker(action: str, store: Path, workspace: str, read_enabled: bool) -> dict:
    if action == 'save-global':
        # 首次保存：全局中文，尚无工作区（Workspace）例外。
        data = {'global': 'zh', 'workspaces': {}}
        store.write_text(json.dumps(data, ensure_ascii=False, indent=2) + '\n')
        return {'pid': os.getpid(), 'action': action, 'saved': data}
    if action == 'save-override':
        # 先回读已有状态，只补充当前工作区（Workspace）的例外。
        data = json.loads(store.read_text())
        data['workspaces'][workspace] = 'en'
        store.write_text(json.dumps(data, ensure_ascii=False, indent=2) + '\n')
        return {'pid': os.getpid(), 'action': action, 'saved': data}

data是该进程内的字典，write_text才把它写进文件。第二个分支保留已有的 global和其他映射，不把A的例外改写为全局英文。pid是进程标识符（Process Identifier，PID），用于把结果与本次进程联系起来；它不是永久不重复的工作身份。

代码中的 en是固定实验输入。这个保存分支尚未接受任意语言参数，所以后面讨论日文时，不能只换工作区（Workspace）名称就宣称完成了功能迁移。

读取分支：关闭读取时连文件也不读

下面接着同一个 worker函数，缩进仍属于函数内部。它先检查读取开关，再读取文件。read-global-only是故意忽略例外的错误读取器，用于负向对照（Negative Control）；正常读取采用前面的选择规则。

    if not read_enabled:
        # 读取开关在文件读取之前判断；文件仍保留。
        # No store read is needed for this branch. The file still exists.
        return {'pid': os.getpid(), 'action': action, 'workspace': workspace,
                'current_request': REQUEST, 'background': [], 'store_read': False}
    data = json.loads(store.read_text())
    # 正常路径先选工作区（Workspace）例外；错误路径故意只选全局。
    # The deliberately broken variant ignores the workspace exception.
    language = (data['global'] if action == 'read-global-only'
                else data['workspaces'].get(workspace, data['global']))
    return {'pid': os.getpid(), 'action': action, 'workspace': workspace,
            'current_request': REQUEST, 'store_read': True,
            'background': [{'kind': 'explanation-language', 'value': language,
                            'source': 'saved-preference', 'authority': 'background'}]}

这里的关键顺序有两点。第一，关闭读取会在 store.read_text()之前返回，结果同时写明 background=[]与 store_read=False。第二，正常读取中的 .get(workspace, data['global'])先查例外，找不到才用全局值；错误读取器则绕过这项判断。

background包含偏好的值、来源及 authority='background'。这个标记表达程序把它当背景材料，不是赋予文件或命令权限（Permission）的安全机制。输出只是JavaScript对象表示法（JavaScript Object Notation，JSON）数据，没有生成任何语言回答。

为什么这不是同一个字典被反复读取？

父程序通过下面的 child函数逐次启动子进程（Child Process），等它退出后才进入下一步。传给子进程（Child Process）的是文件路径和参数，不是前一个 data字典。

def child(action: str, store: Path, workspace: str = 'A', enabled: bool = True) -> dict:
    command = [sys.executable, str(Path(__file__).resolve()), '--worker', action,
               '--store', str(store), '--workspace', workspace]
    if not enabled:
        command.append('--read-disabled')
    # 每次另启子进程（Child Process），等待成功结束后才解析输出。
    completed = subprocess.run(command, check=True, capture_output=True, text=True, timeout=15)
    return json.loads(completed.stdout)

sys.executable使用当前Python解释器；subprocess.run启动脚本的工作分支、等待完成并捕获输出。check=True使异常退出不能悄悄成为正常结果，json.loads再解析子进程（Child Process）输出。这解释了为什么新读取进程必须依靠文件恢复信息。

以上三段来自实际固定程序的核心函数，保存与读取两段合起来是完整 worker。命令行接口（Command-Line Interface，CLI）、输出路径检查和主入口在完整脚本中；片段本身依赖这些定义和导入，不能单独运行。

Maka组件：先区分读取链与事务（Transaction）链

第二项实验在独立测试（Test）状态根（State Root）中保存明确给定的内容。写入进程退出后，新进程重新取得同根使用资格并回读（Readback）。它使用当时构建的Maka模块，不读取用户日常记忆（Memory），也不调用模型（Model）。

本地记忆笔记（Local Memory）使用 MEMORY.md与 PENDING.md文件组（Bundle）；条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）使用独立数据库。下图中的两条路径各有消费者（Consumer），并没有把数据库查询接到本地组装器（Composer）。

本地记忆笔记（Local Memory）分支使用真实根租约（Root Lease）、策略存储（Policy Store）、记忆协调器（Memory Coordinator）和组装器（Composer）。根租约（Root Lease）在这里提供该状态根（State Root）的独占写入资格。为隔离本题，技能说明包（Skill）目录清单（Inventory）和工具（Tool）集合为空，工作区指令（Workspace Instructions）关闭；第23章再展开技能说明包（Skill）的装载。

条目化长期记忆（Atomic LTM）分支直接调用低层存储（Store）的故障注入点（Failpoint），检验事务（Transaction），没有运行模型（Model）提取器，也不能据此声称生产权限（Permission）已验证。若环境或原生依赖导致进程无法启动，或尚未取得根租约（Root Lease），失败发生在记忆（Memory）操作之前。

文件已经新增，为什么本轮提示词（Prompt）仍不变？

实验先让组装器（Composer）为同一会话（Session）的 turn-1捕获正文，之后再保存一个带 M_AFTER_CAPTURE标记的新偏好。下面是探针对缓存（Cache）的完整局部分支；mutate负责显式保存，promptContext中已有会话（Session）、工作轮次（Turn）与目录。

    if (action === 'local-cache') {
      // 文件先保存；随后分别观察同一工作轮次（Turn）和新工作轮次（Turn）。
      await mutate(ADDED, { kind: 'workspace' });
      const same = await composer.resolveSystemPrompt(promptContext);
      const next = await composer.resolveSystemPrompt({ ...promptContext, turnId: 'turn-2' });
      await writeFile(join(output, 'local-next-turn.prompt.txt'), next.text ?? '');
      return { sameTurnContainsAdded: (same.text ?? '').includes(ADDED), nextTurnContainsAdded: (next.text ?? '').includes(ADDED), hasAtomic: (next.text ?? '').includes(ATOMIC) };
    }

先调用 mutate再重新解析同一个 promptContext，得到的 same仍是已捕获材料；只把 turnId改成 turn-2后，next才重新采集。原结果为 sameTurnContainsAdded=false、nextTurnContainsAdded=true。

这不是持久化（Persistence）失败。文件已保存，变化发生在输入何时重新采集；同一工作轮次（Turn）的缓存（Cache）不会追溯改写已发出的请求。输出是实际组装器（Composer）的提示词（Prompt）。探针没有调用模型协议适配器（Model Adapter），所以这还不是提供方协议请求（Provider Wire Request），更不是模型（Model）回答。原实验停在这里。

事务提交（Commit）前后：相同失败表象，不同持久结果

条目化长期记忆（Atomic LTM）实验提交明确构造的条目（Memory Item），并一起推进游标（Cursor）、保存回执（Receipt）。游标（Cursor）说明已覆盖范围，回执（Receipt）说明该操作的结算结果；三者需要在同一事务（Transaction）中决定，防止重复提取或漏存。

探针固定操作身份（Operation Identity）为 lab-extraction，预期游标（Expected Cursor）为0，提交（Commit）后游标（Cursor）为1。条目（Memory Item）文本、来源和检索键（Retrieval Key）均由程序给定；它们不是模型（Model）真实提取出的成果。

先看存储实现中的顺序：BEGIN IMMEDIATE开始写事务（Transaction），检查已有回执（Receipt）与预期游标（Expected Cursor），写入条目（Memory Item）和游标（Cursor），再写操作与回执（Receipt），最后 COMMIT。探针在两个既有位置制造故障：

  const store = new SqliteMemoryItemStore(databasePath, { now: () => 1000, idFactory: () => 'atomic-item',
    // 两处故障注入点（Failpoint）跨在事务提交（Commit）两侧。
    failpoint(point) {
      if (action === 'atomic-before-commit' && point === 'after_cursor_write') throw new Error('LAB_BEFORE_COMMIT');
      if (action === 'atomic-after-commit-kill' && point === 'after_commit') {
        writeFileSync(join(output, 'atomic-kill-boundary.json'), JSON.stringify({ point, pid: process.pid }));
        process.kill(process.pid, 'SIGKILL');
      }
    } });

这段为已选定的 databasePath建立存储（Store），固定时间与条目（Memory Item）名称，再提供故障注入点（Failpoint）回调。提交（Commit）前试验使用单独的回滚（Rollback）数据库，提交（Commit）后试验使用测试（Test）状态根（State Root）中的数据库；两者不会互相承接未提交（Commit）的状态。after_cursor_write位于事务提交（Commit）之前；after_commit已经在提交（Commit）之后。后者通过 SIGKILL硬终止（Hard Termination）子进程（Child Process），令它来不及返回成功。

若故障回调抛出普通异常，存储方法的异常处理（Exception Handling）会尝试回滚（Rollback）；本例的 SIGKILL直接终止进程，不会继续执行该处理。无论如何，回滚（Rollback）都不能撤销已经完成的事务提交（Commit）。因此“调用方（Caller）没收到成功”只描述回复路径，无法单独确定数据库结果。

重开与同一操作重放（Operation Replay）怎样消除歧义？

新进程重新打开数据库后，先读条目（Memory Item）、游标（Cursor）和回执（Receipt），再提交相同的固定请求。下面的 extractionRequest()每次返回相同内容，绝不只是复用名称却换了参数。

    // 重开后查询数据库中的三份状态，不依赖旧进程对象。
    const item = await store.readItem('atomic-item');
    const cursor = await store.readExtractionCursor('atomic-session');
    const receipt = await store.readExtractionReceipt('lab-extraction');
    if (action === 'atomic-read-rollback') return { itemMissing: !item, cursorMissing: !cursor, receiptMissing: !receipt };
    // 只有提交后分支继续重放（Replay）；请求内容仍由同一函数产生。
    const replay = await store.commitExtraction(extractionRequest());
    return { hasItem: item?.item.content === ATOMIC, cursor: cursor?.processedOrdinal, hasReceipt: Boolean(receipt),
      replayed: replay.replayed, matchCount: (await store.searchByKeys({ terms: ['atomic-lab'], match: 'exact' })).length };

提交（Commit）前故障对应三个缺席标记均为 true。提交（Commit）后故障对应 hasItem=true、cursor=1、hasReceipt=true；相同请求返回 replayed=true，按固定键查询得到 matchCount=1。存储会检查操作身份（Operation Identity）与请求内容是否匹配，不能把同一身份用来提交另一份修改。

这里的幂等（Idempotency）来自查回同一决定。另造一个操作身份（Operation Identity）会失去这层关联，不能因为上次没有返回就盲目重做。回执（Receipt）并不证明偏好内容有用，只帮助确定该次事务（Transaction）发生了什么。

十项检查的整体边界

Maka原实验返回 PASS，十项检查全部通过：旧版本（Revision）拒绝、跨进程留存、会话作用域（Session Scope）、关闭读取保留字节、不可信提示块（Untrusted Block）、同轮缓存（Cache）、提交（Commit）前回滚（Rollback）、提交（Commit）后留存、同请求重放（Replay）一次、条目化长期记忆（Atomic LTM）未进入本地输入。

最后一项把同一状态根（State Root）中的数据库与本地提示词（Prompt）并排检查：数据库确有 ATOMIC常量指定的标记，本地组装结果没有。readItem或 searchByKeys成功，只证明存储查询；本地组装器（Composer）没有调用这条查询链，不能自动补出尚未接通的召回（Recall）消费者（Consumer）。

这些代码摘自完整Maka探针，局部变量、模块导入和启动条件由整份脚本提供；它们不是可单独提交给生产接口（Interface）的程序。十项Maka组件检查与前面的七项Python检查必须分别解释，不能相加后称“十七项Maka测试（Test）”。

从观察结果（Observation）走到结论

问题1。 文件已更新而同一工作轮次（Turn）提示词（Prompt）不变，是保存失败吗？

参考答案。 先区分文件状态和输入采集。该例已经保存成功，但组装器（Composer）命中同一会话（Session）/工作轮次（Turn）的缓存（Cache）；新工作轮次（Turn）取得新内容，才是对应的下一项观察。

问题2。 事务提交（Commit）前后两个故障都使调用失败，为什么数据库结果相反？

参考答案。 前者尚未提交（Commit），未提交（Commit）的修改可共同回滚（Rollback）；后者已经提交（Commit），只是回复没有到达调用方（Caller）。重开数据库并核对回执（Receipt）才能区分，外层退出码（Exit Code）不能替代它们。

问题3。 数据库有条目（Memory Item）且按键查询命中，为什么没进入提示词（Prompt）？

参考答案。 数据库提供查询能力，本次组装器（Composer）却只消费本地记忆笔记（Local Memory）。保存、查询、请求消费是不同阶段，打开本地读取开关也不会创建条目化长期记忆（Atomic LTM）的召回（Recall）调用链。

问题4。 这些结果能证明模型（Model）遵守偏好吗？

参考答案。 不能。两项实验均没有模型（Model）输出。第22章另以相同保存条目、不同读取条件的新会话（Session）观察实际请求和回答；那是另一组已有真实运行，不能拼成这里的一次执行（Run）。
