第 02 章｜代理循环（Agent Loop）的执行过程

本章概览

核心问题：上一轮的执行结果怎样进入下一轮判断？循环为何会继续，又凭什么停下？

关键概念：代理循环（Agent Loop）连接决策与执行；单步推进（Step）完成一次查询与动作批次（Action Batch）；消息列表（Message List）保存当前输入；观察消息（Observation Message）是承载观察结果（Observation）、供后续调用读取的消息（Message）。

关系主线：先跟随同一项文档修复，观察材料怎样增长，再映射到 run、step、query 与 execute_actions，最后解释预算（Budget）、批次中断与保存边界。

前情回顾

第01章区分了模型（Model）、运行支撑（Agent Harness）和执行环境（Environment）：前者依据当前材料提出下一步，中间一层组织输入并控制执行，后者承接对文件与进程的实际操作。行动请求（Action）表达意图；观察结果（Observation）是执行后取得的材料。只有这些材料进入后续输入，下一次判断才有机会使用它们。

本章沿用同一项任务（Task）：只把 README 中错误的测试入口修正为 npm test，检查并交付；项目代码假设正常。前章已经讲清 npm test → scripts.test → node --test 的配置消费关系，这里把注意力移到本轮结果在哪一步成为下一轮依据。四步过程及简化消息（Message）均为教学示意；涉及真实函数修复的历史片段会另行交代。

一次结果怎样进入下一轮代理循环（Agent Loop）

设想刚收到要求时，模型（Model）还没读到两份文件。它可以提出读取请求，却不能只凭请求内容知道磁盘上的真实配置。执行环境（Environment）返回文件内容以后，运行支撑（Agent Harness）还要把它组织为观察消息（Observation Message），加入消息列表（Message List）。第二次调用才会带上这个新增依据。

这说明代理循环（Agent Loop）连接的并非几个函数名，而是三次变化：提出请求、取得执行结果、改变下一次输入。 默认实现的正常路径如下：

图中，query 取得并追加模型消息（Model Message），execute_actions 执行整批行动请求（Action），整批返回后才追加观察消息（Observation Message）。回边指向下一次单步推进（Step），不会重新初始化消息列表（Message List）。这里展示直接使用 DefaultAgent 的正常路径；普通回答文案不是它的退出信号，完成标记、限制或异常会转入相应结束分支。

用同一项任务（Task）追踪四次单步推进（Step）

开始时只有规则与用户要求。下面假定每个正常步骤都有一个行动请求（Action），执行后形成一条观察消息（Observation Message）；这使我们可以先看懂材料增长，再讨论多次调用和中断。

表 1 / Table 1 · 用同一项任务（Task）追踪四次单步推进（Step）
阶段本次模型调用（Model Query）得到什么依据行动请求（Action）观察结果（Observation）怎样影响后续

测试（Test）修改已经尝试，但还没有测试结论执行 npm test本例给定结果为测试通过，退出码（Exit Code）为0
提交（Submit）已有改动与检查结果发出规定的完成标记执行层产生提交信号（Submission Signal），外层处理退出

在前三个正常步骤中，每次都是“已有材料 → 新请求 → 执行结果 → 更多材料”。修改执行返回正常，并不单独证明文档改对；后续读取与差异检查仍有意义。这里没有训练模型参数（Model Parameters），变化的是本次输入。新材料也可能重复、失败或不完整，因此增加消息（Message）不保证判断进步。

默认课程配置用一条特殊 Bash 命令表达完成：

echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT

LocalEnvironment 识别成功输出的第一行后抛出 Submitted，外层将这个提交信号（Submission Signal）转为退出消息（Exit Message）。因此，第四步不同于前三步的普通返回，不能机械地把它也计成一条普通观察消息（Observation Message）。默认命令行入口还会用 InteractiveAgent 增加交互层，询问是否追加工作；第05章解释具体交互。

本例的四步是教学顺序，不是实际执行轨迹（Trajectory）。第04章会增加函数修复并先运行出失败测试；后面本章另给一段历史真实记录，用来说明相同的输入更新关系。

先看正常路径的伪代码（Pseudocode）

下面要解决的问题很具体：怎样让本轮执行结果进入后续调用？先忽略模板、成本、异常与保存，只保留这个顺序。伪代码（Pseudocode）的输入是任务（Task），核心状态（State）是消息列表（Message List）；它没有完整实现退出消息（Exit Message）的产生，也不是可独立运行的程序。

阅读时，def 定义函数（Function），调用后才执行其中内容；= 把右侧结果交给左侧名字，while 按条件重复。append 加入一项，extend 依次加入另一个列表（List）中的各项。代码里的列表推导（List Comprehension）会依次处理行动请求（Action），先收齐整批输出（Output），然后才统一追加。

def run(task):
    # 输入组织（Input Composition）：先放规则与任务（Task），后续复用。
    messages = [system_message, user_message(task)]

    while last_message_is_not_exit(messages):
        # 模型调用（Model Query）：先记录意图，此时还未执行行动请求（Action）。
        assistant_message = model.query(messages)
        messages.append(assistant_message)

        # 动作批次（Action Batch）：先收齐整批输出（Output），再整理观察消息（Observation Message）。
        outputs = [environment.execute(action)
                   for action in assistant_message.actions]
        messages.extend(observations(outputs))

最后两行故意分开：outputs 是执行层返回的数据；observations(outputs) 把它们整理为观察消息（Observation Message），extend 才使其进入下一次输入。执行返回、格式转换、输入更新是三个相连但不同的动作。 如果收集整批结果时被中断，就可能还没有走到最后一行；后面的批次分析将解释这个后果。

从阅读 Python 到理解控制接口（Control Interface）

现在已经知道循环要连接什么，再看 DefaultAgent 的四个入口：run(task) 建立与结束整次工作；step() 推进一步；query() 请求模型（Model）；execute_actions() 执行并整理结果。先补齐读懂这些片段所需的最少语法，然后逐个解释它们的输入、变化与返回。

Python 最小阅读卡

对象（Object）可以保存数据并提供操作；按一个类（Class）创建出的具体对象叫实例（Instance）。这里 self 指当前 DefaultAgent 实例（Instance）。点号读取其属性（Attribute），方法（Method）则是通过这个对象调用的操作。

本章写法怎样读空值或缺失时怎样
self.messages当前实例（Instance）的消息列表（Message List）可以存在但没有任何一项，即 []
messages[0]、messages[-1]列表（List）从0编号；负索引（Negative Index）-1 取最后一项空列表（List）读取末项会抛出 IndexError，不是返回空消息（Message）

下面三行摘自真实 run() 的末尾。此前已经建立非空消息列表（Message List），并尝试推进一步；if 与 break 仍在循环中，最后的 return 位于循环之后。缩进表达这些层级，== 比较是否相等：

    if self.messages[-1].get("role") == "exit":
        break
return self.messages[-1].get("extra", {})

可以按“读什么—改变什么—返回什么”理解这段源码摘录（Source Excerpt）：

  1. 先读取最后一条消息（Message）的角色（Role）。若末项是 {"role": "exit", "extra": {"exit_status": "Submitted"}}，比较结果为真。
  2. break 只结束所在循环，不追加消息（Message）或改写字典（Dictionary）。若缺少 role，.get 返回 None，比较不成立；若整个列表（List）为空，则更早就会在 [-1] 处报错。
  3. 离开循环后，return 将 extra 交回调用者，上例得到 {"exit_status": "Submitted"}；缺少该键（Key）时得到 {}。返回内容说明停止原因，不能只凭“循环结束”认定成功。

赋值（Assignment）与比较（Comparison）也要分开：self.messages = [] 让当前实例（Instance）改用新建的空列表（List），== 则只进行相等判断，不重新赋值。

run(task)：怎样建立一次运行（Run）？

任务（Task）先进入消息模板（Message Template）

run(task) 不把 Python 变量 task 原封不动交给服务，而是先组织输入。消息模板（Message Template）可以理解为预留内容位置的文本；实现通过 extra_template_vars 将任务（Task）与其他参数（Argument）提供给两个模板。

其中，instance_template 把要求组织成用户消息（User Message）。本例可以简化为以下内容；这是教学表示，不是完整协议或真实调用日志：

system: 你是一个能通过 Bash 与电脑交互的助手……
user:   请解决这个任务：检查 package.json 和 README.md……

这里的执行器（Executor）把命令（Command）交给命令解释器（Shell）；Bash 是其中一种。模型（Model）看到的工具协议（Tool Protocol）名称也叫 bash，但实际启动哪种命令解释器（Shell）由实现决定，不能凭这个名字断言使用 /bin/bash。第03章进一步区分协议名、命令参数（Command Argument）与实际执行程序。

消息列表（Message List）在每次 run() 开始时重建

初始化包含一行：

self.messages = []

随后加入系统消息（System Message）与用户消息（User Message）。因此，最小路径中第一次模型调用（Model Query）前的材料是：

表 3 / Table 3 · 消息列表（Message List）在每次 `run()` 开始时重建
位置角色（Role）主要内容
messages[0]系统（system）行动规则、命令格式、执行环境（Environment）说明
messages[1]用户（user）当前任务（Task）

这两项是决策输入，不是执行记录。重建输入也不自动重置整个实例（Instance）的所有状态（State）；预算（Budget）小节会解释为什么第二次调用 run() 仍可能沿用旧计数。

外层循环（Outer Loop）怎样决定继续与退出？

初始化之后，run() 进入 while True，每轮尝试调用一次 step()，然后检查：

if self.messages[-1].get("role") == "exit":
    break

最后一条是退出消息（Exit Message），就结束；否则继续下一次单步推进（Step）。开头的文档案例可能四次模型调用（Model Query）就完成，也可能因失败而需要更多次，任务（Task）描述不预先决定精确步数。

循环结束后，run() 返回末条退出消息（Exit Message）的 extra。其中通常包含 exit_status、submission，也可能含错误信息。它是本次运行（Run）的退出摘要（Exit Summary），不是完整执行记录（Execution Record）库；未处理异常还可能继续向调用者抛出。

step()：怎样连接一次查询与动作批次（Action Batch）？

真实的单步推进（Step）实现很短。返回类型注解（Return Type Annotation）-> list[dict] 表示预期返回字典（Dictionary）组成的列表（List），但不单独检查运行时数据：

def step(self) -> list[dict]:
    return self.execute_actions(self.query())

从内向外读：先调用 query()，得到模型消息（Model Message），再将其交给 execute_actions()，最后返回新增加的观察消息（Observation Message）。这行代码连接两个阶段，真正的执行细节在被调用的方法（Method）中。

正常路径中的一次单步推进（Step）对应一次模型调用（Model Query），但不等于一项完整任务（Task）。读取、修改、测试与提交可能分别占用一次，也可能采用别的组合。

一个工具类型（Tool Type），为什么还能有多次工具调用（Tool Call）？

execute_actions() 遍历模型消息（Model Message）的 extra.actions 列表（List），所以同一响应可以包含多个行动请求（Action），按顺序交给执行环境（Environment）。默认 LitellmModel 只暴露名为 bash 的一个工具类型（Tool Type），不代表只允许一个工具调用（Tool Call）。

这两个计数回答不同的问题：类型数说明“可选择哪些能力”，调用数说明“这次提出了几次执行请求”。文本变体对行动请求（Action）数量另有格式约束，第03章会单独说明。

query()：模型调用（Model Query）前后改变了什么？

在请求之前先检查限制，通过后增加调用计数；取得可用模型消息（Model Message）后，更新成本并追加内容。这里统计的是模型调用（Model Query），与执行命令（Command）的次数不同。

模型协议适配器（Model Adapter）如何处理协议（Protocol）？

model.query(self.messages) 接收当前消息列表（Message List）。模型协议适配器（Model Adapter）负责将它转换成模型服务提供方（Provider）接受的格式，调用服务，再把返回响应、行动请求（Action）、成本与时间整理为统一结果。

DefaultAgent 因而不需要在主循环里处理每家服务的所有响应格式，而是依赖模型（Model）接口（Interface）提供统一可消费的消息（Message）。这种分工只说明接线方式，不能免除适配器自己的解析与检查。

追加模型消息（Model Message）为何还不等于执行？

取得结果并更新成本后，query() 调用：

self.add_messages(message)

本例第一次查询后的简化状态（State）是：

execute_actions(message)：原始输出（Output）怎样变成观察消息（Observation Message）？

该方法（Method）先对每个行动请求（Action）调用 self.env.execute(action)，收集输出（Output），再让模型协议适配器（Model Adapter）格式化，并追加到消息列表（Message List）。下面跟随一条实际格式的教学请求，逐层看数据变化。

从命令参数（Command Argument）取得原始输出（Output）

假设第一个行动请求（Action）如下。sed 按文本规则读取文件，-n 关闭默认输出，1,220p 只打印第1–220行。这个命令（Command）将两份文件按顺序连接成连续行号，并非各取220行。 本例假设合计不足220行，因此都能读到。

{
  "command": "sed -n '1,220p' package.json README.md",
  "tool_call_id": "call-1"
}

执行环境（Environment）返回下列形状的结果；其中正文省略号是教学占位，不是本章新增的实际读取日志：

{
  "output": "...真实文件内容...",
  "returncode": 0,
  "exception_info": ""
}

output 承载文本，returncode 是退出码（Exit Code），exception_info 提供异常信息。它们仍是执行层的数据，尚未自动成为服务能够接收的工具结果消息（Tool Result Message）。

格式转换为什么交给模型协议适配器（Model Adapter）？

主循环知道“这些输出（Output）来自刚才那批行动请求（Action）”，但不同模型服务提供方（Provider）要求的工具结果消息（Tool Result Message）格式可能不同。模型协议适配器（Model Adapter）因此负责表达方式，完成后 add_messages() 再把观察消息（Observation Message）追加进去。

消息（Message）与执行顺序问答

问题 1。 第一次模型调用（Model Query）前有哪些材料？正常一步后增加什么？

解释。 最初是系统消息（System Message）与由任务（Task）渲染的用户消息（User Message）；正常一步增加模型消息（Model Message）及对应观察消息（Observation Message）。多个行动请求（Action）或批次中断会改变条数。

问题 2。 行动请求（Action）已经在消息列表（Message List）里，为什么文件还可能没被读取？

解释。 query() 先把意图加入进程内存（Process Memory），execute_actions() 随后才调用执行环境（Environment）。追加还不等于写入磁盘，请求存在也不证明现实操作已经发生。

问题 3。 下次调用怎样得知测试失败？模型参数（Model Parameters）是否因此被训练更新？

解释。 主循环将失败输出（Output）整理为观察消息（Observation Message），再交给后续模型调用（Model Query）。这条路径改变的是输入，没有进行参数训练。

预算（Budget）、动作批次（Action Batch）与执行记录（Execution Record）

正常路径说明“怎样继续”，还需弄清“何时停止”和“中断后留下了什么”。以下沿用同一实现，不把交互变体、普通异常与硬终止混在一起。

模型调用（Model Query）前的限制检查

真正请求服务之前，程序检查步数上限（Step Limit）、成本上限（Cost Limit）和总耗时上限（Wall-Time Limit）。达到配置条件时，通过控制流异常（Control-Flow Exception）产生退出消息（Exit Message），不继续发起下一次请求。

通过检查以后，调用计数才增加：

self.n_calls += 1

这个计数对应模型调用（Model Query），不等于命令（Command）执行次数，也不等于任务（Task）数量。一条响应若有两个行动请求（Action），n_calls 增加1，env.execute() 却可能被调用2次；若格式无效或批次中断，实际执行次数还会不同。计数口径决定了预算（Budget）限制的对象。

重建消息列表（Message List），为什么没有得到新预算（Budget）？

n_calls、cost 与 _start_time 在实例（Instance）构造时初始化，run() 不重置它们，也不会替模型（Model）重置自己的游标。因此，复用同一实例（Instance）第二次调用 run()，虽然输入重新开始，却不获得全新的预算（Budget）。本课程已有实验为每次运行（Run）创建新对象（Object），分别初始化消息列表（Message List）、计数和时钟。

这一区分来自状态（State）的归属：一部分在“本次开始”时重建，另一部分在“对象创建”时才建立。不能只看到 messages = [] 就推断所有计数都归零。

动作批次（Action Batch）中断，前面的结果去了哪里？

考虑同一响应中的三个行动请求（Action），顺序为 echo FIRST、完成标记、echo THIRD。使用 DefaultAgent 时，第一条实际执行；第二条触发 Submitted；第三条没有执行。但 execute_actions() 使用列表推导（List Comprehension）收齐整批输出（Output）后才格式化，第二条的提交信号（Submission Signal）打断了收集，所以第一条也尚未作为观察消息（Observation Message）追加。

按“现实执行”和“已追加材料”两条线读，就不会混淆：

按序执行，不等于每条结果立即进入输入。 这是前面伪代码（Pseudocode）将收集与追加分开写的实际含义。

InteractiveAgent.execute_actions() 采用另一条路径：逐条积累输出（Output），并在 finally 中格式化已有结果。工具调用格式化器（Tool-Call Formatter）为缺少结果的位置补 returncode=-1 / action was not executed。因此第一条真实返回可以保留，完成命令（Command）与未执行的第三条却都可能显示占位结果（Placeholder Result）。

第二条实际上执行过；这里的占位结果（Placeholder Result）表达的是“没有普通返回可交给格式化器”，不能据文字断言现实中没有运行。不同实现的保存范围需要分别核对，提交信号（Submission Signal）的具体异常路径见第05章。

消息（Message）增长为什么不等于持久记忆（Persistent Memory）？

一次 DefaultAgent.run() 内，self.messages 是线性内存列表（In-Memory List）。正常步骤将行动请求（Action）及观察消息（Observation Message）加入其中，供后续模型调用（Model Query）使用；前述中断可能跳过普通结果追加。

这承担的是当前运行（Run）的工作记忆（Working Memory）：本次可用，不意味着下次自动可用。重新启动后是否载入历史需要另有读取入口，跨进程恢复（Cross-Process Recovery）与并发写入也不能由一个内存列表（In-Memory List）自动承担。

消息（Message）追加与执行轨迹（Trajectory）保存的先后关系

在 DefaultAgent 中，query 先追加模型消息（Model Message），execute_actions 收齐整批输出（Output）后才追加观察消息（Observation Message），外层本轮的 finally 再调用 save()。

若批次被 Submitted 打断，外层先处理退出信号，再保存当时状态（State）；已执行动作的普通结果可能还没加入。若进程（Process）直接收到 SIGKILL，这个 finally 也不会执行，磁盘可能只剩前一轮快照（Snapshot），文件却已经改变。

因此，执行轨迹（Trajectory）快照（Snapshot）不自动等于持久执行账本（Durable Execution Ledger）。后者必须支持恢复时核对已经发生的事，还要处理工作身份、写入权与不确定效果。第05章继续解释保存结构，第06章展示指定硬终止（Hard Termination）窗口；本章没有重新注入故障。

接口（Interface）可替换，哪些结论不能一起继承？

DefaultAgent 的主循环依赖模型（Model）与执行环境（Environment）接口（Interface），没有把特定服务或执行后端（Execution Backend）完全写死。因此可以更换模型协议适配器（Model Adapter），选择本地、Docker、Singularity 等执行环境（Environment），或采用 InteractiveAgent 增加交互。

相似的调用形状仍能连接查询、执行与观察消息（Observation Message），但它不证明这些实现拥有相同安全隔离（Isolation）、持久化（Persistence）与恢复（Recovery）保证。刚才两个批次路径就是具体反例：外表都“执行一批请求”，结果追加时点却不同。

调用、批次与对象状态（Object State）问答

问题 1。 模型调用（Model Query）次数与命令（Command）执行次数为什么不相等？

解释。 一条响应可带多个行动请求（Action），格式错误（Format Error）也可能没有可执行请求；提交信号（Submission Signal）或其他错误还会使动作批次（Action Batch）提前停止。

问题 2。 第一条正常返回、第二条抛出 Submitted，DefaultAgent 会追加第一条观察消息（Observation Message）吗？

解释。 不会由 execute_actions() 追加。列表推导（List Comprehension）在统一格式化和 add_messages() 之前被打断；外层保存的是当时状态（State）。InteractiveAgent 在 finally 中整理已有结果，路径不同。

问题 3。 同一实例（Instance）再次调用 run()，输入重新开始是否表示预算（Budget）归零？

解释。 不表示。n_calls、cost 和构造时钟未在该入口重置，模型（Model）也有自己的状态（State）。已有课程实验每次创建新对象（Object），不能把其独立计数无条件推广到复用情境。
