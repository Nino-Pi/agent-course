第 02 章｜Agent Loop 的执行过程

本章概览

核心问题：一次请求怎样经过多轮模型与命令调用，并在预算、完成信号或异常出现时停下？

关键概念：run（外层循环）控制整体执行；step（单步推进）连接查询与动作批次；messages（消息列表）保存当前输入材料；observation（观察消息）表达执行结果。

关系主线：正常步骤把模型动作交给环境，再将普通结果追加到消息中；外层循环处理终止与保存。批次中断、未处理异常和硬终止会留下不同的消息与轨迹状态。

模型、执行接口与循环控制的关系见 第01章。 本章沿用其中“只修 README 测试命令”的任务：读取配置与说明、把错误入口改成 npm test、检查并交付。下面的四步和消息片段是教学示意，项目代码假设正常；涉及真实函数修复的片段会另行交代。

DefaultAgent 的执行循环

query 取得并追加模型消息，execute_actions 执行整批动作，整批返回后才把 observations 放进下一次模型输入。最外侧的回边表示下一 step，不表示重新初始化消息。这张图展示直接使用 DefaultAgent 的正常循环；普通回答文案不是退出信号，程序会根据完成信号、限制或异常转入相应结束分支。

读本章代码时，先认清“数据放在哪里”与“哪一行使程序继续或停下”。对象（Object）可以同时保存数据和提供操作；按 DefaultAgent 这个类创建的一个具体对象叫实例（Instance），本章的 self 指当前这个实例。

下面三行摘自真实 run() 的末尾。到这里，前面已经建立非空消息列表并尝试推进一步；if 和 break 仍位于循环中，最后的 return 位于循环之后。缩进表示这些层级，== 比较是否相等：

    if self.messages[-1].get("role") == "exit":
        break
return self.messages[-1].get("extra", {})
  • 读取什么？ 第一行先取当前列表的最后一条消息，再取它的 role。若最后一条是 {"role": "exit", "extra": {"exit_status": "Submitted"}}，比较结果为真。
  • 改变什么？ 这几行没有追加消息，也没有修改字典；break 只结束所在循环。若 role 缺失，.get("role") 返回 None，与 "exit" 不相等，本轮不会由这句 break 退出；若整个列表为空，取末项时就已报错，还到不了 .get。
  • 返回什么？ 离开循环后，return 把最后一条消息的 extra 交回调用者；上例得到 {"exit_status": "Submitted"}。若 extra 键缺失，得到 {}。停止原因要读返回字段，不能只凭“循环结束”认定任务成功。

下面回到正常路径。def 定义一个函数，调用函数时才执行它的内容；= 把右侧得到的值交给左侧名字或属性，区别于上面的相等比较 ==。例如 self.messages = [] 会让这个实例改用新建的空列表。

正常路径的伪代码

如果去掉模板、成本统计、异常类型和保存逻辑，DefaultAgent 的主干可以被压缩成：

下面用 Python 表达顺序。run(task) 表示将任务作为输入交给 run；messages 保存一组消息，while 表示按条件重复。[处理动作 for action in 动作列表] 叫列表推导：依次处理每项并收集成新列表。append 加入一项，extend 则依次加入另一列表里的每项；这里先收齐 outputs，随后才用 extend 将观察加入消息列表。

def run(task):
    messages = [system_message, user_message(task)]

    while last_message_is_not_exit(messages):
        assistant_message = model.query(messages)
        messages.append(assistant_message)

        outputs = [environment.execute(action)
                   for action in assistant_message.actions]
        messages.extend(observations(outputs))

这段伪代码只表示正常路径，不是逐字源码；它省略模板、异常和退出消息的产生过程，保留先收集整批 outputs、再统一追加 observations 的顺序：

模型消息产生 action
action 产生 output
output 变成 observation message
observation 进入下一次模型调用

run(task)：初始化消息并拥有外层循环

Task 先被放进模板变量

run(task) 先把任务填进模板，形成给模型的初始消息。模板可以理解为预留了任务位置的一段提示文本。实现中，Task 与其他参数通过 extra_template_vars 供两个模板使用。

这意味着模型并不是直接收到 Python 的 task 变量。中间还有一次“把任务组织成消息”的过程：

task 字符串
  ↓
instance_template
  ↓
第一条 user message

这里的执行器把命令文本交给 shell 解释；shell 是解释并运行这类命令的程序，Bash 是常见的一种。本课程片段中的 bash 也用作模型看到的工具协议名称，实际启动哪种 shell 由执行器决定，不能仅凭这个名字认定一定使用 /bin/bash。第03章会把工具名称、命令参数和实际执行器进一步分开。

固定案例最开始可以简化成：

system: 你是一个能通过 Bash 与电脑交互的助手……
user:   请解决这个任务：检查 package.json 和 README.md……

messages 在每次 run() 开始时清空

run() 会执行：

self.messages = []

然后加入 system message 与 user message。

因此，在这条最小路径中，第一次 query() 前的状态是：

这两条消息不是命令执行记录。它们只是第一次模型判断的输入。

while True 表示由退出消息结束，而不是预先知道步数

初始化完成后，run() 进入 while True。每一轮尝试调用一次 step()，最后检查：

if self.messages[-1].get("role") == "exit":
    break

也就是说，正常循环不是“固定执行四次”，而是：

继续 step
  ↓
最后一条消息是否为 exit？
  ├─ 否：继续
  └─ 是：退出

固定案例也许四个 model calls 就完成，也可能因为命令失败需要更多轮。Task 的内容并不预先决定精确步数。

run() 返回什么

循环结束后，run() 返回最后一条 exit message 的 extra 字段，通常可以包含：

  • exit_status；
  • submission；
  • 某些错误或异常信息。

它返回这次运行的退出摘要，不是完整的任务状态库。

step()：一轮“问模型，然后执行动作”

真实源码中的 step() 很短。self 是调用这个方法的当前实例；-> list[dict] 标注预期返回一个由字典组成的列表，不会单独检查运行时数据：

def step(self) -> list[dict]:
    return self.execute_actions(self.query())

这行代码可以从内向外读：

  1. 先调用 query()；
  2. 得到一条模型消息；
  3. 把模型消息交给 execute_actions()；
  4. 返回新增加的 observation messages。

一个 step 通常包含一次模型调用

在 DefaultAgent 的正常路径中，一个 step() 会调用一次 query()，所以也就对应一次 Model query。

但一个 step 不等于一个完整 Task：

Task：修正文档并测试
  ├─ step 1：读取文件
  ├─ step 2：修改 README
  ├─ step 3：运行测试
  └─ step 4：提交结果

一个模型消息可以包含多个 action

execute_actions() 遍历消息中 extra.actions 的列表。因此源码允许同一次模型消息产生多个 action，然后逐个交给 Environment。

这里要区分两个“单一”：

  • 默认 LitellmModel 只暴露一个可用工具类型：名为 bash 的 function/tool；
  • 一条模型消息在数据结构上仍可能包含多个 Bash tool calls。

所以“只有一个工具类型”不等于“每一步只能有一个调用”。文本变体对 action 数量有自己的格式约束，第03章会单独说明。

query()：检查限制、调用 Model、追加模型消息

在模型调用前先检查限制，通过后记录调用计数；取得可用模型消息后再更新成本并追加它。计数对象是模型请求；它与动作执行次数不同。

调用 model.query(self.messages)

此时当前完整 messages 被交给模型适配器（Model adapter），由它转换模型服务提供方（provider）的协议。Model adapter 负责：

  1. 把内部消息整理成 provider 接受的格式；
  2. 调用具体模型服务；
  3. 从返回中解析 action；
  4. 把原始响应、action、成本与时间等整理成一条模型消息。

DefaultAgent 不自己理解不同 provider 的所有响应格式。它只依赖 Model 接口返回统一可消费的消息。

统计成本并追加消息

Model 返回后，query() 更新本次 Agent 的成本，然后调用：

self.add_messages(message)

此时 messages 才增加 assistant message。

固定案例第一次 query 后，可以简化成：

execute_actions(message)：让请求接触现实，再形成新消息

execute_actions() 做两件事：

  1. 对每个 action 调用 self.env.execute(action)；
  2. 让 Model adapter 把 outputs 格式化成 observation messages，并追加到 messages。

第二个 step 为什么能获得更多依据

第二个 step 再次进入 query() 时，Model 收到的不再只有任务描述，还收到第一次命令的 observation。

它现在可以看到：

所以它可以生成更有依据的 action，例如请求把 README 中的过时命令替换成 npm test。

正常追加的回执会成为下一次输入的一部分，即使它只是重复旧结果或报告失败。模型参数在这里没有经过训练更新；变化的是系统交给模型的消息。

消息与执行顺序问答

问题 1。 第一次 query 前，messages 通常是哪两条？正常一步后又增加什么？

解释。 system 与由 Task 渲染的 user；正常一步增加 assistant 和对应 observation。多个 actions 或中断会改变条数。

问题 2。 为什么 assistant action 已在 messages 中时，文件仍可能没有被读取？

解释。 query 先把请求加入内存 messages，随后 execute_actions 才调用 Environment。这里的追加还不等于写入磁盘；请求存在也不证明执行已发生。

问题 3。 下一次请求怎样得知上一次测试失败？模型参数是否因此被训练更新？

解释。 Agent 把失败 output 形成的 observation 放入 messages，再交给下一次 Model.query。这是输入变化，没有在这条循环中训练模型参数。

预算、批次与记录

模型请求前的限制检查

在真正请求模型前，它会检查：

  • step limit；
  • cost limit；
  • wall-time limit。

如果已经达到配置条件，就通过控制流异常生成退出消息，而不是继续花费下一次模型调用。

限制检查发生在模型请求之前：

先检查限制
  ↓
再请求模型

增加模型调用计数

通过限制检查后：

self.n_calls += 1

这个计数表示 Model query 次数，不表示 Environment 执行次数，也不表示 Task 数量。

如果一条模型消息包含两个 Bash actions：

n_calls 增加 1
Environment.execute 可能发生 2 次

计数口径必须先说清楚，数字才有意义。

新消息列表为什么不等于新预算

注意“清空 messages”的准确范围：n_calls、cost 与 _start_time 在对象构造时初始化，run() 不重置它们，也不会替模型重置游标。复用同一 Agent 对象调用第二次 run()，不会获得全新的预算。实验为每次运行创建新对象，分别初始化消息、计数和时钟。

同一批 action 中断时，前面的结果是否已经加入 messages？

DefaultAgent.execute_actions() 用列表推导先收集整批 outputs，全部完成后才统一格式化并追加 observation。假设一批依次为 echo FIRST、完成标记、echo THIRD：第一条实际执行；第二条触发 Submitted；第三条未执行。但因为整批收集被打断，DefaultAgent 还没有追加第一条 output，最后直接记录 exit。不能把“按序执行”解释为“每条结果立即落入 messages”。

InteractiveAgent.execute_actions() 使用不同接线：逐条积累 outputs，并在 finally 中格式化已有结果；tool-call formatter 为缺少的结果补 returncode=-1 / action was not executed。因此第一条的真实 output 可保留，完成命令和未执行第三条都可能显示占位结果。完成命令实际上执行过，这个占位文本表达的是“没有普通 output 返回给 formatter”，不能据它断言现实中没有执行。提交信号的异常路径见 第05章。

消息增长不是“模型拥有持久记忆”

在一次 DefaultAgent.run() 内，self.messages 是一个线性内存列表。正常完成的一轮把 action 与 observation 加入列表，供下一次 Model query 使用；前述批次中断可能跳过普通 observation 追加。

这是当前运行的工作记忆。下次启动是否重新装入历史，需要另有读取入口；跨进程恢复和并发写入也不能只由一个内存列表承担。下面沿保存时点说明这条边界。

为什么这种拆法容易扩展

DefaultAgent 并不把某个特定模型 API 或某个特定执行后端写死在主循环里。它只依赖 Model 和 Environment 接口。

因此可以替换：

  • 不同 Model adapter；
  • 本地、Docker、Singularity 等不同 Environment；
  • DefaultAgent 与 InteractiveAgent。

主循环仍保留相似结构：

query → action → execute → observation

不过“容易替换”不等于“所有实现具有相同安全、持久化和恢复保证”。那需要逐个实现核对，不能从接口形状自动继承。

调用、批次与对象状态问答

问题 1。 model call 数与 command 执行数为什么不相等？

解释。 一条响应可带多个 actions；格式错误可能没有可执行 action。完成信号或错误也会使批次提前停止。

问题 2。 同一批第一条正常返回，第二条 Submitted，DefaultAgent 会保存第一条 observation 吗？

解释。 不会由 execute_actions 追加；列表推导被打断，尚未到统一格式化与 add_messages。InteractiveAgent 的 finally 路径不同。

问题 3。 同一对象第二次 run，messages 重新开始是否表示 step/cost/time 预算归零？

解释。 不表示。n_calls、cost 和构造时钟没有在 run 中重置，模型对象也有自己的状态。本课程实验每次创建新对象。

消息追加与保存的先后关系

DefaultAgent 的调用顺序是 run → step → query → execute_actions。query 先追加 assistant 消息；execute_actions 收齐整批 outputs 后才追加 tool observations；外层这一轮的 finally 再调用 save。

前述批次若被 Submitted 打断，外层会处理退出信号，再在 finally 保存当时状态；已执行动作的普通结果可能还没加入消息。若进程直接收到 SIGKILL，这个 finally 也不会执行，磁盘上可能只剩前一轮快照，文件却已经改变。

因此，保存 trajectory 快照不等于拥有 durable ledger——可用于恢复核对的持久执行记录。后者还要解决工作身份、写入权与不确定效果的处理；第05章继续解释保存结构，第06章展示指定硬终止窗口。
