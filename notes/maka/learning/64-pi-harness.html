第 64 章｜Pi：最小核心怎样组织运行支撑（Agent Harness）

本章概览

核心问题：只有少量默认工具（Tool），为什么仍能完成连续工作；增加自定义能力时，又该把责任放在哪里？

关键概念：代理循环（Agent Loop）连接决策与结果；会话树（Session Tree）保留不同探索路径；上下文压缩（Context Compaction）缩短当前输入；扩展（Extension）在明确接点改变行为；项目信任（Project Trust）控制项目资源加载。

关系主线：Pi用四个默认工具（Tool）启动一个短任务，再把结果保存、选择、整理后送回模型（Model）。可扩展性（Extensibility）让工作流（Workflow）可以替换，同时要求区分输入、实现、权限（Permission）和真实文件效果（Effect）。

前情回顾：记录、输入与能力分别交给谁

第14章说明，事件（Event）被观察到、持久记录写出、消费者（Consumer）取得视图，是三件不同的事；其中已用Pi的叶节点（Leaf）解释探索路径选择。第15章把上下文（Context）定义为本次模型调用（Model Query）实际获得的材料，文件保存在磁盘上不代表已经进入输入。

第19章进一步区分持久历史（Persistent History）、上下文压缩（Context Compaction）与长期记忆（Long-Term Memory）：较短摘要（Summary）只改变表示，不能替代原始证据或自动形成未来偏好。第23章则区分技能说明包（Skill）提供的方法、插件（Plugin）提供的实现，以及子代理（Subagent）的独立工作。

本章把这些关系放回一套具体实现。Pi是面向终端的代码代理（Code Agent）运行支撑（Agent Harness）：默认能力保持集中，具体工作方式可以通过扩展（Extension）调整。这里既看它怎样完成工作，也看这种设计把哪些责任交给了使用环境。

1. 用四个默认工具（Tool）完成一个短任务

先固定初态与允许范围

沿用第14/15章的README教学初态：Git工作区（Workspace）中，package.json声明 "test": "node --test"，README却写着不存在的 npm run check。函数已经正确，四项既有测试（Test）原本通过。用户要求只把README命令改为 npm test，检查测试（Test）与差异（Diff），最后用中文解释。

本例采用普通本地文件与命令执行路径，不启用替代工具（Tool）的扩展（Extension），也没有改变默认工具（Tool）选择。下面给定的调用、结果和分支是教学推演，未运行Pi或模型（Model）。四项通过是这一初态下的预期，不能当作新运行日志。

Pi的初始默认工具（Tool）为读取（Read，read）、命令执行（Bash，bash）、编辑（Edit，edit）和写入（Write，write）。设置或启动选项可以改变可用集合，所以“四个默认工具（Tool）”不表示整个项目只实现四种能力。

表 1 / Table 1 · 先固定初态与允许范围
默认工具（Tool）实际改变什么在这个任务中的位置
读取（Read）把文件的一段正文或图像变成观察结果（Observation）取得README与配置；大文件还需注意截断（Truncation）和后续窗口
编辑（Edit）在一个文件中定位旧文本并替换只更正命令；多个替换须在原文件中可定位且不重叠
写入（Write）创建或覆盖文件正文本例不需要整文件重写，因此不必调用
命令执行（Bash）运行工作目录中的命令，返回输出与失败信息运行已有测试（Test），再检查差异（Diff）

这里的工具（Tool）数量不是步骤数量。两份文件可以通过两次读取（Read）取得；一个任务也不必用完所有可用工具（Tool）。任务本身已经足够简单，额外建立规划文件或子代理（Subagent）会增加交接，而不会自动增加验证（Validation）证据。

从“准备修改”走到“可以报告”

阅读时只跟踪一个变量：每一步之后，模型（Model）比刚才多知道了什么？

表 2 / Table 2 · 从“准备修改”走到“可以报告”
阶段提出的行动请求（Action）返回后新增的依据仍不能声称什么
查看读取（Read）README和 package.json说明与真实脚本不一致，正确入口是 npm test不能说文件已修改
修改编辑（Edit）README中的命令工具结果（Tool Result）报告目标替换完成不能说测试（Test）通过
验证命令执行（Bash）运行 npm test在给定教学初态下，预期发现并通过四项测试（Test）不能据此证明没有改动其他文件
范围核对命令执行（Bash）查看变更文件与README差异（Diff）预期只有README的目标命令变化不能把一次检查推广成所有环境正确
交付生成中文说明分别报告修改、实际验证（Validation）与限制不能补写未执行的检查

本例的编辑（Edit）参数可以很短。下面是符合所核参数结构（Schema）的教学输入，不是已执行的工具调用（Tool Call）：

{
  "path": "README.md",
  "edits": [
    {
      "oldText": "npm run check",
      "newText": "npm test"
    }
  ]
}

外层 path 定位文件；edits 中每一项描述同一份原文件上的一处替换。实现先读取当前正文、定位全部替换并检查重叠，再写入结果。如果这句话出现多次，应该取得足以唯一定位的相邻正文；不能把“看上去只有一处”当作实现已经检查过。当前匹配还包含格式归一化（Normalization）与模糊匹配（Fuzzy Matching）处理，因此编辑（Edit）成功也不等于资源版本（Resource Version）没有发生任何变化。

write 能覆盖整个文件，bash 也可能写文件。由此可见，默认工具（Tool）的分工方便模型（Model）选择动作，工具（Tool）名称本身不构成单文件写入边界。这个区别会在后面的扩展（Extension）例子里再次出现。

2. 代理循环（Agent Loop）把一次请求接到下一次判断

先看信息流，再进入函数

下图只画正常工具调用（Tool Call）及一个执行前拦截接点；它省略流式显示、重试和多工具并发的细节。每次请求中的系统提示词（System Prompt）与工具声明（Tool Specification）一同交给模型（Model），不是另外启动一个执行者（Worker）。

AgentSession.prompt()先处理输入、方法展开及会话（Session）条件，再交给代理循环（Agent Loop）。循环取得模型（Model）的完整响应后，找到工具调用（Tool Call），准备并验证参数，运行执行前钩子（Before Hook），随后才调用对应实现。找不到工具（Tool）、参数不合法或被阻止，都可以形成错误结果供后续判断；不是所有请求都会到达真实文件操作。

完成的工具结果（Tool Result）进入消息列表（Message List），随后构造下一次模型调用（Model Query）。在所核路径中，transformContext先让已接入的上下文（Context）处理器整理消息（Message），convertToLlm再转换为模型服务协议接受的类型。这就是第15章“谁真正把内容送进请求”的具体消费者（Consumer）。

正常响应没有新工具调用（Tool Call）时，循环还会检查后续消息（Follow-up Message）；没有待处理内容才结束。错误、中断和显式终止另有退出分支。尤其是输出因长度上限截断时，当前实现不会冒险执行其中可能残缺的参数，而是为该响应里的调用产生失败结果。

引导消息（Steering）改变下一次输入，不撤销在途效果（Effect）

假设测试（Test）正在运行，用户补充“最后也说明测试（Test）数量”。引导消息（Steering）会排入队列，在当前助手响应所带工具调用（Tool Call）处理完毕后的边界进入后续输入；它不是把文字插进已经发出的模型请求。

后续消息（Follow-up Message）采用另一个时机：在当前循环原本准备结束时接入。因此两种队列的区别是什么时候让消费者（Consumer）看到新要求，不只是界面上两个快捷键。

这也解释了一个限制。如果用户改口“不要修改README”，而编辑（Edit）已经写入，引导消息（Steering）不能让旧效果（Effect）消失。它可以约束下一步，由后续过程核对文件并处理；取消（Cancellation）、消息接纳与文件恢复仍是不同操作。

3. 会话树（Session Tree）怎样保留探索，又只选择一条输入路径

Pi的会话（Session）条目包含 id 与 parentId。新条目接在当前叶节点（Leaf）之后；沿叶节点（Leaf）向前追溯并反转，便得到本次所选路径。它保留的是对话与处理记录的分支，不是Git工作树（Worktree）。

假设读完配置后有一个检查思路B，后来想回到同一观察点换成思路D。下面A/B/C/D/E都是教学条目标签，已省略真实类型需要的其他字段。

从E构造输入时，B/C不因保存在同一个文件里就全部进入请求。SessionManager.branch(a)只把内存叶节点（Leaf）移到A；下一次追加记录才在A后形成新分支。没有新增并写出条目就退出，不能把这次内存选择当作已保存的导航位置。

选择分支也不回滚文件。若C阶段已经改了README，新路径还面对当前磁盘状态；模型（Model）需要重新观察，或由明确的文件检查点（File Checkpoint）机制恢复。把对话位置退回去，再拿旧正文覆盖文件，会混淆证据状态（Evidence State）与环境状态（World State）。

切换路径时可以生成分支摘要（Branch Summary），在目标位置保存被离开路径的要点。这是把经验带入新路径的另一条材料来源，与为了腾出窗口而做的上下文压缩（Context Compaction）有不同触发原因。两个机制都可能生成摘要（Summary），不代表它们在选择相同历史（History）。

文件写出与界面事件（Event）还有一层边界

在当前普通消息（Message）路径中，AgentSession处理 message_end 时先通知扩展（Extension）和观察者，再调用 SessionManager.appendMessage()。所以界面已经看到文字，不能独立证明持久写入（Persistent Write）完成。

持久化（Persistence）启用时，SessionManager通过文件写入或追加保存条目。新普通会话（Session）尚无助手消息（Assistant Message）且尚未写出时，记录可以暂留内存；已有写出状态与首次助手消息（Assistant Message）到达走不同分支。这里的 flushed 表达实现的文件写出状态，不是每条记录都执行文件同步（File Synchronization，fsync）的保证。

这条链足以解释怎样保存与选择材料，却没有证明文件效果（Effect）和会话（Session）记录共同组成原子事务（Atomic Transaction）。若文件已修改而记录写出报错，仍需回查真实文件；不能从缺少成功消息（Message）推出“肯定没有修改”。

4. 上下文压缩（Context Compaction）怎样接入同一条路径

一个阈值决定何时尝试，不证明压缩一定有效

把有效的当前上下文（Context）用量记为 uuu，上下文窗口（Context Window）容量记为 WWW，预留词元（Token）数记为 rrr。在功能启用时，所核主动阈值条件是：

u>W−ru > W-ru>W−r

这个不等式对应 shouldCompact() 的比较，而不是整个模型请求的通用计费公式。实际用量如何估算、不同模型服务提供方（Provider）如何接纳请求，还在这一步之外；阈值被触发只意味着尝试上下文压缩（Context Compaction）。

正常自动路径可以在工具结果（Tool Result）已追加、准备下一个助手响应之前整理输入。手动 compact() 则先中断当前代理操作，完成后不会自动继续被打断的那次工作；容量溢出（Context Overflow）的自动恢复另有条件和重试限制。不能把所有“压缩结束”都理解为“自动把任务做完”。

切点（Cut Point）先保护协议关系，再产生摘要（Summary）

默认算法从较新的记录向前累计估算大小，寻找接近保留预算的切点（Cut Point）。它不能随意在工具结果（Tool Result）处切开，否则保留的消息（Message）可能失去对应调用。若一个用户要求引出的连续工作太长，可以在中间的助手消息（Assistant Message）处分开，并单独整理前半段工作。

这里要留意源码术语的局部含义：压缩算法的 turn 指从一条用户类消息（User-like Message）到下一条用户类消息（User-like Message）之前的连续交互；底层循环的 turn_end 又对应一次助手响应及其工具结果（Tool Result）完成。二者都不能未经说明直接等同Maka的工作轮次（Turn）身份对象。

默认准备结果把待摘要历史（History）、被拆分工作的前缀（Prefix）、已有摘要（Summary）以及 firstKeptEntryId 分开保存。上一轮留下的原文也可能在下一次成为待整理材料，因此连续压缩不是反复只读最新几句话。若确有被拆分的前缀（Prefix），生成器会整理它；只有同时存在更早待摘要历史（History）时，才另外生成那部分摘要（Summary）。不能简单说每次都调用两遍模型（Model）。

给README案例增加较长旧记录后，一个合格的教学摘要（Summary）至少要留下：只改README、正确命令是 npm test、已执行到哪一步、测试（Test）结果是否已取得、最后用中文说明。若只留下“文档已修复”，下一次可能误把尚未运行的测试（Test）写成通过。语义正确性（Semantic Correctness）不能由切点（Cut Point）合法或文本变短自动得到。

真正生效的接点是“记录之后重新构造输入”

下面片段来自当前手动压缩路径的连续步骤，只增加注释和换行。阅读目的不是记住变量名，而是找到三个责任：追加记录、构造视图、交给消费者（Consumer）。

// 追加压缩条目（Compaction Entry）。
this.sessionManager.appendCompaction(
  summary,
  firstKeptEntryId,
  tokensBefore,
  details,
  fromExtension,
  usage
);
const newEntries = this.sessionManager.getEntries();
// 构造会话上下文（Session Context）。
const sessionContext = this.sessionManager.buildSessionContext();
// 采用选定消息（Message）。
this.agent.state.messages = sessionContext.messages;

第一条语句生成压缩条目（Compaction Entry），包含摘要（Summary）和保留边界。newEntries随后用于寻找保存条目并发出扩展（Extension）通知；buildSessionContext()则沿当前路径选取最新压缩条目（Compaction Entry），组合摘要（Summary）、从 firstKeptEntryId 开始的保留原文，以及该条目之后的新记录。最后一行把得到的消息（Message）真正交给代理状态（Agent State）。

原始记录仍保留，不代表下一次发送原文全集。反过来，摘要（Summary）进入消息（Message）也不证明模型服务提供方（Provider）接受了请求，更不证明模型（Model）正确使用了约束。这正是第19章机制在Pi里的具体落点。手动压缩与消费者源码

5. 扩展（Extension）改变哪个接点，就承担哪里的正确性

方法文字与可执行实现要分开

技能说明包（Skill）可以告诉模型（Model）怎样核对文档。Pi的默认提示词（Prompt）组织会在具备适合文件读取的工具（Tool）时放入可见技能说明包（Skill）的名称、描述与位置，引导按需读取正文；某些只能显式调用的条目会被排除。发现说明、读取正文、实际采用仍然是三步。

扩展（Extension）则是加载到Pi进程中的TypeScript模块。它可以注册新工具（Tool）、命令或事件（Event）处理器，也能替换已有行为。增加一个 check_docs 可执行实现，改变的是执行链；增加一份文档检查技能说明包（Skill），改变的是方法输入。两者可以配合，不能相互冒充。

为了理解设计，不需要把扩展（Extension）的全部应用编程接口（Application Programming Interface，API）列一遍。沿本章案例看三个接点就够了：

表 3 / Table 3 · 方法文字与可执行实现要分开
接点本章可以怎样使用必须守住的边界
tool_call：工具调用（Tool Call）前在调用实现之前检查本次请求并返回阻止结果只有走过该接点的请求受它控制；参数检查不自动覆盖其他写入入口
context：上下文（Context）整理保留当前文档范围与未完成检查，过滤不需要的旧材料必须保持合法消息（Message）关系与真实证据，不能把失败删除成成功
session_before_compact：上下文压缩（Context Compaction）前取消本次压缩或提供自定义摘要（Summary）与边界定制者需要维护摘要（Summary）语义及保留边界，不能只返回短文本

这些接点不是同一种失败策略。所核 tool_call 处理器抛错会阻止相应工具（Tool）执行；context 处理器抛错则报告扩展（Extension）错误，继续后面的处理。因此，不能因为某个事件（Event）“可以拦截”，就推断所有钩子（Hook）失败都会关闭执行入口。

一个具体反例：只拦编辑（Edit）为什么不够

设一个扩展（Extension）规定：edit 的目标不是README就拒绝。这能阻止经该工具（Tool）提出的越范围编辑（Edit），但同一进程仍可能通过写入（Write）覆盖文件，或通过命令执行（Bash）运行另一个修改命令。更直接地说，扩展（Extension）自身就是可执行代码，也不必通过模型（Model）的工具调用（Tool Call）才能访问文件。

所以这条规则适合作为工作流程中的范围检查，不足以单独证明系统已经强制“只能写README”。要形成安全边界（Security Boundary），还需让所有相关操作实际经过不可绕过的限制，或把进程放进操作系统（Operating System，OS）、容器（Container）或虚拟机（Virtual Machine，VM）提供的隔离边界。这里没有安装扩展（Extension）或部署任何一种隔离方案。

6. 项目信任（Project Trust）与运行权限（Permission）各管什么

当前Pi存在项目信任（Project Trust）流程，用来决定是否加载项目本地设置、资源、包与扩展（Extension）。在尚无适用信任决定、项目确有受保护资源的交互启动中，默认策略会询问；非交互入口有不同的默认处理，不能假定总会出现对话框。

拒绝项目信任（Project Trust）会跳过受保护项目资源，但 AGENTS.md 等上下文文件（Context File）不因此一概停止加载，除非另外禁用相应读取。先读规则文本与执行项目扩展（Extension）是不同路径。这个加载门禁（Loading Guard）也不限制开始工作后模型（Model）能够请求的全部文件和命令操作。

Pi官方明确把默认执行定位为使用启动进程的权限（Permission），并未内置限制文件、进程、网络和凭据访问的完整沙箱（Sandbox）。可信扩展（Extension）可以接入额外控制或把工具（Tool）路由到隔离环境，但只有核对实际接线后，才知道哪些入口被覆盖。Pi安全边界说明

这不是对某一种交互风格下结论。频繁询问、项目信任（Project Trust）、工具（Tool）限制与操作系统（OS）隔离分别回答不同问题：谁的代码可以加载、什么请求需要确认、哪些资源事实上不可访问。读者需要识别的是责任，而不是用一个“安全”标签替代全部机制。

7. 从Pi的设计里学什么

Pi的独特取舍是：让少量默认工具（Tool）、连续消息（Message）与会话（Session）管理形成可工作的核心，再通过扩展（Extension）改变工作方式。它没有要求每种团队流程都先成为核心功能。这里“最小”描述默认职责与产品选择，不是断言源码永远只有几百行，也不是断言没有任何复杂状态（State）。

这种设计有三项可迁移的启发。第一，先把工具结果（Tool Result）回到模型输入（Model Input）的闭环做清楚，能力数量才有意义。第二，保存探索记录与选择当前路径应分开，使同一份历史（History）能够支持不同消费者（Consumer）。第三，扩展（Extension）的接口（Interface）必须说明执行位置和失败语义，否则灵活性会变成隐含依赖。

代价同样具体：工作流（Workflow）作者需要决定如何规划、委派、保护路径及验收（Acceptance）；多个扩展（Extension）的组合也需要检查。对于需要强制隔离、统一权限（Permission）或持久工具结算（Durable Tool Settlement）的系统，不能仅凭“可以加扩展（Extension）”声称这些保证已经具备。

问题与参考答案

问题1：默认工具（Tool）只有四个，为什么任务仍可能完成得很深入？

参考答案： 读取（Read）不断带来新证据，编辑（Edit）或命令执行（Bash）改变环境，工具结果（Tool Result）反馈给下一次模型调用（Model Query）。深度来自有依据的连续判断与验证（Validation），不是一次性列出更多工具（Tool）；复杂任务仍可能需要额外能力。

问题2：退回会话树（Session Tree）的旧节点（Node），能否直接拿旧正文重新写入？

参考答案： 不能仅据对话位置这样做。分支选择不撤销文件效果（Effect），当前磁盘可能已经变化；应先取得新观察结果（Observation），或依靠明确的文件恢复机制，再决定修改。

问题3：压缩条目（Compaction Entry）已经追加，为什么还要找 buildSessionContext()？

参考答案： 追加回答“保存了什么”，构造视图回答“本次使用什么”，写入 agent.state.messages 才找到实际消费者（Consumer）。之后仍要形成合法请求并由模型（Model）使用，不能在第一步就宣告完整成功。

问题4：项目信任（Project Trust）通过，是否意味着命令执行（Bash）已经受沙箱（Sandbox）限制？

参考答案： 不意味着。前者控制项目资源加载，后者需要实际进程与资源边界。被加载的扩展（Extension）可以增加限制，也可以直接执行代码；必须检查其所处环境与具体覆盖入口。

相关机制可以回看第14章的路径与投影（Projection）、第19章的上下文压缩（Context Compaction）与第23章的能力分工。需要追踪当前源码和设计范围时，见Pi设计参照。
