第 37 章｜代码检索与仓库图

本章概览

核心问题：代码尚未进入模型输入时，怎样找到、筛选并回读足以支持修复的证据？

关键概念：词法搜索：按字符串查匹配；候选：值得进一步读取的对象；RepoMap（仓库图）：代码定义与依赖线索；PageRank：沿图传播关注分数；预算选择：限制最终展示的片段；回读：核对当前正文。

关系主线：Maka 搜索与读取补齐具体证据，Aider 用结构关系和聊天信号排序，再按渲染成本选入；排名、命中与根因判断仍是不同结果。

前置：第36章的输入选择。

先在 Maka 闭合搜索与回读

这里限定为 Session 中已绑定执行环境的（bound）Read、Glob、Grep 文本文件调用。buildBuiltinTools 把模型给出的参数转换成带类型的文件系统操作，并带入 Session cwd、执行边界与取消信号。createBoundaryFilesystemExecutor 决定由 workspace executor 还是受管理的 filesystem worker 执行；要求 managed worker 却没有可用 worker 时会拒绝，不能把检索方便理解成额外的读取授权。

下面的 ripgrep 是搜索文件内容的命令行工具，命令名为 rg；它按正则表达式匹配文本，正则就是描述待匹配文本形状的规则。默认搜索还会受忽略规则等条件影响，因此“没有命中”要结合实际搜索范围解释。

表 1 / Table 1 · 先在 Maka 闭合搜索与回读
工具及参数执行操作（Execution）返回给工具运行时的对象它还不能证明什么
Glob({pattern,cwd?})在选定目录用 node:fs/promises 的 glob 遍历，收集至多 200 条{files: string[]}，文件路径候选路径存在于候选，不代表内容相关；遍历顺序不是相关性评分

另一种常见管线会先把文件编码成向量表示（embedding），存入向量库，再选距离较近的前 k 个候选（top-k）。这里的文本文件调用不走这条管线：文件系统本身提供当前内容；Grep 查字符串，Glob 查路径，模型按结果决定是否补查。搜索引擎没有替模型自动生成第二个 query，也没有在这里维护语义相关性分数。Atomic 等子系统虽提供 searchByKeys 一类查询能力，却未因此接入这条模型输入链。

结果也不是从临时数组直接贴回下一请求。ToolRuntime.settleToolCall 执行工具；这些 binding 没有自定义 toModelOutput，因此 projectToolResult 用默认编码把上述对象变成 JSON 型 durable model projection，并发布工具结果。仍允许继续时，下一 step 的 AiSdkTurn 等待事件队列已被消费，重新读取本 Turn 的 RuntimeEvents，经 foldEffectiveModelHistory → buildRuntimeEventModelReplayPlan → materializeRuntimeReplayPlan 组成消息，再经请求整形交给 modelAdapter.startStream({messages: attemptMessages})。因此模型能依据被投影的命中改查询；若内容已被归档或压缩，下一请求不保证仍带着原始全文。搜索结果如何回到模型，与 UI 是否展开过结果是两回事。

平台差异会改变工具是否可用。例如 Windows sandbox preview 的文件 worker 拒绝 Grep；这与 ripgrep 正常执行后没有匹配是两种结果。前者需要调整执行方案，不能改写成“仓库没有命中”；后者的退出码 1 才转换为空 matches。

用同一个小仓库，根据缺失证据改查询

沿用 第04章 四文件 fixture：任务同时要求修正测试命令与时长格式。下面是依据真实文件内容设计的查询序列，不是模型运行轨迹；假设 cwd 指向这份 fixture 的副本、相关路径可读、期间无人修改文件。教学调用写作 工具(参数)，不代表某个 provider 的 wire 格式。

任务有三个待补的证据面：E1 是项目实际测试入口，E2 是任务期望，E3 是与期望冲突的当前实现。查询和回读的目标是补齐它们。

再给这一过程一个小预算。仅为手算，设已回读且保留出处的四种片段成本为 README 60、scripts 60、相关测试 90、实现 90 token；这些数字不是 fixture 的实测 token 数，且预算 250 仅指此次选入的证据片段，不含系统指令、工具 schema 和历史。若先放 README、scripts、测试，用掉 60+60+90=210，余下 40 放不进实现；E1–E3 只覆盖 2/3。改为 scripts、测试、实现，用掉 60+90+90=240，覆盖 3/3。保留更多关于命令的说明，反而可能挤掉解释行为所需的实现；“多命中了一篇”与“补齐一个证据面”不是同一指标。若当前输入中 README 已无法直接移除，这个选择只是后续请求整形的目标，不能假定模型改一次查询便能重写已有历史。

这个例子也给出失败反例：只修 README 就结束，确实找到了一个错误，却留下第二个独立要求。增加相同查询的候选数，或把窗口翻倍，都不会替模型提出“实际行为还没有解释”这个问题。查询改写解决查什么，回读解决候选到底说什么，输入选择解决哪些证据同时留在请求里。

1. 为什么不能只给文件名，也不宜贴全仓

假设任务是修复路径带空格时的文件读取。模型已经看到 cli.py 的失败输出，却不知道参数在哪里解析、文件在哪里打开。目录列表能暴露文件名，全文能暴露实现，但前者缺关系，后者成本过高。

Aider 的 RepoMap 提供一种中间表示：给出相关文件、定义及结构片段，帮助继续定位；它不替代需要精读的文件正文。官方说明将其用于根据当前聊天选择仓库中较相关的结构，而非完整列出每个函数。

2. 从源码到输入的一条实际链

tree-sitter 是按语言语法解析代码的工具，这里用它标出名称的定义与引用，再以文件为节点建立关系图。下图从上往下表示材料如何变化；右侧聊天信号改变排序，底部预算选择决定哪些结构真正展示。这里是 Aider RepoMap 的路径，不是 Maka 已接入仓库图的声明。

图中有两次选择：先按关系和聊天信号排序，再按渲染成本选入。排名靠前不能证明根因，map 的近似预算也不保证整个请求不超限；静态标签漏掉动态依赖时，后续搜索与正文核对仍不可省略。虚线是后续取证要求，不表示 RepoMap 自动执行了正文读取。

get_tags_raw 使用语言查询抽取定义/引用（def/ref）标签；get_ranked_tags 建立引用文件指向定义文件的图，并将已在聊天中的文件、提及的名称等作为排序信号。get_ranked_tags_map_uncached 尝试不同长度的排名前缀，调用 to_tree 渲染后再计量。缓存和启发式使它可用于交互，但也会带来语言解析、刷新和排序误差。

这条链的关键是保留“谁依赖谁”，而非让模型先读完整仓库再生成摘要。它把模型输入选择中的一部分工作交给确定性的程序。

3. 图排序的依据：相关文件的依赖也值得看

PageRank 可以理解为：一个节点把自己的重要性按边权分给它指向的节点，再混入一部分外部给定的关注分布。这里节点是文件，r(v) 是文件 v 的分数，u→v 表示文件 u 引用文件 v；w(u,v) 是该关联的权重，出边权重之和就是把 u 指向各文件的边权加起来。p(v) 表示外部对 v 的关注份额，d 控制沿图传播的比例。下面暂假设每个节点都有出边，且 p 已归一化为总和 1：

沿边 u→v 传来的份额 = r(u) × w(u,v) / u 的全部出边权重之和
r_new(v) = (1-d) × p(v) + d × 所有指向 v 的文件传来份额之和

读法是：先看每个引用 v 的文件 u，用 u 的旧分数乘以“这条边占 u 全部出边权重的比例”，再把所有这样的份额相加。最后混入外部关注份额 (1-d) × p(v)，得到 v 的新分数。r_new 专指新一轮结果，右边所有 r(u) 都来自上一轮。

求解时，每一轮都用上一轮所有节点的分数同时计算新分数，不能刚更新一个节点就拿新值计算本轮另一个节点。一般图还会有无出边的 dangling 节点：其分数需要按指定的归一化分布重新分配，否则上式会漏掉这部分概率质量；图算法库 NetworkX 未另指定 dangling 分布时使用上述个性化关注分布（personalization）。个性化、带权转移和 dangling 处理是不同输入，不能只说“按被引用次数排序”。

用一个自拟简化图手算，忽略 Aider 的多重边与启发式：A 是 cli.py，B 是 parse.py，C 是 fs.py，边为 A→B、B→C、C→C；C 的自环仅为简化计算。令 p=(1,0,0)，d=0.85，初始分数均为 1/3：

4. 从排名到 token 预算，仍有一次选择

假设三个候选结构片段分别占 80、120、160 token，预算为 250。即使第三项相关，也不能因此把三项全文全放进去；先保留前两项，剩余细节可由后续读取补足。这是教学算例，用于区分“排到前面”和“最终进入请求”。

源码中的预算搜索是近似过程：它渲染排名前缀后计量，并接受接近目标的误差；ok_err=0.15 的判定可接受略高于目标的结果，较长文本的计数也使用采样估计。因此不能把 map budget 写成严格不可超过的请求上限。最终请求还包含系统指令、聊天和正文，需要另一层总预算管理。这里依据前述预算搜索函数 get_ranked_tags_map_uncached 及其计数函数 token_count 的分支，不是运行测量。

这些方法可以串联：词法/语义召回提出候选，结构关系扩展邻域，正文读取核对假设。RepoMap 补充的是代码结构的输入选择；第36章中的会话压缩和长期记忆维护仍负责另外两类信息。

回到 Maka：何时才值得加地图或索引

在前面的四文件任务里，按 import 回读已能闭合主要证据；Aider 的图排序不自动补出正确测试命令，更不会证明 % 100 是根因。若换成数千文件、业务描述没有源码术语、同一调用邻域反复查找，结构地图或语义候选才可能节省搜索轮次。它们增加的是发现入口的能力，仍要把候选交给当前正文读取和任务验证。

Maka 索引扩展的参考合同分成三部分；以下是设计方案，不是 Maka 已实现的索引：

  • 生产和新鲜度。 谁从哪个 workspace 的哪些文件生成符号或文本切片（chunk），何时更新、撤回删除项；返回候选要带可回读的文件/符号位置及生成时的内容标识。旧地图只记录旧观察，当前 Read 是较新的观察，两次观察间仍没有跨调用快照保证。若文件已移动或正文改变，就重新定位，不用旧索引片段直接生成写入前提。
  • 选择和授权。 查询要带任务与代码范围，返回候选的来源、覆盖缺口和截断边界；检索与回读都须服从当前可读范围，不能让已失去访问权的内容通过缓存摘要泄露。提高 top-k 只解决候选截断，修正错误 scope、语言过滤或失效项需要改变生产/查询合同。
  • 消费和代价。 指定哪个入口把候选变成回读、哪一层分配最终输入预算，保留路径出处和读取时点；以任务完成、证据覆盖、无关输入、调用延迟及索引维护成本共同评估。不能用近似搜索找回精确向量近邻的比例（ANN recall）代替任务证据召回，更不能只因返回了相近段落就称为有材料支持的回答。

稀疏/稠密、ANN、融合与重排的结构推导见通用检索专题；候选预算与最终证据覆盖的完整演算见其数值例子。

6. 图排序与检索失败的参考结论

图的节点与边分别表示什么？

本章 Aider 链中的排序图以文件为节点，引用方指向定义方，让引用文件的分数沿依赖关系传给定义所在文件。它不是直接对所有函数建立调用图；动态派发等关系也可能缺失。

用户提及文件以后，为什么还要再按定义选择？

提及信号改变个性化关注分布，影响文件排序；源码再沿出边把文件分数分给被引用定义，最后渲染排名前缀并估算成本。文件重要只说明值得检查，定义选择才把结构线索压成有限输入，二者都不证明根因。

动态插件没有静态调用边时，参考处理是什么？

旧排序可能没有通往插件实现的路径。定向搜索插件名和加载配置，再回读实际绑定入口，可以补足这条缺边；若行为取决于运行时加载，静态地图本身无法证明当时加载了哪个实现。

查询范围与文件时点变化后的结果

题 1：零命中要修哪里？ 仍是上面的 JavaScript fixture，工具可用且路径有权限；模型发出 Grep({pattern:"formatDuration",path:".",glob:"*.py"}) 得到空 matches。它准备把候选上限从 200 提高到 2,000，并认为不行就需要 embedding。应先改什么，回读什么，何时才能说缺少实现？

参考答案。 先改错误的语言过滤，或用 Glob 确认实际 .js 文件；再搜 formatDuration，读测试中的 import 与目标实现。扩大候选上限不能找回被过滤掉的 JavaScript 文件；bound Grep 本身也没有这个上限参数可由模型调到 2,000。即使正确范围内仍零命中，也只能说明这次词法查询未找到，应再查任务入口、别名或配置；本例已有直接 import，不能据一次错误查询认定仓库缺少实现或必须上语义索引。

题 2：索引和当前文件冲突时信谁？ 这是对 fixture 的虚构时序变体：旧地图保存 % 100，另一位开发者随后已把当前文件改成 % 60；Agent 用旧地图定位后，Read 看见 % 60，而它手上的失败日志来自修改之前。它能否再次把旧片段写回、直接宣告修好，或只刷新地图就完成任务？

参考答案。 三者都不成立。旧索引有定位价值，不能覆盖较新的正文；旧失败日志也不能证明当前版本仍失败。应确认当前函数及测试契约，基于当前文件做验证，并核对实际差异及责任范围；当前状态已满足要求时无需重复编辑。刷新地图能改善后续发现的新鲜度，却不是行为验证。若又有并发修改，Read 本身没有锁住后续文件，应重新取得写入前提，而不是把“刚读过”当成原子快照。

RepoMap 适合提供大仓库中的结构定位线索；是否值得采用，仍要看它能否减少漏查和无关读取，以及增加了多少构图与更新成本。
