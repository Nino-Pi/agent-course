第 37 章｜代码检索（Code Retrieval）与仓库图（RepoMap）

本章概览

核心问题：代码尚未进入模型输入（Model Input）时，怎样找到、筛选并回读（Readback）足以支持修复的证据？

关键概念：词法搜索（Lexical Search）：按字符串查匹配；候选（Candidate）：值得进一步读取的对象；仓库图（RepoMap）：代码定义（Definition）与依赖线索；页面排名算法（PageRank）：沿图传播关注分数；预算（Budget）选择：限制最终展示的片段；回读（Readback）：核对当前正文。

关系主线：Maka 搜索与读取补齐具体证据，Aider 用结构关系和聊天信号排序，再按渲染成本选入；排名、命中与根因判断仍是不同结果。

前情回顾：保存、选入与回读（Readback）是三件事

第36章区分了外部保存和进入当前模型输入（Model Input）：只有已选入本次请求的材料，才能直接参与这次判断。第04章的四文件修复还说明，说明文档、测试入口、断言和实现各自提供一种证据；看到其中一项，不等于完成整个任务。第31章解释了工具返回仍要经过结果消费，才能影响后续决策。

本章从这三点继续：还不知道应读哪个文件时，先用查询（Query）缩小候选（Candidate），再回读（Readback）当前正文，最后选择能共同解释任务的证据。仓库图（RepoMap）帮助发现入口；它既不能代替当前正文，也不能代替修复后的验证。

先在 Maka 闭合搜索与回读（Readback）

先区分三个动作：只知道文件名形状，用 Glob 找路径；知道代码中的词，用 Grep 找命中；需要确认代码实际怎样工作，用 Read 取得正文。前两个动作缩小候选（Candidate）范围，最后一个动作才提供解释所需的上下文（Context）。这里限定为 Maka 会话（Session）中已绑定执行环境的文本文件调用（bound），所查路径始终受当前读取边界约束。

下面的 ripgrep 是搜索文件内容的命令行接口（Command-Line Interface，CLI）工具，命令名为 rg；它按正则表达式匹配文本，正则就是描述待匹配文本形状的规则。默认搜索还会受忽略规则等条件影响，因此“没有命中”要结合实际搜索范围解释。

这些参数怎样抵达文件系统？buildBuiltinTools 把模型参数转换成带类型的操作，并带入会话（Session）的当前目录 cwd、执行边界与取消信号；createBoundaryFilesystemExecutor 再选择工作区执行器（Workspace Executor）或受管理的文件系统执行者（Filesystem Worker）。要求受管理执行者（Managed Worker）却没有可用执行者（Worker）时会拒绝。这解释了为什么一次查询（Query）既需要“搜什么”，也需要“在哪个允许范围内执行”。

另一种常见管线会先把文件编码成向量表示（Embedding），存入向量库，再选距离较近的前 k 项（Top-k）候选（Candidate）。这里的文本文件调用不走这条管线：文件系统本身提供当前内容；Grep 查字符串，Glob 查路径，模型按结果决定是否补查。搜索引擎没有替模型自动生成第二个查询（Query），也没有在这里维护语义相关性分数。条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）等子系统虽提供 searchByKeys 一类查询（Query）能力，却未因此接入这条模型输入（Model Input）链。

搜索完成以后，下一次模型判断需要的是可消费的内容。可以把这段接线分成“执行得到对象→形成可重放（Replay）表示→组装下一请求”，先理解每层解决的问题，再对照实现名：

  1. 谁执行。 工具运行时（Tool Runtime） ToolRuntime.settleToolCall 取得表中的 files、matches 或 content。对象的字段说明结果是什么，还没有说明后续哪个消费者（Consumer）会读取它。
  2. 怎样表示。 这三个工具绑定没有自定义 toModelOutput；projectToolResult 使用默认编码，形成 JavaScript 对象表示法（JavaScript Object Notation，JSON）类型的持久模型投影（Durable Model Projection）。持久模型投影（Durable Model Projection）保存供模型重放（Replay）的结果表示，并发布相应的工具结果。
  3. 谁消费。 仍允许继续时，下一模型步骤（Model Step）的 AiSdkTurn 等待事件（Event）队列消费完成，回读（Readback）本工作轮次（Turn）的运行时事件（Runtime Event），重建有效模型历史（Model History）和重放（Replay）计划，再按本次请求整形。模型协议适配器（Model Adapter）最终收到 modelAdapter.startStream({messages: attemptMessages})；这里的 attemptMessages 才是该次尝试传入的消息集合。

对应第三步，foldEffectiveModelHistory 决定哪些事件（Event）表示仍有效，buildRuntimeEventModelReplayPlan 建立重放（Replay）计划，materializeRuntimeReplayPlan 形成消息。函数名较多，是因为“保存了什么”“哪些仍有效”“怎样编码给模型”有不同职责；不能把搜索工具的原始返回直接等同于最终模型输入（Model Input）。

模型因此能根据刚取得的命中改变下一查询（Query）。若结果已被归档或压缩（Compaction），下一请求可能只保留整理后的表示，不能假定原始全文始终在场。用户界面（User Interface，UI）展开过一段结果，也不代替这条输入接线。

平台差异会改变工具是否可用。例如 Windows 沙箱预览（Sandbox Preview）的文件系统执行者（Filesystem Worker）拒绝 Grep；这与 ripgrep 正常执行后没有匹配是两种结果。前者需要调整执行方案，不能改写成“仓库没有命中”；后者的退出码 1 才转换为空 matches。

为什么需要介于文件名与全文之间的表示

前面的四文件任务已经能沿测试里的 import 找到实现。现在另设一个 Python 仓库：任务是修复路径带空格时的文件读取，模型已经看到 cli.py 的失败输出，却不知道参数在哪里解析、文件在哪里打开。它与上面的 JavaScript 测试夹具（Fixture）不是同一个项目。目录列表能暴露文件名，全文能暴露实现，但前者缺关系，后者成本过高。

Aider 的仓库图（RepoMap）提供一种中间表示：给出相关文件、定义（Definition）及结构片段，帮助继续定位；它不替代需要精读的文件正文。官方说明将其用于根据当前聊天选择仓库中较相关的结构，而非完整列出每个函数。

仓库图（RepoMap）怎样变成可选入的结构片段

tree-sitter 是按语言语法解析代码的工具，这里用它标出名称的定义（Definition）与引用（Reference），再以文件为节点（Node）建立关系图。下图从上往下表示材料如何变化；右侧聊天信号改变排序，底部预算（Budget）选择决定哪些结构真正展示。这里是 Aider 仓库图（RepoMap）的路径，不是 Maka 已接入仓库图（RepoMap）的声明。

图中有两次选择：先按关系和聊天信号排序，再按渲染成本选入。排名靠前不能证明根因，仓库图（RepoMap）的近似预算（Budget）也不保证整个请求不超限；静态标签漏掉动态依赖时，后续搜索与正文核对仍不可省略。虚线是后续取证要求，不表示仓库图（RepoMap）自动执行了正文读取。

get_tags_raw 使用语言查询（Query）抽取定义（Definition）/引用（Reference）标签（def/ref）；get_ranked_tags 建立从引用方（Referencer）指向定义方（Definer）的文件图，并将已在聊天中的文件、提及的名称等作为排序信号。get_ranked_tags_map_uncached 尝试不同长度的排名前缀，调用 to_tree 渲染后再计量。缓存和启发式使它可用于交互，但也会带来语言解析、刷新和排序误差。

这条链的关键是保留“谁依赖谁”，而非让模型先读完整仓库再生成摘要（Summary）。它把模型输入（Model Input）选择中的一部分工作交给确定性的程序。

求解时，每一轮都用上一轮所有节点（Node）的分数同时计算新分数，不能刚更新一个节点（Node）就拿新值计算本轮另一个节点（Node）。一般图还会有无出边节点（Dangling Node）：其分数需要按指定的归一化（Normalization）分布重新分配，否则上式会漏掉这部分概率质量；图算法库 NetworkX 未另指定无出边再分配分布（Dangling Distribution）时使用上述个性化关注分布（Personalization）。个性化（Personalization）、带权转移和无出边节点（Dangling Node）处理是不同输入，不能只说“按被引用次数排序”。

用一个完整数值程序核对同步更新

下面是纯教学 Python 程序，直接实现上面两式，不调用 Aider。old 始终保存上一轮分数，new 只接收本轮贡献；遇到无出边节点（Dangling Node），把它的分数按关注分布重新分配。输入限定为同一组节点（Node）、非负边权和总和为 1 的分布，这些条件保证每轮总分保持为 1。

from math import isclose

def rank_step(old, edges, attention, damping=0.85):
    nodes = set(old)
    assert nodes == set(edges) == set(attention)
    assert 0 <= damping < 1
    assert all(x >= 0 for x in old.values())
    assert all(x >= 0 for x in attention.values())
    assert isclose(sum(old.values()), 1.0)
    assert isclose(sum(attention.values()), 1.0)
    new = {v: (1 - damping) * attention[v] for v in nodes}
    for u in nodes:
        assert set(edges[u]) <= nodes
        assert all(weight >= 0 for weight in edges[u].values())
        total = sum(edges[u].values())
        # 正出边按边权分配；没有正出边时按关注分布分配。
        transfer = ({v: weight / total for v, weight in edges[u].items()}
                    if total > 0 else attention)
        for v, fraction in transfer.items():
            new[v] += damping * old[u] * fraction
    assert isclose(sum(new.values()), 1.0)
    return new

edges = {"A": {"B": 1}, "B": {"C": 1}, "C": {"C": 1}}
attention = {"A": 1, "B": 0, "C": 0}
rank = {v: 1 / 3 for v in edges}
for iteration in (1, 2):
    rank = rank_step(rank, edges, attention)
    print(iteration, " ".join(f"{rank[v]:.4f}" for v in ("A", "B", "C")))

这能解释为什么起点只有命令行接口（CLI），文件访问层仍会进入候选（Candidate）。也立即暴露代价：高中心性不是“错误一定在这里”。真正错误可能只是 A 把路径拆成了两个参数，C 的实现完全正确。排序是在安排观察顺序，不是在判定根因。

从排名到词元（Token）预算（Budget），仍有一次选择

假设三个候选（Candidate）结构片段分别占 80、120、160 词元（Token），预算（Budget）为 250。即使第三项相关，也不能因此把三项全文全放进去；先保留前两项，共 200 词元（Token），剩余细节可由后续读取补足。这是教学算例，用于区分“排到前面”和“最终进入请求”。

源码中的预算（Budget）搜索是近似过程：它渲染排名前缀后计量，并接受接近目标的误差；ok_err=0.15 的判定可接受略高于目标的结果，较长文本的计数也使用采样估计。因此不能把仓库图（RepoMap）预算（Budget）写成严格不可超过的请求上限。最终请求还包含系统指令、聊天和正文，需要另一层总预算（Budget）管理。这里依据前述预算（Budget）搜索函数 get_ranked_tags_map_uncached 及其计数函数 token_count 的分支，不是运行测量。

根据已有线索选择检索方法

下面是方法层比较，不是测得的项目排名：

表 4 / Table 4 · 根据已有线索选择检索方法
已知条件更直接的起点必须保留的不足
报错里有精确函数名或字符串词法搜索（Lexical Search）定位命中，再读上下文（Context）同名、包装层、生成代码可能误导
知道入口，关键逻辑分散在依赖文件结构图传播、展示定义（Definition）及关系静态标签不能保证解析出运行时全部依赖
只有业务描述，没有源码术语语义检索（Semantic Retrieval）可补充候选（Candidate）语义相近不等于调用关系，也不等于正确实现
已锁定错误发生的几行精读正文、调用点和约束此时继续扩大仓库图（RepoMap）可能只增加噪声

这些方法可以串联：词法/语义召回提出候选（Candidate），结构关系扩展邻域，正文读取核对假设。仓库图（RepoMap）补充的是代码结构的输入选择；第36章中的会话（Session）压缩（Compaction）和长期记忆（Long-Term Memory）维护仍负责另外两类信息。

回到 Maka：何时才值得加地图或索引

在前面的四文件任务里，按 import 回读（Readback）已能闭合主要证据；Aider 的图排序不自动补出正确测试命令，更不会证明 % 100 是根因。若换成数千文件、业务描述没有源码术语、同一调用邻域反复查找，结构地图或语义候选（Candidate）才可能节省搜索轮次。它们增加的是发现入口的能力，仍要把候选（Candidate）交给当前正文读取和任务验证。

Maka 索引扩展的参考合同分成三部分；以下是设计方案，不是 Maka 已实现的索引：

  • 生产和新鲜度。 谁从哪个工作区（Workspace）的哪些文件生成符号或文本切片（Chunk），何时更新、撤回删除项；返回候选（Candidate）要带可回读（Readback）的文件/符号位置及生成时的内容标识。旧地图只记录旧观察，当前 Read 是较新的观察，两次观察间仍没有跨调用快照保证。若文件已移动或正文改变，就重新定位，不用旧索引片段直接生成写入前提。
  • 选择和授权。 查询（Query）要带任务与代码范围，返回候选（Candidate）的来源、覆盖缺口和截断边界；检索与回读（Readback）都须服从当前可读范围，不能让已失去访问权的内容通过缓存摘要（Summary）泄露。提高前 k 项（Top-k）上限只解决候选（Candidate）截断，修正错误作用域（Scope）、语言过滤或失效项需要改变生产/查询（Query）合同。
  • 消费和代价。 指定哪个入口把候选（Candidate）变成回读（Readback）、哪一层分配最终输入预算（Budget），保留路径出处和读取时点；以任务完成、证据覆盖（Evidence Coverage）、无关输入、调用延迟及索引维护成本共同评估。不能用近似最近邻（Approximate Nearest Neighbor，ANN）搜索找回精确向量近邻的比例代替任务证据召回，更不能只因返回了相近段落就称为有材料支持的回答。

稀疏/稠密、近似最近邻（ANN）、融合与重排的结构推导见通用检索专题；候选（Candidate）预算（Budget）与最终证据覆盖（Evidence Coverage）的完整演算见其数值例子。

图排序与检索失败：直接问答

图的节点（Node）与边分别表示什么？

本章 Aider 链中的排序图以文件为节点（Node），引用方（Referencer）指向定义方（Definer），让引用方（Referencer）文件的分数沿依赖关系传给定义（Definition）所在文件。它不是直接对所有函数建立调用图；动态派发等关系也可能缺失。

用户提及文件以后，为什么还要再按定义（Definition）选择？

提及信号改变个性化（Personalization）关注分布，影响文件排序；源码再沿出边把文件分数分给被引用的定义（Definition），最后渲染排名前缀并估算成本。文件重要只说明值得检查，定义（Definition）选择才把结构线索压成有限输入，二者都不证明根因。

动态插件没有静态调用边时，参考处理是什么？

旧排序可能没有通往插件实现的路径。定向搜索插件名和加载配置，再回读（Readback）实际绑定入口，可以补足这条缺边；若行为取决于运行时加载，静态地图本身无法证明当时加载了哪个实现。

查询（Query）范围与文件时点变化后的结果

题 1：零命中要修哪里？ 仍是上面的 JavaScript 测试夹具（Fixture），工具可用且路径有权限；模型发出 Grep({pattern:"formatDuration",path:".",glob:"*.py"}) 得到空 matches。它准备把候选（Candidate）上限从 200 提高到 2,000，并认为不行就需要向量表示（Embedding）。应先改什么，回读（Readback）什么，何时才能说缺少实现？

参考答案。 先改错误的语言过滤，或用 Glob 确认实际 .js 文件；再搜 formatDuration，读测试中的 import 与目标实现。扩大候选（Candidate）上限不能找回被过滤掉的 JavaScript 文件；已绑定环境的 Grep 本身也没有这个上限参数可由模型调到 2,000。即使正确范围内仍零命中，也只能说明这次词法查询（Query）未找到，应再查任务入口、别名或配置；本例已有直接 import，不能据一次错误查询（Query）认定仓库缺少实现或必须上语义索引。

题 2：索引和当前文件冲突时信谁？ 这是对测试夹具（Fixture）的虚构时序变体：旧地图保存 % 100，另一位开发者随后已把当前文件改成 % 60；智能代理（Agent）用旧地图定位后，Read 看见 % 60，而它手上的失败日志来自修改之前。它能否再次把旧片段写回、直接宣告修好，或只刷新地图就完成任务？

参考答案。 三者都不成立。旧索引有定位价值，不能覆盖较新的正文；旧失败日志也不能证明当前版本仍失败。应确认当前函数及测试契约，基于当前文件做验证，并核对实际差异及责任范围；当前状态（State）已满足要求时无需重复编辑。刷新地图能改善后续发现的新鲜度，却不是行为验证。若又有并发修改，Read 本身没有锁住后续文件，应重新取得写入前提，而不是把“刚读过”当成原子快照。

仓库图（RepoMap）适合提供大仓库中的结构定位线索；是否值得采用，仍要看它能否减少漏查和无关读取，以及增加了多少构图与更新成本。
