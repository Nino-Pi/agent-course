第 13 章｜Session、Turn、Run 与 Owner

本章概览

核心问题：同一会话中的多项工作、多次模型调用和重试，怎样归到正确的身份与负责者？

关键概念：Session（会话）标识长期归属；Turn（轮次）标识一项顶层工作；Run（运行）标识具体执行；Owner（所有者）拥有相应状态的决定权。

关系主线：会话容纳不同工作，一次执行又可包含多个模型和工具步骤。身份说明“是哪一份”，owner 说明“谁能决定”；进程、数据库写入能力和界面显示不能代替这两种关系。

沿用 第12章 的一次完整请求，下面把 S1、T7、R7 与模型调用分别定位。

核心路线

“正在运行”需要哪些身份

Agent 系统里很容易出现一句含糊的话：

“这个任务正在运行。”

但工程上必须继续追问：

  • 是哪个长期会话里的任务？
  • 用户提出的是哪一项工作？
  • 系统具体执行的是哪一次 Run？
  • 谁有资格决定它能否开始、是否结束？
  • 一次 Run 里的第几个模型请求出了问题？

只更新 README 的例子用 S1 / T7 / R7 分别标识会话、工作和执行，所有者（Owner）则标识谁负责决定状态变化。完整 formatDuration 修复的工具步骤更多，但区分身份的方法相同。

工作归属、顶层意图与具体执行

三个身份分别标识不同时间尺度。先把它们放进同一项 README 任务，后面再看重发请求时哪些身份应该保持：

表 1 / Table 1 · 工作归属、顶层意图与具体执行
身份回答的问题本例中的对象
Session（会话）S1这些前后相关的工作归到哪里？同一项目的长期会话，还可容纳后来的新任务
Turn（顶层工作）T7用户这次要求完成什么？读配置和 README、修改测试说明、跑测试、中文总结
Run（具体执行）R7哪次执行在落实这项工作？驱动模型与工具，并保存本次执行身份、过程和结果

Owner 回答的是谁有资格为某种状态作最终决定。身份把事实归到正确对象，owner 再决定这个对象能否进入下一状态。

例如，Storage 可以帮忙写入 Run 状态，但不因为“它会写数据库”就有资格自行决定新工作应该开始。机制和决定权不是一回事。

为什么不能只用一个 taskId

初学项目常常会设计一个万能 taskId，既表示聊天，又表示用户消息，又表示一次模型调用。Demo 阶段很方便，进入真实生命周期后就会出现歧义。

设想下面过程：

  1. 用户在同一个聊天房间里先问“项目怎样运行？”；
  2. 接着发起 T7，让 Agent 修改 README 并测试；
  3. R7 内部连续调用模型四次；
  4. 网络断开，Client 重发同一个 T7；
  5. 稍后用户又在同一房间提出另一项工作 T8。

如果只有一个 taskId，很难同时回答：

  • 哪些历史属于同一个长期房间？
  • 重发的是同一用户意图还是一项新任务？
  • 哪组模型和工具事件属于同一次执行？
  • 哪次重新请求模型只是 R7 内部的重试，而不是新 Run？

Session、Turn、Run 是把不同时间尺度分开的三把尺子。

Session：长期存在的工作房间

会话（Session）保留长期对话及关联的项目背景，身份是 sessionId。这里的“工作房间”是逻辑归属，不是磁盘上的目录。

可以把 S1 想成一间项目工作室：项目与会话设置、以前完成的 Turn、当前工作状态和未来的新 Turn 都归到这间工作室。某次工作结束，房间仍可继续使用。

Session 解决什么问题

Session 把多项前后相关的工作放进同一长期边界。关闭 Client 再打开，S1 仍可以从持久存储中被识别；它不是某个 React 组件或某条 WebSocket 连接的寿命。

Session 不是什么

  • 不是一次模型 API 请求；
  • 不是一条用户消息；
  • 不是一段只存在内存中的聊天数组；
  • 不是“当前正在执行的函数调用栈”；
  • 也不天然等于一个 Git 仓库。

统一案例中的 S1

T7 开始前，S1 可能已有历史。T7 完成后，用户还可以在 S1 中提出 T8，例如“再把测试步骤翻译成英文”。S1 负责长期归属，但不把所有工作混成一次 Run。

Turn：用户能够指认的一项顶层工作

轮次（Turn）是 Session 中的一项顶层工作，身份是 turnId。

T7 对应的用户意图是：

检查 package.json 与 README.md，更新 README 的测试步骤，运行测试，最后用中文总结；以后也请记住我希望使用中文解释。

为什么 Turn 不等于一条网络请求

Client 可能因为超时把相同 T7 发送两次。网络请求有两次，但用户意图仍应被识别为同一个 Turn。反过来，一个 Turn 也可能通过订阅、重连和多条协议消息持续向 Client 发布进展。

为什么 Turn 不等于一次模型调用

T7 内部可能有：

模型 step 1：请求两个并行 Read
模型 step 2：请求 Edit
模型 step 3：请求 Bash
模型 step 4：生成总结

四次模型交互仍服务于同一项用户工作 T7。

Run：执行工作的持久运行封套

运行（Run）包含这项工作的一次具体执行，以及随执行保存的身份、状态与记录，身份是 runId。教学案例使用 R7。“持久运行封套”（durable execution envelope）只是强调：同一次执行的记录放在一起，进程退出后还能读取。能读回记录，不表示已经恢复原来正在运行的函数；恢复未完成工作需要 第18章 的额外判断。

“封套”意味着 R7 把同一次执行产生的事实包在一起：固定的 S1 / T7 归属、执行组成信息、多个模型 step、Read / Edit / Bash 的调用与结果，以及使用量、运行事件和最终的 completed / failed / cancelled 状态。后面的嵌套图把这些归属放在同一视野里。

Run 的典型生命周期

下面的教学状态图表示一次执行可能经过的阶段，不列出产品的完整状态枚举：

created
  → running

三种身份怎样嵌套

同一 Session 中的多项工作可以表示为：

外框表示归属，内部卡片列出执行内容与记录，并不把存储记录当成下一执行步骤。图帮助区分长期归属、用户工作与具体执行，不是对所有恢复路径的数量关系作承诺；Owner（负责者）另行说明谁有权决定这些状态。

Owner：谁有资格拍板

所有者（Owner）不是“代码文件归谁维护”，而是某种状态或决定的权威负责者。

最简单的判断题是：

当不同部件意见不一致时，谁的记录或决定算数？

用饭店类比

  • 顾客提出点菜请求，类似 Client 提交 Turn；
  • 前台确认是否接单，类似 Host 做 admission；
  • 厨房真正烹饪，类似 Runtime 执行；
  • 收银系统记录订单，类似 Storage 持久化；
  • 屏幕显示“制作中”，类似 UI projection。

收银系统能写订单，但它不会凭自己看到一张空表就决定“再炒一份”；屏幕也不能因为动画播放完就宣布菜已经交付。

回到 README 修复：Client 提交意图，Host 判断是否接纳，Runtime 驱动执行并确定执行结果，Storage 提供保存机制，Client 再展示结果。若 Client 仍显示“运行中”，负责执行状态的持久记录却已结束，应更新显示；不能让界面要求文件再改一次。这样就把“谁会存、谁会画”与“谁有权决定”区分开了。

把身份放回一次真实工作

第22章 的 Maka 修复是一项用户任务，记录为一个 Session 中的一个 Turn 和一个 Run；内部却有 7 次模型请求与多次 Read/Edit/Bash。因此每问模型一次，不等于新建一个 Turn 或 Run。这组记录中的 7 次请求计算的是模型交互次数，用户工作仍只有一项。

核心问题解析

问题 1。 在 S1 中完成 T7 后又开始 T8，哪些身份不变，哪些代表新工作？

解释。 Session S1 保持长期归属；T8 表示新的顶层工作，具体执行拥有对应 Run。不要把连接重建当成创建新 Session。

问题 2。 T7 内模型连续请求 Read、Edit、Bash，是否意味着创建了三个 Turn？

解释。 不是。多个模型 step 和工具调用可以共同服务一个 Turn / Run。这里的编号用于区分层次，不能用网络请求次数代替工作次数。

问题 3。 Storage 能写入接单记录，为什么不表示它独自决定接单？

解释。 写入是机制，是否允许工作开始由相应业务 owner 判断。需要核对调用者、准入规则与已保存事实，而不是由能写数据库推导决定权。

实现深化

Root execution：Host 当前接纳的顶层执行

Root execution描述 Host 的准入范围：这是某个 Session 当前被接纳的顶层工作。

对 T7：

root execution identity = { S1, T7, R7 }

Maka 由 Host 接纳顶层工作时，要维护一个重要约束：同一个 Session 同时最多有一个待执行或活跃的顶层工作（pending/active root execution）。这可以防止下列冲突：

用户消息 T7 正在修改 README
+ 定时任务同时启动另一项顶层修改
+ 持续目标控制器同时开始下一轮

它们若未经协调共同写同一 Session 的顶层状态，Client 很难得到一致顺序，恢复也会变得含糊。

这条约束不表示什么

  • 不表示整个 Maka 只能串行执行一个任务；
  • 不表示不同 Session 之间不能并行；
  • 不表示 Runtime 内所有可能执行都被简化成单值；
  • 不表示关联子代理（linked subagent）与父任务共享一个无边界的 Run。

Maka 用带父子关联信息（lineage）的子会话（child Session）承载这种子代理。它有自己的组合、历史和生命周期；第23章将展开委派与结果交付，本节只用它说明父子任务的身份边界。

系统发起的 Turn 与普通用户 Turn

Maka 的顶层工作也可以由持续目标（Goal）、定时任务（ScheduledTask）或依赖图的唤醒机制（Agent Graph wake）发起。它们分别依据目标进度、到期时间或依赖状态提出新工作，第24章再展开各自控制逻辑。无论来源如何，都应走统一的 hosted root execution authority，而不是每种功能各自偷偷实现第二套 Agent loop。

Run 内的逻辑调用与物理 attempt

R7 可以包含多个逻辑模型调用，也就是循环中不同步骤的模型请求；其中某一步在受控重试时，又可能发出多个物理 attempt，即实际向模型服务发送的请求尝试。

Run R7
  ├─ logical model call C1
  │    └─ physical attempt A1
  ├─ logical model call C2
  │    ├─ physical attempt A2a
  │    └─ physical attempt A2b（只有规则允许时）
  └─ ...

所以看到 provider 发出两次请求，不能立刻推断系统建立了两个 Turn 或两个 Run。

预算限制的是哪一个单位？

区分身份之后，再问“最多还能运行几次”才有明确含义。当前默认 AiSdkTurn 的几种限制作用在不同单位上：

表 2 / Table 2 · 预算限制的是哪一个单位？
限制计算什么不应推导什么
maxSteps一次 send 中已完成的模型 step；本次输入可覆盖 backend 配置一个 step 只有一个工具，或它是所有网络请求的次数上限
provider attempt 限制与恢复条件同一步中能否再发一个物理请求有剩余 attempt 就必定安全；还需检查输出/效果、错误类型与剩余 step budget
Context window / 输入容量一次模型请求能否容纳当前输入还有输入空间就允许无限循环，或压缩成功等于得到更多执行步骤

这些限制各自解决一个问题，也都不直接等于金额预算。此处没有假定产品默认固定为三步；下面是调用者提供 maxSteps=3 的源码推演，不是实际执行记录：

R7，maxSteps = 3
  step 1：请求两个 Read → 两个结果已结算        已完成 step = 1
  step 2：请求 Edit → 编辑结果已结算           已完成 step = 2
  step 3：请求 Bash → 测试结果已结算           已完成 step = 3
  第 4 步总结需要再次调用模型                  没有剩余 step

在没有另一个优先交接控制权（handoff）的原因、最后以 tool-calls 结束的这个分支里，Runtime 不再请求总结，而是以 step_limit 结束，映射为 failed。测试可能已经通过，但“四步旅程”还没全部完成；系统不能编造未产生的模型总结。反过来，若最后允许的 step 已正常给出最终回答，不应只因数字达到上限就判它失败。

再假设 step 2 的第一次 physical attempt 在形成任何可观察输出前断开：若错误和恢复额度允许，可仍在 R7 内发下一 attempt。这种不完整流没有形成已完成的 step，不会仅因建立过一次连接就消耗一个 step；但它可能已经产生 provider 请求或成本，不能把“未计为完整 step”写成“没有调用模型”。一旦出现工具活动或回答文本，判断又不同，不能只数次数决定重试。

AiSdkTurn 用 runtimeSteps 计数、mayTakeAnotherStep 判断能否继续，再由 provider retry guard 判断失败请求可否重发。这三处分别回答“已完成多少”“还能否继续”“失败请求可否重发”，不能共用一个计数推断。

身份简图的适用范围

这是一张教学简图，不应被推广为“任何 Turn 在所有情况下永远只能有一个可能的执行记录”。在当前普通 hosted root 主路中，durable admission 会固定 exact {sessionId, turnId, runId}；协作式 Host 交接提供了一个具体例外：原物理执行（invocation）在持久边界封存，后继物理执行继续同一逻辑 Turn，顶层准入仍拥有决定权。这里先区分逻辑工作与物理执行，交接与持续工作将在第24章展开。它不等于第二项用户任务或重新执行已完成的工具。

持久身份与进程寿命分别记录

假设进程 P1 已完成并保存 S1/T7/R7，随后退出。以后 P2 读取 S1 的记录，在用户新请求 T8 被准入后执行 R8。S1 的身份持续存在，P1 的调用栈没有回来，R7 的终态也没有重新打开。这个教学例子说明长期身份与进程寿命可以分开；它没有证明未完成的 R7 能在任意机器接着跑。

读历史、接纳新工作、恢复未完成的执行，是三个不同操作。后者还需要核对执行接手、实际文件、权限与结果未知的边界，见 第18章。一份持久记录不能自动带来休眠、跨机器迁移或原进程恢复；这些能力还需要各自的执行合同。

再改变一个条件：P1 留下了 R7 的回答文字，却没保存 terminal 就退出。S1/T7/R7 的身份仍可找到，但它只帮助恢复程序定位该查哪份记录，并不证明 R7 成功。当前普通恢复路径若没有续接认领（continuation claim，即已有控制者声明负责后续推进）或执行交接（handoff），会把这种开放执行收束为 failed / app_restarted；如果原 terminal 已经存在，则保留原结果。新进程先读事实，再由相应 owner 决定接下来做什么，不能因为重新找到 R7 就重放全部动作。

这里的“恢复成功”可能只表示正确记录了中断。恢复观察读取已有结果，重建输入准备后续请求，收束中断保存失败终态，继续执行则需要相应 owner 的准入决定。一份回答和四条持久记录展示了这些操作怎样分开。

这里的终态认领与屏障用于协调竞争的结束信号、确认结果提交，下一章再拆解。不同业务域（domain）的协调器（coordinator）各自维护规则，账本保存相应事实。一个部件能够读写记录，并不因此获得表中其他决定权。

Authority 与 mechanism：决定权和实现手段要分开

Authority可以翻成“最终裁决权”。Mechanism是实现这种决定的手段。

例如：

RootTurnCoordinator 决定并组织 T7 的准入
Storage 提供原子追加（append）和比较后更新（CAS）等写入机制

这里的 CAS 指先核对预期状态，仍匹配才接受更新；它帮助拒绝过时写入，不替业务层判断用户意图。Storage 当然很重要，但仅有这些通用写入机制，还不能自行决定：

  • T7 是用户消息还是 ScheduledTask；
  • 是否符合业务层 exact retry 规则；
  • 是否应该等待另一项 root execution；
  • 发生歧义时产品应该停止操作（fail closed）还是继续。

因此：

谁把数据写进去  ≠  谁拥有这项业务状态

同样：

谁把状态画出来  ≠  谁拥有这项事实

invocationId：从 opening 到 terminal 的执行事实坐标

Maka 的 RuntimeEvent 等记录还会携带 invocationId（执行事实关联坐标）。对普通 production Run，当前实现通常让它绑定为 runId，所以 R7 的事件往往有 invocationId = R7。

opening 指执行开始记录，terminal 指执行结束记录。这个坐标把执行事件、工具恢复或后续续接中的相关事实关联起来，而不新增独立的调度层：

Session / Turn / Run  是主要生命周期身份
invocationId          是 opening / events / terminal 的执行事实坐标

“当前值相等”也不表示两个概念的语义永远完全相同。当前 RuntimeInvocationRecord 已从 opening + events + terminal 重建这次执行；历史 codec 与 continuation 也依赖该关联。它有明确数据结构，但不新增独立调度器。

身份必须在哪些地方保持一致

从 T7 准入到 R7 完成，至少要跨越下面边界：

Client request
  → Host admission
  → Runtime start
  → invocation_opened（执行事实）
  → RuntimeEvents
  → Tool journal
  → terminal snapshot
  → Client projection

每一层都不能随手换一个新的 runId。例如 Host 已把 T7 准入为 R7，而 Runtime 回报它启动的是 R9，这不是“小差异”，而是身份不变量被破坏。系统无法再可靠回答哪些事件属于已准入工作。

为什么“同一个 ID 重试”也要检查内容

假设第一次提交：

T7 = “只读取 package.json”

网络超时后，第二次却提交：

T7 = “删除整个项目”

如果 Host 只检查 turnId 相同，就可能把完全不同的意图伪装成同一个重试。Maka 因此要求 exact retry（原请求的精确重试）匹配已经固定的 payload 和 descriptor：payload 是提交的任务内容，descriptor 是本次执行的描述。这里先抓住共同作用——身份相同时，内容也必须与已经接受的那一份匹配；内容漂移应被拒绝。

这条规则同时保护：

  • 幂等重试；
  • 审计可解释性；
  • 权限决策的一致输入；
  • 恢复时对原始意图的判断。

正常例子和失败例子

正常例子：T7 只被执行一次

Client 提交 S1/T7
→ Host 准入并固定 R7
→ Runtime 明确启动 R7
→ 所有执行事件携带一致身份
→ R7 写入 completed terminal
→ Client 显示 T7 已完成

即使 Client 中途断线再连接，身份仍能闭合。

失败例子一：重复提交相同 T7

如果内容完全一致，Host 可以识别已有 admission，而不是偷偷创建另一个会产生重复副作用的 Run。具体返回和恢复方式取决于当前事实状态。

失败例子二：同一 T7 的 payload 漂移

Host 应拒绝把新内容塞入旧身份。用户若真想发起不同工作，应使用新的 Turn identity。

失败例子三：UI 显示 running，但 R7 已 terminal

这可能只是 Client 断线或投影未更新。恢复时应从 canonical facts 重建，而不是要求 Runtime 再执行一次。

常见误解

误解一：“Session 就是一串 messages”

Messages 只是可展示内容的一部分。Session 还关联执行、权限、continuity 和其他 domain 状态。

误解二：“一次用户消息只会有一个模型响应”

Agent Turn 通常通过多个模型—工具 step 才得到最终回答。

误解三：“数据库是唯一 Owner”

数据库可以是 durable authority 的承载机制，但具体业务 owner 仍由 coordinator/runtime contract 定义。Maka 也不是所有事实都塞在一张表里。

误解四：“同一 Session 同时最多一个 root，所以不能有 Subagent”

linked subagent 使用 child Session；不同 Session 和不同作用域可以并行。约束的是同一 Session 中未经协调的顶层准入。

机制问题解析

问题 1。 provider retry 为什么通常不需要创建新 Turn？

解释。 它可以仍是同一执行中一次逻辑调用的物理 attempt；能否重试还受已发生效果与 lane 契约约束。

问题 2。 同一个 T7 携带不同内容重发，为什么应拒绝？

解释。 同一身份必须对应固定的意图和执行描述，内容漂移破坏幂等和权限判断的输入。

问题 3。 同一 Session 最多一个 pending/active root，为什么不等于整个系统不能并行？

解释。 这是单个 Session 的 Host 顶层准入范围；不同 Session、child Session 以及 Runtime 内特定作用域需分别判断。

问题 4。 假设 R7 只有三个模型 step 的额度，两个 Read、Edit、Bash 都已返回，是否保证还能生成最终总结？step 中一次安全请求重试会变成新 Turn 吗？

解释。 不保证。两个 Read 可属于同一个 step，随后 Edit、Bash 分别再用一步；没有下一模型 step 的额度就不能假造总结。允许的 physical retry 仍可在同一 Run 内；它的次数与已完成 step 数不同。
