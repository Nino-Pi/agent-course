第二部分：Maka 核心机制与任务接续 · 13 / 66

第 13 章｜工作身份（Work Identity）与负责者（Owner）

本章概览

核心问题：同一聊天里出现新任务、模型（Model）重试或进程重启时，怎样认出是哪项工作，并找到有权改变它的部件？

关键概念：会话（Session）表示长期归属；工作轮次（Turn）表示一项顶层工作；执行（Run）表示落实它的一次具体运行。身份（Identity）区分对象，状态归属（State Ownership）明确谁负责维护，裁决权（Authority）限定谁能接受状态（State）变化。

关系主线：先分清工作与内部步骤，再沿准入（Admission）、执行（Run）和读取寻找负责者（Owner）。同一身份（Identity）可以经历状态（State）变化；重试需要核对原内容，读回旧记录也不等于继续旧进程。

前情回顾：同一项工作怎样跨过多个部件

第12章沿一项README修复说明了接纳、执行（Run）和展示：宿主（Host）先保存准入（Admission）依据，运行时（Runtime）组织模型（Model）与工具（Tool），客户端（Client）再读取结果。本章沿用会话（Session）S1、工作轮次（Turn）T7、执行（Run）R7，进一步解释这些编号为什么不能合并。

任务仍是读取配置与README、更新测试（Test）入口、运行检查、核对差异（Diff）并用中文总结，还提出“以后也请记住我希望使用中文解释”。函数已经正确，四个既有测试（Test）原本通过；README却写 npm run check，配置实际提供 "test": "node --test"，所以只应把说明改为 npm test，保留函数、测试（Test）与配置。它与第04章仍含 % 100 缺陷的初态不同。

S1/T7/R7及四个模型步骤（Model Step）是教学记号。本章把测试（Test）与差异（Diff）核对安排在第三步，不固定该步内部的工具调用（Tool Call）总数；一项检查不能因为未单列编号就被省略。后面另引第22章的历史七次模型调用（Model Query），不会把两组数字拼成一次运行。

核心路线

先区分“哪项工作”与“现在怎样”

“这个任务正在运行”只给出了一个阶段，还缺少对象和负责范围。需要先定位它属于哪个会话（Session）、哪项工作轮次（Turn）、哪次执行（Run），再判断哪个负责者（Owner）的记录能回答当前问题。

表 1 / Table 1 · 先区分“哪项工作”与“现在怎样”
身份（Identity）回答的问题README案例中的含义
会话（Session），sessionId = S1前后相关的工作归到哪里？项目的长期工作空间，可以容纳以前和以后的任务
工作轮次（Turn），turnId = T7这次发起的是哪一项顶层工作？更新说明、检查结果并总结这一整项要求
执行（Run），runId = R7哪次具体运行正在落实要求？本次模型（Model）与工具（Tool）过程及其结束记录

身份（Identity）回答“是哪一份”，状态（State）回答“目前处于什么阶段”。例如R7开始时尚未结束，后来保存了合法结束记录；改变的是R7的状态（State），并不因此把它改名为R8。相反，用户另提一项T8，就不能只把旧R7重新显示为运行中来冒充新工作。

为什么一个 taskId 不够

考虑同一房间里发生的五件事：先询问项目怎样运行；接着提出T7；R7内多次询问模型（Model）；连接超时后重发T7；稍后再提出新的T8。它们同时包含长期归属、用户意图、具体执行（Run）和内部请求四种关系。

只用一个 taskId，就难以区分“重发同一意图”和“发起新任务”，也难以判断两次模型（Model）服务请求是否只是内部重试。拆开身份（Identity）不是为了多加编号，而是为了让不同操作拥有不同的判定条件。

会话（Session）：长期归属可以跨过连接与进程

会话（Session）是长期的逻辑归属。S1可以关联项目设置、历史对话、以前的工作轮次（Turn）和当前工作，也可继续接纳未来的新要求；它不等于磁盘目录或某个代码仓库。

客户端（Client）关闭再打开，不必新建S1。某个进程结束后，新进程也可以从持久记录识别它。这说明会话（Session）的寿命不依赖一条连接或一个界面组件，尚不能证明旧程序能从原暂停点继续。

同样，一份聊天消息（Message）列表只是可读材料的一部分。会话（Session）还关联权限（Permission）、工作身份（Work Identity）及其他业务状态（State）；一条模型（Model）服务请求、一个用户消息（Message）或一段函数调用栈都不能单独代表它。

工作轮次（Turn）：用户能够指认的一项要求

工作轮次（Turn）是会话（Session）里的一项顶层工作。T7包含完整的README要求，而不是其中某一次读取。

网络超时后，客户端（Client）可能发送两次相同T7。发送次数是两次，原意图仍可以是一项工作轮次（Turn）；反过来，订阅、重连和多条进展消息（Message）也可以共同服务T7。能否按原请求重试，还要核对已接受内容，不能只看编号。

这项工作可以经过四个模型步骤（Model Step）：

第一步可同时提出两个 Read，仍只占一个模型步骤（Model Step）。一项工作轮次（Turn）既不等于一个模型调用（Model Query），也不等于一个工具调用（Tool Call）。

执行（Run）：把同一次运行的记录放在一起

执行（Run）把本次过程的身份（Identity）、状态（State）和记录关联起来。R7可以包含多个模型步骤（Model Step）、工具调用（Tool Call）、工具结果（Tool Result）、使用量和最终结果。

“持久执行封套（Durable Execution Envelope）”是帮助阅读的说法：这些记录保存后还能读回。它不是原函数调用栈的快照（Snapshot），也不意味着进程退出后一定自动续跑。

状态（State）变化不需要换身份（Identity）

为了理解阶段，可以把本例概括为准备、进行中、必要时等待交互、最后结束。这是教学顺序，不是统一的产品枚举。读源码还要区分模型（Model）结束原因、运行时事件（Runtime Event）的状态（State）字段、宿主（Host）工作视图与资源清理是否结束。

例如默认流的 user_stop 会映射为 aborted，其他接口可能使用 cancelled；end_turn也不能越过先前失败分类的判断。第12章已给出映射条件，第14章会继续从终态（Terminal State）的保存与读取解释它们。不要把同一组字符串套在所有层。

三种身份（Identity）的归属图

下图限定普通教学路径中的S1/T7/R7。边界表示归属，不表示程序调用顺序；也不承诺任何恢复（Recovery）情形下都永远是一项工作配一次执行（Run）。

保存记录的卡片没有指向下一动作，因为存储（Storage）本身不会主动推进工作。负责者（Owner）及其裁决权（Authority）是另一层关系，需要沿实际控制链寻找。后面的协作交接（Cooperative Handoff）会说明，同一逻辑工作怎样保留归属而更换物理执行（Physical Invocation）。

负责者（Owner）：谁能决定，谁负责落实

负责者（Owner）指负责某项状态（State）或决定的部件，不是源文件的维护人。状态归属（State Ownership）说明哪一方维护规则和生命周期（Lifecycle）；裁决权（Authority）说明发生冲突时，哪一方有资格接受或拒绝变化。

先回到README任务：客户端（Client）提出T7，宿主（Host）决定能否接纳，运行时（Runtime）组织R7，存储（Storage）执行相应写入，客户端（Client）读取并展示结果。每一方参与了流程，参与本身不代表拥有全部决定权。

如果界面仍显示运行中，而R7的合法持久终态（Terminal State）已经存在，应更新界面，不能因此再修改一次文件。读写数据库的能力，也不能授权存储（Storage）自己决定“再接一单”。

裁决权（Authority）与机制（Mechanism）

机制（Mechanism）是实现决定的手段。例如 RootTurnCoordinator 组织T7准入（Admission），底层存储（Storage）提供原子追加与比较后写入（Compare-And-Swap，CAS）：先检查预期状态（State）仍匹配，再接受更新。

比较后写入（Compare-And-Swap，CAS）帮助拒绝过时写入，却不会自动判断T7究竟是用户要求还是定时任务（Scheduled Task）、是否符合重试条件、是否应等待另一项工作，以及遇到不确定结果时是否应停止推进。这些都是相应负责者（Owner）的规则。

问题。 最后执行数据库写入的函数，是否就是这项业务的负责者（Owner）？

参考答案。 不能这样判断。沿调用链（Call Chain）找到谁检查准入（Admission）、固定内容并处理冲突；实际写入者可能只是执行该决定。界面最后显示结果，也不因此取得终态（Terminal State）的裁决权（Authority）。

把身份（Identity）放回一份历史运行

第22章的Maka修复记录了一项完整函数与文档修复：一个会话（Session）中的一项工作轮次（Turn）、一次执行（Run），内部有7次模型调用（Model Query）及多次 Read/Edit/Bash。这里沿用该历史记录，没有把本章只改README的四步教学过程当成它的实际轨迹（Trajectory）。

这组7次统计的是模型（Model）交互次数，不是7项用户工作。它也不能单独说明每次失败请求背后的物理请求尝试（Physical Attempt）总数；统计单位必须随证据一起说明。

核心问题解析

问题1。 S1中完成T7后发起T8，哪些对象保持，哪些发生变化？

参考答案。 会话（Session）S1保持长期归属；新的工作轮次（Turn）T8拥有相应执行（Run）。一次重连不自动创建新会话（Session），一个旧状态（State）变化也不自动创建新工作。

问题2。 两个 Read、一个 Edit和后续检查，为什么不按工具（Tool）数创建工作轮次（Turn）？

参考答案。 它们共同服务同一意图。工具调用（Tool Call）是执行（Run）内部动作，一个模型步骤（Model Step）也可以提出多个动作；不同层次必须分别计数。

实现深化

顶层执行（Root Execution）：同一会话（Session）的准入（Admission）范围

顶层执行（Root Execution）描述宿主（Host）当前接纳的整项工作。普通路径会固定精确的 {sessionId, turnId, runId}，本例就是 {S1, T7, R7}。同一会话（Session）同时最多有一个待执行或活跃的顶层执行（Root Execution），以协调用户消息（Message）、定时任务（Scheduled Task）和持续目标（Goal）提出的工作。

这个约束限定的是宿主（Host）准入（Admission）范围，不是整个系统只能串行工作。不同会话（Session）可以并行；运行时（Runtime）内部能表示多次活跃执行（Run），也不代表产品允许未经协调的多个顶层写操作。

关联子代理（Linked Subagent）使用带父子关联信息（Lineage）的子会话（Child Session），拥有自己的组成、历史和生命周期（Lifecycle）。它不会无边界地共用父任务的R7。第23章再展开委派；这里先保留父子身份（Identity）的区别。

系统发起的工作轮次（Turn）

持续目标（Goal）、定时任务（Scheduled Task）或依赖图唤醒（Agent Graph Wake）也可以提出新工作，分别依据进度、时间或依赖条件。它们仍应经过宿主（Host）的顶层准入（Root Admission），不能各自另启一套未经协调的代理循环（Agent Loop）。第24章继续解释相应控制规则。

模型步骤（Model Step）与物理请求尝试（Physical Attempt）

R7内的模型调用（Model Query）表示循环中的一次逻辑请求工作；受控重试可能使它包含多次实际发往模型服务提供方（Provider）的物理请求尝试（Physical Attempt）。下列编号只是层次示意：

执行 Run R7
  ├─ 模型调用 Model Query C1
  │    └─ 物理请求尝试 Physical Attempt A1
  └─ 模型调用 Model Query C2
       ├─ 物理请求尝试 Physical Attempt A2a
       └─ 物理请求尝试 Physical Attempt A2b（规则允许才重发）

A2a与A2b不自动成为两项工作轮次（Turn），也不要求建立两个执行（Run）。但它们确实可能产生两次服务请求与费用，不能因为逻辑归属相同就把第二次当作没有发生。

源码还要处理停止和交接（Handoff），不能只算减法。下面是 AiSdkTurn 的真实片段（Apache-2.0）：先判断上限，再处理沙箱边界（Sandbox Boundary）的专用收束条件，最后决定能否继续。

          const stepLimitReached = maxSteps !== undefined && runtimeSteps >= maxSteps;
          if (
            sandboxBoundaryFinalizationStep ||
            (stepLimitReached &&
              (toolRuntime.shouldFinalizeSandboxBoundary() ||
                toolRuntime.hasSandboxBoundaryDenial()))
          ) {
            this.loopStopReason = 'permission_handoff';
            this.loopStopRequested = true;
          }
          const mayTakeAnotherStep = !stepLimitReached && !this.loopStopRequested && !this.aborted;

runtimeSteps记录已完成模型步骤（Model Step），maxSteps是本次适用上限；loopStopRequested与aborted分别表达已请求停止和中断条件。sandboxBoundaryFinalizationStep及两个工具（Tool）边界判断用于专用交接（Handoff），这里完整保留，避免误读为“达到上限就只有一种结束原因”。

在本例没有优先交接（Handoff）或其他停止原因、最后模型（Model）以 tool-calls 结束的分支里，后续结束原因是 step_limit，映射为 failed。反过来，若最后允许的一步已正常给出最终回答，不应只因达到数字上限就判失败；其他已记录失败仍须按第12章的条件处理。

再改变一个条件：第二步第一次请求在形成可观察输出前断开。只有错误、恢复（Recovery）额度与剩余步骤均允许，才可在R7内重发。这类未完成流没有形成已完成步骤，不能仅因连接建立过就增加 runtimeSteps；已有请求与可能费用仍应如实保留。出现回答文字或工具（Tool）活动后，不能继续套用无输出重试；只有思考输出（Thinking Output）的符合条件分支另有专用封存与恢复（Recovery）规则，不能推广到全部未完成输出。

本章涉及的三组数字至此可以分清：4是教学流程所需模型步骤（Model Step），3是显式设定上限，7是另一项历史真实修复的模型调用（Model Query）数。源代码用 runtimeSteps 计数、mayTakeAnotherStep判断继续，再由物理请求尝试（Physical Attempt）的守卫判断重发，它们没有共用一个计数。

身份（Identity）简图的例外：协作交接（Cooperative Handoff）

普通顶层准入（Root Admission）固定本次身份（Identity）关系；协作交接（Cooperative Handoff）则允许原物理执行（Physical Invocation）在已证明的持久边界封存，后继继续同一逻辑工作轮次（Turn）。原准入（Admission）仍拥有裁决权（Authority），后继必须遵守已固定的关联与剩余步骤。

它改变了物理执行（Physical Invocation），不会把同一工作变成新的用户任务，也不重放（Replay）已经完成的工具效果（Effect），更不恢复旧JavaScript调用栈。图中的一对一关系因此只适合普通教学路径；具体交接（Handoff）条件见第24章。

持久身份（Identity）与进程寿命

假设进程P1已保存R7的合法终态（Terminal State）后退出，进程P2后来读取S1；只有新的T8被准入（Admission）后，才执行R8。S1持续存在，R7没有重新打开，P1的调用栈也没有回来。

再改成P1留下回答文字、尚无终态（Terminal State）就退出。身份（Identity）帮助恢复（Recovery）程序找到该查的记录，却不证明成功。对记录可读、无续接认领（Continuation Claim）、无交接（Handoff）及其他专用恢复（Recovery）条件的普通例子，系统把开放执行（Run）收束为 failed / app_restarted；已有合法终态（Terminal State）则保留原结果。

实际恢复（Recovery）还要检查导入、工具（Tool）欠缺结算、沙箱边界（Sandbox Boundary）重启归因与损坏记录等条件。严格读取失败时应报错；不能把读不到当成不存在，也不能把所有失败分类都改成 app_restarted。第14章用完整的四条记录推演这个限定例子。

invocationId：执行事实（Execution Fact）的关联坐标

运行时事件（Runtime Event）还携带 invocationId，把开始记录（Opening Event）、过程与终态事实（Terminal Fact）关联起来。在普通生产路径中，它通常绑定为 runId，所以R7的相关记录常见 invocationId = R7；当前值相同不表示语义永远相同。

RuntimeInvocationRecord 从开始记录（Opening Event）、过程和终态事实（Terminal Fact）重建一次执行（Run）的历史结构。它已有明确数据类型，历史解码与续接也使用该关联，但没有因此增加第四套独立调度器。

身份（Identity）怎样跨边界保持

从客户端（Client）请求到宿主（Host）准入（Admission），再到运行时（Runtime）启动、invocation_opened、工具（Tool）日志与最终展示，每个消费者（Consumer）都要核对相应身份（Identity）。宿主（Host）固定T7→R7，运行时（Runtime）却报告R9，不能被当作无关字段不同；那会使后续记录无法归属于已经接纳的工作。

精确重试（Exact Retry）：编号相同，内容也要相同

第一次提交“只读取 package.json”，超时后却用同一T7提交“删除整个项目”，显然不是同一个意图。精确重试（Exact Retry）因此核对已经固定的请求内容（Payload）与执行描述（Descriptor），而不只比较 turnId。

这里的请求内容（Payload）是提交的任务材料，执行描述（Descriptor）包含已固定的执行（Run）安排；实际匹配还经过对应规范化规则，不等于对任意两段原始文字作简单字符串比较。

精确重试（Exact Retry）维护幂等性（Idempotency）、审计可解释性与权限（Permission）判断的输入一致性；它没有证明任意外部操作重复执行都安全。正常路径只落实已接纳的T7，不能因为连接失败就再改一遍README。

问题1。 第三步检查全部返回，maxSteps=3是否保证还有总结？

参考答案。 不保证。两个 Read共同使用第一步，编辑使用第二步，检查使用第三步；总结需要新的模型步骤（Model Step）。没有剩余额度就不能编造回答；如果最后允许的一步已经给出回答，则应按实际结束原因与既有失败判断。

问题2。 内部服务重试会自动建立新的工作轮次（Turn）吗？

参考答案。 不会。它可以仍是同一模型调用（Model Query）内的物理请求尝试（Physical Attempt）；能否重发取决于输出、效果（Effect）、错误与额度，不由编号数量决定。

问题3。 数据库保存全部相关记录，就能成为所有状态（State）的负责者（Owner）吗？

参考答案。 不能。存储（Storage）承载已接受事实（Fact），不同协调器（Coordinator）和运行时（Runtime）合同仍分别决定准入（Admission）、执行（Run）、权限（Permission）与长期记忆（Long-Term Memory）。也不是所有事实（Fact）都放在同一张表。

问题4。 一份旧回答恢复出来，是否说明原R7已经成功续跑？

参考答案。 只说明相应内容可读。还要查看合法终态（Terminal State）及负责者（Owner）的处理决定；收束中断也可能是正确恢复（Recovery）的结果。第14章继续把记录、读取与展示分开。
