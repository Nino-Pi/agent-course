第 48 章｜设计问题与参考方案

本章概览

核心问题：一份代码修复智能代理（Agent）方案，怎样从用户要求推导出组件、执行顺序和失败处理？

关键概念：任务合同（Task Contract）规定成功条件与允许范围；组件职责（Component Responsibility）说明谁持有决定权；数据流（Data Flow）连接已有观察结果（Observation）与下一请求；状态机（State Machine）表达当前可以继续、等待还是停止。

关系主线：先固定问题，再选择满足合同的最小组件；沿一次具体修复说明各组件怎样消费信息，最后用失败条件检查方案是否闭合。验收（Acceptance）依据当前产物和检查结果，模型（Model）的完成声明只是需要核对的报告。

前情回顾：从“知道机制”到“说明设计”

第01章区分了智能代理（Agent）与运行支撑（Agent Harness）：模型（Model）提出下一步，程序提供输入、执行工具并控制工作。第04章的分秒转换展示了这条循环：先获得真实实现和断言，再修改一般规则，最后检查结果。一个正确输出能说明该输入的表现，不能独自证明所有需求都满足。

第18章中的未知效果（Unknown Effect）是“尚不能确认操作是否产生结果”，例如文件已写但回执丢失。第28章把这种问题落实到负责者（Owner）和消费者（Consumer）：谁能确认文件现状，谁会根据结果决定下一步，需要分别指出。刚读过的第47章进一步说明，局部状态不能替整项任务作结论：子产物尚未采纳（Adoption），与父任务（Parent Task）的另一次编辑结果未知，可以同时存在。

本章把这些知识收束到一个短任务。阅读时只需跟住三个问题：当前知道什么、谁据此作决定、下一步怎样得到新证据。

1. 问题与已确定的条件

一个智能代理（Agent）怎样读取代码、修复问题并验证结果？

这里固定为单用户、本地仓库、一次一个顶层任务（Top-Level Task）。用户只允许修改 README.md 和 src/duration.js，要求保留已有改动，不允许修改测试来掩盖错误。目标是修正测试步骤及 formatDuration 的一般分秒转换规则。假设原函数对 125 秒返回 2:25，应返回 2:05。

设非负整数秒数为 sss，整分钟数为 mmm，剩余秒数为 rrr。一般规则是：

m=⌊s60⌋,r=s−60m=s mod 60,0≤r<60.m=\left\lfloor\frac{s}{60}\right\rfloor,\qquad r=s-60m=s\bmod 60,\qquad 0\leq r<60.m=⌊60s​⌋,r=s−60m=smod60,0≤r<60.

因此 s=125s=125s=125 时，m=2m=2m=2、r=5r=5r=5，余秒显示为两位数字 05。旧实现若把余秒误写为 % 100，就会得到 25。这个推导说明为什么要改一般公式，而不能只把输入 125 单独写成特殊分支。

本例的任务合同（Task Contract）有三个同时成立的条件：复现问题消失，相关测试通过，文件差异（Diff）符合授权范围并保留用户内容。模型（Model）说“已修复”不能代替其中任何一项。

这些条件也限制设计规模。短任务可以采用顺序循环和有界输出（Bounded Output）；跨进程恢复（Cross-Process Recovery）是额外要求，出现后才需要相应的持久执行合同。多智能代理（Multi-Agent）、向量索引（Vector Index）或分布式调度（Distributed Scheduling）都有适用场景，此处先解决已给出的任务。

2. 完整参考方案：沿一次修复看消费者（Consumer）

先按决定权分工。任务入口（Task Entry）固定目标与允许范围；运行控制器（Run Controller）保存工作身份和预算（Budget）；上下文组装器（Context Composer）选择规则、任务、已读文件和测试结果，形成模型输入（Model Input）。模型（Model）提出行动请求（Action），工具执行器（Tool Executor）在受控环境中检查参数与当前权限（Permission），执行后将结果交回后续请求。

这里每条连接都有消费者（Consumer）。模型（Model）消费文件与失败信息来提出补丁；执行器（Executor）消费当前许可和资源前提来决定是否写入；运行控制器（Run Controller）消费工具结果（Tool Result）来更新状态。把这些内容都叫“上下文（Context）”，会遮住它们各自的决定权。

模型（Model）负责提出和解释，程序负责执行、记录与停止条件（Stop Condition）。例如模型（Model）提出的补丁已经过时，程序仍须拒绝；模型（Model）暂时没有注意到预算（Budget）耗尽，运行控制器（Run Controller）仍须阻止新的调用。

条件变长时，增加哪一层

若任务变长，上下文压缩（Context Compaction）改变后续输入表示，原始事实仍需保留可用入口。若要跨任务沿用语言偏好，则增加独立的记忆（Memory）写入、读取和注入步骤；一次要求用中文，不自动等于永久偏好。

若要求崩溃恢复（Crash Recovery），可能产生效果（Effect）的操作需要稳定身份，以及执行前后可恢复的记录。结果未知时，先向资源负责者（Resource Owner）核对。记录“开始”与记录“成功”之间仍可能发生文件写入，两个记录本身不构成跨资源原子事务（Atomic Transaction）。

4. 一份已填写的设计记录

下面的 Python 字典是方案记录，只保存数据，不实现执行器（Executor），也不是智能代理（Agent）软件开发工具包（Software Development Kit，SDK）的启动配置。按三组阅读即可：scope、allowed_writes 和 acceptance 固定合同；owners 指定谁持有决定权；normal_path 和 failure_policy 说明正常与异常时的处理顺序。

design = {
    # 合同：任务规模、允许修改的文件、交付必须满足的条件。
    "scope": {"user_count": 1, "workspace": "local", "top_level_tasks": 1},
    "allowed_writes": ["README.md", "src/duration.js"],
    "acceptance": ["一般分钟/余秒契约成立", "相关测试通过", "保留用户改动"],
    # 决定权：控制工作、提交文件、接纳结果是不同职责。
    "owners": {
        "task_and_budget": "run_controller",
        "file_commit": "workspace_executor",
        "accepted_results": "result_store"
    },
    # 消费前面的事实，再选择下一步；失败不一律重做。
    "normal_path": ["读取", "复现", "诊断", "条件编辑", "复测", "检查差异"],
    "failure_policy": {
        "stale_file": "重新读取，保留并发修改，再决定补丁",
        "effect_unknown": "查询或对账，不直接重做",
        "budget_exhausted": "停止新调用，结算已开始操作并报告未完成范围"
    }
}

allowed_writes 表达政策，工具执行器（Tool Executor）仍需落实路径和资源边界。file_commit 的条件提交（Conditional Commit）要由资源负责者（Resource Owner）在实际提交时实现；配置里填了这个名字，不会自动提供版本检查。accepted_results 保存运行程序接纳的结果，不能代替外部文件或服务的真实状态。

这三个限制解释了“设计字段存在”和“实现已经接通”的距离：记录能帮助检查职责是否遗漏，真正的保证来自消费这些字段的控制逻辑与执行入口。

6. 常见设计问题与完整回答

为什么不直接用多智能代理（Multi-Agent）？ 两个短文件的读取可以通过并行工具完成。子代理（Subagent）适合独立多步探索，或需要隔离大量上下文（Context）的工作。新增身份、输入、等待和交付都有成本；可独立验收（Acceptance）的子任务（Subtask）才能提供清楚的委派（Delegation）边界。

必须用事件溯源（Event Sourcing）吗？ 不必。恢复（Recovery）、审计（Audit）与用户界面（User Interface，UI）重建各需要某些事实，可以由状态表、追加记录或二者组合满足。选择依据是哪些状态需要原子更新、哪些过程需要重放（Replay）、哪些记录必须跨重启保留。

类型定义了 safe=true 就安全了吗？ 类型约束数据形状，真实效果（Effect）仍须经过可信授权（Authorization）与执行限制。版本条件必须在提交时成立；取消（Cancellation）也必须由执行入口处理。字段存在不能证明这些行为已接线。

方案和运行结果是什么关系？ 本章给出可实现的职责与合同，尚未报告产品运行结果。实际测试只能支持所覆盖的输入、环境和失败窗口（Failure Window）；一次正常修复不能证明所有工具都能安全恢复（Recovery）。产品比较也分别保留源码事实、公开设计与自拟方案的边界。
