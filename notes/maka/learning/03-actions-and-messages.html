第 03 章｜动作、观察与消息协议

本章概览

核心问题：模型发出的工具请求，怎样变成命令执行结果和下一轮能够读取的消息？

关键概念：Action（动作请求）描述要执行什么；Output（执行输出）包含进程结果；Observation Message（观察消息）把结果交回模型；tool_call_id（调用标识）关联请求与回执。

关系主线：解析器提取动作，环境执行命令，格式化逻辑生成观察消息。参数可解析、命令成功退出和消息协议完整分别需要检查，不能用其中一项代替另外两项。

沿用 第02章 的控制循环，下面用同一条文件读取命令展开数据转换。

请求、执行与回执

一次命令的四份数据

本节继续 README 文档修复：先读取 package.json 中的测试脚本配置和 README.md 中的命令说明，核对二者是否一致。命令沿用第02章的 sed 读法，显示两份小文件按顺序串接后的第1–220行；随后只观察同一请求怎样改变数据表示。

模型返回 tool call

以下四份数据使用虚构的调用 ID 和省略内容，只演示转换关系，不是实际 trace。arguments 是装着 JSON 的字符串，所以内层引号写成 \"。

{
  "id": "call-read-files",
  "function": {
    "name": "bash",
    "arguments": "{\"command\":\"sed -n '1,220p' package.json README.md\"}"
  }
}

Model adapter 解析成 action

{
  "command": "sed -n '1,220p' package.json README.md",
  "tool_call_id": "call-read-files"
}

LocalEnvironment 执行并返回 output

{
  "output": "...两份文件的真实内容...",
  "returncode": 0,
  "exception_info": ""
}

Model adapter 格式化 observation message

{
  "role": "tool",
  "tool_call_id": "call-read-files",
  "content": "...由模板表示的文件内容与返回码...",
  "extra": {
    "raw_output": "...真实内容...",
    "returncode": 0
  }
}

下一次 Model query 才会同时看到：

  • assistant 发出的 call-read-files；
  • tool 返回的同一个 call-read-files 的结果。

把上面同一个调用的四份数据连起来：解析改变请求的表示，执行才取得环境结果，格式化再把结果交给下一次模型。tool_call_id 沿这条转换链关联同一次请求与回执。

Action、Output 与 Observation Message

Action：希望环境做什么

Action 是从模型响应中解析出的执行请求。在默认 Bash 路径中，核心字段是：

{
  "command": "某条 shell 命令",
  "tool_call_id": "对应的调用 ID"
}

Action 可以被记录、检查或拒绝；仅仅存在于消息中不会自动改变现实。

Output：Environment 实际观察到什么

LocalEnvironment.execute() 返回的 output 主要包含：

  • output：合并后的标准输出和标准错误文本；
  • returncode：进程返回码；
  • exception_info：执行异常的解释；
  • 某些异常情况下的 extra：异常类型和字符串。

Output 描述 Environment 这一层的执行结果。

Observation Message：下一轮模型怎样看到 Output

模型 provider 不一定接受任意 Python 字典。Model adapter 必须按照当前 API 的 tool-result 约定，把 output 转成消息。

因此：

Output 是执行层结果
Observation Message 是模型输入层表示

两者有关联，但不能混为同一个对象。

默认路径：一个 Bash 工具类型

默认配置给模型一种名为 bash 的工具，参数 command 表示希望执行的命令。工具类型只有一种，一条响应仍可能请求调用它多次；比如分别读取两个文件。schema（参数结构声明）规定允许的字段和类型，parser（解析器）负责实际提取和检查；两者是否覆盖同样约束仍需分开核对。

Bash 是一个宽工具表面

虽然只有一个工具名，Bash 本身可以表达很多操作：

  • 读取文件；
  • 搜索代码；
  • 修改文件；
  • 启动测试；
  • 调用其他本地程序；
  • 在宿主环境允许时接触网络或系统资源。

所以“工具数量少”不等于“能力范围窄”。一个宽泛的 shell 工具可能比十个小工具拥有更大的现实影响面。

人工确认不能替代执行时的强制隔离。

为什么必须保留 tool_call_id

假设一条 assistant message 请求了两个 Bash calls：

call-A：查看 package.json
call-B：查看 README.md

下一轮模型不能只看到两段没有身份的文本，否则无法可靠判断哪段 output 对应哪个请求。

配对关系应该是：

assistant tool call A ───── tool result A
assistant tool call B ───── tool result B

tool_call_id 就是这条局部配对键。

这个 ID 只关联局部工具请求与结果，不承担整个用户任务或一次完整执行的身份语义。

每次执行换进程，文件变化却可以留下

每个 action 都创建 fresh subprocess

v2.4.6 的 _run() 对每次 action 调用 subprocess.Popen(...)。因此每个 action 都启动新的 shell 进程，而不是在一个长期存活的交互式终端中连续敲命令。

进程状态与文件状态的寿命不同：

会持续的：写入磁盘的文件变化
不会自动持续的：只存在于某个 shell 进程里的 cd、export、临时 shell 变量

例如第一轮执行：

cd packages/app

下一轮新的 subprocess 不会自动留在 packages/app。如果后续命令依赖该目录，需要在同一个 action 中写 cd packages/app && npm test，或者让 Environment 使用明确的工作目录（cwd）。这里用 && 表示只有切换目录成功才运行测试，避免目录不存在时在错误位置继续执行。

相反，如果第一轮确实修改了 README.md，文件位于共享文件系统中，第二轮新进程通常仍能看到这个修改。

“fresh subprocess”与“全新文件系统”不是同一个概念。

LocalEnvironment 为什么不是生产级隔离

执行部件可以配置工作目录、收集输出并处理超时；这些行为并没有自动把程序限制在工作区中。对于本机文件、网络和子进程，仍要看实际执行边界。

每次启动新进程，不会自动获得新的隔离边界。 人工确认见 第05章，权限与强制隔离见 第17章。

把输出变成下一轮能读的消息

Environment 返回输出、返回码和异常说明；Model adapter 再把它们组织成当前 provider 接受的 observation。默认 native 路径使用 role: tool，并保留相同的 tool_call_id，这样结果才配回原来的请求。

模型需要有用的输出，却不一定需要整份长日志。模板可以缩短发给模型的文本；内部调试字段还可保存更多信息。因此“模型这一刻看见的内容”和“内部对象记录的内容”也要分清。模型可见文本由模板生成，内部字段是否保留则由记录路径决定。

真实 observation 中一个容易误读的 0

下面摘取后面第22章的真实命令片段，只观察命令失败怎样被消息表示，不需要先读完整修复过程。

该次模型实际运行 npm run check 2>&1 | head -10; echo "---exit: $?---"。返回正文中有 Missing script: "check"，外层命令却返回 0。管道末端及后续 echo 掩盖了原命令的失败；这说明读取 observation 要把命令结构、正文、退出状态放在一起。不能看到 0 就写“测试成功”。原片段与解释

测试命令的结果解析

问题 1。 对 npm test，分别指出 action、output、observation 是什么。

解释。 action 携带 command；output 是 Environment 返回的输出、返回码等；observation 是 adapter 转成下一轮模型可接受的消息。

问题 2。 同样 returncode 1，若输出分别是 Missing script（未找到脚本）和测试断言失败，为什么要采取不同动作？

解释。 前者未找到入口脚本，后者已运行测试并暴露程序行为。需要阅读输出，不能只用退出码分类；接下来的第04章会完整展示这两种情况。

问题 3。 第一次 action 执行 cd subdir，第二次会自动处于该目录吗？第一次写入的文件会消失吗？

解释。 不会继承进程里的 cd；每次都是 fresh subprocess。文件系统上的修改会保留，这和进程工作目录状态不同。

解析器、进程与协议变体

BASH_TOOL 定义了工具 schema

LitellmModel._query() 调用 LiteLLM completion 时，传入的 tools 列表只有一个定义：BASH_TOOL。

它的核心形状是：

{
  "type": "function",
  "function": {
    "name": "bash",
    "description": "Execute a bash command",
    "parameters": {
      "type": "object",
      "properties": {
        "command": {"type": "string"}
      },
      "required": ["command"]
    }
  }
}

这表示默认 Model 看到的工具表面非常小：

可用工具类型：bash
必填参数：command 字符串

这里的 bash 是协议名称，不保证实际解释器固定为 /bin/bash；不要仅凭工具名依赖某种 shell 独有语法。下面的 LocalEnvironment 小节继续核对实际启动方式。

不要把“单一 Bash function/tool”误读成“每个模型响应的数据结构只能出现一个调用”。parser 会遍历 tool calls 列表；这里的单一，指的是只暴露一个工具名称和 schema。

tool call 怎样被解析成 action

LitellmModel.query() 取得 provider response 后，会调用 _parse_actions()，最终进入 parse_toolcall_actions()。

没有 tool call：不是正常空动作

默认配置要求模型响应至少包含一个 Bash tool call。如果 parser 找不到任何 tool call，会产生 FormatError 消息。

为什么不把它当成“模型只是说了一段话”？因为这条 Agent 协议把行动循环定义为：每次响应必须继续以工具调用推进，完成也通过一条约定 Bash 命令表达。

arguments 必须是合法 JSON

parser 会读取 tool_call.function.arguments 并做 JSON 解析。如果模型给出：

{command: npm test}

它不是合法 JSON；正常形式应类似：

{"command": "npm test"}

解析失败会形成 FormatError，而不是把原始字符串直接交给 shell。

工具名必须是 bash

如果响应请求了未知名字，例如 read_file，parser 会拒绝，因为当前工具表面没有这个工具。

这说明：

模型能够生成某个工具名称，不等于 Agent 当前配置真的提供了该工具。

command 必须存在

即使工具名正确，arguments 中缺少 command 也会被视为格式错误。

但“存在”不等于“完成严格类型校验”。BASH_TOOL schema 声明 command 是 string，当前 Python parser 实际检查 JSON 可解析、工具名为 bash、参数是含 command 的字典；它没有再检查值是否为字符串。{"command": 123} 仍能通过这个 parser。不要从 schema 声明推导出运行时已经强制了全部参数约束，也不要把格式解析成功当成执行安全或执行成功。

通过所有检查后，parser 为每个调用产生：

{
  "command": "...",
  "tool_call_id": "..."
}

LocalEnvironment 怎样执行 action

先选择 command 与 cwd

execute(action, cwd="", *, timeout=None) 从 action 中读取 command；* 表示 timeout 只能用关键字传入，例如 timeout=15。工作目录按下面的优先顺序选择：

本次 execute 显式传入的 cwd
  ↓ 如果没有
Environment config 中的 cwd
  ↓ 如果也没有
os.getcwd()

这让同一个 Environment 可以有默认目录，也允许某次调用覆盖它。

合并环境变量

启动命令时使用：

当前进程 os.environ
  +
LocalEnvironment config.env 覆盖项

这表示配置项可以覆盖同名宿主环境变量。

但请注意：这只是传入子进程的环境。Agent 不会因为模型在某一次 shell 中执行 export X=1，就自动把这个变化写回 Python 主进程或下一次新 shell。

shell=True 表示命令由 shell 解释

Popen 使用 shell=True，所以管道、重定向和命令组合等 shell 语法可以工作。这也意味着 action 的能力面很宽，不能把它当成一个只允许读取文件的结构化工具。

再次注意：工具 schema 名叫 bash，不等于 _run() 固定启动 /bin/bash。当前实现没有显式设置 shell executable。

stdout 与 stderr 合并

源码把 stderr 重定向到 stdout，所以返回的 output 是合并流。这样模型可以在一个文本字段里看到常规输出和错误信息，但也失去了两个流的独立结构。

超时会尝试终止进程组

默认 timeout 是 30 秒。在采用 POSIX 类 Unix 进程接口的环境中，进程在新的 OS 进程会话（session）中启动；这里的 session 是操作系统组织进程组的单位。超时时尝试对进程组发送 SIGKILL，减少 shell 子进程遗留的风险。其他平台则调用 process kill。

随后 execute() 捕获异常，并返回结构化错误：

{
  "output": "超时前已经产生的输出",
  "returncode": -1,
  "exception_info": "An error occurred while executing the command: ...",
  "extra": {
    "exception_type": "TimeoutExpired"
  }
}

注意：这里的命令超时通常被转成 output，而不是直接让整个 Agent Python 进程因为该异常退出。

output 怎样变成 observation message

使用 observation_template

format_toolcall_observation_messages() 用 Jinja 模板把每个 output 的字段填成 observation 消息；Jinja 是这里使用的模板库。

默认 mini.yaml 中，短输出大致渲染为：

{
  "returncode": 0,
  "output": "..."
}

如果 output 超过配置模板中的阈值，模型可见的 content 会保留头部与尾部并报告省略字符数。当前 mini.yaml 使用 10,000 字符阈值，保留前 5,000 和后 5,000 字符。

这体现了一个重要原则：

Environment 可以产生很大的原始输出，但下一次 Model query 不一定适合看到全部文本。

请求和结果重新配对

tool-call 路径把原 action 的 tool_call_id 放进 tool result message。下一次 provider 请求才能把结果归属到正确调用。

extra 保存执行辅助字段

内部 observation message 的 extra 还可以保存：

  • raw_output；
  • returncode；
  • timestamp；
  • exception_info。

这些字段有助于 trajectory 和调试，但发送给 provider 前，Model adapter 通常会移除内部 extra。不要因为内部消息保存了更多字段，就假设模型 API 每次都收到完整内部对象。

默认 tool call 与文本代码块变体

结构化工具调用与文本围栏使用不同的解析器和结果格式。

默认路径：native tool calling

当前 mini 默认配置文件是 mini.yaml。配合默认 LitellmModel 时：

  1. 请求向模型暴露名为 bash 的 function/tool schema；
  2. 模型通过 provider 的 tool call 字段表达 action；
  3. parser 从结构化 tool calls 中读取 name 与 JSON arguments；
  4. observation 以 tool result message 返回。

所以不要把默认路径描述成“从回答里的三反引号代码块抓命令”。

变体路径：text-based parsing

mini_textbased.yaml 提供要求模型输出 mswea_bash_command 围栏代码块的 prompt/config 变体；对应的 LitellmTextbasedModel 不向 provider 传 tools，而是在响应文本中用正则提取 action。

在 v2.4.6 中，mini_textbased.yaml 文件自身没有设置 model.model_class。因此，通过当前 CLI 真正选择这条路径时，还必须同时指定 --model-class litellm_textbased，或者在合并的自定义配置里写入等价字段。只加载这份 YAML 而仍使用默认 LitellmModel，不会仅凭 prompt 自动切换 parser。

该 parser 要求恰好匹配一个 action：

0 个匹配 → FormatError
1 个匹配 → 形成 {command: ...}
2 个或更多匹配 → FormatError

因此，无论通过 CLI 参数还是自定义配置，文本 prompt 和 model_class: litellm_textbased 都必须作为同一协议理解。仅仅看见代码块模板，不应该自动假设当前 Model adapter 已切到文本解析。

两条路径共享什么

不管 action 来自结构化 tool call 还是文本代码块，进入 Agent 核心后都尽量收敛为：

{"command": "..."}

随后仍由 Environment execute，再由对应 Model adapter 格式化 observation。

两条路径不能混写什么

协议约束与实际校验问答

问题 1。 BASH_TOOL 声明 command 是 string，当前 parser 会拒绝数字 123 吗？

解释。 不会仅因其为数字而拒绝；当前 parser 检查 JSON、工具名和含 command 的字典，未检查 command 值的字符串类型。

问题 2。 一个 bash 工具类型是否只能产生一次调用？一个文本围栏是否只能含一条 shell 命令？

解释。 都不是。native 响应可含多个 bash calls；文本 parser 要求恰好一个匹配围栏，但没有把围栏内部解析成只能一条 shell 命令。

问题 3。 tool_call_id 的作用是什么？只换 mini_textbased.yaml 会自动换模型类吗？

解释。 用于把 result 配回 request。配置文件不会自动切换 model_class，必须显式选择相应 text-based wrapper。

同一命令的三次数据转换

以 npm test 为例，provider 的 tool call 最初用 JSON 字符串表达 {"command":"npm test"}，并带调用 ID。parse_toolcall_actions 解析后得到含 command 与调用关联信息的 action；LocalEnvironment.execute / _run 执行命令，返回含 output、returncode 等字段的原始结果；format_toolcall_observation_messages 再把结果变成带相同 tool_call_id 的 role: tool 消息。

因此，JSON 合法只说明请求能被解析，returncode 属于执行器观察，最终 tool 消息才是下一次 provider 请求可消费的协议表示。相关实现位于 actions_toolcall.py 与 LocalEnvironment。
