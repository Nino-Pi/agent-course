第 03 章｜行动请求（Action）、观察结果（Observation）与消息协议（Message Protocol）

本章概览

核心问题：模型（Model）发出的工具请求，怎样变成命令执行结果和下一轮能够读取的消息（Message）？

关键概念：行动请求（Action）描述要执行什么；执行输出（Output）包含进程（Process）结果；观察消息（Observation Message）承载观察结果（Observation），把结果交回模型（Model）；调用标识（Call ID）tool_call_id 关联请求与回执。

关系主线：解析器（Parser）提取行动请求（Action），执行环境（Environment）执行命令，格式化逻辑生成观察消息（Observation Message）。参数可解析、命令成功退出和消息协议（Message Protocol）完整分别需要检查，不能用其中一项代替另外两项。

前情回顾

第01章把模型（Model）的决策与运行支撑（Agent Harness）连接执行环境（Environment）的责任分开，第02章又追到一轮控制循环：先取得并记录模型（Model）请求，再执行行动请求（Action），最后把普通结果加入下一轮输入。到这里还留下一个接口问题：模型（Model）服务返回的工具调用（Tool Call）、Python 中的行动请求（Action）对象、进程（Process）输出和下一条消息（Message），究竟是不是同一份数据？

本章沿用“只修 README 测试（Test）命令”的任务，项目代码仍假设正常。先读取配置与说明，追踪同一调用怎样穿过四种表示；再解释多调用配对、进程（Process）状态和协议变体。下一章才增加函数错误，并用固定响应驱动真实执行。这里先建立一个判断顺序：请求能解析，才谈怎样执行；取得结果以后，还要检查它怎样到达下一位消费者（Consumer）。

请求、执行与回执

一次命令的四份数据

本节继续 README 文档修复：先读取 package.json 中的测试（Test）脚本配置和 README.md 中的命令说明，核对二者是否一致。命令沿用第02章的 sed 读法，显示两份小文件按顺序串接后的第1–220行；随后只观察同一请求怎样改变数据表示。

先看每份数据交给谁。消费者（Consumer）指实际读取并使用这份数据的程序部件；只把数据保存下来，还不能证明下一个部件已经取得它。

表 1 / Table 1 · 一次命令的四份数据
数据直接消费者（Consumer）消费者（Consumer）要完成什么
工具调用（Tool Call）模型协议适配器（Model Adapter）中的解析器（Parser）读取工具名与参数，形成内部行动请求（Action）
行动请求（Action）本地执行环境（Environment）取得命令，按当前工作目录（Working Directory）和执行环境（Environment）启动进程（Process）
执行输出（Output）模型协议适配器（Model Adapter）中的格式化逻辑选择文本并组成模型（Model）服务接受的观察消息（Observation Message）
观察消息（Observation Message）下一轮模型（Model）将结果与原调用配对，作为下一步判断的输入

本课程把一次向模型（Model）取下一份响应称为模型调用（Model Query）；代码中的入口通常名为 query()。这四行不是四次模型调用（Model Query）。同一请求在不同接口之间换了表示，只有执行环境（Environment）真正运行命令时，才读到文件内容。

模型（Model）返回工具调用（Tool Call）

以下四份数据使用虚构的调用标识（Call ID）和省略内容，只演示转换关系，不是实际执行轨迹（Trajectory）。arguments 是以 JavaScript 对象表示法（JavaScript Object Notation，JSON）编码的字符串；这种格式用字段和值表达结构化数据。因为这一层仍是字符串，内层引号写成 \"。

从外向内读这个对象：id 给本次调用命名；function.name 指定当前提供的 bash 工具；function.arguments 才装着待解释的参数。看到其中有一条文件命令，只能说明模型（Model）提出了请求。

{
  "id": "call-read-files",
  "function": {
    "name": "bash",
    "arguments": "{\"command\":\"sed -n '1,220p' package.json README.md\"}"
  }
}

模型协议适配器（Model Adapter）解析成行动请求（Action）

解析器（Parser）把 arguments 中按对象表示法（JSON）编码的字符串读成字典，取出 command，再把外层调用标识（Call ID）记入 tool_call_id。下面的命令内容没有改变，也尚未执行；改变的是执行环境（Environment）接收的数据形状。

{
  "command": "sed -n '1,220p' package.json README.md",
  "tool_call_id": "call-read-files"
}

LocalEnvironment 执行并返回执行输出（Output）

执行环境（Environment）这时才启动命令并取得结果。output 是返回文本，returncode 是进程（Process）结束状态，exception_info 说明执行异常。本例假设命令正常返回，所以退出码（Exit Code）为 0；省略号不是实际文件正文。

{
  "output": "...两份文件的真实内容...",
  "returncode": 0,
  "exception_info": ""
}

模型协议适配器（Model Adapter）格式化观察消息（Observation Message）

下一位消费者（Consumer）是模型（Model）服务，因此还要按它接受的协议组装消息（Message）。role: "tool" 表示这是工具结果；相同的 tool_call_id 指回原请求；content 是提供给模型（Model）的表示，extra 则是内部辅助字段。两者不必包含同样多的文本。

{
  "role": "tool",
  "tool_call_id": "call-read-files",
  "content": "...由模板表示的文件内容与返回码...",
  "extra": {
    "raw_output": "...真实内容...",
    "returncode": 0
  }
}

下一次模型调用（Model Query）才会同时看到：

  • role: assistant 消息（Message）发出的 call-read-files；
  • role: tool 消息（Message）返回的同一个 call-read-files 的结果。

把上面同一个调用的四份数据连起来：解析改变请求的表示，执行才取得执行环境（Environment）结果，格式化再把结果交给下一次模型（Model）。tool_call_id 沿这条转换链关联同一次请求与回执。

行动请求（Action）、执行输出（Output）与观察消息（Observation Message）

行动请求（Action）：希望执行环境（Environment）做什么

行动请求（Action）是从模型（Model）响应中解析出的执行请求。在默认 Bash 路径中，核心字段是：

{
  "command": "某条 shell 命令",
  "tool_call_id": "对应的调用 ID"
}

行动请求（Action）可以被记录、检查或拒绝；仅仅存在于消息（Message）中不会自动改变现实。

执行输出（Output）：执行环境（Environment）实际观察到什么

LocalEnvironment.execute() 返回的执行输出（Output）主要包含：

  • output：合并后的标准输出（Standard Output）和标准错误（Standard Error）文本；
  • returncode：进程（Process）退出码（Exit Code）；
  • exception_info：执行异常的解释；
  • 某些异常情况下的 extra：异常类型和字符串。

执行输出（Output）描述执行环境（Environment）这一层的执行结果。

观察消息（Observation Message）：下一轮模型（Model）怎样看到执行输出（Output）

模型服务提供方（Provider）不一定接受任意 Python 字典。模型协议适配器（Model Adapter）必须按照当前 API 的工具结果约定（role: tool），把执行输出（Output）转成消息（Message）。

执行输出（Output）服务于执行层，观察消息（Observation Message）服务于下一次模型（Model）输入。比如进程（Process）产生了一万多字符日志，执行输出（Output）可以保存完整文本，观察消息（Observation Message）则按模板（Template）只展示头尾，并说明省略量。两者仍关联同一调用，内容范围却不同。判断“模型（Model）当时知道什么”时，应检查实际发送的消息（Message），不能只看内部保存的对象。

默认路径：一个 Bash 工具类型

默认配置给模型（Model）一种名为 bash 的工具，参数 command 表示希望执行的命令。工具类型只有一种，一条响应仍可能请求调用它多次；比如分别读取两个文件。参数结构（Schema）规定允许的字段和类型，解析器（Parser）负责实际提取和检查；两者是否覆盖同样约束仍需分开核对。

Bash 工具的工具表面（Tool Surface）很宽

工具表面（Tool Surface）是模型（Model）能够请求的工具及参数范围。这里虽然只暴露名为 bash 的一种工具，命令字符串仍可以表达很多操作：

  • 读取文件；
  • 搜索代码；
  • 修改文件；
  • 启动测试（Test）；
  • 调用其他本地程序；
  • 在宿主执行环境（Environment）允许时接触网络或系统资源。

所以“工具数量少”不等于“能力范围窄”。一个宽泛的命令解释器（Shell）工具可能比十个小工具拥有更大的现实影响面。

人工确认（Confirmation）不能替代执行时的强制隔离（Isolation）。

为什么必须保留 tool_call_id

假设一条 role: assistant 消息（Message）请求了两个 Bash 工具调用（Tool Call）：

call-A：查看 package.json
call-B：查看 README.md

下一轮模型（Model）不能只看到两段没有身份的文本，否则无法可靠判断哪段执行输出（Output）对应哪个请求。

配对时必须同时保留来源请求和对应回执：

表 2 / Table 2 · 为什么必须保留 `tool_call_id`
调用标识（Call ID）原工具调用（Tool Call）对应观察消息（Observation Message）
call-A读取 package.json该次读取 package.json 的结果
call-B读取 README.md该次读取 README.md 的结果

tool_call_id 就是这条局部配对键。

这个调用标识（Call ID）只关联局部工具请求与结果，不承担整个用户任务或一次完整执行的身份语义。

每次执行换进程（Process），文件变化却可以留下

每个行动请求（Action）都创建新子进程（Subprocess）

v2.4.6 的 _run() 对每次行动请求（Action）调用 subprocess.Popen(...)。因此每个行动请求（Action）都启动新的命令解释器（Shell）进程（Process），而不是在一个长期存活的交互式终端中连续敲命令。

进程（Process）状态与文件状态的寿命不同。cd 改的是当前命令进程（Process）的工作目录（Working Directory），export 改的是该进程（Process）向后续子进程（Subprocess）传递的环境变量（Environment Variable）；这两项不会自动写回负责下一次启动的 Python 主进程（Process）。文件写入则作用于共享文件系统，原进程（Process）结束后，文件仍可能保留。

例如第一轮执行：

cd packages/app

下一轮新的子进程（Subprocess）不会自动留在 packages/app。如果后续命令依赖该目录，需要在同一个行动请求（Action）中写 cd packages/app && npm test，或者让执行环境（Environment）使用明确的工作目录（Working Directory），即 cwd。这里用 && 表示只有切换目录成功才运行测试（Test），避免目录不存在时在错误位置继续执行。

相反，如果第一轮确实修改了 README.md，文件位于共享文件系统中，第二轮新进程（Process）通常仍能看到这个修改。

“新子进程（Subprocess）”与“全新文件系统”不是同一个概念。

LocalEnvironment 为什么不是生产级隔离（Isolation）

执行部件可以配置工作目录（Working Directory）、收集输出并处理超时；这些行为并没有自动把程序限制在工作区（Workspace）中。对于本机文件、网络和子进程（Subprocess），仍要看实际执行边界。

每次启动新进程（Process），不会自动获得新的隔离（Isolation）边界。 人工确认（Confirmation）见 第05章，权限与强制隔离（Isolation）见 第17章。

把输出变成下一轮能读的消息（Message）

执行环境（Environment）返回输出、退出码（Exit Code）和异常说明；模型协议适配器（Model Adapter）再把它们组织成当前模型服务提供方（Provider）接受的观察消息（Observation Message）。默认原生工具调用（Native Tool Calling）路径使用 role: tool，并保留相同的 tool_call_id，这样结果才配回原来的请求。

模型（Model）需要有用的输出，却不一定需要整份长日志。模板（Template）可以缩短发给模型（Model）的文本；内部调试字段还可保存更多信息。因此“模型（Model）这一刻看见的内容”和“内部对象记录的内容”也要分清。模型（Model）可见文本由模板（Template）生成，内部字段是否保留则由记录路径决定。

真实观察消息（Observation Message）中一个容易误读的 0

下面摘取后面第22章的真实命令片段，只观察命令失败怎样被消息（Message）表示，不需要先读完整修复过程。

该次模型（Model）实际运行 npm run check 2>&1 | head -10; echo "---exit: $?---"。返回正文中有 Missing script: "check"，外层命令却返回 0。管道末端及后续 echo 掩盖了原命令的失败；这说明读取观察消息（Observation Message）要把命令结构、正文、退出状态放在一起。不能看到 0 就写“测试（Test）成功”。原片段与解释

这里的证据链可以拆成三问：输出正文说明 npm 没找到 check；命令结构说明原始退出状态可能被后续程序遮住；因此这个 0 只对应外层命令的结束，不能证明测试（Test）断言（Assertion）已经运行。下一步先确认项目配置中的测试入口（Test Entry），再取得真正的行为检查结果。

测试（Test）命令的结果解析

问题 1。 对 npm test，分别指出行动请求（Action）、执行输出（Output）、观察消息（Observation Message）是什么。

解释。 行动请求（Action）携带 command；执行输出（Output）是执行环境（Environment）返回的输出、退出码（Exit Code）等；观察消息（Observation Message）由模型协议适配器（Model Adapter）转成下一轮模型（Model）可接受的消息（Message）。

问题 2。 同样退出码（Exit Code）为 1，若输出分别是 Missing script（未找到脚本）和测试（Test）断言（Assertion）失败，为什么要采取不同行动请求（Action）？

解释。 前者未找到入口脚本，后者已运行测试（Test）并暴露程序行为。需要阅读输出，不能只用退出码（Exit Code）分类；接下来的第04章会完整展示这两种情况。

问题 3。 第一次行动请求（Action）执行 cd subdir，第二次会自动处于该目录吗？第一次写入的文件会消失吗？

解释。 不会继承进程（Process）里的 cd；每次都是新子进程（Subprocess）。文件系统上的修改会保留，这和进程（Process）工作目录（Working Directory）状态不同。

解析器（Parser）、进程（Process）与协议变体

前半章已经把四份数据接起来，下面只展开三个容易改变结论的位置：参数实际检查到哪一层，命令进程（Process）继承哪些状态，以及结果遵循哪种消息协议（Message Protocol）。类名与字段用于定位这三项责任，不要求先记住全部调用链。

BASH_TOOL 定义了工具参数结构（Schema）

LitellmModel._query() 调用 LiteLLM 的生成接口时，传入的 tools 列表只有一个定义：BASH_TOOL。

它的核心形状是：

{
  "type": "function",
  "function": {
    "name": "bash",
    "description": "Execute a bash command",
    "parameters": {
      "type": "object",
      "properties": {
        "command": {"type": "string"}
      },
      "required": ["command"]
    }
  }
}

这表示默认模型（Model）看到的工具表面（Tool Surface）的声明非常小：

可用工具类型：bash
必填参数：command 字符串

这里的 bash 是协议名称，不保证实际解释器固定为 /bin/bash；不要仅凭工具名依赖某种命令解释器（Shell）独有语法。下面的 LocalEnvironment 小节继续核对实际启动方式。

不要把“单一 Bash 工具类型”误读成“每个模型（Model）响应的数据结构只能出现一个调用”。解析器（Parser）会遍历工具调用（Tool Call）列表；这里的单一，指的是只暴露一个工具名称和参数结构（Schema）。

工具调用（Tool Call）怎样被解析成行动请求（Action）

LitellmModel.query() 取得模型服务提供方（Provider）的响应后，会调用 _parse_actions()，最终进入 parse_toolcall_actions()。

没有工具调用（Tool Call）：不是正常空行动请求（Action）

默认配置要求模型（Model）响应至少包含一个 Bash 工具调用（Tool Call）。如果解析器（Parser）找不到任何工具调用（Tool Call），会产生格式错误（Format Error）FormatError，控制循环随后将错误反馈给模型（Model）。

为什么不把它当成“模型（Model）只是说了一段话”？因为这条智能代理（Agent）协议把代理循环（Agent Loop）定义为：每次响应必须继续以工具调用（Tool Call）推进，完成也通过一条约定 Bash 命令表达。

arguments 必须符合对象表示法（JSON）的语法

解析器（Parser）会读取 tool_call.function.arguments 并按对象表示法（JSON）解析。如果模型（Model）给出：

{command: npm test}

它不符合对象表示法（JSON）的语法；正常形式应类似：

{"command": "npm test"}

解析失败会形成格式错误（Format Error）FormatError，而不是把原始字符串直接交给命令解释器（Shell）。

工具名必须是 bash

如果响应请求了未知名字，例如 read_file，解析器（Parser）会拒绝，因为当前工具表面（Tool Surface）没有这个工具。

这说明：

模型（Model）能够生成某个工具名称，不等于智能代理（Agent）当前配置真的提供了该工具。

command 必须存在

即使工具名正确，arguments 中缺少 command 也会被视为格式错误（Format Error）。

但“存在”不等于“完成严格类型校验”。BASH_TOOL 参数结构（Schema）声明 command 是字符串类型 string，当前 Python 解析器（Parser）实际检查对象表示法（JSON）数据可解析、工具名为 bash、参数是含 command 的字典；它没有再检查值是否为字符串。{"command": 123} 仍能通过这个解析器（Parser）。不要从参数结构（Schema）声明推导出运行时已经强制了全部参数约束，也不要把格式解析成功当成执行安全或执行成功。

通过所有检查后，解析器（Parser）为每个调用产生：

{
  "command": "...",
  "tool_call_id": "..."
}

LocalEnvironment 怎样执行行动请求（Action）

先选择命令参数 command 与工作目录（Working Directory）cwd

execute(action, cwd="", *, timeout=None) 从行动请求（Action）中读取 command；* 表示 timeout 只能用关键字传入，例如 timeout=15。工作目录（Working Directory）按下面的优先顺序选择：

表 3 / Table 3 · 先选择命令参数 `command` 与工作目录（Working Directory）`cwd`
优先级工作目录（Working Directory）的来源何时使用
1本次 execute() 传入的 cwd值非空时
2执行环境（Environment）配置的 cwd本次参数为空、配置非空时
3Python 主进程（Process）的 os.getcwd()前两项都为空时

这让同一个执行环境（Environment）可以有默认目录，也允许某次调用覆盖它。

合并环境变量（Environment Variable）

启动命令时，先复制当前进程（Process）的 os.environ，再用 LocalEnvironment 的 config.env 更新它。这表示配置项可以覆盖同名宿主环境变量（Environment Variable）；没有被覆盖的项继续沿用。

这里传递的是子进程（Subprocess）的环境变量（Environment Variable），不是重新配置整个执行环境（Environment）。智能代理（Agent）不会因为模型（Model）在某一次命令解释器（Shell）中执行 export X=1，就自动把这个变化写回 Python 主进程（Process）或下一次新命令解释器（Shell）。

shell=True 表示命令由命令解释器（Shell）解释

Popen 使用 shell=True，所以管道、重定向和命令组合等命令解释器（Shell）语法可以工作。这也意味着行动请求（Action）的能力面很宽，不能把它当成一个只允许读取文件的结构化工具。

再次注意：工具参数结构（Schema）名叫 bash，不等于 _run() 固定启动 /bin/bash。当前实现没有显式设置命令解释器（Shell）的可执行文件。

标准输出（Standard Output）与标准错误（Standard Error）合并

源码把标准错误（Standard Error）重定向到标准输出（Standard Output），所以返回的 output 是合并流。这样模型（Model）可以在一个文本字段里看到常规输出和错误信息，但也失去了两个流的独立结构。

超时会尝试终止进程组（Process Group）

默认超时参数 timeout 是 30 秒。在采用 POSIX 类 Unix 进程（Process）接口的执行环境（Environment）中，进程（Process）在新的操作系统（Operating System，OS）进程会话（Process Session）中启动；这里的进程会话（Process Session）是操作系统（OS）组织进程组（Process Group）的单位。超时时尝试对进程组（Process Group）发送 SIGKILL，减少命令解释器（Shell）子进程（Subprocess）遗留的风险。其他平台则终止相应进程（Process）。

随后 execute() 捕获异常，并返回结构化错误：

{
  "output": "超时前已经产生的输出",
  "returncode": -1,
  "exception_info": "An error occurred while executing the command: ...",
  "extra": {
    "exception_type": "TimeoutExpired"
  }
}

注意：这里的命令超时通常被转成执行输出（Output），而不是直接让整个智能代理（Agent） Python 进程（Process）因为该异常退出。

执行输出（Output）怎样变成观察消息（Observation Message）

使用 observation_template

format_toolcall_observation_messages() 用 Jinja 模板（Template）把每个执行输出（Output）的字段填成观察消息（Observation Message）；Jinja 是这里使用的模板（Template）库。

默认 mini.yaml 中，短输出大致渲染为：

{
  "returncode": 0,
  "output": "..."
}

如果执行输出（Output）超过配置模板（Template）中的阈值，模型（Model）可见的 content 会保留头部与尾部并报告省略字符数。当前 mini.yaml 使用 10,000 字符阈值，保留前 5,000 和后 5,000 字符。

这体现了一个重要原则：

执行环境（Environment）可以产生很大的原始输出，但下一次模型调用（Model Query）不一定适合看到全部文本。

请求和结果重新配对

工具调用（Tool Call）路径把原行动请求（Action）的 tool_call_id 放进工具结果消息（Tool Result Message）。下一次模型服务提供方（Provider）请求才能把结果归属到正确调用。

extra 保存执行辅助字段

内部观察消息（Observation Message）的 extra 还可以保存：

  • raw_output；
  • returncode；
  • timestamp；
  • exception_info。

这些字段有助于执行轨迹（Trajectory）和调试，但发送给模型服务提供方（Provider）前，模型协议适配器（Model Adapter）通常会移除内部 extra。不要因为内部消息（Message）保存了更多字段，就假设模型（Model） API 每次都收到完整内部对象。

默认工具调用（Tool Call）与文本代码块变体

结构化工具调用（Tool Call）与文本围栏使用不同的解析器（Parser）和结果格式。

默认路径：原生工具调用（Native Tool Calling）

当前 mini 默认配置文件是 mini.yaml。配合默认 LitellmModel 时：

  1. 请求向模型（Model）暴露名为 bash 的工具参数结构（Schema）；
  2. 模型（Model）通过模型服务提供方（Provider）的工具调用（Tool Call）字段表达行动请求（Action）；
  3. 解析器（Parser）从结构化工具调用（Tool Call）中读取工具名与对象表示法（JSON）参数；
  4. 观察消息（Observation Message）以工具结果消息（Tool Result Message）返回。

所以不要把默认路径描述成“从回答里的三反引号代码块抓命令”。

变体路径：文本解析（Text-based Parsing）

mini_textbased.yaml 提供要求模型（Model）输出 mswea_bash_command 围栏代码块的提示与配置变体；对应的 LitellmTextbasedModel 不向模型服务提供方（Provider）传 tools，而是在响应文本中用正则提取行动请求（Action）。

在 v2.4.6 中，mini_textbased.yaml 文件自身没有设置 model.model_class。因此，通过当前命令行接口（Command-Line Interface，CLI）真正选择这条路径时，还必须同时指定 --model-class litellm_textbased，或者在合并的自定义配置里写入等价字段。只加载这份 YAML 而仍使用默认 LitellmModel，不会仅凭提示文本自动切换解析器（Parser）。

该解析器（Parser）要求恰好匹配一个行动请求（Action）：

0 个匹配 → FormatError
1 个匹配 → 形成 {command: ...}
2 个或更多匹配 → FormatError

因此，无论通过命令行接口（CLI）参数还是自定义配置，文本提示与 model_class: litellm_textbased 都必须作为同一协议理解。仅仅看见代码块模板（Template），不应该自动假设当前模型协议适配器（Model Adapter）已切到文本解析（Text-based Parsing）。

两条路径共享什么

不管行动请求（Action）来自结构化工具调用（Tool Call）还是文本代码块，进入智能代理（Agent）核心后都尽量收敛为：

{"command": "..."}

随后仍由执行环境（Environment）的 execute() 执行，再由对应模型协议适配器（Model Adapter）格式化观察消息（Observation Message）。

两条路径不能混写什么

表 4 / Table 4 · 两条路径不能混写什么
问题原生工具调用（Native Tool Calling）默认路径文本解析（Text-based Parsing）变体
行动请求（Action）在哪里模型服务提供方（Provider）的工具调用（Tool Call）字段role: assistant 消息（Message）的 content 围栏代码块
怎样解析检查工具名、解析对象表示法（JSON）参数在文本中匹配约定的围栏

两者共享行动请求（Action）抽象，具体消息（Message）格式不能互换。

协议约束与实际校验问答

问题 1。 BASH_TOOL 声明 command 是字符串类型 string，当前解析器（Parser）会拒绝数字 123 吗？

解释。 不会仅因其为数字而拒绝；当前解析器（Parser）检查对象表示法（JSON）数据、工具名和含 command 的字典，未检查 command 值的字符串类型。

问题 2。 一个 bash 工具类型是否只能产生一次调用？一个文本围栏是否只能含一条命令解释器（Shell）命令？

解释。 都不是。原生工具调用（Native Tool Calling）响应可含多个 bash 工具调用（Tool Call）；文本解析（Text-based Parsing）路径的解析器（Parser）要求恰好一个匹配围栏，但没有把围栏内部解析成只能一条命令解释器（Shell）命令。

问题 3。 tool_call_id 的作用是什么？只换 mini_textbased.yaml 会自动换模型（Model）类吗？

解释。 调用标识（Call ID）把结果配回原请求。配置文件不会自动切换 model_class，必须显式选择对应的文本解析（Text-based Parsing）模型协议适配器（Model Adapter）。

同一命令的三次数据转换

以 npm test 为例，模型服务提供方（Provider）的工具调用（Tool Call）最初用按对象表示法（JSON）编码的字符串表达 {"command":"npm test"}，并带调用标识（Call ID）。parse_toolcall_actions 解析后得到含 command 与调用关联信息的行动请求（Action）；LocalEnvironment.execute / _run 执行命令，返回含 output、returncode 等字段的原始结果；format_toolcall_observation_messages 再把结果变成带相同 tool_call_id 的 role: tool 消息（Message）。

因此，符合对象表示法（JSON）的语法只说明请求能被解析，returncode 属于执行器观察，最终的 role: tool 消息（Message）才是下一次模型服务提供方（Provider）请求可消费的协议表示。相关实现位于 actions_toolcall.py 与 LocalEnvironment。
