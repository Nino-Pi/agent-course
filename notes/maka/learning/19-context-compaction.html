第 19 章｜长上下文与压缩

本章概览

核心问题：长任务装不下历史时，怎样缩小模型输入而不把未完成工作写成已经完成？

关键概念：raw history（原始历史）保留事件；effective history（有效历史）服务当前输入；compaction（压缩）整理旧前缀；checkpoint（检查点）记录来源与覆盖；归档引用支持有界回读。

关系主线：来源校验、摘要生成、持久提交与后续重载各有作用，提交失败不能让新检查点生效。压缩改变输入表示，不补做工具，也不自动保证摘要更小、请求可容纳或任务正确。

工具结果怎样结算见 第18章；压缩处理已有记录的后续表示，不补做缺失的工具操作。

核心路径：给有限工作台整理材料

问题：全部重发和随意删除都不能解决它

继续使用 S1 / T7 / R7：读取 package.json 与 README、修改 README、运行测试、中文总结。假设前六个 Turn 已包含大量代码片段、工具调用、图片和三份 20 万字符的日志。每次请求全部重发，会超过窗口、增加成本，并让旧噪声遮住当前目标；只留最后五条消息，又可能删除用户决定和工具调用的另一半。

History是保存的事实；Context是当前工作台上的材料。Projection是为某种用途从事实生成的视图。整理工作台并不要求清空档案库。

机制：旧前缀用书签，近期原文继续保留

在 Maka 的 Compaction 路径中，系统保留 canonical RuntimeEvents，选择一个可以安全处理的旧前缀，为它生成 checkpoint，并在模型输入里替换这一段：

保存的事实       = [旧前缀] + [近期原文尾部]
checkpoint       = 旧前缀的摘要或兼容状态 + 来源与覆盖信息
下一次模型输入   = [有效 checkpoint] + [近期原文尾部] + 当前规则与工具

checkpoint 是可核对来源的摘要书签，不是新的历史真相。压缩不删除它覆盖的原始事件；删除或退役整个 Session 是另一项生命周期操作。prefix 是被它覆盖的旧前缀，tail 是继续保留的近期尾部；近期原文保住精确路径、错误码、刚发生的工具调用、当前要求和待验证的修改。Maka 用 prefix/tail 分工压缩较旧历史，同时保留近期细节。

工具 T2 保存“这次调用得到什么结果”，Context checkpoint 保存“后续输入怎样表示一段已有历史”。 如果 T2 记录测试失败，摘要应保留失败；如果效果仍未知，摘要也只能保留未知。checkpoint 不补做工具、不补出缺失的成功结果，也不保存旧进程的调用栈。

这张图从已保存事实开始，依次选择范围、生成候选、校验与保存；只有保存成功，才将 checkpoint 与近期原文一起用于后续输入。校验或保存失败都保留此前投影并报告原因。本地验证仍不能证明摘要语义完全正确，也不能保证 provider 接受请求。

两条必须守住的边界

调用和结果不能随意分家。 如果摘要只覆盖了 Edit 调用，却把对应失败结果留在尾部，模型或 provider 就失去完整关联。选择范围必须保护这种协议单元，也不能把尚未完成的流式内容当成完整事实。

先验证、保存，再应用。 如果内存已经用新摘要继续工作，保存前进程却崩溃，下次启动就无法证明模型刚才依据哪一份输入。顺序应是：

validate → persist checkpoint → apply replacement

下面只是课程的 Python 概念骨架，不是 Maka 原码，也不是可独立运行的实验：

prefix, tail = select_safe_prefix(effective_history)
checkpoint = summarize_with_source(prefix)
if replay_is_valid(checkpoint, prefix):
    persist(checkpoint)  # 失败就不能走到 replacement
    next_history = replay(checkpoint) + tail
else:
    next_history = effective_history

决定行为的是验证分支与 persist 的顺序；生成了字符串尚不构成有效 checkpoint。真实代码还处理异步保存、当前用户锚点和 provider 状态。

同一代码任务：先保住当前要求，再处理大日志

T7 之前，第 1–4 轮讨论架构并贴出旧日志，第 5 轮明确“不升级 Node”，第 6 轮完成无关文档任务。Runtime 可以让前 4 轮使用有效 checkpoint，保留后两轮的必要原文，再加入 T7“更新 README 并用中文解释结果”。这里按轮次描述历史，避免与 第18章 的工具提交边界 T1/T2 混淆。

两个 Read 结果加入近期尾部后，模型才看到真实 scripts 与文档。Edit 成功后仍要保留“尚未测试”的状态；压缩不能将“计划修改”改写成“修改并验证完成”。

摘要是否保留任务状态，可以直接与原事实比较：

原事实：README 已修改；测试尚未运行；用户要求不升级 Node
可接受的表达：文档修改已完成，待运行现有测试入口；继续保留 Node 约束
错误的表达：修改和测试全部完成；必要时升级 Node

第一种摘要仍需通过结构与来源检查；第二种即使格式正确、长度更短，也改变了完成状态和任务约束。

若 Bash 返回退出码 1 和 30 万字符日志，另一种整理方式是把大结果正文外置，给模型一个可回读引用。这和总结整个旧前缀不是同一种操作：

真实补例：摘要说“还没修”，下一轮才继续修

第22章 的真实压缩案例先让 Maka 读文件、分析失败，再只改 README。原生手动压缩得到的摘要明确保留：文档已改，函数仍用 % 100，测试仍 2 通过、2 失败；下一步才是修函数并复测。之后真实 Agent 按当前请求继续完成修复。

压缩前的对话、生成的摘要与后续工具结果展示了状态变化：摘要保留“待修复”，之后的工具结果才报告修复与验证。摘要也没有复述此前的中文要求；最终中文来自继续消息再次提出的要求，不能当成这条要求被摘要保留的证据。

本例手动调用原生压缩入口，不演示自动溢出触发，也没有额外运行大日志 ArchiveRead。

缩短输入与保留事实问答

问题 1。 为什么完整 History 不等于下一次 Context？

解释。 历史保存过去，模型输入只装经过选择、投影和适配的本次材料；窗口和相关性都有限。

问题 2。 prefix + raw tail 保住了什么？

解释。 旧前缀用 checkpoint 表示，近期原文保留精确请求、路径、错误码和新工具结果。摘要不需要承担所有细节。

问题 3。 为什么不能在 call 与 result 之间切？

解释。 它们共同表达一次动作及其观察。拆开可能破坏重放协议，也会让结果失去来源。

问题 4。 先保存再应用防止什么？它能代替工具 T2 吗？

解释。 防止后续执行已经依赖一份只在内存存在的摘要，崩溃后无法重建这份依据。保存失败应保持旧投影或报告失败。它不能代替 T2：摘要表示已有历史，不负责执行工具或结算缺失的工具结果。

问题 5。 大日志归档、compaction、Memory 是一回事吗？

解释。 不是。归档提供大正文的间接读取，compaction 整理历史输入，Memory 为以后选择性保留并召回信息；当前要求中文也不证明 Memory 已写入。

实现深化：检查来源、重放和持久化

失败：错误压缩会让模型“记得一段从未发生的过去”

切断 tool call/result pair

假设旧前缀以 tool call 结束，raw tail 从 tool result 开始：

checkpoint: “模型准备读取 package.json”
raw tail:   tool result without matching call

很多 provider 协议要求工具调用与结果配对。不完整 pair 不只是信息损失，还可能让请求直接被 provider 拒绝。因此 compaction boundary 不能切在 pair 中间。

把 partial stream 当作完整回答

模型正在流式输出时可能先产生半句话或半个工具参数。若把 partial event 纳入 checkpoint，摘要会把不完整状态固化成事实。安全前缀必须排除 partial event。

摘要吞掉 pinned steering

用户可能在旧历史里明确说：“不要访问网络”或“任何删除都先问我”。如果 compactor 把这类仍有效的 steering 简写成“用户希望谨慎操作”，含义就变弱了。

安全策略需要识别不可被普通摘要吞掉的 pinned 内容，或由当前 Host composition 重新注入 authoritative instructions。

摘要自己产生幻觉

LLM 可能把“测试尚未运行”总结成“测试已通过”。因此模型只能提出摘要内容；Runtime 必须决定覆盖范围、验证结构、绑定 digest（用于核对来源的内容指纹）并检查兼容性；摘要是否准确仍需独立评估。

摘要不是新的 authority。与原始 ledger 冲突时，不能因为摘要更短就相信摘要。

保存了摘要，却无法证明它对应当前前缀

如果历史发生 repair、branch 或 migration，旧 checkpoint 可能仍在存储中，但其 source digest 不再匹配 exact prefix（它实际覆盖的完整旧前缀）。直接复用会把另一条历史的摘要塞进当前上下文。

因此 replay 前要核对 through identity（覆盖到哪条事件）、exact prefix 和 digest，而不能只看“这是 S1 的最新摘要”。

压缩后反而更长

短历史生成的摘要可能比原文更长，这是摘要质量与成本问题。当前 Maka 不把本地“严格更小”设为 checkpoint 应用门槛：结构安全、前缀匹配、兼容且可 materialize 后可应用，由 provider 判断请求能否容纳；字符/token 估算只作诊断。评估时仍应记录压缩收益，但不能把建议冒充现行代码条件。

大工具结果被“复活”

假设 20 万字符测试日志已经被归档，effective history 只保留引用。下一次 compaction 若直接从 canonical raw result 取原文，日志会重新灌回模型窗口，绕过此前的裁剪决定。

因此 compaction、replay、budgeting 必须读取同一个有效投影折叠（effective projection fold），尊重持久的 projection transition，而不是各自随意读原始 body。

Provider-native state 被错误迁移

某些 provider 可以返回 opaque（内部内容不可直接解释）、甚至加密的 compact state。它把部分状态交给 provider 私有表示，但不能从 opaque 推断更高保真度；提供方原生状态的重放条件很严格：必须仍是 OpenAI Codex provider 类型，并且 exact connectionId 与 exact modelId 同时匹配。只匹配其中一项也不够；把它交给另一个连接或模型，可能无法解码或语义不成立。

可移植的文本摘要和 provider-bound state 是两种不同 checkpoint，不能假装完全可互换。

反复对同一个失败输入做摘要

若 summarizer 对同一来源和配置总是生成 malformed（结构不合法）结果，无限重试只会重复花费。Runtime 需要有界的 liveness guard（活性保护）：相同 fingerprint（输入指纹）的重复失败应打开 circuit（熔断），保留尊重已提交 transition 的有效历史；无法安全重建时暴露真实失败，而不是陷入 compaction loop。

Maka：从 RuntimeEvent 重建每一次模型输入

正常事实源是 RuntimeEvent ledger

Maka 的正常主链是：

prior AgentRuns / RuntimeEvents
  → 读取 durable model-projection transitions
  → fold 成 effective events
  → RuntimeEvent-to-model-history projection
  → checkpoint replay / stale-result pruning
  → context measurement and shaping
  → provider-specific messages

普通 Session 的 StoredMessage 展示视图现从 RuntimeEvents 派生，legacy/import 和 WorkHub coordination 的消息行另有边界；它仍不作为 provider-history fallback。缺少 RuntimeEvent context 时 prior history 为空；native 语义无法重放时，逐项过滤或 text-only 降级也只使用 RuntimeEvent。

System composition 不伪装成历史消息

Workspace instructions、Local Memory、Skill inventory、Plan context 和当前工具面由 Host 在本 Turn 重新 compose。它们不是模型过去说过的话，不应写回 history 假装成旧对话。

provider input 包含两类生命周期不同的材料：

相对稳定的 envelope：system instructions、model config、工具与能力组成
不断增长的 tail：user/model/tool 的有效事件投影

同一 Turn 内稳定部分可以复用，变化的部分按 step 重建。

Tool result 有 canonical result 与 model projection 两层

工具执行结果可能很大。Maka 区分：

  • canonical function_response.result：Runtime 接受并规范化的 durable 事实；
  • modelProjection：以后给模型看的有界形态。

当 result 被归档或裁剪时，当前 Host 先证明 ledger 中的原投影与 transition 链能够重建待移出的有效表示，再在 Session admission 内复核并追加 durable projection transition。提交后 effective history 才改为可回读引用；新路径无需再写一份正文 Artifact，旧 Artifact 引用仍可兼容读取。恢复得到的是那份有效表示，更早已经省略的字段不会自动补回。

用一次具体输入核对：raw result 含“完整日志及不应重发的内部字段”，初次 modelProjection 只含允许给模型看的测试错误；后来 transition 把这份错误正文替换为引用。ArchiveRead 应恢复被这一步移走的测试错误正文，不能恢复 raw 内部字段，也不能随便返回整条 transition 链最终的结果。当前实现先用 SQLite 按 Session/event 读取必要 projection 字段，再沿 reducer 接受的链找到这一步的前驱表示；缺少提交记录、Session/digest/前驱不匹配就拒绝。

归档前的准备成功还不够：Host 在 Session admission 内再次检查 Session 未删除、来源未变化，才追加 transition；append 后根据共同 fold 的 winner 展示结果。这样两条并发分支即使都完成 append，也不能各自宣称自己的 replacement 就是模型应见的版本。此处的新写 ledger 路径无需单独再保存正文副本；旧 Artifact reader 是兼容分支。

如果本次归档失败，应保留此前有效投影，而不是生成一个打不开的假链接。ArchiveRead 允许模型在有该 capability 时执行有界的 inspect / read / query / search，按需取回片段。

Model projection transition 不改写原事件

正常可解码的 projection transition 以 source digest 和 predecessor digest 串联，折叠到目标 RuntimeEvent。它不删除 canonical response，但所有 effective-history consumer——live continuation、下一 Turn、冷启动、compaction 和 branch——都应尊重相同 fold。损坏记录是否也受到保护，还要检查各读取入口有没有把失败标记传到底。

模型可见内容有界
后续压缩不会绕过 transition 把旧大结果复活

Compaction 的安全前缀

Maka 选择 compact prefix 时会保护：

  • 连续 prefix；
  • 无 partial event；
  • 不切断 tool call/result pair；
  • 不吞掉 pinned steering；
  • 保留规定的 verbatim tail；
  • mid-turn 情形下保留正确的 current user head anchor。

这里的 head anchor 可以理解为“当前这项用户工作从哪里开始”，避免 mid-turn 压缩把本轮目标混进旧历史摘要。

两类 checkpoint

Maka 使用两种表示：

表 3 / Table 3 · 两类 checkpoint
检查点（Checkpoint）通俗解释主要限制
文本摘要（Text Summary）结构化文本 summary可读、相对可移植，但保真度取决于摘要
提供方原生状态（Provider-native State）OpenAI Codex provider-native opaque stateprovider-bound、不能直接人工审阅；只允许 OpenAI Codex provider 类型且 exact connectionId、exact modelId 同时匹配时 replay

checkpoint 保存 coverage、through identity、source digest、phase/head anchor。应用前必须 exact prefix 和 digest 匹配，并通过兼容性与 replay admission；没有本地 strict-smaller 门槛。对提供方原生状态来说，“兼容”不是宽泛的 model/provider 相似：它明确要求 OpenAI Codex provider 类型以及 exact connectionId、exact modelId 三项同时成立。

主动 shaping 与真实 overflow 分开

Runtime 的主动容量触发使用同 model/connection 上一次被接受的真实 inputTokens + outputTokens，再预留 min(2 × 上次 outputTokens, 8000)，与用户声明的 window 比较。没有声明或有效实测 input 就不开主动触发。新增日志、图片和用户文本是否能装下仍由 provider 判断；不以字符估算裁决发送。

摘要请求本身被 provider 拒绝时，Maka 只退到同 route 先前接受过的输入边界，不猜测减半；无可证明边界或再次拒绝则保留原投影并报告失败。这种“曾接受过”不是保证：摘要指令与原请求不同，所以仍尊重 provider 的实际结果。

若 provider 明确返回 context-length 拒绝，Maka 会进行一次有界恢复：先尝试省略历史图片；没有可省略的历史图片时再 compact，然后只重试一次。仍失败则暴露 context_overflow，而不是无限压缩和重发。

contextRemaining 是观察值，不是历史真理

最后一次物理请求的 input token 数可以生成 contextRemaining，进入 durable message 和 live event，帮助 UI 在重启后继续显示窗口余量。但它描述某次 provider 请求的观测，不是永远精确的模型容量承诺。

Context Offload 与 Tool Result Archive 不等于 Memory

Maka 当前有两个容易混淆的大内容通道：

  • Read image snapshot 使用 content-addressed ContextOffloadStore，有 Session ownership、copy、release、retirement 与 GC；
  • 大 tool result 使用 ledger archive capability 和 ArchiveRead，旧 Artifact ref 保留兼容。

当前 tool_result_archive 的 ContextOffload owner quota 仍为 0，因此不能笼统说“所有工具结果都已统一迁入 ContextOffloadStore”。两者都解决 payload materialization，不会自动学习用户偏好，也不是长期 Memory recall。

源码走读：一份可用摘要，为什么还不能立即生效

第10章的 fail_open 来自压缩规划结果 PlanHistoryCompactionResult，表示规划没有给出可用替换。这里进入负责保存与应用的外层函数 compactActiveRequestHistory，返回类型是 ActiveRequestCompactionOutcome：规划不可用、替换无法构造成消息，或保存失败，都会在这一层返回 fail。两个标签属于不同层，不能互相改名。

规划 fail_open → 外层返回 fail
规划得到候选 → 外层检查替换并等待保存
                 ├─ 失败：返回 fail，不应用候选
                 └─ 成功：更新投影状态，返回 compacted

这条简图只比较本节的成功与失败分支，不列全部返回类型。fail 也不是整个 Run 必然失败；继续、重试或终止由调用方结合当前条件处理。下面具体看“候选已准备好，但保存失败”的分支。

进入这个窗口前，Runtime 已为 replacement 建立 replay plan，拒绝不可 materialize 的结构，并准备 replacement messages。准备出消息仍没有把它们应用为后续投影。 接下来必须跨过保存边界。compactActiveRequestHistory 调用 recorder 的代码是：

    try {
      await Promise.resolve(recorder(plan.checkpoint, turnId));
    } catch {
      return {
        decision: 'fail',
        diagnosticReason: 'write_failed',
      };
    }

recorder 可以同步返回或返回 Promise；Promise.resolve 统一为可等待结果，await 确保保存的成功或失败先被处理。失败分支直接返回，后面的 checkpoint 状态更新不可达。成功后，中间还有通知记忆模块处理该历史范围的独立步骤，写入机制将在第20章展开；其异常被限制在自身，不改变 compaction 的保存结论。随后才到同一函数中从 state.previousCheckpoint = plan.checkpoint 开始的连续窗口：

    state.previousCheckpoint = plan.checkpoint;
    state.projectionCheckpoint = plan.checkpoint;
    return {
      decision: 'compacted',
      checkpoint: plan.checkpoint,
      replacementMessages,
      estimatedTokensBefore: plan.estimatedTokensBefore,
      estimatedTokensAfter: plan.estimatedTokensAfter,
    };

如果把后一个窗口的更新移到保存前，磁盘失败时内存就可能选择一个无法恢复的 checkpoint。如果去掉 await，异步 recorder 尚未结算，代码就可能错误报告 compacted。反过来，保存成功只证明这份 checkpoint 的提交顺序成立，不证明摘要没有遗漏、不证明请求一定装得下，也不保证整项代码修复已经完成。

这与 第06章 的窗口可以并列思考：两者都要问“外部可观察状态与保存事实之间是否存在空隙”；checkpoint 的先保存后应用不意味着任意外部工具都可以获得相同事务边界。

checkpoint 的保存与读取链

checkpoint 能在重新打开后使用，是因为保存回调连接到了持久账本，而读取入口会重新校验它。compactActiveRequestHistory 先等已完成 step 的事件被消费，再从当前 Turn 的 durable 事件池读取来源，和 prior events 拼成候选历史。队列已消费不等于持久读取一定成功；读取失败或找不到当前用户 head anchor，就不能继续生成覆盖它的 checkpoint。

随后 planHistoryCompaction 选取合法前缀。覆盖身份来自 raw events，摘要输入来自 effective events。 前者回答“这份书签覆盖了哪些原始事实”，后者回答“生成摘要时，模型实际可读的是这些事实的哪种表示”。归档或裁剪可能只改变后者，因此 checkpoint 分别保存 coverage.sourceDigest 和 coverage.effectiveSourceDigest。digest 是核对来源是否一致的指纹，不是摘要真实性证明；本页的 d_raw/d_eff_1 都是教学标签，不是实际 hash 值。

摘要生成后先做文本结构、配对与可重放检查，并构造 replacement messages。通过后，注入的 recorder 进入 HistoryCompactCheckpointCoordinator.record：以 Session 为范围排列提交，先读取已保存 checkpoint，再用 canReplaceHistoryCompactCheckpoint 判断候选是否已被较新结果取代。能替换才调用 AgentRun.recordHistoryCompactCheckpoint，经串行写队列等待 runStore.appendEvent 追加 history_compact_checkpoint_recorded。成功后才更新 coordinator 的内存缓存；调用返回后，compaction 才把本次 state 切换到新 checkpoint。保存的是摘要连同来源与覆盖信息，不是只写一个 summary 字符串。

新加载时，loadLatestHistoryCompactCheckpointFromRunLedger 读取可用派生 checkpoint；需要恢复时再从 run ledger 选择合法记录。加载到记录仍不等于可直接重放。 AiSdkTurn 的 loadDurableTurnProjection 再核 raw prefix；原始覆盖不匹配不能继续用它，effective digest 不匹配则放弃该 checkpoint 的旧内容，用当前有效来源重新组成可回放输入。之后才是 replay plan、消息物化、本次 shaping 和 ModelAdapter.startStream。若需要滚动生成新摘要，planHistoryCompaction 也不能继承来源已失效的旧摘要，否则会把过时正文带进新书签。

“保存成功”在这里指 append 合同已经完成；是否还能抵抗断电，要继续看存储后端的刷盘与恢复保证。

H1–H5：原始历史没变，旧摘要为什么仍会失效

沿用 README 修复，但把它写成独立的教学历史，不声称 第22章 真实轨迹具有这些编号。H1 是旧任务，H2 是 Read 调用，H3 是关联结果，H4 是 assistant“仅阅读，尚未修改”；H5 是当前用户“只改 README”。本题选择首步整形中允许的 pre-turn 切点：H1–H4 已完整、可安全覆盖，H2/H3 不拆开，H5 作为当前 head anchor 原文留在 tail。这里的 head anchor 是当前工作起点；首步整形是在本 Turn 第一次调用前按规则调整输入表示，不是已经获得 provider 的容量确认。具体合法切点不是由这五个教学编号决定的。

假设 H3 的 raw 正文有 20,000 字符，已有有效投影只给出 200 字符及来源；C1 摘要只读后者。下表假设摘要格式与重放结构检查均通过，简写的摘要句子本身不是可提交的真实 checkpoint payload。

拒绝行与成功行是两个分支，不是同一次失败提交自动转成成功。最后一行尤其关键：旧摘要可能仍复述 H3 先前的 200 字符。若只看原事件 id 和 raw digest，就会借摘要重新放回已经移出当前有效视图的内容。新投影必须再次 fold；重新摘要时也要放弃不再有效的 previous checkpoint。这个规则约束后续输入，不能撤回已经发给模型的旧请求，也不是删除原始事实。

简化字符计算可以量化这种差异：令 H1/H2/H4 合计 300 字符，H3 的有效正文 200，H5 为 50，暂忽略消息包装和系统/工具说明。整理前可见正文是 300+200+50=550。若 C1 的替代表示为 350 字符，整理后是 350+50=400，少 150 字符；这只说明本题正文节省约 150/550≈27.3%，不是 provider token 或总请求 fit 的测量。若替代表示为 600，结果反而是 650；当前 Maka 没有“必须严格更小”的本地 gate，在其他校验满足时仍可提交，最后请求是否装得下由 provider 判断。

同一历史换成 Pi：消费者靠树上切点继续

Pi 是另一种开源 Code Agent，它提供另一份真实合同。默认压缩先找合法保留点、生成摘要；手动路径在未取消时调用 SessionManager.appendCompaction(summary, firstKeptEntryId, ...)，再 buildSessionContext() 更新 agent.state.messages。buildContextEntries 沿当前 leaf 的分支路径找最新 compaction entry，留下它、从 firstKeptEntryId 开始的旧尾以及之后的新 entries。若把同题 H5 选为 first-kept，对模型的目标表示同样是“摘要 + H5 原文”，但书签在树中的位置和边界引用参与了重建。

这说明不同状态结构可以表达摘要消费者，不能只比较“两个项目都保存 summary”。Pi 的切点推导见 第36章。相似的摘要加尾部，不意味着两者有相同的持久化方式或 raw/effective 双指纹合同。

两道迁移题：改来源或提交时机

题 1。 C1 刚通过 replay 检查，recorder 因并发候选 C2 已提交而拒绝。模型已经生成了一份很好的摘要，能否先放进下一请求，稍后再补存？若 C1 已成功保存，后来只有 H3 的 effective digest 变了，是否仍可按 raw digest 复用？

答案。 两种做法都不成立。第一种绕过 persist-before-apply；本次更新不可达，也不能把内存旧状态擅自当成已经加载了 C2。应沿失败/重新读取路径处理，不能报告 C1 生效。第二种混淆覆盖身份与内容时效性：raw 不变仍需通过 effective 检查，否则放弃旧 checkpoint 内容，基于当前有效来源重建或重新摘要，不能回灌 raw H3。

题 2。 H5“只改 README”被错误地划进了可改写摘要；另一方案保留 H5，却把 550 字符正文换成 650 字符。哪一个问题能靠“摘要必须更短”解决？设置这个门以后，能否保证摘要忠实并装进模型窗口？

答案。 第一个问题要查当前 head anchor、保护内容与切点，长度门救不了被改写的权限/任务约束。第二个方案可用显式 strict-smaller 政策拒绝，但必须先定义比较的是 covered prefix、replacement messages 还是整个请求，不能比较一个 raw 大正文与早已缩短的有效输入来夸大收益。即使更短，语义仍可能错，系统/工具/媒体也可能让总请求超窗。当前 Maka 没有该本地门，新增它属于采用建议。

若问题是重复大日志，先考虑带来源的归档回读；若问题是长历史关系，才需要摘要保留状态和约束；若问题是更换 provider，先查兼容性与实际请求组成。增加压缩率、改摘要模型与加检索分别改变不同环节，不能互相代替来源校验、提交合同或任务质量评价。

机制问题与方法比较

问题 1。 StoredMessage 为什么不能替代 RuntimeEvent？

解释。 前者服务 UI/兼容，正常模型重放需要后者承载的配对、partial、可见性、terminal 和 provider 来源语义。当前没有 transcript fallback。

问题 2。 为什么不能从 canonical body 重新灌入已归档大结果？

解释。 所有有效历史消费者必须尊重 durable projection transition，否则会绕过此前裁剪并让内容复活。

问题 3。 文本摘要与提供方原生状态的主要差别是什么？

解释。 文本摘要较易审阅和迁移；提供方原生状态是 provider-native opaque state，要求 OpenAI Codex provider 类型、exact connectionId 与 exact modelId 同时匹配，不能由 opaque 推断更高保真度。

问题 4。 没有声明 window，是否靠字符估算主动触发容量压缩？

解释。 不会。当前主动触发还需要同 route 的有效 usage；未知不当作 0。真实 provider 拒绝后仍有独立的有界恢复。

问题 5。 checkpoint 更长是否必然被本地拒绝？

解释。 不必然。现行 gate 验证结构与可重放，大小只是诊断，fit 由 provider 裁决。摘要质量和压缩收益还应另行评价。

问题 6。 recorder 抛错后会更新 projectionCheckpoint 吗？

解释。 不会。catch 返回 write_failed，更新语句不可达；这就是短窗口中可直接检查的控制关系。

同一历史的三份具体输入对照用固定 H1–H9 比较全文、summary + tail 与 placeholder + ref：哪份包含失败断言，哪份需要回读，哪种摘要错误地把未完成写成“全部通过”。该对照沿 README-only 权限分支展开。

**换模型的反例：**同一历史从模型 A 换到 B，能否继续使用完全相同的压缩预算和 provider-native 摘要？不能仅由历史未变作判断；应核对当前模型预算、提示投影与 replay compatibility。Pi 的逐模型设置和 DeepSeek 开源 Harness（DSH）的 system prompt 投影提供两种具体对照，见模型身份与压缩。
