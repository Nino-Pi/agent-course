第 19 章｜长历史（History）与上下文压缩（Context Compaction）

本章概览

核心问题：历史记录太长时，怎样减少本次模型输入（Model Input），同时保住当前目标、未完成状态与可核查来源？

关键概念：有效历史（Effective History）是当前可用的记录表示；前缀（Prefix）与尾部（Tail）划分整理范围；检查点（Checkpoint）将摘要（Summary）或兼容状态与来源绑定；投影变换（Projection Transition）记录表示怎样改变。

关系主线：先选安全范围，再生成、验证和保存候选，最后由后续消费者（Consumer）重新核对并采用。来源一致、提交成功、语义准确和请求可容纳，是四项不同判断。

前情回顾：已有结果怎样成为下一次依据

第15章区分了历史（History）与上下文（Context）：前者保存发生过的记录，后者是本次真正送给模型（Model）的材料。第18章进一步说明，工具效果（Effect）与持久结果不是同一时刻发生；结果结算边界T2可以记录成功、失败或效果未知。这里的T2是协议阶段标签，不是工作轮次（Turn）的编号。

本章处理这些记录以后怎样被表示。已经失败的测试（Test）不能因整理而变成成功，尚未确定的效果（Effect）也不能由摘要（Summary）补成已完成。上下文压缩（Context Compaction）不执行缺失的工具（Tool），不保存旧进程的调用栈，也不代替工具结果（Tool Result）结算。

继续采用第12章的教学分支：会话（Session）S1中的工作轮次（Turn）T7，由执行（Run）R7完成README入口更正。函数原本正确，四个既有测试（Test）原本通过；本次只允许修改README，将 npm run check 改为 npm test，最后用中文解释。下面为S1增加较长旧记录；这些身份、日志大小和历史分段都是教学条件，不是新增执行轨迹（Trajectory）。

从历史（History）到本次上下文（Context）

有限输入先约束什么？

假设前六个工作轮次（Turn）已经留下代码片段、工具调用（Tool Call）、图片和三份各20万字符的日志。每次全部重发会占用上下文窗口（Context Window）、增加处理成本，也会让当前问题淹没在旧材料中。只取最后五条消息（Message）则可能丢掉用户决定，或留下没有对应调用的工具结果（Tool Result）。

这两个极端共同漏掉一个问题：下一步判断究竟需要哪些信息，以什么精度需要？ 当前文件路径和失败断言（Assertion）可能要逐字保留，旧背景讨论则可能只需结论。投影（Projection）是从事实为某种用途构造的表示；整理本次工作台，不要求清空档案库。

旧前缀（Prefix）用摘要（Summary），近期尾部（Tail）保留原文

Maka的主路径保留权威运行时事件（Runtime Event），选择一段安全的旧前缀（Prefix），用检查点（Checkpoint）表示它，再接上仍需原文的尾部（Tail）。先用一个教学抽象表示这种分工：

Heff=P∥T,H^=S(P)∥T.H_{\mathrm{eff}}=P\mathbin{\Vert}T, \qquad \widehat H=S(P)\mathbin{\Vert}T.Heff​=P∥T,H=S(P)∥T.

HeffH_{\mathrm{eff}}Heff​表示整理前的有效历史（Effective History）；PPP是被覆盖的前缀（Prefix），TTT是继续保留的尾部（Tail）；S(P)S(P)S(P)是该范围的替代表示，∥\Vert∥表示按顺序拼接。这里沿用第15章的符号，表达的是表示关系，不是直接赋给某个提供方接口（Provider Interface）的完整数组；实际请求还包括当前规则、工具声明（Tool Definition）及协议转换。

检查点（Checkpoint）也不只是一个摘要（Summary）字符串。它还带来源、覆盖范围和兼容性信息，使后续代码能够核对“它对应哪一段记录、现在是否仍可用”。删除或退役整个会话（Session）属于另一项生命周期（Lifecycle）操作，不能与这次表示替换混为一谈。

原文尾部（Raw Tail）承担近期精确细节：当前要求、路径、错误码、刚发生的工具调用（Tool Call）和待验证修改。旧背景由较短表示承担。若将“测试尚未运行”和“测试已经通过”两段不同过去都概括成“修改完成”，后续消费者（Consumer）就可能失去决定是否还需测试（Test）的信息。因此，变短本身不是质量标准；需要保留能改变后续判断的状态与约束。

图中从已保存事实出发，先选范围并生成候选，再检查来源和重放（Replay）结构，最后等待保存。验证或保存失败不会让本次候选生效；即使走到最后，本地检查也没有证明摘要（Summary）完全忠实，或模型服务提供方（Provider）一定接受这次请求。

两条先于长度优化的规则

第一条是保住完整协议单元。若覆盖了 Edit 的工具调用（Tool Call），却将对应失败结果留在尾部（Tail），就会破坏关联；没有结果的开放调用，以及尚未完成的流式内容，也不能简单按数量截断。

第二条是先验证、保存，再应用。若内存先采用新检查点（Checkpoint），保存前进程却崩溃，下次启动就可能无法重建刚才依赖的表示。下面的Python代码只表现这两个分支与先后关系，不是Maka原码，也不是独立实验。

prefix, tail = select_safe_prefix(effective_history)
checkpoint = summarize_with_source(prefix)
if replay_is_valid(checkpoint, prefix):
    persist(checkpoint)  # 保存失败就不能继续构造 replacement
    next_history = replay(checkpoint) + tail
else:
    next_history = effective_history

先读前两行的“选择与提出”，再读 if 的“判断与采用”。persist失败时不会经过下一句；本骨架未展开外层异常处理，不能把它当成完整恢复函数。真实路径还要等待异步结果（Promise）、保护当前用户锚点（Head Anchor），并核对提供方原生状态（Provider-native State）。稍后的源码窗口会明确失败如何返回。

同一任务：先保住当前要求，再处理大日志

在教学历史（History）中，第1–4轮讨论架构并贴出旧日志，第5轮明确“不升级Node”，第6轮完成无关文档工作。如果实际安全切点允许，运行时（Runtime）可以整理前四轮，让后两轮保留必要原文，再加入T7的新要求。按轮次描述只帮助理解，不意味着任意轮次边界都天然满足协议检查。

两个 Read 结果进入尾部（Tail）后，模型（Model）才取得实际脚本配置和文档；Edit成功后，状态仍是“尚未测试”。下列两个摘要（Summary）句子展示的差异，比字符多少更关键：

原事实：README 已修改；测试尚未运行；用户要求不升级 Node
可接受的表达：文档修改已完成，待运行现有测试入口；继续保留 Node 约束
错误的表达：修改和测试全部完成；必要时升级 Node

正确表达仍需通过格式和来源检查；错误表达即使格式有效、长度很短，也改写了完成状态与约束。

若 Bash 返回退出码（Exit Code）1及30万字符日志，还可以把大结果正文外置，留下有界内容和可回读引用。这与概括整个旧前缀（Prefix）解决的是相邻问题：

方法本次输入留下什么后续消费者（Consumer）怎样取得细节

引用必须确实可读；仅制造一个看似能跳转的地址，不会建立恢复能力。整理后请求仍被模型服务提供方（Provider）拒绝时，应保留真实失败。已取得测试（Test）失败与必要错误片段时，则可以准确报告文档已改、测试（Test）失败，以及已知错误。T7的中文要求仍来自当前输入，不证明长期记忆（Long-Term Memory）已经写入。

既有真实案例：摘要（Summary）保留“待修复”

第22章的真实压缩案例使用的是另一条完整修复分支：原函数仍有 % 100 缺陷，Maka先读文件、分析失败并只改README。原生手动上下文压缩（Context Compaction）得到的摘要（Summary）保留了文档已改、函数未修、测试（Test）2通过2失败，下一步才修函数并复测。之后的真实工具结果（Tool Result）才证明修复与验证发生。

这段旧记录没有证明所有重要信息均被保留：摘要（Summary）未复述中文要求，最终中文来自继续消息（Message）再次提出的要求。它也没有演示自动溢出触发或大日志归档读取。分清这些范围，才能用实例说明状态连续性，而不扩大结论。

缩短输入与保留事实问答

问题1。 完整历史（History）为什么不等于下一次上下文（Context）？

参考答案。 前者保存过去；后者只装经过选择、投影（Projection）与适配的本次材料。窗口和相关性有限，保存过并不等于这次全部发送。

问题2。 前缀（Prefix）与原文尾部（Raw Tail）怎样分工？

参考答案。 旧背景由检查点（Checkpoint）表示，近期原文保住精确要求、路径、错误码与工具结果（Tool Result）。摘要（Summary）不必承担所有细节，却必须保住影响后续判断的状态与约束。

问题3。 为什么不能在工具调用（Tool Call）与工具结果（Tool Result）之间任意切开？

参考答案。 两者共同描述请求与观察，拆开会让结果失去来源，也可能破坏重放（Replay）协议；不能只按消息（Message）条数决定切点。

问题4。 保存检查点（Checkpoint）为什么不能代替结果结算边界T2？

参考答案。 前者使后续输入表示可恢复；后者结算一次工具（Tool）执行。摘要（Summary）只表示已有事实，不能执行缺失操作或补造成功结果。

问题5。 结果归档（Result Archive）、上下文压缩（Context Compaction）与记忆（Memory）分别处理什么？

参考答案。 依次是大正文间接读取、旧历史（History）输入表示、供未来选择并召回（Recall）的信息。当前请求使用中文，不能单独证明第三条路径已生效。

实现深化：从来源到后续消费者（Consumer）

第一遍阅读已经得到两个约束：不能破坏记录关联，不能先采用尚未保存的表示。现在把它们放进真实接线：先确定从哪里读取，再追候选怎样提交与重载，最后检查容量和失败边界。

运行时事件（Runtime Event）怎样变成本次输入

事实来源与展示视图（Read Model）分开

Maka普通执行路径以运行时事件（Runtime Event）账本（Ledger）重建模型（Model）历史；其权威性限定在执行与模型重放（Replay）语义，不代表会话（Session）元数据、批准（Approval）或其他业务状态全部归同一存储。

先前执行（Run）的运行时事件（Runtime Event）
  → 读取持久投影变换（Projection Transition）并折叠
  → 得到有效事件（Effective Event）
  → 构造模型历史（Model History）
  → 检查点重放（Checkpoint Replay）与过时结果裁剪
  → 本次输入整形（Shaping）
  → 提供方专用消息（Provider-Specific Message）

StoredMessage是展示视图（Read Model）相关类型。普通会话（Session）的这份视图现从运行时事件（Runtime Event）派生；旧式导入和WorkHub协调消息（Message）另有用途，不能据此把它们当作提供方历史（Provider History）的后备来源。缺少所需运行时事件（Runtime Event）时，先前历史（Prior History）为空；原生内容无法重放（Replay）时，过滤或纯文本降级也沿该事实源处理，不退回界面文字拼凑过去。

当前规则由宿主（Host）重新组成

工作区指令（Workspace Instructions）、本地记忆笔记（Local Memory）、技能说明包清单（Skill Inventory）、计划上下文（Plan Context）和工具面，由宿主（Host）为本工作轮次（Turn）组成。它们是当前输入的规则与背景，不能写成模型（Model）过去说过的话。

可以区分相对稳定的输入外层结构（Envelope）与逐步增长的尾部（Tail）：前者放系统指令（System Instructions）、模型（Model）配置与能力（Capability）组成，后者放用户、模型（Model）、工具（Tool）的有效事件（Effective Event）投影（Projection）。同一工作轮次（Turn）内前者可按合同复用，后者随模型步骤（Model Step）重建；这不是所有内容永久缓存的承诺。

同一个工具结果（Tool Result），为什么有三份内容？

先看两层：function_response.result是运行时（Runtime）接受并规范化的权威结果（Canonical Result）；modelProjection是以后给模型（Model）看的表示，可能早已省略内部字段。随后一次结果归档（Result Archive）又可能把这份有效正文替换成引用，于是出现第三份表示。

用具体条件理解：原始结果（Raw Result）含完整日志及不应重发的内部字段；初始模型投影（Model Projection）只留下允许发送的测试（Test）错误；后来的投影变换（Projection Transition）再把这段错误正文移出当前输入。ArchiveRead应恢复被这一步移走的前驱有效正文，不能返回原始内部字段，也不能随意返回整条变换链最后的状态。

当前宿主（Host）先证明账本（Ledger）的原投影（Projection）与变换链可以重建这份正文，再进入会话准入（Session Admission）范围，复核会话（Session）仍存在且来源未变，随后等待追加持久投影变换（Projection Transition）。准备成功不等于提交成功；只有提交后，新的有效历史（Effective History）才采用可回读引用。

这里的新写入路径利用账本（Ledger）重建，不要求另存一份完整正文工件（Artifact）；旧工件（Artifact）引用仍有兼容读取分支。读取时通过SQLite按会话（Session）和事件（Event）取得必要投影（Projection）字段，再沿折叠器（Reducer）接受的链找前驱。缺少提交记录，或会话（Session）、内容指纹（Digest）、前驱不匹配，就拒绝恢复。已经在更早阶段省略的字段不会自动补回。

并发时也不能以“我的追加调用成功”代替最终选择。宿主（Host）提交后按共同有效投影折叠（Effective Projection Fold）的胜出结果展示，避免两条并发分支各自宣称自己的替代表示就是当前版本。若本次归档失败，则保留此前仍可读的有效投影（Projection），不生成虚假的可读引用。实际提供能力（Capability）时，ArchiveRead才允许有界的 inspect / read / query / search。

投影变换（Projection Transition）不改写原始事实

正常可解码的记录用来源指纹（Source Digest）和前驱指纹（Predecessor Digest）串联，作用于目标运行时事件（Runtime Event），并不删除其权威结果（Canonical Result）。当前续步、下一工作轮次（Turn）、冷启动、上下文压缩（Context Compaction）和历史分支（History Branch）都需要尊重同一有效投影折叠（Effective Projection Fold）。

再看恢复时的四种情况。把某次 Bash结果标为B1，这只是本表的教学名字：

表 2 / Table 2 · 投影变换（Projection Transition）不改写原始事实
失败或变化发生在哪里当前处理不能推出什么
本次归档B1失败，此前有效投影（Projection）仍可读继续保留此前表示不能制造一个无法读取的引用
已提交变换无法解码，但能定位目标B1先前历史（Prior History）与当前续步返回该投影（Projection）不可用的表示不能绕过记录，重发原始B1正文；标记不可用也没有修好记录
已提交变换无法解码，连目标都不能定位共同加载器（Loader）报告读取错误不能猜测应替换哪个结果
检查点（Checkpoint）覆盖的事实未变，但有效表示已变重新核对当前有效来源，旧内容可能失效不能借旧摘要（Summary）恢复已移出的正文

新替换失败与旧提交损坏不是同一恢复问题。前者可能仍能沿此前表示继续，后者不能未经核对就回退到更早原文。这条规则保护后续输入，不负责撤回已经发送的请求。

安全前缀（Safe Prefix）究竟安全在哪里？

Maka的选源代码寻找连续前缀（Prefix），把切点退到未完成内容与固定保留项之前，同时保护工具调用（Tool Call）和工具结果（Tool Result）的关联，并保留规定数量的原文尾部（Raw Tail）。它维护的是结构与来源条件，不是摘要（Summary）的语义正确性。

当前用户锚点（Head Anchor）表示本项用户工作从哪里开始。首步前的 pre_turn阶段将它留在后续原文；轮内的 mid_turn阶段可以将覆盖范围延伸过它，但必须按检查点（Checkpoint）合同把该锚点原文重新呈现。不能把两种阶段都说成“当前用户请求绝不在覆盖范围内”。引导消息（Steering）中需要固定保留的当前指令也有独立保护。

这个区别解释了为什么“保留最近N条”仍不充分：数量相同，切点可能落在开放调用、未完成内容或当前要求之间。真实合法范围由结构与阶段判断，不能由教学编号或长度单独决定。

源码走读：候选为什么还不能立即生效？

第10章的规划类型 PlanHistoryCompactionResult用 fail_open表示没有可用替换。本节进入外层 compactActiveRequestHistory，其结果类型是 ActiveRequestCompactionOutcome；规划不可用、替换无法物化（Materialization）成消息（Message）或保存失败，会在这一层返回 fail。两个标签分属不同层，不应互换。

规划 fail_open → 外层返回 fail
规划得到候选 → 外层检查替换并等待保存
                 ├─ 失败：返回 fail，不应用候选
                 └─ 成功：更新投影状态，返回 compacted

简图只列本节相关分支，fail也不等于整个执行（Run）必然失败；继续、重试或终止由调用方（Caller）判断。下面两段是Maka真实源码窗口：第一段检查保存，第二段更新当前状态。两段之间还有独立记忆（Memory）通知，已在文字中说明，不能把它们当作紧邻的完整函数。

      };
    }

recorder是注入的保存回调。Promise.resolve将同步返回值与异步结果（Promise）统一处理；等待（await）确保结果先被处理，catch则在失败时直接返回。此后更新语句不可达。保存成功后，程序还可通知记忆（Memory）模块处理该历史范围；这项通知的异常被限制在自身，不推翻已完成的上下文压缩（Context Compaction）提交。

之后才进入同一函数中的状态更新窗口：

    state.previousCheckpoint = plan.checkpoint;
    state.projectionCheckpoint = plan.checkpoint;
    return {
      decision: 'compacted',
      checkpoint: plan.checkpoint,
      replacementMessages,
      estimatedTokensBefore: plan.estimatedTokensBefore,
      estimatedTokensAfter: plan.estimatedTokensAfter,
    };

前两句分别记住后续滚动可能使用的检查点（Checkpoint）和当前投影（Projection）选择；返回值再把候选记录、替代消息（Replacement Message）与估算数据交给调用方（Caller）。估算字段不能解释成完整请求的实际账单，第10章已说明其覆盖范围。

把更新移到保存之前，会让内存可能依赖无法恢复的检查点（Checkpoint）；删掉等待（await），则可能在异步保存尚未结束时报告 compacted。反过来，提交顺序成立也不证明语义无遗漏、请求一定装得下或代码任务已经完成。它与第06章共享“效果和记录之间有无空隙”的提问，但不能由此推出任意外部工具（Tool）都能获得相同事务（Transaction）边界。

检查点（Checkpoint）的保存与读取链

保存之所以能连接后续读取，是因为回调接到了账本（Ledger），消费者（Consumer）又会重新验证。compactActiveRequestHistory先等待已完成模型步骤（Model Step）的事件（Event）被消费，再读取当前工作轮次（Turn）的持久事件池，与先前事件（Prior Event）拼成候选历史（History）。队列（Queue）消费完成不保证这次持久读取必然成功；读取失败或找不到当前用户锚点（Head Anchor），就不能据此生成候选。

planHistoryCompaction随后选择合法前缀（Prefix）。覆盖身份来自原始事件（Raw Event），摘要（Summary）输入来自有效事件（Effective Event）。 因此记录同时保存 coverage.sourceDigest与 coverage.effectiveSourceDigest：前者核对“哪些原始事实”，后者核对“当时允许以什么表示读取”。内容指纹（Digest）用于判断来源一致性，不是真实性证明；下文的 d_raw等只是教学标签，不是实际哈希（Hash）值。

通过文本结构、配对和重放（Replay）检查后，保存回调进入 HistoryCompactCheckpointCoordinator.record。协调器（Coordinator）按会话（Session）排列提交，读取已有检查点（Checkpoint），用 canReplaceHistoryCompactCheckpoint判断候选是否已被较新结果取代。允许替换后，调用 AgentRun.recordHistoryCompactCheckpoint，经串行写队列（Queue）等待 runStore.appendEvent追加 history_compact_checkpoint_recorded。成功才更新协调器（Coordinator）缓存，再由外层切换本次状态。

重新加载时，loadLatestHistoryCompactCheckpointFromRunLedger先取得可用派生记录，需要恢复时再从执行账本（Run Ledger）选择合法项。AiSdkTurn中的 loadDurableTurnProjection继续核对原始前缀（Raw Prefix）；原始覆盖（Raw Coverage）不匹配不能复用，有效来源指纹（Effective Source Digest）不匹配则放弃旧内容，依据当前有效来源重建。之后才进行重放计划（Replay Plan）、消息物化（Message Materialization）、输入整形（Shaping），最终进入模型协议适配器（Model Adapter）。

滚动摘要（Rolling Summary）同样受此约束：旧内容已失效时，不能把它继承进新检查点（Checkpoint），再用新的指纹包装成有效来源。“保存成功”在这条链中只到已读追加合同完成；断电耐受性还要继续核对存储后端刷盘和恢复保证。

H1–H5：原始事实未变，为什么旧内容仍会失效？

为这条链建立独立教学历史（History）：H1是旧任务，H2是 Read调用，H3是对应结果，H4是模型（Model）说明“仅阅读，尚未修改”，H5是当前用户要求“只改README”。本例假定首步前的 pre_turn合法切点允许覆盖H1–H4，H2/H3不拆开，H5作为当前用户锚点（Head Anchor）留在原文尾部（Raw Tail）。这些编号不属于第22章的真实执行轨迹（Trajectory），也不自行证明切点合法。

H3的原始正文为20,000字符，而已有有效投影（Projection）只给出200字符及来源，候选C1只读后者。下面假设格式和结构检查均通过；简写句子不是可提交的完整检查点（Checkpoint）负载（Payload）。

现在量化本题可见正文的差异。令H1/H2/H4合计300字符，H3有效正文200字符，H5为50字符，暂时忽略消息包装、系统规则和工具说明：

Lbefore=300+200+50=550.L_{\mathrm{before}}=300+200+50=550.Lbefore​=300+200+50=550.

Lafter=350+50=400,ΔL=550−400=150,ρ=150550≈27.3%.L_{\mathrm{after}}=350+50=400,\qquad \Delta L=550-400=150,\qquad \rho=\frac{150}{550}\approx27.3\%.Lafter​=350+50=400,ΔL=550−400=150,ρ=550150​≈27.3%.

改来源或提交时机的两道解析

问题1。 C1通过重放（Replay）检查后被较新C2阻止保存，能否先用C1、稍后补存？若C1已保存，后来只有有效来源变了，能否只凭原始指纹复用？

参考答案。 两种做法都不成立。第一种绕过先保存后应用，也不能假定当前内存已采用C2；应沿失败或重新加载路径处理。第二种混淆覆盖身份与内容时效性，必须重新核对当前有效来源，必要时重建或重新摘要（Summary），不能回灌原始H3。

问题2。 H5被错误纳入可改写摘要（Summary），与将550字符换成650字符，分别需要什么检查？

参考答案。 前者要检查当前用户锚点（Head Anchor）、保护内容与切点，长度门无法修复约束丢失。后者可以由新增严格更小（Strict-Smaller）政策拒绝，但先要定义比较范围；这属于设计建议，不是现行门槛。即使正文更短，语义仍可能错，系统、工具（Tool）或媒体仍可能使总请求超窗。

错误表示会在哪些地方改变判断？

调用结果配对与未完成内容

若旧前缀（Prefix）结束于工具调用（Tool Call），尾部（Tail）却只留下工具结果（Tool Result），重放（Replay）会失去完整协议单元，甚至直接被模型服务提供方（Provider）拒绝。开放调用也不能被提前覆盖。未完成流（Partial Stream）中的半句话或半份参数同样不能视为稳定事实；安全前缀（Safe Prefix）会退到部分事件（Partial Event）之前。

当前约束、语义与来源是不同检查

固定保留的引导消息（Pinned Steering）可能要求“不访问网络”或“删除前先询问”。把它概括为“谨慎操作”已经改变含义，需要切点保护或当前宿主（Host）重新提供权威指令。大型语言模型（Large Language Model，LLM）还可能把“测试未运行”写成“测试已通过”；结构有效与来源指纹（Source Digest）匹配并不能发现所有此类错误。

来源检查解决另一类失败：历史（History）修复、分支或迁移后，旧记录可能不再对应当前完整前缀（Exact Prefix）。重放（Replay）前需核覆盖终点身份（Through Identity）、范围和指纹，不能只挑“会话（Session）最新摘要（Summary）”。与原始账本（Ledger）冲突时，不能仅因表示较短就把它当作更可信的证据（Evidence），或让它覆盖来源事实。

过时正文与重复失败

已经归档的20万字符日志若从原始结果（Raw Result）重新读回摘要（Summary）输入，就绕过了已提交投影变换（Projection Transition）。上下文压缩（Context Compaction）、重放（Replay）与预算（Budget）计算必须使用共同有效投影折叠（Effective Projection Fold），不能各自随意取原始正文。

相同来源与配置反复生成结构不合法（Malformed）的候选，又会形成另一种无进展循环。活性保护（Liveness Guard）按输入指纹（Fingerprint）限制重复失败，必要时熔断（Circuit），保留尊重既有变换的有效历史（Effective History）；无法安全重建就报告失败。这类保护减少重复尝试，不证明摘要（Summary）语义正确。

两类检查点（Checkpoint）

Maka当前提供方原生状态（Provider-native State）的重放（Replay）要求同时满足：模型服务提供方（Provider）类型为OpenAI Codex，connectionId精确相同，modelId精确相同。只匹配一个字段、或只认为两个模型（Model）相似，都不够。文本摘要（Text Summary）与这种私有状态不能任意互换。

两类检查点（Checkpoint）都需要覆盖范围（Coverage）、覆盖终点身份（Through Identity）、来源指纹（Source Digest）及阶段/锚点信息。兼容性、前缀（Prefix）匹配和可物化（Materialization）结构是采用条件；本地并没有严格更小（Strict-Smaller）的硬门。短历史（History）的摘要（Summary）反而更长，是质量与成本问题，不能把希望它更短写成已有代码保证。

主动整形（Shaping）与真实溢出（Overflow）不是同一信号

Maka的主动容量判断使用同模型（Model）、同连接（Connection）上一次实际接受请求的用量。假设有效输入词元（Input Token）数为 I>0I>0I>0，输出词元（Output Token）数为 O≥0O\ge0O≥0，用户声明窗口为 WWW，容量检查中的比较量为

B=I+O,R=min⁡(2O,8000),B+R≥W.B=I+O,\qquad R=\min(2O,8000),\qquad B+R\ge W.B=I+O,R=min(2O,8000),B+R≥W.

BBB是已知基线，RRR是按上次回答预留的数量，WWW是当前声明的上下文窗口（Context Window）；三者单位都是词元（Token）。这只是主动触发中的容量条件，不是本次完整请求大小公式。没有声明窗口或有效实测输入时，不把未知当作零再强行触发；新增日志、图片与用户文本是否能装下，仍由模型服务提供方（Provider）实际判断。

如果摘要（Summary）请求本身被拒绝，Maka只退到同路径先前被接受过的输入边界，不随意猜测减半；没有可证明边界或再次拒绝，就保留原有效投影（Projection）并报告失败。曾接受过的范围也不是新请求必然成功的证明，因为摘要（Summary）指令已经不同。

当模型协议适配器（Model Adapter）将真实错误分类为 context_overflow，并且当前路径具备恢复状态、尚未用过重试机会时，程序才进入有界恢复：优先省略可省略的历史（History）图片；没有这种图片时才尝试上下文压缩（Context Compaction），随后只重试一次。失败仍暴露真实错误，不无限压缩重发。

窗口余量与两种大内容通道

contextRemaining可由最近物理请求的输入词元（Input Token）观测形成，进入持久消息（Message）和实时事件（Event），供用户界面（User Interface，UI）重开后展示。它描述一次请求的测量，不能当成之后永远准确的容量承诺。

读取图片快照（Image Snapshot）的上下文外置（Context Offload）使用内容寻址（Content Addressing）的 ContextOffloadStore，包含会话（Session）归属、复制、释放、退役和垃圾回收（Garbage Collection，GC）。大工具结果归档（Tool Result Archive）则使用账本（Ledger）归档能力（Capability）和 ArchiveRead，旧工件（Artifact）引用继续兼容。

当前 tool_result_archive在上下文外置（Context Offload）负责者（Owner）配额中的值仍为0，不能说所有工具结果（Tool Result）都已统一迁入该存储。这两条通道解决内容负载（Payload）的物化（Materialization），不会自动提取用户偏好或完成长期记忆召回（Memory Recall）。

同一历史（History）换成Pi：看真正的消费者（Consumer）

Pi是另一种开源代码代理（Code Agent）。其默认压缩路径先寻找合法保留点并生成摘要（Summary）；手动路径未被取消时，调用 SessionManager.appendCompaction(summary, firstKeptEntryId, ...)，再用 buildSessionContext()更新 agent.state.messages。

读取方 buildContextEntries沿当前叶节点（Leaf）的分支路径找到最新压缩条目（Compaction Entry），留下该条目、从 firstKeptEntryId开始的旧尾部（Tail），以及它之后的新条目（Entry）。若本题把H5选为首个保留项，目标同样是摘要（Summary）加H5原文，但树中位置与切点引用参与了重建。

两个项目都保存摘要（Summary），不意味着它们具有相同持久化（Persistence）方式或原始/有效双来源指纹合同。更细切点见第36章。跨项目比较应追到各自消费者（Consumer），不能只比一个字段名称。

机制问题与方法比较

问题1。 StoredMessage为什么不能直接替代运行时事件（Runtime Event）？

参考答案。 展示视图（Read Model）与正常模型重放（Replay）承担不同职责；后者需要配对、部分内容（Partial）、可见性、终态（Terminal State）和模型服务提供方（Provider）来源语义。当前所述路径不回退到界面转录文本。

问题2。 已归档大结果为什么不能从权威正文重新注入？

参考答案。 权威事实仍在，不表示它仍被选为当前模型输入（Model Input）。后续消费者（Consumer）必须尊重已提交投影变换（Projection Transition）。

问题3。 提供方原生状态（Provider-native State）比文本摘要（Text Summary）更准确吗？

参考答案。 不能从不透明（Opaque）形式推出保真度。两者主要差别在可审阅性与兼容条件，语义质量仍需另外评价。

问题4。 没有声明窗口，是否依靠字符估算主动触发容量压缩？

参考答案。 所述主动判断不会这样做，还需要同路径的有效用量；真实溢出仍有独立、有条件的恢复入口。未知不等于零。

问题5。 检查点（Checkpoint）更长是否必然被本地拒绝？

参考答案。 不必然。当前采用门检查结构和可重放性（Replayability），大小用于诊断，可容纳性（Fit）由实际模型服务提供方（Provider）请求检验。收益仍应另外评价。

问题6。 recorder抛错后会更新 projectionCheckpoint吗？

参考答案。 不会。catch返回 write_failed，更新语句不可达；这是本章短源码窗口可以直接核对的顺序。

同一历史的三份输入对照用固定H1–H9比较全文、摘要（Summary）加尾部（Tail）、占位符（Placeholder）加引用（Reference），沿README只读写授权分支检查失败断言（Assertion）和待完成状态。

换模型（Model）时，也不能只因历史（History）没变便复用全部预算（Budget）与原生状态。需要重新核对当前窗口、输入投影（Projection）及重放兼容性（Replay Compatibility）。Pi的逐模型设置与DeepSeek开源运行支撑（DeepSeek Harness，DSH）的系统提示词（System Prompt）投影（Projection）提供不同对照，见模型身份与压缩。
