第一部分：最小 Agent、项目环境与机制桥接 · 08 / 62

第 08 章｜从 mini 到 Maka 的机制对应

本章概览

核心问题：Maka 怎样分配同一行动循环中的责任，并依据状态和结果继续工作？

关键概念：Harness（运行支撑）：连接模型与环境；工作身份：关联会话和执行；持久事实：供后续查询的记录；owner（负责者）：持有对应决定权；评价：按结果判断任务。

关系主线：六组责任把 mini 的简单实现接到 Maka；中断、长任务和协作分别引入新的状态与控制。

mini 已经展示了输入、模型请求、真实命令与观察怎样连接。第07章又暴露了写入发生而记录落后的窗口。转到 Maka，问题从“循环能否运行”扩展为“多轮工作由谁接纳，哪些结果可信，失败后依据什么继续”。

从共同闭环到六组责任

第01章把 Harness 分成六组学习责任。下面的箭头从共同闭环指向职责地图，框内六组并列，不是必须顺序执行的步骤；一份观察可以同时参与输入、恢复和评价。

表 1 / Table 1 · 从共同闭环到六组责任
责任组mini 已给出的起点Maka 中继续追踪的问题
输入组织（Input Composition）任务、消息与命令结果组成下一输入第15章追当前输入，第19章处理长历史；哪些材料入选、怎样保持可用？
模型与工具循环（Model / Tool Loop）Model 提出动作，Environment 执行并反馈第12章、第16章追请求准入、工具绑定和下一步消费
状态与恢复（State / Recovery）内存消息、轨迹快照与文件效果第13章、第14章、第18章区分身份、事实、未知与恢复；第20章另管长期信息
权限与隔离（Permissions / Isolation）执行前确认和具体环境能力第17章区分准许动作与实际资源限制
任务推进与协作（Task Progress / Collaboration）一次 run 的循环与简单退出规则第23章解释方法复用与委派，第24章解释持续工作与触发
观察与评价（Observation / Evaluation）output、退出状态、测试和差异第26章把任务结果、判断范围和总成本连接起来

Maka 的 Host（宿主）负责接纳和协调工作，Client（客户端）负责提交请求和展示结果。Host 与 Client跨越多组责任，把连接、执行与状态观察接起来。Skills 的正文装载连接输入与方法复用，Memory 的读取连接长期状态与当前输入；边界之间需要真实的消费者。

发现和检索也跨越这些责任：挑选相关代码证据参与输入组织，提出并执行搜索参与模型与工具循环，能发现和调用哪些方法或工具还受可用性与准入限制。后面的第37章代码检索、第16章工具调用与第23章方法发现都能放回这张地图，不需要为它们另设一组固定职责。

短任务可以在简单循环里完成；持久恢复、长期记忆、子任务和定时调度分别针对增加的需求。组件更多是否值得，要看它解决的失败、节省的工作和新增的成本。

工作身份、记录与控制责任

一次 mini run(task) 与 Maka 的 Session、Turn、Run 分别处在不同层次。到 第11章后，同一修复将逐步固定会话归属、用户工作和执行身份，而不是只按相同英文名称对应类。

轨迹快照与持久事实的边界也不同。mini 的 messages 让下一次模型获得已加入的材料；trajectory 保存的是某个时点的状态。Maka 还要区分执行事实、模型输入与界面投影，以及各自负责更新的组件。

模型说“完成”、界面仍在运行和文件已经改变可以同时出现。要解释它们，需分别查当前执行、实际效果与任务验收，不能用一个标签覆盖全部状态。

同一修复任务的两条执行链

这里先摘取将在第22章展开的真实任务作对照：修正 README 命令，并修复 formatDuration 的余秒计算（% 100 → % 60）。mini 与 Maka 都完成了这两处修改，过程却不同。

下表中的 Maka 工具 Read 表示读取文件，Edit 表示修改文件，Bash 表示执行命令；本节只比较它们在闭环中的职责，具体参数与执行过程在第16章展开。

表 2 / Table 2 · 同一修复任务的两条执行链
同一个学习问题mini 实际片段Maka 实际片段
文件内容从哪里来？Bash 中 cat 四份文件一次回答提出四个 Read
谁真正修改文件？Bash 执行 sed两个原生 Edit 调用
测试在什么时候发生？修改前观察失败，修改后复测读源码后先修改，再运行测试
怎么继续？环境结果进入下一次 messages工具结果形成原生记录并进入后续模型请求

两条真实路线都能讲清“动作 → 观察 → 下一步”，不需要逐步相同。这次修复支持给定场景的结果；任意崩溃窗口是否得到解决，还要检查相应身份、记录和恢复合同。

问题解析

身份与记录

问题 1。 用户在断开后重发同一句修复要求。为什么仅看文本，不能判断是在继续原来的工作还是发起新尝试？

解释。 相同文本没有提供工作身份与执行尝试的关系。要查系统怎样标识、接纳这次请求，不能把 mini run 与 Maka Run 直接画等号。

问题 2。 磁盘保存着测试日志，下一次模型回答却没提到它。应该继续检查什么？

解释。 检查它是否实际进入本次模型输入，以及以什么形式进入。保存着一份日志，不能证明模型已经看到它；回答没提到，也不能单独证明它没看到。

问题 3。 界面写着“运行中”，模型说“完成”，README 已改而测试记录缺席。哪些负责者和记录能说明当前状态？

解释。 找到负责推进执行、保存状态的组件，核对实际文件、已有工具结果与退出记录。分别说明已证实与待确认的部分；三个表面描述不能互相代替。

工具、权限与效果恢复

沿同一修复继续追踪：模型请求修改 README，首先要有可解释、可绑定的工具；动作允许后，由相应执行环境操作文件；得到或丢失回执，又决定后续能确认什么。人工批准、执行隔离、持久结算分别解决许可、访问和记录问题。

例如写入已经发生而回执缺失，重新看到旧轨迹只说明恢复了一部分记录。第18章将解释怎样保存已知与未知、核对效果并选择后续动作。具体保证取决于该执行路径；同一接口接入不同后端，不能自动继承相同的恢复能力。

输入、委派与宿主机制

长日志需要选择与压缩，未来任务需要保存和读取长期信息，复用方法与委派工作则分别改变输入和执行。这些都是在共同闭环上增加特定能力。

表 3 / Table 3 · 输入、委派与宿主机制
新条件应追问的连接
保存了一个偏好哪次读取会选择它，何时进入模型输入？
加载了一个 Skill正文提供了什么方法，后续工具是否实际执行？
交给一个子任务它收到哪些材料、能修改什么、结果由谁采纳？
到了定时时间本次触发是否已认领，当前任务与权限是否仍有效？
Client 断开工作归谁管理，当前状态如何重新观察？

另起 mini 进程可以承担独立工作，但父子关系、交付状态和恢复合同仍需另外建立；给 prompt 加一段方法，也不自动获得 Skill 的发现和装载机制。比较从实际状态与连接开始。

具体执行路径的比较

问题 1。 为什么确认（Confirmation）、工具可见性（Tool Visibility）与执行隔离（Execution Isolation）不能合成一个开关？

解释。 确认（Confirmation）让用户对已展示的候选动作决定是否继续；第05章的 mini 确认模式针对一组动作询问，不会因此新增 OS 隔离。工具可见性（Tool Visibility）决定本步向模型展示哪些工具及其请求格式，工具出现不等于具体调用已经获准。执行隔离（Execution Isolation）由实际执行环境限制资源访问，要看越界行为能否被强制阻止。三者各有作用；一次确认不替代当前权限与边界检查，隐藏工具也不能代替执行隔离。

问题 2。 从保存日志走到构造模型输入，新增了哪一个决定？

解释。 决定这一次判断需要看到哪些信息，如何表示并控制大小；持久存在并不等于实际进入模型输入。

问题 3。 如何判断某项 Maka 保证可以应用于一个具体 adapter？

解释。 查该路径的真实接线、状态负责者和失败处理，并分开源码推导与实际运行范围。共享接口或另一条路径通过检查，都不足以覆盖它。

项目环境怎样接到这张地图

Harness 的能力需要在具体仓库中取得材料和反馈。项目入口规则、测试脚本、代码结构和当前改动说明分别提供工作约定、执行入口和当前事实；它们仍需被发现、读取与核对，规则文字也不代替硬权限。

Agent 可操作的项目环境将把这些材料组织成一份完整仓库案例，展示“可以开始诊断”与“业务已经正确”的区别。随后，语言桥解释 TypeScript 控制流，Maka 章节再逐步展开上面的机制。
