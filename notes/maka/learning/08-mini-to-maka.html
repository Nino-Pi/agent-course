第一部分：最小 Agent、项目环境与机制桥接 · 08 / 66

第 08 章｜从 mini 到 Maka 的机制对应

本章概览

核心问题：当一次修复扩展为可中断、多轮和协作的工作，运行支撑（Agent Harness）怎样分配新增责任？

关键概念：运行支撑（Agent Harness）连接模型（Model）与执行环境（Environment）；工作身份（Work Identity）关联归属与执行；持久事实（Durable Fact）为后续判断保留记录；负责者（Owner）管理相应状态（State）；消费者（Consumer）实际读取并使用某份材料。

关系主线：先把共同循环放回六组教学职责，再用同一修复比较两种实现。新增机制要连接具体对象和消费者（Consumer），名称相同或一次修复成功都不能替代保证核对。

前情回顾：把第07章的问题带入新的实现

最小循环（Minimal Loop）已经走通“行动请求（Action）→执行→观察结果（Observation）→下一次判断”。第06–07章又说明：效果（Effect）可以先于记录保存；停止也不等于任务成功。因此，继续工作需要知道当前状态（State）、可用证据（Evidence）以及谁来决定下一步。

本章把这些问题带到 Maka。目的不是记住更多类名，而是理解同一个问题怎样由不同组件承担。先沿职责地图阅读，再看两条真实修复链，最后判断新需求还要求哪些连接；具体字段和调用细节留到对应机制章。

从共同闭环到六组责任

第01章给出了运行支撑（Agent Harness）的六组教学职责。它们是按“需要解决什么问题”分组，不规定组件数量，也不是六步执行流程。一个工具结果（Tool Result）可以同时进入当前模型输入（Model Input）、帮助恢复（Recovery），并作为评价（Evaluation）的材料。

读图时先看上方共同循环，再看下方六个并列框。真正的实现会跨框连接：例如选择一份测试结果作为输入，既涉及记录从哪里来，也涉及本次判断需要看什么。图中布局用于并列职责，不要求运行时逐框经过。

表 1 / Table 1 · 从共同闭环到六组责任
责任组mini 已给出的起点Maka 中继续追踪的问题
输入组织（Input Composition）任务、消息（Message）与命令结果组成下一次输入第15章追实际入选材料，第19章处理长历史（History）；保存过的内容怎样进入当前判断？

宿主（Host）负责接纳与协调工作，客户端（Client）负责提交请求和展示结果；第25章会解释它们怎样跨越多组职责。技能说明包（Skill）的正文装载连接输入与方法复用，记忆（Memory）的读取连接长期记录与当前判断。这里的消费者（Consumer）指实际读取并使用材料的人或程序：只有文件存在，没有读取和使用链，能力就还没有进入本次工作。

发现与检索也能放回这张地图。代码检索（Code Retrieval）选择相关证据（Evidence），工具发现（Tool Discovery）确定可以请求哪些能力；前者参与输入组织（Input Composition），后者与调用格式、可用性（Availability）及接纳条件有关。后续第37章、第16章和第23章再展开它们，不需要为每个新名词新增一组固定职责。

短任务可以在简单循环中完成。引入更多组件的理由应落在新增需求上：中断以后依据什么继续，长期信息何时被使用，子任务（Subtask）的结果由谁接纳。判断设计是否值得，要同时看解决了哪些失败和新增了什么成本。

工作身份（Work Identity）、记录与控制责任

mini 的 run(task) 是一个入口调用。Maka 的会话（Session）、工作轮次（Turn）和执行（Run）分别关联交互归属、用户可观察的一项工作与一次具体运行。它们回答不同问题，不能因为都出现了 run 就把对象画等号；第11章以后会逐步展开。

记录也要按用途区分。mini 的消息列表（Message List）为下一次模型（Model）请求提供材料，执行轨迹（Trajectory）保存某个时点的快照（Snapshot）。Maka 进一步区分执行事实（Execution Fact）、模型输入（Model Input）与界面投影（UI Projection），每种表示都有负责更新的组件。

例如界面仍写“运行中”，模型（Model）却说“完成”，文件也已经改变。这三个描述可以同时出现，因为它们分别来自展示、生成文本与实际效果（Effect）。要判断整项工作，仍需核对当前执行（Run）、可信工具结果（Tool Result）及验收条件；某个标签不能替所有对象结账。

同一修复任务的两条执行链

这里摘取将在第22章展开的真实案例作对照。任务包括修正 README 的命令，以及把 formatDuration 的余秒计算从 % 100 改为 % 60；测试和差异（Diff）共同支持结果判断。mini 与 Maka 都完成了这两处修改，使用的请求表达和执行顺序不同。

Maka 的 Read、Edit、Bash 是工具标识，分别承担读取文件、修改文件、运行命令。mini 则可通过命令工具完成对应操作；标识保留原文，具体参数与结果合同在第16章展开。

表 2 / Table 2 · 同一修复任务的两条执行链
同一个学习问题mini 实际片段Maka 实际片段
文件内容从哪里来？命令工具（Command Tool）中用 cat 读取四份文件一次回答提出四个 Read 请求
谁真正修改文件？命令工具（Command Tool）执行 sed两个原生 Edit 调用

两条路线都闭合了“行动请求（Action）→观察结果（Observation）→下一步”。职责相同不要求调用形式、次数和顺序相同。反过来，给定场景中修复成功，也不证明任意中断都可恢复（Recovery）；那还需要核对具体执行路径的身份（Identity）、持久记录和失败处理。

问题解析

身份（Identity）与记录

问题1。 用户断开后重发相同要求，为什么仅看文本不能判断是继续原工作还是新建尝试？

参考答案。 相同文本没有说明工作身份（Work Identity）与执行尝试的关联。应查系统如何标识并接纳这次请求，不能把 mini 的 run 调用与 Maka 的执行（Run）直接等同。

问题2。 磁盘有测试日志，下一次回答却没提到。应继续检查什么？

参考答案。 检查它是否被选入当前模型输入（Model Input）、以什么形式进入。保存不能证明已被消费；回答没有提到，也不能单独证明模型（Model）没有看到。

问题3。 界面写“运行中”，生成文本说“完成”，README 已改而测试记录缺席，怎样描述现状？

参考答案。 查相应负责者（Owner）掌握的状态（State），核对文件、工具结果（Tool Result）与退出记录。已知修改发生，但测试结论仍待确认；界面标签和生成文本不能补出缺失证据（Evidence）。

工具（Tool）、权限（Permissions）与效果恢复（Effect Recovery）

沿同一修复继续追踪：行动请求（Action）首先要能被解释并绑定到执行者；允许以后，由执行环境（Environment）操作文件；返回或缺失的观察结果（Observation）决定当前可以确认什么。批准（Approval）、隔离（Isolation）和持久结算（Durable Settlement）分别处理许可、资源访问和记录，不能压成一个“安全”开关。

如果写入发生而反馈缺失，重新装载旧执行轨迹（Trajectory）只说明恢复了一部分记录。第18章会解释如何保留已知与未知、核对效果（Effect），再选择后续动作。同一接口接到不同适配器（Adapter）时，实际执行与返回逻辑可以不同；共享接口不自动保证相同恢复（Recovery）能力。

输入、委派（Delegation）与宿主（Host）机制

长输出需要选择与压缩，未来任务可能需要记忆（Memory），可复用方法与子任务（Subtask）则分别改变输入内容和执行分工。每种扩展都应追到实际消费者（Consumer），而不是停在“已经配置了一个组件”。

表 3 / Table 3 · 输入、委派（Delegation）与宿主（Host）机制
新条件应追问的连接
保存了一个偏好哪次召回（Recall）会选中它，何时进入当前模型输入（Model Input）？
加载了一个技能说明包（Skill）正文提供什么方法，后续工具（Tool）是否实际执行？
委派了一个子任务（Subtask）它收到哪些材料、允许修改什么，结果由谁采纳？
到了定时时间触发（Trigger）是否已经被认领，任务与权限（Permissions）是否仍有效？
客户端（Client）断开工作由哪个负责者（Owner）管理，怎样重新观察当前状态（State）？

另起 mini 进程可以承担独立工作，但父子关系、交付状态（Delivery State）与恢复（Recovery）合同仍需另外建立。向提示词（Prompt）加一段方法，也不自动获得技能说明包（Skill）的发现与装载机制。比较应从真实对象与连接开始。

具体执行路径的比较

问题1。 为什么确认（Confirmation）、工具可见性（Tool Visibility）和执行隔离（Execution Isolation）不能合并？

参考答案。 确认（Confirmation）让用户对已经展示的候选操作决定是否继续；第05章的 mini 模式针对一组操作询问，不会因此新增操作系统（Operating System，OS）隔离。工具可见性（Tool Visibility）决定本步展示哪些工具（Tool）及请求格式，不代表具体调用已获准。执行隔离（Execution Isolation）由环境强制限制资源访问。三者分别回答“是否继续、可以请求什么、执行时能访问什么”。

问题2。 从保存日志到构造模型输入（Model Input），多了哪一个决定？

参考答案。 决定本次判断需要哪些信息，以及怎样表示并控制大小。持久存在不等于实际进入这次请求。

问题3。 某项 Maka 保证能否应用到具体适配器（Adapter），该怎样判断？

参考答案。 查这条执行路径的实际接线、状态负责者（State Owner）和失败处理，分别说明源码推导与运行核验范围。另一条路径通过检查，不能替代当前路径的证据（Evidence）。

项目环境（Project Environment）怎样接到这张地图

运行支撑（Agent Harness）需要在具体仓库中取得材料和反馈。入口规则说明工作约定，测试脚本提供执行入口，源码与已有差异（Diff）说明当前事实（Fact）。这些材料仍需被发现、读取和核对；规则文字本身也不替代权限（Permissions）的强制执行。

第09章的项目环境（Project Environment）将用一个完整仓库案例展示接手过程：怎样确认可以开始诊断，以及为什么这还不是业务已经正确。随后第10章补 TypeScript 的语言读法，再逐步进入 Maka 的具体机制。
