第 07 章｜最小循环的能力边界

本章概览

核心问题：最小循环能够完成正常修复，却还缺哪些安全继续工作的条件？

关键概念：effect（效果）改变外部状态；observation（观察）向循环提供反馈；保存保留过程；identity（身份）区分原工作与新尝试；owner（负责者）决定状态变化。

关系主线：效果、观察和保存有先后间隔，恢复不能只重放旧消息。工作身份、权威记录、执行权限与输入选择分别补足不同缺口；一次本地故障案例不证明通用恢复能力。

本章的文件、轨迹与退出结果来自 第06章 的固定故障窗口。

1. 正常情况下，三件事紧挨着发生

mini 的正常执行顺序是：

Model 提出修改 README 的 action
    ↓
Environment 执行，文件实际改变
    ↓
output 形成 observation，追加 messages
    ↓
这一轮 finally 保存 trajectory
    ↓
下一次 Model.query 读取当前 messages

文件改变叫 effect；执行结果进入 Agent 的信息叫 observation；把当前对象写到磁盘是保存。平时它们挨得很近，看起来像一件事，但并不是一个不可分割的操作。

Maka 是本课程持续研究的 TypeScript Agent Harness 实现。mini 用于看清最小循环，Maka 用于继续追踪状态、权限、恢复等较完整的运行职责。

真实模型也能完成这条正常链：第22章中，mini 和 Maka 都修正了 README 命令与时间格式化函数，并通过测试。第06章 则在预定时点终止进程，让“效果已发生、结果还没保存”的窗口可被重复检查。两类实验分别回答正常修复和记录窗口的问题。

2. 第06章 的文件、轨迹与退出记录

第06章 使用真实 DefaultAgent 与 LocalEnvironment：第一步读 README 并保存；第二步写 README 后，定点终止子 Agent，来不及返回 observation。

表 1 / Table 1 · 2. 第06章 的文件、轨迹与退出记录
证据（Evidence）实际看到什么它能回答什么
文件系统中的 README已从 npm run check 改成 npm test读回时，目标文件确实已经改变
trajectory.messages仍只有第一步读取旧 README 的消息最近一次保存的消息停在哪里
控制进程记录的退出结果子 Agent 被定点硬终止这次运行没有走到正常退出

第二步 action、result 与 exit 都尚未保存进磁盘 trajectory 的 messages 快照。退出原因来自实验控制进程的记录，不能因为能在实验报告里看到它，就假设 Agent trajectory 里也有同一条事实。

所以同一句“Agent 失败了”过于粗略。更准确地说：进程被终止，循环没有正常完成；README 的修改已经发生；已保存历史还不知道这次修改结果。

此处缺席的不只是成功 observation，第二步 action 也尚未落入磁盘 messages 快照；它可以已经加入进程内的消息列表，两者处于不同保存时点。确定性模型配置里预先保存的脚本不算已经执行的历史。

3. 下一步应该做什么

如果只拿旧 trajectory 继续，会面临三种看似合理的选择：

  • 再执行一次：若动作是追加内容，可能重复写入。
  • 直接宣布成功：若原操作只完成一部分，会报告不完整结果。
  • 直接宣布失败：这次 README 明明已经改过，又会遗漏现实中的变化。

对这个可以直接读回的小文件，先检查 README 和 diff，确认目标状态，再继续测试。如果目标替换已完成，就接着验证；如果只改了一部分，再确定剩余修改。读回文件解决的是“当前状态是什么”，它未必能重建所有中间步骤。

对无法直接查询的外部操作，答案可能仍是“尚未确认”。这不是第四种猜测；它承认当前证据不足。后面的恢复机制要做的是缩小这种不确定性，并为仍不确定的情况安排处理办法。

没有 observation，不能推导出没有 effect。

4. 身份、记录与负责者

安全地继续工作，需要明确三个对象：

  1. 这是谁的工作？ 用户重发请求时，是继续原来的意图，还是新建一次尝试？需要区分一份长期工作空间、一次用户请求与一次实际执行。
  2. 哪些记录代表已经发生？ 模型准备修改的文本、工具结果、磁盘中的目标文件，是不同证据；模型下一次看到的输入也不必等于全部历史。
  3. 谁决定接下来做什么？ 界面显示“正在运行”、模型说“完成”、后台进程正在退出，可能不同步。需要知道谁负责保存和裁决相应状态。

后面进入 Maka 时，会用 Session（会话归属）、Turn（用户可观察的一项工作）、Run（一次具体执行）区分这些身份，用 Owner 表示有权管理状态的负责者。记录本身与由记录整理出的视图则分别称为事实和投影。第08章先建立对应关系，第13、14章再展开定义与实现。

问题解析

写入窗口

问题 1。 第06章 的文件已改而轨迹停在读取，是矛盾吗？

解释。 不是。effect、observation 和保存有先后顺序，强制退出发生在它们之间。

问题 2。 为什么下一步应该检查 README，而不是只重复原命令？

解释。 先读回目标状态并检查 diff，才能决定还需做什么；比如追加文本重复执行会多写一行。读回结果也不一定重建出全部执行历史。

问题 3。 当前实验是否已经证明自动恢复、所有副作用可去重？

解释。 没有。它只证明一个固定本地写入窗口，未实现通用恢复，也未验证外部系统的去重能力。

5. 权限、输入与跨进程工作

执行权限与效果恢复

在第04章中，npm test 可以启动 package.json 声明的脚本。若采用第05章的交互确认模式，即使用户确认了这条命令，也不等于操作系统已经限制脚本能读哪些文件、能访问哪些网络。第17章分别解释策略允许范围与执行时的强制限制。

第06章 的结果缺席会引向 第18章：执行前后留下哪些记录，何时能查证，何时不能重放。那一章把执行前和结果结算时的两次持久提交简称为 T1/T2，本章只先提出“效果与记录可能不同步”的问题。

长日志与长期信息

如果修复要进行很多轮，日志会越来越多。原始输出值得保留，但下一次模型未必需要全部重读。第19章解释历史输入的压缩；第20章解释信息怎样跨任务保存和召回。

跨进程工作与所有权

再设想一个正常场景：README 已修改，测试也结束并保存了结果，用户还没提出下一问。聊天记录和项目文件需要留下，但执行进程是否必须一直占着内存？先问哪些内容必须保存、哪些运行现场可以重建、谁有权开始下一次工作，再讨论何时可以释放当前计算。这个问题接到 第13章 的身份与进程和 第25章 的执行载体；第06章 并没有验证这种自动释放能力。

委派、持续推进和断线后的观察还会增加新的责任，第08章将把这些问题放回共同的机制地图。

授权与输入选择问答

问题 1。 “用户允许执行 npm test”还没有回答什么执行边界问题？

解释。 尚未说明底层能否强制限制脚本访问的文件、网络和子进程；确认与隔离需要分别解释。

问题 2。 为什么保存完整日志与下一轮把完整日志交给模型，是两个决定？

解释。 保存服务于留存、核对等需求，模型输入服务于本次判断并受窗口限制；两者可由不同视图承担。
