第 07 章｜最小循环（Minimal Loop）的能力边界

本章概览

核心问题：一次正常修复能够完成，为什么中断以后仍不能直接继续？

关键概念：效果（Effect）是执行环境（Environment）中的实际变化；观察结果（Observation）是程序得到的反馈；执行轨迹（Trajectory）保存某个时点的过程。身份（Identity）区分原工作与新尝试，负责者（Owner）拥有相应状态（State）的管理权。

关系主线：实际变化、收到反馈和保存记录之间存在间隔。先依据证据（Evidence）确定当前状态（State），再决定下一步；工作身份（Work Identity）、权威记录与执行边界（Execution Boundary）分别补足不同缺口。

前情回顾：完成了动作，不等于留下了全部记录

前面几章已经把一次循环拆开：模型（Model）提出行动请求（Action），执行环境（Environment）真正运行命令，返回的观察结果（Observation）进入消息（Message），供下一次判断使用。第05章进一步说明，停止执行与通过任务验收是两个判断；执行轨迹（Trajectory）也只能保存已经进入当前对象的内容。

第06章把这种区别变成了一个可检查的例子：先读 README，再把其中的 npm run check 改成 npm test；文件写完以后，控制进程立即终止子进程。磁盘上的文件已经改变，最近一次保存的记录却仍停在读取旧文件。本章沿用这组条件，讨论继续工作之前究竟还缺什么。

1. 正常情况下，三件事紧挨着发生

正常路径可按下面五步阅读。右栏刻意分开“谁获得了新信息”与“哪里真的改变”，因为这正是中断以后容易混淆的两件事。

表 1 / Table 1 · 1. 正常情况下，三件事紧挨着发生
顺序发生的操作此时新增了什么
1模型（Model）提出修改 README 的行动请求（Action）程序得到一个候选操作；文件尚未因此改变
2执行环境（Environment）运行修改命令文件变化形成效果（Effect）
3返回值形成观察结果（Observation），追加到消息列表（Message List）后续判断可以使用这份反馈
4当前步骤的 finally 保存执行轨迹（Trajectory）磁盘留下此时对象的快照（Snapshot）
5下一次 Model.query 读取当前消息列表（Message List）模型（Model）依据已经加入的材料继续

这些操作挨得很近，正常阅读日志时容易把它们当作一个整体。但“先后执行”不等于“不可分割”：进程可能在两个操作之间终止，文件写入也不会因为后续保存没发生就自动撤销。这是一个原子性（Atomicity）问题——若要声称一组变化要么全部发生、要么全部不发生，就必须有实现该保证的机制；一段顺序代码本身并不提供它。

Maka 是本课程继续研究的运行支撑（Agent Harness）实现。mini 帮助我们看清正常闭环；后续章节再用 Maka 解释更完整的状态（State）、权限（Permissions）和恢复（Recovery）职责。这里先把问题讲清，不提前假设某个实现已经解决了所有窗口。

第22章会展示真实模型（Model）的正常修复案例；第06章使用预写响应并在指定时点终止进程。前者检验给定任务中的实际修复过程，后者检查一个固定记录窗口，不能相互扩展证明范围。

2. 第06章的文件、执行轨迹（Trajectory）与退出记录

该实验使用真实 DefaultAgent 与 LocalEnvironment：第一步读取 README 并完成保存；第二步写入以后硬终止，来不及返回观察结果（Observation）。

表 2 / Table 2 · 2. 第06章的文件、执行轨迹（Trajectory）与退出记录
证据（Evidence）实际看到什么可以据此判断什么
文件系统中的 READMEnpm run check 已改成 npm test读回时，目标文件确实已经改变
执行轨迹（Trajectory）中的 messages只有第一步读取旧 README 的消息（Message）最近一次保存停在哪里
控制进程记录的退出结果被测子进程遭到定点硬终止这次执行没有正常结束

第二步的行动请求（Action）、返回值与退出原因都没有进入磁盘上的这份快照（Snapshot）。其中一部分内容可能已经存在于进程内存，但内存中的对象与已保存文件处于不同时间点。预写响应配置里有下一条命令，也不能把配置当成已经执行的历史（History）。

因此，“智能代理（Agent）失败了”不足以描述这个现场。准确描述应拆成三句：执行被终止；README 已经改变；已保存记录尚未反映第二步。控制进程知道退出原因，也不代表被测对象自己的记录里保存了同一条事实（Fact）。

3. 下一步应该做什么

只看旧记录，会产生三种仓促决定：重新执行、宣布成功、宣布失败。它们的问题都在于把“记录缺了什么”直接变成“现实发生了什么”。例如重做追加文本的命令会多写一行；宣布成功可能漏掉只完成一半的修改；宣布失败又可能忽略已经发生的变化。

对本例的小文件，可以先读回 README 并检查差异（Diff），然后按目标状态（Target State）继续：

表 3 / Table 3 · 3. 下一步应该做什么
读回得到的结果接下来做什么仍不能据此推出什么
目标替换已完整发生保留这次变化，继续测试与验收不证明全部测试已经通过，也不一定能重建写入过程
只发生了部分目标修改明确剩余差异（Diff），再决定补做哪些操作不把部分完成记为整个任务完成
无法读取或证据不足保持结果未知（Outcome Unknown），寻找其他可核对材料不把未知改记为“没有执行”

读回解决的是“现在是什么”，其效果不等于重放整段历史（History）。同样，一条命令可否安全重试，还要看重复执行是否引入额外变化。幂等性（Idempotency）描述的正是重复相同操作在相关效果上保持一致的性质；它需要结合操作及条件判断，不能仅凭命令名称认定。第18章会进一步解释。

缺少观察结果（Observation），不能推导出没有效果（Effect）。 这句话保留了不确定性，同时告诉我们下一步应寻找什么证据（Evidence）。它没有承诺所有外部操作都能查询、撤销或去重。

4. 身份（Identity）、记录与负责者（Owner）

继续工作还需要回答三类问题。可以把它们理解为“关联谁、相信什么、由谁决定”，每类都补一个不同缺口。

  1. 关联谁：用户重发同一句要求，是继续原工作还是创建新尝试？需要身份（Identity）把长期归属、用户可观察的一项工作和具体执行区分开。
  2. 相信什么：准备执行的文本、返回的工具结果（Tool Result）、磁盘中的文件分别说明不同事情。用于判断的事实（Fact）要与从记录整理出的投影（Projection）区分；一个界面视图不自动拥有裁决权。
  3. 由谁决定：界面仍显示运行、模型（Model）宣称完成、后台进程正在退出，可以同时出现。负责者（Owner）表示有权管理某一状态（State）的组件，不能仅由谁显示信息来判断。

后面会用会话（Session）关联一组交互，用工作轮次（Turn）表示用户可观察的一项工作，用执行（Run）标识一次具体运行；这些是 Maka 的语境，不能仅按同名词把别的项目对象强行对应。第08章先给问题地图，第13、14章再展开各自的记录和实现。

问题解析

写入窗口

问题1。 文件已改而执行轨迹（Trajectory）停在读取，是矛盾吗？

参考答案。 不是。效果（Effect）、观察结果（Observation）与保存存在先后顺序，中断发生在它们之间。最近保存的快照（Snapshot）不必包含最新文件变化。

问题2。 为什么先检查 README，而不是只重复原命令？

参考答案。 先确认目标状态（Target State），才能区分已经完成、部分完成与结果未知（Outcome Unknown）。重做追加操作可能重复产生效果（Effect）；读回也不保证重建全部执行历史（History）。

问题3。 当前实验是否证明自动恢复（Recovery）和所有外部操作可去重？

参考答案。 没有。它只检查一个固定本地写入窗口。一般的查询、重试与去重还需要对应执行路径的实际机制。

5. 权限（Permissions）、输入与跨进程工作

执行权限（Permissions）与效果恢复（Effect Recovery）

第04章的 npm test 会启动 package.json 声明的脚本。即使采用第05章的交互确认（Confirmation）并得到用户同意，也没有因此证明操作系统（Operating System，OS）会限制它访问哪些文件、网络和子进程。许可与资源强制限制要分别说明；第17章再展开权限策略（Permission Policy）和隔离（Isolation）。

第06章的记录缺口则连接到第18章：执行前写下什么、什么时候结算结果、缺失时怎样核对。那一章将两次持久提交（Durable Commit）简称为 T1/T2。本章只需要记住，文件变化与记录提交不是天然同步的一件事。

长日志与长期信息

一次任务可能积累很多输出。历史（History）值得保存，却不必全部进入下一次模型输入（Model Input）；有限的上下文窗口（Context Window）还要求选择与组织。第19章讲上下文压缩（Context Compaction），第20章讲记忆（Memory）怎样跨任务保存和召回（Recall）。它们分别回答“这一次看什么”和“以后怎样再次使用”，不能用一个保存动作代替。

跨进程工作与所有权（Ownership）

再换一个正常场景：README 已修改，测试结束且结果已经保存，用户尚未提出下一问。文件与聊天记录仍需留下，但计算进程是否必须常驻？判断之前应先列出必须保留的状态（State）、可以重建的运行现场，以及谁有权开始下一次执行（Run）。释放计算资源与遗忘工作身份（Identity）是不同选择。

这会连接到第13章的身份与进程及第25章的执行载体。第06章没有测试自动释放，也没有测试跨进程恢复（Recovery）。委派（Delegation）、持续推进与断线观察会继续增加责任，第08章将它们放回共同地图。

授权（Authorization）与输入选择问答

问题1。 “用户允许执行 npm test”还没有回答什么边界问题？

参考答案。 没有说明底层能否强制限制脚本访问的文件、网络和子进程。交互确认（Confirmation）与隔离（Isolation）需要分别验证。

问题2。 为什么保存完整日志与下一次交给模型（Model）阅读，是两个决定？

参考答案。 保存服务于留存和核对；模型输入（Model Input）服务于当前判断，并受上下文窗口（Context Window）限制。被保存不等于被选入，更不等于已经用于判断。
