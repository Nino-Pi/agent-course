第 62 章｜三组完整设计案例

本章概览

核心问题：路径修复、巨型日志和定时协作，怎样分别形成从输入到故障恢复的完整方案？

关键概念：参数数组：保留路径的参数边界；条件编辑：保护读取后的用户修改；有效输入：当前实际提供的材料；记忆撤回：使旧规则不再参与新读取；采纳：检查并使用子任务产物；未知效果：缺回执时保留未确认状态。

关系主线：三组教学案例分别连接工具与验收、输入与偏好、触发与批准；恢复围绕原操作和当前许可判断，窗口重连、子任务完成和任务成功属于不同状态。

输入、接口与预期结果是教学设计，不是产品运行记录；Codex 与 Claude Code 的对照保留各自公开实现或产品资料的范围。

1. 案例 A：路径包含空格的代码修复

前情回顾。 第 49–52 章围绕一条执行链展开：模型提出动作，工具层保留参数与结果，权限裁决限定能执行的范围，资源 owner 才实际改变文件。读取与修改之间，文件可能已被别人更新，因此修改要核对读取时的条件；命令结束后，还要另行验收任务。本案用一个含空格的路径串起这几个环节。

设计问题与条件

一个 Python 文档检查器在路径包含空格时失败。用户允许修改检查器和 README，要求保留已有改动，确认相关行为后报告 diff。

初始任务没有给出测试入口，不能默认采用 npm。本例补充以下教学观察：项目配置声明使用 pytest；检查器的包装函数通过 shell 拼接字符串启动子程序；无空格路径正常，docs/guide draft.md 被拆成两个参数；用户在 README 开头保留一段自己的部署说明。以下参考方案以这些已给定观察为依据。

允许写入范围只有检查器包装函数和 README，测试文件不在修改范围内。成功需要路径参数保持完整、错误仍能返回、相关测试确实执行、diff 不覆盖用户说明。没有远端发布需求。

正常流程与完整参考方案

执行链是：接纳任务与范围 → 读取配置、包装函数和相关测试 → 用正确入口复现 → 将字符串命令改为参数数组 → 更新 README 中实际测试说明 → 复测 → 核对 diff → 报告。

包装函数的关键修改如下。代码展示参数边界的修复，cwd 与允许的脚本路径由可信运行配置固定；它不代替 sandbox、超时或权限系统。

import subprocess
import sys

def run_checker(path: str, cwd: str):
    return subprocess.run(
        # 每个列表元素都是一个参数；path 中的空格不再拆分参数。
        [sys.executable, "checker.py", path],
        cwd=cwd,
        shell=False,
        capture_output=True,
        text=True,
        check=False,  # 将非零退出码和诊断交回上层判定，而不是吞掉失败。
    )

path 作为列表中的一个元素传递，即使包含空格也不会被 shell 分词。check=False 保留非零退出状态供调用者解释，不把它伪装成成功；上层应读取 returncode、stdout 和 stderr。shell=False 减少 shell 解释，仍不证明 checker 本身没有文件或网络副作用。

实际编辑交给资源 owner 的条件提交：Read 返回内容与 v7；模型形成仅修改包装函数的补丁；owner 在同一受保护操作中核对当前版本仍为 v7、目标唯一，再提交 v8。普通文件系统若没有覆盖竞争写者的合同，就必须保留并发风险或使用隔离工作副本；不能把普通 rename 叫作版本 CAS。

故障分支与参考处理

Read 后用户再次保存文件。 若 owner 当前版本变为 v8，旧 v7 条件提交拒绝且本次不写入。重新读取用户变化后重建补丁；用户已经修好同一位置时直接进入验证，不重复修改。匹配仍唯一也不能消除版本已陈旧的事实。

命令 exit 0，却没有发现测试。 这里另设一层故障：外层脚本吞掉测试进程的非零退出状态，自己返回 0，并非 pytest 在未收集到用例时正常通过。外层退出结果不是任务验证；保留“0 tests collected”等实际输出，检查测试选择、入口与各层退出状态。可以使用项目定义的正确用例或受控最小复现；没有取得行为结果前，报告“修改已准备，验证尚不充分”。

用户在模型等待期间停止，模型随后返回两条 Edit。 运行器在模型返回后、每次新工具准入前检查停止意图，拒绝启动这两条尚未执行的修改。已开始的其他操作接收取消信号，并结算真实结果或 unknown；停止不抹去先前写入。

文件似乎已改，最终回执丢失。 保存原 operation 身份并查询 owner 或只读核对文件。若内容已符合目标，可以确认当前状态并继续获准的验证；没有可归因回执时，不能宣称一定是原操作成功，更不能因为没收到结果就再次覆盖文件。

方案验收结果

本方案将“错误测试入口”“断言失败”“陈旧版本”“停止请求”“效果未知”分成不同结果，分别导向找入口、诊断、重读、停止新调用和对账。完整验收不是只看最终 exit 0，而是同时核对行为、实际测试执行、diff 范围和未确认的效果。

2. 案例 B：巨型日志与长期偏好撤回

前情回顾。 第 53–55 章区分了当前输入与长期存储：模型只看到本次真正装入请求的材料，保存过的日志或 Memory 不会自动全部进入上下文。压缩旧历史与缩短一个巨大工具结果也是两个操作。再结合第 59 章的证据判断，本案要同时回答“下一次看见什么”与“哪些长期变化已经得到确认”。

设计问题与条件

历史接近窗口上限，最新工具返回 20 万字符。当前只允许改文档；Memory 已保存“全局中文、工作区 A 英文”，用户现在撤回 A 的例外。下一请求与长期更新怎样形成？

当前工作区为 A，没有正在执行的写入。已知 b1 调用了项目确认的测试入口，结果 exit=1；关键行是“125 秒期望 2:05，实际 2:25”，其余主要是重复进度。完整输出已保存为本 Session 有权读取的 log-b1。这是本例给定的存储与读取合同，不是某个产品的 API。

撤回尚未确认持久提交。用户的撤回请求授权更新这条长期偏好，但不扩大项目文件修改范围；当前源码和测试仍不能改。旧历史的具体内容没有全部给出，摘要只能使用实际选中且可核对的材料。

正常流程与完整参考方案

请求组装将四类对象分开：当前规则、旧历史、最新工具结果、长期 Memory。当前“只改文档”与撤回意图独立进入请求；旧前缀按完整协议单元选择，近期 b1 的调用与结果关联保留；20 万字符的正文另做有界表示，并带可靠引用。

如果还需要压缩旧前缀，候选摘要只概括实际收到的范围，记录原始覆盖与有效输入身份；来源/协议检查通过且 checkpoint 已持久保存后才安装。结构正确不保证语义正确，也不保证新请求一定更短或被 provider 接受。

下一请求的完整教学表示可以是：

当前任务：只修改文档，不修改源码或测试。
当前工作区：A。用户现在撤回 A 的英文例外；本次解释采用全局中文。
长期状态：已保存 global=zh 与 A=en；本次撤回尚未确认持久提交。
Memory 后续工作：撤回 A 例外，取得提交确认后才报告长期更新完成。
工具调用：b1，运行项目已确认的测试入口。
工具结果：exit=1；125 秒期望 2:05，实际 2:25。
结果范围：其余主要是重复进度；完整日志通过本 Session 的 log-b1 回读。
可得结论：测试未通过，不能宣称函数已经修好。
后续动作：在文档范围内处理说明并报告源码问题；需要细节时受控回读。

这里没有编造旧阶段完成了哪些修复。当前用户指令足以决定本轮中文，不需要等长期写入完成；但“未来会按新规则读取”必须由持久更新及后续读取另行证明。

Memory 使用如下状态轨迹。M1/M2 是教学条目标识，具体版本提交由选定 Store 合同实现。

故障分支与参考处理

最新结果无法放进 tail。 压旧 prefix 不能保证解决单个巨大结果。保留 b1 身份、退出状态、关键差异、截断说明和 log-b1，按需求回读；若必须保留的结构自身仍超限，则缩小任务或明确停止，不能无限摘要。

摘要写“修复成功”。 源范围和格式校验可能通过，语义仍与 exit=1 矛盾。候选不应作为完成证据；本例用关键事实约束检查“测试失败、未改源码、只改文档”，后续报告仍以实际结果为准。digest 不能证明文字理解正确。

摘要保存失败。 新 checkpoint 不应用，旧有效表示保留。若旧请求已超窗，接下来选择针对大结果的缩减或停止；“保留旧表示”不等于可继续发送同一无效请求。

log-b1 已失效。 返回明确的引用失效；已有 exit 与关键错误仍可报告，全文缺失单列。只在任务允许且检查可安全重跑时重新观察，不能因正文不可读而重做先前编辑。

Memory 服务失败。 返回 unavailable，而不是空列表或 no_match；当前用户撤回仍是本轮有效输入，长期更新保持未确认。服务恢复后按原操作身份查询或受控重提，避免重复写入或虚报保存。

方案验收结果

本轮请求保留“只改文档”、b1 的失败与可靠来源，不把工具结果截短当作任务成功。Memory 的长期完成要求撤回提交成功；后续新读取排除 M2，才能得到跟随 global 的行为。

比较另一方案时同时记录输入/输出成本、压缩与回读延迟、约束保留、错误细节可找回率、M1/M2 更新状态和最终回答。只减少 token 却越权改源码，或者写成功却没有被读取，都不能判为全面改善。

3. 案例 C：定时协作、批准与跨客户端观察

前情回顾。 第 56–61 章把长任务拆成触发、执行、交付与观察：到点触发只决定何时接纳工作，不自动增加写入权限；子任务完成只表示已有局部产物，还要由父任务检查并采纳；客户端重连取得的是状态快照，不应重新执行原动作。本案把这三条区别放进一次定时检查，先给只读流程，再解释批准后的修改变体。

设计问题与条件

系统每天核对文档与测试入口，可派子任务检查不同模块；任何修改都要用户批准。用户从桌面端发起，也可能换一个客户端查看。

本例假设一个持续驻留的 Host 管理持久控制状态，两个模块的配置可以只读检查。每日 fire 有唯一身份，父任务负责汇总；初始没有写入授权。子任务默认只读、使用明确材料和文件范围，不能从“每天检查”推出每天自动修改。Host 退出或机器关机不在“进程继续运行”的承诺内。

正常流程与完整参考方案

控制链为：保存 Schedule → 到点认领 fire f7 → 原子查找或创建 admission → 绑定父 Run r7 → 分派只读 child c1/c2 → 保存带来源结果 → 父任务汇总差异 → 形成具体修改请求 → 用户批准后重新核对范围与基线 → 应用修改并验收。

三个 owner 分开：Schedule owner 决定某次触发；权限裁决者（Permissions Authority）决定当前允许的动作；Run/资源 owner 管理执行和结果。共用持久存储不意味着这三者可以用一个 pending → run 规则替代。

教学接纳骨架如下；claim_fire_atomically 的实现必须与取消/修订经过同一事务或串行 owner，单独的先查后写不满足合同。

def resume_fire(fire_id, payload, revision):
    # 在同一受保护操作中检查触发身份、请求内容与当前修订。
    decision = claim_fire_atomically(fire_id, payload, revision)
    if decision.kind == "existing":
        # 重复送达复用原 Run；恢复观察或尚未完成的派发。
        return query_or_resume_dispatch(decision.run_id)
    if decision.kind == "rejected":
        return decision.reason
    # 新接纳也只派发刚绑定的 Run，不再另建执行身份。
    return query_or_resume_dispatch(decision.run_id)

query_or_resume_dispatch 按原 Run 身份处理已认领但未开始的派发；运行中或已 terminal 的 Run 只查询与收敛。它还必须在执行 owner 处与停止请求仲裁，不能每次恢复都创建新进程。

故障分支与参考处理

接纳成功但调度器没收到响应。 恢复后按 f7 查到 r7，修复 pending 展示并查询其状态。重复请求还要核对相同 payload；不能新建另一个 r8 执行同一 fire。

两个 child 的局部测试都通过，合并后失败。 这是加入批准后的并行修改变体：两个 child 分别从明确基线产出 patch。独立 worktree 只隔离执行期间文件，父任务仍要处理文本和语义冲突。父区集成测试失败时保留两份产物及失败观察，由父任务诊断；不能用“两票通过”宣布总体成功。

父任务停止时 child 恰好完成。 停止后不再派新工作，向运行中的 child 发送停止并收集可得结果。已完成结果保留；父任务可以标为未采纳，不能删除事实来伪装未执行。结果引用不可读时先恢复交付，不重跑 child 修改。

快照与订阅之间漏掉完成事件。 参考协议在同一观察流中取得快照与游标，并回放游标后的事件，或在快照期间缓冲增量。消费者核对订阅身份、序列与 revision；发现缺口后补齐或重取快照。新的订阅可以有新序列起点，不能拼接旧订阅迟到帧。查询状态不会重放原修改命令。

Client 断线，或 Host 也退出。 只有 Client 断线且普通执行器随 Host 存活时，r7 可以继续。Client 提供的能力丢失要另行处理；Host 退出后，新进程读取已提交事实，并按实际恢复合同收束或接管，不能承诺恢复任意执行栈和远端资源。
