第 12 章｜一次请求的完整生命周期

本章概览

核心问题：客户端发送请求之后，系统怎样区分已经接纳、正在执行和已经结束？

关键概念：Admission（准入）固定工作身份与输入；Host（宿主）接单并协调；Runtime（运行时）驱动模型和工具；model step（模型步骤）形成一次决策；terminal（终态）记录执行结束。

关系主线：请求先经准入；普通工具分支再循环组装输入、执行与保存结果，客户端读取状态视图。最终文本、持久终态和任务验收并不等价，断线也不自动授权重新执行。

核心路线

从任务要求确定执行对象

任务包含文件操作、测试和长期偏好：

检查 package.json 与 README.md，更新 README 的测试步骤，运行测试，最后用中文总结；以后也请记住我希望使用中文解释。

这是 第11章 主任务中只改 README 的简化阶段：暂时假设功能测试原本已通过，尚未展开 formatDuration 的缺陷。我们把长期会话记为 S1、这次用户工作记为 T7、实际执行记为 R7。

本章 R7 的顺序是教学示意。后面的第22章 Maka 主案例将展示包含函数修复的真实调用；真实模型可以先依据源码修改再测试，不需要逐步照着本章示意走。

准入、执行与展示的完整链路

**model step（模型步骤）**指一次模型决策：系统把本次输入交给模型，得到文字或工具请求；一个步骤可以请求多个工具。

图中 Host 保存准入成功后发起执行，Runtime 才进入“输入 → 模型 → 工具 → 结算记录 → 下一次输入”的循环。Runtime 在组装输入时回读执行事实；虚线提供回读材料，不表示记录库主动启动下一步。Read、Edit、测试可以多次经过这个循环。底部由 Host 根据执行记录整理展示：准入记录说明工作被接纳，执行记录说明后续发生了什么。

边界与失败。 最终文本进入 Runtime 处理，不等于文字本身就是 Run 终态；错误、取消或额度耗尽也可能让执行结束，且不保证还能生成总结。图中的记录与回读只表示本章普通路径：工具效果可能先于结果记录发生，保存失败时不能据缺少回执重做；Client 断线也不能据旧画面重启任务。终态与任务是否做对、资源是否已清理，仍须分别核对。

这里的运行时（Runtime）是实际驱动模型—工具循环的程序部分；Runtime Host 则是更外层的长期控制者，负责接受连接、准入工作并协调生命周期。

第 0 站：工作开始前，S1 已经存在

会话（Session） S1 是长期存在的工作房间。它可能已经包含以前的用户消息、模型回答和工具事实，也可能是一个刚建立的空会话。

开始 T7 前，可以把状态想成：

Session S1
  历史：若干已有事实
  当前顶层工作：无
  Client：已经连接并正在显示 S1

“当前顶层工作为空”很重要：Host 要防止同一个 Session 的两项顶层任务未经协调地同时争抢控制权。这里的“顶层”指 Host 接纳的整项工作，内部仍可有并行工具；精确的准入范围放在 第13章 深化区。

用户此时看见什么

用户看见一个聊天或任务界面，以及输入框。

系统此时知道什么

Host 能识别 S1，知道它是否存在、是否归档、是否已有待执行或正在执行的顶层工作。

模型此时知道什么

本例尚未把 T7 交给模型。模型不是一直挂在 S1 上持续思考；只有 Runtime 真正发起请求时，它才收到为那次调用构造的输入。

第 1 站：Client 提交 T7，但它没有权力宣布“已经开跑”

用户点击发送后，客户端（Client）把大致如下的意图交给 Host：

sessionId = S1
turnId    = T7
content   = "检查 package.json 与 README.md……以后用中文解释"

轮次（Turn） T7 表示用户能识别的一项顶层工作。Client 可以提出 turnId 和内容，但不应自行编造权威 runId，也不能因为界面已经出现一个 loading 动画，就断言执行已经开始。

为什么要这样分权？设想网络在发送后立刻断开：

  • Client 不知道 Host 是否收到；
  • Host 可能已收到并持久化；
  • UI 的本地状态无法证明服务端事实。

因此按钮状态只是用户体验层面的临时视图。

第 2 站：Host 检查并准入，固定 S1 / T7 / R7

准入（Admission）是 Host 正式接受这项工作并固定关键输入与身份的过程。对本案例，Host 要确认至少这些问题：

  • S1 确实存在，并且没有归档；
  • 当前没有冲突的顶层执行；
  • 输入是否合法，所需执行能力是否可用；
  • T7 如果以前出现过，这次是否是内容完全相同的重试。

检查通过后，Host 为这项工作建立运行（Run） R7，并先保存一条持久化的准入事实：

这不是实际 schema，只是教学表示：

admission {
  session: S1,
  turn: T7,
  run: R7,
  input: 规范化后的用户要求
}

这里采用“先保存，再启动”的顺序。原因是：如果先启动模型、后保存身份，进程刚好在两者之间崩溃，重启后就很难判断那次工作是否已经开始。

第 3 站：Host 组成这一轮稳定的工作基础

正式调用模型前，系统要决定 R7 以什么规则、能力和模型配置工作。可以把它类比成开工前发放一个“工作包”：

R7 工作包
  ├─ 必须遵守的规则
  ├─ 项目背景
  ├─ 本轮任务
  ├─ 允许看到的历史
  ├─ 工具说明
  └─ 模型配置

第 4 站：Runtime 为模型 step 1 构造它真正能看到的内容

Runtime 不会把整个数据库或整个工作目录直接塞给模型。它会构造工作上下文（Working Context），例如：

系统规则与项目指令
+ 可注入的长期信息
+ S1 中选中并整理过的历史
+ T7 的当前用户输入
+ 本 step 可用工具的名称与参数说明

此时模型通常还看不到 package.json 与 README.md 的真实内容。它只知道存在一个 Read 工具，以及用户要求检查这两份文件。文件内容要等工具实际读取后，才会进入下一次模型调用。

这是理解 Agent 的关键分界：

模型知道“可以请求 Read”
    不等于
模型已经知道文件内容

第 5 站：模型 step 1 请求两个互不依赖的 Read

第一次模型调用可以在同一个 step 输出两个互不依赖的结构化意图：

tool_call A { name: "Read", arguments: { path: "package.json" } }
tool_call B { name: "Read", arguments: { path: "README.md" } }

这段示例是教学用简化表示，不是 Maka 的实际序列化格式。

执行器先检查参数和当前读取边界，不能把模型愿望当成执行许可。

检查通过后，两个只读调用可以并行执行，并分别返回内容或错误。这里的关键区别是：一个 model step 可以产生多个 tool call；step 是一次模型决策，不是某一个工具调用的别名。

Read 成功时

Read result A:
  package.json 内容
Read result B:
  README.md 当前内容
两者都可能是受控、可能截断的读取结果

工具结果会形成可追踪的执行事实，再成为下一步上下文的一部分。

Read 失败时

可能原因包括：路径不存在、越过当前边界、编码或读取错误。模型下一步看到的应该是明确失败，而不是系统悄悄假装文件为空。

第 6 站：模型 step 2 基于两份真实文件内容请求 Edit

Runtime 再次构造模型输入。这一次与 step 1 不同：

原有规则和任务
+ 两个 Read 调用意图
+ package.json 与 README.md 的真实结果
+ 当前仍可用的工具说明

模型现在才能把 package.json 的实际脚本、包名或项目结构与 README 当前文本对照，生成可定位旧文本的精确修改，并请求 Edit：

Edit(README.md, 精确修改内容)

Edit 是会产生副作用的工具：它可能改变用户磁盘上的文件。因此“模型请求 Edit”和“Edit 已完成”之间必须有明确执行边界。

执行器返回修改结果后，Runtime 保存它，下一次模型调用才有依据选择测试。若写入已发生、结果却没保存，恢复判断就会遇到不确定窗口。

第 7 站：模型 step 3 请求 Bash 运行测试

Edit 结果进入下一次上下文后，模型请求 Bash 执行在 package.json 中确认过的测试命令。

Bash 的结果不只有屏幕上的几行文字，还包括至少两个维度：

stdout / stderr  人类可读输出
exit status      程序是否成功退出的机器信号

例如：

Tests: 4 passed
exit status: 0

和：

Tests: 1 failed
exit status: 1

会让模型得出不同的总结与下一步。输出说明命令做了什么，退出码按该命令的约定报告成功或失败；还必须确认这确实启动了目标测试，而非只打印了一句“passed”。本段的 4 passed 假定函数原本正确；若仍使用第04章的原始 % 100 版本，只改 README 后仍是 2 通过、2 失败，真实记录见第22章第3例。完整函数修复中的失败分支在第16章展开。

第 8 站：模型 step 4 生成中文总结

如果模型已经看到：

  • Read 的文件内容；
  • Edit 的完成结果；
  • Bash 的输出与退出状态；
  • 用户要求用中文说明；

它就可以生成有证据依据的最终文本，例如：

已根据 package.json 中的实际命令更新 README，并运行测试。
测试共 4 项，全部通过。

这段文本本身仍不是整个生命周期的终点。Runtime 还要把模型输出和终态（Terminal State）写入负责执行语义的持久记录。

终态可能是：

  • completed：正常完成；
  • failed：因错误结束；
  • cancelled：被取消。

这里的“正常完成”描述本次执行如何结束，任务是否做对仍要看文件、测试与用户要求。Agent 可以正常结束并诚实报告“测试仍失败”；也可能因步骤额度用尽而结束，没有机会再调用模型生成总结。读到结束状态，不能替代核对完成证据。

第 9 站：Host 和 Client 从事实得到完成视图

Runtime 写入终态后，Host 从权威记录整理出当前状态快照，并向订阅 S1 的 Client 发布更新。Client 再把它画成聊天气泡、完成状态或运行详情。第14章 会把这种“从记录整理显示内容”的过程称为投影。

这里的方向是：

持久执行事实 → Host 状态快照 → Client 展示

而不是：

Client 显示完成 → 系统因此认定执行完成

这使得 Client 断线重连后，仍可以从持久事实恢复同一项工作的状态。

核心问题解析

问题 1。 从发送 T7 到第一次模型调用，Host/Runtime 分别补上了什么？

解释。 Host 检查并持久接纳工作、固定 R7；Runtime 组成输入并驱动模型与工具。界面出现 loading 不是已准入的事实。

问题 2。 为什么第一次 Read 前不能可靠生成 README 的精确替换？

解释。 模型还没有当前文件内容与匹配位置。Read 将真实内容变成下一轮可用的观察，才能形成有根据的编辑请求。

问题 3。 Bash 的输出与退出码各能证明什么？最终通知丢失后应该重做任务吗？

解释。 输出帮助解释运行过程，退出码表示命令自己的成功/失败约定，还要核对它覆盖了什么要求。通知丢失应读已有事实并恢复展示，不能据此重做任务。

实现深化

准入重试：同一个身份也要核对内容

网络超时后，Client 可能重发 T7。安全的处理方式不是简单再开一个 Run，而是检查：

相同 T7 + 相同规范化输入 → 可以识别为同一意图的重试
相同 T7 + 不同输入       → 拒绝，避免身份指向两项不同工作

这就是“固定身份与输入”的意义。

组成快照与物理调用诊断

组成快照之前，系统还要固定或核对这些来源：

  • 基础系统规则；
  • 当前 workspace instructions（工作区指令）；
  • 允许注入的用户长期信息；
  • 当前 Skill，或 Plan（计划）/Goal（持续目标） 等控制域附带的上下文；
  • 选择的模型与 provider（模型服务）选项；
  • 这项 Run 最多可以使用哪些工具；
  • 工具在当前 step 是否可用。

Maka 会保存一份组成快照及指纹，标识这一轮采用的配置和来源。当前公共 provider 主路径还记录物理调用 attempt（一次实际请求尝试）及有界的 promptComposition（各类请求材料的大小与组成诊断）。这能帮助核对配置变化前后的执行依据和调用状态，但指纹与大小分布都不是完整请求正文，不能靠它们还原模型看过的每一个字。

普通工具调用前的检查

Runtime 收到工具请求后，不会只凭模型的意愿直接执行。普通工具路径还要经过多层检查，例如：

  • 参数是否符合 schema（声明的参数结构与类型）；
  • 这项工具是否在 R7 的有效能力范围内；
  • 当前 step 是否允许它出现；
  • 调用次数和循环限制是否允许；
  • 实时执行边界是否允许读取目标路径。

Edit 的持久边界与扩权分支

在 production Runtime Host 已接入持久结果接收端（durable sink）的普通 MakaTool 路径中，执行顺序是：

检查调用
  → 记录“实现可能从这里开始”的边界
  → 在当前 sandbox / executor 中执行
  → 记录结果
  → 再把结果交给模型

前后两个持久边界分别称为 T1 和 T2：T1 表明实现可能开始执行，T2 保存这次调用的结算结果。恢复程序用它们区分尚未进入实现、已有结果和结果仍未知的情形。

如果 Edit 越过边界

假设当前只允许修改 workspace，模型却请求写入外部目录。工具不能因为模型“很确定”就自行扩大权限。当前边界不覆盖这次操作时，先拒绝越界执行；只有相应入口允许申请、且工具返回了明确的扩边需求，才由模型在后续步骤提出申请。批准后还需按新边界重新判断下一次调用，不会自动重做原 Edit；命中显式拒绝也不能靠普通扩边绕过。

Shell 字符串为何需要执行边界

一段 shell 字符串可以间接读写大量资源、启动子进程或访问网络。静态看命令名字往往不足以推断真实效果，因此 Runtime 仍要在实际执行位置应用安全边界，而不是只在提示词中写“请勿越权”。

终态与资源结算的两个时刻

最终回答出现与所有后台资源彻底清理完，也可能是两个时刻。Maka 区分权威执行终态（canonical terminal）与随后的资源收尾（settled/cleanup），避免把“用户已经有结果”与“所有事件迭代器和资源已释放”混为一谈。用户按 Stop 时也要区分“已请求取消”“终态已保存”“资源已收敛”；取消不能撤销已经完成的文件修改。工具结算案例见 第18章。

第 10 站：“以后记住中文偏好”走另一条路径

用户的句子同时包含本轮要求和长期意图：

本轮要求：最终总结用中文
长期意图：以后也希望中文解释

前者可以直接作为本轮指令进入 T7 的上下文，是否遵循要看实际回答。后者还需要明确的 Memory 写入，以及后续的读取和使用路径。

本节先区分“保存”与“未来读到”，完整 Memory 机制在第20章展开。当前 Maka 有两套接近但不同的机制：

  1. Local Memory（本地记忆笔记）：以 MEMORY.md 为主体、用户可见且可编辑的一组笔记；
  2. Atomic LTM（条目化长期记忆）：由 memory_remember 等路径写入 memory.sqlite 的结构化记录。

Atomic LTM 已有结构化写入和存储查询，但生产 Agent 尚未接通从中选取相关记忆、装入模型输入的调用链；它也不会自动同步到 MEMORY.md。因此：

memory_remember 报告保存成功
    不等于
下一轮模型一定会自动看到这条偏好

如果产品希望下一轮稳定注入这项偏好，还需要使用已启用读取的透明 Local Memory 路径，或者未来接通 Atomic LTM 的召回侧。

把整条链拆成四种不同信息流

同一个请求里，其实有四条同时发生的流：

表 1 / Table 1 · 把整条链拆成四种不同信息流
信息流（Information Flow）从哪里到哪里例子
控制流（Control Flow）Client → Host → RuntimeT7 被准入为 R7；开始、停止、完成
模型流（Model Flow）Context → Model → 下一步意图请求 Read、Edit、Bash，最后生成文本
副作用流（Effect Flow）Tool Runtime → 外部世界读取文件、写 README、启动测试进程
事实流（Fact Flow）Runtime/Host → durable stores → projection保存调用、结果、终态，再重建 UI

控制流决定工作能否推进，副作用流改变外部状态，事实流保存已知结果；模型只能基于已进入上下文的结果选择下一步。

三个关键时间点

这项任务至少有三个不能混淆的时间点：

① submitted  Client 已提交 T7
② admitted   Host 已持久接受并固定 R7
③ terminal   Runtime 已写入 R7 的最终执行事实

它们之间都可能发生断线或崩溃。

情况 A：submitted 后、admitted 前断线

Client 不能仅凭本地界面判断是否已被接受。重试时要用相同 T7 和相同内容，让 Host 判断是否为身份与内容都相同的精确重试（exact retry）。

情况 B：admitted 后、模型调用前崩溃

持久准入仍在，因此重启后系统知道 R7 已被接受；恢复逻辑不应无身份地创造另一个重复工作。

情况 C：Edit 开始后、结果记录完成前崩溃

文件可能已经修改，也可能没有。这是危险的不确定窗口。系统应依据工具执行边界核对原操作与实际效果（reconcile），或暂时停放工作，不能盲目重复一个非幂等修改。

情况 D：terminal 已写入、Client 尚未收到

重连后 Client 可以从 canonical facts 重新得到完成视图；不需要要求模型再生成一次答案。

一个正常分支和两个异常分支

正常分支

两个 Read 都成功
→ Edit 成功
→ Bash exit 0
→ 中文总结
→ R7 completed

异常分支一：测试失败，但系统仍正常工作

两个 Read 都成功
→ Edit 成功
→ Bash exit 1
→ 模型根据错误决定修复或报告

“测试失败”是任务世界中的失败，但工具链本身可能运行得完全正确。模型不能把 exit 1 改写成“测试通过”。

异常分支二：模型 provider 中途断开

如果 provider 请求还没有产生可观察输出，Runtime 还要检查错误是否可重试、剩余步骤与 attempt 额度，才可能重发。已有回答文本或工具活动时，不能把它当成“什么都没发生”。仅有 thinking（思考输出）片段的少数情况有专用恢复路径，需先封存片段并发布 retry 事件，不是静默抹掉旧输出。

这与 Bash exit 1 的下一步不同：测试错误已经是一条可交回模型的观察；provider 错误若不满足恢复条件，当前模型调用无法继续，应保留 partial（未完成的流式片段）与失败事实，结束 Run。源码里的 CompleteEvent 只是一次流的结束通知，complete(error)、complete(step_limit) 都会映射为失败，不能按名字读成成功。第13章 的计数例解释为何三步额度不保证还有第四步总结。

机制问题解析

问题 1。 同一 T7 换了输入，为什么不应作为重试接受？

解释。 身份需要对应同一项规范化意图，内容变化会破坏重试语义。

问题 2。 Edit 已写入但结果尚未保存时，为什么不能只看 transcript 判断能否重做？

解释。 记录可能落后于 effect；需结合该执行路径的持久边界与核对现实的能力判断，不能从缺少结果推导没有执行。

问题 3。 长期偏好已写入 Atomic LTM，下一次是否必然进入模型输入？

解释。 不必然。当前的写入与存储查询，不等于生产 Agent 已接通记忆选择和输入装载。

下一步行动怎样取得进展

工具结算后，后续模型步骤取得可用反馈；Runtime 按预算、停止条件与执行边界判断是否允许继续，模型再依据观察选择下一行动。允许继续回答控制条件，值得做什么回答决策问题，两者不能合成一个“还没完成就一直运行”的规则。

普通 Maka 失败闸门会阻止同一调用签名连续失败后的再次执行，限制无效消耗；但它不判断修改后的请求是否增加了信息。改一个无关参数可能绕开重复签名，却没有取得进展。第16章的循环深化将继续比较补充观察、直接修改与重复测试，并给出完整预算演算。

工具反馈怎样进入下一次请求，见第15章的返回与再次输入。这里保留生命周期的主线：取得结果、检查是否可继续、再做新的模型决策；任何一步失败都不能被“模型还想继续”替代。
