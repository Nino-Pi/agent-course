第二部分：Maka 核心机制与任务接续 · 12 / 62

第 12 章｜一次请求的生命周期（Request Lifecycle）

本章概览

核心问题：客户端（Client）发送请求以后，怎样分别确认工作已被接纳、工具（Tool）已执行、结果已保存以及界面已更新？

关键概念：准入（Admission）固定工作身份（Work Identity）与输入；运行时（Runtime）推进模型步骤（Model Step）；工具结算（Tool Settlement）保存调用结果；终态（Terminal State）记录执行（Run）怎样结束；投影（Projection）把事实（Fact）整理成视图。

关系主线：沿同一项 README 修复追踪输入、消费者（Consumer）和状态（State）变化，再检查重试、写入中断、取消与长期偏好。最终文本、持久终态（Terminal State）和任务验收各有证据，断线不能自动授权重做。

前情回顾：把责任地图变成一条请求

第11章已经分清：宿主（Host）接纳并协调工作，运行时（Runtime）组织模型（Model）与工具（Tool）循环，客户端（Client）提交意图并显示结果。负责某项状态（State）的部件是负责者（Owner），实际读取并使用材料的部件是消费者（Consumer）；这两种角色必须沿真实连接寻找。

本章沿用会话（Session）S1、工作轮次（Turn）T7和执行（Run）R7。会话（Session）回答长期归属，工作轮次（Turn）回答用户发起哪项工作，执行（Run）回答本次具体运行是哪一次。一个执行（Run）可以包含多个模型步骤（Model Step）：每个步骤把输入交给模型（Model），取得文字或工具调用（Tool Call），一个步骤也可以提出多个工具（Tool）请求。

现在把这些对象放进时间顺序。我们不仅问“哪个部件做了事”，还问“它当时拿到什么、改变了什么、下一位消费者（Consumer）是否已经得到结果”。第10章的等待与事件交接读法仍然适用：调用存在、返回成功和结果已经持久保存，不应仅凭名字推导。

核心路线

从任务要求确定执行对象

教学请求继续是：

检查 package.json 与 README.md，更新 README 的测试步骤，运行测试，检查改动范围，最后用中文总结；以后也请记住我希望使用中文解释。

条件与第11章相同：函数已经正确，四个既有测试（Test）原本通过；README却写着 npm run check，配置只提供 "test": "node --test"，所以真正入口是 npm test。本章只允许修改README，保留函数、测试（Test）与配置。这与第04章仍含 % 100 函数缺陷的原始样例不同。

S1、T7、R7以及后面的四个模型步骤（Model Step）都是教学记号，不是新运行记录。第22章的真实 Maka 案例包含函数修复，其模型（Model）可采用不同的读取、编辑与检查顺序。本章不把示意步骤补进那份真实执行轨迹（Trajectory）。

准入（Admission）、执行（Run）与展示的完整链路

本章使用当前普通宿主（Host）和默认 ai-sdk 执行后端（Agent Backend）路径，并限定工具（Tool）走已接入持久结果接收端的普通调用链。运行时（Runtime）是驱动模型（Model）与工具（Tool）的程序部分；外层运行时宿主（Runtime Host）在本文简称宿主（Host），负责连接、准入（Admission）和生命周期（Lifecycle）协调。

图中的循环由运行时（Runtime）推进，记录库的虚线只提供回读材料，不会主动启动下一步。准入记录说明工作被接纳，持久执行记录说明后续发生了什么。普通工具（Tool）结算成功且控制条件允许时，结果才成为后续判断的依据。

底部只画基于持久事实（Durable Fact）的状态（State）展示；运行中的文字增量还可经宿主（Host）直接用于界面更新，并非每个可见片段都已经结算。工具效果（Effect）也可能早于结果记录发生。因此，缺少回执不能证明没有执行，旧界面也不能授权重新开始任务。

第0站：工作开始前，会话（Session）S1已经存在

S1可以已有用户消息（Message）、模型（Model）回答与工具（Tool）事实（Fact），也可以刚刚创建。本例开始时，S1未归档，没有冲突的顶层工作；客户端（Client）已连接并显示它。“顶层工作”是宿主（Host）接纳的整项工作，内部仍可以有并行工具（Tool）。具体准入（Admission）范围在第13章继续展开。

第2站：宿主（Host）检查并准入（Admission）

宿主（Host）检查S1存在且未归档、没有冲突的顶层执行（Run），再核对输入与执行能力。若T7已经出现，还须判断是不是同一项规范化意图的精确重试（Exact Retry）。精确重试（Exact Retry）要求身份（Identity）和已固定的内容、执行描述等保持一致，不能只比较一段相同文字。

接纳以后，宿主（Host）把T7关联到R7，并先保存准入（Admission）事实（Fact）。可以用下面的四项理解这份记录的用途，不把它当实际存储结构：

表 3 / Table 3 · 第2站：宿主（Host）检查并准入（Admission）
记录关系回答的问题

先保存，再启动避免一种缺口：若先发起模型调用（Model Query），随后才保存工作身份（Work Identity），中途崩溃就可能留下实际请求，却没有可核对的归属。保存返回异常也不能一律解释为没有接纳；恢复（Recovery）仍要按负责者（Owner）的合同核对记录。

第3站：宿主（Host）组成稳定的工作基础

正式调用前，宿主（Host）决定R7使用哪些规则、项目资料、模型（Model）配置与工具（Tool）能力。组成基础不是把整座仓库复制给模型（Model），而是确定本次工作可以从哪些来源取材料、采用哪些配置。

这里的可用性（Availability）表示某项能力在当前步骤能否被提供或调用；它与“包里定义了这个工具（Tool）”不同。宿主（Host）固定工作基础以后，运行时（Runtime）仍会为不同模型步骤（Model Step）选择不同材料。

第4站：运行时（Runtime）构造第一个模型步骤（Model Step）的输入

工作上下文（Working Context）是为本次判断选取并整理的内容：适用规则、允许注入的长期信息、S1中选中的历史、T7的输入，以及本步骤可用工具（Tool）的名称与参数说明。直接消费者（Consumer）是本次接收输入的模型（Model）。数据库、文件系统或记忆（Memory）中未被选入的材料，不能自动算作模型（Model）已知内容。

本例给定第一步没有预先载入两份文件正文。模型（Model）只知道存在 Read 工具标识，以及要检查 package.json 与 README.md，还不知道它们此刻的真实内容。知道可以请求读取，不等于已经完成读取。

这也是为什么不能直接生成可靠的精确替换：旧文本、匹配位置与可能存在的用户段落都尚未取得。工具（Tool）实际读取之后，结果才可能进入下一次模型输入（Model Input）。

第5站：第一个模型步骤（Model Step）请求两次读取

Read 是实际工具标识。模型（Model）在同一步提出读取配置和README的两个工具调用（Tool Call），它们的参数分别指向两条文件路径。两个读取互不依赖，允许时可以并行；这不意味着任意两个工具调用（Tool Call）都可以并行。

调用关系执行输入成功时的结果后续消费者（Consumer）
读取Apackage.json 的路径当前测试（Test）脚本配置下一模型步骤（Model Step）中的模型（Model）确认实际入口
读取BREADME.md 的路径当前说明文字下一模型步骤（Model Step）中的模型（Model）定位错误命令与保留内容

工具执行链（Tool Execution）先检查参数和当前读取边界，再交给真正执行者。一个模型步骤（Model Step）产生了两个工具调用（Tool Call）；两者不是同一个计数单位。

读取成功时

返回的是受读取规则约束的内容，可能因范围或大小限制而截断。当前片段足以看见目标配置，不代表已经通读整个文件；下一步必须按实际返回范围判断。工具结果（Tool Result）形成可追踪的执行事实（Execution Fact），再进入后续工作上下文（Working Context）。

读取失败时

路径不存在、越过当前边界、编码错误等原因，应返回明确失败。失败消息（Message）不能被悄悄替换成空文件，否则下一步可能把“读不到”误解为“文件为空”，据此覆盖有效内容。

第6站：第二个模型步骤（Model Step）请求编辑

运行时（Runtime）重新组装输入，加入两个读取意图与实际结果。模型（Model）这时才有材料比较：README写 npm run check，配置只声明 test；它据此请求 Edit，以当前旧文本定位局部替换，并保留其余内容。

编辑请求与文件效果（Effect）之间有执行边界（Execution Boundary）：参数必须有效，操作必须在当前授权（Authorization）内，实际执行环境（Environment）还要落实资源限制。模型（Model）希望修改，不等于文件已经改变。

普通结果完成持久结算（Durable Settlement）以后，下一模型步骤（Model Step）才能将其作为已接纳的结果。若写入发生但结果保存失败，应转入相应失败或恢复（Recovery）处理，不能凭缺少记录重做。下文的工具（Tool）持久边界会解释这个窗口。

第7站：第三个模型步骤（Model Step）运行测试（Test）

编辑结果进入下一次上下文（Context）后，模型（Model）请求 Bash 运行从配置确认的 npm test。Bash 是工具标识，执行时使用命令解释器（Shell）；它返回文本与退出状态（Exit Status），两者要结合命令结构读取。

标准输出（Standard Output）与标准错误（Standard Error）提供可读过程，退出码（Exit Code）按命令自己的约定报告结束情况。下面两块都是教学结果示意，不是原始日志：

Tests: 4 passed
exit status: 0
Tests: 1 failed
exit status: 1

它们应导向不同结论。第一块还需要确认确实运行了目标测试（Test），不能只打印一句“passed”；第二块不能因为工具调用（Tool Call）本身正常返回，就被写成“检查通过”。本例还需要查看文件差异（Diff），证明修改没有扩出README目标位置。

4 passed依赖本章函数原本正确的初态。若沿用第04章的 % 100 缺陷，只改README仍会得到2项通过、2项失败，第22章的只修README案例保留了该区别。不能把两个初态合并为一次运行。

第8站：第四个模型步骤（Model Step）生成中文总结

现在模型（Model）已取得读取内容、编辑结果、测试（Test）输出及差异（Diff）检查，才有材料说明当前结果。给定所有检查都符合本章条件时，可以形成下面的教学回答：

已根据 package.json 中的实际命令更新 README，并运行测试。
测试共 4 项，全部通过。

实际交付还应说明修改范围与检查限制。这段文字本身仍不是执行（Run）的终点；运行时（Runtime）要接纳模型（Model）输出，并保存终态（Terminal State）事实（Fact）。

终态（Terminal State）表示相应执行（Run）怎样结束，具体状态值还取决于读的是哪个接口。先隔离结束原因本身：在默认流转成运行时事件（Runtime Event）时，若此前没有已记录的失败分类 failureClass，映射如下：

表 6 / Table 6 · 第8站：第四个模型步骤（Model Step）生成中文总结
原始结束原因标识映射后的状态标识可以怎样解释
end_turncompleted模型流按这一结束原因收束，不等于任务验收已经通过

完整映射还会优先检查此前记录的失败分类 failureClass：已经记录失败时，end_turn、max_tokens等原因最终仍形成 failed；user_stop保留 aborted。因此，上表不能代替整个运行时事件（Runtime Event）的判断。

其他状态（State）接口还可能出现 cancelled，不能把所有取消相关字段替换成同一个字符串。CompleteEvent 只是流结束通知，不能看见“Complete”就判断成功；未记录先前失败时，max_tokens等原因可映射为 completed，却仍可能留下不完整回答。

智能代理（Agent）也可以正常结束并诚实报告测试（Test）仍失败。读到终态（Terminal State）支持的是执行（Run）如何结束，不能替代任务要求、文件效果（Effect）与验证（Verification）材料。

第9站：宿主（Host）与客户端（Client）恢复完成视图

终态（Terminal State）提交后，宿主（Host）回读相应事实（Fact），构造状态快照（Snapshot）并发布给订阅S1的客户端（Client）。客户端（Client）再显示聊天内容、运行详情与结束状态（State）。把已有记录整理成特定可读视图的过程称为投影（Projection）。

方向是“持久事实（Durable Fact）被宿主（Host）读取，再由客户端（Client）显示”；界面显示完成，不会反向创造执行终态（Terminal State）。运行增量可以更早显示，但完成视图仍须来自负责者（Owner）接受的记录。

若最终通知丢失，重新连接后读取已有事实（Fact）即可重建同一项工作的视图。这不要求模型（Model）重新回答，更不要求再运行一遍修改命令。第14章继续区分执行事实（Execution Fact）与不同展示形式。

核心问题解析

问题1。 从发送T7到第一次模型调用（Model Query），宿主（Host）与运行时（Runtime）分别补上了什么？

参考答案。 宿主（Host）核对并持久接纳工作、固定R7与输入基础；运行时（Runtime）取得执行依据，组装本步骤输入并驱动模型（Model）与工具（Tool）。加载动画不是准入（Admission）成功的证据。

问题2。 为什么第一次读取前不能可靠生成README的精确替换？

参考答案。 本例没有预先载入文件，模型（Model）还不知道当前旧文本与匹配位置。读取把真实内容变成下一次可用材料，才能提出有依据的编辑；仍需检查返回内容是否截断。

问题3。 命令文本与退出码（Exit Code）各能证明什么？最终通知丢失后应重做任务吗？

参考答案。 执行输出（Output）帮助判断实际运行过程，退出码（Exit Code）按命令约定报告结束情况，还需核对目标行为与修改范围。通知丢失应回读事实（Fact）并恢复展示，不能据此重做已有工作。

实现深化

准入（Admission）重试：同一身份（Identity）还要核对内容

网络超时后，客户端（Client）可以重发同一T7，但宿主（Host）不能仅凭编号就再开一次执行（Run）。原身份（Identity）必须继续指向原规范化意图与已固定的执行描述：

重试材料应如何判断
同一T7，规范化输入及已固定描述一致可按精确重试（Exact Retry）核对已有准入（Admission），不任意创建重复工作

实际准入（Admission）还核对已保存的执行（Run）、用户消息（Message）等关联，不只是比较这张教学表里的文本。相同编号不是跳过内容校验的通行证；相同文本也不是相同身份（Identity）的充分证据。

组成快照（Composition Snapshot）与物理请求尝试（Physical Attempt）

组成快照（Composition Snapshot）记录这次执行（Run）采用的配置和来源标识，便于比较“为什么两次请求的工作基础不同”。来源包括系统规则、工作区指令（Workspace Instructions）、允许读取的长期信息、当前技能说明包（Skill），以及计划（Plan）或目标（Goal）等控制域提供的适用内容。技能说明包（Skill）是可按条件装载的方法材料，不是名字出现就已执行的方法。

工具（Tool）上限、当前步骤可用性（Availability）、模型（Model）与模型服务提供方（Provider）选项也要对应本次执行（Run）。模型服务提供方（Provider）是接收模型请求并返回结果的服务；模型协议适配器（Model Adapter）按其协议组织实际请求。

一次逻辑模型调用（Model Query）还可能有物理请求尝试（Physical Attempt）：例如原请求失败后，在满足条件时重新向服务发出请求。当前公共模型服务提供方（Provider）路径记录尝试状态（State），以及有界的 promptComposition，即请求材料的组成与大小诊断。

组成指纹与大小分布都不是完整请求正文。 它们可以帮助定位配置变化与调用状态（State），不能据此逐字还原模型（Model）看过的每一段内容，也不能从同一个R7推导服务只收到过一次请求。

普通工具调用（Tool Call）前的检查

运行时（Runtime）取得工具调用（Tool Call）以后，至少还要分别确认下列问题：

表 8 / Table 8 · 普通工具调用（Tool Call）前的检查
检查位置要确认什么失败意味着什么
参数结构（Schema）与实际校验参数满足声明及具体工具（Tool）的运行时检查不能把格式错误交给实现盲目执行
本次执行（Run）的能力范围该工具（Tool）属于获准的能力集合模型（Model）提出了当前并不允许的能力

参数结构（Schema）说明合法输入的形状；实际校验还要看具体实现。检查通过之后，也只意味着可以进入对应执行路径，并没有提前产生成功结果。

Edit 的持久边界与扩边分支

在本章普通工具（Tool）路径中，运行时宿主（Runtime Host）已经接入持久结果接收端（Durable Result Sink）。接收端负责把结果交给相应持久写入逻辑；它不是额外的模型（Model）或自动恢复（Recovery）算法。

表 9 / Table 9 · `Edit` 的持久边界与扩边分支
阶段状态（State）改变后续可以依据什么
执行前检查确认参数、能力与当前边界尚不能据此说文件已改变
工具开始边界（T1）保存实现可能从这里开始的记录实现可能已经进入，不能仅凭此认定效果（Effect）完成
实际执行执行器（Executor）在当前沙箱（Sandbox）或其他执行环境（Environment）中运行外部文件可能已经改变
工具结果边界（T2）保存该调用的结算结果后续模型（Model）与恢复（Recovery）程序有已接纳结果可读

T1、T2是一个工具调用（Tool Call）前后的边界标签，不是工作轮次（Turn）T7，也不是两个新的工作轮次（Turn）。T1之后、T2之前崩溃时，结果可能仍未知；有T1不证明写入完成，无T2也不证明写入没有发生。

这套顺序不能直接移植到所有后端或由模型服务提供方（Provider）内部执行的工具（Tool）。普通结果的持久提交失败也不能降格成“测试（Test）失败”继续喂给模型（Model），应交给相应失败与恢复（Recovery）逻辑。第18章会把具体窗口展开。

如果 Edit 越过边界

假设当前只允许修改工作区（Workspace），却请求写入外部目录。当前执行边界（Execution Boundary）不覆盖时，先拒绝这次操作；只有对应入口允许申请，并且工具结果（Tool Result）给出明确扩边需求，模型（Model）才可在后续步骤提出扩边申请。

批准（Approval）以后仍须按新边界重新判断下一次调用，不会自动重做原 Edit。命中显式拒绝（Explicit Deny）时，也不能靠普通扩边绕过。审批消息（Message）与执行许可、实际效果（Effect）是连续但不同的材料。

命令解释器（Shell）字符串为何需要执行边界（Execution Boundary）

一个 Bash 请求中的命令字符串，可以间接读写文件、启动子进程或访问网络。静态看程序名，不足以证明所有间接行为。因此实际执行位置仍须应用授权（Authorization）与隔离（Isolation）条件，不能只在提示词（Prompt）中写“请勿越权”。

参数可解析、当前获准、环境强制限制资源、执行结果符合任务，这四个判断不能互相替代。这里不把整段命令解释为任意情况下都能安全重试的单一操作。

终态（Terminal State）与资源结算（Settlement）的两个时刻

最终文本可见、终态（Terminal State）已持久保存、后台资源全部释放，可能是三个时点。资源结算（Settlement）在这里对应后续的 settled 承诺与清理：事件迭代器、活动工具（Tool）和相关资源完成收尾。它不是前文单个工具结果边界（T2）的同义词。

用户按 Stop 后，还应区分已发出取消（Cancellation）请求、已提交终态（Terminal State）以及资源已收敛。取消（Cancellation）不能撤销已写入的文件；普通工具（Tool）仍需完成可结算结果，具体终态负责者（Owner）再依据事实（Fact）收束。晚到的停止请求也不能覆盖已接纳的终态（Terminal State）。

这些是本章默认路径的控制关系，不保证任意远端执行端立即停止。第18章继续说明停止时的工具结算（Tool Settlement）。

第10站：“以后记住中文偏好”走另一条路径

同一句请求中的“本轮总结用中文”，可以作为当前指令进入模型输入（Model Input）；是否遵循看实际回答。“以后也希望中文解释”还需要记忆（Memory）写入，以及未来读取和使用的消费者（Consumer）。

先定义两条不同的数据路径，完整机制在第20章展开：

表 10 / Table 10 · 第10站：“以后记住中文偏好”走另一条路径
机制写入哪里当前读取与使用边界
本地记忆笔记（Local Memory）以 MEMORY.md 为主体的用户可见笔记用户开启读取并满足适用范围时，可由输入组装选入；仍受范围、大小与缓存条件约束

memory_remember 是实际写入工具标识。它返回保存成功，不能证明下一次模型（Model）已读到偏好；条目化长期记忆（Atomic LTM）也不会自动同步到 MEMORY.md。存在 readItem、searchByKeys 存储接口，不等于生产输入组装已经调用它们。

所以需要追踪“谁读取、何时选入、哪次模型（Model）收到”。使用已开启读取的本地记忆笔记（Local Memory）时也仍要核对实际输入与回答；不能把开启开关直接写成永远遵循。条目化长期记忆（Atomic LTM）未接入的结论限定这里的默认生产路径，不声称已经穷尽所有应用或外部调用者。

把整条链拆成四种信息流（Information Flow）

同一项工作里有四种不同方向。它们可以在不同时间交错，不要求每个时刻都同时活跃：

表 11 / Table 11 · 把整条链拆成四种信息流（Information Flow）
信息流（Information Flow）主要方向与消费者（Consumer）本例说明什么
控制流（Control Flow）客户端（Client）提交，宿主（Host）接纳，运行时（Runtime）推进T7被准入（Admission）为R7；是否开始、继续或停止
模型流（Model Flow）工作上下文（Working Context）交给模型（Model），意图交回运行时（Runtime）提出读取、编辑、检查或总结
效果流（Effect Flow）工具执行链（Tool Execution）进入外部执行环境（Environment）读取文件、改写README、启动测试（Test）进程
事实流（Fact Flow）负责者（Owner）提交记录，输入或展示消费者（Consumer）再回读保存调用、结果与终态（Terminal State），按用途构造视图

读取工具（Tool）会接触环境并返回信息，但不必产生文件修改。把它放在效果流（Effect Flow）这一行，只表示执行跨入外部环境；具体发生了什么变化仍要按操作判断。

三个关键时间点

表 12 / Table 12 · 三个关键时间点
时间点谁已完成什么仍可能缺少什么
已提交（Submitted）客户端（Client）发出T7请求不一定已收到接纳答复
已接纳（Admitted）宿主（Host）持久固定T7与R7模型调用（Model Query）可能尚未开始
已有终态（Terminal）运行时（Runtime）已写入R7结束事实（Fact）客户端（Client）可能未收到通知，资源也可能仍在清理

这里的已提交（Submitted）描述请求时点，与第05章mini的 Submitted 异常类型不是同一协议。三个时点之间都可能发生断线或崩溃。

情况A：已提交（Submitted）后、已接纳（Admitted）前断线

客户端（Client）不能仅凭旧界面判断是否收到。重试要保留原工作身份（Work Identity）和相同规范化意图，让宿主（Host）核对是否是精确重试（Exact Retry），而不是先创造一个无关联的新任务。

情况B：已接纳（Admitted）后、模型调用（Model Query）前崩溃

准入（Admission）事实（Fact）仍在，恢复（Recovery）程序可以知道R7已被接受，再检查执行打开记录与实际进展。它不能无身份地创建重复工作，也不能仅凭已接纳就断言服务请求已发出。恢复（Recovery）状态（State）不等于重建旧程序调用栈。

情况C：编辑开始后、结果记录完成前崩溃

文件可能已经修改，也可能尚未修改。需要对账（Reconcile），即结合原执行记录与现实效果（Effect）核对当前情况；证据不足时保留结果未知（Outcome Unknown）或停放状态（Parked），不能盲目重复非幂等修改。幂等性（Idempotency）只说明重复特定操作是否保持相同结果，不能由局部替换推导整条组合命令都可重放。

情况D：已有终态（Terminal）而客户端（Client）尚未收到

重连后回读持久事实（Durable Fact），重建完成视图即可。已经保存的答案不需要重新生成；显示失败也不能把原成功结果改写成执行失败。

一个正常分支和两个异常分支

正常分支

在给定初态下，两次读取取得实际内容，编辑成功，Bash运行目标测试（Test）并返回退出码（Exit Code）0，差异（Diff）检查符合范围，模型（Model）中文总结，运行时（Runtime）记录结束。这条分支中每个结论都有材料，但正常结束仍不替代对任务要求的核对。

异常分支一：测试（Test）失败，工具执行链（Tool Execution）仍可正常工作

假设读取与编辑都成功，测试（Test）却返回退出码（Exit Code）1及失败断言（Assertion）。工具执行链（Tool Execution）可能完整执行并正确返回了这个错误；失败发生在任务世界中，不能因此断言工具（Tool）传输损坏。

已结算的失败结果可以进入后续模型输入（Model Input）。若预算（Budget）与停止条件仍允许，模型（Model）可诊断或如实报告；它不能把退出码（Exit Code）1改写成测试（Test）通过，也不能超出“只改README”的授权（Authorization）去修函数。

异常分支二：模型服务提供方（Provider）中途断开

要先问本次物理请求尝试（Physical Attempt）已经留下什么可观察结果。若还没有可观察输出，还需同时满足错误可重试、剩余模型步骤（Model Step）与尝试额度等条件，才可能重发。没有输出不是“可以无限重试”，也不证明服务没有收到请求或产生费用。

若已经有回答文本、工具（Tool）活动或完成的步骤边界，就不能沿“没有输出”的分支重发整个请求。只有思考输出（Thinking Output）片段的少数情况具有专用恢复（Recovery）路径：先封存符合条件的片段，再发布可观察的重试事件；不能静默抹掉旧片段，伪装成一次没有失败的调用。其他未完成片段（Partial Output）不因此都具备重试资格。

不满足恢复（Recovery）条件时，应保留可保存的片段和失败事实（Fact），结束相应执行（Run）。这与 Bash 测试（Test）失败不同：后者已经有一条可交回模型（Model）的业务结果，前者可能连当前模型步骤（Model Step）都无法完成。

源码中的 complete(error)、complete(step_limit)都会映射为失败；不能依据事件名 CompleteEvent 解释成成功。第13章会用计数例说明，为何三步额度不保证还有第四步总结。这里不混同模型步骤（Model Step）、物理请求尝试（Physical Attempt）与工具调用（Tool Call）的计数。

机制问题解析

问题1。 同一T7换了输入，为什么不应作为原重试接受？

参考答案。 工作身份（Work Identity）对应已固定的规范化意图与执行描述。内容改变会让同一身份（Identity）指向不同工作；精确重试（Exact Retry）必须核对这些条件，而不是只检查编号。

问题2。 Edit可能已写入但结果没有保存，为什么不能只看聊天记录决定重做？

参考答案。 展示和持久记录都可能落后于效果（Effect）。需要结合本路径的T1/T2、实际文件与对账（Reconcile）能力判断。缺少结果不能推导没有执行，重放也可能产生重复效果（Effect）。

问题3。 偏好已写入条目化长期记忆（Atomic LTM），下一次是否必然进入模型输入（Model Input）？

参考答案。 不必然。该默认生产路径有写入与存储查询，尚未接通智能代理（Agent）的选择、召回和输入装载。还需找到实际消费者（Consumer），不能用“已保存”代替“已读到”。

下一项行动请求（Action）怎样取得进展

工具结算（Tool Settlement）后，后续模型步骤（Model Step）取得可用反馈。运行时（Runtime）按预算（Budget）、停止条件和执行边界（Execution Boundary）判断能否继续；模型（Model）再根据材料选择值得做什么。允许继续是控制问题，取得进展是决策问题，两者不能合成“没有结束就一直运行”。

普通失败闸门按调用来源、工具（Tool）名与规范化参数形成签名（Signature），限制相同请求的连续失败。它保存的是最近一组失败签名（Signature）的连续计数：同签名此前失败两次，第三次尝试就在实际实现前被挡住；任意成功清空该串，另一签名（Signature）失败则从一次开始。这个普通路径的闸门不比较错误文本，也不判断请求是否增加了信息。

所以，改一个无关参数可能改变签名（Signature），却没有取得新证据。闸门只是限制某类机械重复，不能当作完整规划算法；计算机操作（Computer Use）等路径还可能有独立控制条件。第16章的循环深化继续比较补充观察、直接修改与重复测试（Test），并给出预算（Budget）演算。

工具反馈怎样进入下一次请求，见第15章。本章保留这条主线：取得结果、检查是否可继续、再形成新的模型（Model）决策；任何一步缺失，都不能由“模型（Model）还想继续”补足。
