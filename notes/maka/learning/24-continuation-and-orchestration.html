第 24 章｜计划、目标与持续执行

本章概览

核心问题：计划获批、目标未完、时钟到点或依赖完成后，什么事实允许系统继续工作？

关键概念：Plan（计划）：用户控制的工作流状态；Goal（目标）：按评估与预算推进的结果要求；Schedule（定时任务）：未来触发机会；Graph（任务图）：依赖与调度状态；claim（认领）：绑定一次确切执行的记录。

关系主线：各控制器维护继续工作的理由，经 Host 准入交给普通 AgentRun；触发、启动、终态与任务验收不能互相替代。

前置：执行身份、事实与投影；Graph 节点使用第23章的独立 child。

核心路线

继续工作的四种触发

复杂 Agent 产品经常需要“以后继续工作”：

  • 用户批准计划后继续；
  • 目标还没完成时再尝试一轮；
  • 明天九点自动检查；
  • 等多个子任务完成后，让主 Agent 以 supervisor（监督者）角色重新审阅结果。

这些都可以口头叫作 continuation，但它们不是同一种机制。domain 指负责某一类业务状态的范围，例如计划或定时任务，不指网络域名。每种 continuation 都必须确定：

谁拥有控制状态，什么事实允许它创建下一项普通 Agent 工作？

README 任务的四种后续需求

任务是：

检查 package.json 与 README.md，把 README 的测试步骤更新正确，运行测试；以后请用中文解释结果。

现在分别想象四种产品需求：

  1. Plan：先把修改计划展示给用户，用户批准后再编辑文件；
  2. Goal：在用户同时授权修复源码的条件下，根据测试失败继续修复，直到满足目标或停止条件；
  3. Schedule：明天上午再检查 README 是否仍与项目配置一致；
  4. Graph：让多个 child 分别检查 package.json 的 test script、README 当前测试步骤和平台差异，全部完成后再综合。

它们最后都会进入普通 AgentRun，但“允许创建下一轮”的理由不同。

四种控制状态分别提供继续理由，汇入同一执行准入；它们是并列的触发机制，不是四步固定流程。

一张后台任务表缺少哪些控制状态

一个简单但危险的实现可能只有一张表：

background_tasks
  id
  prompt
  status = pending | running | done
  run_at?

然后所有功能都调用同一个 resume()：

if status != done:
  call_model_again(prompt)

这样做会马上遇到问题：

  • Plan 还没被用户批准，系统是否可以继续？
  • Goal evaluator（完成评估器）的输出解析失败，是“完成”还是“未知”？
  • Schedule 到点后进程崩溃，重启会不会触发两次？
  • Graph 的一个 child 失败，supervisor 应等待、取消还是继续？
  • 已经开始的新 Run 与旧 running row 之间怎样对应？

“下一轮再调用一次模型”只是执行动作，不是控制语义。每个 domain 必须拥有自己的状态和合法触发条件。本章后文的 Goal/Graph checkpoint 是推进和恢复的控制检查点；第19章的 Context checkpoint 则表示一段模型历史，两者保存的对象不同。

四个 domain 的触发与执行职责

表 1 / Table 1 · 四个 domain 的触发与执行职责
需求谁决定可继续后续实际做什么
Plan：先计划、再批准用户批准与 Plan owner创建普通 Run 执行获准工作
Goal：目标尚未满足Goal owner 根据评估、预算和当前策略判断需要时创建下一轮普通 Run

这些 owner 管理继续的理由与状态，实际模型—工具执行仍复用普通 AgentRun。触发或启动成功，不能替代工作结果。

Plan：由用户控制的 durable workflow

它解决什么问题

有些修改需要先把步骤展示给用户，再等待批准。例如：

1. 读取 package.json 与 README.md
2. 修改 README 测试步骤
3. 运行测试

Plan 保存的是工作流控制状态。用户可以查看、批准、推进、取消或恢复它。

它不是什么

Plan 不是“模型自己一直循环直到完成”。用户批准是关键 trigger。在批准并启动工作的路径中，新 AgentRun 执行计划中的工作；批准保存的是工作流状态，真正修改与测试仍由 Run 执行。

在案例中怎样运行

R7 生成计划
→ Plan durable 保存
→ 当前阶段等待用户批准
→ 用户 approve
→ Plan coordinator 创建新的 root execution intent（顶层工作启动意图）
→ Host admission
→ 新 AgentRun 执行 Edit/Bash
→ 模型根据观察调用 update_plan 报告进度，Plan 保存状态

因此，计划显示“步骤完成”还需要对应的修改和测试证据。进度报告不是独立验证器；某一轮模型已经结束，也不等于所有计划步骤都已完成。

Goal：由完成判断驱动的自主 continuation

它解决什么问题

Goal 表达的是结果，例如“让 README 测试步骤正确且测试通过”。它不会自动扩大文件或工具授权；若本次只获准改文档，源码中的错误仍需要按实际范围处理。保存目标也不等于已经开始工作：Client 的 goal.arm 只建立目标状态，等待后续 Turn 承载它；它本身不启动模型。对已暂停的目标，用户也可以通过合法的 resume 恢复驱动。

下面把身份写全。G1、T7、R7 等都是教学记号，不是本次运行记录：

S1：用户先 arm Goal G1；尚无新 Run
  → 用户提交 T7，Host 准入 R7；这项 Turn 承载 G1
  → R7 读取、修改、测试并报告结果，Turn 完成结算
  → evaluator 对 G1 与近期对话做一次无工具评估
  → 若未满足且预算、状态与准入条件允许，形成 continuation
  → S1 的新 Turn T8 / Run R8 继续实际工作
  → R8 结算后再次评估；若判定 met，G1 进入 achieved

工作模型和 evaluator 要分开理解。R7/R8 通过普通 AgentRun 调用 Read、Edit、Bash；evaluator 是使用该 Session 模型配置的一次辅助模型调用，没有工具，也不创建一个“评估 AgentRun”。它判断收到的文本，不会自己重跑测试。因此，R7 的结果报告需要说明真实测试入口、输出和未完成项；独立调用评估模型并不自动获得独立验证。

Goal terminal 与 Run terminal 不相等

某一次 Run 完成只说明这一轮 AgentRun 已 terminal。Goal 可能仍未满足；反过来，Goal 已取消也需要协调正在运行的 Run。两个生命周期不能合并。

这描述正常完成判断的路线；当前实现对评估失败仍可能选择继续，不应把每次 continuation 都解释成模型已经可靠证明“目标未完成”。具体分支见Goal evaluator 的失败策略。

ScheduledTask：时钟只负责到点，不负责完成工作

它解决什么问题

Schedule 让某个工作意图在未来时间获得触发机会。案例中可以创建：

明天上午九点检查 README 与 package.json 是否仍一致。

“到点”与“执行成功”之间还有很多步骤

clock says due
→ coordinator 取得 fire claim
→ 冻结或解析目标 Session/Connection
→ Host admission
→ AgentRun start 稳定
→ Schedule 将本次 fire 结算为 ok/fired
→ AgentRun 随后独立运行并形成 terminal

fire 是一次到点触发，fire claim 是对这次机会的认领记录。它配合执行身份与准入检查，避免重启或多个 worker 把同一次触发重复启动。Schedule 的 ok/fired 在 hosted root 已 admission、Run start 稳定后即可结算，不会等待 AgentRun terminal；它只能证明触发和启动边界已经完成，不能证明后续 Agent 工作成功。

Agent Graph：依赖与唤醒的持久控制平面

第一步：DAG 表达偏序，不是固定的全序脚本

当任务可拆成多个依赖节点时，Graph 记录“哪些工作依赖哪些结果”，并决定何时可以派发工作。节点由独立的 child Session/Run 执行，也就是 第23章 中有自己身份、输入与结果的子任务。图的结构常称为 topology（拓扑）；这里最基本的结构是 DAG（有向无环图）：

下图的边表示前置依赖（Dependency）：N1–N3 的结果满足后，N4 才有汇总所需材料；并列节点之间没有先后边。

边表达“谁必须先完成”，而不是预先排好所有节点的执行次序。N1、N2、N3 之间没有依赖，所以它们构成可并发的偏序；N4 必须等待自己的前置输入满足。三个基本对象是：

Node  = 一个边界明确的 Operator
Edge  = 前置依赖或结果流向
Ready = 依赖条件当前看起来已满足

每个节点仍由普通 child AgentRun 工作，Graph 负责依赖和推进状态。一个节点返回结果，只能说明这个子步骤的情况；主任务还要检查其他依赖、综合结果并完成修改与验证。revision、claim 和 wake把依赖判断连接到实际派发。

核心问题解析

问题 1。 Schedule 显示 fired，为什么不能据此说 README 已经修好？

解释。 fired 说明触发和启动边界已经结算；还要等待随后 Run 的工具结果和终态，并核对 README 与测试要求。Run 正常结束本身也不能证明任务验收通过。

问题 2。 一个 Run 已完成，Goal 为什么仍可能继续？

解释。 Run terminal 结束一次执行；Goal 还要依自己的完成条件、评估和预算决定目标状态。

问题 3。 Graph 中检查 package.json 的节点完成，主任务还缺什么？

解释。 还需核对其他依赖、已提交结果与综合结论，再完成修改和测试；节点终态不能代替整个目标的完成。

问题 4。 重新打开 Desktop 为什么通常不是业务 continuation？

解释。 重连先恢复观察同一份事实，并不自动创建新的业务工作。

问题 5。 Goal 已 arm，但用户尚未提交后续 Turn，能否认定测试修复已开始？evaluator 能否自己运行测试？

解释。 不能。arm 保存目标，后续承载 Turn 或合法的 resume 才推动实际工作；evaluator 只做无工具文本判断，实际测试属于普通 AgentRun 的工具执行。

问题 6。 Plan 显示某个步骤已完成，为什么仍需要修改或测试证据？

解释。 Plan 保存模型报告的工作流进度；实际修改与测试由普通工具和 Run 执行，进度状态不独立验证这些结果。

实现深化

这些控制器都需要处理状态过期、重复触发和进程重启。已经启动的 Run 还可能留下 第18章 所述的未知工具效果，控制状态恢复不能替它消除不确定性。

Plan：批准、进度与实际结果各自说明什么

例如 Bash 明确返回测试失败，模型却把前两步标 completed、测试步骤标 skipped：在其他输入约束满足时，当前 PlanStore 会完成这份 execution。这只反映收到的步骤报告，不能据此写“测试通过”。反向也成立：R8 已正常结束，但没有把全部步骤报告为 completed/skipped，Plan 可以仍为 active。

源码把两个入口分开：plan.control 控制状态，plan.turn.start 将 approve/resume 与新 hosted root Turn 组合；批准还会核对是否是最新待批准版本。不要把一个过时按钮或重复请求当成新的执行授权。若 R8 failed/cancelled，或 Host 在 active Plan 中重启，Plan 转为 interrupted；用户对这个执行合法 resume 后，由新 Turn 继续工作，旧 Run 不会复活。恢复时仍要读取已经发生的工具效果，不能从原步骤列表推断文件没有改变。

Plan 的工具返回与会话结束

update_plan 更新步骤或结束 execution 只是 tool boundary，不意味着当前 conversational Turn 必须立即停止；模型仍可能读取工具结果并给用户总结。

Goal evaluator 的当前失败策略

从 arm 到驱动的承载关系

goal.arm 即使返回 active，也可能还没有任何 Goal 驱动的执行。Host 在普通 Turn 开始前绑定当时的 Goal control lease，完成后才按这份绑定结算；如果先开始 T7、再从 Client arm G1，T7 不会被事后归入 G1，后续 Turn 才承载它。恢复同样区分“已开始驱动”和“仅保存目标”：重启不会让从未被 Turn 承载的 armed Goal 自动开跑。

暂停后，Client 的 goal.control(resume) 会核对目标身份与 revision，再恢复驱动意图；仍要经过普通 root admission。已经结束的模型调用不会复活，Session 忙也不意味着可以越过准入立即新开 Run。

评估器真正能看到什么

当前 Host 经 SessionManager 取得 RuntimeEvent 派生的 StoredMessage，再筛选最近六条 user/assistant 消息，逐条截断后组成近期对话，再与 Goal condition 一起交给 evaluator。它没有直接拿到完整 RuntimeEvent 或原始工具结果，也不能读文件、执行 Bash 来补证据。假如 assistant 只写“测试没问题”，评估器获得的就是这份报告；它不会凭空知道测试入口是否错误、失败行是否被省略。

这是专门的 Goal 评估输入，不应与普通工作模型由 RuntimeEvent 构造的 provider history 混为一谈。当前辅助调用使用 Session 的连接与模型配置、输出上限为 1,024 token；它有自己的调用记录，但不成为新的 Turn/Run。

为什么 evaluator 是关键边界

Goal 是否继续是一项业务 authority，需要检查 evaluator 结果的类型，并为未知结果设置预算和失败处理。Maka 拒绝非布尔 flag：字符串 "false" 与 timeout、调用错误或不可解析结果一样，进入 evaluatorFailed 的中性结果；采用 fail-open 策略，允许在状态、预算和准入仍满足时继续。

当前实现有 iteration 上限，evaluator 持续失败时仍可能继续多轮。检查布尔类型也不等于完整 schema 校验：缺字段仍有默认值，额外字段也未全面拒绝，需逐项看 contract。

parseGoalEvaluation 解释输出，processCompletion 和 GoalManager.settleTurn 再按 owner、预算和准入条件消费它。解析出一个结果只是这条决策链的起点。

ScheduledTask 的目标与配置身份

两类常见触发意图

  • session_resume：在既有 Session 中启动新的普通 root Run；
  • agent_run：按冻结配置创建或核对 fresh Session，再启动普通 root Run。

当前新建 agent_run 会冻结 exact LLM connection identity。旧的 slug-only row（只保存可读名称、没有确切连接 ID 的记录）属于兼容数据，不能代表新路径的完整保证。

Graph 从依赖图到持久调度

第二步：中间结果会推动动态 Schedule Revision

Agent 工作通常不能在开始前把所有步骤一次性穷举。N1 可能发现测试命令由另一个 workspace 生成，N3 也可能证明平台差异其实不存在。此时 root Session 中的主 Agent 需要增加节点、替换旧路线、停止过时分支，或选定最终产物。

因此，Maka 的 Graph 不是“一次写死后只会向前跑”的静态 DAG。主 Agent 通过 update_agent_graph 提交一份结构化 Schedule Revision；revision 描述要新增、替换、停止或采纳什么。它先进入持久控制面，成为可供恢复与审计读取的 durable intent，而不是工具一返回就直接等同于某个模型调用已经开始。

这里的 durable 应谨慎理解为“调度意图先形成持久事实，恢复逻辑可以重新观察它”，不是脱离存储事务、claim、恢复实现和实际测试后仍可宣称的“绝不会丢失”。

第三步：主 Agent、Coordinator 与 supervisor 不抢同一份职责

表 5 / Table 5 · 第三步：主 Agent、Coordinator 与 supervisor 不抢同一份职责

第四步：从 durable intent 到 reconcile

update_agent_graph 的直接效果是追加 revision 并请求协调，不是亲自运行 child。Coordinator 被唤醒后，从持久状态重新折叠当前计划，并把它与已经提交的 child Run/RuntimeEvent facts 对齐：

读取 durable revisions 与既有执行 facts
  → 应用 stop / replace / finish 决策
  → 补齐缺少的 child Operator 容器
  → 重新计算哪些节点 Ready
  → 检查或取得 exact execution claim
  → 经共享 Host authority 派发普通 child AgentRun

这一步叫 reconcile，因为 Coordinator 的工作不是相信一份长期驻留内存的 DAG，而是反复比较“持久意图”与“已经发生的执行事实”，再决定缺少哪一步。

第五步：Readiness projection 不等于 conditional claim/admission

第六步：节点仍是普通 child AgentRun，结果要 committed 且有界交接

Graph 不重新实现 Prompt/Context、provider adapter、ToolRuntime、Permission/Sandbox、RuntimeEvent 或 terminal。取得 claim 并完成 admission 后，节点在 linked child Session 中运行普通 AgentRun；输出与终态仍由普通 Run/RuntimeEvent ledger 拥有，不归 Graph callback 私藏。

下游节点或 supervisor 通过 committed bounded handoff（已提交的有界结果交接） 消费结果：交接依据已经提交的 terminal/result facts，携带完成下一步所需的有界摘要、正文或 artifact reference，而不是把 UI 上看到的每条流式事件、child 的整段私有历史或一个尚未落盘的临时输出都当成 Graph 输入。

一次定时触发，在崩溃前后还能对应同一份工作吗

让 README 检查明早再做一次，看似只要设置 timer 并保存 prompt。真正的问题是：时钟可以重复提醒“到点了”，但系统如何知道已经接纳了哪一次执行？下面以 session_resume 的一次 fire 为主，身份和故障时点都是教学假设，没有运行定时器。

把这一火次写为四层对象，而不是一个 running 布尔值：

F = (task, fire claim, exact Session/Turn/Run/message)
A = Host 是否接纳这组身份与工作内容
S = 该 Run 的 start 是否已稳定
T = 该 Run 是否已有合法 terminal，以及它的结果

F 是“哪次触发、准备交给谁”，A 是执行准入，S 是启动边界，T 才是执行结束。任务验收又比 T 更进一步：正常结束仍需检查 README 和测试证据。这个对象用于推演，没有新增一份与源码竞争的状态库。

这里的 message 指这次定时输入的 userMessageId，如 U8，不是其完整正文或后续全部消息。bindFireExecution 对 sessionId、turnId、runId、userMessageId 四字段逐一比较；即使 S/T/R 不变，换成 U9 也冲突。内容一致性另由 Host admission 校验，不能仅靠 ID 相同推断正文相同。

表 9 / Table 9 · 一次定时触发，在崩溃前后还能对应同一份工作吗
崩溃/观察位置新 Host 读取什么当前 Maka 的限定处理

以一个重复到点信号为例：pending claim FC1 已绑定 R8（FC1 是火次认领，与 第23章 的 child Session C1 无关）；第二次扫描发现该 task 仍有 pending claim，所以本次不再认领第二份。bindFireExecution(FC1, S1/T8/R8/U8) 重复提交相同身份可接受；试图改成 R9 或 U9 则拒绝。这里固定的是同一火次的执行身份，不是给所有以后到期的火次使用一个 Run，也不证明 Run 内每个外部操作都 exactly-once。

真实消费者是 Host coordinator：恢复读 claim 后，#fulfill 确认 Session，再交 #admitAgentRun；root admission 的 start callback 把四个身份和 required durability 交给 SessionManager.sendMessage，检查实际 started Run 一致，稳定后再结算 fire。Store 保存身份，Host 决定准入，Runtime 执行工作，不能让 timer 跳过中间两层。

如果换成创建 fresh Session 的 agent_run，还多一项重要前提：模型 Connection 的 ID 与 slug 在模板中冻结，创建 Session 和紧邻 admission 时都检查。即使新 Connection 的显示名称、slug 或模型名一样，也不能据此继承旧实体的身份；旧模板缺少 exact ID 时当前实现失败关闭。这说明“执行意图持久化”还必须保存它实际绑定的资源身份。

什么时候需要更强的工作流恢复

四类 domain 分别处理不同触发：Plan 等合法批准，Goal 消费评估与预算，Schedule 消费时间和 fire，Graph 消费依赖与结果。共同底层不是“不断调用模型”，而是先保存允许继续的理由，再由执行 owner 接纳确切工作。故障重试、观察恢复和新的业务意图应分别命名；一套通用 resume(prompt) 无法自动补齐这些条件。

相邻领域的 Temporal 提供另一种恢复单位：Workflow 是可重放的控制逻辑，Activity 是工作进程执行的动作单元。事件历史记录 Workflow command 与 Activity 的结果；控制代码重放到已完成的 Activity 时复用历史结果，未取得完成结果的 Activity 则有其等待/重试语义。它比一个 fire claim 管得更深入控制程序，但要求确定性命令与代码版本兼容；外部效果已发生、Activity完成回执未到时仍可能重复。可以在 Temporal 原理与失败例中继续追踪重放时的判断。

恢复单位决定机制选择：只要未来启动一次普通 Agent 工作，可用具有身份与恢复规则的 Schedule；如果要跨多个服务、长时间等待并复用控制程序中的已完成结果，再考虑持久 Workflow。外层 Activity 包住整个 Agent 时，Activity 重试可能重新做整段调查，所以内外两层必须分配重试预算和效果身份，不能让每层各自认为可以无限再试。涉及付款、发布或长期浏览器状态时，更要回到 第18章 核效果回执，不能从 timer 或 Workflow 名字直接推导安全。

还要定义 wrapper 怎样映射结果：Agent Run 为 failed，既可能让 Activity 报失败，也可能作为 {status:failed} 的正常返回值被记录为 Activity completed。只有前一种且重试政策允许时，才能继续讨论失败重试；后一种的控制重放会复用这个返回值。不能由 Run failed 单独推断 Activity 没有完成记录，两种映射都不替原工具消除效果未知。

变式一：恢复时只有 fire claim，没有 execution identity。为了不漏任务，能否创建R9；如果已有R8，能否给同一claim换R9？

参考答案

按当前实现，第一种失败结算，不在恢复中猜新身份；第二种也不能换，绑定相同值可以重复，不同值会冲突。产品若要改变“尚未绑定就失败”的策略，需要显式定义新业务触发和授权/去重边界，而不是把改策略叫作透明恢复。已有R8还必须由其owner核对，避免制造第二份副作用。

变式二：fired已保存，R8的Edit出现outcome_unknown；现在改用外层Workflow自动重试整个Agent。是否就能省去文件对账？

参考答案

不能。fired只证明触发/启动，未知工具效果还在。外层重试可能创建新调用并重复已经发生的编辑；Workflow复用的是已记录的完成结果，缺少完成回执的效果仍需资源方幂等或对账。应先核原Run、工具记录与当前文件，明确能复用什么、谁决定新尝试，再继续验收。两层恢复合同不能互相当作对方已经处理过。

Deep Research 与 Swarm 放在哪里

Deep Research

Maka 当前的 Deep Research 更接近受限 Session mode：执行仍由普通 AgentRun 承担，工具白名单偏只读，并维护研究 artifacts/checklist。

Swarm

Maka 当前的 Swarm 更像 Graph 上层的薄策略：帮助决定怎样生成或组织拓扑。它不应被描述成与 Graph、Runtime 并列的完整执行系统。

Deep Research 的执行仍属于普通 AgentRun，Swarm 的推进仍依赖 Graph；产品功能名并不另建执行 owner。

WorkHub：从协调会话接续指定委派

WorkHub 是处理用户委派的协调会话入口，也沿用“模型提出、Host 准入”的分工。它不另建一套 Agent 执行器。假设用户要求“继续此前委派的文档检查”，接续过程是：

  1. 用户要求先进入专用 Runtime Turn，协调模型据此提出接续操作；提案本身不提供用户权限。
  2. Host 回读已准入的用户内容，找回指定委派的来源，核对本次请求是否确实指向那份工作。
  3. Host 检查安全接续边界（safe-boundary），也就是必须能证明当前条件允许从指定位置继续。相关开关未启用或条件不足时，不猜测原工作已经安全结束，也不擅自重发。
  4. 条件成立，Host 才创建新的 Turn 承担后续工作。旧执行及其结果保持原记录，不会因此复活旧请求或抹去已发生的效果。

这个例子把“用户要继续什么”“模型提议什么”和“Host 可以接纳什么”分开。若操作回复丢失，重复请求仍须对应原来那次接续，不能碰巧继续后来另一场中断。

机制问题解析

问题 1。 Graph 与 child Session 分别拥有哪些状态？

解释。 Graph 拥有 schedule/topology/revision/claim/wake；child 的执行过程与终态仍由普通 Run/RuntimeEvent 记录。

问题 2。 系统重启后看到 running domain row，还必须核对什么？

解释。 冻结身份、admission、invocation opening/terminal、工具边界与 domain claim 等事实，不以单个状态字替代完整判断。

问题 3。 为什么 readiness 可以重算，而 claim/admission 不能任意重复创建？

解释。 readiness 是读侧推导；claim 是对指定意图与 exact execution 身份的条件持久提交，重复派发可能产生第二份效果。

问题 4。 supervisor wake 怎样回到普通 root Run？

解释。 已提交结果形成检查点与 durable wake，再由 Host 创建新的 root Turn/Run；不是复活旧模型请求或调用栈。

问题 5。 T7 开始后才从 Client arm G1，T7 的完成是否自动启动 G1？单纯重启能否启动从未承载的 Goal？

解释。 不会。T7 开始时的绑定没有 G1；后续承载 Turn 或合法 resume 才驱动它。恢复不会把仅 armed、从未承载的 Goal 当成已经开始的循环。

问题 6。 evaluator 返回 {"met":"false"} 与超时，当前分别怎样处理？为什么都不能当作可靠的测试结果？

解释。 字符串 flag 与超时都标为 evaluatorFailed，不计真实进展或停滞，仍可能在条件允许时继续。两者都不能证明真实测试结果，且 evaluator 只能评估近期对话文字，不能独立重跑测试。目标已失效时，旧评估也不能越过 control/checkpoint 检查。

问题 7。 三步 Plan 的测试失败，模型却把前两步标 completed、测试标 skipped，Plan 会怎样？如果 Run 先 failed，恢复后应继续旧 Run 吗？

解释。 在输入合法且 execution 仍 active 时，全部 completed/skipped 会使 Plan completed，不能推断测试通过。若 Run failed 时 Plan 仍 active，会进入 interrupted；合法 resume 通过新 Turn 继续，不复活旧 Run，也不撤销先前工具效果。

问题 8。 上述已获准修改与测试的 W1 曾显示 Ready，stop 分别赢在 claim 前、claim 后 admission 前、Edit 已执行后；哪两种仍能阻止 backend 启动？第三种能否抹去修改？

解释。 前两种由 expected revision 检查与 durable cancel 阻止开始；第三种只能停止并收敛已经执行的 child。已发生的修改仍要检查与处理，stop 不等于 rollback。
