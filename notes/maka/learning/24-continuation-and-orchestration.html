第 24 章｜计划（Plan）、目标（Goal）、定时任务（Scheduled Task）与任务图（Agent Graph）怎样继续工作

本章概览

核心问题：计划（Plan）获批、目标（Goal）未完、时钟到点或依赖完成后，什么事实允许系统继续工作？

关键概念：计划（Plan）：用户控制的工作流（Workflow）状态（State）；目标（Goal）：按评估与预算推进的结果要求；定时任务（Scheduled Task）：未来触发机会；任务图（Agent Graph）：依赖与调度状态（State）；认领（Claim）：绑定（Binding）一次确切执行的记录。

关系主线：各控制器维护继续工作的理由，经宿主（Host）准入（Admission）交给普通代理执行（AgentRun）；触发、启动、终态（Terminal State）与任务验收（Acceptance）不能互相替代。

前情回顾：先找到继续理由，再接回普通执行

第13章区分会话（Session） S1、工作轮次（Turn） T7、执行（Run）R7：长期归属相同，后续任务仍要有自己的工作身份（Work Identity）。第14章说明可读投影（Projection）不能反向裁定执行事实；界面没有完成结果，不等于可以重做。第18章进一步把终态（Terminal State）与未知工具（Tool）效果分开。第23章则让独立子任务（Child Task）交回有界结果，由父任务（Parent Task）继续判断。

本章把这些关系用于“下一项工作为什么可以开始”。计划（Plan）、目标（Goal）、定时任务（Scheduled Task）和任务图（Agent Graph）各自保存控制状态（State），由相应负责者（Owner）判断继续条件；宿主（Host）再核对确切工作身份（Work Identity）并准入（Admission）。已经开始的模型（Model）与工具（Tool）过程仍走普通代理执行（AgentRun），不需要为每一种触发重新实现一套循环。

核心路线

继续工作的四种触发

复杂智能代理（Agent）产品经常需要“以后继续工作”：

  • 用户批准计划（Plan）后继续；
  • 目标（Goal）还没完成时再尝试一轮；
  • 明天九点自动检查；
  • 等多个子任务（Child Task）完成后，让主代理（Main Agent）以监督者（Supervisor）角色重新审阅结果。

这些都可以口头叫作 继续执行（Continuation），但它们不是同一种机制。业务域（Domain）指负责某一类业务状态（State）的范围，例如计划（Plan）或定时任务（Scheduled Task），不指网络域名。每种继续执行（Continuation）都必须确定：

README 任务的四种后续需求

任务是：

检查 package.json 与 README.md，把 README 的测试步骤更新正确，运行测试；以后请用中文解释结果。

先固定文档支线的初态：README 写错测试入口 npm run check，package.json 实际提供 "test": "node --test"；函数正确，四项既有测试原本通过，工作范围是修改说明、检查结果并用中文报告。会话（Session） S1 中的 T7/R7 表示这项工作轮次（Turn）及其执行（Run）；G1、T8/R8、FC1、N1–N4、W1 都将在各自使用前定义。以下过程是教学情境与源码推演，不是新运行日志。

现在分别想象四种产品需求，分支之间不继承后文才增加的授权：

  1. 计划（Plan）：先把修改计划（Plan）展示给用户，用户批准后再编辑文件；
  2. 目标（Goal）：另切回第04章仍含 % 100 函数缺陷的初态，用户同时授权修复源码；根据测试失败继续修复，直到满足目标（Goal）或停止条件；
  3. 定时任务（Scheduled Task）：明天上午再检查 README 是否仍与项目配置一致；
  4. 任务图（Agent Graph）：让多个子代理（Subagent）分别检查 package.json 的测试脚本（Test Script）、README 当前测试步骤和平台差异，全部完成后再综合。

它们最后都会进入普通代理执行（AgentRun），但“允许创建下一轮”的理由不同。

四种控制状态（State）分别提供继续理由，汇入同一执行准入（Admission）；它们是并列的触发机制，不是四步固定流程。

这样做会马上遇到问题：

  • 计划（Plan）还没被用户批准，系统是否可以继续？
  • 目标（Goal） 评估器（Evaluator）的输出解析失败，是“完成”还是“未知”？
  • 定时任务（Scheduled Task）到点后进程崩溃，重启会不会触发两次？
  • 任务图（Agent Graph）的一个子代理（Subagent）失败，监督者（Supervisor）应等待、取消还是继续？
  • 已经开始的新执行（Run）与旧 running 记录之间怎样对应？

“下一轮再调用一次模型（Model）”只是执行动作，不是控制语义。每个业务域（Domain）必须拥有自己的状态（State）和合法触发条件。本章后文的目标（Goal）/任务图（Agent Graph）检查点（Checkpoint）是推进和恢复的控制检查点（Checkpoint）；第19章的上下文（Context）检查点（Checkpoint）则表示一段模型（Model）历史，两者保存的对象不同。

计划（Plan）：由用户控制的持久工作流（Durable Workflow）

计划（Plan）解决什么问题

有些修改需要先把步骤展示给用户，再等待批准。例如：

1. 读取 package.json 与 README.md
2. 修改 README 测试步骤
3. 运行测试

计划（Plan）保存的是工作流（Workflow）控制状态（State）。用户可以查看、批准、推进、取消或恢复它。

计划（Plan）批准没有证明什么

计划（Plan）不是“模型（Model）自己一直循环直到完成”。用户批准是关键触发（Trigger）。在批准并启动工作的路径中，新代理执行（AgentRun）执行计划（Plan）中的工作；批准保存的是工作流（Workflow）状态（State），真正修改与测试仍由执行（Run）落实。

目标（Goal）：由完成判断驱动的自主继续执行（Continuation）

目标（Goal）解决什么问题

目标（Goal）表达的是结果，例如“让 README 测试步骤正确且测试通过”。它不会自动扩大文件或工具（Tool）授权；若本次只获准改文档，源码中的错误仍需要按实际范围处理。保存目标（Goal）也不等于已经开始工作：客户端（Client）的 goal.arm 只建立目标（Goal）状态（State），等待后续工作轮次（Turn）承载它；它本身不启动模型（Model）。对已暂停的目标（Goal），用户也可以通过合法的 resume 恢复驱动。

工作模型（Model）和评估器（Evaluator）要分开理解。R7/R8 通过普通代理执行（AgentRun）调用 Read、Edit、Bash；评估器（Evaluator）是使用该会话（Session）模型（Model）配置的一次辅助模型调用（Model Query），没有工具（Tool），也不创建一个“评估代理执行（AgentRun）”。它判断收到的文本，不会自己重跑测试。因此，R7 的结果报告需要说明真实测试入口、输出和未完成项；独立调用评估模型（Model）并不自动获得独立验证。

目标（Goal）终态（Terminal State）与执行（Run）终态（Terminal State）不相等

某一次执行（Run）完成只说明这一轮代理执行（AgentRun）已到终态（Terminal State）。目标（Goal）可能仍未满足；反过来，目标（Goal）已取消也需要协调正在运行的执行（Run）。两个生命周期（Lifecycle）不能合并。

这描述正常完成判断的路线；当前实现对评估失败仍可能选择继续，不应把每次继续执行（Continuation）都解释成模型（Model）已经可靠证明“目标（Goal）未完成”。具体分支见目标（Goal）评估器（Evaluator）的失败策略。

核心问题解析

问题 1。 定时任务（Scheduled Task）显示 fired，为什么不能据此说 README 已经修好？

解释。 fired 说明触发和启动边界已经结算；还要等待随后执行（Run）的工具结果（Tool Result）和终态（Terminal State），并核对 README 与测试要求。执行（Run）正常结束本身也不能证明任务验收（Acceptance）通过。

问题 2。 一个执行（Run）已完成，目标（Goal）为什么仍可能继续？

解释。 执行（Run）终态（Terminal State）结束一次执行；目标（Goal）还要依自己的完成条件、评估和预算决定目标（Goal）状态（State）。

问题 3。 任务图（Agent Graph）中检查 package.json 的节点完成，主任务（Main Task）还缺什么？

解释。 还需核对其他依赖、已提交结果与综合结论，再完成修改和测试；节点终态（Terminal State）不能代替整个目标的完成。

问题 4。 重新打开桌面端（Desktop）为什么通常不是业务继续执行（Continuation）？

解释。 重连先恢复观察同一份事实，并不自动创建新的业务工作。

问题 5。 目标（Goal）已设置（Armed），但用户尚未提交后续工作轮次（Turn），能否认定测试修复已开始？评估器（Evaluator）能否自己运行测试？

解释。 不能。设置（Arm）保存目标（Goal），后续承载工作轮次（Turn）或合法恢复（Resume）才推动实际工作；评估器（Evaluator）只做无工具（Tool）文本判断，实际测试属于普通代理执行（AgentRun）的工具（Tool）执行。

问题 6。 计划（Plan）显示某个步骤已完成，为什么仍需要修改或测试证据？

解释。 计划（Plan）保存模型（Model）报告的工作流（Workflow）进度；实际修改与测试由普通工具（Tool）和执行（Run）落实，进度状态（State）不独立验证这些结果。

实现深化

这些控制器都需要处理状态（State）过期、重复触发和进程重启。已经启动的执行（Run）还可能留下 第18章所述的未知工具（Tool）效果，控制状态（State）恢复不能替它消除不确定性。

目标（Goal）评估器（Evaluator）的当前失败策略

从目标（Goal）设置（Arm）到驱动的承载关系

goal.arm 即使返回 active，也可能还没有任何目标（Goal）驱动的执行。宿主（Host）在普通工作轮次（Turn）开始前绑定（Binding）当时的控制租约（Control Lease），完成后才按这份绑定（Binding）结算；如果先开始 T7、再从客户端（Client）设置 G1，T7 不会被事后归入 G1，后续工作轮次（Turn）才承载它。恢复同样区分“已开始驱动”和“仅保存目标（Goal）”：重启不会让从未被工作轮次（Turn）承载的仅已设置的目标（Goal）自动开跑。

暂停后，客户端（Client）的 goal.control(resume) 会核对目标（Goal）身份（Identity）与修订（Revision），再恢复驱动意图；仍要经过普通顶层准入（Root Admission）。已经结束的模型调用（Model Query）不会复活，会话（Session）忙也不意味着可以越过准入（Admission）立即新开执行（Run）。

评估器（Evaluator）真正能看到什么

当前宿主（Host）经 SessionManager 取得运行时事件（Runtime Event）派生的 StoredMessage，再筛选最近六条角色（Role）为 user / assistant 的消息（Message），逐条截断后组成近期对话，再与目标条件（Goal Condition）一起交给评估器（Evaluator）。它没有直接拿到完整运行时事件（Runtime Event）或原始工具结果（Tool Result），也不能读文件、执行 Bash 来补证据。假如 assistant 只写“测试没问题”，评估器（Evaluator）获得的就是这份报告；它不会凭空知道测试入口是否错误、失败行是否被省略。

这是专门的目标（Goal）评估输入，不应与普通工作模型（Model）由运行时事件（Runtime Event）构造的模型服务历史（Provider History）混为一谈。当前辅助调用使用会话（Session）的连接与模型（Model）配置、输出上限为 1,024 词元（Token）；它有自己的调用记录，但不成为新的工作轮次（Turn）/执行（Run）。

为什么评估器（Evaluator）是关键边界

目标（Goal）是否继续由相应负责者（Owner）裁决；这项裁决权（Authority）不能交给任意模型（Model）字符串。负责者（Owner）需要检查评估器（Evaluator）结果的类型，并为未知结果设置预算和失败处理。Maka 拒绝非布尔标志字段（Flag）：字符串 "false" 与超时（Timeout）、调用错误或不可解析结果一样，进入 evaluatorFailed 的中性结果；采用 失败可继续（Fail-open）策略，允许在状态（State）、预算和准入（Admission）仍满足时继续。

当前实现有迭代（Iteration）上限，评估器（Evaluator）持续失败时仍可能继续多轮。检查布尔类型也不等于完整结构约束（Schema）校验：缺字段仍有默认值，额外字段也未全面拒绝，需逐项看合同（Contract）。

任务图（Agent Graph）从依赖图到持久调度

第二步：中间结果会推动动态调度修订（Schedule Revision）

智能代理（Agent）工作通常不能在开始前把所有步骤一次性穷举。N1 可能发现测试命令由另一个工作空间（Workspace）生成，N3 也可能证明平台差异其实不存在。此时根会话（Root Session）中的主代理（Main Agent）需要增加节点、替换旧路线、停止过时分支，或选定最终产物（Artifact）。

因此，Maka 的任务图（Agent Graph）不是“一次写死后只会向前跑”的静态有向无环图（DAG）。主代理（Main Agent）通过 update_agent_graph 提交一份结构化调度修订（Schedule Revision）；修订（Revision）描述要新增、替换、停止或采纳什么。它先进入持久控制面，成为可供恢复与审计读取的 持久意图（Durable Intent），而不是工具（Tool）一返回就直接等同于某个模型调用（Model Query）已经开始。

这里的持久性（Durability）应谨慎理解为“调度意图先形成持久事实（Durable Fact），恢复逻辑可以重新观察它”，不是脱离存储事务、认领（Claim）、恢复实现和实际测试后仍可宣称的“绝不会丢失”。

什么时候需要更强的工作流（Workflow）恢复

四类业务域（Domain）分别处理不同触发：计划（Plan）等合法批准，目标（Goal）消费评估与预算，定时任务（Scheduled Task）消费时间和火次（Fire），任务图（Agent Graph）消费依赖与结果。共同底层不是“不断调用模型（Model）”，而是先保存允许继续的理由，再由执行负责者（Owner）接纳确切工作。故障重试、观察（Observation）恢复和新的业务意图应分别命名；一套通用 resume(prompt) 无法自动补齐这些条件。

相邻领域的 Temporal 提供另一种恢复单位：工作流（Workflow）是可重放的控制逻辑，活动（Activity）是工作进程执行的动作单元。事件历史（History）记录工作流命令（Workflow Command）与活动（Activity）的结果；控制代码重放到已完成的活动（Activity）时复用历史（History）结果，未取得完成结果的活动（Activity）则有其等待/重试语义。它比一个火次认领（Fire Claim）管得更深入控制程序，但要求确定性命令与代码版本兼容；外部效果已发生、活动（Activity）完成回执未到时仍可能重复。可以在 Temporal 原理与失败例中继续追踪重放时的判断。

恢复单位决定机制选择：只要未来启动一次普通智能代理（Agent）工作，可用具有身份（Identity）与恢复规则的定时任务（Scheduled Task）；如果要跨多个服务、长时间等待并复用控制程序中的已完成结果，再考虑持久工作流（Workflow）。外层活动（Activity）包住整个智能代理（Agent）时，活动（Activity）重试可能重新做整段调查，所以内外两层必须分配重试预算和效果身份（Identity），不能让每层各自认为可以无限再试。涉及付款、发布或长期浏览器状态（State）时，更要回到第18章核效果回执，不能从定时器（Timer）或工作流（Workflow）名字直接推导安全。

还要定义包装器（Wrapper）怎样映射结果：智能代理（Agent）执行（Run）为 failed，既可能让活动（Activity）报失败，也可能作为 {status:failed} 的正常返回值被记录为活动（Activity） completed。只有前一种且重试政策允许时，才能继续讨论失败重试；后一种的控制重放会复用这个返回值。不能由执行（Run） failed 单独推断活动（Activity）没有完成记录，两种映射都不替原工具（Tool）消除效果未知。

变式一：恢复时只有火次认领（Fire Claim），没有执行身份（Execution Identity）。为了不漏任务，能否创建R9；如果已有R8，能否给同一认领（Claim）换R9？

参考答案

按当前实现，第一种失败结算，不在恢复中猜新身份（Identity）；第二种也不能换，绑定（Binding）相同值可以重复，不同值会冲突。产品若要改变“尚未绑定（Binding）就失败”的策略，需要显式定义新业务触发和授权/去重边界，而不是把改策略叫作透明恢复。已有R8还必须由其负责者（Owner）核对，避免制造第二份副作用。

变式二：fired已保存，R8的Edit出现outcome_unknown；现在改用外层工作流（Workflow）自动重试整个智能代理（Agent）。是否就能省去文件对账（Reconcile）？

不能。fired只证明触发/启动，未知工具（Tool）效果还在。外层重试可能创建新调用并重复已经发生的编辑；工作流（Workflow）复用的是已记录的完成结果，缺少完成回执的效果仍需资源方幂等或对账（Reconcile）。应先核原执行（Run）、工具（Tool）记录与当前文件，明确能复用什么、谁决定新尝试，再继续验收（Acceptance）。两层恢复合同不能互相当作对方已经处理过。

深度研究（Deep Research）与群体协作（Swarm）放在哪里

深度研究（Deep Research）

Maka 当前的深度研究（Deep Research）更接近受限会话模式（Session Mode）：执行仍由普通代理执行（AgentRun）承担，工具（Tool）白名单偏只读，并维护研究产物（Artifact）与检查清单（Checklist）。

群体协作（Swarm）

Maka 当前的群体协作（Swarm）更像任务图（Agent Graph）上层的薄策略：帮助决定怎样生成或组织拓扑（Topology）。它不应被描述成与任务图（Agent Graph）、运行时（Runtime）并列的完整执行系统。

深度研究（Deep Research）的执行仍属于普通代理执行（AgentRun），群体协作（Swarm）的推进仍依赖任务图（Agent Graph）；产品功能名并不另建执行负责者（Owner）。

WorkHub：从协调会话（Session）接续指定委派

WorkHub 是处理用户委派的协调会话（Session）入口，也沿用“模型（Model）提出、宿主（Host）准入（Admission）”的分工。它不另建一套智能代理（Agent）执行器（Executor）。假设用户要求“继续此前委派的文档检查”，接续过程是：

  1. 用户要求先进入专用运行时工作轮次（Runtime Turn），协调模型（Model）据此提出接续操作；提案本身不提供用户权限（Permission）。
  2. 宿主（Host）回读已准入（Admission）的用户内容，找回指定委派的来源，核对本次请求是否确实指向那份工作。
  3. 宿主（Host）检查安全接续边界（Safe Boundary），也就是必须能证明当前条件允许从指定位置继续。相关开关未启用或条件不足时，不猜测原工作已经安全结束，也不擅自重发。
  4. 条件成立，宿主（Host）才创建新的工作轮次（Turn）承担后续工作。旧执行（Run）及其结果保持原记录，不会因此复活旧请求或抹去已发生的效果。

这个例子把“用户要继续什么”“模型（Model）提议什么”和“宿主（Host）可以接纳什么”分开。若操作回复丢失，重复请求仍须对应原来那次接续，不能碰巧继续后来另一场中断。

机制问题解析

问题 1。 任务图（Agent Graph）与子会话（Child Session）分别拥有哪些状态（State）？

解释。 任务图（Agent Graph）拥有调度（Scheduling）/拓扑（Topology）/修订（Revision）/认领（Claim）/唤醒（Wake）；子代理（Subagent）的执行过程与终态（Terminal State）仍由普通执行（Run）/运行时事件（Runtime Event）记录。

问题 2。 系统重启后看到业务域（Domain）中标为 running 的记录，还必须核对什么？

解释。 冻结身份（Identity）、准入（Admission）、调用开始与终态（Invocation Opening / Terminal State）、工具（Tool）边界与业务域（Domain）认领（Claim）等事实，不以单个状态（State）字替代完整判断。

问题 3。 为什么就绪投影（Readiness Projection）可以重算，而认领（Claim）/准入（Admission）不能任意重复创建？

解释。 就绪投影（Readiness Projection）是读侧推导；认领（Claim）是对指定意图与确切执行身份（Exact Execution Identity）的条件持久提交，重复派发可能产生第二份效果。

问题 4。 监督唤醒（Supervisor Wake）怎样回到普通顶层执行（Root Run）？

解释。 已提交结果形成检查点（Checkpoint）与持久唤醒（Durable Wake），再由宿主（Host）创建新的顶层工作轮次（Root Turn）/执行（Run）；不是复活旧模型（Model）请求或调用栈。

问题 5。 T7 开始后才从客户端（Client）设置 G1，T7 的完成是否自动启动 G1？单纯重启能否启动从未承载的目标（Goal）？

解释。 不会。T7 开始时的绑定（Binding）没有 G1；后续承载工作轮次（Turn）或合法恢复（Resume）才驱动它。恢复不会把仅已设置（Armed）、从未承载的目标（Goal）当成已经开始的循环。

问题 6。 评估器（Evaluator）返回 {"met":"false"} 与超时，当前分别怎样处理？为什么都不能当作可靠的测试结果？

解释。 字符串标志字段（Flag）与超时都标为 evaluatorFailed，不计真实进展或停滞，仍可能在条件允许时继续。两者都不能证明真实测试结果，且评估器（Evaluator）只能评估近期对话文字，不能独立重跑测试。目标（Goal）已失效时，旧评估也不能越过控制状态（Control State）与检查点（Checkpoint）检查。

问题 7。 三步计划（Plan）的测试失败，模型（Model）却把前两步标 completed、测试标 skipped，计划（Plan）会怎样？如果执行（Run）先 failed，恢复后应继续旧执行（Run）吗？

解释。 在输入合法且计划执行（Plan Execution）仍为 active 时，全部 completed/skipped 会使计划（Plan） completed，不能推断测试通过。若执行（Run） failed 时计划（Plan）仍 active，会进入 interrupted；合法恢复（Resume）通过新工作轮次（Turn）继续，不复活旧执行（Run），也不撤销先前工具（Tool）效果。

问题 8。 上述已获准修改与测试的 W1 曾显示就绪（Ready），停止请求（Stop）分别赢在认领（Claim）前、认领（Claim）后准入（Admission）前、Edit 已执行后；哪两种仍能阻止执行后端（Agent Backend）启动？第三种能否抹去修改？

解释。 前两种由预期修订（Expected Revision）检查与持久取消（Durable Cancel）阻止开始；第三种只能停止并收敛已经执行的子代理（Subagent）。已发生的修改仍要检查与处理，停止（Stop）不等于回滚（Rollback）。
