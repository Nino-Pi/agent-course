第 60 章｜Codex 的机制与设计取舍

本章概览

核心问题：Codex 怎样连接工具执行（Tool Execution）、输入延续和子任务（Subtask），哪些责任划分值得借鉴？

关键概念：应用服务（App Server）：承接产品协议；会话（Session）：持有内核运行状态；工具路由（ToolRouter）：匹配声明与处理器；钩子（Hook）：介入执行前后处理；压缩（Compaction）：更新后续历史表示；记忆（Memory）：经整理与读取复用跨任务信息。

关系主线：客户端意图进入内核，工具结果（Tool Result）回到后续输入，子任务（Subtask）产物由父任务（Parent Task）消费；压缩（Compaction）和后台记忆各有接线条件，执行后拒绝不能回滚已发生效果（Effect）。

前情回顾：同一任务包含几种不同的状态

第29章将应用服务（App Server）的任务线程（Thread）、工作轮次（Turn）和过程项（Item）与内核会话（Session）区分：前者让客户端表达和观察工作，后者承载模型（Model）与工具（Tool）循环。第32章进一步解释工具计划（Tool Plan）：本步向模型（Model）声明哪些能力，要与调用回来时实际查找的执行对象对应。

第38章区分活跃模型历史（Model History）与保存的过程记录（Rollout）。压缩（Compaction）改变下一次请求使用的材料，但不自动证明旧细节已取回。第41章把记忆（Memory）、技能说明包（Skill）和子任务（Subtask）放到不同的消费链：长期信息要读取，方法正文要装载，子产物还要由父任务（Parent Task）验收（Acceptance）。

本章在一次代码修复中连接这四组关系。源码结论限于相应开源客户端路径；提供方（Provider）、功能开关（Feature Flag）和宿主（Host）接线可能改变实际行为。读图时关注当前信息由谁消费，不把产品名当成统一执行保证。

设计问题与实现范围

Codex 怎样从用户需求走到工具执行（Tool Execution）？压缩（Compaction）、记忆（Memory）与子任务（Subtask）分别改变哪些状态，哪些设计值得在相似约束下采用？

沿用四文件教学任务：package.json 定义 test: node --test，README 给出运行说明，测试规定非负整数秒应显示为 m:ss，src/duration.js 负责计算。用户允许修 README 与目标函数，要求保留已有内容、运行相关测试并用中文汇报；测试与配置只读。题设中的错误是 % 100 使 125 秒显示为 2:25，应为 2:05。

以下选择经过应用服务（App Server）的工作路径解释机制；这些文件与观察结果（Observation）是教学输入，没有在本章启动 Codex。内核、协议集成和特定客户端的部署行为分别判断。

模型调用（Model Query）、工具执行（Tool Execution）和观察结果（Observation）回写构成主循环，会话（Session）归属、展示、授权、窗口管理与长期信息围绕该循环提供不同合同。

机制总览

架构上，可以分成产品协议和执行内核两层。应用服务（App Server）用任务线程（Thread）、工作轮次（Turn）、过程项（Item）表达对话、一轮工作和过程中的消息或工具（Tool）事件；内核会话（Core Session）持有运行状态，处理输入、打断、批准和压缩（Compaction）。客户端读取过程，不应自己再运行一份工具（Tool）循环。

工具（Tool）方面，一个步骤（Step）的工具路由（ToolRouter）同时带着模型（Model）可见的工具声明（Tool Specification）和匹配的注册表（Registry）。调用回来以后还有真实的名称与输入检查、钩子（Hook）、处理器（Handler）；涉及执行权限（Permission）的工具（Tool）再由执行编排器处理批准（Approval）、环境权限（Permission）和沙箱（Sandbox）。一个参数模式（Schema）不能替代执行边界。

长会话（Session）要区分当前窗口和长期记忆（Long-Term Memory）。源码会按功能开关（Feature Flag）与提供方（Provider）能力选路：有的路径生成摘要（Summary）或压缩（Compaction）输出，窗口预算分支（TokenBudget）路径则安装新窗口，相关恢复（Recovery）扩展按条件提供。长期记忆（Long-Term Memory）另有旧过程记录（Rollout）提取、跨记录整合、摘要（Summary）注入与按需读取；不能把这些机制统称为一段聊天摘要（Summary）。

技能说明包（Skill）主要提供可发现、可读取的方法资料；这里的协作路径会创建真实子任务线程（Child Thread），并支持历史分叉、发消息或触发继续工作。这些责任边界用于定位消费者（Consumer），再按项目需要选择复杂度；机制存在不等于任务质量更好，仍应说明适用条件，并用任务和故障场景检验。

这些机制的共同连接点是实际消费者（Consumer）：模型（Model）请求消费工具说明（Tool Description）和输入材料，处理器（Handler）消费工具调用（Tool Call），父任务（Parent Task）消费子任务（Subtask）产物；只有真实经过的路径才支持相应结论。

组件与状态所有权

下面是依据工具调用（Tool Call）与模型输入（Model Input）路径简化的组件图。实线是调用或数据方向，虚线是可选扩展/后台信息进入请求；它不是完整部署图。

客户端经协议层进入会话（Session），再由模型（Model）与工具（Tool）循环推进工作。记忆（Memory）与子任务（Subtask）是有条件的扩展，主循环不以它们存在为前提。

关键箭头解释：

  • start 或 steer：新工作与给正在工作的智能代理（Agent）追加输入不同，应用服务（App Server）的 turn_start_inner 检查实际提交结果。
  • ToolRouter → 请求 和 模型 → ToolRouter：同一份计划连接工具声明（Tool Specification）与执行选择，便于检查两端是否一致。
  • handler → history：执行结果是后续行动的依据，图中不把命令发出当成任务完成。
  • Session → rollout：保存可定位记录；这条箭头本身不证明任意外部副作用与记录有原子事务。

边界条件：用户界面（User Interface，UI）的连接状态不能替代执行状态；模型（Model）看到工具（Tool）不能替代运行时（Runtime）允许效果（Effect）；子任务（Subtask）结果不能替代父任务（Parent Task）验收（Acceptance）。 精确路径和配置条件见前述机制章节。

从工具计划（Tool Plan）到一次效果（Effect）

图中的批准（Approval）/沙箱（Sandbox）是所选执行型处理器（Handler）的路径；不能据此说所有模型上下文协议（Model Context Protocol，MCP）工具（Tool）、提供方原生（Provider-native）或远端工具（Tool）共享完全相同的强制边界。已核对的实际消费者（Consumer）包括补丁执行的 execute_verified_patch。

E → O 表示效果（Effect）发生后才处理结果：后置钩子（PostToolUse Hook）在效果（Effect）之后，可以拒绝结果进入模型（Model），却不能撤销文件已经改变。需要防越界时，把许可判断放在效果（Effect）之前，并让实际执行环境限制它。

教学接口：将声明与执行绑定到同一身份

下面的 TypeScript 是教学设计，不是 Codex 官方应用编程接口（Application Programming Interface，API）或 Rust 类型的完整翻译。先读三组对象：ToolIdentity 识别工具（Tool）；StepToolPlan 同时保存本步声明与执行映射；ModelCall 带回工具身份（Tool Identity）、参数和调用标识。Executor 接收的权限（Permission）与取消信号来自可信运行环境。

随后看 dispatch 的三步：按当前计划查对象、解析参数、交给该对象执行。辅助函数的职责在代码后说明；这段接口没有实现存储与恢复（Recovery）控制，不能作为可直接部署的运行器。

// 一份身份同时服务模型声明与实际查找。
type ToolIdentity = { namespace: string; name: string };
type StepToolPlan = {
  advertised: Array<{ id: ToolIdentity; schema: object }>;
  executors: Map<string, Executor>;
};
// 执行对象接收真实上下文，不能由模型提供授权。
type Executor = {
  parse(raw: string): unknown;
  execute(input: unknown, context: ExecutionContext): Promise<Observation>;
};
type ExecutionContext = { permissions: object; signal: AbortSignal };
type Observation = { status: "ok" | "rejected" | "failed" | "unknown"; text: string };
type ModelCall = { identity: ToolIdentity; rawArguments: string; callId: string };

async function dispatch(plan: StepToolPlan, call: ModelCall) {
  // 只查当前步骤的映射；模型不能注入新的执行对象。
  const handler = lookup(plan.executors, call.identity);
  if (!handler) return observation("rejected", "unknown tool");
  // 参数合法不等于获准；实际权限仍由执行入口落实。
  const input = handler.parse(call.rawArguments);
  // pre hook、许可检查与真实 sandbox 仍须在具体执行路径落实。
  return handler.execute(input, executionContextFor(call));
}

ModelCall 固定调用身份、原始参数与调用标识（Call ID）callId。lookup 使用与建表相同的 namespace/name 编码查找当前计划中的处理器（Handler），不接受模型（Model）传入新的执行对象。executionContextFor 从受信运行状态提供当前权限（Permission）和取消信号，不能从 rawArguments 读取授权。

这段 dispatch 没有捕获 parse 的异常：解析失败会在 execute 之前向上传播，完整运行器才负责把它记录为拒绝结果。执行之后的异常还须结合处理器（Handler）的证据区分已知失败与未知效果（Unknown Effect），不能统一记成“没有产生效果”。运行器保存 callId 与结果，取消信号传入已开始执行的处理器（Handler）；动态工具（Dynamic Tool）更换时，当前步骤（Step）继续使用固定计划，新步骤（Step）才安装新计划。这里展开接口责任，没有实现所有提供方（Provider）、存储和沙箱（Sandbox）分支，因此不是可直接部署的完整运行器。

压缩（Compaction）选路与新历史安装

各分支最终都需要建立下一次请求可消费的状态，但产生该状态的方式不同。路径选择节点说明提供方（Provider）能力与客户端配置怎样共同影响压缩（Compaction）；公开压缩接口（Compaction API）不能代表所有 Codex 宿主（Host）的接线。

这张图只表达正常完成路径。窗口预算分支（TokenBudget）优先，其余为客户端摘要（Local Compaction）与流式远程压缩（Compaction）；客户端摘要（Local Compaction）仍会调用模型（Model），窗口预算分支（TokenBudget）的这条换窗路径则不请求摘要（Summary）。历史恢复（Recovery）扩展有装配条件，不能因窗口已切换就认定旧信息已经取回。完整走读见第38章。

失败路径：如果压缩（Compaction）调用自己已经超窗，客户端摘要（Local Compaction）实现会在仍有多项输入时删除最旧项后重试；无法继续缩减时报告错误。此时不能说“压缩（Compaction）工具返回了，所以任务安全继续”，需要区分失败、重试成本和删掉关键约束的风险。

验证方法是给后续任务加入必须使用 U1/U2 的检查，记录是否覆盖用户改动、是否按预期修复以及费用和延迟。只量词元（Token）减少无法证明压缩（Compaction）质量。测试代码存在同样不能代替真实模型（Model）的保真评估。

记忆、方法与独立工作分别由谁消费

记忆写入与后续读取

本地应用服务（App Server）在含输入的工作轮次（Turn）实际进入已启动状态（Started）且主环境就绪时调用后台入口；入口还看功能开关（Feature Flag）、根任务（Root Task）、临时运行（Ephemeral）、数据库（Database，DB）和额度等条件。第一阶段（Phase 1）从合格过程记录（Rollout）提取原始记忆与摘要（Summary），第二阶段（Phase 2）取得全局认领（Claim）后整合记忆工作区（Memory Workspace）。读取侧根据配置把有界摘要（Summary）加入上下文（Context），专门的列举、读取与搜索工具（List / Read / Search）还有独立开关。

这与当前长会话（Session）压缩（Compaction）的目标不同。压缩（Compaction）为了在这个窗口继续工作；记忆（Memory）为未来任务准备可复用信息。对于“以后用中文”，必须分别观察有没有写入、下次有没有读取、模型（Model）最终有没有遵循；后台任务启动不等于三者都已发生。

方法目录与实际正文

先有目录（Catalog）的名字和描述，再按可用包（Package）、资源归属环境（Authority）和资源身份读取正文。正文告诉智能代理（Agent）怎样做事，不能代替执行器（Executor）。读到了测试规范之后，还要看到实际测试调用与结果。

子任务（Subtask）的输入、消息与交付

这里的协作路径用 spawn 创建子任务线程（Child Thread），历史范围（History Scope）可以选择 none（不继承）、all（全部）或最近 N 个工作轮次（Turn）；本地此路径默认 all。它还区分仅入队模式 QueueOnly 的 send_message 与请求工作轮次（Turn）模式 TriggerTurn 的 followup_task。前者向普通空闲目标送材料，不要求新开工作；但任务线程（Thread）保留尚未结束的持久等待（Outstanding Durable Sleep）时也能触发新的普通工作轮次（Turn），不能概括为永远不唤醒。若两个子任务（Subtask）要改同一文件，还得单独设计工作副本（Working Copy）与合并策略；任务线程（Thread）独立不自动证明文件独立。

递进追问与参考答案

追问一：我看到参数模式（Schema），就能执行这个工具（Tool）吗？

不够。参数模式（Schema）是请求界面，运行时（Runtime）仍要按名称解析实际处理器（Handler）、校验输入、检查策略，并由真实执行环境落实许可。Codex 的同份工具路由（ToolRouter）方便连接两侧；它不自动证明每种外部工具（Tool）的动态绑定和权限（Permission）都经过相同路径。在参考接口中，未知身份由 lookup 查找失败后拒绝，坏参数在解析时抛错并由上层处理，权限（Permission）不足由具体执行入口拒绝；三者不会因为参数模式（Schema）曾出现而自动消失。

追问二：Codex 的压缩（Compaction）是不是“老消息都删掉，剩一段摘要（Summary）”？

这句话漏掉选路、保留消息、初始上下文（Initial Context）补回、提供方（Provider）表示和持久记录。客户端摘要（Local Compaction）是模型（Model）生成的摘要（Summary）加有预算（Budget）的用户消息（User Message）；远程压缩（Remote Compaction）路径会处理返回的压缩历史与输出（Compacted History / Output）；窗口预算分支（TokenBudget）换窗并不在该函数里请求摘要（Summary）。活跃输入改变不等于持久记录被同样删除，更不等于它使用 Maka 的精确前缀检查点（Exact-prefix Checkpoint）合同。

追问三：记忆（Memory）已有两阶段，是不是就比向量数据库更先进？

不能这样比较。两阶段描述写入与整合，向量检索描述一种读取方法，它们属于不同设计轴。本次本地搜索（Local Search）读到的是文本匹配与分页。该任务应比较事实正确率、过期信息误用、召回成本与实际任务成功率；源码结构不能提供这些结果。

追问四：子代理（Subagent）默认继承所有历史，你会照搬吗？

本题选择的 spawn 路径默认 all，也支持 none 或最近 N 个工作轮次（Turn）。若子任务（Subtask）只有“检查 README 测试说明”，显式给文件、约束与结果格式可能更节省成本；若任务强依赖前文协商，全历史可能减少漏传。设计建议和产品默认值必须分开。还需单独限制工具（Tool）、预算（Budget）和文件写入。

追问五：记忆（Memory）整合（Consolidation）是内部任务，可以直接认定安全隔离吗？

不能。这里的整合执行者（Worker）对父托管配置（Managed Profile）设置记忆根目录（Memory Root）写入和禁网；父禁用或外部配置（Disabled / External Profile）有保留分支。内部执行者（Worker）也可能读取或写入敏感内容，实际边界须按环境配置解释。

用“约束出现 → 增加机制 → 引入代价 → 设计验证”组织采用判断。

两种失败的完整处理

压缩（Compaction）失败。 沿用 U1/U2 的修复任务，客户端摘要（Local Compaction）请求自身超窗，尚未取得可用替换历史（Replacement History）。该分支可以在仍有多项输入时移除最旧项后有界重试；因此要分别保留压缩（Compaction）失败、已花费用和可能丢失的约束。不能因为发起过压缩（Compaction）就报告完成，也不能假设候选文字已经安装。仍不能形成合法输入时，明确停止或按实际路径允许的方式缩减；恢复（Recovery）后修改 README 仍需当前文件内容与用户新增开头的约束。

后置钩子（PostToolUse Hook）拒绝结果。 假设补丁执行器（Patch Executor）已修改 README，后置钩子（PostToolUse Hook）拒绝将该结果交给模型（Model）。后置拒绝影响结果消费，不撤销已发生的文件效果（Effect）。后续处理区分执行器（Executor）记录、文件当前内容与模型（Model）可见的观察结果（Observation）：读取可靠结果或当前文件差异（Diff），修复结果传递问题；不能把“模型没看见成功”当成重做补丁的理由。更强的自动恢复（Recovery）取决于选定处理器（Handler）与存储合同，不能只由后置钩子（PostToolUse Hook）名称推出。

这两类故障分别发生在输入重建和效果（Effect）之后。它们都可能让下一步模型（Model）缺少材料，但前者不等同于文件已改，后者也不等同于文件已回滚。
