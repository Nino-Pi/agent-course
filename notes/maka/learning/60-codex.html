第 60 章｜Codex 的机制与设计取舍

本章概览

核心问题：Codex 怎样连接工具执行、输入延续和子任务，哪些责任划分值得借鉴？

关键概念：App-server（应用服务）：承接产品协议；Session（会话）：持有内核运行状态；ToolRouter（工具路由）：匹配声明与处理器；Hook（钩子）：介入执行前后处理；压缩：更新后续历史表示；Memory（记忆）：经整理与读取复用跨任务信息。

关系主线：客户端意图进入内核，工具结果回到后续输入，子任务产物由父任务消费；压缩和后台记忆各有接线条件，执行后拒绝不能回滚已发生效果。

前置：整体架构、Tool 契约、压缩、Memory、Skills 与子任务。

机制详解：运行与生命周期 → 工具与权限 → 上下文与压缩 → Memory、Skills 与子任务。

以下机制限定到 Codex 开源客户端的相应路径；provider、feature 和宿主接线不同，行为也可能不同。

设计问题与实现范围

Codex 怎样从用户需求走到工具执行？压缩、Memory 与子任务分别改变哪些状态，哪些设计值得在相似约束下采用？

以下以经过 app-server 的工作路径为例：用户要求修正 README 测试步骤、修复时间格式化函数、运行相关测试并用中文汇报。coding agent 内核、app-server 集成和特定客户端的部署行为分别判断。

模型调用、工具执行和观察回写构成主循环，会话归属、展示、授权、窗口管理与长期信息围绕该循环提供不同合同。

机制总览

架构上，我把它分成产品协议和执行内核两层。app-server 用 Thread、Turn、Item 表达对话、一轮工作和过程中的消息或工具事件；core Session 持有运行状态，处理输入、打断、批准和压缩。客户端读取过程，不应自己再运行一份工具循环。

工具方面，一个 step 的 ToolRouter 同时带着模型可见的 specs 和匹配的 registry。调用回来以后还有真实的名称与输入检查、hook、handler；涉及执行权限的工具再由执行编排器处理 approval、环境权限和 sandbox。一个 schema 不能替代执行边界。

长会话要区分当前窗口和长期 Memory。源码会按 feature 与 provider 能力选路：有的路径生成摘要或压缩输出，TokenBudget 路径则安装新窗口，相关恢复扩展按条件提供。长期 Memory 另有旧 rollout 提取、跨记录整合、摘要注入与按需读取；不能把这些机制统称为一段聊天摘要。

Skills 主要提供可发现、可读取的方法资料；这里的协作路径会创建真实 child Thread，并支持历史分叉、发消息或触发继续工作。我会借鉴这些责任边界，再按项目需要选择复杂度；机制存在不等于效果质量更好，仍应说明适用条件，并用任务和故障场景检验。

这些机制的共同连接点是实际消费者：模型请求消费工具说明和输入材料，handler 消费工具调用，父任务消费子任务产物；只有真实经过的路径才支持相应结论。

组件与状态所有权

下面是依据工具调用与模型输入路径简化的组件图。实线是调用或数据方向，虚线是可选扩展/后台信息进入请求；它不是完整部署图。

客户端经协议层进入 Session，再由模型与工具循环推进工作。Memory 与 child 是有条件的扩展，主循环不以它们存在为前提。

关键箭头解释：

  • start 或 steer：新工作与给正在工作的 Agent 追加输入不同，app-server 的 turn_start_inner 检查实际提交结果。
  • ToolRouter → 请求 和 模型 → ToolRouter：同一份计划连接工具声明与执行选择，便于检查两端是否一致。
  • handler → history：执行结果是后续行动的依据，图中不把命令发出当成任务完成。
  • Session → rollout：保存可定位记录；这条箭头本身不证明任意外部副作用与记录有原子事务。

边界条件：UI 的连接状态不能替代执行状态；模型看到工具不能替代 runtime 允许效果；子任务结果不能替代父任务验收。 精确路径和配置条件见前述机制章节。

从工具计划到一次效果

图中的 approval/sandbox 是所选执行型 handler 的路径；不能据此说所有 MCP、provider-native 或远端工具共享完全相同的强制边界。已核对的实际 consumer 包括补丁执行的 execute_verified_patch。

E → O 表示效果发生后才处理结果：post hook 在效果之后，可以拒绝结果进入模型，却不能撤销文件已经改变。需要防越界时，把许可判断放在效果之前，并让实际执行环境限制它。

教学接口：将声明与执行绑定到同一身份

以下 TypeScript 是教学设计，非 Codex 官方 API，也不是原 Rust 类型的完整翻译。它只要求声明与执行引用同一工具身份：

type ToolIdentity = { namespace: string; name: string };
type StepToolPlan = {
  advertised: Array<{ id: ToolIdentity; schema: object }>;
  executors: Map<string, Executor>;
};
type Executor = {
  parse(raw: string): unknown;
  execute(input: unknown, context: ExecutionContext): Promise<Observation>;
};
type ExecutionContext = { permissions: object; signal: AbortSignal };
type Observation = { status: "ok" | "rejected" | "failed" | "unknown"; text: string };
type ModelCall = { identity: ToolIdentity; rawArguments: string; callId: string };

async function dispatch(plan: StepToolPlan, call: ModelCall) {
  const handler = lookup(plan.executors, call.identity);
  if (!handler) return observation("rejected", "unknown tool");
  const input = handler.parse(call.rawArguments);
  // pre hook、许可检查与真实 sandbox 仍须在具体执行路径落实。
  return handler.execute(input, executionContextFor(call));
}

ModelCall 固定调用身份、原始参数与 callId。lookup 使用与建表相同的 namespace/name 编码查找当前计划中的 handler，不接受模型传入新的执行对象。executionContextFor 从受信运行状态提供当前权限和取消信号，不能从 rawArguments 读取授权。

解析失败发生在 execute 之前，可返回 rejected；执行后的异常则必须结合 handler 证据区分 failed 与 unknown，不能一律标记没有效果。运行器保存 callId 与结果，取消信号传入已开始执行的 handler；动态工具更换时，当前 step 继续使用固定计划，新 step 才安装新计划。这里展开接口责任，没有实现所有 provider、存储和 sandbox 分支，因此不是可直接部署的完整运行器。

压缩选路与新历史安装

各分支最终都需要建立下一次请求可消费的状态，但产生该状态的方式不同。路径选择节点说明 provider 能力与客户端配置怎样共同影响压缩；公开 Compaction API 不能代表所有 Codex Host 的接线。

这张图只表达正常完成路径。TokenBudget 优先，其余为客户端摘要与流式远程压缩；客户端摘要仍会调用模型，TokenBudget 的这条换窗路径则不请求摘要。历史恢复扩展有装配条件，不能因窗口已切换就认定旧信息已经取回。完整走读见第38章。

教学输入是以下历史片段，内容与标号都不是一次真实 Codex 运行日志：

表 1 / Table 1 · 用具体消息走一遍
当前信息下一个阶段为什么可能需要
U1：修 README 和格式化函数，用中文说明用户目标与表达约束

正常路径：先确定本次分支，以 local 为例，由压缩任务组织 summarization 输入并请求模型；随后构造有预算的用户消息与摘要，并处理初始上下文补回；安装 replacement 后继续请求模型。这里不是承诺每个字段逐字保留，而是说明应在验证时检查哪些信息仍可用。

教学候选摘要可以是：“目标是修正 README 与时间格式化；125 秒的预期结果为 2:05；验证入口 npm test；保留 README 用户新增开头；尚未完成修复后的回归。”这段摘要由教材编写，不是 Codex 的固定格式或模型实测输出。

失败路径：如果压缩调用自己已经超窗，local 压缩实现会在仍有多项输入时删除最旧项后重试；无法继续缩减时报告错误。此时不能说“压缩工具返回了，所以任务安全继续”，需要区分失败、重试成本和删掉关键约束的风险。

验证方法是给后续任务加入必须使用 U1/U2 的检查，记录是否覆盖用户改动、是否按预期修复以及费用和延迟。只量 token 减少无法证明压缩质量。测试代码存在同样不能代替真实模型的保真评估。

Memory 与 Skills、子任务放在哪里

Memory 主链。 本地 app-server 在含输入的 Turn 确实 started 且主环境就绪时调用后台入口；入口还看 feature、root、ephemeral、DB 和额度等条件。Phase 1 从合格 rollout 提取原始记忆与摘要，Phase 2 取得全局 claim 后整合 memory workspace。读取侧根据配置把有界 summary 加入上下文，专门 list/read/search 等工具还有独立开关。

这与当前长会话压缩的目标不同。压缩为了在这个窗口继续工作；Memory 为未来任务准备可复用信息。对于“以后用中文”，必须分别观察有没有写入、下次有没有读取、模型最终有没有遵循；后台任务启动不等于三者都已发生。

Skills。 先有 catalog 的名字和描述，再按可用 package、authority 和资源身份读取正文。正文告诉 Agent 怎样做事，不能代替执行器。读到了测试规范之后，还要看到实际测试调用与结果。

子任务。 这里的协作路径的 spawn 创建 child Thread，历史参数可以是 none/all/最近 N turns；本地此路径默认 all。它还区分 QueueOnly 的 send_message 与 TriggerTurn 的 followup_task。前者向普通空闲目标送材料，不要求新开工作；但 Thread 保留 outstanding durable sleep 时也能触发新的普通 Turn，不能概括为永远不唤醒。若两个 child 要改同一文件，还得单独设计工作副本与合并策略；Thread 独立不自动证明文件独立。

递进追问与参考答案

追问一：我看到工具 schema，就能执行这个工具吗？

不够。schema 是请求界面，runtime 仍要按名称解析实际 handler、校验输入、检查策略，并由真实执行环境落实许可。Codex 的同份 ToolRouter 方便连接两侧；它不自动证明每种外部工具的动态绑定和权限都经过相同路径。在参考接口中，未知身份由 lookup 拒绝，坏参数在解析时拒绝，权限不足由具体执行入口拒绝；三者不会因为 schema 曾出现而自动消失。

追问二：Codex 的压缩是不是“老消息都删掉，剩一段摘要”？

这句话漏掉选路、保留消息、初始上下文补回、provider 表示和持久记录。local 是模型摘要加有预算的用户消息；remote 路径会处理返回的 compacted history/output；TokenBudget 换窗并不在该函数里请求摘要。活跃输入改变不等于持久记录被同样删除，更不等于它使用 Maka 的 exact-prefix checkpoint 合同。

追问三：Memory 已有两阶段，是不是就比向量数据库更先进？

不能这样比较。两阶段描述写入与整合，向量检索描述一种读取方法，它们属于不同设计轴。本次 local search 读到的是文本匹配与分页。该任务应比较事实正确率、过期信息误用、召回成本与实际任务成功率；源码结构不能提供这些结果。

追问四：子代理默认继承所有历史，你会照搬吗？

本题选择的 spawn 路径默认 all，也支持 none/N。若子任务只有“检查 README 测试说明”，显式给文件、约束与结果格式可能更节省成本；若任务强依赖前文协商，全历史可能减少漏传。设计建议和产品默认值必须分开。还需单独限制工具、预算和文件写入。

追问五：Memory consolidation 是内部任务，可以直接认定安全隔离吗？

不能。这里的整合 worker 对父 Managed profile 设置 memory root 写入和禁网；父 Disabled/External profile 有保留分支。内部 worker 也可能读取或写入敏感内容，实际边界须按环境配置解释。

可选设计值得采用的约束代价与验证

用“约束出现 → 增加机制 → 引入代价 → 设计验证”组织采用判断。

两种失败的完整处理

压缩失败。 沿用 U1/U2 的修复任务，local 压缩请求自身超窗，尚未取得可用 replacement。该分支可以在仍有多项输入时移除最旧项后有界重试；因此要分别保留压缩失败、已花费用和可能丢失的约束。不能因为发起过压缩就报告完成，也不能假设候选文字已经安装。仍不能形成合法输入时，明确停止或按实际路径允许的方式缩减；恢复后修改 README 仍需当前文件观察和用户新增开头的约束。

post hook 拒绝结果。 假设补丁执行者已修改 README，后置 hook 拒绝将该结果交给模型。后置拒绝影响结果消费，不撤销已发生的文件效果。后续处理区分执行器记录、文件当前内容与模型可见观察：读取可靠结果或当前 diff，修复结果传递问题；不能把“模型没看见成功”当成重做补丁的理由。更强的自动恢复取决于选定 handler 与存储合同，不能只由 post hook 名称推出。

这两类故障分别发生在输入重建和效果之后。它们都可能让下一步模型缺少材料，但前者不等同于文件已改，后者也不等同于文件已回滚。
