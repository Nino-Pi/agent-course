第 35 章｜沙箱（Sandbox）与文件执行边界（Filesystem Boundary）

本章概览

核心问题：一条规则说“禁止访问”，怎样判断它是否真正约束了进程？写入后丢失回复，又该怎样理解失败？

关键概念：沙箱（Sandbox）约束进程可访问的资源；文件工作进程（Filesystem Worker）执行具体读写；文件身份（File Identity）用设备号与对象号确认目标；文件描述符（File Descriptor，fd）指向已打开对象；效果未知（Unknown Effect）表示调用方无法确认完整结果。

关系主线：先分清应用判断、操作系统限制和资源结果，再沿同一文件说明规则组合与写入顺序，最后把已有测试放回它们真正覆盖的位置。

前情回顾：允许、执行与知道结果

第17章区分权限（Permission）与沙箱（Sandbox）：前者判断某项请求是否获准，后者把访问限制交给实际执行环境。第18章又区分效果（Effect）与观察结果（Observation）：文件已经变化，调用方仍可能因为回复丢失而收到失败。

本章把这两组区别放在一起。学习时始终问三件事：谁拒绝了请求、文件实际变没变、调用方凭什么知道？ 以下沿用已有的本地文件与回环网络案例，不包含模型（Model）参与。先读允许条件，再读拒绝与回复丢失，才能判断每种结果支持什么结论。

1. 一次文件访问要经过哪三层判断

这里使用 macOS 的进程限制机制 Seatbelt。宿主（Host）生成策略，再启动负责文件操作的工作进程（Worker）。应用层拒绝发生在进程启动前；操作系统（Operating System，OS）拒绝发生在进程访问资源时；写入后回复丢失又发生在结果返回路径。三者都可能表现为“调用失败”，但对应的文件状态不同。

2. 先看允许场景，再判断拒绝来自哪里

原生冒烟测试（Native Smoke Test）实际启动 Seatbelt 和文件工作进程（Filesystem Worker），检查基本路径能否运行。已有两份测试共 13 项通过、0 跳过，覆盖工作区（Workspace）写入、祖先目录与文件正文的区别、临时目录别名、工作区外写入拒绝、精确授权（Exact Grant）不开放相邻路径、显式拒绝（Deny），以及真实创建、删除和内容搜索。

这组结果里，拒绝位置仍然不同。文件工作进程（Filesystem Worker）的越界路径可在客户端（Client）检查权限配置（Permission Profile）时被挡住；直接在 Seatbelt 中运行命令解释器（Shell）的越界写入，则由受限进程所在的操作系统（OS）拒绝。用例名字写“沙箱拒绝”，不能代替对发生位置的判断。标准权限配置（Permission Profile）还允许写工作区（Workspace）的 .codex，不能预设所有元数据目录都受保护。

网络检查尤其需要正对照（Positive Control）。原有网络冒烟测试（Network Smoke Test）只尝试连接回环网络（Loopback）的9端口，并检查非零退出码（Exit Code）。如果那里没有服务，连接同样失败。失败现象本身不能区分“策略阻止”与“目标不可用”。 下一节使用同一活跃的超文本传输协议（Hypertext Transfer Protocol，HTTP）服务，把这个条件固定下来。

3. 规则组合：单项拒绝为什么仍可能漏掉文件

已有探针（Probe）先创建固定测试样本（Fixture），再启动本地超文本传输协议（HTTP）服务。它调用 SandboxManager.transform 与 MacosSeatbeltBackend，记录启动参数（Arguments，argv）及 Seatbelt 沙箱配置语言（SBPL）策略文本。网络只访问该回环服务，文件也都是案例自有数据。

表 3 / Table 3 · 3. 规则组合：单项拒绝为什么仍可能漏掉文件
改变的条件已有观察结果（Observation）可以怎样解释
允许读取固定样本（Fixture）读到预定字符串程序、目标与读取路径可用
对同一样本增加精确拒绝（Exact Deny）受限进程读取失败这组动态授权（Dynamic Grant）的排除生效
再把该目录加入可信运行依赖可读根（Runtime-readable Root）Core canReadPath=false，操作系统（OS）读取却成功额外授权（Grant）没有继承同一拒绝（Deny）
同一活跃服务，网络开启（Network Enabled）返回指定正文，服务计数变为1连接路径与服务本身可用
同一服务，网络受限（Network Restricted）连接失败，服务计数仍为1超文本传输协议（HTTP）处理器没有收到这次请求，不能用“无人监听”解释

第三行为什么与第二行不同？先用一个局部集合模型（Set Model）解释。设动态可读路径集合为 AAA，应排除的路径为 DDD，另外为启动依赖开放的路径为 RRR。在这个已测组合中，动态授权（Dynamic Grant）先得到 A∖DA\setminus DA∖D，额外规则又独立提供 RRR：

Pexample=(A∖D)∪R.\mathcal{P}_{\mathrm{example}}=(A\setminus D)\cup R.Pexample​=(A∖D)∪R.

对样本文件 fff，即使 f∈Df\in Df∈D，只要 f∈Rf\in Rf∈R，仍有：

f∉A∖D,f∈(A∖D)∪R.f\notin A\setminus D, \qquad f\in (A\setminus D)\cup R.f∈/A∖D,f∈(A∖D)∪R.

普通规则说“目录可读，但排除这个文件”；另一条规则又说“依赖目录可读”，却没有带上相同排除。两条放在一起，就把样本重新纳入可访问集合。这是本组规则的集合表示，不是完整操作系统策略的通用公式。

实现中，buildReadableRootsPolicy() 对动态允许项排除拒绝项，而 buildRuntimeRootsPolicy() 另建运行依赖允许项。后者覆盖同一路径时，产生上述缺口。探针（Probe）把实际 osReadSucceeded 写入JavaScript对象表示法（JavaScript Object Notation，JSON）结果；脚本退出码（Exit Code）为0只表示探针完成，不表示被测限制全部成立。

本例由脚本向可信宿主（Host）提供的路径上下文（Path Context）手工加入自有辅助目录。它证明这组编译输入的组合问题，没有证明模型（Model）能修改产品中的 pathContext，也没有经带类型的工作进程（Worker）接口完成任意读取。启动依赖为什么需要额外授权（Grant）、应用检查如何限制真实操作，仍要沿各自实现判断；不能把这一个交集推广到所有路径。

4. 文件写入：核对对象，再核对回执（Receipt）

这一节保持真实工作进程（Worker）执行文件操作，分别改变目标身份与返回时序。先看已有结果，再解释为什么实现需要相应顺序。

表 4 / Table 4 · 4. 文件写入：核对对象，再核对回执（Receipt）
时序（Timeline）已有观察结果（Observation）文件效果（File Effect）
原目标不存在，执行器（Executor）捕获 missing 后启动创建成功，传入身份为 missing文件包含第一份样本文本
目标处于当前权限配置（Permission Profile）之外sandbox_boundary_required，启动次数不增加没有进行这次写入

真实写入成功并返回，包装器（Wrapper）丢弃回复ToolOutcomeUnknownError文件已经是新文本，调用失败没有回滚它

共 3 次真实工作进程启动（Worker Launch）。第二行在启动前拒绝，不是第四次受限进程运行。这里使用真实文件执行器（Filesystem Executor）、FilesystemWorkerClient、默认 SandboxManager、启动描述（Launch Spec）、进程运行器（Process Runner）及编译出的工作进程（Worker）。

为什么先捕获文件身份（File Identity），再等待写锁（Write Lock）

写锁（Write Lock）让参与同一锁协议的工作按顺序执行，但等待期间，文件路径（Path）仍可能被其他操作替换。filesystem-executor.ts 在等待前捕获 T0 身份快照（Identity Snapshot），目的是固定请求原先接受的对象。若等到获得锁后才记录身份，替换后的B就会被误当成最初目标。

写入请求还需明确选择身份条件。missing 表示原目标应不存在，独占创建（Exclusive Create）会拒绝等待期间出现的新文件；unchecked 则明确放弃这项身份比较。后者不能被解释为已经检查通过。

为什么先打开，再比较同一个句柄

下面摘出 openStableTarget 的已有对象分支。先读整体顺序：打开时不截断文件；在同一文件描述符（File Descriptor，fd）上读取元数据；对象不匹配就关闭并报错。代码依赖外层函数与类型，不能单独运行，中文注释用于说明其职责。

// 打开时保留原字节；尚未开始覆盖。
const handle = await openExistingNoTruncate(input.path);
// 对已打开对象取元数据，不再按路径另查一次。
const metadata = await handle.stat({ bigint: true });
if (
  String(metadata.dev) !== input.approvedIdentity.dev ||
  String(metadata.ino) !== input.approvedIdentity.ino
) {
  await handle.close();
  throw pathChanged('The approved filesystem target changed before execution.');
}
return handle;

随后写入函数 writeThroughHandle 才在同一文件描述符（File Descriptor，fd）上截断并从位置0写入。若先用会截断文件的打开方式，再检查对象，发现错误时原字节可能已经被清空；如果检查后又按路径（Path）重新打开，也会重新出现目标被替换的窗口。

这项保证保护文件身份（File Identity）。同一索引节点（inode）中的内容仍可能被其他进程改写，因而它不等于比较上次读取的内容版本（Content Version），也不能单凭它声称整个文件替换具有事务原子性（Transactional Atomicity）。写入中途磁盘错误还可能留下截断或部分内容，实现会对相应错误保留效果未知（Unknown Effect）。

为什么写入成功还会收到失败

探针（Probe）在真实工作进程（Worker）成功后，由包装器（Wrapper）向 runProcess 调用方注入回复丢失。底层文件已经改变，上层却拿不到完整回执（Receipt）。因此调用失败不能证明效果（Effect）未发生，也不能自动成为重复写入的理由。

失败分类也要区分位置。spawn_failed 表示这次工作进程（Worker）没有启动；worker_io_incomplete 属于可能产生效果（Effect）但回执（Receipt）不完整的情况。取消（Cancellation；此分支标识为 aborted）则还要看是否已派发（Dispatched）：classifyFailedMutationOutcome 只在 dispatched=true 的取消分支返回未知（Unknown）。所有错误统一写“未执行”会抹掉这些区别。

本例的路径替换与回复丢失均有确定的注入时点。它没有执行操作系统强杀（OS Kill）、断电或宿主崩溃（Host Crash），也没有走完整工具运行时（Tool Runtime）的T1/T2记录或批准界面（Approval UI）。

6. 从结果推导有范围的结论

问题一：Core 返回拒绝（Deny），足以保证受限进程读不到文件吗？

不足以。本章规则组合反例中，动态授权（Dynamic Grant）排除了样本，额外运行依赖授权（Grant）却重新允许。需要检查实际最终策略及受限进程结果，不能用一个应用函数替所有层作保证。

问题二：文件身份（File Identity）相同，是否可以沿用旧内容的检查结论？

不能。设备号与索引节点号（inode）确认的是对象；内容版本（Content Version）可能已经变化。若下一步依赖旧内容，还要核对所依赖的字节或资源版本条件。

问题三：写后丢回复的调用失败，为什么不能直接重试（Retry）？

已有观察显示文件已是新文本。重复执行可能再次产生效果（Effect），或覆盖后来的变化；先回读原操作与资源现态，再判断是否还欠工作。效果未知（Unknown Effect）是调用方知识的限制，不是“文件没有改变”的同义词。

已有结果支持允许场景中的实际访问、具体边界的拒绝，以及写入与回执（Receipt）分离这三类判断。它们没有覆盖真实模型（Model）、完整批准流程、完整宿主T1/T2或断电。后续第45章再讨论宿主恢复（Host Recovery）；本章先把一次文件操作的边界与观察位置讲清。
