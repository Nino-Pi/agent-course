第 35 章｜沙箱与文件执行边界

本章概览

核心问题：Maka 的文件与网络限制实际在哪里拒绝访问，写入后丢失回复又怎样分类？

关键概念：Seatbelt：本章 macOS 进程限制后端；文件执行子进程：承接受控文件操作；T0 身份：排队前接受的文件对象；fd（文件描述符）：已打开对象的句柄；未知效果：写入可能发生但回执不完整；规则组合：多条允许与拒绝的共同结果。

关系主线：沿已有探针核对策略、进程访问和文件字节，区分启动前拒绝、真实写入与回复丢失，并用允许项重叠的反例说明组合边界。

前置：第17章权限与隔离、第18章未知效果。沿用两章的区别：权限规则表达允许范围，执行边界实际限制访问，结果记录说明调用方知道了什么。本章用已有文件与本地网络探针逐层检查这三件事，已有执行记录不含模型参与。

Seatbelt 是这里使用的 macOS 进程限制机制。文件 worker 是负责实际文件操作的子进程；它由宿主启动，因此“请求被应用拒绝”和“已启动的进程被 OS 拒绝”发生在不同位置。第 3 节先用允许访问的样本确认探针能运行，再改变规则；第 4 节保留真实写入，只改变回复是否送达。

下面是 macOS Seatbelt 与文件 worker 的已有本地案例，使用与所说明实现匹配的编译产物，不含模型或 Desktop。结果只覆盖这些场景，不能直接推广到其他平台或后续实现。

本机进程由 Maka 生成的 Seatbelt 限制。外层执行环境若先阻止进程启动、测试目录访问或本机回环网络（loopback）连接，尚未到达被测策略；它与应用边界拒绝、OS 拒绝、写入后回复丢失是不同失败位置。改变限制后的结果不能替代原场景。

文件样本均为案例自有数据，不读取个人凭据，也不访问外网。第 3 节的网络探针使用活跃的 loopback HTTP 服务，以允许访问的正对照确认目标和连接本身可用；它补足第 2 节原有网络 smoke 的限制。

2. 原生执行与限制测试

两份原生冒烟测试（native smoke，用于检查基本路径能否运行）实际启动 Seatbelt 和文件 worker，覆盖 workspace 写入、祖先目录与文件内容的区分、临时目录别名、工作区外写入拒绝、exact 扩边不开放相邻路径、显式 deny，以及真实 worker 的创建、删除和 grep。已有运行结果为 13 项通过、0 跳过。标准 profile 允许 workspace 的 .codex 写入，不能预设所有元数据目录都受到保护。

这些断言也有层次：worker的outside path可以在client的profile检查时被拒绝，未必已经由OS拒绝；Seatbelt直接shell写入的outside拒绝则确实来自受限子进程。一个用例标题不能代替拒绝位置。

官方网络smoke连接loopback的9端口并只检查非零退出。端口没有服务也会失败，所以单独看这条断言，不足以证明是network policy拦截。下一节的已有记录使用活跃服务提供正对照。

可以把该组合按同一个样本文件读一遍：普通动态规则说“允许这个目录，但排除该文件”，额外的运行依赖规则又说“允许这个目录”，第二条没有带上同一排除条件。在这个已测组合里，文件便仍处于 OS 的允许范围。Core 的单次判断返回 false，只说明应用规则拒绝它，不能替另一份最终策略作保证。这也解释了为何需要同时记录应用判断与实际读取结果。

这个探针向**可信宿主提供的路径上下文 pathContext**手工加入一个自有 helper 目录。它证明编译器对这种输入组合的限制，没有证明模型能修改实际产品的 pathContext，也没有利用带类型的 worker 操作执行任意读取。worker 启动依赖为何需要额外 grant、应用检查怎样限制操作，必须继续沿实现核对。其他基础 allow/deny 交集需逐项检查，不能从这个组合推到所有路径。

4. 把文件写入追到真实worker和响应

文件身份与失败分类的实现解释

先区分路径、对象和内容：路径是用来寻找文件的名字；inode 是文件系统中的对象编号，通常与设备编号 dev 一起识别对象；内容是该对象当前保存的字节。把名字从对象 A 改为指向对象 B，与在对象 A 内改写字节，是两种不同变化。这里的 T0 捕获前一种身份，不能据此判断后一种内容版本是否仍和上次 Read 相同。

filesystem-executor.ts 在等写锁前捕获 T0，是为了固定排队前接受的文件对象。等锁后才取身份，会把等待期间换来的对象当成原目标。

filesystem-worker/client.ts 要求写操作显式提供 identity。missing 要求原目标不存在，并以独占创建防止覆盖新出现的文件；unchecked 则明确放弃这项身份比较。

file-stable-write.ts::openStableTarget 先不截断地 open，再对同一 fd 执行 fstat 比较，最后写入，从而避免“尚未确认是原文件就先清空它”。这些检查约束对象身份，不保证同一 inode 内的字节从未被其他进程修改。

filesystem-authority.ts::classifyFailedMutationOutcome 再按失败时点分类：spawn_failed 表示这次 worker 没有启动；worker_io_incomplete 表示没有完整回执，须保留效果可能已发生的情况。

5. 用合同测试补齐确定性的失败分支

另一组定向合同测试覆盖确定性失败分支，不依赖模型；已有记录为 171 项通过、0 跳过。

这些测试混合了纯 policy 函数、fake runner、真实临时文件、进程生命周期和确定性 race 注入。其中，filesystem-mutation-outcome 直接注入 worker 错误，检查 Host 分类；filesystem-stable-write 交换临时文件路径，检查字节落在哪个 inode；第 2 节的 smoke 则直接启动真实 Seatbelt 和 worker。

通过某组断言，只回答了它明确检查的情境；Linux/Windows 后端、其他文件系统竞态和外部服务效果需要各自的检查。

6. 已有结果能够支持什么

已有结果形成三条不同结论：允许场景中进程确实读到固定字节或服务正文；拒绝场景中具体边界阻止本次访问或 worker 启动；unknown 场景中真实写入已经发生，但调用方没有完整回复。规则组合反例又说明，Core 的 deny 与 OS profile 的实际允许集合可能不一致。测试数量不替代这些发生位置和后置状态。

本实验没有运行真实模型、approval UI 或完整 Host 的 T1/T2，也没有模拟断电。Host 恢复实验见 第45章，未知效果的处理见 第18章。
