第 55 章｜设计记忆的写入与读取

本章概览

核心问题：跨会话偏好和经验怎样保存、更新与撤回，才能在适用的新任务中正确使用？

关键概念：来源：信息由谁声明或观察；Scope（范围）：条目适用的用户或项目；有效性：规则是否过时或撤回；候选检索：找出待筛选条目；注入：把选中内容加入请求；采用：模型实际据此回答或行动。

关系主线：写链决定条目怎样提交和更新，读链依次检索、筛选、注入并观察使用；查不到、读取失败和未获准读取不同，撤回也不能改写已经发出的请求。

前置：第20章、第53章。第20章已经把“保存了偏好、下一次取回、进入请求、实际使用”分成四步；第53章解释怎样组装本次输入。本章沿这条链增加一个问题：用户先设全局偏好，再增加局部例外，之后撤回例外，旧条目究竟该怎样变化？

下面的完整读写链是教学方案。Maka Local Memory 与 Atomic LTM 是不同系统；Atomic 的查询能力不等于默认 Agent recall 已接通。

1. 原题与约束

用户希望 Agent 跨会话记住偏好和项目经验。你怎么设计 Memory？信息过时、冲突或越来越多时怎么办？

用户明确偏好、可观测项目事实与失败经验具有不同的可信来源和更新方式。scope、查看与撤回权限、有效时间共同决定写读合同。

最小场景只有同一用户U和两个工作区A、B。用户先说“全局使用中文”，之后说“A用英文，其他仍中文”，最后撤回A的例外。问题不在于记住两个语言名称，而在于判断第二句话增加了什么、第三句话撤回了什么。

为便于沿表追踪，把三次声明分别标为T7、T20、T22；它们是对话位置标签，不是超时或版本。全局规则的条目叫M1，A的例外叫M2；B没有单独例外。后文每次读取都发生在新会话，用户不会再次提示语言。写入失败或读取不可用时，系统还必须如实说明状态。

2. 参考方案

我先把当前会话历史和长期 Memory 分开。小规模偏好可以用透明的文件或条目保存，关键是写入、范围、读取和注入闭环。写入时保留原话来源、适用范围和有效状态；更新前找相关旧信息，区分新增例外、替代旧规则和冲突。读取时根据当前用户、工作区、权限和任务选择候选，过滤已撤回或不适用项，再按预算进入本次请求。检索排序不能代替范围判断，向量数据库也不是第一版必需。信息变多以后再根据实际漏检问题选择关键词、语义或混合检索。最后分别验证存得对、找得到、注入正确，以及模型实际用了；经验记忆还需要验证适用条件，防止把一次失败的猜测传播到所有任务。

把方案放回两条偏好就能看清顺序：T20先保留M1并新增M2；A的新请求优先采用M2，B仍采用M1；T22撤回M2后，A重新跟随M1。先把这个正常过程闭合，再增加并发、检索遗漏和存储故障，便能知道每一种机制在补哪个缺口。

3. Memory 的写链与读链

Store 两侧分别是写入和读取；“检索到了”和“用对了”之间还有筛选、注入与模型行为。

不变量：未获准的信息不能跨 scope 读取；撤回后的新读取不再将该内容纳入有效集合；写入失败不能确认已保存；来自模型的推测不能默认为用户声明。撤回不能追溯修改已捕获的输入或已经发出的请求，后者需要另行取消或重建。

4. 最小条目与读取契约

先看T20新增的M2。scope解释它只对谁生效，source保留它为什么存在，status决定它当前能否被采用。以下是教学数据结构，不是 Maka Atomic Item schema：

MemoryItem = {
    "id": "M2",
    "kind": "explicit_preference",
    "key": "explanation_language",
    "value": "en",
    "scope": {"user": "U", "workspace": "A"},
    "source": {"turn": "T20", "text": "A 用英文，其他项目仍中文"},
    "status": "active",
    "version": 1
}

读取时最关键的判断是：全局中文与A英文同时出现，究竟选谁？本题规定明确的工作区例外优先于全局规则；同一优先级若有不同值，就保留冲突。下面将这一步写完整。输入 candidates 只包含同一语言偏好key的、已获准读取的候选；全局条目的scope没有workspace字段。本函数只做适用性选择，存储访问与权限检查在它之前，预算选择和请求组装在它之后。

def choose_language(candidates, user, workspace):
    # 只保留对当前用户和工作区仍有效的候选。
    applicable = [item for item in candidates
                  if item["status"] == "active"
                  and item["scope"]["user"] == user
                  and item["scope"].get("workspace") in (None, workspace)]
    # 明确的工作区例外优先；没有例外时才使用全局层。
    specific = [item for item in applicable
                if item["scope"].get("workspace") == workspace]
    selected = specific or applicable
    if not selected:
        return {"status": "no_match", "items": []}
    # 同一优先级的不同值保留为冲突，并把来源条目一并返回。
    values = {item["value"] for item in selected}
    if len(values) != 1:
        return {"status": "conflict", "items": selected}
    return {"status": "found", "value": next(iter(values)),
            "items": selected}

specific or applicable 表示有工作区例外就使用这一层，否则使用全局层；values收集这一层所有不同语言值。返回完整条目使来源跟着选择结果保留下来，不能在此只剩一个失去出处的“en”。按本题数据，参考结果为：

候选与当前工作区选择结果原因
M1=全局中文、M2=A英文；当前Afound，en，保留M2A的明确例外优先

这一步不能发现没有被召回的M2，也不证明模型已经使用结果。version则服务另一处问题：需要防并发覆盖时，它参与写链的条件更新；串行单写者文件可以采用更简单的规则。

完整读取接口还要区分选择结果与访问失败。Store异常由接口层归类为unavailable，不能先改成空列表再调用上面的函数；有适用候选却因预算无法注入，也应报告预算缺口。no_match只表示当前取得的候选中没有适用项，是否检索完整仍须另查，不能据此断言用户从未提供信息。写入请求重发需要可辨认的操作或receipt；提交成功与响应丢失也要有明确查询方式。

表中的背景是按前述读取政策选入的值，最终回答还需核对模型是否遵循。T23另增加一次“全局改日文”的声明，用它检验T22是否真的撤回了例外。

T22 若把 M2 改为“A 固定中文”，当时的回答也可能正确，却没表达“跟随全局”。到 T23 才暴露错误。这是为什么 Memory 更新要用多步状态轨迹评估，不能只检查一次最终回答。

6. 失败走读与恢复边界

提取错误。 把“同事喜欢英文”记成用户偏好。需要原文主体与来源检查；无法确定时保留为候选或不写入，不应依靠检索排名修正错误写入。

检索遗漏。 只找到 M1，没有找到 A 的例外 M2。模型忠实使用 M1 仍然会答错。记录候选和过滤结果，才能把召回失败与模型不遵循分开。

并发覆盖。 两个更新器都基于版本 1 写入，后者覆盖前者。若场景允许多写者，使用条件版本提交或串行 owner；版本冲突应回读重判，不能把旧提取决定无条件再提交。

模型没用。 输入已注入 en，最终仍输出中文。写链和读链可能都正确；错误发生在行为阶段，应看实际请求与输出，不能把保存成功作为证据替代。

7. 递进追问

为什么不用聊天历史充当 Memory？

历史保留发生过什么，Memory 为未来任务选择适用信息。完整历史有大量无关内容，也包含已过时规则。两者可以互相引用，但需要不同的读取与生命周期策略。

必须使用向量数据库吗？

几条语言偏好按 key 和 scope 读取就足够。信息多且用户措辞变化导致漏检时，比较语义/混合检索；引入向量索引之后仍要处理权限、时间、冲突和有效状态。相关性不能替代有效性。

Memory 很大，怎样“压缩”？

先区分去重、语义合并、过期归档和本次请求的有界选择。整理长期信息必须保留例外、来源和可撤回性；只把全部条目总结成一段话可能丢掉更新依据。请求预算问题则先通过选择/回读处理，旧任务上下文压缩见 第54章。

可以自动从工具失败里学经验吗？

可设计另一条经验 admission：记录环境、实际失败、行动、验证和适用条件，把归纳当可撤回建议。Maka Atomic 的既有 user-authored evidence 边界不能直接推广到所有工具结果；扩展属于新设计，不能写成已经接线。

用户删除 Memory 后，旧备份和摘要怎么办？

先确认删除承诺涉及哪些派生数据。逻辑撤回、搜索过滤、缓存失效、备份保留和物理删除是不同范围。若产品承诺删除，必须追踪相关副本；只从 UI 隐藏一个条目不足以证明全部删除。

9. 固定注入与主动检索的完整对照

沿用 T20 后的状态：M1 是 global=zh，M2 是 A=en，新会话的当前工作区为 A，用户没有重述语言偏好。

固定注入： Host 在新请求组装时读取有效条目，先按用户与工作区过滤，再按“明确工作区例外优先”选择 M2，将带来源的 en 背景加入请求。若错把 B 的条目注入，错误在 scope 选择；若正确注入 en 却输出中文，错误在行为阶段。固定注入减少了模型主动搜索的必要，但增加常驻输入。

主动检索： 初始请求只提供 Memory 查找入口，模型判断本任务需要历史偏好后查询 explanation_language，读取 M1/M2，按同一适用性政策选 M2，再形成回答。模型不发查询会导致漏用；返回候选仍需筛选，不能将 top-1 排名当优先级。

到 T22，M2 已撤回，两个方案的新读取都应排除它并采用 M1。到 T23，global 改为 ja，两者都应得到 ja。若读取服务不可用，则返回 unavailable；不能把基础设施错误解释为用户没有偏好。已经捕获 en 的旧请求不会被 Store 修改追溯改写。
