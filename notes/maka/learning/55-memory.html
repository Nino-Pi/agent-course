第 55 章｜记忆（Memory）的写入、读取与撤回（Retraction）

本章概览

核心问题：用户先给全局偏好，再加局部例外，后来撤回（Retraction）例外，系统怎样记得准确、用得合适？

关键概念：来源（Provenance）说明信息依据；作用域（Scope）限定适用对象；有效性（Validity）决定当前能否使用；检索（Retrieval）先找候选，选择（Selection）再处理范围与冲突（Conflict）；撤回（Retraction）改变后续读取的有效集合。

关系主线：写链保存可追溯条目，读链选择适用内容并加入模型输入（Model Input），实际使用（Use）还要从回答与行动观察。存储（Store）成功、找到候选与使用正确各有证据。

前情回顾：保存了什么，与本次实际看见什么

第20章区分保存、取回、组装和使用；第21章又说明，提交（Commit）成功与回执（Receipt）返回并非同一时点。读取开关关闭不删除条目，数据库查询存在也不证明模型（Model）已经发起查询。

第53章负责本次模型输入（Model Input）的组装，第54章解释旧任务材料怎样缩减或回读（Readback）。本章处理另一类变化：为未来任务保留的记忆（Memory）怎样更新。把旧对话压短，并不会自动理解“新增例外”与“撤回（Retraction）例外”的区别。

下面完整读写链是教学方案。本地记忆笔记（Local Memory）与条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）是 Maka 的两个不同系统；本章自拟的用户与工作区（Workspace）条目及选择（Selection）算法，不能当成它们的统一默认实现。

先给同一用户的四次声明明确身份（Identity）

本题只有同一用户U、工作区（Workspace）A/B和一个偏好键 explanation_language。每次读取发生在新会话（Session），用户不会重复语言要求。任务是让适用偏好进入本次请求，并检查回答是否遵循；不允许从“同事喜欢英文”推断U喜欢英文。

三次原始声明依次为“全局使用中文”“A用英文，其他仍中文”“A跟随全局”。将它们标为T7、T20、T22；这些是对话位置标签，不是时间上限、存储（Store）版本或产品执行编号。全局条目是M1，A的例外是M2，B没有例外。最后另加T23“全局改日文”，检验前面的撤回（Retraction）是否正确。

两条链：先保存依据，再为新任务选择（Selection）

用户明确偏好、可观测项目事实与失败经验有不同来源（Provenance）。最小实现可以使用透明文件或条目存储（Store）；向量数据库（Vector Database）不是几条偏好的必要起点。更先要确定谁可查看与撤回（Retraction）、条目适用哪里、怎样处理失效和写入冲突（Conflict）。

图的左半边围绕提交（Commit）决定新增、更新、撤回（Retraction）或保留冲突（Conflict）；右半边为当前任务做检索（Retrieval）、筛选、预算（Budget）选择（Selection）与请求组装。箭头到模型请求（Model Request）之后才进入行为：条目进入输入（Input）仍不保证实际使用（Use）。

写入时保留原话来源（Provenance）及允许用途，读取相关旧信息后再决定怎样更新。读入时先遵守用户与工作区（Workspace）的授权（Authorization），再按有效性（Validity）、作用域（Scope）和任务选择（Selection）。检索（Retrieval）排名回答“可能相关”，不能替代这些判断。

几条不变量（Invariant）约束整条链：未获准内容不能跨作用域（Scope）泄露；已撤回（Retraction）的条目不进入后续读取的有效集合；写入失败不能确认保存；模型（Model）推测不能伪装成用户声明。已经捕获或发出的模型输入（Model Input）不会被存储（Store）更新追溯改写，若要改变它还须另行取消（Cancellation）或重新组装。

最小条目：来源（Provenance）、作用域（Scope）与有效性（Validity）

T20新增的M2如下。scope约束适用对象，source保存声明来源（Provenance），status决定这份条目当前能否参与选择（Selection）。这是教学数据结构，不是条目化长期记忆（Atomic LTM）的条目结构（Schema）：

MemoryItem = {
    "id": "M2",
    "kind": "explicit_preference",
    "key": "explanation_language",
    "value": "en",
    "scope": {"user": "U", "workspace": "A"},
    "source": {"turn": "T20", "text": "A 用英文，其他项目仍中文"},
    "status": "active",
    "version": 1
}

M1使用同一偏好键，值为 zh，作用域（Scope）只有 user: U、没有 workspace字段；来源（Provenance）是T7声明。T22保留M2的历史（History）及撤回（Retraction）依据，将 status改为 inactive。保留历史（History）是为了能解释更新，不表示它仍有效。

本例用 active/inactive表达有效性（Validity）。真实合同若另有生效时间或期限，还须在候选读取时检查相应字段；下面的函数并没有实现所有时间规则。version则服务并发更新：它能参与条件提交（Conditional Commit），不能替系统判断两句话是否语义冲突（Conflict）。

从相关候选到适用集合，再判断同层冲突（Conflict）

先声明函数的输入合同：candidates是同一偏好键、已经获准读取的候选；用户与工作区（Workspace）已明确，本例只取A或B。存储（Store）访问和权限（Permission）检查发生在它之前，预算（Budget）选择（Selection）与请求组装发生在它之后。

可以用三组有限集合看清关系。CCC是已取得候选，A(u,w)A(u,w)A(u,w)保留仍有效、属于用户uuu且作用域（Scope）为全局或当前工作区（Workspace）www的条目；W(u,w)W(u,w)W(u,w)是其中明确指定www的例外。最终要比较的集合为：

这不是把两个层次一起投票。先按本题事先规定的“明确工作区（Workspace）例外优先”选择（Selection）层次，再比较这一层的值。SSS为空时没有适用候选；其中值的集合只有一个元素时可给出语言，否则保留冲突（Conflict）。相同层次的重复同值可以同时保留来源（Provenance），不同值不能只靠检索（Retrieval）排名裁决。

下面代码按“适用筛选→例外层→空集/冲突（Conflict）/唯一值”展开。返回条目本身，让来源（Provenance）留在结果中；它不是返回一个失去依据的 en：

def choose_language(candidates, user, workspace):
    # 只保留对当前用户和工作区仍有效的候选。
    applicable = [item for item in candidates
                  if item["status"] == "active"
                  and item["scope"]["user"] == user
                  and item["scope"].get("workspace") in (None, workspace)]
    # 明确的工作区例外优先；没有例外时才使用全局层。
    specific = [item for item in applicable
                if item["scope"].get("workspace") == workspace]
    selected = specific or applicable
    if not selected:
        return {"status": "no_match", "items": []}
    # 同一优先级的不同值保留为冲突，并把来源条目一并返回。
    values = {item["value"] for item in selected}
    if len(values) != 1:
        return {"status": "conflict", "items": selected}
    return {"status": "found", "value": next(iter(values)),
            "items": selected}

specific or applicable对应上面的分段定义；values收集所选层次的不同值。返回的 found只说明选定规则得到了一个值，conflict保留不能裁决的同层条目，no_match只描述本次候选集合。按给定数据可得到完整结果：

函数不会凭空找回没有被检索（Retrieval）到的M2，也没有检查模型（Model）行为。把各层职责说清楚，才能解释下面的失败。

空候选、无权限（Permission）与不可用不能合并

存储（Store）异常由访问接口（Interface）返回 unavailable，不能先转成空列表再调用选择（Selection）函数。未获准读取应按权限（Permission）合同拒绝；有适用内容却因预算（Budget）无法加入输入（Input），也应报告这一缺口。

no_match不证明用户从未提供偏好：检索（Retrieval）可能漏掉例外，过滤也可能排除了所有当前候选。写入请求重发需要可识别的操作身份（Operation Identity）或回执（Receipt）；提交（Commit）成功而返回丢失时，先查询原操作，不应据此再造一条偏好。

表内结果来自前述选择（Selection）规则，是完整给定的教学过程，没有运行模型（Model）。新请求选入 ja之后，仍需看实际回答是否使用；不能由存储（Store）状态代替这一步。

这也解释了T23为什么必要：若T22错误地新建“A固定中文”，它与“跟随全局”在T22输出（Output）相同，在T23才分叉。记忆（Memory）更新需要多步状态（State）变化来检查，不只评价某一时点的语言。

失败走读：四种不同的修正位置

提取（Extraction）错误。 把“同事喜欢英文”写成用户偏好，错误发生在主体与来源（Provenance）判断。保留原话；不能确定时留作候选或不写入，不能等检索（Retrieval）排名补救。

检索（Retrieval）遗漏。 A请求只取回M1，漏掉M2。模型（Model）忠实使用M1也可能答错；保留候选与过滤结果，才能把召回（Recall）不足和不遵循输入（Input）分开。

并发覆盖（Concurrent Overwrite）。 两个更新器都基于版本1写入，后提交者覆盖先前变化。多写者可以采用条件版本提交（Conditional Commit）或串行负责者（Owner）；冲突（Conflict）时回读（Readback）并重判，不能无条件重交旧决定。串行单写者文件可以使用更简单的规则。

模型（Model）没有使用。 本次输入（Input）已有带来源（Provenance）的 en，回答却仍为中文。写链与读链可能正确，错误在实际使用（Use）；应检查真实请求与输出（Output），不再重复证明“数据库有条目”。

固定读入与主动检索（Retrieval）的完整对照

沿用T20之后：M1为全局中文、M2为A英文，新会话（Session）的工作区（Workspace）是A，用户不再重述偏好。两种方案使用同一条目、授权（Authorization）与优先规则，只改变谁发起读取。

固定读入。 宿主（Host）在新请求组装时读取有效条目，按用户及工作区（Workspace）筛选，以明确例外优先选M2，再把带来源（Provenance）的 en加入模型输入（Model Input）。错放B的条目是作用域（Scope）错误；选入 en却输出（Output）中文则是行为错误。它减少主动搜索需要，也增加常驻输入（Input）。

主动检索（Retrieval）。 初始请求只提供记忆（Memory）查找入口。模型（Model）认为需要历史（History）偏好时查询 explanation_language，取得M1/M2，再按同一规则选择（Selection）M2并回答。不发查询会漏用，返回候选仍要筛选；前一名 top-1不能替代例外优先规则。

到T22，两个方案的新读取都应排除M2；T23改全局后都应得到 ja。存储（Store）不可用时返回 unavailable，不能解释成“没有偏好”。已捕获 en的旧请求仍保留原内容，更新存储（Store）不会追溯改写它。

放回Maka时，哪些是已有机制，哪些仍是设计

本地记忆笔记（Local Memory）的正文筛选会检查条目活动状态（Active Status）、安全解析与会话作用域（Session Scope）；其工作区作用域（Workspace Scope）并不等同于本题按A/B项目键做选择（Selection）。第20/21章已经用独立状态根（State Root）解释实验隔离，本题的U/A/B字段不能自动赋予产品同一合同。

条目化长期记忆（Atomic LTM）已有结构化写链与存储查询接口（Interface），但在所核普通运行时（Runtime）/宿主（Host）主链中，没有把该查询接成模型（Model）主动召回（Recall）。因此本节“主动检索（Retrieval）”是完整设计选项，不能用查询接口存在宣布默认接线完成。

自动经验提取（Experience Extraction）还需另外的准入（Admission）合同。Maka已核的证据投影只接受稳定、用户撰写的文本：并非任意工具（Tool）失败都能直接变成这条写链的用户依据。扩展到经验学习时要明确环境、实际失败、行动请求（Action）、验证（Verification）和适用条件，将归纳当可撤回（Retraction）的建议；这属于新设计。

为什么不直接使用聊天历史（History）？

历史（History）保留发生过什么，记忆（Memory）为未来任务保留适用信息。旧对话还有无关内容和失效规则；两者可相互引用，但读取与生命周期（Lifecycle）合同不同。

必须使用向量数据库（Vector Database）吗？

少量语言偏好按键与作用域（Scope）读取已经足够。确有措辞变化导致漏检时，再比较语义检索（Semantic Retrieval）或混合检索（Hybrid Retrieval）；向量索引（Vector Index）仍不替代权限（Permission）、时间、冲突（Conflict）和有效性（Validity）。

记忆（Memory）变大后，怎样压缩？

区分去重（Deduplication）、语义合并（Semantic Merge）、过期归档（Archiving）和本次请求的有界选择（Selection）。整理长期记忆（Long-Term Memory）要保留例外、来源（Provenance）和可撤回性（Retractability）；只总结成一段话可能丢失更新依据。当前输入（Input）的预算（Budget）先用选择（Selection）与回读（Readback）解决，旧任务上下文压缩（Context Compaction）另见第54章。

能自动从工具（Tool）失败中学习吗？

可以设计另一条经验准入（Admission）链，但不能把一次失败的猜测推广到所有任务。保留环境、行动请求（Action）、真实失败、验证（Verification）与条件，允许后续修正或撤回（Retraction）；不要把它写成Maka现有用户证据写链已经接受所有工具（Tool）结果。

删除记忆（Memory）后，旧备份与摘要（Summary）怎么办？

先说明删除承诺包含哪些副本。逻辑撤回（Retraction）、检索（Retrieval）过滤、缓存失效（Cache Invalidation）、备份保留与物理删除（Physical Deletion）是不同范围。若承诺删除，就要追踪相应派生数据；用户界面（User Interface，UI）隐藏条目不能证明所有副本已经删除。
