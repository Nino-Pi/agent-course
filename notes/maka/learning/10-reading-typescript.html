第 10 章｜Python 与 TypeScript 控制流（Control Flow）对照

本章概览

核心问题：读到 TypeScript 的类型与异步语法，怎样判断程序检查了什么、何时继续，以及谁真正处理了结果？

关键概念：静态类型（Static Type）描述允许的数据；运行时检查（Runtime Check）判断实际值；判别联合（Discriminated Union）按标签区分字段；异步结果（Promise）与消费确认（Acknowledgment，ack）分别表达操作结果和事件（Event）交接进度。

关系主线：先读数据形状，再读分支与等待，最后追到实际消费者（Consumer）。类型、控制顺序和持久化（Persistence）各回答不同问题，需要逐项建立依据。

前情回顾：把“返回以后”读得更精确

第02章的Python最小阅读卡已经解释对象、方法调用、列表（List）和字典（Dictionary）。代理循环（Agent Loop）的基本顺序是：模型调用（Model Query）返回行动请求（Action），执行器（Executor）执行，再把观察结果（Observation）加入消息列表（Message List）。只要调用是同步的，“返回以后继续下一句”就足以理解那段程序。

后续Maka源码还包含等待存储、逐个产出事件（Event）等操作。这时看见函数调用，不一定说明操作已经完成；看见某个类型名，也不说明数据经过检查。本章用三件小事建立读法：检查角色（Role）字符串、区分摘要规划结果、等待保存并交接事件（Event）。摘要与事件（Event）的完整机制将在第19、14章展开，这里先给理解片段所需的背景，不要求提前掌握整个系统。

本章是按需阅读的语言桥。熟悉相关语法的读者可以继续第11章，遇到具体控制顺序再回查。以下明确标注的真实代码摘自Maka（Apache-2.0）；源码中的标识符和注释保留原文，中文框架解释放在代码前后。

静态类型（Static Type）与运行时检查（Runtime Check）分别保证什么？

假设模型（Model）返回一份准备读取文件的参数。写成Python的类型标注（Type Annotation），或TypeScript的 input: ReadInput，都可以帮助作者发现类型使用错误；但磁盘或网络送来的实际内容，仍可能缺字段、用错字段类型，甚至根本不是对象。程序中声明“这里需要什么”，与实际检查“拿到的是什么”，是两步。

表 1 / Table 1 · 静态类型（Static Type）与运行时检查（Runtime Check）分别保证什么？
写法或概念对阅读有什么帮助不应据此推导什么
静态类型（Static Type），如 ReadInput描述读取文件所需参数的形状外部输入已经通过检查
未知类型（Unknown Type），即 unknown要求使用前先缩小允许范围，不能直接假定字段存在这个值一定有问题或无法使用
类型断言（Type Assertion），如 value as ReadInput要求检查器按作者指定的类型理解表达式程序已经转换或验证实际数据
运行时检查（Runtime Check），如字符串判断执行时根据当前值决定通过或拒绝已经检查本函数没有覆盖的其他条件

运行时事件（Runtime Event）是描述用户输入、模型响应或工具结果等情况的记录，其中角色（Role）标明这份记录在模型（Model）所读历史中的类别，而不是精确的作者身份。下面只检查角色（Role），不检查完整记录。代码可以先按三块读：列出允许值、建立对应类型、写出实际判断。

真实片段来自 packages/core/src/runtime-event.ts 的角色（Role）类型与检查函数：

export const RUNTIME_EVENT_ROLES = ['user', 'model', 'tool', 'system'] as const;
export type RuntimeEventRole = (typeof RUNTIME_EVENT_ROLES)[number];

export function isRuntimeEventRole(value: unknown): value is RuntimeEventRole {
  return typeof value === 'string' && (RUNTIME_EVENT_ROLES as readonly string[]).includes(value);
}

第一行的 as const 保留四个字面值（Literal）；第二行的 [number] 取得数组（Array）各成员类型的联合（Union），所以合法取值是四种字符串之一。这两处服务静态类型（Static Type），没有处理任何外部数据。

第三块才真正判断：先确认 value 是字符串，再看它是否属于允许集合。返回类型中的 value is RuntimeEventRole 是类型守卫（Type Guard）的声明：返回 true 后，检查器可以在相应分支里按这个较小范围理解该值。它依赖函数中的实际判断写得正确，并不是自动生成检查逻辑。

这就能解释三个输入："model" 通过，"assistant" 和数字 7 不通过。前者也只证明角色（Role）合法；完整的解码函数 decodeRuntimeEvent还要检查对象形状、标识、时间、内容与归属。不能拿一个局部判断替代整份记录的验证（Validation）。

另一个容易误读的词是只读（Readonly）。片段里的 readonly string[] 限制通过这份类型视图修改数组（Array），不表示对象已深度冻结（Deep Freeze），更不表示进程隔离（Process Isolation）或数据库事务（Database Transaction）。判断谁能写入、写入是否完成，仍需继续找实际负责者（Owner）。

问题。 把外部输入的 unknown 改成 RuntimeEvent，是否可以删掉解码器（Decoder）？

参考答案。 不可以。改名只改变静态类型（Static Type）的约定，没有使外部数据自动满足条件。要保留的实际保证来自运行时检查（Runtime Check），不是类型断言（Type Assertion）。

判别联合（Discriminated Union）：先认结果分支，再读字段

第07章提到的上下文压缩（Context Compaction），会把一段旧历史（History）整理为较短表示，供后续模型输入（Model Input）使用。本段源码以 HistoryCompaction 命名这项历史表示处理，并不是另一种需要重新学习的能力。这里先认识两个对象：检查点（Checkpoint）记录摘要（Summary）及其来源范围；投影（Projection）是根据这些记录整理出的表示。本节只读“规划得到了什么”，暂不把规划结果当作已经保存并生效。

假设一个函数有两种返回结果：没有得到可用替换时返回原因；得到候选检查点（Checkpoint）时返回该记录及相关事件（Event）。在Python里，常见读法是先检查 result["decision"]，再取对应键。TypeScript的判别联合（Discriminated Union）把这条规则写进类型：先用一个固定标签区分形状，标签确定后才有对应字段。

下面先看每个分支开头的 decision，再看它后面的字段；不必一开始记住所有名称。真实类型来自 packages/runtime/src/history-compaction.ts 的规划结果 PlanHistoryCompactionResult：

export type PlanHistoryCompactionResult =
  | {
      decision: 'fail_open';
      reason: HistoryCompactionFailReason;
      diagnosticReason?: HistoryCompactSummarizerFailureReason;
    }
  | {
      decision: 'compacted';
      checkpoint: HistoryCompactCheckpoint;
      /** Deterministic checkpoint-block plus verbatim successor projection. */
      replacementEvents: RuntimeEvent[];
      coveredRuntimeEvents: RuntimeEvent[];
      tailRuntimeEvents: RuntimeEvent[];
      estimatedTokensBefore: number;
      estimatedTokensAfter: number;
    };

| 表示两种形状之一，? 表示字段可以缺失，RuntimeEvent[] 表示运行时事件（Runtime Event）的数组（Array）。沿标签阅读，可以把这些字段分成几组：

表 2 / Table 2 · 判别联合（Discriminated Union）：先认结果分支，再读字段
分支或字段组在本次规划中的含义
decision: 'fail_open'本次未得到可用压缩替换，返回原因，不应用新的检查点（Checkpoint）；能否继续由调用方处理
decision: 'compacted' 与 checkpoint已得到候选检查点（Checkpoint），可进入后续验证（Validation）、保存和应用流程
coveredRuntimeEvents、tailRuntimeEvents区分被摘要覆盖的历史前缀（Prefix）与仍保留的后缀（Tail）
replacementEvents用检查点（Checkpoint）表示覆盖部分，并接上仍保留的后续投影（Projection），组成候选替换
estimatedTokensBefore、estimatedTokensAfter比较被覆盖前缀（Prefix）与检查点（Checkpoint）表示的估算词元（Token）数量；不等于包含全部后缀（Tail）的真实请求账单

最后一组尤其要按计算范围理解：名字里的 Before、After 不是“整个系统之前与之后”的承诺。词元（Token）在这里是模型文本计量所用单位，源码得到的是估算值；是否覆盖全部请求、是否为服务端实际计费，都要另找依据。

通过 decision 判断后，检查器会进行类型收窄（Type Narrowing）：进入 compacted 分支，才可以按这个类型安全地读取 checkpoint。反过来，尚未判断就访问该字段，等于把“某一分支拥有”错当成“两种结果都拥有”。用类型断言（Type Assertion）压掉报错，只会隐藏这个推理缺口。

还要再跨过一层边界：候选结果存在，不等于副作用（Side Effect）完成。 这个类型来自规划函数；保存、验证（Validation）和应用还在调用链（Call Chain）后面。第19章的源码走读会继续解释，一份可用摘要为什么不能立即替换当前模型输入（Model Input）。

问题。 看到 decision === 'compacted'，能否报告“检查点（Checkpoint）已保存，恢复时可读”？

参考答案。 不能。这里确认的是候选规划分支，不是持久化（Persistence）终态。还需找到保存调用、成功条件、失败处理和后续读取路径；类型标签不能代替这些步骤。

异步结果（Promise）与等待（await）：下一句何时执行？

同步函数直接返回结果时，可以接着使用返回值。异步操作（Asynchronous Operation）还需要表达“工作已开始，结果可能稍后才有”。异步结果（Promise）就是这样一个对象：它可以处于等待中（Pending），也可以兑现（Fulfilled）为成功值，或拒绝（Rejected）并给出原因。

表 3 / Table 3 · 异步结果（Promise）与等待（await）：下一句何时执行？
写法控制流（Control Flow）怎样继续适用边界
Promise<T>表达异步结果（Promise）；成功时可得到类型为 T 的值拿到对象不等于操作结束，也不保证它会及时结束
await operation()当前异步函数（Async Function）等待结果；成功后取得值，拒绝时进入异常路径（Error Path）其他工作仍可运行；重试（Retry）与事务（Transaction）需要另外实现
yield event 与 for await逐个产出与消费事件（Event），相邻两项之间也可以等待交出一项不等于已经保存，也不等于整个任务（Task）结束

先把等待（await）放回一个具体问题：新检查点（Checkpoint）已经准备好，程序希望保存调用成功后，再更新正在使用的投影（Projection）。下列两行是教学伪代码，recorder 表示保存记录的函数，完整实现还要处理验证（Validation）与异常。

await recorder(checkpoint);   // 等待保存调用成功；拒绝时不会直接进入下一句
updateProjection(checkpoint); // 此时再更新后续使用的视图

需要看到的是顺序，而不是两个函数名：第一句还在等待，第二句不能越过它；第一句以拒绝结束，执行进入异常路径（Error Path），也不会直接经过第二句。

第19章使用的真实保存调用遵循这个顺序：await Promise.resolve(recorder(...)) 将同步返回值与异步结果（Promise）统一交给等待（await）；保存调用抛错或返回的异步结果（Promise）拒绝时，catch 分支返回失败，后面的投影（Projection）更新不再执行。调用正常返回后，程序才能继续更新相关状态。

顺序成立仍不等于任意 recorder 都拥有同样的持久性（Durability）。如果某个函数只把记录放入内存就返回，那么等待（await）等到的也是这个函数约定的完成点。要判断是否已经写入可恢复存储，还须看它的真实实现与合同（Contract）。语法能保证“先等待这次调用，再继续”，不能替被调用方补出不存在的存储保证。

问题。 删除第一句的 await，第二句一定会等到保存完成吗？

参考答案。 不会。若保存函数返回尚未完成的异步结果（Promise），第二句可以继续，失败也不再由原来的等待位置接收。是否造成数据丢失取决于其余实现，但这里的先后保证已经被改变。

事件（Event）交接与消费确认（Acknowledgment）：交出以后发生什么？

逐项读取还有一种不同的暂停：生成器（Generator）先产出一项，把控制权交给消费者（Consumer）；当对方请求下一项时，生成器（Generator）从上次暂停处继续。异步生成器（Async Generator）写成 async *，允许这个过程中还出现异步等待。

在本例中，消费确认（Acknowledgment，ack）表示队列（Queue）记下某项已按交接合同（Contract）处理。要把三个时点分开：yield ev 交出当前事件（Event）；对方完成本轮处理并继续拉取；ackConsumed() 才推进确认计数。若把第三步提前到第一步之前，就会把“即将交出”算成“已处理”。

下面是AiSdkTurn.drain的完整真实方法。先看 try 中的交出与确认，再看 finally 中的分离处理；保留的英文源码注释描述这条接线的设计意图，实际存储条件在片段后解释。

  private async *drain(queue: AsyncEventQueue<SessionEvent>): AsyncIterable<SessionEvent> {
    try {
      for await (const ev of queue) {
        yield ev;
        // Generator backpressure IS the consumer's ack: this line runs only
        // when the consumer's loop body finished for `ev` and pulled the next
        // event, so `consumedCount` counts fully PROCESSED events. AgentRun
        // persists each mapped event before continuing, so an acked event is
        // either durable or deliberately skipped (partials, non-terminal
        // errors) — exactly the set a durable read can ever return.
        queue.ackConsumed();
      }
    } finally {
      // The consumer abandoned or finished the stream; wake any seq-ack waiter
      // so it observes `consumerDetached` instead of blocking forever.
      queue.noteConsumerDetached();
    }
  }

AsyncIterable<SessionEvent> 是异步可迭代对象（Async Iterable）的类型，表达逐个提供会话事件（Session Event）的接口（Interface）。循环中的 ev 就是当前一项，读法可拆成四个控制点：

  1. for await 从队列（Queue）取得一项；没有就等待，取得后进入循环体。
  2. yield ev 将它交给消费者（Consumer），暂停在这里。当前暂停不说明对方已经完成处理。
  3. 对方完成处理并继续请求下一项，生成器（Generator）才执行 ackConsumed()。队列（Queue）据此推进已消费计数，并唤醒相应等待者。
  4. 当迭代正常结束或被关闭而进入 finally，noteConsumerDetached() 标记消费者（Consumer）分离，唤醒等待确认的代码，使其能观察到分离，而不是一直等待。这不是代替尚未处理的事件（Event）补发成功确认。

这里的背压（Backpressure）通过拉取节奏体现：对方尚未继续请求，当前方法就不会越过 yield 去确认本项。若对方交出后既不继续拉取、也不关闭迭代，这段代码不会仅因时间过去而自动确认；也不能从 finally 的存在推导出对方一定会及时关闭。

消费确认（Acknowledgment，ack）是否意味着持久化（Persistence）完成，要看实际消费者（Consumer）与存储策略。 相邻的 AgentRun 接线会按事件（Event）类型分流：部分事件（Partial Event）进入专门处理路径，非终止错误（Non-Terminal Error）可以跳过常规运行时事件（Runtime Event）写入，已由工具协议（Tool Protocol）保存的投影（Projection）也避免重复写入。记录路径还区分必须成功的持久写入与其他写入模式：写入是否为强制条件、怎样确认已写入，以及写失败是否允许继续，都由接线与模式决定。因此，不能把源码注释里的简写扩展为“任何收到消费确认（Acknowledgment，ack）的事件（Event）都已经可靠保存”。

语言语法在这里给出交接顺序；程序合同（Contract）决定已处理究竟覆盖了哪些动作；持久性（Durability）则需要追踪具体写入及失败政策。这三层分别核对，才不会把一个名称读成完整恢复保证。第14章将把事件（Event）与投影（Projection）放回运行时（Runtime）的完整关系中。

导入（Import）之后，还要找到实际负责者（Owner）

从Python的 import 寻找定义来源，这个习惯可以延续到TypeScript。不过，静态类型（Static Type）的来源和运行时（Runtime）函数的来源需要分开看。下面是真实的导入（Import）片段，来自 packages/runtime/src/history-compact-checkpoint.ts：

import { createHash } from 'node:crypto';
import { Buffer } from 'node:buffer';
import type { ExecutionLogCoverage } from '@maka/core/execution-log-coverage';
import type { RuntimeEvent } from '@maka/core/runtime-event';
import type { ModelMessage } from './model-protocol.js';
import { stableStringify } from './request-shape.js';

先按用途拆开。类型导入（Type Import）写作 import type，只供静态检查（Static Checking），不在运行时（Runtime）取出一个运行时事件（Runtime Event）对象。createHash、Buffer 和 stableStringify 则作为实际值导入，其中函数可以参与后续执行；仅有导入（Import）语句，还不说明当前路径一定调用过它们。

再看路径。@maka/core/runtime-event 是包导出（Package Export）入口，不是相对于当前文件的路径。core/package.json中的 exports 将它指向构建产物（Build Artifact），对应源码在 src 下。相对路径写 .js 也不说明旁边没有 .ts 源码，需要结合模块解析（Module Resolution）与构建安排判断，不能只按扩展名停止查找。

找到定义之后，还应沿当前问题再走三步。以检查点（Checkpoint）为例：

表 4 / Table 4 · 导入（Import）之后，还要找到实际负责者（Owner）
接下来寻找什么要回答的问题
类型与数据定义它包含哪些字段，怎样表达来源与覆盖范围？
使用这些数据的调用链（Call Chain）谁验证候选、等待保存调用，再决定采用哪个投影（Projection）？
真实接线与写入谁提供保存函数，写到哪种账本（Ledger），失败怎样处理，之后由谁读取？

类型归属（Type Ownership）、状态归属（State Ownership）与执行负责者（Owner）不是同一件事。类型放在Core包中，不说明Core包会自行启动压缩或保存记录。第19章的检查点（Checkpoint）保存与读取链将继续追到实际消费者（Consumer），而不是停在接口（Interface）名称上。

问题。 找到了 RuntimeEvent 的接口（Interface），是否就可以断言这份运行时事件（Runtime Event）已经保存？

参考答案。 不能。类型定义没有存储副作用（Side Effect）。需要继续查创建、调用、实际写入和失败处理；导入（Import）关系只提供了追踪入口。

把三种读法带回后续机制

读后续源码时，可以沿同一条短线推进：先问数据属于哪个分支，再问当前语句何时继续，最后问结果交给哪位消费者（Consumer）。遇到陌生字段，先确定它在这条线中回答什么问题，再追完整定义。

第15章的模型输入（Model Input）主要帮助理解数据如何组织，第19章的检查点（Checkpoint）保存会用到等待与应用顺序，第16章的工具执行（Tool Execution）则继续展开行动请求（Action）如何产生副作用（Side Effect）。本章的语言桥提供阅读方法；各条路径的实际保证，仍由对应机制与实现来证明。
