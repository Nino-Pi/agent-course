第 10 章｜Python 与 TypeScript 控制流对照

本章概览

核心问题：怎样从 TypeScript 的类型、异步语法和导入关系读出真实控制顺序？

关键概念：unknown（未知类型）要求先检查；判别联合按标签区分字段；Promise/await（异步结果与等待）控制继续时点；yield（产出事件）交给消费者；import type（类型导入）只供静态检查。

关系主线：类型约束数据形状，运行时检查验证输入，等待与事件消费决定何时继续。只有结合实际写入和消费者合同，才能判断事件是否保存，不能从类型或语法名称推导持久保证。

第02章的 Python 最小阅读卡已经在首次代码前解释了 self、列表末项、字典取值和方法调用。本章在这些读法上增加后续 TypeScript 源码的语言对照，类型、等待和事件交接都会配中文解释；不熟悉这些新写法时，从本章建立读法再进入后续实现。已经熟悉相关语法的读者可以继续第11章。这里提前选用的摘要保存与事件例子，只用于解释控制顺序；完整机制将在第14、19章展开，理解它们不需要先猜测本章尚未给出的系统细节。

以下代码摘自 Maka（Apache-2.0）。

类型声明与运行时检查

mini 的 Python 类型标注可以帮助阅读方法的输入与输出，但不会自动检查模型返回的每一份 JSON。TypeScript 也一样：ReadInput 是“读取文件所需参数”的类型名，input: ReadInput 是静态约定，网络或磁盘来的值还要在运行时检查。unknown 表示“暂时不能假定它有什么字段”；as ReadInput 只是让检查器接受一种断言，不会把坏输入变成正确数据。

运行事件是描述用户输入、模型响应或工具结果等情况的记录。下面只检查事件的角色字段，完整事件机制将在第14章展开。Maka 的真实短窗口来自 packages/core/src/runtime-event.ts 的 角色类型与检查函数：

export const RUNTIME_EVENT_ROLES = ['user', 'model', 'tool', 'system'] as const;
export type RuntimeEventRole = (typeof RUNTIME_EVENT_ROLES)[number];

export function isRuntimeEventRole(value: unknown): value is RuntimeEventRole {
  return typeof value === 'string' && (RUNTIME_EVENT_ROLES as readonly string[]).includes(value);
}

静态类型与实际判断分别起作用：

  • as const 保留四个字面值；[number] 从数组成员得到允许的联合类型。它们服务静态检查，不会验证外部输入。
  • typeof value === 'string' 与 includes(value) 是实际会运行的判断。value is RuntimeEventRole 告诉检查器：函数返回 true 时，该值通过了这项检查。

这里 readonly string[] 中的 readonly 也要按范围理解：只读数组类型限制通过这份类型视图进行修改，不代表深度冻结对象、进程隔离或数据库事务。找到写入 owner 仍然是另一项工作。

例如 "model" 满足角色检查，"assistant" 和数字 7 不满足。这里仅检查 role，不能拿它证明整个事件合法。完整 decodeRuntimeEvent还检查对象形状、身份、时间、内容和归属，再返回或抛错。

**问题：**把 unknown 改成 RuntimeEvent，是否可以删掉 decoder？不能。类型写法不会让磁盘内容或外部数据自动符合契约；删除检查会改变运行时保证。

判别联合：标签决定字段范围

先借历史摘要的规划结果说明类型分支。这里的压缩是把一段历史整理成较短摘要；checkpoint 指记录摘要及其来源范围的数据，compacted 表示规划结果含有这种记录。摘要怎样保存和生效，将在第19章展开。

在 Python 中，你可能先写 if result["decision"] == "compacted" 再取 checkpoint。TypeScript 可以把两种结果的合法字段直接写在类型中。这叫判别联合：每种形状有一个可以区分它的固定标签。

两种标签决定可用字段。fail_open 表示本次规划没有得到可用的压缩替换，返回原因而不应用新 checkpoint；能否继续由调用方处理。compacted 则带有候选 checkpoint，可交给后续保存与应用流程。下面是 Maka 的完整真实类型，来自 packages/runtime/src/history-compaction.ts 的 PlanHistoryCompactionResult：

export type PlanHistoryCompactionResult =
  | {
      decision: 'fail_open';
      reason: HistoryCompactionFailReason;
      diagnosticReason?: HistoryCompactSummarizerFailureReason;
    }
  | {
      decision: 'compacted';
      checkpoint: HistoryCompactCheckpoint;
      /** Deterministic checkpoint-block plus verbatim successor projection. */
      replacementEvents: RuntimeEvent[];
      coveredRuntimeEvents: RuntimeEvent[];
      tailRuntimeEvents: RuntimeEvent[];
      estimatedTokensBefore: number;
      estimatedTokensAfter: number;
    };

| 表示两种形状之一；? 表示字段可能缺失；RuntimeEvent[] 表示事件数组。根据 decision 区分结果：fail_open 有失败原因，compacted 才有 checkpoint 与 replacementEvents。检查器会在判断标签后收窄字段范围。

这是一份规划函数的结果，不是整个持久化流程已经成功的终态证明。调用者还要验证、保存并应用 checkpoint；“类型叫 compacted”不能代替查调用者。对应因果链见 第19章 源码走读。

**问题：**在判断 decision 前读取 result.checkpoint 为什么有问题？因为 fail_open 分支没有这个字段。应先处理分支，而不是用类型断言压掉错误。

Promise 与事件流的控制顺序

mini 的基础调用线可以同步读成“query 返回，再 execute，再记录 observation”。Maka 有模型流、异步存储和事件消费者，需要区别三种动作：

表 1 / Table 1 · Promise 与事件流的控制顺序
写法如何读仍需注意
Promise<T>表示一次异步操作的结果；成功时得到 T，拒绝时带有原因，也可以仍在 pending（等待中）拿到 Promise 对象时，操作可能尚未结束；它也不保证及时结束
await operation()等待操作结果；成功后取得结果并往下执行，拒绝则走异常路径等待只暂停当前异步函数，其他工作仍可运行；重试与事务需另行实现
yield event / for await逐个交付／消费事件，中间可以等待交付事件本身不保证事件已保存，也不表示整个任务结束

recorder 在这里指保存记录的函数。先用两行教学伪代码表示顺序，完整实现还要处理校验与异常：

await recorder(checkpoint);  // 等待保存记录
updateProjection(checkpoint); // 保存成功后才更新使用中的视图

下图仍只解释这两行伪代码的控制顺序：等待正常返回才可进入后续更新，异常支路不经过这条更新语句。它没有承诺任意 recorder 都提供相同的持久性。

第19章的真实 recorder 调用展示这条顺序：等待保存成功之后，才更新投影；catch 返回时，后面的更新不再执行。Promise.resolve(...) 让一个同步返回值或 Promise 都能通过同一 await 处理。

事件交接遵循另一条顺序。ack 是 acknowledgment（确认）的缩写：yield ev 交出事件，消费者继续拉取后，ackConsumed() 才执行消费确认。确认具体覆盖哪些处理，由消费者和队列的合同决定。

AiSdkTurn.drain 的完整方法将交付、确认和分离写成三个控制点：

  private async *drain(queue: AsyncEventQueue<SessionEvent>): AsyncIterable<SessionEvent> {
    try {
      for await (const ev of queue) {
        yield ev;
        // Generator backpressure IS the consumer's ack: this line runs only
        // when the consumer's loop body finished for `ev` and pulled the next
        // event, so `consumedCount` counts fully PROCESSED events. AgentRun
        // persists each mapped event before continuing, so an acked event is
        // either durable or deliberately skipped (partials, non-terminal
        // errors) — exactly the set a durable read can ever return.
        queue.ackConsumed();
      }
    } finally {
      // The consumer abandoned or finished the stream; wake any seq-ack waiter
      // so it observes `consumerDetached` instead of blocking forever.
      queue.noteConsumerDetached();
    }
  }

async * 定义异步生成器；AsyncIterable<SessionEvent> 表达逐个产出 SessionEvent 的接口。yield ev 把当前事件交给消费者，消费者继续拉下一项后，生成器才走到 ackConsumed()。finally 在这段迭代结束或被关闭时处理消费者分离。

关键区别在于：JavaScript 提供交接顺序，Maka 的消费者合同才赋予 ack 以含义。 该代码与相邻消费者约定相配合，已处理事件要么持久化，要么按规则跳过；不能从任意 yield 或 ack 名称推出持久化保证。Runtime 的整体事实边界见 第14章。

**问题：**删掉 await recorder(...)，或把 ack 放到 yield 之前，会怎样？前者可能在保存尚未结束时继续；后者在消费者尚未处理时就确认。两者都改变控制顺序。是否真的导致数据丢失，还取决于上下游实现，不能仅靠语法宣布完整恢复保证。

import、类型归属与执行负责者

读 Python 时会从 import 找类在哪里定义；TypeScript 也可以这样读，但要分清只用于类型检查的名字和实际执行的函数。下面是 packages/runtime/src/history-compact-checkpoint.ts 的真实 import 片段：

import { createHash } from 'node:crypto';
import { Buffer } from 'node:buffer';
import type { ExecutionLogCoverage } from '@maka/core/execution-log-coverage';
import type { RuntimeEvent } from '@maka/core/runtime-event';
import type { ModelMessage } from './model-protocol.js';
import { stableStringify } from './request-shape.js';

import type 只带入静态类型，不在运行时取得一个 RuntimeEvent 对象。createHash 和 stableStringify 则是实际函数依赖。@maka/core/runtime-event 是包的公开导出入口，不能把包名当成本地相对路径；core/package.json的 exports 指向构建产物，源码定义位于对应 src 文件。源码中写 .js 也不说明旁边没有 .ts，要结合模块导出和构建结构判断。

找到定义只是第一步。例如 checkpoint 类型描述什么字段合法，不负责决定何时压缩，也不负责把它写到磁盘。继续沿当前问题找：

  1. 定义：history-compact-checkpoint.ts 怎样表达来源与覆盖范围；
  2. 使用：第19章 的 compactActiveRequestHistory 为什么验证、等待 recorder、再选择投影；
  3. 实际接线：谁向 Runtime 提供 recorder，写入何种 ledger；后面的第19章保存与消费链将继续追踪。

不要仅凭 @maka/core 或一个 interface 就认定 Core 是执行 owner。类型归属、状态归属、执行负责者是不同问题。

**问题：**找到 RuntimeEvent interface 后能否断言事件已经保存？不能。类型定义没有存储副作用；还要找调用、写入与失败处理。
