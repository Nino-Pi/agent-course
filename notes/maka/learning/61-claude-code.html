第 61 章｜Claude Code 的机制与设计取舍

本章概览

核心问题：从 Claude Code 的公开行为，怎样理解代码修复中的反馈、材料延续和独立委派（Delegation）？

关键概念：钩子（Hook）在事件（Event）时点执行扩展处理；权限（Permission）约束可采取的动作；压缩（Compaction）整理当前输入；记忆（Memory）保留跨会话背景；技能说明包（Skill）复用方法；子任务（Subtask）承担有边界的工作。

关系主线：工具观察结果（Observation）推动下一次选择，材料经读取才参与请求，子任务（Subtask）结果仍由父任务（Parent Task）验收（Acceptance）；公开能力说明不能补出未披露的内部事务，教学扩展也不等于产品默认行为。

前情回顾：反馈、材料延续与独立工作

第16章把工具结果（Tool Result）看作后续决策的观察结果（Observation）：调用已经返回，还要看它返回了什么、是否覆盖当前问题。第19章中的压缩（Compaction）改变下一次输入的表示；原始日志存在，不代表模型（Model）已经看到其中的关键断言。

第20章说明跨任务记忆（Memory）需要保存、选择与读取；本轮修复条件仍要依据当前文件。第23章则区分技能说明包（Skill）与子任务（Subtask）：前者提供方法，后者承担独立工作，结果还需父任务（Parent Task）验收（Acceptance）。

本章用同一项修复把这些关系连接起来。Claude Code 的公开行为提供产品实例；未公开的内部事务与调度保持未证实。图中的概括职责与后面的接口属于教学设计，不能当作官方源码模块或默认配置。

1. 设计问题与适用条件

Claude Code 完成代码修复时，长对话、跨会话记忆与子代理（Subagent）分别怎么参与？类似系统可以采用哪些责任划分？

沿用第04章的四文件任务：package.json定义命令，README说明怎样运行，测试规定非负整数秒应格式化为m:ss，src/duration.js负责计算。以下是使用这些需求与故障的教学推演，没有启动Claude Code。先固定正常修复所需的条件：

  • 用户授权修README.md和src/duration.js中的目标函数，要求运行相关测试、给出文件差异（Diff），并用中文说明结果；测试和项目配置只读。
  • 当前工作区（Workspace）可能有用户改动，因此新的观察结果（Observation）不能被旧记忆（Memory）替代。
  • 先用一个主代理（Main Agent）闭环；只有出现独立且费上下文（Context）的任务才考虑委派（Delegation）。

这些是题设，不是 Claude Code 默认权限（Permission）或默认调度策略。

2. 先区分三种改变，再连接一次修复

同一份错误信息会经过几种机制，但每种机制改变的对象不同。先用这张表固定读图时的判断：

表 1 / Table 1 · 2. 先区分三种改变，再连接一次修复
机制改变什么本题中的例子后续由谁使用
当前工作输入保留失败断言，裁去重复日志，留下来源入口下一次模型（Model）请求据此继续定位
跨会话背景保存长期项目规则，下一会话选取仍适用的条目输入组织读取后才参与当前判断
工作分配让只读子任务（Subtask）核对文档入口父任务（Parent Task）核实依据并把结论用于修复

一次修复从反馈环（Feedback Loop）推进。Claude 模型（Model）根据当前材料决定下一步，Claude Code 提供读文件、搜索、编辑和命令等能力，把真实结果再交回模型（Model）。读到失败断言后，下一步可能改变定位或修改方案；最终要用测试与文件差异（Diff）支撑完成判断。该过程依据公开产品行为，不能推出未公开的全部内部源码接线。

当前上下文（Context）与跨会话背景是两类状态（State）。长对话需要整理输入；项目指令、长期记录、当前错误日志承担不同责任。CLAUDE.md 与自动记忆（Auto Memory）也要分开解释。参考设计要求当前约束、未完成状态（State）与证据入口仍可核对，而不会把“摘要（Summary）生成成功”当成任务完成。

例如同一条“125秒应为2:05、实际为2:25”的观察结果（Observation），在反馈环（Feedback Loop）里提示继续定位，在上下文（Context）整理里应保留为未解决证据，委派（Delegation）调查时又可能成为子任务（Subtask）需要的背景。材料会跨越几种机制，含义不能在转交时悄悄改变；第7节把这项修复从头走到交付。

扩展与控制承担另一组责任。技能说明包（Skill）适合复用步骤，子代理（Subagent）适合有边界的独立工作；委派（Delegation）前应明确它拿到什么背景、能改什么文件、交回什么证据。权限（Permission）决策和执行隔离分开讨论。内部事务与远端效果恢复（Recovery）没有完整公开接线时，保留未知；下文提出的操作身份（Operation Identity）、对账和失败保留属于教学设计，不能把 Maka 的实现名词移植成 Claude Code 事实。

3. 产品能力怎样组成反馈环（Feedback Loop）

下图是依据公开能力绘制的职责教学图，不是 Claude Code 源码模块图。上下文组织和执行入口是本课概括的职责名。

C → M → P → O → C 是反馈环（Feedback Loop），文件、命令和外部工具分别返回实际观察结果（Observation）。每条回边都对应一个已经取得的结果，它可能改变下一步决策，也可能只是重复已有状态（State）。重复结果也可能支持合法等待，但不能仅因返回一次就算一次进展。

设计验收（Acceptance）条件是：行动请求（Action）不等于效果（Effect）；没有观察结果（Observation）不能编造成功；模型（Model）看见工具也不等于任意调用都被允许。

图中执行入口表示职责，没有声称某个内部类名。教学接口可以定义输入与结果合同，但框名不能冒充官方源码符号。

4. 压缩（Compaction）与记忆（Memory）的两条链

本次对话中的旧材料与未来任务需要的信息是不同对象。前者整理工作输入，后者还需要写入、保存和后续读取。

这是用于分清职责的教学图。实线分别表示当前输入与有选择的读取；虚线表示需要单独核对的保存行为，不能因为本轮出现一条偏好就假设它必定写入。

官方的 MEMORY.md 索引与主题文件提供一个可解释的文件式实例；压缩（Compaction）后哪些指令重新装入有各自规则。

按本题需求，压缩（Compaction）后的任务状态（State）至少包含四类信息：改了什么、哪个检查仍失败、用户允许的范围、下一步需要的观察结果（Observation）。这是教学设计的验收（Acceptance）条件，不声称它们是 Claude Code 真实摘要（Summary）模式（Schema）。以下补充一个中途状态（State）作为输入：已经从配置定位测试入口，测试报告 125 秒实际为 2:25、期望为 2:05，函数尚未修复；这些是给定观察结果（Observation），完整修复走读在第7节展开。

task: 修 README 与时间格式化函数，最后中文报告
done: 测试入口已定位，尚未完成函数修复
evidence: 125 秒的期望为 2:05，实际为 2:25
next: 核对余秒计算，修改后复测并检查 diff

当前会话整理与跨会话详细读取只在“本次工作上下文（Context）”汇合；压缩（Compaction）摘要（Summary）没有默认写成永久用户偏好的箭头。

原始日志太大时还要单独决定怎样有界读取。Claude Code 公开的整理能力不证明它采用 Maka 的 ArchiveRead 协议；可回到 第54章说明自己怎样设计引用与回读（Readback）。

5. 技能说明包（Skill）与子任务（Subtask）怎样参与主任务（Main Task）

选择委派（Delegation）之前，先固定背景来源。公开文档中的不继承父对话（Non-fork）子代理（Subagent）依赖自足任务说明；对话分叉（Conversation Fork）可以沿用父对话背景。技能说明包（Skill）的 context: fork 又是把方法放进子上下文（Context）执行的配置，不能直接视为复制完整父对话。可用性仍依运行方式、版本和分叉模式（Fork Mode）判断。

这里有两个独立选择：需要哪些背景，以及可以访问哪些资源。更多背景可能帮助理解，也可能携带旧条件；独立上下文（Separate Context）能减少主任务（Main Task）的输入噪声，却不自动隔离文件。后面的类型据此分别设置背景模式与读写范围。

图中先决定是否值得独立委派（Delegation）：不委派（Delegation）就由主任务（Main Task）继续处理；决定委派（Delegation）后，再选择自足说明（Brief）或可用的对话分叉（Conversation Fork）来提供背景。这是本课设计判断，不是声称模型（Model）固定执行这棵决策树。文件隔离（File Isolation）使用虚线，因为独立上下文（Separate Context）不自动创建独立文件系统。

两个子上下文（Context）的结果都汇入主任务（Main Task）核对点；工作区（Workspace）边界另行标注，因为独立上下文（Separate Context）仍可能修改同一份文件。

为了看清交接，本题单独展示“核对README中的命令”这个只读子任务（Subtask），主任务（Main Task）保留函数修改权。四文件规模下由主任务（Main Task）直接读取也合理；这个拆分用于说明背景与结果怎样交接，不预设委派（Delegation）能加速。子任务（Subtask）输出应含文件位置、当前内容与结论依据，不必交回所有搜索噪声。

6. 委派（Delegation）接口与交接责任

下面的 TypeScript 是教学类型，不是 Claude Code 应用编程接口（Application Programming Interface，API）或可直接使用的子代理（Subagent）配置。按两组阅读：DelegatedTask 规定目标、背景来源、读写范围和交付条件；DelegatedResult 返回结论、证据、改动、检查与未完成项。

发送方用第一组限定工作，父任务（Parent Task）用第二组逐项验收（Acceptance）。类型不提供执行循环，也不会自动落实权限（Permission）或产生真实结果；这些是接口必须连接到的消费者（Consumer）职责。

// 输入合同：目标和事实说明要做什么，资源范围限制在哪里做。
type DelegatedTask = {
  objective: string;
  contextMode: "brief" | "conversation-copy";
  relevantFacts: { statement: string; evidence: string }[];
  // 独立背景与独立文件是两个选择，分别传递。
  readScope: string[];
  writeScope: string[];
  acceptance: string[];
};

// 输出合同：已返回、局部检查通过与整项任务完成分别判断。
type DelegatedResult = {
  status: "complete" | "partial" | "blocked";
  findings: { claim: string; evidence: string }[];
  changedFiles: string[];
  checks: { name: string; outcome: "pass" | "fail" | "not-run" }[];
  // 部分完成与无法继续时仍保留未解决事项。
  remaining: string[];
};

contextMode 固定输入来源；writeScope 使并行文件责任可检查；checks 让“任务返回了”与“测试通过了”成为不同状态（State）。

将这些字段填回同一个只读调查，关键内容如下。它们是上面类型的具体值，仍是教学交接约定：

表 2 / Table 2 · 6. 委派（Delegation）接口与交接责任
字段或结果本题传递的内容主任务（Main Task）据此核对什么
objective、relevantFacts核对README命令与项目scripts是否一致；当前修复同时要求文档入口正确子任务（Subtask）只判断入口，不接管函数修复
contextMode、readScope、writeScope自足说明（Brief）；读取README.md和package.json；可写集合为空输入自足，工作范围可检查
findingsREADME写npm run check；配置只有test: node --test，没有 check，并附字段位置结论能否由实际返回的两份内容支持
changedFiles、checks、remaining无修改；文件内容核对完成，执行测试为not-run；README待主任务（Main Task）更新只读调查完成不等于整个修复已经通过测试

这个类型没有实现执行约束（Enforcement）。若要做生产系统，还需把工具执行能力绑定到作用域（Scope）、决定取消（Cancellation）和部分完成语义，并验证返回内容。不能仅凭类型字段宣称隔离已经成立。

7. 具体走读：一次修复中逐步增加证据

以下是纸面推演，使用课程教学夹具（Fixture）的需求和故障，不是 Claude Code 真实执行轨迹（Trajectory）。题设初态为 README 指向缺失脚本、实现用 % 100 计算余秒。

表 3 / Table 3 · 7. 具体走读：一次修复中逐步增加证据
步骤输入与观察（Input · Observation）现在能得出的结论下一步
1用户要求修入口和函数两项修改在题设授权内核对文件与用户已有改动
2package 定义 test: node --test测试入口可确定更新 README 的错误命令
3125 秒输出 2:25，期望 2:05至少有功能断言失败读实现并排除分钟、补零等候选
4已读代码的余秒为 % 100当前观察结果（Observation）支持修改周期根据非负整数秒契约改为 % 60
5相关检查通过且文件差异（Diff）范围正确本题证据支持交付区分已测范围与未测范围

独立只读子任务（Subtask）可以并行检查文档入口，但若测试依赖刚发生的编辑，测试就应等待修改完成。这里依据数据依赖安排顺序，不依据“多智能代理（Agent）应该更快”的预设。

现在加入失败：主代理（Main Agent）刚准备调用编辑（Edit），用户已改了同一段 README。参考处理是重新读取和定位，保留用户意图；旧记忆（Memory）中的文本不能证明当前目标仍唯一。是否可自动合并要根据实际差异判断。

再加入长日志：压缩（Compaction）后只知道测试失败，却看不到具体预期值（Expected）与实际值（Actual）。正确下一步是获取可靠错误片段或重新执行有界检查；不能把摘要（Summary）里没有记录的细节当作事实。

8. 设计追问与完整回答

追问一：为什么不用 CLAUDE.md 装下所有东西？

先区分持续生效的规则、按需步骤和临时观察结果（Observation），再讨论上下文（Context）成本。对本题，项目测试规范可以是长期规则，一份具体失败日志应有自己的证据位置。选择条目常驻还是按需，需要测相关性、漏读和下一步行动质量，不能只测文件长度。

追问二：技能说明包（Skill）就是子代理（Subagent）吗？

可复用步骤与独立执行上下文（Context）是两个选择轴；同一过程可以留在主任务（Main Task），也可以委派（Delegation）。官方支持在特定配置中把技能说明包（Skill）放到子上下文（Context），但不能据此把所有技能说明包（Skill）都画成独立进程。还要区分说明正文和实际权限（Permission）配置。

追问三：所有子代理（Subagent）都看不到父历史吗？

先问类型。当前文档已有对话分叉（Conversation Fork）例外；不能照搬旧的全称结论。本题若只查测试入口，足够清晰的自足说明（Brief）更容易审查；若要评估此前多轮设计的兼容性，再考虑更完整背景。无论哪种，任务返回后仍要检查证据。

追问四：启用沙箱（Sandbox）就能把所有工具关在里面吗？

先定位执行路径（Execution Lane）。官方命令执行（Bash）沙箱的覆盖范围不等于所有远端工具；初始化失败的配置也影响实际行为。如果自己的产品要求强制隔离，就必须把不可用处理写成明确验收（Acceptance）条件，而不能只显示一个“沙箱（Sandbox） on”标签。

追问五：有回退（Rewind），为何还要担心命令副作用？

文件编辑工具的可回退状态（State）不能覆盖任意命令执行（Bash）或远端动作。官方检查点（Checkpoint）有明确范围；创建远端任务后超时时，需要另行设计稳定操作身份（Operation Identity）、查询/对账（Reconciliation）与未知效果（Unknown Effect），不能用文件回退按钮证明远端动作未发生。

追问六：它是不是直接用了 Claude 应用编程接口（API）的压缩（Compaction）？

应用编程接口（API）支持什么与 Claude Code 默认调用什么是两种证据。公开产品资料不足以给出全部默认请求接线；默认请求形式、功能开关（Feature）与模型服务提供方（Provider）选路仍需具体配置或请求证据。可以比较机制，不能补写调用链。

9. 取舍与验证：怎样把方案变成可反驳的判断

下表是教学评估设计，不是 Claude Code 性能报告。

固定教学夹具（Fixture）、模型（Model）配置、预算（Budget）、权限（Permission）与起始改动，再重复比较；记录基础设施失败，别只保留成功样例。衡量“主上下文（Context）变小”之外，还要记录整项任务的成本和结论正确性。

记忆（Memory）验证另做反事实对照（Counterfactual Comparison）：同一新请求不重复旧偏好，一方正常读取目标条目，另一方关闭该次读取；其余当前输入、项目指令、模型（Model）配置和文件初态保持相同，并核对真正进入请求的材料。只删除一个文件，却让同一偏好继续留在父对话或项目指令中，没有隔离所比较的因素。

若两边都答对，说明这一次输出仍不能证明目标条目起作用；若读入方更好，还需保留重复试次、未知结果和全部费用。这个对照是本课的评价设计，本章没有运行 Claude Code 实验。

10. 十个配置文件的只读核对案例

将任务改为“核对十个配置文件的部署域名，输出报告，不修改”。本例给定十个文件 deploy/app01.yaml 至 deploy/app10.yaml，规则要求 api.example.test；实际读取显示 app07 为 staging.example.test，其余九个为要求值。这些是教学输入，不是实际仓库扫描结果。

参考流程是先确认十个路径属于允许范围，按资源与工具并发条件读取，保留每份内容的字段位置；然后比较规则与实际值。发现不一致不触发编辑（Edit），读取动作也不需要对域名发网络请求。若文件由用户并发修改，结论注明对应观察结果（Observation），关键交付前可重新读取发生变化的文件。

文件范围（File Scope）读到的部署域名完整参考结论
app01–app06、app08–app10api.example.test9 项与给定规则一致

交付可以明确写为：“已读取十个给定配置；九项符合要求，app07 的部署域名不一致。所有结论来自本次文件观察结果（Observation），未发网络请求，未修改文件；未核对运行中的实际部署。”若某个文件读取失败，则把它列为无法判定，不能计入九项一致或忽略分母。

该任务可直接用并行只读工具；只有文件调查需要独立多步解释时才委派（Delegation）只读子任务（Subtask）。子任务（Subtask）自足说明（Brief）固定文件集合、预期域名、禁止修改、返回路径与原值；父任务（Parent Task）合并十项结果并检查缺项。由于没有写入需求，编辑（Edit）、写入批准（Approval）和回退（Rewind）不进入正常执行链。

11. 相关机制与完整案例

Claude Code的展开机制可按当前问题回读（Readback）：

  • 循环与上下文（Context）：逐步代码修复、请求预算（Budget）、压缩（Compaction）后的输入重建、会话连续性。
  • 工具与安全：工具发现、钩子（Hook）前后时序、权限（Permission）冲突、命令执行（Bash）与远端模型上下文协议（Model Context Protocol，MCP）边界。
  • 记忆（Memory）与技能说明包（Skill）：四种保存对象、范围与冲突、写读应用闭环、方法装载与临时权限（Permission）。
  • 子任务（Subtask）与恢复（Recovery）：自足说明（Brief）/分叉（Fork）、工作区（Workspace）隔离、父任务（Parent Task）验收（Acceptance）、取消（Cancellation）、检查点（Checkpoint）与未知效果（Unknown Effect）。

通用设计与综合案例：

  • 工具与执行：第50章、第51章、第52章。
  • 工作输入与记忆：第53章、第54章、第55章。
  • 方法与委派（Delegation）：第57章；产品对照：第60章 Codex。
  • 综合案例：三组完整设计案例；设计问题目录。
