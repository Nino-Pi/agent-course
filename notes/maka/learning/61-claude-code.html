第 61 章｜Claude Code 的机制与设计取舍

本章概览

核心问题：从 Claude Code 的公开行为，怎样理解代码修复中的反馈、材料延续和独立委派？

关键概念：Hook（钩子）：在事件时点执行扩展处理；权限：约束可采取的动作；压缩：整理当前上下文；Memory（记忆）：保留跨会话背景；Skill（技能说明）：复用方法；子任务：承担有边界的独立工作。

关系主线：工具观察推动下一次选择，材料经读取才参与请求，子任务结果仍由父任务验收；公开能力说明不能补出未披露的内部事务，教学扩展也不等于产品默认行为。

前置：第16章 工具、第19章 压缩、第20章 Memory、第23章 Skills 与子任务。工具、压缩和 Memory 的通用设计分别见 第50章、第54章、第55章。

以下以 Claude Code 公开产品行为为实例；未公开的内部事务和调度机制不作实现断言，扩展方案另标为教学设计。

相关机制章节：

  1. 循环与上下文：逐步代码修复、请求预算、压缩后的输入重建、会话连续性。
  2. 工具与安全：工具发现、Hooks 前后时序、权限冲突、Bash 与远端 MCP 边界。
  3. Memory 与 Skills：四种保存对象、范围与冲突、写读应用闭环、方法装载与临时权限。
  4. 子任务与恢复：brief/fork、工作区隔离、父任务验收、取消、checkpoint 与未知效果。

1. 设计问题与适用条件

Claude Code 完成代码修复时，长对话、跨会话记忆与子 Agent 分别怎么参与？类似系统可以采用哪些责任划分？

以下限定为一次本地代码修复，并明确任务授权、网络需求、委派条件与产品资料边界：

  • 用户授权修 README 和目标函数，要求运行相关测试、给出 diff，并用中文说明结果。
  • 当前工作区可能有用户改动，因此新观察不能被旧记忆替代。
  • 产品行为以官方公开资料为限；未公开的内部机制保留未知，教学参考设计另行标明。
  • 先用一个主 Agent 闭环；只有出现独立且费上下文的任务才考虑委派。

这些是题设，不是 Claude Code 默认权限或默认调度策略。

2. 参考方案

一次修复从反馈环推进。Claude 模型根据当前材料决定下一步，Claude Code 提供读文件、搜索、编辑和命令等能力，把真实结果再交回模型。读到失败断言后，下一步可能改变定位或修改方案；最终要用测试与 diff 支撑完成判断。该过程依据公开产品行为，不能推出未公开的全部内部源码接线。

当前上下文与跨会话背景是两类状态。长对话需要整理输入；项目指令、长期记录、当前错误日志承担不同责任。CLAUDE.md 与 auto memory 也要分开解释。参考设计要求当前约束、未完成状态与证据入口仍可核对，而不会把“摘要生成成功”当成任务完成。

扩展与控制承担另一组责任。Skill 适合复用步骤，子 Agent 适合有边界的独立工作；委派前应明确它拿到什么背景、能改什么文件、交回什么证据。权限决策和执行隔离分开讨论。内部事务与远端效果恢复没有完整公开接线时，保留未知；下文提出的 operation identity、对账和失败保留属于教学设计，不能把 Maka 的实现名词移植成 Claude Code 事实。

3. 产品能力怎样组成反馈环

下图是依据公开能力绘制的职责教学图，不是 Claude Code 源码模块图。上下文组织和执行入口是本课概括的职责名。

C → M → P → O → C 是反馈环，文件、命令和外部工具分别返回实际观察。每条回边都对应一个已经取得的结果，它可能改变下一步决策，也可能只是重复已有状态。重复结果也可能支持合法等待，但不能仅因返回一次就算一次进展。

设计验收条件是：动作请求不等于效果；没有观察不能编造成功；模型看见工具也不等于任意调用都被允许。

图中执行入口表示职责，没有声称某个内部类名。教学接口可以定义输入与结果合同，但框名不能冒充官方源码符号。

4. 压缩与 Memory 的两条链

本次对话中的旧材料与未来任务需要的信息是不同对象。前者整理工作输入，后者还需要写入、保存和后续读取。

这是用于分清职责的教学图。实线分别表示当前输入与有选择的读取；虚线表示需要单独核对的保存行为，不能因为本轮出现一条偏好就假设它必定写入。

官方的 MEMORY.md 索引与主题文件提供一个可解释的文件式实例；压缩后哪些指令重新装入有各自规则。

按本题需求，压缩后的任务状态至少包含四类信息：改了什么、哪个检查仍失败、用户允许的范围、下一步需要的观察。这是教学设计的验收条件，不声称它们是 Claude Code 真实摘要 schema。以下补充一个中途状态作为输入：已经从配置定位测试入口，测试报告 125 秒实际为 2:25、期望为 2:05，函数尚未修复；这些是给定观察，完整修复走读在第7节展开。

task: 修 README 与时间格式化函数，最后中文报告
done: 测试入口已定位，尚未完成函数修复
evidence: 125 秒的期望为 2:05，实际为 2:25
next: 核对余秒计算，修改后复测并检查 diff

当前会话整理与跨会话详细读取只在“本次工作上下文”汇合；压缩摘要没有默认写成永久用户偏好的箭头。

原始日志太大时还要单独决定怎样有界读取。Claude Code 公开的整理能力不证明它采用 Maka 的 ArchiveRead 协议；可回到 第54章说明自己怎样设计引用与回读。

5. Skill 与子任务怎样参与主任务

当前官方区分 non-fork 子 Agent 与继承父对话的 conversation fork；Skill 的 context: fork 又不能直接按后者理解。fork 的可用性取决于运行方式、版本和 fork mode，不能将交互模式选项当成所有入口默认能力。

图中先决定是否值得独立委派：不委派就由主任务继续处理；决定委派后，再选择自足说明或可用的对话分叉来提供背景。这是本课设计判断，不是声称模型固定执行这棵决策树。文件隔离使用虚线，因为独立上下文不自动创建独立文件系统。

两个子上下文的结果都汇入主任务核对点；工作区边界另行标注，因为独立上下文仍可能修改同一份文件。

本题只把“核对 README 中的命令”委派成只读子任务，主任务保留函数修改权。子任务输出应含文件位置、当前内容与结论依据，不必交回所有搜索噪声。

6. 委派接口与交接责任

下面是自拟 TypeScript 教学类型，不是 Claude Code API，也不是可直接使用的 subagent 配置。它只约束本题想传递和验收的内容，未执行。

type DelegatedTask = {
  objective: string;
  contextMode: "brief" | "conversation-copy";
  relevantFacts: { statement: string; evidence: string }[];
  readScope: string[];
  writeScope: string[];
  acceptance: string[];
};

type DelegatedResult = {
  status: "complete" | "partial" | "blocked";
  findings: { claim: string; evidence: string }[];
  changedFiles: string[];
  checks: { name: string; outcome: "pass" | "fail" | "not-run" }[];
  remaining: string[];
};

contextMode 固定输入来源；writeScope 使并行文件责任可检查；checks 让“任务返回了”与“测试通过了”成为不同状态。

这个类型没有实现 enforcement。若要做生产系统，还需把工具执行能力绑定到 scope、决定取消和部分完成语义，并验证返回内容。不能仅凭类型字段宣称隔离已经成立。

7. 具体走读：一次修复中逐步增加证据

以下是纸面推演，使用课程 fixture 的需求和故障，不是 Claude Code 真实轨迹。题设初态为 README 指向缺失脚本、实现用 % 100 计算余秒。

表 1 / Table 1 · 7. 具体走读：一次修复中逐步增加证据
步骤输入与观察（Input · Observation）现在能得出的结论下一步
1用户要求修入口和函数两项修改在题设授权内核对文件与用户已有改动
2package 定义 test: node --test测试入口可确定更新 README 的错误命令
3125 秒输出 2:25，期望 2:05至少有功能断言失败读实现并排除分钟、补零等候选
4已读代码的余秒为 % 100当前观察支持修改周期根据非负整数秒契约改为 % 60
5相关检查通过且 diff 范围正确本题证据支持交付区分已测范围与未测范围

独立只读子任务可以并行检查文档入口，但若测试依赖刚发生的编辑，测试就应等待修改完成。这里依据数据依赖安排顺序，不依据“多 Agent 应该更快”的预设。

现在加入失败：主 Agent 刚准备 Edit，用户已改了同一段 README。参考处理是重新读取和定位，保留用户意图；旧记忆中的文本不能证明当前目标仍唯一。是否可自动合并要根据实际差异判断。

再加入长日志：压缩后只知道测试失败，却看不到具体 expected/actual。正确下一步是获取可靠错误片段或重新执行有界检查；不能把摘要里没有记录的细节当作事实。

8. 设计追问与完整回答

追问一：为什么不用 CLAUDE.md 装下所有东西？

先区分持续生效的规则、按需步骤和临时观察，再讨论上下文成本。对本题，项目测试规范可以是长期规则，一份具体失败日志应有自己的证据位置。选择条目常驻还是按需，需要测相关性、漏读和下一步行动质量，不能只测文件长度。

追问二：Skills 就是子 Agent 吗？

可复用步骤与独立执行上下文是两个选择轴；同一过程可以留在主任务，也可以委派。官方支持在特定配置中把 Skill 放到子上下文，但不能据此把所有 Skill 都画成独立进程。还要区分说明正文和实际权限配置。

追问三：所有 subagents 都看不到父历史吗？

先问类型。当前文档已有 conversation fork 例外；不能照搬旧的全称结论。本题若只查测试入口，足够清晰的 brief 更容易审查；若要评估此前多轮设计的兼容性，再考虑更完整背景。无论哪种，任务返回后仍要检查证据。

追问四：启用 sandbox 就能把所有工具关在里面吗？

先定位执行 lane。官方 Bash 沙箱的覆盖范围不等于所有远端工具；初始化失败的配置也影响实际行为。如果自己的产品要求强制隔离，就必须把不可用处理写成明确验收条件，而不能只显示一个“sandbox on”标签。

追问五：有 rewind，为何还要担心命令副作用？

文件编辑工具的可回退状态不能覆盖任意 Bash 或远端动作。官方 checkpoint 有明确范围；创建远端任务后超时时，需要另行设计稳定身份、查询/对账与未知结果，不能用文件回退按钮证明远端动作未发生。

追问六：它是不是直接用了 Claude API 的 compaction？

API 支持什么与 Claude Code 默认调用什么是两种证据。公开产品资料不足以给出全部默认请求接线；默认请求形式、feature 与 provider 选路仍需具体配置或请求证据。可以比较机制，不能补写调用链。

下表是教学评估设计，不是 Claude Code 性能报告。

固定 fixture、模型配置、预算、权限与起始改动，再重复比较；记录基础设施失败，别只保留成功样例。衡量“主上下文变小”之外，还要记录整项任务的成本和结论正确性。

Memory 验证另做反事实：新请求不重复旧偏好，检查本次读入来源；移除或关闭对应读取后复测。若两种条件下都答对，仍不能仅凭输出证明记忆起作用。实验需要进一步控制其他提示来源。

10. 十个配置文件的只读核对案例

将任务改为“核对十个配置文件的部署域名，输出报告，不修改”。本例给定十个文件 deploy/app01.yaml 至 deploy/app10.yaml，规则要求 api.example.test；实际读取显示 app07 为 staging.example.test，其余九个为要求值。这些是教学输入，不是实际仓库扫描结果。

参考流程是先确认十个路径属于允许范围，按资源与工具并发条件读取，保留每份内容的字段位置；然后比较规则与实际值。发现不一致不触发 Edit，读取动作也不需要对域名发网络请求。若文件由用户并发修改，结论注明对应观察，关键交付前可重新读取发生变化的文件。

表 3 / Table 3 · 10. 十个配置文件的只读核对案例
文件范围（File Scope）读到的部署域名完整参考结论
app01–app06、app08–app10api.example.test9 项与给定规则一致
app07staging.example.test1 项不一致；报告路径和对应字段，未修改

交付可以明确写为：“已读取十个给定配置；九项符合要求，app07 的部署域名不一致。所有结论来自本次文件观察，未发网络请求，未修改文件；未核对运行中的实际部署。”若某个文件读取失败，则把它列为无法判定，不能计入九项一致或忽略分母。

该任务可直接用并行只读工具；只有文件调查需要独立多步解释时才委派只读子任务。子任务 brief 固定文件集合、预期域名、禁止修改、返回路径与原值；父任务合并十项结果并检查缺项。由于没有写入需求，Edit、写入批准和 rewind 不进入正常执行链。
