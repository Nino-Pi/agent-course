第 65 章｜观察（Observation）、对象定位（Grounding）与计算机使用（Computer Use）

本章概览

核心问题：模型（Model）知道要点“保存”，为什么仍可能改错对象，甚至把一次成功操作当成失败再做一遍？

关键概念：观察（Observation）是环境在某个时刻提供的有限信息；对象定位（Grounding）把行动意图绑定到可执行对象；观察引用（Observation Reference）说明对象来自哪次采集；后置条件（Postcondition）规定动作完成后应看到什么。

概念关系：先观察，再定位和校验，执行后用新证据判断下一步。定位正确、动作送达、界面变化和业务完成是四个不同判断。

前情回顾：从文件编辑走到界面操作

第16章解释了工具（Tool）的输入、执行和返回：编辑（Edit）前必须读到目标文本，工具返回又会成为下一次模型输入（Model Input）。这已经包含对象定位（Grounding）的基本问题——“改这一行”必须落到正确文件里的当前内容。

第17章区分授权（Authorization）和执行隔离（Execution Isolation），第18章说明缺少回执不能证明效果（Effect）没有发生。浏览器（Browser）和桌面同样遵守这些边界：一个按钮可见，不表示允许点击；一次点击超时，也不表示没有提交。

本章把任务改为一个教学场景：在测试账户的设置页中，把显示名称从“研究组”改为“课程组”，保存后重新进入页面核对。账户、原值、新值和成功条件都已给定；下面的观察结果（Observation）、编号和结果用于说明机制，没有实际操作任何账户。

1. 观察（Observation）为什么不等于环境状态（Environment State）

假设模型（Model）读到一张截图（Screenshot），右下角有“保存”按钮。截图没有告诉它：后台请求是否完成、按钮是否被透明浮层挡住、当前账户是否刚被切换。即使图像内容毫无识别错误，模型（Model）仍然只看见环境的一部分。

用一个简单的教学表示区分这些对象：

ot=O(st),at=π(ct),st+1=T(st,at,et).\begin{aligned} o_t &= O(s_t),\\ a_t &= \pi(c_t),\\ s_{t+1} &= T(s_t,a_t,e_t). \end{aligned}ot​at​st+1​​=O(st​),=π(ct​),=T(st​,at​,et​).​

sts_tst​是时刻ttt的环境状态（Environment State）；oto_tot​是观察函数（Observation Function）OOO给出的可见材料；ctc_tct​是包含目标与选定观察（Observation）的上下文（Context）；决策策略（Policy）π\piπ据此提出动作ata_tat​。状态转移（State Transition）TTT还受到外部事件（External Event）ete_tet​影响，例如用户切换账户、页面重新加载或服务器延迟响应。这组符号用于解释本章，不是某个产品的内部类型。

观察（Observation）可以正确，但不完整；也可以曾经正确，现在已经过时。 前一种情况需要补充信息，后一种需要重新观察（Re-observation）。把两种问题都叫“模型（Model）不够聪明”，就找不到合适的工程改进位置。

例如页面显示新名称，只能说明当前界面呈现了新值。如果页面采用乐观更新（Optimistic Update），它可能在服务器保存前就更新文字。本章的成功条件要求重新进入正确账户的设置页，并确认读到的是服务端持久值，而非客户端缓存（Client-side Cache）；也可以使用可信的业务查询核对持久状态（Durable State）。下面的正常案例明确假定回读接口返回服务端当前保存值。仅在单页应用（Single-page Application，SPA）内切换页面、重新看见同一文字，还不足以满足这个条件。

2. 对象定位（Grounding）：从“那个按钮”到当前对象

对象定位（Grounding）至少有两个环节。第一步是语义选择（Semantic Selection）：用户说的“保存”对应哪个控件？第二步是引用解析（Reference Resolution）：运行程序怎样把这个选择解析为当前可操作的对象？模型（Model）选对名称，并不保证第二步仍然指向同一个对象。

观察表示（Observation Representation）目标如何表示帮助解决什么仍须核对什么
文件文本（File Text）工作区、路径、匹配文本或版本把编辑意图落到具体内容文件所属工作区、文本是否已变、匹配是否唯一

应用编程接口（Application Programming Interface，API）在这里指程序直接访问业务对象的接口；结构化结果仍要带有账户和对象范围。

这些表示没有一条通用的优劣排名。可访问性树（AX Tree）可能缺少自绘画布中的对象；截图（Screenshot）能显示它们，却要另做定位。结构化应用编程接口（Structured API）提供稳定对象标识，也可能使用了错误账户或过时版本。

Playwright 的定位器（Locator）是一个有用对照：执行动作时会重新查找当前文档对象模型（DOM）元素，而不是永久保存第一次找到的节点。因此重新渲染后仍可能找到新节点。但重新解析只解决引用新鲜度的一部分；页面若切到另一个账户，同名“保存”按钮仍可能被成功找到。技术上的唯一匹配，不等于任务上的正确对象。 这一对照依据官方定位器说明，不意味着所有浏览器代理（Browser Agent）都采用相同实现。

带编号的截图（Set-of-Mark）怎样搭桥

WebVoyager 的公开方法从网页交互元素生成带数字标签的边框，并向模型（Model）提供截图（Screenshot）及辅助文本；模型（Model）输出要操作的元素编号，再由执行程序完成动作。它将“视觉上那个控件”转成可引用目标。原方法按步骤更新观察（Observation），并将执行异常交回模型（Model）；它限制在当前标签页工作，实验也有非登录任务等条件。这里讨论的是论文方法，不把它当成个人代理产品的默认实现。WebVoyager 方法与限制。

这带来一个独立的工程问题：编号只在生成它的观察（Observation）中有意义。 旧图上的元素7和新图上的元素7，不能仅凭数字相同就视为同一业务对象。运行支撑（Agent Harness）要么绑定观察（Observation）与对象，要么在执行前重新解析并检查其含义；不能把已经失效的编号悄悄解释成当前列表的第7项。

现在只改一个条件：观察2（Observation 2）之后，用户切换到了账户B。继续点击旧坐标，可能修改错误账户。重新找到一个名为“保存”的按钮也不够，因为语义范围已经变了。正确下一步是暂停当前动作，重新确认账户和目标值；账户A的任务授权（Authorization）不能随同名按钮迁到B。

这就是检查时与使用时之间的变化（Time-of-Check to Time-of-Use，TOCTOU）问题。缩短观察（Observation）与动作的时间间隔有帮助，但不能证明期间没有变化。更强的办法是让动作携带对象身份与预期版本，由尽可能靠近执行的位置检查；界面没有这种能力时，就要接受相应的不确定性，并限制动作范围。

4. Maka 的语义动作（Semantic Action）怎样绑定观察（Observation）

Maka 当前的计算机使用（Computer Use）路径提供一个具体实现对照。本节只讨论已核对的 macOS maka-cu 接线；后端选择还要求辅助执行程序和预期摘要，不能由源码存在推成所有平台均可用。

先区分三种标识（Identifier）：模型（Model）看到的观察标识（Observation ID）、后端持有的快照标识（Snapshot ID），以及快照（Snapshot）中的元素标识（Element ID）。它们负责不同边界。工具层（Tool Layer）先检查当前观察（Observation）与动作绑定，再把模型（Model）引用映射到后端观察（Observation）；后端把较短的元素编号解析成执行程序使用的令牌（Token）及摘要（Digest）。这种元素令牌（Element Token）用于引用对象，与计算上下文长度的词元（Token）不是同一含义。

沿一个元素点击（Element Click）读源码，可以看到完整的职责衔接：

  1. 观察路径（Observation Path）采集窗口材料，保存快照（Snapshot），建立元素编号、令牌和摘要的对应关系。观察（Observation）还携带采集时间及截断（Truncation）信息，避免把有限列表误读成完整窗口。
  2. 工具层（Tool Layer）将当前动作绑定到已记录的观察（Observation），检查执行租约（Execution Lease），把模型侧观察标识（Observation ID）转换为后端标识，再调用语义执行（Semantic Execution）。
  3. 后端（Backend）检查快照是否属于当前会话（Session）与工作轮次（Turn）。过期、被新观察（Observation）替代或已经消耗的引用会失效；元素不属于该快照时也不能继续分派。
  4. 执行请求（Dispatch Request）携带窗口快照、元素令牌、预期元素摘要和动作。该元素路径采用元素层面的严格性（Element Strictness），并请求动作后的新观察（Observation）；校验语义与实际效果仍依赖辅助执行程序的合同。
  5. 返回链（Return Path）分别保留效果证据（Effect Evidence）与后置观察（Post-action Observation）。工具层生成模型可读结果（Model-visible Result），新观察（Observation）通过这个结果进入后续模型输入（Model Input），而不只是保存在后端缓存里。

这种选择解决了“旧编号恰好还能解析，却已经不是原对象”的一类问题。代价是维护观察生命周期（Observation Lifecycle），并处理过期、截断和重新采集。元素层面的检查也有取舍：窗口里无关时钟变化不必让所有动作失效；但元素自身相似，并不自动证明所属业务账户仍是任务指定账户。业务范围仍需单独核对。

键盘动作（Keyboard Action）还涉及焦点（Focus）。输入文字会落到实际接收键盘事件的控件；Maka 的该路径要求已观察到的焦点或明确指定的控件，并保留物理输入干预检查。语义元素动作（Semantic Element Action）则通过可访问性接口操作目标，不能机械套用同一焦点争用假设。两条路径共享目标有效性问题，具体保护条件有区别。

“拿不到新图”不能统一翻译成“失败”

假设保存请求已经执行，随后采集新观察（Observation）超时。至少存在三种情况：

表 3 / Table 3 · “拿不到新图”不能统一翻译成“失败”
当前证据正确解读合理后续
请求在分派前被拒绝（Refused Before Dispatch）此次请求没有进入执行修正目标或重新观察，再决定是否发起动作

Maka 后端在没有新快照（Snapshot）时区分已确认效果（Confirmed Effect）与未知效果（Unknown Effect），还单独处理目标窗口按动作目的消失的情况。这里的确认仅说明该执行合同检查到的局部效果，例如可访问性树（AX Tree）的变化，并不等于账户名称已经持久保存。

继续追到工具层（Tool Layer），还会发现一个需要保留的实现边界：它会尝试补取观察（Observation）；如果已有不带图像的新观察（Observation），较丰富的采集失败不必丢弃这份有效材料。但如果完全没有所需的新观察（Observation），当前 deliveredWithoutFreshObservation 仍统一生成 outcome_unknown 的失败说明，同时保留底层效果证据（Effect Evidence）。因此后端已确认局部变化，并不保证最终给模型（Model）的状态说明也准确区分了两种不确定性。这个例子说明，审查必须追到消费者（Consumer）；上表是应当维持的语义区分，不能宣称现有每层实现都已完整做到。

5. 一个简短控制框架：先解释，再看伪代码（Pseudocode）

下面用伪代码（Pseudocode）表达教学上的顺序。这里从输入框已填入“课程组”的保存阶段开始，不重复前面的文本输入步骤。observe取得有来源的观察（Observation），bind选择目标并绑定条件，execute返回明确区分的结果，verify检查业务后置条件。它没有实现浏览器驱动、授权服务或数据库；这些名字是职责占位，不是 Maka 的可调用接口。

observation = observe(test_account)       # 观察：保留账户与采集时点
target = bind(observation, "保存")        # 定位：只引用本次观察里的对象
if not target.is_current:
    return need_new_observation           # 旧引用不能悄悄替换成当前同名对象
result = execute(target, current_scope)   # 执行：使用当前授权范围
if result.refused_before_dispatch:
    return explain_refusal(result)        # 未分派与未知效果需要不同反馈
evidence = read_back(test_account)        # 查询：不重复发送保存动作
return verify(evidence, expected_name)    # 验收：检查账户、目标值与持久结果

其中最关键的是倒数第二行：回读（Readback）取得新证据，不是再发一次原动作。如果保存操作具有额外业务效果，例如产生一条审核申请，那么“重新点击试试”就可能制造重复申请。幂等键（Idempotency Key）能否帮助恢复，要看业务服务是否实际支持；不能仅在工具参数里加一个名字就获得幂等性（Idempotency）。

6. 观察预算（Observation Budget）与评价（Evaluation）

重新观察（Re-observation）不是越多越好。每次读取整棵树或整屏图像都会占用上下文（Context）、时间和推理成本；重复相同观察（Observation）也可能淹没真正变化。合理设计要保留当前目标的来源和新鲜度，同时按任务选择局部文本、树差异（Tree Delta）或完整图像。

例如只修改一个输入框时，最新值和相关控件状态往往比整屏图片更直接；若任务是核对图表是否遮挡，结构化文本就不足以证明视觉结果。使用差分观察（Delta Observation）时还必须知道它基于哪次完整观察（Observation），否则“删除元素3”无法正确合并。上下文压缩（Context Compaction）可以保留过去的任务进展，却不能延长旧界面引用的有效期。

评价（Evaluation）至少应拆开四层：

7. 常见追问与参考答案

问题1：有视觉模型（Vision Model），为什么还需要对象定位（Grounding）？

视觉模型（Vision Model）可以识别按钮及布局，但运行程序还要把选择落实到当前窗口里的对象。识别、引用、时效和执行是不同环节；窗口变化后，旧截图上的正确坐标也可能失效。

问题2：使用语义定位器（Semantic Locator），能消除过时观察（Stale Observation）吗？

不能。重新解析可以找到当前节点，却可能找到另一账户、另一行或另一对话框中的同名对象。还要核对任务范围、对象身份及动作前置条件（Precondition）。

问题3：工具（Tool）确认发生变化，可以直接宣布任务完成吗？

要看确认的是哪一层。输入框的值变了，只是局部界面效果（Local UI Effect）；本例要求持久保存后回读。验收（Acceptance）必须采用与任务后置条件（Postcondition）对应的证据。

问题4：把观察（Observation）写进记忆（Memory），能跨会话复用按钮编号吗？

不能自动复用。记忆（Memory）可以保存“此任务处理账户A的显示名称”，不能让旧观察引用（Observation Reference）重新有效。新会话（Session）应重新观察和定位；长期知识与短期可执行引用有不同生命周期（Lifecycle）。

问题5：这部分在运行支撑（Agent Harness）中归谁负责？

工具（Tool）层负责观察（Observation）、动作引用和结果合同；宿主（Host）负责页面、窗口和环境生命周期（Lifecycle）；上下文（Context）层决定哪些材料交给模型（Model）；代理循环（Agent Loop）决定何时再观察；授权（Authorization）、效果恢复（Effect Recovery）和评价（Evaluation）分别约束能否行动、怎样处理未知、怎样判断完成。这是职责分解，具体产品可以采用不同组件划分。
