第 23 章｜Skills、插件与子 Agent

本章概览

核心问题：复用一套方法、增加工具实现与委派独立工作，分别改变系统的哪一层？

关键概念：Skill（技能说明包）：可加载的方法正文；Plugin（插件）：提供工具绑定的可信实现；代际：一次加载的实现身份；Subagent（子代理）：独立的关联子会话；Artifact（产物）：可供父任务检查的输出。

关系主线：方法经加载进入输入，插件经发布和激活提供能力，子任务交回状态与产物；权限、在途调用和父任务验收分别处理。

前置：执行身份、工具与执行边界。

核心路线

方法复用与独立委托

Skill 和 Subagent 改变系统的方式不同：

  • Skill 主要提供 Agent 可采用的方法说明；
  • Subagent 创建一个新的受控执行者，让另一条 Session/Run 去 独立做一部分工作。

子任务之间还有依赖时，第24章 的调度机制决定它们何时开始。

文档规范与独立检查

文档任务是：

检查 package.json 与 README.md，把 README 的测试步骤更新正确，运行测试；以后请用中文解释结果。

现在增加两个需求：

  1. 项目要求 README 必须遵循一套固定文档规范；
  2. 修改前，希望有另一个 Agent 独立检查 package.json 与 README 是否一致。

第一项适合 Skill，第二项可能适合 Subagent。

图中的 Skill 分支增加父任务的方法输入；child 分支另有执行身份，检查结果再交回父任务。两项分支不表示谁必须先完成。

为什么模拟专家不等于创建子任务

一个非常简单的 Agent 系统可能把两者都实现为“往 Prompt 里塞一段文字”：

Skill:
  system prompt += 文档规范

Subagent:
  system prompt += 请模拟另一个专家再检查一遍

第一种做法可以勉强表达 Skill。第二种做法却没有创建新的执行者：

  • 没有新的 Session 或 Run identity；
  • 没有独立 Context；
  • 没有独立工具和权限边界；
  • 无法单独停止、观察或恢复“子任务”；
  • 所谓“另一个专家”仍然只是同一次模型生成中的角色扮演。

因此，真正的 Subagent 需要一个可识别、可约束、可观察的执行生命周期。

Skill：给 Agent 一份可复用说明书

Skill 解决什么问题

许多任务不是缺少工具，而是缺少稳定的方法。例如文档评审可能要求：

  • 先核对测试命令的真实来源；
  • 不把未运行的测试写成已通过；
  • 更新正文后检查相对链接；
  • 最后按固定模板报告变更和证据。

如果每次都让用户重新写这些要求，容易遗漏，也会让 Prompt 变长。Skill 把方法、检查清单、脚本说明或模板组织成可重复加载的内容。

Skill 改变了什么

在教学案例中，加载文档 Skill 后，R7 可以知道：

先读项目规则
→ 从 package.json 核对测试命令
→ 修改 README
→ 检查链接
→ 只报告实际运行过的验证

它改变的是 R7 的工作方法和可用上下文。

看见名字、加载正文、采用方法是三步

假设 documentation-review 的描述是“核对项目测试说明”，正文包含：

先从 package.json 找到真实测试入口。
修改 README 后运行该入口；失败时保留失败输出。
报告修改、实际验证和仍未证明的内容。

这是教学用的短正文。模型只看到名字和描述时，本次输入还没有这三条正文要求，不能声称已经读过这份方法。正文可以由用户显式调用时预先加载，也可以由模型在后续步骤按需加载；两者都要确保正文实际进入输入。按需路线经过以下步骤：

按需路线如下；箭头只到工具选择，实际调用仍要经过权限（Permissions）与执行边界（Execution boundary）。

SkillSearch 只找候选，Skill 才取得正文。加载成功仍不证明模型已经遵循方法，更不证明附带脚本已经执行或测试通过；后面这些结果需要各自的工具观察。两种入口都为本次普通 Turn 提供方法，不创建独立执行者。两种入口的消费链见正文加载。

Skill 没有改变什么

Skill 本身不会自动：

  • 创建新的 Run；
  • 获得本来没有的 Write 或 Bash 工具；
  • 扩大 ExecutionBoundary；
  • 绕过用户批准；
  • 证明附带脚本可信；
  • 让 Agent 在未来自动更新这份 Skill。

它的作用范围是：

Skill = 方法与上下文增强
Skill ≠ 新执行者
Skill ≠ 新权限

Subagent：创建一个受控的关联子会话

Subagent 解决什么问题

当一部分工作需要独立 Context、可以并行、应有单独结果或不应污染父任务主线时，可以委托给 Subagent。

在这个案例中，child 只检查配置和说明是否一致，父任务负责采纳结论并修改。父任务可以先整理文档规范，待这次检查返回再编辑 README，避免把 child 观察到的旧内容误当成修改后的状态。委托要明确目标、输入、允许做什么和结果格式；自然语言中的“只读”还要由实际工具与执行边界落实。

Maka 的当前主路径

Maka 的 production Subagent 主路径是 durable linked child Session。通俗地说：

  1. 父 Run 提出创建 child 的请求；
  2. Host 检查 lineage（父子关联）、深度、数量和能力边界；
  3. 创建一个与父任务有关联、但身份独立的 child Session；
  4. child 在自己的 Session 中运行普通 AgentRun；
  5. child 的 terminal 结果被父任务读取或接收；
  6. 父 Run 根据这个结果继续自己的 model step。

它没有另造一套“Subagent Runtime”。child 最终仍走普通 Hosted Execution 主干。

用同一个案例逐步重放

第一步：父 Run 决定是否需要委托

R7 先判断任务是否真的值得创建 child。如果检查只需读两行配置，直接调用 Read 可能更简单。Subagent 会增加：

  • 新的身份和 Context；
  • 调度与等待成本；
  • 结果整合成本；
  • 取消和失败处理。

第二步：冻结最小子任务

父任务不应只说“帮我看看项目”。先通过系统配置把 child 的可执行能力限定为只读检查，再给出自足的任务文字：

比较 package.json 中的测试命令与 README 当前测试说明。
只读，不修改文件。
返回：每个不一致项、观察到的原文与文件位置、推荐修改。

目标、输入、能力上限和输出形状越明确，父任务越容易判断结果是否可用。任务中的“只读”表达意图，冻结后的 tool ceiling（可用工具集合的上限）与 ExecutionBoundary 负责强制执行。

第三步：child 独立运行

C1/CT1/CR1 在自己的 Context 中读取两个文件并形成结论。它可能调用多次模型和工具，但这些都属于 child 的执行事实，不与 R7 的事件混成同一个 Run。

第四步：父任务消费结果

CR1 完成不等于 R7 自动完成。父任务还要：

  1. 判断 child 的观察和结论是否充分，文件是否已被其他操作改变；
  2. 在用户已有授权内执行 README 修改，需要扩边时再走授权链；
  3. 运行测试；
  4. 生成最终回答。

第五步：处理 child 失败或取消

如果 child 失败，父任务至少需要知道：

  • child 是未开始、运行失败、被取消，还是结果不确定；
  • 是否可以改由父任务直接处理；
  • 已返回的部分结果能否安全使用；
  • 父任务取消时是否应该级联取消 child。

这也是为什么真实 Subagent 需要独立生命周期，而不仅是 Prompt 中的一个角色。

核心问题解析

问题 1。 项目给出一份文档 Skill，为什么不会因此获得新的文件或网络权限？

解释。 Skill 增加方法与上下文；实际工具绑定、权限和隔离由执行系统决定。说明书不能自行改变这些边界。

问题 2。 child 已完成只读检查，为什么父 Run 仍不能直接算完成？

解释。 child 的结果只是父任务的输入。父任务仍需检查结论，执行目标修改、运行验证并形成自己的终态。

问题 3。 只需读取两行配置时，怎样判断是否值得创建 child？

解释。 先比较独立上下文或并行检查的收益与交接、等待、结果整合成本；直接 Read 已能解决时无需增加一份执行。

问题 4。 模型在 SkillSearch 中找到 documentation-review，能否直接声称已经读过正文、执行了检查？

解释。 不能。搜索返回候选信息，按需路线还需要 Skill 返回正文，再由模型选择工具并取得检查结果。若用户显式调用已将正文注入本轮，则无需重复加载，但执行结果仍需独立证据。

问题 5。 child 返回 README 某行仍是旧命令，父任务刚刚编辑了那一行，应直接按 child 建议再改一次吗？

解释。 不应。child 的结果反映它读取时的内容；父任务应核对当前文件及差异，判断建议是否仍适用。独立执行者和共享文件的当前状态需要分别确认。

实现深化

正文加载、实现绑定与独立执行有不同生命周期。worktree（同仓库的独立 Git 工作副本，后文展开）中的修改还受到 第18章 的效果恢复条件约束；有依赖的子任务由 第24章 的 Graph协调。

一个 Turn 冻结了什么：不只是目录名字

当前默认 Interactive composer 按 sessionId + turnId 缓存同一份 canonical inventory（本轮采用的方法目录与正文快照），供 prompt 目录、SkillSearch 和 Skill 共用。扫描结果包含去掉文件开头元数据块（frontmatter）的 content 与原文件的 contentSha256；repository 冻结这些扫描记录。Skill 直接读取记录中的 content，清洗并按长度截断后返回 instructions，不会在这一步重新打开磁盘上的 SKILL.md。

所以，在下面这个单 Turn 例子里，正文与名字一起保持一致：

S1/T7 首次组成输入：快照里是 old / OLD_DESCRIPTION / OLD_BODY
目录更新：现在可发现 new / NEW_DESCRIPTION / NEW_BODY
T7 调用 Skill(old)：仍返回 OLD_BODY
S1/T8 首次组成输入：重新取得目录，可看到 NEW_DESCRIPTION

这里演示的是 inventory 被替换后的读取选择，不能由此推导整个文件系统在并发更新时也保持同一快照。

冻结也有明确范围。正文提到的其他文档、脚本或网络资源没有因此一起快照化，之后读取或执行仍是新的工具动作。上述 resolver 是有界的进程内缓存，不能据此推导任意重启后的永久正文快照保证。显式 invocation 则先通过独立的 inventory 读取生成已加载用户内容，再随准入保存；不要把这次读取与稍后的 composer inventory 读取说成同一个原子操作。

Skill 来源与依赖的边界

为什么 Skill 仍然需要安全审查

“只是文字”不代表没有风险。Skill 可能引导 Agent：

  • 读取不必要的敏感文件；
  • 运行来源不明的脚本；
  • 把数据发送到外部服务；
  • 把一次临时做法写成长期规则。

强制边界仍由工具、Permission 和 Sandbox 承担，但 Skill 的来源、内容和依赖也属于供应链治理问题。这类似于：说明书不能打开上锁的门，但坏说明书仍可能诱导拿着合法钥匙的人走错房间。

方法正文没变，执行工具却换了一代

Skill 解决“如何做”的复用，Plugin 可以提供实际可调用的实现。这里讲已经安装、受信任的 Host 插件；扫描到一份 SKILL.md 不会因此执行插件代码。

热更新首先要区分同名工具的不同实现。generation 是这次加载的绑定代次，retired 表示这代绑定不再接受新调用，activeCalls 是已经进入这代实现、尚未退出的调用数。下面用一个教学对象表示它们，不是调用 API：

绑定 B = (作用域, entry, extension, generation, name, schema)
运行状态 = (是否 retired, 已进入的 activeCalls 数)

entry/extension 标识插件入口与扩展，name/schema 是工具名称与参数结构。同名、同参数结构的工具，也可能绑定到不同代次的代码。正常调用依次经过四步：

  1. 加载一代代码。 TrustedPluginPackageLoader.loadInstalled 从已安装包加载独立代码代次。加载出来只说明代码可供组成，还没有向模型发布工具。
  2. 发布工具绑定。 MakaCompositionLoader 先暂存贡献的工具，再提交发布。交互运行的组成者通过 PluginToolService 取得当前 Session 的有效绑定。
  3. 冻结本步工具表。 每个逻辑 step 重新取得可用工具快照。ToolAvailabilityRuntime.prepare 比较 Turn 保存的激活身份；如果实现换代，旧的搜索激活资格会被清除。
  4. 调用这份实现。 模型依据本步声明返回请求，ToolRuntime 再检查调用条件并进入相应工具。包已加载、绑定已发布、本步已激活、实现已进入，是不同状态。

卸载旧代也有顺序：先标记 retired、拒绝新进入，再等已进入调用的 finally 将 activeCalls 减到零。退役负责等待和清理，不会强制杀死正在运行的插件，也不撤回它已经产生的效果。

Skill 的发现与读取快照

假设目录已展示，正文随后从“运行命令A”改成“运行命令B”。Maka 本 Turn inventory 缓存有效时，lazy Skill 读扫描所得 content，仍可返回A；Codex 的普通 Host Skill 按关联 filesystem 读取选定正文，如果该来源可变，此时可能返回B或读取失败。后者的 snapshot 主要保存发现结果与来源关联。来自不可变 plugin generation 的文件、executor/orchestrator 的分页缓存另有规则，不能由这一例推断所有 Codex Skill 都立即刷新。

这里比较的是“发现目录后、实际加载正文前”的变化。第41章的分页快照则追踪本地 executor-backed 路径同一次读取的后续页：继续页命中缓存时会延续那份正文。发现时记录了什么，与一次分页读取保持哪份内容一致，时间范围不同。

因此选型取决于复用对象：复用方法文字用 Skill；增加可信执行实现及热替换用 Plugin 的绑定与清理合同；另起有独立任务/历史的执行者用 child。如果产品要求“审核过的确切正文及脚本在重启后继续使用”，应把内容和资源版本纳入持久合同，仅靠任一 snapshot 名称都不够。

变式一：Skill 已载入，但 check_docs 被卸载。模型还能因为方法正文要求它，就继续调用旧工具吗？

参考答案

不能。已加载文字是输入历史，不是当前可执行 binding。新 step 可能已经没有该工具；旧 wrapper 如果 retired 也拒绝新进入。已经进入 impl 的 A 仍需收束，不能从卸载推导它没有产生效果。

变式二：产品要求同名、同 schema 的 g18 自动继承 g17 激活，只按名字缓存是否足够？

参考答案

这会改变当前合同：旧代实现的搜索激活将自动延续到新实现；这是可用性资格，执行权限仍独立核对。要这样设计，必须另行定义等价性、审核与失效策略；不能只删掉 generation 就说仍保留原保证。若需求反而是审核内容在恢复后不漂移，则还要持久保存确切正文与资源，代际内存对象本身也不能完成跨重启合同。

只读 child 的实际约束

在案例中，父任务要修改 README；子任务只负责只读检查：

definition/profile：选择 `local_read` preset
输入：package.json、README.md、检查问题
输出：不一致项和证据
任务文字：只读，不修改文件，不运行有副作用命令

这里必须区分“告诉 child 不要做什么”和“系统真的不让它做什么”。任务文字表达委托意图；真正的 enforcement 来自 local_read definition/profile 冻结的 explore mode、只包含 Read / Glob / Grep 的 tool ceiling，以及最终的 ExecutionBoundary。只在 Prompt 里写“禁止修改”并不能构成安全边界。

如果把代码修改也委托出去，改的是哪一份文件

上面的只读 child 有独立对话，文件仍从父任务的工作目录读取。Context 独立、工具受限、文件工作副本分离是三种不同机制。 Maka 的 implementation profile 才会要求 Host 建立独立 Git worktree，也就是同一个 Git 仓库的一份单独工作副本；它可以运行本地修改与 shell 工具，最后交回 patch。worktree 自身不等于 OS sandbox，实际访问许可仍由执行边界决定。

理解起点时，先分开 Git 的已提交版本和工作目录当前文件。提交记录某一版文件；HEAD 通常指向当前分支，由此确定当前检出的提交，也可能直接指向某个提交。工作目录中的未提交编辑不会自动进入该提交。本节的 dirty（有改动）表示 Git 状态检查发现尚未提交的变化；没有这些变化时称为干净。

例如，HEAD 中的 README 仍写 npm run check，父工作目录却已将它改为 npm test、尚未提交；直接从 HEAD 建立的副本不会包含这次编辑。本节所查的 Maka fresh worktree 路径会拒绝这样的 dirty 起点，避免静默漏掉父目录改动。这是该创建路径的约束，不是 Git 一概禁止从有改动的目录创建 worktree。

下面重新以父工作区干净、已提交 README 仍含错误测试命令为初态，沿用“修改 README 测试步骤”的子任务。这是依据源码设计的状态轨迹，没有实际创建 child：

表 5 / Table 5 · 如果把代码修改也委托出去，改的是哪一份文件
时点child 工作副本父工作副本与可得结论
创建前尚不存在父 Git 工作区干净；Host 从其 HEAD 建立 child 的起点
child Edit 并测试README 已修改，child 保存自己的观察父 README 仍未因此改变；child 测试只说明它测试的那份状态
child Run 到达终态文件 delta 仍在 worktree；Host 还须确认没有活动运行资源completed 本身不证明补丁已经发布
Host 发布结果保存相对起点的 workspace.patch Artifact父收到 child 状态、摘要和产物 ID；仍不是自动合并
父任务采纳child 原产物可供追溯父检查 patch、决定如何应用或重做修改，再验证最终工作副本

这解释了“结果交回”和“父任务验收”的差别。child 说测试通过时，父任务仍要检查测试范围、补丁内容和自己的当前文件是否已变化，不能只转述成功文字。若父目录后来已有另一份 README 修改，是否还能采用该 patch 需要新的判断；创建 child 时的干净起点并不保证未来合并无冲突。

两个失败窗口尤其值得辨认：

  • 父目录本来就有未提交修改：当前 fresh worktree 路径会拒绝创建，而不是默默从 HEAD 出发漏掉这些修改；父任务必须重新选择和确认工作起点，不能假定 child 已看到 dirty state。
  • child 已结束，但发布前失败：恢复逻辑可以在最新 child Run 已 terminal 时，从仍保留的 worktree 补发它的 patch；已发布的产物会复用。它不能任意重建所有历史 Turn 的旧补丁。child 失败或被取消也可能留下修改，产物存在不代表修改可采纳。

父子之间的上下文与能力继承

父子关系中哪些东西不会自动相等

父 Session S1 与 child Session C1 具有 lineage，但不应该因此假设：

表 6 / Table 6 · 父子关系中哪些东西不会自动相等
项目是否自动完全继承为什么
父会话全部聊天历史否child 只应获得完成任务所需的上下文
父 Run identity否child 有自己的 Session、Turn、Run
父工具集合否child capability 应按委托和 policy 计算
父执行边界（ExecutionBoundary）否能力扩张必须显式受控
父记忆（Memory）否跨 Session 记忆需要明确读取和治理
父任务目标部分child 获得的是边界明确的子目标
结果与状态（Result / State）否child 有独立 terminal，父任务再消费结果

父子关联只建立 lineage；哪些内容会跨过去，取决于对应的组合、委托和授权合同。

上下文分叉的实现边界

上下文分叉不是操作系统 Copy-on-Write

“从父任务分出 child”容易让人联想到操作系统 fork() 的 Copy-on-Write（CoW）：先共享内存页，写入时再复制。这个类比只能帮助理解“分叉后各自演进”，不能当成 Maka 的上下文实现说明。

LLM Context 不是平坦、只读、由 MMU 管理的内存页。它可能包含用户消息、模型输出、工具结果、权限事件和已经过时的试错路径；把父历史全部交给 child 会同时带来噪声、隐私与 token 成本。Maka 的直接 child 默认获得独立历史，由冻结的角色配置、工具边界和显式 task 构造初始工作集，而不是自动引用父会话前缀后再做“写时复制”。

从一次委托到多 Agent 协调

Operator 与 Participant：先问 child 扮演什么角色

Maka 的官方设计文章把协作角色分为下面两类。这个区分用于理解设计取向，并不说明产品已经提供了表中所有通信能力。

表 7 / Table 7 · Operator 与 Participant：先问 child 扮演什么角色
角色视角怎样协作主要协调状态放在哪里
Operator（算子）接受边界封闭的任务，在受限 Runtime 中工作，终态交回结果或 artifact ref显式任务、Graph 拓扑与调度状态
Participant（参与者）有可寻址身份和私有 Mailbox，可在多轮消息中补充、追问或横向协商多个 Agent 的会话与消息流

Maka 的直接 agent_spawn 更接近前者：parent 交付自足的 task，child 在独立 Session/Run 中完成，然后做一次有界结果回传。当前这条直接父子路径没有让 parent 与 child 共享 Mailbox，也没有给 sibling child 暴露持续横向协商通道；前端能看到 child 的执行事件属于可观察性，不等于 Agent 间通信。

这个区分还能防止把两个层次混在一起：

direct agent_spawn = 创建一个边界明确的 child Operator
Agent Graph         = 用拓扑、revision、claim 与 wake 编排多个 Operator

因此，调用一次 agent_spawn 不等于 已经进入 Agent Graph 路径。Graph 还要有独立持久化的 topology、Schedule Revision、claim 与 supervisor-wake 控制机制；一张刚创建的图未必已经抵达 checkpoint，所以不能用“当前是否已经产生 wake”判断图是否存在。其推进过程见 第24章。

压缩后的子任务结果，是否足够让父任务决策

继续让只读 child 检查 README 与配置。普通 agent_spawn 的 task 被送入独立 child Session；返回时，Maka 组合 invocation status、有界 summary 和 Artifact IDs。当前 summary 在最后一次完整文本非空时优先取它，否则用流式尾部或错误文字，不会回溯较早完整事件，最多4,000个 JavaScript 字符；它不是自动生成的一份完整证据报告。父模型通过普通工具结果的有效投影读到它，再决定要不要补读原文。

为这类委托设计两个教学对象：

委托输入 I = (明确子问题, 可用背景, 能力边界, 输出要求)
交回证据 E = (child身份与状态, 观察范围, 结论, 证据位置, 未知项)

I/E 表示任务文字与结果应覆盖的语义，不是 Maka 已强制验证的完整 schema。例如 I 明确“仅检查脚本和说明，返回原文位置，不推断测试通过”；E 应报告“package.json有npm test，README写npm run check；未运行测试”。如果 E 只剩“应改为npm test，一切完成”，父任务就丢失了决定是否已验收的关键信息。保留结论却删掉观察范围，可能比少传一点背景更危险；子任务输出压缩和 第19章 的上下文压缩都要说明哪些决策前提必须保留。

表 8 / Table 8 · 压缩后的子任务结果，是否足够让父任务决策
父任务收到的东西已证明什么本例中还要做什么
child status=completed这次子执行有其完成状态核对它实际检查了什么，不等于主任务通过
summary 给出两处不一致子模型报告了观察和建议必要时回读当前正文，检查是否已被修改
implementation child 的 patch Artifact可定位交回的工作副本差异检查状态/差异，再决定采纳；不会自动合并到父目录
父侧修改并获得验收证据有了针对最终状态的检查才能按 第26章 的任务要求报告完成

同题的另一种实现是持续通信。 Codex 的可寻址消息协作路径（实现中称 Multi-Agent V2）把发消息和触发新工作分开：普通消息先入队，活跃 Turn 在允许消费输入的 step 边界接收；follow-up 请求还能在目标空闲、容量等条件满足时开新普通 Turn。这适合发现新线索后继续协商，而 Maka 本例的 foreground child 更适合输入明确、返回有界结果的一次委托。这条路径有个细节：queue-only 表示仅投递消息，通常不单独启动普通空闲任务；但目标没有活跃 Turn、仍保留 durable sleep（持久等待）记录时，也可触发新的普通 Turn 处理等待中的工作。它不重开旧 Turn，也不恢复旧调用栈；第41章会展开该接收分支。消息已提交不证明目标读过或完成任务，也不能由正常投递流程推导崩溃后邮箱必然完整恢复。

选择持续通信，需要额外定义谁可以发什么、接收时点、旧消息的相关性、重复与取消，以及谁最终提交结论。若几个只读检查相互独立，先用普通委托或 DAG 即可；若结果不断改变对方的任务，再考虑通信模式。目录共享、工具授权与结果合并仍分别设计，多一套消息 API 不会自动解决它们。

并行收益与约束变化

时间推演的条件是：两个独立只读检查 A/B 分别需8秒和12秒；设置与派发总计3秒，整合5秒，最终检查7秒。假定资源足够、没有排队与失败，并保持其他开销相同：

顺序安排：3 + 8 + 12 + 5 + 7 = 35 秒
并行安排：3 + max(8,12) + 5 + 7 = 27 秒

并行省下的是重叠执行的8秒，最终整合和验证仍在关键路径上。这里比较同一分工的两种安排，没有证明它比单 Agent 直接处理更快；token 总量还要累加父子输入、输出、重试，不能只按27秒计成本。并发上限、累计 child-run 上限和失败收敛也可能改变这个理想时间。

变式一：总预算30秒，但父任务在 child 回来前改了配置，必须再用6秒核对原观察。还能照原推演说按时完成吗？

参考答案

不能沿用27秒。若新增核对不能与剩余步骤重叠，理想时间成为33秒，已超预算。应调整计划、缩小有授权的交付或如实说明未完成验证；不能用 child completed 或旧观察省略最终状态检查。新增共享写冲突也会破坏原来的独立前提。

变式二：child 的摘要说“已修好”，状态却是 failed，且返回 patch。父任务能直接合并并宣布主任务完成吗？如果改用消息协作，send 成功能代替验收吗？

参考答案

不能。失败也可能留下有用甚至部分正确的 patch；父任务需核对失败原因、完整差异、当前工作副本和检查结果，在已有授权内决定是否采纳。summary、status、artifact 和主任务验收是不同证据。消息协作的 send 成功也只说明提交被接受，不证明对方已经阅读、做完或结论正确；它不能替代结果和验收链。

机制问题解析

问题 1。 child 的任务文字说“只读”，具体什么机制才限制修改？

解释。 本例由 local_read definition/profile 固定 explore mode、Read/Glob/Grep ceiling，并结合 ExecutionBoundary 执行；提示词表达意图，不能代替强制约束。

问题 2。 为什么分出 child 不能理解为自动共享父历史的 OS Copy-on-Write？

解释。 当前直接 child 有独立历史，使用冻结配置与显式 task 组成工作集；不能借 OS 内存页语义解释 LLM Context。

问题 3。 为什么直接 agent_spawn 不能证明已拥有 Graph 或 Mailbox？

解释。 spawn 是一次有界委派；Graph 还需要拓扑、revision、claim/wake，Mailbox 还需要独立消息投递与唤醒契约。

问题 4。 在上面的 T7 快照例子中，目录更新后加载 old 会得到什么？正文引用的脚本是否也被冻结？

解释。 T7 的按需加载返回快照中的 OLD_BODY；T8 首次组成输入才重新读取 inventory。附带脚本没有被这一正文快照冻结，不能推导其内容或运行结果。

问题 5。 一个 Skill 的 required-tools 包含 Bash，但当前 Host 没有 Bash；把它改成 allowed-tools 是否就能运行命令？

解释。 required-tools 不满足会阻止资格；改成 allowed-tools 只改变声明，不会产生 Bash 工具或执行许可。既不能把加载成功当成授权，也不能把授权当成实际执行。

问题 6。 implementation child 返回 completed 和 patch ID，父 README 是否已经改变？如果父目录在创建前已有未提交修改，会发生什么？

解释。 不一定；这条 write-back 链发布产物，没有自动合并到父目录。父任务仍须检查、采纳并验证。fresh worktree 在父目录 dirty 时拒绝创建，不能假定 child 复制了未提交修改。

问题 7。 child Run 已 terminal，但 Host 在发布 patch 前退出；能否仅凭这个终态认定产物已交回？恢复可以补什么？

解释。 不能，Run terminal 与 Artifact 发布是两个事实。在绑定仍有效且工作区无活动运行资源的条件下，恢复可在最新 child Run 已 terminal 时补发它尚未发布的 patch；它不是任意历史 Turn 的快照恢复。
