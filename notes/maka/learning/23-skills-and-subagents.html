第二部分：Maka 核心机制与任务接续 · 23 / 62

第 23 章｜技能说明包（Skill）、插件（Plugin）与子代理（Subagent）的职责边界

本章概览

核心问题：复用一套方法、增加工具（Tool）实现与委派独立工作，分别改变系统的哪一层？

关键概念：技能说明包（Skill）：可加载的方法正文；插件（Plugin）：提供工具（Tool）绑定（Binding）的可信实现；代次（Generation）：一次加载的实现身份（Identity）；子代理（Subagent）：独立的关联子会话（Linked Child Session）；产物（Artifact）：可供父任务（Parent Task）检查的输出。

关系主线：方法经加载进入输入，插件（Plugin）经发布和激活提供能力（Capability），子任务（Child Task）交回状态（State）与产物（Artifact）；权限（Permission）、在途调用和父任务（Parent Task）验收（Acceptance）分别处理。

前情回顾：复用什么，就要找到谁来消费

第13章用会话（Session） S1、工作轮次（Turn） T7、执行（Run）R7 区分长期归属、一项要求和一次具体运行。第16章说明工具（Tool）的名字与参数结构（Schema）只是声明，实际调用还要检查并执行；第17章把方法文字与可执行权限（Permission）分开。第18章进一步说明，有返回结果也可能仍需核对文件现态。

本章将这些关系放进协作：方法正文交给模型输入（Model Input），插件（Plugin）绑定（Binding）交给工具（Tool）执行链（Execution Chain），子任务（Child Task）结果交给父任务（Parent Task）。三个消费者（Consumer）不同，所增加的状态（State）也不同。先看它们各自解决哪一部分问题，再追踪发现、加载、执行与结果交接。

核心路线

方法复用与独立委托

复用一段方法、安装一份实现和另请一个执行者，都可以帮助同一项任务，却要经过不同的消费链：

表 1 / Table 1 · 方法复用与独立委托
复用对象输入交给谁新增什么状态（State）本例中的作用
技能说明包（Skill）的方法正文本次或后续模型输入（Model Input）已加载的方法内容；不另开工作身份（Work Identity）规定怎样核对文档和报告验证
插件（Plugin）提供的工具（Tool）实现宿主（Host）发布的工具（Tool）绑定（Binding）与实际调用入口可调用实现的代次（Generation）、激活与退役（Retired）状态（State）提供可信的 check_docs 实现
子代理（Subagent）的独立任务关联子会话（Linked Child Session）中的普通代理执行（AgentRun）独立工作身份（Work Identity）、历史、结果与终态（Terminal State）只读核对配置和说明，交回观察（Observation）

这张表按责任分组，不能把“方法写了要调用工具（Tool）”直接跳接成“插件（Plugin）实现已经执行”，也不能把方法加载当成创建了另一份工作。

子任务（Child Task）之间还有依赖时，第24章的调度机制决定它们何时开始。

文档规范与独立检查

文档任务是：

检查 package.json 与 README.md，把 README 的测试步骤更新正确，运行测试；以后请用中文解释结果。

沿用第13章只改 README 的初态：package.json 提供 "test": "node --test"，README 错写 npm run check；函数已经正确，四项既有测试原本通过。父任务（Parent Task）只获准修正文档并检查结果，不把这里当成第04章尚含函数缺陷的初态。前面这句用户要求保留了中文偏好，但本章只追踪委派与工具（Tool），不据此声称偏好已写入长期记忆（Long-Term Memory）。

父任务（Parent Task）属于会话（Session） S1、工作轮次（Turn） T7、执行（Run）R7；另建的子任务（Child Task）用 C1、CT1、CR1 表示自己的会话（Session）、工作轮次（Turn）和执行（Run）。以下身份（Identity）、热替换与失败过程都是教学记号及源码推演，本章没有实际创建子任务（Child Task）或运行模型（Model）。

现在增加两个需求：

  1. 项目要求 README 必须遵循一套固定文档规范；
  2. 修改前，希望有另一个智能代理（Agent）独立检查 package.json 与 README 是否一致。

第一项适合技能说明包（Skill），第二项可能适合子代理（Subagent）。后文若接入可信的 check_docs，将另行说明插件（Plugin）实现；本例并不要求为两份文件安装新插件（Plugin）。

图中的技能说明包（Skill）分支增加父任务（Parent Task）的方法输入；子代理（Subagent）分支另有工作身份（Work Identity），检查结果再交回父任务（Parent Task）。两项分支不表示谁必须先完成。

为什么模拟专家不等于创建子任务（Child Task）

一个很小的智能代理（Agent）系统可能把两种要求都化为提示词（Prompt）追加：给现有输入增加“文档规范”，或者增加“请模拟另一个专家再检查一遍”。前者能表达方法注入的最小含义；后者只改变同一次生成应扮演的角色，还没有创建新的执行者：

  • 没有新的会话（Session）或执行（Run）身份（Identity）；
  • 没有独立上下文（Context）；
  • 没有独立工具（Tool）和权限（Permission）边界；
  • 无法单独停止、观察或恢复“子任务（Child Task）”；
  • 所谓“另一个专家”仍然只是同一次模型（Model）生成中的角色扮演。

因此，真正的子代理（Subagent）需要一个可识别、可约束、可观察的执行生命周期（Lifecycle）。

技能说明包（Skill）：给智能代理（Agent）一份可复用说明书

技能说明包（Skill）解决什么问题

许多任务不是缺少工具（Tool），而是缺少稳定的方法。例如文档评审可能要求：

  • 先核对测试命令的真实来源；
  • 不把未运行的测试写成已通过；
  • 更新正文后检查相对链接；
  • 最后按固定模板报告变更和证据。

如果每次都让用户重新写这些要求，容易遗漏，也会让提示词（Prompt）变长。技能说明包（Skill）把方法、检查清单、脚本说明或模板组织成可重复加载的内容。

技能说明包（Skill）改变了什么

在教学案例中，加载文档技能说明包（Skill）后，R7 可以知道：

先读项目规则
→ 从 package.json 核对测试命令
→ 修改 README
→ 检查链接
→ 只报告实际运行过的验证

它改变的是 R7 的工作方法和可用上下文（Context）。

看见名字、加载正文、采用方法是三步

假设 documentation-review 的描述是“核对项目测试说明”，正文包含：

先从 package.json 找到真实测试入口。
修改 README 后运行该入口；失败时保留失败输出。
报告修改、实际验证和仍未证明的内容。

这是教学用的短正文。模型（Model）只看到名字和描述时，本次输入还没有这三条正文要求，不能声称已经读过这份方法。正文可以由用户显式调用时预先加载，也可以由模型（Model）在后续步骤按需加载；两者都要确保正文实际进入输入。按需路线如下；箭头只到工具（Tool）选择，实际调用仍要经过权限（Permission）与执行边界（Execution Boundary）。

SkillSearch 只找候选，Skill 才取得正文。加载成功仍不证明模型（Model）已经遵循方法，更不证明附带脚本已经执行或测试通过。可以按每一步新增的材料判断：

表 2 / Table 2 · 看见名字、加载正文、采用方法是三步
当前阶段新增材料下一位消费者（Consumer）还要决定什么
找到候选名字、描述与来源关联是否值得加载正文
取得正文这次实际读取的方法内容哪些要求适用于当前授权和文件状态（State）
依据方法提出请求结构化工具调用（Tool Call）工具（Tool）执行链（Execution Chain）核对参数、可用性与执行许可
取得检查结果原文、退出结果或差异等观察（Observation）父任务（Parent Task）核对覆盖范围，再报告可支持的结论

后面这些结果需要各自的工具（Tool）观察（Observation）。两种入口都为本次普通工作轮次（Turn）提供方法，不创建独立执行者。两种入口的消费链见正文加载。

技能说明包（Skill）没有改变什么

技能说明包（Skill）本身不会自动：

  • 创建新的执行（Run）；
  • 获得本来没有的 Write 或 Bash 工具（Tool）；
  • 扩大 执行边界（Execution Boundary）；
  • 绕过用户批准；
  • 证明附带脚本可信；
  • 让智能代理（Agent）在未来自动更新这份技能说明包（Skill）。

从状态（State）变化看，加载成功只增加模型（Model）可以读取的方法正文；谁运行、有哪些工具（Tool）、哪次调用能获准，仍由原执行链（Execution Chain）负责。方法的来源可信度和执行边界（Execution Boundary）也需要分别判断。

子代理（Subagent）：创建一个受控的关联子会话（Linked Child Session）

子代理（Subagent）解决什么问题

当一部分工作需要独立上下文（Context）、可以并行、应有单独结果或不应污染父任务（Parent Task）主线时，可以委托给子代理（Subagent）。

在这个案例中，子代理（Subagent）只检查配置和说明是否一致，父任务（Parent Task）负责采纳结论并修改。父任务（Parent Task）可以先整理文档规范，待这次检查返回再编辑 README，避免把子代理（Subagent）读取时得到的旧内容误当成修改后的状态（State）。委托要明确目标、输入、允许做什么和结果格式；自然语言中的“只读”还要由实际工具（Tool）与执行边界（Execution Boundary）落实。

Maka 的当前主路径

Maka 当前生产路径中的子代理（Subagent）是关联子会话（Linked Child Session）。通俗地说：

  1. 父执行（Run）提出创建子代理（Subagent）的请求；
  2. 宿主（Host）检查父子关联（Lineage）、深度、数量和能力（Capability）边界；
  3. 创建一个与父任务（Parent Task）有关联、但身份（Identity）独立的子会话（Child Session）；
  4. 子代理（Subagent）在自己的会话（Session）中运行普通代理执行（AgentRun）；
  5. 子代理（Subagent）的终态（Terminal State）结果被父任务（Parent Task）读取或接收；
  6. 父执行（Run）根据这个结果继续自己的模型步骤（Model Step）。

它没有另造一套“子代理（Subagent）运行时（Runtime）”。子代理（Subagent）最终仍走普通宿主执行（Hosted Execution）主干。

用同一个案例逐步重放

第一步：父执行（Run）决定是否需要委托

R7 先判断任务是否真的值得创建子代理（Subagent）。如果检查只需读两行配置，直接调用 Read 可能更简单。子代理（Subagent）会增加：

  • 新的身份（Identity）和上下文（Context）；
  • 调度与等待成本；
  • 结果整合成本；
  • 取消和失败处理。

第二步：冻结最小子任务（Child Task）

父任务（Parent Task）不应只说“帮我看看项目”。先通过系统配置把子代理（Subagent）的可执行能力（Capability）限定为只读检查，再给出自足的任务文字：

比较 package.json 中的测试命令与 README 当前测试说明。
只读，不修改文件。
返回：每个不一致项、观察到的原文与文件位置、推荐修改。

目标、输入、能力（Capability）上限和输出形状越明确，父任务（Parent Task）越容易判断结果是否可用。任务文字中的“只读”表达意图；工具上限（Tool Ceiling）固定允许使用的工具（Tool）集合范围，并与执行边界（Execution Boundary）共同落实限制。

第三步：子代理（Subagent）独立运行

C1/CT1/CR1 在自己的上下文（Context）中读取两个文件并形成结论。它可能调用多次模型（Model）和工具（Tool），但这些都属于子代理（Subagent）的执行事实，不与 R7 的事件混成同一个执行（Run）。

第四步：父任务（Parent Task）消费结果

CR1 完成不等于 R7 自动完成。父任务（Parent Task）还要：

  1. 判断子代理（Subagent）的观察（Observation）和结论是否充分，文件是否已被其他操作改变；
  2. 在用户已有授权内执行 README 修改，需要扩边时再走授权链；
  3. 运行测试；
  4. 生成最终回答。

第五步：处理子代理（Subagent）失败或取消

如果子代理（Subagent）失败，父任务（Parent Task）至少需要知道：

  • 子代理（Subagent）是未开始、运行失败、被取消，还是结果不确定；
  • 是否可以改由父任务（Parent Task）直接处理；
  • 已返回的部分结果能否安全使用；
  • 父任务（Parent Task）取消时是否应该级联取消子代理（Subagent）。

这也是为什么真实子代理（Subagent）需要独立生命周期（Lifecycle），而不仅是提示词（Prompt）中的一个角色。

核心问题解析

问题 1。 项目给出一份文档技能说明包（Skill），为什么不会因此获得新的文件或网络权限（Permission）？

解释。 技能说明包（Skill）增加方法与上下文（Context）；实际工具（Tool）绑定（Binding）、权限（Permission）和隔离由执行系统决定。说明书不能自行改变这些边界。

问题 2。 子代理（Subagent）已完成只读检查，为什么父执行（Run）仍不能直接算完成？

解释。 子代理（Subagent）的结果只是父任务（Parent Task）的输入。父任务（Parent Task）仍需检查结论，执行目标修改、运行验证并形成自己的终态（Terminal State）。

问题 3。 只需读取两行配置时，怎样判断是否值得创建子代理（Subagent）？

解释。 先比较独立上下文（Context）或并行检查的收益与交接、等待、结果整合成本；直接 Read 已能解决时无需增加一份执行（Run）。

问题 4。 模型（Model）在 SkillSearch 中找到 documentation-review，能否直接声称已经读过正文、执行了检查？

解释。 不能。搜索返回候选信息，按需路线还需要 Skill 工具（Tool）返回正文，再由模型（Model）选择工具（Tool）并取得检查结果。若用户显式调用已将正文注入本轮，则无需重复加载，但执行结果仍需独立证据。

问题 5。 子代理（Subagent）返回 README 某行仍是旧命令，父任务（Parent Task）刚刚编辑了那一行，应直接按子代理（Subagent）建议再改一次吗？

解释。 不应。子代理（Subagent）的结果反映它读取时的内容；父任务（Parent Task）应核对当前文件及差异，判断建议是否仍适用。独立执行者和共享文件的当前状态（State）需要分别确认。

实现深化

正文加载、实现绑定（Binding）与独立执行有不同生命周期（Lifecycle）。独立 Git 工作副本（Worktree，后文展开）中的修改还受到 第18章的效果恢复条件约束；有依赖的子任务（Child Task）由 第24章的任务图（Agent Graph）协调。

入口正文什么时候进入模型输入（Model Input）本例会发生什么

这两条入口的扫描和冻结时点不同，不能从“都加载同一个文件”推出它们处于同一个原子快照（Atomic Snapshot）。冻结范围取决于每条入口的读取与缓存时点。

一个工作轮次（Turn）冻结了什么：不只是目录名字

当前默认交互运行组成器（Interactive Composer）按 sessionId + turnId 缓存同一份权威目录快照（Canonical Inventory），也就是本轮采用的方法目录与正文快照，供方法目录、SkillSearch 和 Skill 共用。扫描结果包含去掉文件开头元数据块（Frontmatter）的 content 与原文件的 contentSha256；目录仓储冻结这些扫描记录。Skill 直接读取记录中的 content，清洗并按长度截断后返回 instructions，不会在这一步重新打开磁盘上的 SKILL.md。

所以，在下面这个单工作轮次（Turn）例子里，正文与名字一起保持一致：

S1/T7 首次组成输入：快照里是 old / OLD_DESCRIPTION / OLD_BODY
目录更新：现在可发现 new / NEW_DESCRIPTION / NEW_BODY
T7 调用 Skill(old)：仍返回 OLD_BODY
S1/T8 首次组成输入：重新取得目录，可看到 NEW_DESCRIPTION

这里演示的是目录快照（Canonical Inventory）被替换后的读取选择，不能由此推导整个文件系统在并发更新时也保持同一快照。

冻结也有明确范围。正文提到的其他文档、脚本或网络资源没有因此一起快照化，之后读取或执行仍是新的工具（Tool）动作。上述快照解析器（Snapshot Resolver）是有界的进程内缓存，不能据此推导任意重启后的永久正文快照保证。显式调用（Explicit Invocation）则先通过独立的目录快照（Canonical Inventory）读取生成已加载用户内容，再随准入保存；不要把这次读取与稍后的交互运行组成器（Interactive Composer）的目录快照（Canonical Inventory）读取说成同一个原子操作。

正文中的“运行测试”告诉模型（Model）应该做什么不会绕过工具运行时（ToolRuntime）、权限（Permission）或执行边界（Execution Boundary）

例如只有 Read 的执行环境不会因为正文写了“用 Bash 测试”就获得 Bash。若技能说明包（Skill）将 Bash 列为 required-tools 必需工具（Tool）声明，当前资格检查会隐藏或拒绝加载它；若只是 allowed-tools 声明工具（Tool）列表，则那只是说明信息。加载失败也必须被观察：显式请求的技能说明包（Skill）全部失败时会在模型（Model）服务调用前阻断；部分成功可以继续并返回失败明细；按需 Skill 失败则返回失败结果，不能假装已读过正文。

技能说明包（Skill）来源与依赖的边界

为什么技能说明包（Skill）仍然需要安全审查

“只是文字”不代表没有风险。技能说明包（Skill）可能引导智能代理（Agent）：

  • 读取不必要的敏感文件；
  • 运行来源不明的脚本；
  • 把数据发送到外部服务；
  • 把一次临时做法写成长期规则。

强制边界仍由工具（Tool）、权限（Permission）和沙箱（Sandbox）承担，但技能说明包（Skill）的来源、内容和依赖也属于供应链治理问题。这类似于：说明书不能打开上锁的门，但坏说明书仍可能诱导拿着合法钥匙的人走错房间。

方法正文没变，执行工具（Tool）却换了一代

技能说明包（Skill）解决“如何做”的复用，插件（Plugin）可以提供实际可调用的实现。这里讲已经安装、受信任的宿主（Host）插件（Plugin）；扫描到一份 SKILL.md 不会因此执行插件（Plugin）代码。

技能说明包（Skill）的发现与读取快照

假设目录已展示，正文随后从“运行命令A”改成“运行命令B”。Maka 本工作轮次（Turn）的目录快照（Canonical Inventory）缓存有效时，按需调用 Skill 读取扫描所得的 content，仍可返回A；Codex 的普通宿主（Host）技能说明包（Skill）按关联文件系统（Filesystem）读取选定正文，如果该来源可变，此时可能返回B或读取失败。后者的快照（Snapshot）主要保存发现结果与来源关联。来自不可变插件（Plugin）代次（Generation）的文件、执行器（Executor）或编排器（Orchestrator）的分页缓存另有规则，不能由这一例推断所有 Codex 技能说明包（Skill）都立即刷新。

这里比较的是“发现目录后、实际加载正文前”的变化。第41章的分页快照则追踪本地执行器支持的（Executor-backed）路径同一次读取的后续页：继续页命中缓存时会延续那份正文。发现时记录了什么，与一次分页读取保持哪份内容一致，时间范围不同。

因此选型取决于复用对象：复用方法文字用技能说明包（Skill）；增加可信执行实现及热替换用插件（Plugin）的绑定（Binding）与清理合同；另起有独立任务/历史（History）的执行者用子代理（Subagent）。如果产品要求“审核过的确切正文及脚本在重启后继续使用”，应把内容和资源版本纳入持久合同，仅靠任一 snapshot 名称都不够。

变式一：技能说明包（Skill）已载入，但 check_docs 被卸载。模型（Model）还能因为方法正文要求它，就继续调用旧工具（Tool）吗？

参考答案

不能。已加载文字是输入历史（History），不是当前可执行绑定（Binding）。新模型步骤（Model Step）可能已经没有该工具（Tool）；旧包装器（Wrapper）如果已退役（Retired）也拒绝新进入。已经进入实现的 A 仍需收束，不能从卸载推导它没有产生效果。

变式二：产品要求同名、同参数结构（Schema）的 g18 自动继承 g17 激活，只按名字缓存是否足够？

参考答案

这会改变当前合同：旧代实现的搜索激活将自动延续到新实现；这是可用性资格，执行权限（Permission）仍独立核对。要这样设计，必须另行定义等价性、审核与失效策略；不能只删掉代次（Generation）就说仍保留原保证。若需求反而是审核内容在恢复后不漂移，则还要持久保存确切正文与资源，代次（Generation）内存对象本身也不能完成跨重启合同。

只读子代理（Subagent）的实际约束

在案例中，父任务（Parent Task）要修改 README；子任务（Child Task）只负责只读检查：

定义与配置（Definition / Profile）：选择 `local_read` 预设（Preset）
输入：package.json、README.md、检查问题
输出：不一致项和证据
任务文字：只读，不修改文件，不运行有副作用命令

这里必须区分“告诉子代理（Subagent）不要做什么”和“系统真的不让它做什么”。任务文字表达委托意图；真正的强制执行（Enforcement）来自 local_read 定义与配置（Definition / Profile）冻结的 explore 模式（Mode）、只包含 Read / Glob / Grep 的工具上限（Tool Ceiling），以及最终的执行边界（Execution Boundary）。只在提示词（Prompt）里写“禁止修改”并不能构成安全边界。

如果把代码修改也委托出去，改的是哪一份文件

上面的只读子代理（Subagent）有独立对话，文件仍从父任务（Parent Task）的工作目录读取。上下文（Context）独立、工具（Tool）受限、文件工作树（Worktree）分离是三种不同机制。 Maka 的 implementation 配置（Profile）才会要求宿主（Host）建立独立 Git 工作树（Worktree），也就是同一个 Git 仓库的一份单独工作副本（Working Copy）；它可以运行本地修改与命令解释器（Shell）工具（Tool），最后交回补丁（Patch）。工作树（Worktree）自身不等于操作系统（Operating System，OS）沙箱（Sandbox），实际访问许可仍由执行边界（Execution Boundary）决定。

理解起点时，先分开 Git 的已提交版本和工作目录当前文件。提交记录某一版文件；HEAD 通常指向当前分支，由此确定当前检出的提交，也可能直接指向某个提交。工作目录中的未提交编辑不会自动进入该提交。本节的 dirty（有改动）表示 Git 状态（State）检查发现尚未提交的变化；没有这些变化时称为干净。

例如，HEAD 中的 README 仍写 npm run check，父工作目录却已将它改为 npm test、尚未提交；直接从 HEAD 建立的副本不会包含这次编辑。本节所查的 Maka 新建工作树（Fresh Worktree）路径会拒绝这样的有未提交改动的起点，避免静默漏掉父目录改动。这是该创建路径的约束，不是 Git 一概禁止从有改动的目录创建工作树（Worktree）。

下面重新以父工作区干净、已提交 README 仍含错误测试命令为初态，沿用“修改 README 测试步骤”的子任务（Child Task）。本分支另有将文档修改与测试委托给子代理（Subagent）的授权，implementation 配置（Profile）及实际执行边界（Execution Boundary）也允许相应操作；不能从前面的只读委托继承可写权限（Permission）。这是依据源码设计的状态（State）轨迹，没有实际创建子代理（Subagent）：

这解释了“结果交回”和“父任务（Parent Task）验收（Acceptance）”的差别。子代理（Subagent）说测试通过时，父任务（Parent Task）仍要检查测试范围、补丁（Patch）内容和自己的当前文件是否已变化，不能只转述成功文字。若父目录后来已有另一份 README 修改，是否还能采用该补丁（Patch）需要新的判断；创建子代理（Subagent）时的干净起点并不保证未来合并无冲突。

两个失败窗口尤其值得辨认：

  • 父目录本来就有未提交修改：当前新建工作树（Fresh Worktree）路径会拒绝创建，而不是默默从 HEAD 出发漏掉这些修改；父任务（Parent Task）必须重新选择和确认工作起点，不能假定子代理（Subagent）已看到未提交改动。
  • 子代理（Subagent）已结束，但发布前失败：恢复逻辑可以在最新子代理（Subagent）的执行（Run）已到终态（Terminal State）时，从仍保留的工作树（Worktree）补发它的补丁（Patch）；已发布的产物（Artifact）会复用。它不能任意重建所有历史工作轮次（Turn）的旧补丁（Patch）。子代理（Subagent）失败或被取消也可能留下修改，产物（Artifact）存在不代表修改可采纳。

上下文（Context）分叉的实现边界

上下文（Context）分叉不是操作系统（OS）的写时复制（Copy-on-Write）

“从父任务（Parent Task）分出子代理（Subagent）”容易让人联想到操作系统（Operating System，OS）的 fork() 所用写时复制（Copy-on-Write，CoW）：先共享内存页，写入时再复制。这个类比只能帮助理解“分叉后各自演进”，不能当成 Maka 的上下文（Context）实现说明。

大语言模型（Large Language Model，LLM）的上下文（Context）不是由内存管理单元（Memory Management Unit，MMU）管理的内存页；后者负责虚拟地址到物理内存的映射与访问保护。模型（Model）的上下文（Context）可能包含用户消息（Message）、模型（Model）输出、工具结果（Tool Result）、权限（Permission）事件和已经过时的试错路径；把父历史（History）全部交给子代理（Subagent）会同时带来噪声、隐私与词元（Token）成本。Maka 的直接子代理（Subagent）默认获得独立历史（History），由冻结的角色配置、工具（Tool）边界和显式任务输入（Task Input）构造初始工作集，而不是自动引用父会话（Session）前缀后再做“写时复制（Copy-on-Write）”。

压缩后的子任务（Child Task）结果，是否足够让父任务（Parent Task）决策

继续让只读子代理（Subagent）检查 README 与配置。普通 agent_spawn 的任务输入（Task Input）被送入独立子会话（Child Session）；返回时，Maka 组合调用状态（Invocation Status）、有界摘要（Summary）和产物（Artifact）标识（ID）。当前摘要（Summary）在最后一次完整文本非空时优先取它，否则用流式尾部或错误文字，不会回溯较早完整事件，最多4,000个 JavaScript 字符计量单位（UTF-16 Code Unit），不保证等于4,000个视觉字符；它不是自动生成的一份完整证据报告。父模型（Model）通过普通工具结果（Tool Result）的有效投影（Projection）读到它，再决定要不要补读原文。

为这类委托设计两个教学对象：

同题的另一种实现是持续通信。 Codex 的可寻址消息（Message）协作路径（实现中称 Multi-Agent V2）把发消息（Message）和触发新工作分开：普通消息（Message）先入队，活跃工作轮次（Turn）在允许消费输入的模型步骤（Model Step）边界接收；后续工作请求（Follow-up）还能在目标空闲、容量等条件满足时开新普通工作轮次（Turn）。这适合发现新线索后继续协商，而 Maka 本例的前台子任务（Foreground Child）更适合输入明确、返回有界结果的一次委托。

这条路径有个细节：仅入队（Queue-only）表示仅投递消息（Message），通常不单独启动普通空闲任务；但目标没有活跃工作轮次（Turn）、仍保留持久等待（Durable Sleep）记录时，也可触发新的普通工作轮次（Turn）处理等待中的工作。它不重开旧工作轮次（Turn），也不恢复旧调用栈；第41章会展开该接收分支。

消息（Message）已提交不证明目标读过或完成任务，也不能由正常投递流程推导崩溃后邮箱（Mailbox）必然完整恢复。

选择持续通信，需要额外定义谁可以发什么、接收时点、旧消息（Message）的相关性、重复与取消，以及谁最终提交结论。若几个只读检查相互独立，先用普通委托或有向无环图（Directed Acyclic Graph，DAG）即可；若结果不断改变对方的任务，再考虑通信模式。目录共享、工具（Tool）授权与结果合并仍分别设计，多一套消息（Message）应用编程接口（API）不会自动解决它们。

并行省下的是重叠执行的8秒，最终整合和验证仍在关键路径上。这里比较同一分工的两种安排，没有证明它比单个智能代理（Agent）直接处理更快；词元（Token）总量还要累加父子输入、输出、重试，不能只按27秒计成本。并发上限、累计子代理执行（Child Run）数量上限和失败收敛也可能改变这个理想时间。

变式一：总预算30秒，但父任务（Parent Task）在子代理（Subagent）回来前改了配置，必须再用6秒核对原观察（Observation）。还能照原推演说按时完成吗？

参考答案

不能沿用27秒。若新增核对时间 tr=6t_r=6tr​=6 秒不能与剩余步骤重叠，而允许的时间预算 B=30B=30B=30 秒保持不变，则：

额外核对改变了关键路径，已经超出预算。应调整计划、缩小有授权的交付或如实说明未完成验证；不能用子代理（Subagent）的 completed 状态（State）或旧观察（Observation）省略最终状态（State）检查。新增共享写冲突也会破坏原来的独立前提。

变式二：子代理（Subagent）的摘要（Summary）说“已修好”，状态（State）却是 failed，且返回补丁（Patch）。父任务（Parent Task）能直接合并并宣布主任务（Main Task）完成吗？如果改用消息（Message）协作，消息发送成功能代替验收（Acceptance）吗？

参考答案

不能。失败也可能留下有用甚至部分正确的补丁（Patch）；父任务（Parent Task）需核对失败原因、完整差异、当前工作树（Worktree）和检查结果，在已有授权内决定是否采纳。摘要（Summary）、状态（State）、产物（Artifact）和主任务（Main Task）验收（Acceptance）是不同证据。消息（Message）协作的发送成功也只说明提交被接受，不证明对方已经阅读、做完或结论正确；它不能替代结果和验收（Acceptance）链。

机制问题解析

问题 1。 子代理（Subagent）的任务文字说“只读”，具体什么机制才限制修改？

解释。 本例由 local_read 定义与配置（Definition / Profile）固定 explore 模式（Mode）、Read / Glob / Grep 工具上限（Tool Ceiling），并结合执行边界（Execution Boundary）执行；提示词（Prompt）表达意图，不能代替强制约束。

问题 2。 为什么分出子代理（Subagent）不能理解为自动共享父历史（History）的操作系统（OS）的写时复制（Copy-on-Write）？

解释。 当前直接子代理（Subagent）有独立历史（History），使用冻结配置与显式任务输入（Task Input）组成工作集；不能借操作系统（OS）的内存页语义解释大语言模型（LLM）的上下文（Context）。

问题 3。 为什么直接调用 agent_spawn 不能证明已拥有任务图（Agent Graph）或邮箱（Mailbox）？

解释。 agent_spawn 是一次有界委派；任务图（Agent Graph）还需要拓扑（Topology）、修订（Revision）、认领（Claim）/唤醒（Wake），邮箱（Mailbox）还需要独立消息（Message）投递与唤醒契约。

问题 4。 在上面的 T7 快照例子中，目录更新后加载 old 会得到什么？正文引用的脚本是否也被冻结？

解释。 T7 的按需加载返回快照中的 OLD_BODY；T8 首次组成输入才重新取得目录快照（Canonical Inventory）。附带脚本没有被这一正文快照冻结，不能推导其内容或运行结果。

问题 5。 一个技能说明包（Skill）的 required-tools 包含 Bash，但当前宿主（Host）没有 Bash；把它改成 allowed-tools 是否就能运行命令？

解释。 required-tools 不满足会阻止资格；改成 allowed-tools 只改变声明，不会产生 Bash 工具（Tool）或执行许可。既不能把加载成功当成授权，也不能把授权当成实际执行。

问题 6。 implementation 子代理（Subagent）返回 completed 和补丁（Patch）标识（ID），父 README 是否已经改变？如果父目录在创建前已有未提交修改，会发生什么？

解释。 不一定；这条结果写回（Write-back）链发布产物（Artifact），没有自动合并到父目录。父任务（Parent Task）仍须检查、采纳并验证。新建工作树（Fresh Worktree）在父目录有未提交改动时拒绝创建，不能假定子代理（Subagent）复制了未提交修改。

问题 7。 子代理（Subagent）的执行（Run）已到终态（Terminal State），但宿主（Host）在发布补丁（Patch）前退出；能否仅凭这个终态（Terminal State）认定产物（Artifact）已交回？恢复可以补什么？

解释。 不能，执行（Run）终态（Terminal State）与产物（Artifact）发布是两个事实。在绑定（Binding）仍有效且工作区无活跃运行资源（Live Runtime Resource）的条件下，恢复可在最新子代理（Subagent）的执行（Run）已到终态（Terminal State）时补发它尚未发布的补丁（Patch）；它不是任意历史工作轮次（Turn）的快照恢复。
