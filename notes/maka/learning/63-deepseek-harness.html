第 63 章｜DeepSeek Harness：插件（Plugin）组合怎样形成执行保证

本章概览

核心问题：把运行支撑（Agent Harness）拆成插件（Plugin）之后，谁真正执行模型请求（Model Request）、保存记录并处理失败？

关键概念：服务（Service）提供稳定的能力入口；消费者（Consumer）实际调用能力；生命周期（Lifecycle）决定能力何时可用、何时撤销；检查点策略（Checkpoint Policy）决定何时必须等待持久保存；未知效果（Unknown Effect）表示记录不足以确认外部操作的结局。

关系主线：DeepSeek Harness（DSH）先组合配置和服务，再把模型与工具接入同一执行链；组合方式改变失败边界，注册可撤销也不等于文件修改可回滚。

1. 前情回顾：这次把分散的保证放回同一套实现

第 19 章区分历史（History）与输入投影（Input Projection）：保存了哪些内容，不等于本次模型（Model）看到了哪些内容。第 28 章沿消费者（Consumer）追踪输入，说明 DSH 认领（Claim）收件箱（Inbox）消息、提交用户消息（User Message）和生成模型请求（Model Request）是不同步骤。本章用这条关系解释实际请求从哪里来。

第 39 章区分消息送达、消费和业务完成；第 44 章进一步区分控制状态（Control State）、证据状态（Evidence State）与环境状态（World State）。本章把三者具体化：代理循环（Agent Loop）决定下一步，会话（Session）日志保存已提交记录，文件系统保存真实 README。三者不会因为都属于一个程序就同时更新。

DeepSeek Harness（DSH）是 DeepSeek 公开的运行支撑（Agent Harness）项目，命令行标识为 dsh，底层插件框架是 Cordis。理解其“能力由插件（Plugin）组合”的主张，关键是追问：配置里选了什么、谁提供能力、谁调用它，以及失败时什么还成立。一个名为持久化的包被加载，还不足以回答外部工具（Tool）何时可以开始。这个设计入口见官方项目说明与Cordis 入门。

本章先用一个小任务固定问题，再讲组合、消费者（Consumer）和恢复（Recovery）。任务的文件、操作过程和结果均为教学设定，未运行 DSH 或调用模型（Model）；后面的短源码片段用于核对实际控制顺序。

2. 一个小任务：只修正 README 的测试（Test）入口

工作区（Workspace）中有 package.json、README.md、src/duration.js 与 test/duration.test.js。项目配置声明 test 脚本为 node --test；README 却写成 npm run check，而项目没有 check 脚本。源码和两条测试（Test）已经正确：0 秒得到 0:00，125 秒得到 2:05。本例与前面“源码仍有错误”的修复题是不同初态。

用户要求：把 README 的入口修正为 npm test，运行项目测试（Test），最后用中文说明修改与验证。只允许修改 README；源码、测试（Test）和项目配置保持只读。这是本例给定的任务范围（Task Scope），不能因为配置了工作区（Workspace）根目录，就声称实现已经强制了单文件写入许可。

正常结果很短：README 的那一行变成 npm test；项目测试（Test）确实发现并执行上述两条用例，预期两条通过；文件差异（Diff）仅涉及 README 的命令行。最终报告分别说明文件修改、测试（Test）结果和范围检查。这里的“两条通过”是教学预期，不是已取得的运行输出。

那么，为什么这个小任务还值得研究运行支撑（Agent Harness）？因为同一个修改可以在不同位置中断：模型（Model）已经提出编辑，工具（Tool）尚未获准；文件已经改好，成功结果尚未保存；用户切换了插件（Plugin），旧注册正在被移除。最终 README 看似正确，仍不能回答这些中间状态。

DSH 的选择是把模型服务（Model Service）、工具（Tool）、会话存储（Session Store）和检查点策略（Checkpoint Policy）分别组织，再通过明确的服务（Service）与事件（Event）连接。这样可以替换其中一项；代价是必须验证实际组合，而不能从某个组件的名称推导整套保证。

3. 配置（Configuration）怎样变成可用能力

3.1 配置档（Profile）选择组合，用户输入不负责安装能力

配置档（Profile）是一套启动时采用的插件（Plugin）组合及其覆盖层。当前实现中，web 和 headless 的模板都包含基础组合包 @deepseek-ai/dsh-base，再接各自的应用入口；sdk-minimal 则选择另一套较小组合，不自动继承基础组合包里的全部能力。

本例固定采用包含基础组合包的配置档（Profile），并假定模型路由（Model Route）、工作区（Workspace）与凭据引用已由运行环境正确提供。不在任务提示词（Prompt）中放置凭据，也不把“请使用某模型”当作已经注册模型协议适配器（Model Adapter）的证明。

有效配置（Effective Configuration）按组合包层、配置档（Profile）用户层、主目录用户层、命令行覆盖层依次组合；启动代码还处理专门的遥测开关。这里描述的是实际配置合成顺序，不意味着每一字段都采用“后者简单覆盖前者”的合并规则。加载器（Loader）处理的是有身份的配置项及其补丁操作。

为什么要保存分层来源？假设用户曾暂时关闭某插件（Plugin），随后删去这一覆盖。系统应能回到基础组合，而不是保留上次被原地修改过的对象。因此启动和实时重新组合会复制原始补丁对象，避免一次应用把后续重新组合所依赖的基础对象也改掉。

配置能否立即生效还有自己的条件：当前 web 模板允许实时重载，headless 模板采用启动时配置。不能看到一个入口能重载，就推断所有配置档（Profile）都在同一时刻更新。

3.2 服务（Service）让消费者（Consumer）依赖合同

服务（Service）是插件上下文（Plugin Context）对象上可查找的能力入口，例如 ctx.llm、ctx.tools、ctx.sessions。服务提供者（Service Provider）实现它，消费者（Consumer）通过这个入口调用，而不用把每一种实现都写进调用者。

这里“消费者（Consumer）”强调实际调用关系。模型（Model）提出了 Edit，不等于它直接写文件；某个存储包存在，也不等于循环在关键位置等待了它。

图中实线表示本章选取的装配或调用关系，虚线表示包裹执行边界；它不是完整依赖图。模型服务（Model Service）与工具服务（Tool Service）负责本身的能力，检查点策略（Checkpoint Policy）在向下游交接前要求保存。底部文件效果（Effect）仍由实际工具实现产生。

3.3 依赖注入（Dependency Injection）解决启动次序，不替代权限（Permission）

插件（Plugin）通过 inject 声明依赖。检查点策略（Checkpoint Policy）声明需要 llm、sessionPersistence、sessions 和 tools；Cordis 在依赖可用时激活相应插件（Plugin）。这使加载顺序由能力需求表达，减少手写“先启动甲、再启动乙”的代码。

但至少有三种“存在”需要区分：包已安装、服务已提供、适合本次请求的模型路由（Model Route）已注册。例如模型协议适配器（Model Adapter）可以已挂载，却因为没有相关提供方设置而尚未注册可用路由。缺少必需服务可能使依赖它的插件（Plugin）尚未激活；一次具体请求选择不到路由，则在请求路径中失败。二者不是同一种状态。

依赖声明也不负责隔离不可信代码。它表达插件（Plugin）使用哪些服务（Service），不能单独阻止同一进程中的代码访问文件或网络。工具准入（Tool Admission）、权限（Permission）检查与实际沙箱（Sandbox）执行各有责任；本例的 README 单文件范围还要由选定执行路径落实。

4. 生命周期（Lifecycle）：替换能力时要收回什么

Cordis 用时空可组合性（Spatiotemporal Composability）描述这类设计问题。空间组合（Spatial Composition）关注同一个程序中，插件（Plugin）通过哪些服务（Service）和作用域（Scope）相互连接，消费者（Consumer）能取得哪个实现；时间组合（Temporal Composition）关注这些关系在什么时候成立，依赖就绪后如何激活，退出时怎样撤销并处理依赖者。前者不指屏幕布局，后者不指执行速度；它们一起回答“现在、在这个作用域（Scope）中，谁可用”。Cordis 论文讨论了这些组合性质，本章借实际接缝解释含义，不把理论性质当作任务效果的证明。

如果工具（Tool）注册只往全局列表追加，重载一次就可能多出一份同名工具、一个重复监听器，或者仍指向旧配置的模型路由（Model Route）。所以“能够加载”只是问题的一半，还需要知道“由谁移除”。

Cordis 将注册视为可撤销效果（Reversible Effect）：工具声明（Tool Specification）、事件监听器（Event Listener）和服务注册有所属插件上下文（Plugin Context）及清理动作。插件（Plugin）退出时，相关注册可以被撤销；依赖关系也参与生命周期（Lifecycle），避免消费者（Consumer）继续把已经退出的服务提供者（Service Provider）当作可用能力。

这里的插件上下文（Plugin Context）是插件框架拥有服务和清理资源的对象，不是发送给模型（Model）的上下文窗口（Context Window）。名字相近，但实际消费者（Consumer）不同。

撤销注册能够避免什么？例如移除一个包装器后，后续调用不再经过它；重建某项服务后，新的消费者（Consumer）取得当前实现。它不能自动做到什么？已经写入 README 的字节不会因为编辑工具（Edit Tool）被卸载就恢复，已发送的远端请求也不会被“取消注册”收回。

这给热重载（Hot Reload）提出两项代价。第一，必须决定状态（State）的负责者（Owner）：需要跨重建保留的会话（Session）不能只放在即将丢弃的临时对象里。第二，必须处理旧执行中的工作：停止接纳新调用、传播取消（Cancellation）、结算已开始操作，不能把重新加载解释成任意指令点的安全暂停。

设计上还要避免把清理函数当作经过证明的逆操作。作者需要正确释放自己登记的资源；框架能够组织清理时机，不会自动验证“这段清理一定撤销了全部外部效果（Effect）”。这也解释了为什么插件（Plugin）系统与持久恢复（Durable Recovery）需要分别设计。

5. 同一个 README 请求怎样抵达真实消费者（Consumer）

5.1 先认领（Claim）消息，再形成模型输入（Model Input）

本例用户消息（User Message）先进入收件箱（Inbox）。ReactLoopAgent.preStep() 在异步提示词（Prompt）组装前调用 inbox.claim()，然后组装本步材料。认领（Claim）使这些消息离开待处理集合；它不证明模型（Model）已经看见消息，也不证明后面的文件修改完成。

进入实际模型步骤时，循环提交被接纳的用户消息（User Message），构造请求头（Request Header），再从会话（Session）事件中派生消息。请求中包含当前模型路由（Model Route）及对应设置，派生结果被固定后才交给模型流（Model Stream）。因此“存在历史（History）记录”和“进入这次模型输入（Model Input）”仍由明确步骤连接。

实际消费发生在模型协议适配器（Model Adapter）的流入口。代码既可能使用已经准备好的绑定调用，也可能走通用 llm.stream()；准备好的调用仍进入 llm/stream 包装链，不能因为名字叫“已准备”就绕过检查点策略（Checkpoint Policy）。

5.2 模型（Model）提出工具调用（Tool Call），工具服务（Tool Service）重新判断

本例先读取项目配置和 README，以实际材料确认入口错误，再准备单行编辑。模型（Model）的行动请求（Action）进入工具链后，调用参数要被解析；错误参数不能被悄悄替换成看似合法的默认值。工具声明（Tool Specification）、参数、准入政策（Admission Policy）和当前取消（Cancellation）状态决定能否继续。

在选定的循环路径中，工具调用（Tool Call）记录 tool/call 先被提交到会话（Session），随后进入准备与分派。前置政策可以询问、拒绝或继续；守卫（Guard）只能收紧许可，不能把已有拒绝重新改为允许。通过这些检查后，仍需经过本章下一节的持久化屏障。

真正执行时，工具服务（Tool Service）再次取得当前工具实现，调用工具主体（Tool Body），并把结果交回循环。调用记录的出现并不意味着主体已经执行；错误结果也不必然意味着文件从未改变，因为错误可能发生在实际写入之后。

若模型（Model）一次提出多个工具调用（Tool Call），实现还要处理并发上限（Concurrency Limit）、独占调用屏障（Exclusive Barrier）和结果顺序。当前执行器按模型（Model）给出的顺序提交结果；取消（Cancellation）时结算已启动调用，并处理尚未启动者。本例使用顺序读取、编辑与验证，不从这里推导“多个工具可以无条件并行”。

6. 为什么持久化后端（Persistence Backend）还不够

6.1 “存到哪里”与“何时必须等它存好”是两项选择

持久化后端（Persistence Backend）回答记录保存到哪里、怎样保存；检查点策略（Checkpoint Policy）回答执行到哪个位置必须等待保存完成。基础组合包同时加载检查点策略（Checkpoint Policy）和逐行持久化后端：后者采用 JavaScript 对象表示法（JavaScript Object Notation，JSON），逐行存储格式称逐行 JSON（JSON Lines，JSONL）。

若只加载后端，事件（Event）可能仍在批量写入窗口中；内存里已经追加记录，崩溃后却不一定读得到。反过来，flush() 返回也要看合同：会话存储（Session Store）等待所有参与监听器（Listener）结算，传播其中的失败；没有任何监听器（Listener）参与时，它返回 false，并不凭空产生持久保存。

因此本节保证限定于：正确激活的检查点策略（Checkpoint Policy）、实际参与并履行合同的持久化后端（Persistence Backend），以及走被包装执行接缝的调用。自定义组合、嵌套工具或脱离智能代理（Agent）的工具调用（Tool Call），必须分别核对。

6.2 一段短代码说明“等待”怎样成为执行条件

下面是检查点策略源码的工具包装部分。exec 是待执行调用，next() 才把控制交给下游；因此它的关键不是多写了一条日志，而是决定何时允许下游开始。首行条件排除了没有智能代理（Agent）的调用以及已有父调用的嵌套调用（Nested Call）。

ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
  if (exec.agent === undefined || exec.parent !== undefined) return next()
  // 等待本次会话记录保存，再检查取消。
  await ctx.sessions.flush(exec.agent.session)
  if (exec.signal.aborted) return abortedBeforeDispatchResult()
  // 只有越过上述边界，才交给下游工具主体。
  return next()
})

这是实际源码节选，只增加两条阅读注释，类型与辅助函数由原模块提供，不是独立可运行程序。abortedBeforeDispatchResult() 构造调用尚未分派时的取消结果；如果 flush() 拒绝，控制不会到达 next()。如果取消（Cancellation）在等待期间到达，保存完成后仍要阻止本次主体执行。

同一插件（Plugin）还包装两个位置：携带有效会话（Session）的模型请求（Model Request），在创建下游模型流（Model Stream）前保存请求前缀；下一步的 agent/pre-step 在继续前保存前一步提交的响应和有序工具结果（Tool Result）。没有有效会话（Session）的模型请求（Model Request）不会由这个包装器凭空获得同一保证。

注意，它在正常路径中没有增加提示词（Prompt）或工具声明（Tool Specification）。两次执行的模型输入（Model Input）可以一样，外部操作前是否存在持久证据却不同。这是运行支撑（Agent Harness）能够改变可靠性，而不必改变提示词（Prompt）的一个具体例子。

6.3 用顺序关系找出仍然存在的空隙

针对本例一次成功的顶层 README 编辑，令 AcA_cAc​ 表示内存中已提交调用记录，DcD_cDc​ 表示该记录已持久保存，EEE 表示实际文件修改，ArA_rAr​ 表示结果已提交到会话（Session），DrD_rDr​ 表示结果已持久保存。符号 ≺\prec≺ 表示本路径中必须先发生。

Ac≺Dc≺E≺Ar≺DrA_c \prec D_c \prec E \prec A_r \prec D_rAc​≺Dc​≺E≺Ar​≺Dr​

这是选定组合下这一次成功编辑的顺序，不是把数据库和文件系统变成一个事务（Transaction）。特别是 Dc≺ED_c \prec EDc​≺E 约束“先保留准备执行的证据”，却没有消除 EEE 与 DrD_rDr​ 之间的崩溃窗口。工具（Tool）也可能在进入主体后、实际文件修改前失败，因此不能从 DcD_cDc​ 反推 EEE 已发生。

图中的未知效果（Unknown Effect）分支关注文件已经修改、结果尚未持久保存的情况；持久调用存在但主体尚未写入时崩溃，也可能落到同一种恢复分类。因此恢复（Recovery）要检查外部状态，不能把分类名称当作实际发生过写入的证据。

故障点（Failure Point）当前可以确认什么处理与保证边界
F1：必要服务（Service）没有提供，检查点策略（Checkpoint Policy）尚未激活配置项存在，依赖未满足检查实际激活与诊断；不把“已安装”写成“屏障已生效”。若改变组合继续工作，须重新核对保证
F2：模型（Model）提出修改源码，超出 README 范围，执行准入（Admission）拒绝产生了行动请求（Action），没有获得本次写入许可保留拒绝原因，回到获准的文档修复；工具声明（Tool Specification）可见不扩大权限（Permission）
F3：本次工具屏障的持久保存失败调用可能在内存中，屏障未成功包装器不进入下游主体；修复存储问题后再按当前任务与许可决定是否继续，不能将失败解释为成功保存
F4：等待保存期间，用户取消（Cancellation）保存可能成功，但取消意图已到达包装器返回分派前取消结果，本次主体不启动；这不回滚更早操作
F5：README 已修改，成功结果持久保存前崩溃恢复日志可能只有调用，没有结果标记未知效果（Unknown Effect），先只读核对 README 与差异（Diff），不能盲目再次编辑

F2 假定选定执行路径确实落实了本例许可；仅在提示词（Prompt）中写“不要改源码”不足以制造这个拒绝。F3 只断言这一调用尚未进入工具主体（Tool Body），不宣称其他并发操作或此前操作没有效果（Effect）。这两个限定把本例条件与产品的整体安全保证分开。

7.1 恢复（Recovery）怎样表达未完成的工具调用（Tool Call）

interruptedTurnClosers() 扫描已加载的有效持久日志前缀，识别没有闭合的最后工作轮次（Turn）。对于助手消息（Assistant Message）中尚未匹配结果的工具调用（Tool Call），按是否存在对应的 tool/call 记录分类：

函数先补缺失工具结果（Tool Result），再按需要补步骤结束，最后补中断的轮次结束。空日志或已闭合日志不需要这些补项；合成记录延续序号并复用最后记录时间，避免为历史修补发明新的真实执行时刻。

这些补项解决消息协议（Message Protocol）和控制边界：让后续模型请求（Model Request）能明确看见中断。它们没有重新执行编辑，也没有写出文件回滚。若自定义组合没有工具主体（Tool Body）前的持久屏障，就不能无条件沿用“日志缺少调用，因此效果一定没发生”的推断。

7.2 F5 的完整参考恢复结果

先只读打开 README，再核对当前文件差异（Diff）。若目标行已是 npm test，且没有覆盖其他内容，就保留现状，继续获准的测试（Test）与范围验证。可以报告“当前文件已经符合要求”；缺少可归因结果时，不把这个状态冒充“已证明原调用成功”。

若 README 仍是旧行，先确认任务范围（Task Scope）仍有效，再基于当前内容重新形成最小编辑。若用户在中断期间改过同一段，就保留用户内容，重新判断如何修正入口，不能重放旧的整文件写入。

最后运行项目声明的测试（Test）入口，检查实际用例数量与断言，再核对文件差异（Diff）。本例的参考终点仍是两条用例通过、只修改 README；恢复分类本身不是任务验收（Task Acceptance）。若测试（Test）尚未取得结果，就明确保留验证未完成状态。

8. 这些设计选择换来了什么，又付出了什么

把能力替换点放在服务（Service）合同上。 不同模型协议适配器（Model Adapter）或存储实现可以接在同一消费者（Consumer）后面，调用者不必知道所有实现细节。代价是合同要足够明确：可用状态、错误、取消（Cancellation）、结果含义与持久保存边界都要兼容；方法名相同不能证明可以替换。

把执行政策放在可组合的包装链上。 检查点策略（Checkpoint Policy）不必重写代理循环（Agent Loop），也不必增加模型（Model）看到的文字。代价是包装位置、适用调用和是否正确向下游交接成为正确性的一部分；忘记加载或从另一入口绕开，都会改变保证。

让注册跟随生命周期（Lifecycle）。 可撤销注册帮助重载和清理，减少陈旧路由、重复工具和悬挂监听器（Listener）。代价是需要明确状态（State）的负责者（Owner）及旧工作的结算策略；清理注册、恢复对话、恢复文件是三项不同工作。

把未知（Unknown）保留下来。 在无法证明效果（Effect）时返回未知分类，避免盲目重试副作用操作。代价是恢复（Recovery）可能需要多一次回读（Readback）与对账（Reconciliation），某些远端操作还需要资源方提供幂等键（Idempotency Key）或可查询回执（Receipt），本章文件案例不能替这些资源给出保证。

因此比较运行支撑（Agent Harness）时，应该比较实际组合和受测任务：相同模型（Model）、相同任务、哪些组件生效、哪些故障被阻止或暴露。插件（Plugin）数量、体系名称或一张架构图，都不能直接推出任务成功率更高。

DSH 的公开定位仍是开发者预览（Developer Preview）；官方安全说明没有把它宣布为已完成安全审计的产品。本章从选定源码路径解释设计，不把这些局部机制推广为所有插件（Plugin）、所有配置档（Profile）或不可信工作负载的整体安全证明。

9. 机制问答：把判断落到具体边界

问题 1：两个系统使用完全一样的提示词（Prompt），运行可靠性还能不同吗？

参考答案。 能。本章检查点策略（Checkpoint Policy）在正常路径中不增加提示词（Prompt）或工具声明（Tool Specification），却要求模型请求（Model Request）和顶层工具主体（Tool Body）前保存记录。相同模型输入（Model Input）不代表外部执行与故障恢复（Recovery）的条件相同。

问题 2：持久化包已安装，是否可以把日志缺少调用解释为工具没运行？

参考答案。 还不行。要核对后端实际参与、调用前屏障已激活并覆盖该路径。仅有包或内存日志，不足以建立“效果之前已有持久调用记录”的顺序。

问题 3：卸载编辑工具（Edit Tool）能恢复旧 README 吗？

参考答案。 不能。卸载撤销能力注册，不撤销已经写入的字节。文件恢复需要另行读取当前状态、判断用户后续修改并获得相应许可，不能由插件（Plugin）清理暗中代办。

问题 4：TOOL_OUTCOME_UNKNOWN 是否就是失败，可以立即重试？

参考答案。 它表示缺少持久结果，未确定真实效果（Effect）。只读或满足幂等性（Idempotency）合同的操作可以在仍然需要且获准时考虑重试；可能改变外部状态的操作，应先核对当前资源。工具（Tool）名字叫“编辑”并不赋予幂等性（Idempotency）。

问题 5：声明依赖与声明工具权限（Permission）解决的是同一件事吗？

参考答案。 不是。依赖注入（Dependency Injection）回答能力何时可用；权限（Permission）回答本次操作是否允许；实际执行层才落实资源访问限制。三者需要配合，不能互相代替。

问题 6：Cordis 的组合理论是否证明 DSH 比其他运行支撑（Agent Harness）更会完成任务？

参考答案。 没有。组合理论讨论接口、依赖和生命周期（Lifecycle）的性质；任务效果还取决于实际实现、模型（Model）、输入、工具与评价条件。证明某类结构性质、检查源码路径和运行任务实验，是不同证据，不能互换。
