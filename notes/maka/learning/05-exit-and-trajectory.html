第 05 章｜交互、退出、预算与执行轨迹

本章概览

核心问题：人工确认、完成标记、预算超限和异常，各自怎样改变循环与保存结果？

关键概念：Interaction（交互）影响动作是否执行；Submitted（提交信号）触发完成退出；预算限制资源消耗；trajectory（执行轨迹）保存 Agent 对象中的过程。

关系主线：执行前的交互、循环中的退出判断与外层保存各有时点。轨迹反映已进入对象并被保存的内容，不是与外部文件同步提交的账本；循环结束也不等于任务正确。

动作与消息的转换见 第03章；第04章提供实际命令和测试结果。

交互、退出与轨迹

控制与记录的分工

第04章 使用 DefaultAgent 让固定响应经过真实循环。日常命令行 mini 默认再加一层 InteractiveAgent，让人在命令执行前参与选择。预算检查由 DefaultAgent 提供，交互层可在部分限制到达时增加询问。运行中的消息可以保存成 trajectory JSON，供之后检查。

为什么默认 CLI 使用 InteractiveAgent

run/mini.py 组装 Agent 时使用：

get_agent(..., default_type="interactive")

InteractiveAgent 继承 DefaultAgent。这里的继承表示在已有类的基础上复用和扩展行为，因此不需要重新写一套 Agent loop。它主要在最小循环上增加：

  • 把消息打印到终端；
  • 支持人直接输入命令；
  • 在执行模型命令前询问确认；
  • 处理键盘中断；
  • 在 Agent 想结束时询问用户是否还有补充任务；
  • 在某些限制到达时允许用户调整限制。

可以把关系画成：

DefaultAgent
  └─ query → execute → observation 的最小循环

InteractiveAgent(DefaultAgent)
  └─ 在若干边界插入人类交互

三种交互模式

confirm：模型提命令，人在执行前确认

这是默认 mini.yaml 的模式。

沿用第01章的 README 文档任务，假设模型提出下面的读取命令；这里说明 confirm 模式的处理方式，不复用第04章的固定响应运行：

sed -n '1,220p' package.json README.md

在执行前，InteractiveAgent 可以显示命令并询问是否执行。用户可以：

  • 直接确认；
  • 输入说明拒绝本次命令；
  • 切换模式；
  • 中断并补充新的上下文。

确认模式的价值是把人放进关键动作之前：模型不会在一组 actions 生成后都无条件立即执行。

当前实现对同一条模型消息中的整组 actions 作一次确认，再按顺序执行，不是每条 command 分别弹窗。

yolo：模型命令无需执行前批量确认

在 yolo 模式中，模型生成的 action 直接进入 Environment。

它只取消命令执行前确认，结束前是否再询问是独立设置。因此切到 yolo，不意味着所有人工交互都会消失。confirm_exit 独立控制结束前询问。

实际命令仍交给同一个 Environment 执行。

human：由人直接提供命令

human 模式不请求模型来决定当前 action，而是提示用户输入命令。InteractiveAgent 把用户命令包装成带 action 的 user message，随后仍复用 Environment execution 和 observation formatting。

因此 human 模式不是“退出 Agent 系统去开另一个终端”。它仍然走当前 Agent 的消息与执行通道，只是 action 的提出者从 Model 换成了人。

模式改变了什么，没有改变什么

三种模式都没有改变一个事实：现实副作用仍由具体 Environment 产生。

确认为什么不等于 Sandbox

确认解决“人是否同意这段可见命令”

确认对话让用户看到模型准备执行的 command，并决定是否继续。它属于人机控制层。

Sandbox 解决“命令实际越界时能否被强制挡住”

如果一条看似普通的命令：

  • 通过脚本间接访问工作区外文件；
  • 启动另一个程序；
  • 在宿主允许时访问网络；
  • 展开到用户没有预见的路径；

仅仅点击“确认”不会额外建立 OS 级隔离。

确认也不能证明用户已经理解命令内部所有动态行为。

所以必须保留下面的边界：

表 2 / Table 2 · Sandbox 解决“命令实际越界时能否被强制挡住”
控制概念生效时点与责任仍需核对什么
确认（Confirmation）执行前由人判断是否接受可见命令不自动限制脚本间接产生的文件、网络和子进程行为
沙箱隔离（Sandbox Isolation）执行时由具体后端落实资源限制要检查所选 Environment 的实际能力；普通 LocalEnvironment 不因确认而获得隔离

mini-SWE-agent 支持选择不同 Environment，但每个 Environment 的实际隔离保证必须独立核对。

一次拒绝怎样回到循环

在 confirm 模式中，用户可以拒绝当前命令并写明原因。InteractiveAgent 把反馈变成用户消息，交回外层循环。例如：

用户：先不要修改，请先读取测试文件。
    ↓
反馈进入 messages
    ↓
下一轮模型看见反馈，再决定动作

因此，拒绝命令不一定等于结束任务。反馈可以成为下一轮的判断依据。该反馈经控制流异常回到外层循环，而不是执行已被拒绝的命令。

Agent 怎样正常提交

完成也通过 Bash 协议表达

默认任务模板要求 Agent 完成后执行：

echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT

并要求不要与其他命令组合。

这条命令不是为了修改项目。它是 Environment 能识别的完成信号。

LocalEnvironment._check_finished() 检查什么

执行命令以后，LocalEnvironment：

  1. 去掉输出开头的空白；
  2. 按行拆分；
  3. 检查第一行是否正好是 COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT；
  4. 检查 return code 是否为 0。

满足条件时，它抛出 Submitted，并把第一行之后的内容作为 submission。

Submitted 为什么是控制流异常

Submitted 继承 InterruptAgentFlow。它不是“程序出现意外 bug”的普通错误，而是一种从深层 Environment execution 跳回外层 Agent loop 的控制信号。

DefaultAgent.run() 捕获后把携带的 exit message 加入 messages。最后一条消息 role 为 exit，循环随即结束。

如果直接使用 DefaultAgent，主路径可以画成：

Model 请求完成命令
  ↓
LocalEnvironment 真正执行
  ↓
输出首行匹配 + returncode 0
  ↓
raise Submitted(exit message)
  ↓
DefaultAgent.run 捕获并追加消息
  ↓
last role == exit
  ↓
break

InteractiveAgent 还能在退出前询问

默认 confirm_exit 为 true。InteractiveAgent 捕获 Submitted 后，可以询问用户：

  • 直接确认结束；
  • 补充新任务；
  • 切换到 human 等模式继续。

因此“模型认为完成”与“交互用户同意结束”在该 CLI 中可以是两个时点。

下一次调用为什么也可能被阻止

即使尚未正常提交，系统也不能无限请求模型。DefaultAgent 在下一次模型 query 前检查已有步数、成本与经过时间；格式错误（例如模型响应不符合工具调用协议）可以先反馈给模型，连续达到上限才退出。这些检查发生在指定控制点，不是能随时打断所有进行中操作的万能计时器。human 命令绕过模型 query，不能把模型调用预算当作所有人工命令的限制。

Trajectory：保存当前已经知道的过程

Trajectory 是本次运行的结构化轨迹快照。它保存当前 messages，以及配置、模型统计和退出摘要，用来调试和复盘。它记录已经进入 Agent 对象的信息；不会自动知道消息之外的文件变化。

什么时候保存

run() 的循环在 finally 中调用 save(output_path)。配置了 path 且控制流走到 finally 时，程序会尝试把当前序列化数据写到该路径。硬终止会跳过这一步，写入自身也可能失败。

命令行 mini 默认也提供 trajectory 输出文件位置，并在结束时提示保存位置。

这比只在最后保存更有利于调试：中途出现预期错误或退出时，通常仍能看到已经进入 Agent 对象的消息。

保存时会覆盖同一个 JSON 快照，而不是为每个现实副作用建立独立的恢复协议。因此，实际效果与下一份快照之间可能存在记录缺口。

一个关键崩溃窗口

固定案例中，假设 Environment 正在执行修改 README 的命令：

t0  上一轮 observation 已经成功保存
t1  query() 把本轮 assistant action 加入内存 messages
t2  LocalEnvironment 启动 shell，shell 把 README 写到磁盘
t3  Python 进程被硬终止，output 尚未追加为 observation
t4  硬终止绕过本轮 finally/save，磁盘 snapshot 仍停在 t0

重新启动后，可能出现：

  • 文件系统中的 README 已经改变；
  • 因为 assistant action 与 Environment execution 位于同一个 step()，而该轮保存发生在外层 finally，上一次成功落盘的 trajectory 通常只到前一轮 observation，甚至还看不到本轮“准备执行修改”的 assistant action；
  • 没有本轮 action/observation 的落盘配对能直接证明命令成功、失败还是部分完成。

第06章 已实际注入一个绕过 Python finally 的 SIGKILL 窗口，并比较旧 trajectory 与已修改文件。它只验证指定时间点，不覆盖保存中途的其他失败。若异常能够正常沿 Python 栈展开，finally 仍可能保存当时已经进入内存的状态；不能把两类退出混写。

如果系统直接重做同一个命令，要先问“重复执行会不会多产生一次效果”。这种重复仍得到同一目标结果的性质，后面称为幂等性。不同命令可能不同：

  • “把确切旧字符串替换为新字符串”第二次可能报告找不到旧字符串；
  • “追加一行文本”可能产生重复；
  • “创建外部资源”可能产生两份资源；
  • 一些命令可能只执行了一半。

trajectory 对定位问题很有价值，却不能单独消除这个外部结果不确定窗口。

真实任务怎样结束

这里先看后面第22章真实函数与文档修复的最后一步，只用于说明退出协议：那次 mini 修复在第 8 次模型回答中先给中文结果，再发出 echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT。原生环境把它识别为完成控制，记录中标出 action was not executed；这不是普通 Bash 执行失败。文件修复和测试在之前已经发生，完成标记负责让循环收尾。不要把保存 trajectory 的成功提示当成另一次测试验收。第22章 完整过程

退出条件与记录缺口问答

问题 1。 confirm、human、yolo 分别由谁提出命令？confirm 是否等于 OS Sandbox？

解释。 human 由用户提出，confirm/yolo 由 Model 提出；confirm 增加执行前决策点，不能强制隔离文件与网络。

问题 2。 仅输出“我完成了”会触发退出吗？本地完成标记还要求什么？

解释。 不会。LocalEnvironment 要求去掉前导空白后的输出首行匹配完成标记，并且 returncode 为 0，才抛 Submitted。

问题 3。 在上面 t0–t4 的假设中，磁盘没有保存写入 observation，能否认定 README 没有改变？

解释。 不能。假设中 t2 已写入文件，t3 硬终止使轨迹只保存上一轮；实际效果（effect）与保存之间有窗口。应核对现实，再决定后续工作。下一章将给出这个窗口的实际运行结果。

异常、预算与保存协议

拒绝反馈怎样回到外层循环

InteractiveAgent 把拒绝原因放入 UserInterruption 携带的 user-role message。UserInterruption 属于 InterruptAgentFlow；DefaultAgent.run() 捕获这类控制信号，把消息加入 messages。它表达当前进程的交互控制，不能据此推导跨进程审批已持久保存。

整批确认的实现条件

当前实现会先收集这一条模型消息中的全部 commands，再调用一次 _ask_confirmation_or_interrupt(commands)。只要其中至少一条 command 不匹配 whitelist，就显示一次 Execute N action(s)?，由用户对整组 actions 作一次确认；确认后再按顺序执行。默认 whitelist 为空。这不是“每条 command 分别弹一次确认”。

confirm_exit 独立控制提交前是否询问，默认 true；--yolo 只移除执行前确认。需要理解立即退出行为时，另查 --exit-immediately。

完成命令为何会留下 not executed 占位

默认 CLI 使用的是 InteractiveAgent，它在这里多一个需要准确记录的 v2.4.6 实现细节：

  1. LocalEnvironment.execute() 识别完成标记后直接抛出 Submitted，没有把普通 output dict 返回给调用方；
  2. InteractiveAgent.execute_actions() 的 finally 仍会格式化 observation；
  3. tool-call formatter 发现这一条 action 没有对应 output，会补一个 returncode: -1、exception_info: "action was not executed" 的 observation；
  4. 如果用户确认结束，Submitted 随后继续向外传播，DefaultAgent.run() 再追加真正的 exit message。

所以当前默认 InteractiveAgent 的具体消息序列是：

assistant：完成 tool call
  ↓
LocalEnvironment：完成命令确实执行并触发 Submitted
  ↓
tool observation：当前实现补出 "action was not executed"
  ↓
exit：Submitted

占位文本描述的是 formatter 没有收到普通 output；实际命令已经执行并触发 Submitted。判断此次执行必须结合 exit，不能仅凭这条 synthetic observation。

中文说明与 submission 不是同一个字段

固定案例要求“用中文总结”。在默认 tool-call 响应中，这段中文可以出现在 assistant message 的普通 content 中，并被终端显示、被 trajectory 保存。

submission 则来自完成标记之后的命令标准输出：

第一行：COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT
后续行：才会被 _check_finished() 拼成 submission

默认 prompt 又要求完成命令单独执行：

echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT

如果严格执行这条单行命令，标记之后没有后续输出，因此 exit extra 中的 submission 通常是空字符串。于是要区分：

assistant content：模型在完成 tool call 同一消息中写出的中文说明
submission：完成标记之后由命令输出提供的文本

二者都可能进入 trajectory，但不会因为用户语义上都像“最终回答”就自动成为同一个字段。

限制怎样阻止无限循环

这一节的三个 Agent limit 都位于 DefaultAgent.query()，所以首先约束的是“准备进行下一次模型调用”的路径。confirm 和 yolo 都会进入这条 Model query 路径；human 模式则在 InteractiveAgent.query() 中直接接收用户命令并提前返回，不调用 super().query()。

因此，human 模式的 action 不会经过下面三项 query-level limit 检查，也不会增加 n_calls。它仍会进入 Environment，所以仍受单条本地 command timeout 等执行层限制。

Step limit

step_limit 限制 Model query 次数。0 表示不启用该限制。

如果限制为 5，系统关注的是已经发生多少次 query()，不是执行了多少条 Bash action。

Cost limit

cost_limit 根据 Model adapter 报告并累计的 cost 判断是否继续。默认 mini.yaml 当前设置为 3.0。

成本统计依赖具体模型响应和成本计算。如果模型没有正确注册成本信息，源码中也有相应错误或忽略配置；不能把配置值简单理解成外部账单的绝对保证。

这里判断的是当前累计成本，无法预知下一次请求的实际费用，因此可能在一次请求后超过阈值，再于下一轮停止。Agent 的 n_calls、cost 和开始时钟属于对象；run() 只重建 messages 等任务输入，不把这些预算归零。GLOBAL_MODEL_STATS 则是同一进程内共享的调用次数与成本统计对象，还支持可选的全局限制。这里的 LitellmModel 在收到响应并计算成本后更新它，检查限制时可能抛出 RuntimeError。这与当前 Agent 对象的预算是两层控制，都不能预留未知费用或在请求中途自动取消。

Wall-time limit

wall_time_limit_seconds 使用 Agent 持有的开始时间检查经过秒数。开始时间在 Agent 对象构造时记录，而不是每次 run() 开头重新记录；0 表示不启用。

它在下一次进入 DefaultAgent.query() 前检查，与单个 LocalEnvironment command 的 timeout 不同：

Agent wall-time guard：准备调用模型时，对自 Agent 构造以来经过时间的检查
Environment timeout：这一条命令最多执行多久

它不是一个实时抢占计时器：不会在已经开始的 Model request 或 Environment command 中途自动介入。正在执行的 command 仍由 Environment timeout 控制；human 模式若持续输入命令，也不会经过这个 query-level wall-time check。

达到限制后的控制流

query() 在请求下一次模型前检查限制。达到 step/cost 条件时产生 LimitsExceeded；达到 wall-time 条件时产生 TimeExceeded。

在纯 DefaultAgent 中，它们通过 InterruptAgentFlow 进入 exit message。InteractiveAgent 对 step/cost limit 可以在交互终端询问新的限制；对 TimeExceeded 则不会通过修改 step/cost 继续绕过时钟限制。

如果没有可交互 stdin，InteractiveAgent 也不会强行调用输入提示造成 EOF 崩溃，而是让限制信号正常退出。

FormatError 怎样形成反馈循环

哪些情况可能是格式错误

默认 native tool-call 路径中，例如：

  • 模型没有产生任何 tool call；
  • 调用了未知工具名；
  • arguments 不是合法 JSON；
  • arguments 缺少 command。

文本变体中，找不到恰好一个规定围栏 action 也会形成 FormatError。

一次 FormatError 不一定立即结束

DefaultAgent.run() 单独捕获 FormatError。它会：

  1. 补记这次已发生模型调用的 cost；
  2. 增加连续格式错误计数；
  3. 如果尚未达到上限，把格式反馈消息加入 messages；
  4. 下一轮允许模型根据反馈重新输出。

只要有一次干净 step，连续格式错误计数就会重置。

连续错误达到上限

如果 max_consecutive_format_errors 为正且达到该数量，Agent 加入 RepeatedFormatError exit message，从而结束循环。

这是一个简单的活性保护：避免模型持续违反 action 协议而无限消耗调用。

落入 except Exception 的未处理异常与“退出消息”

如果异常不是预期的 InterruptAgentFlow 路径、并且落入 run() 的 except Exception 分支，代码会调用 handle_uncaught_exception()，加入包含：

  • exit_status；
  • exception_str；
  • traceback；
  • 空 submission；

的 exit message，然后继续重新抛出原异常。

这有两个效果：

  1. trajectory 中尽量留下诊断信息；
  2. 调用者仍能感知未处理异常，而不是被静默吞掉。

“记录了一条异常 exit”不表示错误已经恢复，只表示诊断上下文被尽量保留下来。

这个分支不等于捕获所有 BaseException。例如，纯 DefaultAgent 下的 KeyboardInterrupt、SystemExit 不应未经核对就归入这里；InteractiveAgent.step() 对键盘中断另有自己的交互处理。

serialize() 的主结构

DefaultAgent.serialize() 生成一个可 JSON 序列化的字典，主要包含：

info
  ├─ model_stats

保存的是快照式 JSON

当前 save() 使用 Path.write_text(json.dumps(...)) 覆盖写入完整序列化结果，而非逐条追加事件。这条路径没有先完整写临时文件、再原子 rename 到目标路径的协议：如果进程恰好在 write_text() 过程中被硬终止，目标 trajectory 文件自身也可能被截断或成为无效 JSON。

这是由覆盖写入方式推得的另一个失败窗口。第06章注入的是写 README 后、保存轨迹前的窗口，没有实际注入轨迹覆盖写到一半的情况。快照能保存已进入对象的信息，恢复所需的其他责任列在下面。

Trajectory 与 durable ledger 的区别

表 3 / Table 3 · Trajectory 与 durable ledger 的区别
问题执行轨迹（Trajectory）当前能帮助什么还不能自动保证什么
看见执行过程保存 messages、配置、统计与退出摘要每个外部效果都有全有或全无的保存边界
调试格式错误保留反馈和部分原始响应信息崩溃后一定从精确位置恢复

可用于恢复核对的持久执行记录（durable ledger）还需要明确以下合同：

  • 谁拥有写入权；
  • 每条工作和 effect 的稳定身份是什么；
  • 一次记录更新是否原子，即要么完整提交、要么不生效；
  • 崩溃发生在 effect 前、effect 后还是结果保存后；
  • 不确定结果如何对账；
  • 哪些状态可以安全重试；
  • 多个观察者怎样得到同一终态。

固定案例的完整退出轨迹

下面仍是“项目代码正确、修正文档后测试通过”的简化教学序列，不是 第04章 或 第22章 的真实 trace：

system
  ↓
user task
  ↓
assistant: Bash call，读取文件
  ↓
tool: 文件内容
  ↓
assistant: Bash call，修改 README
  ↓
tool: returncode 0
  ↓
assistant: Bash call，运行 npm test
  ↓
tool: tests passed
  ↓
assistant: Bash call，输出 COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT
  ↓
tool: InteractiveAgent 当前补出的 action was not executed observation
  ↓
exit: Submitted

上面这条 synthetic tool observation 来自默认 InteractiveAgent 的补位逻辑；若直接使用 DefaultAgent，Submitted 会从 Environment 越过普通 observation formatting，序列中不会出现这一步。

这条序列中，assistant 里的命令是模型意图，tool 消息承载 Environment 返回的观察，Submitted 经外层处理才使循环退出。README 的修改发生在文件系统，不在消息列表内部。

崩溃位置决定最后留下哪份记录：写入前只有旧文件；写入后、保存前可能是新文件加旧 trajectory；本轮保存成功后才有覆盖该轮消息的快照。若硬终止落在 trajectory 的覆盖写入过程中，文件自身还可能不完整，不能假定总能得到一份完整的旧快照。

限制与异常分支问答

问题 1。 yolo 是否关闭 confirm_exit？human 命令是否经过 DefaultAgent.query 的预算检查？

解释。 yolo 只取消执行前确认，confirm_exit 独立；human 输入命令绕开 Model query 及该处预算检查，但仍经过 Environment timeout。

问题 2。 cost_limit 和 wall_time_limit 是否能中途抢占请求、保证绝不超额？复用对象会重置预算吗？

解释。 都不能；guard 在下一次 query 入口按已有统计检查，进行中的操作不受其抢占。run 不重置对象计数、成本与构造时钟。

问题 3。 InteractiveAgent 为完成 action 填入 not executed，为什么不能据此认定命令没执行？

解释。 完成命令已运行，但 Environment 抛 Submitted 而没有普通 output 返回；formatter 对缺口生成占位。它不能证明 effect 未发生。

问题 4。 什么错误进入反馈循环，什么普通异常记录 exit 后仍会向调用者抛出？SIGKILL 属于哪一类？

解释。 FormatError 可作为反馈继续，连续达到上限才退出；落入 except Exception 的异常会记录 exit 后重新抛出。SIGKILL 直接终止进程，两条 Python 路径与 finally 都不会执行。

确认、提交与硬终止分别留下什么

InteractiveAgent.execute_actions 与 DefaultAgent.run / save 共同形成三种代表路径：

表 4 / Table 4 · 确认、提交与硬终止分别留下什么
路径命令与消息保存结果（Persistence）
执行前拒绝被拒绝的命令不执行，拒绝信息成为后续反馈外层正常走到 finally 时保存当前消息
完成命令触发 Submitted命令已经产生完成输出；没有普通 output 的位置由 formatter 补位，外层记录 exit正常退出路径保存当前快照
写 README 后遭 SIGKILL文件可能已改变，进程尚未返回和追加这一轮结果Python finally 不执行；此前快照不能代表最后的文件状态

补位文本、退出消息和磁盘文件各描述不同对象，不能用任意一个代替另外两个。
