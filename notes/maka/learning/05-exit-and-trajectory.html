第 05 章｜交互（Interaction）、退出（Exit）、预算（Budget）与执行轨迹（Trajectory）

本章概览

智能代理（Agent）能执行命令以后，还需要决定谁同意执行、何时停止，以及留下什么记录。本章把交互（Interaction）、退出（Exit）、预算（Budget）和执行轨迹（Trajectory）放回运行支撑（Agent Harness）：确认（Confirmation）决定是否开始，提交信号（Submission Signal）结束代理循环（Agent Loop），预算（Budget）限制后续调用，保存（Save）把已知过程写到磁盘。它们分别回答不同问题；任务成功（Task Success）仍须靠验收，已存记录也可能落后于效果（Effect）。

前情回顾：从行动请求（Action）到任务成功（Task Success）

第03章区分了三个相邻步骤：模型（Model）提出行动请求（Action），执行环境（Environment）真正运行命令并返回执行输出（Output），运行支撑（Agent Harness）再把结果整理成观察消息（Observation Message）。观察消息（Observation Message）承载观察结果（Observation），本体是供后续读取的消息（Message）。因此，看到一条命令只能证明它被提出；看到命令返回码（Return Code）为 0，也只证明那次命令按自身约定结束。

第04章把这个区别放进修复案例：README 原先写错测试命令，formatDuration(125) 原先返回 2:25，要求是 2:05。在使用正确的 npm test 后，已有案例的测试从 2 项通过、2 项失败变为 4 项通过、0 项失败；修改范围还必须符合 README 与实现文件的约束。这些结果共同支撑那个限定案例的任务成功（Task Success）。案例采用预先写好的响应和真实本地执行，不能据此评价真实模型（Model）的修复能力。

现在还有三个问题没有回答：执行前有人不同意怎么办；模型（Model）说“完成”怎样让程序停下；文件改好了，记录是否也已经保存（Save）？本章分别追踪这些控制点。读者只需记住上述背景，不需要先读后面的恢复（Recovery）或分布式执行章节。

1. 先分清确认（Confirmation）、退出（Exit）与保存（Save）

智能代理（Agent）推进任务，运行支撑（Agent Harness）承担调用、执行、消息（Message）组织和停止控制。代理循环（Agent Loop）指这些决策、执行与反馈反复衔接的过程。这里讨论 mini-SWE-agent 的具体实现，类名 DefaultAgent 与 InteractiveAgent 是实现入口，不是所有智能代理（Agent）的统一定义。

命令执行得到什么？执行输出（Output）与观察消息（Observation Message）返回码（Return Code）为 0 不等于整个任务成功（Task Success）

目标与约束是否满足？任务成功（Task Success）的验收需要测试结果、修改范围和任务要求共同支持

2. 交互（Interaction）：谁提出命令，谁允许执行

三种交互模式（Interaction Mode）

默认命令行界面（Command-Line Interface，CLI）通过 get_agent(..., default_type="interactive") 选择 InteractiveAgent。它继承（Inheritance） DefaultAgent：继承（Inheritance）是复用已有类并扩展部分行为，因此基本代理循环（Agent Loop）不需要重写。扩展内容包括打印消息（Message）、接收人工命令、执行前询问、键盘中断反馈，以及结束前追加任务。

表 2 / Table 2 · 三种交互模式（Interaction Mode）
交互模式（Interaction Mode）命令由谁提出执行前的确认（Confirmation）实际执行者
确认模式（confirm）模型（Model）对需要询问的一整批命令询问一次执行环境（Environment）
免执行前确认模式（yolo）模型（Model）跳过这道批量询问执行环境（Environment）
人工模式（human）人人直接提供本次命令执行环境（Environment）

例如，模型（Model）在独立的命令行界面（CLI）场景中提出 sed -n '1,220p' package.json README.md。确认模式（confirm）会让人先看命令，允许继续、写下拒绝原因，或切换模式。这只是交互（Interaction）说明，不是第04章固定运行记录的新增步骤。

一次模型（Model）响应可能含多个行动请求（Action）。实现先收集这一批的全部命令；只要至少一条不匹配白名单（Whitelist），就询问一次 Execute N action(s)?，获准后依次执行整批。默认白名单（Whitelist）为空。因此，“每次都询问”不能被理解为“每条命令之间都再停下来问一次”。

免执行前确认模式（yolo）只改变这道执行前询问。它不绕过执行环境（Environment），也不自动关闭独立的 confirm_exit；结束时是否继续询问，由该配置与 --exit-immediately 等入口设置控制。

人工模式（human）将人的命令包装成带有 extra.actions 的用户消息（Message），再走相同的执行环境（Environment）和观察消息（Observation Message）整理过程。它是在代理循环（Agent Loop）内替换本次命令的来源，没有跳出整套运行支撑（Agent Harness）。

拒绝如何成为下一轮可读的反馈

拒绝时，InteractiveAgent 抛出 UserInterruption，其中携带用户角色的反馈消息（Message）。它属于用于改变代理循环（Agent Loop）走向的控制流异常（Control-flow Exception）；外层 DefaultAgent.run() 捕获其基类 InterruptAgentFlow，把消息（Message）追加进 messages，随后可以继续。

于是，模型（Model）下一轮能看到拒绝原因，并提出新的行动请求（Action）。被拒绝的命令不会在该分支继续执行。这是进程内的交互（Interaction）协议，不能据此推出已有跨进程的持久审批记录或重启后自动续接机制。

3. 退出（Exit）：提交信号（Submission Signal）怎样结束代理循环（Agent Loop）

先看完成命令，再看实际消费者（Consumer）

本例的完成协议要求单独运行下面这条命令，不要把它接在其他命令后面凑成一条：

echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT

命令先由 LocalEnvironment 真正执行。执行输出（Output）的消费者（Consumer）是 _check_finished()，它检查返回码（Return Code）和标准输出（Standard Output），再决定是否通过 Submitted 异常（Exception）发出提交信号（Submission Signal）。仅在普通说明文字中写“任务完成”，不等于触发了这个协议。

下面是 _check_finished() 的关键判断，添加了教学注释；这是类方法中的片段，不是独立脚本。output 是本次命令的执行输出（Output），Submitted 是携带结束信息的异常（Exception）类型。

lines = output.get("output", "").lstrip().splitlines(keepends=True)
# 去掉首部空白后，检查首行标记；同时要求命令返回码为 0。
if (
    lines
    and lines[0].strip() == "COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT"
    and output["returncode"] == 0
):
    # 首行之后的标准输出（Standard Output）才进入 submission 字段。
    submission = "".join(lines[1:])
    raise Submitted(
        {
            "role": "exit",
            "content": submission,
            "extra": {"exit_status": "Submitted", "submission": submission},
        }
    )

匹配过程容许前导空白，首行还会去除首尾空白；不是在任意一行找到标记就结束。返回码（Return Code）非 0 时，也不会走这个成功匹配分支。

承载提交信号（Submission Signal）的异常（Exception）类型 Submitted 继承（Inheritance） InterruptAgentFlow。这里用异常（Exception）机制把“结束当前代理循环（Agent Loop）”从执行环境（Environment）传到外层，并不意味着发生了意外故障。外层追加退出消息（Exit Message），执行到本轮 finally 时尝试保存（Save），再检查最后一条消息（Message）的角色；角色是 exit 才结束代理循环（Agent Loop）。

人可以在退出（Exit）前补充任务

默认 confirm_exit=true 时，InteractiveAgent 会先截获提交信号（Submission Signal），询问是否结束。人可以按回车结束，也可以补充任务，或切换到人工模式（human）。补充任务会转成用户反馈并回到代理循环（Agent Loop）。

因此，模型（Model）判断“可以完成”和人决定“现在结束”是两个时点。这个询问检查的是是否继续工作，不能把它当成自动测试，也不能单凭按回车就补出任务成功（Task Success）的证据。

为什么完成命令会留下 action was not executed

普通 DefaultAgent 收到提交信号（Submission Signal）后，不会得到该命令通常应返回的执行输出（Output）字典。交互（Interaction）分支还多一层 finally：无论是否收到提交信号（Submission Signal），它都会调用格式化器，为这一批行动请求（Action）补齐观察消息（Observation Message）。

需要按顺序读这四步，才能解释已核对的交互（Interaction）分支行为：

  1. LocalEnvironment.execute() 已执行完成命令，随后抛出提交信号（Submission Signal）。
  2. 因为函数没有普通返回，该命令的执行输出（Output）没有追加进 outputs。
  3. InteractiveAgent.execute_actions() 的 finally 仍调用格式化器；缺少匹配结果时，格式化器生成占位观察消息（Observation Message），含 returncode: -1 和 exception_info: "action was not executed"。
  4. 如果人允许结束，提交信号（Submission Signal）继续传到外层，外层再追加真正的退出消息（Exit Message）。

这里的占位内容描述“没有收到匹配的普通返回”，不能单独证明命令未执行。必须连同执行环境（Environment）的完成判断和最后的退出状态（Exit Status）一起解释。也不能把这个特殊分支推广到所有 returncode: -1：普通命令失败还需要按其实际错误调查。

回答文字与 submission 分别来自哪里

模型（Model）在同一条助手消息（Message）里写的中文总结属于 content，可以显示在终端，也能进入执行轨迹（Trajectory）。submission 则只取完成标记首行之后的标准输出（Standard Output）。

若命令只有上面的 echo，标准输出（Standard Output）通常只有标记那一行，submission 就是空字符串。空字符串不表示助手没给总结；有总结也不表示它自动被复制进 submission。两个字段的消费者（Consumer）需要按各自来源读取。

后面的第22章真实案例保存（Save）了一次原生 mini 命令行界面（CLI） / K3 的限定记录：第 8 次模型（Model）响应给出中文结果说明并发出完成命令，随后出现上述占位内容。这是已有运行片段；修复和测试发生在此前，本章没有重新运行它，也没有把占位内容当作 Bash 失败。

4. 预算（Budget）：检查发生在哪一个时点

三种限制分别数什么

DefaultAgent.query() 在发起下一次模型调用（Model Query）之前检查限制。先检查调用次数和累计成本，再检查已过时间，通过后才增加 n_calls 并调用模型（Model）。这不是后台随时抢占正在运行工作的计时器。

表 5 / Table 5 · 三种限制分别数什么
预算（Budget）或限制实际计量与检查需要保留的条件
步数限制（Step Limit）n_calls 达到 step_limit 后阻止下一次模型调用（Model Query）计的是模型调用（Model Query），不是 Bash 命令条数；0 表示不启用此限制
成本限制（Cost Limit）模型调用（Model Query）前检查模型协议适配器（Model Adapter）累计到 self.cost 的成本默认配置为 3.0，0 表示不启用此限制；下一次请求费用事前未知，某次响应后累计值可能已经越过限制
墙钟时间限制（Wall-time Limit）模型调用（Model Query）前用当前时间减 _start_time从对象构造时起算；0 表示不启用，不是每条命令的超时设置

用 nnn 表示模型调用（Model Query）前对象里的调用次数 n_calls，ccc 表示对象里的累计成本 cost，SSS 和 CCC 分别表示配置的步数限制（Step Limit）与成本限制（Cost Limit）。阻止本次模型调用（Model Query）的条件是：

(S>0∧n≥S)∨(C>0∧c≥C).(S > 0 \land n \ge S) \lor (C > 0 \land c \ge C).(S>0∧n≥S)∨(C>0∧c≥C).

这里两项都包含等于：模型调用（Model Query）之前已经达到正数上限，就不再开始本次请求。限制必须为正值才启用；设为 0 时，对应条件不成立。墙钟时间限制（Wall-time Limit）在后面的独立检查中，以已过整秒数与正数上限比较。

例如，步数限制（Step Limit）设为 5，一条响应中包含多条 Bash 命令，仍不能把它误读成“最多执行 5 条命令”。而成本限制（Cost Limit）依赖模型协议适配器（Model Adapter）如何登记费用：登记失败是抛错还是忽略还受配置影响，不能据此承诺绝不超过外部账单金额。

n_calls、cost 和 _start_time 属于同一个对象。run() 会重建任务消息（Message），但不会把这三个字段重新归零。因此，复用对象运行新任务，不能直接假定获得全新预算（Budget）。

模型调用（Model Query）限制与命令超时是两个控制点

墙钟时间限制（Wall-time Limit）不会在模型（Model）请求或命令已经执行时主动中断它。命令是否超时，由执行环境（Environment）的独立超时设置处理。

人工模式（human）接收命令的分支不经过 super().query()：不会执行上述三个模型调用（Model Query）限制检查，也不增加 n_calls，但命令仍受执行环境（Environment）的超时规则约束。这一差别来自调用路径，不能把“人工也在同一个代理循环（Agent Loop）”当成“人工也经过每一个检查点”。

进程内另有共享统计 GLOBAL_MODEL_STATS，记录调用次数与成本，并可配置共享限制。已核对的 LitellmModel.query() 先取得服务响应、计算成本，再调用 GLOBAL_MODEL_STATS.add()；共享检查通过后，才继续解析行动请求（Action）并返回消息（Message）。共享预算（Budget）在响应后检查，与单对象的模型调用（Model Query）前检查是两个不同位置。

add() 先累加本次成本并把调用次数加 1，再进行判断。用 NNN 和 GGG 表示这次累加后的共享模型调用（Model Query）次数 _n_calls 与成本 _cost，QQQ 和 KKK 分别表示共享 call_limit 与 cost_limit，抛出 RuntimeError 的条件是：

(K>0∧G>K)∨(Q>0∧N+1>Q).(K > 0 \land G > K) \lor (Q > 0 \land N + 1 > Q).(K>0∧G>K)∨(Q>0∧N+1>Q).

共享成本使用严格大于；共享模型调用（Model Query）次数虽然也写成严格比较，却比较的是更新后的 N+1N+1N+1。对正整数调用上限 QQQ，这一项等价于 N≥QN \ge QN≥Q，不能误读成“调用数已经超过 QQQ 才报错”。两种共享限制也只在正值时启用，0 表示关闭对应限制。

特别是共享模型调用（Model Query）上限为 2 的那一行：第二次服务响应已经收到，但共享检查让 LitellmModel.query() 在返回正常消息（Message）之前抛错。不能把它写成“等到第三次响应才发现超限”，也不能认为本次助手消息（Message）必然已经追加进 DefaultAgent.messages。随后走普通异常（Exception）处理，具体记录行为见下一节。并发调用还可能交错更新共享统计，上表只解释串行条件，不承诺并发请求获得精确的全局配额。

两层预算（Budget）都不是预知下次费用或抢占所有进行中请求的机制；要读懂一次停止，既要看比较运算符，也要看计数更新和检查发生的位置。

达到限制以后怎样退出（Exit）

步数限制（Step Limit）或成本限制（Cost Limit）触发 LimitsExceeded，墙钟时间限制（Wall-time Limit）触发 TimeExceeded。默认代理循环（Agent Loop）通过 InterruptAgentFlow 分支接收它们携带的退出消息（Exit Message），再尝试保存（Save）。

交互（Interaction）分支在有交互式标准输入时，可以询问新的步数限制（Step Limit）与成本限制（Cost Limit）。没有交互式输入时则直接传出限制异常（Exception），避免因为再次读输入而产生 EOFError。墙钟时间限制（Wall-time Limit）单独传出：只增加步数或成本不会重置时钟，反复询问也无法解除它。

5. 异常（Exception）怎样改变消息（Message）与退出（Exit）

先读分支框架，再读代理循环（Agent Loop）代码

这里有三类处理，不能合并成“出错就停”：格式错误（Format Error）可能变成下一轮反馈；控制流异常（Control-flow Exception）携带拒绝或结束等消息（Message）；其余落入 except Exception 的异常（Exception）会留下诊断信息后重新抛出。

下面摘出 DefaultAgent.run() 的完整代理循环（Agent Loop）分支，省略的是代理循环（Agent Loop）之前的初始消息（Message）构建，添加了中文注释。self.step() 包含本轮模型调用（Model Query）与执行；add_messages() 追加内存消息（Message）；handle_uncaught_exception() 的内容在代码后解释。代码保留格式错误（Format Error）的成本补记、连续计数、终止阈值，以及所有异常（Exception）分支。

while True:
    try:
        self.step()
        # 一轮正常完成后，清零连续格式错误（Format Error）计数。
        self.n_consecutive_format_errors = 0
    except FormatError as e:
        # 模型调用（Model Query）抛错前可能已产生费用；错误消息（Message）携带的成本在此补记。
        self.cost += e.messages[0].get("extra", {}).get("cost", 0.0)
        self.n_consecutive_format_errors += 1
        if 0 < self.config.max_consecutive_format_errors <= self.n_consecutive_format_errors:
            self.add_messages(
                *e.messages,
                {
                    "role": "exit",
                    "content": "RepeatedFormatError",
                    "extra": {"exit_status": "RepeatedFormatError", "submission": ""},
                },
            )
        else:
            self.add_messages(*e.messages)
    except InterruptAgentFlow as e:
        # 消息（Message）决定是继续反馈，还是在本轮末尾退出（Exit）。
        self.add_messages(*e.messages)
    except Exception as e:
        self.handle_uncaught_exception(e)
        raise
    finally:
        # 只有执行到这里，才会尝试把当前状态写入配置路径。
        self.save(self.config.output_path)
    if self.messages[-1].get("role") == "exit":
        break

finally 说明正常展开调用栈（Call Stack）时会尝试这一步，不是“任何情况下必定写成文件”的承诺。没有配置路径时不写文件；写入自身可能失败；硬终止（Hard Termination）不会让 Python 执行这个分支。

格式错误（Format Error）为什么允许再次模型调用（Model Query）

原生工具调用（Native Tool Calling）的模型协议适配器（Model Adapter）可能在没有工具调用（Tool Call）、工具名未知、参数不符合 JavaScript 对象表示法（JavaScript Object Notation，JSON）的格式，或缺少 command 时产生 FormatError。使用文本代码块的模型协议适配器（Model Adapter），则可能要求响应中恰好存在一个规定格式的行动请求（Action）代码块。具体判定取决于模型协议适配器（Model Adapter），不能把两种输入协议混为一谈。

第一次格式错误（Format Error）通常还不结束：错误消息（Message）回到上下文，让模型（Model）修正格式。连续次数达到正数阈值后，程序追加 RepeatedFormatError 的退出消息（Exit Message）；阈值为 0 时不启用这个连续错误上限。一轮正常完成会清零连续计数。补记费用则避免把“没解析成功”误当成“没有发生收费请求”。

诊断信息保留以后，异常（Exception）仍会抛出

handle_uncaught_exception() 追加退出消息（Exit Message），其中记录异常（Exception）类型对应的 exit_status、exception_str、调用栈（Call Stack） traceback 和空 submission。随后原异常（Exception）重新抛出；若正常展开到 finally，程序还会尝试保存（Save）。这使排查有机会看到失败现场，但没有自动修复或吞掉异常（Exception）。

这条分支只针对 except Exception 捕获的异常（Exception）。KeyboardInterrupt、SystemExit 等不能一概套入它；InteractiveAgent.step() 另有键盘中断处理。硬终止（Hard Termination）则连这种 Python 处理机会也没有。

6. 执行轨迹（Trajectory）：保存（Save）了哪一份已知状态

快照（Snapshot）包含什么，谁会读取

执行轨迹（Trajectory）是当前对象已知过程的结构化快照（Snapshot），包括消息（Message）、配置、统计和退出（Exit）信息。复盘工具或另有装载入口的程序可以成为消费者（Consumer）；记录存在本身，不表示消费者（Consumer）已经接通自动恢复（Recovery）。

serialize() 先组织主要字段，再合并模型（Model）与执行环境（Environment）各自的序列化（Serialization）结果：

表 7 / Table 7 · 快照（Snapshot）包含什么，谁会读取
字段本例含义
messages当前内存消息（Message）序列，包括已追加的行动请求（Action）、观察消息（Observation Message）或退出消息（Exit Message）
info.model_stats.instance_cost、api_calls当前对象累计成本与调用次数
info.config.agent、agent_type配置和具体实现类型
info.mini_version记录使用的 mini 版本
info.exit_status、submission从结束信息整理出的退出状态（Exit Status）与提交内容
trajectory_format此处为 mini-swe-agent-1.1，表示格式标识

配置里存在某条预先安排的命令，不等于该命令已经执行。判断一项效果（Effect）还要看执行记录与现实状态；第06章会具体展示这个容易误读的地方。

为什么是快照（Snapshot）写入，而非可靠的执行账本（Durable Ledger）

save() 的框架很短：先得到序列化（Serialization）数据；有路径时创建父目录，再把整份数据按 JavaScript 对象表示法（JSON）编码并写入该路径；最后返回数据。下面是带教学注释的实现片段，self.serialize(*extra_dicts) 就是上一张表解释的序列化（Serialization）过程，并合并调用者额外提供的数据；path 是传入的 Path 对象或空值。

data = self.serialize(*extra_dicts)
if path:
    # 普通文件写入：没有与工具修改文件构成同一个原子事务。
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(json.dumps(data, indent=2))
return data

默认代理循环（Agent Loop）每轮在 finally 中调用它；命令行界面（CLI）提供输出路径并显示位置。但这种覆盖写没有先写完临时文件再原子替换的步骤，更没有把工具产生的效果（Effect）与执行轨迹（Trajectory）合成一个不可分割的事务。

因此有两个不同风险：文件已经修改，本轮记录还没写；或者正在覆盖执行轨迹（Trajectory）时被中断，采用 JavaScript 对象表示法（JSON）的文件内容可能不完整。后者是根据写法作出的推断，下一章没有实际注入这个窗口，不能把两种情况都算作已运行结果。

可靠的执行账本（Durable Ledger）还要明确：谁负责写记录；怎样标识同一项工作与效果（Effect）；哪些记录更新是原子的；执行前后中断时如何判定未知；何时允许重试；多个消费者（Consumer）怎样看到一致的终态。本例的执行轨迹（Trajectory）不能只凭保存（Save）了采用 JavaScript 对象表示法（JSON）的文件就自动获得这些能力。

崩溃窗口（Crash Window）：记录为什么会落后一整步

把一轮拆开来看，模型调用（Model Query）与执行都在 self.step() 内部，保存（Save）在本轮末尾。于是可能出现下面的顺序：

表 8 / Table 8 · 崩溃窗口（Crash Window）：记录为什么会落后一整步
时点文件与进程里发生的事情磁盘上的执行轨迹（Trajectory）
t0第一轮读取结束，观察消息（Observation Message）已追加已记录第一轮读取
t1第二轮模型调用（Model Query）返回，行动请求（Action）已在内存仍是第一轮
t2执行环境（Environment）写好 README，效果（Effect）已发生仍是第一轮
t3硬终止（Hard Termination）发生，尚未追加本轮观察消息（Observation Message）仍是第一轮
t4已无机会执行本轮 finally 中的保存（Save）缺少第二轮行动请求（Action）与观察消息（Observation Message）

这不是“程序已经记录请求，只差结果”那一种窗口：在这里，磁盘记录连第二轮行动请求（Action）都没有。也不能用缺少结果推出完全失败；效果（Effect）可能已经发生，其他任务里还可能只完成了一部分。

如果是普通异常（Exception）并且调用栈（Call Stack）能正常展开，finally 有机会保存（Save）内存中的行动请求（Action）；这与硬终止（Hard Termination）不同。下一章的完整案例专门验证表中的一个窗口，没有实现自动恢复（Recovery）。

重试之前为什么要读回效果（Effect）

幂等性（Idempotency）指重复执行仍得到相同目标状态的性质。某次精确文本替换重复运行可能不再找到旧文本；追加一行却可能产生两行；远程创建请求还可能建立两个资源。多条命令中途停止，也可能留下部分完成的状态。

所以，执行轨迹（Trajectory）不足以决定“整步重来”。先读取当前文件、检查差异，再判断剩余工作，才有依据。即使其中一个替换操作具有幂等性（Idempotency），也不能因此推断整个组合命令都适合重放。

7. 直接问答：把控制、证据与恢复（Recovery）分开判断

问：命令返回码（Return Code）为 0、提交信号（Submission Signal）、任务成功（Task Success）是同一件事吗？

答：不是。返回码（Return Code）说明命令按自身约定结束；提交信号（Submission Signal）使代理循环（Agent Loop）进入退出（Exit）协议；任务成功（Task Success）依赖目标和约束的验收。即使完成命令返回码（Return Code）为 0，也不能补出从未执行过的测试结果。

问：确认模式（confirm）是不是逐条批准，而且批准后就获得沙箱隔离（Sandbox Isolation）？

答：两个判断都不成立。它对同一条响应里需要询问的整批命令问一次，获准后依次执行。确认（Confirmation）也不会改变操作系统权限；沙箱隔离（Sandbox Isolation）需要执行环境（Environment）另外实施。

问：免执行前确认模式（yolo）为什么还可能在结束时询问？

答：执行前确认（Confirmation）与 confirm_exit 是不同控制点。前者由交互模式（Interaction Mode）改变，后者决定是否在退出（Exit）前接收人的追加任务。

问：助手有中文总结，为什么 submission 仍为空？

答：总结在助手消息（Message）的 content 中；submission 来自完成标记之后的标准输出（Standard Output）。独立 echo 只有标记时，后者通常为空。消费者（Consumer）必须读对字段，不能把空字段解释成没有回答。

问：出现 action was not executed 就应重跑完成命令吗？

答：不能只凭该字符串决定。在已解释的交互（Interaction）完成分支里，它是缺少普通返回时生成的占位观察消息（Observation Message），命令其实已执行。要连同提交信号（Submission Signal）、退出状态（Exit Status）和实际任务材料判断。

问：设置预算（Budget）后，长命令是否会在整段时间一到就被终止？

答：模型调用（Model Query）前的墙钟时间限制（Wall-time Limit）不抢占已经开始的命令。命令超时由执行环境（Environment）另行控制。人工模式（human）也绕过模型调用（Model Query）前检查，不能据此宣称所有路径都受同一个总时限约束。

问：为什么连续格式错误（Format Error）有时会退出（Exit），有时还能继续？

答：计数尚未达到正数阈值时，错误反馈进入下一轮；达到阈值时追加 RepeatedFormatError。阈值为 0 不启用这项上限，正常一轮会清零连续计数。其他异常（Exception）也不是全走这条可继续的分支。

问：有 finally 和执行轨迹（Trajectory），为什么还要讨论恢复（Recovery）？

答：硬终止（Hard Termination）可以让 finally 根本不执行；已经写好的文件也不会因此自动回滚。保存（Save）本身还可能失败。恢复（Recovery）时需要核对效果（Effect），不能把磁盘快照（Snapshot）当成现实的完整复制品。
