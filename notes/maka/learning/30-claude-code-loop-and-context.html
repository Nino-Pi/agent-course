第 30 章｜Claude Code：代理循环（Agent Loop）与上下文（Context）

本章概览

核心问题：动作反馈怎样推进修复，长对话整理后又怎样保留继续工作所需的信息？

关键概念：观察结果（Observation）来自实际执行；模型输入（Model Input）是本次请求使用的材料；上下文预算（Context Budget）限制材料规模；上下文压缩（Context Compaction）改变历史（History）表示；摘要（Summary）保存继续所需的任务状态。

关系主线：工具反馈改变下一步判断，预算要求选择和整理材料；恢复（Resume）出的历史（History）仍须结合当前文件、最新约束和检查结果，才能支持下一次行动或交付。

前情回顾：工具反馈、模型输入（Model Input）与历史（History）

第15章说明，磁盘中保存的材料不一定进入当前模型输入（Model Input）。第16章把行动请求（Action）、实际执行和工具结果（Tool Result）分开。第19章进一步指出，上下文压缩（Context Compaction）重建的是后续输入表示，不能把“已改动”自动提升成“已验证”。

带着这条关系阅读 Claude Code：模型（Model）决定下一步，运行支撑（Agent Harness）提供工具、环境与输入管理，观察结果（Observation）再影响后续判断。本章依据公开产品行为解释机制，图和案例是教学抽象，不假定闭源内部存在 Maka 同名的执行（Run）、检查点（Checkpoint）或执行器（Executor）。

本章沿用后续 Claude Code 专题的独立案例：scan.py 接受目录、检查 Markdown 链接并生成报告。带空格的路径会失败，README 命令也有问题；已有一份用户未提交的配置修改。任务允许修改相关实现、README 和必要的回归测试（Regression Test），要求验证，禁止上传和发布，必须保留原配置差异（Diff）。

1. 先让观察结果（Observation）改变一个具体判断

当前有两个未知：错误来自参数拆分还是文件解析，正确测试入口是什么。因为本题尚无这些依据，立即大改会把假设当成结论；这不表示所有修复必须遵守固定动作顺序。若已经读到足够源码，先提出局部补丁再验证也可能合理，关键是说明依据和待查条件。

Claude Code 的公开说明以收集材料、行动、检查解释代理循环（Agent Loop），同时区分负责判断的模型（Model）与负责执行的工具（Tool）。运行中可以补充输入，也可以中断；两种入口不能简单等同于撤销全部既有效果（Effect）。公开工作方式

回边传递的不是一个泛泛的“完成”。Read 返回目标函数，可以减少实现未知；测试（Test）返回断言（Assertion），可以减少行为未知；权限拒绝（Permission Denial）改变可执行方案；网络超时可能仍留下效果未知（Outcome Unknown）。四种结果都参与判断，却不能互相替代。

图中的验收检查（Acceptance Check）是一项教学职责，不是本章声称产品存在独立、确定性的自动验收器。模型（Model）提出结束后，仍要核对原目标、允许范围和检查记录。

2. 完整案例：从一个路径变成两个参数说起

以下七步均为教学推演，没有启动 Claude Code 或运行完整扫描器。其中失败和通过是题设中的过程结果，用来解释各步需要什么观察。

第一步，固定边界。 读取任务、相关项目规则及当前差异（Diff），记下用户已有配置修改。它属于初态，不能计入本次成果，也不能为了得到干净差异（Diff）而覆盖。

第二步，寻找入口。 README 写 python scan.py docs input，项目测试（Test）却用 main(["docs input"])。前者在命令解释器（Shell）中可能成为两个参数，后者明确是一个列表元素。文档缺少正确路径表达，与实现是否正确仍是两件事。

第三步，定位失败链。 在本题带空格样例中观察到 FileNotFoundError；读取相关实现后，发现它把参数列表拼成字符串，再按空格切开。问题不是“空格天然不能用”，而是调用层丢掉了参数边界。

# 只演示参数边界；不调用命令解释器（Shell），不读取目录。
args = ["docs input"]
broken = " ".join(args).split(" ")
kept = list(args)
print(broken)
print(kept)
['docs', 'input']
['docs input']

这段轻量程序的输出可直接核对：一个路径经错误转换变为两个。它不证明完整扫描器已修好；真实调用还须确认参数怎样进入实际消费者（Consumer）。

第四步，收窄修改。 若合同要求接受参数列表，就让列表穿过调用层，避免重新拆分；README 同时改为带引号的路径示例，例如 python scan.py "docs input"。仅修文档不能证明实现已正确，反之亦然。

第五步，验证（Verification）。 本题参考过程分别检查普通路径和空格路径，并确认报告写到允许位置。退出码（Exit Code）为0之外，还要读取目标用例确实被发现和执行的结果。

第六步，检查差异（Diff）。 参考结果只触及允许的实现、回归测试（Regression Test）和README，用户原配置修改仍在。行为与范围各有依据，不能只用测试（Test）变绿代替两项检查。

第七步，交付（Delivery）。 报告参数边界的修复、检查结果与未覆盖场景；禁止上传和发布仍生效，成果停留在本地。任务完成不会自动产生新的操作授权（Authorization）。

七步不是固定算法。若测试（Test）推翻了修复假设，下一步应回到定位；若返回重复或无关材料，也不能仅因工具调用（Tool Call）增加就宣布更接近目标。

3. 上下文预算（Context Budget）怎样约束模型输入（Model Input）？

完整历史（History）可以很长，单次模型请求必须有界。项目规则、当前任务、已读片段、观察结果（Observation）、技能说明包（Skill）和工具定义可能共同占用上下文窗口（Context Window）。/context 是查看实际占用的入口，官方演示里的词元（Token）数不能当成本仓库的费用记录。

先定义同为词元（Token）的三个量：窗口容量 WWW，输出预留 RoutR_{\mathrm{out}}Rout​，以及已经单独保留的协议与固定系统开销 HHH。粗略分配给其余材料的预算为：

B=W−Rout−H.B=W-R_{\mathrm{out}}-H.B=W−Rout​−H.

HHH 只能扣一次；已算入这部分的系统材料，不应又从 BBB 重复扣除。B≤0B\le0B≤0 时，不能继续塞入可变材料。这个式子用于预算分配，不是 Claude Code 的公开实现公式。

材料组装还涉及编码边界，不能把几段文本的独立长度当成严格可加。完整请求必须再按实际编码检查：

Nrequest=Tokens⁡ ⁣(Encode⁡(Assemble⁡(M)))≤W−Rout.N_{\mathrm{request}} =\operatorname{Tokens}\!\left(\operatorname{Encode}(\operatorname{Assemble}(\mathcal M))\right) \le W-R_{\mathrm{out}}.Nrequest​=Tokens(Encode(Assemble(M)))≤W−Rout​.

M\mathcal MM 是全部请求材料，包含前面预留的固定部分；NrequestN_{\mathrm{request}}Nrequest​ 是完整编码后的输入词元（Token）数。组装（Assemble）与编码（Encode）只是教学记号，不规定产品的固定排列顺序、缓存计费或压缩触发阈值。

容量足够与事实足够是两个判断

假设本题产生20万字符日志，只有12行能说明参数拆分错误。这两个数是教学情境中的字符与行数，不是词元（Token）测量。整份反复放入请求会占空间，只写“测试失败”却丢掉定位依据。

合理的材料应保留失败类型、关键片段、运行条件和原始位置，缺少什么再读取什么。最短摘要（Summary）不一定最好：若删掉“空格路径未复测”，后续可能错误交付；即使只有一行，也已破坏任务含义。

4. 上下文压缩（Context Compaction）后，材料怎样重新进入请求？

公开说明描述了整理旧工具输出、必要时概括对话的处理，早期细节可能丢失；/compact 可提供关注点。图中的事实检查也是教学问题，不是自动正确性证明。某项大输出反复填满窗口时，仍需改变获取策略，不能把整理本身当成进展。输入整理说明

现在回到第五步的中间：实现已改，普通路径已经检查，空格路径还未复测。此时可以留下如下连续性摘要（Summary）：

objective: 修复扫描器的空格路径，并修正 README
constraints:
  - 不上传仓库，不发布结果
  - 保留用户已有配置修改
observed:
  - 空格路径在命令字符串切分处变成两个参数
changed:
  - 调用层保留参数列表
checks:
  - 普通路径通过
  - 空格路径待复测
next: 运行空格路径用例，再核对最终 diff

这不是产品的摘要模式（Summary Schema）。objective/constraints 保留目标与限制，observed 记录当时观察，changed 记录改动，checks 区分已查与待查，next 只是后续计划。把最后两行压成“问题已解决”会把计划改写成事实；缺少预期与实际结果时，必须回查。

重建规则（Reconstruction Rule）取决于材料来源

CLAUDE.md 是项目指令文件，自动记忆（Auto Memory）是 Claude Code 保存供后续使用的材料，钩子（Hook）是在指定事件（Event）触发的扩展动作。它们的装载时机不相同。

例如，压缩前读过子目录规则，压缩后却尚未回读匹配文件，当前模型输入（Model Input）就可能没有原文。诊断应查实际装载，不能只搜索磁盘。工具控制见第33章，自动记忆（Auto Memory）与技能说明包（Skill）见第42章。

5. 三个失败场景：摘要（Summary）流畅也可能不能用

约束丢失。 “禁止上传”只在很早的聊天中出现，整理后模型（Model）准备把文件交给外部服务。本次继续必须重新提供任务约束；持续规则可放在适当项目指令中；必须强制阻断的外传还需要权限（Permission）和实际执行边界。文字保留与操作拦截是不同职责。

大输出反复回填。 摘要（Summary）刚生成，又整份读取同一日志，窗口立即填满。应限定测试（Test）目标、限制返回片段、保留完整日志的定位入口。只增大窗口可能延后问题，未改变每次取入无关材料的方式。

最新要求变成只读。 用户说“先停下，只做报告”，旧计划里的 Edit 不再代表新授权（Authorization）。应区分已开始动作、已发生效果（Effect）和尚未执行计划，报告当前文件状态。中断控制不会自动撤销外部变化；相关边界见第43章。

三种情况都要求重问：当前材料是否准确表达现在的任务？不能仅凭摘要（Summary）的语气、格式或长度判断。

6. 恢复（Resume）、分叉（Fork）与重新确认现场

公开会话（Session）管理说明中，恢复（Resume）延续原标识，分叉（Fork）创建另一标识；后者复制对话背景，不自动创建独立文件目录。本节采用命令行界面（Command-Line Interface，CLI）的公开说明，不能将其全部启动细节推及所有桌面或网页入口。

表 3 / Table 3 · 6. 恢复（Resume）、分叉（Fork）与重新确认现场
目的使用的对象仍需检查
昨天未完成，今天继续原会话（Session）的历史（History）文件、分支（Branch）和外部状态是否改变

标准设置文件会在启动时重读；原来经 --mcp-config、--settings、--plugin-dir、--fallback-model 或 --add-dir 提供的配置需要重新提供，运行中 /add-dir 加入的目录也不自动恢复。权限模式（Permission Mode）取决于恢复入口及例外，不能笼统说沿用上次。历史（History）里的未完成工具也不会因为恢复（Resume）就自动补完或重跑。会话（Session）恢复说明

因此，保存历史（History）解决信息连续性，重读现场解决事实新鲜度。昨天“文件未改”不能代替今天检查，分叉（Fork）也不能证明两份工作已经隔离。

7. 从字段走到消费者（Consumer）：接受、回读还是拒绝？

先声明材料形状，再让消费者（Consumer）作出判断。它们是教学设计，不是 Claude Code 的应用程序编程接口（Application Programming Interface，API）或内部实现。

type Continuation = {
  objective: string;
  constraints: string[];
  observations: { claim: string; observedAt: string; locator: string }[];
  completed: string[];
  outstanding: string[];
};

type RequestMaterials = {
  instructions: string[];
  continuation: Continuation;
  selectedObservations: string[];
  deferredReferences: string[];
  missingRequiredFacts: string[];
};

类型只声明材料形状，不能自动证明摘要（Summary）真实、权限（Permission）有效或文件未变。observedAt 是观察时间，locator 是回查位置；两者都不自动保证新鲜。示例消费者（Consumer）还要接收当前目标、操作许可，以及外部检查者已经发现的变化位置。

type CurrentGate = {
  objective: string;
  action: "edit" | "report";
  allowEdit: boolean;
  changedLocators: string[];
};

function decide(m: RequestMaterials, gate: CurrentGate) {
  // 当前目标来自本次权威输入，不能由旧摘要（Summary）自行授予。
  if (m.continuation.objective !== gate.objective)
    return { kind: "read", reason: "task_changed" };
  if (gate.action === "edit" && !gate.allowEdit)
    return { kind: "reject", reason: "edit_not_allowed" };
  const stale = m.continuation.observations.some(o =>
    gate.changedLocators.includes(o.locator));
  if (stale || m.missingRequiredFacts.length > 0)
    return { kind: "read", reason: "facts_missing_or_stale" };
  // 待查项目不能变成通过；此处只决定下一步，不代跑测试。
  if (m.continuation.outstanding.length > 0)
    return { kind: "check", reason: "checks_outstanding" };
  return { kind: "ready", objective: gate.objective };
}

为读清结果，下面单独设定一个基线：两类路径已查，相关观察引用 scan.py，仍禁止上传。随后每次只改一个条件；这些是本地轻量程序输入，不是产品执行轨迹（Trajectory）。

8. 常见场景与完整参考结论

问题。 Claude Code 为什么能够实际修代码？

参考答案。 模型（Model）提出行动请求（Action），运行支撑（Agent Harness）把它连接到文件和命令，再反馈观察结果（Observation）。权限（Permission）、输入管理与验收仍需正确接线；仅暴露命令解释器（Shell）不保证修复成功。

问题。 已有完整会话（Session）记录，为什么还需要上下文压缩（Context Compaction）？

参考答案。 持久保存容量与一次模型请求容量不同。历史（History）便于恢复（Resume）和回查，当前模型输入（Model Input）只能选取有界材料。整理可能有损，必须保留任务状态并允许补取细节。

问题。 摘要（Summary）写“已修好”，测试（Test）记录却是未运行，以哪个为准？

参考答案。 拆开主张：文件可能已改，行为尚未验证。应保留“已实施、待检查”，按授权（Authorization）和环境补查；自信语气不提升证据。

问题。 恢复（Resume）昨天的会话（Session），可以直接继续 Edit 吗？

参考答案。 先核对本次依赖的文件和最新要求。用户、其他会话（Session）或切换分支（Branch）都可能改变现场；历史（History）只能说明当时观察。

问题。 整理后仍缺事实，应连到完成还是补取材料？

参考答案。 按缺口回读、缩小范围或报告无法继续；不将未完成目标改成成功，也不无限重读整份大输出。

问题。 若任务改成只读检查十个配置文件，设计怎样变化？

参考答案。 保留任务、观察结果（Observation）、判断与验收的循环，去掉修改分支。验收改为覆盖十个对象、报告一致和冲突项以及不可读文件；输出仍有界，文件范围仍需明确，无须强行加入代码回退。

工具控制的完整场景见第33章，产品机制参考见第61章。
