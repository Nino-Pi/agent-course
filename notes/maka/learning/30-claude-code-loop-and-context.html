第 30 章｜Claude Code：循环与上下文

本章概览

核心问题：Claude Code 怎样用动作反馈推进修复，并在长对话整理后保留继续所需的信息？

关键概念：工具观察：实际执行返回的内容；工作输入：本次请求选用的材料；上下文预算：输入与输出可用空间；压缩：整理旧历史的表示；会话分支：从已有对话起点另行推进；验收：核对最终任务条件。

关系主线：动作产生观察，观察参与下一步决策；预算促使系统选择和整理输入，恢复出的材料仍要结合当前文件、最新约束和测试结果判断。

所属主题：第 1–3 节对应 第28章 架构，第 4 节起对应 第36章 上下文。

前置：第15章 模型实际看到什么、第16章 工具循环、第19章 长上下文。本课用公开产品行为解释机制，图中的职责框和案例数据属于教学抽象。

1. 从 Maka 带过来的问题

Claude Code 的工作循环同样由模型提出动作、宿主执行动作，再将结果送回模型。工具结果是否改变下一步，取决于它补充了什么观察，以及当前约束允许什么行动。

本章及后续 Claude Code 专题沿用一个 Python 文档检查器案例：scan.py 接受目录，检查 Markdown 链接并生成报告。当前路径中带空格时扫描失败，README 又给了错误命令。用户要求修复并验证，但不允许上传仓库或发布任何内容。目录里已有一份用户尚未提交的配置修改。本课题设允许修改扫描器的相关实现、README 和必要的回归测试；配置中的用户改动必须保留。

这里先调查两个未知：失败来自参数拆分还是文件解析，正确测试入口是什么。同时守住两个已知约束：修改限于题设文件，测试通过后也不发布。Agent 如果直接开始编辑，就把定位假设提前当成结论；如果看到测试通过就发布，则把完成任务错误扩展成了后续操作。

Claude Code 官方用收集材料、行动、检查结果解释工作循环，并区分模型判断与宿主提供的工具和环境。产品也允许运行中打断或补充指令。课程据此研究可观察的输入与输出，不假定内部存在与 Maka 同名的 Run、checkpoint 或 executor 类型。

2. 动作、观察与验收之间传递什么

图中间是动作与观察的循环，项目规则、当前要求和完成条件共同约束它。核对验收条件表达本课希望系统完成的职责，并不声称 Claude Code 使用一个独立且确定性的验收组件。

回边传递的是可区分的实际结果。Read 返回目标函数，减少了实现未知；测试返回断言，减少了行为未知；权限拒绝减少了可执行方案；网络超时往往没有减少远端效果未知。四种结果都进入后续判断，但含义完全不同。

表 1 / Table 1 · 2. 动作、观察与验收之间传递什么
环节本题输入应保留的工作状态对后续的有效输出
定义任务（Task definition）修空格路径与 README；禁止上传目标、允许范围、验收条件有边界的调查任务
调查（Investigation）文件结构、测试配置、当前 diff已观察事实与未验证假设分开可复现的失败入口
修改（Modification）当前文件内容与修复假设修改对象、理由、待测条件真实文件变化
检查（Verification）测试结果与修改后 diff通过、失败、未运行分别记录是否足以交付
收口（Delivery）目标与全部检查记录剩余限制、未覆盖场景用户可理解的结论

这张表可以用来审查一次对话：如果某步只有模型的意图，没有真实观察，就不能跨过对应的状态门槛。

3. 正常案例：七步如何收敛

下面是完整的教学推演，不是一次真实 Claude Code 运行。

第一步，建立边界。 读取任务、相关项目规则和当前修改状态。已有配置 diff 暂时只作为起始事实记录。它既不能自动归到本次改动，也不能为了让检查更干净而被覆盖。

第二步，找入口。 README 写着 python scan.py docs input，但项目测试使用参数列表调用 main(["docs input"])。现在只能断言文档示例缺少必要的路径表达，不能断言实现一定相同。

第三步，复现。 使用包含空格的临时样例得到 FileNotFoundError。读取失败附近代码后发现实现先拼接命令字符串再按空格切分。现在有了从输入到失败的具体链：一个路径变成两个参数。

第四步，收窄修改。 若设计合同要求接受参数列表，就保持参数列表穿过调用层。此时 README 的引号示例与实现参数边界是两处相关但独立的修复，不能只修文档就宣布功能已完成。

第五步，运行检查。 普通路径和空格路径都验证，确认报告写到题设允许的位置。命令退出码为零还不够，应确认测试实际发现并执行了目标用例。

第六步，检查 diff。 核对只触及本次允许的实现、测试与文档，用户原有配置差异仍在。测试证明某些行为，diff 证明修改范围，两者互补。

第七步，交付。 说明输入边界如何修复、实际执行了什么检查、哪些场景尚未覆盖。禁止上传的约束仍然生效，因此交付停留在本地结果。

动作数量并不固定，选择取决于待解决的未知；实际返回也可能重复、无关或仍无法判断。如果测试把假设推翻，流程应回到定位，而不是补一句解释后继续原方案。

4. 当前工作输入与完整历史是两份不同的对象

完整对话能很长，单次模型请求必须有界。项目规则、当前请求、已读文件片段、工具观察、已装载的 Skill 等可以共同进入工作输入。/context 是查看占用与装载情况的产品入口；官方交互图中的 token 数是演示数据，不能用来估计本仓库真实成本。

本例使用以下预算关系：

可用输入预算 = 模型窗口 - 输出预留 - 协议及系统开销
本轮输入 = 必要规则 + 当前任务状态 + 相关观察 + 必要工具定义

这只是课程预算模型。实际协议、缓存计费和产品内部保留策略需要各自核对。用这条模型思考时，最先问的不是“摘要压缩率多高”，而是“哪些材料常驻、哪些按需、哪些可以回查”。

假设本题突然产生 20 万字符日志，其中只有 12 行能够证明参数拆分错误。把整份日志反复放进请求会消耗预算；只写“测试失败”又失去定位价值。较好的教学方案是保留失败类型、关键片段、运行条件和原始记录位置，下一步缺什么再取什么。这个选择是在维护任务所需的信息，不是在奖励最短摘要。

5. 第二张图：整理工作输入后怎样继续

官方描述接近限制时会整理旧工具输出并在需要时概括对话；早期细节可能丢失，也提供 /compact 的关注点入口。图中的“是否足够”是教学验收问题，不代表一个已公开的自动正确性证明器。

重建后的输入至少要能回答：用户要什么、当前实际改了什么、还缺哪项验收、最近结果能支持什么。现在回到上述第五步的中间：实现已改，普通路径已验证，空格路径尚待复测；假设此时整理输入。这个时点的连续性摘要可表示为：

objective: 修复扫描器的空格路径，并修正 README
constraints:
  - 不上传仓库，不发布结果
  - 保留用户已有配置修改
observed:
  - 空格路径在命令字符串切分处变成两个参数
changed:
  - 调用层保留参数列表
checks:
  - 普通路径通过
  - 空格路径待复测
next: 运行空格路径用例，再核对最终 diff

这是自拟内容格式，不是 Claude Code 摘要 schema。changed 与 checks 分开，正是为了防止压缩把“实现已改”提升为“功能已通过”。若摘要缺少 expected/actual，应补取观察，而不是按照记忆猜出错误细节。

不同材料采用不同的重建规则与装载时机；具体条件和限额可能随配置或版本变化。下表的 CLAUDE.md 是 Claude Code 的项目指令文件，auto memory 是它保存供后续使用的记忆材料；Hook 是宿主在指定事件触发的扩展动作。这里先看它们何时进入输入；工具控制见第33章：Claude Code 工具、Hooks 与安全，长期记忆见第42章：Claude Code 记忆、规则与 Skills。

表 2 / Table 2 · 5. 第二张图：整理工作输入后怎样继续
材料压缩后的公开处理对后续输入的影响
系统提示与输出风格不属于要概括的消息历史请求不是一整块任意截断的字符串
根级 CLAUDE.md、无路径范围的规则、auto memory从文件重新注入持久材料可以独立于聊天摘要恢复
嵌套 CLAUDE.md、路径规则随匹配文件的读取重新装入曾经出现过不保证立刻再次出现
已读或已改文件最多重新读取五个，优先最近修改自动回填有边界，不能假设全部源码仍在
较大文件超过所述单文件限额时保留路径引用有定位信息与有完整内容不同

先前 Hook 增加的材料随消息概括；匹配 compact 的 SessionStart Hook 可再次运行一次性动态材料与可重新生成材料不同

由这些重建规则可以解释一个具体故障：压缩前读过某个子目录规则，压缩后尚未读取匹配文件，模型当前输入就可能还没有那条规则。正确诊断要检查装载时机，而不是仅搜索磁盘上文件是否存在。

6. 三个失败场景：信息整理也会引入错误

场景一：禁止上传只在很早的聊天里出现。 压缩后模型准备调用外部分析工具。修复思路分两层：本次继续工作必须重新明确这一任务约束；持续适用的项目要求应放入适当的长期指令；必须强制阻断的数据外传还需要工具权限或执行边界。把所有问题都交给一句“请摘要保留”是不完整设计。

场景二：同一大日志被反复读入。 先压缩，再整份重读，再次挤满，形成输入整理的循环。课程方案是改变获取策略：限定测试目标、限制输出、保存完整日志但返回关键片段。只调高窗口可能延后问题，却没有改变每次都获取无关材料的方式。

场景三：用户中途说“先停下，只做报告”。 原计划里的 Edit 已不再代表下一步授权。教学上要区分已开始动作、已完成效果和尚未执行计划，记录哪些变化已经发生，再决定报告内容。产品的中断控制不能证明所有先前副作用自动消失；取消与回退见第43章。

三种失败的共同检查点是“当前输入是否仍准确表达现在的任务”。一份摘要语句通顺，并不足以证明它有用。

7. 会话连续性：resume、branch 与新会话

Claude Code 提供恢复既有会话和从既有历史分出新会话的操作；恢复延续原会话身份，分叉创建另一会话。新会话的长期背景则由其加载机制提供。会话入口与文件所在目录还应一起检查。

恢复也不等于所有启动配置自动重现。标准设置文件会重新读取，某些通过启动参数传入的 MCP、settings、plugin 或附加目录配置需要再次提供；权限模式还与恢复入口有关。因此一个昨天能调用的工具今天不可用，既可能是环境变化，也可能是恢复了历史却没有重建同一配置。“恢复任务材料”和“恢复执行条件”因此是两项不同检查。

表 3 / Table 3 · 7. 会话连续性：resume、branch 与新会话
想解决的问题合适的思考对象操作后必须重新检查
昨天任务没做完，今天继续原会话的历史与任务状态文件、分支和外部环境是否变化
想尝试另一种修复方案一份新分支会话及其背景两份会话是否写同一目录
这次工作与前一任务无关新任务输入与相关长期背景旧偏好是否适用于新范围
希望撤销错误修改文件状态与可恢复范围哪些修改被追踪、哪些是外部效果

从这里可以推导一个工程要求：保存历史解决信息连续性，重读现场解决事实新鲜度。 昨天记录“文件未修改”，不能替代今天的文件检查。分叉复制历史，也不会自动给另一份工作目录。

8. 请求构造的完整参考合同

以下参考接口表达本例的请求构造合同，不是 Claude Code API。

type Continuation = {
  objective: string;
  constraints: string[];
  observations: { claim: string; observedAt: string; locator: string }[];
  completed: string[];
  outstanding: string[];
};

type RequestMaterials = {
  instructions: string[];
  continuation: Continuation;
  selectedObservations: string[];
  deferredReferences: string[];
  missingRequiredFacts: string[];
};

接口的重点在 missingRequiredFacts。系统应当允许诚实地输出“当前信息不足”，再安排读取，而不是为了总能构造请求而编造完整状态。observedAt 标记观察时间，locator 提供补查入口，二者都不保证对应资源永远有效。

这份接口对四种条件变化给出具体结果：压缩后仍保留原目标；新增禁止修改后不再准入新编辑；目标文件变化后把旧观察标为需更新并重新读取；缺少测试结果时保留 outstanding 检查，不输出已通过。若其中任何一项不成立，请求即使更短，也没有保持任务语义。字符数与 token 数只衡量输入规模。

9. 常见场景与完整参考结论

题一：Claude Code 为什么能修代码，而普通聊天只能建议？

参考答案：模型提出行动，宿主把行动连接到真实文件和命令，再把结果作为观察送回。能力来自模型判断和可执行反馈环的组合。还需要权限、输入整理和交付验收；仅把 Shell 暴露给模型并不能保证正确修复。

题二：已有完整会话记录，为什么仍需压缩？

参考答案：保存能力与单次请求容量不同。完整记录帮助恢复和回查，工作输入只选择本轮需要的内容。压缩可能有损，因此必须保留关键任务状态，并允许重新获取细节。

题三：摘要写“代码已修好”，测试记录写“未运行”，以哪个为准？

参考答案：拆开主张。文件修改可能已完成，功能正确尚未验证。应把摘要改成“修复已实施，检查未运行”，再根据授权和环境补检。自然语言自信程度不会提升证据。

题四：恢复昨天的会话后可以直接继续 Edit 吗？

参考答案：先检查本次依赖的文件状态。历史保留的是当时观察；用户、其他会话或分支切换都可能改变目标。重新读取目标片段并核对改动责任，才能继续修改。

题五：在图中，压缩失败应连到任务完成还是补取材料？

参考答案：根据缺失内容补取或缩小任务，必要时报告无法继续。不能因窗口耗尽就把未完成目标标成完成；也不能无限重复整份大输出。应改变观察策略。

换成只读检查十个配置文件时，设计怎样变化？

参考答案：保留任务—观察—判断—验收的循环，删去修改分支。验收改为覆盖十个对象、记录一致与冲突项、说明不可读文件。日志仍需有界，分叉仍需限定文件范围；没有修改就无需强行加入代码恢复。
