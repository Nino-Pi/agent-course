第 25 章｜Host、Client 与连接连续性

本章概览

核心问题：界面失联时，怎样区分观察中断、执行器丢失与 Host 退出，避免重复工作？

关键概念：Host（宿主）：接纳工作并管理运行控制；Client（客户端）：提交意图和显示结果；快照：当前权威状态的表示；订阅游标：某条更新流的位置；未知效果：可能已执行但结果尚未确认；settled（资源结算）：清理与释放完成。

关系主线：连接按身份、快照和游标恢复观察；Host 存活时按原执行记录结算工作，宿主退出或客户端能力丢失则另按恢复合同处理。

前置：Owner 与执行身份、事实与视图、效果窗口。

核心路线

工作与界面为何有不同寿命

用户通过 Desktop、TUI 或 CLI 操作 Agent。直觉上很容易认为：哪个界面启动了任务，哪个界面就拥有任务；界面断线，任务也应该消失。

Maka 的边界不是这样。工作的长期控制责任和事实 authority 由 Runtime Host 与 Runtime/Storage 共同承载，Client 负责提交意图、订阅状态和呈现结果。长期逻辑责任不等于要求某一个 Host 进程永久存活；但下面的断线案例明确以当前 Host 仍存活为前提。

测试期间关闭 Desktop

S1/T7/R7 已经开始：

模型 step 1 → 并行 Read(package.json) 与 Read(README.md)
模型 step 2 → Edit(README.md)
模型 step 3 → Bash(test) 正在运行

就在 Bash 运行时，用户关闭 Desktop 窗口，或 Desktop Client 与仍然存活的 Host 失去连接。稍后，用户从 CLI 打开同一个 Session。

在同一 Host 仍存活、普通工具由 Host 执行的条件下：

Desktop connection lost
  ├─ 不凭断线宣布 R7 cancelled
  └─ R7 继续由 Host/Runtime 拥有

CLI connects to the same Host / Session
  → 取得 canonical snapshot
  → 从正确 sequence 继续订阅
  → 看到 Bash 结果和 R7 terminal

CLI 应先确认自己接入的是同一 Host 和 Session。看到同名项目或标题，不足以证明目标身份相同。也不应为了“恢复”再次发送同一条用户消息，因为那可能创建重复修改或重复测试。

合上笔记本可能让操作系统睡眠并暂停本地 Host；Host 进程退出或机器休眠属于 Host/recovery lifecycle，而不是单纯的 connection continuity。当前结论只证明：Client disconnect 本身不会取消一个已经 admission、且其 Host 仍存活的 execution；它不证明机器睡眠时工作仍持续消耗 CPU 或继续向前执行。

把循环放进 UI 进程会失去什么

许多 Demo 把 Agent loop 直接放在网页或 Desktop 进程里：

button click
→ UI process calls model
→ UI process executes tools
→ UI memory stores messages

这种设计简单，但有几个直接后果：

  • 页面刷新就丢失 active state；
  • UI 无法区分“网络断了”和“Run 失败了”；
  • 两个 Client 可能各自运行一份 Agent；
  • 重连时只好重发最后一条消息；
  • loading spinner 很容易被误当成业务事实。

Maka 把产品界面和长期执行 authority 分开，就是为了让连接生命周期不等于工作生命周期。

三种状态必须分开

Client UI state

例如：

  • 输入框内容；
  • 当前选中的 Session；
  • loading 动画；
  • 已渲染到第几个 stream event；
  • 本地窗口是否仍打开。

这些状态可以丢失或重建，不能证明 Run terminal。

Host connection state

例如：

  • Client 是否已认证；
  • WebSocket/IPC 是否连接；
  • 当前 subscription sequence；
  • capability offer（客户端声明可提供的能力）是否仍有效；
  • reconnect epoch（重连代际）是否变化。

连接状态决定 Client 能否继续通信，但不自动决定 R7 是否完成。握手还会检查 protocol version 与 compatibility epoch：它们表示通信双方是否兼容，与某条订阅的序列号或重连代际分别判断。

Canonical execution state

例如：

  • S1/T7/R7 是否已 admission；
  • AgentRun 和 RuntimeEvents 已持久化什么；
  • Tool T1/T2 记录到哪里；
  • 是否已有唯一 terminal fact。

这才是恢复和多 Client 观察时的裁决依据。

三种状态的恢复来源不同：

窗口状态      可以消失
连接状态      可以重建
canonical fact 必须从 durable authority 读取

Runtime Host 为什么存在

Runtime Host 接纳工作、管理连接和订阅，并让不同 Client 观察同一份执行状态。它的存活周期不等于某个窗口的周期。

真正的模型—工具 loop 仍由 Runtime 执行。Host 和 Runtime 不是竞争的两套 Agent，而是控制面与执行面的分工。

一次断线重连怎样发生

阶段 A：Desktop 断线

Desktop 不再收到 live events（实时更新）。Host 处理连接中断；如果这个 Client 还提供执行工具的能力，Host 也要按那条能力的约定处理丢失，不能只清除界面状态。

关键点：连接关闭本身不是 R7 的 stop 或 terminal fact。 若产品确实想在关闭窗口时取消任务，必须通过显式 stop/cancel operation 表达，而不是从 TCP/WebSocket 断开猜测。

阶段 B：R7 继续或进入自己的失败状态

在 Host 仍存活的前提下，如果 Bash 是 Host/Runtime 拥有的普通工具，执行和 settlement 继续由原 Run 管理。它可能成功、失败、超时或被显式取消；结果由工具和 Run 账本证明。

阶段 C：CLI 连接并选择 S1

CLI 先建立新的已认证连接，选择同一 Session target，并打开新的订阅。服务端返回当前 snapshot、新 subscriptionId 与这条订阅的起始 sequence。Snapshot 告诉它当前已接受的状态，而不是让它从自己最后一次 UI cache 猜测。

阶段 D：继续接收更新

CLI 在快照基础上接收后续增量。如果发现更新不连续，就重新读取权威快照，不用重复执行用户任务来补显示。sequence 与 epoch用于识别这些缺口。

阶段 E：CLI 看到 terminal

Bash 结算后，模型产生最终中文回答，R7 写入 terminal fact。CLI 收到的是这个事实的 projection。Desktop 以后重新打开，也应看到同一个 canonical 结论，而不是重新运行 T7。

执行者的位置决定断线后果

上述 Bash 由仍存活的 Host/Runtime 运行。若工具实际依赖 Desktop 操作浏览器或本机应用，断线影响的是执行者的一部分，不能直接套用 Bash 的结论。

表 1 / Table 1 · 执行者的位置决定断线后果
这次操作由谁执行Desktop 断线时先判断什么
Host/Runtime 的普通 Bash原 Run 是否仍在运行、工具是否已有结果；断线本身不取消它
Desktop 提供的 Client CapabilityClient 是否已获准开始、是否已返回结果；必要时保留效果未知

Query 重试和 Command replay 为什么不同

Query

Query 只读取状态，例如“给我 S1 当前 snapshot”。连接中断后重新发送，通常不会产生外部副作用，因此更容易安全重试。

Command

Command 会改变状态，例如“开始 Turn”“批准权限”“停止 Run”“发送消息”。如果 Client 已发送 command，但在收到响应前断线，它不知道 Host 是否已经接受。

盲目 replay 可能导致：

  • 创建第二个 Turn；
  • 重复批准或触发工作；
  • 重复外部副作用。

安全系统需要 exact identity、dedupe/admission contract 或重新查询 canonical state，而不是把所有 command 当普通 HTTP GET 重发。

在贯穿案例中，CLI 应读取 S1/T7/R7，而不是再次提交“检查配置、更新 README”。

核心问题解析

问题 1。 Host 仍存活时，Desktop 在普通 Bash 执行期间断线，是否等于 R7 被取消？

解释。 不是。连接关闭本身不是 stop 或 terminal fact；执行仍由原 Run 按自己的成功、失败、超时或取消规则处理。

问题 2。 CLI 接入 S1 时，为什么先读 snapshot，而不是重新提交 T7？

解释。 snapshot 用持久事实恢复观察；通知丢失不代表工作未接受或未执行。重发修改类 command 需要独立的 identity、payload 与去重契约。

问题 3。 同样一次断线，如果模型使用的是 Desktop 提供的外部能力，是否能直接套用普通 Host 工具的结论？

解释。 不能直接套用。先确认真实执行器与工具 lane；Client capability 断线时效果是否已开始，需要它自己的边界与记录。

实现深化

连接时序还要与资源寿命相接：断线可能只丢失观察流，也可能丢失真正的执行器，或伴随 Host owner 退出。三者需要读取的状态和恢复操作不同。

一次 turn.start：请求返回后，谁继续消费工作

在 S1/T7/R7 修复任务中，Client C1 提交请求，Host 已接纳，普通 Host 工具正在测试，此时 C1 失联。一次连接请求与已接纳的业务执行有彼此独立的寿命。下面的字母、数字与断线时点用于教学推演，不是实际捕获的运行记录。

开始前，Host 必须取得 State Root 的有效 writer authority。tryAcquireInteractiveRootOwner 经 root authority 获取写锁与 lease；kernel 启动时核对这个 owner，再完成组成、恢复和监听准备。State Root 组织长期控制状态，其身份与 Session 的 workspaceRoot/cwd 分开：前者回答“谁能修改这些运行记录”，后者回答“在哪份项目文件上工作”。同一 Root 的写锁不锁住整个项目，也不接管 Client 的浏览器或远端服务。

  1. 连接先被认证，operation 再被授权。 RuntimeHostConnectionSession.#handleRequest 对具体 operation 核对 grants 和边界，随后分派 turn.start。这里的 Peer 是通信对端；能连上它，不等于能观察 S1 或开始 T7。连接中的 requestId 用于匹配请求响应，不自动成为业务效果的幂等键。
  2. Turn 先持久准入，再交给 Runtime。 root coordinator 规范化内容、取得 reservation，并核对已知 admission。重复 T7 必须匹配原 execution、content、authorization；一个新 ID 加相同文字不是同一项 exact replay。新工作被接纳后，startRootMessageTurn 将已分配身份和 durability: 'required' 交给 SessionManager.sendMessage。
  3. Host 持有持续消费任务。 prepareAdmittedTurn 取得执行期间所需的 residency（保持宿主资源不被提前回收的持有条件），并登记 ActiveRootTurn；其 entry.done 承接 drainTurn，持续消费 Runtime events，送入 continuity 并完成终结清理。这里的 drain 是把事件流持续读完，不是“停止接纳新工作”的停机流程。这个消费者不在 UI 的渲染循环里。
  4. 回执和终态有不同消费者。 resolveStartDisposition 等准入启动结果并读取 canonical snapshot，给原请求返回接纳结果；drainTurn 继续处理其后的执行事件。Client 没收到回执时，T7 仍可能已经入账。若只为恢复观察，先查询/订阅 S1/T7/R7；不能用新 Turn 再做同一修改。

这条结构解释了普通主路中“连接关闭不等于取消”的原因：连接资源会释放，已接纳的执行仍有自己的 owner 和收尾任务。它没有承诺 Host 永不退出、工具永不失败或所有资源都在 Host。

同一个失联提示，三种不同的状态变化

用四个小对象记录本题状态，避免一个 connected=false 同时代表失去观察、失去执行器和失去 owner。组合方式是教学模型，不是新增产品 schema；其中 hostEpoch 标识宿主代际：

H = (State Root, 有效 writer, hostEpoch)       谁能控制运行状态
W = (Session, Turn, Run, 执行阶段)             哪份工作仍在推进
V = (connectionId, subscriptionId, nextSequence) 哪条观察流的下一帧
E = (执行者, 资源位置, 已知结果)                谁可能已改变外部世界

断线前假设 H 的 writer 有效，W=(S1,T7,R7,active)，V=(C1,U1,42)：U1 已接受 sequence 41，下一帧应为 42。E 此时是 Host 上的普通测试工具，结果尚未结算。

A/B 分支假设 Host 仍活着；C 分支先处理 owner 和持久事实，不能沿用旧界面的执行状态。

图中的箭头恢复的是连接、控制条件和视图，没有一条表示重新执行工具。A 还要求路径恢复受支持且未超出恢复预算；条件失效时，须重新判断逻辑连接与 Host 状态。B 的新订阅不能沿用 U1 的游标。若实际执行器在 Client，例如浏览器，断线还可能带来能力丢失或未知效果；不能因为 Host 活着就认定所有动作都能继续。

A：Peer 物理路径断了，逻辑流与 Host 还活着在支持恢复且未超预算的路径中，重新认证并 attach 新路径；原 Host connection、U1 仍可保留同一 U1 可继续等待 42；不能因路径换了就新建 T7 或声称迁移了 Host

A 中的 ResumablePeerStream.reserve/attach 还用 generation 拒绝迟到旧路径，按字节 offset 去重；ACK 是传输层字节确认；这条实现确认上层 read 已取走的字节，仍不证明 JSON 已处理、T7 已准入或文件已修改。B 中新 subscription.open 先返回 snapshot、subscriptionId 等信息，服务端在响应 flushed（经连接写出，不指数据库持久化）后才激活增量；Client 分别核对 hostEpoch、subscriptionId、sequence 与投影版本，不能把它们混成一个“全局版本”。这套检查能拒绝不匹配的更新，但不保证所有 Desktop/CLI 错误都能自动恢复。

C 还必须分开合作升级与意外崩溃：合作交接路径会关闭相关 admission、核对 seal、residency 和在途操作条件，再提交 detach；资源收束后才释放 owner。它可在对应接续合同下让后继物理执行继续同一逻辑 Turn，不能重新开放旧物理执行。项目文件、Client 浏览器、远端效果是否可用，是 E 的问题，不随 H 的 writer 移交自动解决。

若把 E 改成 Client 提供的浏览器点击，B 的结论也要改变：连接释放时仅 dispatched/accepted 的调用可报告 capability_lost；已进入执行准入、结果却没回来时可能是 outcome_unknown。Host 仍存活时，应由其按记录保存和解释这些状态，不能因此推断点击尚未发生，也不能排除持久化或 owner 失效。具体窗口见Client 能力断线。

这套设计适合多界面观察和较长工作：将业务身份、控制权与观察游标分别保存，可以重建显示而不重复效果。代价是必须管理资源持有、订阅 bootstrap、失效代际和未知结果。单进程脚本无需先复制全部协议；确实需要路径恢复时补 A，需要新 Client 观察时补 B，需要 owner 交接时再补 C。对照 Codex 的资源分支，不能仅凭“也有 App Server”就借用上述全部结论。

Host 的具体职责与其他唤醒机制

Runtime Host 承担以下长期控制职责：

  • State Root 的单 writer/lease（状态根的单写者约束）；
  • Client 认证和 protocol；
  • root execution admission；
  • Session 目标与 subscription；
  • stop、recovery 和 managed lifecycle；
  • Plan/Goal/Schedule/Graph 等 domain coordinator；
  • 共享 Session 的 grant/approval；
  • Client Capability broker（客户端能力中介）。

业务唤醒与恢复观察： Agent Graph 的 supervisor wake 也必须经过 Host root admission，随后创建新的普通 root Turn / Run，并不是把旧 Run 重新打开。Inter-agent Mailbox 则是可寻址 Agent 之间的通信与调度原语；它不同于本章的 Client ↔ Host connection continuity，后者是在重连后继续观察同一份 Host-owned canonical execution。

长期责任与执行载体能否分开

长期逻辑工作是否必须一直绑定同一份计算环境？Maka 的官方 Serverless 设计文章把它作为资源运行契约：需要时取得计算，之后按规则冻结、复用或释放；业务正确性不能依赖下次必定还是同一个进程。文章用外部 Sandbox/Actor 系统分析不同选择，不表示 Maka 已集成这些实现。

同一份 README 修复可以遇到四种恢复需求：

前两种涉及访问和 Host 生命周期，第三种涉及执行准入，第四种涉及保存计算现场。不能从某一层的恢复推导其他层也已恢复。

问题。 CLI 经新的 Peer 路由看到 S1/T7/R7 的旧记录，同时发现一份 Context checkpoint。能否据此说“Host 已搬到另一台机器，原浏览器进程仍在，R7 自动继续”？

参考答案

三项都不能。新路由只支持连接路径的判断；Context checkpoint 服务于模型历史，不证明浏览器现场仍在；是否能继续执行还须核对 authority、已保存结果和 continuation 条件，不能从可读记录推导旧 Run 被重新打开。要证明计算迁移或进程恢复，需要对应机制与运行证据。

升级 Host 时，工作完成了吗？

假设 R7 已执行一次 Edit，结果已写入账本；此时客户端要更新 Host。当前 cooperative handoff 会请求下一个可证明的持久边界。抵达边界之前取消交接，R7 继续；抵达后由 Host 完成 seal 和 detach，后继物理 invocation 继续同一个逻辑 Turn。旧物理执行结束，不代表用户的修复任务完成，也不应再次执行已经确认的 Edit。

再假设导出 S1，导出前检查时它空闲，复制期间另一个客户端开始工作。若只凭第一次检查打包，就可能把运行中的状态叫作静止快照。当前 portable export 在一致数据库副本中判断 quiescence，使检查对象与交付对象相同；包中没有用户项目目录或凭据，更没有旧浏览器/进程的执行现场。

问题。 看到 handoff_pause 和一个 Session 导出包，能否直接将 T7 标为完成并在另一台机器重发 Edit？不能：前者证明物理边界与后继接续权，后者是有范围的状态出口；完成事实、接管权及旧效果是否可重做仍须分别核对。这个情境用于区分交接与交付，不能当作已经完成的跨机运行实验。

Client 提供能力时的断线窗口

如果调用依赖 Desktop 提供的 Computer Use/Client Capability，需要把“愿意接收”和“准许执行”分开：

Host 发 call → Client accepted（接受准备请求）
  → Host 完成准入条件；Runtime 提交 T1
  → prepared.admit 发出 admitted（准许执行）
  → Client 执行 → 返回结果

仍存活的 Host 在连接释放时，broker 将 dispatched 或 accepted 阶段的丢失判为 capability_lost；发送执行准入之后没有收到结果，则保守地判为 outcome_unknown。因此，仅收到 Client 的 accepted，并不意味着已经准许它产生效果。这个区别依赖 Client 遵守协议，不是 Host 能监视一切外部进程的证明。发送 admitted 本身失败也可能被判为未知，因为 Host 不能确定远端是否已经收到。

这里的连接阶段还不能直接代替 Host 重启时的判断。重启后 broker 的内存阶段已经丢失；恢复器只能按未结算 operation 的持久记录保守结算。连接测试与存储恢复测试分别检查这两种输入条件。

因此，“Host 继续存在”不意味着所有 Client 提供的外部能力都获得 exactly-once。

从断言到有边界的结论

因此可以说：这两个测试验证了指定连接时点的错误分类，以及给定存储输入上的恢复结算、范围和顺序重复调用行为。不能说：已验证真实外部效果是否发生、磁盘掉电恢复、并发恢复、多 Client 产品全流程或任意 adapter 的 exactly-once。尤其 :memory: Store 的断言不能独自证明跨进程持久性。

改变一个条件后，哪些结论需要改变？

  1. 如果 Client 已回 accepted，但 Host 尚未发 admitted 就失联，能否套用测试第二行的未知结果？不能直接套用；连接仍由存活 broker 处理时，accepted 分支按源码是 capability_lost。上面的两项测试没有单独触发这个中间窗口。
  2. 如果 Host 已退出，存储只有目标的 T1、没有 outcome，能否凭自己记得“也许还没 admitted”自动重做？不能。恢复器按持久输入结算未知，不能恢复已经丢失的内存阶段。
  3. 第二次恢复返回 0，是否证明外部操作只发生一次？不证明。它只表明该存储场景下没有再次创建结算；外部效果的次数没有被此测试观察。
  4. 若把恢复目标改成 session-2，预期哪个 operation 被结算？other-session-operation；这是根据相同选择规则的纸面推导，本节没有运行该变体。

Sequence 与 epoch 怎样修复增量缺口

sequence 属于某个 subscription，不是 RuntimeEvent 的全局编号。下面两种状态必须分开：

同一逻辑连接、同一订阅 U1 仍存活：
  U1 最后接受 41 → 继续期待 U1 的 42
  受支持的 Peer 换路可以保留这条上层连接与订阅

逻辑连接已关闭，重新握手并新开 U2：
  subscription.open → 新 subscriptionId + 当前 snapshot + nextSequence=1
  从 U2 的 1 开始；不把 U1 的 42 当作续点

新订阅的 Client 以返回值建立游标；hostEpoch 相同也不能替代 subscriptionId 匹配。遇到 gap、错误 subscription 或旧 epoch，应拒绝把不匹配帧接到现有视图，再按连接/订阅恢复合同重建基线。Snapshot 可以恢复当前投影，不表示它逐帧补回每个历史增量，更不会自动恢复工具进程。详见状态演算。

Terminal 与 Settled

Terminal state 回答“这次 Run 最终是完成、失败还是取消”。Settled 回答“相关 iterator、后台清理和资源释放是否全部结束”。

终态同时支持结果展示与后续清理；展示不是清理的前置条件，资源真正释放后才达到 settled。

产品可以快速发布 terminal，但关闭 Host、复用资源或判断进程完全退出时，可能仍需等待 settled；后续工作能否接纳也须服从对应 gate，不能仅凭界面完成就跳过。把两个信号合并，会让 UI 响应性和资源正确性相互冲突。

多入口与顶层执行准入

Host 的 root admission gate/reservation 防止多个入口同时为同一 Session 创建冲突的顶层工作。Runtime 内允许的并发 Run 模型和 Host 对 root execution 的准入约束是两个层次，不能用一句“Session 是否允许并发”概括。

共享 Session 与 Peer Mesh 的边界

Shared Session

共享 Session 需要明确的 guest/grant/approval/revoke 状态。Guest 可以提出受限请求，但 Session owner 的 authority 不会因为 transcript 可见就自动转移。

还要单独考虑披露：thinking、tool result、请求组成与调用诊断、Memory 和 attachment 是否应向 guest 展示，不能只用“共享了会话”一项开关概括。当前 shared transcript 保留 thinking 文本与 tool_result.content，但消息整体仍经过字段投影。

凭据的有效条件是另一项限制。guest credential 在 finalize 后转为 active，当前实现会移除它的到期时间，认证时也不再按时间判它失效。该 credential 仍可被撤销或替换，guest 访问具体 Session 也仍受 Session grant 等条件限制。因此“只读共享”只限制 guest 能否修改，并不等于已经做到最小信息披露或短期凭证治理。

Peer Mesh

Peer Mesh 解决节点发现、路由和成员关系，不等于 Session grant。某个 peer 能被找到或能转发消息，不能证明它有权读取 S1 或创建 R7。

官方将 direct-peer transport 标为 experimental。不能从接口存在推导它在各种 WAN、NAT、relay 或密钥轮换条件下都可靠。

机制问题解析

问题 1。 sequence 出现 gap 时，为什么重读 snapshot？

解释。 本地投影缺少连续前缀，不能可靠应用后续增量；应从权威快照重建，再接收匹配更新。

问题 2。 一个 command 响应丢失时，需要核对什么才能判断是否可重试？

解释。 命令的幂等契约、exact identity 与 payload，以及已持久化的 receipt/admission 等事实。

问题 3。 terminal 已发布、settled 尚未到达，用户与 Host 分别可以依据它做什么？

解释。 可以展示语义终态；资源清理与后续准入仍需服从相应 settled/gate，不因显示完成而跳过。

问题 4。 Peer 已认证、guest 能读 transcript，是否就获得 Session 的全部 authority？

解释。 不会。节点连通、credential 与 Session grant 是不同边界；共享还要单独核对披露字段和撤销条件。

改变条件：失联发生在哪一层

以下改变 H/W/V/E 的一项状态，其余条件沿用前面的推演。

问题 1。 U1 已接受 41。先假设仅 Peer 路径从 generation 6 换到 7、原逻辑流仍存活；再假设 C1 真正关闭，C2 打开 U2。两种情况下 V 的订阅与 nextSequence 分别是什么？为什么相同 hostEpoch 不足以共用 42？

解释。 有限恢复成功且原逻辑流仍在时，V 可保持 C1/U1，期待 42；真正重开后是 C2/U2，以 open 响应的 nextSequence=1 与 snapshot 建立新基线。epoch 识别宿主代际，subscriptionId 区分观察流，sequence 只在该流内解释；三个量职责不同。

问题 2。 同一时刻测试仍由 Host 运行，但另一个动作是 Client 提供的浏览器点击。Client 分别在仅 accepted、已准入但未回结果时失联，能否把两种点击都换到新 Client 重做？

解释。 不能统一重做。普通 Host 测试仍查原 W 的运行与结算；点击仅 accepted 时，在协议被遵守的前提下尚未获准产生效果，连接丢失可判 capability_lost。执行准入已发而结果缺席时可能已点击，应保留未知、查外部状态或由专用恢复合同处理。新 Client 连通不提供旧效果未发生的证据。

问题 3。 R7 已有 terminal，但资源尚未 settled；旧 Host 要退出，新机器已有项目 worktree。还缺哪些条件，才能说执行权和工作已安全交接？若 Host 仍持 Root writer，外部编辑器是否仍能改变 README？

解释。 本题 R7 已有 terminal，它不会因换 Host 再续跑；此时交接的是控制责任，不能跳过剩余资源的收束与 writer 释放。新 owner 还需有效并完成就绪检查，核对项目文件、Client/OS 进程及外部效果的所在位置和状态。只有另有未完成工作需要继续时，才进一步核对那份工作的持久接续点与准入条件。worktree 只提供一份代码工作副本，不搬进程或内存，不证明远端操作可回滚；任意崩溃不能冒充合作 handoff。Root writer 约束运行状态库，不锁住全部项目内容，外部编辑器仍可改 README，旧 Read 只是原时刻观察。
