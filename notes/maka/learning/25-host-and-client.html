第二部分：Maka 核心机制与任务接续 · 25 / 62

第 25 章｜宿主（Host）、客户端（Client）与连接连续性（Connection Continuity）

本章概览

核心问题：界面失联以后，怎样知道工作是否仍在执行，怎样恢复观察而不重复修改？

关键概念：宿主（Host）接纳工作并维持运行控制；客户端（Client）提交意图和显示结果；快照（Snapshot）提供当前状态基线；订阅游标（Subscription Cursor）指出某条更新流的位置；效果未知（Outcome Unknown）表示操作可能发生、结果尚未确认。

关系主线：先分清失去的是观察路径、实际执行器（Executor）还是控制责任，再恢复对应状态（State）。终态（Terminal State）说明执行如何结束，资源结算（Settlement）则说明清理是否完成。

前情回顾：同一份工作，有哪些不同身份（Identity）？

第13章区分了会话（Session）、工作轮次（Turn）与执行（Run）：前者组织长期工作，第二个对应一次被接纳的任务，第三个承载实际推进。界面换了，这三种身份（Identity）不必跟着变。第14章进一步区分运行时事件（Runtime Event）与投影（Projection）：持久记录保存发生了什么，界面只是其中一种表示，丢失画面不等于丢失工作。

第18章的两个持久边界解释了另一种缺口：T1 标出操作可能开始，T2 保存结果。只有 T1、没有 T2 时，外部世界可能已经改变。连接恢复可以让我们重新读取记录，却不能凭空确认缺失回执对应的效果（Effect）。

本章沿用第12章的文档任务分支：函数已经正确，只需检查配置、把 README 的测试入口修正，再运行测试；不把第04章的函数缺陷重新带进来。记会话（Session）为 S1、工作轮次（Turn）为 T7、执行（Run）为 R7。下面的关窗、换路和升级时点是教学推演，不是实际捕获的桌面到命令行运行记录。

1. 测试正在运行，关闭窗口会发生什么？

先固定宿主（Host）与执行器（Executor）的位置

假设桌面客户端（Desktop Client）已经提交任务，R7 依次完成了下面的步骤：

表 1 / Table 1 · 先固定宿主（Host）与执行器（Executor）的位置
模型步骤（Model Step）已提出的工具调用（Tool Call）本题当前状态
1并行 Read(package.json) 与 Read(README.md)已取得配置与文档
2Edit(README.md)修改结果已返回

此时关闭窗口，稍后从命令行界面（Command-Line Interface，CLI）打开同一个目标。先给出结论：如果宿主（Host）仍存活，且普通测试工具由它和运行时（Runtime）执行，客户端（Client）断线本身不会取消已经准入的 R7。 原工作仍可能成功、失败、超时或被显式取消；要看它自己的记录。

这个条件很具体。合上笔记本可能让操作系统睡眠，暂停本机进程；浏览器操作也可能实际依赖已关闭的界面。两种情况都改变了执行器（Executor）的可用性，不能从“窗口和任务分开”推导机器休眠时仍能向前执行。

命令行界面（CLI）正确的下一步是确认同一宿主（Host）和会话（Session），读取当前快照（Snapshot），再接收后续更新。相同项目名或标题不够；重发“检查配置、更新 README”也不能用来补画面，因为那可能建立第二份修改任务。

三种状态（State）分别由谁解释

运行时宿主（Runtime Host）管理工作准入、连接与订阅（Subscription）；运行时（Runtime）推进模型与工具；存储层保存持久事实。客户端（Client）通过用户界面（User Interface，UI）提出请求与显示结果。这是控制面（Control Plane）和执行面（Execution Plane）的分工，不是两套互相竞争的智能代理（Agent）。

这里的“权威”限定在运行记录，不能代替对外部文件或服务的实际核对。把代理循环（Agent Loop）直接放在界面进程、只在其内存保存历史的简单实现，容易同时失去执行和显示；两个窗口还可能各跑一份。拆开这三种状态（State），才有可能重建显示而不重复效果（Effect）。

查询（Query）与命令重放（Command Replay）为何不同

查询（Query）读取状态，例如取得 S1 的快照（Snapshot）；命令（Command）改变状态，例如开始工作、批准权限或请求停止。响应丢失后，前者通常较容易重试，后者必须先回答“原请求是否已经被接受”。

连接里的 requestId 用于匹配响应，不自动成为业务幂等键（Idempotency Key）。安全的命令重放（Command Replay）需要原身份（Identity）、原内容和授权匹配，以及对应的去重（Deduplication）或准入（Admission）规则。新建一个标识、填入相同文字，不等于原请求重放。

问题。 命令行界面（CLI）没看见启动回执（Receipt），是否应该再提交一次 T7？

参考答案。 先查询原工作。回执（Receipt）丢失时，宿主（Host）可能已经接纳任务；重建观察只需快照（Snapshot）和订阅（Subscription）。只有查清原身份（Identity）、内容及幂等（Idempotency）约定，才能判断能否重发修改类命令（Command）。

2. 请求返回以后，谁继续消费运行时事件（Runtime Event）？

状态根（State Root）约束哪一份写权

在 turn.start 之前，宿主（Host）必须取得状态根（State Root）的单写者（Single Writer）约束。tryAcquireInteractiveRootOwner 经状态根（State Root）的控制机制获取写锁与租约（Lease），启动内核再核对该负责者（Owner），完成组成、恢复和监听准备。

这份身份（Identity）与会话（Session）的 workspaceRoot/cwd 分开：前者回答“谁能修改运行记录”，后者回答“在哪份项目文件上工作”。持有运行记录的写锁不锁住整个项目，外部编辑器仍可改变 README；它也不会接管客户端（Client）的浏览器或远端服务。旧的 Read 只是原时刻的观察结果（Observation）。

沿着 turn.start 找到持续消费者（Consumer）

理解生命周期（Lifecycle），不必先记住所有类名。只追踪四次交接：谁接受请求，谁启动工作，谁持续读取事件，谁回答原请求。

  1. 连接认证后，具体操作仍要授权。 RuntimeHostConnectionSession.#handleRequest 核对操作授权（Operation Grant）与边界，再分派 turn.start。通信对端（Peer）能连上，不等于能读 S1 或启动 T7。
  2. 顶层工作先持久准入（Admission）。 协调器（Coordinator）规范化输入并取得预留（Reservation），核对已有准入（Admission）。重复 T7 必须匹配原执行描述、内容与授权。startRootMessageTurn 将已分配的身份（Identity）和 durability: 'required' 交给 SessionManager.sendMessage。
  3. 宿主（Host）留下持续消费者（Consumer）。 prepareAdmittedTurn 取得驻留持有（Residency），避免在途资源被提前回收，并登记 ActiveRootTurn。entry.done 承接 drainTurn，持续读取运行时事件（Runtime Event），送入连续性发布链并完成终结清理。这里的 drain 指“读完事件流”，不同于停止接纳新工作的停机收束（Drain）。
  4. 启动回执（Receipt）走另一条等待路径。 resolveStartDisposition 等启动结果并读取权威快照（Canonical Snapshot），回答原请求；长期消费者（Consumer）继续处理其后的事件。前者返回或原连接失效，不会自动撤销后者的工作。

这条链在 Maka 顶层工作协调器（Root Turn Coordinator）的 prepareAdmittedTurn、startRootMessageTurn 和 drainTurn 中相接。解释的关键是持有者与消费者（Consumer）在哪里，而不是函数名称中有没有“后台”二字。

顶层准入（Root Admission）还防止多个入口为同一会话（Session）建立冲突工作。它与运行时（Runtime）内部允许的并发执行（Concurrent Run）模型属于不同层次；不能用一句“会话能否并发”概括两个约束。

3. 同一个失联提示，对应三种恢复（Recovery）

用四组坐标分清控制、工作、观察与效果（Effect）

以下是教学元组，不是产品新增的数据结构。字母只用于在改变条件时指出哪一部分发生变化：

H=(state root, valid writer, host epoch),W=(session, turn, run, phase),V=(connection ID, subscription ID, next sequence),E=(executor, resource location, known outcome).\begin{aligned} H &= (\text{state root},\ \text{valid writer},\ \text{host epoch}),\\ W &= (\text{session},\ \text{turn},\ \text{run},\ \text{phase}),\\ V &= (\text{connection ID},\ \text{subscription ID},\ \text{next sequence}),\\ E &= (\text{executor},\ \text{resource location},\ \text{known outcome}). \end{aligned}HWVE​=(state root, valid writer, host epoch),=(session, turn, run, phase),=(connection ID, subscription ID, next sequence),=(executor, resource location, known outcome).​

HHH 表示状态根（State Root）、有效写者（Writer）与宿主代际（Host Epoch）；WWW 表示会话（Session）、工作轮次（Turn）、执行（Run）及阶段；VVV 表示连接身份（Connection ID）、订阅身份（Subscription ID）和下一序号（Next Sequence）；EEE 表示执行器（Executor）、资源位置与已知结果。

这张图的箭头恢复连接、控制条件和观察，没有一条代表再次执行工具。A/B 以原宿主（Host）仍存活为前提；C 必须先重建有效控制责任。

A：物理路径（Transport Path）变化，原逻辑流仍在

受支持的对端（Peer）换路机制可以把原逻辑字节流接到新路径。ResumablePeerStream.reserve/attach 重新核对通信身份（Identity），并用代次（Generation）拒绝迟到的旧路径。例如从 6 换到 7，旧的 6 不能稍后回来覆盖新连接。原逻辑连接 C1 和订阅（Subscription）U1 若都保留，仍期待 42。

这里依赖活动进程中的有限恢复预算；不支持恢复、超过预算或旧流已失效时，就不能沿用这个结论。换路也没有迁移 HHH 所代表的控制责任，更不会新建 T7。

还要区分两种“收到”。传输层确认（Acknowledgment，ACK）按字节偏移（Byte Offset）管理去重（Deduplication）；本实现确认的是上层 read 已取走的字节。它不证明 JavaScript 对象表示法（JavaScript Object Notation，JSON）消息已经处理，也不证明 T7 已准入或 README 已修改。可恢复对端流（Resumable Peer Stream）源码将字节消费位置与后续业务处理分开保存。

B：逻辑连接（Logical Connection）关闭，新建观察基线

如果 C1 真正关闭，但宿主（Host）仍存活，新的 C2 要打开新订阅（Subscription）U2。subscription.open 返回当前快照（Snapshot）、新 subscriptionId 和 nextSequence=1。这次应从 U2 的 1 开始，不能把 U1 的 42 搬过来。

服务端先让打开响应经连接写出，再激活增量发布；源码中的 receipt.flushed 是连接写出完成，不是数据库持久提交。这保证客户端（Client）有机会先建立基线，再解释新流中的更新。

客户端订阅接收器（Client Session Subscription）先核对身份（Identity），再按消息类别处理。上表的连续序号（Sequence）规则针对普通状态更新；伪终端（Pseudo-Terminal，PTY）数据有专用处理分支，不能把该规则说成所有帧共用一套业务编号。

若普通更新出现缺口，后续增量就不再有完整前缀。应重新取得匹配快照（Snapshot）和观察基线，不能用重新执行任务来补齐。快照（Snapshot）恢复当前投影（Projection），不保证逐帧补回所有旧通知，也不恢复工具进程。

握手中的协议版本（Protocol Version）和兼容代际（Compatibility Epoch）另用于判断双方是否能通信；它们既不替代 hostEpoch，也不替代订阅游标（Subscription Cursor）。这些校验能拒绝不匹配更新，不能据此承诺所有界面错误都自动恢复。

C：宿主（Host）退出，先恢复有效控制责任

宿主（Host）退出后，原对端流（Peer Stream）的内存状态可能已经消失。新入口不能凭旧画面继续写运行记录。先核对旧写者（Writer）的收束、新负责者（Owner）的有效性与持久事实，再建立就绪连接和观察基线。

如果是协作交接（Cooperative Handoff），系统可以在规定边界封存旧物理执行（Physical Invocation），让后继继续同一逻辑工作轮次（Turn）；如果是意外崩溃，必须按已有事实与恢复合同处理。两者不是同一个入口。项目文件、客户端（Client）的浏览器和远端效果（Effect）是否还在，仍是 EEE 的问题，不会随着 HHH 的移交自动解决。

问题。 U1 已接受 41，换路与重连为何不能统一写成“继续从 42 开始”？

参考答案。 换路成功且原逻辑流仍在时，可以保留 C1/U1 并期待 42。真正重开后是 C2/U2，以返回的 nextSequence=1 与快照（Snapshot）建立新基线。相同宿主代际（Host Epoch）只说明控制端代际相同，不说明订阅（Subscription）相同。

4. 客户端能力（Client Capability）丢失，效果（Effect）可能已经发生

接受准备（Accepted）与执行准入（Admitted）之间有一道门

把普通测试换成桌面客户端（Desktop Client）提供的浏览器点击，EEE 就变了。宿主（Host）仍能控制工作记录，却可能失去真正产生效果（Effect）的执行器（Executor）。不能直接把相同点击交给新客户端（Client）重做。

存活的客户端能力中介（Client Capability Broker）在 releaseConnection 中用阶段分类连接丢失。下面只摘它选择错误对象的一段，外围仍负责找到该连接的调用、结束交互（Interaction）或结算结果：

// 教学注释：前两阶段尚未获得执行准入（Admitted）。
const error =
  invocation.phase === 'dispatched' || invocation.phase === 'accepted'
    ? new ClientCapabilityInvocationError(
        'capability_lost',
        'Client Capability provider disconnected before admission',
      )
    : new ToolOutcomeUnknownError(
        'Client Capability provider disconnected after accepting the call',
      );

capability_lost 表示在该分支尚未获得执行准入（Admitted）的能力丢失；后一个错误保留效果未知（Outcome Unknown）。这里应读判别条件，不能只读第二条英文错误文字中的 accepting，就把它误当成协议的 accepted 阶段。

准入消息发送结果也可能不确定：发送已经尝试但失败，宿主（Host）未必知道远端是否收到，所以源码保守使用 ToolOutcomeUnknownError。另有明确找不到发送端、尚未发送的分支仍返回 capability_lost；不能把所有发送前失败都概括成未知。

这套区分依赖客户端（Client）遵守“获准以后才产生效果（Effect）”的协议。它不是宿主（Host）能监视一切外部进程的证明，也不自动提供恰好一次（Exactly-once）效果（Effect）。

两项测试分别观察了什么

现有测试提供两个局部场景：一项控制连接断开的时点，另一项直接调用存储恢复器。它们使用受控测试场景（Fixture），不是 S1/T7/R7 的完整产品执行轨迹（Trajectory），也没有启动真实桌面或点击浏览器。

连接分类测试的 assertLossClassification 创建协调器（Coordinator）、模拟连接并注册工具；发送回调决定何时断开。辅助函数 invoke 直接调用工具的 impl，没有经过完整工具运行时（ToolRuntime）的 T1/T2。

重启以后，恢复器（Recovery Handler）只能读取持久输入

宿主（Host）重启后，中介（Broker）内存中的阶段已经丢失。恢复器（Recovery Handler）不能凭维护者记得“可能还没获准”重做操作，只能按未结算操作（Unsettled Operation）的持久输入处理。

对应测试使用真实 SQLite 运行存储（Runtime Store）的 :memory: 数据库，先用 commitToolPrepared 建立三条记录，再调用恢复函数。这里没有真实杀进程，内存数据库也不证明跨进程持久性。

问题。 若把恢复范围改为 session-2，会处理谁？若只有 T1，没有结果，能否凭猜测自动重做？

参考答案。 按同一选择规则，预期处理 other-session-operation；这是未运行变体的推导。只有 T1 时应按恢复模式（Recovery Mode）保留未知，不能恢复已丢失的内存阶段，也不能由结果缺席推断效果（Effect）未发生。

5. 终态（Terminal State）、资源结算（Settlement）与宿主交接（Host Handoff）

显示完成以后，哪些资源还没有释放？

终态（Terminal State）回答“这次执行（Run）如何结束”；资源结算（Settlement）回答“迭代器（Iterator）、后台清理和资源释放是否全部结束”，代码状态 settled 保留其原名。

展示与清理从同一终态事实（Terminal Fact）分叉；展示不是清理的前置条件。界面可以及时显示结果，关闭宿主（Host）或复用资源仍须等待对应资源结算（Settlement）与准入门（Admission Gate）。将两者合并，要么拖慢显示，要么把尚在清理的资源误当已经可用。

协作交接（Cooperative Handoff）结束的是哪个边界？

先改变条件：假设 R7 仍未终结，但一次 Edit 的结果已经入账，此时需要升级宿主（Host）。协作交接（Cooperative Handoff）请求下一个可证明的持久边界；抵达并提交之前取消，原工作继续。满足条件后，系统封存（Seal）旧物理执行（Physical Invocation），核对驻留持有（Residency）、在途命令（Command）与连接，再解除绑定（Detach）。后继可以按持久接续合同继续同一个逻辑工作轮次（Turn）。

这里没有恢复旧 JavaScript 调用栈，也没有重新执行已确认的 Edit。旧物理执行（Physical Invocation）结束，不意味着用户任务完成；一旦交接进入提交边界，旧取消信号也不能重新放行它。

Maka 宿主内核（Host Kernel）中的 #prepareCooperativeHandoff 与 #closeResources 分别核对交接条件、完成资源收束并释放负责者（Owner）。新端仍须取得有效写权并完成就绪检查；安装命令返回不能替代这些条件。

可携带导出（Portable Export）为何先复制，再检查静止？

再换一种需求：把 S1 导出成包。若先检查它空闲，再复制数据库，复制期间其他客户端（Client）可能开始新工作；“检查过的状态”与“交付的状态”就不是同一份。

当前会话导出（Session Export）先取得一致数据库副本，再在将交付的副本中检查静止条件（Quiescence），筛选会话（Session）子树、所需资源与引用，并核对外键。运行时（Runtime）入口要求静止；已有目标不覆盖，活动工作、缺失资源、越界引用、不支持的结构或限额失败会使导出失败。存储导出策略（Session Bundle Policy）的 exportSessionBundleState 与 filterBackedUpDatabase 明确了这个顺序。

包里不包含用户项目目录、凭据（Credential）或旧浏览器进程。它是有范围的状态出口，不自动证明另一台机器已完成导入、写权接管或计算现场恢复。

问题。 R7 已有终态（Terminal State），资源却尚未结算；新机器已有项目工作副本，能否立即“恢复 R7”并重发 Edit？

参考答案。 不能重新开放已终结的 R7。此时要交接的是控制责任，并完成剩余清理、旧写权释放与新端就绪。项目工作副本不搬运进程或内存；只有另有未完成工作时，才进一步核对它的持久接续点。看到 handoff_pause 或导出包，也不能直接宣布任务完成或允许重做旧效果（Effect）。

6. 连通、授权与共享披露是三道不同边界

共享会话（Shared Session）让谁看见什么？

访客（Guest）读取会话（Session），仍受授权（Grant）、批准（Approval）与撤销（Revoke）状态约束。能看见对话记录（Transcript），不代表负责者（Owner）的裁决权（Authority）转移给了访客（Guest）。

只读权限与披露范围也不同。共享投影（Shared Projection）会筛选消息字段，但当前保留思考文本（Thinking Text）及其文本分段，以及 tool_result.content；不能说保留了完整工具结果（Tool Result）记录的每个字段，也不能说所有敏感内容已最小化。共享对话投影（Shared Session Transcript）具体决定哪些字段进入视图。请求组成诊断（Prompt Composition）、记忆（Memory）和附件（Attachment）的可见性也需分别判断。

凭据（Credential）的时效是另一层。待激活凭据（Pending Credential）有到期时间；finalize 后变为有效凭据（Active Credential），当前实现移除到期字段，认证时不再按时间判它失效。它仍能撤销或替换，具体会话（Session）授权（Grant）也仍须满足。因此这不是永久访问权，也不能由“只读分享”推导短期凭据（Credential）治理已经完成。

对等网络（Peer Mesh）与业务唤醒分别解决什么？

对等网络（Peer Mesh）解决节点发现、路由和成员关系，不等于会话（Session）授权（Grant）。能找到或转发到某个对端（Peer），不能证明它有权读取 S1 或创建 R7。官方把直接对端传输（Direct-peer Transport）标为实验性（Experimental）；接口存在不能替代真实广域网络（Wide Area Network，WAN）、网络地址转换（Network Address Translation，NAT）、中继（Relay）或密钥轮换（Key Rotation）条件的检验。

运行时宿主（Runtime Host）还承接计划（Plan）、目标（Goal）、调度（Schedule）和代理图（Agent Graph）的业务协调。代理图（Agent Graph）的监督唤醒（Supervisor Wake）仍经顶层准入（Root Admission），创建新的普通工作轮次（Turn）与执行（Run），不会把旧 R7 重新打开。私有信箱（Mailbox）负责智能代理（Agent）之间的通信与调度；本章的连接连续性（Connection Continuity）负责重新观察同一份工作。两者可共存，但唤醒新工作与恢复显示需要不同证据。

7. 直接问答：改变一个条件，再判断恢复（Recovery）

问题 1。 宿主（Host）仍在测试；同一客户端（Client）的浏览器点击分别在 accepted 和执行准入（Admitted）后失联，能否统一换端重做？

参考答案。 普通测试仍查询原 R7。对点击，存活中介（Broker）在 accepted 阶段按源码归为 capability_lost，前提是对端遵守准入（Admission）协议；执行准入（Admitted）已发、结果缺席时可能已点击，应保留效果未知（Outcome Unknown），检查外部状态或按专用恢复合同处理。新端连通不证明旧效果（Effect）未发生。

问题 2。 新路由看到 S1/T7/R7，还看到上下文检查点（Context Checkpoint），能否说原浏览器已迁移且 R7 自动继续？

参考答案。 不能。路由支持连接判断，检查点（Checkpoint）服务模型历史；浏览器是否仍在属于资源位置问题。继续工作还需要有效裁决权（Authority）、已有结果和接续（Continuation）条件。

问题 3。 界面已显示完成，但资源结算（Settlement）尚未结束，能否直接释放状态根（State Root）的写者（Writer）？

参考答案。 不能用显示替代停机合同。语义终态（Terminal State）可以展示，资源清理、驻留持有（Residency）和后续准入（Admission）仍各有条件；旧端收束、新端取得有效写权和就绪必须分别成立。

问题 4。 恢复器（Recovery Handler）第二次返回 0，是否证明外部效果（Effect）只发生一次？

参考答案。 0 只说明该存储场景没有重复创建结算，未观察外部效果（Effect）次数。记录的顺序幂等性（Idempotency）与外部操作的次数是不同问题。

问题 5。 访客（Guest）能看见结果，凭据（Credential）又没有到期字段，是否已经取得永久的全部权限？

参考答案。 不能。可见性只说明共享披露，访问仍受会话（Session）授权（Grant）、凭据（Credential）撤销或替换约束，负责者（Owner）的裁决权（Authority）也没有转移。
