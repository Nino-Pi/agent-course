第 31 章｜工具合同（Tool Contract）、执行（Execution）与恢复（Recovery）

本章概览

核心问题：一个工具（Tool）怎样把模型（Model）参数（Argument）可靠地连接到受控执行，并让失败后仍能判断下一步？

关键概念：声明合同（Declaration Contract）：名称、参数（Argument）与用途；执行合同（Execution Contract）：身份（Identity）、许可和资源前提；结果合同（Result Contract）：效果（Effect）及失败的表达；条件编辑（Conditional Edit）：满足资源前提才写入；未知效果（Unknown Effect）：缺回执但可能已生效；数据流策略（Data-Flow Policy）：规定哪些内容可传给谁。

关系主线：工具（Tool）从发现和绑定（Binding）走到最终输入（Input）检查，再执行、保存并按预算（Budget）返回结果；事后反馈（Feedback）、取消（Cancellation）与重试（Retry）依据效果（Effect）状态（State），工具（Tool）切换和参数（Argument）来源都不能扩大业务授权（Authorization）。

前情回顾：把决定、执行与证据接起来

第28章把一项修复分成模型（Model）提出请求、执行层（Execution Layer）检查当前条件、资源发生变化、结果进入后续判断。第16章说明普通编辑工具（Edit）怎样匹配文本；第17章把批准（Approval）与实际资源限制分开；第18章说明效果（Effect）发生和结果记账之间可能中断。它们在本章汇成同一个问题：工具（Tool）应交给模型（Model）哪些决定，又必须由可信程序保留哪些决定？

本章先沿用README修复：文档误写npm run check，配置中的真实入口（Entry Point）是npm test；只修改允许的目标片段，保留用户其他说明。后文用v7/v8标记资源版本，是条件编辑（Conditional Edit）的教学接口，不声称普通Maka Edit接受版本参数（Argument）。先完成前三节的输入（Input）与结果定义，再看正常、陈旧、未知三条路径；实际产品只用来检验这些责任是否接到了消费者（Consumer）。更完整的文件案例见第50章和第51章。

1. 从使用者的决策推导参数（Argument）

以编辑 README 为例。模型（Model）真正需要决定的是“在哪份资源上，把先前读到的哪段内容变成什么”。工作区根目录、权限（Permission）对象、凭证、操作身份（Identity）由可信运行时（Runtime）提供，不应让模型（Model）通过参数（Argument）任意指定。

先分清两个生产者（Producer）：模型（Model）提供编辑意图，可信运行支撑（Agent Harness）提供工作范围（Work Scope）、当前授权（Authorization）和调用身份（Call Identity）。资源版本可以由模型（Model）原样传回，但执行层（Execution Layer）仍要核对它与目标的关联及当前值，不能把模型（Model）写出的版本号当作可信事实。工具（Tool）描述应使模型（Model）知道什么时候适合调用，执行合同（Execution Contract）则使不合条件的请求真正无法提交。

下面将这份教学声明写完整。每个失败结果都给后续消费者（Consumer）一个可采取的方向，避免把重新读取、缩小匹配和查询效果（Effect）混成同一种重试（Retry）：

这是一份教学描述。真实参数模式（Schema）还要给出大小上限、编码和空串语义。例如空旧文本到底表示插入，还是参数（Argument）非法，不能交给执行器临时猜。模型（Model）能生成符合JavaScript对象表示法（JavaScript Object Notation，JSON）语法的文本，只证明请求满足一层格式约束。

2. 三层合同共同决定行为

三层合同分别交给不同的消费者（Consumer），因而不能用其中一层的成功替代另外两层：

表 2 / Table 2 · 2. 三层合同共同决定行为
合同谁主要消费本例必须回答什么
声明合同（Declaration Contract）选择工具（Tool）的模型（Model）目标片段怎样表达，什么时候该先回读
执行合同（Execution Contract）可信执行层（Execution Layer）与资源负责者（Owner）当前许可、版本和匹配条件是否仍成立
结果合同（Result Contract）下一步决策、记录与验收（Acceptance）文件是否已改、知道多少、缺哪项验证

例如JavaScript对象表示法（JSON）能解析但版本陈旧，声明层的格式合法并不能让执行层（Execution Layer）写入；写入返回成功但测试没跑，结果可以证明一次操作完成，却还没有完成任务验收（Task Acceptance）。

图中声明层约定如何表达，运行时（Runtime）决定本次是否允许，资源层（Resource Layer）决定效果（Effect）如何提交。“可信上下文（Context）→检查”必须独立于模型（Model）参数（Argument）；“结果→保存→观察结果（Observation）”说明完整结果与本次输入（Input）可以采用不同表示。

这张图是自拟设计分层。Maka 的实际接线与外部工具（Tool）通道有自己的约束；不要假定一套包装器能对任意远端服务提供相同保证。

3. 结果类型比一个成功（Success）布尔值更重要

先按输入（Input）、结果、可信执行上下文（Execution Context）三块读下面的类型。输入（Input）表达意图；结果用kind区分下一步；执行上下文（Execution Context）由运行支撑（Agent Harness）注入，不是模型（Model）还能随意补填的参数（Argument）。以下类型用于讨论行为，没有实现存储、事务（Transaction）或沙箱（Sandbox）。observedVersion 是先前读取时的资源版本；TrustedWorkspace 与 CurrentAuthority 表示可信运行时（Runtime）提供的工作范围（Work Scope）和当前授权（Authorization），signal 是取消（Cancellation）信号。operationId 关联同一逻辑操作，attemptId 区分其执行尝试（Execution Attempt）；重试（Retry）关系在下一节展开：

先看由模型（Model）提供的编辑输入（Input）：

// 表达编辑意图；执行层仍须核对版本。
type EditInput = {
  target: string;
  observedVersion: string;
  oldText: string;
  newText: string;
};

再看结果的判别联合（Discriminated Union）。每个分支明确需要补读、缩小匹配还是查询效果（Effect）：

// kind 是判别字段，后续操作按该分支读取所需字段。
type EditResult =
  | { kind: "applied"; newVersion: string; changedRanges: string[] }
  | { kind: "stale"; rereadTarget: string }
  | { kind: "no_match"; rereadTarget: string }
  | { kind: "ambiguous"; matches: number }
  | { kind: "rejected"; reason: string }
  | { kind: "failed_before_effect"; reason: string }
  | { kind: "effect_unknown"; operationId: string; queryHint?: string };

最后是可信执行上下文（Execution Context）。它和模型输入（Model Input）有不同来源：

// 可信程序注入身份与能力，模型不能自行授权。
type ExecutionContext = {
  workspace: TrustedWorkspace;
  authority: CurrentAuthority;
  operationId: string;
  attemptId: string;
  signal: AbortSignal;
};

kind构成判别联合（Discriminated Union）：消费结果时先判断是哪一类，再读取该类存在的字段。陈旧、零匹配和歧义说明本次条件编辑（Conditional Edit）未按意图提交；applied保存新版本；effect_unknown保留操作身份（Identity）供查询。这里的TrustedWorkspace与CurrentAuthority是留给真实实现定义的可信类型占位，名字本身不实现权限（Permission）检查。

effect_unknown 不能被格式化器改成普通失败。超时可能发生在执行前，也可能发生在对方提交后、响应返回前；取消（Cancellation）信号到达同样不证明效果（Effect）不存在。

applied 也不是完整任务（Task）成功。修改已经提交之后，还要检查约束、运行相关测试并判断验收（Acceptance）范围（Scope）。工具（Tool）应提供足够的信息供下一步验证，不能只返回“Done”。

如果只用 read→compare→write 三个独立文件操作，比较后仍可能发生外部写入。要提供更强条件写，需要一个能把版本检查和提交作为不可分割的原子操作（Atomic Operation）处理的负责者（Owner）；只用进程内锁时，应明确外部编辑器不受该锁约束。

未知效果（Unknown Effect）的恢复（Recovery）还取决于操作类型。设置目标状态（State）有时可以通过读取后置状态（State）确认；追加一条记录、发出一次消息（Message）等操作则可能需要服务端幂等（Idempotency）键或查询接口。读到“看起来一样”不总能证明就是本次操作完成，也可能来自别的调用。

operationId 标识一次逻辑操作，重试（Retry）同一意图时沿用；attemptId 标识一次执行尝试（Execution Attempt），每次新建。改变了目标或内容，就不能继续把它伪装成原请求的重试（Retry）。身份（Identity）本身也不提供幂等（Idempotency）保证：服务端还需要约定键的作用域（Scope）、有效期、同键不同参数（Argument）如何处理，以及重复请求返回原结果还是拒绝。键已经过期时，旧调用不能无条件重发。

落回普通 Maka Edit：三种状态（State）要同时保存

上面的 observedVersion 是有意设计的更强接口。当前普通 Maka Edit 没有这个字段，而是用 path、old_string、new_string 表达编辑；旧片段先做精确匹配，符合条件时才尝试有限的容错匹配（Tolerant Matching），具体流程见第16章。这里对照的是当前 Maka 实现；前面的带版本工具（Tool）描述仍是本章的教学合同。

普通 Maka 文件层在排队等本次写锁前采样设备号 dev 和文件对象编号 ino；二者合起来用于核对文件身份（File Identity）。随后在固定文件描述符（File Descriptor，fd）上读改写：描述符指向已经打开的对象，避免每次操作都重新按路径寻找目标。它能检测部分对象替换，却不保证模型（Model）上次 Read 之后内容未变。这个采样在运行时（Runtime） T1 之后，不能因代码称其为 T0 就挪到持久准入之前。带版本的教学接口与普通 Edit 的实际能力因此要分开判断。

固定“把 README 的 npm run check 改为 npm test”，在普通宿主（Host）运行时（Runtime）、受管理（Managed）的文件工作进程（Worker）路径推演。工具（Tool）绑定（Binding）与步骤（Step）可见性解决“这次调用如何解释”，T1 与当前执行边界（Live Execution Boundary）解决“哪次尝试在什么许可下开始”，工作进程（Worker）与文件描述符负责实际写入，T2 保存给模型（Model）的结果。相同输入（Input）若在写完后丢失回包，结果会变成已记录的未知；第18章同例已展开每个中间状态（State）。这里把判断写成教学上的三个坐标：

O=(R,E,A).O=(R,E,A).O=(R,E,A).

RRR表示执行记录（Execution Record）的结算状态（State），EEE表示对现实效果（Effect）的已知程度，AAA表示任务验收（Task Acceptance）状态（State）。这是同一现场的三个坐标，不是三个先后阶段。例如RRR已有匹配响应（Matching Response），仍可同时有EEE未知、AAA未完成：保存了一条“结果未知”的错误响应，并没有补出丢失的文件回执。

它们可以独立变化，不能压成一个成功（Success）布尔值：

这就是把状态（State）空间拆成多个维度的用途：第二行和第三行可能面对完全相同的磁盘内容，却拥有不同执行证据；第一行和第二行也不能仅凭界面完成标签合并。若随后Read发现 README 已符合目标，它增加的是“当前文件满足谓词”的证据，不会自动证明这必然由原操作造成，更不能替系统重写原操作记录的结论。文件还可能被人或另一个调用修改。

同题换成 Codex 的多文件 apply_patch，已知变化通过已知变更（Delta）与精确性（Exactness）标志exact传给差异跟踪器（Diff Tracker）；写入不精确时聚合差异（Diff）会失效，失败界面也可对应部分文件已改。这个真实替代没有因此获得 Maka基于SQLite的提交协议。沿 第32章部分效果（Partial Effect）比较输出和消费者（Consumer），别仅比较两家都有“日志（Log）”。

采用条件。 模型（Model）老是选错操作，应改描述、参数（Argument）和反馈（Feedback）；目标被换掉，应完善对象身份（Identity）与实际执行边界（Execution Boundary）；同对象内容被并发（Concurrency）改写，应考虑资源方支持的条件提交；回复丢失而业务可能完成，应补效果（Effect）查询/幂等（Idempotency）或明确人工核对。沙箱（Sandbox）约束可访问对象，批准（Approval）限定允许意图，二者均不填补业务回执窗口。后面的 沙箱（Sandbox）深度课会继续展开操作系统（Operating System，OS）检查与隔离（Isolation）后端。

两种条件变化的判断。 ① 同一文件对象（相同inode）中有人改了别的段落，旧文本仍唯一，能否保证 Edit 因陈旧观察结果（Observation）而拒绝？② 表示错误的T2已记录后用户按 Stop，随后独立 Read 发现目标文本已存在，是否可把原调用改成成功（Success），并宣布任务（Task）完成？

参考结论

① 不能。dev/ino 未变，旧片段仍可匹配；它不是先前内容版本。要检查和保留外部更改，完整版本保证须由负责提交的资源方实现。② 不能。Stop 不撤销已发生的写入；Read 支持当前目标状态（State），未必唯一归因于原调用，也没有完成测试等验收（Acceptance）。保留原已记录未知，用新证据说明当前状态（State），再按授权（Authorization）和剩余任务（Task）安排后续工作。

假设一次模型（Model）往返约占主要延迟，而两次独立读取成本很低，批量读取可能值得做；但把“搜索 → 猜测修复 → 提交 → 发布”塞进同一个工具（Tool），会使审批和未知效果（Unknown Effect）难以定位。减少工具（Tool）次数不是独立目标，最终应比较任务（Task）正确率、总耗时、资源成本和失败后的恢复（Recovery）能力。

6. 大工具（Tool）集：发现、可见、可执行分开

工具（Tool）从 5 个增加到 500 个时，全量参数模式（Schema）会占预算（Budget），并使相似工具（Tool）更难区分。可采用目录元信息、按问题检索候选、装载少量完整参数模式（Schema）的分层方式。检索结果必须携带稳定身份（Identity），执行仍根据可信注册表（Registry）解析。

发现不到是召回（Recall）问题；声明已装载却没有实现，是绑定（Binding）问题；实现存在但不允许调用，是权限（Permission）问题。三类错误分别影响目录、配置或用户范围（Scope），不能全返回 tool not found。

若本步声明后注册表（Registry）或权限（Permission）变化，执行器需要重新校验身份（Identity）和有效范围（Scope）。固定本步工具快照（Tool Snapshot）能帮助维持声明一致性，但不能冻结已经被撤回的权限（Permission）。本章的产品案例用于检查声明、绑定（Binding）和权限（Permission）分别由谁处理。

工具快照（Tool Snapshot）失效的具体过程。 工具（Tool）目录在 10:00 显示 search，10:01 原插件被卸载，同名工具（Tool）由另一负责者（Owner）注册，10:02 模型（Model）提交旧调用。执行器应检查哪个事实？参考答案是原绑定（Binding）的负责者（Owner）/作用域（Scope）/代际（Generation）及当前有效权限（Permission）；名称相同不能自动换到新实现。若用户同时补充“不要联网”，先前候选也不能替这次执行保留网络授权（Authorization）。这个反例检验的是绑定（Binding）和权限（Permission）是否仍有效，不需要先发生一次真实卸载事故。

7. 结果大小与进程生命周期（Process Lifecycle）也属于合同

Shell 可能输出数十万字符；Read 可能遇到一行很长的文件。返回一段有界观察结果（Observation）时，应说明截断发生在哪个范围（Scope）、完整结果如何回读、游标是否绑定（Binding）版本。没有版本约束的“继续读取第 N 页”可能把两版文件拼成一个不存在的文本。

命令启动、进程运行、退出码取得、后台子进程结束、文件状态（State）稳定，是不同的状态（State）。需要长任务（Task）时，可以返回后台作业（Job）身份（Identity）并提供查询/等待/取消（Cancellation）操作；不能把工具（Tool）函数返回误当成所有子进程都退出。

并发（Concurrency）也要经过依赖（Dependency）和资源判断：两个读取通常可以并行；基于旧文件产生的编辑必须等待相应读取；两个写入如果作用同一资源，需要冲突策略；依赖（Dependency）改动完成的测试不能提前当成修复后的验证。

在 Codex 的模型上下文协议（Model Context Protocol，MCP）通道，工具注册表（Tool Registry）查找调用处理器（Handler）并运行前置钩子（Pre Hook）。钩子（Hook）是宿主（Host）插在工具（Tool）执行前后的一段处理，pre 表示执行前；McpHandler 准备并捕获本次调用绑定（Binding）；handle_mcp_tool_call 把参数（Argument）字符串解析为JavaScript对象表示法（JSON）；批准（Approval）路径再通过 PreparedMcpCall 调用绑定（Binding）的客户端（Client）；结果处理与模型（Model）投影随后发生。把 timeout_s: 30 改成 timeout_s: "30" 仍是符合JavaScript对象表示法（JSON）语法的文本，不能从解析成功推出满足要求整数的参数模式（Schema），更不能推出当前授权（Authorization）覆盖这个目标。这条链及源文件见工具合同（Tool Contract）专题的输入（Input）演算。

工具（Tool）目录、技能说明包（Skill）方法和执行扩展（Extension）也要分开：Codex的宿主（Host）技能说明包（Skill）文件先产生元数据（Metadata）；发现阶段实际读取文件文本，但元数据（Metadata）不保存正文。选中后再读取主体形成模型（Model）片段；Pi的执行扩展（Extension）则导入并运行扩展初始化函数（Factory），向宿主（Host）注册工具（Tool）。前者已装载不保证方法中提到的工具（Tool）接口存在，后者注册失败也不自动撤销初始化函数（Factory）已产生的外部效果（Effect）。见实际技能说明包（Skill）生产消费链。

想进一步理解为何分层，可再读专题中的编译器与应用二进制接口（Application Binary Interface，ABI）、模型上下文协议（MCP）两代协议和程序化子调用。这些相邻领域帮助推导检查点；它们不把合法输入（Input）、接口互通或代码结束变成业务成功的保证。

参考结论

读取订单历史（Order History）与向商家发送订单历史（Order History）是不同权限（Permission）。网页只能提供待核对的数据，不能代表用户授权（Authorization）。应检查实际请求的数据范围（Scope）及目的，拒绝不在当前委托内的外传。

保护批准（Approval）入口（Entry Point）仍能防止工作智能代理（Agent）自行改写裁决或绕过控制；负责批准（Approval）的人员或组件的语义判断质量则需要另外评估。应分别统计错误放行、误阻断和不必要审批，不能把入口（Entry Point）隔离（Isolation）解释为任何判断都正确。购买提交后若回执丢失，继续使用本章第 4 节的 effect_unknown 与对账（Reconciliation）规则。

应用编程接口（API）提交和浏览器付款是两个最终效果（Effect）入口（Entry Point），却必须核对同一份业务批准（Approval）：账户、商品、数量、最终总价和当前委托。完整状态（State）推演见七天购买委托示例。

9. 参考结论与三类工具（Tool）的完整合同

题一：描述（Description）写“仅允许工作区文件”，是否已经实现路径限制？

没有。执行层（Execution Layer）还需处理目标解析、符号链接（Symbolic Link）、实际打开资源与工作范围（Work Scope）之间的关系。自然语言帮助模型（Model）选对工具（Tool），不能替代资源层（Resource Layer）边界。

题二：后置钩子（Post Hook）发现危险效果（Effect），返回 block 可以撤销吗？

效果（Effect）之后的钩子（Hook）可以影响结果展示、后续流程或补偿（Compensation）请求，不能自动逆转已发生效果（Effect）。要阻止效果（Effect），在效果（Effect）前检查并由执行环境（Execution Environment）落实；补偿（Compensation）本身是另一个可能失败的操作。

题三：压缩工具（Tool）输出只保留“测试失败”，为什么不够？

下一步需要知道哪条断言、预期与实际、测试是否真的启动、失败结果如何回读。摘要应服务下一步决策，同时保留定位原始结果的方式。

跨实现题：能否用一条“任意工具（Tool） → 本地沙箱（Sandbox） → PostToolUse，失败就重试（Retry）”表示两个产品？

不能。执行环境（Execution Environment）与工具（Tool）通道决定适用的隔离（Isolation），事后反馈（Feedback）不逆转效果（Effect），失败也可能来自断言或未知结果。隔离（Isolation）边界随实际通道变化，错误类别决定如何选择改参数（Argument）、修代码、查询效果（Effect）或适用的权限（Permission）流程。
