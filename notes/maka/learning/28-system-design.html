第 28 章｜Agent 系统的设计方法

本章概览

核心问题：怎样把一次代码修复的目标和新增约束，转换成必要的组件、状态与恢复规则？

关键概念：任务合同：明确目标、范围与验收；身份：关联会话、要求和执行尝试；owner（负责者）：拥有某类决定权；投影：由事实重建的视图；效果窗口：操作与结果记录之间的间隙；设计记录：写明选择、代价与失效条件。

关系主线：从任务合同确定身份和负责者，连接模型输入、工具与结果，再沿故障时间线检验哪些保证成立、哪些复杂度值得增加。

第27章把已知状态和下一步条件交给后续工作；本章继续追问，系统应怎样把目标、权限、状态与完成证据组织成明确的任务合同。相关基础见任务评价与综合设计。下面的完整示例把同一项修复依次表示为需求表、负责者图和设计记录。

1. 从修复目标到任务合同

统一案例是修复 formatDuration：输入 125 秒应该显示 2:05，当前显示 2:25；同时修正 README 的测试步骤，保留用户新增的说明，用中文汇报。

“能修改代码”只说明一种动作。要判断工作是否完成，还必须知道允许修改哪里、怎样识别正确结果、谁可能同时改文件、停止时如何处理已经发生的效果。

2. 用最小链条检查必要组件

图中间是模型与工具的反馈环，接纳位于循环之前，验收决定何时结束。执行 → 观察解释下一步凭什么改变；完成候选 → 验收解释为什么模型说“完成”还不够。

子 Agent、向量库和工作流引擎是否必要，取决于任务是否需要分工、检索或持久编排。执行边界和失败表示则直接影响这次修复能否安全完成，即使最小方案也需要明确。

从反馈决策理论看：哪些是模型的工作，哪些必须由程序完成

沿用修复任务：第一次只知道输出错误；读函数后知道余数表达式；测试后又得到边界输入。下一步应根据新观察调整。若在第一次请求中把所有动作排好再盲目执行，就无法利用第二步刚得到的证据。这是闭环决策相对于固定动作列表的价值。

ReAct 把基于已有上下文的行动，与对观察的语言推理交错起来；外部动作改变环境或取得新信息，内部推理帮助选择下一步。论文提供的是决策组织方法，不提供文件事务、进程隔离或工具幂等协议。

用下面的课程抽象把这个思想与工程模块接起来，记号不是任何框架的 API。t 表示决策步，a_t 是模型提出的动作，o_next 是执行层返回的下一份观察；~ 表示从模型输出中采样选择，Select 是输入选择，Executor 是执行层：

H_t = 已记录的观察、动作和反馈
L_t = 执行账本中已知的动作身份与效果状态
C_t = Select(H_t, 长期信息, 当前任务, 输入预算)
a_t ~ Model(C_t, 当前工具声明)
(o_next, effect_state) = Executor(a_t, 当前授权, 当前资源状态)
L_next = RecordEffect(L_t, a_t, effect_state)
H_next = Record(H_t, a_t, o_next)

L 保存可用于恢复和对账的已知效果状态，H 保存可供后续输入选择的观察；两者可以关联，不能相互替代。这份简式省略了执行前的 intent/claim 等转换，且不假定外部效果、L_next 与 H_next 原子提交。回执丢失时，账本可能只能记为 unknown，不能从缺少观察推断动作没有发生。

这里有三个不能省掉的分界。H_t 不等于世界当前状态：文件可能被别人修改；C_t 不等于全部历史：选择与压缩可能丢信息；模型提出 a_t 不等于动作被准许或成功：执行层还要检查真实资源并产生结果。这是把论文的决策视角扩展到工程问题的推导，不是论文声称已经解决这些保证。

Context 决定模型观察什么；Memory 决定哪些信息能跨任务被选用；Tools 决定动作与反馈的形式；Sandbox 限制动作能触及的资源；Runtime 记录实际发生到哪一步；编排决定下一项工作何时可开始。它们控制不同变量，不能相互替代。

看两份真实循环，理解“框架更复杂”究竟增加了什么

mini 的 DefaultAgent.step() 直接连接 query() 与 execute_actions()：模型收到 messages，Environment 执行动作，格式化后的 observation 追加回去；外层 run() 处理停止与异常，并在 finally 中保存。代码短，使反馈链容易看清；但轨迹写入不与外部文件效果组成事务。保存聊天记录与安全恢复副作用是两个问题。

Pi 是另一种开源 Code Agent。它的 runLoop 在工具反馈之外插入步骤间准备、steering（运行中补充输入）和 follow-up（当前工作将结束时取用的后续输入）；streamAssistantResponse 先按配置做可选的 transformContext，再用 convertToLlm 转成 pi-ai 的通用消息，交给具体模型适配器编码请求。Session 层的 buildContextEntries 又按当前 leaf（所选分支的末端条目）和 compaction 重建参与本轮的记录。这样扩展了输入选择与交互控制的接缝，而不是给模型增加一个神秘的持久记忆器。

具体推演：用户在一次工具运行时追加“不改 README”。模型已经发出的动作不会因此从历史中消失；Pi 在后续边界取队列并组成新输入。需要保护尚未发生的写入，还要由执行层检查当前权限。由此可以看出，输入队列解决“何时看见”，权限系统解决“此刻能否做”，两者并不重复。

mini/Pi 虽然都有循环，持久恢复机制却不同；后续用 第39章 和 checkpoint/replay 深化讨论不同恢复单位。

再追到消费者：“收到用户消息”具体承诺了什么

在 Pi 中，把“不改 README”交给 AgentSession.steer 后，_queueSteer 把消息交给 Agent.steer；PendingMessageQueue.enqueue 将它放进内存数组。Agent 把队列的 drain 接成 getSteeringMessages，runLoop 在允许的边界取出消息，先追加到 currentContext.messages，随后才调用 streamAssistantResponse。follow-up 走另一条队列，在当前工作将要结束时取用。这条链闭合到了下一次模型请求的输入消费者，不能缩写成“接纳后立即改变在途请求”。

one-at-a-time 和 all 控制一次取一条还是取全部；enqueue 没有容量上限，队列本身也没有写盘。这说明的是该队列对象的合同，不否定外围 UI 可以限制输入。Session 历史能重建，不足以证明尚未消费的这些内存消息能跨进程恢复；同样，“每次取一条”不会让生产者自动变慢。

DeepSeek Harness（下文简称 DSH）把待处理消息也记为事件。这里的投影是从事件计算出的当前队列状态；它能重建什么，取决于哪些事件实际保存。send 通过 ReactLoopInbox.splice 追加 agent/inbox/spliced 事件，inboxProjectionDefinition.apply 按事件重建 next-step/next-turn 列表。preStep 从这个投影 claim，移除本次消息并发出 claimed 通知；允许进入步骤后，step 把消息记成 user/message，buildRequest 通过 Session.deriveMessages 得到模型历史，最终传给 prepared stream 或 llm.stream。因此 pending 投影、claimed 通知与模型消息是三种不同状态。

事件接纳与持久保存之间还有间隔：Session.append 同步接纳到内存 log，存储插件异步缓冲；SessionStore.flush 才等待已注册的持久化监听者。base 配置接入的 checkpoint policy 在 pre-step、模型下游 stream 构造前和顶层工具 body 前等待 flush；失败会阻止相应下游派发。自定义组合仍须确认该 policy 和存储 listener 实际启用，不能从裸 loop 继承保证。

按源码顺序推演一次失败：claim 的队列移除早于异步 prompt assembly，也早于 user/message 追加；前者返回不证明后者发生。即便某段前缀已经 flush，也不能把“pending 中没有这条消息”解释成“模型一定处理成功”。仅凭这段顺序还不能判断外围插件是否会补偿；需要检验的条件是：如果产品要求已接纳输入最终被处理，验收必须覆盖 claim 后、模型消费前的中断。

用事件序号算一次 projection 恢复

DSH 的 projection checkpoint 保存 {ver, seq, val}：ver 是投影状态格式版本，seq 是已经折叠进去的最后事件序号，val 是结果。它与 Session 的 seq = log.length 不同：后者表示下一个事件的位置。以下是依据 restoreFloor/restore 的手算，不是运行结果。

假设仅有一个已注册投影，兼容的 checkpoint 覆盖到事件 41，存储实际还有 42、43、44：

  1. restoreFloor 要求从 41 读取，而非直接从 42 读取；41 是证明存储尾部仍达到 checkpoint 的锚点。
  2. 读取 [41, 42, 43, 44] 后，已包含在 checkpoint 的 41 不再 apply，只折叠 42–44。返回 asOfSeq = 44；完整 Session 的下一位置为 45。
  3. 如果存储被修复截断到 40，从 41 读到空尾部，算出的末尾为 40。checkpoint 的 41 超过它，恢复拒绝这个尾读并要求从 0 重读，不能继续展示过新的缓存状态。
  4. ver 不匹配也要回到完整日志重新折叠。格式版本检查与事件 cursor 检查分别防止“算法不兼容”和“覆盖范围不真实”。

由此得到更精确的选型问题：需要恢复的是已消费历史、待处理意图，还是已经发生的外部效果？它们各自需要不同证据。数据库 WAL、业务事件、actor mailbox 和 outbox 分别在哪一层起作用，见Runtime 与分布式系统深研；这里的两条 Agent 链不因此自动拥有这些外部机制。

3. 分别决定谁拥有工作、事实和资源

Maka 的 Session/Turn/Run 提供了一种具体划分方式。设计自己的系统时可选择不同命名，但要分清三类身份：可持续的工作背景、一次用户要求，以及一次实际尝试。工具调用还需要自己的身份，以便把结果对应回来。

4. 把异常加到真实时间线上

现在让任务经过五个时点：读取文件 v7、模型生成编辑、用户写成 v8、执行器收到编辑、工具结果保存。正常情况下顺序一致，异常来自其中的间隔。

这里需要的是“检查前提与写入不能被同类受控写入穿插”的合同。进程内锁只能协调服从同一锁的参与者；普通文件系统上的外部编辑器不一定服从它。要么由统一资源服务提供原子条件写，要么缩窄保证，并使用安全补丁、检测和用户冲突处理。

接着加入第二种异常：改动已经落盘，进程在记录结果前崩溃。重新执行编辑可能重复作用，直接报告失败也可能误导用户。此时需要先说明可观察状态和可查询能力，再选择幂等重试、对账、补偿或人工接管。失败处理由效果语义决定，不能统一写成 catch → retry。

5. 条件编辑的完整设计记录

下面是一份已填写的参考设计记录，不是 Maka 或任何产品的真实 API：

决策：使用绑定观察版本的条件编辑。
解决的问题：模型思考期间用户也可能写文件。
输入：文件身份、观察版本、编辑意图、当前允许范围。
负责者：执行最终检查和提交的资源层。
正常结果：返回新版本、实际修改范围和验证入口。
失败结果：陈旧版本、冲突、明确未写入、结果未知。
替代方案：统一写入服务；独立工作副本后人工合并。
代价：冲突会增加回读和模型请求。
推翻条件：并行编辑实验显示仍能静默覆盖用户内容。

记录要能区分“方案想保证什么”和“现在证明到了哪里”。例如用户段落仍被静默覆盖，就推翻了“该条件编辑保护并行修改”的保证；此时需要统一写入 owner，或收窄为可检测冲突而非完全防止竞争。

8. 约束变化后的参考结论

题一：用户只要求修 README，Agent 发现函数有错，应否一起改？

不能从发现错误推出获得写入授权。可以定位和说明问题，完成允许的文档修改，并把函数修复作为需要新范围的工作。任务合同决定成功条件，不能用“改得更多”替代它。

题二：已经有一份持久任务表，是否还需要工具调用身份？

需要能区分任务内部的不同调用和重试尝试。任务身份只证明归属，不能指出哪次写入发生、哪份结果迟到。具体是否独立建表取决于存储方案，身份与关联关系不能省略。

题三：让两个 Agent 同时修两处代码一定更快吗？

只有在可独立调查、写入冲突可控、合并和复测代价小于节省时才成立。计算总时长要包括启动、上下文分发、等待、采纳和整体验证，总成本也要累计所有子任务。

跨实现题：两种产品都支持中途补充要求，能否画成相同的“新消息立即替换当前输入”？

不能。Codex 的接纳与步骤边界之间存在间隔；Claude Code 的公开交互能力也不足以证明在途请求即时替换。接纳、生效与效果结算是三个不同边界，未公开的内部关系仍保留未知。

本例得到两条失败结论：外部写入不服从同一锁时，进程内互斥不能保证不覆盖；效果后崩溃时，缺少结果不能保证安全重做。完整处理由资源合同和可查询能力决定，见工具与执行。

同一设计还可以解释输入变化的影响：同一模型、同一任务，仅把完整历史改成遗漏“保留用户 README 段落”的摘要，行为为什么可能变化？因为策略接收的是被选择后的输入，不是全知的环境状态。换更大的模型也不能保证恢复这次被删去的具体约束；应先找信息在哪个选择或压缩环节丢失，再讨论模型能力。

把“请求模型”继续拆到协议与执行闸门

“内部消息变成请求”和“响应返回循环”是不同阶段。以本课读取的 Pi OpenAI Responses 适配器为例：

  1. Agent 层准备输入。 已运行的 runLoop 等待 streamAssistantResponse；后者依次经过可选的 transformContext 与 convertToLlm，把内部消息转换成 pi-ai 通用消息，并组成共享的 Context。
  2. 适配器编码请求。 convertResponsesMessages 在内部调用 transformMessages 做消息兼容整理，再编码为 OpenAI Responses 的请求项。这与第1步的 Agent 通用消息转换属于不同层，也不代表所有 provider 都走这两个函数。
  3. 响应回到等待中的循环。 processResponsesStream 按输出槽归并增量参数和响应状态；streamAssistantResponse 消费适配器的事件流，取得最终消息后返回。runLoop 再判断停止还是进入工具处理；它不是由响应解析器新调用起来的。

第15章的八事件例把“参数已可解析”与“响应已完整结束”分开；因此完整的参数对象也不能绕过终止政策直接执行。模型适配与流式执行继续展开这些转换及其执行闸门。

这些阶段可与编译器 IR、增量解析、队列背压和 vLLM 前缀缓存设计对照。跨模型时，签名思考可能是仅对原模型或协议有效的不透明状态，适配器不能把它当通用历史原样重放；合成缺失 toolResult 只补消息关系，没有执行文件回滚；sessionId 只是关联或提示信息，不能证明实际请求满足前缀复用条件，缓存命中仍需服务端观测。这些转换取决于模型协议，不能据一条 adapter 路径推广到所有模型。
