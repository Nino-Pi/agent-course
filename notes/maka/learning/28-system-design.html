第 28 章｜智能代理（Agent）系统的设计方法

本章概览

核心问题：怎样把一次代码修复的目标和新增约束，转换成必要的组件、状态（State）与恢复规则？

关键概念：任务合同（Task Contract）：明确目标、范围与验收（Acceptance）；身份（Identity）：关联会话（Session）、要求和执行尝试；负责者（Owner）：拥有某类决定权；投影（Projection）：由事实（Fact）重建的视图；效果窗口（Effect Window）：操作与结果记录之间的间隙；设计记录（Design Record）：写明选择、代价与失效条件。

关系主线：从任务合同（Task Contract）确定身份（Identity）和负责者（Owner），连接模型（Model）输入（Input）、工具（Tool）与结果，再沿故障时间线检验哪些保证成立、哪些复杂度值得增加。

前情回顾：把六组职责放回同一项任务（Task）

第27章区分交接（Handoff）资料、当前要求与当前产物：接手者必须重新判断哪些观察（Observation）仍适用。第13–18章建立了身份（Identity）、事实（Fact）、投影（Projection）、工具（Tool）结算（Settlement）与未知效果（Unknown Effect）；第19–20章说明压缩和记忆（Memory）改变模型（Model）本次能读到什么；第23–26章再讨论分工、接续（Continuation）与验收（Acceptance）。

本章用这些知识做设计判断：先写清修复合同，再找每个决定的负责者（Owner），然后检查读取、执行和记录之间的间隔。先读完前六节，可以形成一套完整的设计；后面的真实循环与输入（Input）队列（Queue）用于检验这些职责怎样接到具体消费者（Consumer）。

2. 用最小链条检查必要组件

图中间是模型（Model）与工具（Tool）的反馈（Feedback）环，接纳（Admission）位于循环之前，验收（Acceptance）决定何时结束。“执行 → 观察结果（Observation）”解释下一步凭什么改变；完成候选 → 验收解释为什么模型（Model）说“完成”还不够。

子代理（Subagent）、向量库和工作流引擎是否必要，取决于任务（Task）是否需要分工、检索或持久编排（Orchestration）。执行边界（Execution Boundary）和失败表示则直接影响这次修复能否安全完成，即使最小方案也需要明确。

从反馈（Feedback）决策理论看：哪些是模型（Model）的工作，哪些必须由程序完成

沿用修复任务（Task）：第一次只知道输出错误；读函数后知道余数表达式；测试后又得到边界输入（Input）。下一步应根据新观察（Observation）调整。若在第一次请求中把所有行动请求（Action）排好再盲目执行，就无法利用第二步刚得到的证据。这是闭环决策相对于固定行动请求（Action）列表的价值。

推理与行动相结合（Reasoning and Acting，ReAct）把自然语言推理（Reasoning）也纳入决策过程：一次“思考”整理当前信息并更新后续上下文（Context），外部行动（Action）才取得新的环境观察（Observation）或改变资源。两者可以按需要交错，不要求所有任务（Task）都机械地“一次思考接一次外部行动（Action）”。ReAct论文第2节提供这一决策视角；它并未因此提供文件事务（Transaction）、进程隔离（Isolation）或工具（Tool）幂等（Idempotency）协议。

用下面的课程抽象把决策视角接到工程模块，记号不是任何框架的应用程序接口（Application Programming Interface，API）。先把“准备什么、提出什么”分开：

这份简式为解释职责而省略了执行前意图与认领（Claim）等转换；它也不假定外部效果、账本更新和历史（History）更新原子提交（Atomic Commit）。回执丢失时，账本可能只能记录未知，不能从缺少反馈（Feedback）推出相应操作未发生。第18章的崩溃窗口正是要补查这些被简式省略的中间状态（State）。

这里有三个不能省掉的分界。HtH_tHt​ 不等于世界当前状态（State）：文件可能被别人修改；CtC_tCt​ 不等于全部历史（History）：选择与压缩可能丢信息；模型（Model）提出 ata_tat​ 不等于行动请求（Action）被准许或相应操作成功：执行层（Execution Layer）还要检查真实资源并产生结果。这是把论文的决策视角扩展到工程问题的推导，不是论文声称已经解决这些保证。

4. 把异常加到真实时间线上

现在让任务（Task）经过五个时点：读取文件 v7、模型（Model）生成编辑、用户写成 v8、执行器收到编辑、工具（Tool）结果保存。正常情况下顺序一致，异常来自其中的间隔。

这里需要的是“检查前提与写入不能被同类受控写入穿插”的合同。进程内锁只能协调服从同一锁的参与者；普通文件系统上的外部编辑器不一定服从它。要么由统一资源服务提供原子条件写（Atomic Conditional Write），要么缩窄保证，并使用安全补丁、检测和用户冲突处理。

接着加入第二种异常：改动已经落盘，进程在记录结果前崩溃。重新执行编辑可能重复作用，直接报告失败也可能误导用户。此时需要先说明可读取的状态（State）和可查询能力，再选择幂等（Idempotency）重试、对账（Reconciliation）、补偿（Compensation）或人工接管。失败处理由效果语义决定，不能统一写成 catch → retry。

7. 沿真实循环检验消费者（Consumer）与保存边界

前面的设计已经交代目标、身份（Identity）、执行与验收（Acceptance）。下面只追一个问题：用户中途追加“不改 README”以后，哪份状态（State）先改变，哪次模型（Model）请求才能看见？先对照两种循环，再深入消息（Message）队列（Queue）与恢复。源码名称用于定位责任，无需先记住所有类名。

看两份真实循环，理解“框架更复杂”究竟增加了什么

mini 的 DefaultAgent.step() 直接连接 query() 与 execute_actions()：模型（Model）收到 messages，环境（Environment）处理行动请求（Action），格式化后的观察（Observation）追加回去；外层 run() 处理停止与异常，并在每轮的 finally 中调用保存；没有配置路径时，只返回序列化数据而不写盘。

代码短，使反馈（Feedback）链容易看清；但执行轨迹（Trajectory）写入不与外部文件效果组成事务（Transaction）。保存聊天记录与安全恢复副作用（Side Effect）是两个问题。

Pi 是一种开源代码代理（Code Agent）。runLoop 在工具（Tool）反馈（Feedback）之外提供步骤间准备：运行中引导（Steering）补充当前工作输入（Input），后续输入（Follow-Up）则在当前工作将结束时取用。两者让新消息（Message）在明确边界进入后续请求。

streamAssistantResponse 先按配置做可选的 transformContext，再用 convertToLlm 转成 pi-ai 通用消息（Message），交给具体模型（Model）适配器（Adapter）编码。会话（Session）层的 buildContextEntries 则沿当前分支末端（Leaf，即所选分支的最后条目）及上下文压缩（Context Compaction）记录重建本轮材料。这些机制扩展了输入（Input）选择与交互控制的接缝；它们各自仍需要具体保存与读取规则。

具体推演：用户在一次工具（Tool）执行期间追加“不改 README”。模型（Model）已经发出的行动请求（Action）不会因此从历史（History）中消失；Pi 在后续边界取队列（Queue）并组成新输入（Input）。需要保护尚未发生的写入，还要由执行层（Execution Layer）检查当前权限（Permission）。由此可以看出，输入（Input）队列（Queue）解决“何时看见”，权限（Permission）系统解决“此刻能否做”，两者并不重复。

mini/Pi 虽然都有循环，持久恢复机制却不同；后续用 第39章 和 检查点（Checkpoint）与重放（Replay）深化讨论不同恢复单位。

再追到消费者（Consumer）：“收到用户消息（Message）”具体承诺了什么

在 Pi 中，把“不改 README”交给 AgentSession.steer 后，_queueSteer 把消息（Message）交给 Agent.steer；PendingMessageQueue.enqueue 将它放进内存数组。Agent 把队列（Queue）的 drain 接成 getSteeringMessages，runLoop 在配置允许的边界取出消息（Message），也可以按配置跳过一次初始读取；先追加到 currentContext.messages，随后才调用 streamAssistantResponse。后续输入（Follow-Up）走另一条队列（Queue），在当前工作将要结束时取用。这条链闭合到了下一次模型（Model）请求的输入（Input）消费者（Consumer），不能缩写成“接纳（Admission）后立即改变在途请求”。

one-at-a-time 和 all 控制一次取一条还是取全部；enqueue 没有容量上限，队列（Queue）本身也没有写盘。这说明的是该队列（Queue）对象的合同，不否定外围 UI 可以限制输入（Input）。会话（Session）历史（History）能重建，不足以证明尚未消费的这些内存消息（Message）能跨进程恢复。

一次只消费一条消息（Message），也没有限制生产者继续入队的速度；若需要稳定内存占用，还要明确容量与背压（Backpressure）合同。

代理运行支撑系统 DeepSeek Harness（简称 DSH）把待处理消息（Message）也记为事件（Event）。这里的投影（Projection）是从事件（Event）计算出的当前队列（Queue）状态（State）；它能重建什么，取决于哪些事件（Event）实际保存。send 通过 ReactLoopInbox.splice 追加 agent/inbox/spliced 事件（Event），inboxProjectionDefinition.apply 按事件（Event）重建下一步骤/下一轮次（Next-Step / Next-Turn）列表。preStep 从这个投影（Projection） claim，移除本次消息（Message）并发出已认领（Claimed）通知；允许进入步骤后，step 把消息（Message）记成 user/message，buildRequest 通过 Session.deriveMessages 得到模型（Model）历史（History），最终传给预备调用的流（Prepared Call Stream）或 llm.stream。因此待处理投影（Projection）、认领（Claim）通知与模型（Model）消息（Message）是三种不同状态（State）：

接纳（Admission）事件（Event）进入内存日志系统已接受这次队列（Queue）变更已经写到持久存储
从待处理投影（Projection）取出并认领（Claim）本次准备步骤已取得消息（Message）异步输入（Input）组装必定成功
追加 user/message会话（Session）已记录用户消息（Message）模型（Model）已经完成处理
生成实际请求并取得回应模型（Model）消费链已经继续先前外部效果已撤销

事件（Event）接纳（Admission）与持久保存之间还有间隔：Session.append 同步接纳（Admission）到内存日志（In-Memory Log），存储插件异步缓冲；SessionStore.flush 才等待已注册的持久化（Persistence）监听者：先等所有监听者结算（Settlement），再传播失败；没有监听者时会返回 false，所以仅仅调用它不能证明数据已持久保存。

base 配置接入的检查点（Checkpoint）策略（Policy）在步骤准备、带会话（Session）的模型（Model）流首个数据片段之前和顶层工具（Tool）执行体之前等待刷写（Flush）；失败会阻止对应下游继续。子工具（Tool）与没有会话（Session）的模型（Model）请求另有路径，不能套用这一结论。自定义组合仍须确认该策略（Policy）和存储监听者（Storage Listener）实际启用，不能从单独循环（Loop）继承保证。

按源码顺序推演一次失败：认领（Claim）的队列（Queue）移除早于异步提示词组装（Prompt Assembly），也早于 user/message 追加；前者返回不证明后者发生。即便某段前缀已经刷写（Flush），也不能把“待处理（Pending）中没有这条消息（Message）”解释成“模型（Model）一定处理成功”。仅凭这段顺序还不能判断外围插件是否会补偿（Compensation）；需要检验的条件是：如果产品要求已接纳（Admission）输入（Input）最终被处理，验收（Acceptance）必须覆盖认领（Claim）后、模型（Model）消费前的中断。

用事件（Event）序号算一次投影（Projection）恢复

DSH 的投影（Projection）检查点（Checkpoint）保存 {ver, seq, val}：ver 是投影（Projection）状态（State）格式版本，seq 是已经折叠进去的最后事件（Event）序号，val 是结果。它与会话（Session）的 seq = log.length 不同：后者表示下一个事件（Event）的位置。以下是依据 restoreFloor/restore 的手算，不是运行结果。

假设仅有一个已注册投影（Projection），兼容的检查点（Checkpoint）覆盖到事件（Event） 41，存储实际还有 42、43、44：

  1. restoreFloor 要求从 41 读取，而非直接从 42 读取；41 是证明存储尾部仍达到检查点（Checkpoint）的锚点。
  2. 读取 [41, 42, 43, 44] 后，已包含在检查点（Checkpoint）的 41 不再执行折叠（Apply），只折叠 42–44。返回 asOfSeq = 44；完整会话（Session）的下一位置为 44+1=4544+1=4544+1=45。
  3. 如果存储被修复截断到 40，从 41 读到空尾部，算出的末尾为 40。检查点（Checkpoint）的 41 超过它，恢复拒绝这个尾读并要求从 0 重读，不能继续展示过新的缓存状态（State）。
  4. ver 不匹配也要回到完整日志重新折叠。格式版本检查与事件（Event）游标（Cursor）检查分别防止“算法不兼容”和“覆盖范围不真实”。

由此得到更精确的选型问题：需要恢复的是已消费历史（History）、待处理意图，还是已经发生的外部效果？它们各自需要不同证据。数据库预写日志（Write-Ahead Log，WAL）、业务事件（Event）、参与者邮箱（Actor Mailbox）和事务发件箱（Transactional Outbox）分别在哪一层起作用，见运行时（Runtime）与分布式系统深研；这里的智能代理（Agent）实现链不因此自动拥有这些外部机制。

把“请求模型（Model）”继续拆到协议与执行闸门

“内部消息（Message）变成请求”和“响应返回循环”是不同阶段。以本课读取的 Pi OpenAI Responses 适配器（Adapter）为例：

  1. 智能代理（Agent）层准备输入（Input）。 正在执行的 runLoop 等待 streamAssistantResponse；后者依次经过可选的 transformContext 与 convertToLlm，把内部消息（Message）转换成 pi-ai 通用消息（Message），并组成共享的上下文（Context）。
  2. 适配器（Adapter）编码请求。 convertResponsesMessages 在内部调用 transformMessages 做消息（Message）兼容整理，再编码为 OpenAI Responses 的请求项。这与第1步的智能代理（Agent）通用消息（Message）转换属于不同层，也不代表所有模型服务提供方（Provider）都走这两个函数。
  3. 响应回到等待中的循环。 processResponsesStream 按输出槽归并增量参数和响应状态（State）；streamAssistantResponse 消费适配器（Adapter）的事件（Event）流，取得最终消息（Message）后返回。runLoop 再判断停止还是进入工具（Tool）处理；它不是由响应解析器新调用起来的。

第15章的八事件（Event）例把“参数已可解析”与“响应已完整结束”分开；因此完整的参数对象也不能绕过终止政策直接执行。模型（Model）适配与流式执行继续展开这些转换及其执行闸门。

这些阶段可与编译器中间表示（Intermediate Representation，IR）、增量解析（Incremental Parsing）、队列（Queue）背压（Backpressure）和 vLLM 前缀缓存（Prefix Cache）设计对照。跨模型（Model）时，签名思考可能是仅对原模型（Model）或协议有效的不透明状态（State），适配器（Adapter）不能把它当通用历史（History）原样重放；合成缺失工具（Tool）结果 toolResult 只补消息（Message）关系，没有执行文件回滚；会话标识（Session ID）sessionId 只是关联或提示信息，不能证明实际请求满足前缀复用条件，缓存命中仍需服务端观测。这些转换取决于模型（Model）协议，不能据一条适配器（Adapter）路径推广到所有模型（Model）。

8. 把设计落到 Codex 与 Claude Code

Codex 是 OpenAI 的代码代理（Code Agent）产品，Claude Code 是 Anthropic 的代码代理（Code Agent）产品，两者均有多种使用入口。本课对 Codex 主要追踪本地开源实现中的选定路径，对 Claude Code 按公开产品机制讨论；具体入口和适用条件在对应章节说明。

现在把用户中途追加的“不改 README”放回生命周期（Lifecycle）图。关键问题是何时接纳（Admission）、哪次请求开始看见它，以及已经发生的效果怎样结算（Settlement）。Codex 的 app-server 路径给出了接纳（Admission）分类与输入（Input）队列（Queue）；Claude Code 的交互模式文档则明确区分消息（Message）排队与中断：工具（Tool）调用期间排队的消息（Message）在这些调用结束后交给模型（Model）；若轮次结束仍有消息（Message），最旧一条作为下一轮，其余继续排队。

命令有不同的派发规则。这个公开交互合同仍不足以证明内部采用与 Codex 相同的接纳（Admission）状态（State）类型，也不表示已发生效果被撤回。

9. 约束变化后的参考结论

题一：用户只要求修 README，智能代理（Agent） 发现函数有错，应否一起改？

不能从发现错误推出获得写入授权（Authorization）。可以定位和说明问题，完成允许的文档修改，并把函数修复作为需要新范围的工作。任务合同（Task Contract）决定成功条件，不能用“改得更多”替代它。

题二：已经有一份持久任务（Task）表，是否还需要工具（Tool）调用身份（Identity）？

需要能区分任务（Task）内部的不同调用和重试尝试。任务（Task）身份（Identity）只证明归属，不能指出哪次写入发生、哪份结果迟到。具体是否独立建表取决于存储方案，身份（Identity）与关联关系不能省略。

题三：让两个智能代理（Agent）同时修两处代码一定更快吗？

只有在可独立调查、写入冲突可控、合并和复测代价小于节省时才成立。计算总时长要包括启动、上下文（Context）分发、等待、采纳和整体验证，总成本也要累计所有子任务（Child Task）。

跨实现题：两种产品都支持中途补充要求，能否画成相同的“新消息（Message）立即替换当前输入（Input）”？

不能。Codex 的接纳（Admission）与步骤边界之间存在间隔；Claude Code 的公开交互能力也不足以证明在途请求即时替换。接纳（Admission）、生效与效果结算（Settlement）是三个不同边界，未公开的内部关系仍保留未知。

本例得到两条失败结论：外部写入不服从同一锁时，进程内互斥不能保证不覆盖；效果后崩溃时，缺少结果不能保证安全重做。完整处理由资源合同和可查询能力决定，见工具（Tool）与执行。

同一设计还可以解释输入（Input）变化的影响：同一模型（Model）、同一任务（Task），仅把完整历史（History）改成遗漏“保留用户 README 段落”的摘要，行为为什么可能变化？因为策略（Policy）接收的是被选择后的输入（Input），不是全知的环境状态（State）。换更大的模型（Model）也不能保证恢复这次被删去的具体约束；应先找信息在哪个选择或压缩环节丢失，再讨论模型（Model）能力。
