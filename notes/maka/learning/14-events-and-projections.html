第 14 章｜事实、事件与投影视图

本章概览

核心问题：聊天气泡、模型历史和持久记录不一致时，哪份信息能决定工作是否完成？

关键概念：Fact（事实）是负责组件保存的记录；Event（事件）描述发生了什么；Ledger（账本）持久保存一类事实；Projection（投影）生成供特定消费者使用的视图。

关系主线：事件按各自通道接纳与保存，读取侧再整理为界面或模型输入。视图可以省略、延迟或重建；保存错误也可能是回执丢失，不能从旧画面或缺少结果推断效果未发生。

工作身份的定义见 Session、Turn、Run；本章关注同一工作留下的不同记录与读取视图。

核心路线

断线后，哪份记录决定完成状态

假设 R7 已经修改说明、运行完测试，也生成了最终回答，但 Desktop 在收到完成通知前断线。重新打开后，系统应该相信什么？完整 formatDuration 修复还会增加源码编辑和验证记录，判断记录与视图的方法相同。

  • Client 内存中最后一个 loading 状态？
  • 聊天列表最后一条 assistant 文本？
  • Runtime 写下的执行事件？
  • 从执行开始、结束等事件整理出的状态？
  • 工具自己的执行记录？

这几种信息分别涉及四个概念：

  • 事实（Fact）：系统声称已经发生并可供判断的记录；
  • 事件（Event）：描述发生了什么的结构化记录；是否持久保存、按什么顺序接纳，要看对应通道；
  • 账本（Ledger）：保存某类事实的持久顺序记录；
  • 投影视图（Projection）：从事实整理出的、可供模型或人阅读的视图。

判断冲突时，先确定信息属于原始记录、owner 的控制状态还是派生视图，再找到负责该问题的事实来源。

从持久事实生成用途视图

完整执行事件先经过接纳和持久保存，再按用途生成视图：

图的上半部是写入确认，下半部是两个消费者。UI 折叠工具详情，模型历史保留需要配对的协议内容，两种视图因此可以不同；它们都从已接纳的记录生成。

边界与失败。 写入报错时，记录可能已保存而回执丢失，所以图中使用“尚未确认”，没有画成“确定不存在”。读视图落后时应回查对应事实，不能据旧 running 画面否认终态。图只突出执行事件这一类事实；接单、Memory 和投影控制记录仍有各自职责，未完成的流式片段（partial）也有独立的展示用途。实际投影还依赖相应规则与记录，图不是全部 Store 的依赖关系，也不意味着账本能证明测试覆盖正确或撤销文件效果。

Desktop 的绿色对勾本身不应该成为 R7 完成的唯一证据。它只是供人阅读的视图。

Maka 由不同部件分别保存接单、执行和长期记忆等记录。查“这项工作是否已结束”和查“中文偏好是否已保存”，需要找到各自负责的记录；不能只查聊天文本。

什么叫“事实”

日常语言里的事实很宽泛。这里的事实特指某个系统 owner 以明确格式保存、可供后续读取和判断的信息。

统一案例可能产生这些事实：

T7 的用户输入是什么
T7 被准入为 R7
模型请求了 Read(package.json) 与 Read(README.md)
两个 Read 分别返回了什么
模型请求了 Edit(README.md)
Edit 的执行结果是什么
Bash 的退出状态是什么
模型生成了哪段最终文本
R7 最终是 completed / failed / cancelled 中的哪一种

事实不是“绝对真理”的同义词

系统保存“Bash 返回 exit 0”，表示执行器报告了这个结果。它不能自动证明测试覆盖了所有业务要求，也不能证明工具实现永远没有 bug。

事实的范围由写入者和记录内容决定。例如测试执行器能报告退出状态，测试是否覆盖用户要求仍要核对断言和任务契约。

canonical 是什么意思

权威事实（Canonical Fact）表示：当多个表示发生冲突时，系统指定哪一个作为该问题的判定依据。

例如：

Desktop 仍显示 running
Runtime 的 canonical terminal fact 显示 completed

这通常意味着 Desktop 的投影过期，而不是 Run 又从 completed 退回 running。

Canonical 总要带范围。Maka 用 RuntimeEvent 记录 Agent 执行中的语义事实，例如模型与工具交互、执行终态；它不因此决定长期 Memory 应该保存什么，或 Host 应该接纳哪项新工作。

什么叫“事件”

事件是一条“发生了什么”的记录，通常被追加到已有历史后面。

可以把 R7 的过程教学化地表示为：

E1  收到/记录本轮用户输入
E2  模型产生两个 Read 调用意图
E3/E4  两个 Read 分别返回项目配置和当前说明（并行时先后可以互换）
E5  模型产生 Edit 调用意图
E6  Edit 返回结果
E7  模型产生 Bash 调用意图
E8  Bash 返回输出与退出状态
E9  模型生成最终中文文本
E10 R7 进入 terminal

这些 E1…E10 是解释顺序的教学编号，不是 Maka 的实际 event type 或字段名。

为什么事件比“最后状态”提供更多信息

若数据库只保存：

R7.status = completed

你无法回答：

  • README 到底怎样修改；
  • 测试是否真的运行；
  • 工具结果支持了什么结论；
  • 模型在哪一步失败或重试；
  • 重建模型上下文时，某个工具结果对应的是哪次调用。

事件保留过程中的语义边界。

什么叫“账本”

账本是保存某一类事实的持久记录。类比财务账本：它不只是一个当前余额，还保留每笔收入和支出的来由。

对 Agent 来说，账本的价值包括：

  • 重启后知道已经发生什么；
  • 为模型重建可见历史；
  • 为 Client 重建界面；
  • 判断工具调用是否可能已产生副作用；
  • 支持恢复、审计和用量计算；
  • 防止迟到结果覆盖已经确定的终态。

账本总要说明记录范围。接单记录回答工作是否被接受，执行记录回答过程中发生什么，Memory 保存长期信息；不能因为都持久保存，就把它们当成一张能回答所有问题的表。具体职责见多账本分工。

投影视图：把事实整理成人或模型能用的形状

投影视图是对事实做筛选、排序、组合后得到的阅读形式。这里“给谁看、用来做什么”决定它的形状。

同一组 R7 事实可以形成多种投影：

表 1 / Table 1 · 投影视图：把事实整理成人或模型能用的形状
投影（Projection）面向谁可能怎样处理事实
对话记录（Chat transcript）用户把事件整理成连续对话气泡，折叠大段工具输出
会话状态（Session status）客户端（Client）汇总为正在执行或已结束
模型历史（Provider history）模型选择可见的完整内容，把工具请求和对应结果放在一起，并控制输入长度
用量视图（Usage view）计量界面汇总模型请求的用量数据
恢复视图（Recovery view）恢复逻辑联合接单、结束和工具执行记录，检查还有什么不确定

它们都来自事实，却服务不同目的，所以不必长得一样。

投影通常应该可以重建

如果 Desktop 丢失本地缓存，理想情况是从持久事实重新生成聊天和状态，而不是让用户重新执行 R7。

投影也可能落后

网络断开、订阅延迟或 Client 崩溃时，视图可能暂时不是最新。这正是不能让 UI 独自决定执行终态的原因。

Terminal：最终状态为什么需要唯一裁决

终态表示 R7 已经结束，不再是可继续追加普通执行过程的 active Run。常见结果有 completed、failed、cancelled。

当 UI 仍显示 running、负责执行状态的记录已经是 completed 时，应修复过期视图，不能让 UI 改写执行结果。当完成、取消与迟到错误同时到达时，终态裁决必须阻止它们反复覆盖同一个结果。

用 R7 看一次事实到投影的转换

执行事实（教学简化）

R7 / Read call: package.json
R7 / Read result: package.json content
R7 / Read call: README.md
R7 / Read result: README.md current content
R7 / Edit call
R7 / Edit result: success
R7 / Bash call
R7 / Bash result: exit 0, output: 4 pass / 0 fail
R7 / assistant final: 中文总结
R7 / terminal: completed

用户看到的 transcript projection

用户：读取配置，更新 README，运行测试……
助手：已更新 README，并运行测试；4 项通过。

为了可读性，UI 可能折叠了工具参数和大量输出。

下一次模型看到的 history projection

它可能包含用户输入、必要的工具调用与对应结果，以及模型最终文本；有些内容会被过滤、缩短或另行组织，所以不保证与界面逐字相同。第15章展开了从历史投影到一次实际模型请求的转换。

同一事实源生成了两种不同视图；二者不同不代表其中一个在撒谎。

对照一次真实 Edit 的两种表示

先摘取将在第22章展开的完整函数与文档修复：同一次 Edit 有原始工具结果，也有送给模型的简短修改报告。之后模型另用 git diff 取得两文件完整差异。文件现态、工具报告与模型输入是三种观察对象。简短编辑报告能描述本次改动，但要核对完整最终文件或 diff，仍需额外读取。

核心问题解析

问题 1。 Desktop 显示 running、RuntimeEvent 已有 completed terminal 时，哪一个作为执行状态依据？

解释。 以负责该执行状态的持久终态事实为依据，再修复落后的 UI 投影。

问题 2。 为什么只保存 R7.status = completed 不足以解释执行过程？

解释。 status 不能说明读过什么、工具是否失败、最终回答根据什么观察；解释过程还需要事件。

问题 3。 RuntimeEvent 为什么不能替代 Memory 或 root admission store？

解释。 canonical 有职责范围。执行语义不自动拥有 Memory 或 admission 的状态与规则。

问题 4。 同一组记录给 UI 生成气泡、给模型生成历史输入，二者不同是否意味着其中一个是假的？

解释。 不意味着。两种投影服务不同目的，可能筛选、折叠或组织不同内容；关键是保留事实来源与用途边界。

实现深化

多账本怎样分配职责

Maka 采用多个 owner 分别保存各自事实：

表 2 / Table 2 · 多账本怎样分配职责
账本 / 存储类别（Ledger / Store）主要回答什么不能单独证明什么
顶层准入（Root Admission）T7 是否被 Host 接受，并固定为哪个 R7provider 已发送、R7 已终结
运行事件（RuntimeEvent）R7 中模型/工具交互的语义过程与 terminal factGoal、approval、共享授权等全部产品状态
运行操作账本（AgentRun Operational Ledger）R7 的组成、请求 attempt、摘要检查点（checkpoint）与投影变换记录（projection transition，记录历史表示怎样被调整）Desktop 当前应画哪种布局
工具边界日志（Tool Boundary Journal）普通工具实现从何时可能开始、怎样结算所有 provider-executed 或 Client capability 都有同样保证
交互（Interaction）sandbox 扩权或用户问题的请求、决定与关闭完整模型历史
长期记忆（Memory）长期信息、来源、版本或文件 bundle 状态Run 是否完成

分开并不是为了复杂，而是为了让每种状态有清晰 owner。一个 Memory 写入失败不应该重写 R7 已经完成的模型与工具事实；一个 UI 投影也不能自行批准 sandbox boundary expansion。

Terminal 裁决与 settled 结算

真实并发中，多个信号可能几乎同时到达：

provider 正常完成
+ 用户点击 stop
+ 超时处理触发
+ 一个迟到的错误 callback

如果任何 callback 都能覆盖最终状态，Client 可能先看到 completed，随后又变 failed，再变 cancelled。Maka 用 terminal claim/barrier 约束第一个 canonical terminal，并拒绝迟到信号随意改写它。

当前 invocation outcome 从 canonical terminal RuntimeEvent 投影；查询状态不能独立于已保存的终态事实另写一份答案。

terminal 与 settled 不同

terminal：用户已经有 canonical 结果
settled：后台 iterator、provider attempt、临时资源等已完成清理/结算

两者可能接近，但不是同一含义。用户不必等所有资源清理才看到最终回答；系统也不能因为已经向 UI 发了文本就跳过后续结算。

RuntimeEvent：执行语义的黑匣子

Maka 用 RuntimeEvent 保存 Agent 执行中的语义事实。可以把它理解为飞机黑匣子：它记录飞行过程中关键事件，但机场订票、旅客权限和维修计划仍由其他系统负责。

RuntimeEvent 需要能够表达的不只是聊天文本，还包括：

  • 模型输出和可能的 partial/streaming（未完成流式片段）；
  • tool call 与 tool result；
  • thinking（思考输出）或特定模型服务重放所需的信息；
  • visibility / origin（可见性 / 来源）等投影规则；
  • usage 与 terminal 语义；
  • S1 / T7 / R7 / invocation correlation。

因此一个普通的 messages = [{role, content}] 数组通常不足以承担完整执行 authority。

SessionEvent 与 RuntimeEvent 的直觉区别

Backend 在运行过程中会产生较靠近执行循环的事件；Runtime 再把其中可保存的语义映射为 RuntimeEvent，经过 AgentRun 接受并写入持久 store。

Backend/session-side event
  → 语义映射与身份补全
  → AgentRun 接受
  → durable RuntimeEvent

程序内部 callback 已发生，仍可能在映射、接纳或写入时失败；只有持久提交完成，恢复程序才能从这条链读回对应事实。

Partial、完整事件与模型可见性

流式模型输出可能逐字到达 Client：

“已” → “已更” → “已更新” → “已更新 README…”

这些 partial 片段对实时 UI 很有用，但重建下一次模型输入时，不能把每个增量都当成独立完整回答重复塞进去。

Runtime 在构造模型历史时会考虑：

  • 是否为 partial；
  • 是否标记为 model-visible；
  • tool call 与 result 是否合法配对；
  • thinking/tool history 是否与当前 provider 兼容；
  • 是否已有有效 compaction checkpoint；
  • 是否存在大型结果的 projection transition（持久投影变换）。

这说明“已经保存的事件”和“下一次全部原样给模型”也不是一回事。事件是事实基础；模型上下文是经过规则构造的投影。

StoredMessage：有用，但不是正常执行语义的最终 authority

聊天产品通常需要容易读取的 StoredMessage：用户消息、assistant 文本、某些工具展示内容。它很适合 renderer 和兼容读取。普通 Session 直接从 RuntimeEvents 派生这份消息视图，因此“消息类型叫 StoredMessage”不意味着系统还维护一套独立的普通执行消息真相。旧格式导入与工作协调记录有另外的专用入口，本节不将它们混入普通执行链。

当前 provider history 只从 RuntimeEvent 构造；StoredMessage 无法承担这条执行语义链，例如它不能完整表达：

  • provider-native thinking state；
  • 精确 tool call/result pairing；
  • partial、visibility 和 origin；
  • terminal barrier；
  • 物理请求 attempt。

没有 RuntimeEvent context 时，backend 不从 StoredMessage 补历史；不支持的 provider-native 项会按能力过滤，text-only 降级也来自 RuntimeEvent。另有 backfill 可在严格条件下修复部分 RuntimeEvent，那是修复过程，不是每次请求的 transcript fallback。

opening 也是事件，operational ledger 仍有用途

一次执行的 model、connection、lineage 来自 invocation_opened；RuntimeInvocationRecord 是从事件投影出来的 opening/terminal 视图。历史 reasoning 能否在当前 provider 上重放，需要核对模型服务路由的来源信息（route provenance），不能只看一张旧 header 的 model 字符串。

同时，checkpoint 与 model-projection transition 仍保存在 operational event ledger。由此得到一个更准确的判断：opening 归入 RuntimeEvent 脊柱，并不等于所有产品 store 或 operational records 都消失。

崩溃场景：为什么事实边界很重要

场景 A：Client 在 R7 terminal 前断线

假设 Host 仍存活，且动作由 Host/Runtime 的普通执行器承担，Client 断线本身不会取消 R7。R7 继续按自身生命周期推进，可能完成，也可能失败；持久终态形成后，Host 才据此发布完成状态，Client 重连时从 canonical snapshot 补齐观察。若动作依赖已经断线的 Client 执行能力，则要另外处理执行中断与效果未知，不能套用这条恢复路径。

场景 B：Client 收到最终文本，但 terminal 尚未 durable

先展示回答文字本身不构成错误；危险的是据此提前把执行状态标为 completed。可靠路径应以 durable terminal 为发布完成状态的依据，避免把“回答文字已到达”写成重启后无法证实的执行结论。

场景 C：Edit 产生效果后、工具结果写入前崩溃

RuntimeEvent 历史可能只有 tool call，没有确定 result。此时必须结合 Tool boundary journal 判断是否能安全 reconcile；不能仅因 transcript 没显示成功就重做 Edit。

场景 D：terminal 已保存，但 Session projection 仍显示 running

恢复程序应修复投影，使它与 canonical terminal 对齐。不能反过来删除 terminal 来迎合过期 UI 状态。

两种顺序：单次执行顺序与 Session 全局顺序

这个细节解释多 Run 历史为什么不能只靠时间戳排序。

Maka 的 RuntimeEvent 有两类顺序坐标：

  • event_seq：在一个 invocationId 内单调递增，用于单次执行前缀、工具边界和 replay；
  • Session ordinal：为同一 Session 中跨 Run 的 immutable events 建立提交顺序。

时间戳可能相同、不同机器的时钟也可能有偏差；runId 的字典序更不代表真实先后。因此 Session-wide projection 需要明确的 ordinal，而不是猜。

同一份回答，怎样从 running 变成中断记录

增加一个恢复要求：**Host 退出后，新进程必须如实说明已经知道什么。**为单独观察状态层，下面把 R7 缩小为“对用户已提供的 README 差异给出中文说明”的无工具任务，用一个最小事件前缀手算。完整修复还会增加工具等事件，序号须按实际记录计算。以下按普通 RuntimeEvent/SQLite 路径推演，不是实测轨迹，也不包含 continuation claim、handoff 或特殊导入路径。

事件与视图之间的关系可以写成：

L：已经接受的完整事件前缀
P：仍在变化的 partial 展示内容
V = Project(L, P)：按用途生成的视图

这不是 Maka 的新 API。Project 还需执行身份和相关 authority 记录；资料损坏时可以失败。关键是 V 中有回答文字，不等于 L 中有结束事实。假设 S1 已有 30 条 immutable events，R7 接下来这样推进：

表 3 / Table 3 · 同一份回答，怎样从 running 变成中断记录
时点R7 内序号 / S1 提交序号（Ordinal）能得出的结论
opening 保存，随后用户请求保存(1,31)、(2,32)知道 R7 存在、收到什么请求
模型逐段输出“这处修改……”写入 partial 展示记录；尚不占 (3,33)可以显示进展，仍未结束
保存完整 assistant 内容(3,33)；移除匹配的 partial snapshot有完整回答，仍没有 terminal
Host 退出，普通启动恢复收束 R7新 terminal 为 (4,34)failed / app_restarted，旧回答仍是历史内容
相同 terminal id 和内容再次提交仍是 (4,34)exact retry，不追加第五条
旧 callback 迟到，要求追加另一个成功 terminal被 seal 拒绝不会把 R7 重新裁决为成功

数字是教学值；真正 immutable 序号由存储事务分配。partial 走独立记录，完整事件替换其展示用途，并不意味着先前每个字都是一条永久普通事件。开放 Run 的显示还可以把尚在到达的文字整理成可读行，这也不是写回账本。

谁实际使用这份状态？SessionManager.getMessages/listTurns 调用 RuntimeReadModel；它读取 invocation 和事件，构造消息与 Turn 视图。没有 terminal 的 invocation 仍标 running，因此“模型已写完一段回答”不会自动变成完成。启动恢复则由 SessionManager 分类：普通无 terminal 执行记录为中断；已存在合法 completed terminal 时保留它。若写入报错但记录其实已落账，要通过相应回读/terminal barrier 分辨，不能从异常推断应该再做一次任务。

这条设计适合回答“谁在何时被系统接受为结束”。它保留过程、支持重新派生视图，也要求承担事件校验、存储与恢复分支的成本。它不能独自证明测试覆盖正确、文件已经回滚或任意进程能接着跑；这些问题分别交给评价、效果与持续运行模块。

视图失效，不等于事实被撤回

还沿用这个例子：Client 最后看见 running 快照，随后 Host 保存 terminal。旧快照应失效，terminal 无需改变。活跃 Host 会撤销旧 transcript overlay 并发布更高 revision 的 canonical projection；Client 消费者核对 Host、订阅身份、下一 sequence 和递增 revision。序列不连续时应报协议错误，不能拿旧帧覆盖新状态。

这些数不能混用：S1 的 ordinal 34 是持久事件坐标；某次订阅的 sequence 41 是那条观察流的位置。新订阅从新 snapshot 开始，不必从 42 接着数。新进程没有旧内存缓存，重建视图与“给旧对象发一次 invalidate”也不是同一动作。具体界面是否自动重连，还取决于 Client 的恢复策略。

换一种需求：保留探索历史，只给模型一条当前路径

如果用户的重点是“从之前的思路重新尝试，同时保留旧分支”，只看 Run 终态还不够。另一种 Code Agent 实现 Pi 提供了具体设计：Session 条目有 id/parentId，当前叶节点（leaf）决定沿哪条祖先路径重建输入。它解决输入路径选择，不能直接代替 Maka 的终态裁决。

用最小树手算，a 是用户问题，b/c 是第一次尝试：

原记录：a → b → c
branch(a) 后追加新条目 d，且已保存：
          a → b → c   仍在文件中
          └→ d       当前路径为 a → d

branch(a) 本身只移动内存 leaf；若尚未追加 d 就退出，重新打开文件会从最后有效条目 c 重建 leaf。若 d 已持久化，重建路径才是 a→d。buildSessionContext 还应用这条路径上的 compaction 边界，把合适条目变成消息；SDK createAgentSession 把结果赋给真实 agent.state.messages。普通 extension custom 记录不进入这份消息，custom_message 才进入，说明“扩展状态已保存”也不等于“模型已经读到”。

持久化另有条件：这里的 flushed 是 Pi 会话写出分支使用的状态，表示已完成该分支的文件写出，不表示每条记录都做了 fsync（请求把数据同步到持久存储）。新普通 Session 尚无 assistant 且未 flushed 时，已有条目可以只在内存；第一条 assistant 到来后才统一写出。已存在并 flushed 的文件另有追加分支。读取会跳过 malformed JSON 行，并可能为非空尾行补换行。这是一种具体的容错与交互取舍，不能提升为事务、每条 fsync 或任意损坏下的正确重放保证。

比较时问“我要恢复的是执行结果、模型输入还是工作文件”：选择历史分支不会撤销 c 阶段已经改过的文件。若需要可恢复的导航决定或更强写入确认，就必须另外定义持久合同，不能靠保留更多聊天文本实现。

机制与条件变化解析

问题 1。 为什么流式 partial 不能全部当成独立历史消息发回模型？

解释。 partial 是进行中的快照，可能被替换；逐个重放会重复甚至引用未完成内容。

问题 2。 RuntimeEvent 不可用时，是否自动读取 StoredMessage 作为 provider history？

解释。 不会。当前 replay 只来自 RuntimeEvent；缺失 context 与独立 backfill 修复应分开。

问题 3。 opening 迁入事件脊柱后，checkpoint operational ledger 是否消失？

解释。 没有。opening/terminal 的来源与 checkpoint、model-call、projection transition 的 operational 记录各有职责。

改变条件，再判断恢复方案

问题 1。 R7 的回答完整，但 Host 重启前没有 terminal。可以根据“已完成”的文字补 completed 吗？若 terminal 实际已存在但回执丢了，答案怎样改变？

解释。 不能。当前普通无 claim/handoff 分支按缺少 terminal 收束为中断；若合法 terminal 已存在，就保留其结果。写失败和未提交不同，须由回读/barrier 确认。两种情况都不授权因为缺少界面回执而重做文件操作。

问题 2。 用户只想在 Pi 中退回 a 继续思考，点击分支后尚未追加新条目就退出。重开后的输入一定以 a 为 leaf 吗？如果要求这个选择也跨重启，该新增什么合同？

解释。 不一定；当前 branch 只改内存，重开默认由最后物理条目重建 leaf。若产品要持久保存纯导航，应新增明确的导航状态或可重放选择记录，并定义其与分支追加的一致性；这是迁移设计，不是当前已实现的功能。切换输入也不回滚旧文件效果。

问题 3。 新订阅收到快照（snapshot）后，旧订阅的一帧声称任务仍 running。应改写 terminal、复用旧序列，还是检查什么？

解释。 核对 hostEpoch、subscriptionId、sequence 与 projectionRevision；不符合当前观察流的帧不能覆盖快照。修复的是观察状态，已有 terminal 不因旧帧失效而改变。协议报错与具体 UI 怎样重连仍是两个层次。

迁移到另一种投影

问题。 同一组 Read/Edit/Bash 事实，可给 UI 形成气泡，也可给 provider 形成完整协议单元；换成摘要或原文归档引用（archive ref）时，改变的是哪一层？

解释。 改变的是消费者得到的投影，不能据此改写原始执行事实。例如 Bash 原结果有两条失败断言，摘要只保留失败数量，模型就不能仅凭摘要复述具体期望值；UI 中仍可能展示原结果。archive ref 则只是定位入口：模型要得到原文，还需在权限与范围允许时调用读取工具，并等结果进入后续输入。保存原文、提供引用、实际回读是三个步骤；它们都不自动成为长期 Memory。三种表示的取舍见 Context 方法空间。
