第 14 章｜事实（Fact）、事件（Event）与投影（Projection）

本章概览

核心问题：回答文字、界面状态（State）和持久记录不一致时，怎样判断工作已经结束，还是只缺少观察？

关键概念：事实（Fact）是负责部件接受并记录的信息；事件（Event）描述发生过程；账本（Ledger）保存一类持久事实（Durable Fact）；投影（Projection）将记录整理成特定消费者（Consumer）可用的视图。终态（Terminal State）记录执行（Run）如何结束，不等于所有资源已经清理。

关系主线：记录经过各自规则接纳与保存，读取侧再生成展示或模型输入（Model Input）。视图可以落后，保存报错也可能只是回执丢失；应沿事实（Fact）来源回查，不能凭旧画面重新执行动作。

前情回顾：身份（Identity）定位对象，记录支持判断

第13章已经把会话（Session）S1、工作轮次（Turn）T7和执行（Run）R7分开，并说明负责者（Owner）与实际写入者不是同一概念。身份（Identity）帮助定位“查哪一份”，状态（State）说明“现在怎样”；本章继续追问，哪份记录能支持这个判断，谁会读取它。

仍沿用第12章只改README的教学条件：函数已经正确，四个测试（Test）原本通过；README把入口写成 npm run check，应依据配置改为 npm test。执行（Run）包括读取、编辑、测试（Test）、差异（Diff）核对与中文总结。这里的S1/T7/R7与后面的E1–E10都不是实际日志编号；第22章的完整函数修复另有历史记录。

先固定一个断线情境：宿主（Host）仍在运行，普通工具（Tool）已经完成检查，模型（Model）也生成了回答，但客户端（Client）在收到结束通知前断开。此时尚不知道终态（Terminal State）是否已保存。这个未知条件必须通过回读（Read-back）解决，不能从“断线”二字猜答案。

核心路线

四个概念怎样组成一条判断链

投影（Projection）按用途筛选、排序和组合记录，形成可读视图面向特定消费者（Consumer），可以省略、延迟或重新构造

回到R7：记录“检查命令返回0”是一项执行事实（Execution Fact）；聊天气泡里的“检查通过”是供人阅读的表达；负责者（Owner）根据合法结束记录判断状态（State）。三者可以互相支持，却不能只凭其中一句文字替代其他条件。

有些状态（State）是负责者（Owner）的控制依据，有些是派生的展示内容。不能把所有状态（State）都说成投影（Projection），也不能把所有事件（Event）都说成持久事实（Durable Fact）。先认清对象，再选择该问题的事实（Fact）来源。

从保存到两个实际消费者（Consumer）

下图突出已接入持久存储的普通完整运行时事件（Runtime Event）。它省略了专用工具结算（Tool Settlement）和其他业务账本（Ledger），也不把每个流式片段都画成完整记录。

上半部回答是否已经确认写入，下半部回答谁读取结果。客户端（Client）可能折叠工具（Tool）细节；模型历史（Model History）则需要保留合法的工具调用（Tool Call）与工具结果（Tool Result）配对。用途不同，因此两份投影（Projection）不必逐字一致。

写入报错时，数据可能已经落账，只是回执丢失，所以分支是“尚未确认”，不是“确定不存在”。相应回读（Read-back）与提交屏障（Commit Barrier）用于消除这种不确定性；无法消除时就保留未知，不能自动重做任务。

图也不表示所有模式都有同样持久保证。第10章已经区分部分事件（Partial Event）、非终止错误（Non-Terminal Error）、已由工具协议（Tool Protocol）保存的记录与不同写入策略。这里限定经过相应持久路径接纳的事实（Fact）；其他通道与存储（Storage）条件仍要单独核对。

事实（Fact）能证明到哪里

“Bash返回退出码（Exit Code）0”说明执行器（Executor）报告了该结果，不自动证明测试（Test）覆盖全部用户要求。要得出后者，还需读取断言（Assertion）、核对实际命令、文件与任务契约（Task Contract）。如果命令只打印“passed”，输出好看也不能代替检查。

账本（Ledger）能够保留这种报告，帮助后续解释过程、重建输入、统计使用量或判断工具效果（Effect）是否可能发生。它不会因此修复不充分的测试（Test），也不会撤销已经改过的文件。

权威事实（Canonical Fact）总有负责范围

权威事实（Canonical Fact）是系统指定用于某个问题裁决的记录。若客户端（Client）仍显示 running，而R7已经有合法且持久的 completed 终态事实（Terminal Fact），应更新展示；不能让旧画面把R7重新打开。

这里回答的是执行（Run）如何结束。运行时事件（Runtime Event）不因此决定长期记忆（Long-Term Memory）应保存什么，或宿主（Host）应接纳哪项新工作。查询“中文偏好是否保存”和查询“R7是否结束”，需要不同的负责者（Owner）和记录。

为了可读性，界面可以折叠参数和长输出。用户因此少看到一些细节，不代表原工具结果（Tool Result）已被删除；是否仍可读取原文，要继续找保存位置与读取入口。

下一次模型（Model）使用的历史投影（History Projection）

下一次模型输入（Model Input）可能包含用户要求、选中的完整回答、工具调用（Tool Call）及对应结果，也可能根据可见性（Visibility）、长度和协议规则过滤或重组。显示给用户的短报告，不能直接拿来充当完整的工具协议（Tool Protocol）历史。

例如，原结果有两条失败断言（Assertion），摘要（Summary）只保留“2项失败”，模型（Model）就不能仅凭摘要（Summary）复述具体期望值。另一份界面投影（Projection）仍可能展示原文。两种表示的差异由用途解释，正确性则要看它们是否保留了各自承诺的信息。

对照一项历史真实编辑

第22章保存了完整函数与文档修复的一次真实 Edit：原始工具结果（Tool Result）与送给模型（Model）的简短修改报告不同，之后模型（Model）另用 git diff取得两文件完整差异（Diff）。这里仅沿用该历史原生宿主（Host）运行与请求捕获，桌面界面未在该例运行，本章也未重跑。

它说明三个观察对象不能合并：文件现态、工具（Tool）修改报告、模型输入（Model Input）。报告可以准确描述这次局部替换，仍不足以证明整个最终文件没有其他内容；要核对完整差异（Diff），需要额外读取。

终态（Terminal State）与完成文字

终态（Terminal State）记录这次执行（Run）已经怎样结束。合法持久终态（Terminal State）形成后，普通执行（Run）过程不能随意追加并重新裁决；这不等于所有其他类别的业务记录都停止写入。

完成、停止和迟到错误可能竞争同一结果。终态认领（Terminal Claim）协调由谁负责结束，提交屏障（Commit Barrier）确认结果已经保存；不是最早出现的一段文字或任意回调函数（Callback）天然获胜。已接纳结果不能因为旧界面或迟到信号反复改写。

核心问题解析

问题1。 客户端（Client）仍显示 running，已有合法持久 completed记录，应相信哪一个？

参考答案。 按负责该执行（Run）的终态事实（Terminal Fact）判断，再修复落后的投影（Projection）。无需为了界面重新执行任务。

问题2。 为什么最终回答不能替代全部事件（Event）？

参考答案。 回答是经过组织的内容，可能省略工具（Tool）输入、失败、原始结果与协议配对。过程解释与恢复（Recovery）仍需要相应记录。

问题3。 记忆（Memory）保存失败，应把原本合法的R7结束记录改写吗？

参考答案。 不能这样推导。各类事实（Fact）有各自裁决权（Authority）与消费者（Consumer）；需要如实报告记忆（Memory）保存问题，不能因此篡改已发生的模型（Model）与工具（Tool）过程。

一个协调器（Coordinator）维护一个明确范围的规则。用户界面（User Interface，UI）投影（Projection）不能自行批准沙箱边界（Sandbox Boundary）扩展，运行时事件（Runtime Event）也不能代替长期记忆（Long-Term Memory）的准入（Admission）策略。

运行时事件（Runtime Event）：先映射，再接纳和保存

执行后端（Agent Backend）产出会话事件（Session Event）；运行时（Runtime）补全工作身份（Work Identity）并映射其语义，交给 AgentRun 接纳。只有相应持久提交完成，恢复（Recovery）程序才能从该保存路径读回事实（Fact）。

结束原因怎样变成状态（State）

先解释分支，再读真实片段。mapCompleteStopReason把一次流结束原因映射为运行时事件（Runtime Event）的状态（State）；其中 user_stop单独映射，其他原因通过失败分类函数判断。下面摘自Maka源码（Apache-2.0），它是完整的局部函数，尚不包含先前失败的影响：

export function mapCompleteStopReason(reason: CompleteStopReason): RuntimeEventStatus {
  if (reason === 'user_stop') return 'aborted';
  return failureClassFromCompleteStopReason(reason) ? 'failed' : 'completed';
}

failureClassFromCompleteStopReason把 error归为 runtime_error，把 step_limit归为 tool_step_cap_reached；其他原因不由这个函数产生失败分类。最终保存前，同文件还有如下真实状态（State）表达式：

  const stopReason = event.stopReason;
  const status =
    memory.failureClass && stopReason !== 'user_stop'
      ? 'failed'
      : mapCompleteStopReason(stopReason);

memory.failureClass是映射过程中已经记录的失败分类，不是长期记忆（Long-Term Memory）。表达式先检查它是否存在；已有失败且不是 user_stop，即使后来收到 end_turn也保持 failed。完整结果如下：

部分事件（Partial Event）与面向模型（Model）的可见性（Visibility）

流式回答可能先显示“已”，再显示“已更”“已更新README……”。这些部分事件（Partial Event）服务即时展示，不能把每个增量当成一条完整回答反复发回模型（Model）。

重建模型历史（Model History）时还要判断：内容是否完整、是否对模型（Model）可见、工具调用（Tool Call）与结果是否配对、思考输出（Thinking Output）是否兼容当前服务、是否存在有效检查点（Checkpoint）及持久投影变换（Projection Transition）。后者记录大型结果等历史表示如何被调整，不等于改写原工具效果（Effect）。

所以，“已经保存”与“下一次全部原样发给模型（Model）”仍是两件事。保存提供材料，实际消费者（Consumer）按本次用途与规则选择。

StoredMessage：读取视图不能代替执行事实（Execution Fact）

StoredMessage是方便界面和兼容读取的消息（Message）类型。当前普通会话（Session）从运行时事件（Runtime Event）派生这份视图，并非维护另一套独立的普通执行（Run）消息（Message）真相。旧格式导入与工作协调有专用入口，本节不把它们混入普通路径。

当前普通模型历史（Model History）只从运行时事件（Runtime Event）构造。缺少相应上下文（Context）时，执行后端（Agent Backend）不会自动从 StoredMessage补历史；不支持的原生思考内容按能力过滤，只保留文本的降级表示也来自同一事实（Fact）来源。

独立回填修复（Backfill）可以在严格条件下修复部分运行时事件（Runtime Event），但它不是每次请求都能使用的聊天记录回退（Transcript Fallback）。把两者混同，会掩盖数据缺失与协议约束。

开始记录（Opening Event）与操作记录各有用途

invocation_opened记录本次模型（Model）、连接与父子关联信息（Lineage）；RuntimeInvocationRecord从相关事件（Event）重建开始和结束视图，不是另一个可任意改状态（State）的执行器（Executor）。

历史思考输出（Thinking Output）能否重放（Replay），还需核对服务路由来源（Route Provenance），不能只看旧记录里的模型（Model）名称。检查点（Checkpoint）、模型调用（Model Query）与投影变换（Projection Transition）仍有操作账本（Operational Ledger）用途；开始记录（Opening Event）改由运行时事件（Runtime Event）承载，不代表所有其他存储（Storage）都消失。

A：客户端（Client）断线，宿主（Host）仍存活，动作由普通执行器（Executor）承担断线本身不取消R7；它仍可能完成或失败合法持久终态（Terminal State）形成后发布结果，重连再读；若依赖断线的客户端能力（Client Capability），另查执行中断与效果（Effect）未知
B：已经显示最终文本，尚未确认终态（Terminal State）持久保存有回答内容，仍缺结束依据可以显示文字，不能只凭文字标完成；回查是否已有合法结束记录
C：Edit可能产生效果（Effect），结果写入前崩溃文件可能已改，普通历史可能只有调用联合工具边界日志（Tool Boundary Journal）与实际文件对账（Reconcile）；缺少成功消息（Message）不授权重做
D：终态（Terminal State）已保存，工作投影（Projection）仍显示 running事实（Fact）已结束，展示落后重建视图，不删除终态事实（Terminal Fact）去迎合旧界面

工具（Tool）结果未知、记录不可读与尚未执行不能合成一种失败。正确恢复（Recovery）有时意味着保留未知或收束中断，未必意味着继续动作。

三种坐标：执行（Run）内、会话（Session）内与观察流

时间戳可能相同，机器时钟也可能偏移；runId的字典顺序更不是执行（Run）顺序。Maka因此使用不同坐标回答不同排序问题：

表 8 / Table 8 · 三种坐标：执行（Run）内、会话（Session）内与观察流
坐标计数范围主要用途
event_seq一个 invocationId内的不可变事件（Immutable Event）顺序执行（Run）前缀、工具（Tool）边界与重放（Replay）
会话提交序号（Session Ordinal）同一会话（Session）跨执行（Run）的不可变事件（Immutable Event）提交顺序跨执行（Run）的历史投影（History Projection）

部分事件（Partial Event）的展示记录另有路径，不能强行塞进普通不可变事件（Immutable Event）的序号中。后面的34和41分别属于第二、第三种坐标，不能直接比较大小决定哪份事实（Fact）更新。

同一份回答，怎样成为中断记录

为单独观察结束判断，现在明确改变任务：R7只对用户已经提供的README差异（Diff）给出中文解释，不调用工具（Tool）。假设记录可读且合法，使用普通SQLite路径；没有续接认领（Continuation Claim）、交接（Handoff）、特殊导入、待修复工具（Tool）结算或沙箱边界（Sandbox Boundary）重启归因。下面是源码条件下的教学手算，不是实际崩溃轨迹（Trajectory）。

先说明投影（Projection）需要哪些材料：已接纳的完整事件（Event）前缀记为 LLL，仍在变化的部分展示内容记为 PPP，用途视图记为 VVV。还要给定工作身份（Work Identity）、相关裁决权（Authority）记录和读取规则。固定这些条件后，用下式简记其关系：

V=Project⁡(L,P).V = \operatorname{Project}(L, P).V=Project(L,P).

Project是教学符号，不是新增应用程序编程接口（Application Programming Interface，API）；公式没有宣称真实实现只有两个参数，也不保证资料损坏时必能成功。它只帮助区分：VVV可以出现回答文字，而LLL仍没有结束事实（Fact）。

假设S1此前已有30条不可变事件（Immutable Event），接下来按完整过程计算：

这里的数字是教学值，真实序号由相应存储事务分配。完整事件（Event）替换匹配的部分展示快照（Snapshot），不意味着先前每个字都是一条永久普通记录；开放执行（Run）的展示还可以把到达中的文字整理为可读内容，这只是读时变换。

真正读取这份结果的是谁

SessionManager.getMessages/listTurns调用 RuntimeReadModel，读取执行（Run）开始与结束结构和相关事件（Event），再构造消息（Message）与工作轮次（Turn）视图。尚未带结束记录的对象仍作为 running读取；完整回答不会自动使它完成。如果已有结束记录却无法验证为合法终态事实（Terminal Fact），读取应报错，不能把损坏内容降格成普通运行中状态（State）。

启动恢复（Recovery）先分类，再保存决定。普通缺少结束记录的路径由 classifyAgentRunRecovery给出 failed / app_restarted；若存在合法终态事实（Terminal Fact），则按它保留结果。续接认领（Continuation Claim）与交接（Handoff）由其负责者（Owner）处理，不由通用恢复（Recovery）随意制造失败。

源码还处理其他条件：读取失败或多个结束记录等损坏，严格模式报错，尽力模式可跳过；代码模式（Code Mode）欠缺工具结果（Tool Result）时先补结算，失败则暂不封印（Seal）；匹配沙箱边界（Sandbox Boundary）重启关闭记录时可调整失败分类。这些都不属于上表的纯文本手算，不能由 app_restarted覆盖全部中断。

如果保存返回异常而记录其实已经落账，相应回读（Read-back）与终态提交屏障（Commit Barrier）须先确认它。异常不直接等于未提交，更不授权重新做文件操作。恢复（Recovery）后允许接纳新工作，也不表示旧R7重新执行。

视图失效，不等于事实（Fact）被撤回

假设客户端（Client）最后看见运行中快照（Snapshot），随后宿主（Host）保存终态（Terminal State）。活跃宿主（Host）会撤销旧对话叠加层（Transcript Overlay），清理相应展示缓存，再发布更高投影修订号（Projection Revision）的权威视图。

客户端（Client）消费者（Consumer）核对 hostEpoch、subscriptionId、下一 sequence及递增的 projectionRevision。旧流或不连续序列不能直接覆盖新快照（Snapshot）；协议错误与具体界面怎样自动重连是两层问题。

S1提交序号34属于持久事件（Event）；某次订阅序号（Subscription Sequence）41属于观察流。新订阅从新的快照（Snapshot）开始，不必接着42计数。新进程也没有旧内存缓存，从事实（Fact）重建与向旧对象发送失效通知不是同一动作。

深化对照：保存探索分支，选择一条模型输入（Model Input）路径

如果用户想退回以前的思路继续尝试，同时保留旧探索记录，问题就变成输入路径选择。代码代理（Code Agent）Pi提供了一个具体例子：会话（Session）条目有 id/parentId，当前叶节点（Leaf）决定沿哪条祖先路径构造模型输入（Model Input）。它不代替Maka的终态（Terminal State）裁决。

下面仍是教学推演：a是用户问题，b/c是第一次尝试，d是后来新增条目。

原记录：a → b → c
branch(a) 后追加 d，并完成相应文件写出：
          a → b → c   旧分支仍保存
          └→ d       当前输入路径为 a → d

branch(a)本身只移动内存叶节点（Leaf）；若还没追加d就退出，重新打开文件会按最后有效条目c重建。d已保存后才形成a→d的当前路径。选择分支也不会撤销c阶段已经发生的文件效果（Effect）。

buildSessionContext按所选路径和上下文压缩（Context Compaction）边界整理消息（Message），createAgentSession再把结果赋给真正的 agent.state.messages。普通扩展（Extension）的 custom记录不进入这份消息（Message），custom_message才进入；保存扩展（Extension）状态（State）与模型（Model）实际读到仍有消费者（Consumer）边界。

写出也有具体条件。Pi的 flushed表示相应会话（Session）文件写出分支已经完成，不表示每条记录都执行文件同步（File Synchronization，fsync）。新普通会话（Session）尚无助手消息（Assistant Message）且未写出时，条目可以只在内存；首次助手消息（Assistant Message）出现后才统一写出，已存在且写出的文件另走追加分支。

读取时会跳过格式损坏的JavaScript对象表示法（JavaScript Object Notation，JSON）行，并可能为非空尾行补换行。这是该实现的容错取舍，不是事务（Transaction）、每条文件同步（File Synchronization）或任意损坏下都正确重放（Replay）的保证。若要求纯导航选择也跨重启保存，需要另外定义持久记录与追加的一致性；不能把这一建议写成Pi已有能力。

条件变化与直接答案

问题1。 流式片段都已经显示，为什么不能每条都放入下一次模型输入（Model Input）？

参考答案。 部分事件（Partial Event）可能是进行中的增量或快照（Snapshot）；逐个当成完整回答会重复内容。实际模型历史（Model History）还要检查完整性、可见性（Visibility）、协议配对及兼容条件。

问题2。 运行时事件（Runtime Event）缺失时，可以自动用 StoredMessage补回吗？开始记录（Opening Event）进入事件（Event）后，操作账本（Operational Ledger）是否就能删除？

参考答案。 两者都不能这样推导。普通模型历史（Model History）不自动采用聊天记录回退（Transcript Fallback），独立回填修复（Backfill）另有条件；检查点（Checkpoint）、物理请求尝试（Physical Attempt）与投影变换（Projection Transition）仍有相应操作记录。

问题3。 回答中写“已完成”，宿主（Host）重启前却没有终态（Terminal State），能据文字补成功吗？如果只是回执丢失呢？

参考答案。 不能据文字补成功。先区分普通开放执行（Run）、专用续接和已有合法终态（Terminal State）；上面的普通纯文本例收束为中断，已有合法结果则保留。回执丢失要先回读（Read-back），两种情形都不自动授权重做动作。

问题4。 Pi执行 branch(a)后没有追加条目就退出，重新打开时一定仍以a为当前叶节点（Leaf）吗？

参考答案。 不一定。内存导航未单独持久保存，重开按最后有效条目重建；若要求该选择也持久，就需要新增合同。输入分支选择不回滚文件效果（Effect）。

问题5。 新快照（Snapshot）之后收到旧订阅的一帧 running，应改写结束记录吗？

参考答案。 不应。检查当前宿主（Host）、订阅身份（Identity）、序号和修订号，拒绝不属于当前观察流的内容。修复的是观察，不是撤回终态事实（Terminal Fact）；具体自动重连仍要看客户端（Client）策略。

换成摘要（Summary）或归档引用（Archive Reference）

问题。 同一份 Bash原结果改成摘要（Summary）或归档引用（Archive Reference）给模型（Model），改变了哪一层？

参考答案。 改变的是消费者（Consumer）获得的投影（Projection），不能据此改写原执行事实（Execution Fact）。摘要（Summary）遗漏的细节不能凭空复述；归档引用（Archive Reference）只是定位入口，模型（Model）还须在权限（Permission）与范围允许时请求读取，并等结果进入后续输入。保存原文、提供引用、实际回读（Read-back）是三个步骤，也不自动等于长期记忆（Long-Term Memory）。
