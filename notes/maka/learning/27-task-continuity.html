第二部分：Maka 核心机制与任务接续 · 27 / 66

第 27 章｜跨会话（Cross-Session）任务（Task）推进与工作交接（Handoff）

本章概览

核心问题：一项修复跨越多次工作，下一次怎样接着推进，又不沿用过时结论或重复操作？

关键概念：任务要求（Requirements）：当前要达到的结果与范围（Scope）；进度（Progress）：已经做过和仍待处理的工作；检查观察（Observation）：绑定文件与条件的结果；交接（Handoff）：下一执行者（Executor）可读取的工作材料；当前验收（Acceptance）：按现行要求（Requirements）判断产物；阻塞（Blocked）：缺少继续所需的条件。

关系主线：保存进度（Progress）和观察（Observation） → 回读当前要求（Requirements）与文件 → 重新判断检查是否适用 → 选择允许的下一工作，最终交付已完成部分和明确的停止原因。

前情回顾：完成过什么，与现在能做什么

第20章把记忆（Memory）的写入、读取与采用分开：保存过一条信息，不保证下一次请求会看到它。第24章说明计划（Plan）保存步骤、目标（Goal）推动有条件的后续工作，但两者都不能自己扩大权限（Permission）。第25章再区分重新接上观察（Observation）与开始新的执行；第26章说明，应把检查结果绑定到具体文件和条件。

本章把这些知识用于一次接手：先找到同一任务（Task）的已保存材料，再读取今天的要求（Requirements）与产物，最后决定可以继续什么。旧交接（Handoff）提供线索，当前事实（Fact）和当前权限（Permission）决定下一步。 这也解释了为什么“请继续”需要恢复业务背景，却不能简单重播上次还没打勾的动作。

四份材料，回答四个不同问题

任务（Task）可以跨越多次会话（Session）。本例每次工作都有明确停止点；一次工作结束不等于整项委托完成。接手者需要知道目标（Goal）、产物现状和剩余工作，而不只是看到上一位执行者（Executor）写了“进行中”。

案例仍是修复 formatDuration(seconds) 和 README：对安全整数取值范围内的非负整数秒，返回 minutes:ss，余秒显示两位；README 应说明项目实际的测试入口。只允许修改 README.md 与 src/duration.js，保留用户已有及随后新增的内容，不修改测试、配置和其他项目文件。

本章将它拆成两次工作的教学案例。后面的文件变化、交接（Handoff）记录和参考程序用于说明设计，没有新增运行结果，也不是 Maka 已有的自动任务（Task）清单调度功能。

“代码已编辑”不能代替“代码正确”，“四例通过”不能代替“整项任务（Task）通过”。进度（Progress）可以保留过去完成的工作，当前验收（Acceptance）则必须面对今天的文件与要求（Requirements）。

这里有一个容易忽略的性质：历史观察（Observation）不会因为后来改了文件而被改写成“当时没通过”；当前验收（Acceptance）却可能从通过变回未满足。可靠交接（Handoff）要同时保留这两层，既不抹掉历史，也不把历史结论永久套用到现态。

第一次工作：函数修好了，README 还欠着

本例给定项目测试入口为 npm test，它调用 node --test。原函数使用 % 100，因此 60 秒得到 1:60，125 秒得到 2:25。执行者（Executor）将取余基数改为 60，保留分钟取整与补零：

export function formatDuration(seconds) {
  const minutes = Math.floor(seconds / 60);
  const remainder = seconds % 60;
  return `${minutes}:${String(remainder).padStart(2, '0')}`;
}

这段实现有三项职责：Math.floor 取完整分钟，% 60 留下不足一分钟的余秒，padStart 只负责显示宽度。令输入（Input）秒数为 sss、分钟为 mmm、余秒为 rrr，关系是：

m=⌊s60⌋,r=s−60m,0≤r<60.m=\left\lfloor\frac{s}{60}\right\rfloor,\qquad r=s-60m,\qquad 0\le r<60.m=⌊60s​⌋,r=s−60m,0≤r<60.

输入（Input）域仍是 0≤s≤253−10\le s\le 2^{53}-10≤s≤253−1 的安全整数；这不是对小数、负数或任意大整数的额外保证。四个样例是具体观察（Observation），公式分析解释一般分秒关系，二者承担不同的证据作用。

现在固定第一次工作的停止点：函数修改和测试都已结束，没有仍在执行的工具（Tool）；本次预算（Budget）已用完，README 尚未处理。以下是交接（Handoff）要使用的完整状态（State）。W1 是本章这次核对所对应的文件状态（State）标签，用来和后来状态（State）区分；它与第24章的任务图（Agent Graph）节点 W1 无关，也不是能恢复进程的快照。

一份能被下一次工作读取的交接（Handoff）

本例设置一个任务（Task）协调者（Coordinator）：它保存用户的当前要求（Requirements）、接纳工作、发布交接（Handoff），并记录是否已有执行者（Executor）在工作。模型（Model）可以提出下一步建议，协调者（Coordinator）按当前范围（Scope）与依赖（Dependency）决定是否接纳，工具（Tool）执行者（Executor）在真正产生效果前再次检查条件。

交接（Handoff）保存在协调者（Coordinator）自己的任务库（Task Store）中，不写入用户项目，因此不会突破“项目只改两个文件”的范围（Scope）。任务库（Task Store）还保留开始前的文件内容与差异基线（Baseline） B0；后续比较以此识别本次修改，并结合用户说明保留已有内容，不能把相对 Git 提交的全部差异都算作智能代理（Agent）的产出。任务标识（Task ID） 用来找到同一项委托；下面的内容均已填写。阅读记录时先看三个区域：要求（Requirements）与基线（Baseline）确定比较对象；文件状态（State）和检查说明已有证据；验收（Acceptance）、停止与下一步说明尚欠什么。它是一份业务记录，不是可执行的程序。

这份记录有三个实际消费者（Consumer）。协调者（Coordinator）使用任务标识（Task ID）、当前执行状态（State）和停止原因判断能否接纳新工作；接手的执行者（Executor）使用文件入口、观察（Observation）与未完成项重建上下文（Context）；交付判定使用当前要求（Requirements）和新检查决定能否结束整项委托。

发布也有先后：执行者（Executor）提交交接（Handoff）草稿，协调者（Coordinator）保存成功后，才把它登记为可被下一次读取的交接（Handoff）。保存失败就只能报告“工作已有这些结果，交接（Handoff）尚未确认保存”，不能声称新会话（Session）已经能读到。下一次用户请求继续时，协调者（Coordinator）主动按任务标识（Task ID） 读取它；文件仅仅存在，不会自动进入模型（Model）请求。

若任务库（Task Store）读不到交接（Handoff），接手者仍可以在允许范围（Scope）内重新调查，但应明确缺少哪些历史结果。若原工作仍在执行，则先接回该执行的观察（Observation），不能仅因换了会话（Session）就派出第二个修改者。一次任务（Task）的进度（Progress）也不宜直接写成全局记忆（Memory）：临时修复状态（State）需要随当前文件更新，不能成为其他项目长期沿用的事实（Fact）。

第二次工作：先回读，再选择下一项

以下两条接续分支都假设新一次工作已获准，并重新分配了足够的只读核对预算（Budget）；正常分支还具有编辑和复测预算（Budget）。上次“预算（Budget）已用完”描述已结束的那次工作，不会自动授予新的额度或权限（Permission）。

下一工作不是“永远执行清单里第一个没打勾的项目”。它至少要满足三项条件：对应当前尚未满足的要求（Requirements）；前置事实（Fact）已经取得；行动请求（Action）仍在当前范围（Scope）内。

正常接续：现态仍是 W1

第二次工作回读后，确认 r1 未变、函数与测试仍是 W1，配置仍声明 test。执行者（Executor）读取 README 当前全文，只将错误命令改为 npm test，保留用户段落。产生写入前，还要确认这次读取依据仍有效；若中间被别人修改，就拒绝旧补丁，重新读取后合并。

本参考方案规定，负责文件写入的一方把“核对读取版本”和“提交编辑”放在同一个受保护边界。这是额外设计条件，不是把普通 Read 后再 Edit 就称为自动防止覆盖写入（Overwrite）。

假设本次编辑已确认，重新运行现有测试仍是四例通过，并且检查一般公式、README 入口及全部项目差异均符合 r1，协调者（Coordinator）才将当前验收（Acceptance）改为完成。最终结果应列明两份文件的修改、四例检查的范围（Scope）、公式分析及无关内容保留情况；不把“检查过”缩成一个没有对象的绿色标记。

这次合理的交付是：“发现函数与文档仍不符合目标（Goal）；本次只读检查已完成；修复委托因当前不可写而阻塞（Blocked）。”原委托未完成，但本次受限工作可以有效结束。下一步需要用户改变范围（Scope）或处理依赖（Dependency），不能由“目标（Goal）还没完成”自行恢复写权限（Permission）。

参考程序怎样消费交接（Handoff）

下面是任务（Task）协调者（Coordinator）的一段教学伪代码。它不执行文件修改，而是返回下一项可交给执行层（Execution Layer）的工作。readCurrentTask 读取可信任务库（Task Store）中的现行要求（Requirements），不能用交接（Handoff）正文中的旧范围（Scope）替代。

程序分成三个阶段：先处理仍在执行或效果未知（Unknown Effect）的旧工作；再判断旧检查能否用于当前文件；最后从未满足要求（Requirements）生成候选，并按当前范围（Scope）过滤。它输出一项提案（Proposal）或一份停止说明，真正的执行层（Execution Layer）仍要重新检查前提。 下面保留完整分支，行内注释对应这三个阶段。

chooseNext(taskId):
  # 1. 先收束旧工作，避免重复派发。
  task = readCurrentTask(taskId)
  if task.hasActiveExecution:
    return ObserveExistingExecution(task.executionId)

  effects = readCurrentOperationStates(taskId)
  if effects.hasUnknown:
    if task.remainingBudget <= 0:
      return HandoffUnknown(effects, reason="缺少核对额度")
    return ReconcileOriginalEffects(effects.unknownIds)
  if task.remainingBudget <= 0:
    return HandoffPartial(reason="预算不足，尚未回读项目现态")

  # 2. 读取已发布材料，再核对今天的文件。
  handoff = readPublishedHandoff(task.handoffId)
  if handoff is missing:
    return InspectCurrentTask(reason="交接缺失，重新调查现态")

  baseline = readTaskBaseline(task.baselineId)
  now = readAllowedProjectFilesAndDiff(task, baseline)
  observations = []
  for check in handoff.checks:
    # 三个条件都成立，旧检查才参与本次判断。
    if sameRelevantFiles(check, now)
       and sameCheckConditions(check, task)
       and supportsCurrentRequirement(check, task):
      observations.add(check)
    else:
      keepAsHistory(check)

  # 3. 判断还欠什么；不足时先补证据。
  assessment = inspectCurrentRequirements(
    task, now, observations
  )
  if assessment.allSatisfied:
    return Deliver(assessment)
  if assessment.needsMoreReadOnlyEvidence:
    return Inspect(assessment.nextMissingEvidence)

  candidates = []
  if assessment.functionFailed:
    candidates.add(EditFunction)
  if assessment.readmeCommandWrong and assessment.currentScriptKnown:
    candidates.add(EditReadmeCommand)

  # 发现缺陷不等于允许编辑。
  # 用现行范围过滤候选工作。
  allowed = candidates.filter(
    work => task.currentScope.allows(work)
  )
  if allowed.isEmpty:
    return HandoffBlocked(assessment, reason="剩余工作缺少允许条件")
  # 带回判断依据，供执行层再核对。
  # 到这里仍没有写入文件。
  return Propose(
    allowed.first,
    requirement=task.revision, files=now.versions
  )

操作记录由任务库（Task Store）关联到 taskId，交接（Handoff）中的 edit-function-1 用于定位；读取的是操作的当前状态（State），而非把交接（Handoff）中的旧状态（State）直接当真。读取不到交接（Handoff）时，程序返回重新调查任务（Task）的工作；该工作同样遵守当前读取权限（Permission）和预算（Budget）。

sameRelevantFiles 比较的是该检查真正依赖（Dependency）的代码、测试、配置等对象；不是只看文件名相同。可以将检查 ccc 的复用条件写成教学判据：

Reusable⁡(c)=SameFiles⁡(c)∧SameConditions⁡(c)∧SupportsCurrentRequirement⁡(c).\operatorname{Reusable}(c)= \operatorname{SameFiles}(c) \land \operatorname{SameConditions}(c) \land \operatorname{SupportsCurrentRequirement}(c).Reusable(c)=SameFiles(c)∧SameConditions(c)∧SupportsCurrentRequirement(c).

三个谓词分别核对相关内容、检查环境与假设、当前需要证明的具体要求（Requirements）。任意一项尚不清楚，都不能直接判为可复用；这不是把正确性简化成三个字符串相等。

inspectCurrentRequirements 使用本例已经展开的规则：分钟取完整分钟、余秒取值范围与两位显示、文档入口、修改范围（Scope）。它不能把任意实现的正确性简化成几个字符串匹配；缺少有效观察（Observation）时返回“还需核对”，而不默认通过。

代入 W1，程序会得到“函数已满足、README 错、脚本已知”，于是提出文档修改。代入 W2+r2，它保留旧检查为历史（History），得到当前函数和文档问题，却找不到允许的编辑，于是返回阻塞（Blocked）交接（Handoff）。效果查询结果由协调者（Coordinator）更新到原操作记录后，再进入选择流程；旧交接（Handoff）中的未知不能替换后来已确认的结果。

选择和执行之间若又发生用户修订，执行层（Execution Layer）还必须拒绝过时提案（Proposal）。回读、核对和新工作也都消耗预算（Budget），每项实际操作还要检查剩余额度；没有查询额度时交付未知及所缺条件。这段选择代码本身不提供事务（Transaction）、权限（Permission）执行或自动调度。

未完成也有合理的停止方式

部分完成（Partial Completion）、效果未知（Unknown Effect）与阻塞（Blocked）可以同时出现在一项任务（Task）中；它们描述不同事实（Fact），不宜挤进一个含糊的 done 字段。

情况有效交付内容继续前需要什么
部分完成（Partial Completion）已取得的产物、剩余要求（Requirements）、本次停止原因新的合法工作机会和足够预算（Budget）
效果未知（Unknown Effect）原操作身份、可能影响的对象、缺少的结果先查询效果或按资源方恢复合同处理

例如 README 编辑可能已发生，却没收到回执。接手者先查原操作记录和当前 README，不能将它当作“未开始”再次执行。读取当前文本能确认当前内容，却未必证明是哪个调用写的。若当前内容已满足目标（Goal）且不存在仍会迟到执行的旧工作，可以据现态继续验收（Acceptance），同时保留调用归属仍未知的事实（Fact）；若旧执行仍可能写入，或效果无法核清，就停止新的写入并保留未知。远端下单、发信更不能靠重新调用来“补回执”。

交接（Handoff）问题与完整答案

问题：交接（Handoff）记录保存成功，为什么新会话（Session）仍可能不知道 README 没改？

保存解决数据存在。协调者（Coordinator）还须按任务标识（Task ID） 找到正确记录，把它加入新执行输入（Input）；执行者（Executor）再回读文件并使用它。若读取错误任务（Task）、只传目标（Goal）不传剩余项，或将交接（Handoff）挤出输入（Input）预算（Budget），保存成功也无法完成这条消费链。

问题：第一会话（Session）函数通过、第二会话（Session）文档通过，可以直接相加成整项通过吗？

不能只拼两个标签。要确认两项检查适用于同一份当前交付物和现行要求（Requirements）。函数被用户改过时旧结果失效；文档依赖（Dependency）的脚本若变化，旧命令判断也失效。不变且条件相同的检查可以复用，改变的部分需要重新核对。

问题：预算（Budget）到期时任务（Task）还有红项，为什么不应一律回滚？

红项描述未满足的要求（Requirements），不表示所有改动都无效。已确认、范围（Scope）内且有价值的函数修复可以保留，连同未完成README交付。只有任务（Task）明确规定失败时全量撤回，且撤回能保护用户内容和已发生效果时，才按相应合同处理；它不是通用的退出规则。

问题：旧交接（Handoff）写着“继续修改README”，用户后来请求只读，模型（Model）该听哪份？

当前用户要求（Requirements）控制本次范围（Scope）。交接（Handoff）建议是历史工作材料，不能签发权限（Permission）。模型（Model）可以指出问题和所需改动；执行层（Execution Layer）也必须拒绝仍引用旧范围（Scope）的编辑提案（Proposal）。本次只读报告可以完成，原修复委托保留阻塞（Blocked）状态（State）。
