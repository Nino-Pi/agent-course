第二部分：Maka 核心机制与任务接续 · 27 / 62

第 27 章｜跨会话任务推进与工作交接

本章概览

核心问题：一项修复跨越多次工作，下一次怎样接着推进，又不沿用过时结论或重复操作？

关键概念：任务要求：当前要达到的结果与范围；进度：已经做过和仍待处理的工作；检查观察：绑定文件与条件的结果；交接：下一执行者可读取的工作材料；当前验收：按现行要求判断产物；阻塞：缺少继续所需的条件。

关系主线：保存进度和观察 → 回读当前要求与文件 → 重新判断检查是否适用 → 选择允许的下一工作，最终交付已完成部分和明确的停止原因。

四份材料，回答四个不同问题

任务可以跨越多次会话。本例每次工作都有明确停止点；一次工作结束不等于整项委托完成。接手者需要知道目标、产物现状和剩余工作，而不只是看到上一位执行者写了“进行中”。

案例仍是修复 formatDuration(seconds) 和 README：对安全整数范围内的非负整数秒，返回 minutes:ss，余秒显示两位；README 应说明项目实际的测试入口。只允许修改 README.md 与 src/duration.js，保留用户已有及随后新增的内容，不修改测试、配置和其他项目文件。

本章将它拆成两次工作的教学案例。后面的文件变化、交接记录和参考程序用于说明设计，没有新增运行结果，也不是 Maka 已有的自动任务清单调度功能。

表 1 / Table 1 · 四份材料，回答四个不同问题

“代码已编辑”不能代替“代码正确”，“四例通过”不能代替“整项任务通过”。进度可以保留过去完成的工作，当前验收则必须面对今天的文件与要求。

第一次工作：函数修好了，README 还欠着

本例给定项目测试入口为 npm test，它调用 node --test。原函数使用 % 100，因此 60 秒得到 1:60，125 秒得到 2:25。执行者将取余基数改为 60，保留分钟取整与补零：

export function formatDuration(seconds) {
  const minutes = Math.floor(seconds / 60);
  const remainder = seconds % 60;
  return `${minutes}:${String(remainder).padStart(2, '0')}`;
}

这一公式表达 seconds = 60 × minutes + remainder，其中余秒在 0 到 59 之间。它解释了一般计算；四个样例只覆盖四个输入，不能取代这个要求。

现在固定第一次工作的停止点：函数修改和测试都已结束，没有仍在执行的工具；本次预算已用完，README 尚未处理。以下是交接要使用的完整状态。W1 是本章这次核对所对应的文件状态标签，用来和后来状态区分；它与第24章的 Graph 节点 W1 无关，也不是能恢复进程的快照。

正确的结束报告是：“函数部分已完成，README 尚未修正，任务部分完成；所有已开始工具均已结算。”不需要把代码回滚成错误版本，也不能把整项任务标成通过。预算停止的是继续工作，并没有否认已经取得的有效产物。

一份能被下一次工作读取的交接

本例设置一个任务协调者：它保存用户的当前要求、接纳工作、发布交接，并记录是否已有执行者在工作。模型可以提出下一步建议，协调者按当前范围与依赖决定是否接纳，工具执行者在真正产生效果前再次检查条件。

交接保存在协调者自己的任务库中，不写入用户项目，因此不会突破“项目只改两个文件”的范围。任务库还保留开始前的文件内容与差异基线 B0；后续比较以此识别本次修改，并结合用户说明保留已有内容，不能把相对 Git 提交的全部差异都算作 Agent 的产出。任务 ID 用来找到同一项委托；下面的内容均已填写。

这份记录有三个实际消费者。协调者使用任务 ID、当前执行状态和停止原因判断能否接纳新工作；接手的执行者使用文件入口、观察与未完成项重建上下文；交付判定使用当前要求和新检查决定能否结束整项委托。

发布也有先后：执行者提交交接草稿，协调者保存成功后，才把它登记为可被下一次读取的交接。保存失败就只能报告“工作已有这些结果，交接尚未确认保存”，不能声称新会话已经能读到。下一次用户要求继续时，协调者主动按任务 ID 读取它；文件仅仅存在，不会自动进入模型请求。

若任务库读不到交接，接手者仍可以在允许范围内重新调查，但应明确缺少哪些历史结果。若原工作仍在执行，则先观察它，不能仅因换了会话就派出第二个修改者。一次任务的进度也不宜直接写成全局 Memory：临时修复状态需要随当前文件更新，不能成为其他项目长期沿用的事实。

第二次工作：先回读，再选择下一项

以下两条接续分支都假设新一次工作已获准，并重新分配了足够的只读核对预算；正常分支还具有编辑和复测预算。上次“预算已用完”描述已结束的那次工作，不会自动授予新的额度或权限。

下一工作不是“永远执行清单里第一个没打勾的项目”。它至少要满足三项条件：对应当前尚未满足的要求；前置事实已经取得；动作仍在当前范围内。

正常接续：现态仍是 W1

第二次工作回读后，确认 r1 未变、函数与测试仍是 W1，配置仍声明 test。执行者读取 README 当前全文，只将错误命令改为 npm test，保留用户段落。产生写入前，还要确认这次读取依据仍有效；若中间被别人修改，就拒绝旧补丁，重新读取后合并。

本参考方案要求负责文件写入的一方把“核对读取版本”和“提交编辑”放在同一个受保护边界。这是额外设计条件，不是把普通 Read 后再 Edit 就称为自动防覆盖。

假设本次编辑已确认，重新运行现有测试仍是四例通过，并且检查一般公式、README 入口及全部项目差异均符合 r1，协调者才将当前验收改为完成。最终结果应列明两份文件的修改、四例检查的范围、公式分析及无关内容保留情况；不把“检查过”缩成一个没有对象的绿色标记。

这次合理的交付是：“发现函数与文档仍不符合目标；本次只读检查已完成；修复委托因当前不可写而阻塞。”原委托未完成，但本次受限工作可以有效结束。下一步需要用户改变范围或处理依赖，不能由“目标还没完成”自行恢复写权限。

参考程序怎样消费交接

下面是任务协调者的一小段伪代码。它不执行文件修改，而是返回下一项可交给执行层的工作。readCurrentTask 读取可信任务库中的现行要求，不能用交接正文中的旧范围替代。

chooseNext(taskId):
  task = readCurrentTask(taskId)
  if task.hasActiveExecution:
    return ObserveExistingExecution(task.executionId)

  effects = readCurrentOperationStates(taskId)
  if effects.hasUnknown:
    if task.remainingBudget <= 0:
      return HandoffUnknown(effects, reason="缺少核对额度")
    return ReconcileOriginalEffects(effects.unknownIds)
  if task.remainingBudget <= 0:
    return HandoffPartial(reason="预算不足，尚未回读项目现态")

  handoff = readPublishedHandoff(task.handoffId)
  if handoff is missing:
    return InspectCurrentTask(reason="交接缺失，重新调查现态")

  baseline = readTaskBaseline(task.baselineId)
  now = readAllowedProjectFilesAndDiff(task, baseline)
  observations = []
  for check in handoff.checks:
    if sameRelevantFiles(check, now)
       and sameCheckConditions(check, task)
       and supportsCurrentRequirement(check, task):
      observations.add(check)
    else:
      keepAsHistory(check)

  assessment = inspectCurrentRequirements(task, now, observations)
  if assessment.allSatisfied:
    return Deliver(assessment)
  if assessment.needsMoreReadOnlyEvidence:
    return Inspect(assessment.nextMissingEvidence)

  candidates = []
  if assessment.functionFailed:
    candidates.add(EditFunction)
  if assessment.readmeCommandWrong and assessment.currentScriptKnown:
    candidates.add(EditReadmeCommand)

  allowed = candidates.filter(work => task.currentScope.allows(work))
  if allowed.isEmpty:
    return HandoffBlocked(assessment, reason="剩余工作缺少允许条件")
  return Propose(allowed.first, requirement=task.revision, files=now.versions)

操作记录由任务库关联到 taskId，交接中的 edit-function-1 用于定位；读取的是操作的当前状态，而非把交接中的旧状态直接当真。读取不到交接时，程序返回重新调查任务的工作；该工作同样遵守当前读取权限和预算。

sameRelevantFiles 比较的是该检查真正依赖的代码、测试、配置等对象；不是只看文件名相同。inspectCurrentRequirements 使用本例已经展开的规则：分钟取完整分钟、余秒范围与两位显示、文档入口、修改范围。它不能把任意实现的正确性简化成几个字符串匹配；缺少有效观察时返回“还需核对”，而不默认通过。

代入 W1，程序会得到“函数已满足、README 错、脚本已知”，于是提出文档修改。代入 W2+r2，它保留旧检查为历史，得到当前函数和文档问题，却找不到允许的编辑，于是返回阻塞交接。效果查询结果由协调者更新到原操作记录后，再进入选择流程；旧交接中的未知不能覆盖后来已确认的结果。

选择和执行之间若又发生用户修订，执行层还必须拒绝过时提案。回读、核对和新工作也都消耗预算，每项实际动作还要检查剩余额度；没有查询额度时交付未知及所缺条件。这段选择代码本身不提供事务、权限执行或自动调度。

未完成也有合理的停止方式

部分完成、效果未知与阻塞可以同时出现在一项任务中；它们描述不同事实，不宜挤进一个含糊的 done 字段。

表 5 / Table 5 · 未完成也有合理的停止方式
情况有效交付内容继续前需要什么
部分完成（Partial completion）已取得的产物、剩余要求、本次停止原因新的合法工作机会和足够预算

例如 README 编辑可能已发生，却没收到回执。接手者先查原操作记录和当前 README，不能将它当作“未开始”再次执行。读取目标文本能确认当前内容，却未必证明是哪个调用写的。若当前内容已满足目标且不存在仍会迟到执行的旧工作，可以据现态继续验收，同时保留调用归属仍未知的事实；若旧执行仍可能写入，或效果无法核清，就停止新的写入并保留未知。远端下单、发信更不能靠重新调用来“补回执”。

交接问题与完整答案

问题：交接记录保存成功，为什么新会话仍可能不知道 README 没改？

保存解决数据存在。协调者还须按任务 ID 找到正确记录，把它加入新执行输入；执行者再回读文件并使用它。若读取错误任务、只传目标不传剩余项，或将交接挤出输入预算，保存成功也无法完成这条消费链。

问题：第一会话函数通过、第二会话文档通过，可以直接相加成整项通过吗？

不能只拼两个标签。要确认两项检查适用于同一份当前交付物和现行要求。函数被用户改过时旧结果失效；文档依赖的脚本若变化，旧命令判断也失效。不变且条件相同的检查可以复用，改变的部分需要重新核对。

问题：预算到期时任务还有红项，为什么不应一律回滚？

红项描述未满足的要求，不表示所有改动都无效。已确认、范围内且有价值的函数修复可以保留，连同未完成README交付。只有任务明确要求失败全量撤回，且撤回能保护用户内容和已发生效果时，才按相应合同处理；它不是通用的退出规则。

问题：旧交接写着“继续修改README”，用户后来要求只读，模型该听哪份？

当前用户要求控制本次范围。交接建议是历史工作材料，不能签发权限。模型可以指出问题和所需改动；执行层也必须拒绝仍引用旧范围的编辑提案。本次只读报告可以完成，原修复委托保留阻塞状态。
