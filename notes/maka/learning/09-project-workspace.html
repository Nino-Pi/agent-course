第 09 章｜代码代理（Code Agent）的项目工作环境（Project Environment）

本章概览

核心问题：代码代理（Code Agent）接手一个仓库，怎样知道可以改什么、应该读什么，以及结果能报告到哪里？

关键概念：任务范围（Task Scope）限定改动；基线（Baseline）保留开始前的状态；项目地图（Project Map）指向资料与实现；消费者（Consumer）实际读取并使用材料；验证（Verification）检查结果是否满足要求。

关系主线：先确定范围与比较起点，再根据问题读取资料、运行检查。通过同一个修复案例，区分文件存在、进入模型输入（Model Input）和真正影响后续行为。

前情回顾：从职责地图进入一个具体仓库

第08章把运行支撑（Agent Harness）的职责放回共同代理循环（Agent Loop）：组织输入、安排执行、保留记录并判断下一步。其中有一条贯穿本章的关系——材料保存在哪里，与哪位消费者（Consumer）实际使用它，是两个问题。 仓库里有规则或测试文件，不代表本次已经读到，也不代表相应检查已经执行。

本章继续第04章的两个问题：README 把测试入口（Test Entry）写成 npm run check，实际入口是 npm test；formatDuration(seconds) 的余秒（Remaining Seconds）错误地使用 % 100，应按60秒一个周期计算。输入仍限定为非负安全整数秒，结果为 minutes:ss。原有四个测试（Test）使用0、9、60、125秒；这里不把它们扩大成全部输入的运行证明。

现在增加一个条件：README 还有用户已经写好的说明，必须保留。这让“找到了修复方法”进一步变成“怎样在当前仓库中安全实施局部修改”。新增资料和用户段落都是本章教学设定，与原固定示例项目（Fixture）的实际运行范围分开。

任务范围（Task Scope）先决定允许做什么

代码代理（Code Agent）的项目工作环境（Project Environment）包括仓库文件、执行所需程序，以及把内容与结果送入模型输入（Model Input）的工具（Tool）。交给它一个目录，只说明工作地点；开始操作之前，还要明确目标、允许修改的对象和必须保留的内容。

本例允许修改 README.md 与 src/duration.js，不允许升级依赖、改变测试（Test）期望值或重写其他功能。发现额外问题不自动扩大任务范围（Task Scope）。若要求缩成只改 README，即使已经识别 % 100 的缺陷，也应记录未修问题，不能继续改函数。

保留用户内容也需要具体落到当前文件。下面是新增的教学片段，不来自原回放产物：

# Duration Demo

本项目用于课堂讲解时间格式化；请保留这段项目说明。

## 测试

测试命令：npm run check

已明确需要保留的是第二段项目说明。本次只替换最后一行中的入口，其他内容留在原位。这个例子说明为什么应读取当前内容再局部修改：用自己生成的完整 README 覆盖文件，即使入口写对，也可能丢掉已有工作。

差异（Diff）能显示内容变化，不能单独证明是谁写的。用户内容的归属来自已知说明；工作区（Workspace）存在未提交改动，也不意味着它们属于本次产出。要分清三个比较对象：

表 1 / Table 1 · 任务范围（Task Scope）先决定允许做什么
比较对象回答的问题本例中的含义
开始前的当前内容接手时已经有什么？错误入口与需要保留的说明段都已经存在
开始与结束之间的差异（Diff）本次改变了什么？README 的入口和函数里的取余周期
相对已有Git提交的差异（Diff）当前内容与版本记录相差什么？还可能包含接手前已有的用户改动

项目规则可以说明约定，却不会自行增加用户没有给出的权限（Permission）。任务范围（Task Scope）、已有内容与执行权限（Permission）共同约束本次动作，不能由其中一项替代另外两项。

运行前的基线（Baseline）：先分清环境、入口与失败

基线（Baseline）是开始修改前可用于比较的状态与检查结果。它不要求所有测试（Test）都通过：修复往往从失败开始。真正需要知道的是，程序能否启动、入口是否存在、执行了哪些断言（Assertion），以及哪些文件变化已经存在。

同样是非零退出码（Exit Code），失败所在的位置不同，后续行动请求（Action）也会不同：

表 2 / Table 2 · 运行前的基线（Baseline）：先分清环境、入口与失败
开始前看到什么当前能确认什么接下来怎样处理
找不到 node 或 npm运行环境（Runtime Environment）缺少前提，测试（Test）尚未开始说明具体缺项；安装仍需满足任务范围（Task Scope）和执行权限（Permission）
npm run check 报 Missing script: "check"所指定脚本名不存在读取 package.json，找到真正的测试入口（Test Entry）
npm test 执行四例，两例失败环境与入口可用，部分行为不符合断言（Assertion）沿失败输入、导入关系与被测函数定位
退出码（Exit Code）为0，却没有运行任何用例命令正常结束，但没有覆盖目标行为查测试（Test）发现规则与路径，不能直接报告通过验收

本仓库的 scripts.test 为 node --test，所以 npm test 启动 Node.js 的测试（Test）程序。README 只是说明文字，真正决定启动什么的是脚本配置。原来两例失败、修复后四例通过，才构成有明确起点的行为比较。

若另外出现无关失败，应记录它在修改前是否已存在，并判断是否阻断当前验证（Verification）。不能为了得到全绿摘要，顺手改变未授权的功能。基线（Baseline）的价值是保留比较条件，让我们知道新结果相对什么发生了变化。

项目地图（Project Map）：每份材料分别回答什么问题

现在为小仓库增加一层教学资料。AGENTS.md、docs/architecture.md 和 tasks/duration-fix.md 都是本章扩展，原固定示例项目（Fixture）没有这些文件；它们也不是所有项目必须采用的目录标准。

duration-demo/
├── README.md                 使用方式与常用命令
├── AGENTS.md                 智能代理（Agent）的项目工作约定（新增）
├── package.json              实际脚本和依赖配置
├── docs/architecture.md      文件职责与调用关系（新增）
├── tasks/duration-fix.md     本次问题和完成条件（新增）
├── src/duration.js           被测函数
└── test/duration.test.js     输入与期望输出

README 面向使用者，解释用途与启动方法。AGENTS.md 面向在仓库里工作的智能代理（Agent），适合放稳定而简短的工作区指令（Workspace Instructions）：保留已有改动，使用实际测试入口（Test Entry），环境缺失时说明原因。架构资料帮助缩小搜索范围，本次工作说明给出目标与完成条件；配置和源码才提供实际执行定义。

本例的架构资料只需说明，测试（Test）导入 src/duration.js，函数没有网络或数据库依赖。这样便能优先查计算逻辑，省去无关部署资料。但项目地图（Project Map）可能过时：若说明中的路径与实际 import 不同，应继续核对当前导入关系，不能让旧说明代替正在执行的模块。

一份有用的工作说明可以很短：

修正 README 的测试入口及 formatDuration 的余秒计算。
保留 README 已有说明，不修改测试文件与依赖。
比较修改前后的既有测试，并确认本次差异只涉及两个目标文件。

这三句分别给出目标、任务范围（Task Scope）和可观察的完成条件。只写“结果必须正确”，还没有告诉消费者（Consumer）从哪里取得足以检查这句话的材料。

持续保留与按需读取（On-Demand Reading）

工作上下文（Working Context）是当前判断实际可用的材料。本例适合持续保留“只修两个问题、保留用户段落、不改测试”这些简短约束，再围绕当前问题进行按需读取（On-Demand Reading）：查入口时读配置，查失败时读断言（Assertion），查计算时读函数。

这里的“持续保留”只描述本次连续判断所需的信息，不等于长期记忆（Long-Term Memory），也不保证文件改变后自动刷新。完整架构资料与全部历史日志不必反复进入每次模型输入（Model Input）；需要保留的是足以指导下一步的内容及可靠的读取入口。

下图区分项目地图（Project Map）的指引与实际内容的进入。只有文件名或目录树，还不能把正文当作已经取得的观察结果（Observation）。

mini 的 DefaultAgent 将任务（Task）和模板（Template）组成初始消息（Message），随后把执行结果整理为观察消息（Observation Message）。这段循环本身不负责自动发现全部 AGENTS.md。工作区指令（Workspace Instructions）可以由入口明确加入模板（Template），也可以通过读取取得，具体方式取决于实际接线。

OpenAI Codex的本地智能代理（Agent）实现提供另一种读取路径：沿项目根到工作目录（Working Directory）寻找适用文件，受信任状态、文件选择与大小预算（Budget）约束，再将加载结果用于上下文（Context）。这条路径还使用缓存（Cache），不在每一步重新读取磁盘。因此“默认读取规则”也是具体实现与配置的行为，不能推广到所有代码代理（Code Agent）。第15章展开输入组成，第37章解释按问题定位代码。

规则文字怎样连接真正运行的检查？

AGENTS.md 写“结束前运行测试（Test）”，是在告诉模型（Model）应该选择什么行动请求（Action）。它不会自行启动程序，也不会仅凭这句话阻止越界写入或错误交付。

在mini的正常路径中，模型（Model）提出命令，LocalEnvironment 启动进程（Process），取得执行输出（Output）与退出码（Exit Code），再由主循环将结果加入消息列表（Message List）。如果使用预写响应的固定回放，后续行动请求（Action）来自脚本，不能称为模型（Model）根据失败自主改了计划。

下图画的是“提出检查—执行—解释结果”的关系。提出请求的一方可以是模型（Model），也可以是本例的固定计划；结果分支表示诊断时应检查什么，不宣称固定计划会自动改写自身。

若要提供“缺少检查就不接受交付”的程序保证，还需有消费者（Consumer）真正读取结果，执行接纳判断。原修复回放脚本在智能代理（Agent）结束后检查返回码、两例失败到四例通过的变化、退出状态（Exit Status）与改动文件范围。任何条件不符，脚本抛错，拒绝将回放记为通过。

这项验收不会撤销已经写入的文件，也不阻止智能代理（Agent）先自行发出提交信号（Submission Signal）。它针对已知小场景，不是所有mini任务（Task）自带的通用完成门。即使完全匹配测试（Test）摘要，也不能代替完整需求检查。

第04章的反例仍然适用：只特判60、125秒，也能让四例通过，却可能把61秒写成 1:61。因此验证（Verification）还应查看一般计算与适用条件，不能只统计绿色用例。工作区指令（Workspace Instructions）指导动作，结果接纳检查决定能否认可交付，执行权限（Permission）与隔离（Isolation）限制资源访问，它们各有实际负责者（Owner）。

完整接手案例：从输入到交付

下面将各项关系放回同一仓库。命令错误、两例失败及修复后四例通过，复用第04章固定回放的已有结果；新增资料、用户说明段与接手顺序属于教学扩展，整段没有作为新增产品场景运行。

1. 明确输入与比较起点

用户要求修正文档入口和余秒（Remaining Seconds）计算，只允许改 README.md 与 src/duration.js，并保留已有说明。运行环境（Runtime Environment）已经具备Node.js和npm，不需要下载依赖。本教学入口把 AGENTS.md 的短规则与用户要求加入初始消息（Message），其他资料通过后续读取取得；这是本例明确选择的装载方式。

先确认需要保留的段落，记录开始前内容与差异（Diff），建立基线（Baseline）。随后读 README 与 package.json：前者指向 npm run check，后者只定义 test。结合原回放的 Missing script，下一步应改用实际测试入口（Test Entry），而不是反复重试不存在的脚本。

2. 用失败输入定位需要改变的计算

原回放中，npm test 执行四个测试（Test），两例通过、两例失败。测试（Test）导入 src/duration.js；60秒得到 1:60，125秒得到 2:25。源码中分钟按60取整，余秒（Remaining Seconds）却按100取余。

用125秒连接现象与计算：完整分钟数为2，每分钟60秒，剩余秒数应为

r=125−2×60=5 秒.r=125-2\times60=5\text{ 秒}.r=125−2×60=5 秒.

这里的 rrr 是余秒（Remaining Seconds），不是总秒数；最终显示为 2:05。这沿用第04章的一般关系，只帮助解释为何应改 % 100，没有新增运行测试（Test）。

3. 局部修改，并保留原有内容

README 只替换测试入口（Test Entry）；函数只把 % 100 改为 % 60。测试（Test）期望值、依赖与其他功能保持原样。本章教学片段相应成为：

# Duration Demo

本项目用于课堂讲解时间格式化；请保留这段项目说明。

## 测试

测试命令：npm test

前后对照可以直接看到说明段仍在。AGENTS.md 不负责写这两个文件，写入仍由实际工具（Tool）或命令完成。若执行前内容已变化，还要依据最新文件重新决定是否需要替换。

4. 比较行为结果与本次差异（Diff）

在上述教学条件下，预期复测对应原回放的四例通过、零失败；范围检查则应确认本次只改入口与余秒（Remaining Seconds）计算，没有覆盖说明或改动测试（Test）。原回放没有新增用户段落，因此“段落保留”是本节前后文本展示出的教学结果，不能作为旧实验已经检查的断言（Assertion）。

交付说明据此写为：“两个目标问题已修正，四个既有断言（Assertion）通过，本次改动限于两个目标文件。”这句话是给定条件下的教学答案；实际执行时，只能报告本次取得的观察结果（Observation）。相对Git提交的差异（Diff）还可能包含用户原有改动，不能全部算作本次产出；四例通过也不等于逐一检查全部合法输入。

这些分支共享同一推理：任务范围（Task Scope）决定允许做什么，当前文件决定还需要改什么，实际执行决定能报告什么。项目工作环境（Project Environment）把这三项接到可读取、可执行、可核查的对象上。

接手工作问答

问题1。 仓库已经有 AGENTS.md，是否说明当前模型输入（Model Input）包含其全文？

参考答案。 不能。还要查读取入口、适用条件、预算（Budget）与缓存（Cache），以及结果是否实际交给消费者（Consumer）。文件存在只说明材料可供查找。

问题2。 开始前测试（Test）失败，是否应先把所有失败修掉再建立基线（Baseline）？

参考答案。 不应这样做。失败本身就是比较起点；先区分运行环境（Runtime Environment）、入口与行为问题，再判断哪些属于任务范围（Task Scope）。否则容易丢掉原始失败，或改变未授权功能。

问题3。 为什么要同时看测试（Test）和差异（Diff）？

参考答案。 前者给出具体输入上的行为结果，后者帮助检查一般计算、授权与原有内容保留。只看其中一项，都可能错过不符合要求的补丁。
