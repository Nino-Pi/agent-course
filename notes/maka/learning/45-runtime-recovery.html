第 45 章｜运行时恢复（Runtime Recovery）与宿主交接（Host Handoff）

本章概览

核心问题：进程退出后，系统凭什么判断能否继续，又怎样把工作交给后继？

关键概念：持久前缀（Durable Prefix）是已提交的事件序列；恢复计划（Resume Plan）对这些事实分类；就绪（Ready）、提交决定（Commit）与封存确认（Sealed）分别表示到达边界、接受交接（Handoff）和保存交接（Handoff）事实。

关系主线：重新读取事实后，消费者（Consumer）才能构造恢复计划（Resume Plan）或接续执行（Run）。本章沿已有本地实验辨认每个环节的结果，保留模型替身（Fixture Backend）、失败位置与尚未覆盖的保证。

前情回顾：保存、重建与重新执行不是同一件事

第18章解释了效果（Effect）与回执（Receipt）之间的空窗：文件可能已经改变，但调用者没有取得结果。第25章进一步把宿主（Host）的负责者（Owner）、状态根（State Root）和客户端连接分开。于是，进程消失之后，不能只根据“没有回复”重做工作，也不能只根据“同一个目录”取得写入资格。

第44章区分检查点（Checkpoint）、重放（Replay）和实际消费者（Consumer）。本章把这个关系落到 Maka 的本地存储与交接（Handoff）测试：先重新读取已保存的运行时事件（Runtime Event），再判断哪些内容可用于重建；若要继续工作，还须满足新的执行（Run）准入条件。重建输入（Input）不会恢复旧模型调用（Model Query）的调用栈。

先认清本章沿用的实验初态：模型（Model）由模型替身（Fixture Backend）提供可控响应，运行时（Runtime）、SQLite 存储和宿主组装（Host Composition）使用实际本地组件。部分测试终止真实子进程，其他测试重开测试夹具（Fixture）或调用恢复入口。它们没有产生真实远端工具（Tool）效果（Effect），也没有让真实模型（Model）选择恢复动作。

1. 三个恢复问题，各自需要什么事实？

一份事件账本（Event Ledger）可以回答“已经保存了什么”，却不能直接回答“现在谁可以继续”。把三个问题分开后，后面的测试名称才有具体含义。

表 1 / Table 1 · 1. 三个恢复问题，各自需要什么事实？
问题输入（Input）与消费者（Consumer）得到的结果尚不能推出
保存了哪些事实？新存储实例读取持久前缀（Durable Prefix）已提交的运行时事件（Runtime Event）序列记录中的命令真的在本实验执行过
哪些事实适合重建？恢复投影（Projection）读取该前缀（Prefix）恢复计划（Resume Plan）、工具（Tool）分类及可重放内容可以无条件重新执行工具（Tool）
哪个执行（Run）能接着做？宿主（Host）核对负责者（Owner）、交接（Handoff）事实和组装条件获准启动的后继（Successor）同一任务已经成功或所有外部效果（Effect）都恰好一次

测试使用与所说明实现匹配的编译产物，实际调用本地存储和进程。既有结果只覆盖这些本机场景；其他平台、完整桌面应用（Desktop）以及远端机器需要各自验证。

取得状态根（State Root）使用资格还依赖本地控制资源。外层执行环境（Environment）若先阻止所需文件访问或本地连接，测试可能在进入恢复断言前返回 lock_failed。这说明环境准入尚未完成，不能据此判断后面的恢复逻辑；同样，越过环境门槛也不保证业务断言通过。

2. 持久前缀（Durable Prefix）：先看真实提交了什么

名为 reopens every fully committed P0-P11 ledger prefix after SIGKILL 的测试，检查十二个失败点标签对应的已提交前缀（Prefix）。它没有连续执行十二次真实 Bash 效果（Effect）。父进程先选一段预制运行时事件（Runtime Event），让子进程逐项提交；子进程输出 READY 后，父进程才用 SIGKILL 终止它。

下面保留测试的数据链。ledgerEvents 构造预制内容，committedPrefix 决定保留到哪里，buildResumePlanFromRuntimeEvents 消费重开的事件，而不是执行其中的命令：

ledgerEvents → 按 committedPrefix 截取事件
→ 子进程 appendRuntimeEvent 逐项提交
→ READY → 父进程 SIGKILL
→ 新 store 重开 → readRuntimeEvents
→ buildResumePlanFromRuntimeEvents

runCrashChild 是写入者，crashWriterAfterCommit 等待提交边界并终止子进程，assertResumePlanForPrefix 检查恢复分类。实际断言逐层收紧结论：

  1. 子进程的 finally 标记不存在，说明这次结束没有执行该清理分支。
  2. 新存储实例读到的事件标识（Event ID）与已提交前缀（Prefix）相同。
  3. 同一输入（Input）重复投影（Projection）得到相同恢复计划（Resume Plan）。
  4. 投影（Projection）后再读账本（Ledger），原始事件（Event）没有被分类过程改写。

四层合在一起支持“已提交前缀（Prefix）可以重新取得，并被确定性分类”。它们没有覆盖任意文件写入空窗，也不保证重复执行命令没有影响。预制内容中的 touch marker 只是一个工具调用（Tool Call）的参数，本测试没有执行它。

P4 与 P5：一个响应为什么改变可判定事实

本例预制序列依次含用户消息（User Message）、工具调用（Tool Call）、工具响应（Tool Response）与终止事件（Terminal Event）。P4/P5 是其中两种前缀（Prefix）选择：

表 2 / Table 2 · P4 与 P5：一个响应为什么改变可判定事实
前缀（Prefix）真正保存的事件标识（Event ID）恢复计划（Resume Plan）与重放（Replay）
P4：after_function_calluser, callblocked；工具（Tool）为 indeterminate，拒绝原因为 dangling_tool_state；只保留 user 供重放（Replay）
P5：after_function_responseuser, call, responsesafe_replay；预制成功响应使工具（Tool）分类为 succeeded，三项进入重放（Replay）

P4 的失败点说明写着“效果（Effect）已完成、结果事务 T2 之前”。这里的 T2 指结果提交边界；这只是失败点的命名背景，测试仍只提交两项预制事件（Event），没有制造那次外部写入。不能由标签反推实验实际执行了什么。

P5 多出的响应使这份输入（Input）能够区分“调用悬而未决”和“已有成功响应”。safe_replay 说的是已有事件（Event）适合重建，不是重新执行一次命令解释器（Shell）命令的许可。若真实世界里回执（Receipt）丢失，还需沿第18章的效果（Effect）查询与恢复合同处理。

3. 就绪（Ready）、提交决定（Commit）与封存确认（Sealed）

交接（Handoff）比重新读取账本多了一项责任：源执行（Run）与后继（Successor）必须对“工作在什么边界接续”达成可检查的约定。测试让模型替身（Fixture Backend）停在可交接（Handoff）边界，真实存储保存运行时（Runtime）事实。

表 3 / Table 3 · 3. 就绪（Ready）、提交决定（Commit）与封存确认（Sealed）
接口结果表示什么一个仍可能发生的反例
requestRunHandoff 所返请求的 ready就绪（Ready）：源执行（Run）到达候选边界后续组装前提缺失，提交仍可能被拒绝
commit() 返回 true提交决定（Commit）：交接（Handoff）请求被接受后面的交接（Handoff）记录写入失败
sealed 兑现为 true封存确认（Sealed）：交接（Handoff）事实已持久保存后继（Successor）的组装检查仍可能失败

因此三个结果不能折叠成一个“成功”布尔值。正常分支保存 runtime_handoff_pause_v1 和剩余步数；源物理执行（Physical Invocation）的终止事件（Terminal Event）不把逻辑任务标为成功。后继执行（Successor Run）使用新的执行身份（Run Identity），沿同一逻辑工作轮次（Logical Turn）继续。

这份运行时（Runtime）测试把剩余步数设为 2，后继（Successor）收到的 maxSteps 也必须是2。它不是预算（Budget）重置；模型（Model）、工具目录（Tool Catalog）、可用性（Availability）、提供方选项（Provider Options）、上下文窗口（Context Window）等组装条件也要通过相应检查。仅版本描述修订变化和真正影响内容的变化在测试中分别判断，不能只比一个版本号。

真实失败注入片段：接受请求以后，保存仍可能失败

先看这段包装器的框架。runtimeEventStore 是本测试的实际运行时事件（Runtime Event）存储；先保存原方法 append，新方法只拦截带 handoffPause 的事件（Event），其他输入（Input）继续交给原方法。下面是测试中的完整包装片段，注释解释拦截范围：

const append = runtimeEventStore.appendRuntimeEvent.bind(runtimeEventStore);
runtimeEventStore.appendRuntimeEvent = async (sessionId, runId, event, options) => {
  // 只让交接暂停（Handoff Pause）的持久写入失败。
  if (event.actions?.handoffPause) throw new Error('pause durability failed');
  // 其他事件（Event）仍调用原存储方法。
  return append(sessionId, runId, event, options);
};

随后测试接受提交决定（Commit），放开模型替身（Fixture Backend）的等待，再分别观察 running 与 request.sealed。前者是消费当前执行（Run）的异步结果，后者是封存确认（Sealed）；两者都被断言为拒绝，错误包含写入失败。片段依赖上述测试上下文，不是可直接粘贴执行的独立产品程序；本章没有新增一次故障运行。

图只展开正常保存和本节写入失败两条路径。取消（Cancellation）和停止（Stop）有各自断言：本测试的取消（Cancellation）分支让源执行（Run）正常结束，停止（Stop）分支将其记为 aborted；两者的 sealed 都为 false，都不带交接（Handoff）暂停记录。不能从一条正常箭头推导所有结束方式，也不能把某层的状态（State）枚举套给全系统。

宿主组装（Host Composition）：关闭存储，再由后继接手

宿主（Host）组装测试向外再走一层：使用产品组装路径（Production Composition）封存、拆离，关闭存储并释放旧负责者（Owner），然后由新负责者（Owner）重开同一状态根（State Root）。模型（Model）依旧是模型替身（Fixture Backend），所以这是本机组装与接续的测试。

这份测试有自己的预算（Budget）初态：源执行（Run）的步数上限为 4，到边界时剩 3，后继（Successor）收到3。重开后可读到两个物理执行（Physical Invocation），它们属于同一工作轮次（Turn）：一个携带交接（Handoff）暂停，一个得到完成结果。这里的4→3不能与上一份运行时（Runtime）测试的剩余2步混为同一场景。

它没有包含跨机器对等节点（Peer）换路、真实模型（Model）流或完整桌面应用（Desktop）生命周期；后继（Successor）能够启动也不证明任意外部效果（Effect）可以重做。

4. 域状态（Domain State）与工作准入（Admission）

目标（Goal）或定时任务（Scheduled Task）存在，只说明某类工作有记录。是否允许进入根工作轮次（Root Turn），仍由相应权威（Authority）判断；恢复（Recovery）还要区分旧记录已结算，还是新一次触发尚待处理。

表 4 / Table 4 · 4. 域状态（Domain State）与工作准入（Admission）
场景本题保存的输入（Input）恢复（Recovery）后的具体结果
目标（Goal）已获准入（Admission），尚无执行（Run）已持久保存的准入记录，带目标身份（Goal Identity）prepareRecovery 建立相应开始事实，结果为 failed、失败类别为 app_restarted；开始事实与用户消息（User Message）的来源仍是该目标（Goal），根状态（State）回到 idle，不直接重放请求
目标（Goal）与定时任务（Scheduled Task）竞争定时任务（Scheduled Task）已占据待准入位置，但持久准入尚未完成目标（Goal）的接续申请得到 busy；原工作释放后再按统一根权威（Root Authority）准入，不能抢先执行
旧触发（Fire）已结算，又出现新触发（Fire）存储保留旧触发（Fire）和更新的待处理触发（Pending Fire），各自绑定执行身份（Execution Identity）已记录执行与要求待处理触发（Pending Fire）的两种恢复准入（Recovery Admission）分别核对；身份（Identity）或指纹不匹配会拒绝，不能把旧新两次混同
绑定连接（Connection）被替换保存的是精确连接身份（Connection Identity），现有同名连接不匹配实际执行入口拒绝继续，本测试没有创建会话（Session）或准入执行（Run）；仅同名不足以沿用授权

最后一行也不表示任何配置操作都会失败：所选测试允许相关创建和更新请求保存配置，真正触发执行时才拒绝不匹配的连接（Connection）。需要判断哪个消费者（Consumer）进行了检查，不能把“失败关闭”扩大为所有入口的同一行为。

这里的重启多为重开测试夹具（Fixture）或调用恢复入口，不等于杀掉完整桌面应用（Desktop）。表中各行也不是同一任务依次经过的四个步骤，而是两份测试文件中的不同场景。

5. 从真实失败的位置读结论

一个实际用例名为 WorkHub correction replaces its link without stopping a shared manual Turn。工作中心（WorkHub）协调中的更正（Correction）只是名称指向的目标；原运行实际报错为 false !== true，停在更正（Correction）之前的 delegated.ok。

判断顺序很重要：先建立源会话（Session）中的手工工作，再取得候选，提交委派（Delegation）并检查结果；通过后才有条件继续检查关联和更正（Correction）。本次失败没有越过委派（Delegation）前置断言，所以不能仅凭名称声称“更正错误停止了用户工作”。

表 5 / Table 5 · 5. 从真实失败的位置读结论
观察到的证据支持的判断不能替它补出的结论
整组在 delegated.ok 得到 false本次委派（Delegation）前置条件未通过更正（Correction）已经执行并出错
同环境单独重跑通过改变运行组合后，该单例通过原整组问题已解决
原断言没有输出具体错误码尚不能解释委派（Delegation）为什么失败根因必然是竞争条件（Race Condition）

候选状态（State）可能随时序变化，是值得核查的解释；它仍是假设。缺少当时的错误码，不能把单例绿色结果补成根因分析。完整结论应同时保留“整组前置断言失败、单例通过、原错误码缺失、根因未确定”。

提交决定（Commit）已接受，为什么还不能安全交给后继（Successor）？

参考答案：完整失败链是模型替身（Fixture Backend）让执行（Run）到边界，运行时（Runtime）接受提交决定（Commit），存储写 handoffPause 时抛错，最终 running 与 sealed 都拒绝。就绪（Ready）更弱，只说明到达候选边界。持久确认缺席时，不能把交接（Handoff）事实当成已经保存。

P4/P5 能否证明支付的恰好一次（Exactly Once）？

参考答案：不能。它们只提交预制事件（Event），没有远端支付、支付幂等键（Idempotency Key）或接收方查询。P5 可重放（Replay）已有响应，也不是重新支付的许可。对真实外部效果（Effect），还要确认对应系统的执行与恢复合同。

新负责者（Owner）接手同一状态根（State Root），是否仍是同一次执行（Run）？

参考答案：所选交接（Handoff）测试通过新执行身份（Run Identity）继续同一逻辑工作轮次（Logical Turn），并保留剩余预算（Budget）与来源。身份（Identity）关系要从保存的交接（Handoff）事实读取，不能由“看起来还是同一聊天窗口”推断。

单例通过是否抹去了整组失败？

参考答案：没有。两种运行条件的结果都要保留，未取得的错误码也仍然缺失。模型替身（Fixture Backend）覆盖的是控制与存储合同，不证明真实模型会选择正确恢复动作；跨机器对等节点（Peer）换路和完整桌面应用（Desktop）也仍在本章实验范围之外。
