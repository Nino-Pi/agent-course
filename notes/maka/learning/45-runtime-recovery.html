第 45 章｜运行时恢复与 Host 交接

本章概览

核心问题：Maka 的已有恢复实验，分别证明了持久前缀、Host 交接与任务准入的哪些行为？

关键概念：持久前缀：崩溃前已提交的事件；恢复计划：由记录推导的接续分类；Ready（就绪）：到达候选交接边界；Commit（提交决定）：接受交接请求；Sealed（封存确认）：交接事实已持久保存；Fixture backend（模型替身）：代替模型提供可控响应。

关系主线：重开存储后读取事实，再构造恢复计划或接续执行；就绪、提交和封存逐层增强可确认的状态，局部通过不能抹去整组失败。

前置机制是 第18章 的未知效果与 第25章 的 Host 所有权。

实验直接调用 Maka 的 Runtime、SQLite 和 Host composition；模型由 fixture backend 替代，便于观察运行与持久化规则。部分测试会终止真实子进程，另一些通过重开 fixture 模拟恢复；不要因为名字含 recovery 就认定它一定杀了进程。这组实验不产生真实远端工具效果。

1. 案例范围与环境边界

测试使用与所说明实现匹配的编译产物，调用真实本地存储与进程；结果只覆盖这组本地场景，不能推广为其他平台或完整 Desktop 的保证。

取得状态根使用资格还依赖本地控制资源。如果外层执行环境先阻止相关文件访问或本地连接，测试可能在进入恢复断言前就以 lock_failed 失败。它说明环境准入尚未完成，不能据此判断后面的恢复逻辑。

2. 持久前缀与恢复计划

runtime-resume-crash.test.ts 的 reopens every fully committed P0-P11 ledger prefix after SIGKILL 并不是连续操纵十二次真实 Bash 效果。父进程为每个失败点选择一段预制 RuntimeEvent 前缀，启动子进程逐项提交；等子进程输出 READY 后再发送 SIGKILL。

测试的数据链是：

ledgerEvents → 按 committedPrefix 截取事件
→ 子进程 appendRuntimeEvent 逐项提交
→ READY → 父进程 SIGKILL
→ 新 store 重开 → readRuntimeEvents
→ buildResumePlanFromRuntimeEvents

实际断言有四层：子进程的 finally 标记不存在；重开的事件 ID 与已提交前缀一致；同一输入重复投影得到相同恢复计划；投影之后再次读账本，原始事实没有变化。这支持“已提交前缀可以恢复并确定性分类”，不支持“任意写文件窗口都不会重复”。预制事件里出现 touch marker 只是事件内容，本测试没有执行那个 Shell 命令。

测试中的 runCrashChild 负责提交，crashWriterAfterCommit 等待 READY 后杀进程，assertResumePlanForPrefix 检查恢复分类。P4/P5 给出一个具体对照：

表 1 / Table 1 · 2. 持久前缀与恢复计划
前缀（Prefix）真正保存的事件 ID恢复计划与重放（Recovery · Replay）
P4：after_function_calluser, callblocked；工具为 indeterminate，拒绝原因 dangling_tool_state；可重放事件只保留 user
P5：after_function_responseuser, call, responsesafe_replay；该预制成功 response 使工具分类为 succeeded，三项进入重放

P4 的边界名描述“效果完成、T2 之前”，但本测试仍只提交预制的两项事件，不执行其中的 touch marker。P5 多出的 response 改变了可判定事实；safe_replay 指已有事件可安全用于重建，不是重新执行一次 Shell 的许可。

3. 交接准备、提交与持久确认

交接测试用 fixture backend 让 Run 停在可交接边界，真实 store 保存 Runtime 事实。requestRunHandoff 返回的 ready 表示已到边界；commit() 决定进入提交路径；sealed 等待持久结果。三者不能合并成一个 success 布尔值。

正常分支保存 runtime_handoff_pause_v1 与剩余步数；源 invocation 的 terminal 不表示逻辑任务成功。后继 Run 沿同一 logical Turn 继续，模型、工具、可用性、上下文窗口等 composition 必须通过相应一致性检查。

失败分支中，测试把实际 store 的 appendRuntimeEvent 包装成只在写入 handoffPause 时抛错：

下图把正常保存和注入写入失败并列展示；仅展开本节这两条路径，取消与停止仍按各自测试判断。commit 是提交决定，sealed 才给出持久封存的结果。

这证明“commit 返回 true”还不是“交接记录已落盘”。cancel 与 stop 分支另有断言，不能从成功分支推导它们。

Host 组装测试再向外走一层，使用 production composition 关闭存储、释放 owner 并让 successor 重开。它覆盖本机组装和接续，尚未包含跨机器 Peer 换路或真实模型流。

4. 域状态与工作准入

两份测试分别检查以下场景：

表 2 / Table 2 · 4. 域状态与工作准入
场景输入与检查点（Input · Checkpoint）要解释的行为
Goal 已有 admission、还没有 Run写入 durable admission 后调用 prepareRecovery；检查 opening、failed/app_restarted、user origin 和 root idle恢复会收口孤立 admission，不凭 Goal 存在就重放工作

这里的重启多数是重开 fixture 或调用恢复入口，不等于杀掉完整 Desktop。

5. 实际运行结果与失败位置

看一个实际诊断例子：WorkHub correction replaces its link without stopping a shared manual Turn 曾报 false !== true。名字提到了 correction，但失败的断言是 correction 之前的 delegated.ok。因此不能仅凭标题断言“更正错误停止了用户工作”：执行还没到那个检查点。

该用例在整组运行时失败，单独重跑却通过。这可以提示我们检查时序和共享条件，但不能据此宣布根因就是竞态。缺少当时的错误码，就还无法解释为何委派没有成功。诊断应保留原失败，记录实际分支与输入，再一次只改变一个条件缩小范围。

单例通过是否表示问题已解决？ 不能。这里的完整结论是“整组在委派前置断言失败，单例重跑通过，原始委派错误码缺失，根因未确定”。两种运行条件的结果都保留，单例通过不能抹去整组失败。

6. 完整结果与保证范围

这次已有运行的结果如下，合计 83 tests：82 pass、1 fail、0 skip。

表 3 / Table 3 · 6. 完整结果与保证范围
运行组结果（Result）解释范围
Runtime resume + handoff17 pass，0 fail，0 skip已提交前缀、交接成功/取消/持久写入失败等选定合同
Host composition + WorkHub52 pass，1 fail，0 skip本地 owner 与存储接手、组装及 authority；整组未通过
Goal root authority + Schedule recovery13 pass，0 fail，0 skip准入、身份绑定与恢复收口

一条完整的失败链是：fixture Run 到达边界 → Runtime 接受 commit → store 写 handoffPause 时被注入失败 → running 与 sealed 都拒绝。输入、执行 owner、持久写入和最终观察在这里闭合，因此能明确反驳“commit 已接受就能安全交给 successor”。仅有 ready 更弱，它只说明源 Run 到达候选边界。

P4/P5 则说明持久前缀决定恢复分类，但没有调用远端支付、没有提交支付幂等键，也没有查询接收方，所以不能证明支付 exactly-once。整组记录使用 fixture 模型，亦不能证明真实模型会正确选择恢复动作；跨机器 Peer 换路与完整 Desktop 生命周期不在这组运行范围内。
