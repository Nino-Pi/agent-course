第 57 章｜选择 Skills 与子 Agent

本章概览

核心问题：复用项目方法、独立调查和并行修改，分别应该增加哪一种能力？

关键概念：Skill（技能说明）：供当前 Agent 使用的方法；子 Agent：有独立身份与生命周期的执行者；委派合同：明确输入、权限与交付；Worktree（工作副本）：分隔文件修改；采纳：父任务检查并合入产物。

关系主线：方法装载改变当前输入，委派另起执行，文件隔离另有合同；子任务结束后仍需定位产物、检查基线和冲突、完成采纳与复测，不能因父文件未变就重做子任务。

前置：第23章、第50章、第52章。

1. 原题与约束

一个任务既要遵守项目规范，又需要独立检查，还可能让两个 Agent 同时改代码。你会怎么设计？

“独立”可以指判断、上下文（Context）、权限（Permissions）或文件隔离（Workspace Isolation），四者不是同一状态。角色扮演提示只改变模型输入，不会自动创建可单独停止和查询的执行者。

本题父任务负责修复，子任务先只读核对配置与 README；如果升级为并行代码修改，要给子任务明确文件边界和产物验收方式。

2. 参考方案

我会先把方法复用和执行委派分开。固定检查步骤适合做成可发现、按需加载的 Skill，加载正文后仍由当前 Agent 使用原有工具执行。需要独立上下文、独立结果或可以并行交付的工作才创建子 Agent。委派时固定目标、输入、权限和输出合同，给它独立身份、生命周期和停止入口。只读检查可以共享同一工作区；并行修改则还要考虑文件隔离，例如独立 worktree。子任务完成只代表交付了结果，父任务仍要核对来源、采纳修改、运行验证。失败时区分执行失败、产物发布失败和父任务未采纳，不能因为父任务没收到消息就重新执行整个修改。最后用单 Agent、并行工具和子 Agent 三种方案比较总成本与交付质量。

3. 第一张图：两种增强方式

父任务可以复用方法，也可以交出独立工作。Skill 的发现信息、正文装入和实际遵循是三步；子任务的创建、完成、被父任务采纳也是三步。

本图为职责教学图。各产品 Skill 能否配置子上下文和工具预批准，要看产品合同，不能把教学上的“方法内容”推成所有产品均相同的权限行为。

4. 第二张图：修改如何交回

传输/存储与文件工作区承担不同责任。终态、产物可读、父区应用、验收通过是四个不同里程碑。

5. 最小委派合同

教学结构，非 Maka Task API：

delegation = {
    "objective": "核对测试脚本与 README 描述是否一致",
    "inputs": ["package.json", "README.md"],
    "allowed_effects": "read_only",  # 还必须落实到执行边界
    "context": {"mode": "selected", "required_constraints": ["不改文件"]},
    "workspace": {"mode": "shared_read_only"},
    "result_contract": ["发现", "原文位置", "建议", "未核对范围"],
    "limits": {"deadline": task_deadline, "max_children": 0}
}

输入要自足，不能只说“你知道刚才的事”。上下文采用选定材料还是完整继承都可以，但必须明确成本、遗漏风险和权限过滤；不同产品和模式可能不同。

修改型任务把 workspace.mode 改为隔离副本还不够：必须约定它从什么基线开始，如何标识父区已变化，返回 patch、文件还是提交引用，以及父任务怎样处理冲突。这些由真实资源与 Git 工作流保证，不靠字段名字自动实现。

6. 正常与失败走读

正常：父任务加载文档规范；子任务只读检查返回 npm run check 不存在、真实入口是 npm test，附配置位置；父任务重新核对当前 README 后修改并测试。

过期观察：父任务在子任务检查期间已改过 README，子任务返回旧文本。该结果能说明观察时状态，不能直接作为现在的编辑基线；父任务应重新读当前文件。

产物发布失败：子任务修改和局部测试完成，但产物引用无法读取。状态应保留“执行完成、交付未确认”，尝试恢复交付或查询工作副本；不能先把子任务重新跑一遍。

取消竞争：父任务发出停止时，子任务可能已写文件或已提交结果。取消要求停止后续工作与回收资源，但不自动回滚既有修改。保留已发生效果和最终结算，再决定是否采纳。

7. 递进追问

两个 Agent 同时改一个文件，用两个 worktree 就不会冲突了吗？

隔离了执行期间的工作文件，不保证合并结果正确。父任务仍需处理冲突、语义冲突和集成测试。两个补丁都能单独通过测试，也可能组合后失败。

子任务拿到了父任务全部工具，是否更方便？

可能减少缺能力问题，也扩大效果范围。根据目标给最小足够能力，并由执行器落实上限；工具名出现在 prompt 不等于限制已执行。上下文共享也不能代替权限授权。

为什么不用并行工具？

两个独立 Read 通常不需要新增 Agent。子 Agent 适合独立多步探索、单独评估或避免大量中间信息进入父输入；收益要扣除新上下文、调度、等待与交接成本。

子任务返回“没问题”可以直接信吗？

先看检查范围、来源位置、命令与输出。父任务对最终结果负责，不能把子任务文本当超出证据的保证。若任务要求独立验证，要避免子任务只复述父任务结论。

8. 取舍与验证

表 1 / Table 1 · 8. 取舍与验证
方案适合的问题应测代价
技能与单 Agent（Skill）方法稳定，工作紧密相关是否实际加载并遵循、额外输入
并行工具（Parallel Tools）独立短调用失败传播、结果关联、延迟
子 Agent（Subagent）可独立完成的多步任务交付质量、父任务整合成本
子 Agent 与工作副本（Subagent · Worktree）并行修改需隔离冲突处理、产物可读性、集成验证

四类代表场景是：并行只读、重叠修改、发布中断、父取消与子完成竞争。记录每个身份、有效范围、产物状态和最终采纳结果。整体耗时要包括父任务等待和整合，不能只比较子任务各自运行时间。

9. 子任务完成但父任务尚未采纳

设 child c7 基于父工作区 v10 创建隔离副本，完成局部修改和测试，保存 completed 终态与产物引用 p7；父工作区已被用户改为 v11。此时能够确认的是 c7 的执行结果，不能确认父区已经包含补丁。

父任务首先读取 p7。若引用不可用，保留“child 已完成、产物暂不可读”，恢复交付或查询原副本；不新建一个 child 重做。若产物可读，则比较 v10 基线、p7 补丁与当前 v11，保留用户变化后决定是否能合并。存在冲突时停止自动应用，给出具体冲突；不能把旧 patch 直接覆盖当前文件。

补丁应用成功只是第三个状态，之后还需要父工作区上的集成测试与 diff 检查。child 局部测试通过无法证明合并结果正确。最终交付分别说明 child 终态、产物读取、父区应用和集成验证四项结果。
