第 57 章｜选择技能说明包（Skill）与子代理（Subagent）

本章概览

核心问题：遵守项目方法、独立调查和并行修改，需要增加哪一种能力，结果又怎样进入最终交付？

关键概念：技能说明包（Skill）向当前执行（Run）提供方法；子代理（Subagent）承担有独立身份的工作；委派合同（Delegation Contract）固定输入、许可和交付；工作树（Worktree）分隔工作文件；采纳（Adoption）把子产物（Artifact）纳入父任务（Parent Task）。

关系主线：先选择方法加载或独立委派（Delegation），再落实文件和权限边界（Permission Boundary）。子任务（Subtask）终态（Terminal State）、产物（Artifact）可读、父区应用与集成验证（Integration Verification）分别提供证据，任何一步都不能替代后续步骤。

前情回顾：方法、执行（Run）与效果（Effect）分别由谁负责

第23章区分了三件事：发现技能说明包（Skill）的名字，只提供选择线索；加载正文，才让方法进入本次或后续模型输入（Model Input）；子代理（Subagent）则形成有独立身份与生命周期的执行（Run）。把角色写进提示词（Prompt），不会自动建立后一种工作对象。

第50章说明，模型（Model）提供行动请求（Action）的参数，可信执行上下文（Execution Context）提供工作区（Workspace）、权限边界（Permission Boundary）与调用身份（Call Identity）。因此，子任务（Subtask）知道父任务（Parent Task）的全部聊天内容，也不意味着它获得了父任务（Parent Task）的全部许可。

第52章把效果（Effect）与回执（Receipt）分开：文件可能已经写入，结果却尚未交回。本章把这个区别延伸到协作（Collaboration）：子任务（Subtask）确实完成了修改，也可能仍缺可读取的产物（Artifact）；产物（Artifact）已经可读，又可能尚未被父任务（Parent Task）采纳（Adoption）。

下面先用只读检查说明怎样委派，再改变条件，完整追踪一份隔离修改如何进入父工作区（Parent Workspace）。两条路径的授权（Authorization）与交付条件会分别交代。

1. 原题：先固定任务（Task），再解释“独立”

同一任务（Task）要遵守项目规范、获得独立检查，还可能让两个智能代理（Agent）同时改代码，应该怎样安排？

先固定一个小项目。package.json 中的测试入口是 "test": "node --test"，没有 check 脚本；README 却写着 Run npm run check.。本题父任务（Parent Task）已获准修正文档、运行相关检查并报告结果。初始子任务（Subtask）只读取配置与 README，回答两者是否一致，不能修改文件，也不能再创建子任务（Subtask）。这些是教学输入与参考过程，本章没有实际启动模型（Model）、子代理（Subagent）或测试进程。

“独立”至少有四种含义。决定是否新增子代理（Subagent）前，应先指出缺少的是哪一种。

四行可以分别选择。两个短文件的独立读取，可能只需并行工具（Parallel Tools）；需要多步调查、单独停止或单独交付时，子代理（Subagent）的独立工作身份才有直接价值。

如果任务（Task）明确要求独立复核，还要避免只把父任务（Parent Task）的结论交给检查者让它复述。应提供原始材料、待检查问题与允许范围，让检查者说明依据；结论一致本身不能证明两个判断相互独立。

2. 参考方案：先补方法，再补工作身份（Work Identity）

固定而可复用的项目检查步骤，可以保存为技能说明包（Skill）。父任务（Parent Task）发现它、加载正文，并把需要的步骤选入模型输入（Model Input），随后仍使用当前执行（Run）的工具（Tool）开展工作。真正增加的是方法材料，以及消费这些材料的机会。

当检查需要独立多步探索、独立结果或独立停止入口时，再创建子代理（Subagent）。委派（Delegation）必须给出目标、输入（Input）、权限（Permission）、期限和交付要求；宿主（Host）建立可查询的身份（Identity），执行器（Executor）落实允许的操作。子任务（Subtask）返回的是一项限定工作所产生的证据，不自动代替父任务（Parent Task）的最终判断。

只读路径可以使用同一工作区（Workspace）。如果后来允许子任务（Subtask）修改代码，先调整该任务的明确授权（Authorization），再选择文件隔离（Workspace Isolation）和交付方式。工作树（Worktree）是准备独立工作文件的一种方式；工作副本（Working Copy）是这里更一般的文件隔离对象。两者都不能代替权限（Permission）检查或采纳（Adoption）规则。

3. 方法加载与独立委派（Delegation）的分流图

上支路回到同一个父任务（Parent Task），表示方法材料改变了当前输入。必须分别检查发现（Discovery）、加载（Loading）与遵循（Following）：目录里有名字，不证明正文已读；正文已进入输入，也不证明下一次行动请求（Action）遵守了其中的检查步骤。

下支路增加独立工作身份（Work Identity）。宿主（Host）消费委派合同（Delegation Contract）后建立子任务（Subtask），结果带回身份（Identity）与来源（Provenance），父任务（Parent Task）据此决定下一步。箭头从结果到父任务（Parent Task），没有直接跳到“整项修复已完成”。

这是职责教学图。不同产品的技能说明包（Skill）还可能支持子上下文（Subcontext）或工具（Tool）预批准（Preapproval）配置，须分别看其产品合同。不能由本图的“方法内容”外推出所有产品具有相同的加载时点与权限（Permission）行为。

5. 最小委派合同（Delegation Contract）如何被消费

回到第 1 节的只读路径。下面是教学数据结构，非 Maka 任务（Task）应用编程接口（Application Programming Interface，API），也不直接启动子代理（Subagent）。

先按三组读字段：objective 与 inputs 固定要检查什么；allowed_effects、context 与 workspace 规定给什么材料、允许什么操作；result_contract 与 limits 规定怎样交回和何时停止。task_deadline 是可信父任务（Parent Task）给定的绝对截止时刻，本例子任务（Subtask）继承这一时刻，不因晚启动而重新计算一整段期限。

delegation = {
    # 目标与原始材料：足够独立核对，不只传父结论。
    "objective": "核对测试脚本与 README 描述是否一致",
    "inputs": ["package.json", "README.md"],
    # 操作范围还须由真实执行入口落实。
    "allowed_effects": "read_only",
    "context": {"mode": "selected", "required_constraints": ["不改文件"]},
    "workspace": {"mode": "shared_read_only"},
    # 交付证据、继承期限，以及禁止再创建子任务。
    "result_contract": ["发现", "原文位置", "建议", "未核对范围"],
    "limits": {"deadline": task_deadline, "max_children": 0}
}

task_deadline 不是一个由模型（Model）任意填大的参数。设父任务（Parent Task）截止时刻为 dpd_pdp​，子任务（Subtask）的截止时刻为 dcd_cdc​，当前时刻为 ttt，本题接纳新工作的必要期限条件为：

t<dc≤dp.t<d_c\leq d_p.t<dc​≤dp​.

本例继承期限，因此 dc=dpd_c=d_pdc​=dp​；若额外收窄子任务（Subtask）期限，只能令它更早。公式只表达期限，不能代替当前授权（Authorization）、剩余预算（Budget）和取消（Cancellation）检查。到期阻止后续工作时，已经开始的操作仍要结算实际结果或未知效果（Unknown Effect）。

输入（Input）必须自足，不能只说“你知道刚才的事”。selected 表示选定材料；完整继承也可以成为另一种设计，但应明确新增输入成本、可能遗漏的约束与信息披露范围。子任务（Subtask）的上下文（Context）选择，与工具权限（Tool Permission）检查是两条连接。

max_children=0 表达不允许继续委派（Delegation）。只有创建入口实际检查它，才能阻止额外子任务（Subtask）；同样，read_only 只有被执行器（Executor）消费，才构成实际限制。把这些词写进提示词（Prompt）或字典不会自动提供保证。

修改型子任务（Subtask）还需要另一份合同：从哪份基线（Baseline）开始，父区变化如何识别，返回补丁（Patch）、文件还是提交引用（Commit Reference），以及父任务（Parent Task）怎样检查和应用。只把 workspace.mode 改成隔离副本，不会自动实现这些步骤。

7. 递进追问与参考答案

两个智能代理（Agent）同时改一个文件，用两个工作树（Worktree）就不会冲突了吗？

工作文件在各自执行期间分开，最终修改仍要进入同一个目标。父任务（Parent Task）需要处理文本冲突、语义冲突与集成测试（Integration Test）。例如一份补丁（Patch）改了测试入口，另一份改了依赖安装方式，两者各自在自己的条件下通过，也可能组合后无法执行。隔离（Isolation）减少即时覆盖，采纳（Adoption）负责组合后的正确性。

子任务（Subtask）获得父任务（Parent Task）全部工具（Tool），是否更方便？

它可能减少能力缺口，同时扩大效果（Effect）范围。本题核对两个文件只需读取，不需要编辑、网络购买或继续委派（Delegation）。按目标给足够能力，并由执行器（Executor）落实上限；工具名出现在提示词（Prompt）中不等于限制已经执行。共享上下文（Context）不能代替授权（Authorization）。

为什么不用并行工具（Parallel Tools）？

两个独立读取（Read）通常不需要新增智能代理（Agent）。子代理（Subagent）适合独立多步探索、单独评价或避免大量中间信息进入父模型输入（Model Input）。其收益要扣除输入组装（Input Composition）、调度（Scheduling）、等待与交接成本；创建得更多并不自动更快。

子任务（Subtask）返回“没问题”，可以直接相信吗？

先看检查范围、来源位置、命令与输出。父任务（Parent Task）承担最终验收（Acceptance），不能把子任务（Subtask）的文本当作超过证据范围的保证。若要求独立检查，还要确认检查者依据原始材料形成判断，而不是仅复述父结论。

四类代表条件是并行只读、重叠修改、发布中断、父取消（Cancellation）与子完成竞争。比较时固定目标、允许范围和最终验收（Acceptance）要求，分别保留工作身份（Work Identity）、有效范围、产物（Artifact）状态和采纳（Adoption）结果。

9. 子任务（Subtask）完成，父区仍停在另一份状态

最后沿第 4 节的可写分支走完一次交付。子任务（Subtask）c7 从父工作区（Parent Workspace）的基线（Baseline）v10 创建隔离副本，完成授权范围内的局部修改和检查，保存 completed 终态（Terminal State）与产物（Artifact）引用 p7。用户随后修改父区，形成当前标记 v11。

这里 v10、v11 是本题区分两份工作区基线（Baseline）的标记，不声明所有文件存在一个原子提交（Atomic Commit）版本。p7 要保留它基于 v10 形成的修改与来源，供逐项比较；不能只交回一句“已经修复”。

5. 验证当前组合已采纳（Adoption）文件与所需测试（Test）在父工作区（Parent Workspace）进行集成验证（Integration Verification）及差异（Diff）检查，保留失败或未运行项
6. 完整交付前五步的实际记录分别说明子终态（Terminal State）、产物（Artifact）读取、父区应用和集成验证（Integration Verification）

即使第 4 步应用成功，第 5 步仍可能发现两个原本可用的修改组合后失败。此时可以确认“补丁（Patch）已采纳（Adoption）”，却不能确认“整项任务（Task）已经成功”。反过来，产物（Artifact）不可读也不抹去已经保存的子终态（Terminal State），更不证明子修改从未发生。

真实实现还可能限制哪些补丁（Patch）可以恢复。例如第23章所述 Maka 工作树（Worktree）交回路径围绕最新已终结子执行（Run）补发，并校验产物（Artifact）归属；这不承诺任意历史副本都能重建。可恢复范围应由实际资源和保存记录决定。

相关机制：第23章技能说明包（Skill）与子代理（Subagent）、第50章工具合同（Tool Contract）、第52章权限（Permission）与恢复（Recovery）。
