第 38 章｜Codex：上下文与压缩

本章概览

核心问题：Codex 窗口不足时，摘要压缩和直接换窗分别保留什么，后续工作怎样继续？

关键概念：活跃历史：下一请求的消息基础；local compaction（客户端摘要）：组织模型总结；远程压缩：接收并组合服务输出；TokenBudget（窗口预算分支）：直接安装新窗口；rollout（过程记录）：支持历史重建的持久材料。

关系主线：配置与模型服务方条件选择路线，替换历史并保存窗口记录；移出输入的细节是否可取回仍有条件，压缩成功不证明约束与任务状态完整。

所属主题：第36章 上下文与 Memory；同题对照：Claude Code 上下文。

贯穿案例设定为一项持续很久的修复任务：检查器读过大量文档、产生多轮测试输出，用户最近补充了“不要修改 README”。现在剩余窗口不足，但修复还没验收。我们的目标是让任务继续，同时不误用过时约束、不重复已经完成的写入。

本章的恢复接口与验收表是教学设计；它们帮助判断实现质量，不表示所有分支已经满足这些要求。

1. 把四种容易混淆的信息分开

想象书桌、档案柜和索引。书桌上放的是当前要处理的材料；档案柜保存过去记录；索引帮助找到相关文件。这三个位置都可能含有同一件事，但它们的读取成本和丢失后果不同。

表 1 / Table 1 · 1. 把四种容易混淆的信息分开
信息层作用例子与压缩的关系
当前模型历史（Model history）形成下一次采样的主要输入最近动作、结果、用户约束、摘要或压缩项会被替换或缩减
宿主持有的保留状态表达不随模型窗口任意丢弃的事实与上下文基线已记录的保留上下文、宿主提供的环境状态表示（world state）基线随新窗口建立适当表示
Rollout 与相关持久记录保存可用于重建的过程事实响应项、压缩 checkpoint、上下文元数据压缩会增加可用于重建的记录
后续可读取资料（Retrievable resources）必要时再取回较长细节历史项、任务笔记、长期记忆材料决定被移出窗口的信息是否仍可用

本地上下文管理组件 ContextManager 还分别维护历史版本（history version）与用户消息修订（user-message revision）。前者可随历史重写变化；后者表示用户输入或重置方面的变化。因此，窗口换了，不一定表示用户又提出了新要求。 如果把一次压缩算成新用户任务，会影响依赖、重放边界和恢复判断。

同样，rollout 的存在并不等于每次模型请求都带着完整 rollout。若一边声称已压缩，一边仍把所有原始工具输出重新塞入 prompt，窗口问题根本没有被解决。

2. 先决定选路，再讨论压缩算法

手动压缩与自动压缩在本地都有选路。TokenBudget 功能开关是优先分支；没有走它时，模型服务方（provider）的 V2 能力选择流式远程压缩，Unsupported 选择客户端摘要工作流。下面的 replacement history 指将被安装为活跃输入基础的替换历史；三条路线构造它的方式不同。

图顶端按运行条件分流。具体任务采用哪条路径，取决于宿主、配置、模型与 provider。

自动触发也不是“token 多就随时打断一切”。主循环会结合是否仍需继续、预算状态以及是否请求新窗口来判断。工具结果、后续采样和输入队列有顺序关系，窗口处理必须嵌入这个生命周期，不能当成一个后台线程任意改写历史。

3. 路径一：客户端组织摘要，什么被留下

这里的 local compaction 指由客户端组织摘要工作流，仍然会调用模型。它不是“离线压缩”，也不是普通字符串截断。

沿正常路径走一遍：

  1. 复制当前 history，并加入用于摘要的输入。
  2. 构造摘要请求，让模型产生可继续工作的摘要。
  3. 从原历史中收集用户消息；已有摘要消息不当成新的真实用户要求重复收集。
  4. 在预算内组合保留的用户消息与新摘要。
  5. 根据手动或中途压缩的场景，处理初始上下文的补回位置与基线。
  6. 安装 replacement history，并记录窗口变化与压缩结果。

这里有两个需要深入理解的选择。第一，用户消息单独参与构造，表示“用户要求”不应该完全依赖一次自由摘要重写。但它仍受到预算约束，所以不能据此声称所有历史用户要求逐字永存。第二，初始上下文有自己的重新注入机制，不能只指望摘要模型记住所有环境与规则。

对于贯穿案例，理想摘要至少应保留：目标是修复带空格路径；最新约束是不改 README；哪些文件已经修改；哪些测试已经运行；当前失败和下一步验证是什么。大段重复日志可以移出窗口，但测试命令和关键失败位置应可找回。

“摘要写得很顺”没有证明这些任务信息保留正确。最危险的摘要往往流畅而过度肯定：把“准备运行测试”改写成“测试已通过”，或者把早期的“更新 README”保留下来，却漏掉最新的禁止修改。

4. 路径二：远程压缩也要解释保留结构

一次远程压缩尝试（attempt）从该步骤的工具路由组件 ToolRouter 取得工具表面，把压缩触发项加入请求。即使后续配置已刷新，这次压缩也需要解释它实际捕获的视图。

远程 v2 通过模型客户端的流式请求收集压缩输出，再与需要保留的消息组合。保留消息有 token 和图像方面的预算，metadata 也需要跟随适当的消息保留。它不是“服务返回什么就整段替换，客户端不再负责结构”。

设计问题为什么不能只说“远程会处理”
最新用户约束保留在哪服务输出与保留消息需要正确组合
图像是否占用保留预算大图也可能让 replacement 超出预期

provider 与 feature 分流决定请求和安装合同，因此不能用一个 compact API 概括所有路径。

5. 路径三：TokenBudget 换窗不强制生成摘要

本地 TokenBudget 压缩入口仍然经过 compact hooks，也产生 ContextCompaction 生命周期项，但其核心动作是开启新窗口。该函数不发起模型或服务器摘要请求，而是调用新窗口安装逻辑。

新窗口建立时会推进窗口身份，构建初始上下文与 world state，并在相应 feature 打开时保留经过预算限制的客户端 developer 消息。随后安装这些 context items，记录窗口和基线，并重算 token 使用。这和“用户消息加摘要”不是同一个 replacement 形状。

为什么敢把大部分旧窗口移走？这条设计将连续性问题的一部分交给窗口外的信息与按需恢复，而不要求每次窗口转换都预先生成一份包罗万象的摘要。本地还存在按条件装配的 history/notes 扩展，客户端提供历史查询和任务笔记读写，并向上下文加入有界提示。

这里的扩展是有条件装配的客户端能力。客户端配置、工具合同与请求封装不能证明服务端的索引、存储、删除和竞争处理方式；也不能推广成每个 Codex 用户都具有同一能力。

图中旧窗口没有把完整内容直接传入新窗口。窗口外可取回，不等于当前已经取回。系统接下来能否继续正确行动，取决于它知道缺少什么、能否检索到正确材料、是否把有用结果放进请求。

TokenBudget 换窗不等于这组恢复能力必定可用。工具不可用、查询失败或没有取回关键约束时，应重新获取可靠材料或报告缺口，不能仅因存在可选扩展就宣称连续性已经保证。

这条路线的取舍很具体：换窗减少一次强制全历史摘要的成本；同时把部分成本推迟到后续恢复，并承担选错查询、遗漏旧约束、索引延迟等风险。任务笔记写得好也不能免除验证；写得太泛，会变成另一份无法指导行动的长摘要。

6. Token 预算不仅是一个百分比

本地 token budget 配置可以来自用户设置或模型提供的默认值，并经过验证与 feature 条件处理。它包含提醒阈值、提醒模板、fallback 提示等。运行时会根据剩余基本窗口预算，在适当条件下记录提醒；是否已经发过提醒或 fallback 由状态中的 claim 处理，避免每一步重复注入。

这体现了一种渐进处理：在资源用尽前提醒模型整理可继续的信息；到了必须换窗的点，由 host 执行转换。提醒是引导，host 的窗口管理是运行边界。不要因为模型收到“即将换窗”的文字，就认为它必然完成了正确整理。

用教学数字举例：如果当前还有 8,000 token，并不意味着可以再读取 8,000 token 日志。还要为模型输出、工具返回、系统上下文和恢复余量保留空间。具体额度随模型与配置变化。

7. 安装与持久记录：先更新了哪里，崩溃会影响什么

replace_compacted_history 的职责超出赋值。它会补齐响应项身份，准备压缩记录，协调设置持久化，更新内存中的活跃历史与保留上下文，再保存压缩、world state、上下文和相关设置事件。

表 3 / Table 3 · 7. 安装与持久记录：先更新了哪里，崩溃会影响什么
状态（State）在压缩中的作用对恢复结果的要求
替换历史（Replacement history）下次模型主要输入的基础是否包含继续任务所需信息
参考上下文（Reference context）判断下次补完整上下文还是增量变化压缩后是否仍有有效基线
环境状态基线（World state baseline）表达新窗口环境状态是否遗漏已变化的工具或环境
窗口身份（Window identity）区分前后上下文窗口历史查询能否定位正确窗口
过程记录检查点与尾部（Rollout checkpoint / Tail）支撑之后的历史重建是否与幸存的工作片段一致

本地重建代码会选择幸存的 replacement checkpoint 和对应尾部，再正向重放；rollback 还会影响哪些用户 Turn 与元数据应保留。不能只寻找“最后一条摘要字符串”就完成恢复。

内存更新与后续持久化调用不自动构成跨存储事务；中途崩溃可能留下不同步的状态。例如 replacement 已进入活跃内存、对应记录尚未落盘时，当前进程与重启进程可用的历史不同。恢复结论必须依据幸存 checkpoint 与尾部重建，不能由某个文件存在推断四类状态都一致。这是故障点推演，不是本章新增的崩溃运行结果。

8. 压缩失败与质量退化的不同结果

Local 摘要请求本身也可能超窗。客户端摘要实现会在输入还可减少时移除最旧项后重试；无法继续减少则报错。普通连接错误有重试限制，取消和预算错误又有不同处理。

这说明技术成功率和任务保真度是两条轴：请求终于成功了，但被移掉的最旧项可能包含关键约束；摘要长度符合上限，也可能把“未验证”写成“已验证”。另一边，摘要内容正确，却可能因 provider 响应或持久化问题无法安装。

贯穿案例的参考验收合同如下：

type ContinuationCheck = {
  latestConstraint: "do_not_edit_readme";
  modifiedFiles: string[];
  verifiedTests: string[];
  unverifiedClaims: string[];
  nextAction: string;
};

// 教学算法：比较换窗前后的后续决策，而非只比较摘要字数。
async function checkContinuation(before: Scenario, after: ModelInput) {
  assertLatestConstraint(after, before.latestConstraint);
  assertNoInventedTestSuccess(after, before.observedTestResults);
  assertCanLocateNeededDetails(after, before.requiredArtifacts);
  return evaluateNextAction(after, before.acceptanceCriteria);
}

本例给定的恢复状态为：最新约束是“不改 README”；scan.py 已修改；测试已经运行但仍失败；尚未证明修复通过。可用下列对象表达参考结果，字段与路径是教学设定：

const expected: ContinuationCheck = {
  latestConstraint: "do_not_edit_readme",
  modifiedFiles: ["scan.py"],
  verifiedTests: [], // 此字段只列已观察到通过的测试；本例没有。
  unverifiedClaims: ["带空格路径已修好"],
  nextAction: "回读失败断言和当前实现，确定原因后在许可范围内继续",
};

若换窗后的输入声称“测试通过”，它与给定失败观察冲突；若重新安排修改 README，它违反最新范围；若只缺日志详情，但能通过正确引用回读，仍可继续定位。这里给出的是参考判定，没有生成一次模型的实测得分。

这里 assertCanLocateNeededDetails 不要求把所有原文保留在 prompt。它要求需要时能可靠找到正确细节；对检索恢复路线，这一点和摘要保真同等重要。所有比较还要固定任务输入与验证标准，否则减少了 token 却改了任务难度，结论没有可比性。

9. 常见场景与参考结论

题一：Codex 的 compaction 一定生成摘要吗？

参考答案：不是所有压缩路径都如此。Local 与远程路径处理摘要或压缩输出；TokenBudget 分支的 compact 动作直接安装新上下文窗口，不在该函数里请求摘要。实际采用哪条要看配置和 provider。

题二：为什么换窗后“历史仍在”不等于“模型仍然知道”？

参考答案：存储中的历史、模型当前输入和按需查询工具是不同层。这些历史内容需要进入本次请求，才能作为当前采样的直接材料；调用工具还要等返回结果被纳入后续请求。模型可能从别的线索推测出相同结论，但那不能证明它取回了这份历史。

题三：压缩成功但 Agent 又改了 README，先检查什么？

参考答案：检查最新禁止修改的约束是否进入 replacement 或被后续正确取回，再检查与旧要求的时间关系、规则补回，以及模型实际行动。不能只看压缩接口返回成功。

题四：为什么保留用户消息仍不足以证明无信息损失？

参考答案：保留受预算、消息类型与具体分支影响，工具结果和任务状态也可能丢失。新旧要求还需要正确解释，单纯保存文字不等于语义处理正确。

题五：怎样比较摘要和检索恢复两种设计？

参考答案：固定同一任务，测转换成本、后续恢复成本、关键约束保留、重复动作、下一步正确性及最终验收。摘要有预先压缩损失，按需恢复有检索遗漏与额外延迟，不能只比窗口变短多少。
