第 38 章｜Codex：上下文（Context）与压缩（Compaction）

本章概览

核心问题：窗口不足时，哪些信息需要保留在当前输入，哪些可以移出后再找回？

关键概念：模型历史（Model History）是下一请求的消息基础；客户端摘要（Local Compaction）与远程压缩（Remote Compaction）构造较短的替换历史（Replacement History）；窗口预算分支（TokenBudget）直接安装新窗口；过程记录（Rollout）与条件可用的回读（Readback）能力，分别支持重建和补证。

关系主线：先固定最新要求与已观察状态（State），再区分选路、安装、持久化（Persistence）和后续消费。压缩（Compaction）完成只说明一个处理步骤结束，不能单独证明智能代理（Agent）记住了约束，或任务已经通过验收。

前情回顾：历史保存不等于当前知道

第29章把任务线程（Thread）的身份（Identity）与过程记录（Rollout）分开；恢复（Recovery）同一任务线程（Thread），不是让模型重新看到每一条旧输出。第36章解释了当前输入、窗口外材料和长期记忆（Long-Term Memory）的不同职责；第37章又说明，候选（Candidate）只有经过回读（Readback）和结果消费，才能成为后续判断的证据。本章接着处理：当前输入太长时，怎样减少它，又让后续动作仍受正确的任务状态（State）约束。

先固定一个教学时序变体：目标是修复 Python 文件扫描器对带空格路径的处理。早期允许修改 README.md，用户后来明确要求“不要修改 README”；scan.py 已修改，相关测试已经执行但仍失败，尚未证明修复通过。此前积累的大量文档与测试输出挤满窗口，任务仍未验收。这些是本例给定条件，不是一次新增 Codex 产品运行，也不能把旧要求当作当前授权。

可直接继续的状态（State）应表达三件事：最新禁止修改什么，已发生什么，下一步还缺什么。下面先看实现怎样换掉输入，再用一个完整教学消费者（Consumer）判断新输入是否仍足以指导动作。同题的另一种产品组织见第30章。

四类信息的位置与丢失后果

想象书桌、档案柜和索引。书桌放当前处理的材料，档案柜保留过去记录，索引帮助找到相关文件。它们可以提到同一件事，却有不同的读取成本，也不能互相证明内容已经被模型读取。

信息层职责本例中需要理解的内容压缩（Compaction）以后怎样判断
当前模型历史（Model History）构成下一次采样的主要消息基础用户要求、动作、结果、摘要（Summary）或压缩（Compaction）项看实际选入了什么
宿主（Host）持有的保留状态（State）维护不随窗口任意丢弃的上下文（Context）基线保留上下文（Context）、环境状态（World State）表示检查新窗口如何建立适当表示，不能视为全部外部事实的实时副本
过程记录（Rollout）及相关持久记录为之后重建提供材料响应项、压缩（Compaction）检查点（Checkpoint）、上下文（Context）元数据（Metadata）依据实际幸存记录重建
后续可读取资料按需补回较长细节历史项、任务笔记、长期记忆（Long-Term Memory）材料必须能定位、读取并纳入后续请求

本地上下文（Context）管理组件 ContextManager 分别维护历史版本（History Version）和用户消息修订（User-message Revision）。replace_compacted 替换模型历史（Model History）并推进历史版本（History Version），保持用户消息修订（User-message Revision）不变；普通重置路径 replace_annotated 则会推进两者。例如仅做一次压缩（Compaction）而没有新要求，输入已经变化，用户授权却没有因此变化。

所以，“窗口换了”不能自动计为新的用户工作轮次（Turn）。这个区别会影响回滚（Rollback）和恢复（Recovery）：压缩（Compaction）生命周期项不是一次新的用户要求，过程记录（Rollout）存在也不意味着下次请求带有完整过程记录（Rollout）。若把所有旧工具输出又装回输入，原来的窗口问题会重新出现。

三条路线：先看替换什么，再看怎样选择

替换历史（Replacement History）是将要安装为活跃消息基础的新集合；不同路线产生的集合不同。这里讨论本地客户端所实现的分支，具体产品是否启用还取决于宿主（Host）、配置、模型和模型服务提供方（Provider）。

表 2 / Table 2 · 三条路线：先看替换什么，再看怎样选择
路线谁组织转换主要替换形状后续风险
客户端摘要（Local Compaction）客户端组织一次模型摘要（Summary）请求预算（Budget）内用户消息（User Message）、新摘要（Summary）及按场景补回的初始上下文（Initial Context）摘要（Summary）遗漏约束，或把未验证写成已验证

窗口预算分支（TokenBudget）TokenBudget 分支开启新窗口初始上下文（Initial Context）、环境状态（World State）表示和条件保留的开发者消息（Developer Message）旧细节不在场，后续回读（Readback）能力或查询（Query）不可靠

手动和自动入口均优先检查窗口预算（Budget）功能开关（Feature Flag）。未走该分支时，RemoteCompactionSupport::V2 选择远程压缩（Remote Compaction）；Unsupported 选择客户端摘要（Local Compaction）。这些是代码中的能力值，不能仅从产品名称推断采用哪条路线。

自动触发还受生命周期约束。主循环结合是否仍需继续、预算（Budget）状态（State）和新窗口请求决定何时转换；工具结果、后续采样和输入队列存在顺序关系。不能把它解释成“词元（Token）一多，就由任意后台线程改写历史”。图的最后一格表示继续后续工作，不是证明修复已经成功。

客户端摘要（Local Compaction）：保留用户要求仍有预算（Budget）边界

客户端摘要（Local Compaction）由客户端组织，但仍调用模型；“客户端”不表示离线，也不表示普通字符串截断。正常路径可以按六步理解：

  1. 复制当前模型历史（Model History），加入用于摘要（Summary）的输入。
  2. 组装请求，让模型产生可用于续行的摘要（Summary）。
  3. 从原历史收集真实用户消息（User Message），过滤已有摘要（Summary），避免把它们重复当成新要求。
  4. 从较新的用户消息（User Message）开始，在预算（Budget）内保留或截短，再按时间顺序排列，追加新摘要（Summary）。
  5. 依据手动或中途压缩（Compaction）的场景，决定初始上下文（Initial Context）补回的位置与基线。
  6. 安装替换历史（Replacement History），记录窗口变化和压缩（Compaction）结果，并重新估算词元（Token）使用。

第四步说明了为何要把用户要求与自由摘要（Summary）分开：用户原话不应完全依赖模型转述。但它依然有预算（Budget），位于预算（Budget）边界的一条还可能被截短，所以不能声称全部历史要求逐字永久在场。第五步也有独立职责：环境与规则有自己的上下文（Context）重建入口，不只依赖摘要（Summary）模型记住它们。

在本例中，有用摘要（Summary）至少应保留目标、最新不改 README、scan.py 已改、测试仍失败和下一步所缺证据。重复日志可以移出窗口，测试命令与关键失败位置仍须可找回。“准备测试”变成“测试通过”，或保留早期修改 README 的要求却漏掉最新禁止，都会让后续行动失去可靠依据。

远程压缩（Remote Compaction）：客户端继续负责消息结构

一次远程尝试使用本模型步骤（Model Step）的工具路由器（Tool Router） ToolRouter 取得可见工具视图，加入压缩（Compaction）触发项，再发送流式请求。这是该步骤实际捕获的视图；后来配置刷新，不会使这个已构造请求自动变成另一套工具。

客户端取得压缩（Compaction）输出后，还会与需要保留的消息组合。保留选择受词元（Token）预算（Budget）约束；图像内容怎样计费还受相应功能开关（Feature Flag）影响，不能说所有部署都用相同图像预算（Budget）。消息与元数据（Metadata）成对处理，然后按场景补入初始上下文（Initial Context）。远程服务输出不是无需再处理的整段本地状态（State）。

表 3 / Table 3 · 远程压缩（Remote Compaction）：客户端继续负责消息结构
结构问题对本例的影响
最新用户约束保留在哪里需要在服务输出与保留消息的组合中仍能解释最新要求
图像如何占用保留预算（Budget）按所启用的计费分支判断，不能把大图当作免费输入

因此，一个泛称“压缩（Compaction）接口”的名字不足以说明完整合同。这里的三条路线有不同请求与安装行为，不能用单一应用编程接口（Application Programming Interface，API）形状概括。

窗口预算分支（TokenBudget）：直接换窗与按需回读（Readback）

窗口预算分支（TokenBudget）的压缩（Compaction）入口仍经过压缩钩子（Compaction Hook），也产生 ContextCompaction 生命周期项；该函数的核心是调用 start_new_context_window，没有在这里发起模型或服务器摘要（Summary）请求。这个限定不表示整个系统永远不会调用模型整理材料。

新窗口安装先推进窗口身份（Window Identity），再构造初始上下文（Initial Context）与环境状态（World State）。启用对应功能开关（Feature Flag）时，还保留经过预算（Budget）限制的客户端开发者消息（Developer Message）。随后安装上下文（Context）项、保存窗口与基线，并重算词元（Token）使用。它与“用户消息（User Message）加摘要（Summary）”的替换形状不同。

这条路线把部分连续性工作交给窗口外材料。源码另有按配置、模型服务提供方（Provider）和认证条件装配的历史与笔记扩展，可提供历史查询（Query）、任务笔记读写和有界提示。客户端工具合同与请求封装只证明这些客户端入口；它们没有闭合服务端索引、存储、删除、竞争处理，也不能证明所有 Codex 用户都具备该能力。

图中旧窗口没有把完整内容直接传入新窗口。窗口外可取回，不等于当前已经取回：模型必须识别缺口，工具必须可用，查询（Query）必须指向正确材料，返回结果还要进入后续模型输入（Model Input）。任一步失败，都不能只凭“有历史扩展”宣称任务连续性已经保证。

这种取舍减少了一次强制全历史摘要（Summary）的成本，同时把部分代价推迟到回读（Readback），并承担遗漏约束、选错查询（Query）或索引延迟等风险。笔记越长也不一定越有用：它必须告诉消费者（Consumer）下一步缺什么、到哪里找、哪项结论尚未验证。

词元（Token）预算（Budget）：提醒与强制边界分开

本地预算（Budget）配置可来自用户设置或模型默认值，并经过验证和功能开关（Feature Flag）检查。提醒阈值、提醒模板与后备提示负责引导模型提前整理；宿主（Host）执行的窗口转换负责资源边界，二者不能互相替代。

maybe_record 在功能开启且配置与剩余预算（Budget）可用时才继续。达到提醒阈值后，它先认领本窗口的提醒机会，再写入提醒；后备提示还要求调用方允许、剩余基本窗口预算（Budget）等于零且配置存在。状态（State）中的认领避免每一步重复注入，并不证明模型已经整理正确。

用教学数字说明：剩余 8,000 词元（Token）不表示还能读取 8,000 词元（Token）日志。还要容纳输出、工具结果、系统上下文（Context）与恢复（Recovery）余量。完整请求的编码与计量也不能只靠正文字符数代替；具体额度由模型与配置决定。

安装与持久化（Persistence）：当前进程和重启进程看到什么

replace_compacted_history 不只是一次赋值。先补齐响应项身份（Response Item Identity）、准备压缩（Compaction）记录，再等待已接纳设置更新的持久化（Persistence）协调；持锁更新活跃模型历史（Model History）、保留上下文（Context）与环境状态（World State）基线，之后把压缩（Compaction）、环境状态（World State）、参考上下文（Reference Context）和设置事件（Event）交给持久化（Persistence）逻辑。锁保护的是相应状态（State）与顺序，不能由此推导跨存储事务。

表 4 / Table 4 · 安装与持久化（Persistence）：当前进程和重启进程看到什么
状态（State）作用恢复（Recovery）时必须确认
替换历史（Replacement History）下一请求主要输入的基础是否含有继续任务所需信息
参考上下文（Reference Context）判断补入完整上下文（Context）还是增量压缩（Compaction）后基线是否有效
环境状态（World State）基线表示新窗口的环境状态（World State）后续变化有没有正确应用

过程记录（Rollout）检查点（Checkpoint）及尾部（Tail）支持后续历史重建二者是否属于同一幸存片段

重建不能只找“最后一条摘要（Summary）”。本地重建逻辑先逆向确定幸存的替换历史（Replacement History）检查点（Checkpoint）及必要元数据（Metadata），再从对应尾部（Tail）正向重放（Replay）。回滚（Rollback）会移除相应用户工作轮次（Turn）；仅上下文（Context）片段不能因此冒充用户要求。较旧、没有替换历史（Replacement History）的记录还有兼容分支，会重新组合用户消息（User Message）与摘要（Summary），并清空相应参考基线。

例如活跃内存已替换，但对应记录尚未完成持久化（Persistence），当前进程与重启进程可能拥有不同历史。重启后只能按实际幸存检查点（Checkpoint）和尾部（Tail）重建，不能凭某个文件存在认定上述状态（State）全部一致。这是故障点推演，不是本章新增的崩溃实验；它也没有承诺外部文件编辑会随模型历史（Model History）回滚（Rollback）。

技术失败与任务信息失真要分别判断

客户端摘要（Local Compaction）请求本身也可能超窗。源码在请求尚有多项时移除最旧历史项后重试；移除操作还处理相应调用与结果配对。已无法继续减少时报告错误。普通连接错误受重试上限约束；中断或取消直接返回，会话（Session）预算（Budget）耗尽则报告并返回，不能全部当成“重连直到成功”。

技术成功与任务保真是两条轴：请求可以成功但摘要（Summary）丢失最新约束，也可以内容合理却未成功安装。只比较字数或压缩（Compaction）接口返回值，无法回答下一步动作是否仍受正确事实约束。

完整案例：由消费者（Consumer）接受、拒绝或要求补证

下面保留一个小合同，接着补齐所有调用，使完整例子可直接追踪。ContinuationCheck 描述换窗后的任务判断；verifiedTests 只列已观察通过的测试，绝不能把“已执行”当成“已通过”。代码是教学消费者（Consumer），不是 Codex 内部验证器。

type ContinuationCheck = {
  latestConstraint: "do_not_edit_readme";
  modifiedFiles: string[];
  verifiedTests: string[];
  unverifiedClaims: string[];
  nextAction: string;
};

// 教学算法：比较换窗前后的后续决策，而非只比较摘要字数。
async function checkContinuation(before: Scenario, after: ModelInput) {
  assertLatestConstraint(after, before.latestConstraint);
  assertNoInventedTestSuccess(after, before.observedTestResults);
  assertCanLocateNeededDetails(after, before.requiredArtifacts);
  return evaluateNextAction(after, before.acceptanceCriteria);
}

上述框架先核最新约束，再核通过声明，再查材料定位，最后判断动作。以下类型与函数完成它：before 的观察来自本例可信的给定状态（State）；readableArtifacts 也是宿主（Host）提供的可读取集合，不接受模型自行声称某引用可用。为了隔离语义问题，这里用预先标注的结构字段，不声称从任意自然语言摘要（Summary）中自动抽取真相。

type Scenario = {
  latestConstraint: string;
  observedTestResults: Record<string, "passed" | "failed">;
  requiredArtifacts: string[];
  acceptanceCriteria: { forbiddenEdits: string[] };
};
type ModelInput = Omit<ContinuationCheck, "latestConstraint"> & {
  latestConstraint: string;
  artifactRefs: string[];
  readableArtifacts: string[]; // 本例可信宿主（Host）提供，不能由摘要（Summary）自行认证。
  proposedEdits: string[];
};
function assertLatestConstraint(after: ModelInput, required: string) {
  if (after.latestConstraint !== required) throw new Error("reject:constraint");
}
function assertNoInventedTestSuccess(
  after: ModelInput, observed: Scenario["observedTestResults"]
) {
  // 无记录和已观察失败，都不能被宣布为通过。
  if (after.verifiedTests.some(name => observed[name] !== "passed"))
    throw new Error("reject:invented_test_success");
}
function assertCanLocateNeededDetails(after: ModelInput, required: string[]) {
  const missing = required.some(ref =>
    !after.artifactRefs.includes(ref) || !after.readableArtifacts.includes(ref));
  if (missing) throw new Error("needs_readback:missing_artifact");
}
function evaluateNextAction(after: ModelInput, rules: Scenario["acceptanceCriteria"]) {
  if (after.proposedEdits.some(path => rules.forbiddenEdits.includes(path)))
    return "reject:forbidden_edit";
  return "continue:read_then_diagnose";
}

这里接受的是“具备按需回读（Readback）的定位，可以继续诊断”，不是“修复完成”。evaluateNextAction 只检查示例中的禁止编辑集合；nextAction 是展示文字，实际判定读取结构化的 proposedEdits；一般行动安全性、路径规范化和自然语言真假不在这个小消费者（Consumer）覆盖范围内。缺材料分支先于动作判定；它要求停止当前推进并补证，补齐后仍须重新检查禁止编辑，不能把补证当成授权。

给定恢复（Recovery）状态（State）仍是开篇的任务：scan.py 已修改，测试跑过但失败，修复未证实。参考对象如下，路径与字段均为教学设定：

const expected: ContinuationCheck = {
  latestConstraint: "do_not_edit_readme",
  modifiedFiles: ["scan.py"],
  verifiedTests: [], // 此字段只列已观察到通过的测试；本例没有。
  unverifiedClaims: ["带空格路径已修好"],
  nextAction: "回读失败断言和当前实现，确定原因后在许可范围内继续",
};

把它和三个反例放入同一个消费者（Consumer）。材料引用只在这个固定教学集合中解释，不是产品历史工具的真实标识。

const before: Scenario = {
  latestConstraint: "do_not_edit_readme",
  observedTestResults: { space_path: "failed" },
  requiredArtifacts: ["current:scan.py", "test:space_path:failed"],
  acceptanceCriteria: { forbiddenEdits: ["README.md"] },
};
const good: ModelInput = {
  ...expected,
  artifactRefs: [...before.requiredArtifacts],
  readableArtifacts: [...before.requiredArtifacts],
  proposedEdits: [], // 先读取，尚不安排一次新的写入。
};
const cases: [string, ModelInput][] = [
  ["ready", good],
  ["invented_pass", { ...good, verifiedTests: ["space_path"] }],
  ["forbidden_edit", { ...good, proposedEdits: ["README.md"] }],
  ["missing_log", { ...good, readableArtifacts: ["current:scan.py"] }],
];
for (const [name, after] of cases) {
  try {
    console.log(name, await checkContinuation(before, after));
  } catch (error) {
    console.log(name, error instanceof Error ? error.message : String(error));
  }
}

合并上述代码块后，纯教学程序实际输出如下；没有请求模型、启动压缩（Compaction）服务或执行修复测试：

ready continue:read_then_diagnose
invented_pass reject:invented_test_success
forbidden_edit reject:forbidden_edit
missing_log needs_readback:missing_artifact

ready 只表示能够先回读（Readback）失败断言与当前实现；读取返回以后仍要进入后续模型输入（Model Input）。第二行拒绝把失败改写成通过，第三行拒绝最新约束禁止的编辑，第四行要求补回无法读取的日志。这比“摘要（Summary）短了多少”更接近任务连续性的要求，但不是任何模型的实测成绩。

常见场景：直接问答

压缩（Compaction）一定生成摘要（Summary）吗？

参考答案：客户端摘要（Local Compaction）和远程压缩（Remote Compaction）处理摘要（Summary）或压缩（Compaction）输出；窗口预算分支（TokenBudget）的压缩（Compaction）函数直接安装新窗口，不在该函数请求摘要（Summary）。实际路线由配置、功能开关（Feature Flag）与模型服务提供方（Provider）能力决定。

为什么历史仍在，不等于模型仍然知道？

参考答案：保存、取回和进入模型输入（Model Input）是三步。历史必须被读取并纳入本次请求，才能直接支持当前判断；模型从别处猜出相同结论，也不能证明它读过这份历史。

压缩（Compaction）结束后智能代理（Agent）又改了 README，先检查什么？

参考答案：检查最新禁止修改是否进入替换历史（Replacement History）或被正确回读（Readback），再检查新旧要求的时间关系、规则补回以及实际行动。不能只看压缩（Compaction）入口返回成功，也不能把旧授权当成最新授权。

保留用户消息（User Message）为什么仍不足以证明没有信息损失？

参考答案：保留受预算（Budget）、消息类型与具体分支影响，工具结果和任务状态（State）也可能缺失。保存用户文字还需要正确解释其先后关系，不能把所有要求无条件并列执行。

怎样比较摘要（Summary）与检索恢复（Recovery）？

参考答案：固定任务输入、最新约束、初始状态（State）与验收标准，再看转换成本、后续恢复（Recovery）成本、关键约束保留、重复动作、下一步正确性及最终验收。摘要（Summary）承担预先压缩（Compaction）损失，按需回读（Readback）承担检索遗漏与延迟；减小窗口而暗中降低任务难度，没有可比性。
