第 58 章｜设计编排（Orchestration）与连续执行（Execution Continuity）

本章概览

核心问题：批准、目标、定时触发和依赖就绪怎样启动工作，客户端断线后又怎样继续查看同一份工作？

关键概念：执行意图（Execution Intent）固定待处理工作；准入（Admission）绑定执行身份；派发（Dispatch）让执行器实际开始；对账（Reconciliation）核对不确定效果；快照（Snapshot）与游标（Cursor）帮助重建观察基线。

关系主线：不同控制域（Control Domain）分别判断能否继续，再交给共同执行基础。恢复（Recovery）先定位原身份（Identity）、状态（State）和权限（Permission），连接重建不自动重放任务，持久记录也不保证原进程或外部资源仍然存活。

前情回顾：继续同一份工作，需要保留哪些区别

第13章把会话（Session）、工作轮次（Turn）与执行（Run）分开；第14章又区分持久事实（Persistent Fact）与用户界面（User Interface，UI）投影（Projection）。因此，界面重新出现一段文字，不证明新执行（Run）已经开始；界面暂时空白，也不证明原工作没有被接纳。

第24章解释不同继续理由：计划（Plan）等待批准（Approval），目标（Goal）依据证据与预算（Budget），定时任务（Scheduled Task）处理一次到期机会，任务图（Agent Graph）等待依赖。它们可以调用共同的执行基础，但不能用同一个“尚未完成就继续”条件。

第25章说明连接连续性（Connection Continuity）与执行连续性（Execution Continuity）不同。客户端（Client）重连后需要重新取得可靠状态；宿主（Host）与工具执行器（Tool Executor）是否仍在工作，则取决于它们各自的寿命和恢复合同。

刚读过的第57章还要求父任务（Parent Task）核对可交付产物（Artifact），不能把子任务（Subtask）的终态（Terminal State）直接当成依赖已经可用。本章将这些关系接成一套教学控制合同，并展开每个关键辅助函数的责任。

1. 原题与明确假设

智能代理（Agent）要在用户批准（Approval）后执行计划（Plan），也要持续追踪目标（Goal）、定时工作和协调多个子任务（Subtask）。用户关闭界面后，还能从另一端查看，应该怎样设计？

先分开控制状态（Control State）与连接状态（Connection State）。前者决定能否创建下一份工作，后者决定怎样查看已经存在的工作。查询（Query）任务状态，不因此重放执行命令（Command）。

本题假设宿主（Host）负责接纳工作，控制状态（Control State）与执行身份（Execution Identity）可以持久保存；客户端（Client）允许断线重连。普通文件与命令执行器（Executor）由宿主（Host）侧持有。客户端能力（Client Capability）提供的工具（Tool）属于另一个条件，最后单独分析。

本题不假定机器关闭后进程仍在运行，也不承诺任意跨机器迁移。以下数据结构、控制流程和结果都是教学设计与推演，没有实际启动模型（Model）、调度（Scheduling）、网络连接或故障注入。

2. 参考方案：控制者先给理由，执行器（Executor）再做工作

让普通执行（Run）承担模型（Model）与工具（Tool）循环，各控制域（Control Domain）决定何时需要下一份工作。每次触发（Trigger）先形成可恢复的执行意图（Execution Intent），再进入准入（Admission）；准入（Admission）成功后，还须取得派发许可（Dispatch Permit），才能实际启动。

取消（Cancellation）、修订（Revision）与完成可能并发发生。对应负责者（Owner）必须根据当前状态收束决定；已经产生的效果（Effect）另行结算。不能把一个过时的继续理由直接交给执行器（Executor），也不能因为恢复（Recovery）请求晚到，就让它覆盖当前授权（Authorization）。

先看四个域分别需要什么事实：

表 1 / Table 1 · 2. 参考方案：控制者先给理由，执行器（Executor）再做工作
控制域（Control Domain）持有决定权者消费的输入（Input）形成执行意图（Execution Intent）前的条件不能当作任务完成

火次（Fire）指某个定时任务（Scheduled Task）的一次具体触发机会。同一个任务明天和后天的触发可以是不同火次（Fire）；两个入口重复报告明天这一机会，却不应自动变成两份工作。身份（Identity）必须表达这一业务区别，单看请求到达次数不够。

共同基础负责绑定身份、准入（Admission）、派发（Dispatch）、结果保存与查询（Query）。各域继续负责自己的状态判断。共享代码减少重复实现，不能删除四行各自的合法条件。

3. 主图：触发（Trigger）怎样进入共同执行（Run）

上方四条箭头传入的是合法继续工作的理由及其身份（Identity），不是四种已经发生的业务效果（Effect）。宿主（Host）接纳后保存绑定，再由派发（Dispatch）入口决定谁能启动；执行结果（Outcome）回到对应控制者，供它更新下一步状态。

就绪（Ready）、认领（Claim）、准入（Admission）与启动（Start）是不同事实。已有执行（Run）正在工作或已经结束时，入口应返回可观察状态或原有结果，不沿首次派发（Dispatch）的箭头再开一遍。

图中“持久”只描述执行意图（Execution Intent）的可恢复记录。它不独自证明文件、远端服务或进程调用栈可恢复；这些资源有各自的效果（Effect）与寿命合同。

4. 接纳合同：固定内容，再决定创建还是查询

先给 intent 中每个输入（Input）一个来源

固定一次教学定时检查：任务标识为 daily-check，用户授权明天只读核对 README 的测试步骤，不修改文件，也不把“检查”扩大为任意命令执行。协调者（Coordinator）保存当前第 1 版任务内容，并为明天这次火次（Fire）使用 one-specific-fire 标识。后续重复触发（Trigger）沿用它。

下面 current_revision 来自这份可信控制记录，本例为第 1 版；frozen_task_input 是上述完整只读要求及其允许范围。它们在形成执行意图（Execution Intent）时固定，不能在重试时偷偷换成另一项任务。数据字典与函数均为教学接口，不是 Maka 应用编程接口（Application Programming Interface，API）。

按“身份—内容—当前阶段”阅读这个结构；函数则处理既有绑定、明确拒绝、新准入（Admission）与异常判定四类结果。

intent = {
    # 控制域与本次触发共同定位原工作。
    "domain": "schedule",
    "domain_id": "daily-check",
    "trigger_identity": "one-specific-fire",
    # 修订与内容来自可信控制记录，重试不替换。
    "revision": current_revision,
    "payload": frozen_task_input,
    "status": "pending_admission"
}

def reconcile(intent):
    # 在同一负责者边界核身份、当前授权和已有绑定。
    decision = claim_or_observe_atomically(intent)
    if decision.kind == "existing":
        if decision.stop_required:
            request_stop_idempotently(decision.run_id)
            return observe(decision.run_id)
        return dispatch_or_reconcile(decision.run_id)
    if decision.kind == "rejected_before_admission":
        return record_rejection(decision.reason)
    if decision.kind == "new_admission":
        return dispatch_or_reconcile(decision.accepted_run_id)
    # 冲突或未识别状态不能进入派发。
    return report_admission_problem(decision)

claim_or_observe_atomically 不是用名称代替实现。它代表本题要求落实的一组原子合同（Atomic Contract）：同一控制状态的读取、判定与唯一绑定写入，要经过同一事务（Transaction）或串行负责者（Owner），并与取消（Cancellation）及修订（Revision）写入协调。

身份相同，也要核对内容与当前权利

设控制域（Control Domain）为 DDD、该域中的任务标识（Task Identity）为 TTT、作用域（Scope）为 SSS、本次触发身份（Trigger Identity）为 FFF，本题用组合键 KKK 定位一次触发所形成的工作：

K=(D,T,S,F).K=(D,T,S,F).K=(D,T,S,F).

这里 SSS 包含该应用选择的账户或工作区（Workspace）等隔离范围，由可信环境提供。相同键只帮助找到原绑定，不会使不同内容合法。已保存载荷（Payload）记为 P0P_0P0​；后续请求必须按事先约定的内容比较规则与 P0P_0P0​ 一致，且调用者仍有权提交或观察该对象。

具体顺序如下：

表 2 / Table 2 · 身份相同，也要核对内容与当前权利
检查位置输入与负责者（Owner）的动作输出及下一位消费者（Consumer）
1. 授权（Authorization）核对调用者能否提交或观察该控制域（Control Domain）与作用域（Scope）无权者被拒绝；知道身份（Identity）不授予查询权
2. 原绑定按 KKK 找既有准入（Admission），核对冻结载荷（Payload）与授权范围一致时定位原执行（Run）；同身份换内容则冲突
3. 新准入（Admission）条件仅对尚未被接纳的意图，核对当前取消（Cancellation）、修订（Revision）与各域合法条件过时或被停止的意图明确拒绝，不先创建执行（Run）
4. 唯一绑定在相同负责者（Owner）的原子边界保存准入（Admission）返回原身份或唯一的新执行身份（Execution Identity），供派发（Dispatch）路径消费

这里“仅对尚未接纳者”不表示已接纳执行（Run）可以忽略后来取消（Cancellation）。已经绑定的工作要定位原执行（Run），走它的停止路径；不能把原绑定改成另一项工作，也不能在原子判断之后假装再没有状态变化。

request_stop_idempotently 要能针对同一执行（Run）重复表达停止意图。请求失败需要重试或对账（Reconciliation）；请求返回也不独自证明所有工具（Tool）已停止。已开始效果（Effect）的结果仍须结算。

5. 派发（Dispatch）与恢复（Recovery）：先确定原执行（Run）处于哪里

这里的 dispatch_or_reconcile 与第49章主循环使用同一教学合同。第49章已经给出首次、并发重复、运行中、终态（Terminal State）后、派发（Dispatch）前崩溃和未知效果（Unknown Effect）六种情境；本节解释收到原执行身份（Execution Identity）以后，恢复者怎样选择动作。

先按消费者（Consumer）区分四种状态。已有记录供恢复者判断，真正启动仍由执行入口裁决。

表 3 / Table 3 · 5. 派发（Dispatch）与恢复（Recovery）：先确定原执行（Run）处于哪里
读取到的状态（State）可作的判断本次允许的方向
已有终态（Terminal State）原执行（Run）已保存结束事实读取原结果；成功、失败、取消（Cancellation）或预算（Budget）耗尽都不自动重新启动
正在执行（Running）原工作已经进入执行阶段查询（Query）或订阅（Subscription）同一工作
已准入、确定未派发（Admitted Not Dispatched）唯一绑定已有，首次启动尚未发生再核当前状态与取消（Cancellation），竞争唯一派发许可（Dispatch Permit）
派发未知（Dispatch Unknown）、未知效果（Unknown Effect）或中断可能已经越过启动或效果（Effect）边界，现有记录不足围绕原执行（Run）与工具调用（Tool Call）核对事实，再按实际合同分类

下面的函数按这个顺序处理。read_authoritative_state 读取由合法负责者（Owner）维护的状态记录，提供判断起点；记录本身不拥有裁决权。

def dispatch_or_reconcile(run_id):
    state = read_authoritative_state(run_id)
    if state.is_terminal:
        return read_recorded_result(run_id)
    if state.phase == "running":
        return query_or_subscribe(run_id)
    if state.phase == "admitted_not_dispatched":
        # 再核取消与当前状态，竞争同一首次启动资格。
        permit = claim_dispatch_atomically(run_id)
        if not permit.granted:
            return observe(run_id)
        return dispatch_same_run_once(run_id, permit.owner_token)
    if state.phase in {"dispatch_unknown", "effect_unknown", "interrupted"}:
        # 先按原身份核事实，不能直接从头执行。
        return reconcile_known_facts(run_id)
    return report_recovery_state_problem(run_id, state)

为什么读取以后还要再认领（Claim）

两个恢复者可能同时读到“尚未派发（Dispatch）”。如果它们各自根据旧读取结果启动，唯一准入（Admission）记录仍挡不住两次真实执行。claim_dispatch_atomically 必须在当前执行负责者（Execution Owner）的边界重新检查状态（State）和取消（Cancellation），只交出一个有效许可。

dispatch_same_run_once 还要求执行入口根据同一执行（Run）与有效负责者凭证（Owner Credential）识别重复派发（Dispatch）。如果入口没有这一合同，单靠数据库里一条准入（Admission）记录，不能承诺不重复开跑。函数名字中的 once 是待落实的合同要求，不是语言自带的保证。

执行入口加载原先冻结的任务（Task）与允许范围，并继续应用当前有效的授权（Authorization）限制。恢复（Recovery）请求不得用新内容替换原任务，也不能延长原期限或重新领取完整预算（Budget）。它启动的是第49章获得派发许可（Dispatch Permit）后的执行骨架，不重新提交一次用户请求。

“确定未开始”与“没有收到响应”不能合并

认领（Claim）成功后、派发（Dispatch）尚未发出就崩溃，可以恢复首次派发（Dispatch）。请求已经发出却丢失响应时，则可能已经执行，必须先查询原执行（Run），不能自行改成“尚未开始”。

若工具（Tool）效果可能已经发生，reconcile_known_facts 还要核对原工具身份（Tool Identity）和外部资源。查到可靠结果时补记事实；查不到时保留未知效果（Unknown Effect），采用该工具（Tool）支持的查询（Query）、有条件的幂等重试（Idempotent Retry）或人工处置。请求身份（Request Identity）本身不提供外部效果的恰好一次（Exactly Once）保证。

负责者（Owner）变更以后，旧执行器（Executor）可能仍在工作

本题先假设由单一负责者（Owner）串行仲裁。若改成可超时接管的租约（Lease），执行入口与事实存储还须检查负责者代际（Owner Generation），拒绝无效旧凭证；这种保护称为隔离令牌检查（Fencing）。

租约（Lease）过期意味着处理资格需要重新判断，不证明旧工具（Tool）或远端请求已经停止。多个恢复者不能各自看见过期就开跑；新负责者（Owner）获得资格以后，相关资源也必须能识别和拒绝旧代际（Generation）。同一有效代际（Generation）中的重复操作，仍由操作身份（Operation Identity）与幂等（Idempotency）合同处理。

派发（Dispatch）、停止与终态（Terminal State）的竞争都要回到当前执行负责者（Execution Owner）。已结束的执行（Run）保留原结果；接管不会自动恢复进程栈，也不会扩大授权（Authorization）。

6. 继续理由无效时，应保留哪一种失败

本题把评估器（Evaluator）不可解析的输出记为“没有得到有效评估”，再按有界错误策略决定重试、等待或停止。它与“有效判断为没有进展”不同：前者缺少可用判断，后者确实给出了判断。把前者直接累加成无进展，会把评估器（Evaluator）故障误写成任务（Task）停滞。

如果采用 Maka 目标（Goal）的具体策略，需要按第24章已解释的分支处理：evaluatorFailed 时不提交 madeProgress，因而不据此增加停滞计数；预算（Budget）与迭代上限（Iteration Limit）仍需检查。缺失布尔字段而形成有效全假判断，又与无法解析的输出不同。不能仅从“评估失败不算停滞”推断下一次执行（Run）必定开始。

无论采用哪一种策略，评估器（Evaluator）都需要实际证据。它只能消费得到的输入（Input）；模型（Model）声称“已完成”而缺少测试（Test）或业务结果，不会因为再问一次评估器（Evaluator）就自动变成独立验收（Acceptance）。

其他三个域也保留自己的失败条件：计划（Plan）的内容已被修订（Revision），旧批准（Approval）不再覆盖新版计划（Plan）；定时任务（Scheduled Task）找不到可靠火次（Fire）身份，不能猜一次新启动；任务图（Agent Graph）的上游终态（Terminal State）存在但产物（Artifact）不可读，不能把依赖当成已经交付。

7. 断线重连：建立读侧基线，不重放工作

这张图固定为首次获准派发（Dispatch）后客户端（Client）断线，宿主（Host）与普通执行器（Executor）仍存活。重复任务请求按第4–5节查询或恢复（Recovery）原执行（Run）；图中重连请求只取得观察基线，不创建新的工作身份（Work Identity）。

快照（Snapshot）给当前状态，游标（Cursor）给相应更新流的位置。两者要属于同一套可解释的合同：若取得快照（Snapshot）后才开始订阅（Subscription），中间恰好发生的新结果可能漏掉。本题可选带回放能力的游标（Replayable Cursor），或先缓冲订阅（Subscription）更新再与快照（Snapshot）衔接；仅写“先 GET 后 subscribe”不能证明没有间隙。

这是一份通用设计合同。Maka 第25章的真实新连接会创建新订阅（Subscription）身份，并以 nextSequence=1 和当前快照（Snapshot）建立基线。旧订阅（Subscription）收到序号（Sequence）41，不意味着新订阅应从42继续。原逻辑流仍存活、只更换传输路径的情形，又与新建连接不同。

序号（Sequence）帮助发现该流中的缺口；代际（Epoch）可区分不兼容的宿主（Host）或状态范围，具体含义由协议规定。发现缺口后应重建匹配基线，不能让缺少前缀的增量继续假装完整。它们不会自动恢复进程栈，也不证明工作文件、环境或远端资源已经迁移；当前投影（Projection）可恢复，也不等于所有历史通知（Notification）都能逐条重播。

8. 沿同一定时任务（Scheduled Task）走读正常与失败

正常路径沿第4节的 daily-check：保存用户的只读要求，明天到点认领（Claim）one-specific-fire，将原触发身份（Trigger Identity）绑定到一次执行（Run），取得许可后开展检查，保存结果与终态（Terminal State），再由定时任务（Scheduled Task）控制者记录该次结果。用户重连读取这份已有记录，不再次触发检查。

每一步新增的事实不同。到点不证明已接纳；接纳不证明已检查；终态（Terminal State）也要结合结果内容，才能说明 README 是否符合要求。

9. 递进追问与参考答案

为什么不能只使用一张 background_tasks 表？

可以共用存储技术，但仍须表达批准（Approval）、目标评估（Goal Evaluation）、触发身份（Trigger Identity）与依赖（Dependency）的不同约束。一张表不是问题；无差别的 status != done → run 会遗漏合法继续条件。同样，保存了状态字段，不证明派发（Dispatch）入口已经消费它。

目标（Goal）没有完成，就一直调用模型（Model）可以吗？

必须限制预算（Budget）与重试，区分有进展、无进展、评估不可用和真正完成。自动继续（Continuation）不扩大授权（Authorization）。如果目标（Goal）无法在现有范围内达成，就要说明缺少的条件并按策略处理；不能靠增加轮次越过用户明确拒绝的路径。

用户关闭窗口以后一定继续吗？

取决于执行负责者（Execution Owner）的实际寿命和宿主（Host）驻留合同。网络连接断开、用户界面（UI）退出、宿主（Host）退出和机器关机，是不同事件（Event）。逻辑责任仍然存在，不等于持有该责任的进程永远存活。

多台机器可以同时当负责者（Owner）吗？

这会增加协调、租约（Lease）、隔离令牌检查（Fencing）与资源归属问题。先明确哪些资源允许并行负责，哪些状态要求唯一写入者（Writer），再定义旧负责者（Owner）的请求如何被拒绝。单机执行（Run）标识不会自动成为分布式互斥（Distributed Mutual Exclusion）。
