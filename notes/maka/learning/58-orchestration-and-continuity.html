第 58 章｜设计编排与连续执行

本章概览

核心问题：批准、目标、定时触发和依赖就绪怎样启动工作，并在客户端断线后保持正确观察？

关键概念：执行意图：待准入的稳定工作身份；认领：取得本次触发的处理权；Admission（准入）：由 Host 接纳执行；Run（执行实例）：运行模型与工具；Snapshot（快照）：重建当前视图；序列：识别观察流中的位置。

关系主线：不同控制者按各自条件形成意图，再共享接纳与执行基础；重连先核对权威状态，恢复连接不重放命令，也不保证机器关闭后原进程继续运行。

前置：第13章、第14章、第24章、第25章。依赖图部分另需 第57章。

1. 原题与约束

Agent 要在用户批准后执行计划，也要能持续追目标、定时运行、多 Agent 协作。用户关闭界面后，还能从另一端查看。怎样设计？

控制状态决定能否创建下一份工作；连接状态决定用户怎样重新观察已存在的工作。查询任务不会因此重放执行命令。

假设 Host 负责接纳执行，控制状态可持久保存；客户端可断线重连。本题不假定机器关机后进程仍运行，也不承诺任意跨机器迁移。

2. 参考方案

我会让普通 AgentRun 负责模型和工具执行，再由不同控制者决定何时创建下一轮。计划需要用户批准，目标需要根据结果和预算判断，定时任务需要认领一次触发机会，依赖图需要等前置节点的可用结果。它们可以复用接纳和执行基础，但各自的合法条件不同。触发先形成可恢复的意图，再进入准入，不能把 ready 当成已经开跑。客户端只提交意图和观察状态，重连时先取权威快照，再按序列补变化；重发命令要有身份与内容核对，避免重复工作。取消和完成并发时由对应状态 owner 收敛，已产生效果另行结算。最后分别验证重复触发、评估失败、取消竞争、连接断开和状态补齐。

3. 主图：不同触发进入共同执行

四种触发共享 Run 执行基础，却不共享无条件 resume。Graph 的就绪、调度认领、Host 接纳是不同阶段；图中的接纳到 Run 箭头还要求取得派发许可。已有 Run 正在运行或已经终止时，入口只返回观察或已有结果，不沿箭头重新执行。

4. 控制契约与具体状态

教学接口，非 Maka 实际操作名：

intent = {
    "domain": "schedule",
    "domain_id": "daily-check",
    "trigger_identity": "one-specific-fire",
    "revision": current_revision,
    "payload": frozen_task_input,
    "status": "pending_admission"
}

def reconcile(intent):
    # 同一状态 owner 内原子读取当前 revision、取消状态和既有 admission
    decision = claim_or_observe_atomically(intent)
    if decision.kind == "existing":
        if decision.stop_required:
            request_stop_idempotently(decision.run_id)
            return observe(decision.run_id)
        return dispatch_or_reconcile(decision.run_id)  # 恢复认领后尚未派发的工作
    if decision.kind == "rejected_before_admission":
        return record_rejection(decision.reason)
    if decision.kind == "new_admission":
        return dispatch_or_reconcile(decision.accepted_run_id)
    return report_admission_problem(decision)  # 冲突或未识别状态不派发

claim_or_observe_atomically 是本题要求实现的原子合同：先核对调用者是否有权提交或观察该控制域，再按控制域、触发身份和作用域查找既有 admission，并核对冻结的 payload 与授权范围。已有绑定不能被新内容覆盖；只对尚未接纳的意图核对当前取消与 revision，再持久创建唯一 admission。该判断与取消/修订写入必须经过同一事务或串行 owner，不能只用 if not exists。原子判定之后的新取消按已接纳 Run 的停止路径处理；停止请求失败要能重试/对账。

这里的 dispatch_or_reconcile 与第49章主循环使用同一合同。第49章已给出首次、并发重复、运行中、终态后、派发前崩溃和效果未知六种情境的参考表。本章展开恢复者如何作决定：

def dispatch_or_reconcile(run_id):
    state = read_authoritative_state(run_id)
    if state.is_terminal:  # 成功、失败、取消、预算耗尽均属于终态
        return read_recorded_result(run_id)
    if state.phase == "running":
        return query_or_subscribe(run_id)
    if state.phase == "admitted_not_dispatched":
        # 执行 owner 再核对当前状态和取消，与其他恢复者竞争同一启动权
        permit = claim_dispatch_atomically(run_id)
        if not permit.granted:
            return observe(run_id)
        return dispatch_same_run_once(run_id, permit.owner_token)
    if state.phase in {"dispatch_unknown", "effect_unknown", "interrupted"}:
        return reconcile_known_facts(run_id)  # 核对后分类，不能直接从头跑
    return report_recovery_state_problem(run_id, state)

read_authoritative_state 的读取只能提供判断起点；真正派发前，claim_dispatch_atomically 必须再次核对取消与状态，避免“读到未开始，别人已派发，我又开跑”的竞争。dispatch_same_run_once 则要求执行入口按同一 Run 与有效 owner 凭证识别重复派发；若执行入口没有这一合同，单靠接纳记录仍不能承诺不重复开跑。该入口还要加载原先冻结的任务与允许范围，继续应用当前有效的授权限制，不能用恢复请求中的新内容替换原任务。恢复入口启动的是第49章取得派发许可后的执行骨架，不重新提交一次用户请求。

“已认领、确定未启动”可以恢复首次派发；“派发请求已发出但响应丢失”必须先查询原 Run，不能误标为未启动。若工具效果可能已经发生、结果却未保存，reconcile_known_facts 还要核对对应工具身份和外部事实。查不到可靠结果时保留未知，采用该工具支持的查询、幂等重试或人工处置策略；请求 ID 本身不提供外部效果 exactly-once（恰好一次）。

本题的单 owner 可以靠串行仲裁实现上述合同；如果改为可超时接管的租约（Lease），还须让执行入口与事实存储拒绝旧 owner 的代次凭证，这称为 fencing。多个恢复者不能只看到租约过期就各自开跑；租约过期也不能证明旧工具已经停下。派发、停止与终态竞争都要回到当前执行 owner 收敛，已结束的 Run 保留原结果，恢复不能刷新预算或扩大授权。

控制域（Control Domain）继续的依据不能误认作完成
计划（Plan）明确批准及当前计划状态进度文字或步骤标记

本题把 evaluator 不可解析的结果保留为评估错误，再按有界策略处理。它与“有效判断为没有进展”不同；如果采用 Maka Goal 的策略，还要分别检查判断有效性、停滞计数、迭代额度和总预算。

5. 断线重连时序图

这是首次获准派发后发生断线的教学协议图；重复请求按第 4 节查询或恢复既有 Run。具体 API 与快照/订阅握手由实现决定。要防“取快照到订阅之间丢事件”的间隙，可以用可回放游标或订阅缓冲配合快照；不能仅画“先 GET 后 subscribe”就声称无缝。

序列用于发现缺口，epoch 可用于区分不兼容的连接或状态代际。它们不自动恢复进程栈，也不证明文件、环境和远端资源已经迁移。

6. 正常与失败走读

正常：明天检查 README → 保存 Schedule → 到点认领该次 fire → 接纳 Run → 执行检查 → 保存终态 → 控制者记录该次结果。用户重连只读取既有 Run，不重新触发检查。

重复触发：进程在接纳后、更新 Schedule 展示状态前崩溃。恢复时按原 fire 身份找到已有 admission，修复投影；不能因展示仍 pending 再开一轮。

取消竞争：取消发生在接纳前，可以阻止该意图；接纳后必须定位已存在 Run 请求停止；如果结果已完成，保留既有终态与效果，不靠覆盖 status 抹去事实。

UI 落后：界面显示 running，持久结果已 terminal。修复客户端投影；不要让 UI 回写 running 以“保持一致”。

7. 递进追问

为什么不能只用一个 background_tasks 表？

可以共用存储技术，但仍要表达批准、目标评估、触发身份和依赖的不同约束。一张表不是问题，无差别的 status != done → run 才掩盖合法触发条件。

Goal 没完成就一直调用模型可以吗？

要限制预算与重试，区分有进展、无进展、评估不可用和真正完成。自动继续不会扩大授权范围；目标要求无法在现有权限下达成时，需要明确处理。

关窗口后一定继续吗？

取决于执行 owner 的实际寿命和 Host 驻留合同。网络连接断开、UI 退出、Host 退出、机器关机是不同事件；本题不把逻辑责任等同于进程永远存活。

多机可以同时当 owner 吗？

这会引入协调、租约、fencing 和资源归属问题。先明确是否真的需要多机接管，再为过期 owner 的写入定义保护；不能把单机 run id 当成分布式互斥。
