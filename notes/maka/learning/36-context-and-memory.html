第 36 章｜上下文（Context）与记忆（Memory）的设计取舍

本章概览

核心问题：历史（History）既要帮助当前决策，又可能对未来有用，怎样分别设计这两种用途？

关键概念：工作上下文（Working Context）是本次请求选入的材料；压缩切点（Compaction Cut Point）决定哪些历史（History）保留原文；长期记忆（Long-Term Memory）保存跨任务（Task）信息；作用域（Scope）与撤回（Revocation）限定规则何时适用；外部工作状态（External Working State）容纳窗口之外的原文与中间值。

关系主线：从输入预算（Input Budget）推导合法压缩（Compaction），再沿记忆（Memory）的写、存、读、用检查适用条件；最后用可选的递归语言模型（RLM）案例说明外部材料怎样参与计算。

前情回顾：历史（History）还在，不等于本次看见

第19章说明，完整历史（History）与模型输入（Model Input）是两个对象：压缩（Compaction）可以保留历史（History）文件，同时只把摘要（Summary）和近期片段放入下一请求。这样节省窗口，却可能遗漏当前限制；协议结构完整与任务语义（Task Semantics）完整，需要分别检查。

第20章和第21章又把记忆（Memory）的写入与消费分开：存储提交（Commit）成功以后，还要有人读取、组装并实际使用。本地记忆笔记（Local Memory）的读取开关，不控制条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）的另一条存储链。

本章继续问：当前放不下的材料怎样处理，其中哪些又值得留给未来？先走输入选择与压缩（Compaction），再走跨任务（Task）记忆（Memory）。后续第53–55章会分别深化请求组装（Context Composition）、压缩（Compaction）与记忆（Memory）；本章所需概念在这里直接解释。

1. 同一条信息的三种用途

先固定一个文档修复情境：函数当前正确，用户只允许修改 README，并要求运行测试、用中文汇报。测试产生一份长日志，其中两条失败最值得继续调查。尚未查明原因，不能把这两条失败写成“函数一定错误”，也不能从允许测试推导出允许改代码。

表 1 / Table 1 · 1. 同一条信息的三种用途
层次要回答的问题本例中的材料
原始事实与产物（Facts / Artifacts）发生了什么，怎样回查细节？命令、参数、退出信息、完整输出与资源版本
工作上下文（Working Context）模型（Model）下一步需要什么？当前要求、修改范围、两条失败、相关代码与未完成项

三层可以引用同一个来源，却有不同的生命周期。压缩（Compaction）改变请求中的输入表示，不自动完成长期记忆（Long-Term Memory）写入；保存条目也不保证下次一定读到。读到后是否正确使用，又是行为层的问题。

若还要判断经验是否改善未来任务（Task），就需要比较同一实例在“保留跨题经验”和“开始前重置经验”下的结果与总成本。第46章会给出收益与负迁移（Negative Transfer）的完整演算。本章先建立可保存、可读取、可使用的链条，避免把它们都叫作“记住了”。

2. 先选择需要的材料，再计算预算（Budget）缺口

预算（Budget）怎样从总窗口推导出来

设输入与输出共享的总上下文窗口（Context Window）为 WWW，输出预留为 OOO，协议、工具定义（Tool Definition）和固定上下文（Fixed Context）合计为 FFF，安全余量为 SSS。待选动态材料的实际用量为 DDD。各项使用同一种词元（Token）计量，FFF 与 DDD 不重复计数，则：

D+F+O+S≤W.D+F+O+S\leq W.D+F+O+S≤W.

把固定占用与预留移到右边，动态预算（Dynamic Budget）上限就是：

D≤Bdynamic=W−O−F−S.D\leq B_{\mathrm{dynamic}}=W-O-F-S.D≤Bdynamic​=W−O−F−S.

教学配置取 W=32,000W=32{,}000W=32,000、O=4,000O=4{,}000O=4,000、F=6,000F=6{,}000F=6,000、S=2,000S=2{,}000S=2,000，所以可选20,000词元（Token）的动态材料。相关文件与日志若共22,000词元（Token），至少还要减少2,000。原材料的保存位置可以不变，改变的是本次选入量。这些数字是算例，不是产品默认值或模型（Model）测量。

如果右侧为负，连固定部分与预留都放不下；把动态用量设为0也不能使请求合法。实际计量还要包括所用模型（Model）和请求格式的协议包装、工具定义（Tool Definition）、图片及相应生成开销，不能把字符数直接当词元（Token）。接口若另设最大输入与最大输出限制，还须同时满足，不能仅凭上式判断可发送。

先区分缺材料，还是材料太多

当前用户要求、文件中的任务数据与检索说明属于不同信任来源。输入组装（Context Composition）仍须保留来源身份：资料里出现“忽略限制”，不会因此升级成授权（Authorization）。

如果只需十行文件，先做有界读取（Bounded Read）；日志只有两条相关失败，就先提取并保留回查入口。只有相关历史（History）本身仍放不下，才需要更强的摘要（Summary）、窗口替换或其他压缩（Compaction）策略。

把材料到达模型（Model）的过程拆开，会更容易定位原因。生产者（Producer）产生并保存文件或观察结果（Observation）；索引（Index）组织可查对象；检索（Retrieval）提出候选；消费者（Consumer）再按身份（Identity）、相关性与预算（Budget）组装模型输入（Model Input）。失败日志从未进入候选时，扩大窗口不能补回它；已进入候选却被重复片段挤掉时，应先查重排（Reranking）与预算（Budget）。

代码关系图（Code Graph）、目录树（Directory Tree）与向量近邻（Vector Nearest Neighbor）是不同选择方法，后者按数值表示寻找距离较近的候选。本章后面讲 Letta 的目录树（Directory Tree），第37章讲 Aider 的代码关系图（Code Graph）。通用解释和数值例见Agent检索与搜索、推荐，其中还区分近似最近邻（Approximate Nearest Neighbor，ANN）的算法找回率、业务召回与必要证据覆盖。

结构保住了，语义由谁带回来

compact 分别生成旧历史（History）摘要（Summary）与轮次前缀摘要（Turn-prefix Summary），再合并并汇总读过、修改过的文件。原例的理想摘要（Summary）应保留：测试入口为 npm test、本轮只许改 README、中文汇报、README已经修改。它不应预言测试成功；H9的真实失败正文仍在保留尾部（Retained Tail）中。

SessionManager 追加压缩条目（Compaction Entry）后，buildContextEntries 沿当前分支取最近摘要（Summary），接上H8起的保留项及其后的新项，再转成模型消息（Model Message）。它没有删除磁盘中的H1–H7，也没有把完整旧日志偷偷塞回当前输入。旧摘要（Summary）还能参与以后增量总结，减少重读，代价是早期遗漏可能沿滚动摘要（Rolling Summary）传播。

如果H5的“只改 README”被漏掉，工具调用/结果对（Tool Call / Result Pair）仍然合法，但任务语义（Task Semantics）已经受损。切点负责结构，摘要（Summary）负责被移出原文的含义。 若H9单条结果就几乎占满窗口，选出合法尾部也可能仍放不下，还需比较结果裁剪（Result Truncation）或更小的读取范围。

4. 候选摘要（Candidate Summary）怎样安全应用

这是参考设计流程：先生成候选，检查来源、结构和约束，再由工作状态的负责者（Owner）协调保存与切换。Maka使用持久检查点（Checkpoint）；Pi追加条目后重建输入；Codex另有活跃状态与过程记录（Rollout）的顺序。图中每个提交点不能直接套在全部产品上。

候选生成期间，用户可能修订限制，历史（History）也可能增加新结果。因此应用前要复核覆盖范围、保留尾部（Retained Tail）与约束代次（Revision）。候选过期时，应重新生成、整合新事实或放弃；两个互不协调的“先检查、后写入”操作仍有竞态（Race），不能凭步骤顺序声称原子性（Atomicity）。

如果总结请求自身超窗，先减少其输入或改走受控路径；无限重试（Retry）同一个过大请求不会改变条件。若摘要（Summary）遗漏当前约束，应回读并修正，而非继续概括同一份错误摘要（Summary）。

行为评价（Behavior Evaluation）至少检查四件事：目标是否保留、限制是否遵循、必要细节能否回读、任务（Task）是否完成。另一个模型（Model）的完整性判断可以辅助发现遗漏，却不能代替这些条件。词元（Token）下降很多，只说明输入变短。

5. 长期记忆（Long-Term Memory）的写入链与读取链

写入链决定什么值得存，读取链决定本任务（Task）用什么。存储（Storage）连接两条链，却不自动实现筛选或正确行为。先用一个教学类型（Teaching Type）明确需要治理的内容：身份（Identity）与正文说明“存的是什么”，作用域（Scope）与来源（Source）说明“凭什么用于这里”，状态（State）与版本说明“现在是否仍可采用”。

type MemoryItem = {
  // 身份与内容：记录是什么。
  id: string;
  key: string;
  value: string;
  // 适用范围与来源：凭什么用于这里。
  scope:
    | { kind: "global" }
    | { kind: "workspace"; workspaceId: string };
  source: { kind: "user_statement" | "observed_fact"; ref: string };
  // 有效状态与版本：字段需由消费者检查。
  // 本类型本身不实现筛选或并发提交。
  status: "active" | "revoked" | "conflicted";
  revision: number;
  validUntil?: string;
};

这是教学类型（Teaching Type），不规定数据库或实际产品字段。修订号（Revision）存在，不表示并发更新（Concurrent Update）已经安全；来源（Source）可回查，不表示内容永远正确。测试入口会变、偏好会撤回（Revocation），外部文件也不应自动成为长期指令。

写入预算（Write Budget）约束长期存量，读取预算（Read Budget）约束本次输入。候选内容可靠，也可能因为文件太大、目录太深或缺少索引（Index）而不能提交（Commit）；反思（Reflection）生成成功，也可能在合并（Merge）时失败。至少应分清候选已生成、已获准、已提交、已进入输入；candidate_generated、admission_passed、committed、read_into_context 在这里仅是教学状态名。

例如，后台整理出30条偏好，却因常驻内容（Always-loaded Content）超限而被提交校验拒绝。应保存候选与失败原因，按作用域（Scope）重新整理；不能宣称已经记住，也不能无限重试（Retry）。若移入其他智能代理（Agent）的历史（History），还须检查旧工具（Tool）与权限环境（Permission Environment）是否适用。

Letta Code：文件怎样变成下一轮可用的记忆（Memory）

另设跨会话（Session）条件：当前工作区（Workspace）为A，已存偏好是“一般中文，A用英文”；新用户只说“解释 README 的测试结果”，本次没有指定语言。这与H5当轮明确要求中文不同，H5仍按当前要求处理。

这里选定 Letta Code 本地后端（Local Backend）的 MemFS 文件格式分支。它使用 system/；根目录 MEMORY.md 属于另一格式，不能混称Letta都这样读取。下面文件名和中文内容由课程设计，选择与编译过程按相应实现解释：

system/preferences.md   正文：一般解释用中文；按工作区检查例外
workspaces/A.md         正文：A 的解释用英文；来源是用户 T20

先修改并提交，再看输入是否变化

memory 工具（Tool）接收创建、替换、插入、删除、改名等操作与非空原因。对应写入链先核对记忆仓库（Memory Repository）存在且干净，再按操作校验目标路径及已有文件的只读标记（Read-only Flag），修改正文后调用 commitMemoryWrite 提交受影响路径。它是明确定位文件后编辑，不是先让向量库（Vector Store）自动推断该改哪条事实。只改了工作副本、尚未提交（Commit），不能宣称默认背景已经改变。

collectCommittedMemoryFiles 枚举当前已提交版本（HEAD）中的Markdown，并读取已提交正文。renderMemfsProjection 将 system/ 正文放入记忆输入块（Memory Block），其他非技能说明包（Skill）文件主要贡献目录树（Directory Tree），不自动贡献正文。读取失败的文件可能被跳过；这些读取由多条Git命令完成，本章不据此声称并发提交期间获得单次原子快照（Atomic Snapshot）。

看见目录，不等于读过正文

getOrCompileSystemPrompt 比较基础系统提示（System Prompt）的哈希值（Hash）与记忆修订（Memory Revision）；未变时复用缓存（Cache），变化时重新编译。支持轮次中更新的分支可另发系统更新片段，resolveSystemPromptForTurn 提供本轮材料。

因此A的新任务（Task）初始可以看到“默认中文、存在A.md”，却未必看到“A用英文”。智能代理（Agent）仍要根据发现线索选中A.md，通过文件读取（Read）取得正文，再把工具结果（Tool Result）带入后续模型输入（Model Input），才有机会选择英文。目录可见、正文已读、回答采用，是三次不同判断。

若A的例外频繁使用，可以把短规则移入常驻内容（Always-loaded Content）。这样降低漏读机会，也让每次任务（Task）承担更多输入成本。设计取舍发生在读取可靠性与常驻预算（Always-loaded Budget）之间，不能只比较存了多少文件。

撤回（Revocation）需要改变有效内容

用户撤回A例外时，应改掉或删除有效规则，并同步常驻发现线索。只在别处追加“现在跟随全局”，可能留下互相冲突的材料。后台反思（Reflection）是另一条写入链：读取执行记录（Transcript）与既有记忆（Memory），在独立记忆工作副本（Memory Worktree）中修改、提交，再整合回父仓库。

整合已合入或确无变化，才进入相应消费判断；实际合入还关系到重新编译，冲突可能使合入失败。内置提示要求纠正旧条目、维护索引（Index），这是模型（Model）执行的方法，Git合并（Merge）本身不能证明撤回（Revocation）的语义被正确理解。

这条路线让内容可读、可编辑，并分开常驻与按需成本；薄弱环节在发现线索、文件组织及主动读取。Maka的本地记忆笔记（Local Memory）使用受控条目投影（Projection），Codex有条件选取过程记录（Rollout）再提取和整合，不能把不同消费者（Consumer）混成同一条自动读取链。

真实Maka的本地记忆笔记（Local Memory）中，workspace没有本题的项目键，读侧也不自动检查表中的有效条件（Validity）。第20章让A/B由不同状态根（State Root）承载，才在那项部署条件下分开材料。旧条目归档（Archive）与新条目追加是两次提交（Commit），不是上述教学转换的一次数据库事务（Transaction）。

少量明确规则可从可审阅条目及作用域（Scope）开始；自动跨任务（Task）积累再考虑Codex的两阶段记忆管道（Memory Pipeline），同时计入资料到达延迟和语义错误风险。若要立即撤销已组装请求，还须另处理取消（Cancellation）、重新组装与正在发生的行动请求（Action）；存储更新不能撤销已发生的外部效果（External Effect）。

9. 条件变化后的参考结论

问题一：工具输出（Tool Output）从100k字符降到2k，就能说压缩（Compaction）更好吗？

不能。要比较词元（Token）与总成本，还要检查失败定位、约束保留、回读次数及任务成功（Task Success）。2k文本若遗漏关键失败，可能让系统更贵且更不准确；长度只是一个量。

问题二：把每次对话摘要（Summary）追加到长期文件，会有什么问题？

临时状态不断累积，旧偏好难撤回（Revocation），冲突材料可能同时进入模型输入（Model Input），不可信内容也可能被无选择保存。应先规定写入价值、来源（Source）、作用域（Scope）、更新与读取规则。

问题三：读取到已撤回（Revoked）条目，应把旧值作为当前偏好吗？

通常不应。撤回（Revocation）记录仍可解释历史（History）、防止旧缓存（Cache）重新激活，但保存历史（History）与注入当前有效背景是不同决定。

跨实现问题：用“都是把历史（History）摘要（Summary）写入记忆（Memory），然后继续”概括产品，漏了什么？

它混淆窗口管理（Window Management）与长期写入，还漏掉Codex条件换窗及不同产品的按需读取。先解释本次请求怎样继续，再解释哪些信息跨任务（Task）保存、何时读取；文件或工具存在都不证明已被实际消费。

Letta的新记忆（Memory）没有影响回答，可能断在哪三处？

一是修改未提交（Commit），没进入按已提交版本编译的材料；二是目录可见，智能代理（Agent）没主动读取正文；三是正文已读，却没正确理解适用规则。重跑存储测试不能回答后两项。

五种变化，分别检查存储、输入与行动

沿用第20章的E0/r0 → 归档（Archive）/r1 → 追加E1/r2。以下是选定实现与给定条件的推演，不是新增运行结果。

E1从工作区作用域（Workspace Scope）改为会话（Session）S1后，S2能否读到？若仍用工作区作用域（Workspace Scope），但把B迁到A的同一状态根（State Root），是否仍自动隔离？

S2不匹配 sessionId，不能由该投影（Projection）获得E1。工作区作用域（Workspace Scope）没有项目硬过滤，同一状态根（State Root）的B可能得到A正文。文本项目名可以提示模型（Model），不能充当确定性隔离；缩到会话作用域（Session Scope）又不能自动满足跨会话（Session）延续。

在新工作轮次（Turn）捕获提示词（Prompt）前关闭 agentReadEnabled，已保存的E1会怎样？

存储（Storage）保留E1，读取门阻止本次本地记忆笔记（Local Memory）正文注入。模型（Model）仍可能从当前文件、消息（Message）或其他材料选择 make check，所以命令正确不证明记忆（Memory）生效。题目把时点放在捕获之前，不混入已缓存请求。

Turn-0已捕获E0，之后才归档（Archive）。旧输入会自动改变吗？若r1成功、r2失败，怎样报告？

不会。会话（Session）/工作轮次（Turn）的缓存（Cache）不因文件归档（Archive）自动刷新，也不会删除旧历史（History）或撤销已发送请求。r1/r2是两次提交（Commit），应报告旧规则已归档（Archive）、新规则未保存，再回读状态处理剩余工作，不能称替换完成。

条目化长期记忆（Atomic LTM）显式 remember 创建了 make check 条目，再开启本地记忆笔记（Local Memory）读取，能证明什么？

不能证明旧条目已替换，也不能证明下一请求会用新命令。当前提取（Extraction）创建新条目；独立变更接口可更新或归档（Archive），不表示提取（Extraction）已经调用它。主执行链没有条目化长期记忆（Atomic LTM）的自动召回（Recall）与输入注入（Context Injection），本地记忆笔记（Local Memory）开关控制另一消费者（Consumer）。

Codex后台整理已启动，为什么当前工作轮次（Turn）仍可能没有新摘要（Summary）？

功能开关等条件先决定是否启用；刚结束的更正还可能未达到默认6小时空闲门槛，或未进入本次有界认领（Bounded Claim）。后台整理与后续初始上下文（Initial Context）消费不是当前工作轮次（Turn）必须等待的同步链。资料到达、整理正确、摘要（Summary）被装入是三个条件；摘要（Summary）也没有当前项目硬过滤，仍需保留范围并判断适用性。

10. 选读：递归语言模型（RLM）怎样使用窗口外材料

前面的有界读取（Bounded Read）已说明，模型（Model）不必同时看到全部材料。递归语言模型（Recursive Language Model，RLM）把原输入留在外部程序环境，让根模型（Root Model）写程序选择片段，必要时发起子模型调用（Sub-model Call），并在外部状态（External State）中保存和组合中间值。“根”负责组织本次计算，“子”处理程序给定的输入；交互式解释环境（Read–Eval–Print Loop，REPL）能连续执行代码并保留变量。这些机制对应原论文第2节与算法1、2。

普通工具智能代理（Tool Agent）也可以主动检索、编程与汇总。这里应比较原文、中间值、子模型调用（Sub-model Call）及最终结果怎样连在一起，而不把两者简化成主动与被动的对立。下面只用六条短记录展示关系，不声称这么短的材料必须采用递归语言模型（RLM）。

先固定输入和判定规则

任务（Task）是按模块统计“操作已成功，界面却提示失败”的反馈，并列出记录标识（Record ID）。只有实际成功与失败提示同时出现才算；操作失败、重复执行、提示成功但实际失败，都不属于本题目标。完整原文保存在外部变量 records：

先解释程序职责，再看完整过程

程序分三步：两次子模型调用（Sub-model Call）分别判断片段；普通程序检查标识覆盖及标签（Label）类型；检查通过后按模块计数。合并（Merge）、检查与保存由程序完成，不是另让模型（Model）自由重写结果。下面是完整教学伪代码（Pseudocode），没有实际运行模型（Model）：

# 1. 给子调用规则及其负责的片段。
左结果 = judge(判定规则, records中的R1到R3原文)
右结果 = judge(判定规则, records中的R4到R6原文)
# 2. 检查覆盖与类型，再保存标签。
检查每份结果：ID恰好覆盖对应片段，没有重复；判断值只能为真或假
若检查失败：返回有身份的错误，不生成最终统计
labels = 按ID合并左右结果，保存在外部变量中
# 3. 程序按标签聚合，不让模型猜计数。
selected = {支付: [], 上传: []}
逐条读取records：若labels中该ID为真，将ID加入对应模块
Final = 各模块的入选数量及ID列表
输出给根调用的简短观察 = “已处理6条；覆盖检查通过；Final已建立”

设教学子模型调用（Sub-model Call）返回左结果 {R1:真, R2:假, R3:真}、右结果 {R4:假, R5:假, R6:假}，程序得到：

Final = {支付:{数量:1, ID:[R1]}, 上传:{数量:1, ID:[R3]}}

返回的是已经建立的外部值，根模型（Root Model）不必根据“处理了6条”的短观察猜出原文与标识（ID）。缺少R3会触发覆盖检查（Coverage Check）；六个标识（ID）齐全但误把R5标真，则结构检查仍通过。程序合并正确与语义判断正确，仍是不同保证。

根模型（Root Model）的历史（History）不会被这条回边清空：后续输入还包含此前代码与有界输出或元信息（Metadata），并非永远只有初始描述。本例选择外部变量返回；原论文附录C的具体提示也允许直接返回答案，不能把 Final 当作所有实现的唯一出口。

什么时候值得采用，预算（Budget）落在哪里

本例自然语言表述不同，子模型调用（Sub-model Call）负责局部语义解释，普通程序负责分组、计数与标识（ID）合并。若原数据已有可信的 actual_success=true 与 displayed_failure=true 字段，直接筛选计数更简单；材料很短时，单次模型（Model）判断也是合理比较基线（Baseline）。

本例最多两次子模型调用（Sub-model Call），每次只含三条记录及规则，失败直接返回错误。根模型调用（Root-model Call）与每个子模型调用（Sub-model Call）分别受输入、输出、时间及费用预算（Budget）约束。外部保存不扩大单次模型（Model）窗口，根模型（Root Model）的代码历史（History）还会增长；程序执行、子调用及复核都要计入总成本。

切分（Partitioning）也可能割裂关联：若R3的“文件”必须借R4才能解释，就应改变片段边界或保留关联证据。本节展示输入与计算的组织，没有声称某产品已实现此机制、运行过本例模型（Model），或证明它优于简单程序；理解选读部分不作为后续课程前提。
