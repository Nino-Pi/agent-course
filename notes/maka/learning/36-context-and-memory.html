第 36 章｜上下文与记忆的设计取舍

本章概览

核心问题：同一份历史怎样分别服务当前决策与未来任务，压缩、保存和使用为何不能合并？

关键概念：工作上下文：下一请求所选材料；压缩切点：保留历史的合法边界；长期记忆：跨任务复用的信息；作用域与撤回：限定规则何时有效；外部工作状态：放在模型窗口之外、可由程序读取和处理的材料。

关系主线：从输入选择与压缩推进到记忆的写、读、用，以 Maka、Pi、Letta 对照成立条件；章末选读再解释外部材料和模型子调用怎样组合，仍需检查最终效果与预算。

第19章已经区分完整历史与下一次模型真正收到的输入：摘要可以帮助继续，却可能遗漏约束。第20章又把长期记忆的保存和读取分开：条目写入成功，不保证新任务已经使用。本章把这两条链放在同一项修复中，回答一个设计问题：当前放不下的材料该怎样处理，其中哪些信息又值得留给未来？

下文先走当前输入与压缩，再走跨任务记忆；两者各用具体实现解释，不要求把产品字段混成一套。后面的第53章 请求组装、第54章 压缩和第55章 Memory会进一步展开对应设计，本章不以这些后续内容作为已掌握的前提。

1. 对同一条信息问三次用途

假设测试返回一份很长的日志，其中只有两条失败断言与当前修复有关。

表 1 / Table 1 · 1. 对同一条信息问三次用途
层次要回答的问题本例中的内容
原始事实与产物（Facts / Artifacts）发生了什么，细节怎样回查命令、参数、退出信息、完整输出与资源版本
工作上下文（Working Context）下一步模型需要什么用户目标、当前约束、两条失败、相关代码及未完成项
长期记忆（Memory）哪些信息对未来任务仍有价值稳定的项目测试入口、经确认的用户偏好；不必保存整段临时日志

这三层可以引用同一个来源，但生命周期和更新规则不同。压缩改变本次或后续模型请求的输入表示，不自动等于长期记忆写入；保存长期条目，也不保证下次一定读到或正确使用。

还有一个更远的问题：即使读到了，保留经验是否让后续任务更好？需要把同一实例在“保留跨题经验”和“开始前重置经验”两种条件下配对，而不能只看后面的题答对了。后面第46章的完整演算会给出正收益、旧规则误用和全部费用；本章先把可保存、可读取、可使用的链条讲清。

2. 先管理输入来源，再选择压缩方法

输入选择要按下一步任务所需分配预算。当前用户要求、文件中的任务数据和检索到的说明属于不同信任来源。把它们拼到一起时仍要保留身份，不能因某段资料写着“忽略限制”就把它升级成授权。

先从总量约束推导预算。设输入与输出共享的总上下文窗口为 WWW，输出预留为 OOO，协议、工具定义与固定上下文合计为 FFF，安全余量为 SSS。四项使用同一种 token 计量；FFF 与待选择的动态材料不得重复计数。动态材料的实际用量记为 DDD，请求需满足：

D+F+O+S≤W.D+F+O+S\leq W.D+F+O+S≤W.

把已经占用或预留的部分移到右边，得到动态材料的上限：

D≤Bdynamic=W−O−F−S.D\leq B_{\mathrm{dynamic}}=W-O-F-S.D≤Bdynamic​=W−O−F−S.

教学算例取 W=32,000W=32{,}000W=32,000、O=4,000O=4{,}000O=4,000、F=6,000F=6{,}000F=6,000、S=2,000S=2{,}000S=2,000，动态预算为20,000 token。若相关文件与日志合计22,000 token，就还需减少至少2,000 token；保存材料的位置不变，改变的是本次选入量。这些是便于推导的虚构配置。若算出的预算为负，连固定部分与预留都无法同时容纳，不能把动态用量设为0就宣布请求可发送。

实际估算要用所用模型和请求格式对应的 token 计算，不能把字符数直接当 token；工具定义、图片和协议包装也可能占预算。

如果接口另有独立的最大输入或最大输出限制，也必须同时满足；此时不能仅凭共享窗口公式判定请求可发送。输出预留也应包含该接口计入输出预算的其他生成开销。

如果文件只需十行，先有界读取。若日志只有少量相关结果，先提取和回读。只有在相关历史本身也无法容纳时，才需要更强的摘要、窗口替换或其他输入管理策略。

代码尚未进入窗口时，选择算法见《代码不在窗口里：Aider 的仓库图怎样选择上下文》：它讨论先选哪些符号，与下面整理已发生历史的位置不同。

“先选材料”还可借鉴搜索与推荐，但要对齐阶段：材料生产者（Producer）产生并保存文件/观察，索引组织可查对象，召回提出候选，消费者再把有身份的证据放进 prompt。代码关系图、文件目录树和向量近邻是不同选择方法；向量近邻按材料的数值表示寻找距离较近的候选。若失败日志根本没进候选，扩大窗口无济于事；若已进候选却被重复片段挤掉，先查重排与预算。本章后文展开 Letta 的文件树，第37章展开 Aider 的代码关系图。通用原理和一个完整数值例子见《Agent 检索与搜索、推荐》，其中还区分近似最近邻（ANN）搜索找回精确近邻的比例、业务召回和必要证据覆盖。

3. 真实算法一：Pi 怎样把一个长 Turn 分开

Pi 不只保存一串聊天文本。会话条目（Session entry）有 id/parentId，当前分支是沿父指针得到的路径；一次 compaction 保存 summary 和 firstKeptEntryId，后者指向仍应逐字保留的第一条 entry。这样可以在完整 Session 记录仍存在时，单独重建较短的模型输入。下面走 Pi 的默认 compaction 路径；扩展可以替换它。

阅读这条算法时先抓住三个问题：预算把切点推到哪里，工具调用与结果是否仍成对，被切走的用户要求怎样回到下一次输入。下文的计数、合法边界和摘要分别回答这三个问题；单看剩余 token 数不能判断压缩是否合格。

先固定下面这份历史。本表的 token 数是为走算法人为给定的估算结果，不由字符数换算，也不是模型测量：

表 2 / Table 2 · 3. 真实算法一：Pi 怎样把一个长 Turn 分开
位置实际内容/关系给定估算
H1–H4已结束的旧调查：读 package.json，确认 npm test本次会进入旧历史摘要
H5新 user：只改 README，运行测试，中文汇报当前 Turn 起点
H6assistant 调用 Edit，id=E1200
H7E1 result：README 已修改1,000

H9B1 result：8,000 token 的日志，测试失败8,000

假定 keepRecentTokens=9,000。findCutPoint 从末尾累加：H9 后是 8,000；加 H8 是 8,200；加 H7 是 9,200，首次达到目标；代码条件是 accumulatedTokens >= keepRecentTokens，恰好相等也停止。不能从 H7 开始保留，因为它是工具结果，会失去 H6 的调用。Pi 在该位置及之后寻找合法切点，选择 H8；H8/B1 与 H9/B1 一起保留。注意这会留下约 8,200，而不是严格不少于 9,000：keepRecentTokens 是寻找边界的目标，合法切点仍会改变结果。

接着 prepareCompaction 发现 H8 不是新 user，而处于 H5 开始的同一 Turn，于是形成两组输入：旧历史 H1–H4，以及当前 Turn 已被切走的前半段 H5–H7。compact 分别生成旧历史摘要与 Turn-prefix 摘要，再合成一份 summary；还从工具调用及前次 compaction details 汇总读过、修改过的文件。理想的本题摘要应说“测试入口为 npm test；本轮只准改 README、中文汇报；README 已改”，不应预言 H9 的测试成功。真正的失败正文仍在保留尾部中。

SessionManager 追加 compaction entry 后，buildContextEntries 沿当前分支选择最近 compaction，输出“摘要 entry → 从 H8 起的保留项 → compaction 后的新项”，再转换成模型消息。它没有从磁盘删除 H1–H7，也没有把完整旧日志偷偷追加回当前输入。旧 summary 会作为以后增量总结的输入，避免每次重读全部历史；相应代价是早期遗漏可能随滚动摘要继续传播。

协议完整但约束遗漏： 如果摘要漏了 H5 的 README-only 限制，工具 pair 仍完整，任务语义却没有保住。边界选择保护协议结构，Turn-prefix 摘要承担被移出原文的语义；两者是不同职责。若 H9 本身几乎占满窗口，保留它也可能无法解压，需比较结果裁剪或另一种范围策略。

4. 摘要不是直接覆盖当前工作状态

这是可供设计的流程。Maka 使用持久 checkpoint；Pi 上节是追加 entry 再重建输入，Codex 又有自己的活跃状态与 rollout 顺序。不能把此图的每个提交点套到所有产品。

生成候选期间，用户可能修订约束，历史也可能增加新结果。因此，应用前要复核候选覆盖的范围、保留尾部和有效约束代次。若过期，应重新生成、合并新事实或放弃候选。要把“复核后切换”做成可靠保证，还需要负责工作状态的 owner 协调检查与提交；两个独立的先检查后写入操作仍有竞争窗口。

如果摘要任务本身超窗，必须先减小摘要输入或选择其他受控路径。无限重试同一个过大请求不会改变条件。若摘要缺少当前约束，应修正或回退，不能以“token 降了很多”宣布成功。

压缩后的行为评估至少包含四类检查：目标有没有保留，用户约束是否遵循，必要细节能否回读，最终任务是否正确完成。自动语义评判可以辅助发现问题，但不能把另一个模型的“看起来完整”当作严格保证。

5. 长期 Memory 是写、存、读、用的双链

写入链需要决定什么值得存，读取链需要决定当前任务应使用什么。两边之间只有一条“存储存在”的连接，不会自动产生正确行为。

下面是治理用教学类型，旨在暴露需要决策的字段，不规定数据库。先按三个职责读：身份与内容说明“存的是什么”，范围与来源说明“凭什么用于这里”，状态与版本说明“现在是否仍可采用”。它只描述一条记录，实际筛选和更新仍由消费者执行：

type MemoryItem = {
  // 身份与内容：区分条目，并定位同一类问题。
  id: string;
  key: string;
  value: string;
  // 范围与来源：这条信息适用于哪里、依据何在。
  scope:
    | { kind: "global" }
    | { kind: "workspace"; workspaceId: string };
  source: { kind: "user_statement" | "observed_fact"; ref: string };
  // 有效状态与更新版本；字段存在不等于已实现筛选或并发提交。
  status: "active" | "revoked" | "conflicted";
  revision: number;
  validUntil?: string;
};

有了 revision 不代表已经解决竞争；写入还要约定条件更新如何提交。source 可以帮助回查，但不自动证明内容永远正确。项目测试入口可能变，偏好可能撤回，来自外部文件的文本也不应自动变成长期指令。

写入也受预算约束。 一段候选记忆来源可靠，也可能因为文件太大、目录太深或缺少索引而不能提交；反思模型生成成功，也可能在合并时失败。因此至少分别记录 candidate_generated、admission_passed、committed、read_into_context，不要用一个 memory_saved 包办。这里是教学状态名，不是某产品事件 schema。

例子：后台整理生成了 30 条偏好，提交校验拒绝根目录的常驻内容超限。正确处理是保留失败与候选，按范围整理并重新审核；不能标记“用户已记住”，也不能立即无限重试。读取预算控制本轮输入，写入预算控制长期存量，两者约束不同。若移入别的 Agent 历史，还要检查旧工具与权限环境是否仍成立。

真实算法二：Letta Code 怎样让文件变成下一轮可用的 Memory

另设一个跨会话情境：把当前项目叫作工作区 A，已有偏好是“一般用中文，A 用英文”；用户在新会话只说“解释 README 的测试结果”，没有指定语言。这与 H5 明确要求中文的那一轮不同，H5 当轮仍应遵从当前要求。选定 Letta Code 本地后端中以文件组织记忆的 MemFS 分支来走读。该分支使用 system/；根目录 MEMORY.md 布局属于另一种格式分支，不能混成“Letta 一律这样读”。示例文件名和中文内容由课程设计，选择及编译算法来自源码。

system/preferences.md   正文：一般解释用中文；按工作区检查例外
workspaces/A.md         正文：A 的解释用英文；来源是用户 T20

第一步是模型或用户明确决定修改什么。memory 工具接收 create/str_replace/insert/delete/rename 等操作和非空 reason；它核对目标在记忆仓库（Memory repo）内、仓库可写且干净，修改指定正文，再调用 commitMemoryWrite 提交受影响路径。因此这条写入链是“定位文件并编辑”，没有先调用向量库自动推断应更新哪条旧事实。若只改了工作树但未提交，不能把它当成后续默认背景已经改变。

第二步是选择。collectCommittedMemoryFiles 用 Git 列出当前已提交版本（HEAD）中的 Markdown，再读取其已提交内容。renderMemfsProjection 把 system/ 文件正文放入记忆输入块（memory block）；其他非 Skill 文件只贡献目录树，不自动贡献正文。下一 Turn 的 getOrCompileSystemPrompt 比较原 system hash 与 Memory revision：相同则复用；变化则重新编译，支持中途 system 更新的分支还可发出更新片段。调用者随后从 resolveSystemPromptForTurn 得到这一轮的系统材料。

这意味着 A 的新任务初始能看到“中文默认、存在 A.md”，却未必已经看到“A 用英文”。Agent 仍须根据目录及常驻提示选择 A.md，调用文件读取，把返回正文作为新工具观察带入后续请求，才有机会正确选择英文。目录存在 → 读过正文 → 用于回答是三步，宿主的文件树并不替模型完成后两步。若 A 是高频场景，可以把短例外晋升到常驻文件；这样减少漏读，却让每次任务都承担它的输入成本。

第三步是更新。用户撤回 A 的例外时，应改掉或删除该文件中的有效规则，并同步常驻发现线索；只在别处追加“现在跟随全局”，会让两份材料继续矛盾。后台 reflection 的另一条写入链是读取 transcript 与已有记忆，在独立 Memory worktree 中筛选、修改、提交，再整合回父仓库。其内置 prompt 要求纠正旧条目、维护索引，但这是模型执行的整理方法；Git 合并只处理文件变更，不能证明它正确理解了“撤回”。

这条路线的价值是可读、可编辑、能把常驻成本和按需成本分开；薄弱处是发现线索、文件组织和模型主动读取。与它相比，Maka Local 是受控条目投影，Codex 有 rollout 提取/整合和有界摘要入口；Claude Code 的索引读取来自官方产品合同，不能补写出未公开的事务算法。

同一命令变更：用知识记录区分“提交成功”和“仍然有效”

接续 第20章：用户将 A 的测试入口从 pytest 改为 make check，B 仍用 pytest。先把需要判断的内容写成一个教学模型：

m = (scope, key, value, validity, source, status)
    适用范围、信息类别、内容、有效条件、来源、当前状态

这里不是 Maka/Codex 的实际 schema。scope 可以在设计中表达项目 A；key=test-command 让不同措辞的规则仍可被当作同一问题；validity 描述何时或在哪种环境下成立；source 指向用户明确声明或独立核验的观察；status 表示 active、撤回或待解决冲突。把字段列出来只暴露问题，不会自动实现解析、时效检查或可信性判断。

固定三条记录：A0=(A, test-command, pytest, 原规则适用期间, 旧声明, active)，B0=(B, test-command, pytest, B 原规则仍适用, B 的声明, active)；用户更正后，A1=(A, test-command, make check, 更正生效后, 新声明, active)。A0/A1 对应 第20章 的 E0/E1，但这里使用教学记录形式。教学更新决定将 A0 标为撤回，保留 B0，让 A1 生效。本题将这项撤回决定落为 第20章 的归档操作；教学上的知识状态与真实存储状态仍分别解释，不表示所有归档都证明原知识为假。对没有重述测试命令的新请求，可手算选择过程：

候选集合是本题给定的，不宣称任何检索器一定找到它们。有效条件不明、或留下两条相互矛盾的 active 规则时，选择器应暴露冲突并回查当前项目说明或请求澄清，不能把“最后存入”当成永远正确。当前任务的明确要求也可以改变本次行动，不自动代表用户要求永久改写 Memory。

再落回真实 Maka：Local 的 workspace 没有本题的项目 key，读侧也不自动检查这里的 validity；第20章 用不同 State Root 承载 A/B，才在该部署假设下保持两套材料分开。更正通过归档旧条目与追加新条目分别提交，不是上述逻辑状态转换的一次数据库事务。即使追加 A1 的 CAS 成功，若操作人忘了归档 A0，两条冲突规则仍可同时 active；反之，正确的语义决定遇到旧 revision，也不能绕过提交冲突。语义有效性与并发提交有效性是两种保证。

采用判断也因此具体：少量明确规则先用可审阅条目，并定义作用域；需要自动跨任务积累时，再考虑 第20章 所讲 Codex 两阶段管道的选源与后台整理，同时接受资料变新的等待窗口和语义错误风险。若目标是立即撤回已组装的请求，应另设计取消、重新构造及动作处理，不把存储更新当成撤销命令。它也不能消除已发生动作的外部效果。

9. 条件变化后的参考结论

题一：工具输出从 100k 字符降到 2k，就能说压缩更好吗？

不能。需要比较 token 和总成本，也要检查失败定位、约束保留、回读次数与任务成功。2k 文本如果遗漏关键失败，可能让系统更贵且更不准确。

题二：把每次对话摘要追加到长期文件，有哪些问题？

临时状态会不断累积，旧偏好难撤回，相互冲突的事实可能一起被注入，敏感或不可信资料也可能被无选择保存。应先定义写入价值、来源、范围、更新和读取规则。

题三：当前读取到 revoked 条目，应把它作为回答背景吗？

通常不把其旧值作为当前有效偏好；撤回记录仍可用于解释历史和避免旧缓存重新激活。存储保留与模型注入属于不同决定。

跨实现问题：用“两个产品都是把历史摘要写入 Memory，然后继续”概括设计，缺少了什么？

混淆了窗口管理和长期写入，也漏掉 Codex 的条件换窗分支与两者的按需读取。应先解释当前请求如何继续，再解释哪些信息跨任务保存、何时取回；不能把文件存在或可选工具存在当作实际读取成功。

Pi 的结果缩短后，保留范围怎样变化？ 将 H7 的估算改为 600，keepRecentTokens 仍为 9,000，H6=200，H5=100。以下是给定数字的算法推演，没有运行产品。

H9=8,000，H8 后 8,200，H7 后 8,800，H6 后 9,000；H6 本身是合法 assistant 切点，所以保留 H6–H9。旧历史摘要为 H1–H4；Turn-prefix 摘要只覆盖 H5，必须保留 README-only 与中文要求。

Letta 的新记忆没有影响回答，可能断在哪三处？

一是修改尚未提交，没有进入按已提交版本编译的输入；二是目录虽可见，模型没有发现或主动读取正文；三是正文已读，却缺少正确的规则范围或被错误解释。重新运行同一条存储测试，不能回答后两项。

Memory 的五种条件变化。 沿用第20章的 E0/r0 → 归档/r1 → 追加 E1/r2；以下结论来自选定实现链的推演，不是新增运行结果。

E1 原用 workspace scope。改为 session=S1 后，新 S2 会不会读到？如果仍用 workspace，但把 B 迁到 A 的同一 Root，是否仍保证 A/B 自动隔离？

S2 不匹配 sessionId，不能由该投影获得 E1。workspace 条目则没有项目硬过滤：同 Root 的 B 也可能获得 A 的正文。文本中的项目名可以提示模型，但不能充当确定性的隔离；把 scope 缩到 Session 又不能自动满足跨 Session 延续。

在新 Turn 捕获 prompt 之前关闭 agentReadEnabled，E1 已经保存。存储、Local 输入和模型可能采取的行动分别怎样判断？

存储中的 E1 保留；读取门阻止本次 Local 正文注入。模型仍可能从当前文件、消息或其他输入选择 make check，所以仅看命令正确不足以证明 Memory 生效。题目把关门时点放在捕获之前，避免混入已缓存请求的另一种情况。

某次 Turn-0 已经捕获 E0，之后才归档 E0。Turn-0 的输入会自动改变吗？若 r1 成功、r2 失败，应如何描述保存结果？

不会。Session/Turn 缓存不因文件归档自动刷新；归档也不删除旧历史或撤销已发送请求。r1/r2 是两次提交，应报告旧规则已归档、新规则尚未保存，重新检查状态后处理剩余操作，不能假报替换完成。

换用 Atomic 的显式 remember 创建了 make check Item，再开启 Local 读取。是否证明旧 Item 被替换、且下一请求会用新命令？

两点都不能证明。当前 extraction 创建新 Item，不自动语义替换；独立 mutation 的 update/archive 能力不能当作 extraction 已调用它。这里的主执行链没有 Atomic 自动 recall/injection，Local 读取开关控制的是另一套 bundle 消费者。

换用 Codex 的两阶段记忆管道，用户的更正刚刚结束。为什么成功启动后台整理仍不能保证当前 Turn 已看到新摘要？

总 feature 等条件先决定是否启用；即便启用，更正还可能未达到默认 6 小时空闲门槛，也可能未进入本次有界认领。后台整理与后续 initial-context 消费不是当前 Turn 必须等待的同步链。新资料到场、模型整理正确、摘要被装配，是三个独立条件。摘要没有当前项目硬过滤，还需材料保留范围并由模型判断适用性。

后续工作安排见第39章持续工作与协作，方案比较见第40章整项任务评价。

10. 选读：RLM 怎样把原文和中间结果留在窗口之外

前面的有界读取已经说明：模型不必一次看到全部材料。递归语言模型（Recursive Language Model，RLM）进一步把长输入放进可持续使用的程序环境，让根模型写程序选择片段，必要时调用子模型，再把中间结果留在外部状态里组合。这里的“根”指负责安排这次计算的模型；“子”指由程序发起、只处理规定输入的模型调用。REPL 是能够连续执行代码并保留变量的环境。

关键区别要沿存放位置和消费者看，不能简化成“普通归档被动、RLM 主动”：普通工具 Agent 也可以主动检索、写程序和汇总。RLM 的这种组织方式把原输入、中间值、程序化子调用与最后返回连接起来。下面特意用六条短记录展示关系，并不声称这点文字已经需要长上下文技术。

输入与判定规则。 任务是“按模块统计操作已成功、界面却提示失败的反馈，并列出记录ID”。只算实际成功与失败提示同时出现；操作本身失败、重复执行、提示成功但实际失败，都不算本题的目标。完整记录保存在外部变量 records 中：

表 7 / Table 7 · 10. 选读：RLM 怎样把原文和中间结果留在窗口之外
ID模块原始反馈本题参考判断
R1支付扣款成功，页面却提示未支付。是：实际成功、界面报失败
R2支付银行拒绝付款，页面提示失败。否：实际付款没有成功
R3上传文件已在列表中，但弹窗说上传失败。是：文件已出现、界面报失败
R4上传网络中断，列表无文件，弹窗提示失败。否：实际上传没有成功
R5支付重复扣款两次，但页面显示成功。否：有其他问题，却不是本题的失败提示
R6上传页面显示上传成功，刷新后文件不存在。否：实际失败、界面提示成功，方向相反

右列是供读者核对的参考答案，不传入子模型。根调用初始得到任务规则、记录数、字段说明和访问变量的方法；原文仍在 records。程序环境提供受控的 judge 子调用，输入是规则与指定片段，输出是逐ID判断。先由两次子调用产生标签，再由程序检查覆盖，最后按标签分组计数。下列是教学伪代码，其中“合并”“检查”“保存”由程序执行，不是再次让模型自由改写结果：

# 第一阶段：只把各片段的规则和原文交给子调用。
左结果 = judge(判定规则, records中的R1到R3原文)
右结果 = judge(判定规则, records中的R4到R6原文)
# 第二阶段：检查结构后，才将标签写入共享的外部结果。
检查每份结果：ID恰好覆盖对应片段，没有重复；判断值只能为真或假
若检查失败：返回有身份的错误，不生成最终统计
labels = 按ID合并左右结果，保存在外部变量中
# 第三阶段：普通程序按已检查的标签聚合，不再要求模型猜计数。
selected = {支付: [], 上传: []}
逐条读取records：若labels中该ID为真，将ID加入对应模块
Final = 各模块的入选数量及ID列表
输出给根调用的简短观察 = “已处理6条；覆盖检查通过；Final已建立”

设本次教学子调用返回左结果 {R1:真, R2:假, R3:真}、右结果 {R4:假, R5:假, R6:假}。程序据此保存 Final = {支付:{数量:1, ID:[R1]}, 上传:{数量:1, ID:[R3]}}。实际返回的就是这个外部值，不需要根模型根据“处理了6条”的计数猜出原文和ID。若缺了 R3，覆盖检查会报错；若六个ID齐全但把 R5 错判为真，结构检查仍会通过，因此还需要语义评价，不能把“程序合并正确”当成子模型判断必然正确。

图中的回边不会把根历史清空。根模型的后续输入还包含它此前生成的代码及有界的执行输出或元信息，不是永远只看初始 metadata。这个例子选择外部变量返回路径；RLM 论文的具体实现也允许模型直接给出答案，不能把 Final 变量当成所有实现的唯一出口。

何时值得用。 这个例子的判断来自不同自然语言表述，子调用用于局部语义解释；分组、计数和ID合并交给普通程序。若输入本来就有可信的 actual_success=true 与 displayed_failure=true 字段，直接筛选计数更简单，无需为了体现递归再调用模型。材料很短时，单次模型判断也是合理基线。

本例的预算边界。 预先限定最多两次子调用，每次只含三条记录和规则，失败后直接返回错误；根调用、每个子调用都分别受自己的输入、输出、时间和费用上限约束。完整材料留在外部不等于拥有无限模型窗口，根的代码历史也会增长；程序、子调用和再次核对都要计费。切分还可能割裂跨片段关系：如果 R3 的“文件”必须借 R4 才能解释，就应调整片段或保留关联证据。这里演示的是输入与计算的组织，不是某个产品已实现该机制，也没有实际运行模型或证明它优于简单程序。理解本节不作为后续课程的前置条件。
