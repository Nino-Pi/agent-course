第 15 章｜模型输入与上下文组成

本章概览

核心问题：系统保存过的信息，为什么不一定出现在这一次模型请求中？

关键概念：Context（上下文）是本次有限输入；有效历史是经选择与整理的记录；工具声明描述可请求的接口；ModelAdapter（模型适配器）转换服务协议；终止状态区分完成、截断与中断。

关系主线：组装基础与有效历史经过本次整形，再交给适配器；流式片段仍需完成与终止判断。保存、入选、发出和模型采用各有条件，不能把数据库内容或可解析参数当作全部保证。

持久记录与读取视图的区别见 事实与投影。

核心路径：跟着一次修复看模型视野

一次调用只获得本次准备的材料

聊天界面让人感觉模型一直记得前文。这里沿用前面只修 README、假设函数测试原本已通过的简化任务。沿第12章的循环顺序，用 Maka 的 Read/Edit/Bash 工具命名来看：

step 1：任务 + 工具说明 → 模型提出 Read
step 2：任务 + 已选历史 + Read 的结果 → 模型提出修改
step 3：任务 + 已选历史 + 修改结果 → 模型请求验证
step 4：任务 + 已选历史 + 测试结果 → 模型总结或继续修复

文件不会因为位于工作目录就自动进入模型输入。本例的文件内容要通过工具结果进入上下文，才能作为下一步的依据。有些模型服务还能接续自己保存的调用状态；这也需要明确的接续机制，不能从聊天界面推断模型自动知道本地文件。不同服务的接续信息还受到兼容性规则限制。

项目资料怎样被组织，见项目工作环境。两章关注相邻的两步：那里先决定“应该准备什么、放在哪里”，这里继续追踪“谁读取它、怎样选入本次请求”。文件已经存在、装载器已经读过、请求实际包含内容，是三个可分别检查的状态。

谁把这些材料放到一起

Maka 的 Host 为这项工作组成相对稳定的规则与能力基础，Runtime 在每个 step 根据持久事实和新观察准备模型输入。图中左侧是 Host 已组成的基础，中间是 Runtime 为本 step 选择的历史，最后由适配器转换为发给模型服务的请求。图中的 Memory 已经过读取与筛选；保存着却未被读入的内容没有这条入边。

这张图表达信息来源与组装责任，不表示网络请求按箭头顺序发送，也不表示每种来源各占一段文本。同一个 Turn 的规则与能力上限相对稳定，Read/Edit/Bash 的新结果则通过有效历史逐 step 加入；当前可用工具和剩余输入容量也可能变化。

如果 Read 的结果未进入有效投影，文件即使在磁盘上也不能沿这条链成为本次观察；Memory 未被读取同样不会因保存过就进入请求。组装后的请求仍可能超限或被 provider 拒绝，工具说明可见也不等于动作获准。

看到了说明，不等于已经执行或取得权限

模型可以看到 Read(path)、Edit(path, change)、Bash(command) 的说明，并据此表达行动意图。真正执行还需完成绑定、参数检查、实时权限和执行边界检查。Context 决定模型获得什么信息；执行边界决定某次动作被允许做什么。

模型不会自动看到工作目录的全部文件、Client 的整个屏幕、SQLite 的所有表、工具函数未返回的变量或未来的测试结果。长期记忆和外部文本也不能通过一句“可以访问任何目录”扩大权限。一项内容只有通过工具返回、历史选择或注入入口加入本次请求，才构成本次输入。

本次输入能支持什么判断

问题 1。 为什么不能仅凭 step 1 的回答，确认模型读过当前 package.json？

解释。 本例 step 1 只有任务和工具说明，没有当前文件的观察。即使碰巧答对，通用 JavaScript 知识或猜测也不能替代这次 Read 返回的内容。

问题 2。 History 和 Context 的差别是什么？

解释。 前者是保存过的事实，后者是本次经过选择和转换的模型输入。保存在库里不证明现在可见。

问题 3。 Edit 成功后为什么还要测试？

解释。 Edit 结果报告对应修改，测试结果才对程序行为提供观察；两者还都要说明实际覆盖范围。

问题 4。 工具说明进入 Context，能否绕过权限？

解释。 不能。接口说明让模型表达请求，执行时的实时边界仍决定是否允许。

问题 5。 保存了中文偏好，下一次就一定看得到吗？

解释。 不一定。还需要读取、选择和注入当前输入。不能从“能存”推断“本次已读”。

实现深化：从事实到某次 provider 请求

这一部分把输入与返回继续拆到协议层。第一遍先把握四层关系：参数片段逐步到达，完整调用项确认这项请求的内容，整次模型响应的结束状态决定如何处理候选，运行时的准入再决定是否实际执行。下文先解释各层，再用两个调用交错到达的八个事件展开；暂不熟悉协议字段时，可以先读每段解释与结论，之后回到事件表核对。后续工具章节仍需保留“参数看起来完整，不等于已经获准执行”的判断。

History 怎样变成 provider context

Runtime 从持久事件构造模型历史时，会应用两类调整：投影变换记录（projection transition）说明某份大结果怎样改用更短表示；摘要检查点（compaction checkpoint）说明哪段历史改用摘要。第19章展开这两类机制，本节先追踪它们如何参与一次请求。转换流程如下：

读取 RuntimeEvents 与 operational ledger 中的投影变化
  → 折叠有效的 tool-result projection transitions
  → 重放兼容的 compaction checkpoint
  → 按 model-history 规则准入并构造时间线
     （过滤、call/result 配对、reasoning 兼容性）
  → 转换成 provider-specific messages/state
  → 组成规则与工具、进行本次输入 shaping 并记录诊断

其中 projection transition 保证已经替换的大正文不会在下一 Turn 或冷启动时重新出现。

为什么 tool call 和 result 必须配对

如果 context 里只有：

模型请求 Edit(README.md)

却缺少结果，模型无法知道：

  • 工具尚未执行；
  • 执行失败；
  • 执行成功但结果丢失；
  • 因权限等待用户。

随意补一个成功结果会制造假事实；随意重做又可能重复副作用。因此投影必须尊重 durable pairing 和恢复状态。

为什么 provider compatibility 重要

某些模型供应商会为思考输出或调用接续（continuation）使用自己的不透明状态（opaque state，由服务解释、调用方不能当普通文本理解的状态）、签名或连接身份。这类状态不一定能安全迁移给另一 provider 或另一模型。Maka 在 replay/compaction 时会检查兼容性，而不是把任意二进制或 native state 当普通文本乱传。

模型回应也有“还没完成”的状态

模型边生成边发送工具参数，Runtime 什么时候可以执行？这取决于参数片段、完整调用项、整个模型响应的终止结果。一段 JSON 已能解析，只说明当前字节形成了一个对象，不证明模型已经结束这项调用，更不证明整次响应正常结束。

下面只比较 OpenAI Responses（模型请求与响应接口）的普通本地函数工具路径；请求不带旧调用的接续状态。Maka 的模型适配器把 messages 与工具说明交给 AI SDK（负责组织模型请求和解析响应的库）：普通工具提供 description/inputSchema，即用途与参数格式，没有交给 SDK 自动执行的 execute 回调。SDK 再把工具调用转为 Responses 的 call_id/name/arguments 等字段，参数在 wire（网络传输的协议表示）上是字符串。它负责协议表达；执行权仍在 Maka Runtime。

返回时也有三份责任。@ai-sdk/openai 按 output_index 将交错片段分配给各次调用，并从 output_item.done 的最终 arguments 形成调用；Maka ModelAdapter 把 SDK 事件变成统一事件，并另外形成 ModelStepOutcome，即整次模型响应的终止判断；AiSdkTurn 收集候选调用，等这个 outcome 后，完成分支才交给 ToolRuntime。普通工具的 input delta（参数增量片段）不会被 translateChunk 当成可执行调用发给 Runtime。JSON / schema 处理仍可能失败或转入 repair / invalid 路由，下面的主例假定最终参数合法，不能推广成“每个 SDK tool-call 都通过了所有检查”。

坏参数最后交给谁处理

换成当前 Maka 的准确内置名称 Read，模型最终给出 {}：既没文件 path，也没合法 resource ref。SDK 校验失败后调用 Maka 的 repair，通常将它改为内部 invalid 工具，保留调用身份，把错误说明放进参数。这里的“修复”是把无法执行的提议转换成可反馈的错误，没替模型猜出路径，也没运行原 Read。

若普通准入门和持久写入都成功，内部 invalid 自己经过 T1，随后抛出错误，由 Runtime 形成 error T2；错误再进入后续模型可读的投影。模型可以依据反馈重新提议，但这不保证新参数正确。另一条分支是 SDK 仍返回带 invalid:true 标记的原调用：Maka 不直接保留该标记，Runtime 还会按工具实际 schema 校验；在那里拒绝则是无 T1 的 preflight 结果。内部工具名、SDK 标记、实际执行原工具，是三件不同的事。

同批 A 参数错、B 合法，也不自动整批取消。在模型已完整结束、账本可读和其他门允许的条件下，两调用分别结算，B 仍能继续自己的执行。这个批次不是事务；提交故障不能倒推已经开始的 B 没有效果。下面八事件例使用合法参数，单独比较流与终止政策。

随后两者怎样继续也应分开。Pi 把工具结果追加到 currentContext.messages，下一轮先做可选的 transformContext，再由 convertToLlm 转成 pi-ai 的通用消息；具体 provider 请求编码在适配器中随后发生。这是 Agent 层的输入处理，不能据此证明 Session 文件持久化。

Maka 等工具事件被消费，再读本 Turn 的 durable 事件，经有效投影 fold、replay plan 和消息物化，经过本次 shaping 才交给下一次 ModelAdapter.startStream。已保存结果也可能只以引用或摘要进入输入，不能把内存中的返回数组当成下一次实际请求。

采用条件与终止分支问答

不同故障对应不同控制位置：调用身份混线要修协议归并；完整性或终止政策不合要求要修 outcome 与 dispatch 闸门；已经获得合法调用却越权，要检查 Tools 的实时授权。换一个 partial parser 不能同时修这三件事。服务端执行工具还可能在本地收到结果前已产生外部效果，本题“尚未 dispatch 所以没有执行”的前提只适用于上述普通本地工具。

题 1。 删除事件 5–8，只保留第 4 行 B 的完整 JSON 后断流。UI 已能展示 B 的全部字段，能否执行 B？若只把 B 的 done 补上，结论是否改变？

答案。 两次都不能据此进入本题正常工具执行：第一次缺 final item 和 response 终止；第二次有 final item，仍缺 response 终止。显示完整字段不是终止证据。应保留真实未完成/失败状态，重试策略另外判断，不能把 EOF 当成 response.completed。

题 2。 将本例两工具换成已注册、最终参数合法的普通本地写工具，保留“交错完成 item 后收到 length”的时序。业务提出“长度终止时，任何本地写操作都不得开始”，能否仅给解析器加更严格的 JSON 校验？能否把该承诺直接套到 provider 已执行的远端操作？

答案。 不能只改解析器：本例参数已合法，差异发生在 outcome→工具结算政策，应在那里定义允许集合、拒绝反馈与下一轮行为；Maka 当前分支不能直接宣称已有 Pi 的 length 门。该承诺也不能撤回服务端已经发生的效果，远端工具须另查效果证据与恢复合同。这是需要另行实现的策略，不能当成已有保证。

Context window：工作台空间是有限的

模型一次能接收的 token 数量有限，这个上限通常称为 context window。S1 越长，完整历史越可能装不下。

最粗暴的做法是删除最旧消息，但可能造成：

  • 工具调用只剩 result，没有 call；
  • 用户最初的约束消失；
  • 摘要覆盖边界不清；
  • 重启后无法解释删了什么；
  • 模型忘记任务尚未完成的部分。

Maka 使用上下文压缩（Compaction） checkpoint，把旧事实前缀投影为更短表示，同时保留原始 canonical events。这里的旧前缀（old prefix）是从历史起点开始的连续一段，原文尾部（raw tail）是它后面的记录；不是任意挑选几条旧消息拼成摘要。

canonical events = old prefix + raw tail

provider context = validated checkpoint(old prefix) + raw tail

Compaction 不是什么

  • 不是删除会话历史；
  • 不是隐私擦除；
  • 不是把 summary 当作新的唯一事实；
  • 不是长期 Memory；
  • 也不是允许模型自行决定覆盖任意事件范围。

Runtime 要验证 checkpoint 覆盖 exact prefix、没有切断 tool pair、没有包含 partial，并且可安全转成 provider messages 且兼容；实际能否装下由 provider 裁决。顺序强调“验证、先持久化、再应用投影”。

大型 Tool Result：保存事实与节省模型输入可以同时成立

Read 或 Bash 可能返回非常大的内容。如果每个后续 step 都原样重复，context 很快被耗尽。

Maka 可以在模型投影中用可回读引用替代大正文。当前新写入的归档引用（ledger archive）根据已保存事件和投影变换记录重建有效表示；旧式文件产物引用（Artifact ref）只保留读取兼容。归档后的输入变化是：

canonical tool response 仍然存在
provider projection 使用 maka://archive/... 占位
需要时由归档读取工具 ArchiveRead 按限定范围回读

关键顺序是先保证归档可用并写下 projection transition，再替换模型视图。归档失败时应保留原结果，而不是生成一个无法读取的假链接。

MEMORY.md 什么时候会进入模型视野

透明 Local Memory 有两个独立开关：

enabled            Memory 产品是否启用
agentReadEnabled   是否允许 Agent 把 active entries 放进 prompt

当前默认重点是：enabled = true 并不自动意味着 agentReadEnabled = true。只有读取被允许时，Host 才会选择 active entries、按 Session scope 过滤、做 secret redaction 和安全截断，再作为 <local-memory> untrusted block 注入。

为什么 Memory 被标成 untrusted

长期笔记可能包含旧信息、用户粘贴的外部文本，甚至类似“忽略之前安全规则”的内容。Memory 能提供背景，但不能因此升级成 system authority 或扩大工具权限。

Memory 提供信息
    不等于
Memory 可以改写安全边界

Atomic LTM 当前为什么不自动出现在下一轮

用户在 T7 中说“以后记住用中文”，模型可能调用 memory_remember，把带来源的结构化 Item 写入 memory.sqlite。

但当前 production 状态是：

Atomic LTM write / extraction / store query API  已存在
Agent recall / prompt injection                 尚未接线

因此 R8 的模型 context 不会仅因为 R7 成功写入 Atomic LTM，就自动多出“用户偏好中文”。MEMORY.md 与 Atomic LTM 目前也不会自动同步。

写入、查询和消费之间还缺少实际调用链：

数据能写入
  ≠ 有检索 API 就一定在用
  ≠ 已接入 Agent 每轮 context
  ≠ 用户体验上已经“会自动记得”

Workspace instructions 为什么不是 Memory

AGENTS.md、CLAUDE.md、GEMINI.md 等属于项目规则。它们由项目或用户显式维护，不是系统从聊天中学习出的个人事实。

统一案例里：

  • “测试前不得覆盖用户改动”可能来自 workspace instructions；
  • “用户偏好中文”更像 Memory；
  • “刚刚 Read 到的 scripts”属于当前执行历史；
  • “旧前缀的摘要”属于 compaction projection。

各类来源的维护者、刷新时机、作用域与信任级别不同；这些差异决定了它们怎样参与一次输入组装。

组成基础与本次请求组成分别记录什么

RunCompositionSnapshot 保存 composer/source revision、system/tool/availability/provider options hash、tool names 与 context window，回答“R7 采用了什么组装基础”。它是指纹，不是完整 prompt。

当前物理 ModelCallAttempt 保存 promptComposition，回答“这一次请求主要被哪些部分占据”：system instructions、tool definitions、messages、other 的序列化字节量，以及有界的具名 tool schema 大小。它在准备请求时折叠，适合分析工具 schema 是否挤占大量输入。

这里没有“保存一份可以逐字回看或原样重发的 prepared request artifact”。旧 PreparedRequestObservation 只继续解码历史记录；也不能把 byte/4 的 UI 估算称为 provider 实测 token。要解释具体工具结果，仍需沿 RuntimeEvent 与有效投影回查。

机制问题解析

为什么 compaction 不能随意拆开 tool call/result？ 它们是关联的协议单元。只留调用会留下未知结果，只留结果会失去来源；不能通过伪造成功补齐。

Local Memory 与 Atomic LTM 分别怎样进入下一次输入？ Local Memory 必须通过读取开关、scope 和安全投影；Atomic LTM 当前存在写链与查询 API，但没有生产 Agent recall/injection caller，保存不意味着自动出现在 R8。

RunCompositionSnapshot 与 promptComposition 能恢复完整请求吗？ 前者记录组装基础及版本/指纹，后者记录本次准备请求的组成字节量；都不是 raw wire capture。

比较大日志的三种输入表示

问题。 测试输出有 20 万字符时，全文、摘要、引用分别让下一步看见什么，还需几次读取？

解释。 读取次数取决于问题所需的内容和工具每次能返回的范围。下面假设两条关键失败断言位于同一可读取片段，且模型已获准读取该范围；这只是计数推演，不是某个工具固定返回长度的保证。
