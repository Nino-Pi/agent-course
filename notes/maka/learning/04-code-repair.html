第 04 章｜代码修复与测试

本章概览

核心问题：测试命令不存在与测试断言失败，为什么需要两条不同的诊断路径？

关键概念：任务契约规定正确行为；断言比较实际值与期望值；退出码描述命令结束状态；diff（差异）说明文件改动；确定性模型返回预写动作。

关系主线：案例先定位测试入口，解释向下取整、取余与差异比较基准，再由失败输入推导修复，以复测和范围检查验收。预写响应驱动真实 mini 循环，全程未调用真实模型。

本章把前面的“只修 README”扩展成“同时修正文档与函数”。示例项目由四份文件组成：README.md 说明使用方法，package.json 配置测试入口，src/duration.js 实现时间格式化，test/duration.test.js 检查结果。这样的固定示例项目也称为 fixture。后文的诊断根据源码和已有执行输出展开。

任务要求。 本案例约定 formatDuration(seconds) 接受非负整数秒，返回 minutes:ss：分钟是完整分钟数，余秒在 0…59 之间并显示为两位。以下输入都在 JavaScript 安全整数范围内：Number 数值类型能精确表示并可靠区分这些整数，非负上限为2的53次方减1，即9,007,199,254,740,991；超过安全范围时，相邻整数可能无法区分。负数、小数、非法输入和超大数的处理不属于本案例。README 则应告诉读者怎样运行项目实际提供的测试。这里的契约是教学任务的要求，既有测试用 0、9、60、125 秒四个输入检查它，不能反过来把需求缩成“只让这四个输入通过”。

从失败输出定位两处问题

基线是修改之前可用于比较的项目状态与检查结果。 本例先读取四个文件，再确认真正的测试入口：错误命令没有启动测试；正确入口得到的 2 pass / 2 fail，才描述了修复前的函数表现。保留基线，才能区分原有失败与补丁引入的问题。

诊断沿着“测试入口 → 失败断言 → 被测实现 → 修复范围”展开：

函数由取整、取余与字符串拼接组成。node:test 只负责运行断言，测试所表达的输入和期望输出是本次定位的依据。Shell 中紧随命令的 echo $? 可读到上一条命令的退出码；0 表示该命令成功退出，非 0 要结合日志判断原因。

先把算术和代码记号对应起来：在本例限定的非负整数范围，Math.floor(x) 表示向下取整，取不大于 x 的最大整数；a % b 表示 a 除以正整数 b 的余数。125 除以 60 是 2 余 5，因此 Math.floor(125 / 60) = 2、125 % 60 = 5，结果应写成 2:05。向下取整与四舍五入不同：59 秒还不满一分钟，Math.floor(59 / 60) = 0，而四舍五入会得到 1。这个 59 秒对照只是说明运算含义的教学计算，不是新增运行测试。

Git 是记录文件版本的工具。工作区是眼前的文件；暂存区（index）保存准备提交的文件状态。默认 git diff 比较工作区与暂存区，git status --short 用简短标记列出暂存、未暂存和未跟踪等状态。该 fixture 已将四份原始文件记录成初始提交；后续固定动作没有再次暂存或提交，所以暂存区保持初始基线。git diff -- README.md src/duration.js 中 -- 后面的路径限定了比较范围，只看这两份文件的差异还不足以证明测试未变，仍要核对全仓变化范围与状态。

正确入口只解决命令选择问题；测试仍可能暴露函数缺陷。

测试入口、计算过程与修复结果

下面把观察与源码计算逐项对应。

package.json 的真实声明是：

{"scripts": {"test": "node --test"}}

调用 npm 的入口是 npm test；scripts.test 的值是它真正启动的 node --test。不要把 test 字段写成 "test": "npm test"，那会再次调用自身。

初始 npm run check 的退出码为 1，关键输出为 Missing script: "check"。这时尚未启动测试，不能说“函数有两个测试失败”。

改用 npm test 后，有 2 个通过、2 个失败：60 秒被写成 1:60，125 秒被写成 2:25，正确值分别是 1:00、2:05。下面是根据这些观察和当前源码作出的教学推导，不是确定性模型的思考日志：

表 2 / Table 2 · 测试入口、计算过程与修复结果
候选解释（Hypothesis）用现有证据检查当前判断
分钟的取整或除数错了两个实际值的分钟前缀都是正确的 1、2；源码是 Math.floor(seconds / 60)不支持用修改分钟来解释这两项失败；这还不等于已测遍所有输入
只是忘记给余秒补零60、25 本来就有两位；单纯补零无法把数值变成 0、5。源码对 9 秒已产生 09不能仅修改字符串格式解决当前失败
余秒使用了错误的周期60 % 100 = 60，125 % 100 = 25，恰好重现错误；余秒却应在减去完整分钟后剩下当前源码与失败现象一致支持修改余秒计算

test/duration.test.js 的 import { formatDuration } from '../src/duration.js' 把断言连到真实实现，而不是靠文件名猜测。对非负整数秒，令 minutes = Math.floor(seconds / 60)，余秒应为 seconds - 60 * minutes，即 seconds % 60。这解释了为什么一个运算符参数的修复能够覆盖一般情况。README 里的 npm run check 另改为 npm test。

修正后的完整函数保留原来的导出、分钟计算和补零方式，只改变取余基数：

export function formatDuration(seconds) {
  const minutes = Math.floor(seconds / 60);
  const remainder = seconds % 60;
  return `${minutes}:${String(remainder).padStart(2, '0')}`;
}

README 中的测试命令相应成为：

npm test

下文固定运行的结果为 4 个通过、0 个失败，退出码 0；diff 仅包含 README 的命令替换与 src/duration.js 的 % 100 → % 60，测试文件未变。这是该案例的结果，不保证任意修改或环境都得到相同输出。

怎样选择足够的验证

验证要能反驳一个看起来合理的错误修复。先把检查与任务要求对应起来：

表 3 / Table 3 · 怎样选择足够的验证
要确认什么本例怎样检查证据边界
测试入口确实可用根据 scripts 运行 npm test，读到测试名称与结果命令存在不证明函数正确
缺陷消失且已有正常行为保留60、125 是原失败样例；0、9 保留零值与不足一分钟时的格式检查四例通过只证明这四例，不是整个输入域证明
修复遵守分钟与余秒的关系阅读 diff 中的一般计算，检查 seconds = 60 * minutes + remainder、0 ≤ remainder < 60 及两位显示这是源码推理；仍不能代替实际执行

反例：只针对测试输入打补丁。 如果一个补丁只给 60、125 写特判，保留其余 % 100 逻辑，它也能让现有四例通过。按契约，59 秒应为 0:59，61 秒应为 1:01；该特判补丁却会把 61 秒算成 1:61。这是根据代码的纸面计算，fixture 的四个测试没有包含这两个边界样例，不能把此推导写成新增运行结果。一般规律、边界样例和 diff 审查互相补充，不能把多跑几个数说成穷尽证明。

本固定案例保持测试不变，是为了让验收可比较；它不是“真实项目禁止改测试”的规则。真实修复可以增加符合独立需求的回归测试，先确认它在旧实现暴露故障、在修复后通过，并保留相关既有检查。若怀疑原断言有误，先依据需求说明理由，不能仅为变绿而删除断言或改期望。

第05章 的退出检查只决定循环怎样停下，不能代替修复验收。第26章讨论多次任务委托的评价；本实验的固定回放次数不能生成模型成功率。

固定响应怎样驱动真实循环

本节使用已有固定响应运行，起点是同一套未修复的四文件项目。每个动作、返回结果与最终差异都已给出，可以直接沿表格理解循环如何推进。

教学脚本把准备与运行分成两个阶段。准备阶段，run_repair() 给出八步命令计划；make_agent() 把每条命令包装成原始 tool call，先调用真实的 parse_toolcall_actions 解析出 actions，再用 make_toolcall_output 装好响应。运行阶段，DeterministicToolcallModel 依次返回这些已经装好的响应，DefaultAgent 接着调用真实 LocalEnvironment 执行命令、取得结果并继续循环。

因此，解析预写命令发生在运行之前；运行时不会再请求真实模型生成动作，也不会因观察变化自动改动八步顺序。这与第03章“真实模型响应到达后再解析”的在线路径不同，但命令执行与结果回传仍是真实代码路径。

表中的 cat README.md package.json 按所列顺序读取两份文件，把内容拼接到输出中；它本身不核对哪条测试命令正确，判断仍要依据返回的内容。

第 5 步的脚本使用 Python str.replace，没有检查目标出现次数：零匹配仍可能正常退出，多匹配会全部替换。这里的固定初始文件使预定替换可用；迁移到未知仓库时必须重新检查目标与差异，不能从此脚本推导“退出 0 就一定改对一处”。

为什么有 8 次 Model.query，却只有 7 条 tool observation？最后一次 action 的命令已经执行，LocalEnvironment._check_finished() 检出完成标记后抛出 Submitted，DefaultAgent.run() 加入 exit。该完成 action 不像普通命令一样返回 output 并生成 tool observation。这个差异是实际控制流，不要补造第 8 条成功 observation。

运行产物分别说明什么

案例保存了以下产物，它们分别回答不同问题：

  • repo/：真实修改后的四文件 Git 仓库。
  • command-trace.json：八步的命令及前七步真实 output/returncode。最后一步的 observation 为 null，终态看 trajectory。
  • trajectory.json：mini 原生序列化结果。按 messages[].tool_call_id 配对 assistant tool call 与 tool observation。
  • diff.patch：最终 diff。
  • verification.json：脚本对返回码、测试结果、修改范围和 exit 的验收。
  • versions.json：实际 Python、Node、npm 与 mini 源码入口。

真实模型生成的修复路线

第22章 的真实 mini 修复沿用四份原始文件，由真实 K3 生成动作。它读取文件、选择测试时点并修改代码，动作顺序由模型响应决定，可与这里预写的八步对比。

失败与修复结果问答

问题 1。 第 2 步与第 4 步都是 returncode 1，为什么不能按同一种故障修复？

解释。 第 2 步失败在 npm 的入口选择，测试尚未运行；第 4 步运行到了测试断言，需核对函数逻辑与测试需求。必须阅读 observation 的内容，不能只看返回码。

问题 2。 第 5 步 returncode 0，能否直接向用户说“修复已验证”？

解释。 不能。那只说明编辑命令成功退出；第 6 步才运行了验证，第 7 步检查修改范围。

问题 3。 什么证据可以排除“修改测试让它通过”？

解释。 本例从已提交的原始文件开始，固定动作没有再次暂存或提交；循环结束后，脚本用不限定路径的 git diff --name-only 列出全仓已跟踪文件的未暂存变更，changed_files 只有 README 与函数文件。结合初始提交、已知动作和两文件 diff，才支持原有测试文件未变。按两条路径筛选的 diff 单独不能排除其他改动；git diff --name-only 也不列出未跟踪文件。git status --short 是可补充的状态检查，本案例没有对 fixture 执行它。

问题 4。 把 fixture 的 bug 换掉，确定性模型还会自己找到正确修复吗？

解释。 不会。响应脚本已经知道具体替换字符串；这验证的是控制流与本地执行，不是模型的定位或规划能力。

问题 5。 一个只特判 60、125 的补丁也让四例通过，为什么仍不满足任务？

解释。 任务要求一般的分钟/余秒格式，四例只是样例。该补丁在 61 秒仍错误；应结合契约、边界检查设计和源码差异判断，不能把样例通过当成需求本身。
