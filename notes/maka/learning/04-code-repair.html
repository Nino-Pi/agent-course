第 04 章｜代码修复（Code Repair）与测试（Test）

本章概览

核心问题：测试（Test）命令不存在与测试（Test）断言（Assertion）失败，为什么需要两条不同的诊断路径？

关键概念：任务契约（Task Contract）规定正确行为；断言（Assertion）比较实际值与期望值；退出码（Exit Code）描述命令结束状态；差异（Diff）说明文件改动；确定性模型（Deterministic Model）返回预写行动请求（Action）。

关系主线：案例先定位测试入口（Test Entry），解释向下取整（Floor）、取余运算（Remainder Operation）与差异（Diff）比较基准，再由失败输入推导修复，以复测和范围检查验收。预写响应驱动真实 mini 循环，全程未调用真实模型（Model）。

前情回顾

第02章解释结果怎样进入下一轮模型（Model）输入，第03章进一步区分行动请求（Action）、执行输出（Output）与观察消息（Observation Message），后者是承载观察结果（Observation）的消息（Message）。同样一个非零退出码（Exit Code），可能意味着“测试入口（Test Entry）根本不存在”，也可能意味着“测试（Test）确实运行，但函数不符合要求”。只知道命令失败，还不足以决定修改哪份文件。

本章把前面的“只修 README”扩展成“同时修正文档与函数”。先按当前文件与失败输出推导两处问题，再看固定响应怎样驱动真实循环。下面的诊断文字是对已有材料的教学解释；行动请求（Action）顺序来自预写脚本，不是模型（Model）现场思考的记录。

从失败输出定位两处问题

基线（Baseline）是修改之前可用于比较的项目状态与检查结果。 本例先读取四个文件，再确认真正的测试入口（Test Entry）：错误命令没有启动测试（Test）；正确入口得到的 2 pass / 2 fail，才描述了修复前的函数表现。保留基线（Baseline），才能区分原有失败与补丁引入的问题。

诊断先按失败发生的位置分流。这张图解释根据结果选择下一步的理由；它不是声称下面的固定脚本会根据结果自动改变计划。图中改用正确入口后的给定结果是 2 pass / 2 fail，因而继续分析失败断言（Assertion）；其他项目若已全部通过，就不应凭空进入函数修复分支。

node:test 负责运行断言（Assertion）；断言（Assertion）比较实际值与期望值，帮助识别函数在哪些输入上失败。命令解释器（Shell）中紧随命令的 echo $? 可读到上一条命令的退出码（Exit Code）；0 表示该命令成功退出，非 0 要结合日志判断原因。第03章的管道反例已经说明，若再拼接其他命令，就要确认读到的是哪一层的状态。

Git 是记录文件版本的工具。工作区（Workspace）是眼前的文件；暂存区（Index）保存准备提交的文件状态。默认 git diff 比较工作区（Workspace）与暂存区（Index），git status --short 用简短标记列出暂存、未暂存和未跟踪等状态。该固定示例项目（Fixture）已将四份原始文件记录成初始提交；后续固定行动请求（Action）没有再次暂存或提交，所以暂存区（Index）保持初始基线（Baseline）。git diff -- README.md src/duration.js 中 -- 后面的路径限定了比较范围，只看这两份文件的差异（Diff）还不足以证明测试（Test）未变，仍要核对全仓变化范围与状态。

测试入口（Test Entry）、计算过程与修复结果

下面把观察与源码计算逐项对应。

package.json 使用 JavaScript 对象表示法（JavaScript Object Notation，JSON）保存字段和值；下面摘取的 scripts 字段又包含名为 test 的字段。它的真实声明是：

{"scripts": {"test": "node --test"}}

调用 npm 的入口是 npm test；scripts.test 的值是它真正启动的 node --test。不要把 test 字段写成 "test": "npm test"，那会再次调用自身。

初始 npm run check 的退出码（Exit Code）为 1，关键输出为 Missing script: "check"。这时尚未启动测试（Test），不能说“函数有两个测试（Test）失败”。

改用 npm test 后，有 2 个通过、2 个失败：60 秒被写成 1:60，125 秒被写成 2:25，正确值分别是 1:00、2:05。下面是根据这些观察和当前源码作出的教学推导，不是确定性模型（Deterministic Model）的思考日志：

先把任务契约（Task Contract）写成计算关系。设输入秒数为 sss，完整分钟数为 mmm，余秒（Remaining Seconds）为 rrr；本例只处理已经限定的非负安全整数。向下取整（Floor）符号 ⌊x⌋\lfloor x\rfloor⌊x⌋ 表示不大于 xxx 的最大整数，对应代码中的 Math.floor(x)：

m=⌊s60⌋,r=s−60m,0≤r<60.m=\left\lfloor\frac{s}{60}\right\rfloor,\qquad r=s-60m,\qquad 0\le r<60.m=⌊60s​⌋,r=s−60m,0≤r<60.

这三部分按同一含义连接：先算已经过了多少个完整分钟，再从总秒数中扣掉这些分钟。对于本例非负输入，代码 s % 60 正好表示余下的秒数；% 100 使用了错误周期。125 除以 60 是 2 余 5，所以显示为 2:05。59 秒还不满一分钟，向下取整（Floor）得到 0，四舍五入却会得到 1；这里需要的是完整分钟数。59 秒只是教学计算，不是新增运行测试（Test）。

test/duration.test.js 的 import { formatDuration } from '../src/duration.js' 把断言（Assertion）连到真实实现，而不是靠文件名猜测。对非负整数秒，令 minutes = Math.floor(seconds / 60)，余秒（Remaining Seconds）应为 seconds - 60 * minutes，即 seconds % 60。这解释了为什么一个运算符参数的修复能够覆盖一般情况。README 里的 npm run check 另改为 npm test。

修正后的完整函数保留原来的导出、分钟计算和补零方式，只改变取余运算（Remainder Operation）的基数。读代码时先追踪两个中间值：minutes 保存完整分钟数，remainder 保存余秒（Remaining Seconds）。最后 String(remainder) 转成文本，padStart(2, '0') 在不足两位时向左补零；反引号中的 ${...} 将计算值放进返回文本。export 让测试（Test）文件能够导入这项函数。

export function formatDuration(seconds) {
  const minutes = Math.floor(seconds / 60);
  const remainder = seconds % 60;
  return `${minutes}:${String(remainder).padStart(2, '0')}`;
}

README 中的测试（Test）命令相应成为：

npm test

下文固定运行的结果为 4 个通过、0 个失败，退出码（Exit Code） 0；差异（Diff）仅包含 README 的命令替换与 src/duration.js 的 % 100 → % 60，测试（Test）文件未变。这是该案例的结果，不保证任意修改或执行环境（Environment）都得到相同输出。

验证（Verification）也有两个消费者（Consumer）：测试（Test）程序消费修改后的函数，给出具体输入的行为结果；检查差异（Diff）的人或程序消费文件改动，判断修改是否符合授权。两边都需要材料，不能把模型（Model）的“已经修好”同时当作两种检查的结果。

反例：只针对测试（Test）输入打补丁。 如果一个补丁只给 60、125 写特判，保留其余 % 100 逻辑，它也能让现有四例通过。按任务契约（Task Contract），59 秒应为 0:59，61 秒应为 1:01；该特判补丁却会把 61 秒算成 1:61。这是根据代码的纸面计算，固定示例项目（Fixture）的四个测试（Test）没有包含这两个边界样例，不能把此推导写成新增运行结果。一般规律、边界样例和差异（Diff）审查互相补充，不能把多跑几个数说成穷尽证明。

本固定案例保持测试（Test）不变，是为了让验收可比较；它不是“真实项目禁止改测试（Test）”的规则。真实修复可以增加符合独立需求的回归测试（Regression Test），先确认它在旧实现暴露故障、在修复后通过，并保留相关既有检查。若怀疑原断言（Assertion）有误，先依据需求说明理由，不能仅为变绿而删除断言（Assertion）或改期望。

第05章的退出检查只决定循环怎样停下，不能代替修复验收。第26章讨论多次任务委托的评价；本实验的固定回放次数不能生成模型（Model）成功率。

固定响应怎样驱动真实循环

本节使用已有固定响应运行，起点是同一套未修复的四文件项目。每个行动请求（Action）、返回结果与最终差异（Diff）都已给出，可以直接沿表格理解循环如何推进。

前面已经解释“为什么这项修改合理”，这里换一个问题：即使下一步早就写好，真实的解析、执行和反馈链是否仍按协议工作？确定性模型（Deterministic Model）用于隔离这条机制链，不用于评价定位能力。

教学脚本把准备与运行分成两个阶段。准备阶段，run_repair() 给出八步命令计划；make_agent() 把每条命令包装成原始工具调用（Tool Call），先调用真实的 parse_toolcall_actions 解析出行动请求（Action），再用 make_toolcall_output 装好响应。运行阶段，DeterministicToolcallModel 依次返回这些已经装好的响应，DefaultAgent 接着调用真实 LocalEnvironment 执行命令、取得结果并继续循环。

因此，解析预写命令发生在运行之前；运行时不会再请求真实模型（Model）生成行动请求（Action），也不会因观察变化自动改动八步顺序。这与第03章“真实模型（Model）响应到达后再解析”的在线路径不同，但命令执行与结果回传仍是真实代码路径。

表中的 cat README.md package.json 按所列顺序读取两份文件，把内容拼接到输出中；它本身不核对哪条测试（Test）命令正确，判断仍要依据返回的内容。

为什么有 8 次模型调用（Model Query），却只有 7 条工具返回的观察消息（Observation Message）？最后一次行动请求（Action）的命令已经执行，LocalEnvironment._check_finished() 检出完成标记后抛出 Submitted，DefaultAgent.run() 加入 exit 消息（Message）。该完成行动请求（Action）不像普通命令一样返回执行输出（Output）并生成工具返回的观察消息（Observation Message）。这个数量差别来自实际控制流，不要补造第 8 条普通观察消息（Observation Message）。

运行产物分别说明什么

  • versions.json：实际 Python、Node、npm 与 mini 源码入口。

真实模型（Model）生成的修复路线

第22章的真实 mini 修复沿用四份原始文件，由真实 K3 生成行动请求（Action）。它读取文件、选择测试（Test）时点并修改代码，行动请求（Action）顺序由模型（Model）响应决定，可与这里预写的八步对比。

失败与修复结果问答

问题 1。 第 2 步与第 4 步都是退出码（Exit Code）returncode 1，为什么不能按同一种故障修复？

解释。 第 2 步失败在 npm 的入口选择，测试（Test）尚未运行；第 4 步运行到了测试（Test）断言（Assertion），需核对函数逻辑与测试（Test）需求。必须阅读观察消息（Observation Message）的内容，不能只看退出码（Exit Code）。

问题 2。 第 5 步退出码（Exit Code）returncode 0，能否直接向用户说“修复已验证（Verification）”？

解释。 不能。那只说明编辑命令成功退出；第 6 步才运行了验证（Verification），第 7 步检查修改范围。

问题 3。 什么证据可以排除“修改测试（Test）让它通过”？

解释。 本例从已提交的原始文件开始，固定行动请求（Action）没有再次暂存或提交；循环结束后，脚本用不限定路径的 git diff --name-only 列出全仓已跟踪文件的未暂存变更，changed_files 只有 README 与函数文件。结合初始提交、已知行动请求（Action）和两文件差异（Diff），才支持原有测试（Test）文件未变。按两条路径筛选的差异（Diff）单独不能排除其他改动；git diff --name-only 也不列出未跟踪文件。git status --short 是可补充的状态检查，本案例没有对固定示例项目（Fixture）执行它。

问题 4。 把固定示例项目（Fixture）的函数缺陷换掉，确定性模型（Deterministic Model）还会自己找到正确修复吗？

解释。 不会。响应脚本已经知道具体替换字符串；这里的验证（Verification）覆盖的是控制流与本地执行，不是模型（Model）的定位或规划能力。

问题 5。 一个只特判 60、125 的补丁也让四例通过，为什么仍不满足任务？

解释。 任务要求一般的分钟/余秒（Remaining Seconds）格式，四例只是样例。该补丁在 61 秒仍错误；应结合任务契约（Task Contract）、边界检查设计和源码差异（Diff）判断，不能把样例通过当成需求本身。
