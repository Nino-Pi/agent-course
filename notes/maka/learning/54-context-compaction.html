第 54 章｜上下文压缩（Context Compaction）：选择、保存与采用

本章概览

核心问题：历史（History）接近窗口上限时，怎样换用摘要（Summary），又保住下一步判断所需的事实与约束（Constraint）？

关键概念：前缀（Prefix）是选定整理的旧历史（History）；尾部（Tail）保留近期完整单元；检查点（Checkpoint）携带替代表示和来源；有效历史（Effective History）决定目前允许使用的内容；回读（Readback）补充有依据的细节。

关系主线：先选来源，再生成、验证和保存候选，最后由消费者（Consumer）采用。来源一致、保存成功、语义准确和请求可容纳，分别需要证据。

前情回顾：已有材料不必每次原样发送

第53章把保存、选择、编码和发送分开：当前“只改README、中文报告”的约束（Constraint）必须进入本次输入，e1编辑（Edit）成功与b1测试（Test）失败则分别保留。第19章解释过，上下文压缩（Context Compaction）改变的是下一次请求采用的表示，原运行时事件（Runtime Event）仍由持久记录保存。

这里继续使用这个只改README的任务（Task），最近测试（Test）退出1、两项通过和两项失败。接下来不是再次修文件，而是设计长历史（History）怎样被替代，以及失败以后怎样继续解释现状。接口（Interface）、阈值和摘要（Summary）内容都是教学设计，未运行产品或用于生成摘要（Summary）的模型（Model）。

先判断增长来自哪里

“输入太长”不是同一种原因。把原因认错，重复执行同一压缩过程也不会解决问题。

表 1 / Table 1 · 先判断增长来自哪里
主要增长来源更直接的处理需要保护什么
很多旧调查与对话用摘要（Summary）替代安全旧前缀（Prefix）来源、未解决事项与仍有效约束（Constraint）
刚返回的巨型工具结果（Tool Result）有界投影（Projection）与可靠回读（Readback）调用身份（Call Identity）、退出依据、关键错误
固定规则与工具声明（Tool Specification）本身过多按当前任务（Task）检查可选范围和能力集合必要规则与授权（Authorization）条件

本题要求原执行事实继续可查，压缩失败不能伪造进展。触发依据可以参考窗口预算（Budget）、输出预留（Output Reserve）与实际用量（Usage），但触发只说明需要处理，不能证明存在可行替代。

前缀（Prefix）、尾部（Tail）与当前要求怎样组合

沿用第19章的符号，将整理前的有效历史（Effective History）记为HeffH_{\mathrm{eff}}Heff​，按一个安全切点分为PPP与TTT。摘要（Summary）或其他替代表示记为S(P)S(P)S(P)：

Heff=P∥T,H^=S(P)∥T.H_{\mathrm{eff}}=P\mathbin{\Vert}T, \qquad \widehat H=S(P)\mathbin{\Vert}T.Heff​=P∥T,H=S(P)∥T.

∥\Vert∥表示按顺序拼接；PPP是本次被覆盖的前缀（Prefix），TTT是仍需原文的尾部（Tail）。这只是表示关系，不是可以直接发给某个模型服务提供方（Provider）的完整数组。当前规则、工具声明（Tool Specification）和最终协议编码还要另外组成。

图中原执行历史（History）继续保留，下一次请求只改变有效表示。删除或退役整个会话（Session）是另一项生命周期（Lifecycle）操作，不能把它当作这次压缩的自然后果。

安全切点首先保护结构：不拆开工具调用（Tool Call）和对应结果，不把未完成流式内容当完整历史（History），保留当前用户锚点（Head Anchor）与必要近期单元。结构安全不等于摘要（Summary）语义正确。 两段不同过去如果都被压成“修改完成”，其中“尚未测试（Test）”与“测试（Test）已通过”的差别就可能消失。

先固定摘要（Summary）究竟看过什么

本次只整理旧的测试（Test）入口调查：已经读取package.json，确认scripts.test为node --test。当前约束（Constraint）独立保留，近期e1与b1完整单元留在尾部（Tail），没有交给本次摘要（Summary）生成器。

下面的检查点（Checkpoint）字典表达两类来源和旧阶段事实，不等于Maka真实结构：coverage回答覆盖哪些原始记录，effective_source回答生成器实际使用了哪份有效内容。其余变量也是教学占位。

checkpoint = {
    # 原始覆盖范围与实际摘要（Summary）来源分别记录。
    "coverage": covered_event_range,
    "effective_source": identity_of_input_actually_summarized,
    "representation": "text_summary",
    # 这里只描述旧前缀（Prefix）已建立的事实。
    "task_state": {
        "prior_goal": "核对项目测试入口",
        "done": ["从 package.json 读到 scripts.test 为 node --test"],
        "known_fact": "该项目声明的测试入口为 npm test",
        "not_established": ["这一旧阶段没有运行测试，未确认功能正确"],
        "evidence": ["旧前缀中的配置读取调用与完整结果"]
    }
}

这里写“旧阶段没有运行测试（Test）”，与当前尾部（Tail）已经存在失败测试（Test）并不矛盾：两句话的时间范围不同。summarize(prefix)没有看过e1/b1，不能把近期结果写成这份旧摘要（Summary）已经证明的内容。

下一份输入把三部分合起来，才得到当前判断：旧摘要（Summary）说明入口依据，尾部（Tail）说明文档已改而测试（Test）失败，当前要求限制只改README并用中文报告。完整任务状态（Task State）属于这份组成结果，不能要求每一个局部来源单独知道全部过去。

候选检查点（Candidate Checkpoint）：三道边界各检查什么

第一道边界检查来源和重放（Replay）结构；第二道等待保存；第三道观察模型服务提供方（Provider）是否接受本次请求。三者都不能替代语义核查。

表 2 / Table 2 · 候选检查点（Candidate Checkpoint）：三道边界各检查什么
判断能支持什么仍不能支持什么
来源与协议有效候选对应指定记录，替代结构可重放（Replay）摘要（Summary）每一句都忠实
保存已确认后续可按保存合同重新加载该候选该候选永远适用于所有后续历史（History）
请求被接受该服务接受了这一次请求模型（Model）必然保留约束（Constraint）并正确完成任务（Task）

若另一轮已覆盖编辑（Edit）与失败测试（Test），生成器却把“文档改了、测试（Test）失败”写成“修复成功，测试（Test）全部通过”，来源字段和格式都可能完全合法。判断摘要（Summary）质量还要核对关键状态（State）、否定条件、未完成事项与下游行为，不能把内容指纹（Digest）当作真实性证明。

上下文压缩（Context Compaction）骨架：先保存，才切换当前表示

阅读下面函数时，先看两个不能开始的出口：没有安全前缀（Prefix），或没有摘要调用预算（Summary Call Budget）。再看生成后的来源检查，最后看保存与应用的顺序。各辅助函数都是未运行的教学合同：

def compact(view, attempt_budget):
    # 先选完整协议单元（Protocol Unit），再申请本次摘要（Summary）的预算（Budget）。
    prefix, tail = select_complete_safe_units(view)
    if not prefix:
        return CannotCompact("没有可安全替换的前缀")
    if not attempt_budget.try_reserve_summary_call():
        return CannotCompact("摘要调用预算耗尽")
    candidate = summarize(prefix)
    if not source_and_protocol_valid(candidate, prefix):
        return KeepPreviousView("候选无效")
    # 保存失败会抛给外层；apply 尚未执行。
    persist_checkpoint(candidate)
    next_view = apply(candidate, tail)
    return ReadyForProvider(next_view, attempt_budget.remaining)

persist_checkpoint要在成功时返回、失败时抛出；失败不会执行后面的apply。这份骨架没有展开外层异常处理，也没有返回一个伪造的ReadyForProvider。真实异步实现必须等待保存结果，不能只发起写入就切换指针。

KeepPreviousView表示本次候选未被采用，不表示之前已超长的请求可以照发。外层仍须判断能否缩减可选内容、按需回读（Readback），或明确停止；摘要调用预算（Summary Call Budget）也要持续扣减，不能因失败而无限重置。

保存未得到确认时，本地不切到新候选，但也不能仅凭异常断言数据库一定没保存。重启后先读取实际持久记录，再检查候选是否仍适用；这和第52章“回执（Receipt）缺失不等于没有提交”保持同一原则。

Maka的相关路径先构造可物化的替代，再等待检查点（Checkpoint）保存回调，失败返回write_failed，成功后才更新当前采用的检查点（Checkpoint）。当前实现没有通用“本地严格变短或估算适配后才提交”的门槛；请求能否容纳仍由具体模型服务提供方（Provider）判断。

同一批原始事件（Raw Event），为什么摘要（Summary）仍可能过时

设旧工具结果（Tool Result）的原始记录没有变，但之后提交了投影变换（Projection Transition），将大正文换成有界表示。覆盖范围仍指向同一批事件（Event），生成器现在允许看到的内容却已经不同。

因此只核coverage不够。实际用于生成摘要（Summary）的有效来源也要匹配；否则旧摘要（Summary）可能继续携带后来已从有效历史（Effective History）中移出的内容。构造新的检查点（Checkpoint）时，也不能先使用过时摘要（Summary），再把当前来源指纹（Digest）贴到结果上，就称它已经核对。

在Maka中，原始覆盖与有效来源分别由sourceDigest和effectiveSourceDigest等维度核对，消费者（Consumer）在后续读取时再次检查。字段相符只能支持来源一致性，不证明文本推断正确，也不保证换一条模型（Model）或连接（Connection）路线仍能重放（Replay）。

这里的失败回退必须保留此前有效表示。先前已经提交的投影变换（Projection Transition）不能因为新摘要（Summary）失败就被忽略；回退不是把原始大正文无条件重新塞回输入。

巨型当次日志：用回读（Readback）补细节

另设一个增长来源：第一次测试（Test）就返回20万字符，旧历史（History）还很短。即使把旧前缀（Prefix）缩到极小，巨型尾部（Tail）仍在；它自身超出可用输入预算（Input Budget）时，反复整理旧阶段没有帮助。

本题保留退出码（Exit Code）、相关报错、有界片段和受控引用（Reference）。全文是否已保存、模型（Model）收到什么表示、以后还能否读取，是三个不同保证。

图中的实线推动处理，虚线提供引用（Reference）或读取材料。读取器（Reader）拿到引用（Reference）与行范围后，先检查权限（Permission）、目标存在性和请求大小，再读取。实际片段或明确错误都成为新的观察结果（Observation），进入后续模型输入（Model Input）；得到一个地址不等于已经看过全文。

它是教学归档方案，不宣称Maka为全部工具原始结果提供统一全文保存。Maka的工具结果归档（Tool-result Archive）可基于账本（Ledger）重建被替换的有效投影（Projection），不会因此补回更早已省略的原始字段；图片读取结果的外置承载（Read Image Offload）则是另一个承载通道。

可靠回读（Readback）的要求是：存在可证明、受授权（Authorization）且有界可读的恢复来源，不必所有实现都复制一份新文件。没有确认可恢复来源，就不能先返回一个看似有效的引用（Reference）。

三个失败场景：保留什么，下一步依据什么

语义错误。 换到更晚的一次压缩，此时已经结束的e1与b1也被选入前缀（Prefix）。摘要（Summary）却把“编辑（Edit）成功、测试（Test）失败”归为“修复成功，测试（Test）全部通过”。这次切点与先前留它们在尾部（Tail）的例子不同；应对关键事实与后续行为作核查，来源一致并不能关闭这个问题。

新候选保存失败。 保留此前有效表示并报告保存错误；如果旧请求已经超限，继续选择允许的缩减或停止。不能在内存先应用，再以“稍后保存”宣称可以可靠恢复（Recovery）。

既有投影记录不可读。 这与新候选没有成功不同。不能把坏记录当成“从未发生裁剪”，重新注入原始正文。Maka所核折叠路径对可定位的坏记录屏蔽目标，对无法定位目标的坏记录报告读取错误；这保护当前输入，不等于记录已自动修复。

按最后NNN条消息（Message）保留不行吗？

消息（Message）数量与协议单元（Protocol Unit）、任务（Task）边界不同。它可能拆调用与结果，也可能删去早期仍有效要求。先以完整单元划界，再按当前任务（Task）和预算（Budget）选择；NNN只是策略（Policy）参数。

每次重新概括旧摘要（Summary），是否更省？

可能减少输入，也可能累积误差。保留来源和可回查证据，观察长任务（Task）后半段的约束（Constraint）遵循与错误事实。必要时从仍可使用的有效来源重建，不能为了恢复原文而绕过已经提交的投影变换（Projection Transition）。

上下文压缩（Context Compaction）后还是超窗怎么办？

先确认增长来自尾部（Tail）、当次大结果还是固定材料，再作针对性缩减并限制重复次数。无安全方案就明确停止。不能用反复执行同一次摘要（Summary）调用来替代预算（Budget），也不能把“应该更短”写成Maka已实现的通用提交门槛。

原生不透明状态（Native Opaque State）与文本摘要（Text Summary）怎样选？

文本便于审阅，但生成可能失真；原生状态（Native State）可能支持特定服务的连续性，重放（Replay）和审查范围却受其合同约束。按模型（Model）、连接（Connection）与模型服务提供方（Provider）兼容性检查，不能把不透明内容当作可以交给任意模型（Model）的通用摘要（Summary）。

完整方案从增长原因和安全范围出发，明确摘要（Summary）看过什么，分别核来源、结构与保存，再由本次消费者（Consumer）采用。长期记忆（Long-Term Memory）更新、旧历史（History）摘要（Summary）和工具结果（Tool Result）裁剪各自改变不同对象；不能用一种“记住了”的说法合并它们。
