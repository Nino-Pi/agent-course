第 54 章｜设计上下文压缩

本章概览

核心问题：历史接近窗口上限时，怎样应用摘要并保留失败后仍能继续判断的原始事实？

关键概念：Prefix（前缀）：选中整理的旧历史；Tail（尾部）：保留的完整近期单元；候选摘要：尚未被采用的表示；Checkpoint（检查点）：保存摘要及来源范围；有效历史：下一请求采用的表示；有界回读：按需取得原文细节。

关系主线：选取范围、生成候选、校验并保存后才能应用；巨型新结果另行控制表示，保存成功不保证摘要更忠实、更短或被模型服务接受。

前置：第19章、第53章。本题中摘要内容、阈值变量和接口均为教学设计。

1. 原题与约束

Agent 已经进行了很多轮搜索和测试，Context 快满了。你会怎样压缩？

窗口压力可能来自旧对话、当前巨型工具结果，或工具 schema 与固定指令。三者需要不同处理；原历史保留、重启恢复与 provider 切换要求进一步限定方案。

本题要求保留原执行事实，允许生成可读摘要，压缩失败时不能伪造进展；当前任务只改 README，最近一次测试失败。若输入已经无法送给模型，要有明确停止或降级结果。

2. 参考方案

我会先分开持久历史和模型输入。压缩针对下一次请求的表示，原始工具结果和执行状态仍保留。触发依据结合窗口预算、输出预留和已知 usage；触发压缩并不保证压完一定能放下。选择范围时保留当前任务约束和近期完整协议单元，不切开调用与结果，也不把未完成流式内容当完整历史。然后让模型生成带任务状态、约束、已做、未做和证据引用的候选摘要，系统校验来源范围与重放结构，先保存 checkpoint，再应用到下一输入。摘要可能失真，所以后续关键动作仍要回查文件或测试证据。当前单次巨型日志则单独做有界投影和受控回读。保存失败保留此前有效表示；服务端仍报超窗时按有界策略处理，不能无限重复同一压缩。

3. 压缩改变哪一部分

摘要在下一请求中替代 prefix，tail 继续保留完整原文单元；数据库中的原事件不因这次替换而删除。当前约束独立保留，细节通过受控 ref 回查。

4. 候选变为已应用的状态

三条关键边界是：生成不等于可用；保存成功后才应用；本地验证不等于 provider 接受。结构检查也不证明摘要中的每个语义判断正确。

5. 最小数据与伪代码

以下为教学类型，coverage 与 effective_source 表示两种核对对象，具体编码不等同 Maka checkpoint schema：

checkpoint = {
    "coverage": covered_event_range,
    "effective_source": identity_of_input_actually_summarized,
    "representation": "text_summary",
    "task_state": {
        "prior_goal": "核对项目测试入口",
        "done": ["从 package.json 读到 scripts.test 为 node --test"],
        "known_fact": "该项目声明的测试入口为 npm test",
        "not_established": ["这一旧阶段没有运行测试，未确认功能正确"],
        "evidence": ["旧前缀中的配置读取调用与完整结果"]
    }
}

本例明确只覆盖“已完成的测试入口调查”旧阶段。当前“只改 README、中文报告”来自单独保留的当前用户约束；最近 Edit 成功与 Bash 的 2 pass / 2 fail 留在原文 tail。summarize(prefix) 没看见这些近期内容，所以不能把它们写成旧摘要已经证明的事实。由摘要和 tail 一起组成下一输入，才得到完整的当前任务状态。

先前如果已经裁剪工具结果，摘要必须知道自己实际看的是哪份有效内容。只核对原事件范围，无法说明摘要是否基于替换前还是替换后的正文。所以要分别记录原始覆盖范围与摘要实际接收的有效内容。

def compact(view, attempt_budget):
    prefix, tail = select_complete_safe_units(view)
    if not prefix:
        return CannotCompact("没有可安全替换的前缀")
    if not attempt_budget.try_reserve_summary_call():
        return CannotCompact("摘要调用预算耗尽")
    candidate = summarize(prefix)
    if not source_and_protocol_valid(candidate, prefix):
        return KeepPreviousView("候选无效")
    persist_checkpoint(candidate)      # 失败时不切换当前 view
    next_view = apply(candidate, tail)
    return ReadyForProvider(next_view, attempt_budget.remaining)

KeepPreviousView 不表示超长请求可以继续无条件发送。如果之前已发生 overflow，保留原表示之后还需选择允许的缩减、回读或明确停止。

6. 巨型工具日志是另一条处理链

当前第一次测试就返回 20 万字符，旧历史还很短，压旧前缀没有帮助。

教学方案是给模型退出码、相关报错、有界片段及受控 ref。读取器接受 ref 与行范围，并检查调用者权限、数据仍存在和请求大小。全文保存、模型表示、归档可读性是三项不同保证。

图中虚线提供引用或读取材料；读取器接收 ref + 行范围 后，先检查权限、目标存在性和请求大小，再尝试读取；检查不通过或读取失败都会返回明确错误。实际片段和错误都成为新观察，进入后续模型输入；得到 ref 本身不等于已经读到全文或指定片段。

这是一份教学方案，不宣称 Maka 为所有工具原始输出提供统一全文归档。Maka 的有效工具结果归档、图片读取结果的外置承载（Read image Offload）与原始字段覆盖不同。若引用目标没有保存成功，不能先返回一个看似可用的 ref。

7. 正常与失败走读

正常：旧阶段已经确定测试入口 → 近期 Edit 和失败 Bash 保留为原文单元 → 摘要只替代旧阶段 → 新请求仍看见只改 README 与当前失败 → 报告错误并保持写入范围。

失败一：换到更晚的一次压缩，已经结束的 Edit 和失败 Bash 也被纳入旧前缀；摘要却把“编辑成功、测试失败”归为“修复成功”。这与上例将两者留在 tail 的范围不同。来源检查可能通过，语义仍错误。设计验证应加入关键事实检查和下游行为对照，不能声称 digest 证明语义正确。

失败二：摘要生成成功，持久保存失败。继续使用先前表示，报告该步骤失败；不能在内存应用后把“稍后保存”当可恢复方案。

失败三：已有投影记录不可读。不能当成从未发生裁剪而重新注入 raw body；根据能否定位目标屏蔽相关内容或报错。

8. 递进追问

按最后 N 条消息保留不行吗？

消息条数与协议单元、任务边界不同。可能拆开调用和结果，也可能删掉早期仍有效约束。先以完整单元为边界，再按任务与预算选取；N 只是策略参数。

每次都把旧摘要再摘要，是否更省？

可能降低输入，但误差会累积。保留来源与可回查证据，用长任务中后段的约束遵循、错误事实比例和任务成功率衡量。必要时从可用原始事实重建，不能假定递归摘要天然可靠。

压完还是超窗怎么办？

检查增长来自 tail、单个大结果还是固定输入；采用针对性的有界缩减，限制重复尝试。若没有安全方案，明确报告不能继续。Maka 没有可概括为“本地严格变短/fit 后才提交”的通用保证，不应在产品描述中编造该 gate。

原生 opaque state 和文本摘要怎么选？

文本便于审阅和跨路线设计，但生成有误差；原生状态可能提供特定 provider 连续性，但重放和可审阅性受限。必须根据实际合同检查 model/connection 兼容，不把 opaque state 交给任意模型。
