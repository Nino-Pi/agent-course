第 44 章｜检查点、重放与工作流恢复

本章概览

核心问题：任务中途失败后，怎样复用已完成工作，同时避免重做已经发生的外部操作？

关键概念：控制状态：决定下一步；Checkpoint（检查点）：保存可恢复状态；Pending writes（待合并写入）：保留当前轮次已完成节点的输出；Replay（重放）：依据历史重建控制过程；幂等：重复请求按合同不增加业务效果。

关系主线：会话、图节点和工作流分别保存不同恢复单位；恢复控制位置后，仍须独立核对文件与远端效果，取消也不会自动回滚现实。

前置：第39章 第 1–4 节与 第18章 效果与恢复。综合设计示例见 第47章。

1. 固定一个任务，给失败精确的位置

沿用 Codex / Claude Code 深度课的扫描器：修复含空格路径被拆开的错误，保留普通路径行为，并更新说明。先由 A 调查参数流，B 调查测试入口；C 汇合证据后生成并应用补丁；D 验证；最后向用户交付。另加一个可选阶段 E：用户批准后把报告发布到远端。E 只用于讨论外部效果，不是本课实际发送动作。

表 1 / Table 1 · 1. 固定一个任务，给失败精确的位置
时刻已发生的事崩溃后必须回答的问题
F1A 已返回，B 失败，C 尚未开始能否保留 A，只重做 B？
F2C 已写文件，成功回执还未保存文件是否已经改变？重做 C 会不会覆盖后来修改？
F3D 已通过，正在等用户批准 E恢复后会再次验证、再次询问，还是直接发布？
F4E 的远端请求已被执行，响应丢失重发是否创建第二份报告？
F5用户取消，但旧 Worker 尚未收到谁还能继续写？晚到结果应接受还是丢弃？

这些问题不能靠一个 status = running 回答。至少有三种状态：控制状态决定下一步；证据状态保存观察和结果；世界状态包含真实文件、进程和远端对象。它们可能分属不同存储，写入时刻也不同。

本课后续算法都是自拟简化模型。它们帮助解释源码机制，不能直接当作框架 API 或生产实现。

2. 会话恢复：重建模型看过什么

先看最轻的方案。mini 的 DefaultAgent.step() 依次调用模型、执行动作、把 observation 加回 messages；run() 的 finally 保存轨迹。它便于重建“模型依据什么做决定”，但这里没有一个把环境写入与轨迹保存一起提交的事务。F2 发生时，最后一段轨迹可能缺少成功 observation，而文件已经变了。再次调用 run() 还会重新初始化 messages；轨迹文件存在，本身不等于自动从某条工具指令继续。

Pi 将会话条目组织为 id → parentId 的路径，buildSessionContext() 从选定叶子重建模型输入；持久模式下 _persist() 写 JSONL，初始尚无 assistant 的条目可能延迟落盘。分支意味着选择另一条上下文路径，不能把工作目录也倒回同一时刻。与此同时，steer/followUp 的待输入数组属于运行中的会话对象；已保存的历史与还未消费的队列必须分别判断。

把这个差别应用到 F2：恢复出的模型输入若仍说“准备修复”，模型应重读当前文件，确认旧内容、目标内容或第三种内容，再决定继续。不能因为会话回到过去，就假定文件也回到过去。

DeepSeek Harness（DSH）展示另一种补充：ReactLoopInbox 把插入、删除、替换写成 agent/inbox/spliced 事件；inboxProjectionDefinition.apply() 顺序折叠这些事件，重建 next-turn/next-step，并拒绝越界 splice 和跨队列重复消息身份。因此它能回答“重启后还有哪些输入待处理”。claim 从 pending 移除输入并发出领取事件，仍没有把该消息未来触发的所有工具效果装进同一个提交。

为什么选择这一层？ 交互式修复最常见的问题是重新打开会话后继续调查。会话路径和持久 inbox 各解决一个有限问题，容易接入既有工具循环。代价是开发者仍要定义步骤完成、未知效果与跨任务交接；它们并不自动提供图节点级恢复。

3. LangGraph：把恢复单位放在图状态与计算轮次

LangGraph 的 Pregel 运行时把一次计算拆成 plan、execution、update：先选本轮节点，再执行，最后更新 channels。channel 是节点之间传递值、保存图状态的通道，具体合并规则由通道或状态字段的定义决定。本轮节点的 channel 写入到下一轮才对其他节点可见。这一轮叫 superstep。它是图计算的同步边界，不是模型的一轮回答，也不是数据库自动替所有工具建立的事务。

对本例，令 S0 包含目标、约束、当前工作区描述，安排 A/B 并行。A 返回 parameter_evidence，B 返回 test_evidence。两者完成后按 reducer 合成 S1，C 才能读取完整证据。reducer 就是“同一字段收到多份更新时如何合并”的函数；如果把两份自然语言报告简单覆盖为最后一份，会无意丢失证据。如果两位作者都更新同一条结论，按稳定证据身份合并并保留冲突，通常比依赖完成先后更可解释。这是本课的数据设计建议。

S0 + 就绪节点 {A, B}
    A(S0) -> 写入 WA
    B(S0) -> 写入 WB
本轮成功 -> S1 = 合并(S0, WA, WB) -> 保存 checkpoint -> 安排 C

关键在 F1：A 成功、B 失败。若只保存整轮后的 S1，这时整轮没结束，A 也要重跑。LangGraph 另存 task 级 pending writes：A 成功后可先保存其输出，关联当前 checkpoint 与 task 身份。恢复时找回 A 的写入，只执行尚未成功的 B；随后再形成完整的下一轮状态。pending writes 是未完成轮次中已完成任务的输出，不是“还没写入磁盘的内容”。本段以没有额外 error-handler 路由的基本图为例。

下图只展开 F1 的恢复：A/B 读取同一轮状态；恢复时 A 的成功输出已经持久保存，B 按本例策略重试并成功。合并前的等待线表示数据依赖，不把“一个任务结束”画成“整轮检查点完成”。

对应源码有三个各自必要的动作。PregelRunner.commit() 区分成功、异常和 interrupt 并提交 task writes；PregelLoop._reapply_writes_to_succeeded_nodes() 恢复成功写入，跳过 ERROR/INTERRUPT 等控制项；after_tick() 调用 apply_writes() 合并状态并保存下一 checkpoint。已核对的当前源码还支持失败 handler 路由，因此不能把所有错误都理解成无限重试原节点。

恢复用的教学算法：
读取本次 thread 的 checkpoint Ck 与 pending writes P
按 Ck 的 channel/version 信息重建待运行任务
对每个任务 t：
    若 P 有 t 的成功输出 -> 复用输出
    否则 -> 按 retry / interrupt / error-handler 策略处理
本轮所需输出齐备 -> reducer 合并 -> 保存 Ck+1

这能避免 A 因 B 的失败反复调用模型、读仓库，尤其适合代价不均衡的并行调查。但 barrier 也让 C 等待慢节点；大输出会增加序列化和存储成本。合并同一字段仍需显式语义。源码 apply_writes() 按 task path 排序后更新 channels 和 version，提供稳定处理顺序；稳定顺序不证明两份互相矛盾的业务结论能正确融合。

上述恢复依赖数据的保存位置和保存时机。InMemorySaver 不提供进程重启后的存储。当前公开 durability 模式中，sync 等 checkpoint 保存后再进下一步，async 与下一步重叠，exit 主要在本次运行退出时保存；越晚保存，越可能在进程崩溃时失去中间进展。F1 的结论以所需写入已成功持久化为前提，不能从类名叫 checkpointer 就省略此前提。

4. 节点能恢复，不代表节点内部每一行都能恢复

将 C 写成“生成补丁 → 写文件 → 返回 patch_applied”。F2 恰好落在后两步之间，C 没有成功 task output 可复用。重新执行这个节点，可能再次调用模型、再次写文件。把生成补丁和应用补丁拆成两个节点，可以复用已保存的补丁，缩小重复范围；它仍无法消除“写文件成功但应用回执未保存”的间隙。

F3 的暂停也有同样的问题。LangGraph interrupt() 恢复时从该节点开头重新执行，resume 值在对应 interrupt 位置返回。假如节点先“发布报告”再 interrupt 询问批准，第一次就已经发布，恢复时还可能再次发布。应将批准放在效果之前，并保证任何可能重跑的前置操作可重复执行。

正常故障恢复与 time travel 还要分开：主动选历史 checkpoint 重新探索时，该点之后的节点可以重新运行，包括模型和 API 调用；这不是拿一份历史记录做无副作用回放。前者希望延续同一次逻辑工作，后者可能有意产生新尝试，业务动作身份也应由应用明确决定。

何时有优势？ 图上需要长期保留可检查状态、局部失败恢复、暂停让人修改输入，且开发者能设计节点边界时。代价是什么？ 必须管理 state schema、reducer、持久化后端和动作身份。未保证什么？ 图 checkpoint 不会冻结共享目录，不会撤销节点内部已经发送的请求，也不使外部系统自动遵守 graph state。

5. Temporal：保存事件，让控制代码重新走到同一位置

Temporal 采用另一种恢复重心。Workflow 写的是控制逻辑；LLM 请求、读文件、修改仓库、发布报告等不确定操作通常放进 Activity。Workflow 的事件历史记录调度和结果；Worker 丢失内存后，可用历史重建执行位置。这里的 deterministic replay 要求控制代码在相同历史下产生兼容的 Workflow command 序列，不要求模型每次生成相同答案。

下面是本例的自拟控制伪代码，activity/await/all/waitApproval 不是任何 SDK 的直接调用格式：

a = activity("investigate-parameters", input)
b = activity("investigate-tests", input)
evidence = await all(a, b)
patch = await activity("propose-patch", evidence)
receipt = await activity("apply-patch", patch, logicalEditKey)
verdict = await activity("verify", receipt)
approved = await waitApproval(reportRevision)
if verdict.pass and approved:
    await activity("publish-report", report, logicalPublishKey)

设历史已有 A scheduled → A completed(resultA) 和 B scheduled，随后 Worker 崩溃。新 Worker 重走控制函数，遇到调度 A 的调用时，SDK 对照历史，而不是重新请求 A；A 的 Future 可由历史结果完成。遇到尚无完成结果的 B 则继续等待对应执行或其重试结果。重做的是控制程序的计算，已经记录完成的 Activity 不因 Workflow replay 再运行。 如果 B 是尚未报告完成的 Activity，其重试是另一件事。

这不是“把任意函数再运行一次”。Go SDK 的 matchReplayWithHistory() 对生成的 commands 与 history events 做顺序匹配；isCommandMatchEvent() 在 Activity 情况下核对事件种类、Activity ID 和类型名，缺失、多余或不匹配会产生 nondeterminism 错误。它检查特定命令合同，不是比较所有应用变量的逐字节相等。

为什么把 LLM 调用移出去？假设 Workflow 直接再次询问模型“是否先验证”，第一次回答 yes、重放回答 no，就可能改变调度顺序，与历史矛盾。放在 Activity 里，已记录的回答是控制逻辑的输入。模型仍然可以动态选步骤；选择结果一旦记录，恢复时必须延续它，或通过明确的新输入产生后续决策。控制代码升级同样需要兼容旧历史或采用版本策略，不能任意交换两个已有步骤。

这一层适合等待跨天审批、多个服务参与、需要 Worker 更换后继续推进的工作。它减少了手工恢复控制位置的负担，同时引入服务与 Worker 的部署、历史管理、确定性 API 和代码升级成本。对于只需数秒完成的本地编辑，这些成本可能大于恢复收益。这是从机制得出的条件判断，不是框架性能排名。

6. 重放可靠以后，F4 为什么仍可能重复发布

Temporal Activity 可以在超时或失败后重试。F4 中远端已经创建报告，但 Activity 未把成功报告给 Temporal，历史中没有相应完成结果；再次执行 Activity 仍可能再次创建。官方明确把 Activities 的幂等设计交给应用，并指出幂等键最终由被调用服务执行。

用自拟业务协议展开这个间隙：

逻辑操作 K = "task-17 / report-revision-3 / publish"
尝试 1：发送 K -> 远端创建 R -> 回包丢失
尝试 2：仍发送 K -> 远端识别已有 K -> 返回同一个 R

K 必须标识逻辑动作，不能每次 retry 都生成新值。若 revision 已变，是否继续同一动作要重新决定；重复使用旧键却发送不同正文，也必须有明确冲突策略。保存期限、账户命名空间、同键并发处理都属于接收方合同。

若接收方没有原子去重，先查询再创建仍有竞争：两个 Worker 都查不到，然后各自创建。这时应考虑可唯一寻址的对象、接收方唯一约束、原子条件写入，或保留 unknown 并人工对账。“至少一次重试 + 一个本地布尔值”不足以推出效果恰好一次。这段是本课系统设计推导，不是声称所有框架已有此协议。

F2 的文件修改可以采用类似思路，但要尊重不同语义：重读后是目标内容，可核对是否符合预期后置条件；仍是原内容，可在满足写入条件时执行；变成第三种内容，就不能以“恢复”为由覆盖。前置版本检查若与写入之间没有资源 owner 的锁或原子操作，仍有竞态。工作区 checkpoint 提供的是另一条路：恢复被捕获的文件状态，而不是确认某个业务动作执行了几次。

这里沿用第23章的 Git 状态区分：提交保存一版文件，工作目录还可能含未提交编辑；HEAD 通常通过当前分支确定检出的提交，也可能直接指向某个提交。Git 引用是指向提交等对象的名称，分支名就是一种引用；update-ref 是更新引用的命令。它的旧值条件要求“引用仍等于先前观察的值时才更新”，以免覆盖检查之后发生的指针变化。未跟踪文件是当前不在 Git 跟踪范围内的工作区文件，不一定刚创建，也不是指 Agent 尚未读过的文件。

Cline SDK 的 applyCheckpointToWorktree() 从 Git checkpoint 恢复，检查当前 HEAD 是否仍对应恢复基点，再用 update-ref 的旧值条件避免分支指针检查后的竞争；是否清理未跟踪文件取决于快照是否捕获它们。这展示了具体的工作区恢复边界，仍不意味着整个恢复步骤、会话元数据与远端发布共用原子事务。Claude Code 的公开 checkpoint 范围另见第43章 第 8 节，不能把一个产品的边界移植给另一个。

7. 取消是一条协议，不能倒转已经发生的事

F5 可以展开为“用户发出取消 → 控制 owner 接受 → 不再调度新工作 → Worker 观察到取消 → 正在执行的工具退出 → 已发生效果完成对账”。每一步都有自己的时刻。只观察到前一步，不足以证明后一步完成。

Temporal 的远端 Activity 通过 heartbeat 接收来自服务的取消，Workflow 可选择是否等待 Activity 接受取消；超时后旧执行也可能仍在工作。源码中 Activity completion 和 cancellation 有独立转换，handleActivityTaskClosed() 会清除已无必要的取消命令。这说明完成与取消可能竞争，不能把 cancel request 当成效果已撤销。

OpenHands 则给出进程内执行的不同粒度：LocalConversation.pause() 在步骤间生效；interrupt() 先设置取消 token，再取消跟踪中的异步 arun()，没有 async task 时退回 pause。并发输入也影响旧动作：arun() 发现新用户消息赶在步骤完成或等待确认时到达，会拒绝被替代的待批准动作，避免下一次 step 把旧动作隐式执行。这是下一步合法性检查，不能追回已完成的外部效果。

Letta Code 的 QueueRuntime.pause() 又是另一个范围：给调用时已经排队的用户消息加 paused 标记，系统来源消息不受同一规则影响；peekReady() 排除 paused 项。它解释为什么“停止当前回答”之后既要阻止旧用户队列自行续跑，又可能允许后台完成通知进入。该队列方法本身不能证明跨进程持久化或定时任务被禁用。

对我们的扫描器，用户取消后应先阻止 E 新发布，检查 C 是否留下修改、D 的证据是否仍对应这些文件，再报告已完成与未知部分。若还有旧 Worker 写入权限，单靠父任务忽略它的消息无法阻止修改；需要资源层的权限收回、串行 owner 或 fencing。已经发布的报告需要撤回动作或业务补偿，补偿本身也是可能失败的新动作。

8. 多 Agent 共享什么，比画几个角色更影响结果

OpenHands DelegateExecutor 是一个明确的实现样本：spawn 创建独立 LocalConversation，复制 LLM 配置、重置子任务统计，但 workspace 使用父工作目录；父会话配置持久化时，子会话继承到 subagents 目录。delegate 为每个任务启动线程，join 后按输入任务顺序汇总结果或错误，并用累计值替换父统计中的对应 child 项，避免重复累加。

把 A/B 放进去很自然：二者只读、输出能分别验收；让 A/B 同时改 scan.py 则不会因“独立会话”自动安全。这条 executor 中 _sub_agents 映射和线程是进程内对象；子会话落盘不能单独证明重启后自动恢复所有委派关系与待交付结果，也没有自动建立工作副本合并协议。

Goose summon 的另一重点是后台执行与观察者分离：spawn_background_task() 用独立 completion token 表示 future 生命周期；refresh_task_turns() 从持久 conversation 的可见 assistant blocks 取数，排除 compaction scaffolding。这有助于等待者离开后仍正确观察完成和计量，但此处核对的 JoinHandle、token、缓存不能推出分布式 Worker crash 后原执行自动复活。

无论采用哪种实现，都要分别设计下面四种共享：

控制权（Authority）一个 owner 决定新任务、取消与交付同一 owner 仍需持久化和代际检查，不能只靠提示词

Codex 的 history fork、消息排队与唤醒，以及 Claude Code 的初始化和 worktree 是进一步的产品对照，分别进入 第41章：Codex 记忆与协作与 第43章：Claude Code 子任务与恢复。Claude Code 的对照限于公开产品行为。

只取 A/B 调查与 C 修改这三项工作，令各自耗时为 tA、tB、tC。一个粗略的教学成本模型是：串行时间约 tA + tB + tC，并行时间约 max(tA, tB) + tC + 初始化 + 交接 + 集成。并行化省掉的上限是 min(tA, tB)；如果交接和冲突恢复更贵，Agent 更多反而更慢。checkpoint 也有类似边际：把昂贵、可复用的步骤拆开可以节省重算，但过细的步骤增加持久化、网络和历史体积。这里没有测量值，不能据此写出跨框架速度排名。

这些机制可以组合。例如外层 Workflow 负责等待、重试和业务动作身份，内部一个有界 Activity 执行 Agent 调查；但 Activity 重试可能重做整段调查，所以要决定是否复用内层持久状态、由谁拥有重试次数，以及如何避免两层同时放大尝试。组合不是自动获得两套保证的并集。

10. 五个故障点的完整参考结论

A 成功而 B 失败，为什么仅保存完整 checkpoint 不够？ 完整下一状态尚未形成。若希望不重做 A，需要保存 A 的独立结果及身份，恢复时把它与 B 的新结果合并；LangGraph pending writes 正在解决这一层问题。若 A 的结果尚未真正持久化，仍可能重做。

Temporal replay 再次走到 apply-patch，为什么不一定再写文件？ 若该 Activity 已有完成事件，SDK 用历史完成结果继续控制程序。若文件已写但 Activity 没有完成回执，Activity retry 仍可能重复写；必须另做效果检查或幂等。

把一个节点拆成生成补丁、应用补丁两个节点，解决了什么？ 生成结果已保存时可复用，缩小重复范围；没有把文件写入与应用结果记录变成同一事务。

两位子 Agent 各自持久化，为什么总任务还会丢交接？ 子会话保存不等于父子关系、待交付状态与父任务采纳已持久化。还要能重新定位产物、识别已采纳结果并再次验收组合后的状态。

什么时候应承认 unknown？ 外部请求已发出但回执缺失，且无法通过接收方幂等、权威查询或其他合同判定是否发生时。把 unknown 改成 failed 然后无条件重试，只是掩盖不确定性。

下面将 F1–F5 补成完整参考方案：外层控制状态持久化，A/B 的成功输出分别保存；C/E 另有业务动作身份；文件与远端服务保持各自的效果合同。这是组合设计，不是任一框架默认提供的完整机制。
