第 44 章｜检查点（Checkpoint）、重放（Replay）与工作流（Workflow）恢复（Recovery）

本章概览

核心问题：中途失败后，怎样复用已完成工作，同时避免重做已经发生的操作？

关键概念：检查点（Checkpoint）保存某个恢复单位的状态；待合并写入（Pending Writes）保留尚未结束的计算轮次中已完成节点（Node）的输出；重放（Replay）依据历史重建过程；幂等性（Idempotency）约束重复操作的效果（Effect）。工作流（Workflow）与活动（Activity）分别组织控制和实际工作。

关系主线：先找失败发生的位置，再判断保存了什么、允许重做什么；恢复控制位置后，文件和远端效果（Effect）仍需独立核对。

前情回顾：恢复（Recovery）要把三种状态重新对齐

第 18 章解释过，工具缺少成功回执时，真实效果（Effect）可能已经发生。第 39 章把可靠协作拆为分配、认领与结果接纳：交出工作后，需要知道由谁继续、哪些产物已被采用。第 43 章进一步说明，对话恢复（Conversation Recovery）与代码恢复（Code Recovery）各有范围，不能代替整体验收。

这些关系可以归为三类状态：控制状态（Control State）决定下一步；证据状态（Evidence State）保存观察与结果；环境状态（World State）包含真实文件、进程和远端对象。三者可能保存在不同地方，也可能在不同时间更新。

本章用同一个任务比较恢复（Recovery）机制。先问“一份已完成调查能否保留”，再问“控制程序如何继续”，最后处理“真实操作是否已发生”。这样就能看出不同框架的保证具体落在哪一层。

固定 A–E 的任务条件，再放入五个故障点

沿用扫描器的含空格路径问题：修正参数被错误拆开的行为，保留普通路径行为，并更新说明。用户允许修改实现、必要测试和 README，保留已有配置改动。A 只读调查参数流，B 只读调查测试入口；C 汇合证据、生成并应用补丁；D 验证修改，之后交付。

另设可选阶段 E：用户批准当前报告修订（Revision）后，才把报告发布到远端。E 是用来讨论外部效果（Effect）的授权变体，不是本课实际发送动作。这里的 A/B 标签按本章重新定义，不能套用第 43 章三份调查的编号。

这里的执行者（Worker）指实际领取并运行工作的程序，不是任务线程（Thread）的别名。一个 status = running 无法回答整张表。必须把状态对应到具体对象：例如“已保存 A 的输出”和“已保存发布回执”解决的就是不同故障。

以下算法、公式与组合方案都是教学抽象，不是可直接调用的框架接口，也不是运行结果。

会话（Session）恢复（Recovery）：先重建模型的判断依据

如果只希望重新打开一项短修复并继续调查，会话（Session）记录就是自然起点。但它首先恢复的是背景与观察，不会自动把文件恢复到同一时刻。

mini 的 DefaultAgent.step() 先请求模型，再执行行动请求（Action），最后把观察消息（Observation Message）加入历史；run() 在循环的 finally 中保存执行轨迹（Trajectory）。这帮助解释模型依据什么作出决定，但环境写入和这份记录的保存并不共用一个原子事务（Atomic Transaction）。F2 发生时，文件可能已经变了，最后成功观察却未保存。再次调用 run() 还会重新初始化消息列表（Message List），因此执行轨迹（Trajectory）文件存在不等于从某条工具指令自动继续。mini 的循环与保存。

Pi 的会话（Session）条目通过 id → parentId 形成路径。buildSessionContext() 从选定叶子重建模型输入（Model Input）；持久模式下 _persist() 写 JavaScript 对象表示法（JavaScript Object Notation，JSON）的逐行格式（JSON Lines，JSONL），初始尚无 assistant 消息的条目可能延迟写入。选择另一条路径改变了背景，不会把工作目录（Working Directory）倒回过去。Pi 路径重建与保存。

还有一类状态是“用户刚追加、但尚未消费的输入”。Pi 的 steer/followUp 待输入数组属于运行中的会话（Session）对象，不能和已保存历史混为一谈。DeepSeek Harness（DSH）则通过持久收件箱（Persistent Inbox）补充这一层：ReactLoopInbox 把插入、删除和替换记为 agent/inbox/spliced 事件（Event），inboxProjectionDefinition.apply() 顺序重建 next-turn / next-step，拒绝越界修改和跨队列重复身份（Identity）。Pi 输入队列、DSH 收件箱。

DSH 的 claim() 从待处理列表移除消息并发出领取事件（Event），回答的是哪些输入已领取；它没有把这些输入未来触发的所有效果（Effect）装进同一个提交。这正是恢复（Recovery）时必须分对象判断的原因。

应用到 F2，重建后的模型输入（Model Input）即使仍写着“准备修复”，也应先重读文件。它可能仍是原内容，可能已经是目标内容，也可能有第三方修改。会话（Session）历史提供调查起点，具体哪一步可以重做，还需要更明确的恢复单位。

F1：为什么要保存待合并写入（Pending Writes）

现在把恢复单位放到图中的节点（Node）。LangGraph 的 Pregel 运行时（Runtime）把一次计算组织为规划（Plan）、执行（Execution）、更新（Update）三个阶段：先选本轮节点（Node），再运行，最后合并写入。节点（Node）之间通过通道（Channel）传值；本轮产生的更新，到下一轮才对其他节点（Node）可见。

这样的一轮称为超级步（Superstep）。它是图计算的同步边界，既不等于面向用户的工作轮次（Turn），也不自动为节点（Node）内部的文件或网络操作建立事务（Transaction）。Pregel 运行时（Runtime）。

令 S0S_0S0​ 表示调查开始前的图状态（Graph State），包含目标、约束与工作区（Workspace）描述；WAW_AWA​、WBW_BWB​ 分别表示 A/B 输出的参数依据与测试依据。先读正常路径：

WA=A(S0),WB=B(S0)W_A=A(S_0),\qquad W_B=B(S_0)WA​=A(S0​),WB​=B(S0​)
S1=merge⁡(S0,WA,WB)S_1=\operatorname{merge}(S_0,W_A,W_B)S1​=merge(S0​,WA​,WB​)

这些式子只表示数据依赖。A/B 读取同一个输入状态，输出齐备并合并后，C 才能使用 S1S_1S1​。这里的合并按通道（Channel）或字段定义执行；状态合并函数（Reducer）决定多份更新如何作用于已有值，并不意味着所有字段都采用同一种运算。

如果只保存完整的 S1S_1S1​，F1 就有困难：B 失败使整轮未完成，A 的成果也可能随进程丢失。待合并写入（Pending Writes）因此单独保存本轮已完成工作的输出，并关联当前检查点（Checkpoint）与任务身份（Identity）。恢复（Recovery）时可以复用 A，只按策略处理 B，而后形成下一状态。

“待合并”指尚未汇入完整下一状态，不是“尚未写入持久存储”。下面以没有额外错误处理路由的基本图为例，并假设 A 的成功输出确已持久保存、B 在恢复后重试成功。

这条路径要同时具备三项能力：记录单项结果，恢复时识别已成功的身份（Identity），最后才合并下一状态。简化算法中的 CkC_kCk​ 是本次任务线程（Thread）的检查点（Checkpoint），PPP 是关联的待合并写入（Pending Writes）；这里的任务线程（Thread）是持续工作的标识，不是操作系统线程（Operating System Thread）。

对每个任务 t：
    若 P 有 t 的成功输出：

对应到源码，PregelRunner.commit() 区分成功、异常和中断（Interrupt）并提交写入；_reapply_writes_to_succeeded_nodes() 找回成功写入，跳过 ERROR、INTERRUPT 等控制项；after_tick() 调用 apply_writes() 更新状态并保存下一检查点（Checkpoint）。当前实现另有错误处理路由，所以不能把所有失败都说成必然重跑原节点（Node）。单项结果提交、恢复与下一状态。

还有两个限制不能省略。第一，保存到哪里、何时完成：InMemorySaver 只放在内存，进程重启后不能复用；sync 在下一步前完成保存，async 让保存与下一步重叠，exit 在本次图执行退出时保存。后两种存在中间进展丢失的相应窗口。F1 的复用结论以所需记录真正保存成功为前提。持久化范围、保存时机。

第二，合并顺序不等于业务正确性。apply_writes() 按任务路径提供稳定更新顺序，仍不能决定两份矛盾结论该信哪份。若把同一报告字段简单覆盖为最后一份，就可能丢失证据。对本例，按来源与稳定身份（Identity）组织证据、保留冲突，是应用需要设计的语义。写入合并实现。

这类机制适合昂贵且可独立复用的分支。不过，C 仍需等待慢分支，大输出会增加序列化与存储成本；多拆节点（Node）并非免费获得更多可靠性。

F2 与 F3：节点（Node）可恢复，内部操作仍可能重做

把 C 写成“生成补丁 → 写文件 → 返回 patch_applied”。F2 落在后两步之间，成功输出还不存在。恢复（Recovery）时若重新执行 C，就可能再次生成、再次写入。

可以把它拆成“生成补丁”和“应用补丁”两个节点（Node）。生成结果保存成功后，后续不必重新询问模型，这缩小了重复范围；但实际写入成功、应用回执未保存的间隙仍在。改变恢复单位，可以减少重算，不能消除单位内部的效果（Effect）间隙。

F3 的中断（Interrupt）也要放对位置。LangGraph interrupt() 恢复时从所在节点（Node）开头重新执行，恢复值在对应位置成为返回值。若先发布再询问批准，第一次已经发布，下一次还可能重复。应先取得有效批准，再产生相关效果（Effect），并使可能重跑的前置操作可重复执行。中断恢复语义。

主动选择历史检查点（Checkpoint）再探索，称为时间旅行（Time Travel）。该点之后的节点（Node）可以重跑，包括模型调用和应用编程接口（Application Programming Interface，API）请求；它不是无副作用（Side Effect）的历史展示。正常故障恢复（Recovery）希望延续原工作，主动探索则可能生成新尝试，业务身份（Identity）应由应用明确选择。时间旅行（Time Travel）的执行范围。

因此图状态（Graph State）适合可检查、可暂停和局部恢复的流程；开发者同时要维护状态结构、状态合并函数（Reducer）、存储后端与动作身份（Identity）。图不会冻结共享目录，也不会使远端系统自动服从本地记录。

工作流（Workflow）重放（Replay）：重走控制程序，怎样不重做已完成工作

Temporal 将控制逻辑放在工作流（Workflow）中，将模型请求、读写文件、发布报告等实际操作放在活动（Activity）中。执行者（Worker）负责运行代码；事件历史（Event History）保存调度与结果，帮助更换执行者（Worker）后继续。

确定性重放（Deterministic Replay）要求控制代码在同一历史下产生兼容的命令（Command）序列，不要求模型每次生成同样答案。已经记录的活动（Activity）结果可以作为恢复后的输入，控制程序再走一遍，并不意味着外部函数又执行一遍。

先把伪代码的输入讲清。input 包含目标、约束与文件定位；logicalEditKey 标识这次逻辑编辑；reportRevision 是本次待审报告修订（Revision）的稳定标识；logicalPublishKey 标识该修订（Revision）的一次逻辑发布。它们由调用方在本轮开始时确定并保留，不因重试换新值。report 则由已取得的调查、补丁和验证结果组成；waitApproval 按该标识呈现这份报告，等待用户针对它的决定。

下面按“并行调查 → 修改验证 → 等待批准 → 条件发布”阅读。activity/await/all/waitApproval 是教学写法，不是软件开发工具包（Software Development Kit，SDK）的直接调用格式。

# 调查互不依赖，汇合以后才形成修改依据。
a = activity("investigate-parameters", input)
b = activity("investigate-tests", input)
evidence = await all(a, b)
patch = await activity("propose-patch", evidence)
receipt = await activity("apply-patch", patch, logicalEditKey)
verdict = await activity("verify", receipt)

# 构造报告只组合已有结果；不在控制代码里重新询问模型。
report = { evidence, patch, verdict }
approved = await waitApproval(reportRevision)
if verdict.pass and approved:
    await activity("publish-report", report, logicalPublishKey)

这里保留了先等待、再联合判断的教学顺序：即使收到了批准，verdict.pass 为假仍不能发布。F3 指向验证已通过的分支。实际产品可把“检查不通过则不发起发布审批”另设为控制分支，但升级既有流程时必须考虑历史兼容，不能任意换序。

现在假设历史已有 A scheduled → A completed(resultA) 和 B scheduled，随后执行者（Worker）崩溃。新的执行者（Worker）重走控制函数，遇到 A 的调度时与历史匹配，A 的异步结果（Future）由既有结果完成；B 尚无完成记录，则继续等待对应执行或其重试结果。

工作流（Workflow）重放（Replay）与活动（Activity）重试是两件事。 前者重建控制过程，后者可能重新执行尚未报告完成的实际工作。

Go 软件开发工具包（SDK）的 matchReplayWithHistory() 对命令（Command）与历史事件（Event）进行匹配；活动（Activity）调度分支中的 isCommandMatchEvent() 检查事件（Event）种类、活动（Activity）标识和类型名的相应部分。缺失、多余或不匹配会产生非确定性错误；它并不比较全部应用变量的每一个字节。重放（Replay）匹配实现。

为什么不能在控制代码里直接再问模型“是否先验证”？若第一次答 yes，重放（Replay）时答 no，就可能改变命令（Command）顺序。把选择放进活动（Activity）并记录结果后，恢复（Recovery）可以继续原选择；需要改变时，再通过明确的新输入推进。控制代码更新也须兼容旧历史或采用版本策略。确定性与版本约束。

这适合跨天等待、多个服务参与、控制寿命超过单个执行者（Worker）的流程；代价是服务部署、历史管理、确定性接口与升级策略。对于几秒完成的本地编辑，这些成本可能超过收益，不能据此给框架排统一的强弱顺序。

F4：控制重放（Replay）可靠，为什么仍会重复发布

假设远端已创建报告，但活动（Activity）没有把成功回执交给 Temporal。历史中缺少完成记录，超时或失败后的重试仍可能再次创建。外部服务的幂等性（Idempotency）必须由应用与接收方落实，不能从控制历史自动获得。活动（Activity）的重试与幂等性（Idempotency）。

以同一逻辑身份（Identity）说明接收方合同。下面的 KKK 是逻辑发布的幂等键（Idempotency Key），RRR 是创建出的远端报告，而两次发送是不同物理尝试。

逻辑操作 K = "task-17 / report-revision-3 / publish"
尝试 1：发送 K -> 远端创建 R -> 回包丢失
尝试 2：仍发送 K -> 远端识别已有 K -> 返回同一个 R

这条路径成立，要满足接收方确实按同一 KKK 识别与处理重复。若每次重试都换键，就变成了两个逻辑动作；若报告修订（Revision）变化，却用旧键发送不同正文，也需要明确的冲突规则。保存期限、账户命名空间与同键并发处理，都属于幂等性（Idempotency）合同。

查询后创建也不天然安全：两个执行者（Worker）可能同时查不到，然后各创建一次。可以使用可唯一寻址的对象、接收方唯一约束或原子条件写入；缺少这类合同与可靠查询时，保留未知效果（Unknown Effect），再对账（Reconciliation）。

“至少一次重试 + 一个本地布尔值”不足以推出效果恰好一次（Exactly Once）。这里是系统设计推导，不是声称所有框架默认具备相同去重协议。

如果前置条件（Precondition）检查与写入之间没有资源负责者（Owner）的锁或原子操作，检查完以后仍可能被别人改变。工作区（Workspace）检查点（Checkpoint）提供另一种能力：恢复被捕获的文件状态，而不是证明某个业务动作执行了几次。

这里沿用第 23 章的 Git 区分：提交（Commit）保存一版文件；工作树（Worktree）还可能包含未提交编辑。HEAD 通常通过当前分支定位检出的提交（Commit），也可以直接指向它。引用（Reference，Ref）是指向提交（Commit）等对象的名称，分支名就是一种引用（Ref）。update-ref 的旧值条件要求名称仍指向先前观察的值，才允许更新。

Cline 软件开发工具包（SDK）的 applyCheckpointToWorktree() 先检查当前 HEAD 是否仍对应恢复基点，再用 update-ref 的旧值条件处理指针检查后的竞争。是否清理未跟踪文件（Untracked File）取决于快照（Snapshot）是否捕获了它们；“未跟踪”指 Git 未跟踪，不是代理没有读过，也不一定刚创建。Cline 文件恢复实现。

这些具体保护不意味着整个恢复（Recovery）过程、会话（Session）元数据与远端发布共用事务（Transaction）。Claude Code 的公开检查点（Checkpoint）范围则见第 43 章，不能把一个产品的条件移植给另一个。

F5：取消（Cancellation）是一条逐步完成的协议

把 F5 展开，会看到多个时刻：用户提出取消（Cancellation），控制负责者（Owner）接纳，不再安排相关新工作，执行者（Worker）收到信号，运行中的工具退出，最后完成效果（Effect）对账（Reconciliation）。前一步发生不能证明后一步已完成。

Temporal 远端活动（Activity）通过心跳（Heartbeat）接收服务的取消（Cancellation）；工作流（Workflow）可以选择是否等待它接受。超时后，旧执行者（Worker）也可能仍在工作。Go 软件开发工具包（SDK）的 handleActivityTaskClosed() 会移除已无必要的取消命令（Command），体现完成与取消（Cancellation）可能竞争；没有把真实操作倒转。活动（Activity）的取消（Cancellation）条件、命令（Command）状态转换。

OpenHands 展示进程内的另一种粒度：LocalConversation.pause() 在步骤之间生效；interrupt() 先设置取消令牌（Cancellation Token），再取消跟踪中的异步 arun()，没有异步任务时退回暂停。若新的用户消息在步骤结束或等待确认时到达，arun() 会重新检查后续处理；其中待批准动作已被新输入替代时，先拒绝它，避免下一步隐式执行旧请求。这限制后续动作，不会追回已完成效果（Effect）。暂停、中断与新输入。

Letta Code 的 QueueRuntime.pause() 又只处理调用时已经排队的用户消息，给它们加 paused 标记；系统来源消息不受同一规则影响。peekReady() 排除被暂停项，所以旧输入可以停住，后台完成通知仍可进入。这个队列方法本身不能证明跨进程保存，也不能证明定时任务被关闭。队列暂停范围。

应用到扫描器，先阻止 E 的新发布，再检查 C 已留下哪些修改、D 的证据是否仍适用。如果旧执行者（Worker）还有写权限，父任务（Parent Task）忽略晚到消息也挡不住它改文件。需要资源层撤销权限、串行负责者（Owner）或隔离令牌检查（Fencing）：在接纳写入的位置核对代际（Generation），拒绝过时执行者（Worker）。

即便本地状态拒绝旧代际（Generation），不检查该标记的外部资源仍可能被写入。已经发布的报告要另行撤回或补偿（Compensation）；补偿（Compensation）也是可能失败的新动作。

子代理（Subagent）协作：独立保存，不等于自动恢复交接

把 A/B 交给子代理（Subagent）很自然：它们只读、相互独立，产物能分别验收。不过独立会话（Session）和共享文件仍要分开。

OpenHands DelegateExecutor 创建独立 LocalConversation，复制大语言模型（Large Language Model，LLM）配置并重置统计，工作区（Workspace）却使用父工作目录（Working Directory）。父会话（Session）配置持久化时，子会话（Session）在 subagents 目录保存。随后通过操作系统线程（Operating System Thread）并行执行，join 后按输入顺序收集结果或错误；累计统计替换父统计中的对应项，避免重复相加。委派（Delegation）实现。

因此让 A/B 同时改 scan.py 不会因各自有历史而安全。该执行器的 _sub_agents 映射与线程属于进程内对象；子会话（Session）落盘不能单独证明父子关系、待交付结果和结果采纳（Result Adoption）已能跨崩溃恢复，也没有自动形成工作树（Worktree）合并协议。

Goose summon 则将后台实际执行与等待者观察分开。spawn_background_task() 用独立完成令牌（Completion Token）表示异步结果（Future）对象的寿命；refresh_task_turns() 从持久对话中的可见助手消息块计数，排除上下文压缩（Context Compaction）的辅助内容。读取失败时仍有缓存回退。这有助于观察完成与计量，但 JoinHandle、令牌和缓存不证明分布式执行者（Worker）崩溃后原工作自动复活。后台执行与观察。

问答与 F1–F5 的完整参考方案

A 成功而 B 失败，为什么只保存完整检查点（Checkpoint）不够？

完整下一状态尚未形成。要保留 A，就要另存其结果与身份（Identity），恢复（Recovery）时与 B 的新结果合并；待合并写入（Pending Writes）解决这一层问题。A 尚未成功持久保存时仍可能重做。

工作流（Workflow）重放（Replay）再次走到 apply-patch，为什么不一定再写文件？

若活动（Activity）已有完成事件（Event），软件开发工具包（SDK）用历史结果推进控制程序。若文件已写却未报告完成，活动（Activity）重试仍可能重复写，需要效果（Effect）核对或幂等性（Idempotency）。

把 C 拆成生成与应用补丁两个节点（Node），解决了什么？

生成结果保存成功后可以复用，缩小重复范围；没有使文件写入与应用回执成为同一个事务（Transaction）。

子代理（Subagent）各自持久保存，为什么总任务仍会丢交接？

子会话（Session）保存不等于父子关系、待交付状态与结果采纳（Result Adoption）都已保存。恢复（Recovery）还要能定位产物、识别已采用的结果并重新验收组合状态。

什么时候应承认未知效果（Unknown Effect）？

请求已发出但回执缺失，且没有接收方幂等性（Idempotency）、可靠查询或其他合同来判定是否发生时。改称失败并无条件重试，只是隐藏了不确定性。

下面给出完整组合方案：外层控制状态（Control State）持久保存，A/B 成功输出分别保存；C/E 各有逻辑身份（Identity），文件与远端服务分别执行效果（Effect）合同。这不是任一框架默认具备的完整能力。
