第 56 章｜工具发现（Tool Discovery）与调度（Scheduling）

本章概览

核心问题：工具（Tool）增多、一次提出多个调用时，怎样减少输入开销，同时保留权限（Permission）、依赖（Dependency）与部分结果？

关键概念：工具目录（Tool Catalog）保存能力说明；可用快照（Active Snapshot）固定本步可调用集合；激活（Activation）改变后续工具声明（Tool Specification）；有向无环图（Directed Acyclic Graph，DAG）表达依赖（Dependency）；资源冲突（Resource Conflict）限制并行；逐项结算（Per-call Settlement）保留各调用的结果。

关系主线：发现（Discovery）选择已绑定能力，调度（Scheduling）再检查依赖（Dependency）、资源和执行准入（Admission）。候选可见不等于获准执行，同批调用也不共享一个成功或失败结论。

前情回顾：先知道一次调用的边界，再安排多次调用

第50章把工具（Tool）名称、参数、执行合同和观察结果（Observation）连起来；第51章说明同一文件名不保证还是读到的版本；第52章区分执行效果（Effect）、提交（Commit）和回执（Receipt）。其中准备边界T1标记从此可能执行，结果结算T2保存已接受的结果（Outcome）；这些含义以持久接收端（Durable Sink）已接线为前提。一次调用的结果尚不确定时，增加并行数量不会替它补齐证据。

第53章还说明，工具声明（Tool Specification）占用模型输入（Model Input）。本章沿两条线扩展：发现（Discovery）决定模型（Model）知道哪些可用动作，调度（Scheduling）决定已形成的动作何时可以执行。 少放完整说明解决输入成本，依赖（Dependency）与资源规则解决执行次序。

下面类型与算法是教学设计，调度（Scheduling）骨架不是 Maka 普通工具（Tool）批次的应用编程接口（Application Programming Interface，API）。跨智能代理（Agent）的负责者（Owner）和任务接续另见第57章、第58章。

原题、任务范围与最小起点

现在接入数百个工具（Tool），全量工具声明（Tool Specification）既贵又容易混淆。本题允许修正 README 与时长函数 duration.js，沿已有错误断言定位问题；这是本题明确的写入范围，并非沿用第53/54章只改 README 的限制。

用户还给出已经存在的持续集成（Continuous Integration，CI）测试任务 j9，只要求查询其状态（State），不创建另一份远端任务。常用的读取（Read）、编辑（Edit）与命令执行（Bash）直接可见，低频的远端查询能力按需发现（Discovery）。若实际只需三个工具（Tool），最小方案仍可直接提供三项工具声明（Tool Specification）。

设计前先固定可信目录来源、动态更新策略、工具声明（Tool Specification）预算（Budget）、服务限流和并发上限。工具（Tool）是否会读写同一资源，不能仅从名字判断；少给声明也不会给未授权动作增加权限（Permission）。

发现（Discovery）先区分三个集合

三条箭头分别有不同含义：目录到上限由宿主（Host）做可信绑定（Binding）；搜索结果到下一步工具声明（Tool Specification）表示激活（Activation）时机；提出调用到执行准入（Admission）检查当前现实边界。搜索（Search）不是授权（Authorization）。

将完整目录记作 C\mathcal CC，当前任务已可信绑定的能力集合记作 B\mathcal BB，第 sss 步的可用快照（Active Snapshot）记作 As\mathcal A_sAs​。本题要求：

As⊆B⊆C.\mathcal A_s\subseteq\mathcal B\subseteq\mathcal C.As​⊆B⊆C.

这里固定绑定集合（Bound Set）来说明一次搜索；动态换代另行刷新。搜索从 B\mathcal BB 中找候选，经预算（Budget）与可用性检查后影响 As+1\mathcal A_{s+1}As+1​，不会改写已经捕获的 As\mathcal A_sAs​。否则同一批搜索和调用的实际先后会决定是否获准，产生竞态（Race）。

Maka已核路径也分开最终绑定工具面（Bound Surface）、providerTools 注册表（Registry）与 activeTools 可用快照（Active Snapshot）。搜索改变激活（Activation）状态（State），下一次投影（Projection）才给出新工具声明（Tool Specification）；当前执行边界仍检查步骤开始时的集合。同批直接调用刚搜到的延迟工具（Deferred Tool）会在派发前被拒绝。

发现（Discovery）合同：候选、版本与未激活（Activation）原因

先看下面两个结构的分工。SearchResult回答搜到什么、为何未激活（Activation）、是否还有候选；StepSurface回答本步实际采用哪份集合。二者不同，模型（Model）不能看到候选名称就立即调用：

type ToolRef = { name: string; generation: string }
type SearchResult = {
  matches: Array<{
    ref: ToolRef
    purpose: string
    activation: "next_step" | "already_active" | "not_activated"
    reason?: "schema_budget" | "schema_too_large" | "unavailable"
  }>
  searchedWithin: string       // 本次可信绑定集合的标识
  moreCandidates: boolean
}

type StepSurface = {
  stepId: string
  active: ReadonlyMap<string, ToolRef>
}

代际（Generation）字段 generation把描述与实际实现约束到同一代，具体换代策略由宿主（Host）定义。next_step只是下一步激活（Activation）的教学标记；执行前仍须核对当前版本、参数与权限（Permission）。返回 not_activated时应说明预算（Budget）、单项过大或服务不可用，不能只给名称。

最小检索（Retrieval）可从名字、用途与可信分类的词项匹配开始。确有同义词漏检，再比较嵌入（Embedding）或混合检索（Hybrid Retrieval）；向量检索（Vector Retrieval）不是必需起点。第三方声称“安全只读”也不能覆盖宿主（Host）的可信执行分类。

依赖（Dependency）和资源相容是两个问题

箭头表示前一步的结果决定后一步输入（Input）。三个读取（Read）调用在参数和资源独立时可以并行；诊断（Diagnosis）需要它们的实际观察结果（Observation）。两个编辑（Edit）调用即使写不同文件，也只是并行候选；测试（Tests）与差异检查（Diff）均等待两次修改，验收（Acceptance）又等待这两种检查。

图里的诊断（Diagnosis）是模型（Model）决策点，没有预知的固定补丁（Patch）。陌生断言出现时，要把输入（Input）、实际值（Actual）、预期值（Expected）及源码带回模型（Model）；不能为了减少轮次，提前假设错误原因和后续参数。

先推导就绪集合（Ready Set），再选择一个批次

设 PPP 为已有具体参数、仍待执行的任务集合，D(t)D(t)D(t) 为任务 ttt 的前置集合，UUU 为已经确认成功的任务集合。每项还必须在当前可用快照（Active Snapshot）内保持同代。则本轮就绪集合（Ready Set）为：

Rs={t∈P∣D(t)⊆U ∧ activeSameGeneration⁡(t,As)}.R_s=\{t\in P\mid D(t)\subseteq U\ \land\ \operatorname{activeSameGeneration}(t,\mathcal A_s)\}.Rs​={t∈P∣D(t)⊆U ∧ activeSameGeneration(t,As​)}.

没有前置的任务，其 D(t)D(t)D(t) 为空，依赖（Dependency）条件自然满足；仍需通过工具（Tool）可用性检查。RsR_sRs​ 为空不表示全部完成：可能还在等运行中前置，或能力尚未在本步激活（Activation）。

从 RsR_sRs​ 选出批次 QQQ 时，还要求并发上限 mmm 与两两资源相容：Q⊆RsQ\subseteq R_sQ⊆Rs​ 且 ∣Q∣≤m|Q|\le m∣Q∣≤m。若可信实现给出每项的读取集合 Read⁡(t)\operatorname{Read}(t)Read(t)、写入集合 Write⁡(t)\operatorname{Write}(t)Write(t)，一种保守的无冲突条件为，对不同的 i,j∈Qi,j\in Qi,j∈Q：

Write⁡(i)∩(Read⁡(j)∪Write⁡(j))=∅.\operatorname{Write}(i)\cap \bigl(\operatorname{Read}(j)\cup\operatorname{Write}(j)\bigr)=\varnothing.Write(i)∩(Read(j)∪Write(j))=∅.

这里对两个方向都检查：不能只排除 iii 写、jjj 读而漏掉相反情况。两个只读调用满足这项条件，但共享服务限流仍可能限制并发。条件只覆盖这些集合表达的资源；任意命令执行（Bash）的缓存、配置和远端效果（Effect）无法完整静态推断时，应保守拆批。

本题同一调度器逐批等待结算（Settlement）后再选下一批。若允许跨批重叠，还须与已经运行的调用一起检查资源；其他调度器或外部写者则要由覆盖它们的资源锁（Resource Lock）或条件提交（Conditional Commit）协调。只检查 QQQ 内部不能得到这些保证。

依赖（Dependency）是先拿结果再行动，资源冲突（Resource Conflict）是两项行动同时执行可能互扰。串行化也不等于能安全重放远端写入；第51章的条件提交（Conditional Commit）仍负责检查实际资源版本。

读懂批次调度（Scheduling）骨架

代码分两层阅读。第一层描述一个已经形成具体参数的任务，保留身份（Identity）、依赖（Dependency）与可信资源声明（Trusted Resource Claims）；状态（State）另存，不混在工具（Tool）的名称里：

type Task = {
  id: string
  tool: ToolRef
  args: unknown
  dependsOn: string[]
  resources: TrustedResourceClaims // 由可信实现计算，不能仅信模型自报
}

type State = "pending" | "running" | "succeeded" |
  "failed" | "unknown" | "blocked"

规划器（Planner）必须先验证标识唯一、前置存在、无环和工具（Tool）代际（Generation）。这里的 dependsOn要求前置成功；如果某类操作本来要根据“失败结果”触发，应另定义条件，不能偷用这个成功专用规则。尚未完成的诊断（Diagnosis）也不能直接变成参数齐全的编辑。

第二层按三个阶段执行：①筛出就绪任务；②按资源与数量限制选批并标为运行中；③让运行时（Runtime）逐项结算（Per-call Settlement），再阻塞无法继续的后代：

async function runReadyBatch(plan, states, step, runtime) {
  validatePlan(plan)
  const candidates = plan.filter(t =>
    states[t.id] === "pending" &&
    t.dependsOn.every(id => states[id] === "succeeded") &&
    isActiveSameGeneration(t.tool, step.active)
  )
  const batch = selectWithinLimitsAndNoConflicts(candidates)
  for (const task of batch) states[task.id] = "running"

  // Runtime 保留每个调用的身份、权限与结算；durability 失败中止调度。
  const settled = await runtime.executeAndSettleBatch(batch)
  for (const item of settled) states[item.id] = item.outcome.status
  blockDescendantsOfFailedOrUnknown(plan, states)
  return settled // 逐项保留结果，不压成单一 batch success
}

isActiveSameGeneration实现上节可用性条件，selectWithinLimitsAndNoConflicts才处理资源相容。executeAndSettleBatch不返回单一“整批成功”：每项结果写回自己的身份（Identity）。这些辅助函数只给出了职责，本章没有给出完整实现，也没有运行此 TypeScript 教学骨架。

随后需要回读（Readback）函数、保留用户改动并重新诊断（Diagnosis），才能形成新的修复动作。骨架没有实现这次重新规划（Replanning）。调用者还需处理空候选、运行中任务、下一步激活（Activation）与真正完成的区别。

executeAndSettleBatch必须收集已启动调用能完成的结算（Settlement）。如果保存 T2 结果的持久化（Persistence）边界出错，不能把它降成普通工具（Tool）失败后继续下一批，也不能丢弃其他已启动调用的结果。具体停止、排空和取消（Cancellation）协议仍需完整实现；这份骨架未验证它们。

放回Maka：三类限制各管哪一层

第16章已区分步骤准入（Step Admission）与嵌套调用（Nested Call）。Maka的 exclusive_step 限制有 stepId 的同一助手步骤（Assistant Step）中外层调用共存；direct_only 限制代码组合（Code Mode）内的嵌套入口。资源锁（Resource Lock）处理资源互扰，本题有向无环图（DAG）再表达行动依赖（Dependency）。

因此外层 exec可以独占该步，获准子调用仍可以并发。已核代码组合（Code Mode）的子调用回到工具运行时（Tool Runtime），不会因写成一个代码单元（Code Cell）就整体原子成功（Atomic Success）。这些实际准入机制也不证明 Maka 普通批次自动推断了本题完整有向无环图（DAG）。

正常走读：激活（Activation）和诊断（Diagnosis）各等一次观察

第0步直接可见读取（Read）、编辑（Edit）、命令执行（Bash）与搜索（Search）能力。模型（Model）并行读取项目配置与 README，得到真实入口和错误文档；针对用户给定的远端持续集成（CI）任务，搜索 query existing CI job status，取得 QueryCI、generation=g3与 next_step。

第1步的工具声明（Tool Specification）才包含 g3 的 QueryCI。模型（Model）用任务身份（Task Identity）j9提出只读查询，同时执行独立的读取（Read）调用；两个结果分别保存。然后结合文件和失败断言诊断（Diagnosis），形成许可范围内的编辑。

两项编辑均确认成功后，再执行相关测试（Tests）与差异检查（Diff）。并行减少独立等待，却保留“观察结果（Observation）→判断→修改”的依赖（Dependency）。远端查询失败不能抹去已经得到的本地事实。这段是给定输入与预期过程，没有新运行产品或模型（Model）。

失败走读：不要把整批压成一个布尔值

搜索与新调用同批。 本步同时提出 tool_search(QueryCI)与 QueryCI(jobId)，但当前快照（Snapshot）尚无后者，它在效果（Effect）前被拒绝。搜索本身可以成功并影响下一步；即使它恰好先执行完，也不能改写本步捕获的可用性。

一项成功、一项明确失败。 README 编辑成功，函数编辑遇到陈旧版本冲突（Conflict）。保留前者成功与后者明确失败，依赖两项的检查暂时阻塞（Blocked）；重读函数后再判断，不能整批重放（Replay）。

回执（Receipt）没收到。 先按原调用身份（Call Identity）查询已提交结果：若 T2 已有匹配的完成记录，就沿该记录继续。只有现有记录和资源对账（Reconciliation）仍不能确定函数编辑的效果（Effect）时，才保留未知效果（Unknown Effect），阻塞以它的成功为前置的工作。其他节点（Node）成功不能投票消除未知；独立只读工作可按任务策略继续。

取消（Cancellation）时停止新调度（Scheduling），对已经启动的调用发送取消请求并收集可得结果。await、串行化与取消请求均不保证远端效果（Effect）回滚；持久记录（Durable Record）与业务对账（Reconciliation）仍按第52章处理。

查询100个订单、更新3个的完整方案

另设一个教学任务：可信服务允许最多10个并发只读查询，100个订单都属于当前已授权账户。只有状态（State）和业务条件满足的订单才可申请更新。给定的查询结果里，o7、o28、o93符合条件，其余97项无需修改；这里的数值与身份（Identity）均为教学值。

第一阶段：读完再形成写入候选。 分批查询，每条保留订单身份（Identity）、观察版本（Observed Version）与错误状态（State）。查询失败表示尚不能判断，不表示无需修改；其他已成功的读取可保留。若每批恰为10项且无失败，共10批，但并发上限不承诺实际耗时。

第二阶段：对三个具体对象取得许可。 查询结果产生三个更新候选，然后核对覆盖账户、对象、动作与有效期限的授权（Authorization）。不能仅凭“账户可读”便写，也不能在结果到达前预先更新全部订单。

第三阶段：按各自版本条件提交（Conditional Commit）。 o7成功；o28被另一写者更新，条件不满足，返回 conflict/no-effect，须重读重判；o93提交回执（Receipt）丢失，先查持久记录（Durable Record）与业务操作身份（Operation Identity）。本例进一步给定查询与对账（Reconciliation）后仍不能确认结果，才保留未知效果（Unknown Effect）。

报告应分别保留这四类，而不是“整批成功”或“全部失败”。代码组合（Code Mode）可承担循环和过滤，但每个子调用仍通过权限（Permission）、版本与结算（Settlement）。外层异常不抹去 o7 的效果（Effect），恢复（Recovery）也不重新更新全部100项。

直接问答

数百个工具（Tool），前5名搜索就够吗？

不一定。要看必需工具（Tool）是否被召回（Recall），相似候选是否误导，被预算（Budget）排除的工具声明（Tool Specification）是否有说明。可从较小的前 kkk 名开始，提供继续搜索与激活（Activation）状态（State）；kkk是待评估参数，不能用“更专注”代替证据。

工具（Tool）标了并行（Parallel），两个调用就能同时执行吗？

并行（Parallel）声明只是上限，具体调用仍可能有依赖（Dependency）或资源冲突（Resource Conflict）。同一路径的两个编辑（Edit）调用、写后测试、共用远端限额均可能要求顺序或限流；未知命令执行（Bash）的效果（Effect）应保守处理。

为什么不能直接用 Promise.all？

它不表达业务依赖（Dependency）与资源锁（Resource Lock）。其中一个异步结果对象（Promise）拒绝时，聚合结果会提前拒绝，其他已启动操作仍可能产生效果（Effect）。需要逐项结算（Per-call Settlement）、取消（Cancellation）与持久记录（Durable Record）协议，不能由聚合失败推断整批未执行。

代码组合（Code Mode）能绕过工具运行时（Tool Runtime）省开销吗？

不应绕过已有权限（Permission）与效果边界（Effect Boundary）。代码处理机械循环与过滤，每个真实子调用仍经可信路径；Maka的嵌套调用（Nested Call）回到 ToolRuntime。代码单元（Code Cell）不是原子事务（Atomic Transaction），需要模型（Model）重新诊断（Diagnosis）时还须返回观察结果（Observation）与控制权。

第三方工具（Tool）自称只读（Read-only），可直接并行吗？

不能仅信非受信描述。宿主（Host）绑定可信执行事实和保守权限（Permission）上限；不能核实的操作按较强效果（Effect）处理。发现（Discovery）字段既不证明实现行为，也不授予业务授权（Authorization）。
