第 56 章｜设计工具发现与调度

本章概览

核心问题：工具数量增多、一次提出多个调用时，怎样减少输入开销而不破坏权限与依赖？

关键概念：工具目录：可发现能力的集合；Active snapshot（本步快照）：当前可用声明；激活：让候选进入后续请求；DAG（有向无环图）：表达依赖先后；资源冲突：并行访问可能互相干扰；逐项结算：分别保留每个调用的结果。

关系主线：发现从已绑定能力中选择工具，调用仍检查当前边界；调度同时考虑依赖、冲突和并发上限，部分失败不能覆盖其他调用的成功或未知效果。

前置：第50章 Tool 合同、第51章 文件与 Shell、第52章 权限与恢复。跨 Agent 的任务依赖、触发和 owner 见 第57章 与 第58章。

本文算法、类型和参数用于教学设计；DAG 调度示例不是 Maka 普通工具批次的实际 API。

1. 原题、约束与最小起点

现在接入数百个工具，全部放进 prompt 太贵，模型还会选错。你怎么让它发现工具？一次返回多个工具调用，怎样决定哪些可以并行？

发现负责让模型知道可用动作，调度负责让已提出的动作在正确顺序和资源条件下执行。减少 schema 成本不会自动解决参数依赖；允许并行也不会使未授权工具获得权限。

本题仍修正 README 和函数，但远端能力从几项增长为数百项。用户还给出已经存在的 CI 测试任务 j9，要求只读查询它的状态，不创建另一份远端任务。常用 Read/Edit/Bash 直接可见，低频的远端 CI 查询等能力按需发现。若任务实际只需要三个工具，最小方案仍是全部直接暴露，不强加搜索步骤。

需要确认目录来源是否可信、工具是否动态变更、schema 总预算、服务限流、允许的并发数量，以及调用之间是否读写同一资源。

2. 完整参考方案

我会把完整工具目录、本次任务的能力上限和本步可见 schema 分开。少量高频工具直接提供，低频工具通过名字、描述和能力分类检索。搜索返回明确候选、限制和下一步可用状态；激活后的 schema 在下一次模型请求中出现，本步快照不被异步修改。

搜索只从任务已经绑定的能力上限里挑工具，不创造权限。调用时还要校验当前快照、工具版本、参数和实时执行边界。找不到、未激活、未授权和服务离线分别反馈，否则模型不知道应该换检索词还是处理环境。

调度时，我先看依赖，再看资源冲突和并发上限。读取 package 与 README 可以并行；Edit 依赖读到的内容，测试依赖编辑完成，因此必须跨过对应结果。工具的可并行声明只是上限，两次调用写同一文件仍需串行或资源条件提交。任意 Bash 的资源效果无法完整静态推断时，用保守策略。

多调用中的部分成功要逐项保留。一个节点失败，其依赖节点暂停；不依赖它的工作是否继续由任务策略决定。取消需要停止新调度并处理已启动调用，不能丢弃它们的结果。代码组合能减少机械轮次，但每个子调用仍要通过权限和效果边界，并保留需要模型重新诊断的观察点。

我会固定任务与能力集合，分别测检索遗漏、选错率、schema 开销、依赖违规、取消后效果和最终完成率，避免只看工具数量或并行速度。

3. 工具发现与执行的两层合同

三条关键箭头分别说明绑定、激活与执行准入：目录 → 上限表示 Host 的可信绑定；搜索结果 → 下一步 schema 表示激活时机；调用 → 权限准入表示即使被发现也要检查实际执行边界。

这里存在三个不应混淆的集合：系统知道的工具、任务允许绑定的工具、当前步骤激活的工具。为了清楚表达，本题把 schema 激活视为下一步发生的变化；正在执行的 step 使用不可变快照，避免搜索和调用发生竞态。

Maka 的事实是最终 bound surface、providerTools registry 与 activeTools snapshot 分离，搜索结果在下一次 projection 激活；同一批次搜索并调用刚找到的 deferred tool 会被拒绝。

4. 发现契约与不同故障

教学返回类型：

type ToolRef = { name: string; generation: string }
type SearchResult = {
  matches: Array<{
    ref: ToolRef
    purpose: string
    activation: "next_step" | "already_active" | "not_activated"
    reason?: "schema_budget" | "schema_too_large" | "unavailable"
  }>
  searchedWithin: string       // 本次可信绑定集合的标识
  moreCandidates: boolean
}

type StepSurface = {
  stepId: string
  active: ReadonlyMap<string, ToolRef>
}

generation 用于将描述与实际实现绑定到一致的一代；具体版本策略由 Host 定义。搜索结果不能把本次任务没有绑定的工具自动加进来；第三方声明的“安全只读”也不能覆盖 Host 的可信执行分类。

一种最小检索方案是规范化名字、用途和可信分类的词项检索，先验证容易混淆的工具描述。只有确实出现同义词与语义召回缺口，再比较 embedding 或混合检索；不预先把向量检索当唯一方案。

观察（Observation）说明什么模型下一步
没有候选当前范围和检索表达未命中换具体任务词或使用现有工具；不臆造工具名

schema 预算要计入编码后的实际请求成本，不能只计工具数量。返回前几个匹配时应说明截断或未激活理由，避免模型把“没有展示”误判成“系统没有能力”。

5. 依赖与并行的边界

实线表示输出决定下一步输入的依赖关系；同一层的节点只是并行候选。三个 Read 在输入和资源独立时可以并行；两个 Edit 写不同文件时可能并行，但要确认工具与资源策略允许；测试要等待要求的修改都完成。

图中的“判断”是模型决策点，不是假装已知根因的固定 patch。若测试暴露陌生断言，应该把具体输入、actual/expected 和源码交给模型再判断，不能为了减少轮次预先把所有修复写死。

依赖不只来自文件名。 测试可能读取整个仓库，两次不同文件的写入也可能影响同一测试；Bash 可能写缓存、配置或远端资源。调度器需要可信资源信息，无法闭合效果时保守串行。资源条件提交仍是最后防线，并行许可不是并发安全证明。

6. 最小批次调度骨架

下面伪代码只展示如何选择一批可运行任务，不是生产调度器。规划器先基于已有观察形成具体参数；它要验证 ID 唯一、依赖存在、无环和工具 generation。图中未完成的模型诊断节点不会凭空变成预知参数。

type Task = {
  id: string
  tool: ToolRef
  args: unknown
  dependsOn: string[]
  resources: TrustedResourceClaims // 由可信实现计算，不能仅信模型自报
}

type State = "pending" | "running" | "succeeded" |
  "failed" | "unknown" | "blocked"

Task 描述一个已形成具体参数的动作，states 另行保存每个动作当前走到哪里。dependsOn 回答“必须先拿到谁的成功结果”，resources 回答“本动作可能读写哪些资源”；前者不能代替后者。下面一轮依次做三件事：选出依赖已满足且工具仍可用的候选，在资源与数量限制内选一批，再逐项保存执行结果。

async function runReadyBatch(plan, states, step, runtime) {
  validatePlan(plan)
  const candidates = plan.filter(t =>
    states[t.id] === "pending" &&
    t.dependsOn.every(id => states[id] === "succeeded") &&
    isActiveSameGeneration(t.tool, step.active)
  )
  const batch = selectWithinLimitsAndNoConflicts(candidates)
  for (const task of batch) states[task.id] = "running"

  // Runtime 保留每个调用的身份、权限与结算；durability 失败中止调度。
  const settled = await runtime.executeAndSettleBatch(batch)
  for (const item of settled) states[item.id] = item.outcome.status
  blockDescendantsOfFailedOrUnknown(plan, states)
  return settled // 逐项保留结果，不压成单一 batch success
}

把它放回上一节的修复图。假定文件和失败断言已经读完，模型已经形成两个具体编辑：edit_readme 修改文档，edit_function 修改实现；两者的观察版本均有效，工具也在当前快照内。下面只摘取两个编辑与测试三个节点：测试需等待两项修改成功，图中的 diff 核对也有这两个前置，最终验收还要等待两条检查链。局部状态变化如下：

节点调度前本轮筛选与结果
edit_readmepending；前置观察已完成成为候选；若资源策略允许，与另一个编辑同批启动

若本轮 README 编辑成功、函数编辑明确失败，循环逐项写回 succeeded 和 failed，再把依赖两者的测试标为 blocked。成功的 README 编辑不会因为同批有失败就被重做。下一步要重新读取和判断函数问题，再形成后续动作；这个函数没有替模型完成重新规划。

validatePlan、资源选择和阻塞传播都只给出了职责，未在这里实现。候选为空也不等于任务完成：可能仍有前置在运行，或工具不在当前快照内。调用者必须根据这些状态决定等待、刷新下一步工具面或重新规划。此处用于读懂调度条件，不能直接当作可运行的完整调度器。

executeAndSettleBatch 必须等待已启动调用的可完成结算；如果一个调用出现持久化边界错误，不能把其余结果丢掉，或把异常普通化后继续下一轮。这个抽象的效果与取消语义需要实际实现和测试。

第16章已说明 Maka 的两类准入：exclusive_step 限制同一 assistant step 的外层调用共存，direct_only 限制代码组合里的嵌套入口。资源锁则协调实际资源冲突，本文 DAG 还负责表达行动依赖。这些职责不能互相代替：外层 exec 可以独占该步，其获准子调用仍能并发；已有准入声明也不能证明普通批次会自动推断本题的完整 DAG。

7. 正常走读：搜索与并行都要等待相应观察

第 0 步只有 Read/Edit/Bash 和搜索能力直接可见。模型并行读取 package 与 README，得到真实入口和错误文档。它还发现任务要求查看远端 CI 状态，于是请求搜索“query existing CI job status”，得到 QueryCI 候选、generation=g3 和 next_step 标记。

第 1 步 schema 才包含 g3 的 QueryCI。模型用用户给定的 job ID j9 提出只读查询，同时执行独立的本地 Read；两个结果分别保存。基于读取的文件和失败断言定位问题，再提出允许范围内的编辑。

编辑结果都确认以后，模型运行相关测试并检查 diff。调度优化缩短了独立等待，但没有消除“观察 → 判断 → 修改”的依赖。远端查询失败也不能抹去已得到的本地事实。

8. 失败走读：一批调用不能只有一个布尔值

失败分支 A：模型在同一步同时 tool_search(QueryCI) 和 QueryCI(jobId)。当前 snapshot 里尚无 QueryCI，后者在效果前被拒绝；搜索本身可以成功并影响下一步。不能因为执行顺序碰巧先跑完搜索就让后者越过冻结快照。

失败分支 B：README 编辑成功，函数编辑遇到陈旧版本冲突。结果应保留 README 的成功与函数的明确失败；依赖两项修改的最终测试节点暂时阻塞。模型先重读函数、保留用户改动并重新定位，而不是整批重新执行 README 编辑。

失败分支 C：函数编辑回执丢失，状态为 unknown。其依赖工作不能当作修改已完成来推进；先对账。与它独立的只读信息收集可以在任务策略允许时继续，但不能用其他节点成功来“投票”消除不确定性。

取消时，停止调度新节点，对已经启动的节点发送取消并收集可得结果。串行化和 await 也不保证远端效果回滚，详情回到 第52章。

9. 递进追问与参考答案

追问一：数百个工具，直接 top-5 搜索就够吗？

不一定。要看必要工具是否被召回、相似候选是否误导、被预算挤出的 schema 是否可见说明。可以从小 top-k 开始，提供继续搜索和激活状态，但 k 是待评估参数，不能用“模型更专注”代替证据。

追问二：工具标了 parallel，两个调用就一定能并行吗？

不一定。工具级声明允许并行不代表特定调用之间没有参数依赖或资源冲突。同一路径两次 Edit、写后立刻测试、同一个远端限额资源都可能要求顺序或限流；未知 Bash 效果应保守处理。

追问三：把所有调用放进 Promise.all，有什么问题？

它不表达业务依赖和资源锁；普通 Promise.all 在一个 reject 时提前返回，还可能让其他已启动操作继续产生效果。需要逐项结算、取消和持久记录协议，不能因主 promise 失败就当整批没执行。

追问四：Code Mode 能否绕过工具 Runtime 省开销？

不应绕过已有权限与效果边界。代码负责机械循环、条件和过滤；每个真实子调用仍经可信执行路径。Maka 的 nested calls 回到 ToolRuntime；整个代码 cell 不会因此原子成功。若中间失败需要模型诊断，要明确返回观察和控制权。

追问五：搜索到的第三方工具自称 readOnly，可以直接并行吗？

不能只相信非受信描述。Host 需绑定可信执行事实和保守权限上限；无法核实的操作按较强效果处理。协议的发现字段不自动证明实现行为，也不赋予业务授权。

依赖正确性要检查实际开始时间和资源状态；检索效果要检查完成所需工具是否进入可用步骤；输出压缩要检查失败 input/actual/expected 是否保留。步骤数与执行时间另计，不能替代这些正确性指标。

11. 查询 100 个订单、更新其中 3 个的完整方案

假设可信服务允许最多 10 个并发只读查询；100 个订单均在当前账户授权范围内，只有状态与业务条件满足的订单才可申请更新。查询结果表明 o7、o28、o93 满足条件，其余 97 个不需要修改。数字与订单身份均为教学值。

第一阶段分批查询，每条结果保留订单 ID、观察版本和错误状态。某条查询失败不代表该订单不符合条件，而是尚不能决定；其余已成功查询的结果可以保留。第二阶段基于具体结果形成三个更新候选，并取得覆盖账户、对象、动作及有效期限的许可。不能在查询尚未返回时预先启动全部更新。

第三阶段以各自 observedVersion 条件提交：o7 成功；o28 的版本被其他写者更新，返回 conflict/no-effect，需重读后重新判断；o93 的提交回执丢失，保留 unknown 并按业务身份查询。最终报告为“1 项确认更新、1 项冲突未更新、1 项效果未知、97 项无需更新”，不能把整批写成成功或全部失败。

代码组合可以承担批次循环与过滤，但每个子调用仍经过权限、版本与结算；一次外层异常不抹去 o7 的效果。重跑时只处理未解决项，不能重新更新所有 100 个订单。
