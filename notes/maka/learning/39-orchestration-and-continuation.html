第 39 章｜持续工作与协作（Collaboration）

本章概览

核心问题：一项工作拆给多个子任务（Subtask）、等待外部事件或中途换执行者（Worker）后，怎样可靠地继续？

关键概念：委派（Delegation）规定独立工作的输入（Input）与交回合同；认领（Claim）绑定一次执行责任；租约（Lease）是有期限的持有条件；反思把失败反馈（Feedback）带入后续尝试（Attempt）；通知（Notification）策略决定何时向用户报告变化。

关系主线：依赖和资源条件决定能否派发（Dispatch），身份与持久记录（Durable Record）支撑接续，父任务（Parent Task）负责采纳（Adoption）和整体验收；跨天委托还要分别维护目标（Goal）、行动许可与通知（Notification）偏好。

前情回顾：分工以后，责任和效果（Effect）仍要接回来

第23章区分了方法复用与独立委派（Delegation）：技能说明包（Skill）给出做事方法，子代理（Subagent）是承担独立工作的执行者（Worker），子任务（Subtask）是分出去的工作。它们有不同输入（Input），仍可能使用同一份文件。第18章提醒我们，缺少返回值不表示外部效果（Effect）没有发生；恢复（Recovery）前要查原身份与资源状态。第25章进一步说明，客户端（Client）断开后，宿主（Host）可能仍在执行，重新连接首先是找回观察。

本章沿用文档扫描器修复的情境：程序错误处理带空格的路径 sample data，用户要求修复并核对测试说明。先安排两个只读调查，再由父任务（Parent Task）统一修改与验收；后文加入并行（Parallelism）写入、崩溃和跨天购买时，会先说明新的条件。案例中的运行过程为教学推演；具体产品的实现和固定参数在相应小节标明。

阅读时抓住四个连续问题：交回来什么、谁允许继续、从哪里恢复（Recovery）、依据什么判断有进展。这样再看具体函数，能知道它解决的是哪一步。

1. 先区分复用步骤和委派（Delegation）工作

修复同一项目时，可能反复需要“识别测试入口、运行相关测试、解释失败”。如果只是复用这套方法，技能说明包（Skill）或明确步骤就可能足够。只有当一部分工作能独立接收目标（Goal）、建立自己的调查过程并交回可验收产物（Artifact）时，才有必要增加子任务（Subtask）。

可以让一个子任务（Subtask）只调查函数缺陷，另一个只核对文档和测试入口。父任务（Parent Task）仍负责整合完整修复、保留用户改动、运行整体相关验证。两个子任务（Subtask）都写“完成”，不能证明交付合在一起仍正确。

2. 从子任务（Subtask）交付到父任务（Parent Task）验收

图中委派（Delegation）与返回连接了工作副本（Working Copy）和验收，返回 → 采纳 → 复测是三个不同的阶段。文件隔离能减少同时写入碰撞，但合并时仍可能发生语义冲突；它也不隔离共享数据库、远端服务或其他外部资源。

交接结构（Handoff）怎样被父任务（Parent Task）使用

以下类型是教学合同，不是产品应用编程接口（Application Programming Interface，API）。把它按三组阅读：taskId/status说明谁交回及其声明；artifacts/changedResources告诉父任务（Parent Task）去哪里核对当前内容；checks/unresolved说明已验证什么、还缺什么。父任务（Parent Task）读取这些字段后仍要检查实际产物（Artifact），类型定义本身不会执行验收或合并。

baseVersion是可选的比较基线。缺少它时不能假装已经检查版本冲突，应重新读取当前文件并建立比较依据。outcome中的not-run保留未验证的区别：它不等于检查通过，也不等于已执行失败。

type Handoff = {
  // 身份与提交者声明；完成标记不是验收结论。
  taskId: string;
  status: "completed" | "blocked" | "cancelled";
  // 产物位置与比较基线，供父任务核对当前内容。
  artifacts: { location: string; baseVersion?: string; kind: string }[];
  changedResources: string[];
  // 检查事实与遗留问题，保留未运行的区别。
  checks: { name: string; outcome: "pass" | "fail" | "not-run" }[];
  unresolved: string[];
};

父任务（Parent Task）应核查产物（Artifact）内容与真实检查结果，不能只信任 status。例如接口显示 completed，但 checks 全为 not-run，只能说明提交者声称完成了某项工作，不能说明修复已经验证。

3. 调度（Scheduling）：依赖满足后，还要检查资源

假设有四项工作：A 读函数，B 读测试，C 基于 A/B 修改函数，D 验证 C 的改动。A/B 可以并行（Parallelism），C 等待 A/B，D 等待修改可见。若另一项 E 也写同一函数，即使图上没有数据依赖，也要处理写入冲突。

调度器（Scheduler）因此至少要看三件事：依赖是否满足，预算（Budget）/并发数是否允许，资源使用是否兼容。对未知结果的上游工作，不能只按“工具（Tool）已经返回”释放依赖；必须按下游实际需要的后置条件（Postcondition）判断。

图中的认领（Claim）是把这项工作与一次执行身份（Execution Identity）绑定；它先回答“由谁推进”，还没有证明实际派发（Dispatch）成功。认领（Claim）记录应能区分尚未派发（Dispatch）、已派发（Dispatch）、已结算（Settlement），恢复（Recovery）时才知道下一步需要查哪一层。

图中“同一负责者（Owner）”是一项设计要求：停止、修订和认领（Claim）之间需要一致的决策点。把三者放在三个无条件更新语句里，会留下“用户已停止，但旧触发仍新开执行（Run）”的窗口。

持久化已认领（Claim）、尚未派发（Dispatch）时崩溃，恢复（Recovery）应根据原执行身份（Execution Identity）继续派发（Dispatch）或明确取消，不能随手新建一个任务身份。持久记录（Durable Record）只解决本地决策连续性；要避免远端效果（Effect）重复，还需要相应服务提供幂等、查询或更强协调能力。

部分进展怎样留下来

为什么只画依赖图还不够？ A 读函数成功而 B 读测试失败时，图只说 C 要等二者，没说 A 的结果是否保存、重启后是否重复读取。LangGraph 把一组并行（Parallelism）节点的计算轮次称为超级步（Superstep），并把轮次未完成时已成功任务的输出（Output）另存为待提交写入（Pending Writes），用这两层记录区分“本轮尚未完成”和“其中某项已经成功”；Temporal 通过事件历史（History）重放（Replay）控制代码、复用已记录的活动（Activity）结果。两者都能解释部分进展，但恢复（Recovery）单位不同，不能统称为“有检查点（Checkpoint）”。具体算法与成本（Cost）见深度课第 3–6 节。

租约（Lease）过期后，旧执行者（Worker）可能还活着

租约（Lease）是有期限的持有条件。如果使用租约（Lease），过期只表示允许重新分配的条件之一，不表示旧执行者（Worker）一定停止。旧执行者（Worker）迟到时仍可能提交结果或产生效果（Effect）。需要提交负责者（Owner）检查代际（Generation）；隔离令牌检查（Fencing）就是在接纳写入的位置，依据代际（Generation）标记拒绝过时参与者。外部资源不配合该检查时，仍必须讨论重复效果（Effect）和对账。

例如旧执行者（Worker）持有代际（Generation）7，新认领（Claim）已推进到8：旧执行者（Worker）迟到提交时，资源端只有在实际比较代际（Generation）后，才能拒绝这次旧写入。若只在调度器（Scheduler）里把状态改成8，而远端付款接口根本不检查该标记，旧付款仍可能发生。拒绝陈旧的状态更新和阻止陈旧的外部动作是两件事。

因此不能把“有数据库”“有租约（Lease）”“可恢复（Recovery）会话（Session）”当作通用恰好一次（Exactly-once）证明。每个保证必须落到特定对象与操作边界。

停止（Stop）与恢复（Recovery）都要指明对象

把“停下”写成明确范围。 当前执行（Run）取消、已经排队的用户消息暂停、未来定时触发禁用，可能由三个负责者（Owner）分别负责。若只暂停用户队列，后台完成回报（Completion）仍应能结算（Settlement）；若用户改了任务约束，旧待批准（Approval）动作应重新判断，不能把新消息当作批准（Approval）。先明确停止哪些工作，再决定队列、执行和通知（Notification）各自怎样处理。

同样，20 个流式数据块（Chunk）不是 20 个工作轮次（Turn）；等待子代理（Subagent）的观察者取消也不表示子代理（Subagent）没有完成。评估要固定轮次定义并从相应持久记录（Durable Record）取数。这些规则补充下文持续任务的“目标（Goal）、行动许可、通知（Notification）”拆分，不替换已有任务验收。

若队列需要跨重启，应像检查执行账本（Execution Ledger）一样追踪待处理状态（Pending）与认领（Claim）的持久来源；若用户暂停目标（Goal），模型（Model）不能凭旧轮次自行恢复（Recovery）它。输入（Input）队列、目标（Goal）状态和执行认领（Claim）各有负责者（Owner），不能把其中一项暂停理解成全部停止。

现在把恢复（Recovery）问题写成四个连续问题：恢复（Recovery）读取哪份状态？从哪个边界重新执行？哪些已完成结果被复用？哪些外部效果（Effect）仍需检查？ Pi 的会话（Session）路径、DeepSeek Harness（DSH）的待处理输入（Input）队列、Cline 的 Git 工作区检查点（Checkpoint），以及 LangGraph/Temporal 的执行进展分别回答其中不同部分。选型的关键不是“谁也有恢复（Resume）”，而是所需对象有没有被覆盖；完整失败表与选型见编排深度课。

Maka 合作交接（Cooperative Handoff）：先关闭接纳，再转交工作

先看有活动任务时的合作交接（Handoff）。这里的宿主内核（Host Kernel）是管理工作生命周期的程序组件，不是操作系统内核（Operating System Kernel）。它不能只观察“当前没在调用模型（Model）”就退出；调度器（Scheduler）可能正在接纳新工作，旧工具结果（Tool Result）也可能尚未结算（Settlement）。Maka 按下列顺序收窄不确定性：

  1. 先暂缓新驱动。execution-composition.prepareHandoff关闭目标（Goal）、定时任务（Schedule）和每日回顾（Daily Review）的驱动入口，等待已接纳操作结算（Settlement），再交给根工作协调器（Root Coordinator）。暂缓未来工作不等于当前工作已经完成。
  2. 再预约安全边界。root-turn-coordinator.prepareHandoff为活动根执行（Root Run）请求交接；SessionManager.requestRunHandoff经运行时内核（Runtime Kernel）找到对应AgentRun。持久事实还必须满足接续条件，预约本身没有转移执行权。
  3. 到边界后封存事实。AgentRun先构造隐藏的交接预备材料（Handoff Preview）；提交后，finalize刷出累积流式片段，再写包含交接暂停（Handoff Pause）的运行时事实。只有写入和封存成功，才兑现sealed。先发内存消息再退出，不能提供这份持久证据。
  4. 最后关闭旧入口并分离。宿主内核（Host Kernel）检查连接、命令与纳入交接的待结算资源（Drain Residency），封存（Seal）后才分离（Detach）。切换一旦提交，迟到的取消不能重新放行旧执行（Run），否则新旧负责者（Owner）可能同时推进。

这条链结束旧的物理调用（Invocation），逻辑工作轮次（Turn）可以继续。交接记录关联宿主代际（Host Epoch）、根执行与后继执行（Root / Successor Run）、后继物理调用（Successor Invocation）、认领（Claim）及剩余预算（Budget）。工作身份与宿主身份各回答不同问题，界面的会话ID不能替代全部关联。它也没有保存JavaScript调用栈，或迁移正在运行的任意进程。

对等连接（Peer）换路：恢复（Recovery）到字节层的哪一个位置

现在改一个条件：宿主（Host）始终活着，只更换连接路径。下面恢复（Recovery）的是同一内存对象管理的字节流，不是前一节的宿主（Host）退出交接（Handoff）。

这条读取链分三站。第一站，peer-listener校验对等连接（Peer）的身份、凭证（Credential）和授权主体（Principal），把新路径接到原ResumablePeerStream。第二站，RuntimeHostPeerByteStream读取字节，交给FramedByteStreamTransport缓存为完整消息帧（Frame）。第三站，握手后建立的RuntimeHostConnectionSession才解码请求，检查授权（Authorization）与接纳（Admission），最后通过dispatchOperation调用处理器（Handler）。

因此，字节流恢复（Recovery）位于业务处理之前。知道第二站读到了数据，仍不能直接推断第三站已经处理。

容量也分层：当前对等连接（Peer）窗口为 2 MiB，排队写入（Write）最多 8 MiB；窗口满会等待确认回执（ACK），排队超限拒绝这次写入（Write）。帧队列达到容量时暂停底层读取（Read），再向上恢复（Recovery）消费；业务连接另有限制在途请求数量。由此可以逐段查出“谁变慢会让谁停”，但不能据此给整个模型（Model）、工具（Tool）和订阅系统证明统一内存上限。宿主（Host）退出后这些对等连接（Peer）内存状态不在，旧恢复（Resume）请求会被拒绝；这条链不提供跨进程持久队列（Durable Queue）。

5. 判断进展时，区分合法等待和无效重复

同一个后台作业（Job）连续两次查询都返回运行中（Running），可能是合理等待。重复读取同一文件，也可能是在确认外部编辑是否出现。仅比较工具（Tool）名字、参数文本或相邻回答相似度，会把这些工作误判为停滞。

更有用的进展表示包含：当前假设是否改变、是否出现新观察结果（Observation）、候选方案（Candidate）是否缩小、完成条件（Completion Condition）是否更接近、外部等待是否仍有合理预算（Budget）。

目标（Goal）判断：没有进展，与不知道有没有进展

评估者（Evaluator）只能利用实际收到的材料。先看Maka的一条有限观察路径，再比较论文怎样把反馈（Feedback）用于下一次选择。

Maka 当前宿主（Host）在一轮结束后，把目标（Goal）和最近六条截断的用户/助手（User / Assistant）文字交给一次无工具（Tool）的辅助模型（Model）调用。它没有在这条判断中重新读取文件或执行测试。模型（Model）返回的布尔标记（Flags）表达是否完成 met、是否等待 waiting、是否有进展 progress 等判断，再由代码决定目标（Goal）的后续状态；另一次调用并不使这些文字自动成为独立证据。

用一个小初态看清消费者（Consumer）：目标（Goal）正在运行，连续无进展计数（No-progress Count）为2，停滞阈值（Stall Threshold）为3，词元（Token）与迭代预算（Budget）仍足够。本题是源码演算，不是模型（Model）实验。

推理与行动交替（ReAct）：反馈（Feedback）究竟改变了哪一步

推理与行动交替（ReAct）在一次执行轨迹（Trajectory）中结合推理、行动（Action）和观察结果（Observation），让后续选择依赖新证据。先只写其中的外部交互骨架：ggg是目标（Goal），hth_tht​是本次选择前的历史（History），π\piπ是给定这些条件的行动（Action）分布；选择行动（Action）ata_tat​后，环境返回观察结果（Observation）oto_tot​，把它们追加到历史（History）：

at∼π(⋅∣g,ht),ht+1=ht∥(at,ot).a_t\sim\pi(\cdot\mid g,h_t),\qquad h_{t+1}=h_t\mathbin{\Vert}(a_t,o_t).at​∼π(⋅∣g,ht​),ht+1​=ht​∥(at​,ot​).

∥\Vert∥表示按顺序追加，不是向量相加。这个简化式没有写出论文的语言推理步骤；原方法还在上下文（Context）中插入推理文本，用于组织计划与已有观察结果（Observation）。推理文本不会自己产生外部观察结果（Observation），实际行动（Action）才会接触环境。工程系统无需向用户展开完整内部推理，仍可检查下一步行动是否利用了新证据。

以处理带空格路径sample data的扫描任务为例，第一次怀疑路径不存在，读目录后却发现完整的 sample data；下一步应检查参数传递，而不是继续重复列目录。发现当前代码按空格切分后，才提出保持参数边界的补丁。这条短推演说明：工具调用（Tool Call）的价值在于排除候选解释、改变下一步；反复说“再认真想想”却不引入新事实，不能充当环境反馈（Feedback）。

反思反馈（Reflexion）：经验要带到下一次尝试（Attempt）

反思反馈（Reflexion）增加的是跨尝试（Attempt）的反馈（Feedback）：行动者（Actor，此处是模型角色）产生执行轨迹（Trajectory），评估者（Evaluator）给出成败或评价，自我反思环节（Self-Reflection）根据执行轨迹（Trajectory）与评价生成可复用经验，下一次尝试（Attempt）把经验作为上下文（Context）。它不要求更新模型权重（Model Weights），经验也不是动作执行账本（Execution Ledger）；原论文将经验容量限制在有限条目，以适应上下文（Context）预算（Budget）。

本例一次失败后的有用经验是“只对命令解释器（Shell）中的命令补引号没有改变程序内部的split；下次先检查入口参数数组与下游再次切分的位置”。这说明错误归因如何改变调查顺序。若反思写成“所有路径错误都来自split”，就把局部经验变成错误规则；如果评估者（Evaluator）用的断言本身不正确，更多反思还会巩固误判。反思应保存条件与证据，下一次仍接受新观察结果（Observation）的反驳。

两种反馈（Feedback）都不提供跨崩溃恢复（Recovery）算法，也不保证成功。原反思反馈（Reflexion）在 ALFWorld 用过重复动作/响应与步数上限触发反思的启发式；那是特定环境中的控制条件，不能原样用于跨天等待的任务。我们的后台作业（Job）running 例子正是反例：没有新内容，仍可能有合法进展来源。比较“加入反思是否值得”时，应固定总尝试（Attempt）预算（Budget），并观察它是否降低同因错误、误停和最终失败，而不是只统计生成了多少反思文本。

6. 持续委托：分别决定能否行动和是否通知（Notification）

沿用 第31章的购买委托，增加七天期限，并约定：只购买一件满足当前商品条件和预算（Budget）的商品，付款前需要具体批准（Approval）；确认买到一件后结束，否则到期停止；没有实质变化不提醒。Muse 的产品设计说明描述了按时间与事件推进任务，并判断后台结果是否值得通知（Notification）。这提供了持续委托的设计动机；下面不假定 Muse 使用同名内部状态。下面的对象与规则均为教学设计。

一次后台运行要分别作出三个决定：当前是否允许继续工作，候选动作是否获准，结果是否值得打扰用户。 保存目标（Goal）不能代替付款批准（Approval）；一次运行成功也不能把尚未成交的七天委托标成完成。

今天系统没有给用户发消息，能否据此判断它按要求安静地完成了检查？

不能。它可能检查后发现无变化，也可能没有获得执行机会或检查失败。后台执行记录、观察结果（Observation）、通知（Notification）裁决与发送结果需要分开保存，才能区分这几种情况。

持续委托是否有效，还需要看重要变化有没有及时提醒、重复通知（Notification）有多少、后台花了多少成本（Cost）。这些指标将在整项任务评价用明确分母解释。

7. 把设计落到 Codex 与 Claude Code

8. 常见场景与完整参考设计

题一：子任务（Subtask）使用独立上下文（Isolated Context），能否放心并行（Parallelism）写同一文件？

不能。上下文（Context）独立减少输入（Input）污染，文件写入是另一种共享资源。要明确工作副本（Working Copy）、受控资源锁、条件写或合并策略，并由父任务（Parent Task）验证最终组合。

题二：租约（Lease）到期后直接换执行者（Worker），旧执行者（Worker）的成功结果要接受吗？

不能只看成功字段。应检查结果所属执行身份（Execution Identity）、认领（Claim）代际（Generation）和当前状态；陈旧结果不应推进当前代际（Generation）状态，但应保留对账记录。拒绝采纳（Adoption）结果不撤销已经发生的外部效果（Effect），仍需要资源侧控制或对账。

跨实现题：能否给两种产品统一下达“分叉（Fork）一份继续做，失败后恢复（Recovery）”，不再说明其他条件？

不能。必须说明分叉（Fork）的输入（Input）合同、工作目录、写入范围、交付与采纳（Adoption）标准，以及恢复（Recovery）的是对话、可追踪文件还是外部效果（Effect）。尤其不能把 Claude Code 的技能说明包（Skill）分叉（Fork）当作完整父历史（History）复制，也不能把 Codex 子代理（Subagent）身份当作文件隔离证明。

四步修复的完整参考设计。 A 读函数、B 读测试，依赖为 A/B → C 编辑 → D 验证。新增 E 也写同一函数时，参考方案让资源负责者（Owner）串行接纳 C/E；后到者重新读取前一提交后的版本，再决定是否仍需修改，不能仅因图上无依赖就同时覆盖。

若 C 已认领（Claim）执行 X7、尚未派发（Dispatch）时崩溃，恢复（Recovery）沿 X7 检查既有派发（Dispatch）和结果，不创建 X8 冒充首次尝试（Attempt）。若派发（Dispatch）可能已产生效果（Effect），则先查询资源状态，不能只凭缺回执（Receipt）重复写入。客户端（Client）断线而宿主（Host）仍活着时，新的连接获取快照与后续事件，观察原工作，断线本身不重开 C。

并行（Parallelism）何时反而更慢

并行（Parallelism）也有可以直接算出的反例。给定两项调查各5秒，串行编辑与验收合计5秒。用TserialT_{\mathrm{serial}}Tserial​和TparallelT_{\mathrm{parallel}}Tparallel​表示从开始到交付的墙钟时长（Wall-clock Duration）；若没有其他开销，串行是：

Tserial=5+5+5=15 s.T_{\mathrm{serial}}=5+5+5=15\ \mathrm{s}.Tserial​=5+5+5=15 s.

两个调查同时开始能省5秒，但新增协调与冲突处理若占8秒，且这8秒不能与调查或编辑重叠，则：

Tparallel=max⁡(5,5)+8+5=18 s.T_{\mathrm{parallel}}=\max(5,5)+8+5=18\ \mathrm{s}.Tparallel​=max(5,5)+8+5=18 s.

这里比较同一交付合同；新增开销超过省下的时间，所以并行（Parallelism）方案更慢。若协调能重叠、调查时长不同或失败要重试，就要按新的时间线计算。以上是教学时长，不是测量；各模块组合见第47章综合设计示例。
