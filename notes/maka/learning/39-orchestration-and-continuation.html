第 39 章｜持续工作与协作

本章概览

核心问题：一项工作拆给多个子任务、等待外部事件或中途换执行者后，怎样可靠地继续？

关键概念：委派规定独立工作的输入与交回合同；认领绑定一次执行责任；租约是有期限的持有条件；反思把失败反馈带入后续尝试；通知策略决定何时向用户报告变化。

关系主线：依赖和资源条件决定能否派发，身份与持久记录支撑接续，父任务负责采纳和整体验收；跨天委托还要分别维护目标、行动许可与通知偏好。

沿用第23章的父子任务与第18章的未知效果：本章先安排分工与共享资源，再处理认领、恢复和进展判断。Host与连接的基础见第25章。这里解释工作怎样推进；下一章将独立比较整项工作的结果与成本。

1. 先区分复用步骤和委派工作

修复同一项目时，可能反复需要“识别测试入口、运行相关测试、解释失败”。如果只是复用这套方法，Skill 或明确步骤就可能足够。只有当一部分工作能独立接收目标、建立自己的调查过程并交回可验收产物时，才有必要增加子任务。

可以让一个子任务只调查函数缺陷，另一个只核对文档和测试入口。父任务仍负责整合完整修复、保留用户改动、运行整体相关验证。两个子任务都写“完成”，不能证明交付合在一起仍正确。

2. 从子任务交付到父任务验收

图中委派与返回连接了工作副本和验收，返回 → 采纳 → 复测是三个不同的阶段。文件隔离能减少同时写入碰撞，但合并时仍可能发生语义冲突；它也不隔离共享数据库、远端服务或其他外部资源。

以下交接结构是教学合同，不是产品 API：

type Handoff = {
  taskId: string;
  status: "completed" | "blocked" | "cancelled";
  artifacts: { location: string; baseVersion?: string; kind: string }[];
  changedResources: string[];
  checks: { name: string; outcome: "pass" | "fail" | "not-run" }[];
  unresolved: string[];
};

父任务应核查产物内容与真实检查结果，不能只信任 status。例如接口显示 completed，但 checks 全为 not-run，只能说明提交者声称完成了某项工作，不能说明修复已经验证。

3. 调度问题包含依赖和资源冲突

假设有四项工作：A 读函数，B 读测试，C 基于 A/B 修改函数，D 验证 C 的改动。A/B 可以并行，C 等待 A/B，D 等待修改可见。若另一项 E 也写同一函数，即使图上没有数据依赖，也要处理写入冲突。

调度器因此至少要看三件事：依赖是否满足，预算/并发数是否允许，资源使用是否兼容。对未知结果的上游工作，不能只按“工具已经返回”释放依赖；必须按下游实际需要的后置条件判断。

图中“同一负责者”是一项设计要求：停止、修订和认领之间需要一致的决策点。把三者放在三个无条件更新语句里，会留下“用户已停止，但旧触发仍新开 Run”的窗口。

持久化已认领、尚未派发时崩溃，恢复应根据原执行身份继续派发或明确取消，不能随手新建一个任务身份。持久记录只解决本地决策连续性；要避免远端效果重复，还需要相应服务提供幂等、查询或更强协调能力。

为什么只画依赖图还不够？ A 读函数成功而 B 读测试失败时，图只说 C 要等二者，没说 A 的结果是否保存、重启后是否重复读取。LangGraph 把一组并行节点的计算轮次称为 superstep，并把轮次未完成时已成功任务的输出另存为 pending writes，用这两层记录区分“本轮尚未完成”和“其中某项已经成功”；Temporal 通过事件历史重放控制代码、复用已记录的 Activity 结果。两者都能解释部分进展，但恢复单位不同，不能统称为“有 checkpoint”。具体算法与成本见深度课第 3–6 节。

如果使用 lease，过期只表示允许重新分配的条件之一，不表示旧 Worker 一定停止。旧 Worker 迟到时仍可能提交结果或产生效果。需要提交负责者检查代际；fencing 就是在接纳写入的位置，依据代际标记拒绝过时参与者。外部资源不配合该检查时，仍必须讨论重复效果和对账。

因此不能把“有数据库”“有 lease”“可恢复会话”当作通用 exactly-once 证明。每个保证必须落到特定对象与操作边界。

把“停下”写成明确范围。 当前 Run 取消、已经排队的用户消息暂停、未来定时触发禁用，可能由三个 owner 分别负责。若只暂停用户队列，后台 completion 仍应能结算；若用户改了任务约束，旧待批准动作应重新判断，不能把新消息当作批准。先明确停止哪些工作，再决定队列、执行和通知各自怎样处理。

同样，20 个流式 chunk 不是 20 个工作轮次；等待 child 的观察者取消也不表示 child 没有完成。评估要固定轮次定义并从相应持久记录取数。这些规则补充下文持续任务的“Goal、行动许可、通知”拆分，不替换已有任务验收。

若队列需要跨重启，应像检查执行账本一样追踪 pending 与 claim 的持久来源；若用户暂停 Goal，模型不能凭旧轮次自行恢复它。输入队列、Goal 状态和执行认领各有负责者，不能把其中一项暂停理解成全部停止。

现在把恢复问题写成四个连续问题：恢复读取哪份状态？从哪个边界重新执行？哪些已完成结果被复用？哪些外部效果仍需检查？ Pi 的会话路径、DeepSeek Harness（DSH）的待处理输入队列、Cline 的 Git 工作区 checkpoint，以及 LangGraph/Temporal 的执行进展分别回答其中不同部分。选型的关键不是“谁也有 resume”，而是所需对象有没有被覆盖；完整失败表与选型见编排深度课。

Maka 的两条真实链：换 Host 与换连接路径为何要分开

先看有活动任务时的合作交接。Host Kernel 不能只观察“当前没在调用模型”就退出；调度器可能正在接纳新工作，旧工具结果也可能尚未结算。Maka 按下列顺序收窄不确定性：

  1. execution-composition.prepareHandoff 暂停 Goal、Schedule、Daily Review 的新驱动，并等待各自已接纳的操作结算，然后交给 root coordinator。暂停未来调度并不伪造正在工作的完成状态。
  2. root-turn-coordinator.prepareHandoff 为活动 root 请求边界；SessionManager.requestRunHandoff 经 Runtime Kernel 找到对应 AgentRun，还要用持久事实评估这个边界能否接续。请求边界是预约，不是已经取得恢复权。
  3. AgentRun 到达允许边界后构造隐藏的交接预备材料（handoff preview）。commit 后，finalize 先写出累积的流式片段（flush partial），再写包含 handoff pause 的 Runtime 事实；只有封存成功才兑现 sealed。先发一个内存通知再退出，无法提供这份证据。
  4. Kernel 还要检查连接、命令和被纳入交接的待结算工作（drain residency）；封存（seal）后才分离（detach）。提交切换后，迟到的取消不能重新放行旧 Run，否则新旧 owner 可能同时继续工作。

这条链结束旧的物理 invocation，逻辑 Turn 可以继续。封印明确关联 host epoch、root/successor Run、后继 invocation、claim 和剩余预算；Session/Turn/Run 是工作关联，Host epoch 是本次 Host 身份，不能拿 UI 会话 ID 替代全部关联。它也没有保存 JavaScript 调用栈或迁移正在执行的任意进程。

再看 Host 仍活着时的 Peer 换路径。peer-listener 校验 Peer/credential/principal，把新路径附着到原 ResumablePeerStream。后者的 read 被 RuntimeHostPeerByteStream 消费，字节进入 FramedByteStreamTransport 的帧队列；Kernel 握手后创建的 RuntimeHostConnectionSession 才解码业务请求、授权、接纳，并经 dispatchOperation 调用 handler。恢复字节流发生在业务消费者之前。

容量也分层：当前 Peer 窗口为 2 MiB，排队 write 最多 8 MiB；窗口满会等待 ACK，排队超限拒绝这次 write。帧队列达到容量时暂停底层 read，再向上恢复消费；业务连接另有限制在途请求数量。由此可以逐段查出“谁变慢会让谁停”，但不能据此给整个模型、工具和订阅系统证明统一内存上限。Host 退出后这些 Peer 内存状态不在，旧 resume 请求会被拒绝；这条链不提供跨进程 durable queue。

5. 判断进展时，区分合法等待和无效重复

同一个 job 连续两次查询都返回 running，可能是合理等待。重复读取同一文件，也可能是在确认外部编辑是否出现。仅比较工具名字、参数文本或相邻回答相似度，会把这些工作误判为停滞。

更有用的进展表示包含：当前假设是否改变、是否出现新观察、候选方案是否缩小、完成条件是否更接近、外部等待是否仍有合理预算。

这是一套工程判断框架，不是已验证的停滞分类器。若要自动停止，应使用代表性任务校准误停率，保留继续等待、请求帮助和明确失败的不同出口。

一次 Goal 判断：没有进展与不知道有没有进展

Maka 当前 Host 在一轮结束后，把目标和最近六条截断的 user/assistant 文字交给一次无工具的辅助模型调用。它没有在这条判断中重新读取文件或执行测试。模型返回的布尔标记（flags）表达是否完成 met、是否等待 waiting、是否有进展 progress 等判断，再由代码决定 Goal 的后续状态；另一次调用并不使这些文字自动成为独立证据。

用一个小初态看清消费者：Goal 正在运行，连续无进展为 2，停滞阈值为 3，token 与迭代预算仍足够。本题是源码演算，不是模型实验。

所以“都是 false”不足以解释控制行为，必须把判断是否有效也带到状态更新。若迭代额度在这一步耗尽，即使停滞未增加，Goal 仍会停止。解析器也不拒绝所有语义矛盾：同时给 met=true、impossible=true 时，当前消费者优先 met。

判断后的 reason 会进入下一轮提示，连同目标和计数指导继续工作；旧 Goal 的迟到判断则要经过 id/revision 复核；当前 lane 或 active Goal 已不匹配时，processCompletion 直接返回，不用这份旧判断结算新 Goal。这不等于自动为新 Goal 重新评估。假设“已修好”的文字之外还有一份真实失败日志：如果日志没有进入这六条文字，就不能声称这次判断检查过该日志；即使结论碰巧正确，也不证明它依据了这份工具证据。要提高验收可信度，应增加明确的证据来源并测量误判，而不是只增加反思次数。

从 ReAct 到 Reflexion：反馈究竟改变了哪一步

ReAct 在一次任务轨迹中交替使用推理、动作和环境观察，让下一次选择条件包含新观察。用简化记号表示：动作 a_t = 策略(目标, 历史 h_t)，执行得到 o_t，再令 h_(t+1) = h_t + (a_t, o_t)。原论文的 reasoning trace 是其提示方法的一部分；工程系统不必向用户展示完整内部推理，仍可检查动作是否利用了新证据。

以处理带空格路径sample data的扫描任务为例，第一次怀疑路径不存在，读目录后却发现完整的 sample data；下一步应检查参数传递，而不是继续重复列目录。发现当前代码按空格切分后，才提出保持参数边界的补丁。这条短推演说明：工具调用的价值在于排除候选解释、改变下一步；反复说“再认真想想”却不引入新事实，不能充当环境反馈。

Reflexion 增加的是跨尝试的反馈：行动者（Actor，此处是模型角色）产生轨迹，评估者（Evaluator）给出成败或评价，自我反思环节（Self-Reflection）根据轨迹与评价生成可复用经验，下一次尝试把经验作为上下文。它不要求更新模型权重，经验也不是动作执行账本；原论文将经验容量限制在有限条目，以适应上下文预算。

本例一次失败后的有用经验是“只对 shell 命令补引号没有改变程序内部的 split；下次先检查入口参数数组与下游再次切分的位置”。这说明错误归因如何改变调查顺序。若反思写成“所有路径错误都来自 split”，就把局部经验变成错误规则；如果 evaluator 用的断言本身不正确，更多反思还会巩固误判。反思应保存条件与证据，下一次仍接受新观察的反驳。

两种反馈都不提供跨崩溃恢复算法，也不保证成功。原 Reflexion 在 ALFWorld 用过重复动作/响应与步数上限触发反思的启发式；那是特定环境中的控制条件，不能原样用于跨天等待的任务。我们的 job running 例子正是反例：没有新内容，仍可能有合法进展来源。比较“加入反思是否值得”时，应固定总尝试预算，并观察它是否降低同因错误、误停和最终失败，而不是只统计生成了多少反思文本。

6. 持续委托：分别决定能否行动和是否通知

沿用 第31章 的购买委托，增加七天期限，并约定：确认买到一件后结束；否则到期停止；没有实质变化不提醒。Muse 的产品设计说明描述了按时间与事件推进任务，并判断后台结果是否值得通知。这提供了持续委托的设计动机；下面不假定 Muse 使用同名内部状态。下面的对象与规则均为教学设计。

一次后台运行要分别作出三个决定：当前是否允许继续工作，候选动作是否获准，结果是否值得打扰用户。 保存 Goal 不能代替付款批准；一次运行成功也不能把尚未成交的七天委托标成完成。

例如，10:00 事件推送首次带来报价 Q7，10:01 定时扫描再次发现同一商家、商品和报价版本。可以保存两次观察，但两次触发不应该各自准备一笔独立购买。应按业务对象和来源版本判断重复工作；只有不同的事件 ID，并不足以证明是两件事。

今天系统没有给用户发消息，能否据此判断它按要求安静地完成了检查？

不能。它可能检查后发现无变化，也可能没有获得执行机会或检查失败。后台执行记录、观察结果、通知裁决与发送结果需要分开保存，才能区分这几种情况。

持续委托是否有效，还需要看重要变化有没有及时提醒、重复通知有多少、后台花了多少成本。这些指标将在整项任务评价用明确分母解释。

7. 把设计落到 Codex 与 Claude Code

让子任务调查测试入口时，先决定它收到什么，再决定它操作哪份文件。Codex 的历史 fork 与 Claude Code 的几种初始化方式各有合同；同样叫 fork，也不能推导出同样的输入。文件隔离、结果交接和恢复仍需另行设计，父任务保留整体验收责任。

8. 常见场景与完整参考设计

题一：子任务使用独立上下文，能否放心并行写同一文件？

不能。上下文独立减少输入污染，文件写入是另一种共享资源。要明确工作副本、受控资源锁、条件写或合并策略，并由父任务验证最终组合。

题二：lease 到期后直接换 Worker，旧 Worker 的成功结果要接受吗？

不能只看成功字段。应检查结果所属执行身份、认领代际和当前状态；陈旧结果不应推进当前代际状态，但应保留对账记录。拒绝采纳结果不撤销已经发生的外部效果，仍需要资源侧控制或对账。

跨实现题：能否给两种产品统一下达“fork 一份继续做，失败后恢复”，不再说明其他条件？

不能。必须说明 fork 的输入合同、工作目录、写入范围、交付与采纳标准，以及恢复的是对话、可追踪文件还是外部效果。尤其不能把 Claude Code 的 Skill fork 当作完整父历史复制，也不能把 Codex child 身份当作文件隔离证明。

四步修复的完整参考设计。 A 读函数、B 读测试，依赖为 A/B → C 编辑 → D 验证。新增 E 也写同一函数时，参考方案让资源 owner 串行接纳 C/E；后到者重新读取前一提交后的版本，再决定是否仍需修改，不能仅因图上无依赖就同时覆盖。

若 C 已认领执行 X7、尚未派发时崩溃，恢复沿 X7 检查既有派发和结果，不创建 X8 冒充首次尝试。若派发可能已产生效果，则先查询资源状态，不能只凭缺回执重复写入。Client 断线而 Host 仍活着时，新的连接获取快照与后续事件，观察原工作，断线本身不重开 C。

并行也有可以直接算出的反例。给定两项调查各 5 秒、串行编辑与验收合计 5 秒：无其他开销的串行方案用 5+5+5=15 秒；并行调查省下 5 秒，但若额外协调与冲突处理占 8 秒，交付需 max(5,5)+8+5=18 秒。这些是教学时长，不是测量；在同样完成合同下，这组条件已足以推翻“增加子任务必然更快”。各模块组合见 第47章 综合设计示例。
