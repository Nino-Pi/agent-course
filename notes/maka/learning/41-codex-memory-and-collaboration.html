第 41 章｜Codex：长期记忆（Long-Term Memory）、技能说明包（Skill）与协作（Collaboration）

本章概览

核心问题：旧经验、复用方法与子任务（Subtask）结果，怎样成为后续决策可用的材料？

关键概念：长期记忆（Long-Term Memory）保存跨任务经验；认领（Claim）和租约（Lease）约束后台写入归属；技能说明包（Skill）提供按需方法；任务线程（Thread）承载独立工作；消费者（Consumer）决定材料在哪里起作用。

关系主线：长期记忆（Long-Term Memory）经提取和整合形成材料，读侧装配模型输入（Model Input）；方法装载与子任务（Subtask）执行分别闭合，父任务（Parent Task）仍承担验收（Acceptance）。

前情回顾：保存、装载与执行各改变什么？

第20章与第36章已经把长期记忆（Long-Term Memory）的写入、读取和实际使用分开：文件存在，只能说明材料留在某个位置；模型输入（Model Input）必须包含相关内容，后续决策才有机会受它影响。本章会沿 Codex 的两阶段写入与独立读侧，找到这三个环节的具体消费者（Consumer）。

第23章区分了技能说明包（Skill）与子代理（Subagent）：前者提供一套方法，后者接收有边界的子任务（Subtask），建立自己的调查过程并返回结果。第39章进一步区分返回、采纳与验收（Acceptance）。因此，本章读到“正文已装载”或“子任务（Subtask）已完成”时，还要追问实际执行和最终结果。

本章设定一项修复完成之后新开的同类检查器任务（Task）。检查器读取文档并检查链接，问题涉及含空格路径；旧经验包括“项目使用 pytest”“测试夹具路径包含空格”“用户要求先做相关测试”。父任务（Parent Task）可以自行修复，让子任务（Subtask）只读审查回归测试（Regression Test），再用技能说明包（Skill）复用验证步骤。这里不是替第38章尚未验收（Acceptance）的长任务（Task）宣布通过；该章的同一次过程记录（Rollout）窗口恢复仍服务当前工作连续性。

以下任务卡、冲突处理和质量判定是完整教学设计，未作为一次真实 Codex 执行。先看后台怎样形成经验，再看当前任务怎样读取、使用和验收（Acceptance）。

1. 长期记忆（Long-Term Memory）：先分清五个状态

如果把每次对话全文追加到文件，再在下次完整读入，只是把窗口问题搬到了文件系统。长期记忆（Long-Term Memory）需要决定哪些经历值得提取、哪些内容具有未来用途，以及何时重新读取。

Codex 的写入分两阶段：对符合条件的过程记录（Rollout）提取候选，再将有界候选整合到长期工作区。读侧是另一条装配路径，不以“后台成功”作为模型（Model）已经使用的证据。

阶段输入（Input）负责处理的部分输出及实际消费者（Consumer）

本地长期记忆（Long-Term Memory）总开关默认关闭；下面假定已启用。应用服务入口 app-server 也不是每轮结束就写入：请求含输入、实际开始而非向运行中追加引导消息（Steering），并已配置主执行环境（Environment），才进入启动调用。启动函数还检查临时会话（Ephemeral Session）、功能开关（Feature Flag）、是否为根智能代理（Root Agent）、状态数据库（State Database，DB）和额度。因此，没有条件的“每轮结束 → 保存经验”会误画触发时点与候选范围。

2. 提取（Extraction）：候选有结构，内容仍需判断

认领（Claim）把处理责任交给谁

系统从数据库认领（Claim）满足来源、时间和数量限制的过程记录作业（Rollout Job）。认领（Claim）带有归属令牌（Ownership Token）与租约（Lease）：前者标识这次持有资格，后者限制有效时间。随后才在有界并发下提取。它们解决重复竞争同一候选的问题，不替模型（Model）判断什么值得记住。

每个作业（Job）的模型输入（Model Input）先经过过滤与敏感信息遮蔽（Secret Redaction）。输出存在两个分支：

表 2 / Table 2 · 认领（Claim）把处理责任交给谁
分支生成字段输入和输出的区别
默认分支 V1raw_memory、rollout_summary、可空的短名称 rollout_slug保留原始记忆材料与摘要
仅摘要分支 V2rollout_summary、字符串 rollout_slug先区分用户、智能代理（Agent）、上下文（Context）和工具（Tool）来源，按预算（Budget）选择输入；输出不包含原始记忆字段

生成字段还会再次脱敏，仅摘要分支限制摘要长度。结构约束让下游可以解析，脱敏降低特定泄漏风险；两者都不能证明语义正确。例如，格式完全合法的一句“这个项目永远不能改 README”，仍可能错误扩大用户仅对本次任务（Task）提出的限制。

从一次性细节中提取适用条件（Applicability）

对检查器而言，“测试目录中包含带空格路径，修改路径解析要覆盖这一边界”可能是项目经验；某次临时文件名通常没有长期价值。“用户本次不要改 README”必须保留任务范围（Task Scope），不能变成未来所有任务（Task）的永久禁令。

提取也需要区分成功但无输出（No Output）和提取失败（Extraction Failure）。解析成功后没有值得保留的材料，可以有明确空结果；请求或解析失败则不能用空结果掩盖。否则，空结果全算失败会鼓励无效重试，空结果全算成功又会掩盖故障。结果分类让后续消费者（Consumer）知道应当跳过、重试还是接受候选，而不是从一段空字符串猜原因。

3. 整合（Consolidation）：关闭写入者后才能验收（Acceptance）

多份候选要更新同一长期工作区，首先需要明确本次写入的负责者（Owner）。整合阶段先取得所选版本存储中的全局认领（Claim），再准备带 Git 基线（Baseline）的工作区、选择有界候选并同步过程记录摘要（Rollout Summary）。默认分支还重建原始记忆材料，仅摘要分支跳过它，然后比较工作区差异（Diff）。

图中的归属心跳（Ownership Heartbeat）用于维持租约（Lease）。流程有两条成功路径：没有变化且已有产物有效时，可以直接更新完成记录，不再调用整合模型（Model）；需要改动或修复产物时，才启动整合智能代理（Consolidation Agent）。后者进入终态之后，仍要经过关闭执行者（Worker）、产物校验（Artifact Validation）和认领复核（Claim Check）。

这些检查回答不同问题：

检查要排除的反例失败后不能作出的声明

产物校验（Artifact Validation）终态正常，但文件缺失或不满足结构合同不能说长期材料已经合格
认领复核（Claim Check）慢执行者（Worker）失去租约（Lease），仍拿旧资格发布不能凭旧令牌宣布当前归属

特别是关闭失败时，当前路径保留租约（Lease）直到过期，避免立即释放后另一个执行者（Worker）与仍在写入的旧执行者（Worker）竞争。产物校验后的认领复核（Claim Check）返回不再持有资格时，这条路径只记录相应日志，不更新基线（Baseline）或标记成功；这不等于一定写出了失败状态。图概括主要路径，不能把所有失败都理解成“立即释放认领（Claim）并重跑”。

最后的 Git 基线（Baseline）更新与数据库成功标记也不是单一事务（Transaction）。基线更新成功、数据库标记失败的窗口仍存在，不能由此推得全局恰好一次（Exactly Once）保证。这里需要的是如实表达哪些步骤已发生，而不是把一条“成功”边当成跨存储原子性。

整合执行者（Worker）设为临时会话（Ephemeral Session），关闭多种不需要的能力，减少递归生成经验和继续委派的路径。权限（Permission）还受父环境分支影响：托管分支（Managed）使用仅长期记忆（Long-Term Memory）根目录可写、禁止网络的配置；禁用分支（Disabled）或外部分支（External）保留相应选择。不能凭“后台整合”这个名字假定所有执行环境（Environment）都有同一种操作系统（Operating System，OS）层隔离（Isolation）。

4. 读侧（Read Path）：来源一致、读取命中和正确使用分别闭合

两种写入分支使用独立存储空间。dual_write 默认关闭；打开时分别运行两条写入管道，不让读侧合并两个版本。运行中修改配置，记忆扩展（Memory Extension）仍保留该任务线程（Thread）初始选择的分支，让已经注入的摘要与后续读取工具（Tool）指向同一空间。所选分支缺摘要时，也不自动借另一分支补齐。

这项选择保护的是来源一致性（Source Consistency）。假如摘要来自一套经验、详细读取却突然切到另一套，模型（Model）可能把互不对应的材料拼在一起。宁可明确缺失，也不能悄悄改变当前材料的来源。

读取扩展由记忆功能（Memory Feature）与 use_memories 控制；专用工具（Tool）还受 dedicated_tools 控制，后者默认关闭。摘要装配不要求专用工具（Tool）已开启：读侧读取 memory_summary.md，按词元（Token）限制构造模型输入（Model Input）片段；细节再由实际可用的读取路径取得。

图中列举、搜索和范围读取假定相应工具（Tool）可用，不能从“摘要已进入输入”推出这些操作必然发生。专用读取支持行偏移、行数、词元（Token）限制和 truncated；搜索是文本匹配（Text Matching），排序后用游标（Cursor）分页，不是向量检索（Vector Retrieval）。截断和游标（Cursor）告诉消费者（Consumer）资料尚未读完，不能只看第一页就宣布没有其他相关内容。

“项目使用 pytest”这条长期记忆（Long-Term Memory）可以降低寻找入口的成本，当前任务（Task）仍要核对项目文件：测试框架可能已迁移。用户偏好也要结合当前明确要求解释，不能把历史（History）中某次约定僵化成无法修改的规则。

因此，评价至少要看写入精度、无价值信息比例、作用域（Scope）错误、旧知识失效、读取命中、实际采纳与任务收益。只数生成条数会奖励噪声，只数读取成功又会漏掉“读对了却没用”或“用到了错误任务”两种失败。

5. 技能说明包（Skill）：目录、正文与执行是三个状态

第23章说明了方法怎样从发现线索进入当前工作。Codex 的技能说明包（Skill）扩展也区分目录（Catalog）和正文：目录有元数据（Metadata）预算（Budget），读取从已启用目录选择包（Package），再按资源归属环境（Authority）和资源标识（Resource ID）取得内容。

这里的资源归属环境（Authority）回答“这个包在哪里、由哪个环境提供”，不是权限（Permission）批准。相同路径文字在编排端（Orchestrator）和执行环境（Environment）可能指向不同文件；读取合同需要核对包（Package）、资源身份（Resource Identity）与环境边界（Environment Boundary），并确认返回身份仍是请求的资源。

目录可见、正文已读、方法已执行是三个状态。技能说明包（Skill）列出测试步骤，不等于模型（Model）已读正文，更不等于测试已经运行。资源内的命令也不会扩大调用者权限（Permission）；实际行动请求（Action）仍要经过第32章的工具（Tool）与环境边界（Environment Boundary）。

图末“是否足够”是教学判断：读到足以解决本题的部分才采用；无后续页却仍缺必要内容时，应说明缺口。页数读完只证明取得了这份材料，不能证明方法能解决当前问题。

分页快照（Pagination Snapshot）：一致性与新鲜度（Freshness）分别判断

执行器提供的技能说明包（Executor-backed Skill）存在复用分页快照（Pagination Snapshot）的路径。继续页命中缓存（Cache）时不探测文件编辑，因此可能返回旧正文的后半段；重新读取可不带游标（Cursor）。缓存（Cache）匹配还涉及包（Package）、资源、环境（Environment）与沙箱（Sandbox），并非任意游标都能复用任意文档。

这种选择有实际理由：若第一部分基于旧参数解释步骤，第二部分却来自新版，整份方法可能自相矛盾。同一次阅读保持一致，仍不等于每页都是最新内容。任务（Task）依赖最新规则时，要在适当边界重新读，不能让缓存（Cache）命中替代新鲜度（Freshness）判断。

第23章的读取快照讨论发现目录与加载正文之间的变化；本节讨论一次读取开始后的继续页。普通宿主技能说明包（Host Skill）的来源是否可变、是否来自不可变插件代次（Plugin Generation）、分页是否命中缓存（Cache），要分别判断，不能推广成所有路径统一的快照保证。

6. 子任务（Subtask）：先交付自足输入，再选择历史分叉（History Fork）

委派（Delegation）增加的是独立调查和决策过程。所选协作路径 spawn 解析角色（Role）、模型（Model）与历史分叉（History Fork）参数，创建真实子任务线程（Child Thread），并传递父级、根级工作身份（Work Identity）和选定执行环境（Environment）。任务线程（Thread）在此是工作组织单元，不是操作系统（OS）线程；执行内核的会话（Session）负责承接其中的工作轮次（Turn）。

历史分叉（History Fork）接受 none、all 或正整数表示的最近若干轮，省略参数默认 all。完整历史分叉（Full-history Fork）还要处理父历史（Parent History）、上下文基线（Context Baseline）和新子任务（Subtask）指令，并非直接复制聊天字符串。较小输入通常更节约，是设计建议，不能写成这里的默认配置。

完整任务卡：谁读什么，交回什么

本例让子代理（Subagent）只读审查 tests/test_checker.py，判断含空格路径的回归测试（Regression Test）是否覆盖真实故障。角色（Role）名“资深测试专家”没有说明工作接口（Interface）；任务卡要提供目标、输入、写入范围、交付与验收（Acceptance）。下面先定义合同形状，再给出完整实例；它是课程自拟 TypeScript，不是产品参数类型。

type ChildTask = {
  objective: string;
  // 输入（Input）：材料位置与阅读目的。
  inputs: Array<{ path: string; purpose: string }>;
  // 写入范围只是任务（Task）合同，仍需执行层约束。
  allowedWrites: string[];
  forbiddenActions: string[];
  // 交付与验收（Acceptance）分别表达。
  deliverable: {
    reportPath?: string;
    requiredFields: string[];
  };
  acceptance: string[];
};

inputs 让消费者（Consumer）知道每份材料为何需要；allowedWrites 与 forbiddenActions 表达任务（Task）约束，不自动建立执行器权限（Permission）。deliverable 定义返回哪些字段，acceptance 说明这些字段怎样支持判断；只填齐字段仍不等于内容通过验收（Acceptance）。

const reviewTask: ChildTask = {
  objective: "检查带空格路径的回归测试是否覆盖实际故障",
  inputs: [{ path: "tests/test_checker.py", purpose: "阅读测试断言" }],
  allowedWrites: [],
  forbiddenActions: ["修改生产代码"],
  deliverable: { requiredFields: ["结论", "缺失场景", "建议断言"] },
  acceptance: ["结论对应具体测试行为", "区分实际执行与静态判断"]
};

本卡的写入列表为空，也没有要求写报告文件。现在给定完整审查条件：现有测试只检查启动命令里的引号，没有覆盖程序内部再次按空格切分参数的分支；子代理（Subagent）只读文件，没有运行测试。参考交付如下：

7. 消息（Message）、续做与文件交付各有合同

send_message 使用仅入队模式 QueueOnly，followup_task 使用请求工作轮次（Turn）模式 TriggerTurn。前者传递材料，后者表达继续工作的意图。普通空闲子任务线程（Child Thread）收到材料，与被要求开启新工作轮次（Turn），是不同状态转换；活跃任务（Task）则在能够处理的边界吸收消息（Message）。

还有一个必须单独判断的状态：任务线程（Thread）没有活跃工作轮次（Turn），但保留尚未结束的持久等待（Outstanding Durable Sleep）记录。此时 QueueOnly 消息（Message）也会进入启动新普通工作轮次（Turn）的调度判断，处理等待中的工作。它不复活已结束的模型调用（Model Query）或调用栈；“这条消息（Message）没有请求续做”不能被简化为绝不会启动执行（Run）。

图强调父任务（Parent Task）实际核对产物后才整合。父子关系可以写入持久图边（Persistent Edge），但不满足条件会跳过，写入失败会记录警告。例如临时子任务线程（Ephemeral Child Thread）不会按该路径保存关系。图边（Edge）存在不证明消息（Message）具有事务性持久投递，也不证明系统是任意有向无环图（Directed Acyclic Graph，DAG）的调度器；冷恢复（Cold Recovery）、完整权限继承（Permission Inheritance）与投递语义仍需沿相应路径判断。

独立子任务线程（Child Thread）也不自动意味着独立工作副本（Working Copy）。spawn 传递环境选择，不能据此认定每个子代理（Subagent）都有隔离工作树（Worktree）。共享目录中的文件变化可能立即互相可见；独立工作副本（Working Copy）则需要明确合并或读取路径。

因此，父任务（Parent Task）要说明可写文件各自的负责者（Owner），约定结果是消息（Message）、文件还是补丁，并核对当前产物与验证范围。并发修改可能使旧结果失效；子任务（Subtask）报告完成，仍不能替父任务（Parent Task）承担最终验收（Acceptance）。

8. 四种信息流怎样共同完成检查器任务（Task）

把完整案例按消费顺序接起来：长期记忆（Long-Term Memory）提示旧项目使用 pytest，父任务（Parent Task）读取当前项目确认；技能说明包（Skill）提供验证方法；只读子任务（Subtask）审查回归测试（Regression Test）；父任务（Parent Task）修复、运行测试、核对审查结论并交付差异（Diff）。若窗口不足，第38章的恢复资料继续当前工作。这是一条教学参考过程，不是新增的产品运行记录。

表 6 / Table 6 · 8. 四种信息流怎样共同完成检查器任务（Task）
机制提供的帮助父任务（Parent Task）保留的责任

比较 Codex 与 Maka 时，可以固定一种信息流，检查来源、消费条件和任务收益。管道长度、工具（Tool）数量或子代理（Subagent）数量，都不能单独证明最终工作更好。

9. 常见场景与参考结论

题一：为什么提取（Extraction）允许成功但无输出（No Output）？

参考答案：并非每段经历都有长期价值。明确空结果可减少无效重试与噪声积累，并把它与解析失败、模型请求失败分开。消费者（Consumer）应依据结果类别处理，不能只看文本是否为空。

题二：整合智能代理（Consolidation Agent）已完成，为什么还要校验产物与认领（Claim）？

参考答案：终态不证明产物满足合同，执行期间也可能失去租约（Lease）。关闭执行者（Worker）、校验产物并重新确认归属，可避免在途写入和过期持有者宣布成功；关闭失败仍有保留租约（Lease）的处理。这些检查没有把文件系统与数据库变成一个事务（Transaction）。

题三：长期记忆（Long-Term Memory）写成功，为什么下次仍重复探索？

参考答案：逐项检查读侧是否启用、所选空间是否有摘要、检索是否命中、内容是否截断，以及模型（Model）是否用到相关材料。保存、进入模型输入（Model Input）和实际使用是不同状态。

题四：技能说明包（Skill）翻到第二页仍读到旧内容，一定是故障吗？

参考答案：不一定。执行器提供的继续页在缓存（Cache）命中时复用分页快照（Pagination Snapshot），优先保持本次阅读一致。文件修改不一定在续页可见；需要最新内容时，应通过重新读取处理新鲜度（Freshness）。

题五：send_message 与 followup_task 为什么分开？

参考答案：传递材料与请求新工作轮次（Turn）是不同意图，目标状态也影响启动。普通空闲目标的 QueueOnly 材料不等于已安排新工作；保留持久等待（Outstanding Durable Sleep）的空闲目标则可能由它触发新普通工作轮次（Turn）。这不重开旧模型调用（Model Query），也不恢复旧调用栈。

题六：子任务（Subtask）说测试通过，父任务（Parent Task）能直接汇报吗？

参考答案：应核对实际命令、验证范围、产物与当前文件是否一致。静态判断、未覆盖部分及后续并发修改都要保留，最终结论不能超过已有检查。更多完整场景见第60章。
