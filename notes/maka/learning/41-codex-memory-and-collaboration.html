第 41 章｜Codex：记忆、Skills 与协作

本章概览

核心问题：Codex 的经验、方法与子任务结果，怎样从已保存或已返回变成后续可用信息？

关键概念：Memory（长期记忆）：从旧执行记录提取整合的材料；claim（认领）：约束后台工作归属；Skills（技能说明包）：按需读取的方法；authority（资源归属环境）：区分编排端与执行环境的读取位置；child Thread（子会话）：独立工作单元；消息唤醒：按目标状态接纳后续输入。

关系主线：记忆写入与读侧装配分开，Skill 目录经正文读取成为方法；子任务按背景和能力执行，消息、产物与父任务验收再分别闭合。

所属主题：第 1–4 节对应 第36章 Memory，第 5 节起对应 Skills 与 第39章 协作。

第38章的同一 rollout 窗口恢复资料用于当前任务连续性，与本章的跨 rollout 长期 Memory 管线分开。

把贯穿案例推进到一次修复完成之后，再设一项新的同类检查器修复任务。新任务也许会受益于“项目使用 pytest”“测试夹具路径包含空格”“用户要求先做相关测试”的旧经验；另一个 Agent 可以独立检查回归案例；一个 Skill 可以提供项目验证流程。这是本章设定的新起点，不表示第38章尚未验收的任务已经取得通过结果。下面分别追踪这些材料怎样变成有效行为。

本文提出的任务卡、冲突处理和质量验收是教学建议，不把它们冒充为已验证的产品保证。

1. 记忆不是聊天记录自动追加到下一次 prompt

如果每次对话结束都把全文附加到一个文件，再在下一轮完整读入，只是把窗口问题搬到了文件系统。Memory 必须先决定：哪段经历适合提取，什么信息值得保留，重复或过时的信息怎样处理，以及未来什么时候读它。

本地 Codex 的生成路径分成两阶段：先对满足条件的 rollout 提取，再把有界候选整合到 Memory 工作区。读取则是另一条独立装配的路径。

表 1 / Table 1 · 1. 记忆不是聊天记录自动追加到下一次 prompt
阶段输入（Input）核心处理（Processing）输出（Output）
资格与调度（Eligibility / Scheduling）Thread 来源、配置、DB、额度等跳过不适用会话，认领候选可执行提取工作
提取阶段（Extraction）一段候选 rollout过滤、脱敏、按版本结构化提取原始记忆与摘要，或仅摘要；两种分支有不同结构
整合阶段（Consolidation）多段提取结果与已有工作区同步、比较变化、必要时整合经校验的长期材料
读侧（Read path）摘要文件、工具配置与当前任务注入有界摘要，按需读取细节本次可用的记忆上下文
使用（Use）记忆与用户最新要求、实际文件判断相关性并验证更合适的行动

Memory 总开关默认关闭；下面先假定该功能已启用。app-server 的触发条件并非“任何新建会话都生成记忆”：请求含输入、实际开始而非 steering，并已配置主执行环境时，才进入该启动调用；启动函数还会检查是否为临时会话（ephemeral）、功能开关（feature）、是否非 root agent、状态数据库（state DB）和额度等条件。因此不能用一张没有条件的“每轮结束 → 写 Memory”图解释它。

2. 提取：把一次经历变成可处理候选

系统首先从 DB 认领满足来源、时间、数量等约束的 rollout jobs。认领包含 ownership token 与 lease 信息，避免多个后台任务都把同一候选当成无主工作。随后在有界并发下执行提取。

每个 job 的模型输入先经过过滤与敏感信息遮蔽（secret redaction）。提取有两种分支：默认分支（配置称 V1）保留 raw_memory、rollout_summary 和可空短名称 slug；仅摘要分支（V2）输出摘要与字符串 slug，并先区分用户、Agent、上下文和工具来源，再按预算选择输入。两者的生成字段都会再次脱敏，仅摘要分支还限制摘要长度。结构约束让下游知道怎样解析，脱敏降低特定泄漏风险，但两者都不证明语义正确。

对于贯穿案例，可以把提取目标理解为：区分通用有效经验和一次性细节。“测试目录中包含带空格路径，修改路径解析要覆盖这一边界”可能值得作为项目经验；“刚才命令用了某个临时文件名”通常没有长期价值。“用户本次不要改 README”则需要明确任务作用域，不能直接变成所有未来任务永不改 README 的偏好。

提取阶段把“没有值得保留的信息”与“提取失败”分开记录：如果空输出一律当失败，系统可能反复花费模型调用，直到编造出一条看似有用的记忆。若任何空输出都当成功，又会掩盖解析错误。因此要用明确结果分类承载其含义。

3. 整合：多份候选怎样更新同一个工作区

整合阶段需要将多份候选写入同一个长期工作区。它先取得所选版本 store 中的全局 claim，再准备带 Git 基线的工作区，加载有界候选，并同步 rollout 摘要；原始记忆分支还重建 raw-memory 材料，仅摘要分支跳过这一步。然后通过工作区 diff 判断是否真的有变化。下图的 ownership 是当前认领归属，heartbeat 是运行期间维持这份归属的周期性心跳。

这个流程中的每一关都有具体作用。没有输入变化且已有产物有效时，可以走无模型整合的快路径；有变化时，整合 Agent 应基于实际差异工作。背景任务运行期间需要 heartbeat 维持 ownership。worker 到达终态后，还要关闭它、校验产物，再确认仍持有 claim，才更新基线与成功记录。

为什么“模型说完成”后还要关闭 worker？如果它仍可能继续写文件，后面的产物校验与基线更新就会和在途写入竞争。为什么重置基线前要重新确认 ownership？慢任务可能已经失去租约，不能凭旧认领继续宣布自己拥有发布权。

这条控制流没有把 DB 和文件系统变成单一事务。比如基线更新成功、后续 DB 成功标记失败时，代码还需要表达这个窗口；Git baseline 不提供全局 exactly-once 保证。

整合 worker 会关闭多种不需要的能力，并设为 ephemeral，以减少递归产生新记忆和进一步委派的路径。权限还存在父环境分支：Managed 情况使用仅 Memory root 写入、禁网的配置；Disabled 或 External 保留相应选择。不能仅凭“后台整合”这个名称假设所有环境都具有同一种 OS 隔离。

4. 读侧：短摘要做入口，细节按需取

写读两边还要对齐存储空间。两种提取分支各自使用独立空间；可选 dual_write 分别运行两条写入管道，默认关闭，并不表示读侧会合并它们。运行中更新配置时，Memory extension 保留该 Thread 初始的分支，让已注入摘要与后续读取工具指向同一空间。所选分支缺少摘要，也不自动用另一空间填补。这是在保持来源一致与尽可能找到材料之间的取舍。

写入完成不代表下次任务自动用对。读取扩展由 Memory feature 和 use_memories 控制；专门读取工具还受 dedicated_tools 控制。专用 Memory 读取工具默认关闭，摘要装配不以它们开启为前提。读侧读取 memory_summary.md，在 token 限制内构造上下文片段。这个摘要更适合承担导航与高价值提示，详细经验再通过相关读取路径获得。

上图的列举、搜索和范围读取假定相应工具可用，不能从摘要进入请求推出这些动作必然发生。专用 read 路径支持行偏移、行数、token 限制以及 truncated 信息；search 路径是文本匹配，排序后以 cursor 分页。不能把它称为向量检索。返回值里的截断和游标也不是装饰：如果只读了前一页就宣布“没有其他相关记忆”，结论可能来自未读完资料。

对于“项目使用 pytest”这条记忆，当前任务仍应检查项目文件或现有说明。项目可能已迁移测试框架，旧经验只能减少寻找成本，不能替代最新事实。对于用户偏好，当前明确要求同样需要优先解释；记忆应帮助完成任务，而不是把历史偏好僵化成无法修改的规则。

完整 Memory 评价至少包括：写入精度、无价值信息比例、作用域错误、旧知识失效、读取命中、实际采纳和任务收益。只统计“生成了多少条”会鼓励系统保存噪声。只统计“读工具调用成功”又会漏掉正确材料被忽略或误用的问题。

5. Skills：目录可以常见，正文应按需读取

Codex 的 Skills 扩展区分目录和正文：目录有 metadata 预算，读取从已启用的目录（enabled catalog）选择技能包（package），再按资源归属环境（authority）和资源标识（resource）找到实际内容。

为什么要保留 authority？一个资源可能属于编排端，也可能属于实际执行环境。相同的路径文字在不同环境里不一定指向同一个文件。读取合同需要知道“谁拥有这个 package，这个 resource 是否属于它，返回的身份是否仍是请求的资源”。这比让模型任意拼接路径更可靠。

图末还保留一个教学判断：读到的方法足够才采用；必要内容缺失时说明缺口。读完页数不证明方法完整，这也不是一项新增的产品状态。

目录可见、正文已读、方法已执行，是三个状态。一个 Skill 声明了测试步骤，并不表示模型已读取正文，更不表示测试已经运行；资源里写了命令，也不会自动扩大调用者权限。真正动作仍要经过第32章的工具与环境边界。

分页快照保持哪一次读取的一致性

本地 executor-backed Skills 读取可以复用分页快照。继续页命中缓存时不会探测文件编辑，因此能读到同一旧正文的后续内容；重新读取时可不带 cursor。这样的快照避免一份长文档前半段来自旧版、后半段来自新版，但也带来时效性取舍。设计时要决定“分页一致”与“每页最新”哪一个更符合任务，不能默认二者同时成立。

第23章的对照讨论发现目录与加载正文之间的变化；本节讨论的是一次读取开始后、继续取得后续页的范围。普通 Host Skill 的来源是否可变、文件是否来自不可变 plugin generation，以及分页是否命中缓存，仍需分别判断，不能把一种快照推广到所有 Skills 路径。

6. 子任务：新的执行单元需要任务输入，不只是角色名字

本章选择的 spawn 协作路径会解析角色、模型与历史分叉参数，并创建真实 child Thread。它还传递父/根工作身份和选定执行环境等信息，保留协作关系所需的上下文。

历史 fork 接受 none、all 或正整数所表示的最近若干轮。本地这条路径省略参数默认 all。因此“最小上下文通常更节约”属于设计建议，不能写成这里的默认行为。Full-history fork 还要处理父历史、上下文基线和新子任务指令之间的关系；不是把父聊天字符串直接复制到一个新 prompt 即告完成。

表 2 / Table 2 · 6. 子任务：新的执行单元需要任务输入，不只是角色名字
输入模式（Input mode）优点风险与适用判断
不复制历史任务边界短，噪声少父任务必须明确提供约束与材料
复制最近若干轮保留近期细节，控制体积可能漏掉更早的关键用户约束
复制全部允许历史减少手写背景，保留更多上下文成本和干扰更大，仍需明确子任务目标

对于文档检查器，父任务可以让子任务只审查“带空格路径的回归测试是否覆盖正确”。它应提供具体文件、允许动作、预期产物和验收标准；一句“你是资深测试专家”没有交代工作接口。

只读审查的完整参考任务卡如下：

type ChildTask = {
  objective: string;
  inputs: Array<{ path: string; purpose: string }>;
  allowedWrites: string[];
  forbiddenActions: string[];
  deliverable: {
    reportPath?: string;
    requiredFields: string[];
  };
  acceptance: string[];
};

const reviewTask: ChildTask = {
  objective: "检查带空格路径的回归测试是否覆盖实际故障",
  inputs: [{ path: "tests/test_checker.py", purpose: "阅读测试断言" }],
  allowedWrites: [],
  forbiddenActions: ["修改生产代码"],
  deliverable: { requiredFields: ["结论", "缺失场景", "建议断言"] },
  acceptance: ["结论对应具体测试行为", "区分实际执行与静态判断"]
};

再给定一个审查场景：测试只检查启动命令中的引号，没有覆盖程序内部再次按空格切分参数的分支；子任务只读了文件，没有运行测试。相应参考交付为：结论“现有断言不足以覆盖内部 split 的故障”；缺失场景“含空格的路径作为一个参数进入内部处理后仍保持完整”；建议断言“内部文件读取收到完整路径，且得到预期文件内容”；检查状态“静态判断，测试未运行”。父任务随后核对实际调用点，在自己的写入范围内补齐回归与修复，并依据真实测试结果结算。报告满足字段合同，也没有把静态审查冒充通过结果。

7. 发消息、要求继续、交付文件分别需要什么合同

本地 send_message 使用 QueueOnly，followup_task 使用 TriggerTurn。前者是传递信息；后者表达需要继续工作的意图。普通空闲 child 收到材料，与被要求开启新 Turn，是不同状态转换。还有第三种状态：Thread 没有活跃 Turn，但保留尚未结束的持久等待（outstanding durable sleep）记录时，QueueOnly 消息也能触发一个新的普通 Turn 来处理等待中的工作。它不会恢复原来已经结束的模型调用；“消息没有要求新任务”不等于绝不新开执行。活跃任务则在可处理的边界吸收消息。

父子关系可以写入持久图边，但不满足条件时会跳过，写入失败会记录 warning。存在父子 edge 不证明所有消息具有事务性持久投递，也不证明它是一套任意 DAG 调度器。冷恢复、完整权限继承和投递语义要沿对应路径进一步验证。

文件交付尤其容易被混淆。child Thread 是独立执行单元；它不自动意味着独立文件副本。spawn 会传递环境选择，不能据此认定每个 child 都拥有隔离 worktree。若两个任务共享目录，文件变化可能立即互相可见；若位于独立副本，父任务又必须有明确的合并或读取路径。

所以父任务至少要说明：谁拥有哪几个可写文件；结果是正文消息、文件路径还是补丁；父任务如何确认文件存在且内容正确；并发改同一文件时怎样处理。一个子任务返回“已完成”只能说明其报告或终态，父任务仍要对最终产物负责。

8. 将四种信息流放回同一任务

现在把案例串起来：Memory 提示项目曾使用 pytest；父任务读取当前项目确认这一点；Skill 给出验证步骤；父任务分配一个只读回归审查子任务；自己修复检查器并运行测试；收到 child 报告后核对断言，再交付最终 diff。若窗口不足，第38章的上下文机制负责继续当前工作。

表 3 / Table 3 · 8. 将四种信息流放回同一任务
机制它提供的帮助父任务仍要承担的责任
长期记忆（Memory）降低重复探索成本检查时效、作用域与当前事实
当前任务恢复资料（Continuation context）继续窗口前的工作找回最新约束与已发生动作
技能说明包（Skill）复用有组织的方法读取适用部分并实际执行
子会话（Child Thread）并行推进可独立子问题划边界、收结果、验收与整合

比较 Codex 与 Maka 时，可以固定表中的一种信息流，检查它的来源、消费条件和任务收益。管线长度、工具数量与 child 数量都不能单独证明收益。

9. 常见场景与参考结论

题一：为什么 提取阶段 要允许“成功但无输出”？

参考答案：不是每段经历都值得形成长期记忆。明确空结果能减少无效重试和噪声积累，同时把它与解析或模型请求失败分开。

题二：整合 Agent 已完成，为什么还要校验 artifact 和 ownership？

参考答案：模型终态不能证明文件形状和内容满足合同；执行期间可能失去 claim。关闭 worker、校验产物、确认 ownership 有助于避免在途写竞争和过期 worker 宣布成功，但没有自动构成跨存储事务。

题三：Memory 写成功，但下一次仍重复探索，可能缺在哪？

参考答案：检查读侧是否启用、摘要是否提供入口、检索是否命中、结果是否截断，以及模型是否把相关材料用于当前任务。写成功只是闭环中的一环。

题四：Skills 翻到第二页时读到旧内容，是一定的 bug 吗？

参考答案：要看合同。本地读取有复用分页快照的路径，优先保持同一次阅读一致性；文件修改不一定在续页命中缓存时可见。需要最新内容应按相应重新读取机制处理。

题五：send_message 与 followup_task 为什么要分开？

参考答案：传递材料与请求新 Turn 是不同意图。普通空闲目标仅收到 QueueOnly 材料，不等于已安排新工作；TriggerTurn 还需满足目标状态等启动条件。若空闲 Thread 保留 outstanding durable sleep，QueueOnly 也会触发新的普通 Turn 来处理这份等待；它不重开旧 Turn，也不复活旧调用栈。

题六：子任务说测试通过，父任务能直接汇报吗？

参考答案：先检查其验证范围、实际命令、对应产物与当前文件是否一致。对子任务未覆盖的部分保留未验证状态；同一共享目录还要考虑后续并发修改使旧结果失效。
