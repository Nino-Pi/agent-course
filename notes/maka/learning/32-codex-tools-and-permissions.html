第 32 章｜Codex：工具、执行通道与权限

本章概览

核心问题：Codex 怎样把模型可见的工具定义绑定到执行端，并在参数变化或失败时保持权限边界？

关键概念：ToolRouter（工具路由器）：连接声明与分派；registry（注册表）：按身份查实现；Hook（钩子）：在执行前后介入；approval（批准）：裁决本次动作；sandbox（沙箱）：限制实际资源访问；部分效果：失败前已发生的改动。

关系主线：本步工具计划连接定义与处理器，前置处理后的输入接受权限检查；执行后保留效果和反馈，按错误类别决定重试或对账。

所属主题：第31章 工具与执行；同题对照：Claude Code 工具与安全。

继续使用文档检查器案例。模型需要查找读取文件的工具，修复路径处理，运行测试，并阅读输出。如果环境里同时有本地 shell、MCP 服务、扩展工具和用于组织多个调用的代码执行表面，工具设计就已经超出“定义一个函数”的范围。

本章沿工具注册到 handler 的调用链理解问题；平台相关 enforcement 需要各自验证。教学伪代码用于推导合同，不表示 Codex 实际类型或完整生产逻辑。

1. 工具系统首先要保证的是身份清楚

考虑两个来源都注册 search：一个搜索项目文件，一个搜索外部知识库。如果 runtime 只用字符串 search 查字典，后注册者可能覆盖先注册者，模型眼前的描述与真正动作随加载顺序改变。这个问题与模型聪不聪明无关。

本地 Codex 的工具 registry 维护带 namespace（区分来源的名称空间）的身份、执行 runtime 和当前暴露方式。注册时存在名称冲突处理，某些内建执行工具名字还受保留规则约束。由此得到一个设计原则：工具名称是调用路由的一部分，工具描述是模型选择的帮助信息；二者不能互相替代。

表 1 / Table 1 · 1. 工具系统首先要保证的是身份清楚
层次应回答的问题文档检查器中的例子
身份（Identity）这个名字解析到哪个操作？默认执行工具与远程搜索工具分别归属谁
描述与参数结构（Description / Schema）模型何时用，传什么输入？工作目录、命令、超时、输出限制
暴露方式（Exposure）本步是否直接展示，是否可发现？常用工具直接提供，其他工具通过搜索发现
执行环境（Runtime）参数如何解析，如何执行？命令交给哪个环境
结果投影（Result projection）模型下一步能看到什么？exit code、输出、截断或继续读取信息
效果治理（Effect governance）什么条件下可以真的行动？文件范围、网络、批准与 sandbox

结果合同还须保留测试实际执行范围和输出；一句“执行成功”不足以支持后续验收。

2. 一份工具计划连接“展示”和“执行”

Codex 主链从 core、MCP、extension、dynamic tools 等来源构建 registry，再完成本步 ToolRouter。Router 同时保存实际分派所用 registry 与模型可见的 specs。模型请求从本步 router 获取工具表面，回来的调用沿相应执行体系处理。

本步计划分出两条线：一条提供模型可见定义，一条保留执行 registry；模型生成的调用随后汇入执行线。这张图表达的是“同一处能检查两端是否匹配”，不是宣称所有远程工具都已经被证明没有更新竞争。

工具暴露还有一个需要保留的细节：工具可以直接展示，也可以通过 namespace、代码模式或延迟发现等方式进入模型的可用范围。“当前 prompt 没有所有 schema”不等于“不存在那些能力”；“发现了名称”也不等于“已经满足执行权限”。这里应区分可发现、可调用、获准执行三个问题。

工程上的取舍来自上下文预算。直接展示全部工具，模型一开始就能选，但付出更大输入成本和选择干扰。延迟发现减小初始工具表面，却多出一次发现请求、额外延迟，以及工具索引过时的可能。对于文档检查器，读取、编辑和测试这些高频能力适合保持容易找到；大量低频业务连接器可以按需发现。

3. 调用回来以后，runtime 还要做什么

模型生成合法 JSON 并不意味着这个调用适合执行。真实系统仍要检查名字、payload 类型、参数含义、当前环境以及允许效果的范围。

本地 registry 的路径先查工具身份，再检查 payload 类型，运行 pre hook，调用 handler，最后处理 post hook 和结果。未知名称可以形成给模型修正的信息；调用的 payload 类型与工具不匹配，则属于更严重的合同错误。工具自己的具体参数解析仍归相应 handler。

表 2 / Table 2 · 3. 调用回来以后，runtime 还要做什么
阶段输入（Input）可能的结果后续应该如何理解
查找（Lookup）名称与 namespace找到 runtime，或未知工具未知工具还没有产生领域效果
类型检查（Type check）Function/Custom 等 payload匹配或合同错误schema 文档不能替代此检查
事前钩子（Pre hook）原始请求的工具输入继续、阻止、返回更新后的输入更新后要重新形成可执行请求
处理器（Handler）实际请求与环境执行结果或执行错误错误未必表示没有效果
事后钩子（Post hook）已完成执行的结果接受、增加反馈、阻止结果这个阶段已经晚于效果发生
结果投影（Result projection）内部结果对象给模型、给日志、给 UI 的表达三种成功语义可能不同

为什么要区分给日志与给模型的结果？日志可能需要完整的调用身份和分类；模型需要足够信息作下一步决策；UI 需要简洁状态和可查看产物。若只保留一条字符串，就很难既控制上下文大小，又保留可诊断性。

本地源码还区分 handler 是否执行与某些生命周期结果，避免“工具流程结束”被误解为“效果成功且任务正确”。领域验收仍需额外判断，例如测试命令 exit 0，但实际只运行了帮助信息；或者改动已写入，但回归测试没有覆盖带空格路径。

4. Hook 的时序决定了它能保护什么

PreToolUse 位于 handler 之前，能够阻止调用或更新输入。PostToolUse 位于 handler 之后，可以治理模型看到的结果和补充反馈，但无法撤销已经完成的执行。

还有一个控制流条件：本章所述 registry 只在 success_for_logging() 为真且提供 payload 时运行 PostToolUse。图中的 post 箭头据此有条件出现，失败或未知结果不保证走到它；不能把“加个 post hook”当作所有失败的自动取证机制。

为了单独观察 Hook 时序，另设一个能修改文档的教学辅助命令 python checker.py --write README.md；这里的 checker.py 及 --write 是新设定，不是前章 scan.py 已有的接口。设模型准备运行这条命令。pre hook 检测到最新约束“不改 README”，可以在效果前阻止它。若命令已经写完 README，post hook 再发现不合要求，它只能表示结果不应被接受或需要进一步处理；不能让文件自动回到原状。

这个区分也影响模型下一步行为。若工具已经修改文件但 post hook 阻止了结果，而反馈只写“失败”，模型可能重复运行命令。因此反馈应尽量帮助区分“执行前被拒”“执行失败”“执行后结果被拒”以及“效果尚待确认”。这是设计建议；本地每条结果投影需要结合其具体实现判断。

下图限定为使用 ToolOrchestrator 的 handler 路径；其他 handler 依照各自执行合同处理，不能从图中推出所有工具都经过同一个 sandbox。

O → E 是效果边界：此前检查身份、参数与允许范围，此后处理结果、验证与可能的补偿。Hook 位于边界哪一侧，决定它能阻止尚未发生的动作，还是只能处理已经产生的结果。

5. Approval 和 sandbox 为什么要同时存在

Approval 回答一个具体动作在当前上下文中是否获准；sandbox 把访问范围约束落实到执行环境。一个批准提示无法持续拦截系统调用；一个文件 sandbox 也不会替用户判断“这次发布是否符合任务意图”。

本地工具执行编排器读取执行环境的 permission profile，判断请求是 Skip、Forbidden 还是 NeedsApproval，再选择执行尝试。Skip 也不能简单理解为绝无审查：严格自动审查分支仍可能请求审查。Forbidden 表示拒绝执行；NeedsApproval 则会在继续前等待审批结果。

权限信息来自工具实际使用的环境。有的执行端自行管理进程 sandbox，本地编排器会保留相应执行端语义。因此调用链应区分“请求 → 执行环境权限 → 适用的 enforcement”，而非将所有工具归入同一个本机 sandbox。

对于文档检查器，审批对象应该包含命令、工作目录、目标范围和申请的权限。若 pre hook 把命令从只读检查改成写文件，审批必须理解改写后的请求；不能复用对原始只读动作的判断。相同命令字符串在不同目录也可能改变完全不同的文件。

用一次补丁落实这条链

只认识通用编排器还不够，要追到一个真正使用它的工具。本地补丁执行路径先拿到目标环境与 cwd，确定是执行端管理还是本地平台 sandbox，计算有效文件权限，再准备实际 patch。随后构造带变更范围和批准要求的请求，交给编排器执行，并通过事件 emitter 展示开始与结束。

这里有一个值得借鉴的失败表示：执行成功时返回输出及 delta（已知文件变化）；执行失败时仍可以从 runtime 取得已经提交的 delta，再交给结束处理。这让“失败时是否已经修改了一部分文件”成为可表达的信息。它不证明所有错误都能自动回滚，而是避免用一个错误字符串抹掉已发生的变化。

delta 还带一个关键字段 exact。若写失败前可能 truncate 或部分写，标志变为 false；ToolEmitter 将其交给 TurnDiffTracker，后者会 invalidate 并清除聚合 diff。这是在拒绝提供不精确的全貌，不能解释成改动为空。这些 denial/rejected 结果也可携带已知前缀，同时显示失败。

回到检查器案例，如果补丁涉及两个文件，第一个写入后第二个失败，后续决策需要知道哪个文件已经变了。再次套用整个补丁可能失败、覆盖新改动，或重复效果。更合理的动作是先检查实际 delta 和当前文件，再生成针对剩余问题的修复。因此完整结果合同需要同时表达已知 delta、未完成范围和不精确状态。

批准还带有时间条件。贯穿案例中，自动审查正评估“修改 README”，用户又补充“不改 README”；先前上下文里的 Allow 就不能直接作为新约束下的通行证。当前源码中自动审查器 Guardian 的 ThreadOwned 模式会在完成 Allow 时重查根授权版本与用户消息 revision，变化时取消该结果。reviewer 本身只满足审查关卡，不扩大动作权限；sandbox 和执行编排仍要履行自己的边界。

6. 重试的核心是错误分类，不是再试一次

第一次执行失败后，先问失败属于哪一类。工具编排器只对符合条件的 sandbox denial 进入特定后续分支，并检查工具是否允许升级、审批策略是否允许请求，以及网络策略等限制。普通程序错误不会自动变成越权重试。

表 3 / Table 3 · 6. 重试的核心是错误分类，不是再试一次
观察优先判断合理的下一步设计
Python 语法错误程序有问题修正代码或参数
文件不存在路径、工作目录或任务假设错误读取目录并修正路径
sandbox 拒绝写入当前效果超出执行范围检查任务授权与可用审批路径
明确不可绕过的网络限制环境策略禁止该访问保留限制，选择可行工作路径
执行超时，效果不明可能已开始或部分完成查询效果后再决定重试
输出缺失但目标文件存在效果与结果记录不一致核对实际内容，避免盲目重复

这个表比“失败时指数退避”更接近 Agent 工具问题。指数退避能控制请求频率，却无法判断重发一笔转账或再次覆盖文件是否正确。对具有副作用的调用，需要领域的幂等键、条件写入、状态查询或补偿机制。读取到 common orchestrator 和 rollout 记录，并不能证明这些合同已被每一种工具实现。

也不能把 sandbox denial 直接归为“效果前拒绝”：多文件补丁可能已写完前面的文件才在后面被拒。要按具体尝试解释错误与 delta；是否允许后续尝试和是否能安全重复业务是两项判断。

7. 执行效果与反馈的参考接口

下面的接口刻意把“执行效果”与“调用反馈”分开。它是本例的参考抽象，不是 Codex 源码的翻译。先看结果：effect 表示对效果的认识，accepted 表示这份反馈是否被接受，两者不能互相推导。例如文件已改、事后检查拒绝结果，可以同时保留确认的效果和 accepted=false。

type EffectState = "none" | "confirmed" | "unknown";
type ToolOutcome = {
  callId: string;
  phase: "precheck" | "execution" | "postcheck";
  effect: EffectState; // none 需要无效果证据；无法确认时保留 unknown。
  accepted: boolean; // 接受反馈不等于用户任务已通过业务验收。
  observation: string;
  nextAction?: "revise_input" | "query_effect" | "verify_artifact";
};

再看生成这份结果的过程。输入是工具调用和本步冻结计划；先解析、处理 pre hook，再对实际输入作权限判断。只有得到 granted 才到达 runtime.attempt，该行之后的反馈处理必须保留已发生效果。这些辅助函数按前文合同理解，以下不是可独立运行的程序。

async function perform(call: ToolCall, step: StepSnapshot): Promise<ToolOutcome> {
  const runtime = step.registry.resolve(call.identity);
  const parsed = runtime.parse(call.payload);
  const revised = await hooks.before(parsed);
  if (revised.blocked) return rejectedBeforeExecution(call.id, revised.reason);
  const request = runtime.validate(revised.input);
  const grant = await policy.decide(request, step.environment);
  if (grant.kind === "denied") return rejectedBeforeExecution(call.id, grant.reason);
  const resolved = grant.kind === "needs_approval"
    ? await policy.awaitApproval(grant)
    : grant;
  if (resolved.kind !== "granted") {
    return rejectedBeforeExecution(call.id, "approval not granted");
  }
  const result = await runtime.attempt(request, resolved);
  return hooks.after(result); // 这里不能把已发生效果改成 none。
}

此处教学权限结果区分 denied、needs_approval 与 granted；待审批不能直接进入执行。等待期间若权限、目标或用户要求变化，还需在实际准入处重新校验。真实 Codex 的分支名称和接线以本章前述源码范围为准。

带空格路径的验证例子可以是读取 fixtures/input files/sample.md，执行针对该路径的测试，再查看修改 diff。路径引用、命令退出码和测试断言解决不同问题。只证明 Shell 能解析路径，不代表检查器自己的路径处理已经正确。

如果需要一次提交多个工具调用，先按依赖和冲突分类：两个无副作用读取通常更容易并发；读取刚修改的文件必须等写入完成；两个写同一路径的工具需要序列或合并机制。工具声明“支持并行”只是调度信号，不能替代对这次请求的依赖判断。

8. 常见场景与参考结论

下面的 pytest 问题假设这个 Python 项目以它作为测试入口；实际入口仍须由项目配置确认。

题一：为什么 schema 正确还需要 runtime 检查？

参考答案：schema 帮助约束模型输出形状，但执行时仍要解析真实身份、确认 payload 类型、验证字段含义，并检查当前环境和权限。外部状态也可能在模型生成期间变化。

题二：PostToolUse 阻止结果，是否说明工具没有执行？

参考答案：不能。本章读取的路径在 handler 之后运行 post hook，阻止的是结果采纳。已经发生的文件或外部效果要单独确认，不能盲目重复调用。

题三：pytest 失败应该申请更高权限吗？

参考答案：先检查错误类别。断言失败、导入失败和 sandbox denial 对应不同修复。只有确为权限限制且任务与策略允许，才讨论适用的审批或执行路径。

题四：工具可以被模型发现，是否意味着它被允许执行？

参考答案：发现决定候选能力，路由决定调用解释，权限决定效果可否发生。即使 schema 可见，runtime 仍可能因当前请求和环境拒绝执行。

题五：怎样判断工具是否具有 exactly-once 保证？

参考答案：指出效果发生与结果记录之间的崩溃窗口，按工具讨论幂等键、条件写、查询或补偿。单凭通用工具 registry、日志和 sandbox，无法证明任意外部副作用 exactly-once。

题六：补丁第二个文件写失败，界面 Failed、聚合 diff 消失，可以原样重试吗？

参考结论

不能据此决定。第一个文件可能已改，第二个可能截断；delta 不精确会使 tracker 清空聚合显示，失败不等于零效果。先回读相关文件、检查保留内容与目标，再决定是否需要新的剩余修复，并保留原调用的未知范围。PostToolUse 也不保证在失败分支执行，不能把未收到它的反馈当作没有问题。

相关机制见Codex 上下文与压缩；工具、文件与恢复的参考设计见第50章、第51章和第52章。
