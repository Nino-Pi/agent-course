第 32 章｜Codex：工具（Tool）、执行通道与权限（Permission）

本章概览

核心问题：Codex 怎样把模型（Model）可见的工具（Tool）定义绑定（Binding）到执行端，并在参数（Argument）变化或失败时保持权限（Permission）边界？

关键概念：工具路由器（ToolRouter）：连接声明与分派；注册表（Registry）：按身份（Identity）查实现；钩子（Hook）：在执行前后介入；批准（Approval）：决定本次行动请求（Action）是否获准；沙箱（Sandbox）：限制实际资源访问；部分效果（Partial Effect）：失败前已发生的改动。

关系主线：本步工具计划（Tool Plan）连接定义与处理器（Handler），前置处理后的输入（Input）接受权限（Permission）检查；执行后保留效果（Effect）和反馈（Feedback），按错误类别决定重试（Retry）或对账（Reconciliation）。

前情回顾：工具（Tool）合法还不等于效果（Effect）获准

第31章把工具（Tool）分成声明、执行、结果三层合同：模型（Model）需要知道怎么选，执行层（Execution Layer）要检查此刻能否做，结果还须区分已发生效果（Effect）与尚缺验收（Acceptance）。第29章说明Codex的任务线程（Thread，非操作系统线程）与会话（Session，执行内核对象）各承担什么；本章不再只看循环，而是追同一次行动请求（Action）怎样从模型（Model）可见定义找到真实消费者（Consumer）。

这里重新交代文档检查器的最小背景：项目包含读取文档的Python程序，路径可能带空格，例如fixtures/input files/sample.md。工作要查明程序与测试入口（Entry Point），修复路径处理，运行相关测试并阅读结果。此处是用于比较工具（Tool）设计的场景，没有新增Codex实跑记录；后文的checker.py --write另设为能修改文档的辅助命令，不能当作已有程序接口。

本章先看工具计划（Tool Plan）如何同时约束声明与执行，再看输入（Input）改写、批准（Approval）、沙箱（Sandbox）及补丁失败的后置证据。平台资源限制仍按具体执行环境（Execution Environment）判断；类型示意不冒充Codex生产实现。同题的公开产品对照见第33章。

1. 工具（Tool）系统首先要保证的是身份（Identity）清楚

考虑两个来源都注册 search：一个搜索项目文件，一个搜索外部知识库。如果运行时（Runtime）只用字符串 search 查字典，后注册者可能覆盖先注册者，模型（Model）眼前的描述与实际执行对象随加载顺序改变。这个问题与模型（Model）聪不聪明无关。

Codex的工具注册表（Tool Registry）用名称空间（Namespace）区分来源，并记录工具身份（Tool Identity）、执行运行时（Runtime）和暴露方式（Exposure）。注册时存在名称冲突处理，某些内建执行工具（Tool）名字还受保留规则约束。由此得到一个设计原则：工具（Tool）名称是调用路由的一部分，工具（Tool）描述是模型（Model）选择的帮助信息；二者不能互相替代。

结果合同（Result Contract）还须保留测试实际执行范围（Scope）和输出；一句“执行成功”不足以支持后续验收（Acceptance）。

2. 一份工具计划（Tool Plan）连接“展示”和“执行”

Codex 主链从内建核心（Core）、模型上下文协议（Model Context Protocol，MCP）、执行扩展（Extension）、动态工具（Dynamic Tools）等来源构建注册表（Registry），再完成本步工具路由器（ToolRouter）。它同时保存实际分派所用注册表（Registry）与模型（Model）可见的工具定义（Specs）。模型（Model）请求从本步工具路由器（ToolRouter）获取工具（Tool）表面，回来的调用沿相应执行体系处理。

本步计划分出两条线：一条提供模型（Model）可见定义，一条保留执行注册表（Registry）；模型（Model）生成的调用随后汇入执行线。这张图表达的是“同一处能检查两端是否匹配”，不是宣称所有远程工具（Tool）都已经被证明没有更新竞争。

工具（Tool）暴露还有一个需要保留的细节：工具（Tool）可以直接展示，也可以通过名称空间（Namespace）、代码模式（Code Mode）或延迟发现（Deferred Discovery）等方式进入模型（Model）的可用范围（Scope）。“当前提示词（Prompt）没有所有参数模式（Schema）”不等于“不存在那些能力”；“发现了名称”也不等于“已经满足执行权限（Permission）”。这里应区分可发现、可调用、获准执行三个问题。

工程上的取舍来自上下文（Context）预算（Budget）。直接展示全部工具（Tool），模型（Model）一开始就能选，但付出更大输入（Input）成本和选择干扰。延迟发现（Deferred Discovery）减小初始工具（Tool）表面，却多出一次发现请求、额外延迟，以及工具（Tool）索引过时的可能。对于文档检查器，读取、编辑和测试这些高频能力适合保持容易找到；大量低频业务连接器可以按需发现。

3. 调用回来以后，运行时（Runtime）还要做什么

模型（Model）生成符合JavaScript对象表示法（JavaScript Object Notation，JSON）语法的文本并不意味着这个调用适合执行。真实系统仍要检查名字、载荷（Payload）类型、参数（Argument）含义、当前环境以及允许效果（Effect）的范围（Scope）。

本地注册表（Registry）的路径先查工具身份（Tool Identity），再检查载荷（Payload）类型，运行前置钩子（Pre Hook），调用处理器（Handler），最后处理后置钩子（Post Hook）和结果。未知名称可以形成给模型（Model）修正的信息；调用的载荷（Payload）类型与工具（Tool）不匹配，则属于更严重的合同错误。工具（Tool）自己的具体参数（Argument）解析仍归相应处理器（Handler）。

为什么要区分给日志（Log）与给模型（Model）的结果？日志（Log）可能需要完整的调用身份（Call Identity）和分类；模型（Model）需要足够信息作下一步决策；用户界面（UI）需要简洁状态（State）和可查看产物。若只保留一条字符串，就很难既控制上下文（Context）大小，又保留可诊断性。

本地源码还区分处理器（Handler）是否执行与某些生命周期结果，避免“工具（Tool）流程结束”被误解为“效果（Effect）成功且任务（Task）正确”。领域验收（Acceptance）仍需额外判断，例如测试命令退出码（Exit Code）为0，但实际只运行了帮助信息；或者改动已写入，但回归测试（Regression Test）没有覆盖带空格路径。

4. 钩子（Hook）的时序决定了它能保护什么

钩子（Hook）是宿主（Host）在一个已命名阶段调用的扩展处理。名称说明进入时点，不说明它拥有整个任务（Task）的裁决权。先问“工具（Tool）处理器（Handler）是否已执行”，才能判断该钩子（Hook）是在阻止效果（Effect），还是处理效果（Effect）之后的反馈（Feedback）。

前置工具钩子（PreToolUse）位于处理器（Handler）之前，能够阻止调用或更新输入（Input）。后置工具钩子（PostToolUse）位于处理器（Handler）之后，可以治理模型（Model）看到的结果和补充反馈（Feedback），但无法撤销已经完成的执行。

还有一个控制流条件：本章所述注册表（Registry）只在 success_for_logging() 为真且提供载荷（Payload）时运行后置工具钩子（PostToolUse）。图中的后置钩子（Post Hook）箭头据此有条件出现，失败或未知结果不保证走到它；不能把“加个后置钩子（Post Hook）”当作所有失败的自动取证机制。

为了单独看清钩子（Hook）的时序，另设一个能修改文档的教学辅助命令 python checker.py --write README.md；这里的 checker.py 及 --write 是新设定，不是本章开头检查器的既有接口。设模型（Model）准备运行这条命令。前置钩子（Pre Hook）检测到最新约束“不改 README”，可以在效果（Effect）前阻止它。若命令已经写完 README，后置钩子（Post Hook）再发现不合要求，它只能表示结果不应被接受或需要进一步处理；不能让文件自动回到原状。

这个区分也影响模型（Model）下一步行为。若工具（Tool）已经修改文件但后置钩子（Post Hook）阻止了结果，而反馈（Feedback）只写“失败”，模型（Model）可能重复运行命令。因此反馈（Feedback）应尽量帮助区分“执行前被拒”“执行失败”“执行后结果被拒”以及“效果（Effect）尚待确认”。这是设计建议；本地每条结果投影（Result Projection）需要结合其具体实现判断。

下图限定为使用 ToolOrchestrator 的处理器（Handler）路径；其他处理器（Handler）依照各自执行合同（Execution Contract）处理，不能从图中推出所有工具（Tool）都经过同一个沙箱（Sandbox）。

O → E 是效果（Effect）边界：此前检查身份（Identity）、参数（Argument）与允许范围（Scope），此后处理结果、验证与可能的补偿（Compensation）。钩子（Hook）位于边界哪一侧，决定它能阻止尚未发生的操作，还是只能处理已经产生的结果。

5. 批准（Approval）和沙箱（Sandbox）为什么要同时存在

批准（Approval）回答一个具体行动请求（Action）在当前上下文（Context）中是否获准；沙箱（Sandbox）把访问范围（Scope）约束落实到执行环境（Execution Environment）。一个批准（Approval）提示无法持续拦截系统调用（Syscall）；一个文件沙箱（Sandbox）也不会替用户判断“这次发布是否符合任务（Task）意图”。

本地工具（Tool）执行编排器（Tool Orchestrator）读取执行环境（Execution Environment）的权限配置（Permission Profile），判断请求是 Skip、Forbidden 还是 NeedsApproval，再选择执行尝试（Execution Attempt）。Skip 也不能简单理解为绝无审查：严格自动审查分支仍可能请求审查。Forbidden 表示拒绝执行；NeedsApproval 则会在继续前等待审批结果。

权限（Permission）信息来自工具（Tool）实际使用的环境。有的执行端自行管理进程沙箱（Sandbox），本地编排器会保留相应执行端语义。因此调用链应区分“请求 → 执行环境（Execution Environment）权限（Permission） → 适用的强制约束（Enforcement）”，而非将所有工具（Tool）归入同一个本机沙箱（Sandbox）。

对于文档检查器，审批对象应该包含命令、工作目录、目标范围（Scope）和申请的权限（Permission）。若前置钩子（Pre Hook）把命令从只读检查改成写文件，审批必须理解改写后的请求；不能复用对原始只读行动请求（Action）的判断。相同命令字符串在不同目录也可能改变完全不同的文件。

用一次补丁落实这条链

只认识通用编排器还不够，要追到一个真正使用它的工具（Tool）。本地补丁执行路径先拿到目标环境与当前工作目录（Current Working Directory，cwd），确定是执行端管理还是本地平台沙箱（Sandbox），计算有效文件权限（Permission），再准备实际补丁（Patch）。随后构造带变更范围（Scope）和批准（Approval）要求的请求，交给编排器执行，并通过事件发射器（Emitter）展示开始与结束。

这里有一个值得借鉴的失败表示：执行成功时返回输出及已知变更（Delta）；执行失败时仍可以从运行时（Runtime）取得已经提交的已知变更（Delta），再交给结束处理。这让“失败时是否已经修改了一部分文件”成为可表达的信息。它不证明所有错误都能自动回滚，而是避免用一个错误字符串抹掉已发生的变化。

先把两个结果维度分开：调用可以失败，同时已经有若干文件改变。delta描述已知的文件变化；exact描述这些变化是否足以精确表示相关修改。失败状态（State）与变化集合不是互相排斥的两种结果。

已知变更（Delta）还带一个关键字段 exact。若写失败前可能先截断文件或仅写入一部分，标志变为false；ToolEmitter 将其交给 TurnDiffTracker，后者会使跟踪状态失效（Invalidate）并清除聚合差异（Diff）。这是在拒绝提供不精确的全貌，不能解释成改动为空。这些拒绝（Denial / Rejected）结果也可携带已知前缀，同时显示失败。

回到检查器案例，如果补丁涉及两个文件，第一个写入后第二个失败，后续决策需要知道哪个文件已经变了。再次套用整个补丁可能失败、覆盖新改动，或重复效果（Effect）。更合理的下一步是先检查实际已知变更（Delta）和当前文件，再生成针对剩余问题的修复。因此完整结果合同（Result Contract）需要同时表达已知变更（Delta）、未完成范围（Scope）和不精确状态（State）。

批准（Approval）还带有时间条件。贯穿案例中，自动审查正评估“修改 README”，用户又补充“不改 README”；先前上下文（Context）里的允许（Allow）判断就不能直接作为新约束下的通行证。当前源码中自动审查器Guardian的ThreadOwned模式（审查绑定拥有该工作的任务线程（Thread））会在完成允许（Allow）判断时重查根授权（Authorization）版本与用户消息（Message）修订（Revision），变化时取消（Cancellation）该结果。审查者（Reviewer）本身只满足审查关卡，不扩大行动请求（Action）的权限（Permission）；沙箱（Sandbox）和执行编排仍要履行自己的边界。

6. 重试（Retry）的核心是错误分类，不是再试一次

需要分开两个判断：政策是否允许另一种执行尝试（Execution Attempt），以及原业务操作能否安全重复。前者成立，不会自动证明后者成立；反过来，操作满足幂等（Idempotency）条件而可重复，也不会扩大当前权限（Permission）。

第一次执行失败后，先问失败属于哪一类。工具（Tool）编排器只对符合条件的沙箱拒绝（Sandbox Denial）进入特定后续分支，并检查工具（Tool）是否允许升级、审批策略是否允许请求，以及网络策略等限制。普通程序错误不会自动变成越权重试（Retry）。

这个表比“失败时指数退避”更接近智能代理（Agent）工具（Tool）问题。指数退避能控制请求频率，却无法判断重发一笔转账或再次覆盖文件是否正确。对具有副作用的调用，需要领域的幂等（Idempotency）键、条件写入、状态（State）查询或补偿（Compensation）机制。读取到共用执行编排器（Common Orchestrator）和过程记录（Rollout），并不能证明这些合同已被每一种工具（Tool）实现。

也不能把沙箱拒绝（Sandbox Denial）直接归为“效果（Effect）前拒绝”：多文件补丁可能已写完前面的文件才在后面被拒。要按具体尝试解释错误与已知变更（Delta）；是否允许后续尝试和是否能安全重复业务是两项判断。

7. 执行效果（Effect）与反馈（Feedback）的参考接口（Interface）

下面的接口（Interface）刻意把“执行效果（Effect）”与“调用反馈（Feedback）”分开。它是本例的参考抽象，不是 Codex 源码的翻译。先看结果：effect 表示对效果（Effect）的认识，accepted 表示这份反馈（Feedback）是否被接受，两者不能互相推导。例如文件已改、事后检查拒绝结果，可以同时保留确认的效果（Effect）和 accepted=false。

type EffectState = "none" | "confirmed" | "unknown";
type ToolOutcome = {
  callId: string;
  phase: "precheck" | "execution" | "postcheck";
  effect: EffectState; // 需有无效果证据，否则保留 unknown。
  accepted: boolean; // 接受反馈不等于通过任务验收。
  observation: string;
  nextAction?: "revise_input" | "query_effect" | "verify_artifact";
};

按本例定义，拒绝采纳反馈不推出没有效果：

accepted=false  ⇏  effect=none.\text{accepted}=\text{false}\;\not\Rightarrow\;\text{effect}=\text{none}.accepted=false⇒effect=none.

再看生成这份结果的过程，按“最终输入（Input）、许可门槛、实际尝试”三段阅读。输入（Input）是工具（Tool）调用和本步冻结计划；先解析、处理前置钩子（Pre Hook），再对实际输入（Input）作权限（Permission）判断。只有得到 granted 才到达 runtime.attempt，该行之后的反馈（Feedback）处理必须保留已发生效果（Effect）。这些辅助函数按前文合同理解，以下不是可独立运行的程序。

async function perform(
  call: ToolCall,
  step: StepSnapshot
): Promise<ToolOutcome> {
  // 第一段：按身份找实现，形成最终输入。
  const runtime = step.registry.resolve(call.identity);
  const parsed = runtime.parse(call.payload);
  const revised = await hooks.before(parsed);
  if (revised.blocked) return rejectedBeforeExecution(call.id, revised.reason);
  const request = runtime.validate(revised.input);
  // 第二段：检查改写后请求的许可。
  const grant = await policy.decide(request, step.environment);
  if (grant.kind === "denied") return rejectedBeforeExecution(call.id, grant.reason);
  const resolved = grant.kind === "needs_approval"
    ? await policy.awaitApproval(grant)
    : grant;
  if (resolved.kind !== "granted") {
    return rejectedBeforeExecution(call.id, "approval not granted");
  }
  // 第三段：执行后保留已经发生的变化。
  const result = await runtime.attempt(request, resolved);
  return hooks.after(result); // 不抹去已发生的效果。
}

此处教学权限（Permission）结果区分 denied、needs_approval 与 granted；待审批不能直接进入执行。等待期间若权限（Permission）、目标或用户要求变化，还需在实际准入处重新校验。真实 Codex 的分支名称和接线以本章前述源码范围（Scope）为准。

这里沿用本章开头的带空格路径。验证需要读取 fixtures/input files/sample.md，执行针对该路径的测试，再查看修改差异（Diff）。路径引用、命令退出码（Exit Code）和测试断言解决不同问题。只证明 Shell 能解析路径，不代表检查器自己的路径处理已经正确。

如果需要一次提交多个工具（Tool）调用，先按依赖（Dependency）和冲突分类：两个无副作用读取通常更容易并发（Concurrency）；读取刚修改的文件必须等写入完成；两个写同一路径的工具（Tool）需要序列或合并机制。工具（Tool）声明“支持并行”只是调度（Scheduling）信号，不能替代对这次请求的依赖（Dependency）判断。

8. 常见场景与参考结论

下面的 pytest 问题假设这个 Python 项目以它作为测试入口（Entry Point）；实际入口（Entry Point）仍须由项目配置确认。

题一：为什么参数模式（Schema）正确还需要运行时（Runtime）检查？

参考答案：参数模式（Schema）帮助约束模型（Model）输出形状，但执行时仍要解析真实身份（Identity）、确认载荷（Payload）类型、验证字段含义，并检查当前环境和权限（Permission）。外部状态（State）也可能在模型（Model）生成期间变化。

题二：后置工具钩子（PostToolUse）阻止结果，是否说明工具（Tool）没有执行？

参考答案：不能。本章读取的路径在处理器（Handler）之后运行后置钩子（Post Hook），阻止的是结果采纳。已经发生的文件或外部效果（Effect）要单独确认，不能盲目重复调用。

题三：pytest 失败应该申请更高权限（Permission）吗？

参考答案：先检查错误类别。断言失败、导入失败和沙箱拒绝（Sandbox Denial）对应不同修复。只有确为权限（Permission）限制且任务（Task）与策略允许，才讨论适用的审批或执行路径。

题四：工具（Tool）可以被模型（Model）发现，是否意味着它被允许执行？

参考答案：发现决定候选能力，路由决定调用解释，权限（Permission）决定效果（Effect）可否发生。即使参数模式（Schema）可见，运行时（Runtime）仍可能因当前请求和环境拒绝执行。

题五：怎样判断工具（Tool）是否具有恰好一次（Exactly-Once）保证？

参考答案：指出效果（Effect）发生与结果记录之间的崩溃窗口，按工具（Tool）讨论幂等（Idempotency）键、条件写、查询或补偿（Compensation）。单凭通用工具（Tool）注册表（Registry）、日志（Log）和沙箱（Sandbox），无法证明任意外部副作用恰好一次（Exactly-Once）。

题六：补丁第二个文件写失败，界面显示失败（Failed）、聚合差异（Diff）消失，可以原样重试（Retry）吗？

参考结论

不能据此决定。第一个文件可能已改，第二个可能截断；已知变更（Delta）不精确会使差异跟踪器（Diff Tracker）清空聚合显示，失败不等于零效果（Effect）。先回读相关文件、检查保留内容与目标，再决定是否需要新的剩余修复，并保留原调用的未知范围（Scope）。后置工具钩子（PostToolUse）也不保证在失败分支执行，不能把未收到它的反馈（Feedback）当作没有问题。
