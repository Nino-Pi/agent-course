第 33 章｜Claude Code：工具（Tool）、钩子（Hook）与安全边界（Security Boundary）

本章概览

核心问题：同一次文件写入，事前拒绝、执行中限制与事后检查，为什么会留下不同结果？

关键概念：权限规则（Permission Rule）决定允许、询问或拒绝调用；钩子（Hook）在指定事件（Event）插入检查；沙箱（Sandbox）限制适用进程实际访问的资源；工具发现（Tool Discovery）寻找能力；效果（Effect）是文件或外部系统已经发生的变化。

关系主线：先理解控制发生的时点，再检查最终输入和实际执行路径；工具（Tool）被找到不代表获准，事后反馈也不能撤销既有变化。

前情回顾：权限（Permission）、隔离（Isolation）与结果各回答什么？

第17章区分了权限（Permission）与隔离（Isolation）：前者回答某项行动请求（Action）是否允许，后者限制实际执行能够访问什么。允许运行一个测试入口，并不等于它递归调用的所有脚本都只会测试。第31章进一步说明，工具调用（Tool Call）需要合法参数、有效授权和可解释的结果；缺少回执时，未知效果（Unknown Effect）不能被改写成“没有执行”。

本章沿用第30章的 Python 扫描器：scan.py 在路径含空格时失败，README 的命令也有问题。用户允许修改相关实现、必要回归测试和 README，要求保留已有配置差异，并禁止上传仓库或发布内容。我们研究这些约束怎样进入运行支撑（Agent Harness）的工具控制；以下是公开产品合同与教学推演，不是一次真实 Claude Code 运行，也不假定其内部类型与 Maka 相同。

1. 同一次写入，检查放在哪里会改变结论

先暂时增加一个明确的教学变体：用户允许在指定输出目录生成 report.md。这个文件只用于解释报告写入，不扩大上述扫描器修复题的文件范围。

模型（Model）提出 Write(report.md) 后，可能出现两种不同情况：

表 1 / Table 1 · 1. 同一次写入，检查放在哪里会改变结论
检查时点已知过程可以得出的结论
写入前最终目标不在允许目录，调用被拒绝这次写入没有经该工具路径执行
写入后文件已生成，检查发现缺少必要字段写入效果（Effect）已发生，报告质量尚不合格

第二行不能描述成“整个动作被阻止，文件没有变化”。补修或删除报告是后续操作，必须根据当前文件、授权和工具能力另行处理；远端报告还需要服务端支持撤回。

钩子（Hook） 是宿主（Host）在指定事件（Event）触发的扩展处理。前置钩子（PreToolUse Hook）可以在工具调用（Tool Call）执行前检查或改变输入；后置钩子（PostToolUse Hook）接收成功执行后的输入与结果。二者的名字相近，能改变的事实却不同。

图说明前后位置，不展开全部钩子（Hook）、权限模式（Permission Mode）和分类器（Classifier）的内部总排序。拒绝分支仅说明该路径没有执行这次调用，不能证明别的进程从未修改同一文件。

公开合同中，后置钩子（PostToolUse Hook）的 block 给模型（Model）增加原因反馈，仍不能回滚已发生的效果（Effect）。

updatedToolOutput 才负责替换送给模型（Model）的结果表示。内置工具的替换值须符合其输出结构（Output Schema）；不匹配时会被忽略，仍使用原结果。通过模型上下文协议（Model Context Protocol，MCP）接入的工具，其结果则不做同样的结构验证。替换显示内容同样不会改写已经写出的文件。成功回包也只是工具层结果，是否满足用户任务仍需检查。

2. 从“工具（Tool）报错”拆出五种不同问题

回到扫描器修复题。一个工具调用（Tool Call）从被想到，到影响下一步决策，中间至少要回答五个问题：

表 2 / Table 2 · 2. 从“工具（Tool）报错”拆出五种不同问题
层次本题具体问题相应失败应检查的位置
发现（Discovery）模型（Model）能否找到有关能力？搜索没有返回所需定义能力目录与连接状态
请求（Request）输入是否指向正确对象？一个空格路径被拆成两个参数工具名、字段与参数边界
决策（Decision）当前调用是否允许？匹配拒绝（Deny）或需要询问（Ask）权限规则（Permission Rule）与相关钩子（Hook）
执行（Execution）进程实际上能访问什么？命令已启动，但文件或网络访问被限制对应执行环境与沙箱（Sandbox）
反馈（Feedback）返回内容说明了什么？断言失败，或远端超时后未知效果（Unknown Effect）真实输出、目标现态与后续检查

这五层解释了为什么同一句“工具（Tool）报错”不足以决定重试（Retry）。找不到定义不等于业务对象不存在；认证（Authentication）失败也不等于查询结果为空；超时不一定意味着远端没有处理请求。

工具（Tool）接口越通用，参数中承载的语义越多。Bash(command) 可以读取文件、运行测试、修改仓库或连接网络。允许 Bash 与允许本次测试的授权粒度不同。 前者开放一种执行入口，后者仍依赖具体命令、被加载的脚本和运行环境。

3. 权限规则（Permission Rule）：具体允许（Allow）为何不能覆盖拒绝（Deny）？

Claude Code 的权限规则（Permission Rule）按拒绝（Deny）、询问（Ask）、允许（Allow）顺序判断。匹配得更具体，不改变这项顺序；它由产品执行，项目说明主要影响模型（Model）尝试什么。

下面保留一份教学配置片段。它把经常使用的确切测试命令放入允许（Allow），把提交放入询问（Ask），把两类发布入口放入拒绝（Deny）；它没有表达所有可能的上传路径。

{
  "permissions": {
    "allow": ["Bash(python -m pytest tests/test_scan.py)"],
    "ask": ["Bash(git commit *)"],
    "deny": ["Bash(git push *)", "mcp__publisher__publish_report"]
  }
}

用同一配置走四个判断：

表 3 / Table 3 · 3. 权限规则（Permission Rule）：具体允许（Allow）为何不能覆盖拒绝（Deny）？
候选输入匹配关系与结果
python -m pytest tests/test_scan.py原精确命令属于允许（Allow）规则
同一命令再增加参数已不是原精确字符串，应重新匹配；不能继承刚才的判断
git commit -m ...匹配询问（Ask），由对应权限（Permission）流程处理
mcp__publisher__publish_report工具名匹配拒绝（Deny），不能因为发现它就使用

若另加 deny: ["Bash"]，精确测试也不能靠原允许（Allow）规则成为例外；裸工具名的拒绝（Deny）还会将该工具从模型（Model）的可见目录中移除。规则设计不能依赖“先广泛禁止，再用更具体允许绕回去”。

这里仍有两个边界。第一，Bash(git push *) 是命令匹配规则，不是“任何形式的发布”证明；换一种程序或命令写法可能属于不同匹配对象。第二，测试脚本本身可以连接网络或写文件，工具名叫测试不保证其效果（Effect）只有测试。若目标是禁止任何未经授权的外传，必须核对实际出站路径与数据范围。

问题：已经允许读取项目，为何还不必反复询问同一范围内的读取？

参考答案。 有效授权已经覆盖该动作时，重复确认不能增加执行边界。需要核对的是目标、范围和条件是否仍成立；当参数变化或将读取内容发送到远端时，才出现需要另外判断的行为。

4. 前置钩子（PreToolUse Hook）：最终输入才是检查对象

假设某个文件工具（File Tool）接收路径与内容两个字段。前置钩子（PreToolUse Hook）发现路径不合要求，可以拒绝，也可能按预先定义的规则改写目标。公开字段 updatedInput 替换整个输入对象，不是自动合并一两个字段；后续权限（Permission）检查针对改写后的输入。

因此，“把路径改到允许目录”仍有两个必要条件：新对象保留工具必需字段；最终目标仍符合当前任务。漏掉内容字段可能导致参数校验失败，只核原路径则可能批准了与实际执行不同的对象。后续检查不能因为输入来自钩子（Hook）就省略。

先讲检查框架，再看伪代码

下面是自拟文件写入检查算法。输入是候选事件（Event）与可信工作范围；输出是拒绝（Deny）及原因，或“不作决定”。它分三步：识别是否属于本检查、解析实际目标、核对任务范围。路径解析、符号链接（Symbolic Link）、并发变化和平台处理尚未实现，不能直接部署。

receive event
# 只处理本检查覆盖的写入事件；不匹配不等于批准。
if event is not a file-write candidate:
    return no decision

# 可信工作范围不能由待检查的参数自行指定。
target = resolve target under trusted workspace
if target cannot be resolved safely:
    deny with actionable reason
if target is outside the allowed task files:
    deny and explain the allowed scope
otherwise:
    return no decision; continue normal permission evaluation

这里的“不作决定”让正常权限（Permission）流程继续，并不是允许（Allow）。在扫描器修复题里，范围集合是实现、必要回归测试和 README；前面的报告变体则有另一份明确允许的产物范围，不能混用两者。

算法不使用“字符串包含 src/”作为通过条件。src/../private/、别名和符号链接（Symbolic Link）会让文本路径与实际对象不同；检查以后到执行以前，链接还可能改变。强约束需要尽量落实到实际使用资源时仍成立的位置，第34章继续解释。

如何把拒绝（Deny）交给宿主（Host）

下列教学返回值只表达“检查已经得出拒绝”，并不执行上面的检查。外层字段选择事件（Event）专用输出，事件（Event）名指向 PreToolUse，后两项给出决定与可理解的原因：

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "本任务只允许修改扫描器、相关回归测试及 README"
  }
}

这段返回值应与实际触发的事件（Event）相连。配置被加载、目标调用匹配、处理程序成功运行、宿主（Host）收到决定，是不同环节；文件里写了钩子（Hook）不证明它保护了目标写入。生产实现还需处理空输入、解析失败、超时，以及检查程序本身可能产生的效果（Effect），不能把这些失败伪装成成功决定。

5. 沙箱（Sandbox）：约束的是具体执行路径

假设已允许测试。若测试内部尝试把日志上传，前面的命令匹配未必足以发现；执行时还需要限制其网络能力。Claude Code 的 Bash 沙箱（Sandbox）通过操作系统（Operating System，OS）机制限制命令及子进程的文件和网络访问。

但同一产品还有内置文件工具（File Tool），以及通过模型上下文协议（Model Context Protocol，MCP）连接外部能力的客户端（Client）。它们可以到达不同资源，不能把所有路径圈进同一个 Bash 沙箱（Sandbox）。

图中只把启用且生效的 Bash 路径画进边界。测试进程上传日志可能触及本机网络限制，经模型上下文协议（MCP）发起的远端发布则由另一条路径产生效果（Effect）。通过标准输入/输出（Standard Input/Output，stdio）通信的本地模型上下文协议（MCP）服务，也要按真实启动与运行方式检查隔离（Isolation），不能因“它也在本机”就归入 Bash 子进程。

初始化失败与无沙箱重试（Unsandboxed Retry）是两个问题

以下仍是参考配置，未安装到任何项目。它希望启用沙箱（Sandbox）、在初始化不可用时停止，并关闭模型（Model）请求无沙箱重试（Unsandboxed Retry）的入口：

{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false
  }
}

failIfUnavailable 针对依赖缺失或平台不支持导致的启动问题；allowUnsandboxedCommands: false 则让 dangerouslyDisableSandbox 不能成为失败后的逃生口。两项不可互相代替。

这份配置仍不是“所有执行都被覆盖”的证明。显式排除项、其他工具路径、平台与设置来源要分别核对。若测试因网络受限而失败，应先确认它是否需要网络、目标是否属于任务，考虑离线样例或既有策略允许的访问；失败本身不提供扩权理由。后端（Backend）与代理（Proxy）怎样落实限制，下一章继续展开。

6. 工具发现（Tool Discovery）：找到能力以后还差哪些条件？

当外部工具很多时，每次模型（Model）请求都携带完整定义会挤占上下文（Context）。Claude Code 的工具搜索（Tool Search）可延迟装入模型上下文协议（MCP）的工具定义，具体条件依赖模型（Model）、配置和模型服务提供方（Provider）。减少定义装载成本，不改变实际调用的权限（Permission）。

表 4 / Table 4 · 6. 工具发现（Tool Discovery）：找到能力以后还差哪些条件？
本轮观察已经知道什么仍然不知道什么
搜索返回 get_report 定义找到了相关能力是否有权访问，目标数据是否存在
没有搜索到相关工具当前发现路径未返回合适结果整个产品是否永远不支持它
调用时认证（Authentication）失败当前连接或身份（Identity）不能完成调用业务对象是否不存在

因而，工具发现（Tool Discovery）需要描述适用任务，工具定义需要说明输入输出，执行阶段还要核对有效身份（Identity）与权限（Permission）。语义相关性不能直接推导成访问授权。

回到本章“不发布”的限制：publish_report 被找到，只增加一个候选能力，不会改变用户范围。若外部工具返回量很大，还需有界摘要（Summary）和后续读取入口；搜索省下了定义、查询却每次取回整库数据，整项任务仍可能耗尽上下文（Context）。

7. 把正常修复与三种失败连起来

正常扫描器修复依次使用已有授权：读取当前文件和失败，基于实际内容编辑，运行确切测试，再检查差异，并向用户给出本地修复报告。路径字段保留自己的边界；含空格不要求压成命令字符串。调查没有发现必须修改的内容，就无需为了流程完整而强行编辑；测试通过以后，不发布的限制仍然生效。

三种条件变化会改变后续动作。第三项另设用户明确允许创建一次远端报告的变体，不扩大原题的发布范围：

表 5 / Table 5 · 7. 把正常修复与三种失败连起来
变化应保留的事实后续处理
文件写出后，格式化钩子（Hook）失败写入效果（Effect）已经发生，事后处理失败读取现态与相关日志，再补修；不能说此前未执行
前置钩子（PreToolUse Hook）改写输入，遗漏必要字段最终参数与原提案不同，可能不满足工具格式补全必要字段并重新检查；不能假设自动局部合并
远端创建报告后超时回执缺席，未知效果（Unknown Effect）按稳定业务标识查询，再决定补发、补偿（Compensation）或报告限制

最后一行是本课程希望系统闭合的恢复（Recovery）责任，不宣称 Claude Code 已有某个内部幂等协议。用户取消时同样先区分：尚未发送的调用可阻止，已发生的效果（Effect）要检查，无法查询的远端结果保持未知。取消（Cancellation）不会使时间倒流。

少询问、强边界与可恢复性各有代价。精确允许（Allow）减少重复交互，但参数变化要重新匹配；动态钩子（Hook）更灵活，却增加自身出错和漏匹配的可能；沙箱（Sandbox）需要平台支持和资源配置；事后验证（Post-execution Verification）能检查质量，但失败发生时可能已经需要补救。理解各自位置，才能解释它们为何同时存在。

8. 场景问答：从观察得出有限结论

问题 1。 后置钩子（PostToolUse Hook）返回 block，是否可以报告“远端报告未发布”？

参考答案。 不能。它是在成功执行后的反馈，应查询远端实际状态。已发布时，撤回需要另外受支持且获授权的操作；当前反馈没有自动回滚（Rollback）能力。

问题 2。 一个广泛拒绝（Deny）与精确允许（Allow）同时匹配，哪个决定结果？

参考答案。 拒绝（Deny）优先，具体程度不能构成例外。需要重新设计规则；不能用其它权限模式（Permission Mode）或钩子（Hook）的存在忽略已经匹配的拒绝（Deny）。

问题 3。 为什么只检查 Edit 无法保证某文件不被修改？

参考答案。 Bash、其他内置工具、外部进程或另一个会话（Session）都可能写它。钩子（Hook）的匹配范围与真实写路径不相同，必须由实际执行层落实所需边界。

问题 4。 怎样判断文件写入检查真的生效？

参考答案。 需要把配置加载、事件（Event）匹配、最终输入、决定和文件现态连起来。允许动作、越界目标、错误输入及检查程序失败分别对应不同观察；只看到“已配置”不够。这是判断依据，不能据本章未执行的配置声称已有运行验证。

问题 5。 若任务改成只读数据库分析，哪些限制要重新表达？

参考答案。 在数据库工具和远端身份（Identity）上选择只读能力与必要表范围，限制查询量和返回字段。本地 Bash 沙箱（Sandbox）只约束自己的路径；查询取消（Cancellation）仍需结合服务端状态，结果进入上下文（Context）后也只是数据，不提供新的授权。
