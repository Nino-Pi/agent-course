第 51 章｜读取（Read）、编辑（Edit）与命令执行（Bash）的资源合同

本章概览

核心问题：大文件、并发修改和长日志出现时，怎样让工具结果仍能支持可靠的下一步？

关键概念：一致观察（Consistent Observation）把内容与观察版本（Observed Version）绑定；游标（Cursor）记录有界续读位置；纯变换（Pure Transformation）只计算候选文本；条件提交（Conditional Commit）由资源负责者（Resource Owner）检查并写入。进程生命周期（Process Lifecycle）管理启动、输出、停止与退出。

关系主线：先知道看到了哪一版，再决定能否写入；命令结束后仍分别判断进程（Process）状态、输出覆盖和实际效果（Effect）。

前情回顾：工具合同（Tool Contract）还需要资源层落实

第50章把模型（Model）提出的参数与可信执行上下文（Execution Context）分开：EditArgs 表达改哪里、依据哪一版，ToolContext 注入工作区（Workspace）、调用身份（Identity）和执行边界（Execution Boundary）。类型声明让请求可读，不能自行阻止越权或并发覆盖。

第16章解释过，旧片段能匹配，只说明当前文本存在这个片段；它不能证明整份文件自上次读取以来没变。第18章进一步区分效果（Effect）和回执（Receipt）：文件可能已写、结果却尚未保存。因此本章分别设计读取前提、提交边界和进程（Process）观察；下一章再处理持久记录失败。

这里的接口（Interface）、版本（Version）和状态（State）属于教学设计。它们用来说明一份较强合同需要什么，不能直接当作 Maka 默认工具已有的保证。

先固定任务，再选择最小能力

沿用第04章四文件测试夹具（Fixture）：修正 src/duration.js 中 seconds % 100 的计算，并把 README 的测试入口改对。任务允许修改这两处，保留测试断言与用户其他改动；这不是第38章禁止改 README 的 Python 扫描器场景。

本题只处理允许工作区（Workspace）中的文本文件：读取（Read）有范围与输出上限，编辑（Edit）默认单文件单片段，命令执行（Bash）使用可信的当前工作目录（Current Working Directory，cwd）和执行边界（Execution Boundary）。文件编码、大小、竞争写入者以及子进程（Child Process）、网络能力，都属于合同条件。

最小方案不必立即引入抽象语法树（Abstract Syntax Tree，AST）编辑器。先把一个精确目标做可靠，比用全局替换掩盖歧义更容易判断。复杂结构何时值得加入，留到最后的大单行例子比较。

读取（Read）：内容和版本必须来自同一观察

假设先查到版本 v7，用户随即改成 v8，再读取内容。如果返回“v7 的内容”却装入 v8 文本，下一次条件提交（Conditional Commit）就失去了明确含义。一致观察（Consistent Observation）要求两者属于同一份材料，而不是各自看起来合理。

下面先读请求的两种形式，再看结果中的范围、版本和续读信息。路径/范围发起新观察，游标（Cursor）延续已有观察；不能将两种请求混合。

type ReadArgs =
  | { path: string; startLine?: number; lineCount?: number }
  | { continuationCursor: string }
type ReadResult = {
  path: string
  observedVersion: string
  startLine: number
  endLine: number
  text: string
  truncated: boolean
  continuationCursor?: string
}

本题 startLine 从 1 开始，lineCount 为正整数；省略范围表示从头读取，仍受输出预算（Output Budget）约束。这与第37章 Maka Read.offset 从0开始的接口不同。运行时（Runtime）还须校验字段组合，不能只靠 TypeScript 联合类型拒绝混入的新路径。

实现按“参数与预算（Budget）→规范化目标与权限（Permission）→一致内容与版本→范围选择→有界结果”推进。资源负责者（Resource Owner）可以提供快照（Snapshot）读取；若直接面对普通文件系统，则要说明采用共同锁保护、变化检测后重读，还是较弱的观察保证。先 stat 后 read 之间可能变化；一次普通读取也不会自动冻结并发写入。

行范围与字节预算（Byte Budget）解决不同问题

行数限制不等于输出大小限制：一行可以很长。文本若采用八位 Unicode 转换格式（Unicode Transformation Format–8，UTF-8），截断应停在完整字符的编码边界；二进制或无法可靠解释的编码应返回明确结果，让调用者选择适当工具。

把一次选定范围对应的快照（Snapshot）字节数记为 LLL，第 iii 块覆盖从 bib_ibi​ 开始、到 bi+1b_{i+1}bi+1​ 之前的字节，单块上限为 BBB。完整续读应满足：

0=b0<b1<⋯<bn=L,bi+1−bi≤B.0=b_0<b_1<\cdots<b_n=L,\qquad b_{i+1}-b_i\le B.0=b0​<b1​<⋯<bn​=L,bi+1​−bi​≤B.

这里的零点是选定范围起点，不是承诺从文件开头读取。相邻块共用一个边界，避免遗漏或重复；每个 bib_ibi​ 又要落在有效编码边界。空范围直接结束；若剩余预算（Budget）连一个完整字符都容不下，应调整允许的块大小或明确拒绝，不能返回无进展的游标（Cursor）让调用者无限循环。这是读取合同的教学表达，不是现有工具的分块算法。

startLine/endLine 只说明片段涉及哪些行，不保证首尾行完整。返回第10–30行，也不表示已经看过全文件。truncated 表示本次请求范围仍有内容未返回；用户主动只读一段，不等于工具截断了整个文件。

游标（Cursor）：续同一份材料，而不是拼接新旧内容

continuationCursor 是负责者（Owner）发出的不透明标记，绑定目标身份（Identity）、观察版本（Observed Version）、请求范围及下一个未返回字节的位置。它可以落在行内，但必须满足编码边界。后续只传这个标记，由负责者（Owner）重新校验当前权限（Permission），再延续同一份观察。

快照（Snapshot）已释放，或只剩当前文件而版本已变，就返回 stale_observation，要求重新读取。不能为了“续完”把 v7 的开头与 v8 的末尾拼接。若请求范围未读完，结果应提供可用游标（Cursor），或明确续读不可用；不能只留下 truncated: true 却没有处理方向。

路径也有身份（Identity）问题：别名或符号链接（Symbolic Link）可能指向别处，不能只检查字符串是否以工作区（Workspace）名称开头。授权（Authorization）最终要约束实际对象。

编辑（Edit）：纯变换（Pure Transformation）与条件提交（Conditional Commit）

读取建立前提，纯变换（Pure Transformation）计算“如果前提仍成立，下一内容是什么”，条件提交（Conditional Commit）才接受真实写入。唯一匹配与版本一致是两项独立判断：旧片段仍唯一存在，文件其他部分也可能已经被人改过。

图中从取得当前目标到接受新内容，必须属于同一受保护操作：资源负责者（Resource Owner）原子检查并提交，或同一把锁覆盖检查、计算与写入。初次授权定位与最终执行之间若有等待，还要落实提交时适用的执行边界（Execution Boundary），不能把旧许可视为永久有效。

版本冲突和目标歧义在写入前拒绝，表示没有接受本次变更。生成新字符串则只完成计算，不能据此报告文件已改。写入后回执（Receipt）丢失的未知效果（Unknown Effect），由下一章接着处理。

先按职责读条件提交（Conditional Commit）的骨架

沿用第50章 EditArgs；为 ToolContext 增加 owner，表示管理目标、版本和提交的资源服务。mutateIfVersion 是抽象协议入口：检查目标身份（Identity）及版本、调用纯变换（Pure Transformation）、接受变化必须具有上述受保护语义。它不是 Node.js 现成应用编程接口（Application Programming Interface，API）。

阅读下面代码时，只抓三层：外层校验并定位；中层交出预期版本和调用编号；内层只计算文本。validateEditArgs 要拒绝空旧片段等非法输入；noEffect 仅用于已经能证明未写入的分支。countExactMatches/replaceOnce/makeDiff 是精确计数、一次替换和差异（Diff）构造的抽象辅助函数，不能把它们省略的底层资源协议理解为已经实现。

async function edit(args: EditArgs, ctx: ToolContext) {
  validateEditArgs(args)
  const target = await ctx.owner.resolveAuthorizedTarget(args.path, ctx.boundary)
  return ctx.owner.mutateIfVersion({
    target,
    expectedVersion: args.observedVersion,
    operationId: ctx.callId,
    transform(currentText) { // 纯函数，无 I/O，无第二次工具调用
      const count = countExactMatches(currentText, args.oldText)
      if (count === 0) throw noEffect("target_missing")
      if (count !== 1) throw noEffect("target_ambiguous")
      const nextText = replaceOnce(currentText, args.oldText, args.newText)
      return { nextText, diff: makeDiff(currentText, nextText) }
    }
  })
}

transform 接收负责者（Owner）在提交保护内取得的当前内容，零匹配返回缺失，多匹配返回歧义，唯一时给出候选文本与差异（Diff）。新文本按字面值放入，不把其中的 $& 等字符解释为替换模板。ctx.callId 关联这次调用；它本身不赋予跨调用业务去重能力。

一种实现让全部写入经过同一资源服务，在事务（Transaction）或版本存储内完成比较和提交。另一种用规范化资源身份（Identity）作为共享锁键，锁内重读、比较、计算和写入。后者依赖竞争写入者遵守同一锁；不协作的外部编辑器仍可能改文件。可改用隔离的工作副本（Working Copy）、支持条件写入的服务，或明确保留风险。

为什么原子替换不等于版本保护

原子性（Atomicity）说明一组动作对观察者怎样表现，必须指明这组动作是什么。以 Linux 同一挂载文件系统的 rename 为例，目标路径替换可原子可见；这个接口并未接受“目标仍是 v7”这样的内容版本条件，也不能单凭成功返回推出掉电持久性（Durability）。后者还涉及文件与目录同步及其错误处理。路径替换语义、同步范围。

所以不能用“先比版本，再普通 rename”实现同名接口，然后声称检查和替换已成为一个原子条件。检查与写入之间出现的竞争，需要在同一资源合同内关闭。

同一个编辑（Edit）的正常、陈旧与未知结果

正常教学路径：读取（Read）得到 v7，目标完整行含 seconds % 100；负责者（Owner）当前仍是 v7，唯一匹配后接受为 v8，返回差异（Diff）引用。随后验证60→1:00、125→2:05，并核对测试断言未改。版本和结果是给定推演，不是本批运行。

变化条件：模型（Model）准备期间，用户添加参数检查，当前版本已为 v8。即使旧片段仍唯一存在，本题也拒绝基于 v7 的条件提交（Conditional Commit）。重读后保留用户检查，再提出新编辑。若用户已把 % 100 改成 % 60，可以直接进入验证，不必重做旧动作。

有限容错匹配（Fuzzy Matching）要另定启用条件、范围、唯一性及新文本缩进规则。第16章的 Maka 编辑（Edit）在精确零匹配且守卫通过后才找有限候选；精确多匹配直接拒绝，候选须唯一且跨度合理，new_string 原样写入。它没有本题 observedVersion 参数，不能用片段匹配证明整份文件自上次读取以来没变。

Maka 当前本地执行器（Local Executor）与文件系统执行者（Filesystem Worker）路径还按规范化路径协调写锁，并检查目标对象身份（Identity）。dev/ino 是设备号与索引节点号（Inode），不是内容版本；锁也不会自动覆盖任意命令执行（Bash）、外部编辑器或远端执行器（Executor）。managed_mutation_v1 托管修改（Managed Mutation）是更强基础协议，尚非普通 Write/Edit 的默认保证。

命令执行（Bash）：先分开进程（Process）、输出和效果（Effect）

进程（Process）退出、日志可读、业务效果（Effect）已确认，是三个不同结果。一个测试脚本可以退出0却没运行测试，也可以退出非零前已经写出报告。因此命令执行（Bash）应管理完整进程生命周期（Process Lifecycle），而不是只等待一个字符串。

图中的收束（Settling）指汇集进程（Process）状态、排空可取得输出并形成资源观察。结果待确认（Unknown）表示进程（Process）或效果（Effect）仍无法判定，不表示持久记录提交失败也可当作普通结果继续。第52章的结果结算T2若失败，外层运行时（Runtime）必须停止当前续行；只有可靠保存了这份不确定性，才可能交给后续消费者（Consumer）。

Starting → Running → Settling 是正常方向；超时（Timeout）或取消（Cancellation）先进入停止中（Stopping）。图中没有“已回滚”分支：停止请求不撤销已写文件，用户界面（User Interface，UI）显示 done 也不证明结果已被外层可靠接受。

请求只暴露命令与所需等待时间；结果同时表达进程（Process）、输出和效果（Effect）。退出码（Exit Code）与信号（Signal）仅在相应观察可用时填写，不能用省略字段伪装成0。

type BashRequest = {
  command: string
  timeoutMs: number
}
type BashObservation = {
  operationId: string
  process: "not_started" | "exited" | "status_unknown"
  exitCode?: number
  signal?: string
  stdoutExcerpt: string
  stderrExcerpt: string
  outputTruncated: boolean
  outputRef?: string
  effects: "none" | "known" | "unknown"
}

timeoutMs 是请求上限，实际值仍受可信工具上限和任务剩余时间限制。当前工作目录（Current Working Directory，cwd）、允许的环境变量、网络与文件边界来自可信执行上下文（Execution Context）；命令名叫 npm test 不证明它没有副作用（Side Effect）。

输出要及时读取，展示仍保持有界

工具需要同时排空标准输出（Standard Output，stdout）与标准错误（Standard Error，stderr）。只读其中一个，另一管道可能写满并让子进程（Child Process）阻塞；管道容量也不是应用可假定的固定常数。管道容量与读取要求。

保存完整输出和展示给模型（Model）也应分开。前者仍有磁盘预算（Budget）、保留期限与清理策略（Policy），不能用“归档”转移无界增长；后者优先保留退出依据、结构化失败项、首尾片段和可回读（Readback）引用。只取最后100行可能丢失位于中间的唯一断言。

超时（Timeout）或取消（Cancellation）后，先请求停止，再按平台能力处理进程组（Process Group）与子进程（Child Process），并给收敛设置有限等待。后台进程（Background Process）能脱离控制时，要保留这个缺口。父进程（Parent Process）退出不能证明全部工作已停止；无法确认时返回查询方向，已知非零退出则保留诊断。

命令执行（Bash）的三条走读

正常。 先从 package.json 的 scripts 确认 npm test，启动并收集输出；假设观察到进程（Process）退出0、四个用例通过，返回检查范围与日志引用。它只支持这组检查，不能自动证明所有输入或 README 改动都正确。

入口错误。 npm run check 返回 missing script、退出码（Exit Code）1。命令已经执行，测试入口却不对；先重读配置，不因此修改函数或扩大权限（Permission）。这是教学给定结果，不是此刻执行的命令日志。

日志过长。 输出持续增长，模型（Model）只见首段、尾部错误、截断标记和日志引用；关键断言若在中间，应能据引用补回。超时（Timeout）时停止并核对进程（Process）状态，保留已捕获结果。测试此前写出的报告不会因取消（Cancellation）删除；若另有经授权的远端作业（Job），还要查远端状态，不能从本机退出推断它结束。

40 MB 单行结构化数据：完整读取与修改方案

另设一个文本场景：40 MB 的八位 Unicode 转换格式（UTF-8）文件采用 JavaScript 对象表示法（JavaScript Object Notation，JSON），只有一行，目标是修改根对象的 timeout。lineCount=1 不限制返回字节，前8 KB又未必含目标。使用绑定版本和下一字节位置的游标（Cursor）；把下一行设成2，会跳过同一行剩余内容。

读取器按字节预算（Byte Budget）在有效字符边界返回。定位目标可以使用有界流式解析器，或让隔离执行器（Executor）在资源预算（Budget）内完整解析。多个层级都有 timeout 时，用结构路径区分；同一根对象出现重复键时也须定义拒绝或处理规则，不能靠全局文本替换猜测意图。解析失败或目标歧义，在写入前明确拒绝。

提交仍基于同一观察版本（Observed Version）：读时v7、当前v8则重新观察。成功后返回新版本、目标前后值和有界差异（Diff），再检查格式可解析及程序行为。保留原格式与重新序列化会产生不同变化范围，须在合同中选择；仅知道解析成功，也不等于相关行为正确。

并发保护（Concurrency）统一负责者（Owner）的条件提交（Conditional Commit）独立工作副本（Working Copy）最后集成，仍可能冲突陈旧版本拒绝、用户改动保留、最终差异（Diff）
大输出（Large Output）短结果直接返回有界投影（Projection）与归档回读（Readback）增加存储/查询成本诊断所需证据、引用可用性与预算（Budget）
测试触发（Test Trigger）模型（Model）依任务选检查固定检查阶段可能漏范围或多次重复错入口、漏测、开销与改动范围

完整方案先建立共同身份（Identity）、权限（Permission）、取消（Cancellation）与结果合同，再分别落实资源语义。读取（Read）给出一致且有界的前提；编辑（Edit）把纯变换（Pure Transformation）交给真正能检查并写入的负责者（Owner）；命令执行（Bash）观察进程（Process）及输出，分别报告已知状态与未知效果（Unknown Effect）。最后检查实际变化与任务要求，而不只看终态（Terminal State）名称。

验证这份设计，应包含零/一/多匹配、读取后并发变化、等待中路径替换、超长单行、错误在日志中段、取消（Cancellation）带子进程（Child Process）的命令、效果（Effect）后回执（Receipt）丢失。每个场景同时记录资源和工具结果。这里给出验证范围，未把这些实验称为已经运行。

两位智能代理（Agent）各持一把进程内锁（In-Process Lock），能防覆盖吗？

不能。互斥锁（Mutex）要共享资源身份（Identity）并覆盖实际竞争者；各自的一把锁互不协调。统一服务的条件提交（Conditional Commit）或独立工作副本（Working Copy）再集成解决不同问题，后者仍需处理冲突。

读取返回内容摘要（Hash），写前再比较一次就够吗？

若比较与写入之间仍有竞争窗口，就不够。内容摘要（Hash）表达内容条件，不能自行建立原子性（Atomicity），也不代表对象身份（Identity）、元数据（Metadata）或跨文件事务（Transaction）。

只保留日志最后100行可以吗？

可以作为初始投影（Projection），不能保证关键诊断在场。保留结构化失败项、退出依据、首尾片段及回读（Readback）入口，并检查“断言恰在中间”的情况。

退出码（Exit Code）0可以直接称为 succeeded 吗？

工具可以记录进程（Process）正常退出，业务合同还要看脚本是否吞掉错误、测试是否真的运行、预期产物和检查范围。高价值场景可加专用结果解析，不能把一个数字当整体正确性证明。

取消（Cancellation）后可以自动重跑吗？

先查是否启动、原进程（Process）是否仍在、哪些效果（Effect）已经发生。已知安全的读取或已停止且可重跑的检查可以按当前条件决定；编辑（Edit）、发布或远端提交不能只凭取消（Cancellation）就假定无效果（Effect）。
