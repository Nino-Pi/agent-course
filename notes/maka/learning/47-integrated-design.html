第 47 章｜跨模块综合设计

本章概览

核心问题：把工具（Tool）、记忆（Memory）、协作（Collaboration）和恢复（Recovery）接入同一任务后，怎样保住用户要求并判断真正交付？

关键概念：负责者（Owner）持有决定权；修订（Revision）标识当前要求；条件编辑（Conditional Edit）在资源前提仍成立时提交；未知效果（Unknown Effect）表示结果尚未确认；采纳（Adoption）由父任务（Parent Task）检查并使用子产物。

关系主线：以代码修复串起输入、执行、保存和验收（Acceptance），再迁移到购买与报名。各组件的局部成功必须连接到同一份任务合同（Task Contract）；当前授权、业务效果、通知（Notification）质量与费用分别判断。

前情回顾：局部成功怎样成为整项任务的证据

第28章用负责者（Owner）与消费者（Consumer）解释组件连接：谁能决定写文件，与谁根据结果决定下一步，可能不是同一组件。第31章把工具合同（Tool Contract）放到执行入口：模型（Model）提出参数，可信程序核对当前范围和资源条件，再产生效果（Effect）。

第36章区分原始事实、当前模型输入（Model Input）与长期记忆（Long-Term Memory）：保存了某条要求，并不保证下一次请求已经选入它。第39章进一步区分委派（Delegation）与采纳（Adoption）：子任务（Subtask）完成后，父任务（Parent Task）仍须找到产物、处理冲突并作整体检查。

第40章要求固定评价单位与完整成本（Total Cost）；第44章提醒我们，恢复（Recovery）控制程序时，还要核对外部效果（Effect）。本章用这些关系回答一个新问题：当“子产物尚未采纳（Adoption）”和“父任务（Parent Task）的一次编辑结果未知”同时出现时，究竟还能确定什么？

先读代码修复主线，再看购买与报名如何复用同一原理。三个案例都有独立、完整的条件；后两个无需借用真实账户或执行操作来理解。

1. 先连接决定权、记录与验收（Acceptance）

模块连接产生四个具体问题：谁接纳工作，哪些记录让下一步可见，未知效果（Unknown Effect）由谁处理，怎样判断最终交付？下面的参考方案把第26章设计分析示例中的身份、状态与判定扩展到一项完整任务。实现事实与额外设计分别标明，避免把更强的参考合同当成产品现状。

在连接这些模块前，完整项目还有两个外层入口：开始时建立项目工作环境，中断后通过工作交接重新确认现状。它们给内部循环提供可用的起点，也让已经产生的结果能服务下一次工作。

2. 固定代码修复的输入与五轮条件

基础任务仍是修 README 测试步骤、修复 formatDuration(125) 的错误输出、运行相关测试并中文汇报。现在项目中存在大量日志和用户自己的未完成编辑。允许多种满足约束的设计，不要求复制 Maka 的命名或照抄某个产品。

为后面的输入保真（Input Fidelity）与故障分析固定两条用户消息，U1/U2 是本例的输入标记：

  • U1，原始完整修复请求：“修正 README 中的测试步骤，修复 src/duration.js 的 formatDuration，使 125 秒输出 2:05 并符合一般的分秒转换规则；运行相关测试，最后用中文说明修改、结果与未完成项。”
  • U2，在第一次编辑前新增的约束：“保留我已有和随后新增的内容，不要覆盖我的未完成编辑；只允许修改 README 和 src/duration.js，不要修改测试文件。”

后续用户修订（Revision）优先于旧动作所依据的范围。例如用户再说“改为只读检查”，就不能凭 U1/U2 继续执行旧编辑，必须按最新范围重新判断；已经开始的效果另行核对。下文“忘了 U2”具体指丢失了保留用户内容、限定两个可改文件或禁止修改测试的约束，不能只凭输出正确就算任务成功。

3. 先读状态含义，再沿流程追踪消费者（Consumer）

下图中的建立、读取、执行与验收（Acceptance）都是动作，箭头表示工作怎样推进。流程所依赖的状态由图后的 RepairState 字段和完整初值表达，不能只凭走到某个动作节点就推断文件效果或任务已经成功。

这张图中的负责者（Owner）可以具体分工：任务协调者（Task Coordinator）持有 U1/U2 的当前修订（Revision），接纳模型工作与委派（Delegation）；工具执行器（Tool Executor）检查当前许可和资源前提，产生文件效果；结果存储保留成功、失败或未知；父任务（Parent Task）依据产物与检查结果决定是否交付。等待批准（Approval）或子结果时，任务仍未完成；停止检查（Stop Check）位于下一次接纳与实际提交之前，已开始的效果另行结算。

下面的教学接口先分三组读：taskId 和 revision 关联同一任务与当前要求；allowedWrites、preserveUserEdits、stopped 约束下一动作；editId、effect、verification 分别追踪一项编辑和验收（Acceptance）证据。它不是 Maka 应用编程接口（Application Programming Interface，API）。

图里的协调者消费当前要求，执行器（Executor）消费许可和资源前提，验收（Acceptance）逻辑消费文件现态与测试结果。effect 只描述当前 editId 的编辑，不是所有文件的总状态；切换到下一项编辑时，必须保留前一项记录，再关联新的身份。

type RepairState = {
  // 身份与当前要求由可信协调者维护。
  taskId: string;
  revision: number;
  // 接纳和提交时都要复核的限制。
  allowedWrites: string[];
  preserveUserEdits: boolean;
  stopped: boolean;
  // 一项编辑的效果，与测试结论分别记录。
  editId: string;
  effect: "not_started" | "unknown" | "confirmed";
  verification: "not_run" | "failed" | "passed";
};
const initial: RepairState = {
  taskId: "repair-17", revision: 2,
  allowedWrites: ["README.md", "src/duration.js"],
  preserveUserEdits: true, stopped: false,
  editId: "repair-17/duration/edit-1",
  effect: "not_started", verification: "not_run",
};

若编辑已发生但回执丢失，只把该编辑的 effect 改为 unknown，不将它写成 not_started。若用户随后改为只读，协调者保存新修订（Revision）并清空可写范围；旧编辑若尚未提交就被拒绝，若已发生则保留效果并重新核对。

模型（Model）若在长调用之后返回新动作，而用户已经停止，必须重新检查准入。若效果已开始，停止新动作与结算旧效果属于两件事。

4. 五轮推演：每次新增一个必要合同

第一轮：保护并发修改

参考方案采用绑定观察版本的条件编辑（Conditional Edit），运行时（Runtime）提供可信工作范围。版本按文件维护：例如读取 README 的 v7 后，用户新增段落成为 v8，旧 v7 编辑被拒绝；重新读取 v8 后，补丁（Patch）保留新增段落并修正测试命令，由资源负责者（Resource Owner）在同一边界检查 v8 并提交该文件的 v9。src/duration.js 另行读取和检查自己的内容版本，再提交 % 100 → % 60；两项编辑分别保存结果，不假设跨文件原子提交（Atomic Commit）。

这个内容版本合同强于 Maka 普通编辑工具（Edit）的对象身份检查，不能当成其现有的读取版本比较并交换（Read-Version Compare-and-Swap，Read-Version CAS）。测试结果区分未启动、断言失败与成功；退出码 0 但没有实际测试仍不满足验收（Acceptance）。

第二轮：预算（Budget）如何约束模型输入（Model Input）

沿用第36章的教学预算（Budget）。这里 k=1000k=1000k=1000，单位均为词元（Token）；共享窗口 B=32kB=32kB=32k，为输出保留 O=4kO=4kO=4k，固定协议与工具等占 F=6kF=6kF=6k，安全余量 H=2kH=2kH=2k。可给动态材料的空间 DDD 为：

D=B−O−F−H=(32−4−6−2)k=20k.D=B-O-F-H=(32-4-6-2)k=20k.D=B−O−F−H=(32−4−6−2)k=20k.

U1/U2 占 1k1k1k、相关代码 6k6k6k、既有失败结果 4k4k4k、旧调查摘要（Summary） 5k5k5k、未结束调用的当前材料 3k3k3k。已选材料 LLL 与剩余空间 RRR 分别为：

L=(1+6+4+5+3)k=19k,R=D−L=1k.L=(1+6+4+5+3)k=19k,\qquad R=D-L=1k.L=(1+6+4+5+3)k=19k,R=D−L=1k.

这些是给定估算，未来工具结果尚未产生，不能当成已装入。剩余 1k1k1k 也不是允许任何长度结果进入的承诺：新结果超过它时，要重新整理或有界读取。摘要（Summary）保留原材料入口，未结束调用保持真实待处理（Pending），不伪造配对结果。压缩（Compaction）失败不能删掉 U2 换取表面成功。

第三轮：从保存偏好到实际使用

把工作区例外与全局默认分成可更新的状态；撤回例外后重新采用全局默认。分别记录写入是否发生、当前任务是否读取、是否进入请求以及回答是否遵循。当前任务的一次要求不自动变成永久偏好。

第四轮：子产物怎样进入最终结果

传给子任务（Subtask）的是足够完成限定目标的上下文（Context）；工具范围与文件范围单独定义。子任务（Subtask）交付产物和检查记录，父任务（Parent Task）检查冲突、采纳（Adoption）并做整体复测。断线恢复（Recovery）从运行事实重建当前投影（Projection），不从用户界面（User Interface，UI）空白推断工作不存在。

多个故障同时出现时，局部结论不能替整个状态下结论。例如子代理（Subagent）的补丁（Patch）尚未合入，只说明父文件没有经这次采纳（Adoption）改变；若父任务（Parent Task）自己的编辑工具（Edit）同时处于未知效果（Unknown Effect），就仍不能断言父文件未变，须按文件与操作分别查询。付款也一样：“尚未确认发生”不等于“已确认没有发生”；超时后的计划表必须保留未知，不能为了填满状态栏改写成未执行。

第五轮：结果缺失时保留原操作身份

接纳、认领（Claim）和派发保留稳定身份。已经发生但不确定的效果需要查询或明确的幂等（Idempotency）合同；无法查询时保留未知，避免伪造确定状态。总预算（Budget）包含父任务（Parent Task）和子任务（Subtask）、重试和恢复（Recovery）成本。

替代方案可以更简单：完全串行减少交接开销；独立工作副本（Working Copy）加人工合并减少直接覆盖，却增加采纳（Adoption）成本；仅保存明确偏好配置减少自动提取错误，却不自动积累经历。它们是否适合，取决于任务规模、失败代价和需要复用的信息。

11. 实现与相邻原理：九组直接问答

下面四组问答沿已讲过的真实实现展开。公开材料没有披露的内部状态仍保留未知；参考设计与产品现状分别说明。

四类实现问题与因果解释

已知入口在命令行接口（Command-Line Interface，CLI），Aider 为什么会把一个依赖文件放进仓库图（RepoMap）？动态插件又会漏什么？

静态解析先提取定义与引用，建立文件间的关联。已知聊天文件（Chat File）和标识符（Identifier）参与个性化关注，页面排名算法（PageRank）将权重沿关系传播，再选择相关定义并受词元（Token）预算（Budget）约束。因此一个依赖文件可以通过引用关系获得排名，但不保证其全文进入最终输入。运行时（Runtime）拼接出来的插件名可能没有对应静态引用边；此时需要读取配置、加载逻辑或运行观察结果（Observation）补充线索。单纯扩大图排序预算（Budget）不能生成原本没有提取出的动态关系。详细过程见第37章。

同一个脚本的 open/read/connect，在原生沙箱（Sandbox）、gVisor 和微型虚拟机（microVM）中分别经过哪里？

原生进程最终使用宿主内核，由对应平台的隔离和访问策略约束资源请求。gVisor 的 Sentry 在用户态实现大量应用可见的系统调用语义，文件和网络访问再经过受控的宿主接口；文件通道还涉及配置的 gofer 等组件。微型虚拟机（microVM）内的应用先请求来宾内核（Guest Kernel），需要外部资源时再通过虚拟设备与宿主侧后端交互，不能把每次应用系统调用都画成直接调用宿主内核。三者的文件挂载、网络出口和允许资源仍需明确配置，执行边界本身不会替用户决定哪些目录可写。详见第34章。

并行调查一个节点（Node）成功、另一个失败，重启后重做什么？发布已经成功却丢回执又怎样？

在 LangGraph 相应持久化（Persistence）配置与恢复（Recovery）路径中，已保存的待合并写入（Pending Writes）可保留同一超级步（Superstep）中成功节点（Node）的输出，恢复（Recovery）时继续失败节点（Node）；未持久保存的结果不能凭空复用。Temporal 则依据事件历史（Event History）重放（Replay）工作流（Workflow）决策，已记录的活动（Activity）结果可用于重建状态。两者都不能仅凭本地记录缺失就证明外部发布未发生：活动（Activity）或节点（Node）的效果已经发生而完成结果未记录时，重试可能再次触发效果，需要业务幂等（Idempotency）、查询或未知状态处理。持久化恢复（Recovery）单位与外部业务效果是两层合同，见第44章。

全局中文、项目 A 英文，随后撤回 A 例外，输入应怎样变化？

先分别保存全局默认与项目例外；在 A 中选择仍有效的英文例外，在其他项目使用中文默认。撤回 A 例外后，使该条规则失效，下一次输入回到中文，而不是把全局默认永久覆盖为英文。真实实现还必须有作用域过滤和实际读取步骤：Maka Local 的工作区作用域（Workspace Scope）不等于按当前工作目录（cwd）自动隔离项目，分项目状态根（State Root）是额外部署条件；Codex 的后台记忆（Memory）流程也有选源、写入和后续消费条件，不能把异步生成当成本轮同步生效。当前明确要求仍需参与输入和优先级判断，见第36章。

相邻领域原理的五组参考解释

近似最近邻（Approximate Nearest Neighbor，ANN）找到了全部精确向量 top-3，为什么回答仍可能漏掉失败日志？

先沿智能代理（Agent）的材料生成、索引、召回和输入消费定位日志。近似最近邻（Approximate Nearest Neighbor，ANN）近邻召回衡量与精确向量近邻的重合，不等于业务上需要的材料覆盖：向量表示若没把失败日志排入 top-3，提高搜索精度不会修正这个相关性问题；日志若已召回但在模型输入（Model Input）预算（Budget）裁剪时被丢掉，问题又在消费端。搜推中的候选生成、排序与展示分层有助于定位，但智能代理（Agent）最终还要检查材料是否支持具体判断。

工具参数看起来完整，随后收到终止原因 length；另一工具已远端执行却丢回执，是否都应重试？

不是同一故障。Pi 的增量解析可以展示结构化参数，但完整的 JavaScript 对象表示法（JavaScript Object Notation，JSON）参数不等于模型消息（Model Message）正常结束；终止状态检查仍可能在截断时阻止这条消息进入工具执行。此时先判断是否越过执行闸门。远端效果后丢回执则已越过该边界，本地需要围绕原操作查询或使用可靠幂等（Idempotency）合同；无法确认时保留未知。流协议的终止条件与分布式效果恢复（Recovery）不能用一个“重试”分支代替。

数据库开启预写日志（Write-Ahead Log，WAL），新执行者（Worker）获得代际（Generation） 42，但资源只见过 41，旧执行者（Worker）一定被挡住吗？

不一定。预写日志（Write-Ahead Log，WAL）帮助数据库恢复（Recovery）本地事务，不会自动让外部资源知道新代际（Generation）。如果资源尚未安装或接收 42，按“拒绝比已见代际（Generation）更旧的请求”这一合同，41 仍可能被接受。资源知道 42 后才能拒绝旧代际（Generation）；同属 42 的同一操作重复到达，还需要操作身份与幂等（Idempotency）处理。隔离令牌检查（Fencing）用代际（Generation）识别旧负责者（Owner），幂等（Idempotency）处理同一操作的重复效果，两者的对象不同。

技能说明包（Skill）先只出现在目录，后来正文载入，随后用户改变要求，分别影响什么？

元数据（Metadata）提供发现和选择线索，正文被选中后才按相应实现进入输入片段（PromptFragment）等输入表示。它们首先影响模型（Model）知道什么、怎样选择动作；实际效果还要经过运行时（Runtime）的当前权限（Permission）与准入检查。用户修订（Revision）任务后，旧技能说明包（Skill）内容不能自行延长旧许可，也不能把任务指导变成资源权限（Permission）。各产品的加载时点和授权合同可能不同，只有明确接通的步骤才能合并描述。

同一评价单元（Cell）三次记录为 infra_failed/null、completed/0、completed/1，Maka 的单次结果选哪条？

在本课程所述复用条件和选择规则成立时，第一条基础设施失败不作为完成结果，第二条 completed/0 已构成首个可选完成结果，因此选择第二条。不能再取第三条最高分并称为同一次尝试的能力。若研究对象改为“最多三次的重试策略”，就要重新规定重试条件、停止规则、样本单位与总预算（Budget），并累计失败和未采用尝试的成本。评价策略改变，指标含义也随之改变，见第40章。
