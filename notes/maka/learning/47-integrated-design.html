第 47 章｜跨模块综合设计

本章概览

核心问题：代码修复、购买委托和报名任务怎样同时守住当前要求、效果边界与最终交付？

关键概念：Owner（负责者）：持有相应决定权；Revision（修订）：标识当前约束版本；条件编辑：前提仍成立才提交；效果未知：尚不能确认操作结果；采纳：父任务检查并使用子产物；验收：按任务合同判断交付。

关系主线：当前要求约束输入、授权与执行，写读记忆服务后续任务，子产物需采纳和复测；恢复围绕原操作核对效果，费用与通知另按各自合同计算。

相关基础是 第28、31、36、39、40章 与14 模块地图中对应的机制；第62章提供完整综合案例。

综合设计的四个连接问题

模块连接产生四个具体问题：谁接纳工作，哪些记录让下一步可见，效果未知由谁处理，怎样判断最终交付？下面的参考方案把第26章设计分析示例中的身份、状态与判定扩展到一项完整任务。实现事实与额外设计分别标明，避免把更强的参考合同当成产品现状。

在连接这些模块前，完整项目还有两个外层入口：开始时建立项目工作环境，中断后通过工作交接重新确认现状。它们给内部循环提供可用的起点，也让已经产生的结果能服务下一次工作。

项目说明不能代替权限检查，交接文本不能继承旧授权，历史通过也不能替代当前检查。下面的五轮设计据此展开。

1. 同一个项目，分五轮增加约束

基础任务仍是修 README 测试步骤、修复 formatDuration(125) 的错误输出、运行相关测试并中文汇报。现在项目中存在大量日志和用户自己的未完成编辑。允许多种满足约束的设计，不要求复制 Maka 的命名或照抄某个产品。

为后面的输入保真与故障分析固定两条用户消息，U1/U2 是本例的输入标记：

  • U1，原始完整修复请求：“修正 README 中的测试步骤，修复 src/duration.js 的 formatDuration，使 125 秒输出 2:05 并符合一般的分秒转换规则；运行相关测试，最后用中文说明修改、结果与未完成项。”
  • U2，在第一次编辑前新增的约束：“保留我已有和随后新增的内容，不要覆盖我的未完成编辑；只允许修改 README 和 src/duration.js，不要修改测试文件。”

后续用户修订优先于旧动作所依据的范围。例如用户再说“改为只读检查”，就不能凭 U1/U2 继续执行旧编辑，必须按最新范围重新判断；已经开始的效果另行核对。下文“忘了 U2”具体指丢失了保留用户内容、限定两个可改文件或禁止修改测试的约束，不能只凭输出正确就算任务成功。

工具合同处理单次动作，输入管理保留当前要求，Memory 服务未来任务，协作分配独立工作，恢复处理动作与记录之间的间隙。下文将这五部分接到同一组身份与状态上。

2. 任务推进流程与状态初值

下图中的建立、读取、执行与验收都是动作，箭头表示工作怎样推进。流程所依赖的状态由图后的 RepairState 字段和完整初值表达，不能只凭走到某个动作节点就推断文件效果或任务已经成功。

这张图中的 owner 可以具体分工：任务协调者持有 U1/U2 的当前修订，接纳模型工作与委派；工具执行者检查当前许可和资源前提，产生文件效果；结果存储保留成功、失败或未知；父任务依据产物与检查结果决定是否交付。等待批准或子结果时，任务仍未完成；停止检查位于下一次接纳与实际提交之前，已开始的效果另行结算。

以下是贯穿案例的教学接口及完整初值，不是 Maka API。effect 描述本次编辑，不代表任务总状态；后续 revision 必须由可信 owner 维护。

type RepairState = {
  taskId: string;
  revision: number;
  allowedWrites: string[];
  preserveUserEdits: boolean;
  stopped: boolean;
  editId: string;
  effect: "not_started" | "unknown" | "confirmed";
  verification: "not_run" | "failed" | "passed";
};
const initial: RepairState = {
  taskId: "repair-17", revision: 2,
  allowedWrites: ["README.md", "src/duration.js"],
  preserveUserEdits: true, stopped: false,
  editId: "repair-17/duration/edit-1",
  effect: "not_started", verification: "not_run",
};

若编辑已发生但回执丢失，只把该编辑的 effect 改为 unknown，不将它写成 not_started。若用户随后改为只读，协调者保存新 revision 并清空可写范围；旧编辑若尚未提交就被拒绝，若已发生则保留效果并重新核对。

模型若在长调用之后返回新动作，而用户已经停止，必须重新检查准入。若效果已开始，停止新动作与结算旧效果属于两件事。

5. 参考设计怎样逐轮变完整

工具轮。 参考方案采用绑定观察版本的条件编辑，运行时提供可信工作范围。读取 v7 后用户新增段落成为 v8，旧 v7 编辑被拒绝；重新读取 v8 后，补丁保留新增段落，只修测试命令与 % 100 → % 60，由资源 owner 在同一边界检查 v8 并提交 v9。这个内容版本合同强于 Maka 普通 Edit 的对象身份检查，不能当成其现有 Read-version CAS。测试结果区分未启动、断言失败与成功；退出码 0 但没有实际测试仍不满足验收。

输入轮。 沿用第36章的教学预算：共享窗口 32k，输出 4k，固定协议与工具等 6k，余量 2k，动态预算为 20k token。设 U1/U2 占 1k、相关代码 6k、既有失败结果 4k、旧调查摘要 5k、未结束调用的当前材料 3k，合计 19k，剩 1k。这些是给定估算，未结束调用未来的结果尚不能视为已装入；新结果超出余额时，需要再次整理或有界读取。摘要保留原材料入口，未结束调用保持真实 pending，不伪造配对结果。压缩失败不能删掉 U2 换取表面成功。

Memory 轮。 把工作区例外与全局默认分成可更新的状态；撤回例外后恢复全局默认。分别记录写入是否发生、当前任务是否读取、是否进入请求以及回答是否遵循。当前任务的一次要求不自动变成永久偏好。

协作轮。 传给子任务的是足够完成限定目标的上下文；工具范围与文件范围单独定义。子任务交付产物和检查记录，父任务检查冲突、采纳并做整体复测。断线恢复从运行事实重建观察，不从 UI 空白推断工作不存在。

多个故障同时出现时，局部结论不能替整个状态下结论。例如 child 的 patch 尚未合入，只说明父文件没有经这次采纳改变；若父任务自己的 Edit 同时处于效果未知，就仍不能断言父文件未变，须按文件与操作分别查询。付款也一样：“尚未确认发生”不等于“已确认没有发生”；超时后的计划表必须保留未知，不能为了填满状态栏改写成未执行。

恢复轮。 接纳、认领和派发保留稳定身份。已经发生但不确定的效果需要查询或明确的幂等合同；无法查询时保留未知，避免伪造确定状态。总预算包含父子任务、重试和恢复成本。

替代方案可以更简单：完全串行减少交接开销；独立工作副本加人工合并减少直接覆盖，却增加采纳成本；仅保存明确偏好配置减少自动提取错误，却不自动积累经历。它们是否适合，取决于任务规模、失败代价和需要复用的信息。

批准后用户把场次改为周日下午，怎样处理？

生成 F1 第 2 版，B1 与第 1 版的绑定不再覆盖当前表单。执行入口拒绝旧提交，展示第 2 版的完整字段，取得对应的新批准后才允许提交。仅在聊天里更新场次、仍把旧表单送到服务端，会同时违反最新要求与批准绑定。

服务端已经登记，回执丢失，怎样恢复？

本地将 S2 保存为 unknown。若服务端提供按 S2 查询的合同，则查询原提交并关联既有 C2，确认后完成 G2；若没有可靠查询或幂等合同，则保留未知，不直接创建 S3 重复报名。两周到期会阻止新提交，但不会把已提交 S2 改成“从未发生”；到期后的查询和通知只能在明确保留的权限与预算内进行。

这一设计复用了代码任务中的四项关系：当前要求约束执行，观察身份关联业务事项，批准绑定最终参数，恢复围绕原操作核对效果。业务从改文件变为报名后，需要额外处理表单版本、截止时间冲突和通知状态。

用真实实现解释设计选择

下面四组问答沿已讲过的真实实现展开。公开材料没有披露的内部状态仍保留未知；参考设计与产品现状分别说明。

四类实现问题与因果解释

已知入口在 CLI，Aider 为什么会把一个依赖文件放进 repo map？动态插件又会漏什么？

静态解析先提取定义与引用，建立文件间的关联。已知聊天文件和标识符参与个性化关注，PageRank 将权重沿关系传播，再选择相关定义并受 token 预算约束。因此一个依赖文件可以通过引用关系获得排名，但不保证其全文进入最终输入。运行时拼接出来的插件名可能没有对应静态引用边；此时需要读取配置、加载逻辑或运行观察补充线索。单纯扩大图排序预算不能生成原本没有提取出的动态关系。详细过程见第37章。

同一个脚本的 open/read/connect，在原生 Sandbox、gVisor 和 microVM 中分别经过哪里？

原生进程最终使用宿主内核，由对应平台的隔离和访问策略约束资源请求。gVisor 的 Sentry 在用户态实现大量应用可见的系统调用语义，文件和网络访问再经过受控的宿主接口；文件通道还涉及配置的 gofer 等组件。microVM 内的应用先请求 guest kernel，需要外部资源时再通过虚拟设备与宿主侧后端交互，不能把每次应用系统调用都画成直接调用宿主内核。三者的文件挂载、网络出口和允许资源仍需明确配置，执行边界本身不会替用户决定哪些目录可写。详见第34章。

并行调查一个节点成功、另一个失败，重启后重做什么？发布已经成功却丢回执又怎样？

在 LangGraph 相应持久化配置与恢复路径中，已保存的 pending writes 可保留同一 super-step 中成功节点的输出，恢复时继续失败节点；未持久保存的结果不能凭空复用。Temporal 则依据事件历史重放工作流决策，已记录的 Activity 结果可用于重建状态。两者都不能仅凭本地记录缺失就证明外部发布未发生：Activity 或节点的效果已经发生而完成结果未记录时，重试可能再次触发效果，需要业务幂等、查询或未知状态处理。持久化恢复单位与外部业务效果是两层合同，见第44章。

全局中文、项目 A 英文，随后撤回 A 例外，输入应怎样变化？

先分别保存全局默认与项目例外；在 A 中选择仍有效的英文例外，在其他项目使用中文默认。撤回 A 例外后，使该条规则失效，下一次输入回到中文，而不是把全局默认永久覆盖为英文。真实实现还必须有作用域过滤和实际读取步骤：Maka Local 的 workspace scope 不等于按 cwd 自动隔离项目，分项目 State Root 是额外部署条件；Codex 的后台 Memory 流程也有选源、写入和后续消费条件，不能把异步生成当成本轮同步生效。当前明确要求仍需参与输入和优先级判断，见第36章。

相邻领域原理的五组参考解释

ANN 找到了全部精确向量 top-3，为什么回答仍可能漏掉失败日志？

先沿 Agent 的材料生成、索引、召回和输入消费定位日志。ANN 近邻召回衡量与精确向量近邻的重合，不等于业务上需要的材料覆盖：向量表示若没把失败日志排入 top-3，提高搜索精度不会修正这个相关性问题；日志若已召回但在 prompt 预算裁剪时被丢掉，问题又在消费端。搜推中的候选生成、排序与展示分层有助于定位，但 Agent 最终还要检查材料是否支持具体判断。

工具参数看起来完整，随后收到 length；另一工具已远端执行却丢回执，是否都应重试？

不是同一故障。Pi 的增量解析可以展示结构化参数，但完整 JSON 不等于模型消息正常结束；终止状态检查仍可能在截断时阻止这条消息进入工具执行。此时先判断是否越过执行闸门。远端效果后丢回执则已越过该边界，本地需要围绕原操作查询或使用可靠幂等合同；无法确认时保留未知。流协议的终止条件与分布式效果恢复不能用一个“重试”分支代替。

数据库开启 WAL，新 Worker 获得代际 42，但资源只见过 41，旧 Worker 一定被挡住吗？

不一定。WAL 帮助数据库恢复本地事务，不会自动让外部资源知道新代际。如果资源尚未安装或接收 42，按“拒绝比已见代际更旧的请求”这一合同，41 仍可能被接受。资源知道 42 后才能拒绝旧代际；同属 42 的同一操作重复到达，还需要操作身份与幂等处理。代际检查解决旧 owner，幂等解决重复效果，两者的对象不同。

Skill 先只出现在目录，后来正文载入，随后用户改变要求，分别影响什么？

metadata 提供发现和选择线索，正文被选中后才按相应实现进入 PromptFragment 等输入表示。它们首先影响模型知道什么、怎样选择动作；实际效果还要经过 Runtime 的当前权限与准入检查。用户修订任务后，旧 Skill 内容不能自行延长旧许可，也不能把任务指导变成资源权限。各产品的加载时点和授权合同可能不同，只有明确接通的步骤才能合并描述。

同一 cell 三次记录为 infra_failed/null、completed/0、completed/1，Maka 的单次结果选哪条？

在本课程所述复用条件和选择规则成立时，第一条基础设施失败不作为完成结果，第二条 completed/0 已构成首个可选完成结果，因此选择第二条。不能再取第三条最高分并称为同一次尝试的能力。若研究对象改为“最多三次的重试策略”，就要重新规定重试条件、停止规则、样本单位与总预算，并累计失败和未采用尝试的成本。评价策略改变，指标含义也随之改变，见第40章。
