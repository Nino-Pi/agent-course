第二部分：Maka 核心机制与任务接续 · 22 / 62

第 22 章｜mini 与 Maka 的任务执行案例

本章概览

核心问题：真实模型怎样依据文件与工具结果完成修复，哪些结果仍不足以证明任务成功？

关键概念：轨迹：实际请求与动作记录；工具观察：执行后返回的信息；任务范围：本次获准处理的内容；压缩检查点：后续请求使用的历史表示；Local Memory（本地记忆）：可按读取开关进入新请求的偏好。

关系主线：比较 mini 与 Maka 的修复、限定范围、压缩和记忆案例，把保存的事实、模型实际输入与最终结果逐一对应。

第04章使用固定回复；本章五个案例由真实模型选择下一步。

所有案例仍使用 README、package.json、src/duration.js 和 test/duration.test.js 四个文件。每个独立实验从原始副本开始。模型为 K3（Kimi 的 k3 模型服务），实际请求携带 reasoning_effort: max；mini 运行原生 CLI，Maka 使用原生 Runtime Host 的生产执行链。这里展示一次实际发生的过程，不要求模型走出原先示意中的固定顺序。

1. mini：它先看什么，什么时候才有证据

**用户任务：**修正 README 测试步骤，修复函数，运行测试并检查修改范围；只允许改 README 和函数文件。

这次 mini 共向模型请求 8 次。每次模型回答里的 Bash 动作由真实 LocalEnvironment 执行，结果进入下一次请求。下表按信息产生的顺序合并相邻步骤。

表中 find 按条件遍历目录树、查找路径，ls 列出目录中的条目信息；本次先用它们看项目结构。第04章已见过的 cat 随后读取并拼接文件内容；sed 在这里改用文本替换规则，不再只是第02章的按行打印。

表 2 / Table 2 · 1. mini：它先看什么，什么时候才有证据
实际片段此时发生了什么支持的判断
第 1 次请求：模型说“我先查看项目结构”，调用 find、ls环境返回四文件目录这次工具观察只提供文件名，还没有提供函数内容
第 2 次：调用 cat 读取四份文件下一次输入出现真实 scripts、README、函数与测试项目知识来自这次返回，不是模型自动看见了磁盘
第 3 次：指出 % 100 与测试入口问题，运行 npm test 和几个输入原测试 2 通过、2 失败，60/125 秒输出错误它先从源码形成判断，再用执行结果核对
第 4–5 次：检查不存在的 check 脚本，用 sed 改两处并回读README 改为 npm test，余数改为 % 60这次修改由 Bash 执行，不存在单独的 mini Edit 工具
第 6–7 次：复测、检查额外输入、查看 diff原测试全过，额外样本正确，只有两文件改变修改、测试、检查范围是三种不同观察
第 8 次：中文总结，再调用 echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUTmini 识别结束标记并保存 trajectory完成 action 是特殊控制入口，不是又执行一次普通 Shell 工作

默认 CLI 的 InteractiveAgent 还会为这个控制动作补上 not executed 占位，具体顺序见第05章的完成动作说明。它表示这项动作未走普通 Shell 执行分支，不是对之前所有动作效果的判断；也不能据此给第04章的 DefaultAgent 记录补出第八条普通 observation。

一个真实的小插曲：为什么退出码不能脱离命令看

模型检查错误测试命令时实际使用：

npm run check 2>&1 | head -10; echo "---exit: $?---"

输出有 Missing script: "check"，但记录中的外层返回码是 0。这不矛盾：管道末端是 head，后面又执行了 echo；外层成功不等于 npm run check 成功。因此，返回码必须结合命令结构与输出正文解释。

**判断：**只知道“编辑命令返回成功”，能否写“所有测试通过”？

参考答案

不能。第 5 次之后只有修改与回读证据；测试通过来自第 6 次的执行结果。最终外部检查再次运行测试，确认 4 项通过；原测试和配置文件保持不变。

2. Maka：同一件工作，换一种工具表达

Maka 在另一份原始副本中使用同一个模型完成任务，共 7 次模型请求。它先 Bash 列文件，再一次提出四个 Read，随后提出两个 Edit；它直接根据源码修复，再运行测试，没有复制 mini 的“先运行失败测试”顺序。

Maka 的模型收到编辑结果后，才提出测试调用。实际 npm test 返回 4 通过、0 失败；之后它又检查 59、61、119、3599、3600、3661 秒等输入并查看 diff。外部检查确认只有 README 与函数文件改变。

它与 mini 的共同点是“动作 → 观察 → 下一次决策”。 工具名称、消息表达和持久记录不同，实际行动顺序也不同。这次成功不支持模型能力排名；工具与状态边界的比较见 第08章。

看见了编辑报告，还没看见整个最终文件

Maka 的 Edit 返回可供模型阅读的简短修改报告；这份报告与原始工具结果分别存在记录中。正文没有自动展开完整 diff。后面真实调用 git diff 才给模型补上完整的两处变更。这可以接到 第14章 的事实与投影 和 第15章 的模型视野。

两者都来自这次真实编辑，但承载的细节不同。不能因为存储里有完整 diff，就假设模型已经读到了它。

**判断：**Maka 没有先跑出红色测试，是否应该重跑直到它照着 mini 的顺序走？

参考答案

不需要。这条路线已从源码形成判断，再用实际测试与 diff 检查修复。没有先跑失败测试会少一份运行前对照，但不能因此认定修复无效；反复重跑直到顺序符合预期，反而改变了要分析的那次过程。

3. 只修 README：为什么测试仍红，也能完成这项任务

第三个案例从原始副本开始，把要求改为“只修 README，运行并解释测试，不修改源码”。Maka 共 6 次模型请求，实际只改 README；原测试仍为 2 通过、2 失败。

模型最后准确列出 1:60 对 1:00、2:25 对 2:05 的差异，并写道：

按照你的要求，我没有修改源码、package.json 或测试文件，也未创建任何新文件。

文件检查与这句话一致。它知道 % 100 应为 % 60，但没有继续改源码。这个片段用于讲清本次任务范围与所有问题是否解决是两回事。

这里的约束由用户任务表达；该次运行没有通过审批或 OS 拒绝来阻止源码写入。它说明 Agent 遵守了任务范围，不能用来证明执行环境会强制拦住越界修改。第17章分别解释授权判断与强制执行边界。

**判断：**为了展示更“成功”的 Agent，把源码也修掉再记作通过，是否合适？

参考答案

不合适。那会违反本次只改 README 的要求。正确的完成报告应保留源码失败，并说明哪些事情尚未授权处理。

4. 压缩后的状态与遗漏

这一例让 Maka 在新会话中依次完成三轮工作：读文件并跑失败测试、分析边界输入、只修 README。随后通过原生 context.compact 显式压缩，再要求它继续修函数。它是一次手动压缩教学案例，没有把短历史冒充自然触发的窗口溢出。

摘要也会省略东西

此前用户要求“最后用中文解释”，这份摘要没有复述语言要求。继续任务的消息又明确说了“用中文说明最终结果”，所以最终中文报告不能证明语言偏好经过摘要保留。这是本次实际可见的遗漏，不据此推断每次压缩都丢失语言要求。

**判断：**看到摘要把“修函数”放在 Next Steps，就能说文件已改吗？

参考答案

不能。摘要明确区分了已完成的 README 与待处理的函数。修改是否发生，要看后续真实 Edit 和文件结果；测试是否通过，要看实际测试输出。

5. Memory：新会话的这三个小标题从哪里来

实验通过原生 Local Memory 管理接口保存了一条合成偏好：

解释测试结果时，固定使用“已修改”“已验证”“待处理”三个部分；没有做过的修改或测试必须明确说明。

这一步由实验客户端调用保存接口，不是模型说了“记住了”就算保存。然后在两个全新的 Session 中提交完全相同的任务：“请运行这个项目的测试，并解释这次测试结果。不要修改任何文件。”第二个 Session 没有第一个的对话历史。

表 5 / Table 5 · 5. Memory：新会话的这三个小标题从哪里来
实际观察（Observation）允许读取关闭读取
保存的条目同一条 workspace 范围偏好条目仍在，没有删除
新请求的背景出现 <local-memory> 与格式要求没有该 Memory 块，也没有格式要求
实际回答结构已修改、已验证、待处理结果摘要、失败的测试及原因、通过的测试、另一个小问题
实际项目状态没有修改；测试 2 通过、2 失败没有修改；测试 2 通过、2 失败

开启读取时，模型在“已修改”下明确写“无”，在“待处理”下保留尚未修复的 bug。这样可以在输入与回答中分别指认格式要求和相符的输出；它支持本例的采用判断，但单次对照还不能排除采样波动，或量化这种效果在新任务中多稳定。关闭读取后条目仍存在，却没有进入新请求，正好接上 第21章已经演示的“存”与“读”的区别。

这是一个小对照教学案例，不是长期记忆效果统计。两次运行都用中文提问，因此两边都回答中文并不能说明 Memory 生效；这里辨认的是保存的特定结构，以及实际输入中有没有这条要求。也没有把 Local Memory 的结果扩展成 Atomic 自动召回已经实现。

**判断：**第二个会话没有采用那三个标题，能否断言偏好文件被删了？

参考答案

不能。本例只关闭了 Agent 读取，条目仍在。查看保存状态、查看本次输入、查看实际回答，分别回答“存了没有”“读了没有”“用了没有”。

案例能解释什么，不能证明什么

表格摘取了真实的文件、工具和模型返回；模型自己解释“为什么这样做”，仍不等于我们看到了它的内部因果过程。单次案例也不能用于成功率排名。案例运行说明保留了原运行条件；这里的结论只覆盖这些已记录的输入与结果。

本页主案例不替代 第06章 的崩溃实验。正常修复没有发生 crash，也不能证明所有工具效果只会执行一次。真实例子与确定性实验各自承担适合的教学任务。
