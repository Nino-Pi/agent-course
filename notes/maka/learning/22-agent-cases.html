第二部分：Maka 核心机制与任务接续 · 22 / 62

第 22 章｜真实智能代理（Agent）的任务执行案例

本章概览

核心问题：真实模型（Model）依据什么推进修复，怎样区分文件已改、测试（Test）通过和本次任务完成？

关键概念：执行轨迹（Trajectory）留下请求与动作；观察结果（Observation）提供下一步依据；任务范围（Task Scope）限定获准处理的内容；检查点（Checkpoint）承载压缩后的历史；本地记忆笔记（Local Memory）提供可读取的背景。

关系主线：从同一带缺陷的项目初态，依次比较两条修复路线、只修文档、上下文压缩（Context Compaction）后继续与新会话（Session）读取偏好。逐项对应实际输入、行动请求（Action）和结果，避免把保存的内容或模型（Model）声明直接当作成功。

前情回顾：恢复哪个初态，沿用哪些判断？

第04章用固定模型（Model）回复解释修复过程；第13–20章多次使用“函数已经正确，只处理文档”的简化情境。本章重新从带有两处问题的原始副本开始，五个案例都由真实模型（Model）选择下一步。前一例修过的文件，不会自动成为后一例的初态。

m=⌊s60⌋,r=s−60m,0≤r<60.m=\left\lfloor\frac{s}{60}\right\rfloor,\qquad r=s-60m,\qquad 0\le r<60.m=⌊60s​⌋,r=s−60m,0≤r<60.

⌊⋅⌋\lfloor\cdot\rfloor⌊⋅⌋表示向下取整。60秒应拆为1分钟加0秒，125秒应拆为2分钟加5秒；余下秒数再补足两位，得到 1:00和 2:05。原来的 % 100分别得到60和25，所以输出 1:60、2:25。这个推导提供缺陷假设，后面的真实测试（Test）再核对实际行为。

五例的模型（Model）均为Kimi的K3服务，实际请求为 model: k3、reasoning_effort: max。mini使用原生命令行接口（Command-Line Interface，CLI）；Maka使用原生运行时宿主（Runtime Host）的生产执行链，由实验客户端提交任务，并未经过桌面界面。

下面的“8次”“7次”等数字指保存记录中的模型调用（Model Query），不等于工具调用（Tool Call）次数，也不能套成所有实现通用的模型步骤（Model Step）数。一次模型调用（Model Query）可能提出多个工具（Tool），也可能只输出最终回答。

1. mini：从文件内容到修改与验证（Verification）

输入与任务范围（Task Scope）

前两例使用相同任务，原始用户文本是：

请检查这个小项目，修正 README 中的测试步骤，找出并修复时间格式化函数的错误，运行测试并检查修改范围，用中文解释结果。只允许修改 README.md 和 src/duration.js，不修改 package.json、现有测试，不创建新文件。可以用内联命令检查其他输入。

因此允许的两处修改是文档测试（Test）入口和函数实现；配置与已有测试（Test）必须保留。额外输入可以通过命令直接检查，无需创建文件。

mini共进行8次模型调用（Model Query）。普通Bash行动请求（Action）由真实 LocalEnvironment执行，观察结果（Observation）进入下一次请求。先读它怎样获得信息，再判断最终结论。

find按条件遍历目录树查找路径，ls列出目录条目；cat读取并拼接文件内容。sed在本例中使用文本替换规则，和第02章按行打印的用法不同。这些命令不会因为名称出现在回答中就自动执行，仍需运行支撑（Agent Harness）接收并处理。

最后一项通过命令解释器（Shell）实际执行。LocalEnvironment.execute()取得命令输出后，识别完成标记并通过 Submitted异常发出提交信号（Submission Signal）。因此该命令没有普通返回，执行输出（Output）未追加进 outputs；默认命令行接口（CLI）的 InteractiveAgent仍在 finally中调用格式化器，为缺少匹配返回的动作补上 action was not executed占位观察消息（Observation Message）。这里的占位不能证明命令未执行，也不证明任务检查自动通过。退出状态为 Submitted，完整关系见第05章。

这里也不能据占位给第04章的 DefaultAgent补出第八条普通观察消息（Observation Message）：两处使用的控制类与记录路径不同。

退出码（Exit Code）必须结合命令结构解释

第4次模型调用（Model Query）中，原始命令如下，保留它当时的写法：

npm run check 2>&1 | head -10; echo "---exit: $?---"

先拆开三个动作。2>&1把标准错误（Standard Error）合并进标准输出（Standard Output）；管道（Pipeline）把内容交给 head -10，只保留前十行；分号后又执行 echo。其中 $?读取前一个管道（Pipeline）的状态，不是从输出正文中辨认 npm是否成功。

实际输出包含 Missing script: "check"，外层退出码（Exit Code）却是0。在该次命令结构下，末端的 head以及随后的 echo使外层成功与 npm run check失败可以同时出现。因此不能看到0就写“测试（Test）通过”，也不应把原命令改成另一种写法后仍称其输出属于这次运行。

问题。 第5次编辑成功后，能立即写“所有测试（Test）通过”吗？

参考答案。 不能。此时只有修改与回读（Readback）；测试（Test）通过来自第6次执行结果。任务结束后的外部检查再次得到4项通过，并确认配置与原测试（Test）文件未改动。

Maka的 Edit有保存的工具结果（Tool Result），也有面向模型输入（Model Input）的简短编辑报告。以这次文档修改为例，略去机器路径后可以并排读：

问题。 Maka没有先跑出失败测试（Test），是否应重跑直到顺序与mini一致？

参考答案。 不需要。这次先从源码形成判断，再用实际测试（Test）与差异（Diff）检查修复。它少了一份执行前的失败对照，但不因此使修复无效。再次运行会产生另一条执行轨迹（Trajectory），不能拿来补写这一次过程。

3. 任务范围（Task Scope）：只修文档，保留源码失败

这一例重新从两处问题都存在的副本开始。原始要求改为：

请检查 README 与 package.json 是否一致，只修正 README 中的测试步骤，运行测试并用中文解释结果。本次只允许修改 README.md，不允许修改源码、package.json、测试或创建其他项目文件。即使发现源码错误，也请保留并准确报告。

Maka共进行6次模型调用（Model Query），实际只改文档。原测试（Test）仍为2项通过、2项失败，模型（Model）在最终回答列出 1:60对 1:00、2:25对 2:05的差异，并写道：

按照你的要求，我没有修改源码、package.json 或测试文件，也未创建任何新文件。

文件检查与这句话一致。这项任务的完成条件是修正文档、运行并准确解释测试（Test）、保留未获准改动的文件。发现源码缺陷提供了报告内容，并没有扩大任务范围（Task Scope）。

这里有一条重要边界：该次运行的权限模式（Permission Mode）为 bypass，外层操作系统（Operating System，OS）沙箱（Sandbox）隔离实验目录，但没有触发审批或验证操作系统（OS）拒绝一次源码写入。它说明这次智能代理（Agent）遵守了指令，不能用来证明越界修改一定会被强制拦截。机制区别见第17章。

问题。 把函数也修好，让测试（Test）全部通过，会让本次任务做得更好吗？

参考答案。 不会，那会违反只改文档的要求。这里应保留失败并准确报告；“本次任务完成”与“项目中所有问题解决”需要分别判断。

4. 上下文压缩（Context Compaction）：保留的状态与遗漏

先交代同一会话（Session）中已经做过什么

本例也从原始副本开始，但内部的几个工作轮次（Turn）共享同一例的文件状态。Maka依次完成三轮工作：读文件并运行失败测试（Test）、分析边界输入、只修文档。此时文档已正确，函数尚未修，测试（Test）仍是2项通过、2项失败。

随后实验客户端调用原生 context.compact，显式发起上下文压缩（Context Compaction），再要求继续修复。它是手动触发的案例，没有发生自然超出上下文窗口（Context Window）后才被迫进行上下文压缩（Context Compaction）的过程。

这组记录保留了首次失败：输出上限配置冲突使上下文压缩（Context Compaction）结果为 failed/provider_error，没有产生成功摘要（Summary），后续仍沿原历史完成修复。因此“最终修好了”本身不能证明上下文压缩（Context Compaction）阶段成功。修正配置后的另一份独立尝试，才取得下面的检查点（Checkpoint）。

摘要（Summary）怎样区分完成与计划？

成功案例共记录14次模型调用（Model Query），其中第10次是摘要（Summary）调用；它读取此前消息（Message），使用原生8000词元（Token）输出上限。这里的14包含摘要（Summary）调用，不能全算为修复动作。

最终中文回答不能证明语言要求被保留

此前用户要求最终用中文解释，这份摘要（Summary）没有复述语言要求。继续任务的消息（Message）却再次明确要求“用中文说明最终结果”，因此最终中文报告不能倒过来证明语言偏好经过了上下文压缩（Context Compaction）。

这是一次可见的遗漏；不能推导每次上下文压缩（Context Compaction）都会丢失语言要求，也不能用本例证明自动触发、全部归档恢复或任意长历史的效果。这些条件需要各自的消费者（Consumer）与观察结果（Observation）。

问题。 摘要（Summary）把修函数放在 Next Steps，能否说明文件已经改过？

参考答案。 不能，计划与已发生的动作必须分开。该摘要（Summary）明确保留文档已改、函数待修；后续 Edit与文件结果证明修改发生，实际测试（Test）输出才证明所列断言通过。

5. 本地记忆笔记（Local Memory）：三个标题怎样进入新会话（Session）？

固定保存内容，只改变读取条件

第21章的固定程序没有调用模型（Model）。这里补上另一组真实回答：实验客户端通过本地记忆笔记（Local Memory）的原生管理接口（Interface）保存合成偏好：

解释测试结果时，固定使用“已修改”“已验证”“待处理”三个部分；没有做过的修改或测试必须明确说明。

保存由客户端实际调用完成，不是模型（Model）说“记住了”就算写入。接着在两个全新的会话（Session）提交完全相同的任务：

请运行这个项目的测试，并解释这次测试结果。不要修改任何文件。

第二个会话（Session）没有第一个的对话历史。两边均使用带缺陷的原始项目，不允许改文件；保存条目相同，只改变本地读取条件。允许读取一侧有5次模型调用（Model Query），关闭读取一侧有6次，不能把合计11次称为同一个执行（Run）。

读取开启时，模型（Model）在“已修改”下明确写“无”，在“待处理”下保留尚未修复的缺陷。于是可以分别在模型输入（Model Input）中定位格式要求，在回答中定位相符结构；读取关闭时则同时看不到这条输入和那三个标题。

观察到采用，不等于得到稳定效果统计

这组对照支持本例的采用判断，但只有一对结果，不能排除采样波动或量化它在新任务中多稳定。两边都以中文提问，因而两边都用中文并不能证明本地记忆笔记（Local Memory）生效；能辨认的差异是那三个特定标题及其实际输入来源。

还要独立检查回答内容。关闭读取一侧的模型（Model）把缺陷概括为跨分钟就出错，这比现有证据更宽：旧函数在600秒仍碰巧输出 10:00，因为600分别对100和60取余都是0。60秒失败，不能推出所有大于等于60的输入都失败。这个反例不改变原始回答，只说明回答的解释仍需核对。

本例没有运行条目化长期记忆（Atomic Long-Term Memory，Atomic LTM）的自动召回（Recall）。本地记忆笔记（Local Memory）进入请求，不能证明另一条数据库查询链已经接通。

问题。 第二个会话（Session）没有采用三个标题，能否断言偏好文件已被删除？

参考答案。 不能，本例只是关闭读取，保存条目仍在。查看保存状态、模型输入（Model Input）与实际回答，分别回答“存了没有”“读了没有”“用了没有”。

从执行轨迹（Trajectory）作出有限结论

五例给出了具体输入、工具（Tool）和模型（Model）返回；模型（Model）自己解释为什么这样做，仍不等于我们看到了它的内部因果过程。单次修复也不能用于成功率排名或证明任意任务都能完成。

案例运行说明保留原运行条件与失败记录。这些是已经发生的独立运行，原记录只支持当时保存的输入和结果。正常修复也没有替代第06章的崩溃边界检查，不能证明所有工具（Tool）的效果（Effect）只会执行一次。
