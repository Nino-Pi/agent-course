Agent 前沿进阶能力增长、自主研究与自我改进

第 01 章｜一次失败之后，究竟该改什么

本章概览

核心问题：智能代理（Agent）没有完成工作时，怎样辨认值得改变的对象，判断一次修好能说明什么？

关键概念：干预（Intervention）是有意改变一个条件；归因（Attribution）是辨认结果变化来自哪里；消费者（Consumer）是实际读取并使用新信息或新程序的后续执行者。

关系主线：从一个路径被拆成两个参数的失败出发，用固定输入的小程序分开决策与执行问题，再追踪改变留在哪里、未来由谁使用，最后形成同条件的改进比较。

前情回顾：提出正确动作，还需要正确执行

在基础课程中，智能代理（Agent）围绕目标观察、决定下一步并取得反馈；模型（Model）提出行动请求（Action），运行支撑（Agent Harness）组织输入、执行工具（Tool）与控制过程，执行环境（Environment）提供被操作的文件和检查程序。比如“读取 README”只是请求，文件内容还要经执行返回，才能成为下一次判断的依据。可以从基础第01章回看这张关系图。

同样，模型（Model）已经写出正确路径，并不保证子程序收到正确路径；子程序正常结束，也不保证完成了用户要求。基础第26章把这几种判断分开。本章向前一步：当失败已经出现，下一项检查应该改变什么，才能把几个可能原因分开？

本章重新交代基础第62章案例 A的必要背景：这是一个 Python 文档检查项目。checker.py 应接收一个文件路径；项目内的 runner.py 提供包装函数 run_checker，负责启动它。普通路径 docs/guide.md 正常，含空格的 docs/guide draft.md 却报“需要一个路径”。先只追这个现象，暂时不扩大成整个项目的修改方案。以下过程是给定的教学执行轨迹（Trajectory），其中的小型参数探针（Probe）另有实际运行结果。

一个报错，为什么可能有三种原因

只看“需要一个路径”，至少还存在三种解释：当前输入没有给出完整路径；模型（Model）看到了完整路径，却生成了两个参数；生成的请求正确，后面的程序才把一个路径拆开。三者都能使检查器报同一句话。

要作归因（Attribution），先补沿途的观察结果（Observation）。本例给定三段彼此关联的记录：

位置 记录中的具体内容 它排除了什么解释
模型（Model）发出的行动请求（Action） check_document(path="docs/guide draft.md") 这一次提交的是一个完整路径字段
工具适配器（Tool Adapter）交给项目包装函数 run_checker 的 path 仍是完整字符串 转交这一步没有拆开它
checker.py 接收到的业务参数 ['docs/guide', 'draft.md'] 参数边界在进入子程序前已经改变

工具适配器（Tool Adapter）在这里是把调用接到项目函数的连接程序，按题设原样转交路径。读取 runner.py 又发现：它把解释器、脚本名和路径直接拼成文本，交给命令解释器（Shell）执行；后者会按语法解释空格等字符。于是，观察结果（Observation）与代码机制相互吻合：当前错误首先位于项目包装函数的参数传递。

这里有两个不同问题。项目为什么处理不了空格路径？ 现有证据已指向包装函数。智能代理（Agent）为什么没有修好它？ 还要继续看后续实际输入和决策。本例给定它没有比较沿途记录，又发了一次相同请求，仍然失败；这说明本次调查没有推进，尚不能推出模型（Model）普遍不懂 Python。

先把改变对象放回职责图

图中实线表示本例的调用关系，框表示对象归属；返回结果的箭头省略了包装函数与适配器的逐层回传。标为“可研究”的位置表示其他实验可以选择的干预（Intervention），不是本题已经取得的修改权限（Permission）。

修 runner.py 改变的是这份项目产物（Artifact），没有改变图中上半部的模型（Model）或运行支撑（Agent Harness）。若明天换到另一个仍有缺陷的项目，这份记录修改内容的补丁（Patch）不会自动教会模型（Model）如何修复它。这个归属区别决定了我们下一步究竟在验证“项目修好”，还是在研究“解题方法更好”。

固定同一输入，只改变参数传递方式

干预（Intervention）比继续看报错多做了一件事：让两个过程保持需要比较的条件相同，有意改变可疑环节，观察差异。 本例固定同一解释器、同一路径与同一段子程序，只比较“文本交给命令解释器（Shell）”和“直接传参数数组（Argument Vector）”。后者是有顺序的参数列表，每个元素表示一个参数。

为了隔开文档内容的影响，先把真实检查器换成固定探针（Probe）：一个只打印收到哪些参数的小程序。这样得到的差异只回答传参问题，不依赖 Markdown 是否合格，也不要求重新调用模型（Model）。下面三段 Python 按顺序组成完整可执行参考程序。

第一步：让接收者把收到的内容显示出来

-c 要求 Python 执行其后的一段代码文本；在这种启动方式中，sys.argv[0] 是 -c，sys.argv[1:] 才是后面传入的业务参数。探针（Probe）用 JavaScript 对象表示法（JavaScript Object Notation，JSON）打印这个列表，父程序随后把它还原为列表比较。

import json
import shlex
import subprocess
import sys

probe = "import json,sys; print(json.dumps(sys.argv[1:]))"
path = "docs/guide draft.md"

这里的 path 是固定教学字符串。文件是否存在不会影响打印，因此这个探针（Probe）不能验证检查器是否真的读取了文档。

第二步：重现旧方式，再换成参数数组（Argument Vector）

下面的旧方式故意不引用路径，保留待解释的缺陷。shlex.quote 只保护解释器路径和固定代码文本，使它们不成为第二处意外分词原因；这段旧方式仅用于本例固定字符串的 POSIX 命令解释器（Shell）对照。

old_command = f"{shlex.quote(sys.executable)} -c {shlex.quote(probe)} {path}"
old = subprocess.run(
    old_command, shell=True,
    capture_output=True, text=True, check=False,
)
new = subprocess.run(
    [sys.executable, "-c", probe, path], shell=False,
    capture_output=True, text=True, check=False,
)

old_command 只有一段文本，空格需要由命令解释器（Shell）重新解释。新方式则已经给出四个元素：解释器、-c、代码文本、完整路径；最后一个元素内部的空格不再用来划分参数。两边的接收者相同，改变的是抵达它的传递路线。

第三步：比较接收到的值，不只看退出码（Exit Code）

退出码（Exit Code）是进程结束时返回的状态数字。先确认打印程序正常执行，再解析标准输出（Standard Output），分别检查参数个数和内容；不能让“打印成功”代替“传参正确”。

assert old.returncode == new.returncode == 0
old_args = json.loads(old.stdout)
new_args = json.loads(new.stdout)
assert old_args == ["docs/guide", "draft.md"]
assert new_args == [path]
print(old_args)
print(new_args)

实际执行这三段参考程序得到：

['docs/guide', 'draft.md']
['docs/guide draft.md']

两个进程都正常结束，收到的内容却不同。它直接支持“在本地 POSIX 条件与这条路径上，改用参数数组（Argument Vector）保留了边界”。前面给定的三段执行轨迹（Trajectory）才把这一机制接回项目缺陷；探针（Probe）本身没有运行真实文档检查、pytest 或智能代理（Agent）。

这里也不能倒推“必须换模型（Model）”。我们固定了生成出的请求，根本没有比较生成能力。相反，如果原请求本来就含两个路径，而后面原样传递，就该回到输入与决策检查。观察在哪里分叉，决定干预（Intervention）首先放在哪里；一个对照只排除它实际控制住的解释。

局部机制修对，还欠哪些任务条件

现在回到实际要交付的项目修复，补齐此时会用到的条件：用户允许修改 runner.py 的包装函数和 README，测试及其他文件只读；README 顶部已有用户部署笔记，需要保留。项目配置声明使用 pytest，成功还要求普通路径仍能检查、缺失文件仍会报错、相关测试确实执行以及文件差异（Diff）符合范围。没有发布要求。

候选补丁（Patch）把同一个传参机制用于真实检查器。输入是路径 path 与可信配置给定的工作目录 cwd；输出是已结束子进程的结果，留给调用者判定。以下是参考实现，当前没有运行真实项目的 checker.py：

import subprocess
import sys

def run_checker(path: str, cwd: str):
    return subprocess.run(
        # 路径是一个元素，内容中的空格不改变参数边界。
        [sys.executable, "checker.py", path],
        cwd=cwd, shell=False,
        capture_output=True, text=True, check=False,
    )

可信配置固定 cwd 和允许调用的 checker.py。check=False 不因子程序非零退出而抛出对应异常，而是把退出码（Exit Code）留在 returncode；stdout 与 stderr 分别保存标准输出（Standard Output）和标准错误（Standard Error）。调用者仍要读取并解释它们；进程无法启动等异常也仍可能发生。这个接口语义来自 Python 的子进程文档。

完整过程是：读取当前文件，形成仅覆盖包装函数的补丁（Patch）；保留用户笔记，按配置修正 README 的测试说明；检查三种路径，再运行相关测试并核对文件差异（Diff）。读取之后若用户又保存了文件，就先重读当前内容再合并；传参修复不提供并发写入保护，也不提供沙箱（Sandbox）隔离。

本次要检查什么 教学给定的修复后结果 结果支持的范围
普通路径 收到一个路径并完成文档检查 原正常行为保持
空格路径 收到完整路径并完成文档检查 本例缺陷解决
缺失文件 非零退出，保留缺失诊断 没有吞掉错误
pytest 与文件差异（Diff） 相关用例被发现并通过；仅两份允许文件变化，用户笔记不变 受测行为与修改范围符合要求

表中是完整教学预期，不能和前面的实际探针（Probe）输出合并成新项目运行报告。按这些给定结果，参考交付可以说：“包装函数改用参数数组（Argument Vector），相关行为和修改范围满足上述条件。”没有检查的文档规则、平台与并发情况仍不能一并宣布通过。

反例：把所有错误都改成成功。 这样空格路径的红色提示也会消失，但不存在的文件会被当成有效文档。它改的是反馈，未满足检查文档的要求。缺失文件这一项使“真的保留了正确行为”与“只是隐藏失败”出现可观察差异；只回测原报错就会遗漏它。

改变留在哪里，决定未来谁可能受益

假设这次工作结束，明天换到另一份尚未修好的项目。消费者（Consumer）指实际读取并使用改变的部件：有文件却没有读取，就没有完成消费；装载了新内容，也还要观察是否改善行为。

先看同一条诊断方法：“比较原请求与接收者拿到的参数，再定位边界。”它可以留在不同位置，形成不同研究对象：

改变留在哪里 未来的消费者（Consumer） 还需要什么证据
当前输入（Input） 本次后续模型请求（Model Request） 方法确实进入请求，后续调查改变了什么
外部记忆（Memory）或技能说明包（Skill） 新任务的检索与输入组织（Input Composition） 适用时被读回，实际采用，额外成本也入账
模型参数（Model Parameters） 装载新数值的推理程序 在固定运行支撑（Agent Harness）下，未来任务表现如何
任务程序（Task Program） 后续启动器与执行器 新程序真的运行，待修项目仍保持共同初态
改进程序（Meta Program） 下一轮提出与选择后继的过程 相同起点与生成预算（Budget）下，能否更有效地产生可用后继

外部记忆（Memory）是在模型（Model）之外保留、供未来读取的经验；技能说明包（Skill）组织可复用的方法说明。把方法写进 lessons.md，新任务却不读它，只能证明保存。若把经验过度写成“所有项目都用 pytest”，新项目只有别的测试入口时，它还可能妨碍修复。需要保留的是适用条件和诊断方法，不能把某题答案当通用规则。

模型参数（Model Parameters）则是参与预测的内部数值。训练（Training）必须让数据按明确目标改变这些数值，部署端再实际装载，才能影响后续预测。基础第46章已给“输出概率（Probability）提高会怎样改变局部目标”的例算，但保存执行轨迹（Trajectory）不会自动触发训练（Training），局部数值下降也不证明未来任务更好。本册第07、08章会给从预测到更新的完整小模型（Model）过程；首次进入时会重新补所需数学，不要求已读基础第46章的选读推导。

任务程序（Task Program）规定怎样调查、修改与检查；改进程序（Meta Program）产生并选择这些方法的后继。本例项目中的 runner.py 是被解题者修改的产物（Artifact），不因文件里也有程序就自动成为上述任务程序（Task Program）。研究共享工具适配器（Tool Adapter）的更新，则要另外允许修改它，并确认后续启动器使用了新实现；本题项目权限（Permission）不会自动扩展到那里。

若新一代还参与产生后续改进，就进入递归自我改进（Recursive Self-Improvement，RSI）的研究问题。基础第46章已给有限的任务程序（Task Program）与改进程序（Meta Program）对照；这里先记住要比较的对象：后继更会解题，和产生更好后继的过程更有效，是两份结论。 后续多代章节会展开实际继承与对照，不能从一次自动补丁（Patch）生成推断长期增长。

还有一种改变只多花本次计算：读取更多证据、重新生成候选（Candidate），或比较多个可能答案。候选（Candidate）就是尚待选择和检查的方案。它可以保持模型参数（Model Parameters）不变，也不留下跨任务经验。是否值得，需把生成、检查、选择的总成本（Total Cost）一起比较；存在正确候选（Candidate）不保证最终选中它。第06章先讲下一次读取如何补证据，完整搜索与选择仍是计划内容。

这些干预（Intervention）可以放回基础六组职责：输入组织（Input Composition）、模型与工具循环（Model / Tool Loop）、状态与恢复（State / Recovery）、权限与隔离（Permissions / Isolation）、任务推进与协作（Task Progress / Collaboration）、观察与评价（Observation / Evaluation）。它们是一组教学坐标，不是唯一分类；例如外部记忆（Memory）既涉及保存，也涉及输入组织（Input Composition）和评价。当前章节只定位改变，后面的路线分别深入。

从修好一道题，走向比较两种解题方法

要问“以后也少犯错”，先定义未来任务。K-A 是本册构造的代码维护任务族（Task Family），即围绕相近工作要求组织的一组题；包括路径边界、测试入口发现、错误状态传播与文档修改范围。每题有自己的初始文件和成功条件，不是本次下载或运行的公开成绩集。同一模板换十个文件名，仍共享来源组（Source Group），不能当成十份独立机制证据。

本题已经被用于诊断和开发，后面不能再拿它充当未见检验。下一步比较两种固定策略（Policy），也就是事先约定的处理规则：

  • Q0：使用原有说明，按原流程处理失败。
  • Q1：在第一次执行失败后，追加固定诊断说明“比较原动作与子程序收到的参数，再定位边界”；每个试次（Trial）只追加一次。试次（Trial）是在规定初态和预算（Budget）下的一次完整解题机会，可以包含多次调用。

这里 Q1 是改变当前输入的方法，没有更新模型参数（Model Parameters）。真实消费者（Consumer）是第一次失败后的下一次模型请求（Model Request）；若预算（Budget）已耗尽，没有下一请求，就不能说方法被使用。Q1 是否值得，还要看它能否帮助当前问题：失败来自缺少依赖时，参数诊断也可能只增加无关读取。

比较前再固定共同条件：两边采用同一模型（Model）M0、同一运行支撑（Agent Harness）H0；每个试次（Trial）最多6次模型调用（Model Query）、8次工具调用（Tool Call）、120秒；跨任务记忆（Memory）初始为空，不继承上一题补丁（Patch）和过程记录。两边从相同、尚未修好的项目副本开始，权限（Permission）和检查要求相同。额外说明、读取和失败调用都占同一预算（Budget），不是给 Q1 免费增加操作。

Q0/Q1比较的是整套策略（Policy）。如果 Q1 胜出，暂时还没分开新增文字的长度、信息与步骤指导分别贡献多少；可以再加长度相近但不含诊断方法的对照材料。这是下一层归因（Attribution），不能直接从总分推断具体机制。

若先把 Q1 一侧项目修好，再让两边做题，难度就已经不同。这个设计可以检查修复后产物（Artifact），不能证明智能代理（Agent）更会修复。反过来，两边任务初态相同，但运行资源不同，也会留下另一种解释。原作者的基础设施对照报告了保持模型（Model）与运行支撑（Agent Harness）不变时的资源影响；这里只用它说明需要控制环境，不借用其成绩作为本课收益。

下一章另给教学任务与试次（Trial）表，沿上述共同条件计算逐题差值与不确定性。本章已经选出了值得研究的方法，还没有取得 Q1 在未来任务上更好的真实成绩。

改变一个条件，再作判断

问题。 新模型（Model）在空格题上成功，旧模型（Model）失败，能确定必须换模型（Model）吗？

参考答案。 先核对实际输入、包装函数、运行资源与总预算（Budget）是否相同；还要看成功来自修复缺陷，还是临时绕过。固定请求的探针（Probe）先查执行边界，未来任务的同条件比较再查解题能力。一条成功路径不足以给出普遍采用结论。

问题。 传参探针（Probe）已通过，为什么仍保留缺失文件检查？

参考答案。 它只显示收到几个参数。吞掉所有错误的包装函数也可能消除原报错，却不满足文档检查合同。缺失文件检查约束错误传播，实际文档与测试再约束受测行为。

问题。 方法保存、程序安装、参数更新（Parameter Update），哪个一定算学习成功？

参考答案。 三者都先表示对象发生变化。还需指出后续消费者（Consumer）实际用了什么，再比较未来任务的行为、成本（Cost）与失败。相同内容写进文件、出现在输入、被行动采用，仍是三种不同观察。
