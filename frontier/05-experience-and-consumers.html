Agent 前沿进阶能力增长、自主研究与自我改进

第 05 章｜一条轨迹（Trajectory）怎样进入下一次改进

本章概览

核心问题：记录已经保存以后，怎样让其中的经验（Experience）进入下一次行动，并判断它是否带来收益？

关键概念：执行轨迹（Trajectory）保存有顺序的输入、动作（Action）与观察（Observation）；消费者（Consumer）按具体目标使用材料；投影（Projection）为该用途保留必要信息；来源组（Source Group）保留切片与变体的共同来历。

关系主线：从一次修复提取不同材料，完整走过记忆（Memory）筛选、实际输入（Actual Input）、后续动作（Action）与新判定；再用配置变化、未知评分（Unknown Score）和同源切片解释适用边界。

前情回顾：总分、过程和后续用途各自说明什么

第02章把任务（Task）与试次（Trial）分开：一道题可以从相同初态执行多次，一次执行内部又可以发生多次模型调用（Model Query）。第03章进一步说明，用于开发与选择的材料已经影响方案，不能再冒充未参与选择的最终评价。第04章则区分有效失败（Valid Failure）与未知评分（Unknown Score）：前者已有不满足要求的证据，后者尚不能完成判定。

把这些关系放回一个小例子：某次修改工具（Tool）返回成功，执行者没有运行规定测试就报告“已经验证”。外层判定器（Grader）可以因缺少必要验证依据判为失败；这不等于补丁（Patch）的每一行都错，也不允许事后把外层检查结果填回当时的模型（Model）输入。接下来要改善行为，就需要知道哪个消费者（Consumer）会读这些材料，以及它究竟需要什么。

本章共同核心承接02、03和04，暂不计算模型参数（Model Parameters）怎样更新。训练（Training）路线在读过07–08后再进入本章末尾的深化部分；只研究固定模型（Model）时怎样利用经验（Experience），可以在共同核心出口继续读06。

一次修复留下的，不只有最后一句“完成”

沿用01与04的Python文档检查器情境，并在这里把该教学项目命名为P。包装函数原先会拆开空格路径，当前配置cfg-v1声明测试入口是python -m pytest；README顶部已有用户笔记。允许修改包装函数与README，测试文件只读。模型（Model）M0与运行支撑（Agent Harness）H0固定，跨任务记忆（Memory）为空；本次仍限6次模型调用（Model Query）、8次工具调用（Tool Call）和120秒，随后按04的合同取得判定。

这里重新给出一条完整的教学执行，不是复用某次真实模型（Model）日志。先叫它尝试（Attempt）A1，也就是这次从开始处理到提交的执行过程。为了说明先后可见性，将四次模型调用（Model Query）依次标为C1–C4：

调用 当时已经可见的输入 本次提出的动作（Action） 动作（Action）后才得到的观察（Observation）
C1 用户合同、工具说明和项目位置 分别读配置、包装函数、README全文 当前入口、旧实现、须保留的用户笔记
C2 合同与C1真实返回 提交一份限定补丁（Patch），同时更正文档入口 两个获准文件写入完成，笔记保留
C3 合同、修改回执与当前入口 请求执行测试，并读取当前差异 测试实际运行且通过；差异显示两份允许文件的变更
C4 合同、测试结果与文件差异 如实报告修改和受测范围 一份交付说明

C1的三次读取占3次工具调用（Tool Call）；C2在本例的一次限定编辑接口中提交两份文件的修改，占1次；C3的测试与差异读取占2次。因此一共4次模型调用（Model Query）、6次工具调用（Tool Call）。C3两项结果都返回后才进入C4，不能让C3在请求测试之前就“知道测试通过”。

判定器（Grader）另行检查产物、范围与必要验证，给出成功（Success）S；本章另用F表示有效失败（Valid Failure），U表示未知评分（Unknown Score）。这个外层判断与表中每一行一样，都是公开设定的教学条件；后文实际运行的只是确定性参考程序，没有运行这个项目、pytest或智能代理（Agent）。

现在才为追踪增加身份：任务（Task）为P-space-01，计划试次（Trial）为1，尝试（Attempt）为A1。一条完整调用键是P-space-01/1/A1/C1，依次对应任务（Task）、试次（Trial）、尝试（Attempt）和模型调用（Model Query）。执行轨迹（Trajectory）就是把这些输入、动作（Action）与观察（Observation）按真实顺序关联起来。单独的C1只在所属过程内有意义；另一道题的同名调用不属于这条记录。本例每个计划试次（Trial）只有一个尝试（Attempt）；若另有预先规定的环境启动重试，可以给它A0/A1等执行身份，但仍归原计划试次（Trial）计数。带着失败反馈继续修复属于接续工作，不能把它重新命名为从独立初态开始。

后文用F1和F2简称本例修改前后的文件内容状态。这两个名称帮助追踪教学情境，不表示取得了原子性的项目快照（Project Snapshot）——同一时刻覆盖全项目的一致版本。如果文件还在写入，评分方仍须按04所述先收束写入、确认当前产物；不能因给状态起了名字就跳过这一步。

先问下一次要解决什么，再决定保留哪些材料

投影（Projection）在这里是“按某个用途，从原始记录生成较小视图”的操作。它不表示原始事实发生了变化。同一条执行轨迹（Trajectory）可以支持诊断、记忆（Memory）、程序优化（Program Optimization）或训练（Training）；各自需要的字段不同，不能只存一段成功摘要就认为材料齐全。

诊断投影（Diagnostic Projection）：保留当时不知道什么

另设同一任务（Task）的第二个计划试次（Trial），尝试（Attempt）叫A2。它从相同F1、cfg-v1、空记忆（Memory）和相同预算（Budget）重新开始，不读取A1反馈。A2修改后立即声称“已验证”，跳过测试与差异读取；外层确认缺少规定验证依据，给出有效失败（Valid Failure）F。

这不是A1成功后的追加动作（Action），也不是一次免费重试。两条记录用于解释不同消费者（Consumer），不能据两例就估计成功率。诊断材料至少要留下以下完整关系：

来源：P-space-01 / trial=2 / attempt=A2；用于开发。
起点：项目P，修改前内容F1，配置cfg-v1；没有A1的反馈。
报告前输入：有编辑回执，没有测试结果。
已发生动作：修改包装函数与README，然后声称已验证。
独立判断：必要验证没有执行，判F；用户笔记仍在。
候选原因：将编辑成功当成验证成功。
尚未知道：如果实际运行测试，这份补丁会通过还是失败。

最后一项阻止一种常见误归因（Misattribution）：总判定是F，就把每一步都标成错误。这里已知的是“验证依据缺失”，补丁（Patch）本身的行为仍未判明。诊断者可以据此研究报告前的证据门，不能把尚未执行的测试结果编进材料。

记忆投影（Memory Projection）：项目事实必须带适用条件

A1的C1读取支持一项具体事实：“项目P在配置cfg-v1下的测试入口是python -m pytest。”如果把它改成“所有Python项目都使用pytest”，就超出了来源能支持的范围。下一次项目配置变了，旧命令也不再自动适用。

因此这条记忆（Memory）至少保留项目、配置、入口、来源调用和是否仍有效。P-space-01/1/A1/C1指向取得入口的那次读取；成功S来自整项尝试（Attempt），二者不能互相替代。一条真实配置读取，即使后来提交失败，也仍可能支持入口事实；反过来，一个成功标签也不能凭空补出当时未读过的配置。

这解释了为什么消费者（Consumer）需要接收合同（Consumer Contract）：明确它需要哪些信息、哪些情况拒收、接受之后交给谁。存储成功只完成了保存，尚未完成后续行为。

下一次回来验证，旧入口究竟改变哪一步

现在另外定义一个有限的后续任务（Task）P-verify-02：“核对提供的修复是否满足普通路径、空格路径和缺失文件错误传播三项要求，并如实报告。”维护者已经提供待核的项目副本；本段不再修改文件，也不把生成修复的开销藏在下面的程序里。它与前例共享项目来源，用于开发示范，不是独立的跨项目评价样本。

两侧面对完全相同的待核内容，只改变是否允许读取上面的记忆（Memory）。当前项目与配置身份由同一受信环境元数据提供，两侧都可见，但它没有给出测试命令。取不到或不能确认这个身份时，就要先读取当前配置；本例只处理身份可确认的情况。命令一旦需要执行，仍受当前只读验证权限（Permission）限制，旧条目不创造新许可。

为把行为变化逐项看清，下面以固定参考规则代替模型（Model）决策：有符合条件的入口，就提出运行测试；没有入口，就先读配置。最多两次模拟工具请求，读配置后至多再请求一次测试。环境夹具（Environment Fixture）是一份预先给定的配置和检查结果，用来验证程序流向；没有启动命令或测试框架。这样可以完整核对“什么输入导致什么动作（Action）”，但不能把固定规则的结果宣称为真实模型（Model）收益。

先把允许的条目放进实际输入（Actual Input）

第一段接收当前项目、配置、读取开关与可选的本次配置读取结果，输出一份实际交给后续参考规则的JavaScript对象表示法（JavaScript Object Notation，JSON）文本，用命名字段组织数据。当前读取优先于旧条目；没有符合条件的入口时保留空值，让后续规则知道还缺什么。

import json

memory = [{
    "project": "P", "config": "cfg-v1", "active": True,
    "command": "python -m pytest", "source": "P-space-01/1/A1/C1",
}]
config_fixture = {
    "cfg-v1": "python -m pytest",
    "cfg-v2": "python -m unittest",
}

def compose(project, config, enabled, current_entry=None):
    selected = [m for m in memory if enabled and m["active"]
                and m["project"] == project and m["config"] == config]
    entry = current_entry
    if entry is None and selected:
        m = selected[0]
        entry = {"command": m["command"], "source": m["source"]}
    return json.dumps({"project": project, "config": config,
                       "test_entry": entry}, ensure_ascii=False)

selected只是符合本例筛选规则的材料；entry才决定实际输入（Actual Input）包含什么。来源字段能让后续追查，但字典中的字符串本身不提供真实性保障。本程序假设记忆（Memory）来自已确认的C1读取；真实系统仍须维护能够回查原记录的关系。

接收者必须真的从这份输入决定下一步

第二段的唯一参数就是上一段返回的文本。它不会绕过文本偷偷读取memory；因此关闭注入后，参考决策确实失去这条入口信息。

def reference_next_action(actual_input):
    state = json.loads(actual_input)
    entry = state["test_entry"]
    if entry is None:
        return {"kind": "READ_CONFIG"}
    return {"kind": "RUN_TESTS", "command": entry["command"],
            "source": entry["source"]}

READ_CONFIG表示请求取得当前入口，RUN_TESTS表示使用该入口提出验证请求。真实模型（Model）可能忽略输入、错误理解来源或提出别的动作（Action）；本函数只把所选参考行为完全展开，给接入真实消费者（Consumer）时提供可检查的边界。

动作（Action）之后还要取得观察（Observation）和判定

第三段把两种请求接到公开夹具（Fixture）。读配置时，返回当前配置对应的命令；请求测试时，先核对命令确实对应当前配置，再接收给定的三项检查结果。这里的检查结果不是执行者自填的通过凭据，而是本例评分方提供的固定输入。

def continue_fixture(config, enabled, checks):
    if len(checks) != 3 or any(x is not None and type(x) is not bool for x in checks):
        raise ValueError("three boolean-or-unknown checks required")
    current_entry = None
    actions, inputs = [], []
    for _ in range(2):
        actual_input = compose("P", config, enabled, current_entry)
        inputs.append(actual_input)
        action = reference_next_action(actual_input)
        actions.append(action["kind"])
        if action["kind"] == "READ_CONFIG":
            current_entry = {"command": config_fixture[config],
                             "source": "current-config-read"}
        else:
            assert action["command"] == config_fixture[config]
            if any(x is False for x in checks):
                verdict = "F"
            elif any(x is None for x in checks):
                verdict = "U"
            else:
                verdict = "S"
            return {"actions": actions, "inputs": inputs,
                    "source": action["source"], "checks": checks,
                    "verdict": verdict, "tool_requests": len(actions)}
    raise RuntimeError("no test request within the fixture budget")

先判F再判U，沿用04的合取合同：三项都必须成立，已有反例就足以失败；没有反例但有缺项时才保留未知评分（Unknown Score）。inputs记录每次参考决策真正收到的文本，actions保存随后请求，checks保留观察（Observation），最后才有verdict。没有在入口被注入时提前给S。

对照正常路径、配置变化和两种不成功结果

第四段给出五个公开输入。前三行使用相同的三项通过结果；第三行明确把当前配置改为cfg-v2，旧条目不匹配。后两行回到cfg-v1并开启记忆（Memory），分别给出一个已确认反例和一个缺失检查。

for config, enabled, checks in [
    ("cfg-v1", False, [True, True, True]),
    ("cfg-v1", True,  [True, True, True]),
    ("cfg-v2", True,  [True, True, True]),
    ("cfg-v1", True,  [True, True, False]),
    ("cfg-v1", True,  [True, None, True]),
]:
    result = continue_fixture(config, enabled, checks)
    print(config, enabled, result["actions"], result["source"],
          result["verdict"], result["tool_requests"])

这四段顺序组成可执行参考程序，实际输出为：

cfg-v1 False ['READ_CONFIG', 'RUN_TESTS'] current-config-read S 2
cfg-v1 True ['RUN_TESTS'] P-space-01/1/A1/C1 S 1
cfg-v2 True ['READ_CONFIG', 'RUN_TESTS'] current-config-read S 2
cfg-v1 True ['RUN_TESTS'] P-space-01/1/A1/C1 F 1
cfg-v1 True ['RUN_TESTS'] P-space-01/1/A1/C1 U 1

第一行没有旧入口，先取得当前配置再验证；第二行使用匹配条目直接进入验证；第三行拒绝旧配置的入口，重新读取当前材料。后两行即使已经消费旧入口，也仍分别得到F与U。因此“已消费”与“完成任务（Task）”不是同一个标签。

最终报告也按结果闭合：前两行可以报告“给定的三项检查均已确认通过”；第四行须报告“缺失文件错误传播已被证伪，不能交付为完成”；第五行须报告“空格路径检查未取得有效结果，目前未确认全部通过”。在真实系统中，这些话必须有真实检查支持；本例只是将预设观察（Observation）送入汇总逻辑，没有把预设通过写成pytest实跑。

这个对照支持的有限结论是：在所给参考规则与匹配配置下，旧入口替代了一次配置读取请求。 两侧的成功条件没有变化，也没有增加已通过的检查数。保存条目、检索（Retrieval）、核对配置和更长输入仍有成本；这里没有测延迟、模型（Model）输入长度或完整费用，不能据请求少一次就宣布整体更便宜，更不能宣称跨任务记忆（Memory）已经有效。后续持续经验（Experience）路线还要比较多次回访、配置变化与任务（Task）顺序下的净收益。

把这条闭环放回消费者（Consumer）关系

图中每个箭头都传递具体材料。拒收旧条目后仍有当前取证路径；末端的新评价用于判断后续效果，不能从“已存储”直接跳到“能力提高”。

图中S为成功（Success），F为有效失败（Valid Failure），U为未知评分（Unknown Score）。本例展示的是明文规则消费者（Consumer）。原方法中也能找到具体消费路径，例如Reflexion让反思文字（Reflection）进入行动者（Actor）后续上下文（Context），再参与下一次尝试（Attempt）。其重复尝试（Attempt）的实验条件与本例不同，不能借它的成绩证明此处的配置记忆（Memory）有跨项目收益。

撤回条目，改变的是哪次输入

现在只改变条目有效性：用户撤回这条经验（Experience），内存中的active设为False。下面同时保留一份撤回前已经组装的输入，观察两者区别。

captured_input = compose("P", "cfg-v1", True)
memory[0]["active"] = False
fresh_input = compose("P", "cfg-v1", True)
print(reference_next_action(fresh_input)["kind"])
print(reference_next_action(captured_input)["kind"])

实际输出为READ_CONFIG、RUN_TESTS：后续新组装不再注入旧入口；之前捕获的文本仍包含它。修改存储对象不会追溯改写已经发出的请求。真实系统若要阻止旧请求产生后续效果，还须按当前权限（Permission）和撤回范围控制动作（Action）；这个Python内存变化没有实现持久化提交、请求取消或远端回收。基础62-B区分的“当前响应服从撤回”与“长期撤回已提交”在这里仍然成立。

另外两个用途，为什么需要不同投影（Projection）

程序优化（Program Optimization）关心“怎样生成、选择并安装更好的流程”。A2可为完成门候选提供诊断材料：报告前检查是否有本次所需验证依据，遇到尚未确认的验证结果时如实报告。优化者还需要允许修改的程序位置、已有流程、同类成功与失败以及搜索成本；只有一个总分，无法区分入口错误、工具（Tool）失败和评分服务不可用。

这里被修改的是智能代理（Agent）流程，不能继承A1对用户项目文件的编辑许可。候选程序（Candidate Program）生成后，要在另行明确的范围内被选择、安装，再由后续启动器（Launcher）实际装载，才发生程序消费。归档里有候选文件只说明产生过；本章没有实现这个候选优化循环，后续程序演化路线会完整展开。

训练（Training）则先取决于目标需要什么监督。由有权策展者整理的新输入—参考输出对，可以成为监督微调（Supervised Fine-Tuning，SFT）的示范来源。它按输入—目标示范调整模型参数（Model Parameters）；它不能因此恢复原执行的采样概率（Sampling Probability）。若原记录只有摘要，就保留“新材料由谁依据什么构造”，不能把重建文本改称当时真实输入。

这里先给两项最短背景：真实前缀（Actual Prefix）是生成某个输出时实际可见的前文；损失掩码（Loss Mask）标记哪些位置直接计入当前损失（Loss），即衡量预测与指定目标差异的数。基础46对此有选读解释，本章的增量是接收合同（Consumer Contract）：诊断可接受哪些缺失，记忆（Memory）怎样核对适用条件，训练（Training）的具体目标还缺哪些字段。数学路线读完07–08后，训练（Training）深化会用两个不同消费者（Consumer）明确演示接收和拒绝，不能把一种消费者（Consumer）的通过泛化成所有用途都足够。

切成四段，为什么仍只有同一条来源

现在回看A1：C1–C4是四次模型调用（Model Query），仍归同一个尝试（Attempt）与计划试次（Trial）。若把它们分别写进四个文件，没有凭空获得四个独立任务（Task）。将C1/C2用于开发，C3用于选择，C4留作最终评价，会让同一执行的解题材料跨越原定边界。

再改变生成方式：从这次修复派生三个改写题，即使各有新任务（Task）ID，它们仍可能共享模板和答案结构。来源组（Source Group）把这种共同来历保留下来；本例称它为P-space-template。若研究的是跨项目迁移（Cross-project Transfer），还需要在项目层次划分，不能只改问题名称。

下面只检查已提供的来源关系，不自动识别真实同源。development表示开发用途，selection表示选择用途；本例采取同来源组（Source Group）不能跨用途的保守合同。

def check_group_split(rows):
    groups = {}
    for row in rows:
        groups.setdefault(row["source_group"], set()).add(row["split"])
    conflicts = {g: sorted(s) for g, s in groups.items() if len(s) > 1}
    if conflicts:
        raise ValueError(f"same source across purposes: {conflicts}")
    return groups

rows = [
    {"task": "P-space-01", "call": "C1",
     "source_group": "P-space-template", "split": "development"},
    {"task": "P-space-02", "call": "C2",
     "source_group": "P-space-template", "split": "selection"},
]
try:
    check_group_split(rows)
except ValueError:
    print("rejected: same source across purposes")

实际输出为rejected: same source across purposes，说明给定两行被拒绝。正确修订是依据真实来源与预定用途，将关联变体共同用于开发，另取没有参与开发的来源用于选择；不能仅改组名让代码通过。按组不交叉也不自动证明组间统计独立，公共依赖、时间事故和传播关系仍要根据研究对象判断。

总判定为未知评分（Unknown Score），不等于全部信息都消失

设一条记录保留verdict=U、reason=grader_unavailable和score=None。如果加工时只写“成功存1，其余存0”，评分服务故障就会被变成模型（Model）能力失败；直接删除所有U，又可能只保留下易于取得反馈的任务（Task）。两种处理都改变了原始信息。

不同消费者（Consumer）可以作出不同决定：诊断者使用故障记录定位评分设施问题；记忆（Memory）可以保留其中已经确认的配置事实；成功率研究保留未知评分（Unknown Score）及计划分母；某个明确要求有效终局评分（Terminal Score）的训练（Training）目标，则拒收该条并报告排除范围。截止前确认交付也可另给0/1，但它描述另一个事件，不覆盖原始未知真值。

因此每份投影（Projection）要保留源记录、所做变换、仍缺哪些字段及用途。归档能保存的信息，并不都应该交给解题模型（Model）：开发者可以读取获准的开发反馈，最终评价材料和事后答案仍按原定边界隔离。记录更完整，不意味着输入可见范围可以扩大。

沿同一记录作出参考判断

问题。 A2得到F，能把它所有动作（Action）都标成错误示范吗？

参考答案。 不能。这里的有效失败（Valid Failure）来自缺少规定验证依据；修改可能正确，配置读取也可能真实。总判定不自动完成每一步的归因（Attribution）。把后来的检查结果回填到当时输入，还会改变原始执行条件。

问题。 新输入确实含旧入口，能宣布记忆（Memory）改善了任务（Task）吗？

参考答案。 还不够。本例继续检查到参考动作（Action）、三项观察（Observation）、S/F/U与模拟请求数，才确认具体消费发生。固定规则下少一次读取仍不是模型（Model）实验；总体收益还要计检索（Retrieval）与维护等开销，并在有代表性的多次回访中比较。

问题。 同一执行轨迹（Trajectory）导出四个文件，能一部分开发、一部分当独立最终检验吗？

参考答案。 本例不能。四份投影（Projection）仍共享任务（Task）、尝试（Attempt）和来源组（Source Group），切片不会阻断信息关系。新文件名与新ID都不能替代真实用途划分。

问题。 撤回后新输入不再带旧入口，长期撤回就一定完成了吗？

参考答案。 这里仅核对了内存筛选与两份已捕获文本。持久化是否提交、在途请求怎样处理、后续动作（Action）是否仍获准，需要真实系统另行确认。参考程序没有把这些效果实现出来。
