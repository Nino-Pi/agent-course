Agent 前沿进阶能力增长、自主研究与自我改进

第 04 章｜工具返回成功，为什么任务仍可能失败

本章概览

核心问题：执行状态、评分与现实结果不一致时，怎样判断任务完成了什么，并阻止错误反馈推动下一轮改进？

关键概念：环境状态是任务现场的实际情况；观察是执行者取得的部分信息；评分器按合同检查结果；有效失败有不满足要求的证据，未知则缺少足够判定依据；监督合同规定谁能评分、修改与放行。

关系主线：沿代码修复辨认业务错误、缺失评分和评分漏洞，再用三份资料区分规则、模型与人工反馈；最后将结果接到有限的改进与交付权限。

先分开现场、观察和判断

第01章已经指出：用户项目中的 runner.py 补丁是任务产物，不能自动当作 Agent Harness 的升级。本章继续这个 Python 文档检查器案例，增加的问题是：谁来确认修复成立，确认不了时留下什么状态，评分器自己判断错了又怎么办？ 本章只需第01章；配对统计与重复选优可以按需另读。

先恢复案例的共同条件：项目配置使用 pytest；普通路径是 docs/guide.md，空格路径是 docs/guide draft.md；runner.py 调用只接收一个文件参数的 checker.py。原包装函数错误地拼接 shell 字符串。Agent 允许修改包装函数与 README，须保留 README 顶部用户笔记；测试与其他文件只读。

本章新增以下教学评价条件。每个计划试次从尚未修好的独立项目副本开始，固定模型 M0、Harness H0，最多6次模型调用、8次工具调用和120秒。运行方在截止时停止接纳新动作、收束已有写入，再冻结该试次产物；评分最多用30秒，且本次确认截止不得晚于试次开始后150秒。若写入尚未收束，不能假装已得到稳定快照，剩余确认时间也不会因此延长。评分服务故障最多重试一次，仍在评分预算与总截止内，使用同一份可确认的产物；不重新让 Agent 改到满意为止。

执行方不能改评分器、参考答案、预算或判定记录。两边没有外部发布工具。这里的所有项目修复过程与评分观察都是教学构造；后文只有一个接收检查结果的小程序实际运行，不运行 Agent、真实项目或 pytest。

现在把容易挤进一个“状态”字段的对象拆开：

对象 本例具体是什么 哪个使用者需要它
环境状态 当前文件内容、进程是否仍在写入、已产生的测试产物 执行层据此落实动作；评分方取得稳定产物后检查
观察 模型收到的文件片段、命令退出码、标准输出与错误输出 模型据此决定下一步；它可能只看到部分状态
动作 读文件、提出补丁、调用检查器等具体请求 工具和资源执行层根据当前权限执行
重置 为另一个试次恢复原始项目、清除前次残留进程与可复用状态 评价运行器保证两次面对约定初态
评分 独立检查后产生的成功、失败或未知判断及依据 比较程序、维护者和后续经验处理程序

执行动作会改变环境，观察只是把其中一些变化告诉模型。一个工具返回“补丁已写入”说明写入完成；它没有同时证明补丁保留错误状态、README 正确或用户笔记仍在。反过来，工具连接断开后，文件可能已经改变；只凭没有回执也不能断言没有写入。

重置同样不是清空一条聊天记录。前次输出文件留在共享目录、评分器读取了旧报告，或者后台进程仍继续写，都可能让下一试次面对不同的现场。本章假设项目副本与评分产物具有明确身份；拿不到这个条件时，记录环境问题，而不是给结果补上“独立”的名称。

三条相似的日志，导向不同处理

以下三条都是从相同缺陷初态出发的独立教学试次，不是一个试次中先后发生的三次尝试。每条记录都保留执行状态与任务判断，不能用某一个布尔值覆盖另一项。

第一条：编辑成功，业务要求却被破坏

Agent 把包装函数改成“调用失败时也返回成功”，工具确认 runner.py 的补丁已写入。它随后检查空格路径，界面不再显示错误，便报告完成。真实验收合同没有变化：文档不存在时必须返回非零状态与缺失诊断。

独立评分方对冻结产物检查三个输入。普通路径通过；空格路径的调用不再显示失败；缺失路径 docs/absent.md 却也返回成功。最后一项已经构成业务反例，即使补丁没有越出允许文件，也不能算完成。

正确记录是“编辑工具成功；任务有效失败；原因是缺失文件错误被吞掉”。有效失败指评分方有足够证据确认至少一项必需条件不成立。它不要求 Agent 本身非零退出，也不意味着所有检查都失败。后续可以据这条证据生成新补丁，但那是新的开发动作，不擦除本次失败。

反过来看：若 Agent 的最后一条说明生成失败，已冻结的补丁仍可能通过全部合同检查。这时“最后调用失败”和“项目修复成功”可以同时成立；是否还要求完整交付说明，必须由事先声明的任务合同决定。本例要求如实报告与 README 说明，评分方仍要检查这部分，不能只看代码。

第二条：补丁看似正确，评分服务没有给出结果

这次 Agent 提交了参数数组补丁，普通文件写入已确认，产物也已冻结。但评分服务启动失败；一次获准重试仍失败，30秒评分期限结束。执行方日志中的“我已修好”不是独立检查结果，因而任务评分保持未知。

若评分方已确认“README 用户笔记被删掉”，则即使其余检查服务后来失败，也有明确的不满足项，可以记录有效失败，并另外保留检查缺失。这里假设没有任何已确认反例，也没有取得全部必需检查，所以记 U：未知，分数为空，而不是成功的1或失败的0。

本章同时定义一个更窄的事件：从试次开始起150秒内，是否已经确认全部合同通过。这个“截止确认交付”事件在本例为0，只说明没有及时确认；它不把项目的未知真值改成失败。若截止后补查同一产物，后来确认成功，可以追加“后续核实成功”，不能回填成150秒内就已确认。

评分器故障重试只重跑评分步骤，不能偷偷让 Agent 再修一次项目。否则后来检查的已是另一份产物，原始失败/未知与新方案结果混在一起。已发生的执行、冻结、评分失败及重试开销都要保留。

第三条：评分器读到了它想看的字样

现在明确改变一个条件：开发人员错误地采用弱评分器，它只检查候选程序的标准输出是否含 ALL_PASS。Agent 提交的项目包装函数打印这个字样，却仍未修复参数传递或错误传播。弱评分器给出成功，用户合同依然没有完成。

这里出现了评分漏洞：优化对象能制造评分器采用的信号，却不必完成信号本来代表的事情。这不要求修改评分器源码；控制它读取的内容就可能足够。输出文本来自待检程序，不能因为像测试报告就自动获得评分权。

本例的修订方式是让独立评分方运行自己的必需检查，确认检查确实执行、当前产物身份一致，再据结果判断。候选 stdout 可以帮助诊断，但不再作为通过凭据。若候选进程能写评分文件、替换测试，或接触评分服务的身份凭据，仅换一个更聪明的判分模型也没有闭合这个边界。

修好评分器后，要用同一规则重新检查需要比较的产物，并说明旧记录来自有缺陷的规则。不能只重评原来的赢家，或悄悄抹掉弱评分器版本下发生过的假成功。评价规则改变了，应保留改变前后的含义。

把判定规则写成能检查的小程序

下面先给评分方拥有的检查含义，再写汇总逻辑。它们不是 Agent 自填字段；本例假设独立检查进程只读冻结产物，并用自己的结果通道提供这些值。这个假设需要执行隔离落实，Python 字典本身不提供可信来源保证。

检查名 为真时必须已经确认的内容
normal_path 普通路径的文档检查按合同完成
space_path 空格路径完整传递且文档检查按合同完成
missing_error 缺失文件仍有非零状态和诊断
notes_preserved 用户原有笔记保留
scope_ok 只有获准的包装函数与 README 被修改
tests_and_report 相关测试实际执行，README 与交付说明符合任务要求

每项值仅有三种：True 是已核实成立，False 是已核实不成立，None 是未取得有效结果。未知没有变成真假之一。因为本例规定所有条件必须成立，任一已确认反例就足以判 F；只有没有反例而仍缺检查时才判 U。

以下是可执行参考代码，只实现这个结果汇总规则，没有把检查本身藏成已实现的功能。字典中的输入是手工构造的教学检查结果；实际项目探测、进程隔离、超时与报告核实都不由这段代码完成。

REQUIRED = (
    "normal_path", "space_path", "missing_error",
    "notes_preserved", "scope_ok", "tests_and_report",
)

def decide(checks):
    values = {name: checks.get(name) for name in REQUIRED}
    for name, value in values.items():
        if value is not None and type(value) is not bool:
            raise ValueError(f"invalid check value: {name}")
    failed = [name for name, value in values.items() if value is False]
    unknown = [name for name, value in values.items() if value is None]
    if failed:
        return "F", 0, failed, unknown
    if unknown:
        return "U", None, failed, unknown
    return "S", 1, failed, unknown

good = dict.fromkeys(REQUIRED, True)
business_wrong = {**good, "missing_error": False}
scorer_down = dict.fromkeys(REQUIRED, None)
fake_report = {
    **good, "space_path": False, "tests_and_report": None,
}
for name, checks in (
    ("correct", good),
    ("business_wrong", business_wrong),
    ("scorer_down", scorer_down),
    ("fake_report", fake_report),
):
    verdict, score, failed, unknown = decide(checks)
    print(name, verdict, score, failed, unknown)

本地运行该汇总程序得到以下结果。它验证构造输入如何被分类，不证明真实 Agent 产生过这些结果：

correct S 1 [] []
business_wrong F 0 ['missing_error'] []
scorer_down U None [] ['normal_path', 'space_path', 'missing_error', 'notes_preserved', 'scope_ok', 'tests_and_report']
fake_report F 0 ['space_path'] ['tests_and_report']

最后一行同时保留了已知失败与未知检查：空格行为已经被独立检查证伪，伪造的输出文字又不能证明测试与报告成立。F 没有把未知字段偷偷填成 False。若缺少某个必需字段，checks.get 会得到 None，也不会由于漏项而默认通过。

同理，Agent 因时间耗尽而停止，只是执行状态。评分方若检查冻结产物，确认缺陷仍在，可给 F；若始终无法取得稳定产物和必要证据，就保留 U。环境接口中的终止、外部截断与任务成功不是同一个概念。另一个研究可以把按时交付本身作为目标，但必须公开该目标，不能在看见结果后偷偷更换。

代码之外，先定义资料研究的真值在哪里

代码检查能写确定条件，资料研究往往还涉及时间、解释与引用。为避免把公开网页的复杂真值假装成单元测试，这里另设 K-C：有限资料研究任务。它属于课程构造，资料库“青岚”与以下文档均为虚构；它们不代表现实产品政策。

用户要求：“以2026年6月15日中午为准，说明青岚新建工作区现在默认保留多少天、7月1日后新建工作区怎样变化、已有工作区是否自动改变，并给出依据。只写结论草稿，不执行配置修改，也不对外发送。”

环境只提供下列三份不可变资料的全文。当前时间固定为6月15日12:00，文件只读，初态没有旧报告、跨题记忆或隐藏网页。Agent 最多4次模型调用、4次资料读取、60秒；评分另有20秒。评分方使用同一资料包判断事实，不掌握一份与题目相冲突的秘密政策。

[D1] 青岚服务公告，2026-06-01发布
自2026年7月1日起，新建工作区的默认保留期由90天改为30天。
此前已存在的工作区不自动改变；管理员可另行修改其设置。

[D2] 当前规则，版本2026-05-01
新建工作区默认保留90天。已有工作区按各自当前设置执行。
管理员可以修改保留期。本文规则持续有效，直至相关新规则生效。

[D3] 公告问答，2026-06-10更新
6月1日公告是未来变更通知，30天默认值在7月1日才生效。
7月1日之前新建的工作区仍使用90天默认值。
已有工作区不会因新公告自动改为30天；是否被管理员改动须查该工作区设置。

这里能作出的完整参考回答是：“截至6月15日，新建工作区默认90天；7月1日起新建工作区默认30天。已有工作区不会自动改变，其实际保留期取决于当前设置。D1给出变更及生效日，D2给出现行规则，D3消除了公告已发布与规则已生效的混淆。”

这个回答不能再延伸为“所有已有工作区都是90天”，因为管理员可能改过；也不能写“已有数据已被删除”，资料没有任何具体删除记录。真值范围是三份资料及固定时间所能支持的政策解释，不是任意真实工作区的状态。这就是为什么引用了真实文字仍可能得出错误结论。

一条具体失败轨迹是：读取D1后只摘出“改为30天”，在草稿中写“目前默认30天”；写草稿工具成功，甚至有D1引用，但现行时间判断错误。正确后续是回查生效条件，用D2/D3区分当前与未来，而不是多找几个都转述D1标题的页面充作独立支持。

规则、模型和人工各自能纠正什么

在K-A，独立运行必需行为检查比匹配 stdout 字样更直接。在K-C，只搜索回答是否出现“90天”“30天”“D1”，会同时接受“现在30天、过去90天”和正确回答。规则适合检验字段、引用是否存在、数字计算与明确状态；它是否检验了用户真正的要求，需要另看。

模型评分器可以接收用户问题、固定日期、资料原文与待评回答，判断“当前/未来是否混淆”“已有工作区是否被过度概括”“引用是否支持结论”。这些是评分维度，不能把“回答流畅”偷偷当成事实正确。评分模型应允许回答“不足以判断”，并给出所缺证据；强迫每次输出成功或失败，会把自身缺信息伪装成确定判断。

人工复核在这里负责根据同一合同裁定具体分歧。为了讲清校准，设维护者预先制作四份回答，参考标签先按上述全文核对；再让一个假设评分器G0判分。四份完整稿都列出对应资料引用，表中只摘判断所需的关键句；除列明问题外，其余格式满足要求。下面结果也是教学设定，没有运行评审模型：

回答中的关键句 按本题合同的参考标签 G0判断 应检查的误差
现在90天，7月1日起新建30天；已有按各自设置 S S 这例判断一致
公告已发布，所以现在新建30天 F S 错放：把发布日期当生效日期
已有工作区的数据现在都被删除了 F F 这例识别了无依据主张
截至六月十五日，新建保留九十日；七月一日起新建三十日；原有不自动变 S F 误拒：拘泥于数字与日期的表达方式

四例中错放一次、误拒一次，不能只说“评分器总体还行”。这里特意选了反例，2/4只是这四份回答的判断一致率，不是未来准确率估计。将生效日期与可接受等价表达写清后，即使G1在四例全对，也只是修复了已知例；还需要另一组未用来调整规则的回答检查共同盲点。

人工也可能漏看D3或偏好自己的措辞。两位复核者分歧时，先指出争议句、引用与合同条件，再由负责该任务定义的人裁决或保留待查。多数票不自动生成真值，多位模型也可能沿用同一个错误解释。更难监督的研究会继续分析这些相关错误；本章最低要求是保留可核对的依据与拒绝确定判断的出口。

反馈进入训练之前，先问谁在什么时候可见

本章不执行训练，但这些评分以后可能成为训练信号，所以现在就要保留信息边界。以K-C为例，解题模型在作答时可以看到问题、固定日期及实际读到的D1–D3；它看不到本次提交尚未产生的评分意见。评分方可以看提交物、全部资料及评分细则，用来给出事后反馈。

任务要求本身应对解题者说清楚；独立评分不意味着用秘密条件为难它。需要隔离的是参考答案、最终评价实例与评分实现的修改权，以及尚未到达的反馈。将完整参考答案藏进工具返回，再用这次成功宣称模型已能独立研究，是改变了它获得的信息。

如果开发过程允许“先交一稿，再看评价意见修订”，那就明确这是一项有反馈的任务，修订和再评分都占预算。若以后训练使用事后反馈来生成目标答案，也应记录反馈在原作答时不可见；部署时没有同类反馈，不能把有反馈下的表现直接搬过去。具体参数怎样更新，后面的训练章节再展开。

U也不能自动变成训练的0分。K-A评分服务故障可能与补丁质量无关；将其当失败奖励，会把服务可用性混入学习目标。若目标明确定义为150秒内确认交付，可以使用那个事件的0/1信号，但仍保留原U状态，说明算法正在优化什么。

评分通过以后，还有一道行动边界

这里的最低监督不是再添加一句“请谨慎”。在两个案例中，候选生成者、独立评分者和最终效果执行者有不同职责。K-A的Agent可以修改获准副本内的包装函数与README，评分方读取稳定产物；K-C的Agent只能交付结论草稿。评分通过不能把这些范围扩大成修改评分器、安装全局工具或对外发送报告。

一条完整的通过路径是：生成候选产物→冻结并关联其身份→独立检查当前产物→记录判断与证据→检查当前任务是否已授权所需交付→执行该交付并确认结果。本章的获准交付仅为本地补丁/草稿及如实说明，没有外部发布步骤，也没有“拿到S就自动发布”的规则。

一条拒绝路径同样要闭合：候选请求写测试或评分文件时，执行边界在效果发生前拒绝并记录实际目标；正常任务产物得到F时，保留反例供后续开发；得到U时，在获准重试与期限内查询同一产物，超限后交付未确认状态。它们不是同一种失败，不能一律不断重试。

如果以后另开实验允许外部发布，应由持有对应权限的执行者核对具体产物、范围与当前许可后执行；模型评分只是其中一项输入。评分器发现“值得发布”不创造新授权，来自D1–D3的文字也不能授权更改真实账户。旧课的工具合同已说明，合法工具名与合法JSON都不足以证明具体效果获准；这里将同一原则用到改进系统。

根据这三种结果作出参考判断

问题。 评分进程超时，所以本次一定是任务失败吗？

答案。 不一定。若已有独立反例，例如用户笔记被删除，可以记录F并保留其他缺失；若没有反例也没收齐必需检查，记录U。截止确认交付可以为0，但这是另一项预先定义的事件。

问题。 换成强模型评分器，能否解决候选打印 ALL_PASS 的问题？

答案。 若仍只把候选控制的输出交给它，缺少独立产物检查，核心漏洞没有关闭。先确定哪些证据由评分方自己取得、候选能否修改评分文件，再校准模型对这些证据的解释。

问题。 K-C的回答引用D1并写“30天”，为什么仍可能失败？

答案。 D1讨论7月1日后的新建工作区；当前时间是6月15日。引用存在不等于支持“目前30天”，也不能说明已有工作区的实际设置。应把结论的时间、对象和适用条件逐项对应原文。

问题。 评分通过的补丁可以直接安装为Agent共享工具吗？

答案。 不能从本例推出。通过的是用户项目修复合同，修改和安装共享工具属于另一个对象、另一份许可与另一组评价条件；下一次执行是否实际消费该工具也要核对。
